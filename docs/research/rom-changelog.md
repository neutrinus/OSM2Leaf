# ROM changelog between builds (M1.37)

Per-module static diff of the modules the project cares about, across two year
pairs of EU cards. Generated by `tools/rom_changelog.py`; regenerate with the
commands in [Reproduce](#reproduce). Vendor bytes stay on disk — this page holds
only module names, VAs, counts, hashes and short firmware strings.

Modules: `Navi.exe`, `Audio.exe`, `BT_MGR.dll`, `BT_ENG.dll`, `BT_FW.dll`,
`Speech.exe`, `DriveComputerCC.dll`.

## What is compared

- **Functions.** The `tools/pdata.py` exception table of each build. A module
  whose `.pdata` section is compressed is decoded with **that build's own**
  `DECOMP_SECT`; the routine moved (EU2011 `0x88037464`, EU2014/EU2016
  `0x88037994`) and is located by matching the EU2011 function's reloc-masked
  digest in the build's `nk.exe` — no fitted address.
- **Function identity** through `tools/fn_match.py`'s reloc-masked fingerprint,
  compared as **digest sets** (not one-to-one). A module full of duplicated leaf
  bodies (`BT_ENG.dll`) otherwise loses rows to `AMBIGUOUS` and a code-identical
  module reads "changed".
- **match** = `shared / max(digests A, digests B)`: the fraction of the larger
  build found in the other. A module below **50 %** is `rewritten` and its
  changed functions are not named (Stop rule).
- **gap** = differing halfwords at equal section offsets that **no `.pdata`
  record of either build covers** (leaf code with no record, literal pools). It
  is a lower bound of what the recorded-function diff did not look at and
  includes relocated pool words. This is why a 100 % recorded match can still be
  a different module (`BT_MGR.dll` 2014→2016: 0 functions change, 12 gap
  halfwords differ).
- **sec** = raw executable-section bytes equal (unmasked, what `rom_atlas`
  calls "different"); it is `no` for every differing module here, so the code
  did move, not only its address.
- **csec** = compressed sections of the module. Their decoders return only the
  stored prefix (`r0`), not VSIZE, so strings are taken from **plain** sections
  only and this count says how much is out of the string corpus.
- **strings** = printable ASCII runs (>= 8 bytes) of the plain sections;
  **+str/-str** is the set difference. The samples keep message-like runs only.
- **exports** = `cerom` export-table name set; **COM** = the plain-`.rgs`
  co-class text. No module here gains an export or a COM class in either pair.

## Control — EU2011 vs US2011 build B

Build B is byte-identical between the two 2011 cards (C-6281), so every module
there must diff to 0 added / 0 removed functions. `rom_changelog.py control`
checks this; `BT_FW.dll` (build B) is also a row of the pair tables below.

```
$ python3 tools/rom_changelog.py control --left EU2011=archive/head256.img \
    --right US2011=archive/us256.img --build B --modules BT_FW.dll nk.exe coredll.dll
```

## Reading the two pairs

**EU2011 -> EU2014 is a real feature step, not a rebuild.** Every code module
changed but most of each one is kept: `Navi.exe` 81 % match (1,392 functions
added, 1,278 removed, including a `meshID(%x) x,y(%d,%d)` cluster and new
`GID_COM_GetRouteGuide` / `DOR:OBJ EVENT` / `SVR_chgLogMode` messages),
`BT_MGR.dll` 91 % (`OppLock` / `OppAccess` messages), `BT_ENG.dll` 68 % (the
`Func[%s] FILE=[%s], LINE=[%d]` trace family is replaced), `Speech.exe` 60 %
(new `PHONEME`/`TEXT` log and speech-guide messages), `DriveComputerCC.dll`
89 %. `Audio.exe` is the one **rewritten** module (47 %): it gained
`CSpeechGuideAccHeapMemory` classes — a whole speech-guide audio path — so it is
not diffed by hand. `BT_FW.dll` (build B) is 100 % function-identical yet not
byte-identical (92 gap halfwords, no string change): the firmware's own code is
the same, which is what the M1.36b atlas predicted for a same-size kernel
module.

**EU2014 -> EU2016 is a small fix release.** `Navi.exe` is 99 % match with only
67/66 functions changed — mostly the version string (`Jun 26 2014` ->
`Nov  1 2016`) and a `RGD_VceCtl` send/timing tweak; `Audio.exe` 95 %
(76/75); `DriveComputerCC.dll` 92 % (a `ScreenStateWindowHandleManager` window
handle rework). **`BT_MGR.dll`, `BT_ENG.dll`, `Speech.exe` and `BT_FW.dll` are
100 % recorded-function identical**: their only 2014→2016 difference is 10–133
gap halfwords (leaf code / a literal pool, no string and no recorded function
change), so there is **nothing new to take from the newer Bluetooth, speech or
firmware build** on this pair. That is the answer the task asked for: the newer
Bluetooth stack has nothing we want.

## Limits

- Strings cover plain sections only; the compressed sections' full contents
  (BSS and stored bodies) are outside the corpus (`csec` column).
- A `changed` function is named by the strings its literal pool points at; a
  function whose pool holds no string is listed with its VA and no name.
- `gap` counts differing halfwords, including relocated literal-pool words, so
  it overstates semantic change; it only says "the recorded functions are not
  the whole story".
- No behaviour is claimed here. Every statement is a count or a string; proving
  a change matters needs an L3 run.
