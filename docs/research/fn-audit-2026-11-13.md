## What `--scope l3` finds

```
python3 tools/fn_audit.py archive/head256.img --scope l3 --quiet

fn_audit: START 712, INSIDE 81, CORRECTED 11, GAP 75 (leaf 75), AMBIGUOUS 5, UNMAPPED 7
```

The open-block scan uses the **docs discipline**, not "every `0x…` in the
block": a bare data address, path offset, range, string pointer or US-build VA
is not a code citation a task can "fix", so it is skipped. Only three things
are cited — a live `fn`/`sub_` label, a documented correction `ctx` with its
own arrow pair, and a documented `CORRECTION_ONLY` pin — which is why this
corpus has **zero open-block `INSIDE`**: every failing VA below comes from an
append-only EXP or a `firmware.md` line, and every `fn`/`sub_` label in a task
block resolves to a `START`/`CORRECTED`.

The 81 `INSIDE` occurrences reduce to **21 unique VAs, 17 `fn` + 4 `sub_`, all
EXP-only** (they vanish from the gate when the owning task appends a
correction, never by editing an EXP). The docs-scope H52 three are already
resolved here: `0x00542256` is a `CORRECTED` pin in an open block, and
`0x0041c7e8` and `0x00412bee` are the only two live `fn` labels that stay `INSIDE`
because an append-only EXP quotes them mid-function (below).

## Staleness behaviour, per source (H69 applied twice)

`--corpus BASE --overlay L3` runs **two independent live comparisons** (the
docs base against a fresh `--scope docs` scan, the overlay against a fresh
`--scope l3` scan) and prints both totals. On this tree (branch rebased on
`main` at `3b34c37`, the M1.31 merge):

```
CORPUS DRIFT: DOCS BASE: 0 new / 0 gone / 125 moved     # warn, exit 0
CORPUS OK: L3 OVERLAY: 0 new / 0 gone / 0 moved         # clean, exit 0
--corpus → exit 0
```

- `moved`-only in **either** layer warns (`CORPUS DRIFT: <layer>: …`) and
  leaves the exit code at 0; an l3 task-block line move never folds into the
  docs `moved` count, because each layer prints its own numerator.
- `new`/`gone`/a count delta/a verdict change in **either** layer is
  `CORPUS STALE: <layer>: …` and exits 1.
- `--no-live-check` skips both comparisons. There is no `--live-check` flag;
  the check is on by default.
- A frozen `INSIDE` row in the **overlay** does not fail the gate: it is the
  register below (EXPs cannot be corrected). A frozen `INSIDE` in the **docs
  base** still fails, because that base is `INSIDE 0` by construction (M1.29).

## Review fixes (Navigator round 1, 2026-11-16)

The first `--scope l3` run reported 59 unique `INSIDE`/137 occurrences, but a
deterministic sample showed 7 of 10 were classifier false positives. Four
fixes turned that into the 21 genuine EXP-only labels above; each is proved by
`fn_audit --selftest`.

1. **Bare-hex over-trigger.** The open-block scan now cites only a live
   `fn`/`sub_` label, a correction `ctx` with its own arrow pair, or a
   `CORRECTION_ONLY` pin — the same discipline as `citations_markdown`
   (`tools/fn_audit.py`). Proof: appending the documented sec1 DATA address
   `0x00d53500` to an open block leaves the gate green (`L3 OVERLAY: 0 new`,
   exit 0); the same block with a live `fn` label whose VA is `0x0041c7e8` is
   `CORPUS STALE`, exit 1.
2. **US-build VAs.** `US_BUILD_STARTS` (`0x0035d894`, `0x00444540`,
   `0x004446f4`, `0x00443da8`, `0x0041ec8c`, `0x0056454c` at the time of this
   review, six values; the set is now 64, M9.61) are the US-2011
   `Navi.exe` map (M1.22/H51, C-3487, M1.28 fixture: the five `UNIQUE` US
   matches plus the US entry). They are skipped for every kind in both scopes,
   because classifying them against the EU head's `.pdata` labelled a valid US
   address `INSIDE`. Proof: a bare or `fn`-labelled US start in an open block
   stays green; a per-build map is M1.22b's job. The sixth VA in the review
   list, `0x0054bd16`, is not a US start at all — it is `Navi.exe` sec0's
   `vsize` (a **size**, C-2197/C-2511), so it is data and the discipline
   skips it; it is not in either snapshot.
3. **Documented corrections resolve in l3.** A `CORRECTION_ONLY` pin
   (`0x00542256` H63, `0x003f5fc2` H49, `0x00413af4` H69) is now scanned as a
   `ctx` in an open block and resolved by `_resolved` against its pinned start
   even when the line names no start. `0x00542256` and `0x003f5fc2` are
   `CORRECTED`; `0x00413af4` is a `CORRECTION_ONLY` call-site instruction (not
   a start), reported as `correction-only` rather than a failure. The two
   `ctx`-on-a-call-site false positives (`0x003f2d34 …`) needed the strict
   markdown path: a bare VA sharing a line with an arrow is a `ctx` only when
   the **pair** names a start, so `0xMID jsr @r3 -> sub_XXXX` is skipped.
4. **Honest fixing task.** The EXP-only rows below no longer name a `done`
   task (M1.23/M1.27) as their fix; each is `accepted data/append-only` — the
   only edit is a correction note appended to the owning EXP, which the gate
   sees as a class change and requires an intentional re-freeze.

## Remaining `GAP` (22 unique VAs, 75 citations, all direct-caller leaves)

All 75 are `GAP(leaf)`: `pdata.gaps` sets `leaf` only for a direct `bsr`
target or a pool value used by `jsr`/`jmp` (M1.25's rule, not the `sh4xref`
`fn` heuristic). No `GAP(DATA/UNKNOWN)` remains in the l3 corpus. Fixing task
for every one stays **M1.20** (all-module `.pdata` record) or **M1.27** (leaf
path) as the owning doc already says; none is a function-start claim.
