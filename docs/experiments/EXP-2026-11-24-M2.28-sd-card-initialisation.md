# EXP-2026-11-24-M2.28: Settings → Other "Initialise SD card": unlock and clear the sub-slot card with the unit PIN, wipe, repartition, format

- **Status:** done (static; not run in the emulator or on the unit)
- **Date:** 2026-11-24

## Question

What does the "initialise SD card" item in Settings → Other do to a card:
does it set the CMD42 password (the PIN), format the card, or write files?

## Hypothesis

none / exploratory. Falsifier for "it sets the PIN": no SET_PWD
(`0x80032014`) or LOCK (`0x80032018`) IOCTL on the path.

## Method

1. **Sample and hash.** As above; image A of the EU 2011 head (start
   `0x200200`), modules `NaviSetCC.dll` (vbase `0x02e30000`) and `Navi.exe`.

3. **Controls.** Positive: the same xref finds the known `SDC1:` state query

## Observations

O1 — **Menu → Navi.** `NaviSetCC.dll` sec3 holds the COM type library with
`method SDCardInitialization` (next to `SetValidationCode` and the EV
charge-spot properties). The only code in `NaviSetCC.dll` that loads message
id `0x841000f7` is `fn 0x02e3eef8`: `this->vtbl[0x278/4](this, 0x841000f7, 0,
0)`. It has no direct caller; its address sits in two vtable pools
(`0x02e335b4`, `0x02e34494`).

O2 — **Navi dispatch.** `Navi.exe` `fn 0x004bda44` compares the message id:
`0x841000f6` → `fn 0x004c64e4`, `0x841000f7` → `fn 0x004beae0`,
`0x841000f8` → another handler.

O3 — **`fn 0x004beae0`** (the initialisation handler):

1. `fn 0x004dd61c`: one-time setup (critical section, loads `fatutil.dll`
   `FormatVolume` through `fn 0x004dd420` → `fn 0x004dd2ec` → `fn
   0x004e759c` → `fn 0x004e7180`: `LoadLibraryW(L"fatutil.dll")`,
   `GetProcAddressW(L"FormatVolume")`). On failure it notifies `0x12be`.
2. `fn 0x004dd270` → `fn 0x004dd028`: the M2.11 check of the card in the
   sub slot (C-1777, C-1778): wait for `SDC1:` state 4, **UNLOCK**
   (`fn 0x004e7dd8`, IOCTL `0x8003201C` on `DSK8:`), then compare
   `\SystemSD\VER_INFO\HDD_INFO.TXT` with `\UserSD\VER_INFO\HDD_INFO.TXT`.
3. Result ≠ 0: notify `0x12be` or `0x12bf` (result 3) and stop. Result 0:
   notify `0x12c0`, run `fn 0x004dd700`, then notify `0x12c1` or `0x12c2` by
   its result; finally `fn 0x004dd214` (cleanup).

O4 — **`fn 0x004dd700` → `fn 0x004dd68c`**, in this order:

| step | function | what it does |
| --- | --- | --- |
| a | `fn 0x004e7ec8` | `CreateFileW(L"DSK8:")`, password from `fn 0x004e7a44`, **CLR_PWD** IOCTL `0x80032020` (C-1951), 50 ms retries |
| b | `fn 0x004dd458` | on `DSK8:`: `memset(buf, 0, n)`, then per sector `DeviceIoControl(2, …)` and `IOCTL_DISK_WRITE` `0x00079C0C` (CE `CTL_CODE(7, 0x703, BUFFERED, WRITE)`) with the zeroed buffer; literal `0x8000` in the function |
| c | `fn 0x004e75d8` | store helpers on `DSK8:` (`fn 0x004e71f4` opens `L"DSK8:"`; `0x004e724c`, `0x004e72b4`, `0x004e7374`, `0x004e7408`) |
| d | `fn 0x004e768c` | `fn 0x004e7468` with `L"Part00"` |
| e | `fn 0x004e7714` | store helpers then `fn 0x004e74c0` |

`fn 0x004dd458`'s second IOCTL code and the sector loop were read from
`0x004dd51c`–`0x004dd584`; the meaning of code `2` (CE `DISK_IOCTL_*`
old-style) and the loop bound were not decoded.

O5 — **Where the password comes from.** `fn 0x004e7a44(ctx, out, 16)` returns
a cached 16-byte value or builds an object (`fn 0x004ecc08`). `fn
0x004ecc54` opens `L"FMD1:"` (string `0x001d6ef4`). `fn 0x004ecd84` issues
IOCTL `0x80112000` (`IOCTL_FMD_READ`, EXP M8.H18) with input block `5`, size
`0x2000`. `fn 0x004e7a44` then copies 16 bytes from buffer `+0x100`. Block
5 of the unit flash is `0xA000` (PROD), so the copy is PROD `+0x100`
(flash `0xA100`), which is the CMD42 password (C-1945, M2.25).

O6 — **No SET_PWD / LOCK in image A.** LE literals in the 128 MiB head:
`0x80032014` at `0x4274d9c`, `0x42dee28`, `0x42eb650`, `0x434e984`,
`0x4c74d9c`, … (images B/C only); `0x80032018` at `0x4274da0`, `0x4c74da0`,
`0x567fda0` (B/C only). `0x8003201C` and `0x80032020` also occur in image A
(`Navi.exe`).

O7 — **US 2011 `Navi.exe`.** The same three literals are loaded in
`fn 0x0050dd88` (`0x8003201C`), `fn 0x0050de78` (`0x80032020`) and
`fn 0x0050e484` (`0x80112000`), so the US build has the same path.

O8 — **Which slot.** `DSK8:` is `Drivers\SD\Card2`, `PortNumber` 1,
`SDProfile2` = "Sub Slot SD Card" → `\UserSD` (rom-registry.md). The map
card is `DSK1:` (port 0, `\SystemSD`). No function on this path opens
`DSK1:`.

## Interpretation

- **FACT:** the menu item ends in `Navi.exe fn 0x004dd700`, which acts on
  the card in the **sub slot** (`DSK8:`, `\UserSD`), not on the map card.
- **FACT:** it unlocks the card and then **removes** its CMD42 password
  (CLR_PWD) using the unit's own 16-byte password read from PROD `+0x100`.
  Then it zero-writes sectors and rebuilds partition `Part00`.
  `FormatVolume` from `fatutil.dll` is loaded for it.
- **FACT:** it does **not** set a password or lock the card: image A has no
  SET_PWD or LOCK code. So the "initialise" menu does not set the PIN. It
  leaves an unlocked, freshly partitioned card.
- **OBSERVED:** initialisation runs only when the version check of
  `fn 0x004dd028` returns 0 (by C-1778, `SystemSD > UserSD`). When the card
  is not readable or not older, it returns 2/3/`0xff`, notifies
  `0x12be`/`0x12bf` and nothing is written. So a blank card would probably
  be refused. HYPOTHESIS: the item prepares a map-update card from the
  sub slot. The text of the notifications was not looked up.
- **RETRACTION:** C-8331 ("`Navi.exe` has no SDHC/CMD42/password code and
  never touches the SD PIN") is wrong for both EU and US 2011. `Navi.exe`
  reads the PIN from flash (`FMD1:`, block 5) and sends CMD42 UNLOCK and
  CLR_PWD to the sub-slot card. C-8333 (a reseller does not need the PIN,
  the unit locks its own card) is not affected. Locking is still in B/C
  (SDHC, boot, the SD LOCK menu).
- **UNKNOWN:** the dispid of `SDCardInitialization` and its vtable slot
  (O1 shows one candidate). Also unknown: what steps c–e call inside
  coredll/storage manager (`OpenStore`/`CreatePartition` are not coredll
  exports by name), and the exact sector range wiped.

## Conclusion

"Initialise SD card" does not set the SD PIN. On the sub-slot card it
unlocks and clears the password with the unit's own PIN, wipes sectors and
recreates `Part00`. `fatutil!FormatVolume` is loaded for it, but the call
site was not pinned. The map card in the main slot is not opened. Claims C-10140–C-10146 are added and C-8331 is retracted. Still
open: the step c–e calls, the wipe range, the notification texts, and an
emulator run (sub-slot model needed).
