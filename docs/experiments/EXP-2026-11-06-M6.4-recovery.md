screen mean **today**, and in what order is a unit returned to the factory map

## Method

reading the records above and classifying each statement by its existing
evidence status:

1. Read the M6.4 acceptance line, the M6.3 plan and its EXP, and the
   `## Recovery` placeholder that M6.4 must replace.
2. Collected every rejection string the plan can actually meet from

4. Separated the three evidence classes: static (reproducible offline),

5. Ordered the recovery by destructiveness: run card out → known-good clone →
   re-lock → untouched original → updater only if the unit offers it → stop.
6. Wrote the pre-test invariants, the signature table, the ordered path, the
   NAND/settings caveat and the do-not-attempt list as checklists.

## Observations

- `## Recovery` previously held only the placeholder and the sentence that
  firmware/NAND recovery was out of scope. The new section keeps that scope and
  states it as a caveat instead of an assumption.
- The four screens named by the task all exist in the `AppLaunch.dll` block:
  `SD UNLOCK NG` `0x8833681c`/`0x8834081c`, `MAP DATA BASE UNMATCH`
  `0x88336890`/`0x88340870`, `DIFFERENT MAP CODE` `0x883368bc`/`0x8834089c`,
  `NAVI VERSION NG` `0x883368e4`/`0x883408c4` (B/C); one dispatcher per build
  (`0x8834ffb8` B, `0x88359c90` C) — C-790, C-803–C-805.
- The same block also carries the boot/update failures the recovery page must
  expect: `SD ACCESS NG`, `SD INIT NG`, `NO SD CARD`, `NAVI STARTUP NG`,
  `NO SERVICE TOOL`, `TARGET INFO NG`, `NO UPDATE FILE`, `NO NAVI-1 FILE`,
  `E-BOOT NG` (C-802, C-806). Their causes are not decoded.
- `MapUpdate.exe` opens `VER_INFO/HDD_INFO.TXT`, `HDD_ADM.TXT`, `HDD_CHK.ATT`,
  `ClarionUpdate.key` and `SystemSD/MapFinish.key`, formats partitions
  (`MapUpSdCardFormat` `0x0001d57e`, `DeleteAndCreatePartition` `0x0001c74c`,
  `DriveFormat` `0x0001c58c`), copies files and sets the VSRAM complete flag
  (C-774–C-778). The task list includes `ValidateReplaceMapCard`
  `0x0001ab64` and `CheckForReplace` `0x0001ccfc`.
- Negative, limited to `SDHC.dll`/`AppLaunch.dll`/`SdCardLch.exe`: no CID/CSD
  and no FAT serial/label check (C-794, C-795). The only card-identity gate
  found is the SD security state (C-790, C-797 HYPOTHESIS).

## Interpretation

- **FACT:** the recovery page now names, per signature, what static analysis
  proved, what is hearsay, and what is untested; no step claims a result.
- **FACT:** every destructive action in the plan (format, re-lock, attestation
  file) is confined to a disposable clone; the original card is never inserted.
- **OBSERVED:** the updater path is a candidate only if the unit shows an
  update/import prompt; no record shows that prompt on any unit.
- **HYPOTHESIS:** a known-good clone that boots returns the unit to the factory
  map, because the map data the unit renders is read from the SD card
  (`sd-card-layout.md`).
- **UNKNOWN:** whether the unit writes to the card, whether a host re-lock is
  accepted, what any screen is actually caused by, and whether unit NAND or
  settings change across a card swap.

## Conclusion

`docs/research/card-test-plan.md` `## Recovery` is filled: six pre-test
invariants (original card off-bench and hashed, known-good clone aside, power
baseline, run-card identity, recovery in reach, stop rule); a five-row
signature table with a first action per screen; the ordered path (run card out
→ clone → re-lock → original → updater → stop); the static/hearsay/untested
split; the NAND/settings caveat; and ten do-not-attempt items. No result is
claimed and no card was touched. C-1120–C-1129 stay unregistered here.
