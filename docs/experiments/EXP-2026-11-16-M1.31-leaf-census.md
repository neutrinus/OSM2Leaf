## Question

Over every `.pdata` GAP of EU `Navi.exe`, how many gaps are `leaf`-flagged,
how many end in their own `rts` (complete), how many have a natural bound past
the `0x400` leaf-window cap, and how many have no `rts` at all — and is the
`fn_match --va 0x00558300` `NOMATCH` a cap artefact rather than a code
difference?

## Hypothesis

The M1.27 leaf path caps every GAP window at `0x400` B. A gap whose natural
bound (next pdata START / called entry / code end) is longer and whose first
`rts` sits past `0x400` therefore cannot be a complete window, so a hash miss on
it is "the cap cannot see it", not "the code differs". SE measured one such
gap, `0x00558300` (bound 18,966 B, first `rts` at 2,572 B), and 79 true
no-`rts` stubs.

**Falsifier:** `0x00558300` has an `rts` inside the first `0x400` B, or its
natural bound is `<= 0x400`, or every other leaf gap is complete inside the
cap while `0x00558300` is the only cap case. A second falsifier, stronger for
the verdict: the capped window hashes to a US function, so `NOMATCH` is a
genuine code difference and not a truncation.

## Method

1. **Sample and hash.** The EU head above (`92aa525d…`), whole file read as
   the first 128 MiB; module `Navi.exe` at image start `0x200200` (build A).
   The US head is re-creatable from the vendor image (both files are
   git-ignored, never committed):

   ```bash
   head -c 268435456 archive/sd-images/LEAF_2011-2012_US.img > archive/us256.img
   sha256sum archive/us256.img   # 70d945d8…04da
   ```
2. **Commands.** Run from the repo root:

```bash
python3 tools/pdata.py gaps archive/head256.img --module Navi.exe | tail -1
python3 tools/pdata.py leaves archive/head256.img --module Navi.exe --called records
python3 tools/pdata.py leaves archive/head256.img --module Navi.exe --called all
python3 tools/pdata.py leaves archive/head256.img --module Navi.exe --called gaps
python3 tools/fn_match.py match archive/head256.img archive/us256.img \
    --module Navi.exe --va 0x00558300 0x00011000 0x003f5194 0x0053a21c 0x00558218
python3 tools/fn_match.py match archive/head256.img archive/head256.img \
    --module Navi.exe --va 0x003f5194   # positive control, same build
python3 tools/fn_match.py --fixture tools/fixtures/fn_match_eu_us_2011.json \
    --eu archive/head256.img --us archive/us256.img --module Navi.exe
python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x00558300 --count 10
```

   `pdata.py leaves` classifies each GAP with the *uncapped* natural bound
   (next pdata START / next call target / code end) and the first `rts` inside
   that bound: `complete` (`rts` inside the natural bound and inside `cap`),
   `truncated` (natural bound `> cap` and `rts` at/after `cap`), `stub` (no
   `rts`). `--called` selects which call set bounds a gap:
   - `records` — calls made from pdata-recorded functions only; this is the
     set `fn_match._called_starts` derives, so it is `fn_match`'s clamp.
   - `gaps` — every call target that is itself a gap start (the tool's
     docstring wording "a called GAP").
   - `all` — every `bsr`/pool-call target in the section.
3. **Controls.** Positive: the 13-row EU→US fixture replays as
   `13 rows, 0 mismatch` (normal record functions still match), and the leaf
   `0x003f5194` still resolves to a US VA (`DIFFERENT` with its first
   differing instruction pair), so the leaf path is unchanged. Negative:
   `0x00558300` must now be `TRUNCATED` and the no-`rts` stubs
   `0x0053a21c`/`0x00558218` must stay `NOMATCH`; `--selftest` carries a
   synthetic 0x420-B complete leaf (truncated) and a 12-B no-`rts` stub (not
   truncated).
4. **Scope.** EU `Navi.exe` build A only, code section 0 read from the first
   128 MiB of the head. US head used only for the `fn_match` verdict on the
   named VAs; the US census is M1.22b, not here. Counted corpus: 7,596 pdata
   records, 677 GAPs `> 8 B`, 635 `leaf`-flagged GAPs.
5. **Falsifier.** As stated in the Hypothesis, before any result.

## Interpretation

- **FACT:** 677 GAPs `> 8 B` exist and 635 are `leaf`-flagged; the stride
  between each GAP start is what the pdata records leave uncovered (C-3960).
- **FACT:** Under `fn_match`'s own clamp (`--called records`) 598 of the 677
  GAPs end in an `rts` inside their natural bound and 77 have no `rts` at all
  (54 of them `leaf`); 2 have a natural bound `> 0x400` with the `rts` past
  the cap: `0x00558300` (the SE case) and `0x00011000` (C-3961).
- **OBSERVED:** `0x00011000` starts before the first pdata record (pre-table,
  code section base) and disassembles as data with a stray `rts` at +2,152 B;
  it is a historical `.word` run, not a function, and is not `fn_match`'s
  false-NOMATCH class (it has no pdata record so `fn_match` never claims a
  leaf verdict for it) (C-3962).
- **OBSERVED:** `--called all` prints **81** no-`rts` stubs (`81 (leaf 58)`),
  not SE's 79, so 79 is not the all-calls stub count. SE's 79 reconciles under
  the `fn_match` clamp (`--called records`) as the non-complete count: `77`
  no-`rts` stubs plus `2` cap rows (`0x00558300`, pre-table `0x00011000`). The
  two call sets differ because a call from inside a GAP (e.g. `bsr
  0x00558300+?->0x00558318` at `0x00558a88`) is invisible to `_called_starts`,
  which only scans pdata record bodies. `0x00558300`'s natural bound is 18,966 B (`0x4a16`) under the
  clamp and under `--called gaps`, so both report it as the cap case (C-3963).
- **OBSERVED:** `0x0053a21c` is a 12-B GAP window holding an 8-byte
  `mov.l @(pc),r0 / mov.l @r0,r0 / jmp @r0` dispatch (then `nop`). Under
  `--called records` its bound is `0xc` (`stub`, `rts -`); under `--called
  gaps` the bound is `0x1010` with `rts +4102` (`truncated`); under
  `--called all` it is again `bound 0xc rts -` (`stub`). The census therefore
  names the call set with every count (C-3964).
- **FACT:** The `0x00558300` window under the cap is 1,024 B with no `rts`
  while the gap's natural bound is 18,966 B. `fn_match` now reports
  `TRUNCATED`, not `NOMATCH` (C-3965).
- **OBSERVED:** The cap class is **clamp-specific**: under `--called all`,
  `0x00558300` has `bound 0x18 rts -` (`stub`) and `0x00011000` has
  `bound 0x71e rts -` (`stub`), so neither is cap-truncated there. The class
  exists only where the call set leaves the bound past the cap (`records`,
  `gaps`), because a call from inside a GAP clamps it under `all` (C-3964).
- **OBSERVED:** The `0x00558300` body is not a clean function: it begins with a
  `0x0001 0x0000` word pair, not an SH-4 prologue. The `rts` at +2,572 B may
  bound a data run, not a function body (see the task's Stop). The task's
  Done-when accepts `TRUNCATED` for this leaf either way; this EXP does not
  claim the +2,572 B `rts` is a function end (C-3966).
- **HYPOTHESIS:** M1.22b must state its unit. Under the clamp there are `598`
  **complete GAPs**, of which `579` are `leaf` and `19` are not; a leaf rate
  uses `579`, not `598`, and neither `635 leaf` nor `677 gaps` is that unit.
  The clamp's other rows are `77` no-`rts` stubs (54 leaf) and `2` cap rows
  (`0x00558300`, pre-table `0x00011000`) (C-3969).
- **UNKNOWN:** Whether any of the 77 no-`rts` stubs is a real body cut by an
  absent pdata record rather than a thunk.

## Conclusion

`fn_match`'s `0x400` cap does not silently corrupt the census once the leaf
verdict names the truncation: `0x00558300` is now `TRUNCATED` (cap `0x400`,
natural bound `0x4a16`, no `rts` in the cap), and the one other gap over the
cap under the clamp, `0x00011000`, is a pre-table data run rather than a
function. Under the clamp 77 GAPs (54 `leaf`) have no `rts`; a synthetic
0x420-B complete leaf and a 12-B stub cover both classes in `--selftest`. The
cap was not raised; `leaf_window_limit`, `trim_words` and the no-`rts` clamp
are unchanged, so the M1.28 13-row fixture still replays `0 mismatch`.
M1.22b must quote a stated unit: `598` complete **GAPs** under the clamp, of
which `579` are leaf and `19` are not, so a leaf rate uses `579`; `635 leaf`
and `677 gaps` are neither the numerator nor the denominator.

## Follow-ups

- **The 77 no-`rts` stub class** (54 leaf under the clamp): are they all real
  thunks, or are some function bodies cut by an absent pdata record? A cheap
  check is to disassemble the first few instructions of each and compare with
  the exported symbol table (M1.23) rather than the pdata table alone.
- **The 19 non-leaf complete GAPs** under `--called records`: they count in
  `598` but are not leaves, so a leaf rate must not include them; they are
  data or unreferenced code between records and need a `leaf` flag audit.
- **Call-set dependence** (C-3963/C-3964): three defensible bounds give three
  different stub/cap counts. Settle which the reader should use — the clamp
  `fn_match` applies, the docstring's "called GAP", or every call — and make
  the EXP/M1.22b adopt it explicitly; today the tool names it and does not
  pick one.
- **Secondary cap case under `--called gaps`** `0x0053a21c` (12-B dispatch,
  `rts +4102`): decide whether a dispatch window should be bounded at its
  `jmp @r0` (8 B) rather than at the next START.
