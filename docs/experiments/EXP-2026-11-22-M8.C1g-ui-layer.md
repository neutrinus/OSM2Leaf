## Question

After M8.C1f the screenshot shows only the map plane; the UI plane is
keyed out. Why does AuiApp never draw a form, and what does it take to
get one AUI form element on screen?

## Hypothesis

The UI host that runs is the wrong one, or it lacks configuration that the
unit's own flash would give (registry values, COM registrations). With
image A's AuiApp, the skin path and the control registrations in place, the
controls initialise and the first form is drawn. Falsifier from the task:
`AUI:WRN:02034302 Failed initialize control` still appears for every
control.

## Method

Runs G13–G18 boot the EU 2011 card with
`-M ze0,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch=FILE,gfx-trace=on`
and `-icount shift=0,sleep=off`, for up to 3000 s each. The IPL patch file
grows run by run:

| run | IPL patch file |
| --- | --- |
| G13 | `ze0_ipl.py patch` (M8.C1d) |
| G14 | + SystemEXE's 45 000 ms AUI wait set to INFINITE |
| G15 | + `--prefer-app auiapp.exe,auirtdll.dll` |
| G16 | + SkinPath default `\windows\ReleaseMain.skn` |
| G17 | + `DllRegisterServer` of 64 control DLLs before the skin loads |
| G18 | same as G17, made only by the committed tools (`ze0_ipl.py` + `ze0_aui.py`), with `ze0-0015` |

The serial log (the firmware's `dbgmsg` output) is the main evidence. The
registry was read from the hives in the ROM `FILES` (`cehive.py`), the
COM registration scripts from each DLL's `REGISTRY` resource, and the
imports from the PE import tables (`cerom.py`).

Screenshots show manufacturer data. They are kept out of the repository.

## Observations

**O1 — The shutdown after 45 s (G13).** SystemEXE's `CAuiMonitorCmn`
waits for the event `AUIMONI_EVT_FOR_SYS_INIT_END`, which
`AuiMonitoringCC` fires when its first form loads. The wait is a literal
45 000 (`0xafc8`) in SystemEXE's literal pool (VA `0x1fba0`, the only
45 000 in the module). On timeout the log shows
`CAuiMonitorCmn::ThreadProc::TIMEOUT!!!!!`, an `ERR_LVL_A` error log entry,
`Pow >> Pow Off 1st Detect!!!`, then the ACC-OFF shutdown and
`Force PowerOff`. The map keeps running only because Navi.exe draws it
by itself. With the wait set to INFINITE (G14) there is no shutdown, but
the UI plane stays keyed out.

**O2 — The running AuiApp is the updater's (G13, G14).** Image B (the
kernel image) carries its own `auiapp.exe`, `auirtdll.dll` and
`UpdateNK.skn`: the AUI of the card updater. `ze0_ipl.py` (M8.C1d)
merges the TOCs and keeps the kernel copy of a duplicate module, so the
updater's UI host ran. The new `--prefer-app NAME,…` keeps image A's
copy for the named modules. It also skips the overlap check for those
modules: image A's `auirtdll.dll` data section (`0x01eb3000`) overlaps the
data of kernel drivers, which is harmless because the data section is
per-process.

**O3 — SkinPath (G15, G16).** Image A's AuiApp reads
`HKCU\Software\Microsoft\Automotive\AuiApp` value `SkinPath`. The
`user.hv` in image B has the key but not the value (nor `StartForm`). With
an empty path AUIRT stops with
`AUI:ERR:82014113 … Only SKN file format is supported in this version.()`.
The value the unit would hold is the skin in image A's `FILES`,
`\windows\ReleaseMain.skn`. With that default (G16) the log shows
`AUI SKN: Load Time = 0 ms, Skins = 65`; ReleaseMain.skn is a 65-entry
launcher skin.

**O4 — COM registrations (G16, G17).** AUI controls are ATL COM objects.
Image B's `default.hv` has 102 CLSID keys, none of them image A's
controls; on the unit they are written to flash when the controls are
registered. 64 image A modules carry a `REGISTRY` resource (the `.rgs`
script). With `DllRegisterServer` called for all 64 before the skin
loads (G17), ReleaseMain.skn loads
`\SystemSD2\SkinChange\001\Substance.skn`:
`AUI SKN: Load Time = 28 ms, Skins = 36905`. The skin chain is the real
one now.

**O5 — Which controls still fail and why (G17, G18).** 16 controls
(G18; 15 in G17) log `AUI:WRN:02034302 Failed initialize control`.
`ctl_PRCOM_System` returns `80020003`, and three other controls return the
same code. For each failing control, the kernel loader logs why its DLL
did not load:

| missing DLL | `DoImport Failed!` lines (G18) | importers (static, image A) | on any card ROM? |
| --- | --- | --- | --- |
| `HCXLog.dll` | 17 (SystemCC, ScreenStateCC, PhoneCC, NaviUserInfoCC, NaviTrfCC, …) | 45 modules, ordinals 1, 2, 4, 5, 6, 7 | no |
| `HCXMemory.dll` | 12 (RDSCC, DiagnosisCC, CdrCC, CddaCC, BtAudioCC, AntitheftCC, Audio.exe, Usb.exe, …) | 58 modules, ordinals 1, 3–6, 9–19, 23, 24, 29 | no |
| `Cws_Apl.dll` | 15 (the `Telema*CC` controls) | — | no |
| `AppTimerDll.dll` | 4 (Speech.exe, Vehicle.exe) | named exports `SetAppTimer`, `KillAppTimer`, `SetAppIntervalTimer`, `RestartAppTimer` | yes, image C |
| `BT_WRPENG.dll` | 2 (PhoneBTA.exe) | itself imports HCXMemory | on A |
| `ScreenState.dll` | 1 (NaviSearchCC) | itself imports HCXLog | on A |

`HCXLog.dll` and `HCXMemory.dll` are in none of the ROM images on the
card (A, B, C). They live in the unit's own flash, like the registry.
`SystemCC` and `AuiMonitoringCC`'s form depend on them, so no form loads
and `AUIMONI_EVT_FOR_SYS_INIT_END` never fires. This is the task's Stop
case.

**O6 — The AUI surfaces exist (G18).** AuiApp creates its surfaces as
on the unit: `Command` 800 × 2400 (384 000 B), `Bitmap` 800 × 2400,
`Alphamap` 800 × 2400 and `FontAlpha` 800 × 960. DU plane 1 is the AUI
surface: mode `0x1002`, 800 × 480 at `0x0edf5400`, window (0, 480). It
holds only `0x0000` and `0x03ff` (clear and key colour), so the screen
still shows the map alone.

**O7 — Plane alpha rule.** On keyed planes (mode bit 12) a pixel is
transparent when alpha bit 15 is clear *or* the pixel equals the key.
The AUI clear writes `0x0000` on plane 1, which the M8.C1f composer drew
as black over the map; `ze0_screenshot.py` now treats it as transparent.
DU register `+0x08` holds `0xa6` (plane 1) and `0xa5` (plane 2). It is not
a plane alpha; its meaning is unknown.

**O8 — 2DG op `0x44` (G17, G18).** AuiApp's lists use
`44000000 000001e0` and `44000000 0000fe20`: add (0, 480) and (0, −480)
to the local offset, so the 2400-line surface is drawn one 480-line page
at a time. `ze0-0015` adds the op. The same lists use `0x80` with
register `0xc0` bit 27 set to clear an area; the bit's meaning is
unknown.

## Interpretation

- The UI host on the card is complete, but it relies on three things from
  the unit's own flash: registry values (`SkinPath`), the COM
  registrations of the controls, and at least two DLLs (`HCXLog.dll`,
  `HCXMemory.dll`, plus `Cws_Apl.dll` for the telematics controls). The
  first two can be supplied by an IPL patch; the DLLs cannot, because
  their code is not on the card.
- The names and ordinal sets suggest small service libraries: a logger
  (`HCXLog`, 6 ordinals) and an allocator (`HCXMemory`, about 20
  ordinals). Stubs written from the call sites in the 45 and 58 importers
  should be enough for the controls to load. `AppTimerDll.dll` can come
  from image C.
- The falsifier is not met: after the registrations, most controls
  initialise (only 16 log the warning, against every control before).

## Conclusion

With `ze0_ipl.py --prefer-app auiapp.exe,auirtdll.dll` and the lines from
`ze0_aui.py --no-aui-timeout`, image A's AuiApp starts, reads the real
skin chain (ReleaseMain.skn → Substance.skn, 36 905 skins) and registers
the 64 control DLLs. The system no longer shuts down. No form is drawn,
because 16 controls, including `ctl_PRCOM_System`, fail to load: their
DLLs import `HCXLog.dll`, `HCXMemory.dll`, `Cws_Apl.dll` or
`AppTimerDll.dll`, which are not on the card's ROM images (except
AppTimerDll in image C). The next step is stub DLLs for them (M8.C1h).
