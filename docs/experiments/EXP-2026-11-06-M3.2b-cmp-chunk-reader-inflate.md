# EXP-2026-11-06-M3.2b: `.cmp` chunk reader via `inflate`

- **Status:** partial / blocked-on-chunk-offset-consumer
- **Date:** 2026-11-06
- **Sample:** `IMG256` `/tmp/opencode/head256.img`
- **SHA-256:** `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Claims:** C-2060–C-2069
- **Supersedes:** none (extends M3.1, M3.2)
- **Superseded by:** none

## Question

Locate the zlib `inflate` implementation(s) in image A, walk up their callers,
and name the caller that loops over `.ind` `chunk_offset[]` to answer M3.2:
(a) does `chunk_size` size a buffer or is it compared against `0x10000`?
(b) does the reader seek by offset or scan for `78 9c`?

## Hypothesis

The `.cmp` chunk reader calls zlib `inflate` (every `.cmp` chunk is an
independent `78 9c` zlib stream). Finding `inflate` and walking up callers
should reach the `chunk_offset[]` loop that M3.1/M3.2's `.IND` string and
`MAL_DataVol_*` leads missed.

### 4. Navi.exe one-shot inflate wrapper (confirmed caller path)

**`0x00542148`** (prologue saves) / body `0x0054214e+`: one-shot complete-stream decompressor. Builds a 56-byte `z_stream` on stack, sets `next_in` from descriptor `*r5` (`@r8`), calls `inflateInit2_` via pool `0x5421b8→0x54232c` (`r4=z_stream,r5=windowBits arg from pool 0x5421b4→0x20a08c, r6=56`), then `inflate` via pool `0x5421bc→0x54233c` with `r5=4` (Z_FINISH), checks `ret==1` (Z_STREAM_END), updates `*r8` from `z_stream.next_in` (`@(36,r15)`), calls `inflateEnd` via pool `0x5421c0→0x54220c` on all paths. Returns 0 on success. Pool self-ref `0x542144→0x542148`.

Literal refs to wrapper `0x542148`: `0x41c8bc` (code pool, after fn 0x41c7e8), `0x542144`.

### 5. Navi.exe chunked decompression reader — **`fn 0x0041c7e8`**

**This is the decompression engine above the zlib wrapper.** Prologue `0x0041c7e8` (`sts.l pr,@-r15`), ends `0x0041c8b8` (`rts; mov r2,r0`), pool `0x41c8bc=0x542148` (inflate wrapper), `0x41c8c0=0x003d146c` (memcpy helper).

Behavior (disassembled, uncompressed sec0): random-access reader over a chunk
table at `@(28,r13)` (r13 = arg r4 context). Iterates entries with stride 20
(`bf/s 0x41c80a; add #20,r8` at `0x41c8a0`). For each entry `r8`:
- `@(8,r8)` = uncompressed start/offset of chunk (compared against requested range)
- `@(12,r8)` = uncompressed chunk length/size (stored to `@(24,r15)`, used for overlap/range math; `mov.l @(12,r8),r3` at `0x41c80e`)
- `@(16,r8)` = compressed source (passed as r6 to inflate wrapper)
- `@(4,r8)` = passed as r7 to inflate wrapper
It computes the overlap of the requested logical range `[r2, r2+req_len)` with
the chunk's uncompressed span, calls the one-shot inflate wrapper
(`mov.l 0x41c8bc,r3; jsr @r3` at `0x41c85c/0x41c866` and `0x41c878`) to
decompress the chunk (or uses a cached buffer path via `r10=r13+308`,
`mov.l @r10,r4` at `0x41c880`), then `memcpy` via `0x003d146c` (pool
`0x41c8c0`, `jsr` at `0x41c888`, `r4=dest r12, r5=src+r11, r6=len r9`) to copy
the requested slice.

**Callers of `0x0041c7e8`:** no literal ref and no `bsr` found in *any*
uncompressed o32 section of *any* build-A module (searched all 527 A sections,
`IMAGE_SCN_COMPRESSED` excluded). The inflate wrapper `0x542148` is called from
`0x41c7e8` (confirmed by pool `0x41c8bc` loaded at `0x41c85c`).

## Interpretation

- **FACT:** Navi.exe (build A) statically links zlib 1.1.3 in **uncompressed** sec0 and exposes `inflateInit2_ 0x542256`, `inflate 0x54233c` (tramp `0x54232c`), `inflateEnd 0x54220c`, `inflateReset 0x5421c4`, `inflate_blocks 0x54332a` (VAs in module realaddr space). A one-shot wrapper `0x542148` performs `inflateInit2_ + inflate(Z_FINISH) + inflateEnd`.
- **FACT:** A chunked random-access decompression engine `fn 0x0041c7e8` (Navi.exe sec0, uncomp) iterates a 20-byte-stride chunk table at `@(28,ctx)`, calls the one-shot inflate wrapper per chunk via a direct compressed-data pointer (`@(16,entry)` / `@(4,entry)`), and `memcpy`s the requested logical slice. It uses entry field `+12` as the uncompressed chunk extent for range math; it performs **no seek** and **no `78 9c` scan** in its own code (it consumes pointers). It performs **no compare of a chunk-size field to `0x10000`** in the visible code.
- **FACT (negative, scoped):** `0x41c7e8` has no literal/bsr callers in any uncompressed build-A o32 section (527 sections searched). Navi.exe sec1 (`psize 0x457c`, `vsize 0xff16ae`) and sec2 (`psize 0x8884`) are `IMAGE_SCN_COMPRESSED`; current tools cannot decode them (M1.3 0/245, M1.2f open). Therefore the caller that *builds the 20-byte chunk table / parses `.ind` `chunk_offset[]`* is **not locatable in uncompressed code** and may reside in compressed sec1/sec2 (or behind a mechanism not found). Positive control: the same literal-search method finds `0x542148`'s ref at `0x41c8bc` and auirtdll's error-string refs.
- **HYPOTHESIS (not proven):** the `.ind`/`.cmp` file-layer reader (opening `.ind`/`.cmp`, reading `chunk_count`/`chunk_size`/`chunk_offset[]`, answering M3.2a/b definitively) calls/feeds `0x41c7e8` and lives in Navi.exe compressed sec1/sec2 or is dispatched via runtime pointers. `0x41c7e8`'s behavior is consistent with `.cmp` chunked random access (decompress-by-chunk, copy slice) but its chunk-table source is unconfirmed.
- **FACT:** 6 modules in build A carry their own zlib in uncompressed sec0 (auirtdll, IconDrawCC, XGLDLL, Navi.exe, TelemaImageDrawCC, Telema.exe); Navi.exe's is the relevant map-app copy. Zlib code/data is **not** in a compressed o32 section in these copies.

## Conclusion

M3.2b is **partially satisfied**: the inflate implementation and the chunk
*decompression* engine in Navi.exe are identified with VAs and call chain.
M3.2's two questions are **not fully answered** because the `.ind`
`chunk_offset[]` consumer / `.cmp` seek-vs-scan and `chunk_size`-validation
layer was not found in uncompressed code; locating it likely requires decoding
Navi.exe compressed sec1/sec2 (M1.2f/M8.E1) or dynamic tracing (M2.11
breakpoints on the inflate/wrapper VAs recorded here). The 0x41c7e8 engine
itself uses direct pointers (no seek, no `78 9c` scan) and uses per-entry
uncompressed sizes (no `0x10000` compare observed) — informative but not a
definitive answer about the `.ind` reader's validation.
