## Question

M8.C1e left the UI submitting 2DG display lists that nothing executed
(C-6925), so no screen frame existed. Which commands do the lists use,
and is a host-side interpreter of those commands enough to get a
screenshot of the UI?

## Hypothesis

The lists are a small fixed command set: register writes, fills, glyph
blits and a stencil polygon fill. An interpreter that runs each list when
SCLR = 1 is written, plus a composer for the DU planes, gives a readable
screen. Falsifier from the task: with fills executed, the DU plane memory
stays zero after the lists that fill it.

## Method

Every run boots the EU 2011 card with
`-M ze0,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch=FILE,gfx-trace=on`
and `-icount shift=0,sleep=off` (runs G8–G12, up to 1800 s each).
With `gfx-trace=on`, `ze0-gfx` logs the first words of every started
list (`ze0-2dl:`). The interpreter logs one summary line per list
(`ze0-2dg: list ADDR: N drawn, M skipped, S steps`).

The command layouts were read from the dumped lists and checked against
the list builder in `auirtdll.dll` (image B, base `0x03cd0000`): the
emitters fn 0x03d07a14, fn 0x03d07a70 and fn 0x03d07b20 write the command
words, and their header constants sit in a table at `0x03cd63f0`. Each
reading was then tested by drawing it and looking at the result: glyph
height from the source spacing, texture size from the data block length,
pixel format from known colours.

The screen comes from `tools/ze0_screenshot.py screen --monitor SOCK -o
FILE.png`. It reads the DU registers (phys `0xfff80000`, 0x500 bytes)
with `xp`, saves each enabled plane's window with `pmemsave`, and draws
the planes from the highest number to the lowest.

Screenshots show the map of the card (manufacturer data). They are kept
out of the repository and were given to Marek directly.

## Observations

**O1 — List structure.** Every list starts with `0x30000081 0xffffffc0`.
This is a call to a preamble 0x40 bytes before the list. The preamble
sets the render target and returns:

```
18000000 00000050 ADDR      reg 0x50 = target address
18000000 0000005c STRIDE    reg 0x5c = target stride (pixels)
18000000 000200d0 V V V     regs 0xd0-0xd8: surface clip min/max
40000000 00000000           local coordinate offset
38000001 00000000           return
```

The list then alternates register groups (`0x18`), inline data blocks
(`0x28 LEN`, LEN counts the header too), syncs (`0x08000000`) and
drawing commands. It ends with `0x12000195 0`. Other `0x12xxxxxx` words
(`0x12000091` after a glyph, `0x12000011`) are traps for the driver and
draw nothing.

**O2 — Command set (coordinates `x << 16 | y`, signed halves).**

| word 0 | operands | meaning | words |
| --- | --- | --- | --- |
| `0x30xxxxxx` | `OFF` | call `op + OFF` | 2 |
| `0x38xxxxxx` | `0` | return | 2 |
| `0x40xxxxxx` | `XY` | local coordinate offset | 2 |
| `0x18000600` | `N << 16 \| R, OFF` | write N+1 registers from R, values at `op + OFF` | 3 |
| `0x18xxxxxx` | `N << 16 \| R, V0..VN` | write N+1 registers from R | 3+N |
| `0x28xxxxxx` | `LEN` | inline data, skip LEN bytes | LEN/4 |
| `0x08000000` | — | sync | 1 |
| `0xa0xxxxxx` | `ROP, C, P0, P1, P2` | filled box (bounding box of 3 corners) | 6 |
| `0xa8xxxxxx` | `C, 0, PIVOT, HALF, XY` | 8-bit alpha glyph, source reg `0x4c`, stride reg `0x58` | 6 |
| `0xe0xxxxxx` | `MIN, MAX` | start stencil polygon | 3 |
| `0xd0xxxxxx` | `N, MIN, MAX, V0..VN-1` | polygon vertices | 4+N |
| `0x80xxxxxx` | `C, P0..P3` | cover: fill the stencil polygon (even-odd) | 6 |
| `0xb0xx3xxx` | `C << 16 \| N, W, V0..VN-1` | polyline, width W | 3+N |
| `0xb0xx7xxx` | `C << 16 \| N, W, OFF` | polyline, vertices at `op + OFF` | 4 |
| `0x82xxxxxx` | `OFF, W << 16 \| H, 0, P0..P3` | textured quad, W × H texels at `op + OFF` | 8 |

Glyph size: height = 2·HALF.lo + 1 and width = min(2·HALF.hi + 1,
stride). The heights match the source spacing: glyphs with HALF.lo = 11
sit `0x170` bytes apart at stride 16 (23 rows), and those with
HALF.lo = 13 sit `0x1b0` apart (27 rows). PIVOT is (stride/2 − 1,
stride/2).

Texture size: a 32 × 32 quad (`0x00200020`) points into a `0x28` block
of length `0x808`, which is 8 header bytes plus 32·32·2 bytes. A
`0x01000001` quad (256 × 1) is a gradient strip.

**O3 — Pixels are (A)RGB1555, not RGB565.** The registry names the
surface format "565" (C-6926). Decoded as RGB565, the map land colour
`0x6f7a` comes out turquoise and main roads come out green. Decoded as
1555, land is light grey (216, 216, 208), main roads are brown, parks are
green and water is blue, which are the colours of the unit's day map.
The UI's grey `0x739c` is (224, 224, 224) in 1555. The interpreter's
alpha blend and the screenshot composer both use 1555.

**O4 — DU planes during the map screen (run G12, about 15 minutes in).**

| plane | mode | size | address | stride | window |
| --- | --- | --- | --- | --- | --- |
| 2 | `0x1002` | 800 × 480 | `0x0e932800` | 800 | (0, 0) |
| 4 | `0x4002` | 800 × 480 | `0x0e9f2000` | 2368 | (1376, 193) |

Plane 2 is the UI layer, with colour key `0x03ff` (DU `+0x248`). The UI
fills the layer with `0x83ff` (key plus alpha bit), so it is transparent
except where widgets are drawn. Plane 4 is the map. The map is drawn
on a 2368-pixel-wide surface and the DU scrolls the window over it.
Mode bit 12 turns the key on. Bit 14 marks an opaque plane. The low bits
(`0x002`) are the same for both planes.

**O5 — Commands drawn versus skipped.**

| run | interpreter | drawn | skipped |
| --- | --- | --- | --- |
| G11 | boxes, glyphs, polygons | 747 | 1494 |
| G12 | + polylines, textured quads | 2669 | 7 |

The 7 commands still skipped are `0xb3007602 N OFF` (5 times, 3 words)
and `0xb10038c2` (2 times, layout unknown). The interpreter skips them
up to the next command word and counts them. G12 ran 8 lists in
15 minutes: 3 at `0x0e8d4c70`, 3 at `0x0edda2f0`, 1 at `0x0ef9eb90` and
1 at `0x0f197490`.

**O6 — The screen.** In G12 `screen` gave 382 721 non-black pixels out
of 384 000. The map is central London in the north-up view:

- grey land with area fills;
- the street network as 1–2 px lines, and main roads as wide brown
  polylines;
- blue A-road shields (A4, A400, A401);
- textured parks (St James's Park) and water;
- street and place labels as alpha glyphs, including rotated labels
  along streets.

The UI layer is fully keyed out, so no buttons or status bar are drawn
yet. Labels along slanted streets ("RICHMOND MEWS", "AIR STREET") come
out slanted, so the glyph positions and bitmaps already carry the
rotation. Small differences remain:

- some label boxes overlap their neighbours ("TROCADERO CENTRE" and
  "JAMES'S");
- texture edges are nearest-neighbour stretched.

## Interpretation

- The 2DG is a display-list engine with a stencil-then-cover polygon
  fill, thick polylines and textured quads. It is not a general
  rasteriser with a transform pipeline. The 3 × 4 matrix the lists
  upload (`0x28000080`, C-6926) does not have to be applied: the
  coordinates in the drawing commands are already in screen space.
- An interpreter on the host side is enough for a readable screen. The
  task's Stop case (a general textured-polygon rasteriser) did not
  happen. Textured quads were drawn by stretching over their bounding
  box.
- The plane mode is a key/opacity flag on 1555 pixels, not a choice
  between 565 and 1555 (O3, O4).

## Conclusion

`ze0-0014` runs every 2DG display list in the host when the guest
writes SCLR = 1. `ze0_screenshot.py screen` composes the DU planes.
Together they give the first screen of the emulated head unit: the
London map with roads, shields, parks and labels. 2669 commands were
drawn and 7 were skipped. The falsifier is not met: the plane memory
holds the map (O6).
