## Question

## Root cause of M8.E1's false refutation

SH-4 instruction words in nk.exe sec0 are stored as **little-endian 16-bit
halfwords** (LE). M8.E1 (and parts of M1.2c's recorded byte strings) searched
for/disassembled the BE byte representation. Positive controls:

| Interpretation | bytes at 0x880385e4 | result |
| --- | --- | --- |
| LE halfwords (correct) | `e6 2f 86 2f 96 2f a6 2f b6 2f c6 2f d6 2f 22 4f` → 0x2fe6,0x2f86… | `mov.l r14,@-r15; mov.l r8,@-r15; ... sts.l pr,@-r15` (standard prologue) |
| BE halfwords (M8.E1) | same bytes → 0xe62f… | `mov #47,r6` (nonsensical prologue), capstone failed on following words |

M1.2c's flag-test pattern `mov #32,r2; mov.l @(20,r8),r3; shll8 r2; and r2,r3;
tst r3,r3; bf` is instruction values `e220 5385 4218 2329 2338 8b03`, stored LE
as bytes `20 e2 85 53 18 42 29 23 38 23 03 8b`. M8.E1 searched for the BE byte
string `e2 20 53 85…` (0 hits). The LE byte string **exists at 0x88038666** in
nk.exe sec0 (1 hit). M1.2c's VAs were correct.

## Method

1. Loaded nk.exe sec0 from IMG256 file `0x03e01200`, 0x4c800 bytes, base VA 0x88001000.
2. Disassembled 0x880385e4 with capstone LE and BE — LE produced a valid prologue; BE did not. Established LE instruction encoding.
3. Searched sec0 for LE-stored flag-test pattern bytes `20e28553184229233823038b`: **1 hit at 0x88038666**.
4. Disassembled `fn 0x880385e4` (0x880385e4..~0x88038760) in LE mode: confirmed o32 walk (base r8 from @(24,r1), stride `add #24,r8` at 0x88038660, rva match @(4,r8) vs r4, count r3), `o32_flags & 0x2000` test at 0x88038666, compressed branch.
5. Followed compressed path: read pool literals, identified calls to DECOMP_ALLOC and DECOMP_WRAP with `(src=dataptr, psize, dest, vsize)` argument flow.
6. Disassembled DECOMP_WRAP 0x88037590, DECOMP_SECT 0x88037464, DECOMP_BLK 0x8803a384; read their pool literals; confirmed chain and call from DECOMP_SECT to DECOMP_BLK via pool 0x8803758c=0x8803a384.
7. Byte-level positive controls: marker `5b80808d` present in sec0 at 0x8804d786 inside an embedded form-1 comphdr (data, not a code ref) — confirms LZXD framing awareness in the image; comphdr parser confirms EXP-49 form 1; `tools/cedecomp.py --selftest`/`tools/cedecomp_run.py --selftest` pass.

### Endianness / M8.E1 correction

M8.E1 C-1600 stated the flag-test pattern and M1.2c VAs/literals "do not match
IMG256 bytes" — that was true only under BE interpretation. Under correct LE
interpretation the pattern is present at 0x88038666 and pool/literal values
match M1.2c (e.g. 0x8803758c stores LE `0x8803a384`; M8.E1 reported BE-read
`0x84a30388`). M8.E1 C-1603 execution fault at 0x88037464 under `qemu-system-sh4eb`
is consistent with running LE code on a BE-configured CPU/mapping. C-1601's
loader/gdbstub mechanics remain useful but the "sh4eb" choice and VA-refutation
conclusion were wrong for nk.exe code.

### Embedded form-1 blob (positive control, data)

`5b 80 80 8d` appears at 0x8804d786 inside a form-1 comphdr at 0x8804d770
(`u24 ulen=0x0ff0, psize=0x088c, flags=0x10, payload=0x0876, marker at +22`) —
stored data near sec0 end, not a code-referenced constant (consistent with M1.2c).
Confirms the image contains form-1/LZXD-framed data of the kind the chain handles.

## Interpretation

- **VERIFIED (FACT, IMG256 bytes):** nk.exe B `fn 0x880385e4` at 0x880385e4 performs an o32 walk (stride 24) and tests `o32_flags & 0x2000` at 0x88038666. The compressed branch calls `DECOMP_ALLOC 0x88034d94` then `DECOMP_WRAP 0x88037590(dataptr, psize, dest, vsize)` at 0x88038698. Pool-confirmed chain: `0x88037590` → `0x88037464` (pool 0x88037620, called 0x880375de) → `0x8803a384` (pool 0x8803758c, called 0x88037542). This confirms M1.2c C-660–C-663 and restores their VAs.
- **VERIFIED (correction):** M8.E1 C-1600/C-1603–C-1605 are endianness artifacts (BE search/exec on LE SH-4 code). They are superseded by C-2290–C-2296; M1.2c VAs were correct.
- **OBSERVED:** DECOMP_WRAP requires kernel lock/context helpers (pools 0x88037614/1c/24/28, global 0x88037618=0x89e6ade0). Bare-metal QEMU execution needs stubs or a direct call into DECOMP_SECT/DECOMP_BLK with a constructed frame; `qemu-system-sh4` (LE) must be used, not `sh4eb`. Full EXP-49 byte decode under emulation remains follow-up work (M8.E1 resume) — the VA/prototype is now verified.
- **FACT (unchanged):** LZXD block codec (C-664) not ported to pure Python; EXP-49 sections not decoded to expected lengths by current codecs (C-665 negative). DECOMP_BLK reads an 8-byte block header and handles LZXD-like framing consistent with `0x8d80805b`/type-4/E8 observations.

## Conclusion

M1.2c's decompressor VAs/prototypes are **verified correct on IMG256 nk.exe B** when
SH-4 is decoded as LE. M8.E1's refutation was an endianness error and is corrected.
Verified entry points for M8.E1 (use `qemu-system-sh4`, LE): **DECOMP_WRAP
0x88037590** or **DECOMP_SECT 0x88037464** with `(r4=src, r5=psize, r6=dest,
r7=vsize)`, noting DECOMP_WRAP's kernel-context dependencies; section loader
flag test is at 0x88038666 in `fn 0x880385e4`. `tools/cedecomp.py` / `cedecomp_run.py`
updated accordingly.
