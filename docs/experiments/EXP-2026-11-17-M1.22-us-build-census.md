# EXP-2026-11-17-M1.22: the US build census, and both L3 readers on US code

- **Status:** done
- **Date:** 2026-11-17
- **Sample:** `archive/head256.img` (EU 2011 head, SHA-256
  `92aa525d…007f9`) and `archive/us256.img` (US 2011 head, SHA-256
  `70d945d8…04da`); the US `REFER001/POINT010.DAT.{cmp,ind}` pair from the
  factory tree (`.cmp` `48812f8c…d4657`, `.ind` `7ac54e3b…c326e`); the full
  US image `archive/sd-images/LEAF_2011-2012_US.img` was **not** needed.
- **Tools:** python3 3.15; `tools/{fn_match,cerom,pdata,nk_decomp,point_walk_l3,chunk_decoder_l3,l3check}.py`,
  `tools/l3_harness/runner.py`, `tools/l3_harness/targets.json`
- **Claims:** C-3530–C-3539, C-3630–C-3639
- **Supersedes:** none
- **Superseded by:** none

## Question

M1.22b mapped the 13 cited readers but left three things open (the PO re-open,
rule 15): the all-module census with the US-only modules named, an honest
statement about the `≥90 % UNIQUE` floor, and the `point_walk_l3` /
`chunk_decoder_l3` reruns **on the US build with the US VAs**. Does the US
build's own code run our page, and does the EU build genuinely fail there?

## Hypothesis

The US `Navi.exe` is a different binary (7,520 vs 7,596 `.pdata` records,
entry `0x0035d894` vs `0x0032edd0`), but its map readers are the same source:
the walkers and the chunk engine will match by masked instruction-form
stream, and running the US VAs on the US page will reproduce the EU verdict.
**Falsifier:** if the US walker or engine cannot be located by its own pool,
or if a wrong-build control also passes, the "US code runs the US card" claim
is not supported.

## Method

1. **Sample.** Both 256 MiB heads; the US factory `POINT010` pair (a copy is
   in `leafre-work/m5.12-us/root-factory/REFER001/`, outside the repo).
2. **Commands.**
   ```bash
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img modules | wc -l
   python3 tools/cerom.py --image-start 0x200200 archive/us256.img modules | wc -l
   python3 tools/fn_match.py match archive/head256.img archive/us256.img \
     --module Navi.exe --va 0x003f5194 0x0041c7dc … 0x00542250
   python3 tools/point_walk_l3.py walk archive/us256.img \
     --cmp …/POINT010.DAT.cmp --ind …/POINT010.DAT.ind \
     --page 0x840ba0 --page-len 42848 --build us2011
   python3 tools/point_walk_l3.py skip archive/us256.img … --build us2011
   python3 tools/chunk_decoder_l3.py run archive/us256.img \
     --cmp …/POINT010.DAT.cmp --ind …/POINT010.DAT.ind --sec1 zero-mask --build us2011
   ```
3. **Controls.** *Positive*: the EU targets keep their EU runs (`--build
   eu2011`). *Negative* (three, all constructed here): (a) the US skip walker
   with the EU global cells; (b) the EU nth reader VA on the US text; (c) the
   US chunk engine with the EU helper stubs.
4. **Scope.** The census (read-only), the two tools' `--build` selector, one
   US target in `targets.json` + its `l3check` evidence row. No map file is
   written.
5. **Falsifier.** Stated in the Hypothesis.

## Observations

**Census** (`cerom.py modules` and an EXECUTE-section SHA-256 per module;
every code section is uncompressed in both builds, 0 of 149 and 0 of 151
compressed sec0):

```
EU modules 149, US modules 151, common 148
only EU (1): RDSCC.dll
only US (3): RBDS_CC.dll, XMCC.dll, XMStatusCC.dll
code-identical (every EXECUTE section, stored bytes): 1   atlce400.dll
code-different: 147
```

`RDSCC.dll` (RDS/RBDS radio data, EU) is replaced on the US card by
`RBDS_CC.dll` (North-American RBDS), and the US card adds the XM satellite
radio pair `XMCC.dll` / `XMStatusCC.dll`; US `XMStatusCC.dll` imports
`naviccipcmsg.dll` like the other US CEs. So the "two modules exist only on
the US card" in the task text is really **three**: `RBDS_CC.dll`, `XMCC.dll`,
`XMStatusCC.dll` (and one US-only, `RDSCC.dll` is EU-only).

**Readers** (`fn_match.py` on the 13 cited readers):

```
# unique: 5  ambiguous: 0  different: 7  leaf: 0  nomatch: 1  truncated: 0  of 13
```

The `≥90 % UNIQUE` floor is **not met and should not be**: `UNIQUE` counts
the frozen hash hit, and 7 of the 13 have the same masked instruction-form
stream with a moved literal pool (`DIFFERENT`). On this measure the honest
sentence is "12 of 13 cited readers are located; 5 by an exact content match
and 7 by an identical form stream with different literal values". That is a
data-layout metric, not a reader-coverage metric.

Independent verification of the 12 relocated bodies (pool slots zeroed, body
length from the first `rts`), EU → US:

```
chunk engine         body EU=111 US=111  first masked diff: NONE
chunk table loop     body EU=131 US=131  first masked diff: NONE
CMP/.ind opener      body EU=59  US=59   first masked diff: NONE
POI name accessor    body EU=34  US=34   first masked diff: NONE
zlib purge           body EU=98  US=98   first masked diff: NONE
MMAIN                body EU=97  US=97   first masked diff: NONE
DRSTR                body EU=382 US=382  first masked diff: NONE
REFER access path    body EU=120 US=120  first masked diff: NONE
ADDRE0 resolve       body EU=61  US=61   first masked diff: NONE
RDSTM                body EU=136 US=136  first masked diff: NONE
POINT namer          body EU=41  US=41   first masked diff: NONE
POINT walker leaf    body EU=32  US=32   first masked diff: NONE

NEGATIVE (known rewrite) EU 0x003fbed8 vs US 0x00424850:
  body EU=233 US=220, first masked diff = halfword 11 @+0x16 (0xdc6f vs 0xdc69)
```

The negative control (the one genuine rewrite) diverges at halfword 11, so the
"identical" above is a measurement, not a matcher that cannot fail.

**Walker disambiguation.** `fn_match` maps both `0x003f39c0` (skip walker) and
`0x003f5194` (nth reader) to `0x0041db44`, because their leaf bodies are
identical. The dispatcher's own pool settles it — EU `[0x003f5d48]=0x003f5194`,
`[0x003f5d88]=0x003f39c0`; US `[0x0041e6a8]=0x0041db44`, `[0x0041e6e8]=0x0041c370`:

```
US skip walker at 0x0041c370, 20 halfwords:
0x0041c370  6343  mov r4,r3
…
0x0041c394  920c  mov.w @(0x0041c3b0,pc),r2  ; [0x0041c3b0]=0x04d8
```

Same body as EU `0x003f39c0` (which loads `0x04e8`), one pool word apart.

**US runs** (`--build us2011`):

```
point_walk_l3.py walk  → 9/9 OK, negative control ok (unswapped page gives 0xc0/0x4c0), result: PASS
point_walk_l3.py skip  → 9/9 OK, guard and count controls ok, result: PASS
chunk_decoder_l3.py run → r0=42848 copied=42848 insns=1057251 memcpy=11 calloc=8
                          verdict: PASS (byte-identical to cmpind.decode)
```

**Wrong-build controls** (all constructed, all fail loudly):

```
(a) US skip walker + EU globals base → UnmappedAccess: no mapped region covers 0x00c8c0d0..0x00c8c0d4
(b) EU nth VA 0x003f5194 on the US text → UnmappedAccess: no region covers 0x00000011..0x00000012
(c) US chunk engine + EU helper stubs → BLOCKED: no mapped region covers 0x00000000..0x00000002
```

**Honest limitation.** `sha256sum` on the US and EU factory `POINT010` pairs:

```
48812f8c…d4657  …/m5.12-us/root-factory/REFER001/POINT010.DAT.cmp
7ac54e3b…c326e  …/m5.12-us/root-factory/REFER001/POINT010.DAT.ind
```

The EU card extracted here has **no** `REFER001/POINT010` at all (its
`REFER001` holds `ADDRE`/`ADF*` pairs), so the "EU page" in any earlier run was
this same US file; the EU **chunk engine** also decodes this page
(`PASS`). That is expected for stock zlib data and is stated here rather than
hidden: what this task proves is that the US **code** paths and addresses run
and reproduce, not that a differing page is decoded.

## Interpretation

- **FACT:** the census is 148 common modules; exactly one module's code is
  byte-identical (`atlce400.dll`); the US-only modules are `RBDS_CC.dll`,
  `XMCC.dll`, `XMStatusCC.dll` and the EU-only one is `RDSCC.dll`. The US
  head has 151 modules against 149.
- **FACT:** every one of the 12 relocated readers has an identical masked form
  stream and body length; the one rewrite diverges at halfword 11. The
  `≥90 % UNIQUE` floor is a freeze-hash metric and is reported as not met.
- **FACT:** the US walker (nth and skip), dispatcher and chunk engine all run
  on the US head and reproduce the Python model on the US page; each
  wrong-build pairing stops on an unmapped access, so the pass cannot be the
  old offset.
- **IMPLICATION:** M9.10 and M9.12 can name `us2011` as the build for the US
  cards; the new `cmp_ind_reader_us2011` target and the two walkers' `--build`
  selector are the mechanism.
- **LIMITATION:** no differing US page was available here; the EU card has no
  `POINT010`. A page that differs byte-wise would be a stronger test and is
  left to M9.10's own corpus work.

## Conclusion

The US build is mapped: 148 of 151 modules by name, its one extra and its
missing one named, the 13 readers located (5 exact, 7 same-form, 1 rewrite, 1
unlocated US counterpart), and the POINT walkers plus the chunk engine run on
US code with their addresses derived from each engine's own literal pool. The
US runs PASS and every wrong-build control fails. `targets.json` gains
`cmp_ind_reader_us2011` (`build: us2011`) and both L3 tools gain `--build`.
