# EXP-2026-11-20-M9.26: Where a POINT page becomes native `u16`, step by step on the real card

- **Status:** done
- **Date:** 2026-11-20
- **Sample:** firmware `archive/head256.img` (IMG256) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` (EU 2011)
  SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`;
  page `REFER001/POINT010.DAT` at `0x6e06d0` (41,958 B compressed, 97,158 B
  inflated, 1,000 records), served from the card's `.cmp`/`.ind` pair
- **Tools:** `python3 3.13.18`, zlib 1.3; repo tools
  `tools/point_byteorder_l3.py` (new: `run`, `--selftest`),
  `tools/vcard_l3.py` (session + `Expected`), `tools/point_walk_l3.py`
  (`run_nth`, `swap16`), `tools/l3_harness/runner.py run cmp_ind_reader`,
  `tools/sh4xref.py`, `tools/sh4dis.py`, `tools/nk_decomp.py pdata`
- **Claims:** C-2900–C-2905
- **Supersedes:** none (refines EXP-2026-11-20-M3.11b-point-byteorder-2; its
  C-5815 is superseded by C-2903)
- **Superseded by:** none

## Question

Is the POINT data the firmware's decoders produce in file order or native
`u16`, where does the page the walker `fn 0x003f5194` reads come from, and
does any consumer see file-order bytes?

## Hypothesis

M3.11b-2 placed the swap in the map-file layer's completion (`0x00417eac`,
request word +20 = 0, C-5810–C-5816) and concluded that the page reaches the
walker swapped by the layer (C-5815). But a POINT page is a **zlib stream**
inside the `.DAT` (`78 9c` at `0x6e06d0`), and a byte-swapped stream cannot
be inflated. So the layer's swap must be undone before the inflate, and the
native page must be produced after it. Static lead: the page loader
`fn 0x003fd690` (EU2011, pdata START, length `0x688`) calls the leaf
`0x003f6968(buf, nbytes)` at `0x003fd9de` (on `@(12,r14)`, before the inflate
wrapper `0x00542100` at `0x003fd9ec`) and at `0x003fda02` (on the inflate
destination `@(16,r14)`, after a zero return); the leaf is a byte-pair loop
(`mov.b @r4`, `mov.b @(1,r4)`, `shll8`, `or`, `mov.w r3,@r4`).

**Falsifier:** the leaf on the layer's +20 = 0 bytes does not give the
file-order stream; or the leaf on the inflated page does not give
`swap16(page)`; or the walker gives `parse_page`'s offsets on the file-order
page too (then the byte form would not be what it reads).

## Inputs

| Item | Value |
| --- | --- |
| Layer read | `vcard_l3` session `read(REFER001/POINT010.DAT, 0x6e06d0, 41958, swap=…)`, firmware code incl. completion `0x00417eac` |
| Chunk decoder | `fn 0x0041c7dc` (`cmp_ind_reader`, M9.11b) |
| Page loader | `fn 0x003fd690` (EU2011; pdata START, length `0x688`) |
| Byte-pair leaf | `0x003f6968` (pdata GAP after `fn 0x003f6908`: a leaf without its own `.pdata` row) |
| Inflate | wrapper `0x00542100` → `0x00542148` (the zlib the chunk engine uses) |
| Walker | `fn 0x003f5194` (C-2540) |

## Method

1. **Sample and hash.** As above. No vendor byte is committed.
2. **Commands:**

   ```bash
   IMG=archive/head256.img
   CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   FACT=/home/user/scratch/factory-eu          # EU 2011 card tree (for the .cmp/.ind pair)
   python3 tools/point_byteorder_l3.py --selftest
   python3 tools/point_byteorder_l3.py run $IMG --card-image $CARD --json run.json
   python3 tools/l3_harness/runner.py run cmp_ind_reader --image $IMG --cmp $FACT/REFER001/POINT010.DAT.cmp --ind $FACT/REFER001/POINT010.DAT.ind --json
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --to 0x00542148
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --to 0x00542100
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --to 0x003f6968
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x003f6968 --count 16
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x003fd9d2 --count 30
   python3 tools/nk_decomp.py pdata $IMG --module Navi.exe 0x003fd690
   python3 tools/nk_decomp.py pdata $IMG --module Navi.exe 0x003f6968
   ```

   `point_byteorder_l3.py run` boots the EU card with `vcard_l3.py`, reads the
   page's compressed bytes through the firmware's layer with word +20 = 1 and
   = 0, runs the leaf `0x003f6968` (PySh4, Navi.exe text, `r4` = buffer,
   `r5` = byte count) on the +20 = 0 bytes, inflates, runs the leaf on the
   inflated page, and runs the walker on the leaf output and on the
   file-order page (n = 0, 1, 2, 3, 10, 500, 999).
3. **Controls.** Positive: the walker on the leaf output must equal
   `mutate_refer_poi.parse_page`. Negative: the walker on the file-order page
   (must differ); the +20 = 0 stream inflated without the leaf (must fail);
   the +20 = 1 read (must equal the file-order stream, the layer did not
   swap); leaf twice = identity. `--selftest` (11 checks) breaks each
   expected value once and requires a FAIL.
4. **Scope.** EU2011 build A, EU card, one page of `POINT010.DAT`. The leaf
   and the walker run as functions, not inside `fn 0x003fd690` (its context
   — page table, handles — is not built here); the call order inside
   `fn 0x003fd690` is from the disassembly. The inflate step is host zlib
   (`0x00542100` is the zlib the chunk engine runs; M9.11b shows that engine
   byte-identical to `cmpind.decode`). US2011 not run.
5. **Falsifier** as stated under Hypothesis.

## Interpretation

- **FACT (C-2900):** the decoders produce **file order**: the chunk engine
  `fn 0x0041c7dc` returns the `.DAT` bytes as stored (M9.11b ACCEPT on the EU
  pair), and the page inflate yields the file-order page (first header word
  `0x6027` big-endian: type `0x18`, `0x27` words = `0x4e` bytes, record 1's
  offset).
- **FACT (C-2901):** the layer's completion swap (word +20 = 0) is applied to
  the **compressed** bytes too; that stream is not inflatable
  (`incorrect header check`). The leaf `0x003f6968` turns it back into the
  file-order stream byte for byte.
- **FACT (C-2902):** the same leaf on the inflated page gives exactly
  `swap16(page)`, and the walker on that buffer returns `parse_page`'s offsets
  for 7/7 n; on the file-order page it does not (`0x6c0`, `None` for n = 1, 2).
- **FACT (C-2903, from disassembly + the runs above):** the native page the
  walker reads is made in the page loader `fn 0x003fd690`: leaf before the
  inflate (undo the layer's swap), inflate, leaf after it (make the page
  native). This supersedes C-5815's "the swap … is the layer's completion"
  for POINT pages: the layer's swap is undone, not passed through. C-5815 is
  right for the plain (not zlib) `.DAT` bytes it measured (header range
  `[0, 0x1000)`).
- **OBSERVED (C-2904):** all three callers of the inflate wrapper
  `0x00542100` (`fn 0x003fd690`, `fn 0x00404994`, `fn 0x004052d4`) also call
  the leaf twice, so the "unswap – inflate – swap" pattern is the firmware's
  general way of reading zlib pages through the swapping layer. Only
  `fn 0x003fd690` is run here.
- **FACT (C-2905), answers C-2545(a):** the place where the POINT page
  becomes native `u16` is the leaf `0x003f6968` called at `0x003fda02` in
  `fn 0x003fd690`; the reason M3.11's swap-loop search missed it (C-2548) is
  that its loop is a byte-pair assembly (`mov.b` + `shll8` + `or`), not a
  `swap.b` loop. No consumer of the walker sees file-order page bytes; the
  inflate (zlib) is the only consumer that sees file-order bytes, by design.
- **Note on the task text:** the Done-when names C-2234/C-2239. Those IDs are
  M9.13 tile-reader rows (`claims.md` "M9.13 — L3 run of the M3.5 tile
  reader"), not POINT byte-order claims; the claims that state the open point
  are C-2545(a) and C-5815, and those are the ones this EXP answers and
  supersedes. C-2234/C-2239 are unchanged.
- **Scope:** EU2011, one page; the leaf and walker run as functions.

## Conclusion

The decoder output is file order, the map-file layer swaps every read
(compressed bytes included), and the page loader `fn 0x003fd690` undoes the
swap with the byte-pair leaf `0x003f6968`, inflates, and swaps the inflated
page with the same leaf; the walker reads that native buffer. All five steps
and four controls hold on the real EU page. C-5815 is superseded by C-2903;
C-2545(a) is answered by C-2905. `docs/format/firmware.md` is updated where it
stated the layer as the source of the native page.
