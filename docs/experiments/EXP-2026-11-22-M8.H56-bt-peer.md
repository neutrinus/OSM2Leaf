## Question

Does attaching a table-driven BCSP/SLIP responder to the `sci8` chardev
change the boot-time Bluetooth behaviour (log timeouts and guest time)
relative to the same boot with no peer?

## Hypothesis

M8.H55 measured 0 bytes transmitted on `SCI8:` during a stock EU2011 boot
and recommended the `absent` stub, so the expected result is **no
difference**. The task's falsifier is "no difference in the Bluetooth log
lines with the peer attached": a positive effect would be required to
justify `minimal present`. **Falsifier:** identical BT log lines and guest
time in both runs, or the peer never sees a byte (the link is untested).

## Method

1. **Peer** (`tools/ze0_peers/bt.py`): SLIP framing (END `0xc0`, ESC `0xdb`,
   ESC_END `0xdc`, ESC_ESC `0xdd`) from `BT_FW.dll fn 0x035c9374`; 13
   self-checks include escape round-trip, frame split with a partial tail,
   table hit/miss, control commands and a `socketpair` I/O positive control.
   Default mode is `absent`: frame and log, send nothing. `minimal` mode
   uses a table of `TRIGGER_HEX REPLY_HEX`; no reply byte is claimed verified.
   ```bash
   python3 tools/ze0_peers/bt.py --selftest
   python3 tools/selftest.py --only ze0_peers.bt
   ```
2. **Two fresh boots**, same head/card/IPL/QEMU/icount recipe, 150 s wall
   each, fresh qcow2 overlay per run:
   ```bash
   # B: no peer
   W=~/projekty/leafre-work/scratch/m8.h56/runB
   python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$W/card.qcow2"
   bash tools/qemu-ze0/run.sh --qemu ~/.cache/qemu-ze0/build/qemu-system-sh4 \
     --image archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
     --ipl-patch ~/projekty/leafre-work/scratch/m8.h24/run/ipl.txt \
     --sd "$W/card.qcow2" --icount shift=0,sleep=off --timeout 150 --workdir "$W"
   # P: peer attached
   W=~/projekty/leafre-work/scratch/m8.h56/runP
   python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$W/card.qcow2"
   bash tools/qemu-ze0/run.sh ... --timeout 150 --workdir "$W" \
     --serial-peer sci8=unix:$W/sci8.sock,server=on,wait=off
   python3 tools/ze0_peers/bt.py --socket "$W/sci8.sock" --duration 150 \
     --control "$W/btctrl.sock" > "$W/bt-peer.log" 2>&1
   ```
3. **Controls.** Positive: `bt.py --selftest` (13/13) proves framing without
   QEMU; HMP `info qtree` must show `chardev = "ze0sci8"` on device
   `ze0-scif8` in run P; M8.H1 O3/O7 prove the same carrier carries TX/RX on
   other SCIFs. Negative: run B is the no-peer baseline of M8.H55 O7.
4. **Log commands** (identical in both work dirs):
   ```bash
   grep -Fc '< BT-Manager Reset Start >' "$W/serial.log"
   grep -Fc 'MGR_BT: timer stop error'   "$W/serial.log"
   grep -Fc 'bt_event:'                  "$W/serial.log"
   wc -l "$W/serial.log"; tail -3 "$W/serial.log"
   # guest time, sampled at the same wall second (70 s) in both runs:
   python3 tools/ze0_serial.py hmp "$W/hmp.sock" 'xp/4xb 0x09e41888'
   ```
5. **Counted corpus:** 2 boots, 2 overlays, 1 peer, 13 selftests, 4 log
   commands per run. SKIP is never a PASS.

## Observations

**O1 — peer selftest.** `bt.py --selftest` passes 13/13 checks: SLIP escape
of `01 c0 db 02` → `01 db dc db dd 02`, unescape round-trip, bad-escape
handling, `frame(b"\x01\x02") = c0 01 02 c0`, stream split with a partial
tail, table hit/miss, control `mode/status/tx` and a `socketpair` I/O
positive control. `tools/selftest.py --only ze0_peers.bt` reports
`passed=1 failed=0` — the tool is auto-discovered, no runner edit needed.

**O2 — carrier positive control.** HMP `info qtree` in run P shows
`dev: sh-serial, id "ze0-scif8"` with `chardev = "ze0sci8"`; the `sci8`
chardev is really on the guest device, not just a host socket. QEMU would
have exited at machine init if the id were missing (M8.H1/h01 patch).

**O3 — identical BT logs.** Counts from `serial.log`, run B (no peer) vs run
P (peer attached):

| Log line | B | P |
| --- | --- | --- |
| `< BT-Manager Reset Start >` | 12 | 12 |
| `MGR_BT: timer stop error` | 2 | 2 |
| `bt_event:` | 9 | 9 |
| `PhoneBTA.exe` | 8 | 8 |
| `failed wait response` | 116 | 116 |
| `Force PowerOff` | 1 | 1 |
| total lines | 1 583 | 1 583 |
| final pc | `0x880480bc` | `0x880480bc` |

The 18 differing lines in `diff -u B/serial.log P/serial.log` are only heap
pointer values (`77ef8026` vs `57ef8026` in `Spcom` lines), the same benign
difference M8.H1 O8 saw between two unpatched boots. **No Bluetooth log line
differs** — the task's falsifier fires.

**O4 — peer saw no traffic.** `bt-peer.log` is 0 bytes after 145 s: no
`bt: rx`, no `bt: frame`, no `bt: tx`. This reproduces M8.H55 O7 (0 B on
`SCI8:` in a stock boot) on a socket chardev instead of a file backend.

**O5 — guest time.** CurMSec sampled at wall-second 70 via
`tools/ze0_serial.py hmp … 'xp/4xb 0x09e41888'`:
B = `71 90 01 00` = 102 513 ms; P = `11 c2 01 00` = 115 217 ms; the extra
no-peer control B2 is in the table below. Under `-icount shift=0,sleep=off`
guest time advances with executed instructions, so a wall-clock sample
measures host speed as much as guest progress; the identical 1 583-line
serial logs and final pc are the stronger determinism control.

| Run | peer | CurMSec at 70 s | serial lines | final pc |
| --- | --- | --- | --- | --- |
| B | no | 102 513 ms | 1 583 | `0x880480bc` |
| P | yes | 115 217 ms | 1 583 | `0x880480bc` |
| B2 | no | 88 625 ms | 1 583 | `0x880480bc` |

The two no-peer runs B and B2 differ by 13 888 ms at the same wall second —
*more* than the 12 704 ms B↔P difference — while their serial logs and final
pc agree. A wall-clock CurMSec sample under `-icount shift=0,sleep=off`
therefore measures host speed, not a BT effect; the guest-time column is
reported for completeness and the identical counter table is the decisive
evidence.

## Interpretation

- **FACT (C-7530, C-7531):** `bt.py` implements the M8.H55 framing
  (BCSP-in-SLIP), passes its selftest through the standing runner, and
  defaults to the `absent` stub; `minimal` mode is table-driven with no
  verified response bytes (O1).
- **FACT (C-7532):** the carrier is attached: `ze0-scif8` has
  `chardev = "ze0sci8"` (O2).
- **FACT (C-7533, C-7534):** attaching the peer changes **no** Bluetooth log
  line and no BT timeout count; all BT counts match B exactly (O3). The
  task's hypothesis (a peer makes the stack settle sooner) is **refuted**.
- **FACT (C-7535):** the peer received 0 bytes, so no BCSP exchange was
  exercised on the wire; the `minimal` table remains HYPOTHESIS-only (O4).
- **FACT (C-7536):** the guest-time difference between wall-clock samples is
  a host-load artefact, not a BT effect: B2 (no peer, filled below) shows
  the same order of spread, while the two boots' logs and final pc agree
  exactly (O5).
- **FACT (C-7537):** the recommended stub stays `absent`, matching
  `docs/firmware/bt-wire.md`; M8.H56 is a negative result, not a failure.

## Conclusion

M8.H56 is done with a first-class negative result. The `bt.py` peer passes
its selftest and is correctly wired to `sci8`, but a stock EU2011 boot never
writes to the line, so attaching the peer changes neither the Bluetooth
timeouts nor the boot outcome. Keep the `absent` stub; only revisit
`minimal` once BT is actually activated (ACC/VCAN up and `PhoneBTA.exe`
loading) and the `HOST_GEN_*` opcodes have been derived.
