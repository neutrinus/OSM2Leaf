## Question

Does every `fn 0x…` label that `sh4xref`, `sh4scan` and `reader_precheck` print come from the module's
`.pdata` table when an image and module are supplied, and does `cerom.e32()` expose the exception
directory that locates it?

## Hypothesis

`cerom.e32()` can return the exception-directory pair `(units[6], units[7])` as an additive
`exception` key without changing any existing caller. With that key, `pdata.load_table` locates the
table, and the three tools label holders from it instead of the `rts`/prologue heuristic. On VAs
where the heuristic already agrees with pdata the label is unchanged; on a load whose heuristic
start is a pool/leaf artefact the pdata label is the true function start.

Falsifier: a tool selftest that cannot pass with pdata labels (the prologue fallback is still needed
somewhere), or a `cerom.e32()` change that breaks an existing caller/selftest, or a spot VA where
the printed holder contradicts `pdata.py fn`.

## Method

1. **Sample and hash.** `archive/head256.img`, SHA-256 above; every command below reads at most the
   first 128 MiB (the firmware lives in the first ~100 MB). Decoded pdata slices are cached under
   `/tmp/opencode/work/m1.20/decomp/` and never committed.
2. **Commands.** Runnable as written, in one block:

   ```bash
   python3 -c "import sys;sys.path.insert(0,'tools');import cerom;d=open('archive/head256.img','rb').read(128<<20);print(sorted(cerom.CERom(d,0x200200).e32(cerom.CERom(d,0x200200).module('Navi.exe')).keys()))"
   grep -c pdata tools/sh4xref.py tools/sh4scan.py tools/reader_precheck.py
   python3 tools/pdata.py --selftest
   python3 tools/pdata.py table archive/head256.img --module Navi.exe | tail -1
   python3 tools/pdata.py fn archive/head256.img --module Navi.exe 0x0041c7dc 0x0041c990 0x004125a8 0x0032ef60 0x0032efb8 0x003f5194
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x0041c7dc
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x0041c990
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x004125a8
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x0032ef60
   python3 tools/sh4scan.py archive/head256.img --image-start 0x200200 --module Navi.exe dump --va 0x0032ef60 --count 4
   python3 tools/reader_precheck.py archive/head256.img --module Navi.exe --anchor 0x0055d924
   python3 tools/selftest.py
   python3 tools/claims_check.py
   python3 tools/todo_check.py
   ```

3. **Controls.**
   *Positive:* `pdata.py table Navi.exe` reproduces C-3483 (7,596 records, first `0x0032ed9c`, last
   ends `0x00558300`); `sh4xref --to 0x0041c7dc` names the holder `fn 0x0041c990`, which equals
   `pdata.py fn 0x0041ca58` (INSIDE `0x0041c990`); the pre-implementation `sh4xref` already printed
   `0x0041c990` from the heuristic, so that line is a control for "pdata and heuristic agree here",
   not for the change.
   *Negative:* a pdata GAP (leaf, `0x003f5194`) has no record; the tools must fall back to the
   heuristic and must **not** invent a start for it. A `cerom.e32()` caller that does not know the
   new key must still work (the whole existing tool suite is the regression control).
   *Self-test:* `pdata.py --selftest` (START/INSIDE/GAP/BEFORE/unsorted/duplicate), `sh4xref.py
   --selftest`, `sh4scan.py --selftest`, `reader_precheck.py --selftest` exercise the synthetic path
   where `mem` has no `fn_of`.
4. **Scope.** Build A `Navi.exe` for the spot checks; the whole tool suite for regression. Sections
   A/B/C census numbers are quoted from EXP-2026-11-12-M1.20, not re-derived (task hint: do not
   re-derive the census). Excluded: build B/C spot checks (they need the same image, same code path,
   already censused in M1.20).
5. **Falsifier.** Any selftest failure, any `cerom.e32()` caller regression, or a spot VA where the
   pdata label differs from `pdata.py fn` would refute the hypothesis.
