## Question

In static EU 2011 firmware, what signal triggers the reversing camera, at which
VA is the check, and which module actually sends the `VIN1:` IOCTLs that
`CameraCC` is credited with?

## Hypothesis

`CameraCC.dll` opens `VIN1:` and sends `IOCTL_VIN_SET_*` on the reverse signal.

**Falsifier:** if `CameraCC` holds no `VIN1:`/`LCD1:`/`CEN1:`/`GPI1:` string and
no `0x8006xxxx`/`0x800d20xx` IOCTL literal in any readable or decompressed
section, and another module (`SystemCC.dll`) holds all of them, then `CameraCC`
is not the sender and the hypothesis is wrong.

## Interpretation

- **FACT:** `CameraCC.dll` contains no `VIN1:`/`LCD1:`/`CEN1:`/`GPI1:` string
  and no `0x80062000`-family or `0x800d20xx` IOCTL word in any section,
  compressed ones decoded.
- **FACT:** `SystemCC.dll` contains all eight IOCTL codes as referenced pool
  words and all nine corresponding error strings, in small wrappers near
  `0x02a82c40–0x02a83300`, and opens `VIN1:` (`0x02a73a30`) and `CEN1:`
  (`0x02a73b90`).
- **FACT:** `navdrv.dll` creates a kernel event named `EVENT_NAV_SENSOR_BACK`
  (`0x039e13a0`) in `fn 0x039e3a34`, reads it in `fn 0x039e3cec` (case `+124`),
  and its sensor decode `fn 0x039e6690` raises it from bit 0 of the word that
  `fn 0x039e6a24` takes from `*(*(obj+44)) & 7`.
- **FACT:** `VIN.dll` is the `VIN1:` driver and takes the `CEN` side of the
  protocol (`0x800d2054` in `fn 0x039564c0`); it has no `0x80062xxx` literal.
- **OBSERVED:** bit 0 is a "sensor" bit in `navdrv`; the `GPI1:` code in the
  driver is GPS antenna only, so the physical wire (CAN vs GPIO) is not in the
  readable code.
- **HYPOTHESIS:** the reverse camera is started by this event (or the
  equivalent `VIN1:` enable sequence `SystemCC` issues), presented by
  `CameraCC` through the COM/IPC path.
- **UNKNOWN:** the argument values for the `VIN`/`CEN` IOCTLs, which image
  consumer acts on `EVENT_NAV_SENSOR_BACK`, and the CEN/`CameraCC` message
  numbers.

## Conclusion

The M1.44 `Done when` is met with a correction: the page names the trigger —
`EVENT_NAV_SENSOR_BACK`, created at `navdrv` `fn 0x039e3a34` (literal
`0x039e13a0` at `0x039e3a80`), read by `fn 0x039e3cec` (case `+124` →
`0x039e3d28`), raised from bit 0 of the sensor word in `fn 0x039e6690` — and
lists the `VIN1:` IOCTLs, but those IOCTLs are sent by **`SystemCC.dll`**
(eight wrappers + strings, table above), not by `CameraCC.dll`. `CameraCC` is
the COM/overlay client: it has no device string and no IOCTL word anywhere in
the module. `docs/firmware/camera.md` was written from this record and
`docs/research/claims.md` gained C-6460…C-6469 plus C-6750, which replaces the
retracted C-6460 with a coverage statement that names the decoder actually
used. (The first replacement used the ID C-6470, which the M1.45 merge had
already claimed for the telematics block; C-6750 is the free ID it moved to.)
