## Question

What do the nine head-unit Bluetooth modules do, how do they call each other, what is the paired/connected device data model, where does the limit that hurts with two phones live, and did the 2014/2016 builds change it?

## Hypothesis

The paired-device list is a fixed-size store in our own code (`BT_DB.dll`), so the two-phone limit is a **policy in code** (one active connection, last-connected wins) rather than a module-firmware HCI error; the radio firmware (`BT_FW.dll` / `BtUpdate.exe`) is unchanged across the four builds. **Falsifier:** if no device-count immediate can be tied to a code VA in our modules, or if the limit is enforced only by the module (HCI error), the "policy in code" hypothesis is refuted and the verdict must be `unknown` or `module firmware`.

### 3. Controls

**Positive:**
- `cerom.py exports BT_ENG.dll` prints the mangled C++ engine names (`DeviceManagementEngine`, `DunEngine`, `PhonebookEngine`, `TelEngine`, `AudioEngine`), proving the export scan sees the engine layer.
- `cerom.py imports BT_ENG.dll` prints 21 `BT_DB!Bt_*` slots, proving cross-module import resolution works.
- `pdata.py table BT_DB.dll` returns `96 records`, proving function starts are available before any `sh4dis` constant claim.
- `ce_strfind.py 'BTA1:'` finds the UTF-16LE device string in `BT_ENG.dll` sec0, proving the registry device-instance view is reachable.

**Negative:**
- A count read only from a string (`BTA1:`–`BTA9:`) is not evidence: no device-count claim is made from those strings alone.
- `va_class.py 0x01e050f8` reports `OUTSIDE no section` (a BSS/heap global, not a stored constant), so it is not cited as a configured constant.
- `sh4literal.py find 0x9 0x8 0x10` in BT_DB sec0 reports 0 referenced pool words for each, so no paired-device count is claimed from a pool word.
- A `module firmware` verdict would require an HCI error from the module; none is found in our code, so it is **not** claimed.

### 5. Falsifier

If the device-count constants cannot be tied to a code immediate with a VA, or if every apparent limit resolves to IAT/BSS, the "policy in code" hypothesis is refuted and the verdict must be `unknown`. If 2014/2016 module sizes were identical to 2011 on the stack above `BT_FW`, the "builds differ above the firmware" expectation would be refuted (negative result still valid).

`BT_DB.dll` (VA `0x032f0000`, sec0 exec `0x032f1000`):

- `Bt_PairedDeviceList_Size` (export rva `0x3170` → VA `0x032f3170`) tail-jumps to helper `0x032f1330` (pool `0x032f3198`); `Bt_PairedDeviceList_Erase`/`Clear` tail-jump to `0x032f2898`.
- `0x032f1350` (`sh4dis`, count 10): `e305 mov #5,r3` then `3326 cmp/hi r2,r3`; loop upper bound `r2 ∈ [0,5]`, i.e. **six iterations** (`cmp/hi` loops while `r2 <= 5`). Body at `0x032f1358`–`0x032f1364` does `mov #1,r3; shld r2,r3; and r1,r3; tst r3,r3` — a one-bit-per-index membership test against a 32-bit word.
- `Bt_PairedDeviceList_Add` (export rva `0x319c` → VA `0x032f319c`) calls impl `0x032f27e8`; the paired-list insert helper `0x032f1384` at `0x032f13b0` loads `mov.w @(...),r7 ; [0x032f146c]=0x021c` and at `0x032f13bc` `cmp/hi r6,r7`, the same bounded bit-slot loop.
- `Bt_DeviceInfo_GetCurrentConnectedId` (rva `0x3044` → VA `0x032f3044`) tail-jumps to `0x032f2904`; at `0x032f291e`/`0x032f2922`/`0x032f2926` it compares the profile id against `2`, `4`, `6`, and at `0x032f2942` sets `mov #6,r5` — profile indexes are 1..6, with 2/4/6 treated specially. All exported `Bt_*` list functions add `0x24` (`36`) to the database handle before use (`add #36,r4` at `0x032f3064`, `0x032f3038`, `0x032f3122`, `0x032f3190`), so the per-device info block is 36 bytes and the paired-list slot uses a 32-bit bitmask.
- `Bt_OpenDatabase` (rva `0x2f7c` → VA `0x032f2f7c`) reads global `0x01e050f8` as a handle; `va_class.py 0x01e050f8` → `OUTSIDE no section` (BSS). `sh4literal.py find 0x9 0x8 0x10` → `referenced pool words 0` for all three in BT_DB sec0.

`BT_ENG.dll` (VA `0x03240000`, sec0 exec `0x03241000`):

- `?maxEventSource@Engine@Bt@@IBAIXZ` (export rva `0x270cc` → VA `0x032670cc`): `rts / mov #4,r0` — max event sources = **4**.
- `sh4xref --to 0x032450e0` (the UTF-16LE `BTA1:` string, `ce_strfind` hit) → `pool 0x03266710 holds 0x032450e0; load 0x03266498 fn 0x03266464 [pdata]`. `fn 0x03266464` opens `BTA1:`, then a series of profile device names (`0x03245098`, `0x03245074`, `0x03245030`, `0x03244fe8`, `0x03244f90`, `0x03244f28`, `0x03244ee0`, `0x03244e88`, `0x03244e20`, `0x03244e10`) and at `0x03266552`/`0x0326660a`/`0x03266628`/`0x03266644` indexes object slots `66`, `87`, `88`, `89` (`mov #66,r3; shll2 r3`) — one slot per logical BT device/profile.
- `DeviceManagementEngine::connect` (export rva `0x225b8` → VA `0x032625b8`) at `0x0326266c`–`0x03262690` compares a result against `1`, `8`, `9`, `11`, `15` (`cmp/eq`/`cmp/ge`) and branches to error logging; these are engine result codes, not device counts.
- Import table: 21 `BT_DB!Bt_*` slots plus `OSMDLL`, `COREDLL`; `?maxEventSource` and the `*Engine@Bt@@` vtables are the COM-facing layer.

`PhoneBTA.exe` imports `BT_DB!Bt_DeviceInfo_GetLastConnectedId`, `…GetSelectedDeviceId`, `…GetCurrentConnectedId`, `Bt_PairedDeviceList_Size/Retrieve/Update/CollectIdList/CollectDispIdList`, and `BT_WRPENG!` engine-open functions; it also imports `HCXMemory.dll` (the missing import noted in `bt-wire.md`).

Reconnect policy evidence (`BT_ENG.dll`): the pair of calls `Bt_DeviceInfo_GetCurrentConnectedId` / `…GetLastConnectedId` reached from the device-list logger at `fn 0x0325fdc4` prints `%s *** Selected device ID ***`, `%s *** Last connected ID ***` and `%s *** Current connected ID ***` (strings at `0x03241a24`, `0x03241a44`, `0x03241aa0`). Exactly one `CurrentConnectedId` is stored in `BT_DB` (single-value getter), so at most one device is the active connection; selection is by last-connected/selected id, not by a simultaneous multi-phone session.

## Interpretation

- **FACT:** The paired-device list uses a 6-slot membership bitmask: `BT_DB.dll` `fn 0x032f1330` iterates `r2 = 0..5` (`mov #5,r3; cmp/hi r2,r3` at `0x032f1350`) and `fn 0x032f1384` uses the same bound via `mov.w 0x021c` at `0x032f13b0`. So **at most six paired devices** are stored, with the constant `5` (six slots) as a `mov #5` at VA `0x032f1350`.
- **FACT:** The connected device is a single value: `Bt_DeviceInfo_GetCurrentConnectedId` / `GetLastConnectedId` / `GetSelectedDeviceId` are scalar getters; `BT_ENG.dll` `?maxEventSource@Engine@Bt@@IBAIXZ` returns `4` (`mov #4,r0` at `0x032670cc`). So **one device is connected at a time** (per active profile session); the profile id set is 1..6 with 2/4/6 special-cased at `0x032f291e`–`0x032f2942`.
- **OBSERVED:** `BT_MGR.dll` starts nine device instances `BTA1:`–`BTA9:` (M1.39) and `BT_ENG.dll` opens them in `fn 0x03266464`; these are logical per-profile endpoints, not nine simultaneous phones.
- **FACT:** The two-phone verdict is **`policy in code`**: the capacity constant (six paired slots) is a code immediate in `BT_DB.dll` (patchable in principle), and the active device is chosen by the last-connected/selected id in our own `BT_DB`/`BT_ENG`; no HCI error from the module was found that would make this `module firmware`.
- **FACT:** `BT_FW.dll` (49152 B) and `BtUpdate.exe` (46080 B) are byte-size-identical in all four builds; the stack modules above them changed (e.g. `BT_MGR.dll` 438784 → 440320, `PhoneBTA.exe` 697856 → 706560 in 2014/2016). The transport is therefore unchanged across builds.
- **HYPOTHESIS:** The real-world "two phones work badly" symptom follows from the single-active-device policy plus a small paired table: a second phone displaces the first on reconnect, and six paired slots are enough for a family but make the table fill quickly. Not verified on hardware.
- **UNKNOWN:** Whether the radio module firmware (`BtUpdate.exe` payload, V850-class) enforces any additional per-profile concurrency limit; out of scope and not patchable by us. The exact semantic of the 6 mask bits (index vs profile id) and of the special-cased profile ids 2/4/6 is not decoded.

## Conclusion

`docs/firmware/bluetooth.md` was added with the module table, call graph, device-table layout, the six-paired/one-connected constants with VAs, a `policy in code` two-phone verdict, and the 2014/2016 comparison. Claims C-6430–C-6439 record the evidence rows. The paired-device capacity constant is a code immediate in our own `BT_DB.dll` (VA `0x032f1350`), so the patch idea is **not** closed by a module-firmware limit; however no patch was built and the behavior was not tested on hardware.
