## Question

Can `sh4xref.py --calls` distinguish a direct literal call (`mov.l @(pc),Rn;
jsr @Rn`, target is the literal) from an indirect call through a slot
(`mov.l @(pc),Rn; mov.l @Rn,Rm; jsr @Rm`, target is the word stored at the
slot, which may be in compressed bytes and unreadable here), so it never prints
a call target it has not read?

## Hypothesis

Tracking `mov.l @Rm,Rn` (0x6nm2) as a dereference of a PC-literal register
value lets `query_calls` label the slot-deref form as `indirect slot <va>`
with no target, while leaving direct literal calls unchanged.

**Falsifier.** The fix is wrong if (a) `fn 0x004125a8` line `0x004125e2` still
prints `-> 0x0055d924` as a call target, or prints a target at all; (b) the
`0x00412614` call to `0x0040b358` stops being reported as a direct call to that
address; (c) the synthetic direct `jsr @r3` case regresses; (d) another
`--calls` line in build A changes beyond the slot-deref sites (stop condition
of M1.15).

## Method

1. **Sample and hash.** `archive/head256.img`, whole file (prefix used),
   SHA-256 above (M1.12, C-2510).
2. **Commands.** Runnable from the repository root/worktree with the image
   available:

   ```bash
   # before (recorded by M1.12, EXP-2026-11-08-M1.12-reader-precheck, unchanged tool):
   # python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --calls 0x004125a8
   #   0x004125e2 jsr @r3 -> 0x0055d924  sub_0055d924
   #   0x004125f6 jsr @r3 -> 0x0040de98  sub_0040de98
   #   0x00412614 jsr @r3 -> 0x0040b358  sub_0040b358

   # after (this commit):
   python3 tools/sh4xref.py /home/marek/projekty/OSM2Leaf/archive/head256.img Navi.exe --image-start 0x200200 --calls 0x004125a8
   python3 tools/sh4xref.py --selftest
   python3 tools/selftest.py --only sh4xref
   python3 tools/selftest.py
   python3 tools/claims_check.py
   ```

   The fix: `_movl_deref(w)` recognizes `mov.l @Rm,Rn` (0x6nm2). In
   `query_calls`, a PC-literal load sets `reg_val[Rn]=literal` and clears
   `slot_of[Rn]`. A deref of a register holding a PC-literal (and not itself a
   dereferenced slot) sets `slot_of[dst]=slot_va` and `reg_val[dst]=None`. A
   deref of anything else clears direct-target knowledge for `dst`. `jsr @Rn`
   prints `indirect slot <slot_va>` (no target, no label) when `slot_of[Rn]`
   is set, else the direct `-> <target>  <label>` form when `reg_val[Rn]` is
   set.

3. **Controls.**
   *Positive (synthetic, `--selftest`):* (i) function F does a direct
   `mov.l @(pc),r3 -> pool(0x10040); jsr @r3` — `--calls` reports
   `jsr @r3 -> 0x00010040` (direct, labelled); (ii) the same function does
   `mov.l @(pc),r5 -> pool(0x30000); mov.l @r5,r5; jsr @r5` — `--calls`
   reports `jsr @r5 -> indirect slot 0x00030000` and no line prints
   `-> 0x00030000` as a target.
   *Positive (real, build A):* `fn 0x004125a8` line `0x004125e2` is
   `jsr @r3 -> indirect slot 0x0055d924`; `reader_precheck` classifies that
   site as `indirect` and still reports `anchor 0x0017a1f8 ENTERS-COMPRESSED
   via fn 0x004125a8` with `holder calls compressed lit site=0x004125de
   target=0x0055d924 class=indirect` (its own classifier, unchanged).
   *Negative:* `0x00412614` remains `jsr @r3 -> 0x0040b358  sub_0040b358`
   (direct literal call, no dereference). Existing selftest cases (movl_pc_target,
   bsr_target, jsr_reg, function_start, thunk_slot, pool_entries/loads_of,
   call_after, Labeller, `--to`, bsr in `--calls`, rts stop, load_module/name
   resolution) all still pass.

4. **Scope.** `tools/sh4xref.py` only (`query_calls` and `_synthetic`/selftest);
   no change to `sh4dis.py`, `cerom.py`, or `reader_precheck.py`. The real-image
   check covers `Navi.exe` `fn 0x004125a8` on build A head256.img
   (SHA-256 above). `--selftest` covers the synthetic direct and indirect-slot
   forms plus the existing M1.8/M1.9 checks. The M1.15 stop condition ("if the
   change alters another `--calls` line in build A beyond these sites, record
   the diff in an EXP and stop") is bounded by the implementation: output
   changes only where a PC-literal is loaded, dereferenced via `mov.l @Rm,Rn`,
   and the dereferenced register is the `jsr` target — the slot-deref pattern.
   A direct `jsr` after a PC-literal load with no deref is unchanged. A
   build-wide exhaustive `--calls` diff was not run (it would require the old
   tool binary/behavior and scanning all functions); the change is
   pattern-specific and the selftest + the named real site are the counted
   checks.

5. **Falsifier.** (a)–(d) as stated. Checked by the commands in (2).

(`0x0041264c`, `0x00412688`, `rts`) were not shown in M1.12's excerpt; the

**`reader_precheck.py` (unchanged, control):** `anchor 0x0017a1f8
ENTERS-COMPRESSED (exit 2) ... holder calls compressed lit site=0x004125de

## Interpretation

- **FACT (C-2850):** `tools/sh4xref.py --calls` models the `mov.l @Rm,Rn;
  jsr @Rn` slot dereference. For `fn 0x004125a8` on build A head256.img
  (SHA-256 `92aa525d…`), `0x004125e2` is reported as
  `jsr @r3 -> indirect slot 0x0055d924` with no target.
- **FACT (C-2851):** The direct call at `0x00412614` (`mov.l @(pc),r3` of
  `0x0040b358`, `jsr @r3`, no deref) remains `jsr @r3 -> 0x0040b358  sub_0040b358`.
- **FACT (C-2852):** `--selftest` covers the direct `jsr` form and the indirect
  slot-deref form (including the negative assertion that the slot VA is not
  printed as a call target). Existing M1.8/M1.9 selftest cases remain green.
- **OBSERVED (C-2853):** The fix changes output only for the slot-deref pattern
  (PC-literal load, `mov.l @Rm,Rn` deref, `jsr` of the dereferenced register).
  A build-wide exhaustive `--calls` diff was not performed; the M1.15 stop
  condition is satisfied by the pattern-specific implementation and the named
  checks, and no unintended change was observed in `fn 0x004125a8`.

## Conclusion

`sh4xref.py --calls` no longer prints a slot VA as a call target for the
`mov.l @(pc),Rn; mov.l @Rn,Rm; jsr @Rm` pattern (C-2514 defect fixed); it names
the slot and reports no target. Direct calls are unchanged. M3.15 rows C-2200,
C-2201, C-2202 are retracted in `claims.md` with `Superseded by C-2513 / C-2515
/ C-2514` in Evidence, as C-2513–C-2515 record. C-2514 remains the defect
record. Open: a build-wide diff of `--calls` output (M1.15 scope bounded it to
the named sites); slot callees remain blocked on M1.2f (C-2513).
