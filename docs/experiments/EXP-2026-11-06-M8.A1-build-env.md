## Question

Can the full-system emulation work (TODO M8) start from a reproducible,
pinned QEMU build environment that lives **outside** the repository, applies
the project's out-of-tree machine patches, builds only `sh4-softmmu`, and
fails loudly and testably when the `ze0` machine is missing — without any
network access during tests and without vendoring a single QEMU byte?

## Hypothesis

Yes. QEMU 8.2.7 is the 8.2 LTS bugfix release the M8 notes already assume
("stock QEMU 8.2"), its release tarball is published with a stable URL, and
`configure --target-list=sh4-softmmu --disable-werror --disable-docs` is
enough to produce `qemu-system-sh4` on this host. The only step a test cannot
do offline is the fetch, so the script must separate "plan" (`--dry-run`) from
"execute", verify the tarball's size and SHA-256, and test the `-M ze0` gate
with a fake binary — including a negative control whose machine list lacks
`ze0`.

## Method

Exact commands, in order.

```bash
cd /home/krzesimir/PycharmProjects/OSM2Leaf.session-ZMxuBT

# 1. syntax
bash -n tools/qemu-ze0/build.sh

# 2. offline self-test: argument parsing, plan, refusals, fake -M ze0 gate
bash tools/qemu-ze0/build.sh --selftest

# 3. the plan, in a scratch cache that must stay empty
mkdir -p /tmp/opencode/ze0-dryrun/patches-empty
bash tools/qemu-ze0/build.sh --dry-run \
    --srcdir /tmp/opencode/ze0-dryrun/cache \
    --patch-dir /tmp/opencode/ze0-dryrun/patches-empty --jobs 4

# 4. real path, with the pinned tarball pre-seeded so the run itself uses no
#    network (verify -> extract -> configure -> make -> -M ze0 gate)
mkdir -p /tmp/opencode/ze0-final/patches-empty
cp /tmp/opencode/qemu-pin/qemu-8.2.7.tar.xz /tmp/opencode/ze0-final/
bash tools/qemu-ze0/build.sh --srcdir /tmp/opencode/ze0-final \
    --patch-dir /tmp/opencode/ze0-final/patches-empty --jobs 12; echo "rc=$?"

# 5. independent control: the same configure line, stock tree, no patches
cd /tmp/opencode/qemu-buildtest/build
../../qemu-8.2.7/configure --target-list=sh4-softmmu --disable-werror --disable-docs
make -j12
./qemu-system-sh4 -M help | grep -E '(^|[[:space:]])ze0([[:space:]]|$)'

# 6. repository self-test registry, for the tail
cd /home/krzesimir/PycharmProjects/OSM2Leaf.session-ZMxuBT
python3 tools/selftest.py
```

The tarball came from a single one-off download while writing this EXP
(URL and SHA-256 in Inputs); steps 4–6 reused it, so no test performed a
network transfer. `--patch-dir` is pointed at an empty directory because a
parallel M8 task populates `tools/qemu-ze0/patches/` in the shared worktree.

## Interpretation

- **FACT:** QEMU 8.2.7 accepts `--target-list=sh4-softmmu --disable-werror
  --disable-docs` and builds `qemu-system-sh4` with the host toolchain
  (meson 1.10.1, ninja 1.13.2, Python 3.14.4) in 2m33s (153 s) on 12 cores.
  The tarball's SHA-256 and size are pinned in `build.sh` and checked on
  every real run, including a pre-seeded tarball.
- **FACT:** the offline `--selftest` proves the parts that do not need the
  network: option parsing and its error codes, the root refusal (fake `id`),
  the in-repository `--srcdir` refusal, the exact command plan (tarball,
  sha256, `configure --target-list=sh4-softmmu --disable-werror`, `make -jN`,
  `-M help`), the git fallback plan, that `--dry-run` leaves the sandbox,
  `HOME` and `tools/qemu-ze0` byte-for-byte unchanged with the cache still
  absent, that the `-M ze0` gate accepts a list containing `ze0`, and that it
  **fails** on a list without `ze0` (negative control) and on a missing
  binary.
- **FACT:** the network-needed path exits 3 with a `NETWORK NEEDED` block
  naming the tarball and git URLs, and leaves no partial tarball; a
  `file://` mirror is used so the test itself cannot reach the network.
- **OBSERVED:** on a stock 8.2.7 build the `-M ze0` gate fails, as intended:
  the machine is M8.A2's `hw/sh4/ze0.c` patch, and M8.A1 ships no machine
  patch of its own. M8.A1's own done-condition (`-M ze0` lists the machine)
  therefore cannot be met by the environment alone; it is met as soon as the
  first machine patch lands and `--force` re-runs the same script.
- **HYPOTHESIS:** a full build from the unseeded path (download included)
  behaves the same; only the fetch and the `tar -x` differ, both exercised by
  the dry-run plan and by the seeded run's real extraction. It was not
  re-run end-to-end with a live download during this task beyond the one
  tarball fetch used for the pin.
- **UNKNOWN:** whether any M8.A2+ patch needs extra configure options (e.g.
  `--enable-debug`); if it does, the patch's task adds the flag here and the
  selftest plan check is updated in the same commit.
