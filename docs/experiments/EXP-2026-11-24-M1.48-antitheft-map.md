# EXP-2026-11-24-M1.48: Static map of the antitheft (IMMO / `SECURE`) path

- **Status:** done
- **Date:** 2026-11-24
- **Sample:** `archive/head256.img` (EU2011 apps, build A) and
  `archive/us256.img` (US2011, build B); full-file SHA-256 below.
- **Tools:** Python 3 (stdlib only); repo tools `tools/cerom.py`,
  `tools/ce_strfind.py`, `tools/sh4xref.py`, `tools/sh4dis.py`,
  `tools/antitheft_map.py` (new, `--selftest`), `tools/board.py`.
  No recompression; `tools/zlibinfo.py` not applicable.
- **Claims:** C-10140–C-10149
- **Supersedes:** none
- **Superseded by:** none

## Question

Who decides the IMMO/SECURE lock (audio MCU, SH-4, or car BCM), what is
compared (PROD `+0xA0` code / `+0x193` flag), over which link, and what each
waiting process refuses while locked — with the VA of each send/receive, or a
statement that the comparison is not in SH-4 code.

## Hypothesis

The SH-4 only relays an iNai/ANT protocol over `SCI1:` and waits on
`ANTITHEFT_UNLOCKOK`; the comparison happens on the audio MCU, so no SH-4
code comparison of the IMMO code exists in the firmware image. The task allows
this as a valid "Done when" outcome.

**Falsifier:** the task's "VA per send/receive" fails if a cited VA does not
resolve through `cerom.py` to a named module; the audio-MCU hypothesis is
refuted if an SH-4 routine is found that reads PROD `+0xA0`/`+0x193` and
compares them. A "string absent" claim is refuted by a different encoding or
image start (ASCII 0 hits is not absence).

## Method

1. **Sample and hash.** Full files as hashed by `sha256sum` above; the tools
   read at most 128 MiB and hash that range (two different digests, both
   quoted above). Build A = apps, build B = kernel/updaters.
2. **Commands.** Runnable as written from the repo root:

```bash
python3 tools/antitheft_map.py --selftest
python3 tools/cerom.py --selftest
python3 tools/ce_strfind.py --selftest
python3 tools/cerom.py --image-start 0x200200 archive/head256.img exports AntitheftCC.dll
python3 tools/ce_strfind.py --image-start 0x200200 archive/head256.img --encoding utf-16le ANT_RCV_SECURITY_LOCK
python3 tools/ce_strfind.py --image-start 0x3e00200 archive/us256.img --encoding utf-16le ANT_RCV_SECURITY_LOCK
python3 tools/antitheft_map.py --image-start 0x3e00200 archive/us256.img
python3 tools/antitheft_map.py --image-start 0x200200 archive/head256.img
python3 tools/cerom.py --image-start 0x3e00200 archive/us256.img exports commondll.dll | grep -i Anti
python3 tools/sh4xref.py --image-start 0x3e00200 archive/us256.img commondll.dll --to 0x3c015c8
python3 tools/sh4xref.py --image-start 0x3e00200 archive/us256.img UpdateMng.exe --calls 0x189e8
python3 -c "d=open('archive/head256.img','rb').read(); print('ascii',d.count(b'ANT_RCV_SECURITY_LOCK'),'utf16le',d.count('ANT_RCV_SECURITY_LOCK'.encode('utf-16-le')))"
```

3. **Controls.** *Positive:* `cerom.py exports AntitheftCC.dll` prints 4
   exports; `ce_strfind --encoding utf-16le ANT_RCV_SECURITY_LOCK` prints
   6 UTF-16LE copies in each full image and hits the named modules (one needle
   per run); all three `--selftest` runs are green. *Negative:* the same
   `ce_strfind` with default `--encoding ascii` prints `hits 0` (the M8.E1
   encoding trap, an expected failure), and swapping `--image-start` to
   `0x200200` for a build-B string lands in a different module set.
4. **Scope.** Build A (149 modules EU) and build B (91 modules) executable
   sections; `ce_strfind` lists compressed `.data` sections as `UNSUPPORTED`
   and excludes them (not "all"). The ANT protocol strings were found in build
   B (`anwdrv.dll`, `UpdateMng.exe`, `commondll.dll`, `AppLaunch.dll`) and in
   build A as waiter event names (`PhoneBTA.exe`, `Telema.exe`, `Usb.exe`) plus
   HMI ASCII strings (`ScreenStateCC.dll`, `EvNoticeCC.dll`, `InfoBarCC.dll`).
   `AntitheftCC.dll` is 98 816 B, load `0x8d5bf000`, vbase `0x03600000`.
   The PROD record of a real unit (M6.19) is not on this machine; C-5202 is
   quoted from the existing claim, not re-derived. Build C VAs not derived.
5. **Falsifier.** A cited VA that resolves to the wrong module, a `hits 0`
   claim later refuted by UTF-16LE, or an SH-4 IMMO-code comparison would
   refute the claims. The negative mutation in the EXP review round is
   reported in `docs/experiments/` review notes if it fails.

## Interpretation

- **FACT:** Every cited send/receive name VA resolves through `cerom.py` to a
  named module (build B `anwdrv.dll`, `UpdateMng.exe`, `commondll.dll`,
  `AppLaunch.dll`, `VIN.dll`; build A waiters). The precheck reproduces with
  `--image-start 0x200200 … exports AntitheftCC.dll` (4 exports) and, for the
  string, with build B + UTF-16LE.
- **FACT:** The SH-4 side receives `ANT_RCV_*` and sends `ANT_SEND_SEC_*`,
  calls `CApi_AntitheftUnlock` (import slot `0x220d0`) and waits on
  `ANTITHEFT_UNLOCKOK`. The link is iNai/`SCI1:` (`anwdrv.md`).
- **OBSERVED:** `VIN.dll`/`anwdrv.dll`/`AppLaunch.dll` import
  `CApi_ReadPrivateArea`, the API over the PROD private area that holds the
  IMMO code and flag.
- **HYPOTHESIS:** The code comparison happens on the audio MCU, not in SH-4
  code (no SH-4 routine reading `+0xA0`/`+0x193` was found; the audio MCU code
  is not in this image).
- **UNKNOWN:** Whether the external `TEST_B1`/CAN bypass (C-082) is sufficient;
  the behaviour of a unit moved to another car; the code and flag values of a
  real unit beyond the quoted C-5202.

collided with M1.45's rows; the fresh range was used. No L3/L4/L5 execution
