# EXP-2026-11-06-M2.12: `HDD_CHK.ATT` CRC16 attestation (`SilentAuthenticate`)

- **Status:** done
- **Date:** 2026-11-06

  `LEAF_2011-2012_QSD-309-101_navi158_eu.img`
- **SHA-256 (IMG256):** `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`

- **Superseded by:** none

## Question

Does the unit require a CRC16 attestation file `HDD_CHK.ATT` on the card, how
is the attestation computed (CRC16 polynomial/seed and byte range), and is it
checked by `Navi.exe` at boot or only by the updater (`MapUpdate.exe`)?

## Hypothesis

`MapUpdate.exe` reads `HDD_CHK.ATT` and attests it with `CApi_MakeCRC16`
(C-775, C-778, EXP-2026-11-06-M2.6). The boot-time `Navi.exe` HDD_INFO path
(M2.11) may or may not also check it; a string search with a positive control
distinguishes the cases.

### `SilentAuthenticate` (`MapUpdate.exe` B, VA `0x0001c210`)

Module VA `0x0001c210` (vbase `0x10000`, sec1) = physical `0x8854f210` = file
`0x434f410`. `sh4xref --to 0x0001c210` finds two literal-pool refs from
`fn 0x0001ccfc` (loads at `0x1cdd2`/`0x1ce44`, pool `0x1cf1c`) and one from
`fn 0x0001cee8` (load `0x1d000`, pool `0x1d058`).

`sh4xref --calls 0x0001c210` shows: `COREDLL!#168` CreateFileW (`0x1c26a`,
`0x1c27c`), `COREDLL!#516` GetLastError (`0x1c294`/`3aa`/`3c6`),
`COREDLL!#545` logging (`0x1c29e`/`37c`/`394`/`3d0`), `COREDLL!#1047` memset
(`0x1c2b4`), `COREDLL!#170` ReadFile (`0x1c2c6`), `COREDLL!#553` CloseHandle
(`0x1c2ce`), `sub_00019eb4` hex-nibble converter (`0x1c320`/`32a`),
`sub_00021104` = `commondll!CApi_MakeCRC16` IAT slot (`0x1c350`), and
`sub_0001e3f4` final comparison (`0x1c360`).

Disassembly (SH-4 LE, capstone): signature `SilentAuthenticate(ctx=r8, flag=r11)`
(saved from r4/r5). `flag` (`tst r11,r11`, `0x1c22c`) selects the file: nonzero
→ `\SystemSD\HDD_CHK.ATT` (pool `0x1c3f4 = 0x00013cc4`) and context code
`108` (`r13`); zero → `\UserSD\HDD_CHK.ATT` (pool `0x1c3fc = 0x00013c9c`) and
`107`. Opens with `CreateFileW(path, GENERIC_READ, share=1, OPEN_EXISTING=3)`;
on failure records error (GetLastError/log) and returns 0.

On success: `memset(ctx+0x11a, 0, 256)` (`r10 = r8 + 0x11a`, `0x1c2a6-2b6`);
`ReadFile(handle, ctx+0x11a, 0x80, &bytesRead@r14+4, 0)` (`0x1c2ba-2c8`);
`CloseHandle`. Requires `bytesRead == 0x80` (`0x1c2d8-2de`, compares
`@(4,r14)` to `0x80`).

Decodes an attestation field: source `ctx+120` (`r9 = r8; add #120`), dest
`r14+8` (16 bytes zeroed). Loop 10 times (`r13=10`, `0x1c31a-344`): for each
pair of bytes at source, calls `sub_00019eb4(ctx, char)` to convert each hex
ASCII char to a nibble (returns low nibble for `'0'`-`'9'`/high nibble `0x30`,
`10-15` for `'A'`-`'F'`/high nibble `0x40`, `0x19eb4-9f0a`) and stores
`(hi<<4)|lo` → 10 decoded bytes from 20 hex chars.

Computes CRC16: `r4 = r14+8` (decoded), `r5 = 10` (`0x1c348 e908 mov #8,r9;
0x1c34a 39ec add r14,r9`), calls `CApi_MakeCRC16` via IAT `0x00021104`
(pool `0x1c41c`, `0x1c346-352`). If `(CRC16_result & 0xffff) != 0` it takes an
error path (`0x1c356-358 bf 0x1c39c`). If CRC16 is 0 it calls
`sub_0001e3f4(file_buf=ctx+0x11a, decoded=r14+8, bytesRead=0x80)`
(`0x1c35a-362`); returns `1` on success (`memcmp-like` result 0,
`0x1c366-36a`), else error.

`sub_0001e3f4` (VA `0x0001e3f4`) is not a plain byte memcmp: it returns `1`
immediately if `len > 0xc0` (`0x1e40a-414`, `r3=0xc0`), otherwise performs a
multi-step check calling imports at `0x1e610/614/618/61c` and copying an 8-byte
struct; its exact verification semantics were not fully decoded here.

Callers: `fn 0x0001ccfc` calls `SilentAuthenticate(ctx->+8, 1)` at `0x1cdd4`
(SystemSD) and `SilentAuthenticate(ctx->+8, 0)` at `0x1ce46` (UserSD);
`fn 0x0001cee8` calls `SilentAuthenticate(ctx->+8, 0)` at `0x1d002`.

### `CApi_MakeCRC16` (`commondll.dll`, image B)

`commondll.dll` (B `--image-start 0x3e00200`): export `CApi_MakeCRC16` rva
`0x00003750` (ordinal 72), `CApi_MakeCRC32` rva `0x00003778`. sec1
`realaddr 0x03c01000 dataptr 0x88322000 file 0x4122200` (uncompressed).

Wrapper at `0x03c03750` (file `0x4124950`): if global `*0x03c03770` is NULL
returns 0; else loads `obj+4`, takes vtable/function pointer at `obj->+4 + 76`,
and tail-calls `jmp @0x03c04214` with `(ctx, buf=r5_original, len=r6_original)`.

Implementation at `0x03c04214` (file `0x4125414`), args `(r4 unused, r5=buf,
r6=len)`: `crc16 = 0` (seed). For each byte `b = buf[i]`: `crc = (crc ^ b) & 0xffff`;
repeat 8 times: if `(crc & 1)` then `crc = (crc >> 1) ^ 0x8408` else
`crc >>= 1`. Returns `crc` (16-bit). Polynomial constant read from literal at
`0x03c04254` = `0x00008408` (reflected polynomial). This is a bitwise, LSB-first
(reflected) CRC-16 over `len` bytes: seed `0x0000`, polynomial `0x1021` in
normal form / reflected constant `0x8408` (CRC-16/CCITT reflected / KERMIT
parameters: init 0, refin true, refout true, xorout 0), no final XOR.

## Interpretation

- **FACT (static, IMG256):** `HDD_CHK.ATT` (UTF-16LE path components) appears
  only in image B / B copy, inside `MapUpdate.exe` sec1; it does not appear in
  image A (`Navi.exe`) or image C. Positive control `HDD_INFO.TXT` is found in
  `Navi.exe`'s A segment, so the absence in Navi is not a search failure.
- **FACT (static):** `MapUpdate.exe!SilentAuthenticate` (B, VA `0x0001c210`)
  opens `\SystemSD\HDD_CHK.ATT` or `\UserSD\HDD_CHK.ATT` (flag-selected),
  reads `0x80` bytes, decodes 20 hex chars from `ctx+120` into 10 bytes,
  requires `CApi_MakeCRC16(decoded, 10) == 0` (low 16 bits), then verifies via
  `sub_0001e3f4(file_buf, decoded, 0x80)`. It is called from
  `0x0001ccfc`/`0x0001cee8` for both SystemSD and UserSD.
- **FACT (static):** `commondll.dll!CApi_MakeCRC16` dispatches to
  `0x03c04214`, a bitwise CRC-16: seed `0x0000`, reflected constant `0x8408`
  (CRC-16/CCITT reflected / KERMIT form, poly `0x1021` normal), no final XOR,
  computed over the `len` argument bytes.
- **OBSERVED:** the 20-hex-char field is taken from `ctx+120` (a `MapUpdate`
  context field), not parsed out of the 128-byte file buffer in the visible
  code path; `sub_0001e3f4` (a non-trivial check, not a plain memcmp) performs
  the final comparison against the 128-byte file. The on-disk `HDD_CHK.ATT`
  layout and which bytes constitute the authenticated range beyond "128 bytes
  read" are therefore **not fully determined** from static disassembly alone.
- **HYPOTHESIS:** `HDD_CHK.ATT` is a 128-byte (or ≥128-byte, 0x80 read)
  attestation record whose validity is tied to a 10-byte/20-hex-char value held
  in the updater context (`ctx+120`) with a CRC-16/KERMIT residue of 0; the
  final acceptance couples that value to the file contents via `sub_0001e3f4`.
- **UNKNOWN:** exact `HDD_CHK.ATT` byte layout/fields, the source of `ctx+120`,
  and the full semantics of `sub_0001e3f4` (it may bind the 10-byte value to
  the 128-byte record cryptographically or structurally). No `Navi.exe` boot-time
  check was found; a dynamic/boot trace remains the only way to prove a
  boot-time absence beyond the static string/reference evidence.

## Conclusion

`HDD_CHK.ATT` is read by **`MapUpdate.exe`** (image B) via `SilentAuthenticate`
for both `\SystemSD` and `\UserSD`; **no reference in `Navi.exe` (A) or image C**
was found (positive control `HDD_INFO.TXT` present in Navi). The CRC16 is
`CApi_MakeCRC16` (`commondll.dll`) = CRC-16/CCITT reflected (KERMIT form):
seed `0x0000`, poly constant `0x8408` (0x1021 normal), bitwise reflected, no
final XOR, computed over 10 decoded bytes from a 20-hex-char context field and
required to yield 0; `sub_0001e3f4` then verifies the 128-byte file against that
decoded value. `docs/format/validation.md` updated; claims C-1870–C-1879 added.
