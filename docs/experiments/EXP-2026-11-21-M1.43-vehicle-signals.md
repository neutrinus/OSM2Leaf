# EXP-2026-11-21-M1.43: vehicle CAN signals and the drive-computer formulas (EU 2011)

- **Status:** done (static, EU 2011 build A; nothing run on hardware)
- **Date:** 2026-11-21
- **Sample:** `archive/head256.img` — the EU 2011 head, **268 435 456 bytes**,
  full SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (the repo-wide canonical hash; `sha256sum archive/head256.img`; vendor data,
  not committed). `tools/ce_strfind.py` reads only its first 128 MiB
  (`READ_LIMIT = 128 << 20`) and so prints a *different*, 128 MiB hash
  `d3e5eac9cb5b4cbd…` — that is not the file hash. Build A at image start
  `0x200200`, build B at `0x3e00200`.
- **Tools:** python3 3.13, stdlib only: `tools/cerom.py`, `tools/ce_strfind.py`,
  `tools/nk_decomp.py`, `tools/sh4xref.py`, `tools/sh4dis.py`,
  `tools/sh4fpu.py` (all in-repo). `tools/sh4dis.py` has **no** FPU decode and
  prints the formatter's FPU halfwords as `.word 0xf…`; the mnemonics/operands
  in this record are the SH-4 ISA decode of the raw halfword, executed in

## Question

Which CAN signals reach the SH-4 (through `CAN.dll` on `UAT3:`), in what units
and resolution, what consumes them, and what the drive computer does with
them — is the energy-economy value shown rounded from a finer value, or does
the coarse value arrive already rounded?

## Hypothesis

The SH-4 is not a CAN node: `CAN.dll` (build B) is a stream driver on `UAT3:`
and a `VCAN`/`MCAN` microcontroller decodes the frames (C-6413, C-6416).
`Vehicle.exe` subscribes to a fixed set of frames and stores the economy
value as an integer (`%d`), so a finer economy display would be a change in
the stored value, not only the screen. **Falsifier:** a float/finer field for
the economy value in `Vehicle.exe`, or the display formatter multiplying an
already-scaled float, would refute "coarse arrives rounded".

python3 tools/sh4dis.py --image-start 0x200200 archive/head256.img DriveComputerCC.dll \

python3 tools/sh4dis.py --image-start 0x200200 archive/head256.img DriveComputerCC.dll \
    --va 0x02519080 --count 1        # prints .word 0xf462 (raw halfword)

e=_asm_run([0xF462], fr={4:f32_bits(3.0),6:f32_bits(2.0)})     # fmul FR6,FR4

print('0xf463 fdiv FR6,FR4 -> 9.0 ; 0xf462 fmul FR6,FR4 -> 6.0')

# formatter constants (LE doubles in the pool)
python3 - <<'PY'
import struct
b=open('DRV/DriveComputerCC.dll.02511000.bin','rb').read(); base=0x02511000

3. **Controls.**

   *Positive control:* the `CAN.dll` export list must print `CAN_Open …
   CAN_Write`, and the 17-frame block must match `^ *[0-9]+ - .*\[0x…\]$`
   exactly 17 times (`grep -c` prints `17`) — a method that found the CAN
   driver strings but not the frame block would be wrong, so both ends are
   checked.

   *FPU control (H119 lesson):* `tools/sh4dis.py` prints `0xf463`/`0xf462`
   as `.word`; the operation is the ISA decode (`n=4,m=6,sub=3` →
   `fdiv FR6,FR4`) confirmed by executing the halfword in `tools/sh4fpu.py`
   (`90.0/10.0=9.0`, `3.0*2.0=6.0`). Citing `sh4dis.py` alone would mislabel
   the operand registers.

   *Negative control:* the `1.6093` constant at `0x02519138` must **not** be
   loaded by `fn 0x02518f58`; a raw scan for `mov.l @(disp,pc)` halfwords in
   the function finds 0 loads of `0x02519138` and exactly 1 (`0x0251909c`) of
   the `99.9` pool word `0x02519148`. If the scan reported the mile constant
   as used by the economy formatter, the "coarse arrives rounded, metric path"
   reading would be wrong.

4. **Scope.** Build A (apps) sections read whole: `Vehicle.exe` sec0
   (`0x11000`, 405 504 B), `DriveComputerCC.dll` sec0 (`0x02511000`, 65 024 B)

   (`0x03b41000`, 92 160 B). Compressed `INIT` data sections were not decoded
   here (they are `.data`, mostly BSS — AGENTS "Compressed `.data`"); the code
   is all in uncompressed executable sections (build A has 0 compressed code
   sections, C-2128). Not covered: US 2011 / EU 2014 builds, and the VCAN
   microcontroller's own firmware.

5. **Falsifier.** Stated in the Hypothesis; evaluated in Interpretation.

## Interpretation

- **FACT:** the SH-4 holds the vehicle bus behind `CAN.dll` on `UAT3:`, and
  `Vehicle.exe` subscribes to exactly 17 frames (`0x180`…`0x625`); the units
  of speed (`0.1`/`1`/`0.01 km/h`), odometer (`0.001 km`, `0.1 m`),
  acceleration (`0.01 G`) and heading (`0.1 deg`) are literal in the code.
- **OBSERVED:** `electric_economy_avg` and `electric_economy_history[]` are
  `%d` integers in `Vehicle.exe`; the display formatter `fn 0x02518f58`
  converts an integer to float (halfword `0xf02d` = `float FPUL,FR0`) and
  divides (halfword `0xf463` at `0x02519072` = `fdiv FR6,FR4`, executed in
  `tools/sh4fpu.py`) before printing `%2.1f`, clamping at `99.9`.
- **HYPOTHESIS:** the economy value arrives rounded (integer) and the display
  adds no finer data; a finer display or other aggregate is a change in the
  stored `%d` value in `Vehicle.exe`, not just a UI change. The falsifier —
  a finer economy field in `Vehicle.exe` or a formatter that scales an
  already-fine float — was **not** found, so the hypothesis stands pending an
  L3/L4 execution run.
- **UNKNOWN:** the scale factors behind `fdiv`/`fmul` in `fn 0x02518f58` (the
  divisor is a property value, not a literal); the units of torque and
  consumption frames (`0x180`, `0x260`, `0x510`), which carry no unit literal
  in the modules read.

## Conclusion

`docs/firmware/vehicle.md` now carries the 17-frame signal table with
consumers and a dimension, the transport (`CAN.dll` on `UAT3:`, VCAN
microcontroller as the node), the temperature rounding model, and the
drive-computer properties. Done-when holds honestly on **10 of 17** frames
with both a consumer and a unit/flag/enum (scaled `0x280`, `0x5C5`, `0x54A`;
flag/enum `0x354`, `0x355`, `0x35D`, `0x421`, `0x50D`, `0x54B`, `0x60D`); the
other 7 (`0x180`, `0x260`, `0x510`, `0x5B3`, `0x5C0`, `0x5EB`, `0x625`) are
`unknown`/`raw` and are not counted. The energy-economy display scaling is
`DriveComputerCC.dll` `fn 0x02518f58` at `0x02519072` (halfword `0xf463`,
`fdiv FR6,FR4` per the ISA and `tools/sh4fpu.py`; `tools/sh4dis.py` has no FPU
decode and prints `.word 0xf463`), fed by an integer `%d` value from
`Vehicle.exe` and clamped at `99.9`. Claims C-6450–C-6459 record these. Open:
the exact scale factor operands and the torque/consumption frame units.
