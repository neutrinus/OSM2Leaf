## Question

So far `-M ze0` ran the card's kernel image B with image A. That needed
three things:

- an IPL patch that joins A to B and drops modules where their windows
  overlap;
- the unit-flash DLLs copied into A;
- `verinf=`, because B's header has no map code.

The unit runs NK1 from its own flash with A. Does NK1 + A boot without
those workarounds, and what does the EU card hit on the way?

## Hypothesis

NK1 and A were built as a pair, so the XIP chain is all they need.
Falsifier from the task: NK1 + A needs the same module drops as B + A.

## Method

1. **Static, `cerom.py` on NK1 and A.**

   | | NK1 | image A (card) | kernel B (card) |
   | --- | --- | --- | --- |
   | VA | `0x88000000`–`0x882cdae8` | `0x8cae1000`–`0x8e233c88` | `0x88000000`–`0x886e18a4` |
   | `ulRAMEnd` | `0x8cae1000` (= A's start) | | `0x8e600000` |
   | DLL window (`dllfirst`/`dlllast`) | `0x01f9`–`0x0200` | `0x01a7`–`0x01f9` | `0x01bf`–`0x0200` |
   | chain pointer template | `0x882e0000` | | `0xffffffff` |

   NK1's chain pointer (the same `.data` variable `ze0_ipl.py` finds from
   `Looking for rom chain`) already points just past NK1's image. The
   unit's flash has `0xff` there (NAND `0x320000`), so the chain is built
   in RAM at boot. The opening-image buffer is `0x8c6e0000` + `0x401000`,
   which ends at A's start.
2. **Model.**
   - `ze0-0018` adds `nk=FILE`, which loads the kernel image from its own
     file (offset 0) instead of the SD image at `kernel-off`.
   - `ze0_ipl.py --nk FILE` writes the XIPCHAIN block at the address NK1
     names and lowers `ulRAMEnd` below the opening-image buffer. It drops
     no module, and it does not change A's `dllfirst` when the DLL windows
     do not overlap.
   - The debug-string sink is `0x880404c4` in NK1. That is kernel B's
     `0x880404f4` code at `-0x30`, found by its first 24 bytes.
   - No `ze0_aui.py` line is used.
3. **Runs.** All runs use `-M ze0,nk=NK1,flash=DUMP,dbgmsg=0x880404c4` and
   the `--nk` IPL patch.

   | run | card | change on the card (overlay only) |
   | --- | --- | --- |
   | N1 | EU 2011 | `HDD_INFO.TXT` map code `QSD-301-100` (as M8.C1m U4) |
   | N2 | EU 2011 | N1 + image A build name `X210ECNI.158` → `X210NBNI.147` in both `NKOK` headers (`0x200016`, `0x2000016`) |
   | US1 | US 2011 | none |

## Observations

**O1 — The IPL patch shrinks to two lines.** `ze0_ipl.py plan --nk`
prints `kernel modules kept 51/51, image A modules kept 149/149`. The
patch has two lines: the XIPCHAIN block at phys `0x082e0000`, and
`ulRAMEnd` `0x8cae1000` → `0x8c6e0000`.

**O2 — NK1 boots and reads the unit's flash itself.** The kernel prints:

- `Looking for rom chain`;
- `Configuring: … Filesystem pages = 80`;
- the backup-table and SRAM restore lines (`RestoreSystemSramMain`,
  `RestoreFlashArea`);
- `Target ID Code >> 10200212` and `Launcher [Area:20 >> USA]`.

**O3 — NK1 loads image A from the card and checks it.** After the SD unlock:

1. `Load Opening Image Data to 0x8c6e0000 (Size=4198400 Bytes)`.
2. `IOCTL_HAL_GET_2ND_BIN_ADDR`, then `Read NK2. To 8cae1000h`. It reads
   0x800-sector blocks from LBA `0x1001` (card `0x200200`, copy NB00).
3. `Sum Check NK2`.
4. On the EU card (N1): `NK Version Error. Try Next Store Region.` NK1
   tries copy NB01 (LBA `0x10001`) and gets the same result. Then it logs
   `AppLch >> Error Proc<00000042>!!`, starts FailSafe, and logs
   `Error Proc<00000041>` and `EndlessLoop`.

On the unit, this loader is NK1's `AppLaunch.dll`, not an IPL. The
`ipl-patch` preload of A is overwritten.

**O4 — The check compares build names (static).**

- The string `NK Version Error` (AppLaunch.dll `0x03e48878`) is printed
  from fn `0x03e520a8` when fn `0x03e52d80` returns 0.
- Fn `0x03e52d80` asks the kernel for XIP regions 0 and 1
  (`KernelIoControl(0x0101302C)`).
- It copies 12 bytes from region 0's header `+0x20` and 12 bytes from
  region 1's start `-0x200+0x16`, which is the card's `NKOK` header.
- It compares bytes 2–11 of the two names.

| | name |
| --- | --- |
| NK1 (Marek's unit) | `X110NBNI.147` |
| US 2011 card, image A | `X210NBNI.147` |
| EU 2011 card, image A | `X210ECNI.158` |

A failing sum check prints `NK Region Error` (fn `0x03e5411c`) with
`Error Proc 0x41` on the second copy.

**O5 — With the name changed, the EU card boots (N2).**

- `Sum Check NK2` passes, so the name is outside the checksum.
- There is no `Error Proc` and no `VerInf` mismatch line.
- `AppLch >> Finish Launch Threads!` follows, with 32 `Process Create`
  lines.
- AUI controls register from NK1's own registry hives without
  `ze0_aui.py`. Only 2 `Failed initialize control` lines remain (29 in
  M8.C1l J16).
- ScreenState starts in `INI_STARTUP` and handles `SK_OTH_STARTUP`, the
  antitheft checks, `HVAC_CC_ITR_IGN_OFF` and `ANTITHEFT_CC_NTF_COMP_OK`.
- The screenshot shows the opening animation (the EV logo, partly drawn)
  and no map.
- The serial log is dominated by `CInaiProtocol … failed wait response`
  (the audio network, 3 464 lines in 400 s) and `ACM::WaitModule Timeout`.

**O6 — Navi.exe is not created (N2 and US1).**

- The launcher prints `Process Create!!! -> \windows\Navi.exe`, then
  `Launch Process Not Create!!!` for Telema.exe and Navi.exe.
- In fn `0x03e4be74`, that line follows a zero result of `CreateProcessW`
  (thunk `0x03e4b748`).
- The US card (US1) does the same. It passes both region checks with no
  change: build name `X210NBNI.147`, map code `QSD-301-100`.
- So this is an emulator gap, not the region. With kernel B (M8.C1m U4),
  Navi.exe was created and drew the map.

**O7 — The serial log contains the card password.** NK1's SDHC driver
prints the 16 password bytes of `SDHC_Lock_Unlock_Card` in plain text. No
serial log of these runs is committed.

## Interpretation

- The falsifier fails. NK1 + A needs no module drops, no unit-flash DLL
  copies, no `verinf=`, no registry patch and no object-store patch. The
  B + A workarounds were all caused by running the card's updater kernel in
  place of NK1.
- There is a **second region check**, which comes before the map code. NK1
  compares the build name of the card's image A with its own (`NBNI.147`
  on this US unit). A car test of an EU card on this unit therefore needs
  both changes: `HDD_INFO.TXT` (map code, C-8356) and the build name in
  both `NKOK` headers. The emulator runs the unit's own NK1 code, so the
  check is the one the car runs. `card_mapcode.py --from-nk1` now makes both
  changes, and the guide `docs/hardware/eu-card-on-us-unit.md` says so.
- The name check does not mean that EU image A is compatible with US NK1's
  drivers. N2 gets as far as the US card does (US1), and the next blocker
  (Navi.exe) is shared, so nothing yet points to an EU/US difference.
- `NK` and `ECNI`/`NBNI` look like region codes (EC = Europe, NB = North
  America). This is not confirmed.

## Conclusion

`-M ze0,nk=NK1,flash=DUMP` with a two-line IPL patch boots the unit's own
kernel with image A to `Finish Launch Threads`. On the unit, NK1 loads
image A from the card and refuses it unless the card's build name matches
NK1's from the third character on. The EU 2011 card (`ECNI.158`) fails
this check on Marek's US unit (`NBNI.147`) with `Error Proc 0x42`, before
the map-code check. With both the build name and the map code changed, it
boots as far as the US card does: the launcher finishes and the opening
animation shows. Navi.exe's `CreateProcessW` fails on both cards; that is
next.
