# EXP-2026-11-05-M4.1: one RDSTM001 row, decode and round-trip

Task: M4.1. Done when: a decoder with a synthetic test exists, and one real
record round-trips byte-identically.

## Method

- Source: the EU 2011 navi158 SD image, partition 0 (FAT32, 64 KiB clusters,
  label `QSD-309-101`). The directory entry `RDSTM001.DAT` (size 23,335,680,
  first cluster 4249) was read by following the FAT chain. The file was written
  to the scratchpad, not the repository.
- Extracted file SHA-256 `f822044c0aab75327b9fb484e9a4c7c8dd5938b21efaacec0e5b2d8b23ab3e49`,
  which matches docs/format/rdstm.md.
- Decoder: `tools/rdstm_record.py`, 16-byte row, little-endian. Seven fields
  cover all 16 bytes (`id`, `pad2`, `ref`, `src`, `dst`, `code`, `tail`).
  Decode then encode returns the same bytes by construction.

## Results

- Self-test (synthetic, no vendor bytes): `selftest: OK`. Checks: known
  little-endian values, 500 random rows round-trip, a short row is refused.
- Real rows `0x1000`–`0x1099` (10 rows, below the `0x10a0` framing drift):
  `roundtrip_ok=10` of 10.

## What this does not show

- Field meanings are HYPOTHESIS, not decodes. The round-trip proves coverage,
  not semantics. The first rows carry repeated values in `id` and `pad2`
  (`0x0100`) that do not look like a clean node/link pair, so the `src`/`dst`
  reading is unverified (rdstm.md, ranked unknown 3).
- Record size 16 is the scanner default, not a proven size (rdstm.md, C-106).
  The framing drift at `0x10a0` is not explained here.
