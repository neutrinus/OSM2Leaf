## Question

Should the three Leaf generations be three `-M` machine types in the one
11.1.3 out-of-tree patch series, and which devices are shared, parameterised
or new?

## Hypothesis

Same CPU/BSP does not mean the same board: AZE0 shifts the CE RAM window and
kernel layout, so a per-generation subclass is justified, while most devices
stay shared. **Falsifier:** if the EU2014 kernel on unmodified `-M ze0`
printed the same boot log as EU2011, only properties would be needed and no
new machine would be justified.

## Method

### 1. Sample and hash

The four 256 MiB firmware heads listed under Sample; `sha256sum` printed the
hashes. QEMU binary `--version` prints `QEMU emulator version 11.1.3` and
`-M help` lists `ze0`. Scratch: `~/projekty/leafre-work/scratch/m8.g2/`
(deleted after this EXP). No vendor bytes are quoted.

### 2. Commands

```bash
S=~/projekty/leafre-work/scratch/m8.g2
cd /home/marek/projekty/OSM2Leaf.task-m8.g2-cycle10
sha256sum archive/head256.img archive/us256.img archive/eu2014-256.img archive/eu2016-256.img
python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img romhdr
python3 tools/cerom.py --image-start 0x3e00200 archive/eu2014-256.img romhdr
python3 tools/cerom.py --image-start 0x3e00200 archive/eu2016-256.img romhdr
ls tools/qemu-ze0/patches/*.patch | wc -l
Q=~/.cache/qemu-ze0/build/qemu-system-sh4
bash tools/qemu-ze0/run.sh --machine ze0 --image archive/head256.img \
     --timeout 5 --workdir "$S/f0-2011" --qemu "$Q" > "$S/f0-2011.stdout" 2>&1
bash tools/qemu-ze0/run.sh --machine ze0 --image archive/eu2014-256.img \
     --app 0 --timeout 5 --workdir "$S/f0-2014" --qemu "$Q" > "$S/f0-2014.stdout" 2>&1
grep -E '^(kernel|qemu-system-sh4: info|unmodelled|exceptions|final pc)' "$S/f0-"*.stdout
sed '/^unmodelled/,$d' "$S/f0-2011.stdout" | grep -vcE '^(kernel|memmap|run.sh|qemu-system|Windows CE|SH-4|CCR|EH |Version)'
sed '/^unmodelled/,$d' "$S/f0-2014.stdout" | grep -vcE '^(kernel|memmap|run.sh|qemu-system|Windows CE|SH-4|CCR|EH |Version)'
```

The two `sed | grep -vc` counts print **423** (EU2011) and **0** (EU2014)
debug lines on the default `dbgmsg=0x880404f4` sink. The image lengths,
entries, unmodelled-access counts, exception counts and final PCs in the
design doc are printed by `cerom.py … romhdr` and `run.sh`'s summary block in
those stdout files.

### 3. Controls

- **Positive control:** the EU2011 F0 boot prints 423 kernel debug lines,
  maps `0x88000000..0x886e18a4` (7,215,268 B) and ends at PC `0x8803d266`;
  this is the known-good ZE0 baseline on the same binary. The `-M help` line
  `ze0  Nissan Leaf ZE0 navigation unit (SH-4A, research skeleton)` confirms
  the machine is the patched one.
- **Negative control / falsifier:** run the EU2014 kernel on the *unmodified*
  `-M ze0`. If it printed the same boot log as EU2011, no new machine would be
  needed. Measured: it maps `0x88000000..0x8870fb90` (7,404,432 B) with entry
  `0x8800f100`, prints **0** debug lines at `0x880404f4`, has 30 unmodelled
  accesses, 48,628 exceptions and ends at PC `0x8803d796`. The falsifier is
  **not met**, so the new machine is justified.
- **Mandatory negative mutation of the doc's own assertion:** replacing the
  EU2014 `ulRAMStart` cell in `docs/research/qemu-machine-types.md` with the
  EU2011 value `0x89e40000` makes the doc contradict the `cerom.py … romhdr`
  output quoted in §1 (which prints `ulRAMStart 0x8a640000`) and the M8.G1
  table; the mutation was applied once, the contradiction printed, and the
  file restored from a byte-copy before commit. This is a documentation
  assertion, so its gate is the printed command, not a test suite.

### 4. Scope

Design only. One design doc (`docs/research/qemu-machine-types.md`), this EXP,
claim rows C-6950–C-6959 and one new follow-up task (M8.G4) on `TODO.md`.
No QEMU code, no vendor bytes, no card change, no L4/L5 run. Four images read
static; two 5 s F0 boots on the same binary. ZE1 is a decision (no image held,
C-6948), not an implemented machine.

### 5. Falsifier

Falsifier of the plan's premise: EU2014 on unmodified `-M ze0` gives the same
boot log as EU2011 → only properties are needed, no new machine. Not met
(different entry, 0 vs 423 debug lines, different final PC). The follow-up
M8.G4 carries its own falsifier (if an X212 kernel prints debug text at the
EU2011 VA and ends at the EU2011 PC, the subclass is unnecessary).

## Observations

1. All four heads are CE 5.0 / SH-4 with `usCPUType 0x000001a6` and BSP
   `R0P7772A00020S`/`CETUS_SH4` (from M8.G1, C-6940/C-6941).
2. AZE0 build-B `ulRAMStart` is `0x8a640000` (EU2014 and EU2016) vs EU2011's
   `0x89e40000`: +8 MiB; `ulRAMEnd 0x8e600000` is identical. Kernel image
   lengths rise 7,215,268 → 7,404,432 → 7,516,228 B.
3. The unmodified `-M ze0` EU2014 F0 boot reaches an idle kernel but emits no
   debug text on the ZE0 sink, while EU2011 emits 423 lines.
4. The patch series has 30 patches; the machine registers one `TYPE_ZE0_MACHINE`
   with property defaults (no per-generation class today).
5. X212-specific deltas that need a model decision: `FlashManager2.dll` +
   `fmmdrv_05/_07` (C-6943), DirectDraw `ddraw/ddcore/ddhel` (C-6944), USB
   still OHCI with `UsbConMngCC.dll` (C-6945), no `UAT3:` in X212 `CAN.dll`
   (C-6946), no Wi-Fi driver (C-6947).

## Interpretation

- **FACT:** the RAM-window shift (+8 MiB) and kernel layout change (entry
  `0x8800ebd0` → `0x8800f100`) are printed by `cerom.py` and `run.sh`.
- **OBSERVED:** EU2014 on unmodified `-M ze0` prints 0 debug lines and ends
  at PC `0x8803d796`; EU2011 prints 423 and ends at `0x8803d266`.
- **HYPOTHESIS:** most devices in the design doc are shared or parameterised;
  flash, graphics and the vehicle link need new models (unproven without an
  X212 F2–F4 run).
- **UNKNOWN:** X212 dbgmsg VA, INTEVT table, NOR geometry and resolution —
  none printable from the heads with the tools used.

Same CPU/BSP does not imply the same board model. The smallest useful next
step is M8.G4 (X212 RAM/entry/dbgmsg subclass to make F0 observable), not a
rewrite of the existing device patches. ZE1 cannot be planned beyond a class
slot until a Leaf 2 image exists.

## Conclusion

generation table and an ordered list of six follow-up tasks with Done-when
