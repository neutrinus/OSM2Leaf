## Question

In what order should a spare SDHC card be tested on a real unit so that each
run isolates one variable, and what must be recorded for the result to be
interpretable?

## Hypothesis

The offline chain already proves the containers; the remaining unknowns are
the unit's acceptance of (a) the clone and lock, (b) non-factory zlib bytes,
(c) changed content, and (d) a changed tile. A staged plan with a no-op
control separates these.

## Method

No commands were run against a unit. The deliverable was assembled from the
records above and checked against the repo's evidence statuses:

1. Read the M6.3 acceptance line, `minimal-change.md`, `sd-card-layout.md`,
   `us-eu-region.md` and EXP-2026-11-06-M2.8.
2. Ordered the stages by risk: clone → zlib control → content → tile →
   map-code, so a rejection is attributed to the smallest change that
   introduced it.
3. Defined per stage the setup, the exact evidence to capture (screens, error
   text, boot time, map screen), pass/fail and rollback.
4. Split the table into offline-proven facts (with claim IDs) and what only
   the unit can show.
5. Left the `## Recovery` section as a marked placeholder for M6.4.

## Observations

- The documented offline state supports the plan but not any stage result:
  EU `.cmp` round-trip 194/194, US 58/58 (C-505, C-506, C-070); US whole-image
  `cardcheck.py` PASS (EXP-2026-11-05-35); same-length rename validated
  offline (C-146); one-vertex tile and byte-identical tile rebuild validated
  (C-920–C-928, C-943).
- The only card property a clone must reproduce, from static analysis, is the
  CMD42 lock state (C-798, `HYPOTHESIS`); CID/CSD/FAT serial/label checks were
  not found (C-794, C-795). No hardware confirmation exists.
- No per-file checksum was found (C-147, C-162, C-168); the scope of that
  negative excludes NAND and runtime activation, which is exactly what S1–S4
  test.
- `DIFFERENT MAP CODE` has three candidate inputs (line 1, the `0x06000000`
  copy, a NAND record); `hddinfo.py` model M0 is `HYPOTHESIS`, so S4 records
  behaviour instead of predicting acceptance (C-077, C-165; M2.5).
- The US 2011 image is the correct source for a US unit; using the EU sample
  would confound market mismatch with the tested variable.

## Interpretation

- **FACT:** the plan's five stages each change one thing and start from the
  previous accepted image.
- **FACT:** every cited offline result is reproducible with repo tools; none
  is a card result.
- **HYPOTHESIS:** if S1 fails while S0 passes, the unit requires factory-exact
  compressed bytes; if S1 passes and S2 fails, a content/activation check
  exists; if S2 passes and S3 fails, the issue is tile-level.
- **UNKNOWN:** boot time, the actual error text per stage, and whether the unit
  writes to the card during boot — all to be measured.
