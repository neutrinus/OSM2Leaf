## Question

For each of the 89 `HDD_INFO.TXT` variants, what does the firmware's check 2
(`AppLaunch.dll` `fn 0x03bd2ce4`, EU2011 build B, MapDBVer range, error
`0x51`) return under declared unit bounds, does it agree with `hddinfo.py
classify --mapdbver-min/--mapdbver-max`, and which codes does the router
`fn 0x03bd2ecc` raise?

## Hypothesis

The M2.15 model of check 2 (line 3 slot 2 chars 5, 6, 7 → three nibbles via
`fn 0x03bd2a40`, `min <= value <= max`, bounds = record `+112`/`+114` u16 BE)
is exact, so only the 12 MapDBVer-changing variants (C-3034) can move and the
firmware agrees with the model on 89/89. The router raises `0x50` then `0x51`
for each failing check when the dispatcher returns, and only the first code
when it does not (C-5351).

**Falsifier:** any variant whose firmware check-2 verdict or logged MapDBVer
differs from the model; a router code list that differs from the model's
`failures`; the factory file failing with bounds that contain `0x010`, or
passing with `min = 0x011`; or a BLOCKED run. Each fails
`hddinfo_check2_matrix.py run` (exit 1 or 4).

## Interpretation

- **FACT (C-5296):** firmware check 2 (`fn 0x03bd2ce4`, EU2011 build B) agrees
  with `hddinfo.py classify` check 2 on 89/89 variants under both declared
  bounds pairs (A: 77 ACCEPT / 12 REJECT, B: 81 / 8), and its logged MapDBVer
  equals the model value on every logged row (20/20). The M2.15 model of check
  2 is confirmed by execution; only the 12 MapDBVer-changing variants move.
- **FACT (C-5297):** the router raises exactly the model's `failures` when the
  dispatcher returns (2 variants raise `0x50`+`0x51` under pair A) and only the
  first code when it does not (89/89 both modes). So C-2080's "does not skip
  check 2 when check 1 fails" holds for the router code and for a returning
  dispatcher (ProtoLevel unit, no screen), but **on a production unit check 2
  is only reached when check 1 passes** (C-5351): a card failing check 1 shows
  `DIFFERENT MAP CODE` only. `docs/format/validation.md` is corrected.
- **FACT (C-5298):** parser corner cases of check 2, observed: a line-3 slot
  shorter than 8 chars gives NUL → nibble 0 (`swap_3_5`); non-hex chars (`-`,
  `V`) give 0 (`0x0e0` from `-EV`); with no file the value is 0, so check 2
  passes when `min = 0`. Check 2 reuses check 1's parse cache (one
  `CreateFileW` in the chained run) and parses the file itself when the cache
  is cold.
- **FACT (C-5299):** the router does nothing for a partition other than 0
  (`fn 0x03bd2ecc(1)`: 8 instructions, no call).
- **HYPOTHESIS (unchanged, C-5146, C-2087):** real unit values of `+0x60`,
  `+112`, `+114`. All verdicts are relative to the declared inputs; pair A is
  the tightest pair a factory card passes.

## Conclusion

The done-when holds: each of the 89 variants has a check-2 firmware verdict
under two stated bounds pairs, compared with `hddinfo.py classify` (89/89
each), and the router was run on all of them, returning `0x50`, `0x51`,
`0x50`+`0x51` or pass. For a generated card: line 1 bytes 0..10 must equal the
unit's `+0x60` and line 3 chars 5..7 must be hex digits giving a MapDBVer
inside the unit's `+112..+114`; on a production unit a check-1 failure hides
any check-2 result. `reader-coverage.md` row 23 and `validation.md` updated;
claims C-5296–C-5299.
