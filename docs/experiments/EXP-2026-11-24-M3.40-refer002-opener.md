## Question

Which firmware function opens `REFER002` (EV-layer files, matrix row 24), and
do its reads go through the same search-type opener as `REFER001`?

## Hypothesis

The `REFER002` string at VA `0x001793a4` is a *directory name* loaded by the
shared search-type opener `fn 0x003fbed8`; the same opener defaults to
`REFER001` (`0x00178c68`). The selector is a derived context word, not a
guessed byte signature: `ctx+104` = `0x14ef` or `0x14f0`, `ctx+124` = 0, plus a
`0x4000` bit in a flag word reached indirectly. Falsifier: no code reference
to the name in any module and no table holding it; or an L3 call with the
derived context never resolves a `REFER002` path.

## Method

### 1. Sample and hash

Hashes printed by `sha256sum archive/head256.img
archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` above. The image
SHA-256 equals `vcard_l3.EU2011["head_sha256"]`, so `tools/vcard_l3.py` mounts
the factory build without an override.

### 2. Commands

```bash
# S0: the name strings in executable-reachable data
python3 tools/ce_strfind.py archive/head256.img --image-start 0x200200 --encoding all REFER002
python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x001793a4
python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x00178e4c
python3 tools/sh4xref.py archive/head256.img Vehicle.exe --image-start 0x200200 --to 0x0001ca9e

# S1: derive the selector from the code (little-endian, pinned in sh4dis)
python3 tools/pdata.py fn archive/head256.img --module Navi.exe --image-start 0x200200 0x003fbed8 0x0040b358
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003fbed8 --count 130
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003fbff0 --count 80
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003fc086 --count 50
python3 tools/callgraph.py build archive/head256.img --module Navi.exe --image-start 0x200200 -o graph.json
python3 tools/callgraph.py callers graph.json 0x003fbed8 --depth 1

# S2: L3 run of the opener on the mounted factory card (positive + controls)
python3 tools/refer002_opener_l3.py --selftest
python3 tools/refer002_opener_l3.py run archive/head256.img \
  --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img

# S3: the same call through the existing generic trace tool
python3 tools/vcard_l3.py trace archive/head256.img 0x003fbed8 \
  --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
  --args ctx,0,2 --ctx 104=0x14f0 --ctx 124=0 --ctx 160=0x4000 --max-insns 5000000
python3 tools/vcard_l3.py trace archive/head256.img 0x003fbed8 \
  --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
  --args ctx,0,2 --ctx 104=0x14f0 --ctx 124=1 --ctx 160=0x4000 --max-insns 5000000

# S4: the on-card file census that the resolved shards must match
python3 tools/refer002_census.py census /path/to/factory/REFER002
python3 tools/gate.py
```

### 3. Controls

- **Positive (must pass):** S3 with `ctx+104=0x14f0`, `ctx+124=0`,
  `ctx+0xa0=0x4000`, n=2 resolves `REFER002/POINT002.DAT` to file id
  `0x00070002`; the tool's 15 shards each resolve a `REFER002` file that exists
  in the on-card census (S4). Known-good control from M3.28:
  `fn 0x003fee70(ctx)` resolves `REFER001/POINT001.DAT` to `0x00060080`.
- **Negative (must fail as expected):** (a) `ctx+124=1` with the same
  `0x14f0`/flag selects `REFER001/POINT002.DAT` (`0x00060081`), **not** EV;
  (b) flag word `0` with `0x14f0` does the same (the 0x4000 bit is absent);
  (c) `ctx+104=0x14e4` (the LCTBL selector, M3.28) does not name `REFER002`;
  (d) the two strings with no literal-pool xref (`0x00178e4c`,
  `0x0001ca9e`) must be named as tables/data, not claimed as code references.
- **Mandatory negative mutation:** change the flag word from `0x4000` to `0`
  and the resolver output changes from a `REFER002` id to the `REFER001` id;
  this is control (b) and it is printed by `tools/refer002_opener_l3.py run`.

### 4. Scope

Build A (`Navi.exe`, `Vehicle.exe`) uncompressed executable sections only —
all code is readable (C-2128). Fourteen callers of `fn 0x003fbed8` were listed
from the pdata-based call graph; the L3 run exercised all 15 EV POINT shards of
the EU 2011 card (16 `REFER002` files including `COORD001.DAT`). US 2011 was
not run; `tools/fn_match.py` is left as the follow-up for cross-build mapping.
No content reader of the EV 11-field dictionary is claimed here — this is a
file-opener/run result at L3, not a record decode (rule 13). Scratch was
`~/projekty/leafre-work/scratch/m3.40/`; it is deleted after this EXP.

### 5. Falsifier

If no module's code loaded `0x001793a4` and it was not in a pointer table, the
task would be blocked after the three xref patterns. If the derived context
resolved no `REFER002` path on the card, the directory-string hypothesis would
be refuted. If a negative context still resolved `REFER002`, the selector
derivation would be wrong.

## Interpretation

- **FACT:** `fn 0x003fbed8` is the shared REFER search-type opener. Its
  directory argument is the pdata-derived literal `0x001793a4` ("REFER002")
  only on the derived context path; it defaults to `0x00178c68` ("REFER001").
- **FACT:** the selector is `ctx+104 ∈ {0x14ef,0x14f0}`, `ctx+124 == 0`, and
  the 0x4000 flag bit in the word at `ctx+0xa0` (0x14f0) or behind the pointer
  at `ctx+0xa4` (0x14ef). The L3 run with only the flag bit changed from
  `0x4000` to `0` flips the resolved directory from EV to REFER001 — the
  mandatory negative mutation fails loudly.
- **FACT:** on the mounted EU 2011 card this opener resolves exactly the 15
  EV POINT shards present in the on-card census. The returned file ids are
  `0x00070002…0x00070010`, distinct from the REFER001 ids `0x0006xxxx`.
- **OBSERVED:** `0x00178e4c` is a volume-id table entry and `0x0001ca9e` is a
  full `\SystemSD\REFER002\%03d` path in `Vehicle.exe`; neither has a literal
  pool xref, so neither is an independent opener (the falsifier's "name the
  table" branch is satisfied).
- **OBSERVED:** no record-level consumer of the EV 11-field dictionary was
  run; `fn 0x003f6c88` (read request) and `fn 0x0041841c` (layer read API) are
  the generic read issuers of the map-file layer (M9.44), not EV-specific
  readers. A dedicated EV content reader remains unlocated.
- **HYPOTHESIS:** the 0x14ef/0x14f0 context selects EV for the charging-station
  search triggered from the EV UI; which caller supplies that context at run
  time is not established by this static+L3 run.
- **UNKNOWN:** US 2011 opener twin; which runtime message supplies
  `ctx+104=0x14f0`.
