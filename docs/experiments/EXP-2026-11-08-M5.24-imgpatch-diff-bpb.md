## Question

Can the imgpatch byte-diff check resolve each replaced file's cluster data
ranges and directory-entry slot from an **independent BPB+FAT read** of the
filesystem (not from a patch plan or write offset), report any diff range that
falls outside that union, and still classify the M5.13b S1/S2 case correctly?

## Hypothesis

Reading BPB geometry and FAT chains fresh from the patched image with
`mkcard.open_map_partition` + `_locate`/`mkcard.chain`/`geo.cluster_offset`
produces the same cluster/dir-entry ranges that the M5.13b ad-hoc check found
(clusters 78193–78258 and dir entry `0xb3bb7e80` for the S2 POINT010 pair), so
`--check-diff` reports `ok` with 0 outside ranges on S2 and reports a mismatch
when a byte is changed outside the allowed union. **Falsifier:** the
independent BPB+FAT read resolves different cluster ranges or dir-entry offsets
than the filesystem actually contains, or it fails to report an out-of-range
diff, or it does not pass on the M5.13b S2 image.

## Method

1. **Sample and hash.** Synthetic images are generated in a temp dir by
   `make_selftest_image` (deterministic content; no vendor data). Vendor-derived
   S1/S2/factory US images are outside the repo; SHA-256s are recorded above and
   match EXP-2026-11-08-M5.13b-us-s1-s2 / C-2350/C-2351.
2. **Commands.**

   ```bash
   # controls + negative case, no vendor data
   python3 tools/imgpatch.py --selftest

   # M5.13b S2 case (vendor-derived images outside repo; paths local to this
   # machine, read-only). Expected: ok true, diff_ranges 17737, outside 0,
   # cmp chain 78193..78257 dir 0xb3bb7e80, ind chain 78258 dir 0xb3bb7ee0.
   python3 tools/imgpatch.py --check-diff \
     --image /home/marek/projekty/leafre-work/m5.13/us_S2.img \
     --reference /home/marek/projekty/OSM2Leaf/archive/sd-images/LEAF_2011-2012_US.img \
     --file REFER001/POINT010.DAT.cmp --file REFER001/POINT010.DAT.ind --json

   # S1 no-op control (vendor-derived): expected 0 diff ranges, ok true.
   python3 tools/imgpatch.py --check-diff \
     --image /home/marek/projekty/leafre-work/m5.13/us_S1.img \
     --reference /home/marek/projekty/OSM2Leaf/archive/sd-images/LEAF_2011-2012_US.img \
     --file REFER001/POINT010.DAT.cmp --file REFER001/POINT010.DAT.ind --json
   ```

3. **Controls.** *Positive*: `imgpatch --selftest` creates a same-cluster-count
   patch and checks that `check_diff_ranges` (independent BPB+FAT read) finds the
   diff ranges inside the file's cluster chain and dir entry; it also checks
   multi-file resolution and that resize outside-cluster diffs are classified as
   FAT/FSInfo metadata (the independent BPB+FAT read still resolves file
   clusters/dir entries). Real-image positive: S2 vs factory gives 17,737 ranges,
   0 outside, with the independently resolved clusters/dir entries above. *Negative*:
   selftest copies an image, flips one byte outside every allowed cluster/dir
   range, and asserts `check_diff_ranges` reports `ok=false` and
   `outside_range_count >= 1`; the CLI exits 1 on mismatch.
4. **Scope.** Changed `tools/imgpatch.py` verification path only (new
   `allowed_ranges_from_bpb`, `check_diff_ranges`, `--check-diff`/`--reference`
   CLI mode, and self-test cases). No change to how bytes are written. The check
   classifies **file data cluster ranges and 32-byte directory entries** resolved
   from an independent BPB+FAT read; FAT/FSInfo metadata diffs caused by a
   cluster-count change are outside that file-cluster union (selftest asserts
   they fall only in FAT/FSInfo regions). Verified on synthetic fixtures and the
   M5.13b US S1/S2 images (same-cluster-count POI rename case).
5. **Falsifier.** An independent BPB+FAT read that returns cluster ranges/dir
   offsets different from the filesystem's actual layout, a missed outside diff,
   or S2 reporting any outside range / wrong clusters.

## Observations

- `python3 tools/imgpatch.py --selftest`: `OK (59 checks)`, including the M5.24
  independent-BPB+FAT diff-check positive, multi-file, outside-diff negative,
  and CLI mismatch-exit cases.
- S2 vs factory (`--check-diff --json`): `ok true`, `diff_range_count 17737`,
  `outside_range_count 0`. Independently resolved files:
  `REFER001/POINT010.DAT.cmp` start cluster `78193`, chain `78193..78257`, dir
  entry `0xb3bb7e80`; `REFER001/POINT010.DAT.ind` start cluster `78258`, chain
  `[78258]`, dir entry `0xb3bb7ee0`. These match M5.13b's recorded ranges
  (C-2351/C-2352 context) without using any patch-plan write offset.
- S1 vs factory (`--check-diff --json`): `ok true`, `diff_range_count 0`,
  `outside_range_count 0` (S1 is byte-identical to factory, C-2350).
- Synthetic negative: a byte flipped outside allowed cluster/dir ranges is
  reported as outside; `--check-diff` CLI exits `1` with `ok=false`.

## Interpretation

- **VERIFIED:** The diff-range check resolves replaced-file data clusters and
  directory-entry slots from an independent BPB+FAT read of the image
  (`mkcard.open_map_partition`, `_locate`, `mkcard.chain`,
  `geo.cluster_offset`), not from imgpatch write offsets or plan `writes`. It
  reports outside diff ranges and exits 1 on mismatch.
- **VERIFIED:** The check still passes on the M5.13b S1/S2 images with the
  recorded SHA-256s and resolves the same POINT010 cluster ranges/dir entry as
  M5.13b (cmp 78193–78257, `0xb3bb7e80`; ind 78258, `0xb3bb7ee0`; 17,737 S2
  ranges, 0 outside).
- **OBSERVED:** For a patch that changes cluster count, FAT/FSInfo bytes change
  and are outside the file-cluster/dir-entry union; the independent BPB+FAT read
  still resolves the file's clusters/dir entry correctly, and the selftest
  confines those outside ranges to FAT/FSInfo metadata.

## Conclusion

M5.24 closes the M5.13b range-check limit: cluster bases come from an
independent BPB+FAT read, not from `imgpatch` write offsets. `tools/imgpatch.py`
now provides `--check-diff --reference ... --file ...` for this verification and
reports mismatches. The M5.13b S1/S2 case remains correctly classified (C-2350–
C-2352 context unchanged). FAT/FSInfo metadata on resize is intentionally
outside the file-cluster/dir-entry union and is separately identifiable as
metadata.
