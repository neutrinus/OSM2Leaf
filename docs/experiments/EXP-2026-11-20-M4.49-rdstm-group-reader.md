# EXP-2026-11-20-M4.49: the RDSTM001 link-group reader is not in the TMC data-layer subtree of Navi.exe (EU2011); messages 0x14e4/0x14f4 lead to a generic sector reader

## Question

Which `Navi.exe` (EU2011) function reads the `RDSTM001.DAT` link-group structures decoded in M4.16e (header sets at `0x1000`, group index `u16 size_dwords, u32 addr, u16 blocks, u32 key_min, u32 key_max, u16 n, n × (u32 parcel, u16 count)`, 4-byte `(node, link)` entries)?

## Hypothesis

The reader sits below the `RDSTM001` access path (volume selector `0x004125a8`, the TMC request `0x003bcac0`) and shows the shape the data imposes. **Signature (derived from the data-side decode, the weakest kind under rule 14):** (S1) `and` with a pool literal `0x1fff` (node / link id of an entry); (S2) the container address build `(v >> 8) * 0x800 + (v & 0xff) * 0x100` (`shlr8`/`shlr16` + `shll8` + `extu.b` + `shll2`/`shll` in one function); (S3) a 6-byte row stride (`add #6`) inside a loop; (S4) an 18-byte group head (`add #18`).

**Falsifier:** a function reachable from the TMC data-layer roots that shows S1 together with S2 or S3 (then disassemble it as the candidate); the search is negative if no function in that subtree shows S1 at all.

## Interpretation

- **OBSERVED (C-5375):** no function reachable from the TMC data-layer roots (EU2011, 230 functions, depth 8) masks a halfword with `0x1fff`, and none shows two of the four derived features; the module's only S1+S2 functions are guidance/car-position code. With this signature, the link-group reader is not in the static TMC subtree of `Navi.exe`.
- **OBSERVED (C-5376):** `0x14e4` and `0x14f4` are message ids of the same data-layer dispatcher entry (`0x004003f4`) and of the generic sector reader `0x00417618`/`0x00412ac0`, each with its own buffer slot; `0x14f4` is a second TMC-side request type next to the location-record request `0x14e4`. Which file and offset a `0x14f4` request reads is not determined statically (`fn 0x004125a8` gives no file for it).
- **HYPOTHESIS (C-5377):** the link groups are read as raw sectors through the generic reader (request `0x14f4`, or `0x14e4` with another kind), and parsed by the requester, which sits outside the static subtree (an unresolved indirect call — 28 inside the subtree — or another task that sends the message with `OSM_TaskSend`). The `0x1fff` / address-build signature would then be at the requester.
- **UNKNOWN (C-5378):** the reader VA, the meaning of `a`/`b` bits 0x4000/0x8000, roles `k&3` (C-5403 hypothesis for roles 0/1), header words `3`/`122`. No L3 run was possible without a candidate.
- **Block (C-5379):** done-when not met; stop reached (reachability walk from the access path and the message dispatcher + two derived signature families — the S1–S4 shape and the message-id constants — without a candidate). Unblock: M4.51 (find the senders of `0x14f4`/`0x14e4` and what `0x14f4` reads, statically through `OSM_TaskSend` callers or dynamically by a read watch in L4).

## Conclusion

Negative with controls: the S1 detector finds `0x1fff` masks where the section-2 code is, and the constant query reproduces the known `0x14e4` sites, but the TMC data-layer subtree holds no function with the link-group signature. The search leaves one concrete lead: message `0x14f4`, a second TMC request handled by the same entry as the location-record request and served by a generic sector reader with its own buffer. M4.49 is `blocked` on M4.51. `docs/format/rdstm.md` notes the negative and the lead.
