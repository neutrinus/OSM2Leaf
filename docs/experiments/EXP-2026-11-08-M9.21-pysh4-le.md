## Question

Does the repository's pure-Python SH-4 interpreter, with `endian="little"` and
the two delayed conditional branches modelled, run the `Navi.exe` POINT-page
walk at `0x3f39c0` on a real US page and return the same record offsets as the
independent Python framing?

## Hypothesis

`PySh4` with little-endian memory and `bt/s`/`bf/s` executes `fn 0x003f39c0`
on the US `POINT010` page 0x840ba0 and returns, for each sampled record `n`,
the offset that `parse_page` gives (and 0 for `n` = record count). The
delay-slot rule is the one of `bra`/`bsr` already in the engine: the instruction
after a `bt/s`/`bf/s` always runs once; a taken branch continues at its target.

**Falsifier:** (a) any sampled `n` where the firmware offset differs from
`parse_page` (and from the model) would refute the engine change or the
delay-slot rule; (b) a non-zero return with the page argument set to
`base + 2` would show the guard does not read `*0x00d5e4e4`; (c) a changed
result from the default `PySh4()` on the existing snippet tests would show the
default is not preserved.

## Method

1. **Sample and hash.** As in the Sample and Inputs above; hashes checked with
   `sha256sum` before the runs (all four match).
2. **Commands.** Run from the repository root with the sample paths shown.

```bash
IMG=/home/marek/projekty/OSM2Leaf/archive/head256.img
P=/home/marek/projekty/leafre-work/m5.13/factory/REFER001
python3 tools/l3_harness/engine.py --selftest
python3 tools/point_walk_l3.py --selftest
python3 tools/point_walk_l3.py walk $IMG --cmp $P/POINT010.DAT.cmp --ind $P/POINT010.DAT.ind --page 0x840ba0 --page-len 42848
python3 tools/point_walk_l3.py skip $IMG --cmp $P/POINT010.DAT.cmp --ind $P/POINT010.DAT.ind --page 0x840ba0 --page-len 42848
python3 tools/selftest.py
```

   Precheck (before the change): the `walk` line above, run with a copy of
   `origin/main`'s `tools/` (`git archive origin/main tools`, commit
   `88332de`), passed with the old local subclass `PySh4LE`. It is run again
   on the branch; the two outputs are compared with `diff` (Observations 3–4).
3. **Controls.** *Positive:* `parse_page` (independent Python framing, C-952)
   on the same page, and the `model_nth` Python model of the walker; the
   engine self-tests pin `bt/s`/`bf/s` on synthetic vectors where the taken and
   untaken outcomes give different register values. *Negative:* (i) the walk
   on the **unswapped** page must disagree with `parse_page` (as in the precheck);
   (ii) the `skip` guard control, `p = base + 2`, must return 0; (iii) the
   `skip` count control, count cell set to 500 with the 1000-record page, must
   return record 499 for `n` = 499 and 0 for `n` = 500.
4. **Scope.** One real page (1000 records; the 9 sampled `n` are
   `0,1,2,3,10,500,998,999,1000`); `fn 0x3f39c0` only; the engine self-tests
   (16 checks run, 2 skipped: Ghidra and QEMU absent on this machine); the
   repo selftest (65 tools). Not covered: any other POINT page, any other
   US/EU card, `bt/s` on real bytes (no firmware path with `bt/s` is run here),
   and the runtime values of the two globals (the tool writes them; see
   C-2555). The SH-4 programming manual was **not** consulted:
   `docs/research/sources.md` has no link to it and it was not fetched in this
   session. The delay-slot rule is stated from the standard SH-4 semantics and
   is checked against the real loop below, not against the manual text. The
   `bt/s`/`bf/s` vectors were not run against a deliberately wrong engine; a
   `bf/s` that read T after its slot would fall through and fail `r3 == 0`,
   which is the discrimination the assertion relies on.
   `cmp/str` (`engine.py`, `cmp` block) is not changed: it tests whether any
   byte lane of the two operands is equal, and both operands use the same lane
   order, so the result does not depend on byte order. The other `"big"` /
   `struct ">"` uses in the class are the snippet builders and the stub, outside
   `PySh4`'s memory path.
5. **Falsifier.** As stated under Hypothesis.

## Interpretation

- **FACT (engine):** `PySh4(endian="little")` loads, stores and fetches
  little-endian; the default is still big-endian; `bt/s` and `bf/s` now run
  instead of raising `IllegalInstruction`. Verified by the engine self-tests
  (section 1).
- **FACT (real bytes):** on the US POINT010 page 0x840ba0, `fn 0x003f39c0`
  returns the `parse_page` offsets for the nine sampled `n`, and 0 past the
  last record (section 5). That path runs the `bf/s` loop at `0x3f39f2` for
  every record it skips, so both the taken outcome (loop continues) and the
  untaken one (loop ends) are exercised across 1000 records.
- **FACT (guard):** with `p` not equal to `*0x00d5e4e4`, the function returns 0
  (section 5, guard control).
- **FACT (count):** with the count cell at 500, `n` = 499 returns record 499's
  offset (`0xfd38`) and `n` = 500 returns 0 (section 5, count control). The
  bound is observed, so the role of `*0x00d5e4d0` is tested, not only read off
  the disassembly.
- **OBSERVED:** the `walk` precheck is unchanged by the switch from the local
  subclass to `PySh4(endian="little")` (sections 3 and 4).
- **HYPOTHESIS:** the `bt/s`/`bf/s` delay-slot rule as implemented is the
  SH-4 rule. Support: the self-tests (one of them has a slot that writes T, so
  the condition is shown to be read at the branch) and the loop result above.
  Not yet checked against the manual text (not consulted; no link in
  `docs/research/sources.md`).
- **UNKNOWN:** the runtime values of `*0x00d5e4d0` and `*0x00d5e4e4` in a
  booted unit (the tool sets them, see C-2555); any firmware path that executes
  `bt/s` on real bytes; the behaviour on any other POINT page or on the EU
  card's POINT pages.

## Conclusion

`PySh4` now runs `Navi.exe` code as it is in the image (little-endian) and
models `bt/s`/`bf/s`. The M9.21 Done-when is met: the engine has
`endian="little"` with the default unchanged, `bt/s` and `bf/s` each have
self-test vectors, `point_walk_l3.py` uses the engine directly, and
`0x3f39c0` runs on the US page with the two globals set and agrees with
`parse_page` on the sampled records. Claims C-2550–C-2557 record this; C-2546
describes the engine before the change. Open: the globals' runtime values
(C-2555) and any `bt/s` target on real bytes (C-2557).
