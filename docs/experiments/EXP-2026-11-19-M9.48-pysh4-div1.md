# EXP-2026-11-19-M9.48: PySh4 models `div1` (and `div0s`/`div0u` M/Q) per the SH-4 manual

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** `archive/head256.img` (EU IMG256, build EU2011) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  `archive/us256.img` (US IMG256, build US2011) SHA-256
  `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`
- **Tools:** `python3 3.13.18`; `tools/l3_harness/engine.py` (changed),
  `tools/l3_harness/decode_audit.py` (bucket exemption removed),
  `tools/l3_harness/div1_l3.py` (new: `sites`/`run`/`isolate`),
  `tools/cerom.py`, `tools/pdata.py` (via the two tools)
- **Claims:** C-5180–C-5185
- **Supersedes:** none (the `div0s` semantics of EXP-2026-11-19-M9.37 are corrected here, see C-5181)
- **Superseded by:** none

## Question

Can the PySh4 engine run `div1` (`0x3nm4`) with the SR.M/SR.Q/T state of the
SH-4 manual, so that `decode_audit.py census` moves it from
IN_SCOPE_UNMODELLED to MODELLED, without changing any other instruction?

## Hypothesis

The manual's `DIV1` C code (and `DIV0S`: Q = Rn[31], M = Rm[31], T = !(M == Q);
`DIV0U`: M = Q = T = 0; SR.Q = bit 8, SR.M = bit 9) is complete enough to
transcribe in one pass. If it is right, the firmware's own divide routines
(found in `nk.exe`) return C-semantics quotients/remainders on every sign case.
**Falsifier:** a runnable firmware divide routine whose `r0` matches none of
`udiv`/`urem`/`sdiv`/`srem` on the operand set, or `isolate` showing a changed
outcome for any form other than `div0s`/`div0u`/`div1`, or `compare` reporting
any disagreement or drift.

3. **Controls.**
   *Positive:* `engine.py --selftest` runs the manual's unsigned
   (`div0u` + 32 × `rotcl; div1` + `rotcl`) and signed (`div0s` … `addc`)
   32-bit divide sequences against Python on 9 unsigned and 11 signed vectors
   (all four sign combinations, `INT_MIN`, `0xFFFFFFFF`), plus four
   hand-computed `div0s; div1` two-step rows, one per sign case. On the image,
   `div1_l3.py run` calls the firmware's own routines on 20 operand pairs.
   *Negative:* the same tests with a `div1` that ignores M/Q (always
   "shift, subtract, Q = borrow"): the engine self-test fails two checks
   (verified on a scratch copy with the two M/Q arguments replaced by `0`),
   the in-test control asserts the blind step gets `-100/7` and `100/7` wrong,
   and `run --mq-blind` must make every firmware match disappear.
   *Isolation:* `isolate` runs every non-FPU halfword (61,440) on BEFORE and
   on the new engine from four register states (SR with T/S/Q/M on and off)
   and diffs registers, 4 KiB of memory, the delay-slot target and the
   exception type; its self-test checks that the engine against itself
   differs nowhere and that an M/Q-blind copy differs on `div1` only.
4. **Scope.** Integer `div0s`/`div0u`/`div1` only. `rotcl`/`rotcr` are not
   modelled by the engine (unchanged); `div1_l3.py run` executes them in a
   tool-local shim subclass and prints how many it ran. Not covered: the
   divisor-zero path of the routines (calls an exception helper), FPU
   (`0x88041244` stops on `0xf04c`), and any Navi.exe divide (none found,
   see Observations). `decode_audit.py`'s `INTEGER_OUT_OF_SCOPE` exemption
   (`{"div1"}`) is emptied so a rejected `div1` would count as drift again.
5. **Falsifier.** As stated in Hypothesis; stated before the runs.

## Observations

Engine diff (`engine.py`): `div0s` now writes Q = Rn[31] to SR bit 8,
M = Rm[31] to SR bit 9 and T = (M != Q); before, it wrote Rn[31] to SR bit 2,
Rm[31] to SR bit 1 (the SH-4 S bit) and T = 0. `div0u` now also clears M and Q.
`div1` (`_exec_alu` sub `0x4`) is new, through `_div1_step()` transcribed from
the manual's nested switch.

Self-tests: `engine.py --selftest` → `selftest: OK (23 checks, 2 skipped, quick)`
(skips: Ghidra/QEMU absent). With `div1`'s M/Q inputs forced to 0 (scratch
copy): `FAILED (2/25 checks)` —
`div0s;div1 Rn from Rn=0x00000010 Rm=0xfffffffd: got 36, expected 30` and
`unsigned 0x00000064 / 0x00000007: got 6, expected 14`.
`decode_audit.py --selftest` → `OK`; `div1_l3.py --selftest` → `OK`.

## Interpretation

- **FACT:** the engine's `div0s`/`div0u`/`div1` follow the manual's
  pseudocode; the firmware's own `nk.exe` unsigned divide (`0x88040b6c`),
  unsigned remainder (`0x88040c18`), signed divide (`0x88042594`) and signed
  remainder (`0x88040988`) return the C result on all 20 pairs, and an
  M/Q-blind `div1` breaks every one of them.
- **FACT:** no instruction other than `div0s` (256), `div0u` (1) and `div1`
  (256 halfwords) changed outcome; `compare` stays 0 / 0 on all three corpora.
- **FACT:** M9.37's `div0s` was not the manual's: wrong SR bits (2/1, where
  bit 1 is S) and T always 0. Corrected here; C-3593's "models `div0s`"
  holds only for decoding, not for M/Q/T.
- **OBSERVED:** `Navi.exe` has no unrolled divide in pdata-covered code on
  either build; its 513 (EU2011) / 860 (US2011) `div1`-shaped halfwords are
  scattered 1–8 per function, next to no `rotcl`. **HYPOTHESIS:** they are
  literal-pool/table data inside pdata ranges, and Navi.exe divides through
  `nk.exe`/coredll helpers.
- **UNKNOWN:** whether the `div1` routines are reachable from any L3 target
  in this repo today: they need `rotcl`/`rotcr`, which the engine does not
  model (follow-up M9.50).

## Conclusion

`div1` is modelled and the census moves it to MODELLED (EU2011 Navi 513,
EU2011 nk 217, US2011 Navi 860 instructions); `compare` reports 0
disagreements / 0 drift on all three corpora; `isolate` proves only
`div0s`/`div0u`/`div1` changed. Claims C-5180–C-5185 added. Open: `rotcl`/`rotcr`
(M9.50) so the firmware's divide routines run without the tool shim, and the
`mac.w` `NameError` (M9.49).
