  `tools/l3_harness/rommap.py`, `tools/l3_harness/runner.py` (this task),

## Question

Can a module-entry target receive caller-supplied, file-derived input at a
chosen guest VA with exact bounds and recorded provenance, so that the EU POINT
walker `fn 0x003f5194` reads a real page instead of stopping at its NULL page
argument `0x0`?

## Hypothesis

Falsifier-first. Refuted if, after `entry.input_region` is added, the EU walker
with a mapped EU page still stops at `UNMAPPED 0x00000000..0x00000002` (the
pre-change fault), or if a read one byte past `va+size` is served instead of
refused, or if the result reports a verdict without a declared `verdict_map`
rule. It is **not** required that the walker return an accepted reader verdict;
the done-when accepts "past the argument-pointer fault" with the observed
return cross-checked against the model.

## Method

1. **Sample and hash.** `archive/head256.img` SHA-256 `92aa525d…a007f9`
   (`sha256sum archive/head256.img`). `cerom.py romhdr`:
   `physfirst 0x8cae1000`, `nummods 0x00000095`, `ulRAMStart 0x89e40000`.
   Memory map: `rommap.py convert --skip-compressed` yields one block
   `Navi.exe/sec0 0x11000 size 5553664 r-x`, skipping `sec1 0x55d000` and
   `sec2 0x0154f000`. `0x0154f000` (highest section start) `< 0x20000000`
   (chosen region) `< 0x89e40000` (`ulRAMStart`).

2. **Produce the served blob.** The walker loads native `u16` (`mov.w`, see
   step 3), so the blob is the swap16 of the decoded page. This is the exact
   producer; it writes 97,158 bytes and prints their SHA-256:

```bash
python3 - <<'PY'
import sys, zlib, hashlib
from pathlib import Path
sys.path.insert(0, 'tools')
import mutate_refer_poi as mrp
root = Path.home() / 'projekty/leafre-work/m5.29-factory-root/REFER001'
out  = Path.home() / 'projekty/leafre-work/scratch/m9.28/eu-point010-0x6e06d0.swapped.bin'
cmp_bytes = (root / 'POINT010.DAT.cmp').read_bytes()
_, _, _, _, offsets = mrp.read_ind(root / 'POINT010.DAT.ind')
dat = mrp.decode(cmp_bytes, offsets)
raw = zlib.decompressobj().decompress(dat[0x6e06d0:0x6e06d0 + 97158])
o = bytearray(len(raw)); o[0::2] = raw[1::2]; o[1::2] = raw[0::2]
out.write_bytes(bytes(o))
print('bytes', len(o), 'sha256', hashlib.sha256(bytes(o)).hexdigest())
PY
# -> bytes 97158 sha256 67f3fe7a51b8848efe77ce6ffd5ec066abd8ec7bae7dc49b52cb3187d5b5b928
```

3. **Commands.** All from the repo root; `$W` is the scratch dir holding the
   blob and the throwaway target files.

```bash

    --modules Navi.exe --out $W/memmap-navi.json

    --segment 0 --skip-compressed --out $W/rommap-navi.json

    --va 0x003f5194 --count 34
python3 tools/point_walk_l3.py walk archive/head256.img \
    --cmp ~/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.cmp \
    --ind ~/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.ind \
    --page 0x6e06d0 --page-len 97158 --build eu2011 --n 2

    --targets $W/targets-eu-page.json --rommap $W/rommap-navi.json \
    --image archive/head256.img --input-root $W --json

    --targets $W/targets-eu-oob.json --rommap $W/rommap-navi.json \

    --targets $W/targets-eu-oob-padded.json --rommap $W/rommap-navi.json \
```

4. **Controls.**
   - *Positive (pre-change, reproduced Precheck):* the same walker with
     `args ["0x0","0x0"]` and no region stops at
     `UNMAPPED 0x00000000..0x00000002` (status `BLOCKED`, exit 4).
   - *Positive (model):* `point_walk_l3.py walk --n 2` returns `0xa8`, matching
     `parse_page` (`n=2 firmware=0xa8 parse_page=0xa8 model=0xa8 OK`,
     `result: PASS`); its own negative control (unswapped page) gives
     `0x6c0, None` instead of `0x4e, 0xa8`.
   - *Positive (after):* the header target runs to `return` and reports
     `returned 0x200000a8` = `PAGE_VA + 0xa8`; `consumed_input true`;
     `input_region.reads` shows three `mov.w` loads at `0x20000000`,
     `0x200000a8` (`widths [2]`, `first_pc 0x003f519e`).
   - *Negative (bounds):* `n=1000` with the exact region is refused
     `UNMAPPED 0x20017b86..0x20017b88`, where `0x20017b86 = 0x20000000 + 97158`.
   - *Negative (pad, same bytes):* with a 97,222-byte region the same `n=1000`
     returns `r0 0x00000000` (the run reads the padding and is not refused),
     while two `UNMAPPED`-free runs prove the pad matters.
   - *Negative (overlap):* a region at `0x003f5000` is `INVALID`
     "overlaps Navi.exe/sec0"; a size `97157` against 97,158 B is `INVALID` with
     the attempted SHA-256 in `input_region`; a missing `provenance` and an
     unknown `input_region` key fail `validate_targets`.

5. **Scope.** One image head (256 MiB of 7.4 GB), one module (`Navi.exe` sec0,
   5,553,664 B; sec1/sec2 skipped), one page (`0x6e06d0`, 97,158 B, 1,000
   records), one walker (`fn 0x003f5194`, EU2011). Excluded: the US build and
   its `0x840ba0` page, other modules and pages, `n > 1000`, stack arguments,
   the Ghidra and QEMU back ends, and any claim that the walker *accepts* the
   page (no `verdict_map` rule for a page offset was invented).

## Interpretation

- **FACT:** a module entry can map caller-supplied file bytes at a chosen VA
  with exact bounds; the EU walker reads them (`consumed_input true`, three
  `mov.w` loads logged with PC `0x003f519e`) and returns a record offset,
  where before the change it stopped at `UNMAPPED 0x00000000..0x00000002`.
- **FACT:** the region is exactly `size` bytes: `n=1000` is refused at
  `va+97158` (`0x20017b86`), and the same bytes padded by `+0x40` are served,
  so the boundary is real and the model tool's pad is what hides it.
- **FACT:** the served bytes are the swap16 form; the model tool's own negative
  control (unswapped page) returns `0x6c0`/`None`, not `0x4e`/`0xa8`, so the
  byte form is a checked property, not prose.
- **FACT:** provenance and the attempted SHA-256 are emitted on refusal paths
  (`INVALID`), so a refused region still names what it tried to serve.
- **OBSERVED:** the walker returns `PAGE_VA + 0xa8` for `n=2`, matching
  `point_walk_l3`'s `parse_page` model; with `0x0` unmapped this is
  `BLOCKED` "no verdict is guessed", i.e. pipeline evidence, not a reader
  verdict.
- **UNKNOWN:** whether the firmware ever reads this page through this walker in
  the same call shape (stack caller, page from `fn 0x0041c044`) — that is
  M9.38's read watch / M3.23's candidate readers, not this task.
- **HYPOTHESIS:** registering `point-walker-eu-page` as a permanent
  `targets.json` row would let `l3check` report the mapped-page path; it is not
  done here because the row is a pipeline fixture, not a reader verdict.

## Conclusion

`tools/l3_harness/runner.py` grows `entry.input_region` (`file`/`literal`
sources, `--input-root`, exact bounds, overlap refusal against module blocks,
stack, heap and IAT trampolines, provenance and SHA-256 on every result path,
and an `input_region.reads` consumption log via `WatchedPySh4`, which composes
with `GuardedPySh4`). The EU POINT walker now runs past its argument-pointer
fault on a real, file-derived EU page and returns `0xa8`, cross-checked against
`point_walk_l3`; the verdict stays `BLOCKED` (no `verdict_map` rule), so this is
pipeline evidence. Ten claims C-3210–C-3219 record the facts and the two
control results. Open: the caller chain (M9.38), the US page pairing, and
promoting the mapped-page path to a `targets.json` evidence row once it has a
reader verdict.
