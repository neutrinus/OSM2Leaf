# EXP-2026-11-20-M3.11b-point-byteorder-2: the firmware's own swap loop reproduces `swap16` on the factory POINT page

- **Status:** done
- **Date:** 2026-11-20
- **Sample:** firmware `archive/head256.img` (EU 2011 head) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`
  (8,057,257,984 bytes) SHA-256
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`;
  the file `REFER001/POINT010.DAT` is read from that card through the
  firmware's own layer.
- **Tools:** `python3 3.13 / zlib 1.3` (host; the firmware side uses the
  firmware's own zlib), repo `tools/vcard_l3.py` (M9.44: card mount, read
  queue, completion), `tools/l3_harness/engine.py` (PySh4),
  `tools/point_walk_l3.py` (`swap16`, `--selftest`), `tools/sh4dis.py`.
- **Claims:** C-5810–C-5816
- **Supersedes:** none (the M3.11 second pass, EXP-2026-11-08-M3.11b-point-byteorder,
  stays; its C-2547–C-2549 are unchanged)
- **Superseded by:** none

## Question

Does the firmware itself turn the factory `POINT` page into native `u16`, and
is the bytes it produces byte-for-byte the model `point_walk_l3.swap16`
already assumed?

## Hypothesis

Yes. C-4641 places the swap in the file layer's completion routine
`0x00417eac` (the `0x00417f1c`–`0x00417f30` loop) keyed on request word +20,
and C-4672 says every client read through `0x003f6c88` leaves +20 = 0.
C-3602/C-3604 say the page reaches the walker already swapped and the `.cmp`
chain is decode-only. If those are right, running the real completion routine
on a real read buffer, with +20 at its two factory values, must produce
`swap16(host_bytes)` for +20 = 0 and the unswapped host bytes for +20 = 1.

**Falsifier:** the firmware's post-loop buffer differs from
`point_walk_l3.swap16(host)` by any byte, or the +20 = 1 run swaps, or the
loop does not run (0 iterations) on the +20 = 0 path.

## Method

A **spec**, not a narrative.

1. **Sample and hash.** `archive/head256.img` (`92aa525d…a007f9`) and the
   factory card (`105e2032…5076307`), as in the header. `REFER001/POINT010.DAT`
   is served by the card's own `.cmp`/`.ind` pair through the firmware's
   layer; the host reference is `cardcheck.decode_cmp` on that pair. No vendor
   bytes are committed.

2. **Commands.** Committed tool `tools/swap_witness_l3.py` (it boots the EU
   card through `vcard_l3.py` and brackets the completion's swap loop), from
   the repo root, EU head, EU card:

   ```bash
   IMG=archive/head256.img
   CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   python3 tools/swap_witness_l3.py --selftest
   python3 tools/swap_witness_l3.py run "$IMG" --card-image "$CARD"
   python3 tools/swap_witness_l3.py run "$IMG" --card-image "$CARD" --length 0x400
   # the standing via-card control of the same swap
   python3 tools/vcard_l3.py read "$IMG" --card-image "$CARD" \
     REFER001/POINT010.DAT --length 0x1000 --swap
   ```

   The tool arms three `on_exec` hooks on the completion routine by
   start-relative offset (`+0x66` pre-swap snapshot, `+0x70` iteration count,
   `+0x86` post-swap snapshot), then issues two reads of
   `REFER001/POINT010.DAT` `[0, length)` through `Session.request`: once with
   request word +20 = 0 (`request(..., swap=True)`) and once with +20 = 1
   (`request(..., swap=False)`). The host reference is
   `Expected(card).read(path, 0, length)`; the model is
   `point_walk_l3.swap16`. The offsets are derived from the routine start,
   `0x00417eac`, so the tool spells no mid-function VA (`fn_audit`).

3. **Controls.**
   - *Positive*: with word +20 = 0 the firmware's own loop runs
     `LEN/2` times and the post-loop buffer equals
     `point_walk_l3.swap16(host)` byte for byte; the pre-loop buffer equals the
     unswapped host decode (so the swap really happens in the watched window,
     not earlier).
   - *Negative*: with word +20 = 1 the loop is never entered (no `pre`/`post`
     capture) and the returned bytes equal the unswapped host decode; the
     swapped output differs from the host bytes (`d0 != host`).
   - *Model control*: `python3 tools/swap_witness_l3.py --selftest` passes
     (6 checks: `swap16` swaps each pair, a correct run passes, one wrong
     post-loop byte / a short loop / an unswapped buffer each fail, the window
     is start-relative) and `python3 tools/point_walk_l3.py --selftest`
     passes; the committed `vcard_l3.py read --swap` prints `IDENTICAL`.

4. **Scope.** EU2011 build A (`Navi.exe`, image start `0x200200`) and the EU
   2011 factory card. One file (`REFER001/POINT010.DAT`), first `0x1000` bytes
   (two sectors' worth at the factory chunk boundary). The US build is not
   re-run here: its `.pdata` differs and M9.38 already credits its walker with
   the same 2-byte native load (C-3602); the swap routine is EU `0x00417eac`
   (C-4641). The client's own call is not executed: C-4672 is a disassembly
   claim (`0x003f6c88` memsets the 40-byte request and never stores +20), so
   the probe drives the request record directly with +20 at each value. A
   `--length 0x400` run repeats the same equality at a non-`0x1000` length,
   showing the loop is `length/2`, not a fixed count.

5. **Falsifier.** As stated under Hypothesis: any byte of the post-swap buffer
   differing from `swap16(host)`, a +20 = 1 run that swaps, or a +20 = 0 run
   whose loop never executes.

```
0x00417f1e  7401  add #1,r4               ;  |

0x00417f28  5388  mov.l @(32,r8),r3       ;  | length reloaded each pass
0x00417f2a  4301  shlr r3                 ;  |
0x00417f2c  3433  cmp/ge r3,r4            ;  |

0x00417f30  7202  add #2,r2               ; /  next pair
0x00417f32  ...   OSM_TaskSend(reply task, message 0x04a0 ...)
```

The length the loop counts is `*(r8+32) >> 1` (`mov.l @(32,r8),r3; shlr r3`)
and the buffer is `r9 = *(r8+36)` (`mov.l @(36,r8),r9` at `0x00417eca`); `r8`
is the completion routine's record argument (`r5`), whose `+20` word the
routine tests at `0x00417efc`/`0x00417f08` to decide whether to swap.

## Interpretation

- **FACT:** the firmware's own loop at `0x00417f1c` runs 2,048 times (=
  `0x1000/2`) on the factory `POINT010` first page when request word +20 = 0,
  and the bytes it leaves are byte-for-byte
  `point_walk_l3.swap16(host)` (SHA-256 `a6c6fec3…260c`).
- **FACT:** the pre-loop buffer equals the unswapped host decode
  (`10dceb1a…9ebf`), so the swap happens inside the watched window, and the
  completion's returned buffer equals the post-loop buffer.
- **FACT:** with word +20 = 1 the loop is never entered and the returned bytes
  are the stored bytes — the same discriminator C-4641 records.
- **OBSERVED:** this is the Done-when's "factory page swapped by the firmware
  code itself in PySh4 and byte-equal to `point_walk_l3.swap16`", on the
  real card, through the *real* completion routine, not a synthetic loop.
- **HYPOTHESIS (already C-4672):** every client read arrives with +20 = 0
  because the only caller of the read API (`0x003f6c88`) memsets the request
  and never stores +20; the tool drives that record directly, so it proves
  the swap code, not the client's choice of +20 (which is C-4672's
  disassembly).
- **UNKNOWN:** none that this task's Done-when needs. The walker's 2-byte
  native load on the swapped page is M9.38's C-3602; the `.cmp` chain being
  decode-only is C-3604.

## Conclusion

`docs/format/firmware.md` already carries the read API and the swap sentence
("The byte swap asked about in M3.11b is here"); this record adds the executed
proof and the loop's exact instructions. `docs/research/claims.md` gains
C-5810–C-5816. The page becomes native `u16` in the file layer's completion
`0x00417eac` (loop `0x00417f1c`), driven by request word +20, and the result is
`point_walk_l3.swap16` on real bytes; the client that always asks for it is
`0x003f6c88` (C-4672), and the `.cmp` chain only decodes (C-3604). M3.11b's
Done-when is met; M9.10 can feed the page in this byte order.

## Overtaken by a later commit

- C-5815 ("the swap … is the layer's completion") | M9.26 (PR #362; `git log --oneline -- docs/experiments/EXP-2026-11-20-M9.26-point-byteorder-revisit.md`) | RETRACTED for zlib pages, superseded by C-2903: the layer also swaps a page's compressed bytes; `fn 0x003fd690` undoes that with leaf `0x003f6968`, inflates, and makes the inflated page native with the same leaf. The equality this record measured (plain bytes `[0, 0x1000)`) stands.
