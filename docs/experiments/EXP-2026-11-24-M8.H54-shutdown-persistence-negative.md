## Question

Does an ACC-off from the vehicle peer at L4 change the NOR flash file in the
region `docs/firmware/power.md` predicts, and does a second boot start from
the saved value?

## Hypothesis

Yes: the vehicle peer's `ignition off` (or the emulator's SystemEXE 45 s AUI
watchdog) moves `PowerMonitor.dll` to `ACC_OFF_FIRST`, the application layer
acknowledges and the MCT/VFlash save is written to `FMD1:`, so the backing
file changes and the next boot reads back the saved setting.
**Falsifier (task):** the flash file is unchanged after a completed shutdown
sequence. **Second falsifier:** the guest never reaches ACC-off. **Third
falsifier:** adding `vcan` makes the boot stall before drivers load (a known
M8.H75 blocker). The negative is only a result if the positive controls pass:
the peer must accept the control commands, the flash file must be provably
writable/detectably mutable, and a boot without the peer must reach the map.

## Method

### 1. Sample and hash

All four samples are hashed above with `sha256sum` from the worktree. The
anonymous flash is built in scratch with
`python3 tools/unitflash_anon.py build -o SCRATCH/flash-anon.bin` and is never
committed. `cmp -l` and `sha256sum` of the flash are read before and after each
boot; no vendor byte is printed or stored in the repository.

### 2. Commands

From the worktree, with `S=/home/marek/projekty/leafre-work/scratch/m8.h54`,
`QEMU=/home/marek/.cache/qemu-ze0/build/qemu-system-sh4`, and
`CARD=archive/sd-images/LEAF_2011-2012_US.img`:

```bash
sha256sum "$CARD" archive/head256.img firmware/unit-flash/nk1-QY7200ND.bin "$S/flash-anon.bin"
python3 tools/ze0_peers/vcan.py --selftest
python3 tools/selftest.py --only ze0_peers.vcan,powermonitor_scan,ze0_launch,unitflash_anon
python3 tools/powermonitor_scan.py archive/head256.img --image-start 0x3e00200 --check
python3 tools/unitflash_anon.py --selftest
sha256sum "$S/flash-anon.bin"; cmp -l "$S/flash-anon.bin" "$S/flash-anon.bin" | head
python3 tools/ze0_launch.py --qemu "$QEMU" --card "$CARD" \
  --flash "$S/flash-anon.bin" --peer vcan --workdir "$S/s1" --timeout 420
python3 tools/ze0_launch.py --qemu "$QEMU" --card "$CARD" \
  --flash "$S/flash-anon.bin" --workdir "$S/c1" --timeout 300
wc -l "$S/s1/serial.log" "$S/c1/serial.log"
tail -3 "$S/s1/serial.log"
grep -a -c 'Pow >>' "$S/s1/serial.log" "$S/c1/serial.log"
grep -a -c 'Pow Off 1st Detect' "$S/c1/serial.log"
grep -a -c 'Application Layer Shutdown Complete' "$S/c1/serial.log"
sha256sum "$S/flash-anon.bin"; cmp -l "$S/flash-anon.bin" "$S/flash-anon.bin" | head
```

The `vcan` control socket speaks `ignition on|off`, `speed KMH`, `reverse`,
`lights`, `soc` and `status` (M8.H50). It was exercised without QEMU with a
standalone `Peer.serve` on a scratch AF_UNIX socket; `status` before and after
`ignition on` / `ignition off` printed the state changes. With no guest
attached, `sent` stayed 0 — the peer has no carrier without the `uat3`
chardev.

### 3. Controls

- **Numbers from commands (mandatory check b):** every count in Observations
  is the output of `wc -l`, `grep -a -c`, `sha256sum`, `cmp -l`, `--selftest`
  or `--check` above; none is transcribed from prose or a ledger.

  (EXP M8.H53 O1); the peer's `encode_frame` refuses an unknown id and an
  oversized payload (M8.H50 O1). A byte missing from the flash file would
  have been caught by the positive mutation detector above.

### 4. Scope

One US 2011 card, one firmware head, one NK1, one anonymous 8 MiB flash,
two L4 boots (one with `--peer vcan`, one without), one peer control-socket
probe, and the four task-relevant selftests. Excluded by hardware access:

### 5. Falsifier

Stated before the result: (1) an unchanged flash file after ACC-off fires
the task falsifier; (2) no `Pow >>` line in the guest log means no completed
shutdown sequence; (3) a boot that stops at `Memory Sections:` when `vcan`
is attached is the M8.H75 blocker. Any of these makes `done` impossible; the
positive controls above must pass first or the negative is void.

## Interpretation

- **FACT:** an 8 MiB anonymous NOR flash boots NK1 + image A to
  `Navi.exe`; the `vcan` peer accepts all documented control commands at
  the tool level (O1, O4, O5).
- **FACT:** the task's persistence loop is **not observed at L4**. The flash
  file is byte-identical before and after both boots; the mutation control
  proves the comparison would catch a real write (O2, O6).
- **FACT:** the guest never enters `ACC_OFF_FIRST` in the 300 s no-peer run:
  zero `Pow >>` lines, zero `Pow Off 1st Detect`, zero shutdown-complete
  lines (O4). With `vcan`, NK1 stalls at the memory-sections line before any
  driver init (O3); M8.H75 owns that routing defect.
- **OBSERVED:** `tools/selftest.py` is red under load for unrelated
  tmpfs/60 s reasons; the four suites this task touches are green in
  isolation (O1, O7). A red full gate is reported, not masked.
- **UNKNOWN:** whether a real ACC-off (once UAT3 is routed, or with a
  hardware L5 run) produces a write to the SRAM/VFlash region. M8.H18 O7
  already showed no erase/program in 400 s; this task does not add a
  positive write sample and cannot confirm the save path.
- **HYPOTHESIS:** `NOTIFY_ACC_OFF_EVENT` → `SystemEXE.exe` → MCT write is
  the save hand-off (C-7509), but it was not executed here.
