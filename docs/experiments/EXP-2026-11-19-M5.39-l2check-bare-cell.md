## Question

Does `l2check --tiles <name>` still report a passing L2 tile gate when the
name is not a file on the card, and does the fix leave the correctly named
run (`B48R058R.DAT`) unchanged on the factory root?

## Hypothesis

At `a90a83f`, `--tiles B48R058R` checks 0 tiles and exits 0 with
`RESULT: PASS` (C-3566). After the change, an explicitly requested name that
is not a `MAPAL001` file exits 2 before any check runs and names the `.DAT`
form, while `--tiles B48R058R.DAT` still prints `tiles=1` and `RESULT: PASS`.
**Falsifier:** the new tool exits 0 (or prints `RESULT:`) for the bare name,
or the `.DAT` run changes its exit code, `tiles=` count or any check line
versus `a90a83f`.

## Interpretation

- **FACT:** at `a90a83f` the bare cell name gives `tiles=0` and
  `RESULT: PASS` on the real factory root (C-3566 reproduced, C-4290).
- **FACT:** with this change the same command exits 2 and names the `.DAT`
  form; the `.DAT` command's output is unchanged (C-4291, C-4292).
- **OBSERVED:** the synthetic branch of `tools/one_tile_pipeline.py` (line
  `"--tiles", cell`) still passes the bare name; it now gets rc=2 instead of a
  silent `tiles=0`. The gate status it reports is unchanged
  (`CANNOT-VERIFY-OFFLINE`); fixing the call is M5.33's scope (C-4294).
- **UNKNOWN:** nothing about firmware acceptance: this is a validator fix
  (rule 13; L3/L4/L5 not touched).

## Conclusion

C-3566's footgun is closed in `tools/l2check.py`: an explicitly requested
`--tiles`/`--semantic-tiles` name that is not a `MAPAL001` file is a usage
error (exit 2) that names the `<cell>.DAT` form, and no `RESULT:` line is
printed. The correct invocation is unchanged on the 480-file EU 2011 root.
The tool gained a vendor-free `--selftest`, so `tools/selftest.py` and the
standing gate now exercise it in CI. Claims C-4290–C-4295 added.
