# EXP-2026-11-08-M8.B4: Boot arguments at phys 0x08000020–0x0800002b (r2)

- **Status:** done
- **Date:** 2026-11-08
- **Sample:** IMG256 (first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img`), SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9` (fetched via `tools/fetch_image.py --image IMG256`, read-only; vendor bytes not committed)
- **Tools:** Python 3.15.0 (stdlib only); repo tools `tools/cerom.py`, `tools/sh4dis.py`, `tools/sh4xref.py`
- **Claims:** C-1340, C-1341, C-1342, C-1343, C-1344, C-1345, C-1346

## Question

What are the boot arguments at physical `0x08000020`–`0x0800002b`, how does `nk.exe` consume them, and what should an emulator (M8) seed there? (Static read of `nk.exe` is sufficient per M8.B4.)

## Hypothesis

The 12-byte region is a diagnostic/version string set by the IPL (not a kernel selector), read by `nk.exe` and printed as a "Navi Version" value (M1.7/C-704,C-705,C-709). Falsifier: finding any `nk.exe` (or other module) branch/dispatch keyed on these bytes, or finding references outside `nk.exe`, or finding a different consumer format than the M1.7 AERTRACE dump.

## Interpretation

- **FACT (C-1340):** Physical `0x08000020`–`0x0800002b` (12 bytes) is the boot-argument region consumed by `nk.exe` on SH-4 via the P2 uncached alias `0xa8000020`–`0xa800002b`. `nk.exe` build B reads it in the AERTRACE dump function at `0x8804cc42` (`.text`, `--image-start 0x3e00200`); build C reads the same region in the corresponding function (refs `0x8804c896`–`0x8804c8ee`, `--image-start 0x5200200`).
- **FACT (C-1341):** `nk.exe` formats the boot args using UTF-16LE format string `Navi Version : %c%c%c%c%c%c%c%c-%c%c%c\r\n` (nk.exe VA `0x8800e5a8`, build B) and prints via `jsr @r9` with `r9=0x8804c1a8`, passing 11 byte values as arguments.
- **FACT (C-1342, refines C-704 count):** `nk.exe` makes 11 literal-pool byte-load references into `0xa8000020`–`0xa800002b` (offsets +0x00..+0x07 and +0x09..+0x0b / P2 `0xa8000020`–`0xa8000027`, `0xa8000029`–`0xa800002b`). Byte at +0x08 (phys `0x08000028`, P2 `0xa8000028`) has **no** `mov.l` literal-pool reference in nk.exe build B or C executable sections. C-704's "12 mov.l loads, one per byte" is inaccurate in count; its scope finding (only nk.exe references the range) is consistent with M1.7 and not re-tested exhaustively across all non-nk modules here.
- **FACT (C-1343):** The AERTRACE consumer performs no compare/branch on the loaded boot-arg byte values (sequence is `mov.b @r3,r3; extu.b r3,r3; mov.l r3,@(disp,r15)` per byte, then print). The region is used diagnostically, not as a kernel/boot selector — consistent with C-705/C-709.
- **OBSERVED (C-1344):** The 11 displayed bytes map to format positions as: bytes @+0x00..+0x07 → the 8 `%c` before `-`, bytes @+0x09..+0x0b → the 3 `%c` after `-`. Byte @+0x08 aligns with the literal `-` in the format string but is not read by this function.
- **HYPOTHESIS (C-1345):** Byte @+0x08 may hold `'-'` (0x2D) or padding in the factory/IPL-written version token; nk.exe does not require reading it for the AERTRACE display. An emulator seeding a plausible token should place `'-'` at +0x08 for fidelity, but behavior of the observed nk.exe dump path does not depend on it.
- **UNKNOWN (C-1346):** The factory 12-byte values for EU 2011 (and the IPL writer/format) are not present in the SD image (C-535/C-706: IPL is on-board flash). Static read of nk.exe establishes consumption/format but not the authoritative byte content. M8 emulation should seed deterministic placeholder bytes (e.g. a documented synthetic version token or zeros) and treat them as non-selecting diagnostic data until IPL/flash evidence provides factory values.

## Conclusion

Static read of `nk.exe` (build B/C, IMG256 `92aa525d…`) characterizes `phys 0x08000020`–`0x0800002b` as a 12-byte P2-accessed (`0xa8000020`–`0xa800002b`) Navi Version boot-arg region read diagnostically by `nk.exe`'s AERTRACE dump and formatted with UTF-16LE `"Navi Version : %c%c%c%c%c%c%c%c-%c%c%c\r\n"` (11 bytes displayed: +0x00..+0x07, literal `-`, +0x09..+0x0b; +0x08 unread by this path). No branch/selection behavior observed. Factory values are IPL-set and unknown from the SD image. M8.B4 is satisfied for emulator bring-up: seed the 12-byte region with a deterministic non-selecting placeholder (recommended: preserve `'-'` at +0x08 for format fidelity) before nk.exe runs; do not treat it as a kernel selector (C-709). Open: authoritative factory byte values require IPL/flash or dynamic capture.
