# EXP-2026-11-08-M1.14: SH-4 decoder debt — one LE reader, a pinned `mov.w`, an oracle

- **Status:** done
- **Date:** 2026-11-08
- **Sample:** first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (EU 2011/2012 SD), SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9` (the `IMG256` read used by the pinned checks)
- **Tools:** `python3` (repo runtime), `zlib` n/a; optional oracle probes: `capstone` (absent on test host) or `sh4*-objdump` (absent on test host) — oracle ran in the pinned `SKIP` mode
- **Claims:** C-2590–C-2599
- **Supersedes:** none (closes M1.11 follow-ups recorded in EXP-2026-11-08-M1.11-sh4dis and resolves C-2489)
- **Superseded by:** none

## Question

Can the M1.11 SH-4 decoder debt be closed without re-deriving firmware conclusions: one shared LE reader for `sh4dis`/`sh4scan`, a pinned real-image positive control for `mov.w @(disp,PC)` (and does the C-2129/C-2540 range use it?), and an independent oracle with a pinned skip/failure mode?

## Hypothesis

`sh4dis.read_u16`/`halfwords_le` can be the single LE implementation; `mov.w @(disp,PC)` (`0x9nnn`) decodes the same mnemonic/literal form as the real POINT walker constants in `fn 0x003f5194` (C-2129 range); the four M1.8 call sites (C-710) are stable decode targets for an independent oracle.

**Falsifier:** `sh4dis.py --check-real` for `nk.exe` changes the `0x88038666` decode; the Navi.exe `mov.w` pins do not read back as the observed constants/pool values; or an available independent oracle disagrees on an M1.8 site (disagreement must be recorded per instruction and the tool not adjusted until explained).

## Method

1. **Sample and hash.** First 256 MiB of the EU 2011/2012 image above, SHA-256 `92aa525d...a007f9`. This covers the build-A/B firmware regions used by the pinned checks (`IMAGE_READ_BYTES` in `sh4dis.py` is 128 MiB).
2. **Commands.** Runnable as written from repo root (image path adjusted to the local archive):
   ```bash
   IMG=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   python3 tools/sh4dis.py --selftest
   python3 tools/sh4scan.py --selftest
   python3 tools/sh4xref.py --selftest
   python3 tools/sh4dis.py "$IMG" nk.exe --image-start 0x3e00200 --check-real
   python3 tools/sh4dis.py "$IMG" Navi.exe --image-start 0x200200 --check-real
   python3 tools/sh4dis.py "$IMG" Navi.exe --image-start 0x200200 --oracle
   python3 tools/selftest.py
   python3 tools/claims_check.py
   ```
   The `--oracle` path probes `capstone` then `sh4*-objdump`; absent probes produce `SKIP` (exit 0). An available oracle that disagrees prints `DISAGREE` per instruction and exits 1; no decoder adjustment is made on disagreement.
3. **Controls.** *Positive*: `nk.exe --check-real` still passes all M1.11 pins including `0x88038666` bytes/mnemonics/target and the four decompressor pool words; Navi.exe `--check-real` decodes `0x9414/0x9112/0x9109` at `0x003f51a8/ae/c2` to the exact pinned text and reads pool `u16` values `0x04e8/0x03ff/0x4e20`; synthetic `mov.w @(disp,PC)` selftest pins `decode(0x9414,0x003f51a8)` with a pool value; M1.8 site constants decode to `jsr @r3`. *Negative*: `sh4dis` selftest keeps the BE-trap case where the same LE prologue bytes read with swapped pairs do **not** yield the prologue and `check_real` fails loudly; an incomprehensible oracle decode path is treated as failure, and absence is `SKIP` (never a pass).
4. **Scope.** `tools/sh4dis.py`, `tools/sh4scan.py`, `tools/sh4xref.py` only. `sh4scan.py` now imports `sh4dis.halfwords_le` (shared LE convention) for its array scan path; it had no `read_u16`/`Mem` class but duplicated LE halfword interpretation logic. No firmware conclusions re-derived. Real-image pins cover: nk.exe uncompressed code/data addresses named above (build B `0x3e00200`) and Navi.exe A `fn 0x003f5194` plus four M1.8 call sites (build A `0x200200`). Compressed sections are not read as code (existing invariant).
5. **Falsifier.** Any change to the `0x88038666` / prologue / pool decode; `fn 0x003f5194` lacking `mov.w @(disp,PC)` loads or loading different pool values; an independent oracle disagreeing on a M1.8 site.

## Interpretation

- **FACT:** `sh4scan.py` delegates LE halfword array decoding to `sh4dis.halfwords_le` (same pinned `ENDIAN_STRUCT` convention); no duplicate LE reader implementation remains in `sh4scan.py`.
- **VERIFIED:** `mov.w @(disp,PC)` (`0x9nnn`) is correctly decoded and literal-read on a real IMG256 sample: `0x9414/0x9112/0x9109` at Navi.exe `0x003f51a8/ae/c2` yield the observed mnemonics and pool `u16` values.
- **VERIFIED:** The C-2129/C-2540 POINT walker range (`fn 0x003f5194`, Navi.exe A) uses `mov.w @(disp,PC)` at three sites; C-2489's "no pinned real-image positive control" is resolved for this addressing mode.
- **VERIFIED:** The `0x88038666` nk.exe flag-test sample still decodes identically (bytes and 6 mnemonics unchanged).
- **OBSERVED (oracle absent):** No independent SH-4 oracle was available on the test host (`capstone` and `sh4*-objdump` absent). The oracle path reports a pinned `SKIP` and exits 0; disagreement handling is implemented (per-instruction `DISAGREE` and stop). Agreement on the four M1.8 call sites is therefore not independently demonstrated on this host, but the sites remain pinned and the code path is ready for an available oracle.
- **HYPOTHESIS:** On a host with `capstone` (SH4 LE) or `sh4*-objdump`, the same oracle command will agree on the four M1.8 call sites; any disagreement would falsify the current decode and must be recorded before changing `sh4dis`.

## Conclusion

M1.14 closes the concrete decoder debt it can close without new firmware conclusions: the LE reader is shared (`sh4dis.halfwords_le` imported by `sh4scan`), `mov.w @(disp,PC)` has a synthetic and real-image pin (resolving C-2489 for that mode) and the C-2129 `fn 0x003f5194` range is confirmed to use it, `0x88038666` still decodes the same, and an independent oracle exists with a pinned skip/failure mode. The only remaining gap is that no Capstone/sh4-objdump oracle was present on this host, so independent agreement is recorded as `SKIP` rather than demonstrated; the implementation will report agreement or stop on disagreement when an oracle becomes available. `docs/research/claims.md` gets C-2590–C-2599.
