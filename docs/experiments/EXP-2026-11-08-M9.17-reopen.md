- **Status:** done (negative: blocked on a compressed `.data` section; both controls PASS)
- **Date:** 2026-11-08

  `LEAF_2011-2012_QSD-309-101_navi158_eu.img`, `archive/head256.img`, SHA-256

- **Tools:** python 3 (stdlib), `tools/cerom.py` (`romhdr`, `va2file`,
  `sections`, `memmap`), `tools/l3_harness/rommap.py convert`,
  `tools/l3_harness/runner.py` (`targets`, `run`, `selftest`) with the PySh4

- **Supersedes:** none

## Question

Does `runner.py run` execute the M3.8 reader (`Navi.exe` VA `0x0041a438`,
`MMAIN001.DAT` open/read, C-1780–C-1789) as a module entry, returning a verdict
for the factory file, with the `0x1000`-byte read and a 4095-byte rejection
checked, now that M9.20 merged?

## Hypothesis

With M9.20 on `main`, the reader VA can be declared (`entry.kind = "module"`),
mapped from the memory map and run. Falsifier: the run finishes at the return
sentinel with an `r0` in the verdict map, or it stops on an error that is not a
missing mapping (for example a missing stub), which would show the reader is
reachable. The negative expectation was a block on the reader's first data
access, because the M3.8 reader's neighbourhood touches `Navi.exe` data and
the data sections of build A are compressed (AGENTS.md).

Dependencies: M9.5 done (`[x]`), M3.8 done (`[x]`), M9.20 merged (`562215a`).
M9.22 is open on `main`; its block (B30R048R rebuild assertion) contains no
input-region work, so it does not provide one (see Interpretation).

## Method

1. **Sample and hash.** `archive/head256.img`, SHA-256 above; `cerom` hashes
   the first 134217728 bytes (`image_sha256_scope`), which the runner rechecks.
2. **Commands** (run from the repo root; `<scratch>` is an empty directory
   outside the repo; the scratch targets file is `tools/l3_harness/targets.json`
   plus one appended row, written by the one-line script below):

   ```bash
   IMG=archive/head256.img
   python3 tools/cerom.py --image-start 0x200200 $IMG romhdr
   python3 tools/cerom.py --image-start 0x200200 $IMG va2file 0x0041a438
   python3 tools/cerom.py --image-start 0x200200 $IMG sections Navi.exe
   python3 tools/cerom.py --image-start 0x200200 $IMG memmap --modules Navi.exe --out <scratch>/rommap_navi.json
   python3 tools/l3_harness/rommap.py convert --report <scratch>/rommap_navi.json --out <scratch>/rommap_navi_l3.json --skip-compressed
   python3 -c "import json,sys; d=json.load(open('tools/l3_harness/targets.json')); d['targets'].append({'name':'mmain_reader','reader':'mmain','what':'M3.8 reader scratch probe','module':'Navi.exe','entry':{'kind':'module','module':'Navi.exe','va':'0x0041a438','endian':'little','args':['0x0'],'verdict_map':{'0x0':'ACCEPT','0x1':'REJECT'},'note':'scratch'},'stubs':[],'expect':{'verdict':'ACCEPT','rule':'probe'}}); json.dump(d,open('<scratch>/targets_mmain.json','w'),indent=1)"
   python3 tools/l3_harness/runner.py targets --targets <scratch>/targets_mmain.json
   python3 tools/l3_harness/runner.py run mmain_reader --targets <scratch>/targets_mmain.json --rommap <scratch>/rommap_navi_l3.json --image archive/head256.img --engine pysh4 --json
   python3 -c "open('<scratch>/zlib_head.bin','wb').write(bytes([0x78,0x9c,0,0]))"
   python3 tools/l3_harness/runner.py run probe-zlib-cmf --engine pysh4 --input <scratch>/zlib_head.bin --json
   python3 tools/l3_harness/runner.py selftest
   python3 tools/l3_harness/selftest.py
   python3 tools/selftest.py
   python3 tools/claims_check.py
   ```

   The scratch row's `args` is `0x0`, so the reader's `dest` is the fixed
   buffer `0x00e23cc0` (C-1784), a value that is not in any mapped region. The
   row was written only to `<scratch>`, not to the repo; `targets.json` is
   unchanged.
3. **Controls.** *Positive, runner path:* `probe-zlib-cmf` on PySh4 with the
   4-byte zlib head `78 9c 00 00` (expected PASS, ACCEPT). *Positive, module
   path:* the M9.20 module fixture in `tools/l3_harness/selftest.py` (a
   synthetic `r0 = r4 + 1` function at a mapped VA; part of the 32 checks).
   *Negative:* the same run with a scratch row whose VA is outside every
   loadable block (`0x00001000`) must be `BLOCKED`; observed
   `BLOCKED, entry VA 0x00001000 is outside every loadable block of Navi.exe`.
   The `UNMAPPED` result below is the observed block on the real reader VA.
4. **Scope.** `Navi.exe` only (`--modules Navi.exe`), within `head256.img`.
   Covered: section 0 (`r-x`, `0x00011000`, `0x0054bd16` bytes) as one mapped
   block. Excluded: section 1 (`0x0055d000`, `rw-`, `COMPRESSED`, vsize
   `0x00ff16ae`) and section 2 (`realaddr 0x0154f000`, `COMPRESSED`, psize
   `0x00008884`), which `rommap` skips (`2 skipped`). Build A's compressed
   share is 56.2 % (AGENTS.md); `Navi.exe` is 75.1 % compressed.
   Counted corpus: 1 reader VA; 1 module block mapped; 2 compressed sections
   skipped; 0 `MMAIN001.DAT` files read; 1 positive control per path; 1 real
   module run.
5. **Falsifier.** The claim "the M3.8 reader runs as a module entry on the
   factory image" is refuted if the run ends at the return sentinel with `r0`
   in the verdict map, or stops with a missing-stub error rather than a
   mapping error. Also refuted if the first data access lies in a mapped
   section.

## Interpretation

- **FACT (tool):** the M9.20 module path runs on the real image up to a data
  access at `0x0055d040`, which lies in `Navi.exe` section 1, a compressed
  `rw-` section that the memory map skips. The run stops as `BLOCKED`
  (`UNMAPPED`), with no verdict.
- **FACT (tool):** the first data access is not in a mapped section, so the
  reader's result on the factory file is unknown; nothing about
  `MMAIN001.DAT` is decided by this run.
- **OBSERVED:** the `r4 = 0` argument is not the blocker; the reader's `dest`
  falls back to `0x00e23cc0`, which the harness does not map either. A caller
  buffer in the heap would be the input region; that is a runner argument
  change, not a file input.
- **HYPOTHESIS:** mapping section 1 zero-filled would let the run get further,
  but its bytes are unknown, so any result from it would not be evidence about
  the firmware. Not done.
- **UNKNOWN:** which instruction issues the access at `0x0055d040`; whether
  the reader also needs the imports it calls (`memset`, `wcstombs`, `strncat`,
  the open/read/close helpers) bound through `Navi.exe` data in section 1.

Dependency check: M9.22 (open) is about the `B30R048R` rebuild assertion; its
block has no input-region work. Its conditional in the task ("if the page
argument needs an input region, M9.22 adds it") therefore does not apply, and
the blocker is the compressed section, not an input region.

## Conclusion

M9.17 is **blocked**, not done. The M9.20 plumbing works on the real image: the
M3.8 reader VA is declared, mapped and run, and the run reports `BLOCKED` at the
first access to a compressed `.data` section. The `0x1000`-byte read and the
4095-byte rejection are not checked. Unblock: **M1.2f** (port `DECOMP_BLK`), so
section 1 can be mapped. `targets.json` is unchanged; no `mmain_reader` target
is committed, because the verdict map (`r0` values for failure) is not
established by M3.8, and a guessed map would be a fitted verdict. Claims
C-2372–C-2373 record the observed block and the map; the older
C-2370–C-2371 stand unchanged.
