# EXP-2026-11-06-M5.9: content-matched tile diff with named records

- **Status:** done
- **Date:** 2026-11-06
- **Sample:** synthetic three-record tile pair generated by
  `tools/tile_diff.py --selftest` (`SYNTHA.DAT`, `SYNTHB.DAT`, 55,040 bytes each).
  No vendor data is present on this machine (`archive/` empty, no `B*R*R.DAT`
  anywhere under `/`), so the M5.8 factory/mutate pair could not be re-diffed
  here — see Limits.
- **Claims:** C-1850
- **Supersedes:** none
- **Superseded by:** none

## Question

Can a one-tile diff report a recompressed record that also moved as **one
changed stream at A -> B**, named by section/level/directory/slot/record and by
the vertex that moved, instead of the M5.8 "removed at A + added at B" pair?

## Hypothesis

Yes, if streams are indexed by inflated SHA-256 and the leftovers are paired by
their structural position from the container walk (`clarion_tile.read_tile`):
content equality turns a move into a "moved" pairing, and a differing hash at
an unchanged structural position turns an edit into one changed pair carrying
both offsets. Only streams with no positional counterpart are add/remove.

| Synthetic records | dir (1,1)/(2,2)/(3,3), one 68-byte section-1 record each |

The record *plain* bytes are deterministic; the file hashes above are specific
to this zlib build (the compressed members can differ across zlib versions), so
they are anchors, not portability checks.

## Method

The tool changed from offset matching to content matching:

1. Inventory. Every zlib stream is collected twice and merged by file offset:
   the container walk names all declared records (`section`, `level`, `dir`,
   `slot`, `rec`, plain bytes), and a byte scan (`78 xx` for X08-02-00,
   `58 85` for X08-03-00) catches streams the walk cannot reach. Structural
   walk failure is not fatal: the scan alone still diffs, with `record: null`.
2. Matching. Streams are paired first by inflated SHA-256 (preferring the same
   structural position, then the same offset). A hash match that changed offset
   is `moved`; a recompression (same plain, different compressed bytes) stays
   `same` and is counted in `reencoded`. Unmatched streams are then paired by
   `(section, level, dir, slot, rec)` and reported as one `changed` entry with
   `offset_a`/`offset_b`; offset pairing remains only as a fallback for unnamed
   streams, so two different named records at one offset are never fused.
3. Naming. A changed pair is described with the most specific layout available:
   background record -> layer/group/shape/vertex (from `clarion_bg`), else
   section-4 record -> parcel/type/country/name delta (`section4.py`), else
   record header words, else byte-level first-diff.
4. `--by-offset` keeps the M5.8 offset-keyed view; JSON always carries both
   views with a fixed key set.

Synthetic tile pair (`make_synthetic_tiles`): one section (id 1), one level
(level 1), three directories `(1,1)`, `(2,2)`, `(3,3)`, each with one slot and
one background record. Tile B differs in exactly two ways: the `(3,3)` record's
first vertex is shifted by `(+40, 0)` parcel units (so that stream also moves),
and the block write order becomes `(0, 2, 1)`, which moves the untouched `(2,2)`
stream to a new offset. The `(1,1)` record keeps position and content.

```bash
python3 -m py_compile tools/tile_diff.py
python3 tools/tile_diff.py --selftest

# demo pair (the self-test writes its own; this reproduces it in a directory)
python3 - <<'EOF'
import sys; sys.path.insert(0, "tools")
import tile_diff
print(tile_diff.make_synthetic_tiles("/tmp/opencode/m5.9-demo"))
EOF

python3 tools/tile_diff.py /tmp/opencode/m5.9-demo/SYNTHA.DAT \
    /tmp/opencode/m5.9-demo/SYNTHB.DAT
python3 tools/tile_diff.py /tmp/opencode/m5.9-demo/SYNTHA.DAT \
    /tmp/opencode/m5.9-demo/SYNTHB.DAT --by-offset
python3 tools/tile_diff.py /tmp/opencode/m5.9-demo/SYNTHA.DAT \
    /tmp/opencode/m5.9-demo/SYNTHB.DAT --json

python3 tools/selftest.py --only tile_diff
```

## Interpretation

- **FACT:** A recompressed stream that also moved is reported once as a change
  with both offsets and its structural position; the M5.9 done-when counts hold
  on the synthetic pair (`changed=1`, `added=0`, `removed=0`).
- **FACT:** An untouched stream written at a new offset is reported as `moved`
  with the same plain SHA-256 on both sides, and the offset view misreports the
  same pair as two changes — the reason for the content view.
- **FACT:** Structural naming is optional: with no parseable container (or with
  `tools_ze0` absent) the diff still pairs content and falls back to byte-level
  descriptions.
- **OBSERVED:** A content-identical recompression is counted in `same` and
  flagged by `reencoded`, so writer work can separate "recompressed" from
  "edited".
- **UNKNOWN:** The M5.8 factory-vs-mutate pair (expected `changed=1`,
  `added=0`, `removed=0`, level 1, dir 42/65424, vertex 1
  `(1943,1580) -> (1983,1580)`) could not be re-run here because no vendor tile
  is present on this machine. The synthetic pair exercises the same code path
  (same reader, same pairing, same vertex walk), but that is not a substitute
  for the factory check.

## Conclusion

`tools/tile_diff.py` no longer reports a moved edit as remove+add: streams are
content-indexed, leftovers are paired by structural position, and the change is
named down to the vertex where the layout is known. The offset view is kept
behind `--by-offset` (and inside `--json`), so the M5.8 report can still be
reproduced. No format-doc change follows from this task — the tool reports
existing knowledge; the claim is recorded here only.
