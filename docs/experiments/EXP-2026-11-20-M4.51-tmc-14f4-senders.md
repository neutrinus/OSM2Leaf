## Question

Which function (EU2011) sends the TMC data-layer message `0x14f4` (the second request type on the TMC handler `0x004003f4`, C-5376), and which file and offsets does that request read?

## Hypothesis

A data-layer request is a small struct whose `u16` at `+8` is the message id (the dispatcher `0x004124dc` reads `@(8,msg)`, C-3553), sent through one helper; the sender of `0x14f4` loads `0x14f4` (or a value that becomes it) and calls that helper. **Falsifier:** a caller of the send helper (or a function in another module) that loads `0x14f4`; the negative holds only if the census of the send helper's callers recovers one known id per caller (control) and none is `0x14f4`.

## Observations

- `0x003c0e68` has 25 static callers; `0x003c01c8` has one (`0x003c0e68`). `0x003c0e68` imports `OSM_Printf`, `OSM_TaskSend`.
- Census (`--callers-of 0x003c0e68`): every caller holds exactly one id literal: `0x14cc` ×5 (`0x003b65c0`, `0x003b6948`, `0x003b6af0`, `0x003b6bf0`, `0x003b7018`), `0x14cd` ×7 (`0x003a3c9c`, `0x003a5344`, `0x003a5fb4`, `0x003a9828`, `0x003aa5e0`, `0x003ac4ec`, `0x003be050`), `0x14d0` ×1 (`0x003b684c`), `0x14d1` ×1 (`0x003ae9b0`), `0x14d3` ×1 (`0x003b6cf4`), `0x14d8` ×2 (`0x003b3ce4`, `0x003bfae8`), `0x14e4` ×1 (`0x003bcac0` at `0x003bcb48`), `0x14ef` ×3 (`0x003b0474`, `0x003b8d04`, `0x003ba9bc`), `0x14f0` ×4 (`0x003a87e8`, `0x003aa79c`, `0x003b6f00`, `0x003baac0`). **No `0x14f4`.**

- DLLs: `0x14f4` loads 0 and `0x14e4` loads 0 in OBJDLL, STDDLL, OSMDLL, RASTERIZER_DLL, ScreenState, IconDrawCC, RDSCC.

## Interpretation

- **VERIFIED (C-5404):** EU2011 data-layer requests are sent through `fn 0x003c0e68` (message id `u16 @(8,req)`, `OSM_TaskSend`); its 25 static callers each carry one id literal, and the TMC location-record request `0x14e4` has exactly one static sender, `fn 0x003bcac0` (the `sdl_rdstmc_search_non_cache` path, C-885).
- **OBSERVED (C-5405):** message `0x14f4` has no static sender: no caller of the send helper and none of seven DLLs loads `0x14f4`; in the four data-layer users disassembled, `0x14f4` is only compared, never stored into a new request (three users not disassembled). Six other dispatcher ids have no static sender either (`0x14f5`, `0x14e5`, `0x14ce`, `0x14d2`, `0x14e8`, `0x14e9`), so "no static sender" is common for this dispatcher and does not by itself mean `0x14f4` is unused.
- **HYPOTHESIS (C-5406):** `0x14f4` requests are built at run time (an id taken from a table or a caller argument, or sent through an indirect call of the helper), most likely by the traffic display/route code when a TMC event is placed — the place the RDSTM link groups would be consumed.
- **UNKNOWN (C-5407):** which file and offsets a `0x14f4` request reads; the link-group reader VA (M4.49).
- **Block (C-5408):** done-when not met; stop reached (no static sender in `Navi.exe` and the DLLs it imports for map/TMC work, and no L4 run reaches TMC). Unblock: M4.53 (L3: feed the data layer a synthetic `0x14f4` request and watch the file/offset it reads) or M8.E4 (full `Navi.exe` run, read watch on `RDSTM001.DAT` `0xcda000`/`0xe78500`/`0xeb6200`).

## Conclusion

M4.51 is `blocked`; the next step is dynamic — either the data layer in L3 with a synthetic `0x14f4` request (new task M4.53) or a full-system run (M8.E4).
