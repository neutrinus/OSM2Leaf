## Question

Does `verify_factory` reject a **legal-but-wrong parcel set** — a tile where a
parcel the input says must be written keeps its factory bytes, or a parcel
holds ways that belong in a neighbouring directory — or does it only re-check
the splice it was handed?

## Hypothesis

`verify_factory` (tools/tilewriter.py) rejects "a section-1 record changed but
was not in `built`" and "a directory changed but was not regenerated". The
M5.61 falsifier is the **reverse**: `--drop-parcel 80,944,5,3` skips a real
parcel's ways, so that parcel is byte-identical to factory and nothing in the
`built`-vs-observed loop fires; `tilewriter_rc` stays 0 (EXP-2026-11-21-M5.61
§7). The missing check is therefore *declared-vs-observed*, in both directions:
a parcel the caller **declared** it wrote must differ from factory, and a
parcel that **differs** must be declared. **Falsifier:** a guard that still
accepts the `--drop-parcel` tile, or that rejects a genuine `B50R050R` build.

## Method

1. **Sample and hash.** Factory tile and cut PBF as above; the cut is rebuilt
   from `~/projekty/leafre-work/osm/poland-latest.osm.pbf` with
   `scratch/m5.68/cut4.py` under `scratch/m5.69/venv` (pyosmium). The old
   M5.61 SHAs (`6400851b…`/`7c6ea211…`) are a different cut and are **not**
   this run's numbers.

2. **Commands.** Run from the repo root; `$S` is the scratch dir.

   ```bash
   S=~/projekty/leafre-work/scratch/m5.71
   FAC=/home/marek/projekty/leafre-work/m5.4/card-factory
   # (cut already produced: sha256sum $S/cut-B50R050R.osm.pbf)

   # Positive: a fresh real B50R050R level-1 build
   python3 tools/m5_61_build_tile.py --osm "$S/cut-B50R050R.osm.pbf" \
       --cell B50R050R --level 1 --factory-root "$FAC" \
       --out "$S/real.tile.DAT" --scratch "$S" --report "$S/real.json"

   # Negative: the M5.61 falsifier — a real parcel left factory
   python3 tools/m5_61_build_tile.py --osm "$S/cut-B50R050R.osm.pbf" \
       --cell B50R050R --level 1 --factory-root "$FAC" \
       --out "$S/neg.tile.DAT" --scratch "$S" --report "$S/neg.json" \
       --drop-parcel 80,944,5,3

   # l2check reachability on the real tile
   mkdir -p "$S/l2root/MAPAL001"
   cp "$S/real.tile.DAT" "$S/l2root/MAPAL001/B50R050R.DAT"
   python3.13 tools/l2check.py --root "$S/l2root" --partial --no-golden --no-cmp \
       --semantic-tiles B50R050R.DAT --factory-root "$FAC" \
       --parcel-declared "$S/B50R050R-L1.declared.json" --skip-mutation
   ```

3. **Controls.** *Positive:* the fresh real `B50R050R` build must pass
   `verify_factory` (it writes `declared==built`). *Negative:* the
   `--drop-parcel 80,944,5,3` build must fail, naming the parcel. *Set-equality
   control:* two identical record streams at two parcels, one left factory,
   must fail (a value-set comparison would miss it; the position-keyed walk
   catches it) — `tilewriter --selftest`. *SKIP-not-pass control:* l2check with
   no `--factory-root` must be SKIP in the JSON, never PASS.

4. **Scope.** Section-1 **level 1** of `B50R050R`; sections 2/4, `LEV3456R`,
   `REFER001` and assets are the factory's. Names are off (`--no-names`), the
   M5.61 clause. This is a *tool* result (L1/L2), no firmware reader (L3) and no
   hardware (L4/L5). The new check reuses `records_by_position` (the
   `verify_factory` walk), no new decoder.

5. **Falsifier.** As in the Hypothesis.

## Interpretation

- **FACT:** `--drop-parcel 80,944,5,3` makes `m5_61_build_tile.py` exit 1 with
  `tilewriter_rc: 1` and the message naming `80,944,5,3` (§2). Before this
  change the same command exited 0 (EXP-2026-11-21-M5.61 §7).
- **FACT:** a fresh real `B50R050R` build still passes at 0 (§1), and l2check
  reaches the check and both PASSes and FAILs it (§3).
- **OBSERVED:** the guard works by comparing the caller's **declared** parcel
  set (OSM alone, before `--drop-parcel`) with the observed section-1 diff,
  both directions, keyed by record position.
- **HYPOTHESIS:** this closes the M5.61 hole for the drop-rule and the
  wrong-directory cases; it does not prove the *values* written are the right
  road geometry (that is `readback`/`tile_semantic`), only that the changed
  parcel *set* matches the declared one.
- **UNKNOWN:** whether a writer that puts a parcel's ways in the wrong **slot
  within the same parcel** is caught — the guard keys on `(dir, slot, pair)`,
  so a swap *between* parcels is a diff at both positions and is caught, but a
  within-parcel permutation that keeps the same parcel set is not in scope.

## Conclusion

`tools/tilewriter.check_declared_parcels` adds the missing reverse check to the
factory splice: it fails when a declared parcel is byte-identical to factory
(the M5.61 `--drop-parcel` falsifier, named) and when a changed parcel is not
declared (a directory written from a neighbour). `tools/m5_61_build_tile.py`
computes the declared set before `--drop-parcel`; `tools/l2check.py` reaches it
as `tile_parcel_guard`. Positive control (fresh real `B50R050R`) passes,
negative control fails naming `80,944,5,3`, and the selftests cover the moved
slot, untouched factory, lost duplicate and SKIP-not-pass cases. Claims
C-6820–C-6829; no `docs/format/` change (tool/gate only). Still open: the
within-parcel permutation and the underlying road *values* (L3/L4).
