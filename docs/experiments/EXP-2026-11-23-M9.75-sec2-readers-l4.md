# EXP-2026-11-23-M9.75 — Section-2 readers caught in a running Navi.exe (L4 route, read watchpoints)

- **Status:** done for framing and the link key (L4); the meaning of the
  remaining link words (one-way, regulation) is follow-up M4.98
- **Date:** 2026-11-23
- **Sample:** EU 2011 card `105e2032…076307` with the map code set from the
  unit's NK1 header (`card_mapcode.py set --from-nk1`, M8.C1m), factory tile
  `MAPAL001/B48R068R.DAT` `76aa5246…d3e60e`; firmware `nk1-QY7200ND.bin`
  (repo) + card image A (EU 2011 build A `Navi.exe`); the owner's unit flash
  dump (`nand.bin`, never in the repository). From-zero tile of M5.100
  (`0717a913…`, our `l2b.DAT`).
- **Tools:** QEMU 11.1.3 + `tools/qemu-ze0` patches; `tools/ze0_launch.py
  --flash … --ui-start`, panel peer taps, `tools/ze0_sdtrace.py`,
  `tools/ze0_sec2_watch.py` (new: `watch`, `decode`, `frame`, `--selftest`),
  `tools/ze0_gdb.py`, `tools/sh4dis.py`, `tools/tile_relayout.py`.
- **Claims:** C-9910–C-9916 (C-9917–C-9919 reserved)
- **Supersedes:** none. Answers M9.75 by L4 instead of L3; M9.74 and M4.55
  stay as negative L3 results (their reader is not in the reply path, which
  this run confirms).
- **Superseded by:** none

## Question

A from-zero map draws roads but cannot route until it carries section 2 (the
route graph). The L3 chain that should give its grammar stalled (M4.55 →
M9.74 → M9.75): the code that walks unit 0 never ran in the L3 engine. Does the
full emulator compute routes, and which code reads which section-2 bytes while
it does?

## Hypothesis

In L4 (`-M ze0`, NK1 + unit flash) the real Navi.exe computes a route from
the map menu, and gdb read watchpoints on the unit pointers that the RPF
request buffers hold catch the walker. Falsifiers: no route on the factory
card; the watchpoints record 0 reads while the route is computed; or a card
without section 2 routes the same as the factory card.

## Method

1. Route on the factory card. Boot NK1 to the map (consent taps 277,98 ×2,
   403,98), drag the map (300,240 → 100,300), Map Menu (763,267), New
   Destination (130,377). The serial log's `NAVI_ROUTE_CC_NTF_*` events and the
   screen are the verdict. SD trace (`trace-event sdcard_read_block on`,
   `ze0_sdtrace.py`) per phase.
2. The same steps on two cards that differ only in `B48R068R`:
   - **from zero:** the M5.100 tile, section 2 empty (`tile_relayout.empty_model`);
   - **hybrid:** the same tile with the factory section 2 put back verbatim
     (`read_model` of both tiles, section id 2 swapped, `write_model`,
     `pad_directory_reads`), so section 1 is ours and section 2 the factory's.
3. Read watch (factory card). After boot, `ze0_sec2_watch.py watch LOG
   --window 0x800` (run 1) and `--window 0x10000` (run 2): breakpoint on the
   RPF reply handler `0x00336dc0`; at each hit read the RPF buffers
   `0x0061a020`/`0x00619818`/`0x0061a848` and set `Z3` on each new unit-0 and
   unit-2 pointer of a kind-8 entry. Then drag (premap) and route. `decode`
   recomputes each access address from the load instruction (QEMU's stop
   reply names the watch start, not the access).
4. Framing check on the whole tile: `ze0_sec2_watch.py frame B48R068R.DAT`
   walks every section-2 record with the rule read off the walker.
5. Controls:
   - **Positive (watch live):** the header reader hits land on fixed record
     offsets (+0, +12, +14, +20, +22, +28, +30, +52) in every record, and the
     walker's node reads land on node starts whose spacing the rule predicts.
   - **Negative (route needs section 2):** the from-zero card.
6. Scope: EU 2011 build A, level-1 records of the London tile, one route per
   run. Not run: US 2011, level-2 records, turn restrictions, a one-way
   mutation (M4.98).

```bash
python3 tools/ze0_sec2_watch.py --selftest
python3 tools/ze0_launch.py --qemu $QEMU --card CARD.img --flash $DUMPS/nand.bin \
    --workdir RUN --gdb 1240 --ui-start --timeout 3000 &
# … consent taps, then:
python3 tools/ze0_sec2_watch.py watch RUN/watch.jsonl --window 0x10000 --max-watch 16 --seconds 2400 &
# drag, Map Menu, New Destination (panel.ctl taps), then:
python3 tools/ze0_sec2_watch.py decode RUN/watch.jsonl
python3 tools/ze0_sec2_watch.py frame $FAC/MAPAL001/B48R068R.DAT
```

Walker `0x003534d4` (static, from `sh4dis`): for each mesh entry (32-byte
stride, count at context `+28`) it takes the node count from unit 0, starts at
unit 0 + 52, and for each node writes a 12-byte index entry (node pointer,
`mesh index << 24 | running link index`, flag `0x100000` when the node has fewer
than three links and its x or y is 0 or `0x7ff`, the mesh edge). The link size
in halfwords is

`7 + ((w2 & 0x3fc0) >> 6) + (w1 & 1) + (w2 & 0x3f) + (w3 >> 14)`

with `w1`…`w3` the link's words 1…3. The route-search reader `0x0035866e…`
uses the same sum.

Framing check (`frame`, factory `B48R068R`): level 1, 45,184 records
(3,923,780 nodes, 9,215,626 links), the walk ends exactly at the unit-0 length
in **45,184**; level 2, 3,214 records with a unit 0 (another 3,214 have none),
exact in **3,214**. Links with `w1 & 1`, `w3 >> 14` or `w2 & 0x3030` set: **0**
at both levels. With the viewer's rule
(`clarion_rd.parse_record`, `((w5 >> 6) & 0x3f) + (w5 & 0xf)`) the result is the
same 45,184/45,184, because those bits are all zero in London.

## Interpretation

- **FACT:** L4 computes and draws a route on the factory card from Map Menu →
  New Destination. With section 2 empty, the same tap gives `CALC_ERR_NBR` and
  "There is no road in the current area" (C-9910).
- **FACT:** with the factory section 2 under our section 1, the route is
  computed (same event counts as the factory card) but no route line is drawn
  (C-9911).
- **FACT:** in the guest, a kind-8 RPF entry's unit-0 pointer is record + 54
  (27-halfword header), and the premap pass reads the header offsets of units
  0, 1 and 2 at the VAs in the table (C-9912, C-9913).
- **FACT:** `0x003534d4` walks unit 0 as node count (u32) → nodes from +52
  bytes → node = 3 words, link count = word 0 `>> 12` → link = 7 words + the
  extra count above (C-9914). VERIFIED on every London record (45,184 level 1, 3,214 level 2); the level-2 records were not watched in the guest. The
  firmware's extra count has three terms the viewer lacks (`w1 & 1`, `w3 >> 14`
  and the wider `w2` masks); London never sets them, so a writer must keep
  them zero or size the link the firmware's way.
- **FACT:** the route search `0x00358382…` finds a link in unit 0 by
  `(word 4 & 0xf, word 3 & 0x1fff)`, the class and link id that M4.39 found
  join section 2 to section-1 road shapes (C-9915).
- **HYPOTHESIS:** the hybrid draws no route line because the route is drawn
  through that key: the factory links' `(class, id)` name factory shapes that
  are not in our section 1 (C-9916). Test: give our section-1 shapes the same
  `(class, id)` as the factory links they follow, or build both sections from
  OSM with shared ids (M5.57).
- **UNKNOWN:** which words carry one-way, travel time and turn restrictions.
  The search reads beyond word 4 only after a match, and the 0x800/0x10000
  windows plus the 4,000-hit cap stopped before the matched-link reads.
- **OBSERVED:** watched pages slow the guest a lot: with 16 × 64 KB windows one
  route took more than 15 minutes of host time and the route had not finished
  when the hit cap was reached. Small windows on the matched link are the next
  step.

## Conclusion

The section-2 reader that the L3 chain could not reach runs in L4 by itself,
both in the premap pass and in the route search, and the gdb read-watch gives
its reading VAs. The framing of unit 0 (node count, node, link with variable
extra words) is now read off firmware and checked on every London record; the
route search looks up links by the M4.39 key. A from-zero card needs section 2
to route at all, and section 2 must share link ids with section 1 for the
route to be drawn. Next: watch the matched link's words during a search and
flip one of them (M4.98); then write section 2 from OSM (M5.57) with the
framing and key above.
