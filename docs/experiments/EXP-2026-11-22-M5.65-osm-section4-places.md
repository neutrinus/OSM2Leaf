# EXP-2026-11-22-M5.65: OSM place names in a tile's section 4

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** EU2011 factory `MAPAL001/B48R050R.DAT`, 68,663,808 B, SHA-256
  `9b0c5c3bcb1f0810ae9d697fdc5cf484eb46b00c2a8fab95e74682c1dda278f5`;
  IMF `B48R050R-L1.imf.jsonl`, 1,837,383,144 B, SHA-256
  `0c25b05da33fb30d72bd45e0c2a588e41588f66bd37388bd566f3d720d970a6f`
- **Tools:** `python3` 3.15.0 / zlib `1.3.1.zlib-ng` (compile and runtime);
  `python3.13` 3.13.17 / zlib 1.3.2 stock (not the pinned 1.3.1);
  `tools/section4.py`, `tools/section4_places.py`,
  `tools/ze0-viewer/harness.py`, `tools/ze0-viewer/ze0_section4.py`,
  `tools/ze0-viewer/tools_ze0/clarion_tile.py`, `tools/l2check.py`,
  `tools/imf_check.py`. `python3 tools/zlibinfo.py` → `1.3.1.zlib-ng`;
  `python3.13 tools/zlibinfo.py` → `1.3.2` (stock).
- **Claims:** C-6650–C-6659
- **Supersedes:** none
- **Superseded by:** none

## Question

Can a generated EU2011 Poland tile's section-4 place-name index carry OSM
`place=*` names from the IMF input, while keeping every undocumented byte and
every other tile byte in place, and can `section4.py verify`, L2 semantic and
the viewer all accept the result?

## Hypothesis

M4.21's `encode_build` refuses names without a `payload_hex` base because the
name-list placement grammar is unknown; therefore the only safe way to add a
name is to start from a **factory named record** and substitute the text bytes
of an existing `d=NAME` slot with an OSM name folded to CP1252 **of exactly
the same byte length**. That changes no prefix, NUL, offset or opaque byte, so
no new grammar is needed and the rest of the tile can stay byte-identical.

**Falsifier:** a generated payload that `section4.py verify` accepts but whose
viewer shows a name from outside the tile's bbox, or a tile whose section-1
records change / gain parse errors, or a no-input run that is not
byte-identical to the factory tile.

## Method

A **spec**, not a narrative. Five parts, in this order:

1. **Sample and hash.** The files and hashes above. The section-4 bbox is read
   from the tile header (`0x2ac`): lat 48.000..53.217, lon 20.000..23.917.
2. **Commands.** Runnable as written; scratch names are under
   `~/projekty/leafre-work/scratch/m5.65/`.

   ```bash
   python3 tools/section4_places.py --selftest
   python3 tools/selftest.py --only section4_places

   S=~/projekty/leafre-work/scratch/m5.65
   T=~/projekty/leafre-work/m5.29-factory-root/MAPAL001/B48R050R.DAT
   I=~/projekty/leafre-work/scratch/m5.68/B48R050R-L1.imf.jsonl

   python3 tools/section4_places.py build --tile "$T" --places "$I" \
       --out "$S/B48R050R.DAT" --report "$S/report.json" \
       --min-names 10 --max-names 40
   python3 tools/section4_places.py build --tile "$T" \
       --out "$S/B48R050R-control.DAT" --report "$S/report-control.json"

   python3 tools/section4.py verify "$S/sec4-changed.bin"
   sha256sum "$T" "$S/B48R050R-control.DAT" "$S/B48R050R.DAT"

   cd tools/ze0-viewer
   python3 harness.py info "$S/B48R050R.DAT"
   python3 harness.py verify "$S/B48R050R.DAT"
   python3 ze0_section4.py "$S/B48R050R.DAT" "$S/sec4.geojson"
   python3 harness.py --selftest
   cd ../..

   python3 tools/l2check.py --root "$S/card" --no-golden --no-cmp \
       --skip-mutation --tiles B48R050R.DAT \
       --semantic-tiles B48R050R.DAT --json "$S/l2.json"
   ```

   `sec4-changed.bin` is the 37 changed zlib records joined with a zero byte;
   it is derived from the output tile by the reader already in `clarion_tile`
   (`rec['raw']` filtered to the 37 `(dir, slot, k)` locators in `report.json`).
   The card root `$S/card` is a symlink tree of the extracted EU2011 factory
   root with only `MAPAL001/B48R050R.DAT` pointing at the generated tile.

3. **Controls.** *Positive*: the factory tile's own section-4 names survive a
   no-input build byte-identically; `harness.py verify` on the generated tile
   reports the factory's exact `records ok 84373 bad 25`; the viewer prints
   OSM names such as `Nowy Targ` and `Gorlice`. *Negative*: a run with no
   `--places` changes 0 records and reproduces the factory SHA-256; a
   wrong-length substitution is refused by `section4_places.py --selftest`;
   a 40th candidate whose rebuilt slot block would need 524 B of a 512 B slot
   is skipped rather than allowed to overrun the next block.
4. **Scope.** EU2011 factory `B48R050R` only: 304 section-4 records, 1,231
   candidate `d=NAME` slots after filtering non-`0x0009` records, 332 OSM
   `place=town|city` nodes inside the tile bbox; 37 names were written. The
   IMF is 1,837,383,144 B and was streamed, not copied. Excluded: `REFER002`,
   POIs, street labels (M5.7), `ADDRE` join (M4.36), and any new section-4
   grammar claim. Firmware acceptance is not claimed (rule 13).
5. **Falsifier.** A viewer name from a neighbouring bbox (none: all 37 names
   come from nodes filtered to the tile bbox), a section-1 regression (none:
   `ok/bad` equals the factory baseline and only 9,061 bytes of 68,663,808
   differ), or a non-identical no-input control (it is identical).

## Interpretation

- **FACT:** exact-length, in-place text substitution in a factory named
  record keeps `section4.py verify`, `harness.py verify` and L2 semantic PASS,
  while the viewer reads the OSM names.
- **FACT:** a full `clarion_tile.write_tile()` rewrite is *not* safe here: with
  growing section-4 streams it moved section-1 blocks and produced 34 bad
  records instead of the factory's 25; the final tool patches only the
  changed slot blocks and directory pairs in the source bytearray (9,061
  differing bytes).
- **OBSERVED:** the name-list start offset and `0x06..0x0f` remain UNKNOWN and
  were copied verbatim from factory records (C-546, C-2391), not derived.
- **HYPOTHESIS:** the firmware will display these names through the section-4
  reader located by M4.40 (`RGD_DATA READ` kind `0x40`, C-5921/C-5925), but no
  L3/L4 run of our generated section 4 exists; rule 13 acceptance is open.
- **UNKNOWN:** which `0x06..0x0f` bytes encode the name list, and whether the
  router's `0x00422eac` consumer (M4.56) would treat the replaced names as
  signposts rather than place names.

## Conclusion

`docs/format/map-tiles.md` §section 4 and `docs/research/reader-coverage.md`
row 19 now record that OSM place names can be written into a generated
section 4 by exact-length substitution into a factory named record, with the
tool and the controls; `docs/research/claims.md` gains C-6650–C-6659. Nothing
in the section-4 grammar was loosened or re-derived: `section4.py verify`
still refuses new grammar, and the firmware reader of our generated names is
still an L3/L4 follow-up (M4.56/M9 tasks), not a claim of acceptance.
