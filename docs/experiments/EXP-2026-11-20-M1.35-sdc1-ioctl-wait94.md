## Question

Which `SDHC.dll` (build B) function answers the two `SDC1:` IOCTLs that
`MountStorage` (`fn 0x03bd2044`, EU2011) sends before `DSK1:` is mounted
(`0x80032004`, `0x80032000`), and is it the CMD42 unlock? And which module
signals ACM id 94, which every non-JP `Navi.exe` record waits for?

## Hypothesis

(a) `0x8003200x` sit in the same IOCTL family as the CMD42 codes
`0x80032014…24` (M2.13b), so one of them is the boot-time unlock.
(b) Id 94 is signalled by some module through `IOCTL_ACM_SET_ID`
(`0x80002000` on `ACM9:`), most likely via `commondll!CApi_ModuleInitializeComplete`.

Falsifiers: (a) the handler of `0x80032000/4` builds no CMD42 frame and calls
no slot of the `SDHC_Lock_Unlock_Card` path; (b) no call in any module of
images A/B/C passes 94 to a SET_ID path while the same scan does find the known
senders (SDHC id 37, AppLaunch ids 22 and 82).

## Interpretation

- **FACT (C-5352):** `SDC1:` is `CSDCMain` in `SDHC.dll` (build B, EU2011 =
  US2011). `SDC_IOControl` `0x039b3970` dispatches through vtable
  `0x039b1290` slot 92 = `fn 0x039b4498`, which handles exactly
  `0x80032000` (`fn 0x039b4664`), `0x80032004` (`fn 0x039b4850`),
  `0x8003200c` and `0x8003202c`.
- **FACT (C-5353):** `0x80032004` is a **slot-state query**: input a u16
  port (< 2), output `state | 0x80000000·(SDHC_GetPower(port) == 0)`, where the
  state is 2 = card driver not active (initial / being activated), 4 =
  `Drivers\SD\Card` activated, 8 = `ActivateDevice` failed, 1 = no card /
  removed. It issues no SD bus command.
- **FACT (C-5354):** `0x80032000` is a **card insert/remove request**: input
  byte `b`, port `= (b >> 4) & 1`, bit 0 = insert. Insert with a card seen
  present raises the port (`PORT_HIGH`) and wakes the slot's load thread; it
  issues no SD command and is **not** CMD42. `AppLaunch` sends it with
  `b = 1` (port 0, insert) only when the state is 2.
- **FACT (C-5355):** the load thread `fn 0x039b48fc` turns the request into
  `ActivateSDCardDriver` `fn 0x039b4b18` → `ActivateDevice(Drivers\SD\Card)`
  → `DSK_Init` → `CDSKMain::Init` `fn 0x039b53c8` → `SDHC_SecurityUnLock`
  `fn 0x039b6ac4` (CMD42, C-1954). So the CMD42 unlock is a side effect of
  the `DSK1:` activation, once per activation; `AppLaunch` only sees the
  activation result (state 4/8) through `0x80032004`. After a successful
  activation `SDHC.dll` signals **ACM id 37** (`CApi_ModuleInitializeComplete(37)`,
  port 0 only), the id `MountStorage` waits for (15 s) before it opens `SDC1:`.
- **FACT (C-5356):** ACM ids are 192 unnamed manual-reset events inside
  `ActivateCtlDriver.dll`; the only way to set one is `IOCTL_ACM_SET_ID`
  (`0x80002000`). In EU2011 and US2011 images A, B and C no call passes 94 to
  a SET path (0 of 71 / 72 calls, 0 dynamic calls hinted), the launch table has
  no record with own id 94, and neither card's map partition holds an
  executable. The same scan finds SDHC's 37, AppLaunch's 22 and the
  `MountStorage` 82 loop.
- **INFERENCE (C-5357):** nothing in these builds signals id 94, so each
  `Navi.exe` (and `AuiApp.exe`) launch thread spends the full 30 s timeout on
  it; the wait loop ignores the result, so this delays `ResumeThread` but does
  not block it. A dynamic id from a run-time function pointer or an
  arithmetic `0x80002000` would escape the scan; an L4 boot (M8) that logs
  `SET_ID` calls would close it.
- **HYPOTHESIS:** if `SDHC_SecurityUnLock` fails, `CDSKMain::Init`
  continues (Observation 9), so a locked card with a wrong password is
  expected to fail later, at `OpenStore`/partition mount (`0x82` `SD INIT
  NG`), not with `0x80` or `0x81` (`SD UNLOCK NG`, which `MountStorage` never
  dispatches, M1.34). Not run.
- **UNKNOWN:** what `fn 0x039b963c` reads (card-detect is the natural
  reading of "value 1 → present"); which product option id 94 belongs to.

## Conclusion

Hypothesis (a) is refuted: the two pre-mount IOCTLs are not CMD42. `AppLaunch`
asks `SDC1:` for the port-0 state (`0x80032004`, `fn 0x039b4850`) and, if the
card driver is not active yet, posts an insert request (`0x80032000`,
`fn 0x039b4664`); the unlock happens inside the `DSK1:` activation that the
request triggers (`fn 0x039b4b18` → `CDSKMain::Init` → `fn 0x039b6ac4`).
Hypothesis (b) is not confirmed: no static SET_ID of 94 exists in the ROM of
either build, with the known senders found by the same scan. For a generated
card this changes nothing on the map side; for the card ladder it means a
card that does not reach state 4 within 4 polls (about 1.3 s after the 15 s
id-37 wait) gives `NO SD CARD`, and that, unless something outside this scan sets it, the boot
pays the 30 s id-94 timeout before `Navi.exe` resumes (C-5357, inference). `docs/research/rom-registry.md` step 1 of
the gate and the `Navi.exe` waits line are updated; claims C-5352–C-5357.
