## Question

Can `-M aze0` boot the EU2014 (X212) kernel to an observable F0 log on the
machine's own debug-string sink, with X212 RAM/entry parameters, while
`-M ze0` stays unchanged — and is the new sink VA derived from the image
rather than guessed?

## Hypothesis

The X212 kernel reaches an idle kernel on today's devices but prints 0 lines
at the EU2011 sink `0x880404f4`; a base-class machine with an X212 `dbgmsg`
default will print a non-zero F0 log. **Falsifier (task's own):** the EU2014
kernel prints debug text at the EU2011 VA `0x880404f4` and ends at the EU2011
final PC `0x8803d266` — then no subclass is needed and this EXP records that
instead of adding a machine.

## Method

### 1. Sample and hash

`sha256sum archive/eu2014-256.img archive/head256.img` printed the two hashes
above. Scratch: `~/projekty/leafre-work/scratch/m8.g4/` (deleted after this
EXP); build scratch must use `TMPDIR=/home/marek/projekty/leafre-work/scratch/tl-tmp2`
because `/tmp` is a 3.8 GiB tmpfs and filled during the first build attempt.
No card image or vendor data was committed.

### 2. Derive the X212 debug-string sink (the printed signature)

The EU2011 sink at VA `0x880404f4` (M8.B6, C-6240) is the positive control.
Its first 20 LE bytes, printed by `sh4dis.py --va 0x880404f4`, start
`2f86 2f96 4f22 7ff0 6843 d90b 6583 d30b 430b 6493` (`r4` = UTF-16 string,
AstLog call). Scanning the EU2014 `nk.exe` image (VA `0x88001000..0x8804ce24`,
file `0x03e01200..`, from `cerom.py sections nk.exe`) for that exact 20-byte
signature finds exactly one hit. The candidate is then disassembled and
cross-referenced; an independent anchor is the pool load in `KernelStart`:

```bash
python3 tools/sh4dis.py archive/head256.img nk.exe --image-start 0x3e00200 --va 0x880404f4 --count 8
python3 tools/cerom.py --image-start 0x3e00200 archive/eu2014-256.img sections nk.exe
python3 - <<'PY'
sig = bytes.fromhex('862f962f224ff07f43680bd983650bd30b439364')
for img in ('archive/eu2014-256.img', 'archive/head256.img'):
    with open(img, 'rb') as f:
        f.seek(0x3e00200); data = f.read(0x89000)
    hits, off = [], 0
    while True:
        i = data.find(sig, off)
        if i < 0: break
        if i % 2 == 0: hits.append(hex(0x88000000 + i))
        off = i + 1
    print(img, hits)
PY
python3 tools/sh4dis.py archive/eu2014-256.img nk.exe --image-start 0x3e00200 --va 0x88040a54 --count 25
python3 tools/sh4xref.py archive/eu2014-256.img nk.exe --image-start 0x3e00200 --to 0x88040a54
python3 tools/sh4xref.py archive/head256.img nk.exe --image-start 0x3e00200 --to 0x880404f4
python3 tools/cerom.py --image-start 0x3e00200 archive/eu2014-256.img romhdr
```

The scan prints `['0x88040a54']` for EU2014 and `['0x880404f4']` for EU2011.
`sh4dis.py` prints the same sink shape at the new VA: `r4 -> r8`, pool
`0x880075dc` = `L"%s"` into `r9`, AstLog call through pool `0x880449d8`, then
the two gate words `0x8a6623d0`/`0x8a6623d4` and the gated `DebugLog` call
`0x880409ec`. `sh4xref.py` prints three pools/callers for each VA
(EU2014 pool `0x880109f4`, `KernelStart` fn `0x880108c8`; EU2011 pool
`0x880104c4`, fn `0x88010398`). `romhdr` prints `ulRAMStart 0x8a640000`,
`ulRAMEnd 0x8e600000`, `physfirst 0x88000000`, `physlast 0x8870fb90`.

### 3. Patch, build and verify the machine class

One new patch, `tools/qemu-ze0/patches/ze0-0019-hw-sh4-aze0-machine.patch`,
turns `TYPE_ZE0_MACHINE` into a QOM base class (`Ze0MachineClass` with
`dbgmsg_va`, `kernel_off`, `app_off`, `ce_ram_start` defaults) and adds
`TYPE_AZE0_MACHINE` overriding only `dbgmsg_va = 0x88040a54` and
`ce_ram_start = 0x8a640000`. The entry `0x8800f100` is derived per image by
the existing `nk.exe` TOC walk, not hard-coded. `run.sh` accepts
`--machine aze0` (previously rejected with exit 2) and uses the machine's own
`dbgmsg` default unless the user sets `--dbgmsg` explicitly.

```bash
cd tools/qemu-ze0/patches && ls *.patch | wc -l
patch -d /home/marek/.cache/qemu-ze0/qemu-11.1.3 -p1 --forward --batch < tools/qemu-ze0/patches/ze0-0019-hw-sh4-aze0-machine.patch
cd /home/marek/.cache/qemu-ze0/build
TMPDIR=/home/marek/projekty/leafre-work/scratch/tl-tmp2 make -j8 qemu-system-sh4
Q=~/.cache/qemu-ze0/build/qemu-system-sh4
"$Q" --version | head -1
"$Q" -M help | grep -E '^(ze0|aze0)'
bash tools/qemu-ze0/run.sh --machine aze0 --image archive/eu2014-256.img --app 0 --dry-run
```

The patch-applies check is done against a scratch copy of the pristine source
with the original `ze0.c` restored; `cmp` against the built tree prints no
difference. `make` prints the compile/link lines; `-M help` prints both
machine lines. The `--dry-run` prints
`-M aze0,kernel-off=0x3e00200,app-off=0x200200 -kernel archive/eu2014-256.img`
with no `dbgmsg=` override.

### 5. Controls

- **Positive:** the signature scan finds the known EU2011 sink at
  `0x880404f4`; `-M aze0` with its own default prints a non-zero F0 log;
  `-M ze0` on EU2011 still prints its known log and reaches final PC
  `0x8803d266`.
- **Negative:** unmodified `-M ze0` on EU2014 and `-M aze0,dbgmsg=0x880404f4`
  both print 0 lines (wrong VA); `--dbgmsg off` passes `dbgmsg=0` and prints 0
  lines; the mutated-binary boot drops from 462 to 3 lines. The mutated
  binary's SHA-256 differs from the original; after restore the two SHAs are
  equal again.
- **Falsifier:** if the EU2014 kernel on `-M ze0` printed text at `0x880404f4`
  and ended at `0x8803d266`, the subclass would be unnecessary.

## Interpretation

- **FACT:** the X212 sink VA `0x88040a54` is derived by an exact signature
  match with a known-good positive control; its gate words and three caller
  pools are printed by the same tools (C-10230, C-10238). The RAM window
  `0x8a640000` and entry `0x8800f100` are printed by `cerom.py` and the
  loader (C-10231).
- **OBSERVED:** `-M aze0` prints 462 lines on its own default, reaches an
  idle kernel at `0x8803d796`, while wrong VA and off both print 0; the
  mutated binary drops to 3 lines and the restored binary is byte-identical
  (C-10233–C-10235).
- **HYPOTHESIS:** the remaining unmodelled accesses and the exception count
  are the same integration gaps M8.G2 saw; the X212 INTEVT table (M8.G5),
  NOR flash (M8.G6) and graphics (M8.G7) are still needed beyond F0.
- **UNKNOWN:** whether the 3 mutated lines are unrelated serial text (they
  are not the sink hook, whose count is 0 with `dbgmsg=0`).
- **Level:** L4 (full-system emulator); L5 remains unavailable. Rule 13 is
  satisfied for F0 observability, not for map acceptance.

## Conclusion

M8.G4's Done when is met: a 5 s `run.sh --machine aze0 --image
archive/eu2014-256.img` boot prints a non-zero count of X212 debug lines
(462) on the machine's own derived `dbgmsg` default, reaches an idle kernel
with no CPU exception line, and this EXP compares the log with the EU2011 F0
baseline (entry `0x8800ebd0`, final PC `0x8803d266`; EU2014 entry
`0x8800f100`, RAM `0x8a640000`). `-M ze0` keeps the same entry, image size
and final PC as before. One QEMU patch, one `run.sh` machine option, this EXP
and claims C-10230–C-10239 are the only repository changes; no format
knowledge changed. The task's falsifier was applied and not met.
