# EXP-2026-11-06-M3.8: The firmware reads `MMAIN001.DAT` (build A, media mount)

- **Status:** done
- **Date:** 2026-11-06
- **Sample:** `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (EU 2011, builds A/B/C)
- **Image SHA-256:** `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
  (first 128 MiB read here: `d3e5eac9cb5b4cbdf2618e686fb3ed1b273d3c6b75753cfc14f31d35c79fd9be`)
- **Claims:** C-1780–C-1789
- **Supersedes:** C-550's "count is `u16 LE`" clause (C-1788); the "no MMAIN code
  reference" wording in `docs/format/drstr.md`
- **Superseded by:** none

## Question

Does the ZE0 firmware read `MMAIN001.DAT`, and if so, which fields does the
reader check — so that M5.6 knows whether a rebuilt card may copy the file
verbatim or must regenerate it?

## Hypothesis

`none / exploratory`. M4.5 had described the file as a FAT root-directory log
(since retracted, C-930/C-1721), so a reference to the real file was expected
to be absent or to sit in a diagnostic path.

## Observations

### String scan

- Build A: 149 modules, 527 sections (282 uncompressed), **1 hit**:
  `MMAIN001.DAT` ASCII, `Navi.exe`, section `sec0` (VA `0x00011000`),
  RVA `0x0016adac`, VA `0x0017adac`, file `0x00df8fac`.
  Context: `...Info Show\r\n\0MMAIN001.DAT\0MGR ADR[0x%08x]\r\n\0VOL ADR[0x%08x]...`
- Build A: no UTF-16LE or UTF-16BE occurrence of `MMAIN`.
- Build B (91 modules, 307 sections): **0 hits**. Build C (88, 277): **0 hits**.
- All 245 (A), 133 (B), 113 (C) `IMAGE_SCN_COMPRESSED` sections were passed to
  `tools/cecompress.py`; every one is reported `UNSUPPORTED` (`cecompress`
  cannot pick a method). Coverage is therefore the uncompressed section set,
  which is where code and literal pools live (C-530).
- Control `HDD_INFO.TXT`, same commands: A 4 hits (UTF-16LE at VA
  `0x001d518e` and `0x001d51ca`, plus the 1-byte-shifted UTF-16BE alias); B 8
  hits (`commondll.dll`, `AppLaunch.dll`, `MapUpdate.exe` × LE/BE); C 4 hits
  (`commondll.dll`, `AppLaunch.dll` × LE/BE). The method would have found a
  `MMAIN` occurrence if one existed.
- `QSD-309-101`: 0 hits in all builds (control found). `DATA VERSION`: 0 hits.
- Raw first 128 MiB: `MMAIN` ASCII 3 occurrences — `0x00df8fac` (the A module
  string), `0x02bf8fac` (byte-identical A copy, +0x1fe0000),
  `0x064e58e0` (root-directory entry text `MMAIN001DAT `, not code). UTF-16
  LE/BE: 0.

### Code

- `sh4xref --to 0x0017adac`: pool `0x0041a514` holds it; **one** load,
  `0x0041a47a (r5)`, in function `0x0041a438`.
- `--calls 0x0041a438`:
  `0x003d13c4` = COREDLL `#1047 memset`, `0x003d14cc` = `#75 wcstombs`,
  `0x0053a384` = `#1069 strncat` (called twice), `0x0041b780`,
  `0x0041b954`, `0x0041b81c` (module-local), `0x0041bbec` (error logger).
- `0x0041a438` listing:
  `memset(buf, 0, 260)`; `wcstombs(buf, L"\SystemSD", 260)` with the wide
  string at VA `0x00049fd4`; reject if `wcstombs` result < 0 or
  `result + 13 >= 260`; `strncat(buf, L"\", 1)` (VA `0x0017a9ec`) and
  `strncat(buf, "MMAIN001.DAT", 12)`; `fd = sub_0041b780(buf, 1)`; success is
  `fd != 0`; `sub_0041b954(fd, dest, 0x1000, 1)` must return exactly `0x1000`;
  `sub_0041b81c(fd, 1)`; returns 0, or 11/−1 on failure.
  `dest` = argument, or `0x00e23cc0` when the argument is 0.
- `sub_0041b780` opens through the CD-ROM manager (`"rb"` at `0x0017ab20`);
  `sub_0041b954` is the read wrapper (`cmp/pz` + `cmp/eq` on the byte count,
  then it calls `0x0041c044`); no content inspection in either.
- Caller `0x00419ca0` (one of two `--to` pools is the handler table at
  `0x0017ab38`): `sub_0041a388(1)` (state global `0x009cfce4 = 1`), then
  `sub_0041ba90()` = `CMP.LST` open (`\CMP.LST`, M3.4); if it fails the
  status global `0x009cfce0` becomes 3. If it succeeds,
  `r = sub_0041a438(0)`, `sub_00419a9c(r)` stores `r` in a 4-entry log at
  `0x00e24d00`; `r == 0` sets `0x009cfce0 = 1` (mounted), `r != 0` calls
  `sub_00419bc0()` (retry timer) and leaves the status at 0.
- `0x00419c38(status_mode)`: `idx = (*0x009cfce0) * 5 + mode`, calls
  `0x0017ab38[idx]`; entries 0/1 are `0x00419ca0` (status 0 = not mounted).
  Table row 1 (status 1) is `0x00419d24`, which reads DRSTR
  (`sub_00419684`) and then the MMAIN buffer.
- After a successful mount, `0x00419d24` calls `0x0041a42c` (returns
  `0x00e23cc0`), `0x0041a304(buf)`, `sub_0041a388(2)`.
- `0x0041a304(buf)` listing: rejects `buf == 0` or `buf & 3`; sets
  `0x009cfcf0 = 1`; **byte-swaps all 2048 `u16` words** (`mov #8; shll8` →
  `0x800`, loop `dt`); then calls `0x0053a93c` with `*0x009cfcec` and `buf`.
  `sh4xref --calls`: `0x0053a93c` = OBJDLL export `OBJ_DriveInfo_writeDataVol`
  (export #244, VA `0x034b984c`).
- `OBJ_DriveInfo_writeDataVol` (`0x034b984c`): type-checks `obj` and `buf`,
  increments `*(obj+4)`, `memcpy(obj+8, buf, 0x1000)`, returns 0. It does not
  parse the buffer.
- `sh4xref --to 0x00e23cc0`: two real loads only — `0x0041a498`
  (`0x0041a438`, read destination default) and `0x0041a546` (`0x0041a52c`,
  debug dump). `0x0041a52c` prints `##### Disc Vol Info #####`, walks 128 records of
  32 bytes over the whole buffer (first 16 bytes each), then
  `VOL ADR[0x%08x]` = `buf+0x800` and
  `MGR ADR[0x%08x]` = `buf`.
- `MAL_DataVol_getOffset` (`0x03498d48`) and `MAL_DataVol_getSize`
  (`0x03498d28`) read a static 20-entry table at `0x01e33290`, not the
  `OBJ_DriveInfo` object, so tile offset/size addressing does not consume the
  MMAIN bytes.

### File sample

`MMAIN001.DAT` from the EU 2011 root (SHA-256 `240e7c97…`, 4096 bytes):

```
0x1ac: 00 03 01 06  06 80 00 01  05 90 00 01  04 91 00 01
0x1bc:             03 91 00 2d  02 91 00 8a  01 92 06 b5
```

Read as big-endian `u16`: counts 1, 1, 1, 45, 138, 1717 (plausible and equal to
the tile sums of C-164). Read as little-endian: 256, 256, 256, 11520, 35328,
46342. `tools/cardcheck.py` already parses this table big-endian (`>BBH`).

## Interpretation

- **FACT:** The only code reference to `MMAIN001.DAT` in all three builds is
  ASCII in `Navi.exe` at `0x0017adac`, loaded once at `0x0041a47a` in
  `0x0041a438`. B and C have none; there is no UTF-16 literal anywhere.
- **FACT:** The reader builds `\SystemSD\MMAIN001.DAT`, opens it read-only and
  demands exactly 4096 bytes. It performs **no** label, version, record-count,
  cluster or checksum check: the only comparisons are the path-buffer bound,
  the open status and the total read length. `QSD-309-101` and
  `DATA VERSION` do not exist as literals in build A, so no code can compare
  the header text.
- **FACT:** The 4096 bytes are copied into the `OBJ_DriveInfo` object and
  byte-swapped from big-endian to little-endian on the way. The on-card format
  is big-endian; the `0x1ac` counts are big-endian (C-1788 corrects C-550).
- **FACT:** The reference is part of the media-mount state machine, not a
  debug menu: the handler table at `0x0017ab38` row 0 (`status = 0`) calls
  `0x00419ca0`; a short or missing file fails the read and schedules a
  retry; a missing `CMP.LST` sets status 3. The debug dump at `0x0041a52c` is a separate "Info Show" path.
- **OBSERVED:** The in-memory buffer is treated as two `0x800` areas
  (debug labels `MGR ADR` at `+0`, `VOL ADR` at `+0x800`) and as 32-byte
  records over the whole 4096 bytes.
- **HYPOTHESIS (decision):** Copying the factory `MMAIN001.DAT` verbatim
  satisfies the firmware mount path, because the reader checks only the size.
  Regenerating the `0x1ac` totals stays an **offline** consistency rule
  (`cardcheck`); the firmware read path does not enforce it. A stale table is
  not proven harmless for the map layer's own consumers, so a tile-set change
  should still regenerate the file.
- **UNKNOWN:** What `OBJ_DriveInfo` consumers do with the copied bytes after
  mount (debug/status only is plausible from the two references); whether the
  map layer ever compares the `0x1ac` totals at runtime. No hardware run.
