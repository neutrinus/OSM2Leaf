## Question

Can the different L3 counts printed on one commit be reduced to one manifest of
card-level L3 runs, one command that re-runs it, and one selftest that compares
the count sources — without adding a CI/vendor-image dependency or a fake pass?

## Hypothesis

A single `tools/l3_harness/runs.json` (one entry per `l3-running` matrix row)
driven by `python3 tools/l3check.py --runs [--only ROW]` can re-run each row and
print PASS / FAIL / NOT RUN with exit 0/1/3, and `map_signals.py` +
`progress_report.py` can source the same row count from the manifest so all
three agree. **Falsifier (task line 6330):** a `l3-running` matrix row with no
manifest entry after this task. Also falsified by a wrong verdict that still
PASSes, by a manifest whose deletion does not fail the count check, or by any
count in this record not traced to a printing command.

## Method

1. **Sample and hash.** The two heads and the card are hashed above by
   `sha256sum` (printed values quoted). The task's Goal numbers were measured at
   `ae2cb0c` on 2026-11-20; this record measures at `58fcb3e` and quotes the
   printing commands, per the rule that a moved count cites its command.

2. **Commands.** From the worktree root, with `TMPDIR` on the home tree (the
   `/tmp` tmpfs is small and filled during an early selftest attempt):

   ```bash
   TMPDIR=/home/marek/projekty/leafre-work/scratch/tl-tmp2
   python3 tools/map_signals.py l3_rows
   python3 tools/map_signals.py l3_rows --runs-manifest tools/l3_harness/runs.json
   python3 tools/progress_report.py --runs-manifest tools/l3_harness/runs.json --json -
   python3 tools/l3check.py --build-corpus
   ls tools/*_l3.py | wc -l
   python3 tools/l3_harness/runs.py --selftest
   /usr/bin/time -f 'TOTAL_WALL %e s' python3 tools/l3check.py --runs \
     --runs-scratch /home/marek/projekty/leafre-work/scratch/m9.62-probe/runs \
     --runs-timeout 600
   python3 tools/l3check.py --runs --only 19 --runs-scratch .../runs --runs-timeout 400
   python3 tools/l3check.py --selftest
   python3 tools/map_signals.py --selftest
   python3 tools/progress_report.py --selftest
   # negative controls (section 3) use a COPY of the manifest in scratch
   python3 tools/l3check.py --runs --run-manifest .../runs-mutated.json --json -
   ```

3. **Controls.**
   - *Positive:* every manifest row is a real re-run of an `l3-running` row and
     must PASS on EU2011; the EXP records wall time per row.
   - *Negative (task Done when):* a deliberately wrong expected verdict in a
     synthetic row gives FAIL and exit 1; with no images every row is `NOT RUN`
     and exit 3 (both in `l3check.py --selftest`).
   - *Negative (mandatory artifact mutation):* delete one real row (row 17)
     from a COPY of `runs.json`; `l3check --runs` must report FAIL and name the
     missing matrix row (a check that survives deletion is not a check).
   - *Count agreement:* a manifest whose row count disagrees with the matrix
     awk count is `NOT RUN` in `map_signals` and a named problem in
     `progress_report`; both selftests exercise the disagree case.

4. **Scope.** 9 manifest rows = the 9 `l3-running` matrix rows (3, 4, 5, 6,
   11, 17, 19, 22, 23), 26 `tools/*_l3.py` scripts, 13 `targets.json` targets.
   EU2011 build A for all nine rows; US2011 head is hashed but no `l3-running`
   row needs it (the US runs of M9.61/M9.63 are other rows). Not covered: new
   L3 runs; `runner.py` targets keep their own `--build-corpus` path; PR CI
   (vendor images). Row 19 is the M9.18 directory/record-serving verdict, not
   the M9.80 writer-acceptance task (which stays `blocked`).

5. **Falsifier.** Stated in the Hypothesis, before the observations.

## Interpretation

- **FACT (C-6370):** the manifest has exactly one entry for each of the nine
  `l3-running` matrix rows; `coverage_problems` is empty and the two counts
  agree (9 = 9).
- **FACT (C-6371/C-6374–C-6378):** `l3check --runs` re-runs all nine rows on
  EU2011 and each prints its pinned verdict line; the gate exits 0. No row is
  `MANUAL`: each reduces to one command with a stable verdict token.
- **FACT (C-6372):** the three tools now share one row list. `map_signals` and
  `progress_report` both read the manifest; `pass_firmware: 6` (matrix metric,
  includes non-l3-running row 10) and `runnable=3/13` (targets.json metric) are
  deliberately left as separate numbers — folding them into 9 would falsify
  their own claims.
- **FACT (C-6373):** the falsifier fails closed — a matrix row absent from the
  manifest is named and the gate FAILs; deleting a row is not silently ignored.
- **OBSERVED:** the `/tmp` tmpfs filled during an early `l3check --selftest`
  (`Errno 28`) before `TMPDIR` was moved to `~/projekty/leafre-work/scratch/tl-tmp2`;
  this is an environment limit, not a code defect. The navigator saw the same
  quota failure in the standing gate.
- **UNKNOWN:** no US256 row among the nine `l3-running` rows, so the US head is
  hashed but not exercised by this gate; US L3 runs stay in their own EXPs.

## Conclusion

`tools/l3_harness/runs.json` + `tools/l3check.py --runs` make the card-level L3
runs re-runnable from one command, and `map_signals.py`/`progress_report.py`
source their "how many L3 runs" number from the same manifest (cross-checked
against the matrix awk count). All nine `l3-running` rows re-run PASS on EU2011;
the wrong-verdict, no-image and row-deletion negatives all fail closed. This is
a local/weekly regression tool, never a PR-CI gate, and adds no new L3 acceptance
claim (rule 13). `docs/research/claims.md` gains C-6370–C-6378.

## Corrections after navigator review

1. Round 1 (nav-plan CHANGES): the driver plan's item 5 named matrix row 10,
   which is not `l3-running` (its column-9 cell is `—`). The final manifest has
   exactly nine rows matching the awk-count rows 3, 4, 5, 6, 11, 17, 19, 22, 23.
2. Row 19's matrix cell ends in the blocked writer task M9.80; the manifest row
   is scoped to the M9.18 directory/record-serving verdict (`RESULT: MATCH`)
   and does not claim writer acceptance. `record_l3.py` needs `--position` and
   `--factory-root`; both are in the row's argv.
3. Verdict tokens were re-quoted from real command output (`boot: ACCEPT` is a
   substring of the printed `boot: ACCEPT  states …` line; `verdict        ACCEPT`
   is the DRSTR line). They are not guessed from source.
4. Count agreement is `manifest rows == matrix awk count == 9`; the distinct
   `pass_firmware: 6` and `runnable=3/13` metrics are not forced to 9.
5. Bug found by a driver self-check after round 1: `{JSON}` resolved to a
   directory, so row 19 failed with `IsADirectoryError`. Fixed by resolving
   `{WORKDIR}` to `scratch/record/` and `{JSON}` to `scratch/record/record.json`;
   `--only 19` then printed `RESULT: MATCH` (wall 44.05 s).
6. Mandatory artifact mutation (delete row 17 from a copy) was executed and
   quoted above: FAIL, exit 1, missing row named.
