## Question

Is the firmware's `DebugShell.dll` started on a retail EU2011 build, what is
its command table (names, handler VAs, input), and can a command be typed into
`-M ze0` over the `sci6` chardev now that M8.H1 is merged?

## Hypothesis

`DebugShell.dll` is a ROM stream driver launched by `AppLaunch.dll` after
`SCI6:` comes up; its built-in commands are a 16-byte-strided name array with
live code references, so the M8.H65 falsifier (dead data) is false. The live
part is exploratory: if the driver owns `SCI6:`, bytes written to the `sci6`
chardev reach it and its output appears on the same socket. **Falsifier:**
no launch record exists in the retail configuration, no code loads a command
name, or the name table is referenced only as data.

3. **Controls.** *Positive*: `sh4xref --to 0x039213b8` must find a load inside
   `fn 0x03924470` (a real code reference), and `--to 0x03921dfc` must find the
   `SCI6:` opener; the registry parser must close with `dangling links 0` and
   the launcher dump must report `structure: OK (112 records)`. *Negative*:
   `sh4xref --to` on a nearby VA with no literal (e.g. `0x03921a2c`, the
   `ID:%3d TIME:%10d ` string) must answer "no literal pool holds …", which
   bounds what the static xref method can claim; a boot without
   `--serial-peer` writes the DBGMSG log to `serial.log` and was the M8.H1
   baseline. *Live*: an ordinary retail boot must show `DebugShellDll`
   PROCESS_ATTACH lines without any injected command.
4. **Scope.** Build B only (91 modules); the two DebugShell modules' uncompressed
   code sections (0x8c00 + 0x2c00 B) plus the decoded registry hives
   (`boot.hv` 32 KiB, `default.hv` 126,976 B, `user.hv` 28 KiB) and 112
   AppLaunch records. Compressed `.data` of `DebugShell.dll` (sec1 804 B,
   sec2 2712 B after the kernel decompressor) was checked for code/literal
   references and contains the IAT and `.pdata` only. Build A was searched for
   the module name (many import references, no module of its own). No other
   head or year was analysed. The live run is one EU2011 card boot per run.
5. **Falsifier.** See §Hypothesis. For the live part, the falsifier is: no
   bytes at all on the `sci6` socket, or bytes that are unrelated to any
   firmware serial output.

## Observations

**O1 — the modules exist in build B.** `cerom.py modules` prints
`68 DebugShell.dll attr=0007 size=46080 load=886c1000 vbase=03920000 objs=3`
and `69 DebugShellDll.dll attr=1007 size=16384 load=886d0000 vbase=03910000
objs=3`. `exports DebugShell.dll` lists exactly 10 `DSD_*` entry points
(`DSD_Init 0x0392351c`, `DSD_Write 0x039235e0`, `DSD_IOControl 0x0392364c`,
…, `DSD_Read 0x03927974`, `DSD_PowerDown/Up 0x039265fc`). `exports
DebugShellDll.dll` lists 3 functions at rva `0x2050/0x2080/0x20a0`.
`sections DebugShell.dll`: sec0 VA `0x03921000` psize `0x8c00` RAW; sec1
`0x01f28000` and sec2 `0x0392b000` are COMPRESSED, decompressing to 804 B and
2712 B by `nk_decomp.py section` (sha256 `ab3e3357…` / `214645d8…`).

**O2 — the retail launch path.** `cehive.py default.hv --grep DebugShell`:
`Drivers\Launch\DebugShell  Dll (SZ) = DebugShell.dll`, `Prefix (SZ) = DSD`,
`Index (DWORD) = 0x1`, `Order (DWORD) = 0x8`; `Drivers\Launch\SCIF6` has
`Dll = serial_scif.dll`, `Index = 6`, `DeviceArrayIndex = 6`. The hive parses
closed: keys 516 (reached 516), values 1149 (reached 1149), dangling links 0.
`applaunch_table.py dump` prints `structure: OK (112 records …)` and, among
others:

```
14 0x03bb4e10 t1 ... id=0x0a prio=110/0 SCI6:              \Drivers\Launch\SCIF6
32 0x03bb8530 t1 ... id=0x28 prio=127/0 DSD1:              \Drivers\Launch\DebugShell  arg='' waits[2]=10/30000 1/30000
```

`ce_drivers.py` joins them as `32 Launch/default DebugShell DebugShell.dll
DSD1 0x8 32 DSD1: id 0x28 waits 10/1`. Neither `boot.hv` nor `user.hv` has a
DebugShell value.

**O3 — the serial device.** `ce_strfind.py --image-start 0x3e00200 --encoding
all SCI6:` finds UTF-16 `SCI6:` in `DebugShell.dll` at rva `0x1dfc`,
VA `0x03921dfc`, and in `AppLaunch.dll` at VA `0x03bb4e24`. `sh4xref --to
0x03921dfc`: `pool 0x0392499c holds … load 0x0392497c (r5) fn 0x03924930
[pdata]`. The UTF-16 `>>` prompt is at `0x03921dec`, loaded in
`fn 0x0392530c` together with `DsdDrv recieve Control Command.`
(`0x03921a50`). `sh4dis 0x03924e48` shows the byte callback: `cmp/eq #8`
(backspace), `#13` (CR) and `#33` (`!`).

**O4 — the command table is live data.** Raw bytes at sec0 file `0x3b8` are
11 NUL-padded 16-byte names: `showid`, `showinitid`, `showidtime`, `fix`,
`release`, `version`, `sramoutput`, `mw`, `mh`, `mb`, `mdump` at VAs
`0x039213b8 + 16*i`; `EXIT` at `0x039213a0` and a 2-byte `C ` at
`0x0392139c`. `sh4xref --to 0x039213b8`: `pool 0x03924514 holds …
load 0x039244b6 (r2) fn 0x03924470 [pdata]`. Disassembly of
`fn 0x03924470`: `mov r6,r8; shll2 r8; shll2 r8; mov.l …,r2` with
`[0x03924514]=0x039213b8`, then `add r2,r8`, `strlen`/`memcmp` thunks
`0x0392811c`/`0x03928104`, and `mov #90,r3; shll2 r3; mov.l @(r0,r3),r3;
jsr @r3`. `fn 0x039237a0` compares 4 bytes against `[0x03923810]=0x039213a0`
(`EXIT`) and 2 bytes against `[0x03923814]=0x0392139c` (`C `), dispatching
slots 92/91. The negative control `sh4xref --to 0x03921a2c` (`ID:%3d
TIME:%10d `) printed `no literal pool holds … in executable sections`: xrefs
are only claimed where the tool found one.

**O5 — handler-side evidence.** `fn 0x03924380`: loads
`[0x0392441c]=0x03921a44` (`%02d `) and `[0x0392442c]=0x03921a34`
(`No RegisterID.`), loops ids 1..99 (`cmp/hs #100,r9`) calling vtable slot
93. `fn 0x03924794` loads `[0x039247e2]=0x03921df0` (`ERROR. Filler is less
than 0xff?`). `fn 0x03925218` switches on a 1..4 size code loading
`0x03921f20` (`%02X `), `0x03921f38` (`%08X: `), `0x03921f4c`, `0x03921f60`.
`fn 0x03923b04` stores `[0x03923b74]=0x03921468` as `this->vptr` and zeroes
60 dwords; `fn 0x03923b7c` does the same. Slot 90 of that table is the thunk
`0x03928534` (jumps via IAT slot `0x01f28190`); slot 210 is `0x03924470`.

**O6 — retail-boot evidence (runs 1–4).** Each `serial.log` is 77,151 bytes
and ends at `Pow >> No Action at ACC-OFF? Timeout!! Force PowerOff!!` followed
by `OEMIoControl:IOCTL_HAL_POWER_SEQUENSE.`. Grep gives
`110: DebugShellDll: DLL_PROCESS_ATTACH`,
`288: DSD: DLL_PROCESS_ATTACH`,
`466: [BTMGR]DebugShell::BtMgrDebugShell resistration res=1`,
`509/825/904: DebugShellDll: DLL_PROCESS_ATTACH`. QEMU argv in `run.out`:
`-chardev socket,id=ze0sci6,…,server=on,wait=off -M
ze0,…,sci6=ze0sci6`. The `sci6` socket received only 15 bytes once:
`53 56 52 5f 44 49 53 43 3a 20 5b 33 30 34 33 38` = `SVR_DISC: [30438`
(a `SVR_DISC: [%d] DiscInfo Public FREE(Timer).` debug string at file
`0xc9dc68`), at t=1.0/1.37 s in run 2 and t=12.33 s in run 4.

**O7 — live injection is negative.** Four boots with `--serial-peer
sci6=unix:…` and clients connected before boot: run 1 sent `version\n` twice;
run 2 sent `version`, `version\n`, `showid`, `showid\r\n`, `EXIT` at
t=12/24/36/48/60 s; run 3 sent `!\r`, `!version\r`, `!showid\r`,
`version\r`, `showid\r`, `EXIT\r`, `?\r` at t=2..10 s; run 4 waited for the
first guest byte (t=12.33 s) and then sent `version\r`, `showid\r`, `EXIT\r`,
`!version\r`, `help\r`, `?\r` every 4 s. Every client finished with
`sent N/N` and **no bytes after the send markers**; no `>>` prompt, no
`Software Build Ver :`, no `No RegisterID.`, no `ERROR. Illegal command
format.` appeared on the socket or in `serial.log`. Run 3 first needed a
recovered `qemu-system-sh4` binary (`cp /proc/<pid>/exe`) because another
agent's `build.sh --force` removed the cache binary mid-session; all four
runs exited 0 with the same 77,151-byte `serial.log`.

**O8 — checks.** `claims_check.py --strict --count-check`: OK;
`todo_check.py`: OK (pre-existing WARNs only).

## Interpretation

- **FACT (C-7620, C-7621):** both modules are in the retail ROM and the shell
  is launched by `AppLaunch.dll` after SCI6/SCI1; the live boot confirms
  `DSD: DLL_PROCESS_ATTACH` and client registrations (C-7627).
- **FACT (C-7622, C-7623):** the driver opens `SCI6:` and the command-name
  array has a real code reference. The M8.H65 falsifier does not fire.
- **FACT (C-7624–C-7626):** names, output strings and several handler/parser
  VAs are established; there is no help command, and full one-VA-per-command
  resolution is still open (C-7625).
- **OBSERVED (C-7628, C-7629):** the `sci6` chardev is the kernel debug SCIF;
  four injection attempts produced no shell reply. The guest reaches
  `Force PowerOff` in every run, and the socket carries only one early
  `SVR_DISC:` line.
- **HYPOTHESIS:** either the shell's receive path is not armed on SCIF6 in
  this boot state (RX details are M8.H66's scope), or the shell expects a
  framing not reproduced here (the byte callback special-cases `!`, CR and
  backspace). Not distinguished by this session.
- **UNKNOWN:** the writer of `DebugShellMode`; the exact RX framing; the
  distinct C++ execution slot of each built-in command.

## Conclusion

`docs/firmware/debugshell.md` now documents the retail start condition, the
13 command names with handler/parser VAs and output strings, the `SCI6:` input
path and the live-channel status. `docs/research/claims.md` gains C-7620–
C-7629. The primary Done-when item (command table + start condition) is met.
The conditional live item is **not** met: commands were typed over the `sci6`
chardev but no command output could be quoted, so this is recorded as a
deviation with the negative result in O7 and an open item in the doc, not as
a blocker — the static result does not depend on it. Follow-ups are the C++
execution slots, the mode flag and the RX framing.

The scratch client used for the injection (also reproduced in Method step 2)
connects to `sci6.sock`, logs all guest→host bytes with timestamps and sends
`version`, `version\n`, `showid`, `showid\r\n`, `EXIT` at t = 12/24/36/48/60 s:

```python
import socket, sys, time
sock_path, out_path = sys.argv[1], sys.argv[2]
SCHEDULE = [(12.0, b"version"), (24.0, b"version\n"), (36.0, b"showid"),
            (48.0, b"showid\r\n"), (60.0, b"EXIT")]
s = None
while s is None:
    try:
        s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
        s.connect(sock_path); s.settimeout(0.5)
    except OSError:
        s = None; time.sleep(0.2)
log = open(out_path, "wb"); start = time.time(); sent = set()
while time.time() - start < 140:
    t = time.time() - start
    for i, (at, data) in enumerate(SCHEDULE):
        if i not in sent and t >= at:
            s.sendall(data)
            log.write(f"\n--- SENT #{i} {data!r} at t={t:.2f} ---\n".encode()); log.flush()
            sent.add(i)
    try:
        data = s.recv(65536)
        if data:
            log.write(f"[{t:7.2f}] ".encode() + data.hex(" ").encode() + b"\n"); log.flush()
        else:
            break
    except socket.timeout:
        pass
log.close(); s.close()
```
