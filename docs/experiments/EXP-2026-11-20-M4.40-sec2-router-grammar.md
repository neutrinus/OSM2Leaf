# EXP-2026-11-20-M4.40: the router asks the data-access task for section 2 (`0x14b5`) and reads the reply in `0x00422eac`

- **Status:** done (the grammar goal is not met: the reader is located, its fields are not decoded; see Conclusion)
- **Date:** 2026-11-20
- **Sample:** `archive/head256.img` (IMG256, EU 2011 head, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`), `Navi.exe` of build A,
  `--image-start 0x200200`. No tile bytes are needed: nothing in this record reads a tile.
- **Tools:** python3 3.13.18; `tools/callgraph.py` (`build`, `reach`, `callers`, `callees`),
  `tools/nk_decomp.py pdata`, `tools/sh4dis.py`, `tools/datask_l3.py tables`. All repo tools at
  this branch, unchanged.
- **Claims:** C-5640–C-5649
- **Supersedes:** none
- **Superseded by:** none

## Question

Does the router data reader `0x004266ec` (EU2011, `RGD_DATA READ`, M3.6) parse the tile's
section-2 records itself, so that the section-2 grammar can be read off its subtree, or does it
hand section 2 to another task (the task's `Stop`)? If it hands it on, where does the router get
the data back and which code reads it?

## Hypothesis

H112's note: the router subtree differs from the renderer's by three small callees, and the
shared `0x0041ee14` calls `OSM_TaskSend`. Expected: `0x004266ec` builds a request message and
sends it; it touches no section-2 record bytes.

**Falsifier** (before the results): `0x004266ec` or a function it reaches loads from a buffer
holding tile bytes (a file-mapping or file-read import in the subtree, or a pointer from a read
completion), or the message it sends does not reach the data-access task (a receiver other than
the task-id global `0x11fff58`, or an id with no handler in that task's table).

### What `0x004266ec` does (EU2011, from the disassembly)

- `0x004266fc`–`0x00426716`: a sequence counter `*0x009e3e30` (wraps at 20) selects a list
  buffer `r8 = 0x009d9dd8 + n * 0x804`; `u16 [r8] = 0`.
- `0x00426718`–`0x00426738`: a message on the stack at `r15 + 24`: `+8 u16 = 0x14b5`
  (`mov.w` pool `0x004267fe`), `+10 u16 = 2`, `+12 u32 = *0x011fff5c`, `+16 u32 = 64`, `+20 u32
  = r8` (the list), `+24 u32 = 2`.
- `0x00426744`–`0x0042683e`: a loop over 4 slots of 20 bytes in the table at `*0x00e99698` and
  12-byte entries at `*0x00ec3954`; per slot whose `u16 +108` is set and which is not yet
  requested, it appends one 32-byte entry to the list (`index << 5`): `+16 u32` = slot `+92`
  (the mesh id), `+14 u16` = slot `+96` (the `DIVID`), then `u16 [r8] += 1`; it prints
  `RGD_DATA READ START MESH_ID=%08x DIVID=%04x` (pool `0x004268ac` → `0x0017c4ac`).
- `0x00426840`–`0x00426856`: if the list is not empty, `0x0041ee14(*0x011fff58, r15 + 24)`;
  on `-1` a debug string (`0x0017c3a4`).
- `0x0042687a`: `rts` with `r0 = 0`. No other load in the function reads anything but the
  slot tables, the list and the message.

`0x0041ee14(task, message)`: checks the message with `0x0041ebc0` / `0x0041e7a8` (C-874),
reads `u16 +8` and `u16 +10`, and calls `OSM_TaskSend` through the import slot `0x0055d8ec`
(`callees`: `0x0041ee14 … imports=OSMDLL!OSM_TaskSend`).

### Control: the renderer `0x00425f40`

### The receiver

`datask_l3.py tables`: row `0x14b5  1  0x004066ac` of the 43-row message table (defer flag 1).
`0x011fff58` is the data-access task id global (`datask_l3.py` `da_task_id`), so the message
goes to the data-access task (entry `0x003ebfb4`, M3.25), whose dispatcher hands `0x14b5` to
`0x004066ac`.

`0x004066ac(message)` (first `0x78` instructions): `r10 = +12`; **only when `+12` ≤ 1** it
copies `0x2004` bytes from the list pointer `+20` to `0x00d53f20` (`0x003d13e8` at `0x004066de`)
and uses the copy; otherwise (`cmp/gt` at `0x004066d2`) it uses the list at `+20` in place. The
router puts `*0x011fff5c` at `+12`; which branch it takes depends on that value. It branches on
`u16 +10` (sub) = 11 → `0x00406020`, = 4 → `0x00405b78`; calls `0x00405cb4`, then
`0x00408480(1, +16)` (the data-kind word), `0x004060a0`, `0x004083d4`.
`callgraph.py reach 0x004066ac`: `140 functions, 1 unresolved indirect calls, 21 distinct
imports`.

### The reply path (found by the navigator, re-read here)

- **A buffer per request.** In the request loop `0x004266ec` calls `0x00425cb0(entry + 4)` at
  `0x0042677a` for each slot it requests (entry = `*0x00ec3954 + 12 * slot`); on `-1` it calls
  `0x00425cf4` and skips the slot. `0x00425cb0` takes the first free block of the pool
  `*0x00ea675c` (4 blocks of `0x1f404` B, `u16` free flag `1` at +0), marks it used and stores
  block + 4 in `*r4`: one `0x1f400`-byte buffer per slot. `0x004255fc` (init leaf) zeroes the four
  12-byte entries and frees the four blocks.
- **The reply.** `0x00427144` dispatches on the message id: `0x07d0`, `0x0fa0`, `0x14b6`. For
  `0x14b6` it takes the data kind from `+20` when sub `+10` = 9, else from `+16`; kind 64 →
  `0x004268c0(message, 0, 0)`, any other kind → `0x0042613c` (the renderer side,
  `0x00427176`–`0x00427194`).
- **`0x004268c0` stores it.** At `0x00426a56` it calls `0x003edf5c(slot +92 = mesh id, 0x40,
  slot +104, &DIVID from message +14)`, a query into the data-access task's tables that writes a
  size to slot `+104`; on `-1` or a size above `0x1f400` (`0x00426a64`–`0x00426a70`) it gives up.
  Otherwise it copies `slot +104` bytes from the message's `+20` pointer into the slot's buffer
  (`0x003d13e8` at `0x00426aea`), sets the entry's state word to 2 and the slot's `+100` to 1.
- **Who reads the buffer.** `sh4xref --to 0x00ec3954`: 13 loads in 12 functions. Ten of them
  manage entries (allocate, free, state; `0x004266ec`, `0x004268c0`, `0x00426638` frees through
  `0x00425c5c`, `0x00426f88`, `0x00427144`, `0x00427870`, `0x00427a34`, `0x00425bdc`,
  `0x00425c50`, `0x00425cf4`); `0x00425650` is the init leaf above. **Only `0x00422eac` loads the
  buffer pointer and reads its content** (`mov.l @(4,r2),r10` at `0x00422fc0`). Its callers:
  `0x0043fabc`, `0x0043fba8`, both called by `0x00440e00`.
- **What `0x00422eac(r4 = query, r5 = out)` reads.** It calls `0x00424464(19, query, …)`, which
  returns a `u16` table `t` and a `DIVID` (meaning UNKNOWN). With `i = u16 query +16` it requires
  `t[i] & 0x1800 != 0x1800` and `t[i+1] & 0x1000`. It picks the slot of state 2 whose mesh id is
  `u32 query +0` and whose `DIVID` matches, then `k = t[i + 3 + ((t[i+1] >> 13) & 1)]` and reads
  the buffer as `u16` words: `buf[k + 15] & 0x0f00` must be `0x0900` (`0x00422fc8`–`0x00422fd6`);
  `buf[k + 7]` (`0x00422fda`), and if it is 0 a loop through `0x004250e4` looks for another `k`;
  then `d = buf[k + 6]` and the result is `(buf[k + d] & 0xf8) >> 3`, stored as `u16 *out`
  (`0x0042305a`–`0x00423070`). So `k` is a word offset of a structure in the buffer whose words
  `+6`, `+7` and `+15` are read, with `+6` a word offset relative to `k`.


- **FACT:** the router reader `0x004266ec` (EU2011) reads no tile bytes and has no file or
  file-mapping import in its 27-function subtree: it reserves a `0x1f400`-byte buffer per pending
  slot of its 4-slot table, builds a list of `(mesh id, DIVID)` requests and sends one message
  `0x14b5`, sub 2, data kind `0x40`, list pointer at `+20`, to the data-access task
  (`*0x011fff58`) through `0x0041ee14` → `OSM_TaskSend`. The section-2 grammar is not read in
  this subtree.
- **FACT:** the renderer `0x00425f40` sends the same message with data kind `4`; the data kind
  word `+16` is the only difference in the message, so `0x40` = route (section 2) data and `4` =
  map (section 1) data is the reading for the receiver to test. That last step is an
  **OBSERVED** correspondence (two readers, two values), not tested by a run.
- **FACT:** the receiver is `0x004066ac` (row `0x14b5` of the data-access task's table,
  deferred while the map is not ready); it passes the kind word to `0x00408480` and reaches 140
  functions.
- **FACT:** the data comes back to the router: reply `0x14b6` kind 64 → `0x00427144` →
  `0x004268c0`, which copies up to `0x1f400` bytes from the reply into the slot's buffer. The
  only code that reads that buffer's content is `0x00422eac` (called from `0x0043fabc` /
  `0x0043fba8` ← `0x00440e00`), which reads words `k + 6`, `k + 7`, `k + 15` and `k + buf[k+6]`
  of it. **The section-2 reader of the router is `0x00422eac`, in the router task, not in
  `0x004266ec` and not in the data-access task.** The task's `Stop` ("handed on by message")
  therefore does not end the search: the reply path returns the data.
- **UNKNOWN:** what the buffer holds (one level-1 section-2 record as stored, inflated, or
  something the data-access task builds from it), its byte order, what `k` indexes (it comes from
  the table that `0x00424464(19, …)` returns), and so which section-2 fields `+6`/`+7`/`+15` are.
  Reading that statically needs `0x003edf5c`'s data source and `0x00424464`; an L3 run answers it
  directly: drive `0x004268c0` with a `0x14b6` reply whose `+20` points at a factory section-2
  block, then run `0x00422eac` with a read-watch on the buffer. That is M4.54.
- The block's `Input` ("the subtree imports `CreateFileMappingW`/`MapViewOfFile`: the tile is
  memory-mapped, so the reader takes a pointer") is false: it came from C-4284, retracted by
  C-4622, and the import list above has no mapping call.

## Conclusion

The router's RGD reader is a request builder, not a parser. It asks the data-access task for
section 2 by message `0x14b5` (kind `0x40`, handled by `0x004066ac`), gets it back as `0x14b6`
into a `0x1f400`-byte buffer per slot (`0x004268c0`), and the router code that reads the buffer
is `0x00422eac`. No field table was produced: the four word reads of `0x00422eac` are listed, but
what the buffer holds and what `k` indexes are open. `Done when` is not met and M4.40 is
`blocked` on M4.54 (L3: drive `0x004268c0` with a factory section-2 block and read-watch
`0x00422eac`). `docs/format/map-tiles.md` records the request, the reply and the reader.
C-5640–C-5649.
