# EXP-2026-11-20-M4.40: the router reader `0x004266ec` does not parse section 2; it asks the data-access task for it (message `0x14b5`)

- **Status:** done (negative for the task's grammar goal; the task's `Stop` applies)
- **Date:** 2026-11-20
- **Sample:** `archive/head256.img` (IMG256, EU 2011 head, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`), `Navi.exe` of build A,
  `--image-start 0x200200`. No tile bytes are needed: nothing in this record reads a tile.
- **Tools:** python3 3.13.18; `tools/callgraph.py` (`build`, `reach`, `callers`, `callees`),
  `tools/nk_decomp.py pdata`, `tools/sh4dis.py`, `tools/datask_l3.py tables`. All repo tools at
  this branch, unchanged.
- **Claims:** C-5640–C-5645 (C-5646–C-5649 handed to M4.51)
- **Supersedes:** none
- **Superseded by:** none

## Question

Does the router data reader `0x004266ec` (EU2011, `RGD_DATA READ`, M3.6) parse the tile's
section-2 records itself, so that the section-2 grammar can be read off its subtree, or does it
hand section 2 to another task (the task's `Stop`)?

## Hypothesis

H112's note: the router subtree differs from the renderer's by three small callees, and the
shared `0x0041ee14` calls `OSM_TaskSend`. Expected: `0x004266ec` builds a request message and
sends it; it touches no section-2 record bytes.

**Falsifier** (before the results): `0x004266ec` or a function it reaches loads from a buffer
holding tile bytes (a file-mapping or file-read import in the subtree, or a pointer from a read
completion), or the message it sends does not reach the data-access task (a receiver other than
the task-id global `0x11fff58`, or an id with no handler in that task's table).

## Interpretation

- **FACT:** the router reader `0x004266ec` (EU2011) reads no tile bytes and has no file or
  file-mapping import in its 27-function subtree: it builds a list of `(mesh id,
  DIVID)` requests, one per pending slot of its 4-slot table and sends one message `0x14b5`, sub 2, data kind
  `0x40`, list pointer at `+20`, to the data-access task (`*0x011fff58`) through `0x0041ee14` →
  `OSM_TaskSend`. The section-2 grammar cannot be read off this subtree. The task's `Stop`
  ("hands section 2 to another task by message") applies.
- **FACT:** the renderer `0x00425f40` sends the same message with data kind `4`; the data kind
  word `+16` is the only difference in the message, so `0x40` = route (section 2) data and `4` =
  map (section 1) data is the reading for the receiver to test. That last step is an
  **OBSERVED** correspondence (two readers, two values), not tested by a run.
- **FACT:** the receiver is `0x004066ac` (row `0x14b5` of the data-access task's table,
  deferred while the map is not ready); it passes the kind word to `0x00408480` and reaches 140
  functions. The section-2 record parser is in that subtree or in a read-completion handler it
  arms (classes `0x09`–`0x25` of the completion table at `0x178d60` were "not run" in M3.25).
- **IMPLICATION:** the next subtree is `0x004066ac` with kind `0x40`. The cheapest way in is an
  L3 run: mount the card with `datask_l3.py`, then post message `0x14b5` sub 2 kind `0x40` with a
  one-entry list for the mounted tile's mesh id, and record which record-block reads it issues and
  which completion handler loads which bytes. That is M4.51.
- The block's `Input` ("the subtree imports `CreateFileMappingW`/`MapViewOfFile`: the tile is
  memory-mapped, so the reader takes a pointer") is false: it came from C-4284, retracted by
  C-4622, and the import list above has no mapping call.

## Conclusion

The router's RGD reader is a request builder, not a parser. It hands section 2 to the
data-access task by message `0x14b5` (kind `0x40`), handled by `0x004066ac`. No field table was
produced; `Done when` is not met and M4.40 is `blocked` on M4.51 (follow message `0x14b5` kind
`0x40` in the data-access task to the section-2 record reader, L3). `docs/format/map-tiles.md`
records the message and the receiver. C-5640–C-5645.
