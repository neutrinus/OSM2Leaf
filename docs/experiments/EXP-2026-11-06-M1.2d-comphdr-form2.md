### Structural findings (all 58, derived)

- Every section contains the CE LZXD block marker `5b 80 80 8d` (u32 LE
  `0x8d80805b`) at a variable offset `m` in {25,28,31,34,40,46,55,58,61,64,76,94,97,124,247}
  (58/58 found). Form 1 HOLDS sections have this marker at offset 22 (after the
  22-byte header), 40/40 sampled.
- For all 58, `(m - 16) % 3 == 0` and `n = (m - 16) / 3 >= 3` (58/58). The
  bytes before `m` are `n` little-endian `u24` values followed by a 16-byte
  trailer.
- `u24[n-1] == psize` (58/58). `u24[0] <= vsize` (58/58); `u24[0] == vsize` in
  37/58, `u24[0] < vsize` in 21/58 (actual uncompressed data length < allocation,
  same relationship form 1 allows).
- Trailer (4 × u32 LE) = `[0x10, 0x1000, block_bytes, 0x1000]` (58/58 for
  elements 0,1,3; element 2 varies, not validated by the parser).
- The payload (from `m` to `psize`) contains exactly `n - 1` `5b 80 80 8d`
  markers (58/58): one per compressed block.
- `vsize > psize` for all 58 (compressed, not stored). `cecompress.py`
  auto/lzss/lzx/xpress/xpress-huffman did not decode sampled form-2 payloads
  starting at `m` (codec not identified by this task).

## Interpretation

**Form 2 is a multi-block compressed framing, not stored and not a different
block-level codec** (relative to an uncompressed payload): a variable-length
header `[u24 × n][u32 0x10, u32 0x1000, u32 block_bytes, u32 0x1000]` (size
`3*n+16`) describes `n-1` compressed blocks, whose data follows at `3*n+16`
starting with `0x8d80805b` markers. It carries the same `u24[0]=uncompressed_len
<= vsize` / `u24[n-1]=psize` semantics as form 1's lengths, so M1.3 knows the
uncompressed target and the payload boundaries for every section. The *codec of
the blocks* (how `0x8d80805b` block bodies decode) remains the M1.2b/c/M1.3
problem; form 2 solves framing, which is what M1.2d requires.

C-1713's `0x10000000 | psize` hypothesis was a partial artefact of reading form-2
bytes through form-1 field positions (true for 33/58 at +14); the real structure
is the `u24` table above.
