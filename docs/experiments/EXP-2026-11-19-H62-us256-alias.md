# EXP-2026-11-19-H62: `fetch_image.py --image US256`, a pinned US firmware head

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** first 256 MiB (bytes `0`–`268435455`) of
  `https://files.viaaq.eu/sd-images/LEAF_2011-2012_US.img` (US 2011 card,
  full-image SHA-256 `53342430a1bb58d3ed6eb68c5563f079c710a400134d522e6192489b324c5383`);
  head SHA-256 `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`.
  Reference copy: `archive/us256.img` (same hash). Negative sample:
  `archive/head256.img` (EU 2011 head, `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`).
- **Tools:** `python3 3.13.18` (stdlib `hashlib`, `urllib`); repo tool

- **Claims:** C-3820–C-3823
- **Supersedes:** none
- **Superseded by:** none

## Question

Can every US task fetch and verify the US 2011 firmware head with one pinned
command (`--image US256`), so a truncated or overwritten local copy is caught
instead of only size-checked?

## Hypothesis

Adding `PART_PINS[("US", "256M")]` and the alias `US256 = US --part 256M`
(the `IMG256` template) makes both `--image US256` and `--image US --part 256M`
verify the SHA-256 `70d945d8…`, and the downloaded head is byte-identical to
`archive/us256.img`. **Falsifier:** the freshly downloaded head hashes to
anything other than `70d945d8…` (upstream re-release; per the task's `Stop`,
the pin would then be wrong and must not be committed), the tool still prints
`no SHA-256 pinned`, or a corrupted copy passes `--verify --image US256`.

## Method

1. **Sample and hash.** As above; the pinned hash agrees with
   `tools/fixtures/fn_match_eu_us_2011.json` `us_head.sha256` (now a selftest
   check).
2. **Commands.** Before the change (base `a90a83f`), then after it:

   ```bash
   mkdir -p /home/user/scratch/h62
   # before (a90a83f)
   python3 tools/fetch_image.py --image US256 -o /home/user/scratch/h62/x.img
   python3 tools/fetch_image.py --verify archive/us256.img
   python3 tools/fetch_image.py --image US --part 256M -o /home/user/scratch/h62/us-part-before.img
   cmp /home/user/scratch/h62/us-part-before.img archive/us256.img
   # after (this branch)
   python3 tools/fetch_image.py --list
   python3 tools/fetch_image.py --image US256 -o /home/user/scratch/h62/us256-new.img
   python3 tools/fetch_image.py --image US --part 256M -o /home/user/scratch/h62/us-part-after.img
   cmp /home/user/scratch/h62/us256-new.img archive/us256.img
   python3 tools/fetch_image.py --verify archive/us256.img
   python3 tools/fetch_image.py --verify archive/us256.img --image US256
   # negative controls
   python3 tools/fetch_image.py --verify archive/head256.img --image US256
   mv /home/user/scratch/h62/us-part-after.img /home/user/scratch/h62/flip.img
   printf '\xff' | dd of=/home/user/scratch/h62/flip.img bs=1 seek=1000 conv=notrunc
   python3 tools/fetch_image.py --verify /home/user/scratch/h62/flip.img --image US256
   head -c 268435455 /home/user/scratch/h62/us256-new.img > /home/user/scratch/h62/short.img
   python3 tools/fetch_image.py --verify /home/user/scratch/h62/short.img --image US256
   python3 tools/selftest.py --only fetch_image
   rm -rf /home/user/scratch/h62
   ```

3. **Controls.** *Positive:* the real head downloaded twice (via the alias and
   via `--part 256M`) must verify and be `cmp`-identical to
   `archive/us256.img`. *Negative:* the EU head, a one-byte flip at offset
   1000 and a one-byte-short copy must each be refused with exit 1; selftest
   `resolve("US256", "1G")` must exit 2.
4. **Scope.** 1 file (`tools/fetch_image.py`), 1 pin, 1 alias; 2 real
   downloads of 268,435,456 B each; 3 negative files. No full-image pin, the
   EU head or any EXP is changed.
5. **Falsifier.** As stated under Hypothesis, before the result.

## Observations

- Before: `--image US256` → `unknown image 'US256'; use --list`, exit 2.
  `--verify archive/us256.img` → `size 268435456, sha256 70d945d8…04da: no
  pinned match`, exit 1. `--image US --part 256M` → `268435456 bytes, size
  verified; no SHA-256 pinned` in 36.4 s, exit 0; `cmp` with
  `archive/us256.img`: identical.
- After: `--list` prints `US256  268435456  70d945d8…04da  = US --part 256M`
  under the `IMG256` row.
- `--image US256 -o …/us256-new.img` → `268435456 bytes, SHA-256 verified`
  (26.6 s), exit 0; `cmp` with `archive/us256.img`: identical.
- `--image US --part 256M -o …/us-part-after.img` → `268435456 bytes, SHA-256
  verified` (35.9 s), exit 0.
- `--verify archive/us256.img` → `matches US 256M`, exit 0;
  `--verify archive/us256.img --image US256` → `matches US256`, exit 0.
- Negative: EU head → `sha256 92aa525d…a7f9 != pinned 70d945d8…04da`, exit 1;
  byte flip → `sha256 83b54ba2d66102c676a1aca8cb18047f64b559e2e08b0bd523adb1a2f3a4b101 != pinned …`,
  exit 1; short copy → `size 268435455 != expected 268435456; sha256
  209f822f…23f5 != pinned …`, exit 1.
- `--selftest`: 5 new checks (`US256 resolves to US 256M head with pinned sha`,
  `US --part 256M is SHA-256 pinned`, `US256 with another part refused`,
  `US256 pin agrees with fn_match fixture us_head`, `US256 pin differs from
  IMG256 pin`) plus the listing check extended to six keys; `failures: 0`.
  `selftest.py --only fetch_image`: `passed=1 failed=0`.

## Interpretation

- **FACT:** the upstream US 2011 card's first 256 MiB hash to `70d945d8…`
  on 2026-11-19, the same value the fixture and M1.22/M1.28 recorded; the
  upstream image has not been re-released.
- **FACT:** `fetch_image.py` now refuses a US head whose bytes differ by one
  byte or one length unit, which the size-only check before this change
  would have accepted (the short copy aside).
- **UNKNOWN:** none for this task.

## Conclusion

`python3 tools/fetch_image.py --image US256 -o PATH` is the re-runnable,
hash-verified way to get the US 2011 firmware head (rule 11), and the
`Shared inputs` table in `TODO.md` names it. `--image US --part 256M` carries
the same pin. Claims C-3820–C-3823 added.
