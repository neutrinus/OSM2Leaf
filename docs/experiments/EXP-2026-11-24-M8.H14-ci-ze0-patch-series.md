## Question

Does every PR/push run a CI job that verifies the pinned QEMU 11.1.3 tarball
by SHA-256, applies the whole ze0 patch series via `build.sh --check-version
11.1.3`, runs `build.sh --selftest` including a patch-name lint, and goes RED
when a patch no longer applies — with no full build and no vendor image?

## Hypothesis

One blocking `ze0-patches` job in `.github/workflows/ci.yml` is green on the
real 30-patch series and red on a series with a deliberately broken hunk.
Falsifier: the job stays green with a patch that does not apply.

## Method

1. **Sample and hash.** No vendor sample. The pinned tarball SHA-256 above
   was read from `build.sh` by the printing command in the Inputs table; the
   CI cache key is `qemu-11.1.3-tar-<that SHA-256>`. Patch count `30` was
   printed by `ls tools/qemu-ze0/patches/*.patch | wc -l`. Revision measured:
   `git rev-parse HEAD` = `e62becb9dbfecb40af43b6095b812885693e9c0f` (clean),
   `bf937b1f824e95362628d4420ce34f07629add7f` (RED control).

2. **Commands.** Runnable from the worktree root; no ellipsis:
   ```bash
   grep -rc check-version .github/workflows/
   ls tools/qemu-ze0/patches/*.patch | wc -l
   sed -n 's/^QEMU_SHA256="\([0-9a-f]*\)"/\1/p' tools/qemu-ze0/build.sh
   bash tools/qemu-ze0/build.sh --selftest
   bash tools/qemu-ze0/build.sh --lint-patches --patch-dir tools/qemu-ze0/patches
   bash tools/qemu-ze0/build.sh --check-version 11.1.3 \
     --srcdir "$HOME/.cache/qemu-ze0" --patch-dir tools/qemu-ze0/patches
   gh pr checks 751
   ```
   RED control (on a temporary commit on the same branch, then reverted):
   ```bash
   # point one hunk's `--- a/hw/sh4/Kconfig` at a nonexistent path
   bash tools/qemu-ze0/build.sh --check-version 11.1.3 \
     --srcdir "$HOME/.cache/qemu-ze0" --patch-dir tools/qemu-ze0/patches
   gh pr checks 751
   ```

3. **Controls.** Positive: the unmodified 30-patch series — local verdict
   `30 applied, 0 failed`, CI job green (run `45374933105`). Negative: a
   hunk in `ze0-0002-hw-sh4-ze0-debug-serial.patch` pointed at a nonexistent
   file — local verdict `28 applied, 2 failed`, exit 4; CI job RED
   (run `45376535423`, failing step `Apply the whole ze0 series (build
   nothing)`). Lint negatives: synthetic duplicate `ze0-0001` number and
   malformed `ze0-h4x` stem both make `--selftest` fail; the real series
   (25 numbered + 5 legacy) stays green. No-op mutations were rejected as
   controls: editing a context line still applied under `patch` fuzz, so the
   final control used a nonexistent target path.

4. **Scope.** Two workflow jobs pre-existed (`quality`, `l3`); this task adds
   one (`ze0-patches`) with four checks. The corpus is the 30 `*.patch` files
   under `tools/qemu-ze0/patches/`, applied cumulatively to the pinned QEMU
   11.1.3 source tree by `patch -p1 --forward --batch`. Selftest runs 88
   checks with build tools present and 84 with meson removed (4 honest
   SKIPs). No QEMU compilation, no vendor image, no card tree, no L3/L4/L5
   acceptance claim (rule 13). The parallel `quality` job failed on
   `refer002_add_station` (another task); `python3 tools/selftest.py --only
   refer002_add_station` passes locally on this tree and the failure is not
   caused by this task's files.

5. **Falsifier.** A patch that does not apply but the job stays green. It did
   not fire: run `45376535423` was RED on exactly the check-version step.

## Interpretation

- **FACT:** the new job is blocking and propagates build.sh's exit; a patch
  that does not apply turns it RED (run `45376535423`).
- **FACT:** the tarball cache is keyed by the SHA-256 read out of build.sh, so
  a pin bump invalidates the cache and forces a re-verified download.
- **OBSERVED:** the patch-name lint covers the real series plus positive and
  negative synthetic corpora inside `build.sh --selftest`.
- **UNKNOWN:** GitHub runner reachability after a cache miss was observed
  once (download succeeded); no second miss was measured.

## Conclusion

`.github/workflows/ci.yml` gains one blocking `ze0-patches` job and
`tools/qemu-ze0/build.sh` gains `--lint-patches` plus selftest coverage and an
honest SKIP of the build-tool-dependent network case. The series-applies gate
is green on PR #751 and red on a deliberately broken hunk. No format or
firmware-knowledge claim is made; the only claims are that the CI gate
behaves as stated. Rule 13: this is CI gating, not firmware acceptance.
