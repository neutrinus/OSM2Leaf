# EXP-2026-11-23-M9.74: OBJDLL binds natively, but the reply path still does not walk unit 0

- **Status:** failed (negative result with positive controls)
- **Date:** 2026-11-23
- **Sample:** `archive/head256.img` SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; EU 2011 card SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Tools:** Python 3.15.0; `tools/vcard_l3.py` (extended), `tools/cerom.py`, `tools/sh4dis.py`, `tools/sh4xref.py`, `tools/rpf_reply_l3.py`, `tools/read_watch` via `vcard_l3.Machine.eng`

## Question

Can binding `OBJDLL.dll` as a native second module expose the firmware code that reads the section-2 unit-0 pointer from the RPF kind-8 reply, with reading VAs?

## Hypothesis

M4.55's zero unit-0 reads were caused by missing OBJDLL models; with OBJDLL's real exports bound, the RPF reply path dereferences unit 0.

**Falsifier:** with OBJDLL exports bound and executing, the unit-0 watch still records 0 reads while a reply-list watch records > 0.

## Method

1. **Sample and hash.** Files above; build A, EU 2011, no vendor bytes committed.
2. **Commands.** From the repo root with `archive/` present:

   ```bash
   python3 tools/vcard_l3.py --selftest
   python3 tools/rpf_reply_l3.py --selftest
   python3 tools/rpf_reply_l3.py archive/head256.img --json rep.json
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img sections OBJDLL.dll
   python3 tools/sh4dis.py archive/head256.img OBJDLL.dll --image-start 0x200200 \
       --va 0x034942d8 --count 60
   ```

   The binding was exercised by a scratch driver that mounts with STDDLL only, then calls
   `Machine.bind_native(image, "OBJDLL.dll", names)`, seeds the pending reply entry and runs
   `0x00336dc0` for modes 1/2/3 with watches on `unit0` and the reply list.

3. **Controls.** *Positive:* reply-list watch (10/20/30 hits in M4.55, reproduced here) proves the watch is live; OBJDLL export call logging (`import_log`) proves the native module is in the engine. *Negative:* sub-5 reply has `0xffffffff` pointers; a watch reporting reads there would be invalid.
4. **Scope.** EU2011 build A. 400 OBJDLL imports / 406 exports enumerated via `cerom.py`; OBJDLL's 4 sections (1 exec, 1 exec, 2 data) mapped; 175,000 SH-4 instructions of OBJDLL `.text` scanned for pointer-then-dereference patterns (29 candidates, each mapped to its nearest export). Excluded: route computation trigger, US2011, L4/L5.
5. **Falsifier.** Any `unit0` watch hit with a PC in OBJDLL would have confirmed the hypothesis.

Binding OBJDLL **before** the card mount is not viable:

```
Blocked: the card did not mount: UnmappedAccess: no mapped region covers
0x01e39ff8..0x01e39ffc (... native/OBJDLL.dll@0x3481000 ...)
```

That address lies in OBJDLL's compressed `.data` (realaddr `0x01e33000`); mapping decompressed
sections fixed the mount, but binding all 400 imports then made the mount fault at
`0x000136b8` (`IllegalInstruction 0x5b`), so binding is done after mount and limited to
the five named graph exports.

OBJDLL `.text` scan (175,000 decoded instructions): 29 functions load a pointer from a
struct field and dereference it; the only one that reads both `+16` and `+24` and then calls
through a table is `0x034942d8`, a struct-copy helper whose callee is an OBJDLL IAT slot at
`0x01e330a4`. The export names of the 29 candidates are mostly `OBJ_Setting_canLoad+…`
(large inlined function) and `OBJ_RoutePntTbl_*`; none is a section-2 unit walker.

## Interpretation

- **FACT:** `vcard_l3` now binds multiple second modules and maps a native module's compressed sections; `Machine.bind_native()` loads a module after mount. All behaviours are covered by `--selftest` for the pure helper and by the run above for the engine.
- **FACT:** binding OBJDLL before mount changes the mount path and faults; post-mount binding is the workable order.
- **FACT:** with OBJDLL in the engine, the RPF reply path still records **0** unit-0 reads and 10/20/30 reply-list reads. The calls made in that path are event/bookkeeping exports (`OBJ_CarPos_*`, `OBJ_RoutePntTbl_setEventPnt`, `OBJ_DiscInfo_*`), none of which reads unit 0.
- **OBSERVED:** the OBJDLL IAT slots inside its decompressed `.data` are not re-bound by this change, so OBJDLL's own call-through helpers cannot yet be executed faithfully.
- **UNKNOWN:** the stimulus that makes the firmware walk unit 0. No route-set/destination message tool exists in `tools/`, so the route-search stage (M9.56/M9.72 territory) was not run.
- **HYPOTHESIS:** unit 0 is consumed by the route computation, not by the reply handler; finding its reads needs an L3 route-request trigger, not more module binding.

## Conclusion

No unit-0/unit-2 word table with reading VAs was produced; `docs/format/map-tiles.md` is unchanged and M4.40/M5.57 stay blocked. The reusable artifact is the multi-module native binding in `tools/vcard_l3.py` (`native_specs`, `bind_native`, compressed-section mapping) plus claims C-9900–C-9903. M9.74 is set `blocked` with `Unblock: M9.75` (trigger a route computation in L3 and read-watch unit 0). This is a negative result with live positive controls, not an inference from a failed run.
