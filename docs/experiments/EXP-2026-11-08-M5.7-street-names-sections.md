## Question

Can `tools/tilewriter.py` write OSM street names into the ZE0 tile name
sections so that each road shape's `name_off` resolves to its label in the odd
partner (background) record's names section, while preserving every byte outside
the regenerated road/background partner pairs and keeping the factory
splice/L2-structural path intact?

## Hypothesis

1. A level-1 road shape's word 4 is the name offset (`0xffff` = none) into the
   odd partner record's names section (`docs/format/map-tiles.md`, C-280
   context); `fa_encode.build_record(..., name_offs=...)` and
   `fa_encode.names_section(labels, items)` produce the road-record name refs
   and the names-section bytes used by `rd_build`. **Falsifier:** a selftest
   shape with `name_off != 0xffff` does not resolve in the partner's parsed
   names section, or `ze0_decode.parse_names_section` cannot read the label.
2. Merging a names section into a `clarion_bg`-parsed background record requires
   a strict rebuild (`r["strict"]=True`) because `clarion_bg.build_record`
   returns the original `plain` bytes in non-strict mode when the rebuilt record
   differs from source; without strict rebuild, names are silently discarded.
   **Falsifier:** merge without `strict=True` produces a record whose names
   section contains the new label (it does not; negative control in Method).
3. The factory splice can update the odd partner background pair (`2*col+1`) in
   the same slot block as the regenerated road pair without changing section 2,
   section 4, header/tables, or any section-1 record not in the changed-pair set.
   **Falsifier:** `verify_factory` detects a changed section-2/4 record or a
   section-1 record outside `changed_pairs`.

## Method

1. **Sample and hash.** No vendor sample. The selftest constructs
   `make_factory("B48R058R")` (synthetic 3-section tile with background partners
   at rows 4/5 col 3, pair 7) and an IMF with `w100` carrying
   `tags={"highway":"secondary","name":"ul. Testowa"}` and `w101` unnamed
   residential. All data is generated in a temp directory.
2. **Commands.**

```bash
cd /home/marek/projekty/OSM2Leaf-wt-M5.7
python3 tools/tilewriter.py --selftest
python3 tools/selftest.py --only tilewriter
python3 tools/claims_check.py
python3 -m py_compile tools/tilewriter.py
```

3. **Controls.** *Positive*: a named IMF way (`w100`, "ul. Testowa") produces a
   road shape with `name_off != 0xffff`; the odd partner background record
   (row 4, pair 7) contains a names section; `ze0_decode.parse_names_section`
   resolves that `name_off` to `('ul. Testowa', '')`. A clipped fragment of the
   same named way in row 5 keeps a resolvable `name_off`. *Negative*: the unnamed
   residential shape in the mixed row-4 parcel has `name_off == 0xffff`;
   `--no-names` (`write_names=False`) produces no `name_off` values and
   `names_merged == 0`. A direct `clarion_bg` merge without `strict=True`
   returns the original plain bytes and discards names (confirmed during
   implementation; the production path sets `strict=True`).
4. **Scope.** `tools/tilewriter.py` factory-splice and synthetic-build paths
   for level-1 road records written through the existing 0x2046 spliceable
   mechanism (C-1063/C-2810 context). Name labels are taken from OSM `name`
   (tag or record-level) and formatted as `1=NAME`; `ref` is not emitted.
   Sections 2 and 4 are unchanged. The test covers the synthetic fixture's two
   parcels/three shape instances (one named, one unnamed, one named clipped
   fragment) and 68 selftest checks total. Not covered: real factory tile bytes,
   L2 on a real card tree with named roads, `ref` labels, cross-tile naming,
   non-0x2046 directories, section-4 name content, or firmware rendering.
5. **Falsifier.** If `name_off` did not resolve in the partner names section, if
   `merge_names_section` silently dropped names (non-strict return), if
   `verify_factory` reported an unchanged-record change outside `changed_pairs`,
   or if `--no-names` still produced merged names, the implementation would be
   wrong.

probe).

## Interpretation

- **OBSERVED:** `tools/tilewriter.py` can set per-shape `name_off` values and
  merge `fa_encode.names_section` bytes into the odd partner background record's
  `names` section (`clarion_bg` w11/w12) during a factory splice; `name_off`
  resolves through `ze0_decode.parse_names_section`. Clipped fragments of a
  named way retain the label. The synthetic fixture passes 68/68 checks and
  `selftest.py --only tilewriter` passes.
- **OBSERVED:** `clarion_bg.build_record`'s non-strict "return source when
  different" path discards a names-section merge unless `strict=True` (or
  equivalent). `tilewriter.merge_names_section` sets `strict=True`.
- **HYPOTHESIS:** The same mechanism works on real EU factory 0x2046 parcels
  with real OSM names and passes L2 when DRSTR is rebuilt (by analogy with
  C-1064/C-1065); not tested in this worktree because the EU 2011 image was not
  present/fetched.
- **UNKNOWN:** Firmware rendering/label lookup of names written by this path
  (rule 13). The effect of `ref` labels, non-ASCII normalization beyond UTF-8
  storage in the names section, and name behavior in non-0x2046/preserve-only
  directories is not established.

## Conclusion

M5.7 is implemented in `tools/tilewriter.py`: IMF `name` tags become `1=NAME`
labels, road shapes receive `name_off` values, and the odd partner background
record gets an updated names section during factory splices (0x2046). The path
is covered by synthetic selftests with positive and negative controls and keeps
header/tables/sections 2 and 4 unchanged outside the declared changed pairs.
Claims C-1090–C-1092 record the mechanism as tool-verified/synthetic; real-tile
L2 with names and firmware acceptance remain open.
