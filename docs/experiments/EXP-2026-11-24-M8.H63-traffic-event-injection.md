# EXP-2026-11-24-M8.H63: one TMC event injected at `fn 0x003bcc7c` reads `RDSTM001/LCTBL001` and returns the located place (present code) vs not-found (absent code)

- **Status:** done
- **Date:** 2026-11-24
- **Sample:** `archive/head256.img` (134,217,728 B read), SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; full EU 2011 card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` (8,057,257,984 B), SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Tools:** Python 3 (stdlib); `tools/tmc_inject_l3.py` (new, `--selftest`), `tools/tmc_req_l3.py`, `tools/lctbl_lookup_l3.py`, `tools/lctbl_build.py`, `tools/tmc_fielddir.py`, `tools/nk_decomp.py pdata`, `tools/sh4dis.py`, `tools/va_class.py`, `tools/rdstm_place.py`, `tools/ce_strfind.py`
- **Claims:** C-7600–C-7609
- **Supersedes:** none
- **Superseded by:** none

## Question

When a decoded TMC traffic event is injected at M8.H62's EU2011 entry point
`fn 0x003bcc7c` with one location code that is present in `RDSTM001/LCTBL001.DAT`
and one that is absent, do the two calls drive different paths — does the
present code read the `LCTBL001` ranges that the model predicts and return a
located place, while the absent code returns not-found without a record-page
inflate?

## Hypothesis

The wrapper forwards the three lookup keys from its context (`+16/+20/+24`)
through `fn 0x003bcac0` → `fn 0x003c0e68` → `OSM_TaskSend` as a `0x14e4:1`
request; the firmware's data-access + map-file tasks (already runnable at L3)
then read `LCTBL001.DAT` and answer `0x14fb`.  A code present in the table
returns status 1 with a 48-byte TMC place record; an absent code returns
status 4 after index-page reads only. **Falsifier** (task wording): both codes
take the same path (identical read sets and outcomes), or the event is dropped
before the lookup with no `LCTBL001` read at all (then the gate is recorded and
the task stops, per the Stop rule).

### 3. Controls

*Positive:* `lctbl_lookup_l3.py run … --lookup 2,25,1203` (the predecesor's
oracle) prints `status 1` and `PASS: record equals the model's (48 B)`;
`--lookup 2,25,60000` prints `status 4` and `PASS: not in the model`. The
injected present code must likewise answer `0x14fb` with status 1, 2 inflates
and a 48-byte record equal to the model; the tool's `judge()` re-checks the
record bytes (`LL.swap16(got) == expected`).

*Negative, three distinct artifacts:*
1. **absent location code** `2,25,60000`: must answer status 4 with no
   record-page inflate; this is the falsifier control (if it produced the
   same reads/status as the present code, the task is falsified).
2. **injected-context mutation** `--mutation null-context`: `r4 = 0` must give
   `r0 = 0xffffffff`, no `0x14e4` message and no `LCTBL001` read (the null
   guard at `fn 0x003bcc7c:0x003bcca0` / `fn 0x003bcac0:0x003bcae4`).
3. **data-layer request-id mutation** `--mutation wrong-id`: id `0x14e4`
   changed to `0x14f4` must read `REFER001/POINT001.DAT` only (4 reads) and
   **zero** `LCTBL001` reads (M8.H62's POINT control, C-5680/C-5682).

No vendor bytes are committed; only the tool command and its printed numbers
are recorded.

### 4. Scope

L3 only: the EU2011 `Navi.exe` data-access task + map-file task + the
`HDL_MapTblTask` inflate run on the real EU 2011 card prefix in PySh4.  The
call is a real `m.call(0x003bcc7c, [p])` in the firmware, not a replay of the
data-layer request.  One fresh mounted machine is used per code: the
firmware's record-decoder global `0x006f3918` survives a lookup, and after a
found lookup a second injection on the same machine fails its null guard
regardless of code (observed, not assumed) — a fresh mount reproduces the
loader's zero state.  Not covered: iNai/RDS group decoding, the in-vehicle
tuner state, US 2011, L4/L5 (rule 13).  Corpus counted: 1 image, 1 card, 4
injections, 2 codes, 2 negative mutations, 10 tool selftests.

### 5. Falsifier

As stated under Hypothesis. The tool prints both codes' `(LCTBL read ranges,
status, inflate count)` signatures and asserts they differ; if identical it
prints `FALSIFIED` and exits 1, and the task would be `blocked` rather than
`done`.

## Interpretation

- **FACT (C-7600):** Calling `fn 0x003bcc7c` with a populated context actually
  drives the EU2011 firmware to issue `0x14e4:1` and read
  `RDSTM001/LCTBL001.DAT`; this is the traffic-side injection the M8.H62 doc
  prescribed (the data-layer replay is only the positive control).
- **VERIFIED (C-7601):** For the present code `(2,25,1203)` the injected call
  reads exactly the ranges `lctbl_lookup_l3`/`lctbl_build.parse` predict —
  header `0x0/0x1000`, catalog `0x1000/0x3600`, two index pages
  `0x4600/0x1000` + `0x7600/0x1000`, page directory `0x721800/0x100` and
  record page `0x318138/0x2678` (twice) — answers `0x14fb` status 1 with 2
  inflates, and returns a 48-byte record equal to the model. The decoded
  place is `first_name='Katerina', second_name='II/605', exit_no='Exit 144'`
  (C-7602). `rdstm_place.py`'s role remains the static record/link model; the
  byte ranges are printed by the L3 tools, not by that tool (C-7603).
- **VERIFIED (C-7604):** For the absent code `(2,25,60000)` the injected call
  takes the not-found path: status 4, four index/header reads, no page
  directory or record page, 0 inflates. The two codes' signatures differ, so
  the task falsifier ("both codes take the same path") is operationally
  refuted (C-7605).
- **VERIFIED (C-7606):** The artifact-level negative controls work: `r4 = 0`
  gives `r0 = -1` with no message and no LCTBL read; id `0x14f4` reads
  `POINT001` only and no LCTBL, so the LCTBL reads are specific to `0x14e4`
  and to a valid context (C-7607/C-7608).
- **OBSERVED (C-7609):** One mounted machine cannot be reused for two
  injections: the firmware's record-decoder global `0x006f3918` keeps state
  and a second call fails its null guard irrespective of code; the recipe
  therefore uses one fresh mount per code. This is an L3 harness constraint,
  not a firmware finding about traffic handling.
- **UNKNOWN:** The iNai/RDS wire-code → event-table row mapping and the in-car
  tuner state remain open (C-7598); no L4/L5 acceptance is claimed (rule 13).

## Corrections after navigator review

- Split the predictor clause: code presence comes from `lctbl_build.parse` /
  `lctbl_lookup_l3`; byte ranges are printed by the L3 tools;
  `rdstm_place.py` is the static record/link model and is **not** cited for
  byte offsets.
- Defined "returns a place" as an observable: status 1 + the model-equal
  48-byte record, decoded via `tmc_fielddir.decode_record` into named fields
  (`Katerina`, `II/605`, `Exit 144`), not a bare exit-0 claim.
- Added the full message-carry loop (HDL_MapTblTask `0x14b8` inflate turns),
  so the present code reaches the record page; selected the EXP recipe option
  and made no edits to `tools/l3check.py` (M9.62 owns it).
- Implemented both distinct negative mutations (null context, wrong id) and
  the side-by-side falsifier signature comparison.
- One fresh mount per code (see C-7609) after observing that the firmware's
  decoder state is not reentrant across injections on one machine.

## Conclusion

`tools/tmc_inject_l3.py` calls the M8.H62 injection point `fn 0x003bcc7c` at
L3 and, for the present code `(2,25,1203)`, records the `RDSTM001/LCTBL001`
ranges the model predicts plus a located 48-byte TMC place record (`Katerina`,
`II/605`, `Exit 144`); for the absent code `(2,25,60000)` it records the
not-found path (status 4, no inflate). The null-context and wrong-id mutation
controls pass, and the two codes' signatures differ, so the task falsifier is
refuted. `docs/research/reader-coverage.md` rows 21–22 now carry this L3
injected-event result. Claims C-7600–C-7609 are added. L4/L5 acceptance and
the iNai wire-code mapping stay open (rule 13).
