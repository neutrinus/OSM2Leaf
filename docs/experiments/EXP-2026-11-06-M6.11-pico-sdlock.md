# EXP-2026-11-06-M6.11: RP2040 SD CMD42 lock/unlock tool

- **Status:** done (design, firmware, host self-test); hardware test is M6.9
- **Date:** 2026-11-06
- **Sample:** none (no vendor data; synthetic simulated card, dummy passwords)
- **Claims:** C-1940–C-1944
- **Supersedes:** none
- **Superseded by:** none

## Question

Can a Raspberry Pi Pico replace the "native SDHCI slot" that M6.9 needs, i.e.
set, lock, unlock and clear an SD card's CMD42 password over SPI, with the
ERASE path made impossible, so that the image-then-lock flow (write the card
image with a USB reader, then lock it) works without special PC hardware?

## Hypothesis

Yes. SPI mode supports CMD42 and CMD13 on every SD card with command class 7
(SD Physical Layer Simplified Spec §4.3.7, §7.3); the RP2040 has hardware SPI
at 3.3 V. The open risks are card-model behaviour and the password encoding,
not the host.

## Method

```bash
python3 tools/sdlock_pico_check.py -v       # host build + simulated card
python3 tools/selftest.py                   # registry picks it up

# Mutation controls (scratch copies, not committed):
#  M1 sdp_lock_block() lets ERASE through   (flags check -> only bit 7)
#  M2 CRC7 polynomial 0x09 -> 0x0B
#  M3 setlock sends SET_PWD without LOCK and returns
cc -std=c99 -I<mut> <mut>/sd_proto.c src/sd_card.c test/test_sdlock.c && ./a.out

# Cross-compile the hardware-independent part for the RP2040 core:
arm-none-eabi-gcc -mcpu=cortex-m0plus -mthumb -Os -std=c11 -Wall -Wextra -Werror \
  -c tools/sdlock-pico/src/sd_proto.c tools/sdlock-pico/src/sd_card.c

# Full firmware (not run here, see Observations):
cd tools/sdlock-pico && cmake -S . -B build -DPICO_BOARD=pico && cmake --build build
```

The simulator is byte-level SPI: it parses 6-byte commands, checks CRC7 on
CMD0/CMD8 like a real card, answers R1/R7/OCR/R2, sends the CSD as a data
block, waits for the `0xFE` token on CMD42, applies the spec's set / clear /
lock / unlock / set+lock / forced-erase semantics, locks at "power-up" when a
password is stored, and sets the clear-on-read `LOCK_UNLOCK_FAILED` bit. Any
command outside CMD0/8/9/13/16/42/55/ACMD41/58 is counted as a driver bug.

## Observations

- Host test: `sdlock host test: 572 checks, 0 failed`; `selftest.py`:
  `tool:sdlock_pico_check PASS`, `passed=27 failed=0 skipped=20`.
- Scenarios passed: init on a fresh and on a locked card; lock without a
  password → `LOCK_UNLOCK_FAILED`; set+lock; locked after power cycle;
  wrong password (bytes reversed) and wrong length → failed, state kept;
  verify; temporary unlock re-locks after power cycle; clear from locked;
  unlocked after power cycle once cleared; card that stores but does not
  lock on the combined command (fallback `LOCK` used); card without class 7
  → no CMD42 sent; all 248 disallowed flag values → `SD_ERR_BAD_ARG` with
  the card intact; no card → `SD_ERR_NO_RESPONSE`.
- Audit across all scenarios: 0 ERASE frames received, 0 non-whitelisted
  commands, 0 CRC failures.
- Mutation controls: M1 → 307 of 692 checks fail ("a forced-erase frame
  reached the card"); M2 → 3 fail (CRC frames, init); M3 → 4 fail.
- Cross-compile: `sd_proto.o` 848 B text, `sd_card.o` 1928 B text, no
  warnings.
- Full `.uf2` build: **not run.** Building the cloned Raspberry Pi Pico SDK
  was refused by the sandbox's permission policy (external code). `main.c`
  (USB shell, SPI binding) is therefore uncompiled.

## Interpretation

- **FACT (spec):** `PWD_LEN` is at most 16 bytes for one password (32 for
  old+new during a change).
- **HYPOTHESIS (C-1940):** the unit password is 16 bytes: the 8 hex digits
  of the "SD PIN" service screen as 4 raw bytes, then the 12-character ASCII
  suffix of C-075. Reading the digits as ASCII gives 20 bytes, which no SD
  card accepts. Byte order of the 4 bytes is UNKNOWN.
- **VERIFIED (simulator, C-1941):** the driver cannot emit a CMD42 block with
  ERASE or a reserved bit, sends only the whitelisted commands, and leaves
  the card in the expected lock state for every operation; the test detects
  each of three seeded mutations.
- **FACT (spec) / PLANNED (C-1942):** a plain unlock lasts one power session,
  so writing a locked card on a PC needs `clear` → write → `setlock`.
- **OBSERVED (C-1943):** firmware `.uf2` not built in the sandbox.
- **UNKNOWN:** real-card behaviour, card models, unit acceptance (C-1944).

## Conclusion

New: `docs/hardware/sd-blocker-pico.md` (parts, wiring, SDK choice, build,
