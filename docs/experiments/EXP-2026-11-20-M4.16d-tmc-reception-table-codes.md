## Question

Does the TMC location-table chain — the receiver's service list `TMC/reception.dat` → the `RDSTM001.DAT` table directory → the location records placed on MAPAL (M4.16b, C-5400) — hold together: which (country code, location table number) pairs does the card serve, and how does a pair name its RDSTM table? (`TFTBL001` does not exist on the 2011 cards, C-122, so the chain is tested through `reception.dat` only.)

## Hypothesis

Formed after reading the 208-byte `reception.dat` rows (`ff 0f CC LTN 00 ff ff ff`) next to the 14 RDSTM table codes (`3219 3409 … 4631`, C-5137): a table code is `ord(hex digit of CC) << 8 | LTN` (e.g. `0x3219` = `'2'`, 25 = Czech Republic, CC 2, LTN 25).

**Falsifier (fixed before the `join` run):** a table code whose (CC, LTN) is not listed in `reception.dat`, a listed pair without a table, or a table whose TMC records land (through their own link refs) in a country whose RDS country code differs from the code's CC — at a rate not clearly above a shuffled-country control.

## Method

1. **Sample and hash** as above (`sha256sum`).
2. **Commands** (repo root; `E=/home/user/scratch/factory-eu`):

   ```bash
   python3 tools/tmc_reception.py --selftest
   python3 tools/tmc_reception.py rows $E/TMC/reception.dat
   python3 tools/tmc_reception.py join $E/TMC/reception.dat $E/RDSTM001/RDSTM001.DAT $E/MAPAL001
   ```

   `join`: per set-1 table row, the code's (CC, LTN) is looked up in the `reception.dat` pairs; 300 refs of the table (seed 1) are resolved to level-2 parcels (`rdstm_links.resolve`) and the majority parcel country is mapped to its RDS CC.
3. **Controls.** *Positive:* the M4.16b placement (C-5400) already ties every table to one country with a random-ref control; here the CZ table must come out as CC 2 / LTN 25 and the DE table as CC D / LTN 1. *Negative:* 1,000 shuffles of the 14 map countries over the 14 tables (count of CC matches); and the reverse direction, `reception.dat` pairs without a table.
4. **Scope.** EU 2011 only; the 14 set-1 tables (set 0 carries the same codes, C-5137). Excluded: the US card (`XMD/` instead of `TMC/`, not parsed), `TFTBL001` (2014+ only, no image of those editions in this run), the `reception.dat` rows that are not `ff 0f`/`03` rows (first two rows `01 3e 0f 1e …`, `02 32 0d 00 01 01 …`, trailing `ff 00 00 00 …` padding; not decoded).
5. **Falsifier** as stated under Hypothesis.

## Interpretation

- **VERIFIED (C-2320):** an `RDSTM001.DAT` table code is `ord(CC hex digit) << 8 | LTN`: the high byte is the ASCII hex digit of the RDS country code (`'2'` … `'9'`, `'A'` … `'F'`), the low byte the TMC location table number. All 14 codes decode to the CC of the country their own records land in (14/14; shuffled max 8, mean 1.4 — the shuffle is generous because CC is shared: BE/FI 6, ES/SE E, FR/NO F, which LTN separates).
- **VERIFIED (C-2321):** `TMC/reception.dat` lists exactly the card's 14 (CC, LTN) pairs, one per RDSTM table (13 in `ff 0f CC LTN 00 ff ff ff` rows, GB in the `03 0a 0c 0a` row), none without a table and no table missing. The receiver-side service list and the map-side TMC tables agree, so a TMC message (CC, LTN, location code) selects the RDSTM table by code and then the record by location code (C-5402) — the full chain to MAPAL node coordinates (C-5400).
- **OBSERVED (C-2322):** the first two rows (`01 3e 0f 1e 00 …`, `02 32 0d 00 01 01 …`) and the leading byte `03` of the GB row are not decoded (HYPOTHESIS: row kind / receiver settings; `0x32` = `'2'` could be an ASCII CC as in the table codes).
- **Consequence (C-2323):** a Poland build needs a location table with CC `3` (RDS CC of Poland) and the Polish LTN, a matching RDSTM table code `0x33nn`, and a `reception.dat` row `ff 0f 03 nn` (HYPOTHESIS for the generator, M5.19 scope; not tested on hardware).

## Conclusion

The TMC location-table chain is closed for the EU 2011 card: `reception.dat` (CC, LTN) → RDSTM table code `ord(CC) << 8 | LTN` → location record by code → link refs → MAPAL parcel/node/link with coordinates (M4.16b/M4.16e). `docs/format/rdstm.md` gains the table-code rule and the `reception.dat` row layout; claims C-2320–C-2323. Open: the undecoded `reception.dat` rows, the US `XMD` equivalent, `TFTBL001` of the 2014+ editions.
