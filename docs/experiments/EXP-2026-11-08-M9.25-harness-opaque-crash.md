## Question

Can `harness.py info` report unreadable/opaque records without crashing, while
leaving `harness.py verify` and control-tile behaviour unchanged?

## Hypothesis

The M5.4-noted crash is an unhandled `zlib.decompress` failure in `cmd_info`'s
record census: records where `clarion_tile.is_zlib` is true but decompression
fails. Wrapping the classify step and counting unreadable records should make
`info` exit 0 and report them. Falsifier: if the crash is in container parsing
(`read_tile`) or in a different harness path, or if the fix changes control-tile
verify/info results.

## Interpretation

- **FACT (VERIFIED):** `cmd_info` crashed with `zlib.error` on factory
  `B48R058R` when classifying a record that `is_zlib` accepted but
  `zlib.decompress` rejected.
- **FACT (VERIFIED):** catching decompression/classification failures and
  counting them as `unreadable` makes `info` exit 0 and report the count; 80
  unreadable records are reported for B48R058R section 1 level 1.
- **FACT (VERIFIED):** B30R048R `info` exits 0 and its census lines are
  unchanged (no unreadable records). Control-tile `verify` results and
  `bg_refused.py --selftest` are unchanged.
- **OBSERVED:** `harness.py selftest`'s render step failed in this environment
  (`render_geojson.py` exit 1); roundtrip/verify phases had already passed on
  B58R070R. Not caused by this change and not in scope.
- **HYPOTHESIS:** the 80 unreadable records are the same damaged/opaque
  container records M5.4 observed on this tile family; this change reports them
  but does not classify or repair them.

## Conclusion

`tools/ze0-viewer/harness.py` `cmd_info` now treats decompression/classification
failures as unreadable records and appends `, unreadable N` when present, so
`harness.py info` degrades gracefully instead of crashing (M5.4 follow-up
(c)). B30R048R and the control tiles keep their previous verify/info behaviour.
The vendored `tools_ze0` parser semantics were not changed. Open: if other
harness or viewer subcommands (`decode`/render paths via `ze0_decode.py`) have
the same unhandled failure on a different tile, handle them in a separate
scoped task.
