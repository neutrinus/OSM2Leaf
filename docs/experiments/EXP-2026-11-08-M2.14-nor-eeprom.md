# EXP-2026-11-08-M2.14: Unit NOR "EEPROM" area at `0x0000A000` (zelemar) vs available SD/CE images

- **Status:** done (negative on NOR-anchor-in-images; code-literal context characterised)
- **Date:** 2026-11-08
- **Sample:** EU 2011 `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`, 8057257984 B); US 2011 `LEAF_2011-2012_US.img` (`53342430a1bb58d3ed6eb68c5563f079c710a400134d522e6192489b324c5383`, 8057257984 B); EU 2014 `LEAF_2014_EU_QSD-357-101.img` (`4a8a21f477e9fc511f94406976b8d67037842f9c043f49ab24e1adc82d6da89b`, 7969177600 B); EU 2016 `ENV200_2016_EU_QSD-390-100.img` (`f53d55f159fd4232caa0b100b9b12e3910c8fe3849201871a71ee38ac19007fb`, 7969177600 B). Vendor bytes not committed (offsets/counts/hashes/short structural descriptions only).
- **Tools:** `python3 3.14.3` (repo host), `tools/cerom.py` (HEAD of `task/m2.14-nor-eeprom`), `mmap` + `hashlib.sha256`; CE image starts A `0x200200`, B `0x3e00200`, C `0x5200200` (AGENTS.md).
- **Claims:** C-2000–C-2009
- **Supersedes:** none
- **Superseded by:** none

## Question

Does the zelemar claim that the Clarion main MCU NOR flash (SST 38VF6401, SH-4A)
keeps an "EEPROM area" at `0x0000A000` holding identification/config data and the
16-byte SD password (last 12 bytes ASCII `Clarion95321`) leave any observable
trace in the available SD/CE images? Specifically: where does `Clarion95321`
occur in IMG256/IMG, does its context match a per-unit NOR EEPROM password record
or the known code literal, and do any NOR-style `0xA000` anchor bytes appear in
the available images?

## Hypothesis

`0xA000` is an offset in the *unit's* internal NOR dump, not in the SD card
image or in the card-resident CE ROM segments we have. Therefore `Clarion95321`
should appear only as the firmware `ProductTestData`/`SecurityCheck` literal
already found by EXP-2026-11-06-M2.13 (PRGUpdate.exe/TestMode.exe), not as a
16-byte `[unit-prefix][Clarion95321]` password field in an EEPROM-style block at
or anchored to `0xA000` in these images.

**Falsifier:** a `Clarion95321` occurrence (or a recognisable 16-byte password
structure) in a non-code data region at/near file offset `0xA000` in an SD image
or at an offset that maps to a NOR/EEPROM-like config block in a CE segment;
or any occurrence whose immediately preceding 4 bytes form a plausible per-unit
password prefix in an EEPROM/config record rather than padding/template bytes.

## Method

1. **Sample and hash.** SHA-256 and size recorded above for each image; no vendor bytes committed.
2. **Commands** (runnable from repo root with the images present):

```bash
# 1) Positive control + exhaustive raw search: find every Clarion95321
python3 - <<'PY'
import hashlib, mmap
needle=b'Clarion95321'
for path in ['archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img',
             'archive/sd-images/LEAF_2011-2012_US.img',
             'archive/sd-images/LEAF_2014_EU_QSD-357-101.img',
             'archive/sd-images/ENV200_2016_EU_QSD-390-100.img']:
    h=hashlib.sha256(); hits=[]
    with open(path,'rb') as f:
        off=0; buf=b''
        while True:
            ch=f.read(8*1024*1024)
            if not ch: break
            h.update(ch); data=buf+ch; s=0
            while True:
                i=data.find(needle,s)
                if i<0: break
                hits.append(off-len(buf)+i); s=i+1
            buf=data[-44:]; off+=len(ch)
    print(path, h.hexdigest()[:16], 'hits', len(hits), [hex(x) for x in hits])
PY

# 2) Attribute hits to CE modules/VAs via cerom.py (EU 2011 example)
python3 tools/cerom.py --image-start 0x3e00200 archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img sections PRGUpdate.exe
python3 tools/cerom.py --image-start 0x5200200 archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img sections TestMode.exe
# (o32 data-range ownership used in the analysis script below maps SD offsets
# to module, section, realaddr-based section VA, dataptr VA, flags.)

# 3) NOR/0xA000 hypothesis checks (negative): no hit near 0xA000 in any image
# (confirmed by step 1: all hits >> 0xA000); read SD offset 0xA000 structure
# and confirm no password/config block. Control: step 1 finds Clarion95321.
python3 - <<'PY'
import hashlib
for path in ['archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img']:
    b=open(path,'rb').read(0xB000)
    print('sd@0xa000 first16', b[0xA000:0xA010].hex(), 'allzero', b[0xA000:0xA200]==b'\x00'*0x200)
PY
```

3. **Controls.** *Positive*: the exhaustive search finds `Clarion95321` (3 hits per image) at the PRGUpdate/TestMode locations consistent with EXP-2026-11-06-M2.13, so the method can find the known string in these images. *Negative / falsifier probe*: no hit occurs at or near SD offset `0x0000A000`, and the 16-byte windows at found hits do not form `[4 per-unit bytes][Clarion95321]` EEPROM password records (prefix bytes are padding/template in the observed contexts).
4. **Scope.** Full byte content of four SD images (EU 2011, US 2011, EU 2014, EU 2016; total 32,209,209,344 B scanned). CE attribution checked against images A/B/C starts on EU 2011 and cross-year offset comparison for 2014/2016. Not covered: a physical dump of the unit NOR (SST 38VF6401) — no such dump is available in the repo; the zelemar EEPROM screenshot bytes are not machine-readable from the article text. Compressed CE data sections were not a factor for these hits (found in uncompressed module sec0 code/data ranges or as a raw duplicate of such a range).
5. **Falsifier.** Stated above; not triggered.

Context (structural description only; no vendor byte dump committed): the two
PRGUpdate-range hits share the same 16 B before / 16 B after window structure:
UTF-16LE `led)\r\n` + NUL padding, then `Clarion95321` + NUL, followed by
`0x99999999 0xffffffff` and `0x23 0x00 0x20 0x00` (short header/value words).
This is consistent with the M2.13-observed `SecurityCheck`/`ProductTestData`
message/value context in updater code, not an EEPROM record. The TestMode hit is
preceded by ASCII digits + NUL padding + `xxxx` (template/placeholder bytes) and
followed by UTF-16LE `[ERROR` text; again a code/message context, not a per-unit
NOR password record. In no case are the 4 bytes immediately forming a
`[4 unit bytes][Clarion95321]` 16-byte password field with plausible per-unit
content; the adjacent bytes are padding/placeholder/message structure.

NOR / `0xA000` checks (EU 2011 representative): SD file offset `0x0000A000` lies
in the disk image's early boot/FAT area (far below CE image A at `0x200200`), not
in CE module data and not a NOR dump; the 512-byte region at SD `0xA000` is not
an EEPROM/password structure (it is disk/boot-area data; `Clarion95321` search
over the full image found no hit there or near it — nearest hits are at
`0x042e5698`+, > 70 MiB). No CE/NOR mapping in the available SD images places a
config block at a NOR offset `0xA000`; the card images contain CE ROM segments
and a FAT data partition, not the SST 38VF6401 NOR contents.

Cross-year: EU/US 2011 share identical hit offsets; EU 2014 and EU 2016 shift by
the image-layout delta but keep the same 3-hit pattern (two in B-range/updater
copy, one in C/TestMode), consistent with the same firmware string placement.

## Interpretation

- **FACT (from cited article, treated as external lead):** zelemar states the
  unit NOR (SST 38VF6401, SH-4A) has an EEPROM area at `0x0000A000` with
  identification/config data and a 16-byte SD password whose last 12 bytes are
  ASCII `Clarion95321`.
- **OBSERVED:** every `Clarion95321` occurrence in the four available SD images
  (3 per image, 12 hits total, all inside IMG256/first 256 MiB) is in early
  card-resident CE firmware regions: PRGUpdate.exe sec0 (B, uncompressed) and a
  byte-identical raw duplicate of that sec0 data, plus TestMode.exe sec0 (C,
  uncompressed). Contexts are updater SecurityCheck/ProductTestData and
  TestMode error/template strings, not per-unit EEPROM records.
- **OBSERVED (negative):** no `Clarion95321` and no plausible 16-byte
  `[unit][Clarion95321]` password record appears at/near SD offset `0xA000` or
  in any NOR-anchored location within the available SD/CE images. The positive
  control (step 1) proves the search can find the string.
- **HYPOTHESIS (consistent, not refuted):** zelemar's `0xA000` EEPROM/password
  storage is in the *unit* NOR flash, which is not present in these SD card/CE
  ROM images; therefore its absence here is expected and does not refute the
  article. Confirming the NOR-side claim requires a NOR dump (hardware/M1.4-class
  access), out of scope.
- **UNKNOWN:** the 4 per-unit password bytes and their NOR location/derivation
  in an actual unit dump; whether the duplicate PRGUpdate sec0 bytes at
  `0x04ce5698` (EU 2011) are a CE copy region, ROM duplication, or unused image
  data (not owned by any B o32 section in the scanned TOC).

## Conclusion

M2.14's hypothesis holds on available data: `0x0000A000` is a unit NOR address
(zelemar lead), not an SD/CE image offset, and our exhaustive search finds
`Clarion95321` only as the known updater/test-mode code literal (PRGUpdate.exe
VA `0x12498` / SD `0x042e5698` on EU/US 2011, duplicate raw copy at
`0x04ce5698`, TestMode.exe VA `0x157f8` / SD `0x057729f8`; same 3-hit pattern on
EU 2014/2016 at shifted offsets). No per-unit 16-byte EEPROM password record and
no NOR-style `0xA000` anchor appears in the four SD/CE images (negative result
with positive control). The NOR claim remains a hardware-only HYPOTHESIS pending
a unit NOR dump. `docs/research/claims.md` gains C-2000–C-2009;
`docs/research/sources.md` records the M2.14 NOR/EEPROM use of the zelemar
article.
