# EXP-2026-11-24-M6.26: LeafSDTools Write NAND sections against the unit flash map

Status: done (source reading, no hardware run)
Claims: C-10180–C-10186

## Question

LeafSDTools `Write NAND` offers ten buttons: `ALL+EEPROM`, `ALL OS`,
`BL IPL`, `PROD`, `BL BASE`, `BL EBOOT`, `BL ENH`, `APP`, `START`, `CANCEL`.
Which flash blocks does each one cover? Does that agree with the M6.19 map
(`docs/hardware/unit-flash.md`)? Does anything follow for this project?
(Marek, 2026-11-24.)

## Hypothesis

The buttons follow the flash's own partitions, so their block ranges confirm
or correct the M6.19 boundaries.

## Inputs

- Upstream source `github.com/developerfromjokela/leafsdtools`, commit
  `422c6538583854aa1d2fab046bf4f915670b0f7c` (2026-10-24), GPL-3.0. It was
  read only. No code is copied here, and the file and line references below
  are to that commit.
- `docs/hardware/unit-flash.md` (M6.19 map of Marek's dump, C-5210–C-5219).
- No unit dump was used.

## Method

1. Clone the repository at depth 1, then read `LeafSDTools/ReadNAND.cpp`,
   `WriteNAND.cpp`, `WriteNAND_QY8.cpp`, `Flash.cpp`, `UserSRAM.cpp`,
   `ProdInf.cpp`, `LeafSDTools.cpp` and `StdAfx.h`.
2. For each button, note the block loop bounds, the file offset and the
   block size. Turn them into flash addresses with the M6.19 rule:
   blocks 0–7 are 8 KiB, and block `n ≥ 8` starts at `(n − 7) × 0x10000`.
3. Compare the result with the layout table in `unit-flash.md`.

Control: the same rule must reproduce the known `SRAM` range, blocks
`0x47–0x56` = `0x400000–0x4FFFFF` (`UserSRAM.cpp:226`). It does.

Falsifier: a button range that cuts through an image or store of the M6.19
map would show the map's boundaries to be wrong.

## Observations

O1. **Only two buttons write anything** (`WriteNAND.cpp:166–227`).
`BL IPL`, `PROD`, `BL BASE`, `BL EBOOT`, `BL ENH` and `APP` print
`… NOT IMPLEMENTED YET!` and write nothing. Their intended sizes survive in
comments as page counts for a progress line:

| Button | Pages in the comment | Blocks (M6.19 rule) | Flash range | M6.19 content |
| --- | --- | --- | --- | --- |
| `BL IPL` | 4 | 0–3 (8 KiB) | `0x000000–0x007FFF` | IPL `IP10XENI.017` (`0x40B0` bytes) + zero block 3 |
| `PROD` | 4 | 4–7 (8 KiB) | `0x008000–0x00FFFF` | `PROD` in block 5, the rest erased |
| `BL BASE` | 1 | 8 | `0x010000` | `BS10XENI.017` |
| `BL EBOOT` | 1 | 9 | `0x020000` | `EB10XENI.017` |
| `BL ENH` | 1 | `0x0A` | `0x030000` | `EH10XENI.017` |
| `APP` "X/W1" | 54 | `0x0B–0x40` | `0x040000–0x39FFFF` | NK1 `X110NBNI.147` + bytes after it + erased + `ASLG` crash log + erased |
| `APP` "PS + MEM" | 1 | `0x41` | `0x3A0000` | `PS10XXXX.009` sub-test |

The block ranges are inferred from the page counts and the order of the
buttons. The code holds no block numbers for these buttons.

O2. **`ALL OS`** (`WriteNAND.cpp:228–317`) seeks the backup file to
`0x10000` and writes blocks `8` to `0x86`, 64 KiB each. That is flash
`0x010000–0x7FFFFF`: BASE, EBOOT, ENHANCE, NK1, crash log, PS, `VEUP`,
**`SRAM` and `VFlash`**. It skips only blocks 0–7 (IPL and `PROD`).

O3. **`ALL+EEPROM`** (`WriteNAND.cpp:317–390`) writes blocks `0` to `0x86`,
which is the whole 8 MiB, the boot loader and `PROD` included. The
"EEPROM" in the label is the eight 8 KiB boot blocks.

O4. **Write mechanics** (`Flash.cpp:233–293`, `WriteSingleBlockFromFile`):
for each block, erase `0x8011200C {block, 1}`, then write `0x80112004
{block, size, buffer, result*}`. Success means only that the driver reports
`size` bytes written. Nothing is read back. On the first failed block the
loop stops (`break`). The blocks before it are already rewritten and the
blocks after it are untouched. Read is `0x80112000 {block, 0}`
(`ReadNAND.cpp`). All three IOCTLs go to `FMD1:`.

O5. **Unattended mode** (`LeafSDTools.cpp:180–191`): if `\SystemSD\writenand.txt`
exists, the tool runs `ALL OS` with no touch input. `dumpnand.txt` does the
same for Read NAND. The file name is `nand_<productId>_<serial>.bin`, and a
file of 8192 bytes or less is refused.

O6. **Other writers of the same flash.** `SRAM` → `RESTORE SRAM` writes blocks
`0x47–0x56`. `RESTORE VFLASH` writes `0x57–0x84` (`UserSRAM.cpp:226–288`).
The `PROD INF` menu (IMMO switch) reads block 5, sets `+0x193`, recomputes the
u16 sum at `+0x2D0` and writes block 5 back (`ProdInf.cpp:193–260`). That is
the only implemented single-section write of the boot area. `GetProdSection`
(`Flash.cpp:362–400`) also reads a second 4-byte product ID at `PROD +0x30`.

O7. **QY8 units** (2013+, `QY8XXX` build, `NEW_NAV`) have a different layout
in the same source:
- 128 KiB blocks, `0x200` of them (64 MiB);
- `PROD` in block 2;
- `ALL OS` writes blocks `3–0x1FC`, `ALL+EEPROM` writes `0–0x1FC`;
- VFlash is block `0x1FD`, and SRAM is `0x1FE–0x1FF`;
- the IOCTL codes have the top bit clear (`0x01112000/04/0C`).

So on QY8, unlike QY7, `ALL OS` leaves the user data alone.

## Interpretation

- The M6.19 boundaries hold (falsifier not met): every button range ends on
  an image boundary of the map. The 54-block `APP` region adds one fact:
  the vendor treats `0x040000–0x39FFFF` as the kernel's partition. NK1
  (`0x2CDAE8` bytes) ends at `0x30DAE8`, and the `ASLG` crash log sits inside
  the same partition at `0x360000`. A larger NK1, for example with added
  modules, has about 329 KiB (`0x52518`) before the crash log, and
  `0x92518` (≈ 585 KiB) before the end of the partition if the crash log
  moves or is dropped.
- **`ALL OS` on a QY7 unit restores the user data too (O2).** It writes the
  `SRAM` and `VFlash` held in the `nand_….bin` file. Running it after
  `RESTORE SRAM` puts back whatever area 0 the NAND file holds. The
  EU-card guide's area-0 reset therefore has to come **after** `ALL OS`, or
  be done inside the NAND file as well (`0x400000–0x45FFFF` of that file).
  Whether Marek's car test used that order is not recorded, so C3 (car
  stays in London) is not explained by this.
- `ALL OS` from an old dump also rolls back the phone book, history and
  crash log to the dump's date. This is harmless, but expected.
- Risk (O4): a failed block in `ALL OS` leaves a mixed flash. Boot blocks
  0–7 are untouched, so IPL survives. If the failed block is in BASE or
  ENHANCE (blocks 8–`0x0A`), the update path from the card may be gone. Nothing
  shows that this has happened to anyone.
- For the emulator (M8.H18), the erase/write IOCTL argument layouts in O4 are
  the ones a writer must accept. Today the NOR model only sees reads at boot
  (C-7151).

## Conclusion

The section buttons match the M6.19 flash map and confirm it. Two of them do
anything. `ALL OS` covers everything except IPL and `PROD`, user data
included. That changes the order of steps in `eu-card-on-us-unit.md`.

## Follow-ups

- If the `APP` partition is the real limit, a modified NK1 must stay below
  `0x360000` (or `0x3A0000` without the crash log). Check what ENHANCE
  writes as `NK1` (its size field) before building one.
