## Question

With the `STDDLL` thunk bound by M9.65, which RPF code dereferences the section-2 **unit-0** pointer carried by the kind-8 `0x14b6` reply, and with which reading VAs?

## Hypothesis

The RPF reply path that M4.40 located (`RPF_PreMap_start 0x00336bf0` → reply handler `0x00336dc0`) walks unit 0 once the import fault at `0x003367c2` is gone, so a read-watch on the unit-0 pointer records the ordered word reads and yields the section-2 field table.

**Falsifier:** the read-watch records **0** unit-0 reads while a positive control (watch on the reply-list bytes the handler demonstrably reads) records **>0** reads, on the real sub-3 reply, for every reachable handler mode.

## Method

1. **Sample and hash.** The two files and hashes above. Firmware build A (apps, image start `0x200200`), EU 2011, no vendor bytes written to the repo.

2. **Commands.** Runnable from the repo root with `archive/` present:

   ```bash
   python3 tools/rpf_reply_l3.py --selftest
   python3 tools/rpf_reply_l3.py archive/head256.img \
       --card archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
       --position 51.70,17.45 --json report.json
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x0061a824
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x00336dd0 --count 20
   python3 tools/callgraph.py callees G.json 0x00336bf0
   ```

   The tool fetches one kind-8 request, keeps both `0x14b6` replies, decodes the sub-3 entry (`+16` unit 0), seeds one pending entry in buffer `0x0061a020`, then runs `0x00336dc0` for modes 1/2/3 with a read-watch on unit 0 and on the reply list.

3. **Controls.** *Positive: * the reply-list watch. The handler must read sub/status/kind/pointers from the list at `0xd8b53c`; the same `eng.watch` that reports 0 unit-0 hits must report list reads, otherwise the watch is inert. *Negative:* the sub-5 reply carries `0xffffffff` for all four pointers (no unit 0); a tool that reported unit-0 reads there would be reading unmapped memory. M9.65's parity (`isValid 3/3` vs `poi_position_l3.py`) independently proves the native `STDDLL` binding executes real factory code.

4. **Scope.** EU2011 build A only; the RPF task and its statically reachable `Navi.exe` subtree (14 functions from `RPF_PreMap_start`, `OBJDLL`/`STDDLL` imports resolved as thunks). 4 OBJDLL exports were disassembled at their CE RVAs (`OBJ_PntInfo_readNeighborLink 0x034a6268`, `OBJ_PrePnt_readNeighborLink 0x034a69fc` and neighbours) and are thin struct-copy wrappers, not the pointer walker. Excluded: US2011, full-system (L4) runs, car/bench (L5), the route-search trigger reached only by a user destination.

5. **Falsifier.** Any `unit0` watch hit with a reading PC inside the RPF subtree would have confirmed the hypothesis; the test could fail loudly because the positive control does fail when the watch is pointed at a region the handler reads.

## Interpretation

- **FACT:** M9.65's binding works — the real kind-8 `0x14b6` reply is fetched, its unit-0 pointer is `0x302abbf2`, and the handler runs to a return verdict for all three modes. The reply-list watch (10/20/30 hits) proves the read-watch is live.
- **FACT:** the reply handler `0x00336dc0` is a **32-byte entry store**: it matches the reply entry against a pending buffer entry by mesh id at `+16`, replaces the entry's words, and hands mode 1/2 to `RPF_PreMap_start`. It never loads through the entry's `+16` pointer.
- **FACT:** `0x003367a0` takes `(mode, mp, mp, [G+8], [G+16], [G+12])`, not the reply list; M9.65's C-6745 is confirmed. With the real mode it still performs 0 unit-0 reads.
- **OBSERVED:** `OBJ_PrePnt_readNeighborLink` and `OBJ_PntInfo_readNeighborLink` are called from `Navi.exe` diagnostics (`0x0033618c`, `0x00339d58`, `0x00339ee0`) but the two OBJDLL exports inspected are fixed-size struct-copy wrappers (sizes 121×4 and 48 bytes), not a walk through a caller-supplied pointer.
- **UNKNOWN:** which code dereferences `0x302abbf2`. It is not in the statically reachable `Navi.exe` RPF subtree under the bindings available today. The likely candidates are an OBJDLL function reached with a translated mesh pointer, or a route-search stage triggered by a destination message that was not issued in this run.
- **HYPOTHESIS (new):** the unit-0 pointer is consumed by a second module (OBJDLL) or by a route-request stage; finding it needs the same kind of harness work M9.65 did for STDDLL, plus a real route-set message.

## Conclusion

No section-2 field table with reading VAs was produced, so M4.40 cannot be unblocked from this run and M5.57 stays blocked. The new artifact is `tools/rpf_reply_l3.py` (with `--selftest`) and claims C-6026–C-6029; `docs/format/map-tiles.md` is unchanged. M4.55 is set `blocked` with `Unblock: M9.74` (bind OBJDLL exports in `vcard_l3` and locate the downstream unit-0 walker). This is a negative result with a positive control, not an absence-of-evidence claim: the watch demonstrably reads the reply list while reading 0 bytes from unit 0.
