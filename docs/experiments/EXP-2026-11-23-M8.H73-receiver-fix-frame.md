## Question

Which frame from the receiver on `SCI7:` carries the position fix? What
is its layout? Does a host peer that sends it move `OBJ_CarPos` and the
map?

## Hypothesis

The receiver sends a 7-bit frame that `navdrv` passes to `Navi.exe`
unchanged. `Navi.exe` decodes it into latitude and longitude, and a
correct frame moves the car position. **Falsifier:** the hand-built frame
leaves the position and both screenshots unchanged (the M8.H31 negative).

## Observations

**O1 — NK1 runs the card's `navdrv` code.** 686 bytes differ, in 668
words. 512 of those words differ by exactly `0x310000` (code VAs, vbase
`0x039e0000` → `0x03cf0000`). The other 156 are as follows:

- 154 are data pointers `0x01f3c0xx` → `0x01fac0xx` (a difference of
  `0x70000`);
- 2 are the security cookie (`+0x4` and `+0x6a04`);
- 4 words `0x2248…0x2254` are the build stamp.

No instruction differs.

**O2 — the RX and TX tables disagree.** RX lengths:

| Start bytes | Length |
| --- | --- |
| `a0` | 36 |
| `a3` | 81 (variable: the walker at `0x039e4748` then looks for the `0xf0` end) |
| `a4` | 100 |
| `a5` | 8 |
| `b0` | 6 |
| `b1`, `b3`, `c0`, `c1` | 4 |
| `b2` | 44 |
| `b4` | 10 |

The TX table makes `a0` 14 bytes and does not allow `a3` or `a4`.
`gps.py` (M8.H30) sized its frames with the TX table, so the M8.H31 frames
(14-byte `A0 00`) could never pass the RX assembler.

**O3 — the 36-byte `NAV1:` record is dead reckoning.**

- `navdrv` builds it in `fn 0x39e5290`, inside the raw/gyro thread
  `fn 0x39e55b0` (`EventNameIntteruptSpeed`, `CGyroIO`). It publishes the
  record with IOCTL `0x800f2004`.
- `Navi.exe` `0x003a391c` reads it with IOCTL `0x80102014`. Only when its
  byte `+33` is 1 does `Navi.exe` read a receiver frame with IOCTL
  `0x8010200c` (128 bytes) into the ring at `0x006495c8` and pass it to
  `0x003a30d8`. Otherwise it gives the record to `0x003a345c`.
- `0x003a345c` reads `+28` and `+34` like EU `0x003752e8`. So the "fix
  decoder" of M8.H29 O2 is the dead-reckoning decoder.

**O4 — the receiver frame becomes OSM message `0x03f4`.**

- `0x003a30d8` posts message id `0x03f4`, with the start byte as sub, data
  at frame + 1 and length frame length − 3.
- The table at `0x0001d7a0` lists `{0x4c0, 0x3f4, 0x3f5, 0x4c1, 0xfa0,
  0x451}`. Its `0x3f4` entry points to the sub-table at `0x0001d2b8`:

  | Sub | Handler |
  | --- | --- |
  | `a0` | `0x003a0b40` |
  | `a3` | `0x003a0d0c` |
  | `a4`, `b1`, `b2` | `0x004d4b54` |
  | `a5` | `0x0039eebc` |
  | `b0` | `0x003a0f70` |
  | `b3` | `0x0039efac` |
  | `b4` | `0x0039f190` |
  | `c0` | `0x0039f288` |
  | `c1` | `0x0039f368` |

**O5 — the layout.**

- `0x0039e880` unpacks the 33-byte payload into a 48-byte record. The
  table in `docs/firmware/navdrv.md` lists each field.
- Function `0x003a12e8` prints that record with these format strings:
  - `0x0001e1ec` "sat num = %d stat = %02x";
  - `0x0001e1c8` "lat = %d ,lon = %d ,high = %d [m]";
  - `0x0001e1a4` "sp = %d[0.1Km/h],dir = %d[0.1deg]";
  - `0x0001e174` "HDOP … VDOP … PDOP = %d[0.2]";
  - `0x0001e13c` "long err … short err … slant = %d[180/128]";
  - `0x0001e12c` "WSVacc";
  - `0x0001e118` "delay = %d [0.1s]";
  - `0x0001e208` the time line.

  These strings give the field names and units.
- Latitude and longitude are 28-bit: `shll2`, `shll2`, then `0x431c` with
  `r1 = −4`.
- `0x0039eb1a…eb60` uses `+18…+28` as the date and time. Years below 90
  get `+2000` (`0x07d0`), the rest `+1900` (`0x076c`).

**O6 — `0x4nmC` is SHAD.** `tools/sh4dis.py` printed `0x4nmC` as `shld`
and `0x4nmD` as `shad`; QEMU and the `l3_harness` engine say the opposite.
So the 28-bit and 14-bit fields are sign-extended, not masked. The live run
confirmed it (O8). The fix in `sh4dis.py` also changes the two M1.11c
pins: `0x003f56fe` `0x431d` and `0x003f5746` `0x423d` are `shld`.

**O7 — the `OBJ_GpsInfo` scale.**

- `0x00497aa0` maps the stat mode (`stat & 0x70`) to 1…7. It returns −1
  for `0x40` and logs "GPS status unknown" for any other value.
- Bits `8/4/2/1` set `OBJ_GpsTunerInfo` parameters 1–4.
- Latitude and longitude go through `float`, `fmul` by the double at
  `0x00497c9c` (`0x403eb851eb851eb8` = 30.72) and `ftrc`.
- `+12` is multiplied by 10. Then `OBJ_GpsInfo_write` is called at
  `0x00497c64`.

**O8 — live: the report reaches `OBJ_GpsInfo`.** In run S9:

- `navdrv` (NK1) stored the 36-byte frame, starting
  `a0 2f 01 19 2e 2e 7d 3f 0b 44 …`.
- The `A0` handler received payload `2f 01 19 2e 2e 7d 3f …`.
- After the decode, the record started `2f00 0100 2e572600 c4c5afff`:
  - stat `0x2f`;
  - latitude `0x0026572e` = 2 512 686 = 41.8781 × 60 000;
  - longitude `0xffafc5c4` = −5 257 788 = −87.6298 × 60 000 (sign-extended,
    O6).
- The record went to `0x011080c0` (breakpoints at `0x003a0c74` and
  `0x003a0c8c`, each hit twice). It was sent on as message `0x04c1` sub
  `0x012e` (`0x0039ecfa`, `r0 = 0x12e`).
- In the positioning thread, `0x00497aa0` loaded `r3 = 0x0026572e` (at
  `0x00497b92`) and `r3 = 0xffafc5c4` (at `0x00497bbc`).
- `navdrv` logged `SckGpsCheck changed OK NotifyEvent` once reports began.

**O9 — the car position does not follow.**

- `OBJ_CarPos_write` was called from `0x00497e5c` (function `0x00497db4`,
  object id 3) about three times a second.
- Its data held COORD001 `0x997192c3`, which is (33.92, −118.52) and
  matches the LAX map on screen. It stayed there.
- `0x00497db4` takes mesh/x/y from the positioning state at `0x00dbce00`.
  The positioning cycle `0x0049bdb0` writes that state after
  `OBJ_GpsInfo`, via `0x0049fa44`.
- All 9 screenshots are byte-identical (`22586413…`):
  - before the reports;
  - after 25 s of reports;
  - after 40 s at each of the stat values `3f`, `1f`, `5f`, `6f`, `7f`,
    `0f`;
  - after 150 s of the moving track at 50 km/h.

**O10 — memory reads need the TLB.** At breakpoints in `Navi.exe`, reads of
`0x00cc1ce4`, `0x0064851a` and `0x00df15c0` sometimes returned `E14` even
though the addresses are in `Navi.exe`'s data range. SH-4 refills its TLB
in software, so the gdb stub can only read pages that are in the UTLB at
that moment. Register values at a breakpoint just after a load (O8) avoid
the problem.

## Interpretation

- **FACT (C-8570):** NK1's `navdrv.dll` is the card's ROM B `navdrv.dll`
  relocated by `+0x310000` (O1).
- **FACT (C-8571):** the RX and TX length tables differ. A receiver `A0`
  frame is 36 bytes, and the old peer's 14-byte frames are the cause of the
  M8.H31 negative (O2, O8).
- **FACT (C-8572):** the 36-byte `NAV1:` record and Navi `0x003a345c` (EU
  `0x003752e8`) are dead-reckoning data. Receiver frames take the IOCTL
  `0x8010200c` → message `0x03f4` path (O3, O4). This corrects C-7261 and
  C-7267.
- **FACT (C-8573):** the position report layout and units (O5), named by
  the firmware's own format strings.
- **FACT (C-8574):** `0x4nmC` is SHAD and `0x4nmD` is SHLD. The fix in
  `sh4dis.py` corrects C-2650 and C-2651 (O6).
- **FACT (C-8575):** `OBJ_GpsInfo` multiplies latitude and longitude by
  30.72, from 1/60000° to 1/512″ (O7).
- **FACT (C-8576):** a 36-byte report from `gps.py` reaches `OBJ_GpsInfo`
  on NK1 with the injected position (O8).
- **OBSERVED (C-8577):** `OBJ_CarPos` and the map stay at the previous
  position whatever the stat byte, including with a moving 50 km/h track
  (O9). The cause is not known.
- **HYPOTHESIS (C-8578):** the positioning cycle (`0x0049bdb0` →
  `0x0049fa44`) only takes the GPS position together with
  dead-reckoning input (wheel pulses and gyro, M8.H32), or after a
  plausibility gate that a stationary DR state fails.
- **FACT (C-8579):** gdb memory reads at a breakpoint only reach pages that
  are in the UTLB (O10).

## Conclusion

The GPS link works as far as `OBJ_GpsInfo`. The receiver's report is a
36-byte `A0` frame, and `gps.py` now sends it with the right length,
checksum, signed 28-bit coordinates and the other fields. The unit takes
it through `navdrv` and `Navi.exe` into the GPS object with the exact
position. The map does not move yet. The car position comes from the
positioning cycle, and that cycle has not accepted the GPS position in
any variant tried. M8.H73 stays blocked on that. M8.H78 should find the
acceptance condition in `0x0049fa44`, or supply DR input (M8.H32).
