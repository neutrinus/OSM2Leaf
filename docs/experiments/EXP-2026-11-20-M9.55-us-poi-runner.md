  the US factory `REFER001/POINT010.DAT.{cmp,ind}` pair

## Question

Can the US POI record walk that M1.22 already runs be registered so that
`python3 tools/l3check.py --build-corpus` lists it as **runnable with its
verdict** on the synthetic corpus (no hand-passed `--image/--cmp/--ind`), and
does that row still return `FAIL (unmapped …)` — never `PASS` — on a
wrong-build pairing?

## Hypothesis

Yes, if `runner.py` gains a `point_walk_v1` `firmware_call` program that calls
`point_walk_l3`'s own nth walker, `l3check` corpus mode derives the image from
the target's `build` and the `.cmp/.ind` pair from the corpus, and
`corpus.py` ships a POINT name-page fixture. M9.41 (C-4223–C-4225) showed the
row cannot exist from `targets.json` + `TARGET_EVIDENCE` alone, so those three
files are the work.

**Falsifier** (stated before the result): the registered row is runnable but
returns `PASS`/`ACCEPT` on the wrong-build pairing (`archive/head256.img` with a
`us2011` target), or its verdict disagrees with `point_walk_l3.py walk` on the
same factory page. Either would refute the row's value as S1/S2 evidence.

## Method

1. **Sample and hash.** As above (`sha256sum archive/us256.img archive/head256.img`).
2. **Commands** (from the worktree root; `S` = the US factory pair dir, `O` = a
   scratch dir outside the repo):

   ```bash
   S=/home/marek/projekty/leafre-work/m5.12-us/root-factory/REFER001
   O=/home/marek/projekty/leafre-work/scratch/m9.55
   mkdir -p "$O"
   # 1. the walker, standalone, is the reference the row must agree with
   python3 tools/point_walk_l3.py walk archive/us256.img \
     --cmp "$S/POINT010.DAT.cmp" --ind "$S/POINT010.DAT.ind" \
     --page 0x840ba0 --page-len 42848 --build us2011 --n 0,1,2,3,10,500,998,999,1000
   # 2. the ported runner program on the same real page
   python3 tools/l3_harness/runner.py run point_walk_us2011 \
     --image archive/us256.img --cmp "$S/POINT010.DAT.cmp" \
     --ind "$S/POINT010.DAT.ind" --json
   # 3. the gate row: corpus mode resolves build us2011 -> us256.img, pair from the corpus
   python3 tools/l3check.py --build-corpus
   python3 tools/l3check.py --selftest
   # 4. negative control A: wrong build (EU image, US VAs) through the runner
   python3 tools/l3_harness/runner.py run point_walk_us2011 \
     --image archive/head256.img --cmp "$S/POINT010.DAT.cmp" \
     --ind "$S/POINT010.DAT.ind" --json
   # 5. negative control B: the corpus page with the wrong offset
   python3 tools/l3_harness/runner.py run point_walk_us2011 \
     --image archive/us256.img --cmp "$S/POINT010.DAT.cmp" \
     --ind "$S/POINT010.DAT.ind" --offset 0x0 --length 0x100 --json
   # 6. negative control C: the build check (a copy of the target table whose
   #    point_walk_us2011 entry declares build eu2011 while keeping the US VA)
   python3 tools/l3_harness/corpus.py build "$O/corpus" --json
   python3 -c 'import json,pathlib; d=json.loads(pathlib.Path("tools/l3_harness/targets.json").read_text()); [t.__setitem__("build","eu2011") for t in d["targets"] if t["name"]=="point_walk_us2011"]; pathlib.Path("'"$O"'/forged-targets.json").write_text(json.dumps(d,indent=1))'
   python3 tools/l3check.py --corpus "$O/corpus" --targets "$O/forged-targets.json" \
     --target point_walk_us2011 --engine pysh4
   # 7. selftests of every touched tool
   python3 tools/l3_harness/runner.py --selftest
   python3 tools/selftest.py --only l3check
   python3 tools/build_targets.py check
   ```
3. **Controls.** *Positive*: the factory US `POINT010` page PASSes through both
   `point_walk_l3 walk --build us2011` and the new `runner.py run
   point_walk_us2011`, and the corpus row is `PASS`/`ACCEPT` under
   `--build-corpus`. *Negative*: (A) the wrong-build pairing must be
   `FAIL (unmapped …)`, exit 5, not a crash (M9.42); (B) a page that is not a
   zlib stream at the declared offset must be `INVALID`, never a fabricated
   verdict; (C) a target whose declared `build` disagrees with the walker VA
   must be `FAIL` from the `build_targets.py` owner check. The M9.39 mutant page
   is a **positive** witness (C-4178), not used as a negative control.
4. **Scope.** The US nth walker (`0x0041db44`) only, on one factory page
   (`0x840ba0`, 1,000 records) of one image plus the EU image as the wrong-build
   control; one synthetic corpus page; the `l3check` target table (9 targets).
   Excluded: the name/coordinate consumer (`0x0041ec8c`, M9.10's own
   `poi_record_decode` runner), the skip walker and dispatcher, EU2011 as a
   walk *subject*, any writer change, any new VA (all VAs come from
   `build_targets.py`).
5. **Falsifier.** As stated in Hypothesis.

## Interpretation

- **FACT:** The corpus-only gate row is runnable and reports `ACCEPT`/`PASS`
  with `l3_claim True`; its `counts` grow from `pass=1 runnable=1/8` (M9.41,
  C-4220) to `pass=2 runnable=2/9` (C-5770, C-5771).
- **FACT:** The ported runner agrees with the standalone walker on every named
  record of the real US page, and the row's verdict is the walker's, not a
  re-implementation (C-5772).
- **FACT:** A wrong-build pairing is `FAIL (unmapped …)`, exit 5, `l3_claim`
  true — a verdict, not a crash (C-5773). A wrong page offset is `INVALID`
  (C-5774), and a forged `build` is a `FAIL` from the `build_targets.py` owner
  check (C-5775).
- **FACT:** The corpus fixture is the synthetic POINT name chain zlib-packed
  inside a `.DAT` at `0x840ba0`, and `point_walk_factory` adds exactly two
  manifest entries (108 → 110, C-5776).
- **OBSERVED:** `point_walk_v1` needs no `sec1_table`; only
  `cmp_ind_chunk_v1`/`mapcode_compare_v1` read sec1, so the validator's sec1
  requirement is now program-scoped (C-5777).
- **UNKNOWN:** The name/coordinate consumer (`0x0041ec8c`) is still M9.10's own
  runner; the walker proves framing only (C-4178), so M9.10's name half stays
  open.

## Conclusion

M9.55 closes M9.41's gap: the US POI walk is now a `l3check --build-corpus` row
(`point_walk_us2011`) that resolves its image from `build us2011` and its pair
from the corpus, and reports the walker's verdict — `PASS`/`ACCEPT` on the
factory page, `FAIL (unmapped …)` on the wrong build, `INVALID` on a bad page,
`FAIL` on a forged build. No format claim changes and no VA is retyped (the
walker VA is read from `build_targets.py`). M9.41 is re-opened by rule 15 as
`done`; M9.10 keeps its walk half as S1 evidence and its name half open on its
own `poi_record_decode` runner plus M3.11b's text byte order. `reader-coverage.md`
row 10's "not a `l3check` row" sentence and the L3-target table's "eight
entries" count are corrected in this PR.
