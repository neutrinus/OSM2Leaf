## Question

Can the pin move from QEMU 8.2.7 to 8.2.10 — the last release of the same
branch — without touching a single patch, and does the resulting binary boot
`head256.img` exactly as the 8.2.7 build does?

## Hypothesis

Yes on both counts: `hw/sh4` did not change between the two releases, so the
series is a byte-for-byte no-op, and the boot result is a function of the
patches, not of 8.2.7-specific behaviour.

**Falsifier:** any `diff -r` difference under `hw/sh4`,
`configs/devices/sh4-softmmu` or `include/hw/sh4`; any patch needing an edit;
any change in the stable boot observables (`exceptions`, the access list).

## Method

1. Download 8.2.10, verify the SHA-256 above.
2. Compare the three trees the patches touch, byte for byte (`diff -r`).
3. Apply all five `patches/*.patch` with `build.sh`'s own tool and order
   (`patch -p1 --forward --batch`, `LC_ALL=C` sort).
4. Build with `TMPDIR=/var/tmp bash tools/qemu-ze0/build.sh --force --jobs 8`
   (the bumped pin), and check `-M help`.
5. Boot with `run.sh --machine ze0|none --timeout 10`, three runs per machine,
   and compare the stable observables with C-4311.
6. Negative control: apply the *pre-fix* `ze0` patch from `main@{before
   #217}` and confirm 8.2.10 aborts with the same two messages (so a failure
   cannot be blamed on the version).
7. `build.sh --check-version 11.1.3` on a scratch tree, to record where the
   pin stops.
