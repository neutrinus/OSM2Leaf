# EXP-2026-11-23-M1.49: Where the UI texts live and what a Polish (or added) language would take

- **Status:** done
- **Date:** 2026-11-23
- **Sample:** firmware head `archive/head256.img` (EU2011 build A), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (the `d3e5eac9…` in `ce_strfind` output is the 128 MiB it actually read);
  cards `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`
  (EU2011), `LEAF_2011-2012_US.img` (US2011), `LEAF_2014_EU_QSD-357-101.img`
  (EU2014). The one file this record is about is `substance.skn` from each
  card's TFAT16 tail, SHA-256 `69e101c6…58621` / `dbb95a1f…32d56` /
  `d5a6f54c…3db5e7` (the C-6500 pins, re-extracted by cluster chain here).
  No vendor bytes are committed; offsets, counts and VAs only.
- **Tools:** Python 3 (stdlib); repo tools `tools/skn_info.py`,
  `tools/ce_strfind.py`, `tools/cerom.py`, `tools/lang_code_table.py`,
  `tools/sh4dis.py`, `tools/fdl_font.py`, and the new `tools/aui_strings.py`
  (`--selftest`, auto-discovered by `tools/selftest.py`). No zlib recompression
  is claimed.
- **Claims:** C-8090–C-8099
- **Supersedes:** none
- **Superseded by:** none

## Question

Where does the 2011-2012 head unit keep its user-visible UI text (module,
container, encoding, per-language tables), how is a language selected, is the
language list fixed in code — and, with that, can Polish be shown by replacing
an existing language, by adding one, or not at all?

## Hypothesis

The task's start hint was the OnStar/Clarion `SRT_*` screen-state names as if
they were UI text. Expectation before the probe: the UI text is a resource of
one of the AUI modules (`auirtdll.dll`, `ScreenStateCC.dll`) or a card file;
the language list is a setting, not a compiled-in table. **Falsifier** (from
the task block): the strings are compiled into the code sections of many
modules rather than one resource — that would make a text-only Polish UI
impractical.

## Method

1. **Sample and hash.** Extract each card's `substance.skn` by TFAT cluster
   chain (below); the hashes equal the C-6500 pins, so the parsed bytes are
   the ones the format page documents.
2. **Commands.** Runnable as written from the repo root (scratch dir in the
   home tree, not `/tmp`):

   ```bash
   S=~/projekty/leafre-work/scratch/m1.49
   python3 - <<'PY'
   import sys, hashlib
   sys.path.insert(0, "tools")
   import skn_info
   for card, name in [("archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img", "eu2011"),
                      ("archive/sd-images/LEAF_2011-2012_US.img", "us2011"),
                      ("archive/sd-images/LEAF_2014_EU_QSD-357-101.img", "eu2014")]:
       fat = skn_info.Fat16(card, 0x1c8400400)
       e = [x for x in skn_info.tfat_walk(fat) if x["path"].lower().endswith("substance.skn")][0]
       data = fat.read(e["clus"])[: e["size"]]

       open("/home/marek/projekty/leafre-work/scratch/m1.49/%s.skn" % name, "wb").write(data)

   for img in head256 us256 eu2014-256; do

   python3 tools/aui_strings.py count "$S/us2011.skn" --anchor "English"
   python3 tools/aui_strings.py count "$S/eu2014.skn" --anchor "English (mile)"
   python3 tools/aui_strings.py block "$S/eu2011.skn" --n 0
   for b in 0 1 2 3 4 5 6; do
     python3 tools/aui_strings.py block "$S/eu2011.skn" --n $b | grep -iE 'Destino|Destinazione|Bestemming|Zielort|Destination'
   done
   # which module turns the setting into a language; what the card advertises
   python3 tools/lang_code_table.py firmware archive/head256.img
   python3 tools/lang_code_table.py card archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   python3 tools/lang_code_table.py card archive/sd-images/LEAF_2014_EU_QSD-357-101.img

   python3 tools/cerom.py --image-start 0x200200 archive/head256.img imports auirtdll.dll | grep rasterizer
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img exports RASTERIZER_DLL.dll | grep -iE 'NamFont|JpnFont'

     --codes U+0041,U+0104,U+0105,U+0106,U+0107,U+0118,U+0119,U+0141,U+0142,U+0143,U+0144,U+00D3,U+00F3,U+015A,U+015B,U+0179,U+017A,U+017B,U+017C
   python3 tools/skn_info.py tfat archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   ```

3. **Controls.** *Positive:* the same `aui_strings.py block` prints the known
   `Destino` and the 35 strings of a EU2011 block; `ce_strfind` with a control
   needle (`Deutsch`) works through the module walk; `fdl_font` positive
   control `U+0041` `A` resolves. *Negative:* `ce_strfind "English (mile)"`
   must find 0 hits in ROM A (the falsifier test); `fdl_font` negative letters
   (Ł, Ś, Ż …) must resolve to no glyph; the second `FDL Font` magic at file
   `0x5df538` does not parse as a cmap (`fdl_font` raises), which shows the
   found font is a real one and not a string coincidence.
4. **Scope.** Three card skins in full (string blocks only); EU2011, US2011
   and EU2014 ROM A `Navi.exe`/`Speech.exe`/`commondll.dll` (build B) for the
   language setting and font. Excluded: the UI-layer selector that maps the
   selected language to a skin block (only its existence is inferred, not
   traced); the map-font byte→Unicode path (M4.87's UNKNOWN stands).
5. **Falsifier.** A ROM-A hit for a UI word would refute "the text is one
   card resource"; the 0-hit result over three builds is the measurement that
   the falsifier did not fire.

## Observations

- **O1 — the text is not in ROM A.** `ce_strfind --encoding all
  "English (mile)"` prints `hits 0` on `head256.img`, `us256.img` and
  `eu2014-256.img`. (The task's precheck words `Deutsch`/`Français` also
  return 0 in ROM A; `Deutsch` and `Français` live only in the skin.)
- **O2 — the pool frame.** At EU2011 skin `0xe979c`: `1c 00 00 00` then
  `45 00 6e 00 67 …` (`English (mile)`, 28 B UTF-16LE), then `00 00`, pad to
  4. A block-frame walk reads 35 such frames for block 0. One frame is a
  fragment (`Prima \u0080/\u0081 p/alterar\nmodos.` — the `\u0080`/`\u0081`
  are inline icon references), so a "string" is not always a whole sentence.
- **O3 — block counts.** `aui_strings.py count` prints:

  ```
  eu2011     language_blocks   7  first_block 0x000e979c   (35 frames each)
  us2011     language_blocks   2  first_block 0x00096f54   (41, 30)
  eu2014     language_blocks  16  first_block 0x001cc480   (38, 44×14, 54×2)
  ```

  The selector labels at the head of block 0 are the same in every block:
  EU2011 `English (mile) | English (km) | Français | Deutsch | Español |
  Italiano | Nederlands | Português` (8, 7 text sets — the two English share
  one); US2011 `English | Français | Español` (3, 2 sets); EU2014 the same 8
  plus `Svenska | Suomalainen | Dansk | Norsk | Polski | Čeština | Ελληνικά |
  Magyar | Slovenčina` (17, 16 sets).
- **O4 — block → language.** The `Destino`/… word per EU2011 block:
  `0=Destino(PT) 1=Destino(ES) 2=Destinazione 3=Bestemming 4=Zielort
  5=Destination(FR) 6=Destination(EN)`; block 0 bumps straight into GPS text
  (`…ligado.`) at `0xe9c80`, so PT is the *default* EU text set.
- **O5 — selection is a setting.** `lang_code_table.py firmware` prints
  `navi_get_lang` at `0x003c0228` (call it `get_lang`) with `table 0x00045d90`,
  14 rows, `default 0x3f`, and `speech_switch_a braf 0x000a6e36`,
  `speech_switch_b braf 0x000a6386` (C-3760/C-3761). `commondll.dll` (build B) exports `CApi_GetLangInfo 0x03c03d20`,
  `CApi_SetLangInfo 0x03c03cf0`, `CApi_GetCautionLangInfo 0x03c03d70`,
  `CApi_SetCautionLangInfo 0x03c03d50`; `sh4dis` at `0x03c03d20` shows a
  null-check on `[0x01f7a168]` and one `jsr @r3` (tail call), no table.
- **O6 — card codes are voices, not the block order.** EU2011 `0x18c` =
  `05 04 02 07 0a 06 08 14` with 7 `SPEECH` dirs (C-2494/C-3763); EU2014 =
  17 codes, 16 dirs (C-5282). The skin's text-block language order (O4) is not
  that code order.
- **O7 — the UI font.** `auirtdll.dll` imports rasterizer `#12`/`#2`/`#3`/`#1`/
  `#15` = `DCW_Font_getNamFontAddr`, `DCW_Raster`, `DCW_GetAw`,
  `DCW_Create`, `DCWx_initFontCache`; `DCW_Font_getNamFontAddr` (VA
  `0x0344fb08`) loads `0x03431020` (file `0x850220`), an `FDL Font`. Polish
  letters: Ą ą Ć ć Ę ę Ó ó **YES**; Ł ł Ń ń Ś ś Ź ź Ż ż **NO** (10 absent).
  The `FDL Font` at file `0x5df538` (VA `0x8cec0338`, inside `auirtdll.dll`'s
  `%s` text) fails `parse_cmap`.
- **O8 — one card file.** `skn_info.py tfat` lists 3070 entries, of which
  `substance.skn` (8,724,512 B) is the only real payload (C-6500). The
  language selector, the texts and the images are in that one file.
- **O9 — `SRT_COLD_*` are state names.** `ce_strfind "SRT_COLD_I_AGREE"`
  hits `ScreenStateCC.dll` sec0 at `0x02adac50`/`0x02adac68`, inside a
  NUL-separated state-name blob (`…SRT_COLD_I_AGREE_NAM\0SRT_COLD_I_AGREE\0…`),
  consistent with C-8359's state tables (675 main, 3,887 events) — window/
  screen engineering identifiers, not UI labels.

## Interpretation

- **FACT (C-8090):** the UI text is not in ROM A; it is the card skin.
- **FACT (C-8091, C-8092, C-8093):** the container is UTF-16LE string frames
  grouped per language, each block opening with the same selector list.
- **FACT (C-8095, C-8096, C-8097):** the setting (`OBJ_Setting_readExpLanguage`
  → `sdl_com_hdl_get_lang`/Speech switches) selects the language; the UI font
  is the rasterizer FDL font with the same 8-of-18 Polish coverage as the map.
- **OBSERVED (C-8094, C-8099):** the skin carries all text sets at once and the
  block order is not the `0x18c` order; the UI-layer selector that picks a
  block is not located.
- **HYPOTHESIS (C-8099):** replacing one existing EU2011 block with Polish is a
  same-container data edit and needs no code patch; adding a language means a
  new block plus a new selector label, with the selector's writer not located.
- **UNKNOWN:** where the selected language index is turned into a skin block
  (a UI/AUI control or `ScreenStateCC` reading `CApi_GetLangInfo`); the UI font
  byte→Unicode conversion (shared with M4.87).

## Conclusion

The UI texts are one card file, `substance.skn`, not firmware: a run of UTF-16
LE frames per language, each block headed by the language-selector list (7/2/16
blocks on EU2011/US2011/EU2014). Language is a user setting turned into the map
code / voice folder by `Navi.exe` `get_lang` (`0x003c0228`) and `Speech.exe`
(switches `0x000a6e36`/`0x000a6386`); `commondll.dll` only forwards
`CApi_*LangInfo` to a COM object.
The UI font is the rasterizer FDL font (`0x03431020`) and covers the same 8 of
18 Polish letters as the map font (M4.87). Verdict: **replace** one existing
EU2011 text block with Polish (card data edit, no code patch) is the feasible
path; **adding** a language is a skin edit plus a selector entry whose writer is
not located; only 10 letters need transliteration or a new font. New page:
`docs/firmware/ui-strings.md`.
