## Question

Does the KIWI 7.4 Name Data Frame (`kiwiread.c:1001–1188`: distribution header, management pairs, name attribute header, placement kind `st`, word-count string) describe our section-4 place-name records and the road-name records they label, and can it tell a writer how to place names? If it does not fit, at which byte does the layout stop, and which parts (if any) survive?

## Hypothesis

From M4.63/M4.69/M4.70/M4.72/M4.78, the ZE0 container is different and shares only concepts and one size-word family, so the expected result is: the KIWI 7.4 **frame does not fit** any section-4 record (their `u16@0` is a parcel word, not a KIWI `SWS` header), while the **string rule already adopted in M4.75** (`u16` word count × 2 → raw single bytes → CP1252) does fit section-4 word6/word7 spans. Placement kinds `st=1/4/5/6` should have no population in ZE0; the digit-prefix `d=` slots are the ZE0 analogue. **Falsifier:** any section-4 record whose `SWS(u16@0)` header, management offsets/counts and `st=1/4/5/6` name string all fit *and* whose string bytes decode to a name that does not match `section4.scan_names` on the same span (or a mutated mandatory control still passes).

### 3. Controls

- *Positive (tool):* `kiwi_name_probe.py --selftest` builds one synthetic KIWI frame for each of `st=1/4/5/6` and walks it; all four parse with the right `st` and text. - *Positive (ZE0 side):* `section4.py --selftest` passes, and the same record's span is decoded identically by `kiwi_name_probe names --target LINDOS` and `section4.scan_names` (both print LINDOS and RODOS). `name_strings.py --selftest` passes.

- *Falsifier cross-check:* `name_strings.py` reads **LCTBL001**, not tiles. ## Interpretation

- **FACT (tool, negative):** 0 of 1,872 section-4 records on three tiles / two cards fit the KIWI 7.4 frame; every record stops at the first field, the `SWS(u16@0)` distribution-header size. The ZE0 first word is a parcel code (`0x9b1d` EU, `0x8e2f` US), so `SWS` gives 79,358 / 36,398 bytes against 152 / 88-byte records. The management `(D, N)` pair, attribute header and placement kinds are unreachable.
- **FACT (tool, positive):** the one KIWI element that does fit is the string form already adopted in M4.75: a big-endian `u16` word count × 2 at `word7`, a `word6` word offset, and raw single bytes decoded as CP1252. `section4.scan_names` on the same span returns exactly the names inside the decoded string on all three example records. The unambiguous high byte `0xdc` (`Ü`) and the shared `0xc1/0xc9/0xd3/0xd4/0xd6/0xda` values decode identically under CP1252 and Latin-2 here, so this task adds no new code-page evidence beyond C-7745.
- **OBSERVED (placement kinds):** the ZE0 analogue of a KIWI placement kind is the one-digit `d=` prefix in the name span (`0=`, `1=`, `2=`, `4=`), with counts printed above; it is a name-category prefix, not a 3-bit geometry-placement value. Treating the candidate ZE0 word as KIWI `attr1` gives `st=7` in the section-4 record, and the odd-record candidate histogram is near-uniform over `0..7` on the German tile (714/720/616/622/615/566/629 for `st=1..7`) and tiny on the US tile — consistent with random bits, not with a KIWI placement population. **No KIWI placement kind is confirmed in ZE0.**
- **FACT (scope of falsifier):** `name_strings.py` is an LCTBL reader, not a tile reader; of the four sampled tile names only `ROSENHEIM` occurs in LCTBL, where its eight variants include the bare `Rosenheim`. The record-level falsifier therefore uses `section4.scan_names` on the same span (passes); the LCTBL cross-check is reported honestly as partial and does not add a coverage claim for Greek/Polish tiles.
- **UNKNOWN:** the `0x06..0x0f` binary span (candidate `na`) is still UNKNOWN; no firmware reader VA and no L3/L4 run is claimed (rule 13); a real KIWI volume remains M4.77's positive control.

## Conclusion

M4.71's Done-when is met in the negative-with-adopted-part branch. The per-field byte table above records a test and verdict for each KIWI 7.4 field; the placement-kind counts are printed on three tiles; the string encoding is confirmed against `section4.scan_names` and the CP1252/Latin-2 table; and the mandatory mutations fail. The KIWI 7.4 Name Data Frame is **not** a reader for section 4 or the tile road-name records, so no KIWI attribute/placement field is promoted into `docs/format/map-tiles.md`; the page now carries a short negative note plus the already-documented ZE0 word6/word7 string rule and `d=` prefix grammar. No change to M5.65's writer beyond a cross-reference is needed. Rule 13 is unchanged.
