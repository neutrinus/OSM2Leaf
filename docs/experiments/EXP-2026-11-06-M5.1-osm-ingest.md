## Question

Can one standard-library tool read both `.osm` XML and `.osm.pbf` and emit IMF
v1 (the extractor stage of
[`docs/research/intermediate-format.md`](../research/intermediate-format.md)),
keeping the drivable ways, the whitelisted road tags and the turn restrictions
whose members survive, in a file that `tools/imf_check.py` accepts — with both
encodings of the same input producing the same bytes?

## Hypothesis

The PBF container is a small, public protobuf framing
(`BlobHeader`/`Blob`, `HeaderBlock`, `PrimitiveBlock`), so a wire-level decoder
is enough; the two passes the whole-cell/complete-ways filter needs (ways
first, then the nodes they reference) can run over the file twice, and the
derived fields (`tile`, `tiles`, `oneway`, `maxspeed_kmh`, `maxspeed_cms`)
come from `tools/imf_check.py`'s own helpers so the extractor and the validator
cannot disagree. Failure mode expected: none of substance — the risk is a
decoder detail that the XML path does not share.

## Method

1. Run the tool's self-test as delivered. It failed on the XML↔PBF comparison:
   `same records`, `byte-identical`, `same counts`, `assign-tiles identical`
   and `bbox records` (`(0, 0, 0)` instead of `(4, 1, 0)`). The XML run alone
   was correct (12 nodes / 5 ways / 1 relation), so the defect was in the PBF
   reader, not in the IMF writer.
2. Decode the fixture PBF's own framing and print its string table and the
   first way's key/value indices (command below). The indices are correct; the
   reader's table is not.
3. Fix the reader, then re-run the self-test and add coverage for the framing a
   real Geofabrik extract actually uses.
4. Validate a standalone XML → IMF run with `tools/imf_check.py`, and run the
   registry suite.

```bash
python3 -m py_compile tools/osm_ingest.py
python3 tools/osm_ingest.py --selftest
python3 tools/osm_ingest.py /tmp/opencode/m51/fixture.osm \
    -o /tmp/opencode/m51/fixture.imf.jsonl --source-name fixture.osm
python3 tools/imf_check.py /tmp/opencode/m51/fixture.imf.jsonl
python3 tools/selftest.py --only osm_ingest
```

The fixture files come from the tool itself, so the run is reproducible
without any download:


## Observations

### 1. The failure, before the fix

```text
$ python3 tools/osm_ingest.py --selftest
  same records                     FAIL
  byte-identical                   FAIL
  same counts                      FAIL
  assign-tiles identical           FAIL
  bbox records                     FAIL (0, 0, 0)
```

and the PBF ingest of the same fixture reported
`records nodes=0 ways=0 relations=0` with `dropped not_drivable=6`: every way
looked untagged, so all six were filtered out.

### 2. The string table as stored

The fixture PBF is spec-shaped: its first `s` entry is the empty string.

```text
table[0:4] = ['', 'highway', 'oneway', 'maxspeed']
way keys [1, 2, 3, 4, 5] -> ['highway', 'oneway', 'maxspeed', 'name', 'access']
way vals [6, 7, 8, 9, 10] -> ['residential', 'yes', '30', 'ul. Testowa', 'destination']
```

The reader prepended its own `""` before appending the entries, so the list it
used was `['', '', 'highway', …]` and every index resolved one entry too early.
Observed before the fix, the first way decoded as
`{'': 'highway', 'residential': 'oneway', 'yes': 'maxspeed', …}` — exactly a
one-slot shift of keys and values. XML was unaffected, which is why only the
PBF arm failed.

The PBF specification settles it: index 0 is the empty string **stored in the
file**, because that slot is also the `DenseNodes.keys_vals` delimiter
(`(<keyid> <valid>)* '0'`). Its published hexdump of a real extract begins the
string table with `0a 00` (field 1, length 0). A reader must therefore use the
table as written, not prepend to it.

## Interpretation

- **FACT (C-1030):** one stdlib tool reads `.osm` XML and `.osm.pbf` and writes
  IMF v1; both encodings of the same fixture produce byte-identical output
  (2731 bytes, 12 nodes / 5 ways / 1 restriction), and both pass
  `imf_check.py` with zero errors. The IMF fields are derived with
  `imf_check.tile_for`/`kmh_to_cms`, so extractor and validator agree by
  construction.
- **FACT (C-1031):** a PBF `StringTable` already contains the empty string at
  index 0 (`table[0:4] = ['', 'highway', 'oneway', 'maxspeed']`); a reader that
  prepends another empty string shifts every tag, role and user index by one.
  This was the only cause of all five failing self-test checks: the PBF arm saw
  `{'': 'highway', …}`, found no `highway` tag, and dropped all six ways.
- **FACT (C-1032):** framing matters. The old single-block fixture could not
  have caught a stale string table; the spec-shaped variant (one group per
  kind, per-block string tables, `raw` header blob) produces the same bytes
  only if the reader takes each block's own table.
- **FACT (C-1033):** a turn restriction survives with a `via` node that no kept
  way references, because that node is added to the needed set when the
  relation's `from`/`to` ways are kept; the relation then validates instead of
  tripping E016.
- **FACT (C-1034):** history PBFs (`HistoricalInformation`) and an `OSMData`
  block before any `OSMHeader` are refused with exit 1; the reader therefore
  never emits deleted ways as live data.
- **FACT (C-1035):** output is deterministic: no wall clock, a fixed generator
  string, sorted `tiles`, sorted way ids, relations sorted by id; the same input
  run twice is byte-identical, and `imf_check.py --assign-tiles` is a no-op on
  the emitted field order.
- **OBSERVED:** `--bbox MINLON,MINLAT,MAXLON,MAXLAT` keeps a way when at least
  one vertex is inside the box and then writes all its vertices
  (`complete_ways`); on the fixture that yields 4 nodes / 1 way / 0 relations
  and drops both restrictions because their member ways are outside.
- **HYPOTHESIS:** the same reader will hold on a Geofabrik extract, because the
  framing it exercises (multi-block, per-block tables, zlib and raw blobs,
  DenseNodes) is the framing Geofabrik writes. Not proven here: no `.pbf` was
  available and OSM hosts are blocked (C-1716). That is M5.1b.
- **UNKNOWN:** throughput on a ~200 MB region. The tool makes two full passes
  and holds every drivable way plus the needed-node set in memory; the region
  run must measure wall time and peak RSS (see open question 2 of
  `intermediate-format.md`).
- **KNOWN GAP (by design, not a defect):** node *tags* are not carried, so
  `addr`, `poi` and `place` nodes are absent (`intermediate-format.md` allows
  them; addresses/POIs are a later extractor task). Only `restriction`
  relations are emitted; `boundary`/`route` stay outside this slice. PBF blob
  compression other than `raw`/`zlib` (lzma, bzip2, lz4, zstd) is refused with
  a named error rather than guessed at.

## Conclusion

`tools/osm_ingest.py` is complete for the M5.1 scope: XML and PBF in, IMF v1
out, validated by `tools/imf_check.py`, deterministic, with drivable ways,
whitelisted road tags, derived `oneway`/`maxspeed` fields and resolvable turn
restrictions. The one implementation defect was the PBF string-table index
origin; the fix also hardened the reader (per-block tables, blob size bounds,
history refusal, `raw` blobs) and made the XML parser namespace-safe and
memory-bounded.

`docs/research/intermediate-format.md` needs no change: the emitted file obeys
the documented encoding, field order and error rules. `claims.md` rows for
C-1030–C-1035 are stated here because this task may not edit the ledger.
