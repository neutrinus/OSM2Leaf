## Question

Which firmware instructions read an `ADDRE` address record, when the record is read with the
context the firmware itself builds, and which of the grammar fields of M4.9 (C-970–C-979) does
each one consume?

## Hypothesis

The POINT field accessor of M3.11c (`fn 0x003f61bc` / `fn 0x003f5d98`, resolver `fn 0x003f51e0`,
locator `fn 0x003f56bc`, EU2011) is not POINT-specific: it takes the field dictionary from the
companion slot of `db`, and `fn 0x003f56bc` already accepts header class 6 (`0xc000`, C-2184).
The `ADDRE` "schema block" (C-970, `ff ff 00 10 …`, names `STREET`, `area code`, `street name`,
`dndc-id`) has the shape of that dictionary. So, if the populate writer that serves `ADDRE`
(message type `0x14e4`, search type 2 at ctx +124, M3.28) stores the page and the dictionary in
a slot pair, the accessor should return the three fields of every `ADDRE` record, and the
`TT LL 00 ff` "name section" (C-974) should be the per-field length block that
`fn 0x003f5e10` reads.

**Falsifier** (stated before the runs): the schema block fails the accessor's dictionary checks
or is not unique; the writer stores no slot for this type; the accessor returns -1/0 or faults
on a record; the street field differs from the name that `addre.parse_record` (which knows
nothing of fields) finds on any `c0` record; any `c8` record gets a non-empty field; the
dispatcher's record `n` differs from the framing on any record; a negative control returns a
pointer.

## Interpretation

- **FACT:** the `ADDRE` record reader is the generic `REFER001` field accessor. With the
  slots the `0x14e4` writer stores for search type 2 (`+0x14` page → `+0x18` dictionary), the
  firmware returns, for every one of 3,650 EU2011 and 57,180 US2011 factory records, three
  fields named by the file's own dictionary: field 0 `area code`, field 1 `street name`,
  field 2 `dndc-id` (empty in every record seen). Street names equal `addre.parse_record`'s
  name on every `c0` record; `c8` records carry three empty fields. All negatives return no
  pointer.
- **FACT (revises C-974):** `TT LL 00 ff` is the **field-length block**: one byte per field in
  words (`TT` = `area code`, `LL` = `street name`, `00` = `dndc-id`, `ff` = pad), placed by
  `rec[2]`/`rec[3]` (`0x003f5774`). The "4–8-byte unparsed header" is the `area code` field.
  `TT` takes 3/4/5 because area codes are 3–5 words; the dictionary's entry word `+4` is the
  shard's largest field length (33/33 shards). `c8` records end with an all-zero length block
  (`00 00 00 ff`).
- **FACT (revises C-973 `c1`):** a record is `2 * (w & 0x3ff)` bytes. `c1` is a `c0` whose
  length has bit 8 set (`L ≥ 256`); the walker `0x003f5b88` steps over it, and the census frames
  every block of all 33 shards to its end with that rule. A street long enough to push `L` past
  255 turns record 0 into `c1` and the firmware still frames and reads the block.
- **FACT (revises C-975):** the house-range block is a list of length-prefixed items: the first
  byte of an item (`06`/`07`/`08`, the "prefix axis" of C-975) is its length in words
  (`0x003f559c`/`fn 0x003f5624`), so `07 54 00 00 :19:;:15: 00` is a 14-byte item with a NUL
  pad. Item positions equal `addre.parse_record`'s range positions on every record run.
- **FACT:** `rec[2]` is the word count of block 1 (coordinate id + point tokens, from `rec+4`)
  and `rec[3]` the word count of the item block (`0x003f5550`, `0x003f54f4`, `0x003f559c`).
  addre.py reads `rec[2..3]` as an `extra_ids` token; it is not a token.
- **FACT:** the schema block is read only through the dictionary checks (`C+2`, `D+24`,
  `D+26`, entry chain and ids) and by `fn 0x003f57a8` (field count).
- **OBSERVED:** `fn 0x0040b358` is a path-name lookup (`0x00409cc8` tests `/` and `\`); it reads
  no record byte. It is not an `ADDRE` reader.
- **OBSERVED:** the dispatcher reaches the record walker through slot `+0x2c`, which the same
  writer stores; the walker's sequential mode applies when the page object's `+4` is 0 (our
  declared input). The indexed mode (`u32` table at `(*(G+4))+20`) was not run.
- **UNKNOWN:** who reads the bytes inside field 0, block 1 (coordinate id, point tokens
  `TT 40 XX YY`) and a range item (`subtype 00 00 :N:;:M:`): the named callers
  `fn 0x003ad680`/`fn 0x003ad9a4`/`fn 0x003b9d38`/`fn 0x003bacc4` (→ `fn 0x003ad440`) were not
  run (M3.32). The index chain, the directory at `0x1108`, the 6-byte cells and the trailer are
  not inputs of the record reader; their readers are not located here.

## Conclusion

M3.13 is done: the `ADDRE` reader is located and runs in L3 on factory data in both builds
(EU2011 3,650 records, US2011 57,180, all `ok`) with the slot binding the firmware's own
`0x14e4` writer makes, and on two edited blocks (a different-length street, and one that turns
the record into `c1`). `docs/format/refer.md` gets the field model (dictionary, field-length
block, word counts, items, 10-bit length) and the field → instruction table above;
`docs/format/firmware.md` the reader chain; `reader-coverage.md` row 11 moves to located with
an L3 run; C-5930–C-5939. Open: the consumers of the field bytes, block 1 and the range items
(M3.32), and the container readers (search path, M3.30).
