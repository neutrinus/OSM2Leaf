## Question

For the real Dolnośląskie extract, how many ways, vertices, names and POIs
fall into each `BxxRyyR` tile, and how much generated road-record data would
each parcel hold at the profile's default simplification tolerances — where
does the fixed 372 B per-parcel slot budget overflow, and which three parcels
are worst?

## Hypothesis

The region fits in one cell (`B48R058R`, C-2344), so a single tile row is
expected and `mesh_split` should report zero cross-border ways. Real ways
carry curvature the synthetic M5.75 town lacks, so at the same 3 m / 12 m
tolerances more parcels will overflow than the synthetic town's zero.
**Falsifier:** no parcel overflows at level 1 (then the budget is not the
constraint at the default tolerance and this EXP must say so), or the tool's
counts disagree with an independent recount of the ingest output, or the
extract SHA-256 differs from the recorded value.

## Plan

1. **Provenance.** Re-verify the extract's SHA-256 against the value recorded
   in EXP-2026-11-08-M5.1b; use the same file, do not re-download.
2. **One command.** `tools/slot_budget.py numbers EXTRACT --profile … --json …`
   ingests the PBF in-process with `tools/osm_ingest.py`, streams the IMF once
   for per-cell feature counts, cuts cross-cell ways with
   `tools/mesh_split.py`'s own crossing function, then builds every populated
   parcel's real `0x00fa` record with `tools/tilewriter.py` at the profile's
   default tolerances and counts records over the 372 B budget. The command
   prints the tile table, the over-budget totals and the three worst parcels.
3. **Definitions.** `ways` = way records whose first vertex is in the cell;
   `vertices` = node records in the cell; `names` = named way records plus
   named node records; `pois` = node records with a `poi` object.
   `bytes_est` = sum of `info["compressed_bytes"]` over populated parcels at
   levels 1 and 2 with `write_names=False`, the M5.75 geometry budget model.
   `parcels_over_budget` = populated parcels whose record exceeds
   `max_record_bytes`; a parcel is one `(level, y, x, row, col)` tuple.
4. **Controls.** *Positive*: `tools/slot_budget.py --selftest` (31 checks
   including the new `numbers` controls) and the synthetic town run, which
   reproduces M5.75's 20 parcels / 0 over budget at the same defaults.
   *Negative*: a cross-border fixture splits into two cells and shares its
   crossing point (selftest); an over-budget synthetic parcel is caught by
   the same `build_road_record` byte path (`geom: dense parcel trips the
   budget guard`). *Falsifier*: stated above.
5. **Scope.** The whole Geofabrik Dolnośląskie PBF: all drivable ways and
   their referenced nodes, plus POI/address/place nodes; 1 extracted cell;
   2 road levels (1 and 2, the only ones `tilewriter.PARCEL_DEG` maps to road
   parcels); 1 tolerance pair (profile defaults 3 m / 12 m); 1 budget
   (372 B, M5.75 Q1 of 252 factory road blocks). Excluded: non-drivable
   highways, ways whose `highway` is not in the writer's class table (counted
   and reported), name-page bytes, firmware acceptance (rule 13), and any
   L3/L4/L5 run.
6. **Record.** Every number below is quoted from a command in Method §2;
   observations and interpretation are kept apart.

## Interpretation

- **FACT:** The one command produces the requested per-tile table with all
  seven columns and names the three worst parcels (C-7961, C-7963, C-7965).
  Every number above is a printed value, not typed by hand.
- **FACT:** The extract is one cell (`B48R058R`) with `cross_border_ways=0`, so
  `mesh_split` inserts no node and the per-tile table has exactly one row
  (C-7962). This confirms the C-2344 scope on real bytes.
- **FACT:** At the profile's M5.75 defaults the real region does **not** fit the
  372 B per-parcel design target: 4,501 of 4,832 populated parcels overflow,
  4,192 of them at level 1. The M5.77 falsifier is refuted on real data — the
  budget is the constraint, not a non-issue (C-7964, C-7966).
- **FACT:** The two largest level-2 parcels cannot be encoded at all: more
  than `0xffff` record words overflows `fa_encode`'s u16 header word, so no
  compressed byte count exists; they are still counted as over budget with
  exact vertex and way counts (C-7968).
- **OBSERVED:** `ways_unmapped_dropped=9` are `highway=road` ways: the writer's
  class table has no entry, so the tool counts them in the tile's `ways` but
  omits them from the byte estimate rather than guessing a class (C-7967).
  The 92,000 POIs and 41,922 named nodes come from the M5.1c POI path, which
  the 2026-11-08 ingest predates; they are not in the M5.1b counts.
- **HYPOTHESIS:** Raising the tolerance or dropping whole ways in dense
  parcels would bring the count down; not measured here (follow-up task).
- **UNKNOWN:** Absolute byte counts under stock zlib 1.3.1 (this host is
  zlib-ng), and firmware acceptance. No L3/L4/L5 run was made, so rule 13
  acceptance is not claimed (C-7969).

## Corrections after navigator review

Solo task — this is my self-review (no navigator):

1. A first draft of `_split_points_by_cell` passed `(lon, lat)` into
   `mesh_split`, which works in `(lat, lon)`; the synthetic crossing test
   returned one cell instead of two. Corrected by converting at the boundary
   and pinning the shared crossing point in the selftest.
2. `ways_to_runs` returns only the runs dict (the docstring's "misses" is
   stale); the first draft unpacked two values and failed. Corrected.
3. The first real run crashed on `struct.error` from a level-2 parcel with
   more than `0xffff` record words. Corrected by recording such parcels as
   unbuildable over-budget rows (vertex/way counts exact, no invented byte
   count) instead of treating them as tool failures; the run now exits 0.
4. The first claim rows used `...` and `P/`-style shorthand in evidence and
   were flagged `NONRUN`; corrected to full invocations with
   `tools/board.py claim-row`, and `claims_check --strict --count-check` is
   clean for C-7960–C-7969.
