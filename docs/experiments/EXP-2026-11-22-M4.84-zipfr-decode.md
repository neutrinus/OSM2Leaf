## Question

Is the `ZIPFR001` field decode reproducible from a committed tool — what is the
record layout, how much of the file does it explain, and does the "119 masks"
of C-137 actually name a mask field?

## Hypothesis

C-137 records `char key[10] + u32 mask` with 36,881 records and 119 distinct
masks. A fixed 14-byte record starting at `0x1008` with a 6-byte key should
walk; the 119 quantity should be reproducible from one byte window. If the
record is not 14 B or the window is not the trailing u32, the census will say
so instead of matching 36,881.

**Falsifier:** the 14-byte walk leaves bytes unexplained or the 119 count
cannot be reproduced from a fixed field across the file (the claimed layout is
then wrong or partial).

3. **Controls.** *Positive*: `--selftest` builds a synthetic 8-record file with
   a known body header and walks it (8 records, 0 unexplained, stride 14 score
   1.0, stride 16 < 1.0), and on the real file each field's distinct count is
   printed next to the C-137 number. *Negative*: `--selftest` mutates one key
   byte and the census reports it as a non-record slot; it mutates a mask byte
   and the distinct-mask count changes while the layout still walks.
4. **Scope.** All 36,881 EU2011 records, all EU2014/2016 records, the shared
   `0x200..0xfff` template and the zero tail. Firmware code is out of scope
   (no 14-byte consumer is located, M3.18 r3); only the offline byte walk is
   claimed.
5. **Falsifier.** Above, stated before the run.

## Interpretation

- **FACT:** The file is a 14-byte record array from `0x1008`; the walk explains
  100 % of bytes on EU2011, EU2014 and EU2016, and the special marker at record
  `projection_end` is the only non-record slot (C-7841).
- **FACT:** The body header at `0x1000` is `u16 3, u16 projection_end, u16
  swap16(projection_end), u16 7` on all three EU cards (C-7842).
- **FACT:** The "119 masks" of C-137 is the `key[4:6]` **sector** count
  (119 distinct across all records, 118 in the plain tail, values spanning
  `0x0000`…`0x3939`), not the trailing `u16` (C-7843).
- **FACT:** `ZIPFR001` is absent from the US2011 card (not listed, not
  present, no string) (C-7844).
- **OBSERVED:** The 23 `flag=0x80` letter records expand `A`–`Z` and are not
  strictly alphabetical (`AB` plain, `AD`/`AL` flagged); the marker record's
  group/mask words are a 4-byte counter (C-7845).
- **OBSERVED:** The trailing `u16` at `+0xc` is a small bit flag (118 distinct
  on EU2011, 191/205 on EU2014/2016), mostly `0`/`8`/`128`; the `u16` at `+0xa`
  is a group index 0…130 (C-7846).
- **HYPOTHESIS:** Key bytes look like (truncated) postal codes and the flag is
  a postal/freeway mask, but no consumer semantics are proven (C-7848).
- **UNKNOWN:** The mapping key→region and the firmware 14-byte consumer remain
  open (C-7847, C-7849).

## Conclusion

`tools/zipfr_decode.py` reproduces the `ZIPFR001` record decode from a
committed tool: 36,881 records on EU2011 (44,068 EU2014, 46,280 EU2016), 14 B
each from `0x1008`, every byte explained, the 119 count tied to a named
`key[4:6]` sector field. The matrix row 15 Offline cell is `tool`; `refer.md`
§ZIPFR carries the field table. The US2011 card has no `ZIPFR001`, so
cross-card is EU2011/2014/2016 only. The remaining gap is semantic and
firmware-side (M3.18 follow-up).
