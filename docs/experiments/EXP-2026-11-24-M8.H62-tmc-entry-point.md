# EXP-2026-11-24-M8.H62: `fmmdrv` is flash, not traffic; the EU2011 traffic injection point is the TMC event pump `fn 0x0038aa4c` → search wrapper `fn 0x003bcc7c`

- **Status:** done
- **Date:** 2026-11-24
- **Sample:** `archive/head256.img` (134,217,728 B read), SHA-256 `d3e5eac9cb5b4cbd…` (full printed by `ce_strfind.py`); full EU 2011 card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307` (reference image, not committed)

## Question

In EU2011, which function receives a decoded TMC traffic message and issues the `0x14e4` request that reads `RDSTM001/DAT`/`LCTBL001.DAT`, and what are its actual arguments (function VA, START, argument layout) so an event can be injected without a radio model?

## Hypothesis

The traffic side is the `TMC_ANDM`/`TMC_Ccm` group of `Navi.exe`, fed by the `TMC` device of `anwdrv.dll`; its event pump calls the known SDL search sender `fn 0x003bcac0` through a thin wrapper. `fmmdrv.dll` at `0xffc55000` is a flash driver (different subsystem). **Falsifier:** the traffic module takes location data only from the US `XMD` path in this build, or `fn 0x003bcac0` has no static caller in `Navi.exe`.

### 3. Controls

*Positive:* `tmc_req_l3.py run … --request 0x14e4:1:2,25,1203` must read
`RDSTM001/LCTBL001.DAT` and answer `0x14fb`; `lctbl_lookup_l3.py` must return
the model's record for an indexed code (status 1). *Negative (mutations):*
`--request 0x14f4:1:2,25,1203` with the same keys must read
`REFER001/POINT001.DAT` and **no** LCTBL (refutes the old "0x14f4 reads
RDSTM" lead); location code `60000` absent from the model must answer status 4
with no record-page inflate. Static negative: `fmmdrv.dll` has no TMC export
and no `TMC1:` string; `TMC_ANDM` lives only in `Navi.exe`.

### 4. Scope

Static EU2011: `fmmdrv.dll` (build B, 1 code section `0x49f2` B), `anwdrv.dll`
(build B, 1 code section `0x262db` B), `Navi.exe` build A (code sec0 `0x54bd16` B;
compressed sec1/sec2 not searched). `sh4xref` covers literal pools of
uncompressed executable sections only (no compressed code exists, C-2128).
L3 runs mount EU2011 with the factory card. Not covered: iNai/RDS group
decoding, the in-vehicle tuner state, US2011, L4/L5. Corpus counted: 149 build-A
modules, 41 `TMC_ANDM` strings, 10 cited STARTs, 3 L3 runs.

### 5. Falsifier

As stated under Hypothesis: a US-`XMD`-only path in EU2011, or no static caller
of `fn 0x003bcac0`. Both would have made the injection-point claim fail; the
first is refuted by the `TMC1:`/`TMC_ANDM`/LCTBL evidence, the second by
`sh4xref.py --to 0x003bcac0`.

## Interpretation

- **FACT (C-7590):** `fmmdrv.dll` in EU2011 build B is a flash-media driver
  behind `0xffc55000`, with `FMM_*` exports and no TMC surface; the task
  brief's `fmmdrv at 0xffc55000` is not the traffic entry (C-7591).
- **FACT (C-7592):** the EU2011 traffic application is `Navi.exe`'s
  `TMC_ANDM`/`TMC_Ccm` group (41 strings), fed by `anwdrv.dll`'s `TMC`/`TNR`
  devices on `SCI1:`. The US `XMD` path (C-070) is a different build, so the
  task falsifier does not hold in EU2011 (C-7598).
- **VERIFIED (C-7593):** the TMC search wrapper `fn 0x003bcc7c` is the only
  static caller of `fn 0x003bcac0`, which builds the `0x14e4` request with
  country/DB/location from context `+16/+20/+24`. STARTs confirmed by pdata.
- **VERIFIED (C-7594):** the chain from the iNai event to the injection point
  is `fn 0x003885a8` (event creation) → `fn 0x003886f0` (event receive) →
  `fn 0x003887c4` (`TMC1:` handle) → `fn 0x00388850` (decode 34 bytes into the
  ring base `0x012243c0`) → `fn 0x0038aa4c` (event pump) → `fn 0x0038a94c`
  (dispatcher) → `fn 0x003bcc7c`. The last two code rows are static xrefs via
  the code table at `0x00039dc0…`; the wire-code→row mapping is not executed.
- **VERIFIED (C-7595):** the injection function's argument is a **context
  pointer** in `r4` with guard at `+0`, count at `+2`, decoded body pointer at
  `+4`, kind at `+8`, and the three TMC keys at `+16/+20/+24`; the decoded body
  is a separate ≤64-byte message with country/table/SID/AID/header groups at
  bytes `0…33`. This is **not** the 64-byte data-layer request (`id@+8`,
  `sub@+10`, `u32 keys @+16/+20/+24`) built at `0x003bcb48…0x003bcb62` — both
  layouts are stated in `docs/firmware/tmc-path.md` §4 (C-7596).
- **VERIFIED (C-7597):** the positive control `0x14e4` request reads
  `RDSTM001/LCTBL001.DAT` and is answered `0x14fb`; the injected traffic path
  reaches it through `fn 0x003bcc7c`. The mutated `0x14f4` control reads
  POINT001 only, so the two request types are distinct (C-7599).
- **UNKNOWN (C-7598):** which iNai/RDS message code selects table row
  `0x23`→`fn 0x003bcc7c`, and the tuner state required to produce it. L4 (full
  system) or a real tuner frame is needed; no L4/L5 claim (rule 13).
