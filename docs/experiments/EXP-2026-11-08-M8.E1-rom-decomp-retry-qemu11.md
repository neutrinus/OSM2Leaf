## Question

With `qemu-system-sh4` (LE) now present on the host, can M8.E1 decode the two
EXP-49 sections to the M1.2a lengths by running the nk.exe decompressor under
`-M none` + gdbstub with RAM-only state, then extend to `Navi.exe` sec1/sec2,
all 245 compressed sections and FILESentry payloads?

## Hypothesis

`cedecomp_run.py probe` (trivial control) should pass under
`/usr/bin/qemu-system-sh4 -M none -cpu sh7785` (LE), confirming the
loader/gdbstub framework (C-1601). With that working, calling
`DECOMP_SECT 0x88037464(src,psize,dest,vsize)` (C-2292/C-2293) or a
stub-bypassed `DECOMP_WRAP 0x88037590` should decode EXP-49 sec1
(`psize 0x2c6`, form-1 `ulen 0x484`, `vsize 0x5b8`) and sec2
(`psize 0x68c`, `ulen/vsize 0xcc0`) (C-665 vectors). **Falsifier:** the probe
fails, or the runtime returns lengths/bytes different from M1.2a / faults in a
way attributable to the decompressor (not harness), or no decode is achieved.

## Interpretation

- **FACT:** The original M8.E1 host blocker (no `qemu-system-sh4` LE) is
  resolved: `/usr/bin/qemu-system-sh4` 11.1.3 (LE, Fedora 45) is present and
  supports `-M none`.
- **FACT:** IMG256 was obtained read-only from the official EU 2011 source and
  its SHA-256 matches the pinned M8.E1b/M1.2a sample
  (`92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`).
- **FACT:** `cedecomp_run.py --selftest`/`info` and `qemu-ze0/build.sh --selftest`
  pass in this environment.
- **FACT (negative):** `cedecomp_run.py probe` fails under QEMU 11.1.3
  `-M none` (`r0=0x0`, `pc=0x8c010000`, expected `r0=0x2a`; 4 nk sections
  mapped). The isolated diagnostic shows bytes loaded correctly at physical
  addresses but virtual P1 access `0x8C300000` returns gdbstub `E14` and
  execution from `PC=0x8C300000` (`SR.MD=1`) steps to `0x8C010000` with
  `T05thread:p01.01` (`sh7785` and `sh7750r`). nk.exe is linked at fixed
  `0x88xxxxxx` VAs (absolute references), so it cannot be executed at
  remapped addresses without relocation.
- **OBSERVED:** `cedecomp_run.py exp49` for verified entry `0x88037464`
  remains `NOT_IMPLEMENTED` (tool does not yet execute DECOMP_SECT/WRAP even
  with qemu available; it reports kernel-context stub/blocker).
- **FACT (negative):** Building a `-M ze0` QEMU (which provides the required
  P1/P2 aliases for phys `0x08000000`, matching nk.exe VAs) is blocked on this
  host by missing `glib2-devel` (no root). `-M r2d` maps RAM at a base
  incompatible with nk.exe's `0x88000000`-linked sections.
- **FACT (negative):** M8.E1 Done when not met — 0/2 EXP-49 sections decoded
  to M1.2a lengths; Navi.exe sec1/sec2, all 245 compressed sections, and
  FILESentry payloads not decoded. No runtime fault attributable to the
  decompressor was observed (execution did not reach decompressor code).
- **HYPOTHESIS:** A `qemu-system-sh4` binary exposing `-M ze0` (or another
  SH4 machine mapping P1 alias `0x88000000` → phys `0x08000000`) plus
  `cedecomp_run.py` support for calling `DECOMP_SECT 0x88037464` with a
  constructed frame / stubbed `DECOMP_WRAP 0x88037590` kernel-context helpers
  (C-2293) would allow the EXP-49 decode gate. QEMU 8.2.x or a ze0-patched
  build is the likely runtime target; QEMU 11.1.3 `-M none` is incompatible
  with the current harness's P1 VA execution model for nk.exe.
- **UNKNOWN:** Whether QEMU 11.1.3 can be made to execute SH4 code at P1 VAs
  under `-M none` via MMU/TLB/gdbstub setup without board memory aliases;
  decoded bytes for EXP-49 under a compatible runtime; Navi.exe sec1/sec2 and
  full-corpus decode results.

## Conclusion

This retry resolves the original M8.E1 host blocker: `qemu-system-sh4` 11.1.3
(LE) is present, IMG256 (`92aa525d…`) is available read-only, and
`cedecomp_run.py`/`qemu-ze0` selftests pass. However, the runtime decode still
does not run: `cedecomp_run.py probe` fails under QEMU 11.1.3 `-M none` because
P1 virtual address `0x8C/0x88xxxxx` access/fetch faults (`E14`/`T05` to
`0x8c010000`), while nk.exe is linked at fixed 0x88xxxxxx VAs. `exp49` remains
unimplemented for the verified DECOMP entry points. Building the repo's `-M ze0`
machine (correct `0x08000000` RAM + P1/P2 aliases matching nk.exe) is blocked by
missing `glib2-devel` on this host. M8.E1 Done when is unmet (0 decoded
sections). C-1604/C-1606 are recontextualized; C-1607 records the retry
probe/incompatibility evidence. `docs/format/` unchanged.
