## Question

Can a default PR job publish an honest per-target L3 table (PASS/FAIL/SKIP/
BLOCKED with counts) from the synthetic corpus, with BLOCKED never counted as
a pass or failure, no runnable target reported as `NO RUNNABLE TARGETS` in
green, and no rule-13 overclaim?

## Hypothesis

`l3check --build-corpus --json` already emits a machine-readable verdict per
target and a result/exit pair that can be published verbatim in a GitHub job
summary. A job that propagates the tool exit unchanged is green only when a
runnable target PASSes, goes RED on a real FAIL and on `NO_RUNNABLE`, and
therefore needs no special-case masking. **Falsifier:** the negative control
(a target expected to ACCEPT that is served an ACCEPT verdict after the
cross-check is bypassed) leaves the job green, or exit 3 is shown as a PASS or
a green SKIP, or a `BLOCKED` row increments `pass`/`fail` in `counts`.

   **CI job command shape** (the deliverable in `.github/workflows/ci.yml`).
   `--json PATH` is the H55 form and writes the *same* document atomically;
   bare `--json`/`-` is stdout only. Do not copy the standing gate's parser:
   `l3check`'s JSON has **no `summary` key**. Its real top-level keys are
   `schema, command, claim, exp, engine, corpus, card, targets, counts, result,
   exit, problems, generated_corpus, target_count, note`; row keys include
   `name, reader, entry, claims, expected, status, verdict, accepted, reason,
   problems, synthetic, l3_claim, runner_exit`; `counts` keys are lowercase
   `pass, fail, skip, blocked, runnable, total`; `result` is one of `PASS`,
   `FAIL`, `NO_RUNNABLE`; `exit` is `0` (PASS), `1` (FAIL) — a usage error is
   `2` and writes **no** JSON file. Read `data['counts']` / `data['targets']` /
   `data['result']` / `data['exit']`, never `data['summary']`.

   ```bash
   set +e
   python3 tools/l3check.py --build-corpus --json l3.json 2>&1 | tee l3.txt
   rc=${PIPESTATUS[0]}
   echo "exit_code=$rc" >> "$GITHUB_OUTPUT"
   python - <<'PY'
   import json, os
   if not os.path.isfile('l3.json'):
       raise SystemExit('l3check wrote no JSON (usage error); not a pass')
   with open('l3.json', encoding='utf-8') as f:
       d = json.load(f)
   c = d['counts']
   with open(os.environ['GITHUB_STEP_SUMMARY'], 'a', encoding='utf-8') as out:
       out.write('## L3 synthetic corpus (H28)\n\n')
       out.write('| target | reader | entry | claims | RESULT |\n')
       out.write('| --- | --- | --- | --- | --- |\n')
       for r in d['targets']:
           out.write('| `%s` | %s | %s | %s | **%s** |\n' % (
               r['name'], r['reader'], r['entry'] or '-',
               ','.join(r['claims']) or '-', r['status']))
       out.write('\npass=%d fail=%d skip=%d blocked=%d runnable=%d/%d; '
                 'result=**%s**; exit=%d\n' % (
                     c['pass'], c['fail'], c['skip'], c['blocked'],
                     c['runnable'], c['total'], d['result'], d['exit']))
       if d['result'] == 'NO_RUNNABLE':
           out.write('\n**NO RUNNABLE TARGETS** (exit 3): no L3 verdict '
                     'was produced; this is not PASS and not SKIP.\n')
       out.write('\n- BLOCKED (reader has no located entry point) is counted, '
                 'not a FAIL and not a PASS; SKIP (absent backend) claims nothing.\n')
       out.write('- Synthetic corpus only: `probe-zlib-cmf` is a runner/dispatcher '
                 'fixture (`synthetic: true`, `l3_claim: false`); the two '
                 'firmware-fragment PASS rows ran on synthetic corpus data. '
                 '**No card acceptance claim (rule 13)**; no L4/L5.\n')
   PY
   exit $rc
   ```

5. **Falsifier.** The claim (a default PR L3 table that is honest under rule 13)
   is refuted if any of the following is observed, each checkable by the command
   named:
   - command (c) leaves the job green, or the FAIL row does not carry exit 1 —
     the negative control did not falsify anything;
   - command (b)'s exit 3 is printed as PASS, mapped to a SKIP, or swallowed by
     `continue-on-error` — that would turn `NO_RUNNABLE` into a fake pass;
   - a `BLOCKED` row increments `fail` or `pass` in `counts`, or `runnable`
     becomes 11 instead of 3 (command (a)) — the policy was weakened;
   - the job summary reads `data['summary']` (a `gate.py` key) or shows 0
     rows while `targets` is empty — the wrong schema was parsed;
   - `gate.py` (command (d)) drops a PASS row after the CI edit — the standing
     gate was weakened;
   - the default PR job invokes `--image`, `--card`, `--factory`, `fetch_image`
     or any network step, or commits/caches vendor bytes — H28 scope violation;
   - the EXP calls any of the 3 PASS rows "card accepted" or "L4/L5 passed":
     rule 13 requires a reader VA for *confirmed* and an L3/L4 run on **our
     generated file** for *accepted*; these rows run on a synthetic corpus, so
     they are at most data-contract evidence. Cite `docs/research/feedback-loop.md`
     and TODO rule 13 verbatim in the EXP's Interpretation, alongside
     `result PASS` and the `note` field quoted from command (a).

## Interpretation

- **FACT:** the default PR job can publish a 13-row table with lowercase
  `counts` and the tool's own `result`/`exit`; exit is propagated unchanged, so
  `BLOCKED` is counted but never a FAIL/PASS, and exit 3 is RED with a
  `NO RUNNABLE TARGETS` label. The corrected negative control produces a real
  FAIL row and exit 1, and `gate.py` stays 5 PASS / 0 FAIL / 0 SKIP.
- **OBSERVED:** the three PASS rows are firmware-head/data-contract evidence
  only — one runner/dispatcher fixture and two firmware-fragment runs on a
  synthetic corpus. The report's own `note` says: *"a PASS on a synthetic
  target proves the runner/dispatcher path, not that the firmware accepts a
  card; BLOCKED and SKIP claim nothing and are counted, not failed"*.
- **RULE 13 (verbatim, TODO.md, "How to take a task", item 13; also
  `docs/research/feedback-loop.md`):** "A file type we generate counts as
  *confirmed* only when its reader in the firmware is located (an M3 task, VAs
  in `docs/format/`) and as *accepted* only when an L3 target (firmware fragment
  harness) or L4 full-system emulator run (M8/QEMU) executes that reader on our
  generated file and gets the expected values." These runs execute on a
  synthetic corpus, **not on our generated file**, and there is no L4/L5 run:
  no card is accepted here, and no row is a rule-13 acceptance verdict. The
  optional IMG256 mode is a firmware-head regression check only.
- **HYPOTHESIS:** publishing the table on every PR makes L3 progress visible
  without inflating it; when a reader gets a located entry point and a runnable
  corpus case, its row will move from `BLOCKED` to a genuine `PASS` with
  `l3_claim: true`.
- **UNKNOWN:** whether `files.viaaq.eu` is reachable from the project's GHA
  runner; the optional manual IMG256 contract is therefore documentation only
  here and owned by H84.

## Conclusion

H28 adds a blocking `l3` job to `.github/workflows/ci.yml` and documents its
verdict policy and the manual IMG256 contract in `.github/workflows/README.md`.
The job publishes the real `l3check` schema, never rewrites BLOCKED/SKIP/
NO_RUNNABLE into a pass, and keeps the standing gate unchanged. Claims
C-2780–C-2784 record the measured counts, controls and limits. Open: real
reader entry points for the 10 BLOCKED targets remain the work of the reader
tasks; no card acceptance is claimed.
