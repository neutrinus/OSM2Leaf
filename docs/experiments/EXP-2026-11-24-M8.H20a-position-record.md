## Question

Can the exact on-flash offset, record layout and checksum of the saved last
vehicle position be derived (from firmware structure or a real dump) so that
a negative control shows the firmware rejects a corrupted record and M8.H20
can be re-opened?

## Hypothesis

The saved position travels through the OBJDLL object store into the VSram
mirror, whose on-flash `SMST` stores have a derivable frame and checksum. If
the CarPos class and the store frame are identified, the exact record offset
and checksum follow. **Falsifier (task):** a candidate record whose mutation
does not change the position read at init. **Second falsifier:** the frame
checksum accepts a corrupted store.

## Observations

- O1 (`objpos_l3.py classes`): 25 class rows at `0x03482c6c` + 36·i, each `{name[32], u32 id}`; class 7 is `OBJ_SEM_CARPOS`, class 8 `OBJ_SEM_CARPOSROAD`. `nk_decomp.py pdata` marks `0x03495c4c`, `0x03495ce8`, `0x03495e28`, `0x03495bb8`, `0x034a14b8` START; `0x0349874c` is a GAP leaf in `fn 0x03498670`. `OBJ_CarPos_initialize` (`0x034a14b8`) calls backup loader `0x03495c4c` with `r4=6` (zero-based) and copies 36 bytes (`r7=36` at `0x034a1518 → fn 0x034a14b8`).
- O2 (`cerom.py imports OBJDLL.dll`): only `commondll!CApi_CommitSram/GetSramVirtualAddress{,i}` and OSMDLL slots — no FMD/flash IOCTL. The backup manager serialises into the VSram mirror; the flash→mirror step is in NK1.
- O3 (`sh4dis` NK1 `0x880483d0`): `CheckAreaData` compares 4 bytes at `+0` with literal `0x8800864c` (`SMST`), `u32` at `+4 == 14`, 4 bytes at `(size−0x10)+12` with `0x88008644` (`SMED`), then `r5 = size−0x10; shlr2 r5; sum of LE u32 words [0, size−0x10); cmp/eq against u32 at size−0x10; movt r0`. The writer `0x880482c6` emits `SMST`, `mov #14`, `SMED` and the same u32 sum (independent agreement).
- O4 (`objpos_l3.py flash firmware/unit-flash/sram-anon.bin`): 8 store copies at `0x000000`, `0x030000`, `0x060000`, `0x070000`, `0x080000`, `0x090000`, `0x0a0000`, `0x0d0000` inside the 1 MiB SRAM image; stored sums `0x960124ff`, `0xd84b18e1`, `0x8bad9775`, `0x321f23b6`, each equal to the computed sum (`OK`). Translated to flash by `unitflash_anon.AREAS`: `0x400000`/`0x430000`, `0x460000`/`0x470000`, `0x480000`/`0x490000`, `0x4a0000`/`0x4d0000` — every store doubled with generation counters 2/1, higher generation wins (second copy yes).
- O5 (`objpos_l3.py --selftest`): `PASS (0 failure(s))`; a mutated payload word makes the frame fail (`mutated sum rejected: got False want False`), and repairing the sum restores acceptance. `unitflash_anon.py --selftest` PASS (includes the bit-flip rejection); `coord.py --selftest` `OK (27/27 checks)`; `coord.py position 40.689 -74.044` → `0x9e84a900`, `position 51.70 17.45` → `0xa6c6d6c0`.

No position read was obtained, so the seed hypothesis is untested at L4.

## Interpretation

- **FACT:** the SMST frame and checksum rule are derived from the firmware's own checker and writer in NK1 (`CheckAreaData 0x880483d0`, writer `0x880482c6`); they match the repo's `unitflash_anon.make_store/check_store` and the committed anon flash (O3, O4, O5). A corrupted store is rejected loudly (O5, O6, C-8861). Every store is doubled with a generation counter, answering “is there a second copy?” **yes**.
- **FACT:** the backup class table identifies class 7 as `OBJ_SEM_CARPOS` and the CarPos init path calls the backup manager with that class and a 36-byte record (O1). OBJDLL reaches the VSram mirror through `CApi_CommitSram`, not a flash IOCTL (O2).
- **OBSERVED:** a candidate word planted at one plausible area offset was not observed to change the boot position (O8); the L4 read path was unavailable, so this is not a valid positive control for a seed tool.
- **UNKNOWN:** the byte offset inside an SMST store where the serialized CarPos value lives, and whether the stored value is the packed COORD001 word or the 1/512 arc-second pair used by the VFlash log. The linking globals (`0x01e54ee4`, `0x01e38164`, `0x01e33094`) are in OBJDLL compressed/BSS `.data`, unreadable without M1.2f/M8.E1; no real dump with a known last position is present. Therefore the exact flash offset and record fields of the saved position are **not** reproduced by a printing command.
- **Result:** Done when is only partially met (checksum + frame + second copy + negative mutation pass; exact position record offset/fields fail). Per the task Stop rule the honest status is **blocked**, not done.

## Conclusion

Blocked with a partial positive result. `tools/objpos_l3.py` (new, `--selftest` PASS) prints the backup class table, verifies all eight SMST store sums of the committed anonymous flash and demonstrates the store negative mutation; new claims C-10130–C-10134 record the derived frame/checksum, the CarPos class binding, the doubled stores, the firmware rejection of a corrupted store and the negative “no witness record” result. The exact on-flash position record offset/layout and its encoding stay UNKNOWN, so M8.H20 **cannot** be re-opened and no `ze0_seed.py` format or `--start-position` option is added. Unblock needs a real unit dump with a known last position (M6.18 on the owner's host) or decompression of OBJDLL sec1 `.data` (M1.2f/M8.E1) followed by an L3/L4 witness that mutating the derived field changes the read position.
