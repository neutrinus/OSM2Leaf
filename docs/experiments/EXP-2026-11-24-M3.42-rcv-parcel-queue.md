# EXP-2026-11-24-M3.42: `MDP_*RcvParcel` — the firmware's parcel receive queue

- **Status:** done
- **Date:** 2026-11-24
- **Sample:** `archive/head256.img` (first 256 MiB of the EU 2011 card image),
  SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (full file); the tool reports the first `134217728` bytes read with truncated
  hash `d3e5eac9cb5b4cbd`.
- **Tools:** `python3 3.15.0`; repo tools `tools/ce_strfind.py`,
  `tools/sh4xref.py`, `tools/sh4dis.py` (SH-4 code is little-endian, pinned in
  that tool), `tools/pdata.py`, `tools/va_class.py`, `tools/callgraph.py`,
  `tools/board.py`
- **Claims:** C-7780–C-7789 (new), C-7632 (status changed, see below)
- **Supersedes:** C-7632 (this EXP narrows its over-broad "no function
  attributed" clause; C-7632 row is marked `RETRACTED` because that clause
  voids the whole row's conclusion, including the un-retested Route Planning
  clause — see Corrections)
- **Superseded by:** none

## Question

What is the element layout of the firmware's `MDP_*RcvParcel` receive queue,
who pushes and who pops it, and is it the parcel queue between the file reader
and the map consumer that M3.25/M3.28 found?

## Hypothesis

The queue's names come from its logging strings; `sh4xref` from each string's
*start* VA to a literal-pool load therefore names the push/pop functions, and
the copy loops in those functions give the element size. Expected: a circular
list of fixed-size nodes, produced by one map-side function and consumed by an
`OSM_TaskReceive` handler. **Falsifier:** the queue carries traffic/telematics
messages, or the producer/consumer cannot be tied to the map/tile path.

3. **Controls.** Positive P1: `sh4xref --to` each string *start* returns a
   literal-pool load inside a pdata START function. P2: PUSH and POP copy
   loops print the same `mov #5,r1` / two `mov.l` / `dt` / `bf/s` / final
   `mov.l` pattern (11 u32 = 44 B), and INIT prints a 44-byte pool stride.
   P3: the sibling RcvMmi queue prints a different size (17 u32 = 68 B).
   Negative N1: the C-7632 mid-string VAs `0x187f10/0x187f78/0x187f9f`
   print "no literal pool holds". N2: a nonexistent string prints `hits 0`

5. **Falsifier.** As stated in Hypothesis: a non-map payload, or no tie to the

## Observations

**O1 — Strings (P1).** `ce_strfind --json` prints hits (VA / rva / file offset):
`MDP_pushRcvParcel` `0x187f70` / `0x177f70` / `0xe06170`;
`MDP_popRcvParcel` `0x187f98` / `0x177f98` / `0xe06198`;
`MDP_freeRcvParcel` `0x187f08` / `0x177f08` / `0xe06108`.
The surrounding bytes read (via `cerom.py va2file` + byte read):
`MDP_freeRcvParcel: error\n` (`0x187f08`), `mdp(parcel): alloc err\n`
(`0x187f58`), `MDP_pushRcvParcel: Invalid parameter.\n` (`0x187f70`),
`MDP_popRcvParcel: Invalid parameter.\n` (`0x187f98`),
`MDP_freeRcvMmi: error\n` (`0x187f24`),
`MDP_pushRcvMmi Invalid parameter.\n` (`0x187fd8`).

**O2 — Signature to code (P1).** `sh4xref --to` on each string start:
```
pool 0x0049a284 holds 0x00187f70
  load 0x0049a228 (r4)  fn 0x0049a21c  [pdata]
pool 0x0049a324 holds 0x00187f98
  load 0x0049a2aa (r4)  fn 0x0049a29c  [pdata]
pool 0x0049a338 holds 0x00187f08
  load 0x0049a30a (r4)  fn 0x0049a29c  [pdata]
```
`pdata.py fn`: `0x0049a21c START … length 0x80, end 0x0049a29c`;
`0x0049a29c START … length 0xa0, end 0x0049a33c`.
Thus PUSH is `0x49a21c`; POP is `0x49a29c`; the "freeRcvParcel" string is
emitted by POP, not by a third named function.

**O3 — PUSH (P2).** `sh4dis 0x49a21c`: `tst r4,r4` / `bf` at `0x49a224`;
on null, load string `0x187f70` and call `OSM_LogMsg`. Otherwise:
- `0x49a22e` pool `0x009e6418` (free-list head) -> `mov.l @r5,r2`;
- `0x49a23e` pool `0x009f1008` (count) -> `add #1,r3` -> `mov.l r3,@r5`;
- copy loop `0x49a24c` `mov.l @r4+,r13` / `0x49a250 mov.l @r4+,r12` /
  `mov.l r13,@r3` / `mov.l r12,@(4,r3)` / `dt r1` (r1=`mov #5,r1` at
  `0x49a238`) / `bf/s 0x49a24c` / `add #8,r3`, then final `mov.l @r4,r13`
  at `0x49a25a` — 5×8 + 4 = **44 bytes (11 u32)**;
- link node into circular list via `0x009f0f70` (`0x49a25e`–`0x49a26c`).

**O4 — POP (P2).** `sh4dis 0x49a29c`: `tst r4,r4` -> string `0x187f98`
(`0x49a2aa`); walks list from `0x009f0650` (`0x49a2b8`) comparing
`mov.b @(8,r2),r0` (u8 at element `+8`) with `r5` (`0x49a2c0`–`0x49a2c4`);
on match `0x49a2d4`–`0x49a2ec` unlinks, then copy loop `0x49a2e2`/`0x49a2e6`
`mov.l @r3+,rNN` / `mov.l rNN,@r4` / `dt r1` (r1=5) / `bf/s` / `add #8,r4`
plus final `mov.l @r3,r13` at `0x49a2f2` — the same **44 bytes (11 u32)**;
restores node to free list `0x009e6418`, decrements count `0x009f1008`
(`0x49a2fe` `add #-1,r2`); on count < 0 logs `0x187f08` via `0x0055d944`
(`0x49a30a`, `0x49a30e`) — this is the `MDP_freeRcvParcel: error` path.

**O5 — INIT / node pool (P2, N3).** `pdata.py fn`: `0x0049a158 INSIDE fn
0x0049a0f0 prologue 6 B, length 0x70`. `sh4dis 0x49a158`:
`0x49a160 mov.l @(0x49a1ec,pc),r2 ; [0x49a1ec]=0x009f0f70`,
`0x49a164 mov.l @(0x49a1f0,pc),r3 ; [0x49a1f0]=0x009f0650`,
`mov.l r4,@r2` / `mov.l r2,@r3` / `mov.l r3,@(4,r2)` / `mov.l r4,@(4,r3)`
(`r4=0`) — the two globals are a circular sentinel pair;
`0x49a16e mov.l …,r2 ; =0x009ed2c0`,
`0x49a170 mov.l …,r3 ; =0x009e6418` (free-list head),
`mov.w @(0x49a1e4,pc),r5 ; [0x49a1e4]=0x012b` (299 nodes),
loop `0x49a178 add #44,r4` / `dt r5` / `bf/s 0x49a178` — **299 nodes × 44 B**.
Sibling loops: `mov #99,r4` with stride 280 (`shll2 r1` of `#70`) at
`0x49a196`–`0x49a1ae` (RcvMmi, 70 u32), and `mov #19,r4` stride 104 at
`0x49a1c4`–`0x49a1d8` (another sibling). `va_class` prints
`0x009e6418 BSS …`, `0x009f0f70 BSS …`, `0x009f1008 BSS …`,
`0x009f0650 BSS …` and `0x0049a21c CODE sec0` (N3).
`va_class 0x0055d944` prints `IAT OSMDLL.dll!OSM_LogMsg`.

**O6 — Producer.** `sh4xref --to 0x0049636c` prints
`pool 0x00185a58 holds 0x0049636c`; `pdata.py fn`:
`0x0049636c START … length 0x80, end 0x004963ec`.
`sh4dis 0x49636c`: id lookup `mov.l @(28,r4),r6` vs a two-entry table at
`0x00ecb940 + 0x5e94`/`+ 0x2b1a4` (`0x49a374`–`0x49a394`); if found,
builds a local 44-B element at `r15+16` (`r2 = r15+16`, `r3 = r2+12`): eight
source u32 loads (`0x4963a4`, `0x4963b2`, `0x4963b4`, `0x4963ba`, `0x4963bc`,
`0x4963c2`, `0x4963c4`, `0x4963ca`) are stored to element offsets
`+12,+16,+20,+24,+28,+32,+36,+40` (8 u32 = 32 B); the table index `r3` is
written as `mov.b r3,@(24,r15)` at `0x4963a8` (local element `+8`, matching
POP's `mov.b @(8,r2)`). Offsets `+0`, `+4` and `+9..+11` are **not written by
this producer**. Then `mov.l @(0x4963e8,pc),r3 ; =0x0049a21c` / `jsr @r3`
at `0x4963d0` (PUSH). PUSH copies the full 44 B, including the unwritten
fields, into the heap node.

**O7 — Consumer and one level up.** `sh4xref --to 0x0048ef24` prints
`pool 0x0048f1b8 holds 0x0048ef24`, load `0x48f168` in fn `0x48f0c4`;

[0x48f008]=0x00496c8c` / `jsr @r3` at `0x48efa6`.
`pdata.py fn`: `0x00496c8c START … length 0x150, end 0x00496ddc`.
`sh4dis 0x496c8c`: `mov.w @(10,r2),r0` (u16 at element `+10`) compared with
3/5/9 to pick one of three downstream handlers (`0x496b98`, `0x496a60`,
…); `mov.l @(12,r2),r6`, `mov.l @(20,r2),r5` (u32 at element `+0x0c` and `+0x14`; decimal 12/20).

## Element layout (44-byte node)

| Offset | Size | Meaning | Evidence |
| --- | --- | --- | --- |
| `+0x00` | u32 | UNKNOWN (not written by producer `0x49636c`; copied by PUSH/POP) | O3/O6 |
| `+0x04` | u32 | UNKNOWN (not written by producer; copied by PUSH/POP) | O3/O6 |
| `+0x08` | u8 | selector / level — POP match key `mov.b @(8,r2)` vs arg `r5`; producer writes the table index here (`mov.b r3,@(24,r15)`) | O4/O6 |
| `+0x09..0x0b` | 3 B | UNKNOWN padding (not written; copied) | O3/O6 |
| `+0x0c` | u32 | payload word 0 from source `r4+0`; consumed by `0x496c8c` as `mov.l @(12,r2),r6` | O6/O7 |
| `+0x10` | u32 | payload word 1 from source `r4+4` | O6 |
| `+0x14` | u32 | payload word 2 from source `r4+8`; consumed by `0x496c8c` as `mov.l @(20,r2),r5` and `mov.l @(20,r2),r3` (decimal 20 = +0x14) | O6/O7 |
| `+0x18` | u32 | payload word 3 from source `r4+12` | O6 |
| `+0x1c` | u32 | payload word 4 from source `r4+16`; no downstream read observed in `0x496c8c` (producer-only) | O6 |
| `+0x20` | u32 | payload word 5 from source `r4+20` | O6 |
| `+0x24` | u32 | payload word 6 from source `r4+24` | O6 |
| `+0x28` | u32 | payload word 7 from source `r4+28` | O6 |

Total **0x2c = 44 bytes**. Fields `+0x00/+0x04/+0x09..0x0b` are inherited
from the caller-prefilled local element; PUSH copies all 11 u32 into the node
and POP copies all 11 u32 back out, so their values survive the queue.

## Interpretation

- **FACT:** the signature source is `ce_strfind` string start → `sh4xref
  --to` literal-pool load → `mov.l @(disp,PC),Rn` → `jsr @Rn` → pdata START
  (error string → xref, **strong**). PUSH=`0x49a21c`, POP=`0x49a29c`.
  The `MDP_freeRcvParcel` string is logged by POP's underflow path, not by a
  separate function.
- **FACT:** the element is **44 bytes (11 u32)**, established twice by the
  PUSH and POP copy loops (O3/O4) and by the 299-node × 44-B INIT pool (O5).
- **FACT:** the queue is a circular doubly linked list; `0x9f0f70` and
  `0x9f0650` are the sentinel pair (INIT stores each into the other), PUSH
  links before `0x9f0f70`, POP walks from `0x9f0650`; `0x9e6418` is the
  free-list head, `0x9f1008` the element count, written by INIT `0x49a158`.
- **OBSERVED:** field meanings from consumer/producer field reads: `+8` u8
  selector (POP match, producer writes table index), `+10` u16 kind (downstream
  3/5/9 dispatch in `0x496c8c`), `+12`/`+20` u32 payload words. The remaining
  words are copied verbatim but their individual meanings are not established
  here.
- **FACT:** producer `0x49636c` (table `0x185a58`) pushes the element;
  consumer `0x48ef24` pops it and forwards to `0x496c8c`, called from the
  task loop `0x48f0c4` that imports `OSM_TaskReceive`/`taskIdSelf`, and POP's
  caller imports `OSM_TaskSend`. This is the map-client/task path the
  falsifier asks for; the falsifier did not fire.
- **UNKNOWN:** no *static* call from the M3.25 read-completion handlers
  (`0x3f72e4`, `0x40b8b4`) to the producer — it is reached via the table at
  `0x185a58`, so the one-hop link to those handlers is not established (Stop
  rule: name the indirect table and stop). The semantic meaning of the
  selector and kind values, and the source of the caller-prefilled bytes
  `+32..+43`, are open.
- **Prior claim:** C-7632 stated the strings at `0x187f10/0x187f78/0x187f9f`
  have no xref so "no firmware function is attributed". That negative is
  reproducible **at those VAs**, but they are 7–8 bytes into the strings; the
  string starts do have xrefs. C-7632 is marked `RETRACTED` for the
  over-broad attribution clause; new C-7780 carries `Supersedes: C-7632`.

## Conclusion

The queue is a firmware-owned 44-byte-element circular list, not a KIWI map
format structure: its element table is documented in `docs/format/map-tiles.md`
under "what the firmware calls a parcel", with producer `0x49636c`, consumer
`0x48ef24`, and the read-completion link left explicitly as UNKNOWN (indirect
call). C-7780–C-7789 record the strings, VAs, layout, globals and controls;
C-7632 is retracted for its over-broad clause. Nothing here asserts a card
format or a confirmed firmware reader VA for our generated data.

## Corrections after navigator review

- Element size corrected from an initial 24 B reading to 44 B (11 u32), after
  the navigator counted the `mov #5,r1` copy loops and the 44-B INIT stride.
- Producer field count corrected: 8 source u32 written by producer `0x49636c`
  to element offsets `+12..+40`, not 9 or 11; offsets `+0/+4/+9..+11` are
  UNKNOWN (caller-prefilled). 11 u32 is the PUSH/POP copy-loop size, not the
  producer's field count.
- Consumer copy count corrected to 8 u32 (32 B) into the table record.
- C-7632 marked RETRACTED via `python3 tools/board.py claim-status C-7632
  RETRACTED` (printed `board: C-7632 -> RETRACTED`); the EXP header and C-7780
  carry `Supersedes: C-7632` explicitly. Retraction (whole row) rather than a
  narrow status was chosen because the row's single conclusion — "no firmware
  function is attributed" — is void; its un-retested `Route Planning` clause
  is therefore not relied on by this EXP.
