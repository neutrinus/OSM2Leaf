## Question

Can `tools/l3_harness/runner.py run` execute the real `AppLaunch.dll` map-code
compare (build B `fn 0x03bd2ad8`, M2.5/M2.15) on the factory `HDD_INFO.TXT`
(accept) and on one edited line-1 variant (reject), and return a firmware verdict?

## Hypothesis

Yes, after the runner can call a function at a module VA (`entry.kind = "module"`).
Falsifier: the runner on `origin/main` cannot load a module VA, or the compare
function cannot be reached and returns no verdict.

is `blocked`. So no firmware verdict is reachable from `main`.

  `pTOC 0x8e232978`, `ROMHDR` at file `0x01951b78`.
- `cerom.py va2file 0x03bd2ad8` on build B: file `0x04157cd8`.
- `AppLaunch.dll` build B sections: sec1 `rva 0x1000`, `realaddr 0x03bb1000`,

  sec2 (`realaddr 0x01f73000`, file `0x03f6ddc0`) and sec3 (`realaddr 0x03bd8000`,

- Open PR #89 (M9.20, `claude/m9.20-l3-plumbing`) adds `entry.kind = "module"`,
  `engine_hook` and the Ghidra entry script. It is still a draft on
  2026-11-08 and is not on `origin/main`.
- `python3 tools/selftest.py`: `passed=50 failed=0 skipped=18 total=68`.
  `python3 tools/l3_harness/selftest.py`: `selftest: OK (19 checks)`.

## Interpretation

M9.6 cannot run its done-when check on `origin/main`. The compare lives in a
module that is loaded at a VA, and the runner has no entry kind to load a
module and call a function at that VA. That plumbing is the scope of M9.20,
which is claimed in PR #89 and not merged. Re-implementing it here would
duplicate that PR and conflict with it, so M9.6 is set `blocked` with
`Unblock: M9.20`.

What is established here is the placement: the compare is in an uncompressed
section of build B `AppLaunch.dll`, so no decompressor is needed for it (C-1681).
The compare's inputs (the factory bytes and the `+0x60` record) and the file path
are not verified here; those belong to the rerun after M9.20 merges.

No firmware verdict is claimed. The map-code compare remains an open
question for M2.4.
