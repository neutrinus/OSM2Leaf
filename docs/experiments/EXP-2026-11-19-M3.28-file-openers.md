# EXP-2026-11-19-M3.28: Who names which map file — openers from the name tables, run on a card

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** firmware: `archive/head256.img` (first 256 MiB of the EU card
  image) SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card: `LEAF_2011-2012_QSD-309-101_navi158_eu.img` SHA-256
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Tools:** `python3 3.13.18`; repo tools `tools/name_loaders.py` (new),

- **Supersedes:** none

## Question

Which `Navi.exe` function opens each map-file family, and through which calls
do the bytes reach it?

## Hypothesis

A file is opened by resolving its name to an id, so the callers of the one
name resolver are the openers, and the names each caller can pass identify the
family.

**Falsifier:** an opener that, run on the card, resolves a name outside the
set its literals predict; or a file read that does not pass through the
resolver's id and the read request function.

**Disassembly facts.** `0x0040b358`: `r5` = name (0 → `-1`), `r4` = directory
path passed to `0x00409cc8(1, path)`; loop over 28-byte entries, skipping kind
2, `strcmp` at `0x0040b3a2`; result `(dir << 16) | word +20`. `0x00409ba0`:
no call except `0x004192c0`. `0x003f6c88`: `memset` of the 40-byte request,
then stores into +0, +4, +8, +12 (from the slot), +16 and +24 (from
`0x00d6ece0`), +32 (from `0x011fff58`); nothing stores to +20.
`0x003f6e40`: the shifts given in `firmware.md`.

## Interpretation

- **FACT:** one function resolves names (`0x0040b358`, 13 callers) and one
  function issues file reads (`0x003f6c88`, the only caller of the read API).
  The falsifier did not occur: every opener that ran resolved names inside the
  set its literals predict.
- **FACT:** the name lookup is case-sensitive.
- **FACT:** `POINT`, `ADDRE`, `FRWAY`, `INTER`, `ZCODE` and `LCTBL` share one
  opener, `0x003fbed8`, selected by the search type in the context;
  `ICADM` and a second `ADDRE` path have their own (`0x003f1640`,
  `0x004011a0`, both number from 0), and a second `POINT` path
  (`0x00410500`, three digits) belongs to the `0x0040f…0x00410…` module.
- **FACT:** every read a client makes through `0x003f6c88` asks for the byte
  swap (request word +20 = 0). This closes the open half of M3.11b: the client
  is `0x003f6c88`, for all files, not a `POINT`-specific function.
- **FACT:** 40 of the 52 file names in the firmware do not exist on the EU
  2011 card.
- **OBSERVED:** `0x0040b3e0` is a presence probe over a table of data kinds
  (it resolves and does not read).
- **HYPOTHESIS:** the 40 absent names belong to other products built from the
  same source (the `CDROM.DAT` column, `DFRMR`, `SOUND`); a generated Leaf
  card does not need them. Supported by the factory card working without
  them; not tested on a unit.
- **UNKNOWN:** who reads `COORD001.DAT` and `ZIPFR001.DAT` (no name reference
  in `Navi.exe`; another module, or an id taken from another file).
- **UNKNOWN:** the record parsers behind each read (M3.13–M3.16).

## Conclusion

The hypothesis holds. The matrix's reader column gets an opener and the
functions that issue its reads for `ZCODE`, `ICODE`, `INTER`, `FRWAY`,
`ICADM`, `LCTBL` and `BICON`; `COORD001` and `ZIPFR001` stay unlocated with
the lookups that were tried.

## Reproduction

The commands under Method. `census`/`openers` need only `head256.img`; the
`vcard_l3.py` commands need the full card image as well (about 10 s each).

- US2011: the same census with `--resolver` from `fn_match`.
