## Question

Does putting a static test picture on the video input on reverse reduce to a
plane switch plus a frame-buffer fill (`simple plane switch`), or does the
capture path need its own model (`needs a video-capture model`)?

## Hypothesis

The `VIN1:` IOCTLs only select/mute/overlay/size the video input, while the
pixels arrive on a separate video-input path; so a plane switch alone cannot
supply camera pixels and the verdict is "needs a video-capture model".
**Falsifier:** if the reverse-event consumer writes camera pixels into a DU
plane frame buffer (a plane register + a CPU/DMA fill found in readable code),
then a simple plane switch would suffice and this hypothesis is refuted. A
second falsifier for the "plane switch" branch: if no reverse-event consumer
changes any display state at all, then "reverse changes nothing on the display
path" holds and neither mechanism is established.

## Interpretation

- **FACT:** `VIN.dll` is a video-input manager. Its `VIN_IOControl`
  (`fn 0x03953f24`, pdata START) dispatches via a computed index and a jump
  table; it owns camera-mode, mute, size, sync and CEN selector handlers.
- **FACT:** The display side is a DirectDraw overlay surface on layer 4
  (`DDCreateSurface [OverLay]`, `DrawSurf`, `SetSh(Layer_4, VIN_VIDEO_MUTE_OFF)`),
  not a CPU-written DU plane frame buffer; the frame source is a video-input
  path that reaches the SoC (C-7584).
- **FACT (negative, with positive controls):** no capture/DU/graphics physical
  register base is referenced in VIN.dll sec0 or either decoded compressed
  section; the driver's hardware access is through `DeviceIoControl` on
  `LCD1:`/`CEN1:`/`GPI1:` and COM/DD imports.
- **OBSERVED:** reverse bit 0 raises `EVENT_NAV_SENSOR_BACK` via navdrv
  `fn 0x039e6690`; the camera UI (`camera.md`) consumes that event through
  `SystemCC`. No L4 run observed the on-screen effect.
- **UNKNOWN:** the capture peripheral's register list — no physical register
  block is programmed in the readable code and the SoC capture block is not
  named in the firmware address map. `Bolero`/`0x19a00000` and `0x10000000`
  graphics-area roles are HYPOTHESIS, not camera evidence.
- **HYPOTHESIS:** feeding a test picture on reverse requires modelling the
  video-input capture (input selector + frame source + overlay compositing);
  a DU-plane-only patch would bypass rather than exercise the path.

## Conclusion

**Verdict: B — needs a video-capture model (with the register list UNKNOWN).**
The static read locates the reverse trigger and the video-input manager, and
shows the camera image is composed through a DirectDraw overlay rather than a
CPU-written DU plane. A "simple plane switch + test image patch" is therefore
not supported by the readable code and is not claimed. The capture register
list could not be recovered from the readable sections and is reported as an
UNKNOWN, not invented. Deliverables: this EXP,
`docs/firmware/camera-capture-path.md`, claims C-7580–C-7589 (via
`tools/board.py add-claims`). No QEMU patch and no video decoder were added.
Follow-up: a dedicated task must locate the capture register block (likely via
L4 tracing the `VIN1:`/`CEN1:` IOCTLs to the hardware) before an on-screen test
picture can be produced.
