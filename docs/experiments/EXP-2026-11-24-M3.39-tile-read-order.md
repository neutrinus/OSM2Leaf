## Question

In which order does the firmware touch the structures of one level-1 map tile
at mount and on a map request — expressed as ordered offset range → structure →
reading `fn` — and how does each frame (management, road, background, name)
compare three ways with `kiwiread`'s parse order (same / different / not read
at mount)?

## Hypothesis

The mount is a fixed parse order: management header → section tables →
directories (level 2 then level 1 per section), with record blocks reached only
by a map request. The three-way comparison should therefore say "same order"
only for the management header; road/background/name frame *content* is either
a different order or not read at mount. **Falsifier (set before the runs):**
if a `--request` of a different kind changes the *position in the sequence* of
the already-mount structures (not merely appends a request-specific read), the
firmware has "an order that depends on the request kind only" and the fixed
order hypothesis is wrong. A second falsifier: the read watch records zero
tile reads (an inert watch is never a pass).

## Interpretation

- **FACT (run):** the tile is walked in a fixed order — management header,
  then each section table followed by that section's level-2 and level-1
  directories — attributed to named `Navi.exe` sec0 functions by a validated
  read watch (O2/O3). Nine tile reads of 28 total at 51.70,17.45.
- **FACT (control):** a directory-count byte mutation changes the parse length
  of read 4 from 16,514 to 33,014 B and the diff verdict from SAME to
  DIFFERENT (O6). The ordered list is therefore a check that can fail, not a
  transcript of an inert watch.
- **FACT (falsifier):** the mount prefix is identical across mount, kind-4 and
  kind-`0x40` runs; a request only appends its own directory/record reads (O5).
  The task's falsifier ("order depends on request kind only") did not fire.
- **OBSERVED:** the three-way verdicts are management = same order, road =
  not read at mount (mount) / different (structural), background and name =
  not read at mount (table above). Rule 13 is unchanged: this is an L3
  observation of the *factory* tile, not acceptance of a generated file; no
  firmware reader VA is claimed from a KIWI struct.
- **UNKNOWN:** whether an L4 full-system draw (M8/H10) reaches the odd
  background record or a name frame; the in-record field order of the served
  record (M9.66/M3.41); US2011 (H51).

## Conclusion

The ordered read list (offset range → structure → reading `fn`) for
`B48R058R.DAT` is recorded in O3, with all 14 reader/handler VAs attributed to
`Navi.exe` sec0 via `cerom.py` (O7). The three-way verdict per frame is in the
table above: management header same order, road not read at mount / different
structurally, background and name not read at mount. `kiwiread`'s true frame
order is background → road → name, not the Goal's wording. C-7790–C-7799
register the order, the fns, the verdicts and the controls; no format doc field
was renamed and no generated file was accepted (rule 13).
