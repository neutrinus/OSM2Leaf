## Question

In which order does the firmware touch the structures of one level-1 map tile
at mount and on a map request — expressed as ordered offset range → structure →
reading `fn` — and how does each frame (management, road, background, name)
compare three ways with `kiwiread`'s parse order (same / different / not read
at mount)?

## Hypothesis

The mount is a fixed parse order: management header → section tables →
directories (level 2 then level 1 per section), with record blocks reached only
by a map request. The three-way comparison should therefore say "same order"
only for the management header; road/background/name frame *content* is either
a different order or not read at mount. **Falsifier (set before the runs):**
if a `--request` of a different kind changes the *position in the sequence* of
the already-mount structures (not merely appends a request-specific read), the
firmware has "an order that depends on the request kind only" and the fixed
order hypothesis is wrong. A second falsifier: the read watch records zero
tile reads (an inert watch is never a pass).

3. **Controls.** *Positive:* `read_watch_l3.py --selftest` is 8/8 PASS including
   "A is credited for a page read" and "B's write lands in the write watch", so
   the watch credits a real guest read and fails closed when unarmed. `datask_l3
   diff F F` prints `SAME`, and the baseline watch attributes concrete byte
   ranges to named fns (O3) — a zero-read run would be reported as `NO HITS`
   and never a pass. *Negative (mandatory):* flipping the directory-count byte
   `0x9a1dc03` from 32 to 64 makes `diff` print
   `fn 0x00414dbc A (16514, 1) B (33014, 1) DIFFERENT`, exit 1 (O6).
   *Falsifier control:* kind 4 vs kind `0x40` (O5).

4. **Scope.** EU2011 build A, `Navi.exe` sec0 (all executable sections
   uncompressed, C-2128). One level-1 tile (`B48R058R`), two car positions,
   three runs (mount, kind-4 request, kind-`0x40` request). The "frames" are the
   KIWI conceptual frames (management / road / background / name); our ZE0
   container is *not* KIWI (M4.63–M4.78: 1 adopt, 3 partial, 6 unrelated), so
   the comparison is vocabulary/order only and never renames a ZE0 field or
   attributes a firmware VA from a KIWI struct. Excluded: US2011 (VAs differ,
   H51), L4 full-system emulation (M8), record-level shape walking (M9.66,
   M3.41), display code, and a real KIWI disc (M4.77, unavailable). No tile or
   firmware byte is committed.

5. **Falsifier.** As stated in Hypothesis: a request kind that reorders the
   mount structures (rather than appending a request read), or a watch with no
   tile reads, refutes the claim. `kiwiread`'s order was quoted from the pinned
   commit (`showmap` reads background `de[1]`, road `de[0]`, name `de[2]` — note
   this is **not** the Goal's phrasing "road, background, name").

## Three-way verdict per frame

| Frame (KIWI chapter concept) | Firmware L3 observation | Verdict vs `kiwiread` |

| Management header (ch.5/6 header + level lists) | seq 1 `0x0..0x1000` then seq 2/5/8 section tables `0x1000+`, handled by `0x0040b8b4`/`0x0040c308` — first, in both | **same order** |
| Road frame (ch.7.2) | at mount: no record read (only header/tables/directories); on kind-4 request: directory seq 10 then record block seq 11 `0x9aead00+0x300`, inflated by `0x0054233C` — not KIWI's `pdmdh`→`lmr`→`bsmr`→road-frame order | **different** (request path) / **not read at mount** |

The KIWI frame order itself (background → road → name, O4) differs from the

as a fact here.

## Interpretation

- **FACT (run):** the tile is walked in a fixed order — management header,
  then each section table followed by that section's level-2 and level-1
  directories — attributed to named `Navi.exe` sec0 functions by a validated
  read watch (O2/O3). Nine tile reads of 28 total at 51.70,17.45.
- **FACT (control):** a directory-count byte mutation changes the parse length
  of read 4 from 16,514 to 33,014 B and the diff verdict from SAME to
  DIFFERENT (O6). The ordered list is therefore a check that can fail, not a
  transcript of an inert watch.
- **FACT (falsifier):** the mount prefix is identical across mount, kind-4 and
  kind-`0x40` runs; a request only appends its own directory/record reads (O5).
  The task's falsifier ("order depends on request kind only") did not fire.
- **OBSERVED:** the three-way verdicts are management = same order, road =
  different/not read at mount, background and name = not read at mount
  (table above). Rule 13 is unchanged: this is an L3 observation of the
  *factory* tile, not acceptance of a generated file; no firmware reader VA is
  claimed from a KIWI struct.
- **UNKNOWN:** whether an L4 full-system draw (M8/H10) reaches the odd
  background record or a name frame; the in-record field order of the served
  record (M9.66/M3.41); US2011 (H51).

## Conclusion

The ordered read list (offset range → structure → reading `fn`) for
`B48R058R.DAT` is recorded in O3, with all 14 reader/handler VAs attributed to
`Navi.exe` sec0 via `cerom.py` (O7). The three-way verdict per frame is in the
table above: management header same order, road different/not read at mount,
background and name not read at mount. `kiwiread`'s true frame order is
background → road → name, not the Goal's wording. C-7790–C-7799 register the
order, the fns, the verdicts and the controls; no format doc field was renamed
and no generated file was accepted (rule 13).
