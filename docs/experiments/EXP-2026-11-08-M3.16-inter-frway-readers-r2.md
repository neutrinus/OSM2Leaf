# EXP-2026-11-08-M3.16: `INTER` / `FRWAY` readers (r2)

- **Status:** done (negative / blocked: content reader VAs not found in decodable build-A code)
- **Date:** 2026-11-08
- **Sample:** `IMG256` = first 256 MiB head of `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (build A), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (file `archive/head256.img` on this machine). No vendor bytes committed.
- **Tools:** `python3 3.14.0` / `zlib` (runtime not used for compression here);
  `tools/cerom.py`, `tools/sh4xref.py`, `tools/sh4dis.py`,
  `tools/reader_precheck.py` (repo, this commit). CE image start `0x200200`.

- **Supersedes:** none

  they are reached only through an indirect path with a bound positive control

## Question

Which build-A firmware function(s) read `INTER0nn` / `FRWAY0nn` (`REFER001`)
file content, and which fields of the 12-byte table / blob structures do they
consume? (M3.16 done-when: reader VAs and consumed fields in `refer.md`.)

## Hypothesis

Exploratory. `INTER0`/`FRWAY0` are members of the REFER001 volume-id table at
`0x00179338` (C-881), adjacent to `ADDRE0`/`POINT0`, so they resolve through
the same REFER001 family access mechanism as POINT/ADDRE (descriptor `0x14e8`
→ `REFER001`+`INDEX003.DAT` in `fn 0x004125a8`, name builder `fn 0x003fbed8`,
volume lookup `fn 0x0040b358`; C-880/C-2180). The content parser that consumes
the `INTER`/`FRWAY` 12-byte table at `0x1108` (u8 id, u16 n, u16 0, u16 offset,
u16 length `6*k`, u16 0; `0xffff` terminator; blob 0 6-byte elements;
FRWAY blob 1 route refs + blob 2 main table with 4-byte mesh ids / serial+text,
per `refer.md` C-135 and format observations) is expected to be reachable from
that access path in decodable build-A executable code.

**Falsifier:** either (a) a decodable function is found whose argument/loop
structure consumes the 12-byte table / 0xffff terminator / 6-byte blob elements
or FRWAY mesh-id/serial fields (with a positive control showing the method
finds a known reader, e.g. POINT/ADDRE access anchors), or (b) two structural
signature families derived from the writer's inverse of the format behavior
(each stated before search, scoped to all build-A decodable executable
sections) find 0 candidates and the access-path membership is the only
confirmed link — in which case the content reader is not located and the
done-when is not met.

## Method

1. **Sample and hash.** `archive/head256.img` SHA-256 above; CE ROM parsed with
   `cerom romhdr/sections/modules`. No vendor bytes committed.
2. **Commands** (run from repo root; runnable as written):
   ```bash
   IMG=archive/head256.img; MS="--image-start 0x200200"
   python3 tools/reader_precheck.py --module Navi.exe $IMG
   python3 tools/cerom.py $IMG romhdr

   python3 tools/sh4xref.py $IMG Navi.exe $MS --to 0x00179354   # FRWAY0
   python3 tools/sh4xref.py $IMG Navi.exe $MS --to 0x004125a8   # descriptor switch
   python3 tools/sh4dis.py $IMG Navi.exe $MS --va 0x003fbed8 --count 80
   python3 tools/sh4dis.py $IMG Navi.exe $MS --va 0x004125a8 --count 120
   python3 tools/sh4xref.py $IMG Navi.exe $MS --to 0x003f51e0   # REFER schema resolver (control)
   ```
   Signature family 1 (writer-inverse of 12-byte record scan: `u16 length` at
   record offset 8 compared to `0xffff` terminator, 12-byte stride) over
   `Navi.exe` sec0 (file `0x00c8f200`, `0x54be00` B, base VA `0x11000`):
   ```bash
   python3 - <<'PY'
   import struct
   img='archive/head256.img'; sec0_file=0x00c8f200; sec0_size=0x54be00; base_va=0x11000
   with open(img,'rb') as f: f.seek(sec0_file); sec=f.read(sec0_size)
   def hw(off): return None if off<0 or off+2>len(sec) else struct.unpack_from('<H',sec,off)[0]
   hits=[]
   for i in range(0,len(sec)-2,2):
       if hw(i)==0x88ff: # cmp/eq #-1,r0
           ctx=[hw(i+j*2) for j in range(-12,13)]
           has_movw8b=any(h is not None and (h&0xFF0F)==0x8504 for h in ctx) # mov.w @(d*2,Rm),R0 d=4 => +8
           has_add12c=any(h is not None and (h>>8)==0x7 and (h&0xFF)==0x0C for h in ctx) # add #12,Rn
           if has_movw8b and has_add12c: hits.append(base_va+i)
   print('family1', len(hits), [hex(v) for v in hits[:20]])
   PY
   ```
   Signature family 2 (writer-inverse of `0x1108` table-offset access:
   construction `mov #0x11,Rn; shll8 Rn; add #8,Rn`, same register, within 6
   halfwords) over `Navi.exe` sec0:
   ```bash
   python3 - <<'PY'
   import struct
   img='archive/head256.img'; sec0_file=0x00c8f200; sec0_size=0x54be00; base_va=0x11000
   with open(img,'rb') as f: f.seek(sec0_file); sec=f.read(sec0_size)
   def hw(off): return None if off<0 or off+2>len(sec) else struct.unpack_from('<H',sec,off)[0]
   hits=[]
   for i in range(0,len(sec)-12,2):
       h0=hw(i)
       if h0 is not None and (h0&0xF0FF)==0xE011:
           n=(h0>>8)&0xF; shll8=0x4018|(n<<8); add8=0x7008|(n<<8)
           w=[hw(i+j*2) for j in range(1,7)]
           if shll8 in w and add8 in w: hits.append(base_va+i)
   print('family2', len(hits), [hex(v) for v in hits[:20]])
   PY
   ```
3. **Controls.** *Positive (access-path anchors):* `sh4xref --to 0x0017935c`
   (ADDRE0, C-2180) resolves to a load in `fn 0x0040114e` in Navi.exe sec0;
   descriptor `0x14e8` resolves `REFER001`/`INDEX003.DAT` in `fn 0x004125a8`
   (C-880); `sh4xref --to 0x003f51e0` resolves multiple pool loads/callers
   (REFER schema resolver, C-2184/C-884) — confirming the xref/disasm method
   finds known REFER-family readers. *Negative:* a method that cannot find any
   12-byte/0xffff/0x1108 construction consumer in 5.55 MB of Navi.exe decodable
   executable code is negative for the specific signatures tested, not a proof
   of absence (indirect dispatch through `.data` pointers or a different
   register/offset form would evade these signatures; `refer.md` warns
   `n`/field meanings are partly unknown, so consumed-field mapping requires
   the actual reader).
4. **Scope.** Signature families 1–2 searched `Navi.exe` sec0 only: 1
   uncompressed executable section, **5,556,224 B** (`0x54be00`, file
   `0x00c8f200`, realaddr `0x11000`–`0x55cd16`). `Navi.exe` sec1/sec2 are
   **compressed data/resources** (0 executable compressed bytes, C-2128;

   modules not exhaustively scanned for families 1–2 in this pass (Navi.exe

   structure. Claim C-2210 (access-path membership) is falsified if the
   `INTER0`/`FRWAY0` id-table entries are shown unreachable by

## Observations

### 1. Precheck (C-2128 context)

`reader_precheck.py --module Navi.exe IMG256`: module `Navi.exe` 3 sections;
executable decodable **5,553,430 B**, executable compressed **0 B**; data
compressed 16,778,254 B (sec1 `realaddr 0x0055d000` vsize `0xff16ae` stored
`psize 0x457c` flags `0xc8002040`; sec2 `realaddr 0x0154f000` vsize `0xed60`
stored `0x8884` flags `0x48002040`). Literal indirect (through slot) 3560
into compressed sec1, but no executable code in compressed sections —
"not found" in decodable executable sections is a complete search of code,
not hidden bytes (subject to indirect `.data` dispatch caveat).

### 2. Volume-id table membership (shared REFER001 access path)

Raw image at `0xdf753c` contains the 8-char volume-id sequence
`ZCODE0\0\0LCTBL0\0\0INTER0\0\0FRWAY0\0\0ADDRE0\0\0POINT0\0\0...RDSTM001` (C-881).
`INTER0` = file `0xdf754c` (~VA `0x0017934c`), `FRWAY0` = file `0xdf7554`
(~VA `0x00179354`), adjacent to `ADDRE0` `0x0017935c` and `POINT0`
`0x00179364`. This is the same volume-id table `0x00179338` used by the
REFER001 family access path (C-881, C-2180).

`sh4xref --to 0x0017934c` (INTER0): pools `0x00179300`–`0x0017930c` hold
`0x0017934c` (no direct `mov.l @(disp,PC)` code load reported). `--to
0x00179354` (FRWAY0): pools `0x001792ec`–`0x001792f8` hold `0x00179354` (no
direct load reported). The pools are in the id-table/data region; access is
consistent with table-index selection (cf. `fn 0x003fbed8` selects from the
volume-id id table, C-2180/C-881) rather than a single PC-relative literal
load of the string pointer.

`INTER001.DAT` appears as a raw string at file `0xdf8140`; `FRWAY001` (no
`.DAT` suffix observed at that hit) at `0xdf83c8`. No claim is made here that
these raw-string hits are literal-loaded by reader code (they may be in
data/on-disk content regions of the image).

### 3. Shared REFER001 descriptor/name-builder anchors (confirmed, Navi.exe sec0)

- `fn 0x004125a8` (descriptor switch, C-880/C-2180): reads `u16` type at
  `r9+8`. `0x14e4` maps to `LCTBL001.DAT`/`RDSTM001` or `RDSTM001`/`0x0017a098`
  family via `jsr 0x0040b358`; **`0x14e8` maps to `REFER001` (`0x00178c68`,
  pool `0x004126c4`) + `INDEX003.DAT` (`0x0017a118`, pool `0x004126c0`) via
  `jsr 0x0040b358`** at `0x00412612/0x00412636`. INTER/FRWAY are REFER001
  family files, so file-level resolution goes through the `0x14e8`/REFER001
  path (same mechanism as POINT/ADDRE, C-2180).
- `fn 0x003fbed8` (name builder, C-881/C-2180): dispatches on object
  type/subkind (`0x14ef`/`0x14f0` checks at `0x003fbefc`/`0x003fbf18`), reads
  kind/id fields, sets `r12` to REFER001/id-table related bases (`0x00178c68`
  at `0x003fbee; pool 0x003fc0ac`, `0x001793a4` at `0x003fbf40` pool
  `0x003fc0b0`), and calls `jsr 0x0040b358` at `0x003fc084` (per C-2180/C-881
  context). The id table containing `INTER0`/`FRWAY0` is selected through
  this family mechanism.
- `fn 0x0040b358` (volume lookup, C-2180): shared 28-byte-entry lookup used by
  the descriptor/name-builder/ADDRE resolver paths.
- `fn 0x003f51e0` REFER schema/field resolver (control, C-2184/C-884/C-2651):
  `sh4xref --to 0x003f51e0` finds pool loads in `fn 0x003f56bc`, `0x003f57a8`,
  `0x003f5a98`, `0x003f5d98`, `0x003f61bc` (Navi.exe sec0) — a positive
  control that `sh4xref` finds known REFER-family field-resolution code. This
  resolver serves tagged/field-dispatched REFER records (POINT/ADDRE/RDSTM
  paths, C-884/C-2184); INTER/FRWAY's 12-byte table+blob structure is not the
  same record form.

## Interpretation

- **FACT (C-2210, access path):** `INTER0` and `FRWAY0` are present in the
  build-A REFER001 volume-id table at `0x00179338` (`INTER0` file `0xdf754c`
  / ~VA `0x0017934c`, `FRWAY0` `0xdf7554` / ~VA `0x00179354`, adjacent to
  `ADDRE0`/`POINT0`, C-881). As REFER001 family members they are resolved
  through the same family-level mechanism as POINT/ADDRE: descriptor type
  `0x14e8` in `fn 0x004125a8` maps to `REFER001`+`INDEX003.DAT` via
  `jsr 0x0040b358`; the volume-id table is selected through the `fn
  0x003fbed8`/`fn 0x0040b358` name-builder/lookup path (C-880/C-881/C-2180).
  Navi.exe carries the REFER001 map-data names (C-881). Navi.exe has **0
  compressed executable sections** (C-2128).
- **OBSERVED (negative, C-2211):** Two structural signature families derived
  from the writer's inverse of INTER/FRWAY content access — (1) 12-byte record
  scan with `u16 length` at +8 tested for `0xffff` and `add #12` stride, (2)
  explicit `0x1108` table-offset construction — found **0 candidates** in
  `Navi.exe` sec0 (5,556,224 B, the module's only decodable executable
  section). No content reader VA consuming INTER/FRWAY 12-byte table fields,
  blob 0 6-byte elements, FRWAY route-ref/blob-2 mesh-id/serial/text fields,
  or the `0xffff` terminator was identified.
- **HYPOTHESIS (C-2212):** The INTER/FRWAY content reader may (a) use a
  different instruction/register form not matching families 1–2 (e.g. computed
  offset, different displacement, loop carried by a callee), (b) be reached
  only through indirect dispatch via pointers in compressed `.data` (sec1
  literal-indirect count 3560 is a lower-bound cross-section call surface,
  but executable code remains in decodable sec0), (c) read the generic
  REFER001 container (0x1108 directory/cell layout shared with ADDRE) and
  dispatch semantically in a way not caught by the blob/table signatures, or
  (d) reside in another decodable module not exhaustively scanned for these
  families. These are unproven; (c)/(d) are constrained because C-881 places
  map-data name resolution in Navi.exe and INTER/FRWAY's 12-byte table+blob
  form differs from the `0x003f51e0` tagged field-dispatch records.
- **UNKNOWN (C-2213):** Consumed fields of the INTER 12-byte table and blob 0,
  and of FRWAY blobs 1–2 (route refs, mesh ids, serial+text) — no reader VA
  mapped, so per-field consumption cannot be attributed to firmware
  instructions. `refer.md` field meanings remain as format observations
  (C-135, M4.16c ref lead C-1811 unaligned/unresolved).

## Conclusion

M3.16's done-when ("reader VAs and consumed fields in `refer.md`") is **not
met**. Confirmed: `INTER0`/`FRWAY0` are REFER001 volume-id table members and
resolve through the shared REFER001 access path (`fn 0x004125a8` `0x14e8` →
`REFER001`+`INDEX003.DAT`, `fn 0x003fbed8`/`fn 0x0040b358`; C-880/C-881/
C-2180) in decodable Navi.exe sec0 (0 compressed executable sections,
C-2128). Not found: any content reader VA or consumed-field mapping for the
INTER/FRWAY 12-byte table / blobs after two structural writer-inverse
signature families searched Navi.exe sec0 (5.56 MB) with 0 hits. Per task
Stop rule, M3.16 is `blocked`. `refer.md` INTER/FRWAY sections record the
access-path VAs and the negative reader search; C-2210–C-2214 added.
