## Question

Can a scripted breadth-first walk from the idle screen reach at least fifteen
distinct screens on a live `-M ze0` guest by tapping the buttons found on each
screenshot, so that `docs/emulator/screens.md` can list 15 screens with path
and hash?

## Hypothesis

Yes — with the M8.C1n `--ui-start` UI bridge the consent, map and menu screens
are reachable by touch and by the documented hard keys, and their plane-1 PNG
hashes are repeatable. **Falsifier:** a dense tap grid and all documented hard
keys reach fewer than 15 distinct screen states, or two runs give different
hashes for the same path. The first condition was met.

## Method

### 1. Sample and hash

The four SHA-256 values above come from one `sha256sum` command on the four
files in the worktree (quoted verbatim in Observations O1). All PNGs, logs and
probe scripts live under the scratch directory named above.

### 2. Commands

Run from the worktree root; `$S` is the scratch directory, `$Q` the QEMU build.
A private gdb port 1270 was used: port 1240 is held by another agent's QEMU,
and the first attempt on 1240 produced
`-gdb tcp::1240: Failed to find an available port: Address already in use` in
`qemu.out` (negative control for port collision; that run yielded no numbers).

```bash
S=/home/marek/projekty/leafre-work/scratch/m8.h42-screen-catalogue
Q=/home/marek/.cache/qemu-ze0/build/qemu-system-sh4
mkdir -p "$S"
sha256sum archive/sd-images/LEAF_2011-2012_US.img \
  archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
  firmware/unit-flash/nk1-QY7200ND.bin archive/head256.img

TMPDIR=/home/marek/projekty/leafre-work/scratch/tl-tmp2 \
nohup python3 tools/ze0_launch.py --qemu "$Q" \
  --card archive/sd-images/LEAF_2011-2012_US.img \
  --flash anon --peer panel --gdb 1270 --ui-start \
  --workdir "$S/live-walk1" --timeout 2400 > "$S/launch-walk1.out" 2>&1 &
```

After `AUI Initialize Complete!!!` appears in `serial.log`, capture the consent
screen, tap the documented OK button (screen (277,382) → panel `tap 277 98`,
running.md §6), wait for `MAP_MAPOPERATION_NORMAL_MAP`, then probe:

```bash
W="$S/live-walk1"
python3 tools/ze0_screenshot.py plane --monitor "$W/mon.sock" -n 1 -o "$S/consent"
sha256sum "$S/consent"
python3 -c "import socket,sys;s=socket.socket(socket.AF_UNIX);s.connect(sys.argv[1]);s.sendall(b'tap 277 98\n');print(s.recv(200).decode())" "$W/panel.ctl"
cat "$W/uistart.log"                  # "touch unlocked" at 183.1 s
python3 tools/ze0_screenshot.py plane --monitor "$W/mon.sock" -n 1 -o "$S/map-idle"
sha256sum "$S/map-idle"

# Screen inventory (the counting command for the falsifier):
grep -a -o 'State\[[A-Z0-9_]*\]' "$W/serial.log" | sort -u
grep -a -o '[A-Z][A-Z0-9_]*::CompleteShowScreen' "$W/serial.log" | sort -u

# Probe helper: one tap, then the state-set delta and plane-1 raw/region hash.
python3 "$S/probe.py" "$W/panel.ctl" X Y NAME
```

The probe grid covered x ∈ {50,150,250,350,450,550,650,750}, y ∈
{60,70,160,260,360,440,460}, plus the documented ZOOM tap (765,70) and the
bottom AUI button band (screen rows 400–430 → panel y 50–80). Hard keys were
sent three ways: `key MENU|DEST|MAP|ENTER` on the control socket, and raw SCI3
key frames `frame 3401`, `frame 342b` (MENU raw 0x2b from keys.md §3.1),
`frame 3f2b`, `frame 36…`.

### 3. Controls

- *Positive:* the consent screen is detected (`SRT_COLD_I_AGREE_NAM`), the
  documented OK tap unlocks touch (`uistart.log` prints
  `183.1 s: … 00f1 -> 0000 (touch unlocked)`), the map screen appears
  (`MAP_MAPOPERATION_NORMAL_MAP`), and the documented ZOOM tap logs one
  `ZOOM ILL EVENT` (grep count 1). The first-touch and screen-transition path
  of H39 is therefore reproduced.
- *Negative, port collision:* the 1240 attempt produced the "address already
  in use" line in `qemu.out` and no `touch unlocked`; no numbers from it.
- *Negative, key frames:* after `key NAME` and `frame 34/3f/36…`, the count of
  `byCmd(0x` lines in `serial.log` is 0 and no new `State[…]` appears — keys
  do not drive the UI in this build.
- *Negative, falsifier:* the inventory command prints 5 distinct screens, far
  below the 15 the Done when requires.

### 4. Scope

One live L4 boot of NK1 + ROM A from the US card, anonymous flash, one panel
peer and the M8.C1n UI bridge; two rapid plan-attempt boots that were killed
before measurement (no numbers used); a 40-minute observation window. The
walk covered consent → map and the map scroll/zoom sub-states. Excluded: any
AUI menu screen that requires a rendered, keyed-out button the peer cannot
press; GPS, routing and generated cards; other cards; L3/L5 and any commit of
vendor screenshots. The screen view is DU plane 1 (`plane -n 1`), not the
keyed composited `screen` (C1t O6).

### 5. Falsifier

Stated before the result (Hypothesis): fewer than 15 distinct screen states
after a dense tap sweep and all documented hard keys refutes the hypothesis.
That falsifier fired — see O3/O4.

## Interpretation

- **FACT:** The L4 setup works: consent renders with the H39 hash, the documented
  OK tap unlocks touch, the map renders and the ZOOM tap fires one `ZOOM ILL
  EVENT`. Rule 13 level L4 for the input/render path.
- **FACT:** Only 5 distinct screen states are reachable by the scripted walk
  (`O3`), 10 fewer than the 15 the Done when requires. The falsifier fired.
- **OBSERVED:** Hard-key injection (`key NAME`, raw `frame 34/3f/36…`) produces
  no key-receive log line and no screen change; the documented AUI menu buttons
  are keyed out of the composited view (C1t O6) and their tap locations did not
  fire a screen transition.
- **HYPOTHESIS:** Reaching the menu tree needs either a working hard-key frame
  grammar (M8.H35 incomplete) or the 2DG blit that makes the AUI buttons opaque
  (M8.C1v); neither exists in this build. Not verified here.
- **UNKNOWN:** Whether any other input path (e.g. a carCAN `PUSH_SW`, or a
  debugger-driven `ScreenStateCC` event) can reach the 15+ menu screens; out of
  scope for this tooling-only task.

## Conclusion

M8.H42 is **blocked**: the scripted walk reaches 5 screens, not the 15 required.
No `docs/emulator/screens.md` catalogue with 15 paths/hashes can be produced
honestly on this build. The unblock is M8.C1v (render the AUI buttons opaque so
they can be tapped) and/or an L4-verified hard-key injection path; a task that
adds those must re-open M8.H42. This is a negative result with a positive
control (the consent→map path), so it is a result, not an absence of one.
