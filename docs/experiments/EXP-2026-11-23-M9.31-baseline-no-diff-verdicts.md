## Question

Can a no-diff card/factory pair earn explicit firmware `pass`/`fail` rows from a
documented baseline corpus, without fabricating a pass when no firmware ran?

## Hypothesis

Yes for the two runnable baselines already evidenced: M9.11 `cmp_ind` on a
factory POINT010 `.cmp/.ind` pair and M9.6 `applaunch_mapcode_compare` on a
factory `HDD_INFO.TXT` with `--unit-from` the same file. Plain `--card` is
unchanged (`NO_DIFFS`, exit 3). Falsifier below.

## Interpretation

- **FACT:** With a documented identical fixture, `--baseline` produces explicit
  `pass` rows from real firmware runs (EU2011 `r0=42848`/`insns=1957314` and
  `r0=1`/`insns=1905`), `pass=2`, exit 0. The M9.12 gap ("S0/S1 all pass" with no
  runnable verdict) is closed for a no-diff pair: the gate no longer has to report
  bare `NO_DIFFS` when a runnable baseline applies.
- **FACT:** A runner status `DRY_RUN` with exit 0, `SKIP`, `BLOCKED`, a missing
  input/head/runner or a build mismatch is `not-yet-available`; the selftest
  injects these and asserts zero pass rows and exit 3. Only a real firmware
  `r0`/`insns` pays for a `pass`. MISMATCH/FAIL/INVALID is a `fail` (exit 1).
- **FACT:** Build pairing is enforced from the card image's first 96 MiB: the US
  card with the EU baseline dir reports two build-mismatch rows and exit 3, never
  an EU-fn verdict on a US card (navigator fix 1).
- **FACT:** Plain `--card` is unchanged (`NO_DIFFS`, exit 3); the new mode is
  opt-in, so no existing gate semantics move.
- **OBSERVED:** The two safe baselines use EU2011 VAs `0x0041c7dc` and
  `0x03bd2ad8`, both already in the frozen fn_audit corpora. The US S1/S2 images
  of M9.12 need the US target registrations/frozen VAs (M9.55 `point_walk_us2011`,
  M9.11b `cmp_ind_reader_us2011`) before the same command yields US-baseline
  passes; no US VA was cited and no snapshot was regenerated.
- **HYPOTHESIS:** M9.12 can cite this path as its S0/S1 unblock: once US VAs are
  frozen, the same `--baseline` mechanism on the US factory yields runnable rows.
- **UNKNOWN:** These are L3 firmware-fragment verdicts (rule 13), not full-card
  acceptance; no L4/L5 run is implied.
- **OBSERVED (residual, not in M9.31 files):** a whole-tree `selftest.py` run is
  red on this host for two unrelated reasons. The re-run
  `python3 tools/selftest.py --only fn_audit_l3_image` prints
  `CORPUS STALE: DOCS BASE: 1 new / 0 gone / 0 moved` with
  `DOCS BASE new TODO.md:0x0041f3dc fn` and
  `CORPUS STALE: L3 OVERLAY: 7 new / 0 gone / 0 moved` with
  `L3 OVERLAY new TODO.md:0x0041f3dc fn`,
  `EXP-2026-11-22-M6.19-unit-flash-map.md:0x880485d4 fn` (twice),
  `…:0x88048724 fn`, and
  `EXP-2026-11-23-M8.H73-receiver-fix-frame.md:0x039e5290 fn`,
  `…:0x039e55b0 fn` (twice). These VAs arrived on `origin/main` after the first
  rebase; they are printed here only as diagnostics, **not used as evidence** by
  this EXP, which uses only the frozen `0x0041c7dc` and `0x03bd2ad8`. Other tools
  intermittently fail with `OSError: [Errno 122] Disk quota exceeded` on the
