## Question

Which chip and register map does the build-B `serial_uat.dll` driver use for
`UAT3:`/`UAT4:`, and can QEMU's `serial-mm` model it as-is?

## Hypothesis

The driver's four P4 base literals map to classic 16550 registers; if so, the
access width and stride decide whether `serial-mm` fits. **Falsifier (task):**
the driver touches no address in `0x19b00000`–`0x19e00000`, in which case the
hardware map is wrong. **Second falsifier:** a 16550-looking layout that is
actually 8-bit at 1-byte stride would make the "u16 shim" recommendation
wrong.

   Baud tables were read as eight u32 pairs at the file offsets that
   `cerom.py va2file` gives for `0x039a1590`, `0x039a15d0`, `0x039a1970` (all
   in plain sec0, so VA minus section realaddr plus file offset applies).
3. **Controls.** *Positive:* `cerom.py modules` finds the module and `exports`
   lists 10 `UAT_*` entrypoints; `ze0_regs.py who` attributes all nine base
   literals to `serial_uat.dll` (a known-present module). *Negative:*
   `va_class.py` classifies all five hardware VAs as `OUTSIDE no section`
   (they must not be mistaken for compressed `.data`); `nk_decomp.py pdata`
   classifies `0x039a48dc` as a `GAP` and `0x039a4a70` as `INSIDE fn
   0x039a4a4c`, so the naked register-builder fragment is not cited as a
   function start.
4. **Scope.** Build B only; sec0 (`0x80a2` B, plain) for register code, the
   decoded `default.hv` for registry values. Excluded: sec1 IAT semantics
   beyond the named stubs, the kernel OAL ISR table (47 rows at `0x88005bc8`,
   no static attribution), compressed sec2 (only `.pdata`), and any runtime
   behaviour. No image C or other builds.
5. **Falsifier.** A base literal that `ze0_regs.py who` attributes to another
   module, or an accessor calling an 8-bit port primitive, would refute the
   map or the u16 verdict.

## Interpretation

- **FACT:** UAT3 is `0x19b00000`, UAT4 is `0x19e00000`; indices 0/1 map
  `0x19d/0x19c00000` but are unused by the registry (O3–O5).
- **FACT:** the register block has eight classic 16550 positions at even
  offsets plus two vendor registers; all accesses are `READ/WRITE_PORT_USHORT`
  (O2, O6, O7).
- **FACT:** DLAB divisor sequencing and two 24/48 MHz baud tables exist;
  230400 is in the 48 MHz table (O7, O8).
- **OBSERVED:** FCR shadow `&0xfff9` and watermark 64/8 (O5, O7).
- **HYPOTHESIS:** the 24/48 MHz clock reading and the recommendation for a
  dedicated `uat-mm` model; no QEMU code was written here.
- **UNKNOWN:** SYSINTR/INTEVT, `+0x1a`/`+0x1c`, FCR trigger bits, boot-time
  table selection, parity/stop/word length.
