## Question

Can we give M5.11/M5.15 and card builders an offline, L2-adjacent verdict for the two known AppLaunch HDD_INFO acceptance checks (M2.5 `DIFFERENT MAP CODE`, M2.15 `MAP DATA BASE UNMATCH`) on a candidate `HDD_INFO.TXT`, while **never** emitting a pass/`ACCEPT` verdict when the required unit target-info inputs (`+0x60`, `+112/+114`) are not explicitly stated?

## Hypothesis

The M2.15 model already pins the card-side bytes and comparison logic (C-2080–C-2084). A strict predictor can enforce `ACCEPT` only when both checks pass against explicitly stated unit inputs; otherwise it returns `BOUNDS_UNKNOWN` or the failing check, never a pass. **Falsifier:** the predictor emits `ACCEPT` or exit code `0` when `--target-line1` and/or `--mapdbver-min`/`--mapdbver-max` are missing; or the 89-variant check1/check2 per-check counts differ from the recorded M2.15 evidence (check1 69 PASS/20 `DIFFERENT MAP CODE`, check2 89 `BOUNDS_UNKNOWN` without bounds) without an evidence-backed explanation; or `hddinfo.py --selftest` regresses.

## Method

1. **Sample and hash.** No vendor HDD_INFO bytes committed. Factory EU 2011 base provenance recorded as SHA-256 `9f014643ed9f4e1359d418f415f264f943e027669b872fc7675f3d99d9bc650a` (72 bytes, not in repo, C-2086/EXP-M2.15). IMG256 context `92aa525d…`. Derived 89-row table committed without variant/base contents.

2. **Commands** (runnable as written from repo root with a caller-supplied base outside the repo for table generation; selftest/candidate predict run without vendor data):
```bash
python3 tools/hddinfo.py --selftest
# Strict predictor (M5.11-callable) on a single candidate HDD_INFO.TXT:
# ACCEPT (exit 0) ONLY when explicit --target-line1 AND --mapdbver-min/--mapdbver-max
# are supplied and both checks pass. Missing inputs => BOUNDS_UNKNOWN, exit 1 (never pass).
python3 tools/hddinfo.py predict CANDIDATE_HDD_INFO.TXT --target-line1 "QSD-302-100" --target-line1-provenance "caller-stated explicit proxy/input" --mapdbver-min 16 --mapdbver-max 16 --json
python3 tools/hddinfo.py predict CANDIDATE_HDD_INFO.TXT --json   # expect verdict BOUNDS_UNKNOWN, exit 1
# 89-row derived table (base is caller-supplied outside repo; --sweep 0-5, permutations on):
python3 tools/hddinfo_variants.py BASE_OUTSIDE_REPO/HDD_INFO.TXT /tmp/m2.18-vars --sweep 0-5
python3 tools/hddinfo.py predict-table BASE_OUTSIDE_REPO/HDD_INFO.TXT --variants-dir /tmp/m2.18-vars --target-line1 "QSD-302-100" --target-line1-provenance "factory EU 2011 base line 1 as explicit proxy for unit target-info +0x60 (caller-supplied; per-unit +0x60 unknown statically, C-2087)" --base-provenance "sha256=9f014643ed9f4e1359d418f415f264f943e027669b872fc7675f3d99d9bc650a (factory EU 2011 HDD_INFO.TXT, 72B, not in repo, C-2086/EXP-M2.15)" --format tsv --out docs/experiments/EXP-2026-11-09-M2.18-hddinfo-predictor-variants.tsv
python3 tools/selftest.py
python3 tools/claims_check.py
```

3. **Controls.** Positive: `predict` with explicit `--target-line1` equal to candidate line 1 and explicit bounds containing extracted MapDBVer => `ACCEPT`, exit 0 (selftest). Negative per check: explicit `--target-line1` mismatching line 1 => `DIFFERENT MAP CODE`, exit 1; explicit bounds excluding MapDBVer => `MAP DATA BASE UNMATCH`, exit 1 (selftest). **Unknown-never-pass:** missing `--target-line1` and/or missing `--mapdbver-min`/`--mapdbver-max` => `BOUNDS_UNKNOWN`, `accepted=false`, exit 1 (never `ACCEPT`/exit 0), including the case where check 1 would pass but bounds are unknown (selftest). Corpus sanity/controls: check1 69 PASS / 20 `DIFFERENT MAP CODE`, check2 89 `BOUNDS_UNKNOWN` (no bounds supplied), overall 69 `BOUNDS_UNKNOWN` / 20 `DIFFERENT MAP CODE` under strict predictor (no bounds => never `ACCEPT`); MapDBVer change set/values match C-2086 patterns (see Observations). Regression: `hddinfo.py --selftest` retains M2.15 controls (C-2085) and adds M2.18 strict controls.

4. **Scope.** Corpus: 89 HDD_INFO variant files (`*.HDD_INFO.TXT`) generated with `hddinfo_variants.py --sweep 0-5` (permutations enabled), each 72 bytes, from the factory EU 2011 base provenance above. Covered: AppLaunch check 1 (line 1 bytes 0–10, 11 bytes) and check 2 (line 3 pos 5,6,7 MapDBVer extraction/range model) only, per C-2080–C-2084. Excluded: firmware execution, `KernelIoControl(0x0101302C)` runtime, real per-unit `+0x60`/+112/+114 values (C-2087, unknown statically), behaviors beyond the two modeled checks, end-to-end unit/hardware acceptance, and any path using `0x06000000` (ruled out for these checks, C-766/C-783).

5. **Falsifier.** Any `ACCEPT` verdict or exit code `0` from `predict`/`predict-table` strict gate when `--target-line1` or `--mapdbver-min`/`--mapdbver-max` is missing; check1 corpus count not 69/20 or check2 not 89 `BOUNDS_UNKNOWN` without explained evidence-backed reason; vendor HDD_INFO bytes/variant contents committed; `python3 tools/hddinfo.py --selftest` not OK.

## Observations

Raw results (derived; no vendor contents):

- `python3 tools/hddinfo.py --selftest`: **OK (62 checks)** (M2.15 controls retained + M2.18 strict predictor controls: explicit-input ACCEPT exit 0; check1/check2 fail exit 1; missing target/bounds/no-input => `BOUNDS_UNKNOWN`, `accepted=false`, exit 1; check1 pass + bounds unknown => overall `BOUNDS_UNKNOWN`, never `ACCEPT`).
- `predict` interface (M5.11-callable, single candidate): `hddinfo.py predict CANDIDATE_HDD_INFO.TXT --target-line1 ... --target-line1-provenance ... --mapdbver-min N --mapdbver-max N [--json]`. Exit: `0` only for `ACCEPT`; `1` for any non-`ACCEPT` (including `BOUNDS_UNKNOWN`, `DIFFERENT MAP CODE`, `MAP DATA BASE UNMATCH`); `2` usage/parse error. `--target-line1` is an explicit caller-supplied input/proxy (provenance recorded); never labeled “factory value” by the tool. `--mapdbver-min`/`--mapdbver-max` required together for a bounds-evaluated check 2.
- 89-variant derived table (`EXP-2026-11-09-M2.18-hddinfo-predictor-variants.tsv`): `variant_count=89`, base SHA-256 `9f014643…c650a` (72B, not in repo), `--sweep 0-5`, permutations on. Explicit `--target-line1` = `QSD-302-100` supplied as caller-stated proxy/provenance; **no** `--mapdbver-min`/`--mapdbver-max` (bounds unknown, C-2087). Counts:
  - `check1_counts`: `{'PASS': 69, 'DIFFERENT MAP CODE': 20}` (matches C-2086).
  - `check2_counts`: `{'BOUNDS_UNKNOWN': 89}` (matches C-2086).
  - `overall_counts` (strict M2.18 gate, no bounds => never `ACCEPT`): `{'BOUNDS_UNKNOWN': 69, 'DIFFERENT MAP CODE': 20}`.
  - Ref MapDBVer `0x010` (16). **12 variant files** change MapDBVer (values/identities match C-2086 patterns): `line3_digits_3_000000..000005`→`0x000` (6 files; check1 PASS), `reverse`→`0x0e0` (check1 `DIFFERENT MAP CODE`), `swap_1_3`→`0x020` (check1 `DIFFERENT MAP CODE`), `swap_2_3`→`0x090` (check1 PASS), `swap_3_4`→`0x0e0` (check1 PASS), `swap_3_5`→`0x000` (check1 PASS), `swap_3_6`→`0x350` (check1 PASS). C-2086 states “10 variants change MapDBVer” but enumerates the `line3_digits_3_*` pattern that expands to 6 files; the hex outcomes and check1 statuses match C-2086 exactly. This is a **count clarification** (12 files), not a verdict/value mismatch; primary sanity counts (check1 69/20, check2 89 `BOUNDS_UNKNOWN`) match C-2086.

## Interpretation

- **FACT (tool/controls):** `tools/hddinfo.py predict` implements the M2.18 strict contract and is covered by `--selftest` (62 checks): `ACCEPT`/exit 0 only with explicit `--target-line1` and explicit `--mapdbver-min`/`--mapdbver-max` and both checks passing; missing either input => `BOUNDS_UNKNOWN`, never `ACCEPT`, exit 1. M2.15 `classify`/`matrix` behavior remains intact (selftest retains M2.15 controls, C-2085).
- **FACT (derived corpus, per-check):** on the 89-variant factory EU 2011 corpus (`--sweep 0-5`, SHA `9f014643…` provenance), check 1 is 69 PASS / 20 `DIFFERENT MAP CODE` and check 2 is 89 `BOUNDS_UNKNOWN` without unit bounds, matching C-2086. The MapDBVer-changing variants have the values/statuses listed in C-2086 (12 files total due to 6 `line3_digits_3_*` expansions).
- **OBSERVED/OPEN:** per-unit `+0x60`/+112/+114 are unknown statically (C-2087). Therefore no offline run without those explicit inputs can produce a firmware-valid `ACCEPT`; the predictor correctly returns `BOUNDS_UNKNOWN`.
- **UNKNOWN:** actual unit target-info values per market/unit; any acceptance behavior outside the two modeled checks.

## Conclusion

M2.18 adds `hddinfo.py predict` / `predict-table`, a strict L2-adjacent pre-L3 gate: it classifies a candidate `HDD_INFO.TXT` as `ACCEPT`/`DIFFERENT MAP CODE`/`MAP DATA BASE UNMATCH`/`BOUNDS_UNKNOWN` and **never** emits `ACCEPT`/exit-0 without explicitly stated unit inputs (`--target-line1` for `+0x60`, `--mapdbver-min`/`--mapdbver-max` for `+112/+114`). M5.11 can call `hddinfo.py predict <candidate> ... [--json]` and gate on exit code 0 = `ACCEPT` only. The committed 89-row derived table (no vendor bytes) reproduces M2.15 per-check sanity counts (check1 69/20, check2 89 `BOUNDS_UNKNOWN`, MapDBVer values matching C-2086; 12 change files clarified from the `line3_digits_3_*` expansion). **Verdicts still requiring M9.6/M2.4 (rule 13):** every `ACCEPT`/failure here is an offline model only — firmware execution of the AppLaunch compare/range (M9.6 when runnable), M2.4 firmware verdicts, the real per-unit `KernelIoControl(0x0101302C)` `+0x60`/+112/+114 values, parse/cache/runtime behaviors beyond the modeled checks, and end-to-end unit/hardware acceptance are **not** replaced by this predictor.
