## Question

Can the per-record length/offset directory behind the `RDSTM001` framing drift
(C-884) be reproduced from bytes, so that real TMC records can be split into
fields and placed on the map (M4.16b done-when: at least 20 records mapped to
tile/mesh/coordinates, a named join key and a random-key control near 0)?

## Hypothesis

The directory is implemented by a small set of Navi.exe functions in an
uncompressed section, so an offline walk is possible. Falsifier: the functions
are in a compressed section, or the walk cannot be reproduced on the EU and US
files with the decoder in `tools/`. The record-to-coordinate join is a separate
claim; falsifier for it is any join key that reaches the random-key control.

   The module attribution of each VA was read from `/tmp/memmap.json`

3. **Controls.** *Positive*: the `va2file` of `0x003f61bc` must fall in the

   `0x003f57a8`, `0x003f5e10`). *Negative*: a naive section-range query on the memmap

   va2file`, not a bare range match. The decoder

4. **Scope.** Five functions of Navi.exe, disassembled for up to 160
   halfwords each (each function ends at its `rts`, so the tail is literal pool

5. **Falsifier.** A walk that reproduces the record boundaries on both files,
   with a shifted-start control collapsing to about 0 %, would support the
   directory model. Any of the five functions being in a compressed section
   would close the static route.

## Observations

Attribution (`cerom.py`, positive control passed):

- `va2file`: `0x003f61bc → 0x010743bc`, `0x003f5e10 → 0x01074010`,
  `0x003f51e0 → 0x010733e0`, `0x003f56bc → 0x010738bc`, `0x003f5d98 → 0x01073f98`.
  All lie inside `Navi.exe` `sec0` (plain, `r-x`).
- A naive range query over the memmap also matches `Telema.exe` `sec1`
  (compressed, `rw-`, `va 0x11c000`). This is a caution, not a second location:
  `va2file` resolves the Navi.exe section.

Call graph (`sh4xref.py --calls 0x003f61bc`):

- `jsr @r3` to `0x003f51e0`, `0x003f56bc`, `0x003f57a8`, `0x003f5e10`; `rts` at `0x003f620a`.

Decoder coverage (`sh4dis --va … --count 160`, halfwords shown as `.word`):

- `0x003f61bc`: 12 `.word` (all `0x003f` literal-pool words after `rts`).
- `0x003f51e0`: 3 `.word`, of which `0x0029` (MOVT r0) and `0x014a` are code gaps.
- `0x003f56bc`: 6 `.word`: `0x431d` at `0x003f56fe` (SHLD r1,r3) and `0x423d` at
  `0x003f5746` (SHLD r3,r2) are code gaps; the rest are pool/after-rts.
- `0x003f5d98`: 11 `.word`, mostly `0x003f` pool words.
- `0x003f5e10`: 14 `.word`; `0x0329` (MOVT r3) at `0x003f5e1a` and `0x4221`
  (SHAR r2) at `0x003f5e1e` are code gaps.
- Across the five functions the distinct `.word` values are `0x003f` (30),
  `0x8a0c`, `0x8a90`, `0x8a5c`, `0xc000`, `0x0000` (pool or after-rts; not
  classified), and the code gaps listed above.

Schema lookup `0x003f51e0`: it loads a global descriptor pointer from
`0x00d53500` and compares the requested kind (`r8`) against fields at offsets
`+12, +20, …, +60, +64, +68, +96` of the descriptor, then follows a pointer. The
table at `0x00d53500` was not dumped.

RDSTM copies: the EU file has the M4.15 hash `f822044c…`; the US file has
`921d9cd4…` and is 1,894,144 bytes larger.

Walk: **not run.** No record boundary was computed from the directory, so there
is no per-record positive or negative control result.

## Interpretation

- **FACT (VERIFIED):** the five C-884 functions are plain code in Navi.exe `sec0`,
  attributed through `cerom.py`, and `0x003f61bc` calls the four functions named
  above. So the static route is open, not closed.
- **OBSERVED:** `sh4dis.py` has no opcode entries for MOVT (`0x0n29`), SHAR
  (`0x4n21`) and SHLD (`0x4n0d`) and SHAD (`0x4n0c`). These appear as real code in
  the length-walk and accumulator functions. An offline walk cannot be run
  faithfully until they are decoded. The decoder change is not part of this task.
- **OBSERVED:** the schema table `0x00d53500` is not decoded, so the field
  lengths that the walk consumes are unknown.
- **UNKNOWN:** whether the directory yields record starts that line up with
  the 10 clean 16-byte rows at `0x1000` (M4.15) or a later stream start.
- **HYPOTHESIS:** the field-to-coordinate path runs through the TMC location table
  (M4.16d), not through the raw record bytes. The decoded twelve fields
  (`docs/format/rdstm.md`, "Record fields") are location, road-name, area and
  attribute codes with no coordinate field, so a join key cannot come from the
  record fields alone.

Done-when: **not met.** No records were mapped, no join key was named, and no
random-key control was run. Per the block, status is `blocked`, not `done`.

## Conclusion

No change to the verified format. `docs/format/rdstm.md` and
`docs/research/claims.md` (C-2300–C-2309) record the gate and the decoder gap. The
M4.16b block is set to `blocked`. Follow-up: `M1.11c` (sh4dis opcode coverage for
MOVT, SHAR, SHLD, SHAD) and then a directory walk task. The join question remains
with M4.16d.
