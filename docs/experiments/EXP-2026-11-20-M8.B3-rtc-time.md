# EXP-2026-11-20-M8.B3 — RTC/time: the EU2011 kernel's date is a software clock seeded from its own data

- **Status:** done

- **Tools:** QEMU **8.2.10** binary `qemu-system-sh4.b1` of

## Question

Does the EU2011 kernel read a hardware real-time clock, and is the date it
sees under `-M ze0` deterministic?

## Done-when (made concrete for this run)

The TODO line "*Done when* the date read is deterministic" is vague, so the
block now says (written before the runs below): `OEMGetRealTime` is located
(EU2011 VA) and every input it reads is named; it reads no hardware
register, or the register is modelled; two or more `-M ze0` runs give the
identical date; plus a positive control (`OEMSetRealTime` with a valid date
is read back) and a negative control (an invalid date is refused).

## Hypothesis

The ZE0 OAL keeps time in software (no RTC block at `0xffe80000` is touched
as an RTC: the only accesses there are `+0x04`/`+0x08` in the ISR
`fn 0x8803fbcc`, INTEVT `0x780`). Then the date is a pure function of RAM
that the kernel itself initialises, and `-M ze0` needs no RTC model.
**Falsifier:** `OEMGetRealTime` loads an MMIO address (P2/P4 literal or a
pointer the OAL fills with one), or two identical boots show different
dates, or the kernel never calls it (then "the date read" is untested).

### Controls

- **Positive:** `rtc-set` must read back 2011-03-15 10:20:30 with
  `OEMSetRealTime` returning 1, and `wDayOfWeek` = 2 (2011-03-15 was a
  Tuesday), proving the decoder and the shim drive the real functions.
- **Negative 1:** `rtc-bad` (month 13) must return 0 and leave the date
  unchanged.
- **Negative 2:** without the kernel loaded the shim must not produce a
  sample (the done marker is missing).
- **Negative 3:** `initdate` on image A (not `nk.exe`) must refuse;
  `ramdate` on a log without the dump must refuse.

### Scope (counted corpus)

`nk.exe` EU2011 only. `OEMGetRealTime` body: 124 instructions
`0x880400a8..0x8804019e`, 16 distinct literal-pool words. Callers: 6
functions → `0x880400a8`, 2 → `0x880401e0` (`sh4xref`). Writers of the date
words: 1 site per word outside `OEMGetRealTime`. Runs: 5 + 1 + 1 + 1 shim
runs, 3 traced boots (75 s, 75 s, 40 s), 2 RAM-dump boots.

### Falsifier

Stated in Hypothesis: an MMIO load in `OEMGetRealTime`, differing dates
across identical boots, or no call at all.

## Observations

### Static

`OEMGetRealTime` (`fn 0x880400a8`) literal pool (all 16 words):

```text
0x89e41888 CurMSec    0x89e61390 base tick   0x89e61394 second
0x89e43088 minute     0x89e4308c hour        0x89e43090 day (x3)
0x89e43094 month (x3) 0x89e43098 year (x3)
0x000003e8 1000       0x10624dd3 /1000       0x88888889 /60
0x91a2b3c5 /3600      0xc22e4507 /86400
0x8803fff8 (x2) day-of-week helper   0x88040c18 (x4) helper   0x8803fec4 helper
```

No literal is a P2/P3/P4 address and no register is loaded from a
pointer the OAL fills: elapsed = (`CurMSec` − base)/1000 is added to the
stored second, carried into minute/hour/day/month/year, written to the
caller's SYSTEMTIME (`wMilliseconds` = 0, `wDayOfWeek` from
`0x8803fff8`), return 1.

`OEMSetRealTime` (`0x880401e0`) checks year `0x641..0x270f` (1601..9999),
month 1..12, day 1..31, hour ≤ 23, minute and second ≤ 59, stores the six
words and sets base = `CurMSec`; it returns 0 on a bad field.

`sh4xref`: callers of `0x880400a8` — `fn 0x880149a0`, `fn 0x8801ba24`,
`fn 0x880220a4` (syscall stub), `fn 0x8804028c`, `fn 0x880453b0`,
`fn 0x8804cc34` (AER report, "Exception Occured Date & Time(GMT)"); callers
of `0x880401e0` — `fn 0x880220dc` (syscall stub), `fn 0x8804028c`. The
date words and `0x89e61390/94` are loaded only in `fn 0x880400a8` and in
the `0x880401e0` body (sh4xref files the latter under `fn 0x880401a2`,
"pdata gap").

`initdate` (copy entries from the ROMHDR at pTOC `0x884e22f0`):

```text
copy entry: src 0x88598000 -> dest 0x89e42000 copylen 0x6790 destlen 0x2f1e0
copy entry: src 0x882ffb88 -> dest 0x89e72000 copylen 0x442 destlen 0x4e4
initial date words (EU2011 0x89e43088..0x89e43098, second 0x89e61394): 2009-07-10 07:10:00
```

The five date words are initialised data (ROM `0x88599088`, inside the
copied part); the second word `0x89e61394` is in the zero-filled tail.
Image A: `initdate: a date word is outside every copy entry` (rc 1).

### Synthetic shim

```text
g1..g5    wYear=0 wMonth=0 wDayOfWeek=1 wDay=0 wHour=0 wMinute=0 wSecond=0 wMilliseconds=0  (set word 0xdeadbeef = not called)
rtc-set   wYear=2011 wMonth=3 wDayOfWeek=2 wDay=15 wHour=10 wMinute=20 wSecond=30 wMilliseconds=0  result 0x00000001
rtc-bad   wYear=0 wMonth=0 wDayOfWeek=1 wDay=0 ... wMilliseconds=0                          result 0x00000000
nokernel  decode: no xp line for the SYSTEMTIME buffer, or OEMGetRealTime had not returned  (rc 1)
```

The shim skips the kernel's copy step, so it reads the zero RAM — identical
in all five runs. An earlier version without the done marker once read
`wDayOfWeek=0` (a dump taken before the function had finished); with the
marker no sample is accepted unless the call has returned.

### Real kernel

```text
boot60-rtc.log:      1 translated block, at 0x880400a8; 0x880401e0 never translated
boot60-rtc-cpu.log:  63 x pc=0x880400a8, 63 x pr=0x880453ca
boot-rtc-ret.log:    63 x pc=0x880453ca r0=1 (OEMGetRealTime), 63 x pc=0x880453d8 r0=1,
                     92 x pc=0x88045416 (fn 0x880453b0 exit; includes the early-out path)
boot-ram1.log:       RAM date words: 2009-07-10 07:10:00
boot-ram2.log:       RAM date words: 2009-07-10 07:10:00
g1.log (ramdate):    ramdate: no xp /5wx 0x09e43088 line  (rc 1)
```

The 63 calls happen in the first seconds (the 40 s run counts the same
63). `fn 0x880453b0` passes the SYSTEMTIME to the function pointer at
`[0x89e6ad58]`, subtracts `0x019db1ded53e8000` (the FILETIME of
1970-01-01) and divides by `0x00989680` (10^7) through `0x88040cd0`: it
returns Unix seconds. At 5 s and 30 s `CurMSec` read `0x78` and `0x9e`, so
under the current model (M8.B2 open) the kernel's clock stays at
2009-07-10 07:10:00.

## Interpretation

- **FACT (C-1330):** EU2011 `OEMGetRealTime` (`fn 0x880400a8`) is a software
  clock over six RAM words plus `CurMSec`; it reads no hardware register.
  `OEMSetRealTime` (`0x880401e0`) range-checks and stores. The falsifier
  (an MMIO load) did not fire.
- **FACT (C-1331):** the date words are initialised data of `nk.exe` (copy
  entry 0, ROM `0x88599088` → `0x89e43088`); the build's power-on date is
  **2009-07-10 07:10:00**, and two boots read exactly that.
- **OBSERVED (C-1332):** driving the real functions from a shim gives the
  identical result in 5/5 runs; set/get round-trips a valid date (positive
  control, day-of-week right) and refuses month 13 (negative control).
- **OBSERVED + INFERENCE (C-1333):** during boot the kernel calls
  `OEMGetRealTime` 63 times, all from `fn 0x880453b0`, which converts the
  result to Unix seconds (INFERENCE from the constants); `OEMSetRealTime`
  is not called in 75 s.
- **Consequence for the model:** nothing to add to `-M ze0` for time. The
  date the kernel sees is deterministic by construction; it moves only
  with `CurMSec` (M8.B2). Setting a different date needs a guest write to
  the words or a call of `OEMSetRealTime`, not a QEMU RTC.
- **UNKNOWN:** whether a later stage (filesys/GPS, after M8.B5) calls
  `SetSystemTime`; what the INTEVT `0x780` ISR at `0xffe80000` serves.

## Conclusion

Done-when met: the date read is deterministic (2009-07-10 07:10:00 at
boot, identical across runs), every input of `OEMGetRealTime` is named and
none is hardware, with one positive and three negative controls. No QEMU
patch; new tool `tools/ze0_rtc.py`.
