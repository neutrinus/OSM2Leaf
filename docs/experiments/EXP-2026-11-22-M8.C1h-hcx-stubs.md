## Question

M8.C1g stopped because image A's controls import `HCXLog.dll` and
`HCXMemory.dll`. These DLLs live in the unit's flash, not on the card. What
do the importers expect from them? With stubs in place, does AuiApp draw its
first form?

## Hypothesis

Both DLLs are small service libraries. Stubs written from the call sites
let the controls load, and `ctl_PRCOM_System` then initialises. The first
form then draws. Falsifier from the task: with the stubs loaded,
`ctl_PRCOM_System` still returns `80020003`.

## Method

**Census.** For every image A module that imports either DLL, a script did
the following:

1. Mapped each import slot to its run-time address. The IAT sits in a
   data section whose `realaddr` differs from `vbase + rva`. For example,
   SystemCC's slot `0x02a8b264` is read at `0x01cd8264`.
2. Found the import thunks (`mov.l @(pc),r0; mov.l @r0,r0; jmp @r0`)
   that jump through those addresses.
3. Collected every `jsr` or `bsr` that reaches a thunk, plus the vtable
   words that hold one.
4. At each site, read the argument registers set before the call and how
   `r0` is used after it.

The script lives in the scratch area. Its output is summarised in O1–O3.

**Stubs.** `ze0_stubdll.py` builds one ROM module per DLL and
`ze0_ipl.py patch --stub-dlls hcx` appends them to image A's TOC:

- Each module is a one-page code section with an export directory (by
  ordinal), plus `e32_rom`/`o32_rom` records.
- The pages reuse the ROM pages of `gwes.exe` in image A. The kernel copy
  of `gwes.exe` runs, so image A's copy is dropped and its pages are free.
- The code VAs are free 64 KiB windows in the ROM DLL code space
  (`0x036d0000`, `0x036e0000`).

**Runs.**

| run | IPL patch file |
| --- | --- |
| H1 | `ze0_ipl.py patch --prefer-app auiapp.exe,auirtdll.dll --stub-dlls hcx` + `ze0_aui.py --no-aui-timeout` |
| H2 | H1 + `ze0_aui.py --start-form frm_PRAGR_AgreeCaution` |

Both runs used the M8.C1g command line. H1 ran for 18 minutes; H2 was

| --- | --- | --- | --- | --- |

| HCXLog | 6 | 89 | `this`; in scalar deleting destructors | base-class destructor |
| HCXLog | 1 | 67 | `this + 44` in control destructors | destructor of a member |

| HCXMemory | 9–19 | 2–12 | only `ScreenState.dll`/`ScreenStateCC.dll` | not read |

Two examples:

- CddaCC builds a shared object (vtable named `CddaSharedMem`), takes a
  26 284-byte block with #23 and zeroes it on first use.
- SystemCC keeps a table of 47 window handles (188 bytes) in a #23 block.
  It fetches the block again on every update under #5/#4, so #23 must
  return the same block for the same name.

**O2 — Stub semantics.** Every ordinal is `return this` (`rts; mov r4,r0`),
which serves the constructors, destructors, lock (non-zero) and unlock.
#23 is the exception. It widens the ASCII name and returns
`MapViewOfFile(CreateFileMappingW(-1, 0, PAGE_READWRITE, 0, size, name),
FILE_MAP_ALL_ACCESS, 0, 0, 0)`. That gives a zeroed block that is the same
for the same name in every process. The stubs never write the object,
because the derived classes keep their own members after the base part.

**O3 — Imports resolve (H1).** No `DoImport Failed!` line names
`HCXLog.dll` or `HCXMemory.dll` any more. The remaining import failures
are `Cws_Apl.dll` (15, all `Telema*CC`) and `AppTimerDll.dll` (8:
Speech.exe, Vehicle.exe, Usb.exe, PhoneBTA.exe, CameraCC). Usb.exe and
PhoneBTA.exe got past HCXMemory and now stop on AppTimerDll.

**O4 — The controls initialise (H1).** `Failed initialize control` drops
from 16 (M8.C1g run G18) to 5, and `ctl_PRCOM_System` no longer logs
`80020003`. The serial log now shows the control code running:

- `CGuideCtrl::FinalConstruct`, `CNaviEvCtrl::FinalConstruct`;
- `SystemCC : Receive Audio Micom Init Event(1)` and an audio-resource
  change to holder `0x8200000C`;
- `IPC Send::[MSG_PROCESS_SYSTEM] -> [MSG_PROCESS_OFF] MsgId[SYS_REQ_ACTIVATE]`.

**O5 — AuiApp paints nothing (H1, H2).** In 18 minutes H1 ran 10 display
lists, and only two of them target the AUI surface (`0x0f089800`, DU
plane 1). Both clear it: `0x80` with register `0xc0` bit 27, no other
drawing command. The first 960 lines of the surface stay all zero, so the
screenshot is the map alone.

With StartForm = `frm_PRAGR_AgreeCaution` (H2), AuiApp reads the value (no
`RegQueryValueEx(...,StartForm...) FAILED`), no control fails, and the
surface is still only cleared. ReleaseMain.skn names six objects, among
them `frm_PRCOM_StartUp`, `frm_PRAGR_AgreeCaution`, `frm_CAM_ForcedCamera`
and `act_SYSCOM_NotifySysEvent`.

**O6 — The audio microcontroller link fails throughout (H1).**
`CInaiProtocol[TX]::WriteProc! WriteData() FAILED` followed by
`CInterface::ComReStart! failed COMSTS_WAIT_RESPONCE count up![N]` repeats
3 785 times in H1. The driver opens fail too:

- `CAudioModeStatus::OpenDriver`, `CVolControl::OpenDriver` and
  `CSysCC::CEN Driver Open Error(55)`;
- three `ERR_PRC_AUI` error log entries.

SystemEXE also reports `SD Card Eject` from its panel interlock thread
just after mounting the system card. The notice goes to the user-SD
clients (`SYS_NOTIFY_USER_SD_CARD_EJECT`).

## Interpretation

- `HCXLog.dll` and `HCXMemory.dll` are C++ class libraries: a logger base
  class and a shared-memory base class with a named block, a lock and an
  unlock. Stubs at this depth are enough for the controls to load and for
  `ctl_PRCOM_System` to initialise. The falsifier is not met.
- A form that holds no failing control (H2) is not painted either, so the
  missing paint is not a control problem. The AUI renders only when the
  system state allows it. The likeliest gate is the power and display
  sequence that SystemEXE/SystemCC run with the audio microcontroller.
  That link never answers here (O6), and SystemCC activates the `OFF`
  source (O4). This is a hypothesis. No run has shown the gate yet.

## Conclusion

`ze0_ipl.py patch --stub-dlls hcx` adds working stand-ins for the two
unit-flash DLLs. Image A's controls load, and only the five controls
behind `Cws_Apl.dll`/`AppTimerDll.dll` still fail. AuiApp still paints no
form, not even the caution screen chosen through StartForm. The next
missing piece is the event that lets AuiApp paint. That is most likely the
power/display sequence that needs the audio-microcontroller peer
(M8.H43–M8.H45, M8.H53).
