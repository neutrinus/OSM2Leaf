## Question

Does the ZE0 firmware at L4 actually test the SD CMD42 lock state on the boot
path, and what are the three card states — no password, the unit's own
password, and a password belonging to another unit — in terms of CMD42
exchange and launcher verdict? At which VA is the verdict made?

## Hypothesis

The firmware refuses both a never-locked card and a card locked to a foreign
password, and accepts a card whose password it knows. With a fixed synthetic
test password added to the `sd-card`/`ze0` model, the three states give
different CMD42 sequences and different launcher markers. **Falsifier:** the
three states give the same boot (then the lock is not checked on this path);
second falsifier: no decision VA is resolvable by sh4xref.

## Method

### 1. Sample and hash

`sha256sum archive/head256.img
archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` prints the two
digests above; the card is never written (qcow2 overlay). `QEMU --version`
prints `QEMU emulator version 11.1.3`.

### 2. Commands

```bash
I=archive/head256.img
CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
Q=~/.cache/qemu-ze0/build/qemu-system-sh4
W=/home/marek/projekty/leafre-work/scratch/m2.23
mkdir -p "$W"
# qcow2 overlay over the 8 GiB card (the card file is read-only)
python3 tools/qemu-ze0/mkoverlay.py "$CARD" "$W/eu.qcow2"
# model self test (no QEMU needed)
python3 tools/ze0_sdlock_model.py --selftest
# three L4 boots; each writes its own serial and -d unimp trace
M="ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,sdhi-trace=on,hpbdmac-trace=on"
boot() { # $1 = label, $2 = extra machine options (may be empty)
  timeout 150 "$Q" -M "$M$2" -kernel "$I" \
    -drive if=sd,index=0,file="$W/eu.qcow2",format=qcow2 \
    -icount shift=0,sleep=off -nographic -serial file:"$W/ser-$1.log" \
    -monitor none -d unimp -D "$W/q-$1.log" 2>"$W/boot-$1.err"
  python3 tools/ze0_sdhost.py serial "$W/ser-$1.log"
  python3 tools/ze0_sdhost.py sdtrace "$W/q-$1.log"
  grep -i 'PIO write block' "$W/q-$1.log"
}
boot A ''                                                              # right password (TOFU baseline)
boot B ',sd-pwd-tofu=off'                                               # no password
boot C ',sd-pwd-tofu=off,sd-fixed-pwd=OTHERUN!OTHERUN!,sd-fixed-locked=on'   # other unit
# mutation control: same fixed pwd but card unlocked at power-up
boot Cmut ',sd-pwd-tofu=off,sd-fixed-pwd=OTHERUN!OTHERUN!,sd-fixed-locked=off'
# static decision-VA anchor and wrong-VA control
python3 tools/sh4xref.py --image-start 0x3e00200 "$I" AppLaunch.dll --to 0x03bb1278
python3 tools/sh4xref.py --image-start 0x3e00200 "$I" AppLaunch.dll --to 0x88336278
```

### 3. Controls

- **Positive:** run A (TOFU, default) must reproduce EXP-M8.C1b:
  `activate_ok 1`, `event2_timeout 0`, `lock_unlock_call 2`,
  `lock_unlock_err 0`, `security_unlocked 2`, `store_ready 1`,
  `part_mounted 2`, no `applch_error`/`failsafe_start`.
- **Negative 1 (never-locked):** B with `sd-pwd-tofu=off` must give
  `lock_unlock_call 1`, `lock_unlock_err 1`, `security_error 1`,
  `applch_error 1`, `failsafe_start 1` and the security-lock error string.
- **Negative 2 (static):** `sh4xref --to 0x88336278` (a physical-VA guess)
  must print `no literal pool holds …`; only the module-relative literal
  `0x03bb1278` resolves.
- **Mandatory mutation:** Cmut flips only `sd-fixed-locked` from `on` to
  `off`; the CMD42 sequence must change from UNLOCK-first to LOCK-first and
  the launcher markers must differ. A check that survives the mutation is
  not a check.
- **Model selftest:** `ze0_sdlock_model.py --selftest` prints
  `12 checks, 0 failed`; `python3 tools/selftest.py --only ze0_sdlock_model`
  prints `tool:ze0_sdlock_model PASS`.

### 4. Scope

One build family (EU 2011 build B), one card image, one QEMU version
(11.1.3), four boots (A, B, C, Cmut) of 100–150 s each under
`-icount shift=0,sleep=off`, and one static VA cross-check. Corpus counted:
3 serial logs, 3 QEMU unimp logs, 4 `ze0_sdhost.py serial`/`sdtrace` runs,
2 sh4xref runs, 1 build of QEMU with 30 patches. Excluded: real PIN bytes,
unit dumps, US/2014 cards, L5, CMD6/ACMD13 data-path re-verification
(already C-6874).

### 5. Falsifier

If A, B and C give the same serial markers, the lock is not checked on this
path; if sh4xref cannot anchor the decision string, the VA item of Done when
is unmet and the task is `blocked`.

## Observations

### O1. The three card states are reachable and distinct

| State | Machine options | CMD42 sequence (PIO first word) | Launcher verdict (markers) |
| --- | --- | --- | --- |
| A — own password | `sd-pwd-tofu=on` (default) | `0x1004` LOCK len 16, then `0x1000` UNLOCK len 16; serial `byFlag[04] … byFlag[00] …` | `security_unlocked 2`, `lock_unlock_err 0`, `store_ready 1`, `part_mounted 2`, `applch_error 0`, `failsafe_start 0`; `AppLch >> SD Card Security Unlocked!` ×2 |
| B — never locked | `sd-pwd-tofu=off` | one `0x1004` LOCK len 16; serial `byFlag[04]`, then `Err = [107]` | `lock_unlock_call 1`, `lock_unlock_err 1`, `security_unlocked 0`, `security_error 1`, `store_ready 1` (mounted before the verdict), `applch_error 1`, `failsafe_start 1`; `AppLch >> Error!!! SD Card is [Security lock state] or [no Security]....` |
| C — other unit's password | `sd-pwd-tofu=off,sd-fixed-pwd=OTHERUN!OTHERUN!,sd-fixed-locked=on` | one `0x1000` UNLOCK len 16; serial `byFlag[00]`, then `Err = [107]` | `lock_unlock_call 1`, `lock_unlock_err 1`, `security_unlocked 0`, `security_error 1`, `store_ready 0`, `applch_error 1`, `failsafe_start 1`; same security-lock error string |

`ze0_sdhost.py sdtrace` command counts at port 0: A 125, B 95, C 18.
The CMD42 order in A matches EXP-M8.C1b O3 (`CMD16 CMD42+data … CMD16
CMD42+data`); C stops after the failed UNLOCK (`… CMD16×2 CMD42+data CMD13
CMD16`), so the opening image is never loaded. The first word of the CMD42
PIO block encodes `[len<<8 | flags]`: `0x1004` = 16 bytes + LOCK (`0x04`),
`0x1000` = 16 bytes + UNLOCK (`0x00`), matching the flag map of C-1951 and
C-6876.

### O2. Falsifier did not fire

The three states are not the same boot: the CMD42 sequence (LOCK+UNLOCK vs
LOCK-only vs UNLOCK-only), the launcher markers and the card-read counts
differ. The firmware therefore checks the SD lock on this path.

### O3. Decision VA

`sh4xref` on the module-relative literal anchor resolves
`pool 0x03bca684 holds 0x03bb1278`, loaded at `0x03bca656` (r4) inside
function `0x03bca5f4` — the function that emits both the "Security lock
state / no Security" error and the "Security Unlocked!" line. With the CE
physical VA `0x88336278` (M2.8's notation) sh4xref prints
`no literal pool holds 0x88336278 in executable sections`; the VA mapping is
module base `0x88498000` + rva `0x1278` = `0x8833…` literal pool, i.e. the
same function M2.8 named `0x8834f5f4` (B). The decision VA is therefore
`0x03bca5f4` (module-relative, EU2011 build B `AppLaunch.dll`), equivalent
to M2.8's `0x8834f5f4` physical-VA notation. The wrong-VA control fails as
required.

### O4. Controls

- The TOFU baseline A reproduces M8.C1b exactly on the lock markers
  (`activate_ok 1`, `security_unlocked 2`, `store_ready 1`, 2 CMD42).
- B (no password) reproduces M8.C1b run C: one LOCK fails with `Err = [107]`,
  security-lock error, `Error Proc<00000081>` region, no opening image.
- Cmut flips only `sd-fixed-locked`: the CMD42 first word becomes `0x1004`
  (LOCK-first) and `security_error 1` remains, but `store_ready 1` — the
  marker set differs from C (`store_ready 0`), so the option demonstrably
  changes the boot. Mutating the option back to `on` restores C's result.
- `ze0_sdlock_model.py --selftest`: `sd-fixed-pwd selftest: 12 checks,
  0 failed`; `tools/selftest.py --only ze0_sdlock_model`:
  `tool:ze0_sdlock_model PASS 0.05s`.

## Interpretation

- **VERIFIED (L4):** the firmware refuses a card with no CMD42 password and
  a card locked to a different password; the two cases are reached by
  different CMD42 flag sequences (LOCK-only vs UNLOCK-only) but end in the
  same launcher security-lock error. A never-locked card is therefore not
  usable without setting a password on it — the emulator answer to "can a
  self-made card work without the lock" is **no on the boot path** unless
  the unit itself first writes its password (M2.13's LOCK menu).
- **VERIFIED:** `sd-pwd-tofu` cannot express the foreign-password case; the
  new `sd-fixed-pwd`/`sd-fixed-locked` options can, with a synthetic value
  only. The model patch contains no real password byte.
- **VERIFIED:** the launcher's verdict is made in `AppLaunch.dll` fn
  `0x03bca5f4` (B; M2.8's `0x8834f5f4`), which emits both the error and the
  success line. The SDHC-level failure is `byFlag … Err = [107]` in
  `CSDHCMain::SDHC_Lock_Unlock_Card` (C-6876, C-1953).
- **OBSERVED:** card B still mounts its FAT (`store_ready 1`) before the
  launcher error; card C does not (`store_ready 0`) because its failed
  UNLOCK precedes every data read — the lock check happens before the mount
  for a powered-up-locked card.

and launcher verdicts; the firmware refuses never-locked and foreign-password
