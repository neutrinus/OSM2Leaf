## Question

Starting from the zlib one-shot wrapper `0x00542148`, which functions open the
`.cmp`/`.ind` pair, which one loops over `chunk_offset[]`, and how does the
reader use `chunk_size` (M3.2a) and locate a chunk (M3.2b)?

## Hypothesis

The pass-2 blocker was a search for `0x0041c7e8`, the seventh instruction of
`fn 0x0041c7dc` (H51). With the true entry, the static chain should continue
upward through ordinary pool loads: `0x0041c7dc` <- `0x0041c990` <-
`0x0041c044` <- the map-file layer's read wrapper, up to the message handler
that serves a read request (H112: the firmware is message-driven).

**Falsifier (stated before the walk):** (a) a link in the chain that
`callgraph.py` lists but `sh4xref.py --to` cannot resolve to a pool load and a
`jsr` in the named caller, or (b) the `.ind` offsets reach the chunk engine
without passing through a function that indexes `ind + 16 + 4*i`, or (c) a
factory `.cmp`/`.ind` pair that violates a rule the code enforces (the code
would then reject a file the car reads).

## Interpretation

- **FACT (C-5100):** the static chain from `inflate` up is
  `0x00542148` <- `0x0041c7dc` <- `0x0041c990` <- `0x0041c044` <- `0x0041b954`
  <- {`0x0041855c` <- `0x00418634` <- `0x00419df8` (state-table handler),
  `0x0041a438`}; every edge is confirmed by two tools. The pass-2 blocker
  ("no static caller") was the mid-prologue VA, as H51 said.
- **FACT (C-5102):** the function that loops over `chunk_offset[]` is
  `0x0041c5f0`, driven by `0x0041c990`. **M3.2(b): seek, not scan** — the
  reader seeks to `chunk_offset[first]` and reads the batch's summed
  compressed length in one call.
- **FACT (C-5104):** **M3.2(a):** the `.ind` `chunk_size` is compared for
  equality with the configured `0x10000` (two sites) and is then the divisor
  and multiplier; it does not size anything — the buffers come from the mount
  config (scratch `0x10000`, compressed batch `0x14000`). M3.26's "no `0x10000`
  compare in the layer" missed that the constant is built by `mov #1; shll16`
  in `0x0041ba90`, outside the `0x41c000…` range it searched.
- **FACT (C-5101, C-5103):** whether a path is compressed is decided at open
  time by the `CMP.LST` content, which **is read** at mount through
  `0x0041c124`; C-1866's "no read of `CMP.LST` content" holds only for the
  probe inside `0x0041ba90` itself.
- **OBSERVED (C-5106):** the caller's flag only *allows* the compressed path:
  `0x0041a438` passes 1 for `MMAIN001.DAT`, which the factory `CMP.LST` does
  not list, so it is served plain. The flag of a queued read is the request's
  `u16 +46`.
- **OBSERVED (C-5107):** every factory pair satisfies the rules the code
  enforces (194/194), and the largest factory chunk (65,562 B) is 16,358 B
  below the batch buffer. A writer that keeps `chunk_size = 0x10000`, exact
  `.ind` word 1 and one zlib stream per 64 KiB cannot exceed `0x14000` (stored
  deflate of 64 KiB is 65,562 B in the self-test).
- **HYPOTHESIS:** `0x004181d8` is the client half that fills that request
  record (third argument = the flag); not traced field by field here.
- **UNKNOWN:** what `off_last_m1`/`off_last_p1` do on the unit — the rules
  pass, so the outcome is decided inside `inflate` (M3.3/M9.11 run it).
