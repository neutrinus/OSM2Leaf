## Question

Does `build.sh --check-version V` answer with a defined exit code and end on
its verdict line, so a caller (M8.A9, a future pin bump) can tell "the probe
says 3 applied / 2 failed" from "the probe broke"?

## Hypothesis

No, at `origin/main` `9beb6a4`: after printing the verdict the probe emits a
second note line and exits `1`, so the verdict is neither the last line nor a
distinct code, and `1` is also the code the full build uses for "failed" and
"no `ze0` machine in this build". Before reading the Precheck I expected an
uncaught shell error rather than the explicit `exit 1`; the reproduction below
shows which it is.

**Falsifier:** a pre-fix probe where some patches fail already exits `4`, or
one where the exit code is not `1`, or a post-fix probe where a failing patch
exits `0`; or the one-line verdict is not the last line of output.

## Method

1. **Sample and hash.** No map sample. The probe's inputs are the two
   immutable release tarballs whose SHA-256 are in Inputs; 11.1.3 is not in
   `QEMU_PINS`, so the probe measures and prints its hash each run instead of
   trusting the table.
2. **Commands.** Run as written, from the worktree root:

   ```bash
   # pre-fix probe, extracted from origin/main into scratch
   mkdir -p ~/projekty/leafre-work/scratch/m5.43
   S=~/projekty/leafre-work/scratch/m5.43
   git show origin/main:tools/qemu-ze0/build.sh > "$S/build.sh.before"
   chmod +x "$S/build.sh.before"

   # the red case (2 of 5 patches fail) and the green case (5 of 5 apply)
   bash "$S/build.sh.before" --check-version 11.1.3 \
     --patch-dir "$PWD/tools/qemu-ze0/patches"; echo "rc=$?"
   bash tools/qemu-ze0/build.sh --check-version 11.1.3; echo "rc=$?"
   bash tools/qemu-ze0/build.sh --check-version 8.2.10; echo "rc=$?"

   # exit 3: a truncated pinned tarball, and the whole-build control on it
   mkdir -p "$S/trunc"
   head -c 13 ~/.cache/qemu-ze0/qemu-8.2.10.tar.xz > "$S/trunc/qemu-8.2.10.tar.xz"
   bash tools/qemu-ze0/build.sh --check-version 8.2.10 --srcdir "$S/trunc"; echo "rc=$?"
   bash tools/qemu-ze0/build.sh --version 8.2.10 --srcdir "$S/trunc"; echo "rc=$?"

   # the offline suite, which carries every outcome
   bash tools/qemu-ze0/build.sh --selftest; echo "rc=$?"
   ```

   The mutant control below needs one more file: copy the fixed script and
   turn its `exit 4` back into `exit 1`.
3. **Controls.** *Positive:* `--check-version 8.2.10`, a release whose five
   patches all apply (M8.A10 measured `hw/sh4` byte-identical 8.2.7→8.2.10),
   must exit `0`. *Negative:* the pre-fix script on 11.1.3 (the state the
   task reports), and a post-fix mutant that keeps the verdict but exits `1`
   — the selftest must go red on it. For the exit-3 path the control is the
   full build on the same truncated tarball: it must stay `1`.
4. **Scope.** `--check-version` only, for two releases (11.1.3 unpinned,
   8.2.10 pinned); 5 patches per release, 10 `patch --dry-run` decisions. No
   build, no boot, no network (both tarballs were already in the cache).
   Excluded: the full-build path (`--force`, `-M ze0`), unchanged by this
   task; the port itself (M8.A9).
5. **Falsifier** as stated in Hypothesis, fixed before the runs.

## Observations

### 1. Pre-fix: verdict, then a note, then `1`

```text
$ bash "$S/build.sh.before" --check-version 11.1.3 --patch-dir "$PWD/tools/qemu-ze0/patches"
check: 0002-sh4-ze0-boot-stubs.patch                  APPLIES
check: m8a4-0001-hw-sh4-add-sh4-ccn-device.patch      APPLIES
check: m8a4-0002-hw-sh4-build-sh4-ccn.patch           APPLIES
check: m8a4-0003-hw-sh4-sh7750-use-sh4-ccn.patch      FAILED
check: ze0-0001-hw-sh4-ze0-machine.patch              FAILED
build.sh: check: QEMU 11.1.3: 3 applied, 2 failed, 1 unpinned-tarball
build.sh: check: a failure here is a porting delta, not a build failure; see docs/research/qemu-ze0-port-delta.md
rc=1
```

Last line is the port-delta note, not the verdict. `bash -x` on the pre-fix
script ends:

```text
+ note 'check: QEMU 11.1.3: 3 applied, 2 failed, 1 unpinned-tarball'
+ printf 'build.sh: %s\n' 'check: QEMU 11.1.3: ...'
+ '[' 2 -gt 0 ']'
+ note 'check: a failure here is a porting delta, ...'
+ printf 'build.sh: %s\n' ...
+ exit 1
```

So the trace is the script's own `exit 1`, on the line after the verdict —
not an uncaught error and not `patch`. That is not the task text's "uncaught
error / exception" wording, nor the hint's "cleanup or hash step": the fault is
the order of two `note` calls and the exit code. The task's Goal and Precheck
are corrected to this in the same PR (item 2 of the navigator's review).

The suite grew from 56 to 69 checks; the new block copies a real `.tar.xz`
cache (a fake `configure` inside) and points `--patch-dir` at one synthetic
patch that always applies plus one that edits `configure`:


The red case's second patch is written against a stale `configure`

### 5. Negative control: the mutant goes red

```text
$ sed 's/^    exit 4$/    exit 1/' tools/qemu-ze0/build.sh > "$S/build.sh.mutant"
$ bash "$S/build.sh.mutant" --selftest; echo "rc=$?"
FAIL check-version one-fails: exit 1, expected 4

```

A verdict without the code is caught: the suite cannot pass by printing the
right table and exiting `1`.

### 6. Exit 3 is now reachable, and the full build keeps `1`

The navigator's first finding was that nothing on the check path exited `3`:
a truncated pinned tarball and a missing `patch` both came out `1`. Now:

```text
$ head -c 13 ~/.cache/qemu-ze0/qemu-8.2.10.tar.xz > "$S/trunc/qemu-8.2.10.tar.xz"
$ bash tools/qemu-ze0/build.sh --check-version 8.2.10 --srcdir "$S/trunc"; echo "rc=$?"
build.sh: qemu-8.2.10.tar.xz has 13 bytes, expected 132685948 (truncated download?) — delete it and re-run
rc=3

$ bash tools/qemu-ze0/build.sh --version 8.2.10 --srcdir "$S/trunc"; echo "rc=$?"
build.sh: qemu-8.2.10.tar.xz has 13 bytes, expected 132685948 (truncated download?) — delete it and re-run
rc=1
```

The second line is the control: the same truncated tarball on the full-build
path is still `1` (`verify_tarball` takes a fault code, default `1`; only
`check_version` passes `3`). `fault()` (next to `die()`) is used solely by the
check path — the missing-tool guard, `verify_tarball 3`, and a missing
`configure` after extraction; `verify_tarball` also treats a zero-byte file as
a fault (before, `wc -c` on a missing file under `set -e` could exit `1` for
another reason).

## Interpretation

- **FACT:** at `origin/main` `9beb6a4` the probe printed the verdict, then a
  port-delta note, and exited `1`; the trace is the script's own `exit 1`
  (`bash -x`), not an exception and not `patch`.
- **FACT:** the Precheck's `56/56` matches the pre-fix suite; the work commit
  raises it to `69/69`, including exit-3 cases.
- **OBSERVED:** `1` was already the full build's failure code (`die()`, and
  `verify_machine`'s "does not list the machine 'ze0'" branch), so a wrapper
  could not separate "probe answered" from "tool broke"; `4` is now unique to
  a porting delta and `3` to a missing input on the check path, while the full
  build keeps `1` for the same fault.
- **UNKNOWN:** whether M8.A9's porting script wants to consume `4` (it should
  treat `4` as the answer, `0` as "no port needed", `2`/`3`/`1` as a real
  fault); that is M8.A9's choice, the README table states the contract.
- **CORRECTED:** the navigator found that `3` was documented but not
  implemented on the check path (truncated tarball and a missing `patch` both
  gave `1`); that is fixed and covered by two selftest cases. See
  [Corrections after navigator review](#corrections-after-navigator-review).

## Conclusion

The probe is now a verdict tool: `0` all patches apply, `4` at least one does
not, `2` usage, `3` missing input or download fault, `1` a real build
failure; the one-line verdict is the last line in every path. `README.md`
carries the exit-code table and the corrected 11.1.3 example (the old one
printed `0 unpinned-tarball` for an unpinned release, which the probe cannot
produce). No format or claim about the card changed; the new claims record
only the exit-code contract and its selftest coverage.
