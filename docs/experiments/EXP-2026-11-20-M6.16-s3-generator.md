## Question

Can the S3 card (`186f2ded…9775c1`) be rebuilt from the repo, and where on
the map is the moved vertex really?

## Hypothesis

1. Applying M5.14's described edit (dir (30,65280) slot 8 rec k=17, layer 8
   shape 1 vertex 2, +40,0; strict `clarion_bg` rebuild; `zlib.compress(…, 9)`;
   NUL-pad to 288 B at `0x1150c0`) to the factory tile reproduces
   `fc4d4bfc…` byte for byte, and `imgpatch.py` puts it into a copy of the
   factory image as `186f2ded…`.
2. The directory header's `x` word is `mesh_x − 1024` stored as signed 16 bit
   (as `ze0_decode.py` / `bg_decode.py` / `tilewriter.x_field` already use),
   so `65280` is mesh column 768 = longitude −156. With that column and the
   M5.44 level-1 grid (row = slot, column = `k // 2`, `y` counted north from
   the parcel's south edge), the moved vertex lies inside parcel (8,8):
   20.1667–20.1875°N, 155.75–155.71875°W, and a +40 `x` move is about 64 m
   **east**, not 11.6 km north (C-2054).

**Falsifier.** (1) any byte of the rebuilt tile or image differs from the
pinned hash; (2) the grid places the factory tile's own coastline away from
three named capes of the island of Hawaii by more than the reference
precision + 500 m, or the y-flipped grid fits them equally well.

## Interpretation

- **FACT (C-5250):** `tools/s3_vertex_patch.py` is a generator for the S3 card:
  from the factory US image it reproduces the patched tile `fc4d4bfc…` and
  the image `186f2ded…` byte for byte (zlib 1.3, level 9); the image differs
  from the base in 117 bytes, all in `[107324608, 107324896)`, as the S3
  package predicted. The lost `/tmp/m5_14_patch.py` is no longer needed.
- **FACT (C-5251):** the directory-header `x` word is signed, `mesh_x − 1024`:
  `65280` is mesh column 768, longitude −156°. With it the level-1 grid puts
  the factory coastline of the island of Hawaii within 161 m (Ka Lae), 202 m
  (Upolu Point) and 1,068 m (Cape Kumukahi, arc-minute reference) of the
  named capes. A y-flipped parcel misses Ka Lae by 1.9 km and Upolu by 4.0 km;
  C-2054's `coord.py` reading misses all three by 39–79 km. The M6.13
  "lon 64356" was `clarion_bg.mesh_to_lon` applied to the raw word without
  this sign step.
- **FACT (C-5252):** the moved vertex is at 20.167196°N 155.721756°W before and
  20.167196°N 155.721146°W after: **63.8 m east, same latitude**, in north
  Kohala on the **island of Hawaii** — not east Maui, not 11.6 km north.
  C-2054 is retracted. The shape is a 33-vertex level-1 layer-8 `0xc110`
  polyline; the vertex is its third point, 59 m north of the parcel's south
  edge.
- **OBSERVED (C-5253):** the S2 card is not reproducible from today's repo:
  `mutate_refer_poi.py` (default and `--whole-blob`) writes a 4,240,425 B
  `.cmp`, not M5.13b's 4,233,336 B, so its S2 is `1f1b444e…`, not
  `af4c9ff1…`; S3 stacked on that S2 is `fc1433d2…`. Removing S2 again does not
  give back `186f2ded…` (`59265a5e…`), because a resize zero-fills the stale tail of the
  last `.cmp` cluster. So a stacked card has to be built forwards from the
  S2 image the bench actually accepted: `s3_vertex_patch.py image --image
  <accepted S2> -o OUT`.
- **HYPOTHESIS:** the `0xc110` line is a stream/gully line (it occurs only on the
  wet north-east side of the island, where gulches are; `map-tiles.md` lists
  class `0x10` as UNKNOWN). A 64 m kink in it may be visible only at the
  closest zoom, if the unit draws this class at all.
- **UNKNOWN:** whether the unit draws level-1 layer 8; the bytes for the S2
  image `af4c9ff1…`.
