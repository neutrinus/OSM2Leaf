- **Status:** done

## Question

Can rule 14's precheck be one command that reports, for any CE module, how much
of it is executable but compressed, which calls go into compressed sections
(the M3.15 failure), and whether a given anchor has an xref in decodable bytes?

## Hypothesis

The precheck can be built from the section table and the SH-4 decoder already
in the repo, and it will reproduce the baseline (C-2128, the M1.12 block):
53,725,980 B of section vsize, 30,212,810 B compressed (56.2 %), 0 B of
executable compressed, 133 of 149 modules with a compressed section, and
`Navi.exe` 16,778,254 B compressed (75.1 %).

**Falsifier.** The tool is wrong if (a) build A's census differs from the
baseline on the same bytes; (b) a decodable call site lies outside the
section's vsize (the bytes past vsize are file padding, not code); (c) the
literal at `0x004125de` is a direct call to `0x0055d924` (the listing shows a
dereference before `jsr`); (d) the pool and load counts for `0x0055d924` and
`0x0055d954` differ from `sh4xref.py --to`.

## Method

1. **Sample and hash.** `archive/head256.img`, whole file, SHA-256 above. The
   EU 2011 image's first 256 MiB is byte-identical to it.
2. **Commands.** Runnable as written from the repository root with the image
   in `archive/` (`reader_precheck.py` also finds `archive/head256.img` in the
   main checkout from a worktree, or reads `$OSM2LEAF_IMG`; `sh4xref.py` and
   `cerom.py` take the path explicitly, so from a worktree pass the main
   checkout's `archive/head256.img`):

   ```bash
   python3 tools/reader_precheck.py --selftest
   python3 tools/reader_precheck.py archive/head256.img --module Navi.exe --anchor 0x00179364 --anchor 0x0017a1f8 --anchor 0x004125a8 --anchor 0x0055d924
   python3 tools/reader_precheck.py archive/head256.img --module OBJDLL.dll
   python3 tools/reader_precheck.py archive/head256.img --module diskcache.dll --anchor 0x03be1010
   python3 tools/reader_precheck.py archive/head256.img --table
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x0055d924
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x0055d954
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --calls 0x004125a8
   python3 tools/selftest.py --only reader_precheck
   python3 tools/claims_check.py
   ```

   The classifier, in one sentence: a `mov.l @(disp,PC),Rn` whose literal lies
   in a compressed range is `direct` if `jsr/jmp @Rn` follows before any other
   use of Rn, `indirect` if `mov.l @Rn,Rx` precedes a `jsr @Rx` (the call goes
   through the pointer stored at the literal), `slot` if it is dereferenced and
   not called, `unclassified` if Rn is used otherwise, and `data` otherwise.
   Calls are `bsr`, `direct` and `indirect`.

   Anchor verdicts and exit codes: 0 DECODABLE (a decodable xref, and its
   holder function calls no compressed code); 1 ABSENT (no decodable xref and
   the module has no compressed bytes); 2 COMPRESSED-ANCHOR (the anchor VA is
   in a compressed section); 2 ENTERS-COMPRESSED (a holder function calls a
   compressed section); 2 INCONCLUSIVE (no decodable xref, but compressed bytes
   exist); 2 OUTSIDE-MODULE; 3 no image.

3. **Controls.**
   *Positive:* (i) the sh4xref counts for `0x0055d924` (25 pools, 29 loads) and
   `0x0055d954` (320 pools, 663 loads) are reproduced by the tool's pool and load
   search and agree with `sh4xref.py --to`; (ii) `0x0017a1f8` (the LCTBL name,
   C-2204) gives ENTERS-COMPRESSED through `fn 0x004125a8`, which is the M3.15
   path; (iii) `0x0055d924` is COMPRESSED-ANCHOR; (iv) the synthetic image
   exercises each classifier class (`direct`, `indirect`, `slot`, `data`) and
   each verdict.
   *Negative:* (i) `0x03be1010` in `diskcache.dll`, a module with no compressed
   bytes, is ABSENT (exit 1); (ii) `0x00179364` has no decodable xref and is
   INCONCLUSIVE (exit 2), not ABSENT; (iii) the synthetic image's `0x3000` is
   OUTSIDE-MODULE.

4. **Scope.** Build A only (the 149 CE modules of `head256.img`; the full EU
   image was checked against the same prefix). Counted corpus: 149 modules,
   527 o32 sections (149 decodable code, 133 decodable data, 245 compressed),
   53,725,980 B of vsize. Executable decodable bytes scanned for edges:
   22,767,466 B. Excluded: compressed bytes (not decodable before M1.2f, so no
   edge is counted from inside them); computed jump targets (lower bounds);
   bytes between a section's vsize and psize (file padding, excluded on purpose,
   see the observations). The edge scan reads only 2-byte-aligned halfwords with
   a top nibble of `0xB` or `0xD`, then checks the target against the compressed
   ranges.

5. **Falsifier.** As stated under Hypothesis (a)–(d). Each one is a `--selftest`
   or real-image pin: (a) `reader_precheck.py --selftest` (the census pins),
   (b) the Navi `bsr` pin of 0, (c) the disassembly pin of
   `function_edges(0x004125a8)`, (d) the pool and load pins.

**Defects found in the tool during the run, and fixed before the pins:**

- Bytes between a section's vsize and psize were scanned as code. Navi sec0
  has vsize `0x0054bd16` and psize `0x0054be00`, so the scan read
  `0x0055cd16`–`0x0055ce00` and reported two `bsr` edges to sec1 that do not
  run. The blob is now cut to vsize; the pin `Navi bsr edges = 0` would fail
  without the cut.
- A first version classified the `0x004125de` load as `slot` (a deref with no
  call). Reading the listing showed the deref is followed by `jsr`, so the
  class is `indirect`; the pin now checks the class.

## Interpretation

- **FACT (C-2510, C-2511):** The census reproduces the M1.12 baseline on
  build A exactly; the full EU image gives the same table. Navi.exe's
  compressed sec1 (`0x0055d000`, 16.7 MB) holds 75.1 % of its bytes.
- **FACT (C-2513):** The M3.15 call at `0x004125de`–`0x004125e2` does not call
  `0x0055d924`. The code loads the literal, dereferences it, and calls the
  word stored there, which lies in compressed sec1. The call target is a
  pointer in compressed bytes. This retracts the call-target clause of C-2200,
  C-2201 and C-2202. The `0x0040b358` volume call is direct and stands.
- **FACT (C-2514):** `sh4xref.py --calls` does not model that dereference, so
  it labels every such call with the slot address. This is a defect in
  `query_calls`, which is M1.8's tool; it is filed as M1.15.
- **OBSERVED (C-2515):** Calls into compressed sections are almost all
  indirect through slot tables that sit in compressed data (20,879 sites;
  852 slots in Navi sec1 alone). The "shared callee set" reading of C-2202 is
  therefore wrong: sec1 is a table of call slots.
- **HYPOTHESIS:** The slot values point into decodable code, which would let
  the LCTBL path reach readable bytes once sec1 is decompressed. This is
  untested; it needs M1.2f, which is the M3.15 unblock.
- **OBSERVED (C-2516, C-2517):** The LCTBL name `0x0017a1f8` is referenced from
  decodable code only in `fn 0x004125a8`, which makes the indirect compressed
  call. The M3.15 path therefore enters compressed bytes, as C-2206 says, but
  through a slot rather than a named callee. The M1.12 example anchor
  `0x00179364` has no decodable xref, which is inconclusive, not absent.
- **UNKNOWN (C-2519):** The four `bsr` edges (ComMid, Consult) target
  compressed data. They may be real calls or data decoded as code.
- **Premise of M3.15's Precheck line:** it says "OBJDLL's compressed bytes are
  data". `--module OBJDLL.dll` shows 396 indirect calls through OBJDLL's
  compressed sec1. Those bytes are data that holds call slots, so the premise
  holds only in the narrow sense that no compressed bytes are executable (C-2128).
- **Done-when wording:** the M1.12 done-when says the tool "exits non-zero
  when the anchor's only xref is inside a compressed section". An xref inside
  compressed bytes cannot be observed before decompression. The tool therefore
  exits 2 in three operational cases: the anchor VA is in a compressed section;
  a decodable xref's holder calls compressed code; no decodable xref exists
  while the module has compressed bytes. ABSENT (exit 1) is reserved for modules
  with no compressed bytes. This is the operationalisation the task asked for;
  it is stated here so a reader can check it.
- **Scope of the precheck's claims:** every number is a lower bound on calls
  and an exact count on bytes. A non-zero exit says "the decodable bytes do not
  settle this", not "impossible" (rule 14).

## Conclusion

`tools/reader_precheck.py` gives the M1.12 precheck as one command. Its
`--selftest` pins the build-A census, the edge counts, the pool and load
counts, and the M3.15 call class; the synthetic image covers each classifier
class and each verdict. `docs/format/firmware.md` gains the per-module table
(`--table`). The claims ledger gains C-2510–C-2519 and retracts the call-target
clauses of C-2200–C-2202. Still open: the slot values in compressed sec1 (M1.2f);
the `sh4xref --calls` dereference model (M1.15); M3.15 stays blocked on M1.2f.

## Reproduction

```bash
python3 tools/reader_precheck.py --selftest                                              # expect: synthetic PASS, real build-A pins PASS
python3 tools/reader_precheck.py archive/head256.img --table | tail -2                   # expect: 149 modules, 133 with compressed; 53725980 / 30212810 / 0
python3 tools/reader_precheck.py archive/head256.img --module Navi.exe --anchor 0x0017a1f8   # expect: ENTERS-COMPRESSED (exit 2) via fn 0x004125a8
python3 tools/reader_precheck.py archive/head256.img --module diskcache.dll --anchor 0x03be1010  # expect: ABSENT (exit 1)
```
