# EXP-2026-11-05-25: No import descriptor; NaviStateCC is a COM DLL

- **Status:** done (thunks unnamed; reader not located)
- **Date:** 2026-11-05
- **Sample:** EU 2011 image
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Claims:** C-390…C-398
- **Supersedes:** “NaviStateCC is a flat library” and “the import descriptor
  names the thunks”
- **Superseded by:** none

## Question

Can the 86 navi import thunks be named, and is NaviStateCC a flat library
containing the reader?

## Hypothesis

A standard 20-byte import descriptor with `FirstThunk = 0x1ab9000` names the
thunks; NaviStateCC is a flat DLL with the fd/reader code.

## Observations

### Import descriptor is absent

- `find_import_desc.py`: every 4-aligned position with
  `FirstThunk ∈ [0x01a00000,0x01b00000]`, solving
  `file_base = dll_string − NameRVA` against 1123 DLL/EXE strings — **219
  descriptor-shaped records, none matching**.
- `0x01ab9000` occurs only at `0x1727658` (IAT slot), `0x15c3044` (pool/code),
  `0x79e7c7`, `0x121fd9f` (C++ EH table), `0x18bd86b` (code/pool); none has a
  coherent 20-byte descriptor window.
- Candidate regions `0x11d7000–0x121fd00` and `0x1725000–0x1726000` contain
  C++ EH/type and thunk tables, not import descriptors.
- The pre-partition area `0–0x200000` contains no `0x1ab9000`.
- 140 ordinal-ILT runs exist (`0x8000xxxx | ordinal`), e.g. `0x285ff0`
  (248 entries), `0x307694` (303), `0x2b9c7c` (96), `0x2a8a00` (55); none is
  contextually matched to the navi IAT.

The navi module is **pre-bound**: the IAT is a RAM region filled by the loader;
the ordinal/name metadata lives in ROM metadata that is stale or absent. The
86 thunks remain **unnamed**.

### NaviStateCC is a COM DLL

Exports only:

```
DllCanUnloadNow     0xc43008
DllGetClassObject   0xc434cc
DllRegisterServer   0xc440f8
DllUnregisterServer 0xc4410c
```

`DllGetClassObject` is a 6-instruction forwarder to framework thunk
`0x2e00eb8` (file `0x171ea2c`) with class-factory data `0x1d0f8a8` (RAM). The
fd/IOB layer (`0xc42520`, `0xc426a4`, `0xc438a4`) consists of **COM methods**
reached through a load-time vtable — hence no `bsr` or static vtable reference
reaches them.

Structural scans of `0xc32200–0xc4c200`:

| Function | Thunks | Loops | Interpretation |
| --- | --: | --: | --- |
| `0xc44cdc` | 16 | 3 | message/print dispatcher |
| `0xc488d0` | 15 | 0 | message/print dispatcher |
| `0xc476e8` | 14 | 5 | UI/message handler |
| `0xc4800c` | 13 | 0 | setup/print |
| `0xc42e48` | 13 | 4 | debug dumper (`+0xAC..+0xC4`, switch `+0xB8` = 35/36) |
| `0xc49f98` | 9 + 8 local | 15 | virtual dispatcher (`jsr [[r4]+8]`, message 35) |
| `0xc438a4` | 5 | 1 | stats formatter |

fd thunk sets:

```
0xc42520: 02e07308 02e07704 02e0773c
0xc426a4: 02e07308 02e07704 02e0773c
0xc438a4: 02e07350 02e073bc 02e073c8 02e076a4
```

Sharp negatives in NaviStateCC: **no `0x10000` pool literal**, **no
`mov #1; shll16`**, no 4-dword header read near the fd layer. The `.ind` reader
likely uses `chunk_size` as a buffer size, not as a comparison value.
