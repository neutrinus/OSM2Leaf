# EXP-2026-11-06-M8.A4: CPU control block (CCN/MMU) factored out of `hw/sh4/sh7750.c`

- **Status:** done (patch series verified to apply, compile and instantiate; kernel-level MMU behaviour UNVERIFIED)
- **Date:** 2026-11-06
- **Sample:** no vendor image used; base tree QEMU **8.2.7** (tag `v8.2.7`, tarball `qemu-8.2.7.tar.xz`, SHA-256 `1f0604f296ab9acb4854c054764a1ba408643fc299bd54a6500cccfaaca65b55`)
- **Claims:** C-1260 (proposed here only; ledger update belongs to the task merge)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the SH-4 CCN/MMU control block (`PTEH`, `PTEL`, `TTB`, `TEA`, `MMUCR`,
`CCR`, `EXPEVT`, `INTEVT`, `TRA`, `PTEA`, the read-only `PVR`/`CVR`/`PRR`,
and the IC/OC/UTLB/ITLB window at `0xf0000000`–`0xf7ffffff`) be factored
out of `hw/sh4/sh7750.c` into a device that a `ze0` machine instantiates
**without** the SH7750 INTC, TMU, SCI, RTC, PCI and GPIO models — and does
the resulting patch series apply and build against the pinned QEMU?

## Hypothesis

Yes. EXP-2026-11-05-37 showed the kernel needs only the CPU, RAM and this
register block to get past cache/MMU setup. In 8.2.7 the registers sit in
the monolithic `sh7750_mem_readl/writel` switch (keyed by the `*_A7`
addresses, `0x1f000000` base) and the arrays in a separate `mmct_iomem`
region, so the extraction must move both the MMIO front end and the SH-4
side effects, not just a struct.

## Method

```bash
# pristine tree from the pinned tarball (scratch copy, outside the repo)
tar -xf qemu-8.2.7.tar.xz && cd qemu-8.2.7
git init -q . && git add -A && git commit -qm base     # only to use git apply

P=/path/to/OSM2Leaf/tools/qemu-ze0/patches
for f in "$P"/m8a4-0001*.patch "$P"/m8a4-0002*.patch "$P"/m8a4-0003*.patch; do
    git apply --check "$f" && git apply "$f" || echo "FAIL $f"
done

# the build.sh invocation
for f in "$P"/m8a4-000*.patch; do patch -p1 --dry-run --forward --batch -i "$f"; done

mkdir build && cd build
../configure --target-list=sh4-softmmu --disable-werror --disable-docs
ninja qemu-system-sh4

./qemu-system-sh4 -M none -device sh4-ccn,help
timeout 3 ./qemu-system-sh4 -M r2d -nographic -serial none -monitor none
```

Ordering with the M8.A5 series was tested in both directions
(`0002-sh4-ze0-boot-stubs.patch` → M8.A4, and M8.A4 → M8.A5).

### 4. What the series contains (against the real files)

| Patch | Contents |
| --- | --- |
| `m8a4-0001-hw-sh4-add-sh4-ccn-device.patch` | new `include/hw/sh4/sh4_ccn.h` (73 lines) and `hw/sh4/sh4_ccn.c` (323 lines): `sh4-ccn` device, P4 MMIO front end, the array-window dispatcher, MMUCR/PTEH side effects, CCR storage, PVR/CVR/PRR from `SuperHCPUClass`, reset, vmstate v1 |
| `m8a4-0002-hw-sh4-build-sh4-ccn.patch` | `hw/sh4/meson.build` builds `sh4_ccn.c` under `CONFIG_SH4_CCN`; `hw/sh4/Kconfig` defines the symbol and `SH7750` selects it (so `R2D` and `SHIX` keep linking) |
| `m8a4-0003-hw-sh4-sh7750-use-sh4-ccn.patch` | `hw/sh4/sh7750.c`: seven hunks. Includes; `SH4CCNState *ccn` replaces `mmct_iomem`; the cache `ccr` field moves into the device; the nine `*_A7` read cases and ten write cases (incl. `PTEA`) collapse into `sh4_ccn_reg_read/write(s->ccn, addr - SH7750_A7_BASE)`; the `MM_REGION_*`/`sh7750_mmct_*` model is deleted; `sh7750_init` creates the CCN and maps `sh4_ccn_arrays()` at `0xf0000000` |

Semantics preserved one-for-one: `MMUCR.TI` still calls
`cpu_sh4_invalidate_tlb()` and stores `value & ~MMUCR_TI`; a `PTEH` ASID
change still `tlb_flush()`es; TRA/EXPEVT/INTEVT still mask to 11 bits and
PTEA to 4; IC/OC arrays are ignored and UTLB/ITLB go through
`cpu_sh4_{read,write}_mmapped_*` (the ITLB data write keeps its historical
`abort()`). `r2d` keeps its `0x1f000000`/`0xff000000` aliases and delegates
to the CCN from the switch; its array region is now the CCN's, so the moved
array code runs on every `-M r2d` start.

## Interpretation

- **FACT:** the series applies to pristine 8.2.7 with `git apply --check`
  and `patch -p1 --dry-run` (rc=0), in both orders with the M8.A5 patch.
- **FACT:** the patched tree builds `qemu-system-sh4` (rc=0) and the
  `sh4-ccn` device instantiates on `-M none`.
- **OBSERVED:** `-M r2d` starts and runs for 3 s without aborting, which
  covers CCN creation, the CPU binding and the array-region mapping.
- **OBSERVED:** 8.2.7 has no `device_class_set_legacy_reset()`; the first
  build caught this, and the patch uses `dc->reset` instead. This is
  evidence that "written against the layout" is not the same as "compiles".
- **HYPOTHESIS:** with the CCN mapped by the `ze0` machine and `MMUCR.AT`
  reaching `CPUSH4State`, the kernel-page call at VA `0x5b90` takes the
  `0x100` TLB-miss exception instead of `illegal_instruction`; the handler
  fills the UTLB via `LDTLB` and the retry translates. Not demonstrated.
- **UNKNOWN:** whether toggling `MMUCR.AT` needs an explicit TB flush so
  already-translated code starts translating. The TI/ASID invalidations
  are preserved, but EXP-37 never reached the point where AT mattered.
- **UNKNOWN:** whether the kernel needs the unimplemented offsets in the
  `0xff000000` page (anything outside the 13 registers modelled); the
  device logs `LOG_UNIMP` and reads 0 for them.

## Conclusion

`tools/qemu-ze0/patches/` holds an ordered series `m8a4-0001…0003` that
moves the CCN/MMU block out of `hw/sh4/sh7750.c` into the `sh4-ccn` device,
with build wiring (`CONFIG_SH4_CCN`) and a README carrying the base tree,
apply order, per-hunk intent, the one-line `select SH4_CCN` M8.A2 must add,
and the acceptance plan. The series is verified against the real pinned
8.2.7 source: it applies, compiles and instantiates.

The task's done-condition — the kernel-page call to `0x5b90` no longer
faults — is still **not measured**. That needs the `ze0` machine (M8.A2),
the M8.A5 stubs to get the unpatched kernel that far, and an image run.
`docs/research/claims.md` is unchanged by this EXP; C-1260 is proposed
below for the task merge.
