## Question

What transport do `BT_FW.dll` and `BT_MGR.dll` put on `SCI8:`, what is the
shortest exchange that lets the stack settle, and which stub (`absent` or
`minimal present`) should M8.H56 attach to the `sci8` chardev?

## Hypothesis

The module is a CSR Bluetooth radio reached over a framed UART (not bare HCI
H4), the head unit downloads firmware into it at start, and a silent module is
recovered from by bounded timeouts. **Falsifier:** the guest never writes to
the line during a stock boot (BT is started on demand only), or the framing is
plain H4, or an unresponsive module hangs boot.

## Observations

**O1 — `SCI8:` resolves to both modules.** `ce_strfind` finds `SCI8:` in
`BT_FW.dll` sec0 at VA `0x035c2300` (build B) and in `BT_MGR.dll` sec0 at
`0x0365c4c4` (build A); `AppLaunch.dll` also has the bare string. `sh4xref`
puts the BT_FW string load in `fn 0x035c4714` and the BT_MGR one in
`fn 0x03694364`. Controls: the two `--image-start` values give the expected
module counts (91 / 149).

**O2 — low-level role of BT_FW.** sec0 is 34,816 B at `0x035c1000`; exports
are exactly `FWB_Close/Deinit/IOControl/Init/Open/Read/Write`. Strings include
`[BtFW]::start DFU_CreatCOMBCSP`, `DFU_CreatCOMBCSP::UartDrv_Start() failed!`,
`ABCSP_DeInit error.`, `[BtFW]::yabcsp_event: %S`, `abcsp_panic: %u`,
`Tx buffer overrun`, `CSR-dfu1CSR-dfu2`, and `[BtFW]::BaudRate=%d`.
Positive control: `cerom.py exports` prints the seven named exports.

**O3 — 38400 in the baud table.** `fn 0x035c8438` contains literal stores
`0x12c0`, `0x2580`, `0x28a0`, `0x3840`, `mov #75; shll8` (19200), `0x7080`,
`0x9600`, `0xe100`, `0x12c00`, `0x1c200`, `0x38400`, `0xe1000` selected by a
14-byte table at `0x035c356c` (`00 06 0c 12 18 1e 24 2a 30 36 3c 4e 42 4e`)
whose entries are offsets from `0x035c846e`; index 6 → `0x9600` = 38400.
`fn 0x035c53a0` maps the value from global `0x01c0e83c` to that index
(`cmp/eq 0x9600` → index 6). `fn 0x035c7f94` sets 8N1, `fFlags = (old &
0xdf87) | 0x1004`, `ReadTotalTimeoutConstant=1000`,
`WriteTotalTimeoutConstant=3000`, then calls `SetCommState`,
`SetCommTimeouts`, `SetCommMask` (import ordinals #118/#119/#117).

**O4 — framing bytes are SLIP-style, not H4.** `fn 0x035c9374` (pdata start,
length `0x1a0`) compares the received byte with `0xc0` (`mov #-64`), `0xdb`
(`mov #-37`), `0xdc` (`mov #-36`) and `0xdd` (`mov #-35`). On ESC `0xdb` it
reads the next byte; ESC_END `0xdc` stores a literal `0xc0` and ESC_ESC `0xdd`
stores a literal `0xdb` (`0x035c947c`–`0x035c94b2`). `fn 0x035c889c` emits
`0xc0` to start a frame (`0x035c88d6`). Above that, BT_MGR logs
`[BCSP] cmdRecvEvent NG::unknown opcode=%d` from `fn 0x03693db0` and
`send_BCCMD`/`Tx:HOST_GEN_ENTER_DFU_MODE_REQ`; BT_FW logs `yabcsp_event`.
Negative control: no HCI-H4-style framing constant is used as the outer
framer; the HCI packet indicators would be inside a BCSP payload.

**O5 — DFU is part of start.** `fn 0x035c4558` calls `fn 0x035c54d0`,
`0x035c52e0`, `0x035c5908`, `0x035c5520`, `0x035c5bc0`, `0x035c5f78`,
`0x035c52b4` and `0x035c4520`, with logs `fail DFU_SetDFUMode`, `DFU OK!`,
`Download Failed! Recovering…`, `Download Success`, `Manifest Success`,
`Reconfigure Failed! Recovering…`, `Reconfigure Success`, `Recover Success`.
`fn 0x035c4bd4` is the `DFU_StartDownload` driver (calls WriteFile and
`GetTickCount`-style polling). `fn 0x035c5bc0` references `dfu_ClrStatus` and
`dfu_Detach`.

**O6 — BT_MGR init is bounded.** `fn 0x0369566c` logs
`Timeout awaiting initialization !!` and retries at counts 2 and 4 with a
`mov #47,r4` timeout argument; other strings are
`device initialize failed, ignore(wait timeout)` and
`@@@ Bluetooth Ready @@@`. This is a recoverable path, not a boot hang.

**O7 — the falsifier fires: no wire traffic in a stock boot.** The 200 s
boot wrote **0 bytes** to `sci8.tx.bin` (file backend, `ls -l` = 0). The same
boot still ran the Bluetooth user-side code: `serial.log` has 9 `bt_event:`
lines (`GAP`, `HFP`, `OPP`, `A2DP`, `AVRCP`, `DUN`, `COM`, `PBAP`, `MISC`),
8 `PhoneBTA.exe` lines, 12 `< BT-Manager Reset Start >`, 2
`MGR_BT: timer stop error (-1)`, and `DoImport Failed! … HCXMemory.dll for
BT_WRPENG.dll` — i.e. `PhoneBTA.exe` cannot load its import and the stack
never reaches the radio. `serial.log` is 1 583 lines with 116
`failed wait response` and 1 `Force PowerOff`, byte-for-byte the same counts
as the no-peer baseline of EXP-2026-11-22-M8.H1 O8; `final pc 0x880480bc`.
Positive control for the carrier: `run.sh --serial-peer sci8=file:…` creates
the `ze0sci8` chardev and the machine property `sci8=ze0sci8`; M8.H1 O1/O3/O7
show that the same mechanism carries TX on `sci1`/`sci7`, and QEMU would have
exited at machine init if the chardev id were missing (h01 patch, line 41).
Negative control: a boot with no `sci8` peer is the measured M8.H1 baseline.

**O8 — no positive wire bytes means no packet trace.** Because 0 bytes were
transmitted, the "first ten exchanges after open" cannot be observed in this
boot. The start-up table in `bt-wire.md` is therefore a static call/log table,
not a captured frame sequence; the 0-byte result is itself the answer to the
task's falsifier (BT is started on demand and is blocked by a missing app
import on this card/image combination).

## Interpretation

- **FACT (C-7520):** the two modules split cleanly: `BT_FW.dll` is the UART/
  BCSP/DFU driver (B, 34 816 B, `FWB_*`), `BT_MGR.dll` is the command layer
  with `HOST_GEN_*`/`BCCMD` (A, 383 488 B) (O1, O2).
- **FACT (C-7521, C-7522):** `SCI8:` is opened with `CreateFileW`; the line is
  38400 8N1 with 1000 ms read / 3000 ms write timeouts; the baud comes from a
  14-entry table at `0x035c356c` (O1, O3). The runtime default is OBSERVED,
  not fully proven (C-6413).
- **FACT (C-7523, C-7524):** the framer is SLIP-style END/ESC (`c0/db/dc/dd`)
  in `fn 0x035c9374`, carrying BCSP (`yabcsp`, `[BCSP] cmdRecvEvent`), not
  bare HCI H4 (O4). This is derived from the state machine, not from a public
  spec.
- **FACT (C-7525, C-7526):** a DFU download is wired into start at the BT_FW
  level; BT_MGR's init has a bounded timeout and ignores failure (O5, O6).
- **FACT (C-7527):** a stock EU2011 boot with an `sci8` chardev emits no bytes
  on the line; the falsifier "modules never write during start" is **not
  refuted**, so no wire-level trace can be claimed from this run (O7, O8).
- **FACT (C-7528):** the recommended stub for M8.H56 is therefore **`absent`**
  for a stock boot: attaching a BCSP responder cannot change a line the guest
  never writes. A `minimal present` peer is only useful once BT is activated
  (ACC on / a phone process that loads), and must speak BCSP-in-SLIP.
- **FACT (C-7529):** `BT_FW.dll` is function-identical in all four builds, so
  the transport conclusion transfers unchanged (M1.37).

## Conclusion

M8.H55 is done as a reader task with a first-class negative result. The
wire format is known (CSR BCSP in SLIP framing over 38400 8N1 on `SCI8:`),
the DFU/startup call order is documented, and the boot-time falsifier shows
that a stock EU2011 image never drives `SCI8:` — `PhoneBTA.exe` fails to
import `HCXMemory.dll`. M8.H56 should implement `bt.py` as a table-driven
BCSP/SLIP responder with a passing `--selftest`, but the honest expectation
is that boot metrics with and without the peer are identical; if so that is a
negative result for the peer, not a failure of this reader task.
