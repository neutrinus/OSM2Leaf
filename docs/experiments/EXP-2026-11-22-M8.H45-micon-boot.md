## Question

Does attaching the M8.H44 audio-micom peer to `sci1` remove the launcher's
`WaitModule` timeouts and make `Finish Launch Threads!` arrive sooner?

## Hypothesis

The peer's framed ACK to the guest's `ReqMo` frames is the module-presence
signal the launcher waits for. **Falsifier (from the task):** the timeout
count is the same with and without the peer. **Falsifier fired.**

```python
import os, sys
ROOT = os.getcwd()
sys.path.insert(0, os.path.join(ROOT, "tools", "ze0_peers"))
import micon
ACK = 0x06
def ack(payload):
    return bytes((ACK,)) + payload
RULES06 = (
    micon.Rule("ReqMo06", b"\x02\x08",
               lambda p: bytes((ACK, 0x02, 0x08, 0x00)), "control 0x06 variant"),
    micon.Rule("ReqMo06", b"\x02", ack, "control 0x06 variant"),
    micon.Rule("Audio06", b"\x04", ack, "control 0x06 variant"),
    micon.Rule("ReqAIr06", b"\x01", ack, "control 0x06 variant"),
    micon.Rule("GetSy06", b"\x09", ack, "control 0x06 variant"),
)
class Peer06(micon.MiconPeer):
    def __init__(self, rules=RULES06, log=None):
        super().__init__(rules, log)
micon.MiconPeer = Peer06
sys.exit(micon.main())
```

## Observations

**O1 — baseline B.** 1787 DBGMSG lines; **19** `ACM::WaitModule Timeout
ID[n] WaitTime[…]` lines, first at `211.629 s`, last at `395.699 s`; one
`[Audio::] Create Thread[1] Wait Modules Error LaunchId=[45] Wait Modules
ID=[6]` at `395.948 s`. No `Finish Launch Threads!` line within 480 s; last
DBGMSG line at `479.811 s` (`CInaiProtocol[TX]::WriteProc! WriteData()
FAILED.`). Timeout IDs/counts: `35:1, 45:1, 46:7, 48:2, 76:1, 77:1, 78:1,
81:1, 92:1, 94:2, 96:1`.

**O2 — peer P (`0x02` ACK).** 1792 DBGMSG lines; **19** timeouts with the
identical ID multiset, first `215.782 s`, last `399.753 s`; the `Wait Modules
ID=[6]` error at `400.000 s`. No idle marker; last line `480.047 s`. The peer
log holds 102 `request` frames, all payload `020800`, and 102 framed replies
`10 02 02 02 08 00 10 03 1b`; BCC validated by M8.H44's codec.

**O3 — peer P6 (`0x06` response class).** 1783 DBGMSG lines; **19** timeouts,
same ID multiset, first `217.554 s`, last `402.510 s`; the `Wait Modules
ID=[6]` error at `402.757 s`. No idle marker; last line `480.136 s` reads
`CInterface::ComReStart! failed COMSTS_WAIT_RESPONCE count up![53]`. The peer
log holds 100 `020800` requests and 100 replies
`10 02 06 02 08 00 10 03 1f`.

**O4 — wire traffic reaches the guest.** Both peer runs received the
identical frame EXP-M8.C2a and M8.H1 observed on `sci1`; M8.H1 O4 proved
writing such a frame to `sci1` lands in channel 1's RX DMA plane. The replies
were therefore transmitted onto the link, not merely generated locally.

**O5 — time to `Finish Launch Threads!`.** Not reached in any of the three
runs within the 480 s window (recorded as `NOT REACHED`; the last DBGMSG
timestamps above bound the observation). No wall-clock improvement from the
peer: first timeout moved from 211.629 s (B) to 215.782 s (P) and 217.554 s
(P6), i.e. later, not earlier.

**O6 — remaining timeouts and the request nobody answered.** Each of the 19
timeouts is a `CApi_WaitModuleInitialize(id, timeout)` → `IOCTL_ACM_WAIT_ID
(0x80002004)` wait on `ACM9:` (M1.34/M1.35), issued by `AppLaunch.dll` /
the launcher threads. The SCI1 peer never receives a wire request carrying
those module IDs: every guest frame it saw was the same `ReqMo` payload

## Interpretation

- **FACT (C-7420, C-7421):** baseline and peer boots use identical options;
  the peer is attached to `sci1` and receives/replies to the guest's frames
  (O1–O4).
- **FACT (C-7422, C-7423):** timeout count is 19 in all three runs and the
  ID multiset is identical; the task's falsifier fires (O1–O3).
- **FACT (C-7424):** `Finish Launch Threads!` was not reached in 480 s in
  any run; no timing improvement was observed (O5).
- **FACT (C-7425, C-7426):** every remaining timeout is an `ACM9:` wait for
  a module ID, a request the SCI1 peer never sees on the wire (O6).
- **OBSERVED (C-7427):** with `0x06` replies the driver still logs
  `COMSTS_WAIT_RESPONCE count up![53]`, so that control class is not the
  expected response either (O3).
- **HYPOTHESIS:** the module-presence signal is raised inside the guest by
  `CApi_ModuleInitializeComplete(id, …)` after a version/exchange the M8.H43
  static map did not decode; a SCI1-only peer cannot raise it yet.
- **UNKNOWN:** which iNai message (if any) makes anwdrv.dll call
  `CApi_ModuleInitializeComplete`, and the mapping from ACM module IDs to
  frames. This is a follow-up to M8.H43, not a claim of this record.

## Conclusion

Attaching the M8.H44 micon peer to `sci1` does **not** remove the launcher's
30-second waits: 19 timeouts with the peer versus 19 without, in both
control-class variants, and no `Finish Launch Threads!` within 480 s. The
task's falsifier fired, so the presence-reply hypothesis is refuted. The
second Done-when branch is met by O6: each remaining timeout is listed with
the `IOCTL_ACM_WAIT_ID` request the peer could not answer. `run.sh --peers
micon` was not added — starting the peer by default would not help. The
follow-up is to find the in-guest path from an iNai message to
`CApi_ModuleInitializeComplete(id, …)`.
