- **Status:** done (negative; task M4.48 `blocked`)

## Question

Which EU2011 code reads bytes `0x18c..0x19f` of the `MMAIN001.DAT` header (the
per-language code list, M4.22/M4.38), so that an L3 run can turn the
code→language reading into a firmware verdict?

## Hypothesis

The reader is in `Navi.exe` and reaches the header through the copy that
`OBJ_DriveInfo_readDataVol` fills (M4.22 census, C-5283) or a callee within
two call levels. **Falsifier:** no call site in any module asks the
data-volume store for a field overlapping `0x18c..0x1a0`, and no function
that holds a whole-header copy (nor its callees to depth 2) accesses a
constant offset in `0x18c..0x1a0`.


   The seed buffers of `taint` come from the `calls` output: each
   `readDiscVol` index-20 call writes a whole copy to a literal buffer
   (`0x00625668`, `0x009c9600`, `0x009c8600`) or to a heap block whose pointer
   is stored in `0x00d8b070` (fn `0x0040b258`, `0x003f77cc`); `0x01205040` is
   the `readDataVol` copy, `0x00e23cc0` the raw file read.
3. **Controls.** Positive: `calls --field 0x162` must find the index-7
   requests of fn `0x00377ae0` and `--field 0x182` the index-8 requests;
   `taint --field 0x184 --size 8` must find the bounds reader fn `0x003f7008`
   (`0x184..0x18a`, known values 4800 1280 −1200 4080 from M4.22).
   Negative: `taint` with a seed global that nothing loads (`0x12345678`)
   must report 0 functions. Self-test: a synthetic function that reads
   `hdr+0x18c` through `mov #99; shll2; mov.w @(r0,rn)` must be found, the
   wrong seed must not.
4. **Scope.** EU2011 build A only. `calls`: every module that imports
   `MAL_DataVol_getSize`, `MAL_DataVol_getOffset` or
   `OBJ_DiscInfo_readDiscVol` (import tables of 149 modules; importers:
   `Navi.exe`, `NaviGeneralCC.dll`, `DiagnosisCC.dll`), plus OBJDLL's own
   literal calls of those exports. `taint`: `Navi.exe` functions that load one
   of the six seeds (24 roots) and callees that receive the header in
   `r4..r7`, to depth 2 (40 functions). The taint is straight-line: it does not
   follow loops with computed indices, copies into other buffers, or the
   header after it is stored in a struct field other than `0x00d8b070`.
   Excluded: US 2011 and later builds, OBJDLL code that walks the store
   without the field table, the meaning of codes `14 17 18 19 1a`.
5. **Falsifier** stated in the Hypothesis; the positive controls show that
   both `calls` and `taint` can report a hit.

## Interpretation

- **FACT (C-5286):** OBJDLL addresses the 0x1000-byte data volume through a
  21-entry field table at `0x01e33290` (EU2011); index 9 is exactly bytes
  `0x18c..0x1a0` (10 u16), index 8 `0x182..0x18c`, index 20 the whole block.
- **OBSERVED (C-5287):** in EU2011 no call site in `Navi.exe`,
  `NaviGeneralCC.dll`, `DiagnosisCC.dll` or OBJDLL asks the store for index 9
  (27 of 31 indices resolved, the other 4 accounted for); readers ask for
  3, 4, 7, 8 or the whole block.
- **OBSERVED (C-5288):** the whole-block copies reach 40 functions within two
  call levels; their constant header accesses cover `0x0c0..0x18a` and
  `0x1ac..`, but none falls in `0x18c..0x1a0` (positive control: the bounds
  reader `0x003f7008` at `0x184..0x18a`).
- **OBSERVED (C-5289):** the data path is `0x0041a438` (file read) →
  `0x0041a304` (u16 swap, `writeDataVol`) → `0x00377ae0` (`readDataVol`,
  `writeDiscVol`) → five `readDiscVol(…, 20, …)` copies; the M4.48 Stop
  condition is met.
- **HYPOTHESIS:** the `0x18c` list is not consumed by the EU2011 head unit at
  all (it may be for the dealer update tool or for a later firmware that
  matches it against the speech sets), or it is read by a loop over the
  whole block (e.g. a hash) that a constant-offset scan cannot see.
- **UNKNOWN:** whether any EU2011 code reads `0x18c..0x1a0` at run time; this
  static negative covers constant offsets and the field API only.

## Conclusion

M4.48 is `blocked`: there is no function VA to run in L3, so the done-when
(an L3 run that changes when `05` → `3f`) cannot be met statically. New
claims C-5286–C-5289; `docs/format/file-header.md` and `drstr.md` now cite
the field table and the negative instead of "not yet traced" (the `0x18c`
codes stay as M4.22/M4.38 left them: a value join, not a firmware verdict). Unblock: a read watch on the
header copies during a full `Navi.exe` run (M8.E4, L4) or a car/bench
mutation (`05` → `3f`, L5); follow-up task M4.50.
