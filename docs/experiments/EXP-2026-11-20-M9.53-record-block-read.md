## Question

M9.13 showed that the firmware reads our tile's header, section tables and
directories like the factory tile. The road records (the zlib blocks
`tilewriter.py` writes) were never asked for. Can one map request (message
`0x14b5`) make the data-access task read, inflate and load a record block,
and does it do the same with the record we wrote?

## Hypothesis

A map request for the mesh of M9.13's changed parcel (directory `0xa10b100`
of `B48R058R`, slot 17) makes the firmware read that slot's record block,
inflate it and load the inflated words. On the generated tile it reads *our*
record (at the place our pair entries give) and inflates it without error.
A wrong pair entry or a damaged record changes what is read or inflated.

**Falsifier (set before the runs):** the firmware reads the record block,
but no function loads the inflated bytes. Then the consumer is another task,
and the EXP must name the message that carries the buffer away. A second
falsifier for the controls: a damaged pair entry (M9.13 C2) or a damaged
record byte still compares SAME.

## Method

1. **Read the handler** (`sh4dis`): `0x004066ac` → `0x00405970` (the
   request check) → `0x00409828`/`0x0040904c` (client slots) →
   `0x0040a33c` (mesh to tile), `0x004089f4`/`0x00408b0c` (mesh decoders).
2. **Open a client and choose the mesh.** The tool opens client task 5 with
   `0x003ed6e8(1, 5, kind, out)` (as `SDL_task`'s init `0x003c001c` does
   for itself). It finds the mesh id by running the firmware's own decoders
   over the 16-bit halves of the id: y 2481 (= 51.70 × 48) and x −2642
   (= (17.45 − 100) × 32) give `0x26c18ab2`.
3. **Runs** (each one: a full mount at `--position 51.70,17.45`, then the
   request; about 40 s each):
   - F: factory card, `--request 0x26c18ab2`;
   - G: F plus `--replace MAPAL001/B48R058R.DAT=G.DAT`;
   - C2: G plus `--flip MAPAL001/B48R058R.DAT@0xa10d436:0xff` (a byte of
     the pair entry of slot 17 record 28, the byte M9.13's C2 flipped);
   - C3: G plus `--flip MAPAL001/B48R058R.DAT@0xa1b45d6:0x55` (byte `+0x20`
     of our compressed record);
   - FR: F with `--kind 0x40` (the router's kind).
4. **Watch.** For each read the tool records who loads the buffer, as before
   (M9.13). New: at the entry of inflate `0x0054233c` it watches the output
   window (`+12` next_out, `+16` avail_out of the stream) and records who
   loads the inflated record.
5. **Compare** with `datask_l3.py diff`: F/G, G/C2, G/C3, F/FR.
6. **Selftest controls** (`--selftest`, 8 new checks): a client
   with no slot; the request in state 3.

## Observations

**The request check** (`0x00405970`, EU2011, static):

- The client task (`+12`) must have a slot in the 24 × 64-byte table at
  data VA `0xd98fe0` (`0x0040904c` compares slot `+0` with the task and
  `+4` with `0xff`). The slot's mask (`+12`) must share a bit with the
  request kind `+16` (`0x00405a2a`–`0x00405a36`). The slot is written by
  `0x003ed6e8` (`0x003ed7ca`–`0x003ed7e0`: `+0` task, `+4` `0xff`, `+12`
  mask).
- At `0x00405aac`–`0x00405ab4` it reads the state word `0xd62490`; if it is
  3 the check fails. A failed check makes `0x004066ac` call
  `0x00405dac(9, …)`: reply `0x14b6` sub 5 with `+12 = 9`.
- The dispatcher `0x003ebee8` (`0x003ebf14`–`0x003ebf22`): progress word
  `0xd98fcc` = 1 and state word ≠ 3 → handler at once; otherwise a row with
  the defer flag goes to `0x003ebd44` first.

**Mesh to tile** (static + run): `0x0040a33c` compares `y >> 5` and
`x >> 5` (from `0x004089f4`, `0x00408b0c`; the mode word at data VA
`0x56389c` is `0x2000` in the run) with the 46 tile boxes at data VA
`0xd624a0` (24 bytes each; `+8` y0, `+10` x0, `+12` y1, `+14` x1). The boxes
are the `BxxRyyR` names read as hex: `B48R058R` is y 72–80 (`0x48`), x −88 to
−80 (`−0x58`). Decoded by the firmware: `0x26c18ab2` → y 2481, x −2642
(row 77, column −83); `0x24008800` → y 2304, x −2816 (the corner 72, −88).

**Run F (factory).** The mount: 28 reads (as in M9.13). The request: one
more read, then idle; state 2, progress 1.

## Interpretation

- **FACT:** one map request reads, byte-swaps and inflates one record block
  of the factory tile in the run (F), and the data-access task loads every
  inflated word (`0x003f6968`, 11,172 B) (C-5912).
- **FACT:** on the generated tile the same request reads **our** record:
  the firmware takes the position and length from our pair entries
  (`0xa1b4500`, `0x200`), inflates our 112-byte zlib stream to 184 bytes (the
  writer's size), checks the Adler-32 and answers the client exactly as for
  the factory record (C-5914). Verdict: **inflated, answered like the
  factory record**.
- **FACT:** the record-level gate has teeth: a flipped pair-entry byte
  (C2, SAME at mount in M9.13) changes the read length 128-fold; a flipped
  record byte (C3) stops the inflate (C-5915).
- **OBSERVED:** the reply to the client does not report the broken record
  in C3 (same words as G). Whether the client checks the inflated words
  itself is not seen here.
- **The falsifier fires in its weak form.** The inflated bytes *are* loaded
  in the data-access task, but only by the word swap and a 4-byte read
  (`0x004048cc`). No function walks the roads of the record here. The
  record goes to the client task: message `0x14b6` sub 9 (`+16` the mesh,
  `+20` the kind) (C-5916). The client is not part of the run. Walking
  our road records in the firmware is the next gate: **M9.58** (new).
- **Correction (C-5913):** state 3 is not "map ready". In state 3 the
  request check refuses every map request, and with progress 1 the
  dispatcher defers `0x14b5` exactly when the state is 3. M9.52 read the
  test the wrong way round. The mount's end state (2, progress 1) is the
  state in which requests are served. M9.52's records are corrected in
  place and its EXP lists this under "Overtaken by a later commit".
- **UNKNOWN:** how the record's byte start inside the 256-byte step reaches
  the buffer. The request names sector `0x1436b` with `+8 = 0x700`, but
  the inflate gets the bytes from `+0xf4` (factory) / `+0xb6` (G). The
  `datask_l3` `pos` column shows the 256-aligned position (C-5912).
- **OBSERVED:** kind `0x40` reads a different block (`0x113ca500`, inside
  the section-4 area of M9.13's map) for the same mesh (C-5917). What it
  holds is not decoded here.
- **Scope:** EU2011 build A, EU card, PySh4 with the models in
  `datask_l3.py`. The client task and its slot are opened by the tool.
  Not a statement about the unit.

## Conclusion

The hypothesis holds; the controls differ. The firmware's data-access
task reads, inflates and loads a record block of the factory tile, and
does the same with the record we wrote, from the place our directory gives.
The road records themselves are walked by the client task that gets
`0x14b6` sub 9, which this run does not include (M9.58).
