## Question

Which byte(s) of a level-1 road-shape record (`section 1`, even pair, tag
`0x00fa`) carry the country code, and does the provisional road-class mapping
M5.4 writes (`fa_encode.CLASSES` → `(layer, c1)` / `tilewriter.py` class table)
match the `(draw layer, shape class nibble)` fields of factory records?

## Hypothesis

M5.4 passed a provisional `--country 616` "taken from the factory context" and
used `fa_encode.CLASSES` as a provisional OSM→class table (C-1064). Hypothesis:
the country is a fixed field in the 0x00fa record header (the position
`fa_encode.build_record` writes), and the factory `(layer, cls_hi = w[p+2]>>12)`
values for common road classes match `fa_encode.CLASSES`' level-1 `(l1, c1)`
tuples.

**Falsifier (country):** factory records show no consistent word position for a
country-like value, or the position differs from the writer's header word 20.
**Falsifier (class):** a common road class (residential/service/trunk/primary,
identifiable by the CLASSES-matched `(layer,cls)` bucket and overwhelming
frequency) has a different `(layer, cls_hi)` encoding than the CLASSES mapping,
or the fields vary by kind in a way incompatible with the table mechanism.

     reads the field the writer targets.
   - *Positive (class mechanism, synthetic):* `tilewriter.py --selftest` (52/52)
     builds records via the CLASSES mapping and re-reads them with
     `fa_encode.parse_record`, confirming `(layer, cls)` round-trips through the
     writer→reader path.
   - *Positive (semantic/geographic, factory):* `B30R060R` (Italy, 380) is a
     small clean tile (37 records, 784 shapes, only 5 `(layer,cls)` values, no
     noise) — a tight control. `B48R058R` is a cross-border tile: `w[20]` takes

     `B28R078R` is 724(ES). For class, `(5,8)` is the overwhelming majority in

     controls.
   - *Negative (false position):* scanning for the `item_words` marker `0x0bc0`

## Observations

### 1. Writer control (synthetic)

`tilewriter.build_road_record(..., country=616)` (residential, level 1) produces
a `0x00fa` plain with `w[19]=0x8104`, `w[20]=616 (0x268)`, `w[2]=0x00fa`. So the
writer targets header word 20 for country and sets word 19 to `0x8104`.

### 2. Factory country word (45,887 level-1 0x00fa records)

| tile | records | `w[19]` | `w[20]` (ISO 3166 numeric) → count |
| --- | ---: | --- | --- |
| `B48R058R` | 43,951 | 0 (all) | 616 PL → 20547, 276 DE → 12292, 203 CZ → 5553, 40 AT → 3196, 703 SK → 2113, 348 HU → 250 |
| `B28R078R` | 1,899 | 0 (all) | 724 ES → 1898, 0 → 1 |
| `B30R060R` | 37 | 0 (all) | 380 IT → 37 |

`w[19]` is `0` for **every** record in scope (45,887/45,887). `w[20]` carries
geographically coherent ISO 3166-1 numeric country codes and **varies per record
within a cross-border tile** (`B48R058R`: PL/DE/CZ/AT/SK/HU). C-1062's "factory
country word was not confirmed (1 of 43,951 records matched the pattern)" is
explained: the prior probe did not read header word 20 with this layout.

### 3. Factory class/layer fields, full scans (with noise caveat)

`parse_record` reports `shape.cls = w[p+2]>>12`, `shape.layer` from the layer
table slot. Full scans of `B48R058R`/`B28R078R` yield very large totals with
regular-count buckets (65,534/131,067/262,132/327,706 and many `(l,0)/(l,14)/
(l,15)`) not treated as road classes here. The CLASSES-relevant and notable
buckets (counts from full scans):

| (layer, cls_hi) | `B48R058R` | `B28R078R` | `B30R060R` | `fa_encode.CLASSES` level-1 `(l1,c1)` |
| --- | ---: | ---: | ---: | --- |
| (4,9) | 138,025 | 6,618 | 62 | service, track |
| (5,8) | 1,012,779 | 30,398 | 656 | tertiary/tertiary_link/unclassified/residential/living_street |
| (6,4) | 21,999 | 481 | — | trunk, trunk_link |
| (6,5) | 56,463 | 845 | 27 | primary/primary_link, secondary/secondary_link |
| (7,1) | 6,276 | 259 | — | motorway, motorway_link |
| (6,7) | 166,003 | 3,194 | — | **no CLASSES match** |
| (6,6) | 5,923 | 72 | — | **no CLASSES match** |
| (7,2) | 1,573 | 65,576 | — | **no CLASSES match** (motorway-adjacent layer) |
| (0,10) | 65,578 | 1,265 | 26 | **no CLASSES match** |
| (0,12) | 18,213 | 2,016 | 13 | **no CLASSES match** |

All five CLASSES `(layer,c1)` tuples appear in factory data with
semantically/geographically plausible roles (motorway at layer 7/class 1, trunk
6/4, primary/secondary 6/5, residential/tertiary family 5/8 dominant, service
4/9). Factory also contains additional `(layer,cls)` values absent from
`CLASSES`; these are **unmapped** by the provisional table (OQ, M5.3/M4.17
scope). `B30R060R` (clean control) contains only CLASSES-matched buckets plus
`(0,10),(0,12)`.

### 4. Writer-vs-factory header difference (w[19])

`fa_encode.build_record` (level 1) writes `w[19]=0x8104, w[20]=country`;
factory level-1 records write `w[19]=0, w[20]=country`. The country *position*
(w[20]) is confirmed; the w[19] constant differs. `parse_record` does not read
`w[19]`. M5.4's splice wrote records with `w[19]=0x8104` and L2 passed (C-1065);
firmware sensitivity to w[19] is unknown (rule 13). This EXP's companion change
aligns `fa_encode.build_record` level-1 `w[19]` to `0` for factory fidelity.

### 5. item_words / 0x0bc0 (negative control)

`fa_encode.item_words` encodes `[..., 6, 0x0bc0, country, ...]` and is stored in
`build_record.last_items`, not packed into the 0x00fa plain. Scanning the 0x00fa
plain for `0x0bc0` yields geometry false positives; it is not the road-shape
record country locator.

## Interpretation

- **FACT:** Level-1 0x00fa road-shape record header word 20 (`w[20]`, 0-based
  over the record's big-endian `u16` words) is the per-record ISO 3166-1 numeric
  country code. Confirmed on 45,887 factory records across 3 tiles (6 countries
  in one cross-border tile; 724 ES; 380 IT), all `w[19]=0`. (C-2660)
- **FACT (mechanism):** The road-shape class is encoded as `(layer, cls_hi)` =
  (layer table slot, `w[p+2]>>12` of the shape), matching what
  `fa_encode.layer_class`/`shape_words` write and `parse_record` reads. All five
  `fa_encode.CLASSES` level-1 `(l1,c1)` values occur in factory data in
  semantically plausible buckets. (C-2661)
- **OBSERVED:** Factory records contain additional `(layer,cls_hi)` values not
  present in `fa_encode.CLASSES` (e.g. `(6,7),(6,6),(7,2),(0,10),(0,12)` plus
  low-frequency/noisy buckets in full scans). The OSM→class *value* mapping is
  therefore incomplete/provisional, not globally confirmed. (C-2662)
- **OBSERVED:** `fa_encode.build_record` level 1 wrote `w[19]=0x8104` while
  factory uses `w[19]=0`; aligned to factory in this task. Firmware effect
  unknown (rule 13). (C-2663)
- **HYPOTHESIS:** Unmapped factory `(layer,cls)` values (notably `(6,7),(7,2)`)
  correspond to road categories not covered by the 15-entry CLASSES table
  (M5.3/M4.17 scope); `(0,10),(0,12)` may be special/non-standard road records.
  Not established here.
- **UNKNOWN:** Whether the navigation firmware reads `w[20]`/`w[19]` or renders
  by `(layer,cls_hi)` exactly as decoded (no L3 run; rule 13). `item_words`
  country in the names/partner structure is separate and out of scope.

## Conclusion

The "country word" is confirmed as level-1 0x00fa header **`w[20]` = ISO 3166-1
numeric, per record** (45,887 records, `w[19]=0` in factory). The provisional
class *mechanism* `(layer, cls_hi=w[p+2]>>12)` = `CLASSES (l1,c1)` is confirmed
for all five CLASSES buckets present in factory; the OSM→value table remains
**provisional/incomplete** because factory contains unmapped `(layer,cls)`
values, so `tilewriter.py` keeps a **named provisional** class mapping with the
evidence gap stated (global semantics remain M5.3/M4.17). `tilewriter.py`
country handling and `fa_encode.build_record` level-1 `w[19]` are aligned with
factory observations. `docs/format/map-tiles.md` and `claims.md` updated;
C-1062's "not confirmed" is refined (not retracted) by C-2660.
