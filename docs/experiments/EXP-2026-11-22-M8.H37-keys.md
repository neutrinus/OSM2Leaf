# EXP-2026-11-22-M8.H37: hard keys, their sources and the code table the UI reads

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** `archive/head256.img` — 134,217,728 bytes read, SHA-256
  `d3e5eac9cb5b4cbdf2618e686fb3ed1b273d3c6b75753cfc14f31d35c79fd9be`
  (the first 128 MiB of the EU 2011 card image; full card
  `leafre-work/leaf2011.img`, SHA-256 `105e2032…76307`)
- **Tools:** Python 3.15.0 (stdlib only); repo tools `tools/cerom.py`,
  `tools/ce_strfind.py`, `tools/sh4xref.py`, `tools/sh4dis.py`,
  `tools/nk_decomp.py` (kernel routine `DECOMP_SECT 0x88037464`),
  `tools/kep_tables.py` (new, with `--selftest`); no external disassembler
- **Claims:** C-7340–C-7349
- **Supersedes:** none
- **Superseded by:** none

## Question

For each ZE0 hard key, which physical source carries it (display unit `SCI3:`,
audio micom `SCI1:`, CAN steering wheel, GPIO matrix), what raw code does it
arrive with, and where is the table that the UI reads to turn that code into a
virtual key?

## Hypothesis

The display unit and audio micom both send framed key commands that a single
driver (`kepdrv.dll`) translates through static `{u8 raw, u8 vk}` tables into
`keybd_event`/`WM_KEYDOWN`. **Falsifier:** one raw code maps to two functions
depending on a mode that the table does not show.

## Method

1. **Sample and hash.** The 128 MiB head above. `python3 tools/cerom.py
   --image-start 0x3e00200 archive/head256.img romhdr` reports
   `nummods 0x5b`, `physfirst 0x88000000`, `physlast 0x886e18a4` — the build-B
   kernel image described in `docs/hardware/head-unit.md`.
2. **Commands.** Runnable as written from the repository root:

   ```bash
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img modules \
     | grep -iE ' lcddrv| anwdrv| kepdrv'
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x3e00200 \
     --module lcddrv.dll --encoding utf-16le --control 'SCI3:' 'SCI3:'
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x3e00200 \
     --module anwdrv.dll --encoding utf-16le 'SCI1:' 'RCV_FLAP_KEY_STATUS'
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x3e00200 \
     --encoding all 'KEPV' 'KeybdEvent' 'KEP_KEY_TOUCH'
   python3 tools/sh4xref.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --to 0x03a02bc8    # (module is lcddrv.dll)
   python3 tools/sh4xref.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --to 0x03a117ac     # FindTable log string
   python3 tools/sh4xref.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --to 0x03a12074     # GetVkey log string
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --va 0x03a161dc --count 120   # FindTable
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --va 0x03a16e60 --count 100   # GetVkey
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --va 0x03a15f40 --count 90    # GetMatrixKey
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll \
     --image-start 0x3e00200 --va 0x03a15d58 --count 130   # table installer
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img \
     decompress --modules kepdrv.dll --check --json
   python3 tools/kep_tables.py --selftest
   python3 tools/kep_tables.py archive/head256.img
   ```

   (The `HardRemoconKey_notice` xref is the same command with
   `lcddrv.dll` as the module and VA `0x03a02bc8`.)

3. **Controls.** *Positive:* `ce_strfind` with `--control 'SCI3:'` finds the
   `SCI3:` string in `lcddrv.dll`, and `kep_tables.py --selftest` finds a
   planted duplicate raw code in a synthetic table (and rejects a truncated
   one). *Negative:* the same search for `NO_SUCH_KEY_TOKEN_XYZ` reports
   `hits 0`; the decoder's truncation case raises `ValueError` rather than
   silently shortening a table. A negative result without these positives is
   not used.
4. **Scope.** Build B (kernel) only, 91 modules; the three modules named
   above plus their uncompressed sec0 and the two compressed `.data` sections
   of `kepdrv.dll` (sec1 696 B / 648 B init, sec2 896 B). Build A was searched
   for key-name strings (`KEY_`, `HardKey`, `STEERING`) and returned only
   registry `HKEY_*` matches, so no build-A key names are claimed. Compressed
   sections of other modules are excluded. Not executed on firmware (no
   L3/L4/L5).
5. **Falsifier.** Duplicate raw codes within one installed table, or a mode
   that changes a code's function without appearing in the table installer,
   would refute the "one code → one function per mode" table model. Stated
   before the result.

## Interpretation

- **FACT:** `SCI3:` is opened in build-B `lcddrv.dll` (string VA `0x03a0272c`)
  and `SCI1:` in build-B `anwdrv.dll` (VA `0x03b890f8`); the head-unit port
  table is thereby confirmed at the code level, not only as strings.
- **FACT:** `kepdrv.dll` receives LCD keys through `InputLcdKey`
  (`0x03a18210`) from `LcdKeyDataMain` (`0x03a19080`, `IOCTL_LCD_GET_KEY`),
  audio-micom keys through `NotifyAudioCpuKey` (`0x03a15fbc`), steering/CAN
  through `InputCanData`/`InputStconKey`, and matrix keys through
  `GetMatrixKey` (`0x03a15f40`). All VAs are from `cerom.py`/`sh4xref`.
- **FACT:** the UI code is `KeybdEvent` (`0x03a17528`) → `AuiKeyEvent`
  (`0x03a16f20`) → `keybd_event` with `WM_KEYDOWN`/`WM_KEYUP`; `GetVkey`
  (`0x03a16e60`) resolves `(KeyType, HardKeyCode)` via `FindTable`
  (`0x03a161dc`) and the `{u8,u8}` tables at `0x01f42xxx`.
- **FACT:** the tables are selected by a panel/maker config word (four
  variants for KeyType 1/2), so the mode is explicit in the installer.
- **OBSERVED:** raw `0x01` occurs twice in the `0x10101100` panel variant
  (`0x01f42140`); the second entry is shadowed by the linear scan. This is
  not a mode-dependent double mapping, so it does not trigger the falsifier.
- **OBSERVED:** the VK set of the KeyType-3 table (`0x17`, `0x18`, `0x19`,
  `0x1a`, `0x21`) looks like a navigation-function vocabulary; no firmware
  string names MAP/MENU/DEST/ZOOM, so those labels remain manual wording.
- **HYPOTHESIS:** KeyType 3 is the display-unit hard-key class and KeyType
  5/6 the steering/audio classes. The code paths are located; the `KeyType`
  argument was not traced to a constant at each call site.
- **UNKNOWN:** the runtime panel word; physical identity of each `0x17`..`0x1a`
  key; long-press/repeat timing; any execution against firmware.

## Conclusion

`docs/firmware/keys.md` now carries one row per key code with name, source,
raw code and the VA of the table or switch, plus the four source entry points
and the panel-mode selector. Claims C-7340–C-7349 record the source VAs, the
translation chain, the table block and the falsifier scan. The falsifier did
not fire: no raw code maps to two functions in a way the table installation
code does not show. Still open: name↔code assignment, runtime panel word and
all dynamic behaviour (L3/L4/L5).
