## Question

When the data-access task of `Navi.exe` (EU2011) receives a message `0x14f4`,
which file and which offsets does the map-file layer read, compared with the
TMC location request `0x14e4`; are they the `RDSTM001.DAT` link groups
(`0xcda000..EOF`, M4.16e)?

## Hypothesis

M4.49/M4.51: `0x14f4` shares the handler of `0x14e4` and has its own slot in
the sector reader `0x00417618`, so it may be the request that reads the link
groups. **Falsifier (stated before the run):** an L3 `0x14f4` request whose
reads stay outside `RDSTM001.DAT` for every value of the request words the
handler copies into its context, while the `0x14e4` control in the same run
reads its known file (`RDSTM001/LCTBL001.DAT`, C-4667). The hypothesis
survives if any `0x14f4` read lands in `RDSTM001.DAT` `>= 0xcda000`.

## Interpretation

- **VERIFIED (run, L3, C-5680):** in the data-access path, a `0x14f4` request
  reads a `REFER001` family file chosen by its sub word (body +10 → ctx +124,
  the search type of `0x003fbed8`, C-4666): 1 `POINT001.DAT`, 2
  `ADDRE001.DAT`, 4 `INTER001.DAT`, 3 `FRWAY001.DAT` (absent, no read); the
  file number `n` is 1 in every call.
- **VERIFIED (run, L3, C-5681):** the control `0x14e4` sub 1 reads
  `RDSTM001/LCTBL001.DAT` header and index pages (`0x4600`, `0x5600`) in the
  same run: only `0x14e4` turns type 1 into the TMC location table (C-4667).
- **OBSERVED (C-5682):** no `0x14f4` request reaches `RDSTM001.DAT`, and the
  M4.51 static chain (`0x00413828` → `0x004129d0` → `0x00417618`,
  `0x004125a8`) is not entered by either request in this path; the
  request goes `0x004007b0` → `0x0041330c` → `0x004003f4` → `0x003fbed8`.
- **HYPOTHESIS (C-5683):** `0x14f4` is a generic REFER-family record request
  (the counterpart of `0x14e4` for POINT/ADDRE/INTER/FRWAY), so the RDSTM link
  groups are read by another path; the `0x14f4` slot of `0x004129d0` (index 2)
  belongs to the map-file task's page cache, which this path did not enter.
- **UNKNOWN (C-5684):** which words a real `0x14f4` sender sets beyond +12,
  and which function reads `RDSTM001.DAT` `0xcda000..` (M4.49 stays blocked).

## Conclusion

The M4.53 done-when is met: an L3 run reports file and offsets for `0x14f4`
requests (`REFER001` `POINT001`/`ADDRE001`/`INTER001` by sub word) and for
the `0x14e4` control (`RDSTM001/LCTBL001.DAT`). The lead that made `0x14f4`
the RDSTM link-group reader is refuted for the data-access path (falsifier
met). M4.49 and M4.51 stay `blocked`; their remaining unblocker is M8.E4 (a
full `Navi.exe` run with a read watch on `RDSTM001.DAT` `0xcda000`/`0xe78500`).
`rdstm.md` "Firmware reader" paragraph updated.
