## Question

Which parts of the unit flash does `-M ze0` need, and can they be produced
without copying any user data of the real unit?

## Hypothesis

Exploratory at the start. After run B: the firmware formats default stores
in RAM when the flash is erased, so the RAM mirrors of such a boot are a
valid "factory" content for `SRAM` and `VFlash`. Falsifier: an image built
from those mirrors stops earlier than the real dump, or logs the same load
errors as an erased flash, or a scan of it finds a value of the real dump.

## Inputs

| Item | Value |
| --- | --- |
| Flash regions | `PROD` `0xA000`, NK1 `0x40000`, `SRAM` `0x400000`–`0x4FFFFF`, VFlash `0x500000`–`0x7DFFFF` |
| VSram mirror | physical `0x09a40000`, 1 MiB (`docs/hardware/head-unit.md`) |
| FlashManager buffer | physical `0x09b40000` |
| Repo tool | `tools/unitflash_anon.py` |

## Method

1. **Sample and hash.** As above. Every run: NK1 + US card, panel peer,
   330 s of wall time, then the two mirrors and a screenshot.
2. **Commands.** `$Q` is the built `qemu-system-sh4`, `$C` the US card,
   `$D` the real dump, `$W` a work directory outside the repository.

   ```bash
   python3 tools/unitflash_anon.py prod --from $D -o $W/prod-anon.bin
   python3 tools/unitflash_anon.py build --bare --prod $W/prod-anon.bin -o $W/bare.bin
   python3 tools/ze0_launch.py --qemu $Q --card $C --flash $W/bare.bin --workdir $W/b --timeout 370 &
   sleep 330
   python3 - $W/b <<'P'
   import sys; sys.path.insert(0, 'tools'); import ze0_screenshot as z
   w = sys.argv[1]
   z.hmp(w + '/mon.sock', 'pmemsave 0x09a40000 0x100000 "%s/mirror.bin"' % w)
   z.hmp(w + '/mon.sock', 'pmemsave 0x09b40000 0x300000 "%s/flm.bin"' % w)
   z.screen(w + '/mon.sock', w + '/screen.png')
   P
   wait
   python3 tools/unitflash_anon.py capture --mirror $W/b/mirror.bin --flm $W/b/flm.bin \
       --sram $W/sram-anon.bin --vflash $W/vflash-anon.bin
   python3 tools/unitflash_anon.py build -o $W/flash-anon.bin --prod $W/prod-anon.bin \
       --sram $W/sram-anon.bin --vflash $W/vflash-anon.bin
   python3 tools/unitflash_anon.py check $W/flash-anon.bin
   python3 tools/unitflash_anon.py scan $W/flash-anon.bin --dump $D --list-shared
   python3 tools/ze0_launch.py --qemu $Q --card $C --flash $W/flash-anon.bin --workdir $W/f --timeout 370
   grep -a -c 'OBJ_BackUp_Load Error' $W/f/serial.log
   ```

3. **Controls.** Positive: run A, the real dump, same options (0 load
   errors, the car at its saved place). Negative 1: run B, the bare image
   (erased user areas). Negative 2: run N, the final image with one bit
   flipped at `+0x1234` in both copies of store 0. The scan has its own
   controls in `unitflash_anon.py --selftest` (a leaked PIN, position word
   and name are each found).
4. **Scope.** One unit (US `QY7200ND`), one card (US 2011), boot to the map
   without touch input. Not covered: an ignition-off cycle, the EU card,
   any screen behind a tap.
5. **Falsifier.** As in the hypothesis.

## Observations

O1 (what the dump holds; counts only). `SRAM` area 3: destination history
and address strings, Bluetooth device names. Area 2: 297 records of 32 bytes
with one packed position word (Poland). Area 1: the locator backup with the
saved car position. VFlash: two phone books in UTF-16, call lists with
numbers, charging-station lists with addresses. `0x360000`: one crash report
(2593 text records, 2017; not copied anywhere). `PROD`: serial at `+0x50` and again at `+0x142`, PIN at
`+0x60` and `+0x100`. No VIN-shaped string was found.

O2 (store sum). In all eight `SMST` stores of the dump the u32 at `end −
0x10` equals the sum of all little-endian u32 words before it; then 8 zero
bytes and `SMED`. `VSram.dll` names the check (`CheckAreaData : SUM NG`,
`AreaStartID NG`, `AreaEndID NG`, `FormatVersion NG`).

O3 (runs).

| Run | Flash | `OBJ_BackUp_Load Error` | `[VSRAM] … NG` | Map |
| --- | --- | --- | --- | --- |
| A | real dump | 0 | 0 | the car's saved place (Kentucky) |
| B | bare: `PROD` + NK1, rest erased | 11 (objects 02 03 05 06 07 09 0A 0C 10 17 19) and `ERROR UnLoad BackUpInfo @OBJ_Carpos_initialize` | 6 × `AreaStartID NG` | default (Los Angeles airport) |
| C | B + the dump's `SRAM` | 1 (object 17) | 0 | not recorded |
| D | B + `SRAM` from the mirror of B | 2 (objects 0A, 17) | 0 | default |
| F | B + `SRAM` and VFlash from the mirrors of B (the committed files) | 1 (object 0A) | 0 | default |
| G | as F, mirrors taken from F again | 1 (object 0A) | 0 | default |

All runs: `Target ID Code >> 10200212`, `Launcher [Area:20 >> USA]`, no
`IOCTL_FMD` error. Run F: `AppLch >> Finish Launch Threads` reached, the
other `ErrorLogMsg` lines by process are the same as in run A (ANTITHEFT 1,
AUI 3, AV_CMN 3, CAMERA 1, CONSULT 1, DEVM 3, NAVI 2).

O4 (mirrors). After run A the first `0x80000` bytes of the VSram mirror are
the four stores back to back (sizes `0x30000`, `0x10000`, `0x10000`,
`0x30000`), each with its `SMST` header; the next `0x80000` are a second
copy. The FlashManager buffer equals the dump's VFlash byte for byte (736 of
736 pages). After run B the mirror holds stores with generation 1 and copy
0 for areas 0, 1 and 3 (area 2 has no header in RAM), and the FlashManager
buffer holds `0x2D3000` bytes of defaults.

O5 (scan of F against the dump, `unitflash_anon.py scan`).

| Search | Result |
| --- | --- |
| serial, PIN unit half, 16-byte password, long serial (raw and hex text) | 0 hits each |
| strings ≥ 6 characters of the dump's user areas | 4133; 22 also in F |
| digit runs ≥ 7 | 813; 9 also in F |
| repeated position words | 15; 0 in F |

The 22 shared strings are format and version labels, keyboard tables,
`Info from NISSAN`, three numbers `18604…`, an APN host and a CARWINGS URL.
All of them are also in run B's mirrors, which were made without the dump.

O6 (run N, one bit flipped in both copies of store 0). The log has two
lines `[VSRAM]CVSramBackupCtrl::CheckAreaData : SUM NG
[0x96012500][0x960124FF]`: the sum the driver computes and the stored one
differ by the flipped bit. Six objects then fail to load (03 05 0A 0C 10
19), so these six are kept in area 0.

## Interpretation

- **FACT:** the store sum rule (O2), and the firmware accepts stores written
  with it (runs D, F, G: no `NG` line).
- **FACT:** `-M ze0` needs only `PROD` and NK1 from the flash to reach the
  map; boot loaders, the crash log, `VEUP`, the sub-test program and the
  bytes after NK1 are not read (run B boots).
- **OBSERVED:** object 17 of the object store is kept in VFlash, the other
  ten in `SRAM` (runs C, D, F).
- **OBSERVED:** the committed image is built without reading the dump's
  user areas; from the dump come only the fields of `PROD_KEEP` in
  `unitflash_anon.py`.
- **UNKNOWN:** what object 0A is and when the firmware first saves it. A
  boot does not; an ignition-off cycle is the likely place.
- **UNKNOWN:** the meaning of `PROD +0x90` (9 bytes) and of the two bytes
  before the long serial at `+0x140`; both are kept.

## Conclusion

`firmware/unit-flash/` now holds `prod-anon.bin`, `sram-anon.bin` and
`vflash-anon.bin`; `unitflash_anon.py build` (or `ze0_launch.py --flash
anon`) makes the 8 MiB image. It boots to the map with one load error
instead of eleven. It does not reproduce the saved locator state of a
driven car: the car starts at the firmware default, so work on the
"car stays in Kentucky" problem (M8.H78, M8.H32) still needs a real dump.
