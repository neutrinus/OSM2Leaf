## Question

At L4 (QEMU `-M ze0`), which card files under the map tree does `Navi.exe`
actually read during one EU2011 boot to idle, and which byte ranges of each
file — as recovered by mapping the guest's SD block reads back through the
card's FAT32?

## Hypothesis

The SD reads of one boot are attributable to individual card files through the
FAT32 cluster chains, and the resulting file list contains at least
`MMAIN001.DAT`, `DRSTR001.DAT` and `CMP.LST` (the three files the L3 mount is
known to read). Falsifier from the task: the trace shows no read of any map
file although the UI reaches idle — then the map loads lazily and the scenario
needs a position (M8.H31); that is reported honestly, not hidden.

## Plan (written before code)

**Approach.** Build one new tool, `tools/ze0_sdtrace.py`, that turns a block-read
log plus a card image into a per-file, time-ordered read list, a per-file
coverage table and JSON. It has two trace grammars, both derived from committed
sources (nothing guessed):

1. **QEMU `-trace sdcard_read_block`.** Source of the grammar: this exact QEMU
   11.1.3 tree's `hw/sd/trace-events` line
   `sdcard_read_block(uint64_t addr, uint32_t len) "addr 0x%" PRIx64 " size 0x%x"`
   and its only caller `hw/sd/sd.c:sd_blk_read()`; `sd_req_get_address()` maps
   the SDHC CMD argument to `arg << 9` (HWBLOCK_SHIFT), and `sd_part_offset()`
   returns 0 for an SD card, so the logged `addr` is a **byte offset into the
   card image** and `size` is a byte count. Lines look like
   `sdcard_read_block addr 0x6400400 size 0x200`.
2. **HPB-DMAC transfer log already parsed by `tools/ze0_sdhost.py`.**
   `ze0_sdhost.decode_dma()` pairs `ze0-sdhiN: wr +0x00/0x04/0x06` with
   `ze0-hpbdmac: chN read ... crc32 ...`, yielding `(port, cmd, arg, dir,
   nbytes, ...)`. For SDHC CMD17/CMD18 the byte offset is `arg * 512` — the same
   conversion `ze0_sdhost.check_card()` already uses.

**FAT/trace grammar source.** The card→file map is derived from
`tools/cardcheck.py:Fat32Image` (MBR → FAT32 boot sector → FAT chains →
directory entries, including the WinCE LFN quirk) and `tools/leafimg.py`. Each
file's cluster chain is converted to a sorted list of on-card byte extents
`(card_start, card_end, file_path, file_offset, file_size)`. A read event
`(card_start, length)` is overlapped against these extents; the per-file,
file-relative byte ranges are emitted. A read whose extent runs past a file's
logical size is reported as **cluster read-ahead** (whole 64 KiB clusters are
the FAT unit; a 4 KiB `MMAIN001.DAT` still occupies one cluster) — the exact
file range is clamped to the file size and the cluster-level range is reported
alongside. A block that overlaps no file extent is reported as **unmapped**,
never silently attributed.

**Files touched.** New `tools/ze0_sdtrace.py` (self-contained, stdlib only,
`--selftest` with a synthetic FAT fixture, `--json`); `docs/research/reader-coverage.md`
F4 column on rows where a file is seen; this EXP; claim rows C-7050–C-7059;
this task's own TODO line via `tools/board.py`. No other task's files.

**Intended Done when.** `python3 tools/ze0_sdtrace.py RUNDIR --card CARD --json`
lists every file opened under the map tree with byte ranges for the EU2011
boot (at least `MMAIN001.DAT`, `DRSTR001.DAT`, `CMP.LST`; a missing one is a
finding); `--selftest` passes and is auto-discovered by `tools/selftest.py`;
the EXP compares the list with `tools/datask_l3.py mount`; reader-coverage F4
rows updated where a file is seen; `board.py done M8.H8` names this EXP.

## Method

**Spec, five parts.**

1. **Sample and hash.** The card image and head above; both SHA-256 values were
   printed by `sha256sum archive/head256.img archive/sd-images/…eu.img` in the
   prepare step. No vendor bytes enter the repo.
2. **Commands.** Prepare (scratch `$W` outside the repo):

   ```bash
   W=$HOME/projekty/leafre-work/scratch/m8.h8
   python3 tools/ze0_ipl.py patch archive/head256.img -o "$W/ipl.txt"
   python3 tools/qemu-ze0/mkoverlay.py \
     archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$W/eu2011.qcow2"
   QEMU=~/.cache/qemu-ze0/build/qemu-system-sh4
   timeout 300 "$QEMU" \
     -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,\
   verinf=QSD-302-100,mapdb=16-16,ipl-patch="$W/ipl.txt" \
     -kernel archive/head256.img -drive if=sd,index=0,file="$W/eu2011.qcow2" \
     -nographic -serial file:"$W/l4run/serial.log" \
     -monitor unix:"$W/l4run/hmp.sock,server,nowait" -icount shift=0,sleep=off \
     -trace "enable=sdcard_read_block,file=$W/l4run/sd-trace.log" \
     2>"$W/l4run/qemu.stderr.log"
   # Done when:
   python3 tools/ze0_sdtrace.py "$W/l4run" \
     --card archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img --json
   python3 tools/ze0_sdtrace.py --selftest
   python3 tools/datask_l3.py mount archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --json "$W/l3-mount.json"
   ```

   The trace grammar is not guessed: it comes from this QEMU tree's
   `hw/sd/trace-events` and `hw/sd/sd.c` (`sd_blk_read`, `sd_req_get_address`,
   `sd_part_offset`); the FAT reader is `tools/cardcheck.py:Fat32Image`.
3. **Controls.** *Positive:* the `--selftest` synthetic FAT maps three known
   reads to three known file/offset pairs (17 checks). *Negative 1:* a bogus
   block at card byte `0x2222` overlaps no file extent and is reported
   `unmapped`, never attributed. *Negative 2:* a corrupted FAT (MMAIN001's
   directory entry repointed to cluster 99) makes its block read unmapped.
   *Falsifier control:* the boot reaches idle and the file list contains
   `MMAIN001.DAT`, `DRSTR001.DAT`, `CMP.LST`.
4. **Scope.** One EU2011 boot to idle; 10523 `sdcard_read_block` events; the
   card FAT has 480 files / 79294 extents. Excluded: `-d` register log (a probe
   with it produced the same 10523 events but 357 MiB of noise); the DMAC

5. **Falsifier.** If the trace showed no map-file read while the UI reached

## Interpretation

- **FACT (C-7050–C-7054):** one L4 EU2011 boot to idle yields an SD read trace
  that maps to 14 card files through the FAT, including all three expected
  files `MMAIN001.DAT`, `DRSTR001.DAT`, `CMP.LST`.
- **FACT (C-7055–C-7057):** the four mount-time files and the traffic file that
  the L3 data-task mount does not report are nonetheless read at L4; the L4
  file list is a superset of the L3 data-task read set on 6 of 7 files.
- **OBSERVED (C-7059):** of 3349 unmapped reads, 3143 start before the FAT
  partition (`0x6400400`) and 206 at/after it; only 1 starts at `0x5c00000`
  and 2048 in `0x5c00000..0x5cfffff`. This distribution is what the command
  prints; no single "all at 0x5c00000" claim is made. They stay unmapped —
  honest block-level reporting, not a false attribution. Bytes past a file's
  logical EOF are the last-sector/cluster tail (e.g. `CMP.LST` 19 B + 493 B),
  reported separately from the exact logical range.
- **HYPOTHESIS (C-7058):** the one L3-only tile (`B28R070R.DAT`) is a position
  input difference (L3 default position vs. no GPS in this L4 run), not a
  reader disagreement; a seeded position run (M8.H31) can test it.
- **UNKNOWN:** what consumes the 2048 unmapped reads in the
  `0x5c00000..0x5cfffff` band (pre-partition firmware area); not a card file,
  so out of this task's scope.

## Conclusion

The L4 SD trace is a Rule 13 witness: the full `Navi.exe` reads 14 files,
including every file family the mount is expected to touch. The new
`tools/ze0_sdtrace.py` makes this reproducible from any run directory plus the
card image; its synthetic fixture supplies positive and negative controls.
`docs/research/reader-coverage.md` F4 cells for the seen rows now record the
L4 factory-card observation (not an M8.E4 generated-card acceptance). No
format or claim was promoted beyond what the command printed. The falsifier is
not met.
