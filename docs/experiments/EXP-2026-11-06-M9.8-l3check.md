## Question

Can one command be the **L3 rung** of the verification ladder — run every
declared L3 target on a corpus, report `PASS`/`FAIL`/`SKIP`/`BLOCKED` per target
with its reader and claim IDs, and exit `0` only when every runnable target
passed — without ever turning an unlocated reader or an absent back end into a
pass?

## Hypothesis

Yes, because `runner.py run TARGET` (M9.5, C-1670) already returns exactly one
of those states per target and `corpus.py` (M9.7, C-1690) already supplies the
input and the Python verdict. The missing piece is only the ladder wrapper: a
target selection, a corpus resolver (build a temp corpus by default, validate a
supplied one), a status mapping that maps `MISMATCH`/`INVALID` to `FAIL` and
keeps `BLOCKED`/`SKIP` out of the pass count, and an explicit reader/claim
table so a target cannot disappear from the report silently.

## Method

```bash
python3 -m py_compile tools/l3check.py
python3 tools/l3check.py --selftest
python3 tools/l3_harness/corpus.py build /tmp/opencode/l3check-corpus
python3 tools/l3check.py --corpus /tmp/opencode/l3check-corpus
python3 tools/l3check.py --corpus /tmp/opencode/l3check-corpus \
    --target probe-zlib-cmf --json
python3 tools/l3check.py --corpus /tmp/opencode/l3check-corpus \
    --target hddinfo_compare                      # blocked target, exit 3
python3 tools/l3check.py --corpus /tmp/opencode/l3check-corpus \
    --target probe-zlib-cmf --engine ghidra       # absent back end, exit 3
python3 tools/l3check.py --corpus /tmp/opencode/l3check-corpus --target nope
python3 tools/l3check.py --build-corpus --target probe-zlib-cmf
python3 tools/selftest.py --only l3check
```

The synthetic corpus used for the CLI runs is byte-identical to the one in
EXP-2026-11-06-M9.7 (108 entries: 13 `cmp_ind`, 3 `drstr`, 2 `tile`, 90
`hdd_info`); its `manifest.json` is validated with size and SHA-256 checks
before any target starts.

Status mapping is fixed in the tool:

| `runner.py` status | ladder status | counted as a failure? |
| --- | --- | --- |
| `PASS` | `PASS` | no (the only pass state) |
| `MISMATCH`, `INVALID` | `FAIL` | yes |
| `BLOCKED` | `BLOCKED` | no, but never a pass |
| `SKIP` | `SKIP` | no, but never a pass |

Exit codes: `0` every runnable target passed, `1` a failure or an invalid
corpus/target table, `2` usage error, `3` nothing was runnable (all blocked or
skipped).

## Interpretation

- **FACT:** `l3check.py` runs the six declared targets on a supplied or freshly
  built corpus and reports `PASS` for the one runnable synthetic target and
  `BLOCKED` for the five readers with no located entry point; exit `0` because
  every *runnable* target passed.
- **FACT:** a blocked target run alone is `NO_RUNNABLE`, exit `3`, with
  `verdict: null` and `l3_claim: false`; an absent Ghidra back end is `SKIP`
  with the same exit; neither is counted as a pass.
- **FACT:** a valid corpus whose file no longer produces the expected verdict is
  `FAIL`, exit `1`; a corpus without `manifest.json`, or with a stale SHA-256,
  is invalid and runs nothing.
- **FACT:** the report carries a reader and claim IDs per target
  (`synthetic`/`C-1670,C-1690`, `hdd_info`/`C-521`, `hdd_info`/`C-520,C-528`,
  `—` for the three readers with no claim yet) and the tool fails if
  `targets.json` gains, loses or re-points a target without its evidence row.
- **OBSERVED:** `--root`/`--image` are recorded in the report as
  `NOT_IMPLEMENTED` (M9.12) and are not used as evidence; card-mode L3 is not
  claimed here.
- **OBSERVED:** the run is deterministic (two runs in one process produce an
  identical payload) and takes about 0.2 s on the 108-entry corpus with PySh4.
- **HYPOTHESIS:** when M9.6/M9.10/M9.11/M9.13 land, their targets become
  runnable without changing this tool beyond their `TARGET_EVIDENCE` row; the
  ladder then reports real reader verdicts and the synthetic probe remains the
  pipeline control.
- **UNKNOWN:** no firmware reader verdict exists for any generated format yet;
  the only `PASS` here proves the runner/dispatcher/corpus path, not that the
  unit accepts a card.

## Claim text (C-1700)

> `tools/l3check.py` is the L3 rung of the verification ladder. It resolves a
> corpus (a fresh `corpus.py` build in a new temporary directory, kept and
> printed, or a supplied `--corpus` root whose `manifest.json` is validated with
> size and SHA-256 checks before anything runs), runs every target declared in
> `tools/l3_harness/targets.json` through `runner.py run_target` on the
> requested back end (`--engine`, default `pysh4`), and reports one row per
> target with its reader, entry kind, claim IDs and status. `PASS` requires the
> engine verdict to equal the target's `expect.verdict`; `MISMATCH`/`INVALID`
> are `FAIL`; a reader with no located entry point is `BLOCKED`; an absent back
> end is `SKIP`; a missing corpus file or manifest is `FAIL`, never a skip. It
> exits `0` only when at least one target was runnable and every runnable
> target passed, `1` on a failure or invalid input, `2` on a usage error, and
> `3` when every target is blocked or skipped (nothing claimed). A built-in
> reader/claim table is validated against `targets.json`, so an added or
> renamed target makes the run fail instead of disappearing; `--selftest`
> covers the synthetic probe, a blocked target, a tampered corpus (`FAIL`), an
> absent back end (`SKIP`) and a missing manifest, with no vendor data. The
> tool's own claim is C-1700; a synthetic `PASS` is pipeline evidence, not a
> firmware reader verdict, and `--root`/`--image` are recorded only because
> card-level L3 is M9.12. Status: VERIFIED (tool, synthetic corpus).
