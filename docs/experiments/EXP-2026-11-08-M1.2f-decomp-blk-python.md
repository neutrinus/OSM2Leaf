# EXP-2026-11-08-M1.2f: Port nk.exe block codec (DECOMP_BLK) to pure Python

- **Status:** failed (blocked — done-when not met)
- **Date:** 2026-11-08
- **Sample:** `IMG256` (first 256 MiB of EU 2011 card `LEAF_2011-2012_QSD-309-101_navi158_eu.img`), SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; EXP-49 section bytes read from this image (file offsets `0x01580ce0` len `0x2c6`, `0x015aca7c` len `0x68c`).
- **Tools:** `python3 3.14.3` (stdlib only for repo tools), `tools/cerom.py`, `tools/sh4dis.py` (M1.11/M1.14), `tools/cedecomp.py`, `tools/cedecomp_run.py`, `tools/cecompress.py`, `tools/fetch_image.py`.
- **Claims:** C-2360–C-2363
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the nk.exe `DECOMP_BLK`/`DECOMP_SECT` CE-LZXD block codec be ported to pure Python so that EXP-49 sec1 decodes to `0x484`, sec2 to `0xcc0`, and `cerom.py --image-start 0x200200 IMG256 decompress --check` reports `245 OK` without QEMU?

## Hypothesis

The M8.E1b-verified chain (`DECOMP_WRAP 0x88037590` → `DECOMP_SECT 0x88037464` → `DECOMP_BLK 0x8803a384`, build B `--image-start 0x3e00200`, nk.exe sec0 file `0x03e01200`, C-662/C-663/C-2292/C-2293) plus M1.2a/M1.2d framing is sufficient to implement a pure-Python decoder for the 245 `IMAGE_SCN_COMPRESSED` sections.

**Falsifier (met):** the EXP-49 vectors cannot be decoded to `0x484`/`0xcc0` by a rigorously derived pure-Python implementation in this session, and `cerom.py decompress --check` cannot report `245 OK` without guessing the codec.

## Observations

- `fetch_image.py` verified `IMG256` SHA-256 `92aa525d…007f9` (268,435,456 bytes).
- EXP-49 sec1: stored `0x2c6` bytes, header `(1156, 710, 16, 1156, 688, 1156)`, payload at +22 starts `5b 80 80 8d 00 20 40 48...`; sec2: stored `0x68c`, header `(3264, 1676, 16, 3264, 1654, 3264)`, payload starts `5b 80 80 8d 00 20 01 cc...`. Both carry the CE block marker `0x8d80805b` (`5b80808d`) at the payload start.
- `cerom.py --image-start 0x200200 IMG256 comphdr --all` → `245 compressed section(s)... 245 HOLDS, 0 REFUTED, 0 UNPARSED (exceptions: 0) forms=[f1:187, f2:58]`.
- `cerom.py --image-start 0x200200 IMG256 decompress --check` → 245 `UNSUPPORTED` (first lines show framing/header misinterpretation by the existing lzss/lzx/lznt1/xpress auto path, e.g. `lzx: invalid block type 0` / `lzx block type unknown(4)` / decode failures; no CE-LZXD section decoder).
- `sh4dis.py` disassembly (LE): `DECOMP_BLK 0x8803a384` reads an 8-byte block header from `r4` via `mov.b @r4+` into stack (offsets 0–7 at r15+16), stores consumed count 8, checks block/framing conditions and calls helper at pool `[0x8803a424]=0x8803a248`. `DECOMP_SECT 0x88037464` parses frame bytes (3-byte LE values read from src), computes per-block boundaries/loop and calls `DECOMP_BLK` via pool `[0x8803758c]=0x8803a384` with `(r4=block src, r5=block size, r6=dest, r7=frame ptr)`. Helper `0x8803a248` calls `[0x8803a374]=0x8803ac54` and `[0x8803a378]=0x8803ada4`; `0x8803ada4` compares a word at `@r4` to literal `[0x8803adc4]=0x4349444c` (bytes form a CE block magic check consistent with a compressed-block header path).
- `cedecomp_run.py probe --image /tmp/opencode/img256.img --qemu qemu-system-sh4` → `{"status":"MISSING_QEMU", "qemu":"qemu-system-sh4"}`. `which qemu-system-sh4 qemu-system-sh4eb` found neither.
- `tools/sh4dis.py` (current) decodes `mul.l` forms seen but reports `.word` for several shift/arithmetic encodings present in the inspected codec paths (`412c,432d,031a,4d3d,493d,081a,091a,0b1a,021a,041a`), so the inner bitstream algorithm cannot be read as a complete, instruction-accurate listing from this tool alone.

## Interpretation

- **OBSERVED:** EXP-49 form-1 vectors and 245/245 section framing (form 1/2) are verified on `IMG256`; the M8.E1b decompressor entry VAs are reachable in nk.exe build B sec0 and disassemble coherently as LE SH-4.
- **OBSERVED (negative):** No pure-Python CE-LZXD block decode exists in the repo for these `IMAGE_SCN_COMPRESSED` payloads; existing `cecompress` methods and the current `cerom.py decompress --check` path do not decode them (245 UNSUPPORTED).
- **FACT (environment):** `qemu-system-sh4`/`sh4eb` is unavailable here, so the M8.E1 runtime reference path cannot be executed in this session.
- **HYPOTHESIS (not proven):** The block format is CE XIP LZXD-like (marker `0x8d80805b`, 8-byte block header read by `DECOMP_BLK`, helper magic `0x4349444c` in `0x8803ada4`). Confirming the exact bitstream/Huffman/E8 semantics requires either a complete, verified SH-4-level port (needs missing shift decodes resolved or an equivalent trusted disassembly), a known-good matching CE XIP LZXD implementation validated against EXP-49, or `qemu-system-sh4` (LE) execution of `DECOMP_SECT/BLK` with correct context.
- **UNKNOWN:** Exact DECOMP_BLK block header field meanings, Huffman tree layout, E8 handling details, and whether all 245 sections (187 form 1 + 58 form 2 multi-block) share one block-stream convention decodable by one routine.

## Conclusion

M1.2f's done-when is **not met**. The task is **blocked**: porting `DECOMP_BLK` to pure Python requires a complete, instruction-accurate understanding of the CE-LZXD block codec; `sh4dis.py` cannot decode several shift encodings in the relevant paths, `qemu-system-sh4` is unavailable for a runtime oracle, and no verified matching CE XIP LZXD implementation is present. No codec behavior was guessed and no vendor bytes were committed. Framing (245/245) and EXP-49 vectors remain the positive controls; `cerom.py decompress --check` still reports 245 `UNSUPPORTED`.
