- **Status:** done (negative result — task M8.H39 is `blocked`)
- **Date:** 2026-11-22
- **Sample:** `archive/head256.img` SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`
  SHA-256 `105e2032…76307`
- **Tools:** `tools/qemu-ze0/run.sh`, QEMU 11.1.3 LE build at
  `~/.cache/qemu-ze0/build/qemu-system-sh4`, Python 3.15.0 stdlib
  (`tools/ze0_ipl.py`, `tools/ze0_aui.py`, `tools/qemu-ze0/mkoverlay.py`,
  `tools/ze0_screenshot.py`, new `tools/ze0_tap.py`), system `gdb` 18.1
  (no SH-4 target compiled in)
- **Claims:** C-7360–C-7369
- **Supersedes:** none
- **Superseded by:** none

## Question

Can one tap, injected at the UI-message level documented in
`docs/firmware/touch.md`, change the screen of a running `-M ze0` guest, with
a stable after-tap hash, an empty-area negative control and a breakpoint hit
at the documented VA `0x03a1b154`?

## Hypothesis

Yes: `PostMessageW(HWND, 0x0201/0x0202, 0, (y<<16)|x)` through a gdbstub
function call would hit the UI path and change the screen. **Falsifier:** the
call faults before reaching the UI, the screen does not change, or the screen
changes without a tap.

## Inputs

| --- | --- |
| Guest | EU2011 A+B, card `LEAF_2011-2012_QSD-309-101_navi158_eu.img` |
| ipl patch | `ze0_ipl.py --prefer-app auiapp.exe,auirtdll.dll --copy-dlls unitflash` + `ze0_aui.py --no-aui-timeout` (25 lines) |

## Method

1. **Sample and hash.** One real firmware head and one real factory card,
   hashes above. No vendor bytes written into the repo; screenshots and logs
   live under `~/projekty/leafre-work/scratch/m8.h39-tap/`.
2. **Commands.** Run from the repo root. Step 4 is the actual negative.

```bash
S=$HOME/projekty/leafre-work/scratch/m8.h39-tap
mkdir -p "$S"
python3 tools/ze0_ipl.py patch archive/head256.img --prefer-app auiapp.exe,auirtdll.dll --copy-dlls unitflash -o "$S/ipl_k.txt"
python3 tools/ze0_aui.py archive/head256.img --no-aui-timeout -o "$S/ipl_aui.txt"
cat "$S/ipl_k.txt" "$S/ipl_aui.txt" > "$S/ipl_final.txt"
python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$S/factory.qcow2"
bash tools/qemu-ze0/run.sh --qemu "$HOME/.cache/qemu-ze0/build/qemu-system-sh4" --machine ze0 \
  --image archive/head256.img --sd "$S/factory.qcow2" --ipl-patch "$S/ipl_final.txt" \
  --verinf QSD-302-100 --mapdb 16-16 --dbgmsg 0x880404f4 \
  --icount shift=0,sleep=off --gdb --timeout 0 --workdir "$S/run2"
python3 tools/ze0_screenshot.py screen --monitor "$S/run2/hmp.sock" -o "$S/idle_a.png"
python3 tools/ze0_screenshot.py screen --monitor "$S/run2/hmp.sock" -o "$S/idle_b.png"
sha256sum "$S/idle_a.png" "$S/idle_b.png"
python3 tools/ze0_tap.py --selftest
python3 tools/ze0_tap.py --probe
python3 tools/ze0_peers/panel.py --selftest
python3 tools/selftest.py --only ze0_tap
```

`run.sh` is a long-running foreground command in the block above; the actual
run used the same arguments with `&` and a PID file.  `--probe` halts the CPU,
sets the four SH-4 argument registers, sets `PC` to the call target and `PR` to
the `rts` trampoline, single-steps 14 instructions, restores all 59 registers
and continues the guest; it never claims a successful call.
3. **Controls.** *Positive*: `tools/ze0_tap.py --probe` showed the call enters
   `0x88098d2c` and executes the first ten instructions; an RSP software
   breakpoint (`Z0`) at the *current* PC stopped the CPU immediately, so the
   RSP harness itself works. *Negative*: the same probe reaches `0x000000aa`
   and then the kernel exception vector `0x8800ebd0`; with the user-mode alias
   `0x03fa9d2c` the very first step lands in the exception vector. A screen
   change without a tap would have refuted the stability check.
4. **Scope.** One boot of EU2011 build A+B with the factory card, 25-line ipl
   patch, gdbstub on port 1234, two screenshots at the rendered-map state, one
   injected-call probe and one control breakpoint at the current PC. Excluded:
   SCI3 wire frames (M8.H35), device.exe-context injection, a hard-key event,
   and any L3/L5 run. The boot never printed
   `AppLch >> Finish Launch Threads!` within the observation window, so the
   "idle" precondition was not proven even though the map was drawn.
5. **Falsifier.** A changed screenshot with matching hashes and a breakpoint
   hit at `0x03a1b154`. Not achieved.

## Observations

- `tools/ze0_screenshot.py screen` on the booted guest: plane 1 at window
  `(0,480)`, plane 2 `800x480` at `(0,0)`, plane 4 at `(1376,193)`;
  `probe2.png` has **384,000 non-black pixels** and shows the factory London
  map (no visible AUI button). SHA-256
  `8f21194861d26f52f45a97b4fea45a7c8ddbe1c60dd792b1c33f7c03ea8dca79`.
- Two later screenshots are byte-identical PNGs, hash
  `94ed90ab5cbd201db34230580160c1aa76b41d278162395c11c85959e72f3ed0` each —
  no animation, both **black** (0 non-black pixels) after the injection
  attempt.
- `grep -c 'AppLch >> Finish Launch Threads' run2/serial.log` = **0**. The log
  ends in the audio-network retry loop (`CInaiProtocol[TX]::WriteProc!
  WriteData() FAILED`) and later `CInterface::ComReStart! failed
  COMSTS_WAIT_RESPONCE count up![18]`.
- `tools/ze0_tap.py --selftest`: `selftest: PASS (0 failure(s))`, 7 checks;
  `tools/selftest.py --only ze0_tap`: PASS (auto-discovered).
- `tools/ze0_tap.py --probe` PCs:
  `0x88098d2e 0x88098d30 0x88098d34 0x88098d36 0x88098d38 0x88098d3a
  0x88098d3c 0x88098d3e 0x88098d40 0x000000aa 0x8800ebd0 0x8800ebd2
  0x8800ebd4 0x8800ebd6`. The `0xaa` and `0x8800ebd0` values are the SH-4
  exception vector and kernel exception handler.
- `run2/qemu.log` ends with `Invalid read at addr 0x3FA9D2C, size 2,
  region '(null)', reason: rejected` and `Invalid read at addr 0xAA, size 2,
  region '(null)', reason: rejected`; the serial log ends with
  `ERROR ... virtmem.c line 1291: Failed VirtualAlloc(00002000) of 00100000
  bytes` / `Exit ErrorAnalyzing_Exception`.
- The `PostMessageW` wrapper at `0x03fa9d2c` reads a per-process pointer from
  low memory (`mov #88,r8; shll8 r8; mov.l @r8,r3` at `0x03fa9d36`–`0x03fa9d3a`);
  that address is not mapped in the interrupted kernel context.
- Breakpoint at the documented VA `0x03a1b154` was never reached (hit count
  0): it is a per-process thunk through IAT slot `0x01f4204c`, not a globally
  callable kernel VA.

## Interpretation

- **FACT:** The rendered factory map can be captured at L4, but the idle
  marker was not observed in this run and the screen shows no AUI button to
  tap.
- **FACT:** Injecting a mouse message by calling `COREDLL!PostMessageW` from
  the interrupted CPU context faults; the guest kernel subsequently aborts
  with `ErrorAnalyzing_Exception`. No UI message was delivered.
- **FACT:** The documented call site `0x03a1b154` is process-local, so a
  debugger call from an arbitrary context cannot hit it. Rule 13 acceptance
  is therefore **not** achieved.
- **OBSERVED:** `tools/ze0_tap.py` works as an RSP client and `panel.py`
  produces the correct 6-byte sample; the failure is the injection context,
  not the command encoders.
- **HYPOTHESIS:** A wire-level injection through `SCI3:` (M8.H35) or a helper
  running in `device.exe` context would reach the real thunk and avoid the
  fault.
- **UNKNOWN:** Whether a stable button exists on a later AUI screen, and the
  runtime HWND value.

## Conclusion

M8.H39 is **blocked**, not done. No after-tap screenshot hash can be claimed,
no empty-area negative control was reached, and the breakpoint hit count at
`0x03a1b154` is 0. The negative result has a positive control (RSP breakpoint
at the current PC, entry into `PostMessageW`) and a falsifier (none of the
done-when observations occurred). The unblocking path is M8.H35 (SCI3 frame
grammar, enabling `panel.py` to emit a real wire frame) or a new
device.exe-context injection helper; this record is the negative EXP the
blocked board line names.
