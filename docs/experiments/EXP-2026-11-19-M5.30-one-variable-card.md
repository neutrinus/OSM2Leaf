## Question

Can the M5.44 changed tile (289,458,162 B — 2 clusters more than its factory
chain) be written into a copy of the factory image so that the card passes
`cardcheck --image`, differs from factory **only** in that tile's clusters and
directory entry plus the two DRSTR size values and the FAT/FSInfo bytes a
2-cluster growth needs, and what exactly did the M5.47 allocator refusal turn
out to be?

## Hypothesis

M5.47 (C-4564, C-4565) says `imgpatch --allow-resize --dry-run` refuses with
`internal-range` because `mkcard.alloc_clusters` bounds its scan by
`len(fat) // 4` (115,200 entries), a bound that is larger than the partition's
data area (14,743,768 data sectors at 128 sectors/cluster = **115,185**
clusters, numbered 2..115,186). With that bound the scan crosses the partition
end **before** wrapping to the free run at 29,687. The hypothesis is that this
is a one-line class of defect — an allocation bound that ignores `FatGeo` — and
that with the bound passed in, the growth draws its 2 clusters from inside the
partition and the card closes.

**Falsifier:** the refusal survives the geometry-bounded allocator (so it is a
second, unmodelled defect); or the patch writes bytes outside the changed tile,
the DRSTR file and the FAT/FSInfo sectors (so it is not one variable); or
`cardcheck --image` fails on the result; or the bound fix changes an
already-passing allocation (the factory and the synthetic selftest change
bytes).

## Observations

### 1. The refusal is the FAT-length bound, and the fix closes it

The dry run **before** the fix (the control, from a scratch copy):

```text
{
  "ok": false,
  "mode": "patch",
  "error": "internal-range",
  "message": "data cluster 115187: 0x1c83f5400-0x1c8405400 falls outside the map partition and the 0x06000000 copy"
}
exit=3
```

Same geometry, same request, after the fix (`dryrun-tile.json`):

```text
extra_clusters [29687, 29688]  free_after_tail 0
chain_before tail [94804, 94805, 94806]  chain_after tail [94804, 94805, 94806, 29687, 29688]
clusters 4415 -> 4417  sizes 289319168 289458162
fsinfo [('primary', 35851, 35849, 29687, 29688), ('backup', 4294967295, 4294967295, 2, 29688)]
```

`free_after_tail 0` is the census's `tail_free_run=0` restated for 2 clusters:
the clusters after the tile's tail (94807, 94808) belong to another file, so the
allocator scans to the 29,687 run. `FSInfo free` goes 35,851 → 35,849 (two
clusters) and both hints move to 29,688 (the primary already pointed at the run;
the backup's stale hint 2 is advanced).

What changed in `tools/`: `mkcard.alloc_clusters(..., max_cluster=...)` caps
the scan at the partition's data clusters, and `imgpatch._build_plan` passes
`(total_sectors − reserved − fat_count·fat_sectors) // spc`:
`data_sectors=14743768`, `spc=128` → `count=115185`, `last=115186`. The
previous bound was the FAT length, `FAT=115200` entries / clusters 2..115,199;
`phantom=14` entries (115,187–115,199) have no bytes in the data area.
While testing the bound, a second defect surfaced and is fixed too:
`alloc_clusters` rescans the same free cluster twice when the scan wraps
(`validate` returned cluster 10 twice for a 116-cluster request), so it now
tracks the clusters it has taken.

### 3. Every diff byte, classified from an independent BPB+FAT read

`check-diff --allow-metadata` (`checkdiff.json`):

```text
ok True  diffs 586  bytes 152815  outside 0
classification {'metadata': {'ranges': 9, 'bytes': 24},
                'file_data': {'ranges': 577, 'bytes': 152788},
                'dir_entry': {'ranges': 1, 'bytes': 3}}
metadata 9 ranges
files: MAPAL001/B48R058R.DAT start 90392 size 289458162 clusters 4417
       DRSTR001.DAT          start 29686 size 11968     clusters 1
```

The 9 metadata ranges are the 3 FAT links × 2 copies (`0x64213dc`, `0x6491bdc`,
`0x64213e0`, `0x6491be0`, `0x6460d58`, `0x64d1558`; each 4 B, 2 B changed per
link because the chain already held the high bytes), the primary FSInfo free and
hint (`0x7e8`, `0x7ec`), and the backup FSInfo hint (`0x13ec`). The single
`dir_entry` range is `0x106525700` (3 changed bytes: two low size bytes; the
cluster field is unchanged because the start is unchanged). `file_data` is the
tile's 4,417 clusters plus DRSTR's cluster — the only 152,788 changed bytes in
the image.

The metadata class is **whole FAT sectors + whole FSInfo sectors**, not the named
fields: the plan writes only the 3 links and 3 count/hint words, but a byte
anywhere else in those sectors would also be admitted by the flag (see §5's
planted FAT-entry control). What bounds the class is the strict run (without
the flag, the same 9 ranges are `outside`, exit 1) and the per-range
classification, which names each range's file or metadata sector. Any byte
outside the two files' clusters, their directory entries and the FAT/FSInfo
sectors fails in both modes.

Diff-range count is not the tile's diff in the common prefix: the generated
tile is not byte-identical to the M5.44 artifact only at the cluster level (the
bytes it holds are identical; it sits in a different chain), so the file-data
ranges are the union, and the point of the proof is that **no range is outside
the two files' clusters, their two directory entries and the FAT/FSInfo
sectors**.

## Interpretation

- **FACT:** the M5.47 refusal was the allocator bound, not free space: with the
  scan capped at the data area's **115,185** clusters (last valid 115,186), the
  same request plans 2 extra clusters at 29,687–29,688 (inside the 35,851 free
  run) and touches nothing past 115,186. The fix is a parameter
  (`alloc_clusters(..., max_cluster=)`), not a rewrite.
- **FACT:** the card passes `cardcheck --image` (`RESULT: PASS`) and differs
  from factory in exactly 586 ranges / 152,815 B: 577 file-data ranges
  (152,788 B) inside the two replaced files' clusters, 1 directory entry (3 B),
  and 9 FAT/FSInfo ranges (24 B) that a 2-cluster growth must write.
- **FACT:** two independent FAT readers agree with the card: `7z t` says
  `Everything is Ok` (39 folders, 480 files, 5,174,104,661 B) and
  `fsck.fat -n` sees 115,185 data clusters, 520 files and no chain/size error;
  its only findings (label not in the boot sector, dirty bit) are on the factory
  slice too.
- **FACT:** the tree walk agrees: exactly two files differ, both intended, and
  every other one of the 480 files is byte-identical.
- **OBSERVED:** run time is dominated by whole-image reads, not by the patch:
  `--hash` SHA-256s the 8 GB card (~21 s per patch call), `cardcheck` ~17 s,
  `7z t` ~5 s, and `cp $IMG $S/card.img` ~0 s (this host's filesystem
  reflinks). The earlier `-o` path cost ~100 s because `copy_image` reads and
  rewrites every non-zero block; that path is not used here.
- **UNKNOWN:** whether the unit reads a 4,417-cluster tile chain that ends in
  the 29,687 hole (rule 13; L3/L4/L5). The L2 run exercises the M5.44 tree, not
  the relocated chain in the image; the image read-back is by `cardcheck`'s FAT
  path, `imgpatch --verify`, and now `7z` + `fsck.fat`. The L2 gap is a
  follow-up (an image-source `l2check` option, or extracting the chain).
- **UNKNOWN:** whether the sector-level backup-FSInfo hint write (`0x13ec`) is
  needed for the unit; it is an FSInfo field with no free count on this card and
  is written because FAT32 readers use it as a hint.

## Conclusion

M5.30's card exists and passes the L1 whole-card gate: a byte copy of the
factory EU 2011 image with only `MAPAL001/B48R058R.DAT` (4,415 → 4,417
clusters, +138,994 B) and `DRSTR001.DAT` (same size, two u32 values) changed,
plus the FAT links and FSInfo fields that the 2-cluster growth requires. Every
diff byte is classified from an independent BPB+FAT read; nothing outside the
two files, their directory entries and the FAT/FSInfo sectors differs, and
`--allow-metadata`'s class is whole-sector (bounded by the strict run and the
classification, not by the named fields). `7z t` and `fsck.fat -n` both accept
the filesystem, with the only `fsck` findings present on the factory slice too.
The M5.47 allocator refusal is explained and fixed with a geometry bound
(115,185 data clusters; last valid 115,186; 14 phantom FAT entries) and the
wrap re-pick defect alongside it. `mapping=provisional-v0`; firmware
acceptance is still unknown (rule 13) and L2 is run on the result tree, not on
the relocated chain inside the image.

- [ ] L2 on the relocated chain: `l2check` reads a root tree, not an image, so
  the card's tile was validated only by `imgpatch --verify` + `cardcheck` +
  `7z`/`fsck.fat`. A `--image` source (or extracting the chain to a tree) would
  close the gap; it is not a new file-format question, just a reader for the
  image.
- [ ] The backup-boot FSInfo page on this card has `free=0xFFFFFFFF`; only its
  hint is written. Confirm against the unit (rule 13) that a stale hint is
