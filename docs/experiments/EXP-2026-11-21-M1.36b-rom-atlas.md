## Question

Can the M1.36 scratch census be turned into one committed command that prints,
per image and per ROM (A/B/C), the module table with a **reloc-masked** code
hash (so a module that only moved in memory reads equal) plus the data side
(FAT32 families, `FILESentry`, the `TFAT16` tail), and does the mask change
which modules read equal on this corpus?

## Hypothesis

M1.36 hashed unmasked XIP code, so a module whose only difference is a
relocated literal-pool pointer or import slot read as "changed". If the mask
is correct, the same pair should read *more* equal modules than raw bytes.

**Falsifier:** if the reloc-masked equality count equals the raw-byte equality
count on every pair (0 modules "gained" by masking), then on this corpus the
mask flips no final answer — it is a safety property, not a source of new
equalities.

## Inputs

| Item | Value |
| --- | --- |
| Image (ROM side) | 256 MiB head of each of the four cards (see Sample) |
| Image (data side) | full EU2011/US2011/EU2014/EU2016 card images (see Sample) |
| Offset(s) | ROM segments `0x200200` (A), `0x3e00200` (B), `0x5200200` (C); FAT32 at MBR LBA 204802; `TFAT16` at `0x1c8400400` |
| Tool / version | `python3 3.15.0` |
| Repo tool | `tools/rom_atlas.py` (the one that produced every number below) |

## Method

1. **Sample and hash.** The 256 MiB head of each card (SHA-256 above) is the
   ROM input; the full card image (SHA-256 above) is the FAT input. The ROM
   side reads the first 128 MiB (`READ_LIMIT`), which holds segments A/B/C on
   all four cards. The data side walks the whole FAT32 volume and reads the
   `TFAT16` boot sector at the partition end.

2. **Commands.** Runnable as written, from the repository root, after
   `python3 tools/fetch_image.py` has placed the four heads (keys `IMG256`,
   `US256`, `EU2014`, `EU2016`) and the four full images are in
   `archive/sd-images/`:

   ```bash
   python3 tools/rom_atlas.py --selftest
   python3 tools/rom_atlas.py atlas \
     --head EU2011=archive/head256.img \
     --head EU2014=archive/eu2014-256.img \
     --head EU2016=archive/eu2016-256.img \
     --head US2011=archive/us256.img \
     --full EU2011=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --full EU2014=archive/sd-images/LEAF_2014_EU_QSD-357-101.img \
     --full EU2016=archive/sd-images/ENV200_2016_EU_QSD-390-100.img \
     --full US2011=archive/sd-images/LEAF_2011-2012_US.img
   python3 tools/rom_atlas.py equal --head EU2011=archive/head256.img --head US2011=archive/us256.img --negative-bcs
   python3 tools/rom_atlas.py equal --head EU2011=archive/head256.img --head US2011=archive/us256.img --mask-check
   python3 tools/rom_atlas.py equal --head EU2011=archive/head256.img --head EU2014=archive/eu2014-256.img --mask-check
   python3 tools/rom_atlas.py equal --head EU2014=archive/eu2014-256.img --head EU2016=archive/eu2016-256.img --mask-check
   ```

   The `atlas` output is checked in as `docs/research/rom-atlas.md`. `--mask-check`
   hashes each module a second time with **no** relocation mask (raw executable
   bytes, same section-index/vsize key) and prints, per ROM, `common`,
   `raw-equal`, `masked-equal`, and `gained` (raw-different but masked-equal).

3. **Controls.**
   - *Positive, synthetic:* `--selftest` builds `cerom.build_synthetic_rom()`
     (two modules, `NK.EXE` with no code, `NAVI.EXE` with one executable
     section), then checks a relocated pool pointer hashes equal, a changed
     constant hashes different, an import-slot value masks, a module compared
     with itself is equal, and a one-byte code mutation changes the digest and
     makes exactly `NAVI.EXE` differ (16 checks, 0 failures).
   - *Positive, real:* the `TFAT16` tail parses on all four full images
     (`TFAT16`, 32768 B/cluster, first entry `__TFAT~1`); every card's FAT32
     label is read (`QSD-309-101`, `QSD-301-103`, `QSD-357-101`, `QSD-390-100`).
   - *Negative, real:* `--negative-bcs` asserts B and C are fully equal for
     EU2011 vs US2011 (C-6281). If masking were broken and read everything
     equal, or the pair really differed, the control fails.

4. **Scope.** ROM side: all modules of segments A/B/C on the four heads (A
   149/151/153/153, B 91/91/95/96, C 88/88/92/92). Every executable section is
   readable (`IMAGE_SCN_COMPRESSED` executable sections are counted as
   `compressed` and contribute a marker, not bytes; `unreadable` stays 0 on all
   four cards). Data side: the FAT32 map partition (family file counts, root
   files) and the `TFAT16` tail; deep subdirectory clusters require the full
   image, so a head-only run reports `FAT tree not walked`. Excluded: the bytes
   after the FAT partition other than the `TFAT16` boot sector; per-function
   diff (M1.37).

5. **Falsifier.** Stated in Hypothesis: 0 modules "gained" on every pair would
   mean the mask is a safety property only, not a new equality source.

## Interpretation

- **FACT (C-6290):** `tools/rom_atlas.py` reproduces M1.36's module census
  exactly on all four cards (A 149/151/153/153, B 91/91/95/96, C 88/88/92/92;
  code bytes 22,806,528 / 23,077,376 / 24,394,240 / 24,416,768 for A).
- **FACT (C-6291):** the reloc mask keys by executable-section index and
  `vsize`, never by a section's absolute `realaddr`, and the pointer mask uses
  the module's process window `[vbase, vbase+vsize)` from the `e32` header, not
  the min/max over all sections (an import/resource section carries a ROM-space
  `realaddr` such as `0x1e6c000` that would leave relocated values unmasked).
- **FACT (C-6292):** raw-byte and reloc-masked equality give the same count on
  all 9 image-pair × ROM rows; 0 modules are "gained" by masking. On this
  corpus the mask flips no final answer — the falsifier in Hypothesis holds.
- **FACT (C-6293):** EU2011 vs US2011 ROM A has exactly one equal module
  (`atlce400.dll`), 1 module only in EU (`RDSCC.dll`) and 3 only in US
  (`RBDS_CC.dll`, `XMCC.dll`, `XMStatusCC.dll`); B and C are fully equal
  (91/91, 88/88), the C-6281 control.
- **OBSERVED (C-6294):** EU2011 vs EU2014 ROM A has 0 equal modules and 147
  different; B has 1 equal (`atlce400.dll`); C has 2 (`AstLogApi.dll`,
  `SdCardLch.exe`). EU2014 vs EU2016 ROM A has 1 equal (`atlce400.dll`), B 5,
  C 9. These are masked-equality counts, not a function-level diff (M1.37).
- **FACT (C-6295):** the data side reports the FAT32 label and family counts
  for all four full images, and a `TFAT16` tail (32768 B/cluster, first entry
  `__TFAT~1`) at `0x1c8400400` on every one.
- **FACT (C-6296):** the atlas resolves a role for some modules from a
  string/export/COM registration and marks the rest `unknown`; A modules with a
  COM co-class: 64 / 66 / 67 / 67; B: 9 each; C: 0. Role is never inferred
  from a name alone beyond the explicit updater/COM patterns.
- **UNKNOWN:** whether the equal modules' code is reachable/used the same way
  in a newer build (needs M1.37 + an L3 run); the purpose of the `TFAT16`
  `DONT_DEL.<nnn>` placeholders.

## Conclusion

`tools/rom_atlas.py` is the committed, reproducible atlas M1.36's scratch script
was not: one command prints, per image and ROM, every module with size,
sections, code bytes, a reloc-masked code hash, imports/exports, COM co-class
and a supported-or-unknown role, plus the FAT32 families, `FILESentry` and
`TFAT16` tail, and writes it to `docs/research/rom_atlas.md`. It reproduces the
census counts exactly and reports `atlce400.dll` as the one equal application
module between EU2011 and US2011 (with B/C fully equal, the C-6281 control).
The raw-vs-masked comparison over all 9 pair×ROM rows shows 0 modules gained by
masking: the mask is a correctness safety net (a module that only moved reads
equal) and does not change any equality answer on these four cards. The newer
cards' 2014→2016 equal sets (B 5, C 9) are the starting points for the
per-module changelog (M1.37). Still open: reachability/behaviour of the equal
modules (M1.37 + L3) and the `TFAT16` placeholders' purpose.
