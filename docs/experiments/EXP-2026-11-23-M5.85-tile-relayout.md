- **Status:** done
- **Date:** 2026-11-23
- **Sample:** EU 2011 card, SHA-256

  `tools/cardcheck.py`, `tools/datask_l3.py`, QEMU 11.1.3 + `tools/qemu-ze0`

## Question

Rung Z1 of `docs/research/osm-from-scratch.md`: a tile with no factory record
needs a writer that places every table, directory and record block itself.
Does the real firmware accept a tile whose every component was placed by our
writer, if the content is the factory's?

## Hypothesis

The firmware follows the section-table, directory and slot/row pointers and
needs nothing at a factory offset. Falsifier: the record content is equal
(model compare 0 differences) but the L3 mount or the L4 screen differs — the
firmware would then depend on a layout property the model lacks.

## Inputs

The tile and card above; the London start position 51.5098 N, 0.1342 W
(M8.H71).

## Method

1. Sample and hash: above.
2. Commands (`W` = scratch outside the repo, `FAC` = extracted factory tree):

   ```bash
   python3 tools/tile_relayout.py --selftest
   python3 tools/tile_relayout.py relayout $FAC/MAPAL001/B48R068R.DAT -o $W/z1/B48R068R.DAT --json
   python3 tools/tile_relayout.py compare $FAC/MAPAL001/B48R068R.DAT $W/z1/B48R068R.DAT
   python3 tools/s1_wide_dir.py census $W/z1/B48R068R.DAT
   python3 tools/section4_wide.py census $W/z1/B48R068R.DAT
   python3 tools/imgpatch.py --image $W/img/eu2011.img --file MAPAL001/B48R068R.DAT --from $W/z1/B48R068R.DAT -o $W/z1/z1.img
   python3 tools/cardcheck.py --image $W/z1/z1.img
   python3 tools/datask_l3.py mount archive/head256.img --card-image $W/img/eu2011.img --position 51.5098,-0.1342 --json $W/z1/l3-fac.json
   python3 tools/datask_l3.py mount archive/head256.img --card-image $W/z1/z1.img --position 51.5098,-0.1342 --json $W/z1/l3-z1.json
   python3 tools/datask_l3.py diff $W/z1/l3-fac.json $W/z1/l3-z1.json
   python3 tools/ze0_ipl.py patch archive/head256.img -o $W/ipl.txt
   python3 tools/qemu-ze0/mkoverlay.py $W/img/eu2011.img $W/fac.qcow2
   python3 tools/qemu-ze0/mkoverlay.py $W/z1/z1.img $W/z1.qcow2
   # per card (SD = fac.qcow2 or z1.qcow2), screenshot once serial.log has `Pow Off 1st Detect`:
   bash tools/qemu-ze0/run.sh --qemu $QEMU --image archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
     --ipl-patch $W/ipl.txt --sd $W/$SD --icount shift=0,sleep=off --timeout 600 --workdir $W/l4/$N --log /dev/null
   python3 tools/ze0_screenshot.py screen --monitor $W/l4/$N/hmp.sock -o $W/l4/$N/shot.png
   ```

3. Controls. Positive: `tile_relayout --selftest` writes one synthetic tile
   in two layouts that differ as bytes and compare as one model, and the
   relayout output does not depend on the input layout. Negative: a flipped
   record byte makes `compare` fail, and a non-zero byte outside every
   component is counted as uncovered (both in the selftest). On the real tile
   the `uncovered_nonzero` count is the guard that no data was dropped. The
   L4 negative control is M8.H71: a changed parcel changes the screen
   (56,671 pixels), so the screen does read this tile.
4. Scope: one tile; records carried as opaque bytes (no decode, no
   recompression, zlib version irrelevant); the start-screen position only.
5. Falsifier: as in Hypothesis.

## Observations

**O1 — the relayout.** `relayout --json`: `tables 3`, `dirs 191`, `blocks
5256`, `records 172863`, `same_offset 71` (so **5,379 of 5,450 components
moved**), `shared_addresses 0`, `uncovered 677804` B of the input outside every
component, **`uncovered_nonzero 0`**, output 264,516,352 B (same size as the
input; the factory tile has no non-zero byte outside its components),
SHA-256 `8eff57b6c8cbe07629859dc82a2ec548e74ab03c665a1086b110ffac78bd6e45`.
`cmp -l` counts 263,152,956 differing bytes. `compare`: `0 difference(s)`.
`s1_wide_dir census` and `section4_wide census` on the output: `OK` with the
factory counts (68 dirs / 117,305 records; 55 dirs / 3,946 records / 84 wide
rows).

**O2 — two models were needed beyond the generic reader.** A first run with
`clarion_tile.read_dir` for every directory except section 1 level 1 failed
`compare` in section-4 directories 33/34 (`0x1446`, `0x1046`), and a run with
the generic reader for section 1 level 2 failed the `s1_wide_dir` census with
27 non-zlib records and one block overlap. Both readers stop or misplace
rows: section 4 level 1 needs the wide-row model (`0x1n46`, 24-byte wide
columns; M4.93 already documented it), and section 1 level 2 needs the
`s1_wide_dir` parser. The final tool uses `s1_wide_dir.parse_dir` for section
1 levels 1–2, its own section-4 row parser (agrees with `section4_wide.py`:
3,946 records, 0 bad), and `clarion_tile.read_dir` only for section 2.

**O3 — L1.** `imgpatch` wrote the tile into its own cluster chain (same
size, no FAT change); card SHA-256
`5b4dfd653c6346f911aef5075ac331ef382a6ee81579551b85f5bf6c4a07f502`;
`cardcheck --image`: `[version] OK (hdd_size=72, image_copy=identical)`,
`RESULT: PASS`.

**O4 — L3.** Both mounts: `both tasks idle; state 2, tile files 46, reads 28`,
`tile reads parsed by the firmware: 18`. `diff`: `DIFFERENT (5
difference(s))`, all five are reads of `B48R068R` with the same tag and
length at another position. Mapped through the two models each pair is the
same directory: section 1 level 2 dir 2 (`0xba0d00` → `0x9600`), section 1
level 1 dir 39 (`0x6be9f00` → `0xb6f00`), section 2 level 2 dir 2, section 2
level 1 dir 39, section 4 level 1 dir 35 (`0xfbc6f00` → `0xfb37700`, a wide
directory).

**O5 — L4.** Both runs reached `Pow Off 1st Detect` (15–16 s wall). The
screenshots (two per run, 5 s apart) all have SHA-256
`7e23cc73ccf579e34372eeff59943add5a2b49e273b717d5c56ebf320f259f74`, 384,000
non-black pixels: **pixel-identical**. The serial logs have 1,583 lines each
and the same 1,043 error/fail lines (digits stripped, counted). The screenshot
(factory data) is kept out of the repository and given to Marek in the
project thread.

## Interpretation

- **FACT:** the firmware reads the London tile through its pointers only: a
  tile in which 5,379 of 5,450 components sit at new offsets mounts with the
  same reads and draws the same screen. The falsifier did not fire.
- **FACT:** our writer can lay out a whole tile — section tables,
  191 directories (including 84 wide rows in section 1 and 84 in section 4),
  5,256 record blocks. Z1 is passed; the container half of "a tile from zero"
  is no longer an unknown.
- **OBSERVED:** the generic `clarion_tile.read_dir` is wrong for section 1
  level 2 and section 4 level 1 on this tile as well as for section 1 level 1;
  any writer built on it alone loses records silently (the compare and census
  caught it here).
- **UNKNOWN:** whether the firmware tolerates layouts other than "sequential
  per section" (e.g. blocks before their directories); not needed for Z2+.

## Conclusion

`tools/tile_relayout.py` (relayout + compare, 8-check selftest) writes a
factory tile through our own layout with nothing copied by position; L1, L3
and L4 accept it and the screen is pixel-identical. Next: Z2 (M5.87) — the
same writer with every record removed, to see what the screen loses.
