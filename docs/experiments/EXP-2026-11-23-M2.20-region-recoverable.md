## Question

If the unit area byte (PROD `+0x21`, flash `0xA021`, `0x20` USA → `0x30` Euro,
C-5201/C-5215) is
changed, does the build-B software-update path still start? Concretely: (1) do
the update-mode launch records (`UpdateMng.exe`/`PRGUpdate.exe`) start for every
area — what are their area masks; (2) which launch records differ between USA
`0x00040000` and Euro `0x00020000` on the US card and the EU card; (3) does the
EU card's build A contain a `Navi.exe` record an area-USA unit starts?

## Hypothesis

The update programs are type-3 processes in the build-B `AppLaunch.dll` launch
table, filtered by the area mask and the boot-mode mask (`fn 0x03bcc564`,
M1.34/C-5350). If their area mask is all-areas (`0xffff0000`), the area byte
does not stop them. Falsifier: an update record whose area mask excludes Euro
`0x00020000`, or evidence that update mode does not go through this launch
table.

2. **Commands.** Runnable as written from the worktree root
   (`W=/home/marek/projekty/OSM2Leaf.task-m2.20-region-recoverable`):


3. **Controls.** *Positive:* M1.34 records reproduce — EU mode-0 selects Navi
   #81 `0x03bc1b40` (`0x00020000`), USA #80 `0x03bc1830` (`0x00040000`), JP #77
   `0x03bc0f00` (`0x00010000`); the table base/count from the code getters;
   `applaunch_table.py --selftest` PASS. *Negative:* `launch_area.py mutate`
   flips record #98's area to `0x00020000` and the USA (`0x20`) mode-4
   selection loses `UpdateMng.exe` while Euro (`0x30`) keeps it — the area
   field really decides, and it is read little-endian. `launch_area.py
   --selftest` also checks a `0x80000`-only record is in neither diff list; a
   zero-shift table and an all-areas-only fixture are the reference.
4. **Scope.** Build B `AppLaunch.dll` sec0 (150,309 B, the only executable
   section of the table), EU2011 and US2011 heads, all 112 records parsed.
   `launch_area.py select` emulates the mode/area/base-type filter but **not**
   the option-flag capability queries (`rec+0x10`, `fn 0x03bcbc18`); it marks a
   selected record `opt` when its flags are non-zero. Every record this EXP
   relies on (`UpdateMng`/`PRGUpdate`/`MapUpdate`, the five `Navi.exe`) has
   `opt=0` (`launch_area.py masks` prints no `opt`), so the selection is exact
   for them.
   Build A only for the module list (`Navi.exe`, `AppLaunch.dll` absence).
   Excluded: the update programs' own code (what they do after start), the
   `ProtoLevel` bypass, and the runtime boot path (M6.17, HYPOTHESIS here).
5. **Falsifier.** An update record whose area mask excludes Euro, or update
   mode reached without this table.

## Interpretation

- **FACT (C-6260):** build B `AppLaunch.dll` (module 41, vbase `0x03bb0000`)
   carries the launch table on both cards; build A has neither the module nor a
   table.
- **FACT (C-6261):** the build-B table is byte-identical on EU2011 and US2011
   (`0` field-differing records; same SHA-256).
- **FACT (C-6262):** the three update programs are type 3, mode mask `0x0010`,
   area mask `0xffff0000`, at `0x03bc4f5c` / `0x03bc526c` / `0x03bc67dc`.
- **FACT (C-6263):** update mode starts for area `0x30`: **yes** by the launch
   table — `UpdateMng.exe` and `PRGUpdate.exe` carry all-areas masks, so the
   area filter `fn 0x03bcc564` passes for Euro and for every other area value.
- **FACT (C-6264):** the USA/Euro launch difference is only the three tuner
   records and the `Navi.exe` build (USA #80, Euro #81); no update record is
   area-tagged.
- **FACT (C-6265):** normal mode starts `Navi.exe` #77/#80/#81 for
   Japan/USA/Euro respectively.
- **FACT (C-6266):** the EU card's build A has a `Navi.exe` module but no
   launch table; the launch record is build B, and an area-USA unit on the EU
   card starts B #80 from the (identical) EU B table.
- **OBSERVED (C-6267):** the area field decides selection (mutating #98 to
   Euro-only drops it from USA).
- **HYPOTHESIS:** update mode (service-tool/update boot, C-5191) reaches
   `UpdateMng.exe`/`PRGUpdate.exe` through this same launch table via
   `fn 0x03bcc5b0`; the update boot mode→mask mapping and the service-tool
   entry are M6.17's, not re-derived here. So "recovers regardless of area"
   is a selection fact, not a whole-path fact.
- **FACT (C-6268):** card image B is not the normal-mode launch table; the
  flash kernel's copy (M6.19, 111 records) is, and it differs partially. The
  M2.20 Q1/Q2 answers are facts about card B; the update-mode table's source
  (card B per C-5191 vs flash per C-5216) is open (O9).
- **UNKNOWN:** what the update programs do once started (outside this task);
  whether an area byte change also affects the boot-mode value read by
  `CApi_GetBootMode`; which table copy (card B or flash) the update path uses.

## Conclusion

The area byte does not gate software-update mode at the launch table: on both
the EU and US 2011 heads, `UpdateMng.exe` (`0x03bc4f5c`) and `PRGUpdate.exe`
(`0x03bc526c`) carry area mask `0xffff0000` and boot-mode mask `0x0010`, so the
area filter selects them for Euro `0x30` and every other area. The area byte
only swaps the three tuner records and the `Navi.exe` build (USA #80 vs Euro
#81). The EU card's build A is the application (`Navi.exe` module) without a
launch table; the launch record an area-USA unit runs is build B #80, from a
table byte-identical to the US one. `update mode starts for area 0x30: yes`,
deciding masks `0x03bc4f5c` (UpdateMng) and `0x03bc526c` (PRGUpdate). The
"still reachable once started" half is M6.17's HYPOTHESIS, and the merged M6.19
note (C-5216) makes the normal-mode table the flash kernel's, so this is a fact
about card image B only (C-6268).
