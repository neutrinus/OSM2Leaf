## Question

Row C10 gave the `ze0` machine an SD host; the card driver's first data
transfer (ACMD13, 64 bytes) timed out because `SDHC.dll` moves all data
through the HPB-DMAC, which had no model (C-1462). Row C1 read the DMA
engine statically and left two questions open: which signal is "event 2",
and what a model must do. Can a DMAC model make the SD data path work, and
how far does the boot then get?

## Hypothesis

The block at `0xffc08000` is a Renesas HPB-DMAC: per-channel
source/destination/count, a control and a command register, and a common
interrupt status/clear/enable triple. A model that copies the bytes between
the card and guest RAM when the channel is enabled and raises the channel's
interrupt is enough for the driver.

**Falsifier:** with a model that moves the bytes and raises every interrupt
the driver enables, `EventID = 2 Timeout` is still logged.

## Inputs

- `archive/head256.img` and the EU card image (SHA-256 above).
- EXP-2026-11-20-M8.C1-hpb-dmac (C-1370–C-1379), EXP-2026-11-20-M8.C10-sd-host
  (C-1460–C-1464), EXP-2026-11-06-M2.13b-sdhc-cmd42 (C-1953, C-1954).

## Method

Scope, counted: one firmware build (EU2011 build B), one card, two QEMU
versions, five boots (`A` model on / 11.1.3, `B` DMAC off, `C` card with no
password, `D` model on / 8.2.10, `E` card powers up locked), each 230–260 s
of host time with `-icount shift=0,sleep=off`.

```bash
I=archive/head256.img
CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
Q=~/.cache/qemu-ze0/build/qemu-system-sh4        # build.sh output (either version)
W=/tmp/c1b; mkdir -p $W

# 1. static: the kernel side of the DMAC (interrupt table, ISRs, OEMInterruptDone)
python3 tools/ze0_sdhost.py inttable $I
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8803e7f8 --count 34   # channel 8 ISR
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8803e618 --count 20   # channel 0 ISR
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8803e8e4 --count 60   # channel 11 ISR (reads +0x80c)
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8803e004 --count 185  # OEMInterruptDone
python3 tools/ze0_serial.py refs $I --image-start 0x3e00200 --module nk.exe --window 0xffc08000:0x1000

# 2. boots (overlay first: QEMU's sd-card needs a power-of-two size)
run() {  # run TAG MACHINE-OPTIONS
  python3 tools/qemu-ze0/mkoverlay.py $CARD $W/eu$1.qcow2
  timeout 260 $Q -M ze0,dbgmsg=0x880404f4$2 -kernel $I \
    -drive if=sd,index=0,file=$W/eu$1.qcow2,format=qcow2 -icount shift=0,sleep=off \
    -nographic -serial file:$W/ser$1.log -monitor none -d unimp -D $W/q$1.log
}
run A ,sdhi-trace=on,hpbdmac-trace=on                      # model on
run B ,sdhi-trace=on,hpbdmac=off                           # negative control 1: no DMAC
run C ,sdhi-trace=on,hpbdmac-trace=on,sd-pwd-tofu=off      # negative control 2: card with no password
run E ,sdhi-trace=on,hpbdmac-trace=on,sd-start-locked=on   # card powers up locked
# D = A with the 8.2.10 binary

# 3. evidence
python3 tools/ze0_sdhost.py serial   $W/serA.log
python3 tools/ze0_sdhost.py sdtrace  $W/qA.log
python3 tools/ze0_sdhost.py dmatrace $W/qA.log --card $CARD     # exit 0 = every block read equals the card
```

- **Positive control:** `dmatrace --card` recomputes CRC-32 of the card
  image at `arg × 512` for every CMD17/CMD18 transfer and compares it with
  the CRC-32 the model logged for the bytes it wrote to guest RAM.
- **Negative controls:** (1) `hpbdmac=off` must bring back `EventID = 2
  Timeout`; (2) the same comparison with the card offset shifted by one
  block must fail for every transfer; (3) `sd-pwd-tofu=off` (a card with no
  CMD42 password) must be refused by the launcher.
- **Falsifier check:** run A must have no `EventID = 2 Timeout`.

## Observations

### O1. The kernel side names the registers

`ze0_sdhost.py inttable` lists one interrupt row per DMAC channel: INTEVT
`0xb60 + 0x20 × ch` for channels 0–11 (`0xb60` … `0xcc0`) and `0xda0 + 0x20
× (ch − 12)` from channel 12 (`0xda0` … `0xea0`). The ISR of each row
masks INT2 bit 19 (`0xff804040 = 0x00080000`), clears **its own bit** in
`0xffc08814` and unmasks: `fn 0x8803e618` (`0xb60`) clears bit 0,
`fn 0x8803e7f8` (`0xc60`) bit 8, `fn 0x8803e850` (`0xc80`) bit 9,
`fn 0x8803e8e4` (`0xcc0`) bit 11 after testing bit 11 of `0xffc0880c` and
writing `0x800` to `0xffc08810`. The channel 8 and 9 ISRs also store 1 at
`0xa9980a04` (port 0; the SDHI ISR `fn 0x8803fcdc` uses `0xa9980a00`) and
return SYSINTR `0x1f` / `0x20`, the SD host's own. `OEMInterruptDone`
(`fn 0x8803e004`), for those two SYSINTRs, writes `0x20080000` to
`0xff804044` and ORs `0x100` / `0x200` into `0xffc08810` and `0xffc08814`.

So `+0x80c` is the per-channel interrupt status, `+0x810` clears it and
`+0x814` enables it; channel 8 = SD port 0 interrupts at INTEVT `0xc60`
and channel 9 = port 1 at `0xc80`, both on INT2 bit 19. "Event 2" of
C-1373 is the DMA-end interrupt: the same SYSINTR as the SD host, told
apart by the flag byte.

### O2. What the driver programs (run A, `hpbdmac-trace`)

For the first transfer (ACMD13, `SD_SIZE = 0x40`):

```
wr +0x224 = 0x00000d00      wr +0x230 = 0x00000001     rd +0x234 = 0x00000000
wr +0x200 = 0xffe4c030      wr +0x204 = 0xa99c1000     wr +0x208 = 0x00000004
wr +0x228 = 0x00202100      rd/wr +0x814 |= 0x100      wr +0x22c = 0x00000001
(SD host) wr16 +0xd8 = 0x0002, SD_CMD = 0x184d
```

Source = SD_BUF0 of port 0, destination = a kernel-RAM buffer, count 4,
then enable. ACMD51 (8 bytes) has the same count 4 with control
`0x00002100`; a 512-byte CMD17 has count `0x20` and a 256-block CMD18
count `0x2000` with `0x00202100`. The serial drivers program channels 1, 3
and 7 (source `0xffe41014` / `0xffe43014` / `0xffe47014`, two 0x80-byte
planes, control `0x00052000`, count `0x80`) and channel 10 (destination
`0xffe4100c`, control `0x20`, count 8). So the count unit is 1 byte, 2
bytes with control bit 8 and 16 bytes with bits 8 and 21.

- C: the LOCK fails (`SDHC_Lock_Unlock_Card() Err = [107]`), the launcher

- E: the driver sends one CMD42, UNLOCK (`0x00`), **before** ACMD6/ACMD13,
  and the rest is as in A. With the card unlocked at power-up (A) it sends
  LOCK then UNLOCK after CMD6: the two branches of C-1954.

### O5. Four things besides the DMAC stood between ACMD13 and the mount

Each was found as the next stop of the boot and is fixed in `ze0-0009`:

1. **QEMU card model, CMD6.** For a group argument `0xF` ("no influence")
   QEMU answered `0xF` in the status ("argument error"). The driver's check
   CMD6 `0x00fffff1` then logged `Err-334`, retried the whole
   initialisation twice and gave up (`Err-308`, `End(NG`). Now the status
   reports the function the group keeps.
2. **`ze0-sdhi`, PIO.** The host model gated SD_BUF0 on the BRE/BWE status
   bit. The driver clears the bit (`SD_INFO2 = 0xfdff`) before it writes
   the buffer, so its only PIO write, the CMD42 block, was dropped and it
   waited for ACCESS END (`Err-314`). The gate is now the transfer state.
3. **QEMU card model, CMD42.** `sd_lock_command` refused a password of the
   stored length (`pwd_len <= sd->pwd_len`), so no UNLOCK or LOCK could ever
   match; 11.1.3 also took 512 data bytes for CMD42 whatever SET_BLOCKLEN
   said (the driver sends 18). Both corrected.
4. **Debug SCIF alias.** After the unlock `serial_scif.dll` opens SCIF
   channel 6 and spun in `fn 0x0398e888` on SCFSR.TEND through
   `0x1fe46010` (QEMU monitor: `pc=0x0398e8a2`, TLB `vpn=9c0 ppn=7f918`);
   the debug SCIF had no area-7 alias. C-1463 named this address; the stub
   patch had skipped channel 6.

### O6. The card password

The unit refuses a card that has no CMD42 password (run C), and the
password is unit-specific (C-1954: 16 bytes from `IOCTL_HAL_GET_USER_PASSWORD`).
`ze0-0009` adds the sd-card property `pwd-tofu`: the card's password is the
first one a host presents, after which QEMU's ordinary lock logic applies.
The firmware's LOCK and UNLOCK then succeed without any password byte in
the patch, the repository or this record. `sdhi-trace` logs only the first
word of a PIO block (mode byte and length).

## Interpretation

- **FACT (C-6870):** the block at `0xffc08000` is an HPB-DMAC with
  interrupt status / clear / enable at `+0x80c` / `+0x810` / `+0x814`; SD
  port 0 uses channel 8 (INTEVT `0xc60`), port 1 channel 9 (`0xc80`), INT2
  bit 19 (O1).
- **FACT (C-6871):** "event 2" is the DMA-end interrupt, delivered as the
  SD SYSINTR with flag byte `0xa9980a04` (O1, run B vs A).
- **OBSERVED (C-6872):** register use and count units as in O2. The names
  (DSAR/DDAR/DTCR/DPTR/DCR/DCMDR/DSTPR/DSTSR) are those of the public Linux
  driver for this IP; that the part is the same IP is a **HYPOTHESIS** that
  fits every access seen. `+0x224 = 0x0d00` as the request source is
  inferred from the serial channels using `0x0100`/`0x0300`/`0x0700`.
- **FACT (C-6873, C-6874):** with the model the driver's init returns
  `End(OK`, all data transfers complete, and the bytes delivered equal the
  card image (42/42; shifted control 0/42).
- **FACT (C-6875):** F3 is reached on EU2011: `Store Mgr Ready! [DSK1:]`,
  two partitions mounted, and a value read from a file of the card
  (`HddInf:QSD-302-100`) is logged.
- **FACT (C-6876):** the unit requires a card with a CMD42 password and
  takes one of two CMD42 paths depending on the locked bit (O4 C, E).
- **OBSERVED (C-6877):** the next stop is the launcher: `VerInf:` is empty,
  `AppLch >> Error Proc<00000050>` follows and `FailSafe.exe` starts
  instead of the applications. **UNKNOWN:** where `VerInf` comes from and
  what `0x50` tests; the adjacent log line suggests a comparison of a unit
  version with the card's `HddInf`.
- **OBSERVED:** `HddInf` reads `QSD-302-100` while the card image is filed
  as `QSD-309-101`; which file the launcher reads is not established here.
- **UNKNOWN:** the INT2PRI field of the DMAC (the model uses level 14, the
  table's IntrPrio); the DMARS-like write (C-1379) was not needed.
- The model completes a transfer at once (no timing). Channels other than
  8 and 9 are register storage: the serial drivers' DMA (channel 10 → SCIF1
  transmit) does not move data, which is one cause of the repeated
  `CInaiProtocol … write failed` lines (row C2).

## Conclusion

The hypothesis holds and the falsifier did not fire: a DMAC model of about
300 lines, three corrections of QEMU's card model, one of the SD host model
and one alias take the EU2011 boot from "first data transfer times out" to
"card unlocked, opening image loaded, both partitions mounted" on QEMU
8.2.10 and 11.1.3 alike. M8.D2 (go to F4?) is now due; the first thing in
the way is not the micon but the launcher's own version check.
