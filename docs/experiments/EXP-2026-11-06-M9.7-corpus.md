# EXP-2026-11-06-M9.7: Synthetic L3 corpus with Python-reader verdicts

- **Status:** done (tool)
- **Date:** 2026-11-06
- **Sample:** no vendor data and no firmware image used. Every fixture is
  generated by `tools/l3_harness/corpus.py` from constants and the repository's
  own writers; the reference image was not read.
- **Claims:** C-1690 (text below; register in `docs/research/claims.md`)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the L3 corpus be generated with **no vendor bytes**, so that every file
carries the verdict its Python reader actually produces, and `manifest.py`
accepts the result as an `osm2leaf.l3.manifest/v1` document?

## Hypothesis

Yes. The repo already has the mutation tools (`ind_mutate.py`,
`hddinfo_variants.py`) and the writers (`cmpind_writer.py`,
`drstr_ze0.build`), so each accepted/rejected fixture can be produced by the
same code that the L3 harness must later agree with. The one case that cannot
be synthesised is the factory acceptance baseline; it stays an operator-supplied
slot and must be reported as skipped, never invented.

## Inputs

| Item | Value |
| --- | --- |
| Tool | `tools/l3_harness/corpus.py` (Python 3.14.4, standard library only) |
| Manifest schema | `tools/l3_harness/manifest.py`, `osm2leaf.l3.manifest/v1` |
| Readers | `tools/cmpind.py`, `tools/drstr.py` + `cardcheck` size rule, `tools/hddinfo.py` (model M0), corpus tile reader |
| Mutators | `tools/ind_mutate.py` (8 variants), `tools/hddinfo_variants.py` (89 variants) |
| Writers | `tools/cmpind_writer.py`, `tools/drstr_ze0.py` |
| Vendor data | none (the vendor `factory/` slot is empty and reported skipped) |

## Method

```bash
# 1. compile + self-test (builds into a temporary directory, validates the
#    manifest with manifest.py and re-runs every reader)
python3 -m py_compile tools/l3_harness/corpus.py
python3 tools/l3_harness/corpus.py --selftest

# 2. build and re-check a real corpus tree
python3 tools/l3_harness/corpus.py build /tmp/opencode/l3corpus
python3 tools/l3_harness/corpus.py check /tmp/opencode/l3corpus

# 3. independent validation of the same document
python3 tools/l3_harness/manifest.py validate \
  /tmp/opencode/l3corpus/manifest.json --root /tmp/opencode/l3corpus

# 4. `manifest.py build` consumes the same files
python3 tools/l3_harness/manifest.py build --root /tmp/opencode/l3corpus \
  --out /tmp/opencode/l3-manifest-rebuild.json \
  --case factory:cmp_ind:cmp/factory/ADDRE001.DAT.cmp \
  --case tile_factory:tile:tile/B28R070R.DAT \
  --case drstr_factory:drstr:drstr/DRSTR001.DAT \
  --case hdd_info_factory:hdd_info:hdd_info/factory/HDD_INFO.TXT

# 5. package and repository self-tests
python3 tools/l3_harness/selftest.py
python3 tools/selftest.py
```

## Observations

The first `--selftest` run of the inherited partial file failed all 11 checks
with the same string:

```
FAIL build: every non-factory case is present: stream count does not match ceil(usize/chunk_size)
...
corpus selftest: FAILED (11/11 checks)
```

Defects found and fixed (implementation, not checks):

1. A leftover probe `CmpFile.from_parts(len(refer), CHUNK, [])` in the
   `poi_rename` branch ran `CmpFile.check()` on a container with zero streams;
   that is the failure above. The object was immediately replaced by
   `from_files`, so the probe was dead weight and is removed.
2. `_write_cmp_pair` used `Path.with_suffix(".cmp")` on the stem
   `ADDRE001.DAT`, which yields `ADDRE001.cmp` / `ADDRE001.ind`: the `.DAT`
   suffix was replaced, not appended. The corpus layout, the docs and the test
   lookups all name `ADDRE001.DAT.cmp`, so the 8 `ind_mutate.py` entries were
   written under a name the test could not find, and the selftest's
   `first_pair` read the same wrong name. The pair is now written as
   `<stem>.cmp` / `<stem>.ind`, dots in the stem included.
3. The tile truncation negative cut 64 bytes from the end of the file, which
   landed in the 256-byte alignment padding after the record; `read_tile`
   correctly ignores that padding, so the test — not the reader — was wrong. It
   now cuts one byte inside the record (`record_end - 1`), and a header-only
   file is a separate negative.
4. Two tile negatives read the slot pair fields at the wrong offsets: the
   directory layout is 12-byte header, 4-byte slot tag, then `words`,
   `inflated`; `+12` is the tag. The tests now patch `+16` (word count) and
   `+20` (inflated count) and keep both.
5. "Every reader must see ACCEPT and REJECT" is unsatisfiable: the manifest
   case table has no rejecting `tile` case (`tile_factory` and `tile_edited` are
   both ACCEPT). The check now requires every verdict the case table *allows*
   for a reader, and the tile negatives are exercised through `read_tile`.
6. The `factory`-case assertion conflated the synthetic baseline
   (`cmp/factory/`, case `factory`) with the operator slot (`factory/`). The
   placeholder is now identified by its `factory/` path prefix; the skipped
   slot and the synthetic baseline can both exist.
7. `_print_check` suppressed every problem starting with `corpus[`, `schema:`
   or `corpus:` — exactly the size/SHA-256 lines — so `check` reported
   "3 problem(s)" but printed two. It now prints every problem it counted.

The hdd_info family was completed to the full matrix that `TODO.md` M9.7
names ("`hddinfo_variants.py` 89"): the default run (73 content edits + 16
permutations) is staged, and each variant's expected verdict is the M0 model's
own verdict, so accepted mutations are entered under `hdd_info_factory` and
rejects under `hdd_info_mismatch`; the variant name is kept in `notes`.

The 108 entries are 13 `cmp_ind` (5 accept/reject container cases + 8 mutated
`.ind`), 3 `drstr`, 2 `tile` and 90 `hdd_info` (reference base + 89 variants:
66 ACCEPT, 23 REJECT). `manifest.py build` on four of those paths wrote a
4-entry document that re-validated `PASS`.

Controls and failure injection:

- **Positive control (tile, vendored reader):**
  `corpus.vendor_tile_roundtrip()` on `tile/B28R070R.DAT` returns `True` — the
  git-ignored `tools_ze0/clarion_tile.read_tile` + `write_tile` reproduce the
  container byte for byte (payload SHA-256
  `1d010c67a09a0449b9d2ab99e844015ad0f7107bb5ad390ebce9d1742b89aeb8`). The
  self-test skips this cross-check only when the vendor tree is absent.
- **Negative control (cmp):** `cmpind.decode` rejects all 8 `ind_mutate.py`
  variants; each rejection is checked directly with the reader.
- **Negative control (drstr):** a root name that is not `/`, an orphan node and
  a one-byte directory-size bump are all reported by `_drstr_problems`; the
  reversed listing is not.
- **Corpus tamper:** appending one byte to `cmp/factory/ADDRE001.DAT.cmp` makes
  `check` exit `1` with 3 problems (`size mismatch`, `sha256 mismatch`, and
  `cmp_ind gave REJECT`).
- **Determinism:** two builds in one process produce identical manifests; the
  self-test asserts the full JSON equality.

`python3 tools/selftest.py` reports `passed=25 failed=1 skipped=20`; the single
failure is `tool:osm_ingest` (`bbox records FAIL (0, 0, 0)`). `tools/osm_ingest.py`
is an untracked file from a different task in this checkout, and this change
does not touch it.

## Interpretation

- **FACT:** the corpus is reproducible from the repo alone: 108 entries, all
  validated by `manifest.py`, and every recorded verdict is the one the named
  Python reader returns.
- **FACT:** the full mutation matrices `TODO.md` names are present — 8/8
  `ind_mutate.py` variants (all rejected) and 89/89 `hddinfo_variants.py`
  variants (66 accepted, 23 rejected by model M0).
- **OBSERVED:** the vendor `factory/` pair is the only case that cannot be
  synthesised; with it absent the build reports one `skipped` line and writes a
  README in the slot instead of a manifest entry.
- **OBSERVED:** the manifest schema cannot express a rejecting `tile` entry
  (`tile_factory`/`tile_edited` are both ACCEPT), so tile negatives live only in
  the self-test; adding a `tile_corrupt` case belongs to `manifest.py`, which
  this task does not own.
- **HYPOTHESIS:** the corpus is a valid input for the Ghidra contract oracle
  (M9.5/M9.8); whether the firmware agrees is untested and needs L3/L4.
- **UNKNOWN:** none of these verdicts has been confirmed on a car or on the
  unit; M0 remains an unvalidated model.
