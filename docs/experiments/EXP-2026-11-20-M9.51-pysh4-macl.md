## Question

Does the engine's `0x0nmF` arm, rewritten as the manual's `MAC.L @Rm+,@Rn+`
(two memory longs, post-increment by 4, SR.S saturation to 48 bits), change
any L3 result recorded so far?

## Hypothesis

The old arm multiplied the register values (C-5304). The opcode shapes seen
in the corpora (`0x001F`, `0x003F`, `0x011F`, `0x07FF`, `0x0FFF` lead the
counts) are mask constants, so `mac.l` is probably data inside pdata ranges
and no L3 run executed it. **Falsifier:** any documented L3 run executing a
`mac.l`; `isolate` naming another form; `compare` reporting a disagreement or
drift; the new selftest rows passing on the old arm.

## Interpretation

- **FACT:** the arm now follows the manual's MACL code (memory operands,
  post-increment, n == m, S = 1 saturation to 48 bits, loads before writes);
  only `mac.l` changed outcome; `compare` stays 0 / 0 on three corpora.
- **FACT:** none of the 11 documented L3 runs executed a `mac.l`
  (31.7 M instructions counted), so no recorded L3 verdict changes.
- **INFERENCE:** the `mac.l` halfwords in the corpora are mostly mask
  constants (`0x1F`, `0x3F`, `0x7FF`, `0xFFF`) inside pdata ranges, like
  `div1`'s (C-5185) — data, not code.

## Conclusion

`mac.l @Rm+,@Rn+` is modelled per the manual; `isolate` lists only `mac.l`
(256 halfwords); `compare` 0 / 0 on EU2011 Navi, EU2011 nk, US2011 Navi; the
fast path leaves it to `_step`; no documented L3 run executes it, so no
behaviour change for existing results.
