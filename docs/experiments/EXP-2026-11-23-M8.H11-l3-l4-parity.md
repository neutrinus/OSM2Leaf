## Question

At L4 (QEMU `-M ze0`, full `Navi.exe` + kernel + card), do the `MMAIN001.DAT`
reader and the `DRSTR001.DAT` parser return the same values the L3 harness
(`tools/mmain_l3.py`, `tools/drstr_l3.py`) models for them at mount?

## Hypothesis

Yes: breaking at the reader/parser entries at mount and reading their `r0`/`r2`
return and the buffers they build yields fields equal to the L3 model (reader
`r0 = 0` and buffer `= swap16(MMAIN001.DAT)`; parser verdict `0` and the
40-directory / 285-file tree the L3 run reads from the same file).

**Falsifier:** a compared field differs (the L3 preconditions are then wrong
for that target); **or** a field cannot be read at the breakpoint, in which
case no `same` may be fabricated and the task stops honestly (the block's Stop
clause: record coverage evidence and stop).

4. **Scope.** EU2011 build A, the EU card, one boot per attempted capture

## Interpretation

- **FACT:** the tool meets the navigator's contract: `--selftest` runs with no
  QEMU/image/card (17 checks), a missing QEMU/image/card/gdbstub is exit **3**
  with one named `NOT RUNNABLE` line (never 0/1), and the negative control is
  produced by the tool (a 4095-byte file) and prints a `DIFF`, exit 1.
- **OBSERVED:** at L4 both readers **do** run at mount: the reader entry fires
  and the parser returns `0` (ACCEPT); the reader's mount argument is
  `r4 = 0` in `fn 0x00419ca0`, consistent with the L3 verdict `ACCEPT`.
- **OBSERVED:** the executing PC of a module VA is `VA - 0x400000` on this
  host (`0x0041a438 -> 0x0001a438`), not the literal VA and not the P1 alias
  `0x8d97…`; a `Z0` breakpoint on the literal or the P1 alias never fires.
- **OBSERVED:** the user buffer IS reachable, but not by the gdbstub `m`
  packet (which fails for `0x0002b598`, `0x00e23cc0`, `0x009cfcd4`,
  `0x00e25420` in user mode). QEMU 11.1.3's HMP has `gva2gpa`: while the guest
  is stopped at the reader entry, `gva2gpa 0x0002b598` prints `gpa:
  0xbee4598`, and `xp /2048wx 0xbee4598` reads the full `0x1000` bytes
  (`words read 2048`). The documented physical-address fallback therefore works
  once the VA is translated.
- **BLOCKED:** the concrete fields still cannot be pinned to the mount call:
  at the reader *entry* the destination buffer holds stale bytes
  (`sha 876f9a1b831e`, `eqswap16(file) False`, `eqraw(file) False`), and the
  *return* capture is interrupt-unstable - a return breakpoint continue was
  stolen by an interrupt (`pc=8800f060 r0=1553a17c`) before the buffer could
  be read, and the reader's mount return was never caught cleanly (the captured
  entries had `pr = 0x0001a438`, the step-over artifact, not the mount caller
  `0x00419cd0`). A match of the reader buffer at the mount return was never
  observed (`buffer_sha256_swap16 = None` in every attempt), so no field may be
  reported `same` - the task's Stop case. The parser tree data
  (`0x009cfcd4`, `0x00e25420`) did not even translate (`gva2gpa` -> no `gpa`)
  while the parser's file work runs before the mount state is set.
- **UNKNOWN:** whether the reader's `swap16` copy happens at
  `fn 0x0041a304` (the M3.8 / C-1787 claim) on the mount path; the three
  `0x0041a304` calls seen were early (4.17 s), not the mount path, and the
  buffer comparisons there were `eqswap=False`.

## Conclusion

No format fact changes: the L3 models of `MMAIN001.DAT` and `DRSTR001.DAT`
stand as before. What this record establishes is the **L4 mechanism and its
limit**: the readers run at mount and the reader returns `ACCEPT`, but the
field-level comparison the task asks for cannot be captured by breakpoints at
the two reader VAs in this environment because the reader's buffer and the
parser's tree data live in user memory the gdbstub `m` packet cannot read while
the guest is in user mode, and a kernel-mode stop was not obtained. The new
`tools/ze0_l3parity.py` (exit-3 not-runnable contract, 17-check selftest,
candidate-PC mapping, tool-produced negative) is in place so the comparison
runs unchanged once a capture method works. TODO M8.H11 is `blocked`; the
`F4` column of reader-coverage rows 3 and 4 is **left unchanged** (there is no
parity result to record, and the existing `L4 factory (M8.H8)` traces are not
contradicted).
