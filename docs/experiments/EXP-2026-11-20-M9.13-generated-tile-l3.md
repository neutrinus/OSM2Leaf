- **Date:** 2026-11-20
- **Sample:** firmware: `archive/head256.img` SHA-256

  `tools/mesh_split.py`, `tools/roadclass_v0.py`, `tools/tilewriter.py`,

## Question

Does the firmware read a tile we wrote the way it reads the factory tile?
M3.25 found the reader (read-completion handlers) and a way to run it
(`datask_l3.py mount`). This run puts a generated `B48R058R.DAT` (the Poland
tile of the P1 card) on the EU card and compares what the firmware asks for
and parses.

## Hypothesis

A tile written by `tilewriter.py --factory` (factory container, our road
records written in place) is read by the firmware exactly like the factory
tile during the mount: same reads, same handlers, same bytes parsed. A tile
written without a factory container is not.

**Falsifier:** the firmware never reads the directory that holds our changed
slot (the comparison would then say nothing); or a damaged directory header
compares as SAME (the comparison would then have no teeth).

## Inputs

- OSM input (hand-written, 4 nodes, 2 ways near Krotoszyn, 51.70 N 17.45 E:
  one `highway=primary` named `Testowa`, one `highway=residential`), file
  SHA-256 `28371ef0cb790f34d1583ef8d22b5e981226aed26b78cf4858548337b9736937`.
- Generated tile **G**: `osm_ingest.py` → `mesh_split.py` → `tilewriter.py
  --factory <factory B48R058R> --cell B48R058R --level 1 --country 616
  --no-names --class-table <roadclass_v0>`; 289,319,168 bytes, SHA-256
  `439a8f79edcdbf2eb8b3b603569d41238ff4bc59f795e65267ca5a999466055f`
  (zlib 1.3; compressed bytes depend on the zlib version). The writer reports
  2 pairs written in place in directory `(y 77, x 941)`, slots 17 and 18.
- Fresh-container tile **S**: `one_tile_pipeline.py --synthetic --cell
  B48R058R` (roads only, no factory bytes), 22,272 bytes, SHA-256
  `a9996371bcced56c3cdd5c37819060f3975ca7219b488397bbec5d33a0259159`.
- Wrocław was tried first and refused by the writer: its directory is kind
  `0x2146` (preserve-only, M5.22). Krotoszyn lies in a `0x2046` directory.

## Method

1. **Choosing the tile the firmware reads.** At mount the firmware reads the
   `BxxRyyR` tile under a start position. `0x0040b49c(kind)` takes it from a
   per-area table (the EU card gives `0xa6a1cde3`); when the table has no row
   the code uses the `u32` at data VA `0xd940e4`. The value is
   `(lat code << 16) | lon code` with the `COORD001` grid of `map-tiles.md`
   (`lat code = 32768 + 192·lat`, `lon code = 52742 + 128·lon`):
   `0xa6a1cde3` is 51.505 N, 0.273 W. `datask_l3.py mount --position LAT,LON`
   writes the global and makes `0x0040b49c` answer "no row".
2. **Where G differs from the factory tile** (byte compare + `clarion_tile.
   read_tile`): 60,416 bytes in four runs. Two are 6-byte runs inside the
   section-1 level-1 directory at `0xa10b100` (kind `0x2046`, y 77), at
   `+0x2336` and `+0x253a`: the pair entries of slots 17 and 18. Two are the
   record blocks of those slots (`0xa1b0a00`…, `0xa1beb00`…).
3. **Runs** (each: `datask_l3.py mount IMG256 --card-image CARD --position
   51.70,17.45 --bytes --json OUT`):
   - F: unchanged card;
   - G: `--replace MAPAL001/B48R058R.DAT=<G>`;
   - C1: G plus `--flip MAPAL001/B48R058R.DAT@0xa10b103:0x60` (directory
     header count `a`: 32 → 64);
   - C2: G plus `--flip …@0xa10d436:0xff` (first byte of slot 17's changed
     pair entry);
   - S: `--replace MAPAL001/B48R058R.DAT=<S>`.
4. **Compare:** `datask_l3.py diff F.json X.json` (read by read: file, tag,
   position, length, status, handler, bytes and runs loaded per function).

## Observations

**Run F** (factory): 28 reads, 9 of `B48R058R.DAT`:

| # | Position | Length | Handler | Object (container model) |
| --- | --- | --- | --- | --- |
| 1 | `0x0` | `0x1000` | `0x0040b8b4` | header |
| 2 | `0x1000` | `0x400` | `0x0040c308` | section 1 table |
| 3 | `0x141e200` | `0x14100` | `0x0041597c` | section 1 level-2 directory |
| 4 | `0xa10b100` | `0x8100` | `0x0041597c` | section 1 level-1 directory (y 77): **the one G changes** |
| 5 | `0xaec5f00` | `0x400` | `0x0040c308` | section 2 table |
| 6 | `0xb762300` | `0x14100` | `0x0041597c` | section 2 level-2 directory |
| 7 | `0x10959f00` | `0x2100` | `0x0041597c` | section 2 level-1 directory |
| 8 | `0x1128cb00` | `0x400` | `0x0040c308` | section 4 table |
| 9 | `0x113c7f00` | `0x6100` | `0x0041597c` | section 4 level-1 directory |

In read 4 the slot-table parser `0x00414dbc` loads 16,514 bytes,
`+0xa`–`+0x408b`: the whole slot table, including `+0x2336` and `+0x253a`.

**Comparisons:**

| Pair | Verdict | Differences |
| --- | --- | --- |
| F / G | **SAME** (0) | none in 28 reads |
| G / C1 | **DIFFERENT** (1) | read 15 of the run (`0xa10b100`): `0x00414dbc` loads 33,014 bytes instead of 16,514 |
| G / C2 | SAME (0) | none: a changed pair entry is loaded but changes nothing the mount does |
| F / S | **DIFFERENT** (9) | header: `0x0040aa50` loads 32 bytes in 11 runs instead of 40 in 7; three section tables of `0x100` at `0x1000`, `0x5500`, `0x5600`; one directory read `0x1100`/`0x8100` that **fails** (status `-1`, nothing parsed); no further reads of the tile |

**Read lengths.** The firmware asks for a fixed length per directory, not
for the directory's own size: `0x14100` (level 2), `0x8100` (section 1 level
1), `0x2100` (section 2 level 1), `0x6100` (section 4 level 1) on this tile
and the same values on `B48R068R.DAT`/`B28R070R.DAT` (M3.25 run). S is 22,272
bytes (`0x5700`), so `0x1100 + 0x8100` is past its end.

**Position check.** With `--position 30.4,-9.6` the firmware reads
`B28R070R.DAT` (header, section tables `0x1000`, `0xec800`, directories
`0x7800`, `0x6ad00`, `0xec900`, `0xf4f00`) instead of `B48R068R.DAT`; with
`51.70,17.45` it reads `B48R058R.DAT`. The directory read in each case is the
one whose box holds the position (`clarion_tile.read_tile`: `0x6ad00` is
y 45, `0xa10b100` is y 77).

**The mount does not finish.** State stays 2 in every run (as in M3.25): the
firmware sends message `0x1507` to a task that is not in the run. No record
block (the zlib records that hold the roads) is requested before that point.

## Interpretation

- **FACT:** on the EU card, with the car placed at Krotoszyn, the firmware
  reads the level-1 directory our writer changed and parses all of its slot
  table.
- **FACT:** for a factory-container tile with our roads written in place the
  firmware's mount is read-for-read identical to the factory tile (F / G
  SAME).
- **FACT:** the comparison detects a damaged directory header (C1) and a
  tile with another container layout (S).
- **FACT:** the fresh-container tile is not readable as written: the
  firmware's directory read runs past the end of the 22 KiB file and fails.
  A writer without a factory container must at least back every directory
  with the length the firmware asks for.
- **FACT:** a wrong pair entry (C2) is not detected by the mount. Pair
  entries are record lengths; they matter when a record block is read.
- **OBSERVED:** the fixed read lengths per level and section (four values,
  three tiles). How the firmware derives them (level table, directory kind)
  is not read from the code here.
- **UNKNOWN:** whether the firmware accepts our road *records*: no record
  block is read during the mount. That needs the mount to finish (answer to
  message `0x1507`) and a map request (message `0x14b5`).
- **Scope:** EU2011 build A, EU card, PySh4 with the models listed in
  `datask_l3.py`. Not a statement about the unit.

## Conclusion

The hypothesis holds on both sides and neither falsifier fired. `tile_reader`
has its first verdicts: the factory-backed generated Poland tile is read
like the factory tile through header, section tables and directories; the
fresh-container tile fails at its first directory read. The gate covers the
container down to the directories, not yet the records.

## Reproduction

```
python3 tools/osm_ingest.py krotoszyn.osm -o k.imf
python3 tools/mesh_split.py k.imf -o ksplit
python3 tools/roadclass_v0.py --class-table-out ctab.json
python3 tools/tilewriter.py ksplit --out G.DAT --cell B48R058R --factory <factory B48R058R.DAT> --class-table ctab.json --country 616 --level 1 --no-names --json
python3 tools/datask_l3.py mount archive/head256.img --card-image <EU card> --position 51.70,17.45 --bytes --json F.json
python3 tools/datask_l3.py mount archive/head256.img --card-image <EU card> --position 51.70,17.45 --replace MAPAL001/B48R058R.DAT=G.DAT --bytes --json G.json
python3 tools/datask_l3.py diff F.json G.json
python3 tools/datask_l3.py mount … --replace MAPAL001/B48R058R.DAT=G.DAT --flip MAPAL001/B48R058R.DAT@0xa10b103:0x60 --bytes --json C1.json
python3 tools/datask_l3.py diff G.json C1.json
python3 tools/one_tile_pipeline.py --synthetic --cell B48R058R --out syn
python3 tools/datask_l3.py mount … --replace MAPAL001/B48R058R.DAT=syn/MAPAL001/B48R058R.DAT --bytes --json S.json
python3 tools/datask_l3.py diff F.json S.json --file B48R058R
```

A mount with a replaced 289 MB tile takes about four minutes.

  factory-backed splice in a `0x2046` directory does not disturb the mount.
