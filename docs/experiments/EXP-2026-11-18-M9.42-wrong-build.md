## Question

When a `point_walk_l3` run names a build whose walker VAs belong to the *other*
card, does the tool return a machine-readable negative verdict, or does it die
with a traceback that a script cannot tell apart from a crash?

## Hypothesis

The M9.39 mutant page proves both builds read both *pages*, so only the
build-vs-image pairing is fatal. A mismatched pairing makes the engine execute
the wrong VAs and raise `UnmappedAccess`; the tool should catch that and print
one `result: FAIL (unmapped 0x… @ build <b>)` line and exit 1, while a matching
build keeps its exact `result: PASS`. **Falsifier** (stated before the runs):
the wrong-build run still exits on a bare traceback with zero `result:` lines,
or a matching build loses its `result: PASS`.

## Method

1. **Sample and hash.** The two 256 MiB heads above; the factory US pair from
   `leafre-work/m5.12-us/root-factory/REFER001/`; the mutant pairs rebuilt into
   `~/projekty/leafre-work/scratch/m9.42/` from the M9.39 recipe (the old
   `/tmp/opencode/m939` is gone, so the pairs were regenerated, not reused).
2. **The defect, before any code change.** Run the US-target walk on the EU
   head with the factory page and count `result:` lines — the crash path the
   task's Precheck names.
3. **The change.** `tools/point_walk_l3.py`:
   - `engine_call(eng, va, args, build)` wraps `eng.call`; an
     `UnmappedAccess`/`IllegalInstruction` from `engine.py` becomes a
     `BuildMismatch` carrying `code`, `fault_va` (the address the engine's
     message names, `covers 0x…` / `at 0x…`) and the SH-4 `pc`.
   - `_verdict(fails, mismatch, build)` prints exactly one `result:` line:
     `result: FAIL (unmapped 0x… @ build <b>, <CODE> pc=0x…)` and returns 1 on
     a mismatch, `result: PASS` / `result: FAIL (n)` otherwise. `PASS` stays
     the only pass token.
   - `check_entry(text_va, text, entry, build)` is the deterministic half: a
     build whose walker entry is not inside the image's executable text is a
     `BuildMismatch` as soon as the pairing is wrong, independent of what the
     wrong code happens to read. `run_nth`/`run_skip` call it with
     `nth`/`skip`.
   - `guarded(thunks)` is the one place a `BuildMismatch` becomes a verdict: it
     runs the record thunks in order, keeps the values produced so far and
     returns `(values, mismatch)`. `cmd_walk`/`cmd_skip` both call it, so a
     deleted `except` there fails the selftest instead of crashing a run.
   - `_verdict(fails, mismatch, build)` prints exactly one `result:` line:
     `result: FAIL (unmapped 0x… @ build <b>, <CODE> pc=0x…)` and returns 1 on
     a mismatch, `result: PASS` / `result: FAIL (n)` otherwise. `PASS` stays
     the only pass token.
   - `--selftest` gains six checks (no vendor data): both `run_nth` and
     `run_skip` raise `BuildMismatch` with `code == "UNMAPPED"` and `fault_va`
     equal to their target VA when the entry lies outside the executable text;
     `guarded` stops at the fault and passes values through otherwise; and
     `_verdict` prints `result: FAIL (unmapped` and `result: PASS` through an
     `io.StringIO` sink.
4. **Controls.** *Positive*: the matching pairing (US on `us256.img`, EU on
   `head256.img`) must still print `result: PASS`; the M9.39 mutant page on
   *its own* build is the positive witness and must also `PASS`. *Negative*:
   the wrong *build* pairing (US target on `head256.img`, EU target on
   `us256.img`) must print `result: FAIL (unmapped …)`, never a traceback.
5. **Falsifier** (stated above, before the runs).

## Interpretation

- **FACT:** before the change the wrong-build run exited 1 with zero `result:`
  lines and a bare `engine.UnmappedAccess` traceback — a script could not tell
  "wrong build rejected" from "the tool crashed".
- **FACT:** after the change a wrong pairing exits 1 with exactly one
  `result: FAIL (unmapped 0x… @ build <b>, …)` line and no traceback, through
  two independent paths: the upstream `check_entry` (the entry is outside the
  executable text) and, for these real pairings, the engine fault itself; every
  matching pairing still exits 0 with `result: PASS`, so the verdict for a
  matching build is unchanged.
- **FACT:** the engine faulted at **pc = walker entry + 4**, on the page word
  the build's own prologue reads: disassembly shows US `0x0041db44 mov r2,r0`,
  `0x0041db46 mov.w @(r0,r8),r0`, `0x0041db48 shll2 r0` and EU
  `0x003f5194 mov #17,r0`, `0x003f5196 mov.b r3,@(r0,r11)`,
  `0x003f5198 mov #18,r0`; the recorded pc is one instruction past the entry
  because `engine._step` advances `pc` before `_execute` (`engine.py:753-761`).
  `check_entry` makes the verdict deterministic even when the wrong bytes
  happen not to fault the engine.
- **FACT:** the mutant page is a *positive* witness, not a negative control:
  on its own build it still prints `result: PASS` with the M9.39 offsets, and
  it is the wrong *build* (not the page) that fails.
- **IMPLICATION:** M9.41's falsifier, which treated the M9.39 mutant as a
  negative control, is replaced by a check that can fail: a wrong-*build* run
  must print `result: FAIL`, and the mutant page is labelled the positive
  witness it is.
- **LIMITATION:** the engine fault path reacts only to an address-space fault
  (`UnmappedAccess`/`IllegalInstruction`); `check_entry` covers the entry
  itself. A mismatch that reaches an import slot before either fires would
  still be a stub problem, which the task's `Stop` hands to M9.24, not a faked
  verdict.

## Conclusion

`tools/point_walk_l3.py` now turns a wrong build/image pairing into one
`result: FAIL (unmapped … @ build <b>)` line and exit 1: `check_entry` rejects
an entry outside the image's executable text as soon as the pairing is wrong,
and `engine_call`/`guarded` turn an engine `UnmappedAccess` /
`IllegalInstruction` into the same verdict, while `result: PASS` is kept for a
matching build. The M9.39 mutant page is the positive witness (it still passes
on its own build) and M9.41's falsifier now names a wrong-*build* check that
can fail. No claim rows are added beyond C-4430–C-4439 in
`docs/research/claims.md`; the reader-coverage matrix row is unchanged because
the verdict for a matching build did not move.
