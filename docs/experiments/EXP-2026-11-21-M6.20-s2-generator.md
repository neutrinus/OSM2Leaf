## Question

Which M5.13b-era code path wrote the 4,233,336 B `POINT010.DAT.cmp` that makes
the recorded S2 `af4c9ff1…`, and is that image a valid card to stack S3 on?

## Hypothesis

The recorded S2 came from the pre-M5.25 `mutate_refer_poi.py` (commit
`339feed8`, the state on 2026-11-08), whose refit padded the edited page to the
next 0x100 boundary and fell back L6 → L9. Because M5.13b's report is internally
consistent only if the inner page used a 4,2534 B stream, the zlib build must be
the host's zlib-ng. **Falsifier:** no setting of a historical commit reproduces
the pair `c2b9c388…`/`dd5398f9…` byte for byte, or the produced image is not
`af4c9ff1…`.

## Observations

- **Encoder.** For the recorded S2 pair, recompressing the unchanged page
  stream in every candidate setting shows exactly one match: the inner page at
  **L9, memLevel 8** under **zlib-ng 1.3.1** (`zlib.compress(inner, 9)`), and
  each unchanged outer stream at **L6, memLevel 8** under the same build.
  Recompressing the recorded `.cmp` blob wholesale at L6/m8 reproduces it
  byte for byte (`recompress == ps: True 4233336 4233336`). Under stock zlib
  1.3.2 the same page at L6/m8 is 42,657 B and L9/m8 is 42,508 B, so the
  recorded bytes are zlib-ng-specific.
- **Legacy path.** Commit `339feed8` (`--page …` with the unconditional
  `limit = (page+consumed+0xFF) & ~0xFF`, `zlib.compress(new_inner, 6)` with an
  L9 fallback) run under zlib-ng writes `.cmp` 4,233,336 B / `.ind` 612 B,
  equal to the recorded pair; through `imgpatch` it gives
  `af4c9ff1…c578e911`, `cardcheck` `RESULT: PASS`.
- **Two earlier candidates fail.** Commit `69fcd8ba` and `25ac79d9` use only
  L6 and refuse the page (`recompressed page is 43305 bytes, only 42848
  available`): under zlib-ng L6/m8 is 43,305 B, larger than the 42,848 B slot,
  and neither has the L9 fallback.
- **What the pad overwrites.** The factory page stream ends at `0x84b231`
  (42,641 B from `0x840ba0`); the next 0x100 boundary is `0x84b300`. An
  **abutting** inner zlib stream starts at `0x84b234` (3 B after the stream
  end, inside the pad window). The recorded S2 writes zero over
  `[0x84b234, 0x84b300)` (204 bytes that were non-zero in the factory), so on
  the recorded image the page at `0x84b234` fails to inflate
  (`unknown compression method`), while on today's valid S2 it inflates to
  127,300 B. The modern refit (`slot_budget`, M5.25) stops the slot at the
  stream end and would refuse, which is why today's tool cannot produce the
  recorded bytes.
- **Byte ranges.** `imgpatch --check-diff` on the recorded S2 reports 17,737
  diff ranges, 0 outside the POINT010 clusters and directory entries — the
  corruption is *inside* the replaced file, so the range check that M5.13b
  relied on cannot detect it.
- **Stacked S3.** `s3_vertex_patch.py image` from the recorded (corrupt) S2
  gives `dd5464d1be88f7e279d0a9fee2ed7e913ca76d8cd0ab2c1121ebe65049f20474`;
  from today's valid S2 (`1f1b444e…`) it gives
  `fc1433d232eacb0f3e86a0ee85776f53e1bc395fad125e076c54e9db34a77f72`
  (unchanged from C-5253).

## Interpretation

- **FACT:** the recorded S2 `af4c9ff1…` **is** reproducible from the repo:
  `mutate_refer_poi.py … --legacy-m513b --whole-blob` (under zlib-ng 1.3.1)
  then two `imgpatch` writes. C-6200.
- **FACT:** the mechanism is the pre-M5.25 unconditional pad to the 0x100
  boundary plus the L6→L9 fallback; both earlier candidates lack the fallback
  and refuse. C-6201.
- **FACT:** that pad overwrites 204 non-zero bytes of an abutting page at
  `0x84b234`; the recorded image is therefore byte-reproducible but **corrupt**,
  and today's slot rule (which stops at the stream end) is the correct one.
  C-6202.
- **FACT:** today's tool's valid S2 is `1f1b444e…`; S3 stacked on it is
  `fc1433d2…`. The bench must not use the recorded `af4c9ff1…` card for S2 or
  for a stacked S3. C-6203, C-6204.
- **OBSERVED:** `imgpatch --check-diff` passes the recorded S2 because every
  diff is inside the replaced file's own clusters; intra-file corruption is
  outside that gate's scope. C-6205.

## Conclusion

M6.20's Done-when is met both ways: a committed command reproduces the recorded
S2 `af4c9ff1…` exactly (`--legacy-m513b`, C-6200), and the investigation shows
that image is corrupt (C-6202), so the S2 record and the S3 package's stacked
row are re-pinned to today's valid card `1f1b444e…` / stacked `fc1433d2…`
(C-6203/C-6204) rather than recommending the historical one. `bench-packages/s3.md`
and C-2351/C-5253 gain a note pointing at this EXP; the format doc need not
change (the slot rule was already correct).
