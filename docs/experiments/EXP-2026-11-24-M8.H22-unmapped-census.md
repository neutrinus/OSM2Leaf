## Question

Which 4 KiB blocks of unmapped hardware are hit most often in one EU2011
`-M ze0` boot to the idle UI, and which existing M8.H task (or new connector
line) owns each of the top blocks?

## Hypothesis

The top blocks are the polled registers of devices that are stubbed but not
modelled (DMAC, area-6 absent chip, GPIO/CAN, USB/OHCI), so the ranking names
the next model to build. Falsifier from the task: the log has no accesses at
idle (all polled blocks already stubbed) — then the table is the list of
existing stubs and the hypothesis is refuted.

## Method

Five parts, written before the observations. The navigator's design review was
in `comm/M8.H22-nav-plan.txt` and `comm/M8.H22-nav-warning.txt`.

### 1. Sample and hash

Printing commands and their verbatim output are in Observations O1/O2: `sha256sum
archive/head256.img` and `sha256sum archive/sd-images/…_eu.img`;
`python3 tools/ze0_card.py describe archive/head256.img` prints build EU2011,
map code `QSD-302-100`, mapdb `16-16`, FAT offset `0x6400400`. Scratch under
`~/projekty/leafre-work/scratch/m8.h22/`, never `/tmp`.

### 2. Commands

Runnable from the repo root, no ellipsis:

```bash
python3 tools/ze0_unmapped.py --selftest
python3 tools/selftest.py --only ze0_unmapped
python3 tools/ze0_ipl.py patch archive/head256.img -o scratch/m8.h22/ipl.txt
python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img scratch/m8.h22/card.qcow2
# boot to idle; -msg timestamp=on adds a host elapsed prefix; HMP socket is used
# by a 5-second guest-clock sampler writing times.txt
/home/marek/.cache/qemu-ze0/build/qemu-system-sh4 \
  -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch=scratch/m8.h22/ipl.txt \
  -kernel archive/head256.img -nographic \
  -monitor unix:scratch/m8.h22/live2/hmp.sock,server,nowait \
  -icount shift=0,sleep=off -drive if=sd,index=0,file=scratch/m8.h22/live2/card.qcow2 \
  -d unimp,guest_errors,int,invalid_mem -msg timestamp=on \
  -D scratch/m8.h22/live2/qemu.log -serial file:scratch/m8.h22/live2/serial.log
python3 tools/ze0_unmapped.py scratch/m8.h22/live2/qemu.log --top 30 \
  --times scratch/m8.h22/live2/times.txt --image archive/head256.img \
  --label 'EU2011 boot to idle'
```

The guest-clock sampler reads `xp /4xb 0x09e41888` over HMP every 5 s and
records `(log_line_no, CurMSec_ms)`; the tool maps each access's timestamp
through that measured calibration (linear interpolation between samples,
clamped at the ends) and labels the result `guest ms (interpolated)`. Accesses
before the first HMP sample clamp to that first reading; this is stated rather
than hidden. No guest time is inferred from line counts or file mtimes.

### 3. Controls

- **Positive:** the synthetic log in `--selftest` contains two area-7 aliased
  accesses at `0x1fc5a000`; the tool must group them into block
  `0xffc5a000` (`GPS/odometer pulse capture or timers`) with count 2, one read
  and one write, first/last guest ms 1000/2000, and attribute a preceding
  `pc=0x8803d266` to `nk.exe`.
- **Negative 1:** a modelled-device trace line (`ze0-sdhi0: wr16 +0x00`) is
  ignored (3 blocks, not 4). A corrupted `pc=0xZZZZZZZZ` is rejected.
- **Negative 2:** dropping one synthetic access lowers the block count 2 → 1;
  changing the address `0x1fc5a000` → `0x1fc41000` renames the block to
  `GPIO ports`. The live log's empty case is the task falsifier (no accesses →
  exit 2 and an honest "0 accesses" table).

### 4. Scope

The corpus is the full `scratch/m8.h22/live2/qemu.log` (10,467,106 lines,
596 MB on disk, SHA-256 above) from one EU2011 boot to the idle UI, streamed
line by line; every `Invalid read/write at addr` and every `ze0-<dev>:
unimplemented device read/write` line is counted (1,027 accesses, quoted in
O3). Modelled-device trace lines, exceptions, register dumps and
`Unauthorized access` lines are excluded. Module attribution is static
`cerom.py` (no live module table), so `AMBIGUOUS` rows stay ambiguous. Block
names come only from `docs/research/full-system-emulation.md` §1 tables;
unlisted ranges are `unmapped/unnamed`.

### 5. Falsifier

If the idle log had no invalid/unimpl lines, the table would be empty and the
ranking meaningless — the EXP would say every polled block is already stubbed.
A single dominant block (>90 % of accesses) would also refute the "rank many
devices" premise and be reported as such.

## Interpretation

- **FACT:** 1,027 unmodelled accesses in 25 blocks; 1011 (98.4 %) carry a PC
  attributed through `cerom.py`; the top block is 29.7 % of accesses, so no
  single poll dominates (the task falsifier did not fire).
- **FACT:** the log is non-empty at idle (PC `0x880480bc`), so polled blocks are
  not all stubbed.
- **FACT:** the top four named blocks are DMAC (0xff801000, 305 writes), area-6
  absent chip (0x19b00000, 196), GPIO/CAN (0x19400000, 138) and USB/OHCI
  (0xffe70000, 41); area-6 absent chip at 0x19e00000 adds 15 more.
- **OBSERVED:** block `0x0000a000` (232) and `0x00000000` (22) are low physical
  RAM probes before the MMU is fully wired, not hardware devices; they are
  listed as `unmapped/unnamed` and are not assigned a device task.
- **OBSERVED:** `0xffc40000`/`0xffc43000`/`0xffcc0000`/`0xff800000`/
  `0xfffec000` are P4 ranges with no name in full-system-emulation.md §1;
  the tool honestly prints `unmapped/unnamed` rather than guessing a device.
- **HYPOTHESIS:** the 305 DMAC writes are setup plus per-transfer polling for
  SD/SCIF DMA; a DMAC model (with the SD host and serial drivers) would remove
  the largest block. The 211 area-6 accesses are the absent external UART
  chip probed by `ceddk.dll` / `serial_uat.dll` (M8.H2/M8.H3).
- **UNKNOWN:** the first/last guest times of the very early kernel probes are
  clamped to the first HMP sample (15,276 ms), so the tool cannot resolve when
  in the first 15 s they occurred without an earlier clock anchor.

## Conclusion

`tools/ze0_unmapped.py` turns a 10.5 M-line EU2011 boot log into a ranked
4 KiB-block census (1,027 accesses / 25 blocks), with real guest-clock times
from an HMP `CurMSec` sidecar and PC→module attribution via `cerom.py`. The
ranking points at DMAC, area-6 external UART, GPIO/CAN and USB/OHCI as the
next models, each already owned by an M8.H task; two new connector lines are
added for the DMAC and unnamed-P4 blocks so every top row has an owner. The
falsifier (empty idle log, or a >90 % single block) did not fire. The early
kernel probes' exact onset remains unknown (clamped to the first clock sample),
and block naming is limited to full-system-emulation.md §1 — no device name was
guessed.
