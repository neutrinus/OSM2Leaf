# EXP-2026-11-06-M9.4: Engine interface with three SH-4 back ends

- **Status:** done (tool); Ghidra and QEMU back ends unexecuted here (SKIP)
- **Date:** 2026-11-06
- **Sample:** no vendor data and no firmware image used. The proof is a
  32-byte synthetic SH-4 snippet (`synthetic_program()` in the tool) run on a
  synthetic map; the reference image is not needed and was not read.
- **Claims:** C-1660 (text below; register in `docs/research/claims.md`)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can one engine interface (`map`, `read_mem`, `write_mem`, `set_regs`,
`get_regs`, `call`, `on_exec`, `run_until`) drive a synthetic SH-4 snippet
through three back ends — a pure-Python SH-4 interpreter, a Ghidra P-code
adapter and a QEMU `-M none` + gdbstub adapter — with identical registers and
memory, while a back end that is absent raises its exact error code and is
reported as SKIP rather than as a pass?

## Hypothesis

The interface is thin enough to implement once in a `Backend` base class and
to leave each back end only seven primitives (`_map`, `_read`, `_write`,
`_get_reg`, `_set_reg`, `_step`, `_probe`). A 26-instruction/step snippet
(`add`, a `dt`/`bf` loop, `jsr` to a host stub that writes memory, `rts`) then
gives the same register file and the same bytes on any correct back end, so
the result is a real engine parity check, not a rendering of one engine's
behaviour. On this machine only the interpreter can run; Ghidra and QEMU must
fail with `MISSING_GHIDRA`/`MISSING_QEMU`, exit `3`, and be listed as skipped.

| Stack / dest | `0x8c1ff000..0x8c200000` / `0x8c201000..0x8c202000` |
| Arguments | `r4 = 5` iterations, `r5 = 0x8c201000` |
| Return sentinel | `RETURN_VA = 0x8c0fff00` (placed in `pr` by `call`) |
| Vendor data | none |
| Ghidra / QEMU | not installed in this environment (that is the point of the SKIP) |

## Method

The snippet is assembled by hand so every encoding is visible in the source:

| off | word | instruction | effect |
| --- | --- | --- | --- |
| `00` | `4f22` | `sts.l pr,@-r15` | save the caller's return address |
| `02` | `e000` | `mov #0,r0` | `r0 = 0` |
| `04` | `d705` | `mov.l @(5,pc),r7` | `r7 = 0x8c100100` (literal at `1c`) |
| `06` | `304c` | `add r4,r0` | loop: `r0 += r4` |
| `08` | `4410` | `dt r4` | `r4--`, `T = (r4 == 0)` |
| `0a` | `8bfc` | `bf 06` | loop while `T == 0` (no delay slot) |
| `0c` | `0009` | `nop` | fall-through after the loop |
| `0e` | `6403` | `mov r0,r4` | `arg0 = r0` |
| `10` | `470b` | `jsr @r7` | call the host stub |
| `12` | `0009` | `nop` | delay slot |
| `14` | `4f26` | `lds.l @r15+,pr` | restore `pr` |
| `16` | `000b` | `rts` | return to `pr` |
| `18` | `0009` | `nop` | delay slot |
| `1a` | `0009` | `nop` | padding |
| `1c` | `8c100100` | `.long` | stub VA |

The stub is `write_stub`: it reads `r4`/`r5`, writes `r4` as a big-endian
`u32` to `[r5]`, reads it back through the engine, and returns `StubReturn`
`0x5a5a` (the base class then sets `r0` and jumps to `pr`).

Hand-computed trace: prologue 3 + 5×(add, `dt`, `bf`) 15 + `nop` 1 + `mov` 1
+ `jsr` 1 + delay `nop` 1 + stub 1 + `lds.l` 1 + `rts` 1 + delay `nop` 1 =
**26** instruction/stub cycles. `bf` is a non-delayed branch, so the `nop` at
`0c` runs once, after the loop.

### Fixes to the previous partial attempt

The untracked `engine.py` left by the earlier attempt failed its own self-test
(7/14). Three real defects and three test-setup defects were fixed:

1. `lds.l @Rn+,…` and `ldc.l @Rn+,…` used the **m** field as the register
   instead of the **n** field (all six forms), so `lds.l @r15+,pr` read
   `[r2]` and crashed at `0x00000000`. This is what broke the snippet.
2. `--demo` compared full snapshots including the `engine` name, so a
   correct Ghidra or QEMU run could only ever print `MISMATCH`; parity now
   compares `snapshot_core()` (everything except the label).
3. The runaway check wrote two `nop`s into a four-byte region: it raised
   `UNMAPPED` after the second `nop` instead of `RUNAWAY`. It now runs
   `clrt; bf -3`, a real two-instruction endless loop inside the region.
4. `test_call_rules` built the world twice on one engine (duplicate region)
   and never checked `r4`-`r7`; it now runs `rts; nop` with four arguments.
5. `test_illegal_instruction` wrote opcodes into an `rx` region and stopped
   at its own start address; both fixed.
6. `test_memory_rules` claimed an unaligned-access check but only mapped a
   region; it now executes `mov.l @r1,r0` at an unaligned address and expects
   `UNALIGNED`.

The instruction count was also wrong in the old test (30): `bf` is a
non-delayed branch, so the loop is 3 instructions per iteration and the true
total is **26**, which the hand table above derives independently.

## Interpretation

- **FACT:** `tools/l3_harness/engine.py` implements the whole interface in the
  `Backend` base class and only the seven primitives per back end; the
  `api:` check asserts no back end inherits a primitive.
- **FACT:** the synthetic snippet produces, on `PySh4`, `r0=0x5a5a`,
  `r4=15`, `r5=0x8c201000`, `r7=0x8c100100`, `r15=0x8c200000`,
  `pc=pr=0x8c0fff00`, `T=1`, destination bytes `00 00 00 0f`, and the saved
  `pr` word `8c 0f ff 00`, in 26 cycles. A second fresh run is identical.
- **FACT:** absent back ends raise exactly `MISSING_GHIDRA` / `MISSING_QEMU`
  and the CLI exits `3`; they are reported as skipped and never contribute a
  pass.
- **OBSERVED:** the Ghidra `EmulatorHelper` adapter and the QEMU gdbstub
  adapter are written against their documented APIs but have never been
  executed here (no Ghidra, no `qemu-system-sh4`). Their parity checks are
  therefore skipped, not verified.
- **HYPOTHESIS:** one `EmulatorHelper.step` and one gdbstub `s` consume one
  SH-4 instruction, delay slots included, so the 26-cycle count will match
  across back ends. This is the assumption the parity comparison makes; a real
  run may need to adjust it (it is checked, not smoothed over).
- **UNKNOWN:** whether `qemu-system-sh4 -M none` provides RAM for `-m`, and
  whether its gdbstub register numbering matches `QEMU_REG_NUMBERS` (both are
  data in the tool, to be corrected by the first live run).
- **NOT CLAIMED:** that any firmware function runs, or that any map data is
  read by the original code. This EXP proves the engine contract only; readers
  remain `UNKNOWN` (M2/M3, M9.5).
