# EXP-2026-11-05-52: `cecompress.py` — LZSS and LZX decoders for CE ROM sections

- **Status:** done (tool, synthetic streams); no vendor image was read, so the
  format identification itself is still unconfirmed
- **Date:** 2026-11-05
- **Sample:** synthetic streams generated by `tools/cecompress.py` itself
  (no vendor bytes); SHA-256 listed under *Inputs*
- **Claims:** C-570 (proposed, below)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the two compression families a Windows CE XIP ROM can use — the 4 KiB-window
LZSS variant ("`CECompress`") and Microsoft LZX as written by `romimage` — be
implemented as a stdlib-only decoder with a matching reference encoder, so that
`IMAGE_SCN_COMPRESSED` sections (`NaviMapCC.dll` `.data`, `psize 0x2c6`,
`vsize 0x5b8`; TODO M1.2) have a candidate decoder ready for the image, and so
that an unsupported stream is refused precisely instead of decoded wrongly?

## Hypothesis

`cecompress.py` can be built and validated without vendor data in exactly one
way: symmetry. A reference encoder for the documented LZSS layout produces
streams from literals, matches, maximum-length matches and a 4 KiB window wrap,
and the decoder must reproduce them byte-exactly at several sizes. LZX cannot be
validated that way without a real Huffman port, so only its block framing, bit
reader and uncompressed ("stored") blocks are implemented and tested at the
header level; verbatim/aligned blocks must raise `UNSUPPORTED(lzx block type …)`
rather than emit partial bytes. `detect` must report evidence, and must not
silently pick LZSS just because almost any byte string survives the LZSS
decoder.

What the 186 self-test checks cover (all synthetic):

- LZSS round-trip on 12 corpora (empty, 1/7/8/9 literals, a 100-byte run,
  period-3 repeats, an 18-byte-alphabet corpus, 4096 B, 4097 B, 5000 B and
  50000 B LCG blobs), comparing the decoded bytes *and* the literal/match/max
  length/max offset counters with the encoder's, plus an encoded-size bound;
- a hand-built stream (`literal 'Q'`, then a match with stored offset 0 and
  length 18) that exercises both the 4-bit length limit and an overlapping
  self-copy;
- a 4 KiB **window wrap**: a 3-byte-prefix-unique 4096-byte prefix followed by
  its own first 200 bytes, asserting the encoder emitted stored offset 4095 and
  a length-18 match, and that the decode is byte-exact;
- LZSS negatives: truncated match, back-reference before output start,
  `expected_size` mismatch (all `DecodeError`, messages asserted);
- LZX bit reader: 16+16-bit words read whole, 5/12/15-bit reads across a word
  boundary compared against the flat bit list, `align16()` discarding exactly
  12 bits after 4 consumed and landing on word 1, short final words,
  truncated word, >24-bit read rejected;
- LZX stored blocks: single block, three blocks including an empty one, block
  type/size/R0-R2/high-byte-zero/complete flags, `expected_size` mismatch, a
  truncated block;
- LZX verbatim and aligned blocks each raise
  `UNSUPPORTED(lzx block type <name>)` and the non-strict probe stops with
  `complete: False`; block type 0 is a `DecodeError`; the reserved stream-header
  bit is a `DecodeError`;
- E8: a stream declaring pre-processing raises by default and the message names
  `e8_translation=True`; with the switch on, an in-range displacement becomes
  absolute (`4 + 0x10`), an out-of-range one is untouched and the `0xE8`
  opcodes survive;
- `detect` on the LZSS and LZX fixtures with and without the size, the

## Interpretation

- **FACT:** `tools/cecompress.py` is stdlib-only and implements exactly the two
  documented layouts: LZSS with a 4 KiB window, 8-bit flag groups (bit 0 first,
  0 = literal, 1 = match), 12-bit offset + 4-bit length (`length - 3`), stored
  offset = distance - 1; LZX with the 16-bit LE word bit reader, the 1-bit
  intel + optional 32-bit filesize + 1 reserved bit stream header, 3-bit block
  type + 24-bit uncompressed size per block, 16-bit alignment and 12-bit R0/R1/R2
  before a stored block, and one 16-bit word per stored byte.
- **FACT:** a decoder for one layout and an encoder for the *same* documented
  layout round-trip byte-exactly over 186 checks, including length 18, overlap
  and offset 4095. That proves internal consistency of the written spec, not
  conformance to the image (see the module docstring and the list below).
- **FACT:** a verbatim or aligned LZX block produces
  `UnsupportedFormat("UNSUPPORTED(lzx block type verbatim …)")`, never partial
  output; `detect` reports the framing it did parse plus `stopped early`, and
  the CLI exits 1.
- **FACT:** `detect` never confirms on structure alone. LZSS success is
  downgraded to `weak` because almost any input survives it; only an
  `expected_size` match confirms a candidate. A valid zlib header suppresses an
  otherwise unconfirmed candidate (map `.cmp` is not a ROM stream). Ties at the
  same evidence level are `ambiguous` with both names, not a coin flip.
- **OBSERVED:** `lzx_e8_translate` is implemented and switchable but has not
  been checked against any published LZX stream; the stored-block quirks
  (0..15 pad bits, one 16-bit word per byte) are documented from memory of the
  MS format, not from a sample.
- **HYPOTHESIS:** `NaviMapCC.dll .data` (psize `0x2c6`, vsize `0x5b8`, ratio
  ≈ 0.49) is consistent with a short, repetitive RW section, so a dictionary
  compressor (LZSS or LZX) is plausible; a 2:1 ratio does not discriminate
  between them. Nothing in the repo proves which family the image uses.
- **UNKNOWN:** which method, if either, the ZE0 image actually uses for its 245
  `IMAGE_SCN_COMPRESSED` sections; whether the ROM even uses the Okumura byte
  order (nibble-swapped and length-in-first-byte variants exist); whether LZX
  stored blocks appear at all or the ROM writes only verbatim/aligned blocks;
  whether CE's `romimage` wraps the stream in an extra length prefix.

### What cannot be verified without the image

1. That either decoder reproduces `vsize` bytes from a real `o32` section — the
   M1.2 "done when" condition. No section has been decoded.
2. Which family the image uses. `detect` can rank candidates on the real bytes,
   but a `confirmed` verdict needs `o32_vsize`, and a `weak` LZSS verdict is
   still not proof.
3. The LZSS byte order (offset low byte first vs length nibble first), the
   match threshold and whether CE prefixes a length — all three are format
   choices this code fixes by fiat.
4. The LZX bit order across word boundaries, the 0..15 vs 1..16 padding rule,
   the "one 16-bit word per stored byte" rule and the E8 algorithm.
5. Whether the ROM's LZX blocks are verbatim/aligned (then this tool can only
   name the block type, not decode it) or stored (then it can).
6. `HCXCmp`: nothing here tests it. If the image uses a proprietary scheme, both
   decoders will refuse (LZX framing error) or produce a `weak` LZSS candidate
   whose output silently differs from `vsize`; the `--size` check is what turns
   that into an error.
7. The other 244 sections, `FILESentry` payloads (`ReleaseMain.skn`,
   `default.hv`) and the `cerom.py decompress` integration (M1.3/M1.4).

## Conclusion

`tools/cecompress.py` adds the missing decompression capability as a candidate
implementation: `decompress`, `detect`, `decompress_file` plus explicit
`decompress_lzss`/`decompress_lzx`, the `detect`/`decompress` CLI, and 186
synthetic self-test checks that `tools/selftest.py` picks up as
`tool:cecompress`. It does not close M1.2: the "output length equals `vsize`"
proof needs the vendor image (`0x01951b78`-based `o32` walk, first candidate
`NaviMapCC.dll` `.data`), which is not in this checkout. `docs/format/cerom.md`
§5 still says the compressor is UNKNOWN and was deliberately not edited here
(outside this task's file set); M1.3/M1.4 remain open.
