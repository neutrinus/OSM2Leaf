## Question

Can one standard-library tool take an IMF v1 file that `tools/mesh_split.py`
already split (one way fragment per `BxxRyyR` cell) plus an optional factory
tile, and emit a tile container in which

1. the common 512-byte header and the descriptor tables are the factory's bytes,
2. section 4 is carried verbatim through `tools/section4.py encode preserve`,
3. the road-shape records are built by the checked-in `tools_ze0` writer
   (`fa_encode`) for a **configurable** road-class table,
4. every road stream is addressed by the documented
   `(A = 32768 + lat*192, B = 52736 + lon*128, tag)` key,

and which reads back through `tools_ze0/clarion_tile.read_tile` with the
unchanged sections byte-identical?

## Hypothesis

The ZE0 container splits cleanly into "bytes that belong to a section" and
"offsets that point at them". A generated tile only *needs* to replace the
section-1 road pair (even pair, `w2 = 0x00fa`) of the parcels it populates, so a
factory tile can be patched surgically instead of relaid out: rewrite the slot
block and, if it grew, append it at the next 256-byte boundary and repoint the
slot's `u32` tag. Everything else (header, level table, box table, section
table, section 2, section 4, background pairs) then stays byte-identical by
construction.

Second hypothesis: the six-byte stream key is the record's own parcel code
(`clarion_bg.parcel_code`), so the `32768 + lat*192` formula is the coarse
address in the high byte and the low byte carries the sub-lattice — meaning a
correct writer must reproduce `parcel_code`, not the raw formula.

`sector_fingerprint()` compares, per section and level, every directory head
(`kind`, `y`, `x`, `typ`, box), every slot body (the pair table) and every
record's raw bytes. It deliberately ignores *offsets*, because the container is
addressed through the tags, not by position. Section 2 and section 4 therefore
come back byte-identical even if a block moved; the level-1 background record
(`key=1234,5678`, 46 B) is byte-identical at its old offset.

The tool runs that comparison itself on every factory write (`verify_factory`)
and aborts with `check failed` (exit 1) instead of writing a damaged tile.

### 4. Stream keys against the documented address

| Parcel (y, x, row, col) | record key `A, B, tag` | `32768+lat*192, 52736+lon*128, 0xfa` | delta |
| --- | --- | --- | --- |
| 72, 936, 4, 3 | `a41c d40f 00fa` | `a410 d40c 00fa` | +12, +3 |
| 72, 936, 5, 3 | `a41d d40f 00fa` | `a414 d40c 00fa` | +9, +3 |

The high byte of `A`/`B` equals the documented address exactly; the low byte is
the sub-lattice that `clarion_bg.parcel_code` packs (it locates the parcel
inside its 64-parcel/lattice group). Measured deltas are +3…+12 on `A` and +3 on
`B`, i.e. well inside one low byte. The writer asserts the high-byte equality on
every record and fails loudly otherwise, and the self-test also asserts
`[A, B] == parcel_code(level, abs_row, abs_col)`.

### 5. Section 4 is carried, not rebuilt

Every section-4 record of the output is parsed by `tools/section4.py` and
re-encoded with `encode preserve`; the tool aborts unless the result is
byte-identical to the factory record. The report carries
`section4 = {records, names, preserved: true}` — here one record with two names
(`0=RODOS`, `0=LINDOS`), 42 compressed bytes, unchanged. Section 4 is never
written by this tool, so its undocumented fields can never be invented.

## Interpretation

- **FACT (C-1060):** `tools/tilewriter.py` writes a tile from mesh-split IMF v1
  in which (a) the 0x1000 header and the descriptor tables are the factory's
  bytes, (b) section 4 is carried verbatim through `section4.py encode
  preserve`, (c) the section-1 road records are built by the checked-in
  `fa_encode` writer for a caller-supplied class table, and (d) every road
  stream is the documented `(A, B, 0x00fa)` record key. On the synthetic
  fixture the 30,720-byte factory tile becomes a 30,806-byte tile whose header,
  level table (`0x1ac`), box table (`0x2ac`) and section table (`0x800`) are
  byte-identical, whose section 2 and section 4 are byte-identical, whose only
  changed/created records are the two `0x00fa` roads, and whose read-back
  through `clarion_tile.read_tile` finds keys `a41c d40f 00fa` and
  `a41d d40f 00fa`; repeated runs are byte-identical and section 4 preserve is
  byte-identical. EXP-2026-11-06-M5.4.
- **FACT:** the factory path is a splice, not a relayout: a rebuilt slot block
  is written at its old offset when it fits the bytes the reader modelled and
  those bytes are actually there; otherwise it is appended at the next 256-byte
  boundary and the slot's `u32` tag is repointed. Bytes the reader did not model
  (a raw slot tail) are never overwritten. One fixture run exercises both
  paths (`in-place 1, appended 1`), and the background record in the same
  directory stays byte-identical.
- **FACT:** the record bytes come from `fa_encode` but the zlib framing does
  not: `fa_encode.build_record` compresses with a 13-bit window (`58 85`,
  X08-03-00), while ZE0 (X08-02-00) streams start `78 9c`
  (`docs/format/map-tiles.md`). The writer takes `build_record`'s plain body and
  recompresses with stock zlib level 6, `wbits 15`, `memLevel 8`; the self-test
  pins the `78 9c` prefix.
- **FACT:** the documented key formula is the *coarse* address. The high byte of
  `A` is `(32768 + lat_south*192) >> 8` and of `B` is
  `(52736 + lon_west*128) >> 8` exactly; the low byte is the parcel
  sub-lattice, so the record's first word is `parcel_code()`, not the bare
  formula. Measured deltas: `A` +9…+12, `B` +3. Any writer that "computes the
  formula" and stores it would misaddress the parcel.
- **OBSERVED:** without a factory tile the tool emits a roads-only container
  (authored header, sections 1/2/4 with only level-1 or level-2 roads). It is
  not unit-ready: no background, no graph, no administrative index, no card
  vintage at `0xe0` beyond the value the caller passes.
- **OBSERVED:** a road fragment cut at a parcel border becomes two shapes in two
  records, each quantised to its own parcel (`0..2047`). The adjacent endpoints
  therefore land on the parcel edge as `2047` and `0`, which is the pair M5.5
  has to stitch; nothing here reconnects them.
- **OBSERVED:** the same code path handles level 2 (parcel 1/8° × 1/12°,
  directory span 4 meshes, `parcel_code(2, …)`); the fixture's two ways share
  one level-2 parcel and land as two shapes in one record.
- **HYPOTHESIS:** on a real ZE0 factory tile the same splice works. Not tested:
  there is no `leaf2011.img`, no extracted `root/` and no `.DAT` in this
  checkout, so `tools/l2check.py`, `harness.py verify` and the L2 tile check
  named in the task cannot run here.
- **KNOWN LIMITATION (by design, no silent default):** the class table is the
  caller's; without `--class-table` it is the upstream `fa_encode.CLASSES`,
  which is a hypothesis for ZE0 until M5.3. A `highway` value outside the table
  is a hard error naming the value and the ways, never a default class.
- **KNOWN LIMITATION:** only the road pair of a parcel is written. A parcel with
  no IMF way keeps its factory road record (nothing is deleted), road names are
  not written (`name_off = 0xffff`, M5.7), the style word is `fa_encode.STYLE`
  (no speed limit, two-way), so one-way/speed is not represented until M4.2
  validates a mapping, and the section-2 router graph is copied, never
  regenerated (M5.6).

## Conclusion

The tools half of M5.4 exists and is self-checked: `tools/tilewriter.py` turns
mesh-split IMF v1 into a tile container that preserves the factory's header and
descriptor tables, carries section 4 through `section4.py preserve`, writes
`fa_encode` road records for a configurable class table, and addresses them by
the documented `(A, B, tag)` keys — verified by a 48-check synthetic self-test
and by reading the output back with the checked-in reader.

**The task stays blocked**, and no unit-readiness is claimed:

1. **The vendor-tile L2 check cannot run here.** The task's "Done when: one
   generated tile passes L2" needs a factory tile and a card tree
   (`tools/l2check.py`, `harness.py verify`); this checkout has neither
   (hardware access unavailable, images git-ignored and absent). Everything
   above is proven on a synthetic factory tile only.
2. **The real OSM class mapping is M5.3/M4.2.** The default class table is the
   upstream `fa_encode.CLASSES` (a hypothesis for ZE0); the one-way/speed style
   word is unvalidated, so the writer deliberately emits the neutral style.
3. **M5.6** (`DRSTR001`/`MMAIN001`/`.ind`/`CMP.LST`) and **M5.5** (cross-tile
   connectivity) are still needed before a generated tile can be put into a
   card tree and read.
