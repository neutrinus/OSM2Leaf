## Question

Can the two ZE0 PCM streams be captured to a WAV file by modelling the SSI
register block and its HPB-DMA channels inside QEMU, and does the guest ever
play a sound we can capture?

## Hypothesis

A register file at `0xffe00000` (P4) and `0x1fe00000` (area 7) plus an
HPB-DMAC channel-12/13 sink into a QEMU `wav` audiodev is enough: the wave
driver's reset writes land in memory and any DMA buffer aimed at the SSI
block becomes non-silent PCM. **Falsifier:** the driver reports success but
never arms a DMA transfer (the task's own falsifier), or the WAV stays silent
even when the model is fed PCM through the same path.

## Inputs

| Item | Value |
| --- | --- |
| SSI block | phys `0xffe00000`, area-7 alias `0x1fe00000`, three channels at `0x10000` stride |
| HPB-DMAC | `0xffc08000`, channels 11/12/13, common DINTSR0/DINTCR0/DINTMR0 at `+0x80c/+0x810/+0x814` |
| Registry (EU2011 build B) | `WaveSSI1`: `PLAY_SSI=1`, `PLAY_CH=12`, `REC_SSI=0`, `REC_CH=11`, `SysIntr=0x24`; `WaveSSI2`: `PLAY_SSI=2`, `PLAY_CH=13`, `SysIntr=0x25` (M1.39) |
| OAL interrupt table | VA `0x88005e18` = `{INTEVT 0xcc0, ISR 0x8803e8e4, prio 14, SYSINTR 0x24}`; `0x88005e28` = `{0xda0, 0x8803e98c, 14, 0x24}`; `0x88005e38` = `{0xdc0, 0x8803ea14, 14, 0x25}` |
| Modules | `wavessi1.dll` build B module 64 (vbase `0x03960000`, code `0x03961000`, 36 864 B) and build A module 36 (vbase `0x03750000`); `wavessi2.dll` build A module 37 (vbase `0x03740000`) |
| Sample rate used by the model | 48 000 Hz, 2 channels, S16 (default; `ssi-rate`/`ssi-channels` machine properties) |

## Method

1. **Sample and hash.** The two files and hashes above, read from
   `archive/`; every VA below comes from `cerom.py` section/module tables,
   never from a fitted delta. SH-4 code is little-endian (`sh4dis.py`).
2. **Commands.** Static read (the string-to-function cross-references):

   ```bash
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img modules | grep -i wavessi
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img modules | grep -i wavessi
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img sections wavessi1.dll
   python3 tools/sh4xref.py --image-start 0x200200 archive/head256.img wavessi1.dll --to 0x0375281c
   python3 tools/sh4dis.py --image-start 0x200200 archive/head256.img wavessi1.dll --va 0x03757f28 --count 220
   ```

   OAL rows and their ISR channel bits (read from the image at the VA
   `cerom.py va2file 0x88005c48` maps to file offset `0x03e05e48`):

   ```bash
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img va2file 0x88005c48
   python3 tools/sh4dis.py --image-start 0x3e00200 archive/head256.img nk.exe --va 0x8803e98c --count 55
   ```

   Boot (no patch, old binary) and boot with the new device, where `W` is a
   scratch directory outside the repo:

   ```bash
   W=$HOME/projekty/leafre-work/scratch/m8.h46-ssi-audio
   python3 tools/ze0_ipl.py patch archive/head256.img -o "$W/ipl.txt"
   qemu-img create -f qcow2 -b "$PWD/archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img" -F raw "$W/card.qcow2" 8G
   QEMU="$HOME/.cache/qemu-ze0/build/qemu-system-sh4"
   timeout 130 "$QEMU" -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch="$W/ipl.txt",hpbdmac-trace=on -kernel archive/head256.img -nographic -serial file:"$W/run0/serial.log" -monitor unix:"$W/run0/hmp.sock",server,nowait -icount shift=0,sleep=off -drive if=sd,index=0,file="$W/card.qcow2" -d unimp,guest_errors,int,invalid_mem -D "$W/run0/qemu.log"
   grep -c 'Invalid write at addr 0x1FE00000' "$W/run0/qemu.log"
   ```

   The positive control for the audio backend (with the patch applied,
   `ssi-selftest=4096` pushes a known PCM pattern through HPB-DMAC channel
   12 -> SSI -> audiodev) and its paired negative control (`ssi-selftest`
   absent) are run by the committed script `tools/ze0_wavcheck.py`:

   ```bash
   python3 tools/ze0_wavcheck.py off
   python3 tools/ze0_wavcheck.py on
   ```

   Both runs use the same image, overlay, IPL patch and 12 s of guest time,
   and differ by one machine option. The audiodev is
   `wav,id=w,path=…,out.frequency=48000,out.channels=2,out.format=s16,out.fixed-settings=on`
   (QEMU 11.1.3 uses `out.*` options; without `fixed-settings` it resamples to
   its 44.1 kHz default). The script sends HMP `quit` and reads the data area
   directly, because this backend leaves the RIFF/data sizes at zero on exit.

   Third boot (UI + audio-microcontroller peer, 200 s) to look for a real
   guest sound:

   ```bash
   python3 tools/ze0_ipl.py patch archive/head256.img --prefer-app auiapp.exe,auirtdll.dll --copy-dlls unitflash -o "$W/ipl_ui.txt"
   python3 tools/ze0_aui.py archive/head256.img --no-aui-timeout --skip-module-wait audio.exe --object-store -o "$W/ipl_aui.txt"
   cat "$W/ipl_ui.txt" "$W/ipl_aui.txt" > "$W/ipl_full.txt"
   python3 tools/ze0_peers/micon.py --listen --socket "$W/run3/micon.sock" --log "$W/run3/micon.log" --duration 220 &
   timeout 200 "$QEMU" -audiodev wav,id=w,path="$W/run3/out.wav" -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch="$W/ipl_full.txt",ssi-audio=w,ssi-trace=on,sci1=ze01 -chardev socket,id=ze01,path="$W/run3/micon.sock" -kernel archive/head256.img -nographic -serial file:"$W/run3/serial.log" -monitor unix:"$W/run3/hmp.sock",server,nowait -icount shift=0,sleep=off -drive if=sd,index=0,file="$W/card.qcow2" -d unimp,guest_errors,int,invalid_mem -D "$W/run3/qemu.log"
   grep -c 'ze0-ssi: played' "$W/run3/qemu.log"
   ```

3. **Controls.** *Positive*: `ssi-selftest=4096` must produce non-silent
   samples in the data chunk; with `out.fixed-settings=on` it wrote 1024 of
   4096 bytes in one transfer (the wav backend buffer), all non-zero.
   *Negative*: the same boot with the option absent produced a 44-byte
   header and zero data bytes. The
   pre-patch boot is a second negative control: three invalid writes at
   `0x1FE00000`/`0x1FE00004` instead of nine accepted SSI register writes.
4. **Scope.** EU 2011 build A (`wavessi1/2`) and build B (`nk.exe` OAL table,
   `wavessi1`), uncompressed sections only; build C and the 2013+ generations
   are excluded. Three boots to idle (120 s, 200 s with the UI/micon peer,
   12 s x 2 for the WAV controls). No car, no unit dump. The QEMU patch was
   checked with `git apply` over the whole series on a pristine 11.1.3 tarball
   (21 patches, 0 failures) and compiled with `--target-list=sh4-softmmu`.
5. **Falsifier.** If the register stub did not remove the invalid writes, if
   the positive control produced no PCM, or if a guest playback attempt
   moved bytes yet the WAV stayed silent, the model would be refuted.

## Observations

**O1 — static attribution.** `wavessi1.dll` code contains the strings
`SSI_Init, g_pSSI_TX_RegBase` (VA `0x0375281c`), `SSI_Init, pSIU2_RegBase`
(`0x03752804`), `SSI_Init, g_pRST_RegBase` (`0x03752878`) and
`module_Clock_Out, g_pSSI_RX_RegBase` (`0x03752728`). `sh4xref --to` finds
them in literal pools loaded by `fn 0x03757f28` (`SSI_Init`) and
`fn 0x037579bc` (`module_Clock_Out`). The init maps phys `0xffcc0000`
(SIU2), `0xfffec000` (RST) and `(config + 0xffe0) << 16` (SSI), each with
size `0x10000` or `0x1000`; the guest later writes the A7 alias
`0x1fe00000`. The OAL rows above attribute the three audio DMA channels to
SYSINTR `0x24/0x25`; ISR `0x8803e98c` tests `DINTSR0` bit 12 (`mov #16,r4;
shll8 r4`), `0x8803ea14` tests bit 13 (`mov #32,r4; shll8 r4`).

**O2 — pre-patch boot.** With the unmodified patch series the 120 s run
logged 3 `Invalid write at addr 0x1FE00000/0x1FE00004, reason: rejected`
lines (two at `+0x00`, one at `+0x04`) and no HPB-DMAC channel 11/12/13 arm.

**O3 — post-patch boot.** The same boot with `ze0-h46-ssi-audio.patch`
logged 0 invalid SSI writes and 9 SSI register writes: offsets `0x10000`,
`0x10004`, `0x10020`, `0x20000`, `0x20004`, `0x20020`, `0x00000`, `0x00004`,
`0x00000 <- 0xbd139`. No `ze0-ssi: played` line and no channel 11/12/13 DMA
arm.

**O4 — WAV controls.** `tools/ze0_wavcheck.py off`: `out.wav` is 44 bytes
(data chunk length 0), 0 non-zero data bytes. `on`: 1068 bytes, 1024 bytes
accepted by `audio_be_write` per the guest log
(`ze0-ssi: played 1024/1024 bytes (total 1024, transfers 1)`), all 1024 data
bytes non-zero; header `fmt` is 2 channels / 48 000 Hz / 16 bits. (QEMU's
`wav` backend writes the RIFF/data sizes as zero when the process is stopped
with HMP `quit`, so the sample counts are taken from the data area, not from
the header.)

**O5 — no guest playback.** Three boots (120 s basic; 200 s with the UI
IPL patch and `micon.py` on `sci1`; 12 s x 2 controls) produced 0 DMA arms
to the SSI block, 0 `ze0-ssi: played` lines and silent WAV files. The UI run
kept logging `CInaiProtocol::GetWriteResult! failed wait response` — the
audio-microcontroller link (M8.H44/H45) is still not answered.

**O6 — patch hygiene.** `git apply` of all 21 patches in
`tools/qemu-ze0/patches/` onto a fresh `qemu-11.1.3.tar.xz` tree: 0 failures;
the target compiled with `--target-list=sh4-softmmu --disable-werror
--disable-docs --disable-fdt`.

## Interpretation

- **FACT:** The SSI register block at `0xffe00000`/`0x1fe00000` was
  unmodelled (3 rejected writes); with the patch all nine driver writes land
  in a mapped region.
- **FACT:** HPB-DMAC channels 11/12/13 are the WaveSSI1/2 DMA channels; the
  OAL interrupt rows and ISR bit tests are read directly from build B.
- **FACT:** The model's PCM path works: a controlled DMA arm produces
  non-silent 48 kHz stereo S16 samples in the WAV, the paired run with no
  playback is silent.
- **OBSERVED:** No boot in this record played a sound, even with the UI and
  the micon peer; the audio-network protocol still waits for a response.
  The task's own falsifier ("driver reports success but never starts a DMA
  transfer") therefore stands: it is a **negative** result for guest
  playback.
- **HYPOTHESIS:** A workload that opens `WAV1:`/`WAV2:` and calls `waveOut`
  (for example `Speech.exe` once M8.H47 resolves `AppTimerDll`) will arm
  channel 12/13 and be captured by this model. This is not measured.
- **UNKNOWN:** The driver's actual sample rate and bit depth (48 kHz/S16
  here are the model's defaults, not a firmware constant recovered from
  `wavessi1/2`); whether the start-up beep goes through `DspDrv` instead of
  SSI.

## Conclusion

The QEMU patch adds the SSI register stub, the HPB-DMAC PCM sink and a
`wav` audiodev binding, with a `ssi-selftest=N` positive control. The
register stub and the capture plumbing are verified; the guest-playback
half of the Done-when is not, so M8.H46 is `blocked` with `Unblock: M8.H47`
(the voice process is the shortest route to a real `waveOut`). Claims
C-7430–C-7439 record the measured parts and the gap.
