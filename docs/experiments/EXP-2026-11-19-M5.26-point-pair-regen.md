## Question

Can a POINT name set larger than the in-place slot budget (M5.21) be written
by regenerating whole inner page sets and rebuilding the `.cmp/.ind` pair, with
page/offset tables kept consistent and a clear refusal when a constraint
fails?

## Hypothesis

Pages are not independent slots: some table records where each page is, so a
whole page set can be re-packed and its table rewritten. **Falsifier:** (1) no
table that describes the pages exists in the file; (2) a no-op regeneration
with the factory encoder is not byte-identical (the model or encoder is wrong);
(3) a regenerated pair that `cmpind.py` does not decode, a requested name not
present with `@`, a table entry that does not land on its page, or a byte
changed outside the regenerated chain and its table; (4) a violated constraint
that is written instead of refused.

## Method

1. **Sample and hash.** As in Sample. The US pairs were read from the card
   with `mkcard.open_map_partition`/`img_read` into
   `/home/user/scratch/m5.26/us/REFER001/` (outside the repo); EU pairs from the
   read-only tree `/home/user/scratch/factory-eu/REFER001/`.
2. **Derivation of the model (how the table was found).** In decoded EU
   `POINT032`, page `0x4200` (655 B stream, 3,848 B inflated) has, at `0x4600`,
   `03e8 0000 | 00000000 00000148 00000784`: `0x148` words = 656 B (655 rounded
   to 4), `0x784` words = 3,848 B. EU `POINT010` `0x74d000` holds 16 such
   triples whose `start_w` sums `comp_w`; the 16 pages lie back to back from
   `0x6a7f00` with 0–3 zero bytes between them. The tool generalises this:
   a table is a 0x100-aligned `u16 per_page, u16 0` followed by triples with
   `start_w[0]=0`, `start_w[i+1]=start_w[i]+comp_w[i]`; its chain base is the
   0x100-aligned zlib header whose stream matches triple 0 (fallback: every
   stream); every page must then inflate at `base+2*start_w` with
   `2*comp_w-4 < stream ≤ 2*comp_w`, inflated length `2*inner_w` (or one less),
   zero padding. Records are walked with the firmware rule of `fn 0x003f5194`
   (EU2011, C-2540).
3. **Commands.** From the repo root; `L` is the stock 1.3.1 library.

```bash
L=/nix/store/xdxxfabbd8w0dadijsd8rkgvnhpn3rkf-zlib-1.3.1/lib/libz.so.1.3.1
EU=/home/user/scratch/factory-eu/REFER001
US=/home/user/scratch/m5.26/us/REFER001
S=/home/user/scratch/m5.26
python3 tools/point_pair_regen.py --selftest
python3 tools/slot_budget.py --selftest
python3 tools/factory_zlib.py --selftest
python3 tools/zlibinfo.py
# 1. locate and verify every chain table
python3 tools/point_pair_regen.py scan $EU --jobs 3 --json $S/scan-eu.json
python3 tools/point_pair_regen.py scan $US --jobs 3 --json $S/scan-us.json
# 2. control: re-encode every name page and every outer chunk with zlib 1.3.1
for f in $EU/POINT*.DAT.cmp; do n=$(basename $f .DAT.cmp); python3 tools/point_pair_regen.py regen $f $S/noop/eu-$n --noop --reencode-outer --libz $L --json $S/noop/eu-$n.json; done
for f in $US/POINT*.DAT.cmp; do n=$(basename $f .DAT.cmp); python3 tools/point_pair_regen.py regen $f $S/noop/us-$n --noop --reencode-outer --libz $L --json $S/noop/us-$n.json; done
python3 tools/point_pair_regen.py summarize $S/noop
# 3. name sets: 100 generated names (same length) and 100 real names moved to other sites
for f in $EU/POINT*.DAT.cmp; do n=$(basename $f .DAT.cmp); for m in permute generate; do python3 tools/point_pair_regen.py regen $f $S/sets/eu-$n-${m}100 --$m 100 --libz $L --json $S/sets/eu-$n-${m}100.json; done; done
for f in $US/POINT*.DAT.cmp; do n=$(basename $f .DAT.cmp); for m in permute generate; do python3 tools/point_pair_regen.py regen $f $S/sets/us-$n-${m}100 --$m 100 --libz $L --json $S/sets/us-$n-${m}100.json; done; done
python3 tools/point_pair_regen.py summarize $S/sets
# 4. one growing set on EU POINT010, then an independent decode
python3 tools/point_pair_regen.py regen $EU/POINT010.DAT.cmp $S/out/eu010-g2-n1000 --generate 1000 --grow 2 --libz $L --json $S/out/eu010-g2-n1000.json
python3 tools/cmpind.py verify $S/out/eu010-g2-n1000
python3 tools/point_pair_regen.py verify $EU/POINT010.DAT.cmp $S/out/eu010-g2-n1000/POINT010.DAT.cmp --names $S/out/eu010-g2-n1000/POINT010.DAT.cmp.names.json
# 5. search the chain locator
python3 tools/point_pair_regen.py locator $EU
python3 tools/point_pair_regen.py locator $US
```

   (Steps 2 and 3 were run three/two files at a time with `xargs -P`; each
   job was exactly the loop body above.)

4. **Controls.**
   - *Positive (model):* the scan must verify each table's pages from the table
     alone; `--noop --reencode-outer` must re-encode every name page and every
     outer 64 KiB chunk with zlib 1.3.1 and give a byte-identical `.cmp` and
     `.ind` (no record byte invented, no table word changed).
   - *Positive (locator search):* the `locator` method must find page 0's
     `comp_w` at `table+8` (encoding `>I`, unit 1) in every file.
   - *Negative (selftest):* a broken `start_w` stops a table; a table word
     broken in a rebuilt pair and a name that was never written each fail
     `verify`; an odd length change, a name not at its offset or not followed
     by `@`, a page in no table, an encoder that does not reproduce the factory
     pages, and a chain that outgrows its slot are each refused before writing.
   - *Negative (real):* name sets that overflow a real chain slot are refused
     with the slot size named (step 3).
5. **Scope.** Chain tables and their pages: EU 33 files / 99 tables / 9,082
   pages, US 11 files / 33 tables / 26,969 pages. Name chains: EU 2,742 pages /
   2,727,806 records, US 8,229 pages / 8,225,647 records. Excluded: the
   `4e 20 00 00` index chains (24-byte index records, not re-packed here),
   streams in no table, the raw (non-zlib) payload, the `.DAT` header and
   directory. The name *index* (24-byte records, `f11 = 2000*page + slot`) is
   not touched; whether any index field is derived from the name text (a sort
   key) is not tested. `NAME@` sites for generated sets are the M5.21 byte
   pattern. Not run on a card image and not run in the firmware (rule 13).
6. **Falsifier.** As in Hypothesis, stated before the results.

## Interpretation

- **OBSERVED (C-2950):** a POINT `.DAT` stores its inner pages in chains
  described by 0x100-aligned chain tables `u16 per_page, u16 0, n × (u32
  start_w, comp_w, inner_w)` (BE, words); three per file (400/1000/2000) in all
  44 files of both builds; every page of every chain is located from its table
  alone (EU 9,082, US 26,969). The firmware reader of this table is not located.
- **OBSERVED (C-2951):** every chain page walks exactly with the 10-bit record
  length of `fn 0x003f5194` (EU2011, C-2540); the `ff ff` record end of
  `refer.md` is not universal. A name length change is written into those 10
  bits and must be even.
- **VERIFIED (C-2952):** with stock zlib 1.3.1 at L6/m8, regenerating every
  name page and every outer chunk reproduces the factory `.cmp` and `.ind`
  byte for byte (no-op control), so the regenerated pairs differ from the
  factory only where names were changed.
- **VERIFIED (C-2953, tool):** `tools/point_pair_regen.py regen` re-packs a
  whole chain from its base, rewrites its table, rebuilds the pair (unchanged
  outer chunks verbatim), and its output is decoded by `cmpind.py`; all
  requested names read back with `@`; no byte outside the chain slot and its
  table changes; violated constraints are refused before any write.
- **OBSERVED (C-2954):** a page may now outgrow its own slot when the chain
  has room (EU POINT010: page 0 +176 B, absorbed by other pages). But the
  pooled room is small: 28 B on EU POINT010, 3,656 B over all 33 EU name
  chains, 1,460 B over 11 US. Real-entropy name sets overflow it (step 3).
- **UNKNOWN (C-2955):** the **chain locator** — where the reader learns a
  chain's base and its table's offset. Not in `0x0`–`0x7fff` under 72 simple
  encodings (positive control 33/33). Without it no chain can move, and no
  chain can grow past the next structure. This is the field the task's Stop
  clause names; mass OSM name generation waits on it (new task M4.42).
- **HYPOTHESIS (C-2956):** the reader finds a page through the chain table
  (`start_w`) rather than through a stored absolute offset, so moving pages
  inside a chain is safe. Only an L3/L4 run of the POINT reader on a
  regenerated pair can confirm it (rule 13).
- **Generator effect (C-2957):** whether a set fits depends on how well the
  new names compress: the word-list generator shrank the chain with 1,000
  names, real names moved between sites grew it. Real OSM names behave like the
  second (HYPOTHESIS; no OSM extract in this run).

## Conclusion

`tools/point_pair_regen.py` regenerates POINT inner pages chain by chain and
rebuilds a `.cmp/.ind` pair that `cmpind.py` decodes, with every requested name
present with `@`, the chain table rewritten consistently, refusals for each
violated constraint, and a byte-identical no-op control on all 44 real pairs
under stock zlib 1.3.1. The task's done-when is met. It does not yet make mass
generation possible: the budget moved from one page (M5.21) to one chain, and a
chain has 24–248 B of slack. Growing past it needs the chain locator, which is
not in the file header area; M4.42 is added to find it. `docs/format/refer.md`
gains the chain-table section; claims C-2950–C-2957.
