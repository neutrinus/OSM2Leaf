## Question

What is the largest road record (inflated bytes), the largest single shape and
the largest point count that the EU2011 firmware reads and walks, and which
instruction enforces the bound?

## Hypothesis

Exploratory. Expected: the bound is not the factory block size (blocks can be
appended within the declared file, M8.H71) but the client's fixed shape-buffer
pool. Falsifier: a record larger than the pool is still copied and walked, or
a small record produces no LOC_map message through the same harness.

## Method

### 1. Sample and hash

The image, card and factory tile above. Each generated tile is a copy of the
factory tile with one road record spliced into the served parcel; the SHA-256
of every generated tile is in `capacity.json` (workdir). The synthetic record
is a repeating point pattern (highly compressible, so a large inflated body
fits the 7,384-B factory slot) built by `fa_encode`/`tilewriter`; no OSM, no
vendor bytes in the repository.

### 2. Commands

```bash
python3 tools/capacity_l3.py --selftest
python3 tools/capacity_l3.py disasm --image archive/head256.img
python3 tools/capacity_l3.py probe \
    --image archive/head256.img \
    --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
    --factory <root>/MAPAL001/B48R058R.DAT \
    --workdir ~/projekty/leafre-work/scratch/m5.92 \
    --json ~/projekty/leafre-work/scratch/m5.92/capacity.json
python3 tools/locmap_l3.py run archive/head256.img \
    --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
    --mesh 0xa6c1d6b2 --xy 1024,1024 \
    --replace MAPAL001/B48R058R.DAT=<workdir>/v1.DAT --json <workdir>/G.json
python3 tools/datask_l3.py mount archive/head256.img \
    --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
    --position 51.70,17.45 --request 0xa6cdd6be \
    --replace MAPAL001/B48R058R.DAT=<workdir>/v1.DAT --bytes --json <workdir>/da1x.json
python3 tools/va_class.py archive/head256.img --module Navi.exe \
    --resolve-with 0x3e00200 0x004262f2 0x004262f8 0x0041f4bc
python3 tools/l4_status.py --json -
python3 tools/l4check.py --card <workdir>/v1.DAT --workdir <workdir>/l4
```

`capacity_l3.py probe` writes one tile per variant, runs `locmap_l3.py run`
on each and records `reply sub-codes`, `window`, `loc_messages` and the walk.
The two edge runs used `--replace MAPAL001/B48R058R.DAT=<workdir>/edge-pass.DAT`
and `edge-fail.DAT` from hand-built records at windows 67,840 and 68,096 B.

### 3. Controls

- **Positive:** the factory tile F (`locmap_l3 run` with no `--replace`) gives
  `replies sub [5,5,5,3,3]`, `window 11264`, `RESULT: walk ran`,
  `trace sha1 4937b8cd70d96d09672796c1d736f29de6b5230e` (reproduces M9.66
  exactly). A small synthetic record (1×) gives `replies sub [5,5,5,3,3]`,
  `window 18688`, `RESULT: walk ran`.
- **Negative:** an 8× record whose appended block extends past the factory
  declared size is not read at all (`replies sub [5,5,5,3]`, rows 0); after
  growing the DRSTR001 declared size it IS served (sub 3, inflate window
  `0x24200`) but still produces no LOC_map message — the record is larger than
  the shape-pool limit. An empty parcel (request `0xa40fcc02`, M5.91) gives
  sub 9 and no read. These are explicit reply/walk failures, not trace diffs.
- **Gate mutation (mandatory navigator check):** changing the shape-pool
  literal in `sh4dis` output from `0x000109a0` to a different value would move
  the threshold; the tool's `--selftest` asserts the constant, so a mutated
  constant fails the assertion. The threshold runs (edge-pass / edge-fail)
  themselves are the negative/positive control for the boundary.

### 4. Scope

EU2011 build A (`Navi.exe`), one mesh (`0xa6c1d6b2`), one position
(x = y = 1024), record kind 4 only, the undivided-record branch of the
receiver (`fn 0x00421548`). 8 L3 probes (5 size multipliers 1×–16× of 18,580 B
and 3 point-count variants 1k/8k/32k) plus 2 hand-built edge runs and a
factory control. Excluded: the divided-record branch (`fn 0x004205b8`),
other positions, `LOC_db`/`RAW_rec`, the kind-`0x40` reply consumer, L4
(not runnable here). All enforcing VAs classified with `va_class.py` as CODE
sec0 (plain, uncompressed) — no compressed-data blocker.

### 5. Falsifier

A record above 68,000 B window still producing `RESULT: walk ran`, or a small
record producing no LOC_map message, would refute the buffer-limit hypothesis.
A shape with > 1000 points still being counted in `rows` would refute the
point-count gate.

## Interpretation

- **FACT:** the firmware reads and fully inflates records far larger than the
  factory maximum: 147,764 B (8×) is inflated at L3 with reply sub 3. The
  reader is not the limit.
- **FACT:** the LOC_map copy handler enforces a 68,000 B (`0x109A0`) shape
  pool: the boundary is between a 67,840 B and a 68,096 B inflate window.
  The instruction is `0x004262f8` (`cmp/ge`) inside `fn 0x0042613c`, with the
  literal loaded at `0x004262f2`; past the bound the handler branches to
  `0x0042640c` and no LOC_map message is posted. This is the answer to limit 6.
- **FACT:** the walk's shape point-count gate is `0x0041f4bc` with the
  `0x03e8` = 1000-point literal from `0x0041f5f2`; a shape with more than
  1000 points is skipped by the branch at `0x0041f4c2`. One shape cannot hold
  32k points anyway (writer `MAX_SHAPE_POINTS = 255`; word-1 count field is
  12 bits); such inputs must be several shapes.
- **OBSERVED:** a single shape above 255 points is refused by our own
  writer/renderer grammar: building a 256-point shape makes
  `fa_encode.parse_record` fail ("the checked-in reader cannot re-read the
  record"). So the firmware's 1,000-point gate is not reachable through our
  writer today; long inputs must be several ≤255-point shapes.
- **OBSERVED:** appended blocks past the factory-declared file size are not
  read at all (the DRSTR001 entry sets the visible size). M5.92's first
  failing size is a FIRMWARE verdict at the shape-pool bound, not a writer
  limit; 16× is not built because `tilewriter.py:882` refuses > 0x10000
  words, which is our writer's bound, not the firmware's.
- **UNKNOWN:** L4 drawing for the largest passing / smallest failing record
  is NOT RUN; the L3-only result is accepted under the task's stop clause.
- **UNKNOWN:** whether the 1000-point gate is checked per shape or per row
  aggregate; the tool records the literal and the skip branch but the 1k/8k/
  32k probes used ≤255-point shapes, so only the "many shapes" path is run.

## Conclusion

Limit 6 in `docs/research/osm-from-scratch.md` is updated from UNKNOWN to the
L3-measured 68,000-B shape-pool window (first failing window 68,096 B), with
the enforcing VA `0x004262f8` and the 1000-point shape gate at `0x0041f4bc`.
Claims C-8720–C-8729 record the measurements. No `docs/format/` change: this
is a reader-capacity measurement, not a format change. L4 remains open
(M5.99 / a runnable card).
