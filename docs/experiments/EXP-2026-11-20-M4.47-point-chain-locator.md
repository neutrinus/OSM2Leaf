## Question

Where does a POINT `.DAT` record the offset of each page chain's base and of
its chain table, and can `point_pair_regen.py` move a chain by rewriting it?

## Hypothesis

The file stores the base and table offset in a unit that M5.26's 72
encodings missed. Derivation (not a guess from a doc): in the smallest file
(EU `POINT032`, 20,224 B) the name chain is at `0x4200` and the block
before it (`0x4000`, starts `ffff 0015`, the field dictionary of M3.11c)
carries `0000 0802 | 0000 0148`; `0x148` words = 656 B = the chain length,
and `0x802` read as "sector 8 of 0x800 B, block 2 of 0x100 B" = `0x4200`. The
same block carries `0000 0806 0000 0008 03e8` (table `0x4600`, 8 words,
per_page 1000). **Falsifier:** in any of the 44 files a chain base or table
that is not reachable through one fixed (directory cell, record offset)
layout, a reference that is not unique in its file, a chain still verified
when the stored address is shuffled or read in a plain unit, or a relocated
pair whose chain the same locator does not reach.

## Method

1. **Sample and hash.** As in Sample.
2. **Commands.** From the repo root.

```bash
L=/nix/store/xdxxfabbd8w0dadijsd8rkgvnhpn3rkf-zlib-1.3.1/lib/libz.so.1.3.1
EU=/home/user/scratch/factory-eu/REFER001
US=/home/user/scratch/m4.47/us/REFER001
S=/home/user/scratch/m4.47
python3 tools/point_pair_regen.py --selftest
# 1. the locator: directory cell -> record -> base/table reference, every page verified
python3 tools/point_pair_regen.py locator $EU --jobs 2 --shuffle --json $S/locator-eu.json
python3 tools/point_pair_regen.py locator $US --jobs 2 --shuffle --json $S/locator-us.json
# 2. the M5.26 search over the same files (negative: the plain encodings stay absent)
python3 tools/point_pair_regen.py locator $EU --legacy
# 3. relocation of the name chain of every pair: verbatim move and 1000 real names
for f in $EU/POINT*.DAT.cmp $US/POINT*.DAT.cmp; do n=$(basename $(dirname $(dirname $f)))-$(basename $f .DAT.cmp); python3 tools/point_pair_regen.py relocate $f $S/noop/$n --libz $L --json $S/noop/$n.json; python3 tools/point_pair_regen.py relocate $f $S/perm/$n --permute 1000 --libz $L --json $S/perm/$n.json; done
python3 tools/point_pair_regen.py summarize $S/noop
python3 tools/point_pair_regen.py summarize $S/perm
# 4. the sets M5.26 refused on EU POINT010, then an independent decode
python3 tools/point_pair_regen.py relocate $EU/POINT010.DAT.cmp $S/out/eu010-permute1000 --permute 1000 --libz $L
python3 tools/point_pair_regen.py relocate $EU/POINT010.DAT.cmp $S/out/eu010-permute10000 --permute 10000 --libz $L
python3 tools/cmpind.py verify $S/out/eu010-permute10000
# 5. firmware: the record the base reference lives in, and the shld-by-11 sites
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f56bc --count 40
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f6ad0 --count 20
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f6d48 --count 20
```

   (Step 3 ran two pairs at a time with `xargs -P 2`, each job the loop body
   above; the output pairs were deleted after their own `verify`.)
3. **Controls.**
   - *Positive:* `locator` follows cell → record → table reference, parses
     the table, then takes the base from the base reference and verifies
     every page against the table (`locate_chain`: zlib stream at
     `base+2*start_w`, length within the rounded `comp_w`, inflated length
     `2*inner_w`, zero padding) and the chain length word. Independently,
     `find_chains` (M5.26, base found by matching page 0 among all aligned
     streams) must give the same base and table.
   - *Negative:* (a) the stored base address read as a plain 0x800-sector
     or 0x100-block number; (b) **shuffled values**: each file's stored base
     address replaced by the next file's (same per_page) — both must stop
     reaching a verified chain; (c) the M5.26 72-encoding search (`--legacy`)
     must still find nothing (the field is not in those encodings);
     (d) selftest: a stale locator after a move, a shuffled address, and a file
     without the directory each fail.
   - *Relocation positive:* `relocate` must leave a pair that `cmpind`
     decodes, whose chain the locator reaches at the new base, that the
     independent `find_chains` scan finds at the new base and not at the old
     one, with every requested name present with `@` and 0 bytes changed
     outside the old chain, its table and the 8-byte base reference.
4. **Scope.** All 44 POINT pairs of both 2011 builds (132 chains: 44 × 400,
   1000, 2000). Directory cells other than `0x82a`/`0xeba` and the rest of the
   descriptor records are not interpreted. The `4e 20 00 00` index chains and
   the `0x1000` record are not moved. Firmware: only the three VAs above were
   read; the code that loads the dictionary block (header-table entry `+44`,
   M3.11c) and reads the base reference is **not** located, and no relocated
   pair was run through the firmware (rule 13).
5. **Falsifier.** As in Hypothesis, stated before the results.

## Interpretation

- **OBSERVED (C-5390):** POINT `.DAT` structures are addressed by a BE `u32`
  block address `(off/0x800)<<8 | (off%0x800)/0x100`; the 6-byte cells at
  `0x800..0xf06` (`u32 addr, u16 blocks`, empty `ffffffff 0000`) list the
  descriptor records.
- **OBSERVED (C-5391):** the chain locator is one layout in 44/44 files:
  cell `0x82a` → the dictionary record, base references at `+0x2e` (1000) and
  `+0x13c` (400), table references at `+0x19a`/`+0x1b6`; cell `0xeba` → the
  2000 chain's record, `+0x24`/`+0x94`. A base reference is `u32 addr, u32
  length in words`; a table reference `u32 addr, u32 length in words, u16
  per_page`. Following it reaches 132/132 verified chains.
- **VERIFIED (C-5392, negative controls):** the stored base address shuffled
  between files, or read as a plain sector or block number, reaches 0 chains;
  each reference occurs once per file. M5.26's C-2955 (UNKNOWN) is answered:
  its search had the right units but not this mixed encoding, and the records
  holding it lie outside `0x0–0x7fff` (only the directory cells are inside).
- **VERIFIED (C-5393, tool):** `point_pair_regen.py relocate` moves one chain
  to the next 0x100 boundary after the end of the `.DAT`, rewrites its table and
  base reference, zeroes the old bytes, writes the pair with unchanged outer
  chunks verbatim, and checks the result through the locator and an
  independent scan.
- **OBSERVED (C-5394):** on real pairs the chain-slot limit of M5.26 is gone:
  44/44 pairs move verbatim and take 1,000 real names (EU 28,668 names, US 11,000; chains grow up to 8,852 B, slack was 24–248 B), 0 bytes outside; EU POINT010 takes 1,000 and 6,199 real names that M5.26
  refused.
- **OBSERVED (C-5395):** the record that holds the 1000/400 references is the
  field-dictionary block the name accessor reads (M3.11c); the base reference
  is at `D+4` of the header whose `D+24`/`D+26` `fn 0x003f56bc` reads (EU2011).
  The code that loads this block or reads `D+4` is not located.
- **HYPOTHESIS (C-5396):** the firmware reaches a chain only through these
  references (no other copy of a base exists in the file), so a relocated chain
  is read at its new base. Untested in the firmware: rule 13 needs an L3 run of
  the POINT open path on a relocated pair (new task M4.52). [Now OBSERVED (L3,
  page-loader path) by M4.52, see Overtaken.]

## Conclusion

The chain locator is found: block-address references in the descriptor
records the `0x800` directory points to, one layout in all 44 POINT files of
both 2011 builds, every reference unique, shuffled values fail. The task's
done-when is met by the file route: the EXP names the fields, and
`point_pair_regen.py relocate` moves a chain to the end of the `.DAT` and
updates the base reference (selftest 37 checks; real runs above).
`docs/format/refer.md` gains the locator section; claims C-5390–C-5396;
`reader-coverage.md` row 10 notes the move. Open: the firmware loader of the
dictionary block and an L3/L4 read of a relocated pair (M4.52); the index
chains and the other directory records are not interpreted.
