## Question

Does the EU2011 `MMAIN001.DAT` reader (`fn 0x0041a438`, M3.8) read the
factory file, a file rebuilt by `mmain.py` and a file our pipeline
generates, return the `0x1000`-byte read, and refuse a 4095-byte file?

## Hypothesis

M3.8 says the reader asks for exactly `0x1000` bytes and checks neither the
label nor the counts; M9.44 runs it inside the firmware's mount. Then every
`0x1000`-byte file, whatever its content, is accepted and lands in the buffer
at data VA `0x00e23cc0` as `swap16(file)` (M3.11b's per-`u16` swap of the
read layer), and a shorter file stops the mount.

**Falsifier:** a 4095-byte or absent file is accepted; or for an accepted
file the buffer is not `swap16(file)` (then either the read or the swap model
is wrong, and the comparison would say nothing).

## Method

1. **Sample and hash.** As above.
2. **Commands:**

   ```bash
   python3 tools/mmain_l3.py --selftest
   python3 tools/mmain_l3.py run archive/head256.img --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img --json run.json
   ```

   For each case the tool boots the card (`vcard_l3.boot_report`), takes the
   `MMAIN001.DAT` entries of the read log, reads 4 KiB at `0x00e23cc0` and
   compares them with `swap16` of the served file; it then parses
   `swap16(buffer)` with `mmain.parse_mmain` and compares the model with the
   file's model.
3. **Controls.** Positive: `factory` (must ACCEPT, buffer = swap16).
   Negative: `cut4095` and `absent` (must REJECT). Comparison teeth
   (selftest, 11 checks): an unswapped buffer, a buffer from another file, a
   short read, and an ACCEPT of a cut file are each a FAIL.
4. **Scope.** EU2011 build A on the EU 2011 card, PySh4 with the
   `vcard_l3.py` import models. US2011 not run (`vcard_l3.py` carries the
   EU2011 addresses only). One file type; no format change.
5. **Falsifier** as stated above.

## Interpretation

- **FACT (C-5970):** the EU2011 reader accepts a `0x1000`-byte
  `MMAIN001.DAT` whatever its table counts: factory, `mmain.py`-rebuilt
  (byte-identical), edited (+1 on a count) and pipeline-generated (all counts
  0) all mount; one read of `0x1000` bytes each.
- **FACT (C-5971):** for every accepted case the firmware's buffer is
  `swap16(file)`, and `mmain.py` parses it back to the file's own model: the
  Python reader and the firmware hold the same header. Rule 13: the
  `mmain.py` writer's output is *accepted* at L3 (EU2011).
- **FACT (C-5972):** a 4,095-byte file is refused: the read is retried three
  times (`got 0xfff`) and the mount verdict is REJECT; an absent file is
  REJECT with no read.
- **OBSERVED (C-5973):** after the short reads the buffer holds the file's
  bytes **unswapped** (its SHA-256 equals the factory file's, whose 4,096th
  byte is the zero the buffer already had), so the swap happens only on a
  complete read. Why (where the completion skips the swap) is not read here.
- **UNKNOWN:** whether any later consumer checks the counts (none is
  reached by the mount); US2011.

## Conclusion

The `mmain_reader` L3 target runs (`tools/mmain_l3.py`) and meets M9.17's
Done-when on the EU 2011 card: the factory and a rebuilt file each return the
`0x1000`-byte read, as do an edited and a generated file, and a 4095-byte file
is rejected. `targets.json` gets a `mmain_reader` entry of kind `blocked`
that names the tool (the reader is reached through the mount, not as a
`runner.py` call), and `reader-coverage.md` row 3 carries the result.
