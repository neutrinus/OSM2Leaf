## Question

Can a recorded QMP `input-send-event` session drive the same ZOOM IN button as
M8.H39 through the live `ze0-gfx` display console (VNC window) rather than the
raw panel control socket, and be measured at the guest SCI3 frame and screen
level without a human at the window?

## Hypothesis

Yes: QEMU's QMP input can be bound to the M8.H4 display console through a new
`QemuInputHandler`, forwarded over a chardev to the panel peer's existing SCI3
display-unit link, so QMP absolute coordinates (765,70) produce the exact same
touch frame `51 02fd 0046 31` M8.H39 observed and fire `ZOOM ILL EVENT`.
**Falsifier:** the click lands at a different guest coordinate than requested
(scaling error — measured by the peer's decoded-coordinate log), the console-
off control still accepts input, or the screen does not change at the button.

## Method

### 1. Sample and hash

The three SHA-256 values above come from one `sha256sum` command each on the
three files in the worktree/primary checkout. All screenshots and logs live
under `~/projekty/leafre-work/scratch/m8.h40/live{,2}/`; no screenshot or
vendor file is committed.

### 2. Commands

Run from the worktree root; `$Q` is the rebuilt QEMU, `$S` the scratch dir,
`$L` a work dir. Two boots (`live`, `live2`) use the same arguments and
different gdb ports (1290, 1291) to avoid parallel agents' port 1240.

```bash
S=$HOME/projekty/leafre-work/scratch/m8.h40
Q=$HOME/.cache/qemu-ze0/build/qemu-system-sh4
CARD=archive/sd-images/LEAF_2011-2012_US.img

sha256sum "$CARD" firmware/unit-flash/nk1-QY7200ND.bin
bash tools/qemu-ze0/build.sh --check-version 11.1.3 --srcdir "$S/checkcache"
bash tools/qemu-ze0/build.sh --lint-patches
$Q --version; $Q -M help | grep -w ze0

# build the session inputs once, reuse for both boots
python3 tools/ze0_ipl.py patch "$CARD" -o "$L/ipl.txt"
python3 -c "import sys;sys.path.insert(0,'tools');import unitflash_anon as u;open('$L/flash.bin','wb').write(u.build(u.read(u.PROD_DEFAULT_FILE),u.read('firmware/unit-flash/nk1-QY7200ND.bin'),u.read(u.SRAM_DEFAULT_FILE),u.read(u.VFLASH_DEFAULT_FILE)))"

TMPDIR="$S/tl-tmp2" python3 tools/ze0_launch.py --qemu "$Q" \
  --card "$CARD" --flash "$L/flash.bin" --peer panel --gdb 1290 \
  --ui-start --display vnc=127.0.0.1:7 --input --qmp \
  --workdir "$L" --timeout 900
```

The recorded, no-human scenario is `docs/emulator/scenarios/live-tap.txt`:
wait `ANTITHEFT_CC_NTF_COMP_OK` + `AUI Initialize Complete`, tap consent OK
(277,98) through `ze0-gfx`, wait `SK_SCT_AGREE_CLICK` +
`NORMAL_MAP::CompleteShowScreen`, tap ZOOM IN (765,70), shot `after-tap`.
The QMP events were injected with `python3 tools/ze0_input.py` semantics and a
small marker-waiting wrapper (`$S/session.py`); the reproducible command that
prints every scaled qword and the decoded round-trip is the tool's selftest:

```bash
python3 tools/ze0_input.py --selftest
# prints x 765 -> 0x7a8d, y 70 -> 0x12b5, x 0x12b4 -> decodes to 69,
# sub-pixel 0x7a8e -> still 765, abs roundtrip (765,70), 15 checks 0 failed
python3 tools/ze0_peers/panel.py --selftest
# prints decoded frame 5102fd004631, x=765 y=70; 0 failure(s)
python3 tools/ze0_launch.py --selftest
python3 tools/ze0_screenshot.py --selftest
```

After each boot reaches the map screen, capture the idle plane, send QMP
abs/btn at (765,70), capture three after-tap planes and hash them:

```bash
python3 tools/ze0_screenshot.py plane --monitor "$L/mon.sock" -n 1 -o "$L/map-idle.png"
# QMP: input-send-event device=ze0-gfx events=[abs x 0x7a8d],[abs y 0x12b5],
#      [btn left down],[btn left up]  (all print {'return': {}})
python3 tools/ze0_screenshot.py plane --monitor "$L/mon.sock" -n 1 -o "$L/after-a.png"
sha256sum "$L/after-a.png" "$L/after-b.png" "$L/after-c.png"
grep -c 'ZOOM ILL EVENT' "$L/serial.log"
grep 'x=765' "$L/panel.log"
```

Named-region hashes (falsifier control) use the committed analyzer:

```bash
python3 tools/ze0_region.py --selftest
python3 tools/ze0_region.py --mask-from "$L/map-idle.png" "$L/after-a.png" \
  "$L/empty-a.png" "$L/empty-b.png" --hash "$L"/after-*.png
```

### 3. Controls

- *Positive, button identity:* QMP (765,70) → peer log
  `input: tap x=765 y=70 st=1 frame=5102fd004631` → SCI3 frames
  `5102fd004631`/`5102fd004630`, the exact touch frame of H39 (its EXP O5).
  `ZOOM ILL EVENT` count rises from 0 to 1 in both boots.
- *Positive, screen changes:* after-tap full plane hash differs from idle
  (`ff200ff6…` → `bf5818c8…` in run 1; different boot-dependent overlay in
  run 2) and is identical across three consecutive shots in each run.
- *Negative, console off:* with `gfx-display=off` QMP `input-send-event` to
  `device=ze0-gfx` replies `Device 'ze0-gfx' not found` (no console); with no
  device it replies `Input handler not found for event type abs`. Both fail
  loud — the input did not traverse a display console.
- *Negative, scaling (large offset):* panel (400,70) → qwords 0x4015/0x12b5 →
  peer log decodes `input: tap x=400 y=70 st=1 frame=510190004631`; no
  `ZOOM ILL EVENT` (count stays 1), the named region stays idle. The wrong
  QMP word x+1 (0x7a8e) still decodes to 765 (sub-pixel truncation), so a
  1-pixel mutation is explicitly NOT used as the scaling falsifier (D8).
- *Negative, checker:* mutating an `expect-hash` to 64 zeroes makes the
  `ze0_ui.py` runner exit 1 (per H39 O9); the `ze0_input.py` selftest's
  click-before-abs returns exit 1 and a missing QMP endpoint returns exit 3.
- *Negative, unknown key:* qcode not in `ze0_keymap.json` is refused by
  `InputBridge` (panel selftest); QMP key events are converted linux→qcode
  before naming (`qemu_input_linux_to_qcode`, D9).

### 4. Scope

Two boots of NK1 + ROM A from the US card, anonymous 8 MiB unit flash, one
panel peer on `sci3` with the forwarded-input chardev, one `--display vnc`
console, `--ui-start --touch-unlock`, one consent unlock tap, one ZOOM IN tap
per boot, one wrong-scale tap, one empty-area pair, one console-off control,
and three post-tap screenshots per boot. The EU card was not used (H39's
negative control: it never reaches `COMP_OK` here); this US fallback is
TL-approved and is an explicit scope deviation from any EU2011 wording.
Excluded: L3/L5, generated cards, other UI screens, real mouse/keyboard
hardware, and any commit of vendor screenshots. The screen view is DU plane 1
(`plane -n 1`, not `screen`) for all hashes.

### 5. Falsifier

The task's stated falsifier ("click lands at a different guest coordinate than
requested — scaling error — measured by the peer's log") was tested directly:
the peer printed the DECODED coordinates and frame for every tap, and the ZOOM
tap's frame equals H39's `5102fd004631`. A genuine scaling error would have
printed a different x/y (as the (400,70) negative control did). The screen also
changed only at the ZOOM button (`ZOOM ILL EVENT`, scale label), not on the
empty tap. The boot-dependent NavTraffic overlay changed full-frame bytes
between boots (documented in H39 §5), so named regions, not full frames, are
used for hash assertions.

## Interpretation

- **FACT:** A recorded QMP `input-send-event` session drives the same ZOOM IN
  button as M8.H39 through the live display console: the peer decodes the exact
  H39 touch frame `5102fd004631` at (765,70) and `ZOOM ILL EVENT` fires in both
  boots. Rule 13 level L4 (full-system emulator); no car/bench run.
- **FACT:** QEMU's integer truncation was derived and printed: (765,70) needs
  qwords 0x7a8d/0x12b5; the previously assumed 0x12b4 maps to 69. The scaling
  falsifier is the peer's decoded-coordinate log, not a region hash.
- **FACT:** The console-off control fails loud, so the input really traversed
  the display console rather than a global fallback handler.
- **OBSERVED:** Full-frame hashes are boot-dependent (NavTraffic/consent
  overlay), matching H39's documented confound; within a boot the after-tap
  hash is stable across three shots. The exact H39 region hash `c64ff230…` is
  not reproduced because the live window's UI is in a different state; the
  button identity is instead proven by the identical SCI3 frame.
- **UNKNOWN:** Why the NavTraffic overlay state differs between boots (out of
  scope; same class as H39's focus-animation unknown).

## Conclusion

M8.H40 is **done**: a QMP input script taps the same ZOOM IN button as M8.H39
through the `ze0-gfx` display console; the peer's decoded frame equals H39's
exactly and the UI reacts (`ZOOM ILL EVENT`, scale label), with a stable
after-tap hash within each boot and a loud console-off negative control. The
new QEMU patch, the input driver, the keymap and the recorded scenario are
committed; claims C-7370–C-7379 are registered. The specific cross-boot H39
region hash is not reproduced due to boot-dependent UI state, which is
recorded as an OBSERVED scope limit rather than hidden.
