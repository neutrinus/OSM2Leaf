## Question

Are two fresh, otherwise identical `-M ze0` boots bit-identical in the four
observables an L4 regression gate would compare — serial log, DBGMSG log, SD
read order and a VRAM hash taken at a fixed point in guest time — and if not,
what exactly differs and why?

## Hypothesis

With `-icount shift=0,sleep=off` and no host-clock device in the machine
(`OEMGetRealTime` is a software clock seeded from `nk.exe`, M8.B3, C-6240 area),
the guest's observable behaviour is repeatable. **Falsifier from the task:** the
runs differ with `-icount` on and no host-clock device. A secondary falsifier is
that VRAM is not stable when sampled at the *same guest time* (as opposed to the
same wall-clock instant).

## Method

1. **Sample and hash.** The four inputs above were hashed with `sha256sum` in
   the worktree at revision `8f1c6140377de9af88af844bf0ae7a40dee3a3b4` (the
   claim commit for M8.H6). All seven boots used the same head image, the same
   card image under a *fresh* overlay per run, the same QEMU binary and the same
   IPL patch file.

2. **Commands.** Committed tools, runnable as written. `PLUGINS` below is the
   absolute path of the scratch QEMU build; `RUN` is a fresh directory.

   ```bash
   # regenerate the IPL patch (the file hashed above), 8 lines
   python3 tools/ze0_ipl.py patch archive/head256.img -o ipl.txt

   # offline tool checks (no vendor bytes, no QEMU)
   python3 tools/ze0_rundiff.py --selftest
   python3 tools/ze0_rundiff_capture.py --selftest
   python3 tools/selftest.py --only ze0_rundiff
   python3 tools/selftest.py --only ze0_rundiff_capture

   # one fresh boot -> one run directory (EU 2011 recipe from M8.C1e)
   python3 tools/ze0_rundiff_capture.py RUN \
     --qemu /home/marek/projekty/leafre-work/qemu-ze0-m8h6/qemu-system-sh4 \
     --ipl-patch ipl.txt \
     --image archive/head256.img \
     --card archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img

   # the same, but stop at a fixed guest time instead of at the milestone alone
   python3 tools/ze0_rundiff_capture.py RUN \
     --qemu /home/marek/projekty/leafre-work/qemu-ze0-m8h6/qemu-system-sh4 \
     --ipl-patch ipl.txt \
     --image archive/head256.img \
     --card archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --msec-target 32000

   # compare two run directories
   python3 tools/ze0_rundiff.py RUN1 RUN2
   ```

   Seven boots were captured: `A`, `B`, `C`, `G`, `H` with the milestone-only
   command and `E`, `F` with `--msec-target 32000`. `A` and `B` were made with
   the identical predecessor script during tool development; `C`, `E`, `F`, `G`,
   `H` were made with the committed command above. The capture writes
   `serial.log`, `dbgmsg.log`, `sd-reads.txt`, `vram.sha256` (the four compared
   channels), plus `serial-full.log`, `vram.bin`, `guest-msec.txt`, `qemu.log`,
   `qemu-argv.txt`, `meta.txt` and the overlay for provenance.

3. **Controls.** *Positive:* the `--selftest` of `ze0_rundiff.py` fabricates two
   run directories with no vendor bytes, compares them (4/4 equal, exit 0), then
   mutates each channel on its own and requires the tool to name it and exit 1;
   `ze0_rundiff_capture.py --selftest` checks milestone cutting, SD-read
   filtering, LF normalisation and VRAM hashing on synthetic captures. Both
   selftests are discovered by `tools/selftest.py`. *Live positive control:*
   `E F` and `G H` are expected to reach 4/4. *Negative control:* `A B` are two
   independent boots with the same recipe; a difference there is a real guest
   difference, not a tool artifact, because every input hash and the SD-read
   channel agree. A second negative control is `C`, whose VRAM was taken at a
   different guest time; its raw log is preserved as `serial-full.log`.

4. **Scope.** Seven boots of the EU 2011 card under the patched SH-4 machine
   (series through `ze0-0014`, i.e. with the 2DG interpreter); four compared
   channels; one 25,559,040-byte VRAM dump per boot; 422 SD block reads per
   boot. Excluded: other card years, kernel C, hardware (rule 11), record/replay,
   and any change to a device model (the task's Stop boundary). `dbgmsg.log` is
   not independent of `serial.log`: on this board the kernel debug sink is
   serial port 0, so the collector only normalises line endings for the second
   channel (C-6240, M8.B6). The compared serial channels are cut at the second
   `MSG_PROCESS_NAVI_MAP_CC` line, a guest event; `serial-full.log` keeps the
   host stop-latency tail.

5. **Falsifier.** Two fresh boots under `-icount shift=0,sleep=off` with no
   host-clock device differ on any of the four channels. A second falsifier:
   VRAM differs when the guest clock at capture is the same. Both are allowed to
   fire; in that case the EXP must name the channel and its cause.

## Interpretation

- **FACT (C-7030, C-7031):** `ze0_rundiff.py` compares the four named channels,
  reports the first difference per channel, and has a passing `--selftest`
  discovered by `tools/selftest.py`; `ze0_rundiff_capture.py` produces those
  channels reproducibly from one boot and has its own passing selftest (O1).
- **FACT (C-7032, C-7033):** two fresh boots captured at the same guest time
  (E/F) and two captured at the same guest milestone (G/H) are bit-identical on
  all four channels; the tool exits 0 (O5). The Done-when's first branch is met.
- **FACT (C-7034):** the SD read order is identical in all seven boots: 422
  reads, same digest (O6).
- **FACT (C-7035):** VRAM at a fixed guest time is stable: six of seven boots
  hash to `5607f4e5…`. C sampled a transient frame 1–2 guest seconds earlier
  and is the negative control that shows why a wall-clock stop is not a fixed
  guest time (O4).
- **OBSERVED (C-7036):** `serial.log`/`dbgmsg.log` are *not guaranteed* equal:
  A vs B differ only in a 9-line `Spcom` log prefix whose per-boot value is
  either `0x57ef8026` or `0x77ef8026` (O3). This fires the task's falsifier for
  those two channels even with `-icount` and no host-clock device. **HYPOTHESIS:**
  the value is uninitialised residue or a per-boot allocation address in the
  speech module's logging prefix; it is constant within a boot, is not host
  time, and does not affect SD reads or VRAM. It was not traced to a writer.
- **FACT (C-7037):** on `-M ze0` the DBGMSG text and the serial capture share a
  port; the two channels are the same bytes modulo LF, so they are coupled, not
  independent evidence (O1, Method 4).
- **FACT (C-7038):** the task's falsifier is met for the serial/DBGMSG channels
  on at least one pair of fresh boots (A/B). Determinism here is conditional on
  which value the speech module logs, not on host clock drift.
- **FACT (C-7039):** the host stop window adds guest lines after the milestone;
  the tool cuts the compared channels at the guest event and keeps the raw tail
  in `serial-full.log` (O7).
- **UNKNOWN:** whether the two `Spcom` values correlate with a specific
  allocation order (and thus which task could make them stable) — not resolved
  here, per the task's Stop boundary.

## Conclusion

`tools/ze0_rundiff.py A B` is implemented with a synthetic `--selftest` and is
in `tools/selftest.py`. Two fresh boots captured at the same guest time (E/F)
and at the same guest milestone (G/H) are bit-identical on all four channels:
the tool exits 0, so the primary Done-when passes. The companion capture tool
makes this reproducible from the repository. The other five boots show the two
sources of difference an L4 gate must handle: a per-boot `Spcom` log-prefix
value that changes the serial/DBGMSG bytes (A vs B), and a wall-clock stop that
can sample a different VRAM frame (C); both are named above with their cause,
so the alternative Done-when is covered as well. The SD read order and the VRAM
hash at a fixed guest time are stable across all seven boots. No device model
was changed.
