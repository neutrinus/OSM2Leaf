# EXP-2026-11-06-M1.9: Cross-image import names (A → B's exporters)

- **Status:** done
- **Date:** 2026-11-06
- **Sample:** `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (IMG256, first 256 MiB) + SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; synthetic ROMs from `tools/cerom.py build_synthetic_rom`/`build_thunks_rom` (no vendor bytes)
- **Claims:** C-1760–C-1769
- **Supersedes:** none
- **Superseded by:** none

## Question

Can ordinal imports of app image A modules be resolved to exporter names by
loading export tables from kernel image B/C segments in the same firmware image,
so `COREDLL!#1145` becomes `COREDLL!_wfopen` and `sh4xref.py --calls` labels
import calls with names?

## Hypothesis

Image B (kernel, `--image-start 0x3e00200`) exports `coredll.dll` with 1651 named
ordinals (C-527, C-1710) and other DLLs (`commondll.dll`, `SYS_INF.dll`,
`Errlogdll`, `CEDDK.dll`). Resolving A's ordinal imports against all modules in
the B segment by `(dll lowercased, ordinal) -> export name` will name the
resolvable slots.

## Observations

- `cerom --selftest`: 359 checks OK (synthetic, no vendor data). M1.9 cases:
  `resolve_import_entry` maps `COREDLL.DLL` ordinal 1145 to `COREDLL!_wfopen`
  when the export table has `{1145: "_wfopen"}`; unknown ordinal 9999 stays
  `#9999` with reason `no export table for COREDLL.DLL`; named imports keep
  `MODULE!name`. `load_names_json` accepts `{"modules": {"coredll.dll": {"1145": "_wfopen"}}}`
  and the flat `{"COREDLL.DLL": {"1145": "_wfopen"}}` shapes. End-to-end CLI:
  `imports NAVI.EXE --names ...` resolves an ordinal slot to
  `OBJDLL!MAL_DataVol_getSize` and prints a resolved/unresolved summary;
  `--resolve-with <image_start>` against the same synthetic segment resolves
  ordinal 6 the same way.
- `sh4xref --selftest`: OK (17 prior checks + 3 M1.9 checks).
  `load_module(..., names_path=...)` resolves an ordinal slot to
  `OBJDLL!MAL_DataVol_getSize`; without a resolver the slot keeps `OBJDLL!#6`.
  The Labeller import table therefore carries resolved names for `--calls`.
- `python3 tools/selftest.py`: `passed=30 failed=0 skipped=19 total=49 time=1.92s selftest: OK`.
- Real IMG256, Navi.exe (A `0x200200`), resolver B `0x3e00200`:
  - summary: `697/846 resolved, 149 unresolved`
  - `COREDLL.dll slot=0055d118 COREDLL!_wfopen` (the done-when example; no
    `#1145` line present)
  - 136 lines contain `COREDLL!` (all COREDLL imports named via B exports)
  - 846 `slot=` lines total in the per-import listing; 149 are reported again in
    the `unresolved:` section with reasons
  - unresolved DLLs (no export table found in segment B) begin with `XGLDLL.dll`
    and end with `OSMDLL.dll` (18 slots at `0055d910`–`0055d954` shown at the
    tail); each line states `no export table for <DLL>`.

## Interpretation

- **FACT (synthetic):** `resolve_import_entry` resolves an ordinal import to
  `MODULE!export` from an export table `(dll, ordinal)->name` and leaves
  unknown ordinals as `#ordinal` with a reason. `cerom.py imports --names` and
  `--resolve-with` use that path; `sh4xref.load_module` uses the same resolver
  so its import labels/`--calls` carry resolved names.
- **FACT (IMG256):** With `--image-start 0x200200` and `--resolve-with 0x3e00200`,
  Navi.exe reports 846 import slots, 697 resolved and 149 unresolved. `COREDLL`
  ordinal 1145 resolves to `COREDLL!_wfopen`. Unresolved slots are listed with
  reasons (their exporter DLLs have no export table in the B segment supplied).
- **HYPOTHESIS:** The 149 unresolved slots (e.g. `XGLDLL.dll`, `OSMDLL.dll`)
  may resolve if their exporting modules exist in another segment (A/C copies or
  a different `--resolve-with`); resolving against all modules of the supplied
  segment is implemented, so adding the right segment/`--names` DB should name
  them.
- **UNKNOWN:** Whether any unresolved ordinal maps to a different name than the
  spec assumed; the mechanism is proven, the exporter location for those DLLs is
  not established here.

## Conclusion

`tools/cerom.py` gains `collect_exports`/`load_names_json`/`load_resolver_tables`
and `resolve_import_entry`, plus `imports --resolve-with IMAGE_START` (repeatable)
and `--names FILE`. It prints `MODULE!name` for resolved imports and lists every
unresolved ordinal with a count and reason. `tools/sh4xref.py` accepts the same
flags and its `load_module` populates import labels with resolved names for
`--calls`. The done-when example holds on IMG256 (`COREDLL!_wfopen`); 697/846
Navi.exe slots resolve from B, 149 are listed unresolved because their exporters
are not in the B segment. `tools/README.md` updated.
