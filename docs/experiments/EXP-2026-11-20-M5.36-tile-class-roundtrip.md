## Question

Does the level-1 road class `(draw layer, cls_hi)` that `tilewriter` emits into
a tile's even `0x00fa` records decode back to exactly the same class, and does a
check built on that comparison fail when one emitted class is changed by one
value?

## Hypothesis

At the class level the round trip is exact: the writer computes
`(layer, cls) = fa_encode.layer_class(highway, 1)` and writes `cls << 12` into
word 2 of the shape; `fa_encode.parse_record` reads `w[p+2] >> 12` back and the
layer from the unit's layer table. **Falsifier (stated before the run):** the
check reports PASS for a tile whose emitted class map differs from the decoded
one by one value, or a decoded class that differs from the emitted list is not
reported.

## Method

2. **Commands.** From the repository root:

```bash

python3.13 tools/tile_class_roundtrip.py check $F --emitted $W/factory/MAPAL001/B48R058R.DAT.class.json

```

3. **Controls.** *Positive*: the same input that produced the tile produces
   the emitted map (`from-imf` is the writer's inverse at the class level);
   `check` must PASS. `dump` then `check --emitted` on the untouched factory
   tile must PASS. *Negative*: one emitted class changed by one value (with
   `mutate`) must FAIL with the same-class decoded list in the error.
4. **Scope.** Level 1 only (the writer emits level 1). The splice tile:
   6 parcels, 8 shapes, 47,656 decoded class records (factory + splice). The
   untouched factory census: 47,656 records, 1,694,111 shapes (level 1:
   43,585 records; level 2: 4,071), 64,233 raw even records. Excluded: level 2
   emitted classes (no writer), road name/speed semantics, and what the class
   means to the firmware (M5.3/M4.17).
5. **Falsifier.** A one-value mutant that reports PASS, or a decoded class
   different from the emitted list that is not reported, refutes the claim.

## Interpretation

- **FACT:** the class the writer emits into the splice is decoded back
  unchanged on all 6 spliced parcels (`match=6`, `fail=0`), and on the whole
  untouched factory tile `dump`→`check` reports 47,656/47,656.
- **FACT:** the check is not vacuous: a one-value class mutant FAILs at
  `tools/tile_class_roundtrip.py check` (exit 1) and at
  `l2check --class-tiles` (exit 1, `RESULT: FAIL`).
- **OBSERVED:** the level-1 class field is recoverable for every road
  (`w[p+2] >> 12` plus the unit layer table); the Stop condition
  `NOT_APPLICABLE — class field not readable` does not apply.
- **UNKNOWN:** which OSM highway a class came from beyond the emitted map,
  whether the class is *correct* on the car, and what the class means to the
  firmware (M5.3/M4.17; rule 13 stays open). The provisional table covers only
  5 of the 11 factory class rows.

## Conclusion

`tools/tile_class_roundtrip.py` and the `l2check` check `tile_class_roundtrip`
(`--class-tiles`, `--class-emitted`, or a `MAPAL001/<tile>.class.json`
sidecar) are the L2 golden for the level-1 road class: the writer's emitted
class map — built from its own IMF input by `from-imf` — decodes back
unchanged, a one-value mutant FAILs, and a tile with no emitted map reports a
`decoded` census, never a PASS. Done-when is met on the synthetic fixture
(`l1l2_fixtures` row `l2.tile.class-roundtrip`, PASS + mutant FAIL), on the
real `B48R058R` splice (6/6 parcels) and on the untouched factory tile
(47,656/47,656). No format change and no new class value were introduced;
`docs/format/map-tiles.md` already states the `w[p+2] >> 12` rule and the
CLI now enforces it. Claims C-5760–C-5762.
