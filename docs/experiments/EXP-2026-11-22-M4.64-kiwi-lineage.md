# EXP-2026-11-22-M4.64-kiwi-lineage: KIWI/Xanavi vocabulary in the firmware

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** `archive/head256.img` `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9` (EU2011 build A `0x200200`; B `0x3e00200` and C `0x5200200` searched too)
- **Tools:** Python 3.15.0; `tools/ce_strfind.py`, `tools/sh4xref.py`, `tools/nk_decomp.py`; `jharg/kiwiread` at `74741c5b` for chapter titles only
- **Claims:** C-7630–C-7636
- **Supersedes:** none
- **Superseded by:** none

## Question

Which KIWI/Xanavi concept names actually appear in the ZE0 firmware, in which module and with which referencing function — and does their presence support the lineage hypothesis for the *map format*?

## Hypothesis

String names alone are weak evidence; the expected result is that `Xanavi`, `MDP_`/`RcvParcel` and task names (`LOC_map`, `LOC_db`, `RAW_rec`) exist, while KIWI chapter terms such as `Multilink` or `Minimum Graphics` do not. **Falsifier:** the parcel/Xanavi strings occur only in a font or telematics module and no map task name is reachable from code.

## Inputs

| Item | Value |
| --- | --- |
| Image | pinned IMG256, 134,217,728 B read by `ce_strfind.py`, modules=149, va_base `0x8cae1000` |
| Vocabulary | KIWI chapter titles quoted by `kiwiread` plus `Xanavi`, `XTP`, `MDP` (parcel, level, block set, block, management record, distribution header, multilink, display class, minimum graphics, name data, route planning, route guidance, integrated information) |
| Encodings | ASCII, UTF-16LE, UTF-16BE (`--encoding all`) |

## Method

1. **Sample and hash.** The pinned firmware head; no card file and no OSM extract. The KIWI source is a public commit read only, no GPL code copied.
2. **Commands.**

   ```bash
   python3 tools/ce_strfind.py --selftest
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x200200 --module Navi.exe --encoding all Xanavi XANAVI RcvParcel MDP_ Parcel 'Route Planning' Multilink 'Minimum Graphics'
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x200200 --encoding all xglXtpDrawXanaviCharacter 'NOT XANAVI'
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x00011190
   python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe 0x0032efa8
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x3e00200 --encoding all XANAVI RcvParcel MDP_
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x5200200 --encoding all XANAVI RcvParcel MDP_
   ```
3. **Controls.** `ce_strfind.py --selftest` passes (synthetic ROM with known encodings). *Negative control:* `MULTILINK` and `Minimum Graphics` are in the vocabulary but return 0 hits in `Navi.exe`; *positive control:* `MDP_` returns 36 hits and one of its string-table VAs has a literal-pool xref. The `--to 0x00187f10` lookup returns "no literal pool holds" for `RcvParcel`, so data-only strings are reported as such rather than assigned a fake function.
4. **Scope.** One firmware image, all 149 modules for the broad scan, `Navi.exe` and `XGLDLL.dll` for the named hits, all three ROM starts for the three key strings. Excluded: decompressed resource data beyond `ce_strfind.py`'s module scan, a real KIWI disc, and any claim that the card format is KIWI.
5. **Falsifier.** As above: if the parcel strings were font-only and no map task name were reachable, the vocabulary would not support lineage.

## Observations

```text
Navi.exe  XANAVI        1 hit  va 0x0017abc8 (NOT XANAVI at 0x0017abc4)
Navi.exe  RcvParcel     3 hits va 0x00187f10 / 0x00187f78 / 0x00187f9f
Navi.exe  MDP_         36 hits, string table at 0x00011190
Navi.exe  Parcel        3 hits (same RcvParcel strings)
Navi.exe  Route Planning 1 hit va 0x000115c0
Navi.exe  MULTILINK / Multilink / Minimum Graphics  0 hits
XGLDLL.dll xglXtpDrawXanaviCharacter 1 hit va 0x03123b16
ROM B (0x3e00200): XANAVI/RcvParcel/MDP_ 0 hits
ROM C (0x5200200): XANAVI/RcvParcel/MDP_ 0 hits

sh4xref --to 0x00011190: pool 0x0032f4f4 holds it, loaded at 0x0032f2e4,
  function starting 0x0032efa8 (pdata START, length 0xa8c)
sh4xref --to 0x00187f10 / 0x0017abc8 / 0x000115c0: no literal-pool xref
```

## Interpretation

- **FACT:** the names are real and concentrated in ROM A: `Navi.exe` carries the map task symbols `MDP_*`, `LOC_map`, `LOC_db`, `RAW_rec` and a function at `0x0032efa8` loads their string table; `XGLDLL.dll` carries an Xanavi drawing symbol. The falsifier did not fire — this is not a font-only occurrence.
- **OBSERVED:** three of the four distinctive KIWI chapter terms checked are absent from `Navi.exe`; `Route Planning` occurs as a generic string and has no literal xref. The vocabulary therefore supports a *naming* lineage, not a structural one.
- **UNKNOWN:** which KIWI version (if any) the names came from (M4.65); no function was attributed to `RcvParcel` because no literal pool holds its VA in executable sections.
- **Process:** the glossary page lists only what was found, with the "not named" verdicts included.

## Conclusion

M4.64's Done-when is met: term → module → VA → referencing function table (or "no literal xref") above, the full searched vocabulary and the 134,217,728-byte corpus printed by the commands, the glossary started at `docs/format/kiwi-glossary.md`, and the `kiwiread` row in `sources.md` updated. No structural KIWI claim is made.
