- **Date:** 2026-11-20

## Question

Can the EU2011 kernel's debug text (what `ze0_dbgmsg.py` reads over the
gdbstub) be put on the `-M ze0` debug serial port, so that `run.sh --serial`
alone gives a plain boot log, and what is the least invasive way?

## Hypothesis

The task's scope ranks three ways: (a) a board/boot argument the OAL reads,
(b) a `ze0` machine option, (c) a one-word guest patch. M8.A6 (C-1282)
already showed that `fn 0x880404f4` sends every string to AstLog and, behind
the gate `0x89e613b0`/`0x89e613b4`, to a `DebugLog` path, and that neither
loads a SCIF address. Expected: no gate value reaches the UART, so (a) and a
gate-presenting (b) fail; an emulator-side hook on `0x880404f4` (an HLE
machine option, no guest byte changed) does.

**Falsifiers (stated before the runs):** the static path from the gate to
`0xffe46000` exists (then a gate value is the cheaper route); or the serial
text differs from the gdbstub capture of the same boot in a line that the
hook itself explains (a missed or extra string, wrong register bank, wrong
decoding); or the boot with the option no longer reaches F1.

## Method

### 1. Static: the gate, its writers, and where each path ends

```bash
I=archive/head256.img
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x880404f4 --count 40   # sink: AstLog always, gated DebugLog call
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8804048c --count 50   # DebugLog path: 0x88043e04, 0x88044fe8
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8804cfa4 --count 26   # SCIF writer, r4 = string
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x88049f4c --count 12   # writes 0x89e613b0 from *r5
python3 tools/sh4dis.py $I nk.exe --image-start 0x3e00200 --va 0x8804aa08 --count 16   # sets 0x89e613b4 = 1
python3 tools/sh4xref.py $I nk.exe --image-start 0x3e00200 --to 0x88049f4c             # pool 0x88009384 (IOCTL table)
python3 tools/sh4xref.py $I nk.exe --image-start 0x3e00200 --to 0x8804aa08             # fn 0x88048f94
python3 tools/cerom.py --image-start 0x3e00200 $I va2file 0x88009360                   # 0x03e09560 (IOCTL table rows)
python3 tools/ze0_serial.py refs $I --window 0xffe00000:0x100000                       # every 0xffe0xxxx..0xffefxxxx pool word in nk.exe
```

### 3. Boots (each 150 host seconds, one QEMU at a time)

```bash
cd /home/user/OSM2Leaf.task-m8.b6-debuglog-uart
Q=/home/user/scratch/qemu/qemu-system-sh4.b6; W=/home/user/scratch/qemu/runs/b6
# positive: run.sh --serial (default log), option on by default; twice for repeatability
bash tools/qemu-ze0/run.sh --image archive/head256.img --machine ze0 --icount shift=0,sleep=off --timeout 150 \
  --qemu $Q --workdir $W/pos --no-memmap --log /dev/null --no-summary
bash tools/qemu-ze0/run.sh --image archive/head256.img --machine ze0 --icount shift=0,sleep=off --timeout 150 \
  --qemu $Q --workdir $W/pos0 --no-memmap --log /dev/null --no-summary
# negative: the same boot without the option
bash tools/qemu-ze0/run.sh --image archive/head256.img --machine ze0 --icount shift=0,sleep=off --timeout 150 \
  --qemu $Q --workdir $W/neg --no-memmap --log /dev/null --no-summary --dbgmsg off
# cross-check: ze0_dbgmsg.py over the gdbstub AND the serial hook in one boot, plus M8.B5 checks 1-3
cd $W && python3 /home/user/OSM2Leaf.task-m8.b6-debuglog-uart/tools/ze0_dbgmsg.py run --duration 150 \
  --count 0x88022164 --count 0x88011cb8 --word 0x89e41888 --dump 0x89e40000:0x40000:x.bin -o x-dbg.log -- \
  $Q -M ze0,dbgmsg=0x880404f4 -kernel /home/user/OSM2Leaf/archive/head256.img -icount shift=0,sleep=off \
  -nographic -serial file:x-serial.log -monitor none
cd /home/user/OSM2Leaf.task-m8.b6-debuglog-uart
python3 tools/ze0_dbgmsg.py modules $W/x.bin archive/head256.img --dump-va 0x89e40000

python3 tools/ze0_serial.py dbgcmp $W/x-serial.log $W/x-dbg.log                  # same boot, first 200 lines
```

`dbgcmp` cuts both logs into text lines the same way (serial on `\n`; the
gdbstub log one message per hook line with `" | "` for an inner CRLF; empty
lines dropped) and compares the first `--lines`.

### Controls

- **Positive:** `pos` (`run.sh`, option on) must write the banner and the
  boot's debug text; `x` must give the same text twice, once over the
  gdbstub and once on the serial port.
- **Negative:** `neg` (same binary, `--dbgmsg off`) must write 0 serial
  bytes (C-1281 reproduced). `dbgcmp`'s selftest has a negative case (one
  changed character is reported as a difference).
- **Unchanged guest:** the gdbstub text of `x` (option on) must equal the
  M8.B5 run `f-pos` (`qemu-system-sh4.b5b`, no option) line for line.

### Scope (counted corpus)

One kernel (EU2011 image B). Static: the sink (`0x880404f4`), its two

## Interpretation

- **FACT (C-6240):** in EU2011 `nk.exe` the debug sink `fn 0x880404f4`
  passes each string (`r5`, format `L"%s"` in `r4`) to AstLog `0x88044478`
  and, when both gate words `0x89e613b0` and `0x89e613b4` are 1, to
  `0x8804048c`, which opens the log handle `L"DebugLog"` (`0x88043e04`) and
  hands a record to `0x88044fe8`. Gate 1 is written from a caller's word by
  `fn 0x88049f4c` (OEM IOCTL table entry at `0x88009384`, next to code
  `0x01013210`); gate 2 is set to 1 by `fn 0x8804aa08` (caller
  `fn 0x88048f94`). No path from either gate loads a debug-SCIF address, so
  no boot argument or gate value can put the text on the UART (scope (a) and
  the gate form of (b) are closed). A guest patch would need two words (the
  call target and its delay-slot `mov r9,r4`, because the SCIF writer
  `0x8804cfa4` takes the string in `r4`), which the task's Stop rule rules
  out.
- **FACT (C-6241):** `ze0-0007` adds the machine option
  `-M ze0,dbgmsg=VA`: a translate-time hook at `VA` reads the UTF-16 string
  at `r4` (bank 1 when SR.MD and SR.RB) through `cpu_memory_rw_debug` and
  writes it as UTF-8 to serial port 0 (the debug SCIF's chardev), ending
  each unterminated message with `\n`. No guest byte changes. `run.sh`
  passes `dbgmsg=0x880404f4` by default on `-M ze0 --image` (`--dbgmsg off`
  disables it) and gains `--icount`.
- **FACT (C-6242):** on one boot with both the gdbstub reader and the
  hook, the serial log equals `ze0_dbgmsg.py run` for all 279 text lines
  (first 200: diff 0). The `run.sh --serial` boot (no gdbstub) is
  byte-repeatable and differs from the gdbstub boot in 2 of 279 lines (1 of
  the first 200), both values the guest derives from time (a tick count and
  a counter): the gdbstub's breakpoint steps shift where the icount timer
  deadlines fall. The same boot without the option writes 0 bytes (C-1281
  reproduced). Done-when met.
- **FACT (C-6243):** the hook does not change the guest: the gdbstub text
  with the option on equals M8.B5's `f-pos` (no option) line for line, and
  the boot still meets M8.B5 checks 1–3 (`filesys.exe` and `device.exe`
  started, 0 hits at `0x88011cb8`/`0x88022164`, no `Exception` line,
  `CurMSec` 837 340 ms).
- **OBSERVED:** `run.sh`'s default `-d int` log reaches 11.4 GB in a 150 s
  F1 boot; long L4 runs should pass `--log /dev/null` (or a smaller `-d`).
- **UNKNOWN:** which process issues IOCTL `0x01013210` (gate 1) in a
  normal boot, and what consumes the `DebugLog` handle. Not needed here.

## Conclusion

The EU2011 kernel's debug text now lands on the `-M ze0` debug serial port:
`run.sh --image … --icount shift=0,sleep=off` writes it to `WORK/serial.log`
(279 lines, 9 288 bytes for the F1 boot), with no gdbstub. The retail kernel
has no gate that routes this text to a UART (C-6240), so the route is an
emulator-side hook (`ze0-0007`, `dbgmsg=0x880404f4`), not a guest change.
`ze0_dbgmsg.py` stays as the cross-check and for RAM dumps. New claims
C-6240–C-6243 in `docs/research/claims.md`; `tools/qemu-ze0/README.md`
lists the patch.
