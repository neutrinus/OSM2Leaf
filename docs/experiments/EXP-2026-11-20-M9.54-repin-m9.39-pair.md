## Question

What do the M9.39 mutant `POINT010` pairs become when the committed command is run with the
M5.52 `--resize` (which also patches the field-5 length byte), does the firmware name accessor
read every record of the rebuilt pairs, and which citations of the old pins stay valid?

## Hypothesis

The pre-M5.52 tool still writes the M9.39 pins (US `ea2d0e0f…`, EU `e75c298f…`) and both of
them carry a stale field-5 length at record 500, so the accessor gives `mismatch=1 ok=999`
on **both** builds (M5.52 showed only the US one). The current tool writes different pairs
on which the accessor gives `ok=1000 of 1000` with the whole new name. The record walker
ignores field lengths, so its offsets on the rebuilt pairs equal the M9.39 table.

**Falsifier** (before the results): the pre-M5.52 tool does not reproduce the M9.39 pins on
this runtime (then the stale pair is not the one cited); the accessor on a rebuilt pair
prints anything but `ok=1000 of 1000` or a record-500 name other than the new name; the
walker offsets on a rebuilt pair differ from the M9.39 mutant row (then the M9.39/M9.42/M9.43
walker results do not transfer to the new pair).

## Interpretation

- **FACT:** the pre-M5.52 tool reproduces all four M9.39 pins, and **both** pairs (not only
  the US one of C-5264) carry a stale field-5 length at record 500: the firmware accessor reads
  the US name 17 words of 19 and the EU name 12 words of 14 (`mismatch=1 ok=999` on each
  build).
- **FACT:** the current CLI with the same arguments writes US `34fb3aab…`/`e525fd19…` and EU
  `979dff4a…`/`7ee2e542…`; its log reports the same record, size and `len2` change as the old
  tool plus the field-5 length byte (US `0xfe07` 17→19, EU `0xbe51` 12→14). A byte-level diff
  of the two decoded pages was not run (no committed tool prints one); the accessor rows are
  the observable. On both pairs the accessor of the pair's
  build returns the whole new name and the original address, `ok=1000 of 1000`, PASS.
- **FACT:** the walker offsets and the wrong-build verdicts on the rebuilt pairs are
  identical to the M9.39 / M9.42 / M9.43 results, as expected for code that reads `len2`
  framing and never the field lengths.
- **IMPLICATION:** every walker / container / wrong-build result that cites the stale pairs
  remains true and is reproduced on the new pairs; only the statements "the committed command
  reproduces `ea2d0e0f…`/`e75c298f…`" (C-4482/C-4483) are stale at `main` after M5.52, and
  the stale pairs are not a well-formed rename for any reader of the name field.
