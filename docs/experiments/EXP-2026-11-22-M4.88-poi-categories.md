## Question

Which POI category codes occur in the EU 2011 `POINT0nn` files, how many
records each has, which `BICON001` icon and which human-readable name can a
compiler attach to each code, and is that attachment stable enough to target?

## Hypothesis

The byte-aligned code that precedes the facility name in a `0x60` POINT record
is a stable category/brand key: its value is constant for one chain or generic
category across shards, and the verified `poi_icons.MAPPING` joins a known
subset of codes to one `BICON001` icon and one visible name. Grouping by high
byte (`0x01xx`, `0x03xx`, `0x0dxx`–`0x0exx`, C-982) supplies a default glyph for
the rest. **Falsifier (task):** the category field has no stable mapping to
icon/name — concretely, if two different codes share every sampled real-world
category (same dominant name *and* same icon and no disjoint brand set), or if
a verified code's records do not consistently carry its mapped name, or if an
unknown code is silently assigned an icon/name by the tool. A code whose
records span many brand names (e.g. a generic hotel category) is **not** a
falsification of the brand-level join; it is a result to report.

## Plan (written before coding)

- **Approach.** One new read-only tool, `tools/poi_categories.py`, with
  `--selftest`, `table ROOT`, `places ROOT` and `verify ROOT` subcommands.
  `ROOT` is either an extracted card tree or the full card image (FAT32 read
  in place). The tool walks all `REFER001/POINT0nn.DAT.cmp/.ind` pairs, finds
  inner zlib streams, splits each name page into `0x60` records, and uses
  `mutate_refer_poi.name_field` to locate the exact facility-name field. The
  two bytes before that field are the category code (C-981), the last two bytes
  of the record are the brand code, and `point_census.fine_position` gives the
  real position. Counts come from this walk, never from a hand transcription.
- **Format/signature source.** The field layout and record framing are the
  verified writer's inverse in `mutate_refer_poi.py` / `docs/format/refer.md`
  (C-5110–C-5117); the code-→-icon/name join is the verified 34-row
  `poi_icons.MAPPING` (C-983) and the `BICON001` table in `assets.md`; the group
  default is C-982/C-984 and is labelled a hypothesis in the output.
- **Files.** New `tools/poi_categories.py`, new `docs/format/poi-categories.md`
  (generated by the tool), this EXP, and claim rows C-7890–C-7899. No existing
  tool, no `selftest.py`, no vendor bytes in the repo.
- **Intended Done when.** `python3 tools/poi_categories.py --selftest` passes
  and `python3 tools/poi_categories.py table ROOT` regenerates
  `docs/format/poi-categories.md` with columns `code, count, icon, name,
  evidence`; EXP and claim rows quote the command output. The check must fail
  if a code is dropped, an icon is invented, or the place control finds fewer
  than ten coded categories at a known real place.

## Method

1. **Sample and hash.** Open the image above in place with
   `vcard_l3.open_source(image=…)`; read only `REFER001/POINT0nn.DAT.cmp/.ind`
   and `BICON001/BICON001.DAT`. Nothing is extracted to disk and no vendor byte
   is committed. The tool prints the SHA-256 of the samples it reads.
2. **Commands.** Runnable as written from the repo root (ROOT may be the image
   path or an extracted card tree):

   ```bash
   python3 tools/poi_categories.py --selftest
   python3 tools/poi_categories.py table archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --out docs/format/poi-categories.md --json scratch/m4.88/categories.json
   python3 tools/poi_categories.py places archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --lat 52.2297 --lon 21.0122 --radius-km 20 --min-codes 10
   python3 tools/poi_categories.py verify archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   python3 tools/ce_strfind.py archive/head256.img 'RESTAURANT' 'PARKING' 'PIZZA' --encoding all
   ```

   Record walk: inflate the outer 64 KiB chunks with `cmpind_codec.decode_blob`
   (`.ind` header: `u32 uncompressed, u32 compressed, u32 count, u32 chunk,
   u32 offsets[count]`); scan inner zlib streams with `poi_icons.iter_streams`;
   split `0x60`/`0x68` records with `poi_icons.iter_point_records`; locate field
   5 with `mutate_refer_poi.name_field`; take `rec[name_start-2:name_start]` as
   the category code and `rec[-2:]` as the brand. A record whose category is
   `0xffff` is "uncoded" and is counted separately, never treated as a code.
   Counts are per **record**; shard coverage is the number of distinct
   `POINT0nn` files containing at least one record of that code.
3. **Controls.** *Positive:* (a) `--selftest` builds a synthetic POINT page and
   a synthetic `BICON001` container with three known codes (`0x0190` fuel pump
   icon 0, `0x0dac` bed icon 21, `0x0dad` Best Western icon 22) and requires
   their counts, icons and names to be recovered exactly; (b) `places` must
   find at least 10 distinct coded categories with real records within 20 km
   of Warsaw centre, each printed with name, code and decoded coordinates.
   *Negative:* an unknown code (not in `MAPPING`, e.g. `0x1234`) must get an
   empty verified icon/name and only a group-hypothesis glyph; `--selftest`
   checks that a shuffled mapping and a displaced coordinate are rejected.
4. **Scope.** All 33 `POINT0nn` pairs of the EU 2011 card (66 files; 324,190,447
   compressed bytes before this task's measurement), all `0x60` name records
   with a field layout that `mutate_refer_poi.name_field` accepts, and all 103
   `BICON001` icon slots. Excluded: `0x68` twin records, uncoded (`0xffff`)
   records except for their count, bit-packed non-name pages, `REFER002` (a
   separate EV layer), other card editions and firmware code beyond the string
   search in Method 2. Names from the search menu were searched for in ROM A;
   if no code-to-string table is found, the `name` column is explicitly
   card-derived (dominant POI name) or the verified chain label — never a
   guessed firmware string.
5. **Falsifier.** As in Hypothesis, evaluated before the result: the tool must
   report `stable=no` if two distinct codes have the same icon and the same
   dominant name with no disjoint brand set, if a mapped code's records lack
   its label in the majority, or if an unmapped code receives a verified icon.
   A stable result requires the verified subset to be injective in
   (icon, name) and the Warsaw control to return ≥ 10 coded categories.

## Interpretation

- **FACT:** the census is reproducible: 33 shards, 531,199 coded records and
  276 codes in either byte-aligned role; counts, shard coverage and dominant
  names are published in `docs/format/poi-categories.md` and backed by
  `tools/poi_categories.py table ROOT`.
- **FACT:** the 34 verified code→icon/name rows are injective and stable on
  the real scan (0 collisions, 0 failures, 0 invented icons) and the
  synthetic selftest's positive and negative controls both pass.
- **OBSERVED:** the category field alone is **not** a one-to-one icon key:
  `0x0dac` spans 62 other codes and branded hotels use the brand field to
  select the logo (C-987). This is consistent with the task falsifier being
  answered at the (code, role) level, not refuted: a *single* code does not
  determine every icon, but the verified subset does determine one icon each.
- **HYPOTHESIS:** the high-byte grouping supplies a default glyph for the 242
  unverified codes (`0x01xx`→0, `0x03xx`→18, `0x0dxx`/`0x0exx`→21). The
  table marks each such icon with `?`; no firmware reader VA was located, so
  the table is not `CONFIRMED` under rule 13.
- **UNKNOWN:** which firmware table (if any) maps a category code to a
  search-menu string; `ce_strfind` found none in ROM A's readable strings, so
  unverified names remain card-derived `card:` hints. The 1,842,727 uncoded
  records are outside this table's scope.

## Conclusion

`tools/poi_categories.py` now generates `docs/format/poi-categories.md` from a
card image or tree, with the required code/count/icon/name/evidence columns,
339 lines and 276 codes. The verified 34-row subset has a stable, injective
icon/name mapping on EU 2011 and passes the synthetic and Warsaw place
controls; the other 242 rows carry a flagged group-glyph hypothesis and a
card-derived name hint. Observations are backed by C-7890–C-7899. The task's
`Done when` is met; no hardware, extra download or firmware reader was needed.
