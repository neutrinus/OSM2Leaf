# EXP-2026-11-19-M1.21: the compressed `FILESentry` payloads decode with the kernel routine

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** `archive/head256.img` (EU2011 head, 256 MiB, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`) and
  `archive/us256.img` (US2011 head, 256 MiB, SHA-256
  `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`)
- **Tools:** python3 3.13.18 (stdlib only); `tools/nk_decomp.py` (`files`,
  new), `tools/cehive.py` (new), `tools/cerom.py` (`scan`, `files`,
  `sections`), the PySh4 engine of `tools/l3_harness/` (unchanged)
- **Claims:** C-3520–C-3527
- **Supersedes:** none (EXP-2026-11-08-M1.4-filesentry-payloads stays: its
  negative was for the stdlib/`cecompress` codecs)

## Question

Does the kernel's own section decompressor (`DECOMP_SECT 0x88037464`, build
B `nk.exe`) decode the compressed ROM files (`FILESentry` rows with
`csize != rsize`) of builds A, B and C, and what do the registry hives say
about the SD card, the SD driver and the Navi launch?

## Hypothesis

The ROM image tool stores files with the same compressor as sections, so the
section call (`r4=src, r5=csize, r6=dest, r7=rsize`, frame `skip 0, step 1,
block 0x1000`) returns `r0 == rsize`. **Falsifier:** `r0 = -1` or
`r0 != rsize` for a file, or a decoded file with no recognisable type
(a shifted payload must fail, or `r0 == rsize` proves nothing).

| Kernel | build B `nk.exe` at `--image-start 0x3e00200`, entry `DECOMP_SECT 0x88037464` (EU2011 = US2011: bytes `0x3e00200..0x4800200` hash the same on both heads) |

## Method

1. **Sample and hash.** The two 256 MiB heads above. Decoded files go to
   `/home/user/scratch/m1.21/` (outside the repo, deleted after the run).
2. **Commands.**
   ```bash
   S=/home/user/scratch/m1.21
   python3 tools/nk_decomp.py --selftest
   python3 tools/cehive.py --selftest
   python3 tools/cerom.py archive/head256.img scan
   python3 tools/nk_decomp.py files archive/head256.img --image-start 0x200200
   python3 tools/nk_decomp.py files archive/head256.img --image-start 0x3e00200 -o $S/eu-B --json $S/eu-B.json
   python3 tools/nk_decomp.py files archive/head256.img --image-start 0x4800200 -o $S/eu-B2
   python3 tools/nk_decomp.py files archive/head256.img --image-start 0x5200200 -o $S/eu-C --json $S/eu-C.json
   python3 tools/nk_decomp.py files archive/us256.img --image-start 0x200200
   python3 tools/nk_decomp.py files archive/us256.img --image-start 0x3e00200 -o $S/us-B
   python3 tools/nk_decomp.py files archive/us256.img --image-start 0x5200200 -o $S/us-C
   python3 tools/nk_decomp.py files archive/head256.img --image-start 0x3e00200 --name boot.hv --src-skip 1
   python3 tools/nk_decomp.py files archive/head256.img --image-start 0x3e00200 --name ceconfig.h --src-skip 3
   python3 tools/cehive.py $S/eu-B/boot.hv --keys
   python3 tools/cehive.py $S/eu-B/default.hv --grep 'SDProfile|Drivers\\SD|Launch\\SD|AppLch|^init'
   python3 tools/cehive.py $S/eu-B/user.hv
   python3 tools/cehive.py $S/eu-C/default.hv --grep 'SDProfile|Drivers\\SD|Launch\\SD|AppLch|^init'
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img sections AppLaunch.dll
   ```
   The `AppLaunch.dll` strings below were located by a UTF-16 scan of its
   code section (file `0x04136200`, `psize 0x24c00`); the VAs are
   `realaddr 0x03bb1000` + offset.
3. **Controls.** *Positive*: the decoded files carry their expected types —
   `ceconfig.h` starts `#ifndef`, `celog.dll` starts `MZ`, the three hives
   carry the same 12-byte header (`00 04 00 00`, `EKIM` at +8) and parse to a
   closed key tree (0 dangling links). *Negative*: the same call with the
   payload shifted by 1 byte (`boot.hv`) and by 3 bytes (`ceconfig.h`) must
   fail; `cehive.py --selftest` breaks one value link and must count it.
4. **Scope.** Every `FILESentry` row of every segment of both heads (A 1, B
   11, C 10 rows per head; the copies `0x2000200`/`0x4800200` included for
   EU2011). Not covered: the content of the decoded text files (vendor
   data, not quoted), the format of `UpdateNK.skn`/`ReleaseMain.skn`,
   `wince.nls`, `OIDEFALT.img`.
5. **Falsifier.** Stated in the Hypothesis.

## Interpretation

- **FACT:** the kernel section routine with the section frame decodes all
  compressed ROM files: B 8/8 and C 7/7 on both heads, each `r0 == rsize`;
  no file-specific header or caller trace was needed (the `Hints`' second
  path was not taken). A 1-byte or 3-byte shifted payload fails, so `r0 ==
  rsize` is not trivially returned.
- **FACT:** at least one file per build with compressed files decodes to a
  recognisable type (B and C: `ceconfig.h` text, `celog.dll` MZ, three
  hives). Build A has no compressed file; its only file is stored.
- **FACT:** the CE hive cell layout in `cehive.py` closes on all six hives
  (0 dangling links, every key reached), so the key paths are a parse of the
  structure, not a string grep. **HYPOTHESIS:** the layout is the CE 6
  ROM-hive format; it is derived from these files only.
- **FACT:** the main SD slot is `SDHC.dll` port 0 → profile `SDProfile` →
  folder `SystemSD`; the second slot is port 1 → `SDProfile2` → `UserSD`.
- **FACT:** `Navi.exe` is not launched from the registry: `init` starts
  `device.exe`/`gwes.exe`, `device.exe` loads `AppLaunch.dll`
  (`Drivers\BuiltIn\AppLch`), and `AppLaunch.dll` carries `\windows\Navi.exe`
  and the `\SystemSD\VER_INFO\HDD_INFO.TXT` check as compiled-in strings.
- **UNKNOWN:** which `AppLaunch.dll` function reads the Navi table entry and
  in what order (outside this task; see the new task in `TODO.md`).

## Conclusion

M1.21's done-when holds: every `FILESentry` is listed with real size,
decoded length, SHA-256 and magic; B and C decode to recognisable types (A
has none compressed); and `docs/research/rom-registry.md` names the
`SystemSD`, SD-driver and launch keys. M1.4 returns to `open` (rule 15).
Claims C-3520–C-3527. No decoded byte is in the repository.
