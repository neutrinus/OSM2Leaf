# EXP-2026-11-22-M8.H28: `kepdrv.dll` dead-reckoning registers and sample

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** `archive/head256.img`, 268,435,456 B, SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Tools:** `python3 3.x` (stdlib only), repo tools `tools/cerom.py`, `tools/sh4dis.py` (LE, pinned), `tools/sh4xref.py` (pdata function starts), `tools/ce_strfind.py`, `tools/pdata.py`, `tools/kepdrv_scan.py` (committed here, `--selftest` 7/7)
- **Claims:** C-7250–C-7259
- **Supersedes:** none
- **Superseded by:** none

## Question

Which registers does the ZE0 head unit use for wheel-pulse capture and gyro
input, what is the sensor sample it hands to positioning, and where do the
units (pulses per metre, gyro scale) come from?

## Hypothesis

The two physical pages named in the task (`0xffc5a000`, `0xffc5b000`) are mapped
by both `kepdrv.dll` and `navdrv.dll` (kernel build B) and accessed through a
pointer table; `navdrv.dll` carries a named `gyroAdc_*` library that builds a
sample struct, so the units are named by getters rather than by literals.
**Falsifier:** no timer-capture code exists in the driver — then pulses arrive
over CAN and this page-mapping story is wrong (cross-check M8.H49). A second
falsifier: the register literals are absent from every uncompressed executable
section (all code is readable, C-2128), so a zero-hit scan would refute the
page claim rather than hide it.

## Method

1. **Sample and hash.** `archive/head256.img`, all 268,435,456 bytes, SHA-256
   as in the header. Only kernel build B is used; build A (`0x200200`) is the
   negative control. No card image, no hardware and no vendor dump were read.
2. **Commands.** Runnable from the worktree root, in this order:

   ```bash
   sha256sum archive/head256.img
   python3 tools/kepdrv_scan.py --selftest
   python3 tools/kepdrv_scan.py archive/head256.img
   python3 tools/kepdrv_scan.py archive/head256.img --json
   python3 tools/ce_strfind.py archive/head256.img --image-start 0x3e00200 \
       --module kepdrv.dll --encoding all KEPI
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img sections kepdrv.dll
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img sections navdrv.dll
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img imports kepdrv.dll
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img thunks kepdrv.dll
   python3 tools/sh4xref.py archive/head256.img kepdrv.dll --image-start 0x3e00200 --to 0xFFC5A000
   python3 tools/sh4xref.py archive/head256.img kepdrv.dll --image-start 0x3e00200 --to 0xFFC5B000
   python3 tools/sh4xref.py archive/head256.img navdrv.dll --image-start 0x3e00200 --to 0xFFC5A000
   python3 tools/sh4xref.py archive/head256.img navdrv.dll --image-start 0x3e00200 --to 0xFFC5B000
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll --image-start 0x3e00200 --va 0x03a1b244 --count 100
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll --image-start 0x3e00200 --va 0x03a1ad04 --count 130
   python3 tools/sh4dis.py archive/head256.img kepdrv.dll --image-start 0x3e00200 --va 0x03a19a9c --count 80
   python3 tools/sh4dis.py archive/head256.img navdrv.dll --image-start 0x3e00200 --va 0x039e59e4 --count 90
   python3 tools/sh4dis.py archive/head256.img navdrv.dll --image-start 0x3e00200 --va 0x039e734c --count 60
   python3 tools/sh4xref.py archive/head256.img kepdrv.dll --image-start 0x3e00200 --calls 0x03a1b244
   ```

   `tools/kepdrv_scan.py` is committed (not a heredoc) and auto-discovered by
   `tools/selftest.py`; its `--selftest` checks LE reads, pool search, literal
   loads, the `braf` opcode and the API-name extractor on synthetic bytes.
3. **Controls.** *Positive:* `ce_strfind … --image-start 0x3e00200 --module
   kepdrv.dll --encoding all KEPI` reports `hits 160` and prints `KEPI:TMuStcon…`;
   `sh4xref --to 0xFFC5A000` reports a literal at `0x03a1b4dc` loaded by fn
   `0x03a1b244`; the import table resolves CEDDK ordinal 8 to `MmMapIoSpace`.
   *Negative:* the same `ce_strfind` command **without** `--image-start`
   autodetects build A and reports `hits 0` — the strings exist only in build B;
   `sh4xref --to 0xFFC5A004` (a wrong base, +4) says `no literal pool holds`;
   `kepdrv_scan.py … --image-start 0x200200` exits with
   `kepdrv.dll is not in the ROM at image-start 0x200200`. A negative without
   these positives would not be a result.
4. **Scope.** Kernel build B of the head firmware: the two uncompressed
   executable sections `kepdrv.dll sec0` (`0x03a11000`, `vsize 0xab12`) and
   `navdrv.dll sec0` (`0x039e1000`, `vsize 0x6b02`) = 71,188 bytes of code.
   Compressed `.data` of both modules is excluded (it is BSS/import slots, not
   code; C-2128/C-3440). The `Navi.exe` consumer and all C/C++ run-time values
   are outside this scan; no section was assumed hidden.
5. **Falsifier.** If no code mapped or initialised a timer-capture page, or if
   no gyro/pulse API strings existed, the page/timer claim would be refuted;
   if the two literals were absent from the uncompressed code, the mapping
   claim would be refuted outright (it would not be an excuse about compression).

## Interpretation

- **FACT:** both modules map `0xffc5a000` and `0xffc5b000` as 4 KiB physical pages with `VirtualAlloc`/`VirtualCopy` (`0x204`); `kepdrv.dll` also maps `0xffd81000` with `MmMapIoSpace` and initialises four TMU register slots. All VAs above reproduce from the committed tool and the repo tools.
- **FACT:** the `0x0204`/`0x1388` halfwords in the mapping functions are a VirtualCopy flag and a 5000 ms wait, not timer reloads; the earlier scratch reading was wrong and is superseded here.
- **OBSERVED:** the `gyroAdc_*` API names and their function VAs; the 8-channel `braf` table; the sample field map; the illumination call. These are decoded from bytes, not executed.
- **HYPOTHESIS:** "100" in `Get100LatchData` names a 100 ms latch, and "500K" in `Get500Kfreq` names a 500 kHz reference; the names imply a sample rate but the live period was not run.
- **UNKNOWN:** pulses per metre, gyro scale (deg/s per count), the `Navi.exe` consumer of the sample struct, and the reverse-signal input. They are named by getters, not derived — per the task stop rule. The physical chip behind every register remains unseen.

## Conclusion

`docs/firmware/kepdrv.md` now carries the register table, the sample struct and
the unit sources with a VA for each, and
`docs/hardware/head-unit.md`'s dead-reckoning row points at those VAs while
keeping "firmware says so" separate from the unseen chip. Nine claims
C-7250–C-7259 are registered. The falsifier is refuted: timer-capture code
exists, so the CAN route (M8.H49) is not required for the pulse input. The
L3/L4 run of the sample builder and the runtime calibration constants remain
open.
