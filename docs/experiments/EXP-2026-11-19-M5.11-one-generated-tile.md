## Question

Can an OSM input be turned into a full card image that differs from the
accepted factory EU 2011 card in exactly one tile — with that tile's change
generated from OSM — and how does that image stand against every known
accept/reject gate of the unit (HDD_INFO fields, map-code comparator inputs,
`HDD_CHK.ATT` attestation, SD lock, plus the version block and tile reader)?

## Hypothesis

The pieces already merged compose: `one_tile_pipeline.py` (M5.29/M5.34)
splices the fixture's 3 ways into the level-1 directory `(76,940)` of
`B48R058R` (the directory M5.37 used), `imgpatch.py` (M5.13/M5.30) writes the
tile into its own cluster chain, and because the tile keeps its size every
other byte of the card — firmware, `0x06000000` HDD_INFO copy,
`VER_INFO/HDD_INFO.TXT`, DRSTR, MMAIN, FAT — stays factory. Every gate whose
card-side input is outside the tile therefore sees factory bytes.

**Falsifier:** any byte of `out.img` outside the tile's clusters differs from
the factory; `cardcheck --image` or `l2check` fails; the generated geometry
does not read back from the tile; the L3 map-code compare on `out.img`'s
`HDD_INFO.TXT` returns REJECT under the record that accepts the factory file;
or the card gains an `HDD_CHK.ATT` file.

   `out.img` as above (`sha256sum`).

2. **Commands.** From the repository root. `S` is scratch outside the repo.

```bash

  --parcel 76,940 --level 1 --osm tools/fixtures/m5.37-splice.osm \
  --out $S/tree --json $S/report.json                       # expect exit 0

  --cell B48R058R --class-table $S/rb/ctab.json --level 1    # negative: FAIL, exit 1
python3 tools/tile_diff.py $F/MAPAL001/B48R058R.DAT $S/tree/MAPAL001/B48R058R.DAT

# 3. the card: copy the factory image, patch the tile in place (same length)

python3 tools/imgpatch.py --image $S/out.img --file MAPAL001/B48R058R.DAT \
  --from $S/tree/MAPAL001/B48R058R.DAT --same-length --hash --json > $S/patch-tile.json

  --from $S/tree/MAPAL001/B48R058R.DAT

# 4. one variable: every diff byte classified from an independent BPB+FAT read
python3 tools/imgpatch.py --check-diff --image $S/out.img --reference $IMG \
  --file MAPAL001/B48R058R.DAT --strict-metadata --json > $S/checkdiff.json   # exit 0
python3 tools/imgpatch.py --check-diff --image $S/out.img --reference $IMG \
  --file DRSTR001.DAT --strict-metadata --json > $S/checkdiff-neg.json        # negative: exit 1
cmp -l $IMG $S/out.img | awk 'NR==1{f=$1} {n++; l=$1} END{print "bytes",n,"first",f-1,"last",l-1}'

# 5. L1 on the image, independent FAT read, L2 on the tree
python3 tools/cardcheck.py --image $S/out.img
7z t $S/out.img
7z l $S/out.img | grep -ci hdd_chk                          # attestation file: expect 0
python3 tools/l2check.py --root $S/tree --no-golden --tiles B48R058R.DAT \
  --semantic-tiles B48R058R.DAT --cmp-limit 20 --graph-tiles B48R058R.DAT \
  --graph-factory $F --json $S/l2check.json

# 6. HDD_INFO gate: the card's own file, through the firmware's compare (M9.6)
python3 tools/mapcode_l3.py extract $S/out.img -o $S/HDD_INFO.out.TXT
python3 tools/mapcode_l3.py extract $IMG -o $S/HDD_INFO.factory.TXT
cmp $S/HDD_INFO.out.TXT $S/HDD_INFO.factory.TXT
python3 tools/hddinfo.py parse $S/HDD_INFO.out.TXT
python3 tools/l3_harness/runner.py run applaunch_mapcode_compare --image $H \
  --input $S/HDD_INFO.out.TXT --unit-from $S/HDD_INFO.factory.TXT          # ACCEPT, exit 0
python3 tools/hddinfo_variants.py $S/HDD_INFO.out.TXT $S/variants
python3 tools/l3_harness/runner.py run applaunch_mapcode_compare --image $H \
  --input $S/variants/line1_lastchar.HDD_INFO.TXT --unit-from $S/HDD_INFO.factory.TXT \
  --expect REJECT                                                          # REJECT, exit 0
python3 tools/l3_harness/runner.py run applaunch_mapcode_compare --image $H \
  --input $S/HDD_INFO.out.TXT --unit-from $S/HDD_INFO.factory.TXT --expect REJECT   # exit 5

# 7. tile reader gate
python3 tools/l3_harness/runner.py run tile_reader --image $H \
  --input $S/tree/MAPAL001/B48R058R.DAT                                    # BLOCKED, exit 4
```

3. **Controls.**
   *Positive:* the fixture's 18 points read back from the generated tile
   (step 2); the factory `HDD_INFO.TXT` is ACCEPT in L3 (M9.6, C-5140), so the

## Interpretation

- **FACT (C-2330):** `out.img` differs from the factory EU 2011 card in
  42,542 bytes, all inside `MAPAL001/B48R058R.DAT`'s clusters (164 ranges,
  0 metadata, 0 outside; two independent reads agree: `check-diff` and
  `cmp -l`), and the tile's change is 6 section-1 level-1 records of one
  directory `(76,940)`, written from the OSM fixture.
- **FACT (C-2331):** `cardcheck --image` PASS, `7z t` OK, `l2check` PASS
  (incl. section 2 `preserved` 73,416/73,416), and the fixture's 18 points read
  back within 1 m (worst 0.0 m) from the generated tile but not from the
  factory tile.
- **FACT (C-2332):** the card's `HDD_INFO.TXT` is the factory file, and the
  EU2011 build-B compare `fn 0x03bd2ad8` returns ACCEPT for it in L3 under the
  declared unit record; a line-1 edit of the same file is REJECT.
- **FACT (C-2336):** of the 12 known gates, 7 are PASS (5 of them by byte
  identity with the accepted card), 2 not-applicable and 3
  cannot-verify-offline (MapDBVer range, SD lock, tile reader); the only gate
  whose card-side input changed and that the firmware could judge — the tile
  reader — has no runnable L3 target.
- **OBSERVED (C-2333):** the splice replaces, not adds: the 6 parcels held
  3,481 factory points and hold 18 after the write; each changed stream
  shrinks (to 148–212 B). In those parcels the generated tile shows only the
  fixture's 3 ways.
- **OBSERVED (C-2334):** `tile_diff.py` names directory x as `65452`
  (`0xFFAC`) where `tilewriter`/`one_tile_pipeline` name it `940`
  (`0xFFAC & 0x3FF`): a display difference in `tile_diff`, not a data
  difference.
- **OBSERVED (C-2335):** `one_tile_pipeline.py` labels this synthetic input
  `fixture: "real-osm"` — the label means "not `--synthetic`", not "real OSM
  data".
- **HYPOTHESIS:** a real EU 2011 unit returns `QSD-302-100` at `+0x60` and a
  MapDBVer range that contains 16 — true for the factory card if it boots,
  and `out.img` carries the same bytes. Not measured.
- **UNKNOWN:** whether `Navi.exe` reads the 6 rewritten records correctly
  (tile reader not located); the SD lock state (property of the physical
  card, set by the bench flow, `card-test-plan.md` P5).

## Conclusion

Done-when is met with one stated deviation: the OSM input is a committed
hand-written fixture located in Dolnośląskie, not a Geofabrik extract, because
the sandbox cannot reach OSM hosts (the same pipeline ran on the real
`dolnoslaskie-latest.osm.pbf` at level 2 in M5.44, off-sandbox). The
documented pipeline above produces `out.img` (`b88a31f4…f95fe3`) in which
exactly one tile carries OSM-generated content (one directory, 6 records) and
every other byte is factory; `cardcheck --image` and `l2check` pass; and the
gate table gives every known gate a verdict: PASS 7 (HDD_INFO fields, map-code
check 1 in L3 under the declared unit record, `0x06000000` copy, version block,
manifests, zlib, FAT), not-applicable 2 (SystemSD/UserSD runtime check,
`HDD_CHK.ATT`), cannot-verify-offline 3 (MapDBVer range, SD lock, tile reader).
Claim rows C-2330–C-2336 added; `reader-coverage.md` row 17 cites this
record. What stays open is the tile reader in L3 (M3.6/M9.13), the unit-side
values (L5), and the one-command wrapper with an evidence bundle (M5.35).
