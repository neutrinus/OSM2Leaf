## Question

Does the committed five-patch series, with the corrected `ze0` machine
patch, make `bash tools/qemu-ze0/build.sh --force` apply every patch, build
`qemu-system-sh4`, list `ze0` in `-M help`, and boot the EU 2011 kernel
image on `-M ze0`; and does that boot reproduce the `ce_qemu_probe.py`
access list?

## Hypothesis

EXP-2026-11-08-M8.A2 recorded two blockers on the earlier host: no QEMU
build deps and no prebuilt LE `qemu-system-sh4`. That host limitation is
gone here (`pkg-config --modversion glib-2.0 pixman-1` → `2.90.1` /
`0.46.2`). The machine patch, however, had two real bugs that only a run
could show: a second RAM block under the already-registered
`default_ram_id`, and `config ZE0` not selecting `UNIMP` for
`create_unimplemented_device()`. **Falsifier:** if a corrected patch still
fails to build, does not list `ze0`, or aborts at machine init, the machine
skeleton is wrong beyond those two lines.

For the access list, the old EXP already expected a difference ("the exact
access list will differ from the stock `-M none` probe because the machine
models CCN and boot-stub windows by design"). This record measures that
difference instead of asserting it.

### What `write 0x38` is

Ordered `-d cpu,guest_errors` trace, first occurrence:

```text
r0=0x00000000 … r2=0x00000000 … r4=0x00000000
pc=0x8802ec44 sr=0x70008001 pr=0x880443dc …
Invalid write at addr 0x38, size 4, region '(null)', reason: rejected
```

The `pc` of that state line is the PC of the store. In one 3 s trace every
`^pc=0x8802ec44` state line was followed by exactly one `0x38` reject and the
two counts were equal; `run.sh` logs one line per store for the whole run.
Both counts scale with run length and are not fixed (see Boot summary).

`sh4dis.py` at that address (LE, `--image-start 0x3e00200`):

```text
0x8802ec3c  e094  mov #-108,r0
0x8802ec3e  d202  mov.l @(0x8802ec48,pc),r2  ; [0x8802ec48]=0x89e41800
0x8802ec40  600c  extu.b r0,r0
0x8802ec42  022e  mov.l @(r0,r2),r2
0x8802ec44  000b  rts
0x8802ec46  124e  mov.l r4,@(56,r2)
```

A leaf getter/setter pair: `r0` is `#-108` (`0x94`) and `extu.b` makes it
`0x94`; `r2 = *(u32 *)(0x89e41800 + 0x94)`; `rts` with the delay slot
storing `r4` at `r2 + 56`. In this run `r4 = 0` and `r2 = 0`, so the store
went to physical `0x38` — a null-derived store, not a device access.
`0x38` is **not** a CAR `0b00xx`-mode window either: CAR's special mode is
entered by the *instruction at physical `0x38`* (`0x00000000 | 0b0011`), and
nothing executes there.

Why `r2 = 0`: the P1 address `0x89e41894` (= phys `0x09e41894`) is outside
both load extents (small: to `0x08090009`; `ce_qemu_probe.py`: to
`0x086e18a4`), so it is fresh RAM. `0x89e41800` is named by a literal in
nk.exe code (`0x8802ec48`) and by six nk.exe functions
(`sh4xref.py --to 0x89e41800`: `0x8804b6ac`, `0x8804b888`, `0x8804c4ac`,
`0x8804c868`, `0x8804ca10`, `0x8804cdf8`). Which piece of code should write
that slot is **not** established here: `cerom.py sections nk.exe` puts
`0x89e40000..0x89e8e000` in a section with `flags=0xc0000080`
(read/write/**uninitialized** — BSS), and `0x89e41800` → `va2file 0x05c41a00`
resolves through an overlapping section of another module, so "the loader
should have filled it" is a hypothesis, not a measurement.

### Is the run still progressing?

The `0x880443dc` cycle is a poll, not instrumentation: in one trace the
same iteration count appears on every PC of the chain `0x880443b8 →
0x880443ce → 0x880443d4 → 0x880443dc → 0x88044478 → 0x880444a0` and on the
code reached at `0x880440f4`, which returns `r0 = 0` each time (the `tst r0,r0` at `0x880443ce` takes the zero path).
Each pass calls `0x88045364` with the constant `0x1e7` and then reaches the
getter and its null store. The busiest PCs are ordinary kernel work
(`0x8802b2de: dt r9` fill loop, 8 562; `0x8802ae60: cmp/eq #37,r0` switch,
9 989; `0xa8010400`: the P2 alias of the `0x88010400` zero-fill). `-d exec`
logged no transition to `pc=0x0`, and the only `pc=0x00000000` tokens in the
`-d cpu` dump are `spc/ssr/gbr/vbr/dbr/delayed_pc/fpul` fields — an earlier
substring count of 315 356 was that mistake, corrected here.

`0x89e41800` is loaded as a literal by six `nk.exe` functions
(`sh4xref.py --to 0x89e41800`: `fn 0x8804b6ac`, `0x8804b888`, `0x8804c4ac`,
`0x8804c868`, `0x8804ca10`, `0x8804cdf8`) plus the pool at `0x8802ec48`
reached from its caller `pr=0x880443dc`; it looks like a per-thread or
per-context pointer slot whose target the small load never initialised.

### Is it the same fault as `-M none`?

No, and the two runs do not reach the same place. `-M none` reports the CCN
page `0xff000000`–`0xff00001c`; the sampled PC in one run was `0xa801045e`,
i.e. nk.exe VA `0x8801045e`, inside the `0x88010400` loop (`mov.l r4,@r2` +
`add #4`, with `r2` walking zero fill), not a CCN store. That PC is read by
HMP `info registers` when `run.sh` stops QEMU, so it is a sample: later
`-M none` runs stopped at `0x8804444c`, `0xa80103e0`, `0xa8010474` and others
(§Boot summary), and **`0xa801045e` did not reproduce**; only "the sample lands
in the zero-fill loop or nearby kernel work" is stable. On `-M ze0` every CCN
access in that page is absorbed by `sh4-ccn`, the invalid list collapses to
the single `0x38` store, and the CPU is still in kernel work at the sample.
So: `write 0x38` is a fault line `-M none` never reports (it is a *store*,
not an unmapped *device*), and the `-M none` `0xff000000` list is not "the
same fault deeper" — the machine removed it.

`-M none` on the `ce_qemu_probe.py` extents (`none-big`) is exactly the

`0xffc8003c`, `0xffe70858`, `0xffe70800/04`, `0xffe70808`. The probe

but the `run.sh` extents, shows only the 8 CCN entries: the extra 7 in
`none-big` are the CPG and `0xffe70000` windows, which that load never
reaches.

`ze0-big` reaches further than either `-M none` run and **faults**: the
first exception is `0x040 [tlb_miss]` at user VA `0x00005bd0`, right after
`ze0-area4` unimplemented writes at `0x10008000`/`0x10008004`, with
`vbr=0x8800ec10`. 30 exceptions follow (mostly `0x040`, PCs
`0x00000de4`, `0x03fafe68`, `0x03fb27d4`, `0x03fbcf54`, `0x8802a034`,
`0x8802a050`, …) and 14 invalid reads outside the modelled windows
(`0x00030029..2B`, `0x0000a000`, `0x00480000`, `0x00490000`). On `-M ze0`
the CCN is modelled, so the M8.A4 activation does not raise
`illegal_instruction`; the access to user VA `0x5bd0` raises the `0x100`
TLB-miss path instead. That is the same class of change EXP-2026-11-06-M8.A4
predicted ("`0x100` TLB-miss instead of `illegal_instruction`"), and it is
the **opposite** of an access-list reproduction.

`ze0-big` with a 30 s timeout produced the identical 6 accesses and 30
exceptions — it is not still progressing; it is stuck in the handler chain.

## Interpretation

- **VERIFIED (build/listing):** with the two fixes, the five-patch series
  applies with build.sh's `patch -p1` on pristine 8.2.7, builds
   `qemu-system-sh4` 8.2.7, and `-M help` lists `ze0`. This closes the half
  that EXP-2026-11-08-M8.A2 marked blocked.
- **VERIFIED (boot):** `-M ze0` on the `run.sh` (declared-length) load runs
  the full 10 s with 0 CPU exceptions; the invalid-access list collapses to
  the single `0x38` store. The trace shows no store to the `0xffe70808`
  poll in this run (`^pc=0x88048b6a` count 0) and no `pc=0x0` execution:
  the work is the `0x880443dc` poll (the code at `0x880440f4` returns 0)
  plus its `0x38` null store, and the RUN poll.
- **VERIFIED (negative controls):** each of the two bugs aborts `-M ze0`
  alone; removing either fix reproduces its abort message.
- **OBSERVED / HYPOTHESIS (0x38):** the store is the delay slot at
  `0x8802ec46`, `mov.l r4,@(56,r2)`, with `r2` read from `0x89e41800+0x94`
  and this run's `r2 = 0`, giving physical `0x38`. Measured: the slot's page
  is outside both load extents and zero; that some code should have written
  it is a **hypothesis** (`0x89e41800` is named by six nk.exe functions and
  lies in an `rw, uninitialized` section).
- **VERIFIED (not the -M none fault):** `-M none`'s list is the CCN page
  (`0xff000000`–`0xff00001c`) and its final PC `0xa801045e` is inside the
  `0x88010400` zero-fill loop, not a CCN store; `-M ze0` absorbs the CCN page
  and leaves only `0x38`, so the machine did not make the `-M none` fault
  deeper — it removed it.
- **VERIFIED (access list not reproduced):** `-M ze0` on the probe extents
  produces 6 accesses and 30 exceptions starting at `0x00005bd0`, which is
  not the probe's 15-access list on `-M none`. The 2 × 2 shows the list also
  depends on the loader's byte extent, not only on the machine.
- **VERIFIED (probe list is a `-M none` property):** the identical `-M none`
  probe extents give exactly the 15-entry `ce_qemu_probe.py` list in the
  same order, so the "reproduces the access list" clause is satisfiable only
  by a machine that does not model the CCN page — i.e. it contradicts the
  machine's purpose.
- **UNKNOWN:** what the `0x89e41894` slot is and who writes it (the
  `rw, uninitialized` section and six loaders point at a BSS/context
  pointer, but no writer was found in this run); whether loading more of
  the data image changes it (`ze0-big` faults earlier, at `0x5bd0`, so it
  does not); and what the `0x5bd0` TLB-miss handler needs.

Duplicate passes were run against every number in §Observations:

- **Patch application.** The first attempt reused a tree that an earlier
  loop had already patched; `git apply --check` then failed with "file

  after the other four.
- **`write 0x38` PC and follow-through.** `run.sh`'s log has no PC, the
  first trace attempt with `-d exec` fell outside the klog size limit, and
  this host has no `gdb-multiarch`; the PC comes from the ordered
  `-d cpu,guest_errors` dump and is cross-checked by (a) the
  `-d guest_errors,in_asm` block and (b) the exact `^pc=0x8802ec44` ↔
  `0x38`-reject equality in one trace. It
  was not taken from a breakpoint. Two later claims were **wrong and are
  corrected here**: (i) "reaches the `0xffe70808` poll and idles at
  `0x88022170`" — the anchored `^pc=` histogram shows neither PC executed in
  this run; (ii) "`-M none` ends on the CCN store with `r9=0xff00001c`" —
  the anchored disassembly shows `0x8801045e` is inside the `0x88010400`
  zero-fill loop. A substring `pc=0x...` count had also inflated the
  `pc=0x0` figure (315 356 matches were `spc/ssr/gbr/vbr` fields); all PC
  counts below use `^pc=`.
- **`0x38` source slot.** An earlier draft (and one "Corrections" line) said
  "`0x38` = A loaded segment" and that the page is `nk.exe` `ro data`.
  `cerom.py sections nk.exe` puts `0x89e40000..0x89e8e000` in
  `flags=0xc0000080` (rw, uninitialized), and `va2file 0x89e41800` →
  `0x05c41a00` resolves through another module's overlapping section; the
  corrected text states only what is measured (page outside both extents,
  zero, `r2 = 0`) and calls the writer a hypothesis.
- **Access-list comparison.** The probe and `run.sh` load different byte
  extents (7 215 268 + 24 456 328 B vs 589 833 + 53 512 B). The 2 × 2 was
  added so the machine effect and the extent effect are not confused; the
  earlier single-run comparison would have attributed the `0x5bd0` fault to
  the probe settings.
- **`0x38` interpretation.** An earlier draft called it a CAR
  `0b00xx`-mode access. That is wrong: CAR's special mode is entered by the
  instruction at physical `0x38`, not by a data store to it; the store is a
  plain null-derived `mov.l`. The source value is still only a hypothesis.
- **Sampled numbers (TL-ordered, second pass).** The driver's
  "Boot summary" block presented `final pc: 0x00000000`, `pr=0x8802abcc`,
  `delayed_pc=0x8802b3c0`, "last executed pc `0x8802b3c0`", 15 384 log lines
  and "2 854 passes", plus `final pc 0xa801045e` and 99 286 lines for
  `-M none`, as observations. **None of them reproduce.** The TL ran 3 × 10 s
  per machine: ze0 stopped at `0x8800ebd0` three times; `-M none` at
  `0x8800ebd0`, `0x8802b286`, `0x8800ebd0`. The navigator's wider set (6 ze0,
  10 none) never produced `0xa801045e` either. The cause is structural:
  `run.sh` samples HMP `info registers` from a wall-clock `sleep 1` poll
  (`run.sh:542-548`), so the PC is where the CPU happened to be; on a host
  where QEMU starts the guest more slowly the sample even lands on the
  pre-start PC `0x8800ebd0`. The record now states only the stable
  observables (0 exceptions; the access list) and carries a repeat-run table.
  The `0x38` attribution is unaffected and was re-verified 3828/3828,
  3644/3644, 3872/3872 in three traces: it does not depend on a sampled dump.
- **Oracle version.** `ce_qemu_probe.py` defaults to `--qemu
  qemu-system-sh4` from `PATH`, which on this host is 11.1.3 and yields **0
  accesses**; the 15-entry list reproduces only against the 8.2.7 pin. Every
  quote of it must pass `--qemu` explicitly (now done in C-4311 and the

- **"fn 0x880440f4".** It is not a `pdata` start in either build (`GAP(leaf)`
