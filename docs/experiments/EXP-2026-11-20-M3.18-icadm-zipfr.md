## Question

M3.23 (done) re-opened this task by rule 15: it gave the family no static root
of its own and named `0x003f1640` (ICADM name builder) as the root to rank
next. With the rebuilt call graph, does the `ICADM0nn` open/descriptor path
reach a function that consumes ICADM record fields (462-byte stride, 7×64-byte
slots, `u16` tag `0x00e7`, ISO-3166 numeric), and does `ZIPFR001.DAT` have a
reachable open path and a 14-byte record consumer (`char key[10] + u32 mask`)?

## Hypothesis

Both families are opened through the same name→id→read machinery as the other
`REFER001` files (M3.28), so their open path is graph-reachable even where the
literal-pool xref fails. A field-consuming reader, if static, is a function on
that subtree that walks the file's stride and reads a defining field.

**Falsifier (field reader found):** a reproducible NAVI.EXE function that,
given the file's buffer, iterates the 462-byte ICADM stride / tests `0x00e7`,
or advances 14 bytes per ZIPFR record while reading key/mask.

**Falsifier (negative complete):** no function on either family's located
open/descriptor subtree contains the family's stride or field constant, while
the positive controls (descriptor lookup, name loader, card read) reproduce.

## Method

1. **Precheck (rule 14).**
   ```bash
   python3 tools/reader_precheck.py archive/head256.img --image-start 0x200200 --module Navi.exe
   ```
   Expect `executable compressed 0 B` (C-2128), so a miss is a wrong
   signature, not hidden bytes.
2. **Rebuild the graph and re-run M3.23's rank.**
   ```bash
   S=~/projekty/leafre-work/scratch/m3.18; mkdir -p $S
   python3 tools/callgraph.py build archive/head256.img -o $S/g.json
   python3 tools/callgraph.py stats $S/g.json
   python3 tools/callgraph.py rank $S/g.json --depth 6 \
     --family ICADM=0x003f1640,0x003f2cc0 --family ICODE=0x003f2cc0 \
     --family REFER=0x003fbed8
   ```
3. **Name census and the literal-pool xref that C-2382 used.**
   ```bash
   python3 tools/name_loaders.py openers archive/head256.img --graph $S/g.json
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x00178e08
   ```
4. **Search the decoded sec1 for the name pointer (the compressed-`.data`
   path C-2382 excluded), and disassemble the loader.**
   ```bash
   python3 tools/nk_decomp.py section archive/head256.img --module Navi.exe --index 1 -o $S/sec1.bin
   # u32 LE scan of $S/sec1.bin for 0x00178e08, 0x00179f30, 0x00178c60
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x00564160
   python3 tools/sh4dis.py  archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f7d94 --count 120
   python3 tools/sh4dis.py  archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f7ae4 --count 80
   python3 tools/sh4dis.py  archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f7b20 --count 40
   ```
5. **Execute the descriptor lookup and the ZIPFR issuer.**
   ```bash
   for a in 4,0 4,1 16,0 16,1; do
     python3 tools/vcard_l3.py trace archive/head256.img \
       --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
       0x003f7ae4 --args $a --max-insns 400; done
   python3 tools/vcard_l3.py trace archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     0x003f7e74 --args 4,0 --max-insns 4000
   ```
6. **Read-completion handler table (where a record parser would live).**
   ```bash
   # table at 0x00178d60, 8-byte rows {u16 tag class, u16 0, u32 handler}
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f7f94 --count 100
   ```
7. **Run the access path on the card.**
   ```bash
   python3 tools/datask_l3.py mount archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --file REFER001/ICADM --max-reads 20000
   ```
8. **Validate every quoted VA is a function start (H52).**
   ```bash
   for va in 0x003f7ae4 0x003f7b20 0x003f7b54 0x003f7c38 0x003f7d94 \
             0x003f7e74 0x003f7f40 0x003f7f94 0x003f8030 0x003f1640 \
             0x003f2cc0 0x0040b358; do
     python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe $va; done
   ```
9. **Controls.**
   - *Positive (descriptor lookup):* `0x003f7ae4(4,0)` must return index 1
     (`COORD001`), `(16,0)` index 4 (`ZIPFR001`), `(16,1)` −1.
   - *Positive (name loader):* `name_loaders.py openers` must still show
     `0x003f1640` → `ICADM0` (C-2381).
   - *Positive (card read):* `datask_l3.py mount` must issue ICADM001 reads.
   - *Negative (field consumer):* no `add #14`/key read on the ZIPFR subtree;
     no 462/`0x00e7` on the ICADM subtree.
10. **Scope.** EU2011 build A `Navi.exe` only; `ZIPFR001`/`ICADM0nn` content
    only. US2011 and the map DLLs are not covered. No field decode is claimed.

### 2. Graph stats and rank (quoting `callgraph.py`)

```

unresolved indirect calls 204, functions with no static caller 696
```

`rank --depth 6` with `ICADM=0x003f1640,0x003f2cc0` returns the same ten
`ICODE` candidates (`0x00401e94`, `0x004082cc`, `0x00402690`, `0x003f6c88`,

`0x003f08cc`); `0x003f1640` adds **no** candidate of its own — it is a leaf

M3.23's finding that the family is a run-time value inside the shared opener.

### 3. `ZIPFR001.DAT` name **is** reachable — via a sec1 descriptor table

`name_loaders.py openers`:

```
0x003f1640  len 0x00cc  direct: .DAT ICADM0 REFER001
```

`sh4xref --to 0x00178e08` still prints `no literal pool holds ...`, and a u32
scan of the **decoded** sec1 finds exactly one pointer to the name:

```
ZIPFR001.DAT ptr in sec1: 1 ['0x5641c4']
ICADM001.DAT ptr in sec1: 0 []
ICADM0 ptr in sec1: 0 []
```

The pointer sits in a **24-byte descriptor table** at `0x00564160` (sec1):

| idx | VA | +0 style | +4 name | +8 id | +12 handler | +20 | name |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | `0x00564160` | 2 | `0x00178e28` | `0x0415` | 0 | 0 | INDEX001.DAT |
| 1 | `0x00564178` | 4 | `0x00178e18` | `0x042d` | 0 | 0 | COORD001.DAT |
| 2 | `0x00564190` | 2 | `0x00178e28` | `0x0415` | 0 | 1 | INDEX001.DAT |
| 3 | `0x005641a8` | 4 | `0x00178e18` | `0x042d` | 0 | 1 | COORD001.DAT |
| 4 | `0x005641c0` | **16** | `0x00178e08` | `0x040c` | 0 | 0 | **ZIPFR001.DAT** |

`0x00564160` is loaded by code (`sh4xref`): pool `0x003f7e08` load
`0x003f7daa` (`fn 0x003f7d94`) and pool `0x003f7b1c` load `0x003f7ae4` (leaf),
pools `0x003f7f8c`/`0x003f7b48` in `fn 0x003f7f40`/leaf `0x003f7b20`. The four
functions use two different addressings:

- `fn 0x003f7b20` takes `r4 = row index` directly: `entry = 0x00564160 +
  24*r4`, reads `+4` (name) and `+20` (directory selector), builds the
  directory string `0x00178e38 + 20*selector` and jumps through `0x0040b358`.
  So `r4 = 4` opens **row 4 = `ZIPFR001.DAT`**.
- `fn 0x003f7ae4` (leaf) matches a row by the `+0` style code and the `+20`
  selector and returns the row index; it is what a caller uses to get the
  index that `0x003f7b20` then consumes.
- `fn 0x003f7f40(code, selector, handler, extra)` uses `0x003f7ae4` to find
  the row, then **registers** the handler at `+12` and `extra` at `+16`. The
  `+12` handler is therefore empty in the static table and filled at run time.
- `fn 0x003f7d94` indexes the same table as `0x00564160 + 24*r9` and calls the
  `+12` handler.

### 4. Descriptor lookup, executed (`vcard_l3.py trace 0x003f7ae4`)

```
0x003f7ae4(2,0)  -> r0=0x0
0x003f7ae4(4,0)  -> r0=0x1
0x003f7ae4(4,1)  -> r0=0x3
0x003f7ae4(16,0) -> r0=0x4        <- style 16 = ZIPFR001.DAT (row 4)
0x003f7ae4(16,1) -> r0=0xffffffff <- no (16,1) row
```

The open path is row-index addressed. `fn 0x003f7b20(r4=4)` reads row 4
(`ZIPFR001.DAT`) and `fn 0x003f7e74(4,0)` on the card resolves it:

```
resolve REFER001   ZIPFR001.DAT   from 0x003f7c64 -> 0x000600c2
```

(`0x003f7c64` is inside `fn 0x003f7c38`, which calls `0x003f7b20`.) The
read-completion table at `0x00178d60` has **no** ZIPFR-specific class —
class `0x2000` → `0x003f7f94` is the generic **read-request issuer** (calls
`0x003f7c38` → `0x003f7b20`), not a record handler. `fn 0x003f7f40`'s two
static callers pass style code 2 (`0x003fec60`) and 4 (`0x00410914`), not 16,
so the ZIPFR handler registration is not statically tied to style 16 — it is
the open item below.

### 5. ICADM path (quoting `datask_l3.py mount --file REFER001/ICADM`)

```
tag 0x0d02  REFER001/ICADM001.DAT  pos 0x0     len 0x1000  handler 0x003f72cc
tag 0x0d00  REFER001/ICADM001.DAT  pos 0x4c00  len 0x200   handler 0x003f72cc
tag 0x0d01  REFER001/ICADM001.DAT  pos 0x8b00  len 0x1900  handler 0x003f72cc
```

Loaders named for these reads (`0x003eff20`, `0x003f17a4`, `0x003f2bc4`,
`0x003f0c7c`) call buffer helpers (`0x0040782c`, `0x00408268`, `0x003f6c3c`)
and the shared search packet; none contains `add #14`, the `0x00e7` tag, or a
462-byte stride. The first page is the `0x1000` search header; the data block
at `0x8b00` is a record blob (`u16 code, u16 len, u32 ffffffff, u8 0, text\0`)
— the writers' term records, but no discrete reader indexes them by a stride
constant in decodable code.

## Interpretation

- **FACT:** `ZIPFR001.DAT`'s name is **reachable**. It lives in a sec1
  descriptor table at `0x00564160` (row 4, `0x005641c0`), points at
  `0x00178e08`, and is loaded by `0x003f7d94`/`0x003f7f40`/`0x003f7b20`; the
  row is resolved on the card by `0x003f7e74` → `0x0040b358`. The row lookup
  `0x003f7ae4(16,0)` returns 4 on the real image. `C-2382` is **retracted**
  for its "no open anchor" half.
- **FACT:** The ZIPFR read is a **search request** (`0xff0a0001`/`00200000`
  packet via `0x0040b358`, M3.28's path; `sh4dis` shows
  `0x003f7b74 [0x003f7bf0]=0xff0a0001` and `0x003f7c5e [0x003f7d6c]=0xff0a0000`); the only completion handler that
  fires is the generic `0x003f7f94` issuer. No function on the subtree walks
  the 14-byte record.
- **OBSERVED:** The ICADM data block (`0x8b00`) is a term-record blob reached
  through `0x003eff20`/`0x003f17a4`/`0x003f2bc4`; no discrete reader indexes
  it by the 462-byte stride or the `0x00e7` tag in decodable code.
- **HYPOTHESIS:** The record consumer for both families is either (a) reached
  through a handler that is registered at run time inside the map-file task
  (`0x003ebfb4`) and not statically tied to a ZIPFR/ICADM tag, or (b) absent
  because the firmware only carries the search result to the caller. Neither
  is shown here.
- **UNKNOWN:** the field-consuming reader VAs for ICADM and ZIPFR.

## Conclusion

M3.18 (r3) meets the **open-path** half of its Goal: it names the descriptor
table `0x00564160`, the lookup `0x003f7ae4`, the issuers `0x003f7b54` /
`0x003f7c38`, the completion issuer `0x003f7f94`, and confirms both families
are openable by executing the lookup on the real image. It **does not** meet
the Done-when ("names the reader VAs and the fields each consumes, or shows
copy-only with a positive control"): no field-consuming reader VA is located
and no copy-only positive control is demonstrated. Per the task Stop rule and
rule 14, after this third signature family the status is **blocked**.

## Retraction

- **C-2382 RETRACTED.** It concluded `ZIPFR001.DAT` had "no decodable static
  open anchor". The name is in sec1 data (excluded by its executable-scope
  filter) and is loaded indirectly by `0x003f7d94`/`0x003f7f40` through the
  descriptor table `0x00564160`; `0x003f7ae4(16,0)=4`. Superseded by C-2386.
- **C-4677 RETRACTED.** Its "no `Navi.exe` function loads their name string
  and no table holds it" is false for both names it names: the same sec1
  descriptor table `0x00564160` holds `COORD001.DAT` (`0x00178e18`, rows 1/3)
  and `ZIPFR001.DAT` (`0x00178e08`, row 4), read by
  `0x003f7d94`/`0x003f7f40`/`0x003f7b20`. It was an executable-section census
  (M3.28), and the pointers are data. Superseded by C-2386.
