# EXP-2026-11-06-M5.13: In-place file patch inside a card image (`tools/imgpatch.py`)

- **Status:** done (tool verified synthetically; real-image S1/S2 build pending)
- **Date:** 2026-11-06
- **Sample:** no vendor image on this machine; the fixture is synthetic
  (`imgpatch.make_selftest_image`, 101,318,656 B sparse, SHA-256
  `f020fe6f3672aaa5c1fa539dee63b39e82050faf1ec033dc438a318f574b6f9a`)
- **Claims:** C-2020–C-2029 (text in "Claims proposed" below)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can one file be replaced inside an existing factory card image **without
re-laying out the FAT**, so that an S1/S2 test card differs from S0 only in
that file (plus its directory entry and, for a cluster-count change, the FAT
links and FSInfo counters), while the pre-partition area and the
post-partition tail stay byte-identical?

## Hypothesis

The factory image's directory entry for a file already points at an intact
cluster chain. Writing the new bytes into that chain and updating only the
entry's size (and the chain links when the cluster count changes) changes
nothing else, so a byte diff against the factory image lies entirely inside
the patched file's clusters and its 32-byte directory entry. `mkcard.py`'s
fresh build cannot do this: it re-populates the partition, re-orders the FAT
and drops the factory root volume-label entry (M5.12 warning, M5.12b).

## Observations

### Tool contract

`imgpatch.py --image IMG --file PATH/IN/CARD --from NEWFILE [-o OUT]` copies
`IMG` to `OUT` (or patches `IMG` in place when `-o` is omitted), resolves the
existing chain and writes. `--dry-run` prints the plan and writes nothing;
`--json` emits the plan, the write list, FAT/FSInfo/dir-entry changes and the
read-back verification. `--verify` reads the file back through
`cardcheck.Fat32Image` and compares size and SHA-256 (and the
`0x06000000` copy with `--update-version-copy`). Exit codes: 0 success,
1 verify mismatch, 2 usage error, 3 refused by a guard.

### Guarantees enforced in code

- Every write must fall inside the map partition or the 72-byte
  `0x06000000` window (`_check_envelope`); anything else aborts before the
  first write. Pre-partition bytes and the post-partition tail therefore
  cannot change.
- Mirrored FAT copies must already agree at every chain cluster, otherwise
  the tool refuses (`fat-mismatch`) instead of "fixing" one copy.
- Timestamps and LFN slots are never rewritten; only bytes 20–21, 26–27 and
  28–31 of the short entry (start cluster, size) can change.
- A cluster-count change updates **both** FATs and the FSInfo free count by
  the exact delta; freed clusters keep their old data bytes (only the link is
  cleared), and slack after a new EOF is zero-filled so the diff is
  deterministic.
- The replacement file is loaded into host memory; map files are a few MB.

## Interpretation

- **FACT:** `imgpatch.py` writes a replacement into the existing cluster
  chain and updated only the data bytes on a same-length patch: the synthetic
  12-byte file that differed in five bytes produced exactly one 5-byte diff
  range (`0x6029400`–`0x6029405`), with no FAT, FSInfo or directory-entry
  change.
- **FACT:** On a cluster-count change the chain was re-linked in both FAT
  copies (grow: `[6, 10]`, shrink: `[6]`, freed cluster 10 = 0 in both),
  FSInfo free count moved by exactly ±1, the directory size field followed,
  and the file read back through `cardcheck.Fat32Image` equalled the host
  file. Replacing `VER_INFO/HDD_INFO.TXT` with `--update-version-copy` wrote
  the same 72 bytes into the file cluster and at `0x06000000`, and both read
  back identically.
- **FACT:** Every diff range of every patched image lies inside the write
  set printed by the plan; refusals (size change, output == source, missing
  card path/host file, wrong `--update-version-copy` target or length) exit 3
  and leave the image hash unchanged.
- **OBSERVED:** `cardcheck.Fat32Image` accepts the synthetic fixture and all
  patched images, which is the same reader the L1 validator uses.
- **HYPOTHESIS:** Because the factory directory, root order, volume-label
  entry and file timestamps are untouched, an S1/S2 card built with this tool
  differs from S0 in exactly the replaced file(s) — the "one variable per
  card" requirement of `card-test-plan.md` — unlike the M5.12 fresh rebuild
  (200 diff ranges, `warn: no volume label`).
- **UNKNOWN:** unit acceptance (S1/S2) and the real-image diff ranges; no
  vendor image or hardware is available in this session. The exact S1/S2
  commands are in the follow-ups.

## Conclusion

`tools/imgpatch.py` provides the missing layout-preserving write path: a file
can be replaced inside a factory image in place, with the FAT, directory,
timestamps, volume-label entry and pre-partition/tail bytes preserved. It
does not remove the need for M5.12b (the compiler path still uses `mkcard.py`)
and it cannot be exercised on the real US image in this session; the exact
commands for S1/S2 are below, and C-2027 stays `UNKNOWN` until they run.
