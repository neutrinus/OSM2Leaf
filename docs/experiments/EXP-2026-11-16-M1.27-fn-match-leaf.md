# EXP-20261116-M1.27: `fn_match` leaf path for the POINT walker

- **Status:** done
- **Date:** 2026-11-16
- **Sample:** EU2011 `Navi.exe` head `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (256 MiB); US2011 `Navi.exe` head `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`
  (256 MiB), both image start `0x200200`
- **Tools:** `python3 3.15.0`; repo tools `tools/fn_match.py`, `tools/pdata.py`,
  `tools/sh4xref.py`, `tools/sh4dis.py`
- **Claims:** C-3700–C-3705 (C-3706–C-3709 reserved)
- **Supersedes:** none (updates the `0x003f5194` row of the M1.28 fixture, C-3740)
- **Superseded by:** none

## Question

Does `tools/fn_match.py` fail to match the POINT walker `0x003f5194` EU→US
because it cannot see a `.pdata` `GAP` (a leaf), and can a leaf path using the
call-site context separate that matcher weakness from a genuine code change?

## Hypothesis

The walker is a leaf with no `.pdata` record, so the record-hash path never
sees it.  A leaf path (bound the gap at its `rts`, hash the instruction
halfwords with the same reloc masking, then use the caller's `jsr` site to pick
the US candidate) will either give a `UNIQUE` hash match or a `DIFFERENT` with
a first differing instruction pair.  **Falsifier:** if `0x003f5194` has no
caller in the EU build or the caller itself has a different instruction
stream, the leaf path cannot produce a candidate and the answer is `LEAF`/`NOMATCH`.

## Method

1. **Sample and hash.** The two 256 MiB heads above; `Navi.exe` pdata section
   index 2 at image start `0x200200`.
2. **Commands.** Run as written from the repo root:

   ```bash
   python3 tools/pdata.py fn archive/head256.img --module Navi.exe 0x003f5194
   python3 tools/pdata.py gaps archive/head256.img --module Navi.exe | tail -1
   python3 tools/fn_match.py match archive/head256.img archive/head256.img \
       --module Navi.exe --va 0x003f5194
   python3 tools/sh4xref.py archive/head256.img Navi.exe --to 0x003f5194
   python3 tools/sh4xref.py archive/us256.img Navi.exe --to 0x0041db44
   python3 tools/fn_match.py match archive/head256.img archive/us256.img \
       --module Navi.exe --va 0x003f5194
   python3 tools/fn_match.py match archive/head256.img archive/us256.img \
       --module Navi.exe --leaf --va 0x003f5194
   python3 tools/fn_match.py --fixture tools/fixtures/fn_match_eu_us_2011.json \
       --us archive/us256.img --module Navi.exe
   python3 tools/fn_match.py --selftest
   python3 tools/selftest.py
   ```

   The pre-fix EU→US `NOMATCH` is reproduced by `git stash`-ing the tool change
   (or `git show 8098ee2:tools/fn_match.py`); the same command then prints
   `NOMATCH` for `0x003f5194` (see the M1.28 EXP-2026-11-15-M1.28-eu-us-fixture,
   which froze that verdict).

3. **Controls.**
   - *Positive:* EU-vs-EU on the same VA prints `UNIQUE` (the leaf is found at
     its own address), proving the classification/hash path works.
   - *Negative:* the pre-fix EU→US run on the same VA prints `NOMATCH` while
     the leaf bytes are present in the US build — the defect this task fixes.
   - *Negative (fixture):* shifting the leaf's `us_candidate` by 2
     (`0x0041db44→0x0041db46`), its `diff_offset` (`0x14→0x16`), or a pinned
     `us_va` (`0x00444540→0x00444542`) makes `--fixture` exit 1 with a
     `MISMATCH` line naming the row.
4. **Scope.** `Navi.exe` of the two 2011 builds only; the tool change is
   `tools/fn_match.py` (leaf path + `--leaf`) and one fixture row.  The full
   module census, the `build` field and `fn_audit.py` are excluded (M1.22b).
   Corpus: 7,596 EU records / 7,520 US records; `pdata.py gaps` reports 677
   gaps over 8 B in the EU module, 635 flagged `leaf`.
5. **Falsifier.** Stated in the Hypothesis.

- `fn_match.py --selftest`: 22 checks OK, exit 0. `tools/selftest.py`:

## Interpretation

- **FACT:** `0x003f5194` has no `.pdata` record (GAP) in the EU build and is
  called through pool `0x003f5d84` + `jsr` from `fn 0x003f5cdc`; the US build
  has a byte-identical leaf at `0x0041db44` called through the same-shape
  caller `fn 0x0041e63c`.
- **FACT:** The leaf's instruction halfwords are identical EU→US; the first
  differing unit is the `mov.w @(disp,PC),r4` at leaf `+0x14`, whose
  non-address pool constant is `0x04e8` (EU) vs `0x04d8` (US).
- **OBSERVED:** The masked whole-leaf digest therefore differs (the constant
  is kept on purpose, M1.22 algorithm), while the instruction-stream digest and
  the call site agree.
- **HYPOTHESIS:** `0x04e8`/`0x04d8` is a per-build record-length or offset
  constant, not a rewrite of the walk; this EXP does not decide which value
  the reader uses on each card.
- **UNKNOWN:** Whether any of the seven remaining `NOMATCH` readers is also a
  leaf or a genuine rewrite (M1.22b).

## Bounding rule (and its residual limit)

A `.pdata` `GAP` has no length, so the leaf window is clamped at
`min(gap_end, next pdata START, next called GAP entry, code-section end)` and
capped at `0x400` B (`leaf_window_limit`), then cut at its own `rts`.  A gap
that has no `rts` inside that bound (a thunk stub) keeps the bounded window but
is treated as an incomplete function: exact masked-hash match only, never
paired through the caller context, so it cannot produce a thunk-table pairing.
Example: EU `0x0032ef6c` (12 B stub, no `rts`, next `START 0x0032efa8`) reads
12 B and is `NOMATCH` EU→US (before this clamp it read 1024 B across
`0x0032efa8` and emitted a false `DIFFERENT → 0x0035da30`, an import-thunk
table).  Residual: a stub with no `rts` whose exact bytes are unique in both
builds would still report `UNIQUE` — that is a true byte match, not a bleed;
the 635-leaf census (M1.22b) must report how many leaves lack an `rts`.

## Conclusion

The record-hash path could never see the leaf; the leaf path now finds the US
candidate through the caller context and reports `DIFFERENT` with the first
differing instruction pair instead of `NOMATCH`.  The POINT walker is **not**
rewritten: the only difference is one non-address pool constant.  M1.22b gets
the `DIFFERENT` row (EU `0x003f5194` → US `0x0041db44`, first difference
`+0x14`, `0x04e8`→`0x04d8`) and does not need the "re-locate the US POINT
reader" branch.  `docs/format/firmware.md`'s EU→US table stays M1.22b's to
update.
