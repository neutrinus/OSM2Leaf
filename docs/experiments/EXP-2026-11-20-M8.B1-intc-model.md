# EXP-2026-11-20-M8.B1 — INTC/INT2 model: the kernel's TMU0 interrupt is delivered and acknowledged

- **Status:** done
- **Date:** 2026-11-20
- **Task:** TODO **M8.B1** (INTC model)
- **Sample:** EU 2011 image head `archive/head256.img`, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (image B at `0x3e00200`, image A at `0x200200`; `cerom.py romhdr`).
  Every VA below is **EU2011** `nk.exe`.
- **Tools:** QEMU **8.2.10** (`v8.2.10` git tag, build tree of
  EXP-2026-11-19-M8.A6, `ninja qemu-system-sh4 -j2`) with the seven
  `tools/qemu-ze0/patches/*.patch`; gcc 13.3.0; Python 3.13.18. Repo tools:
  `tools/ze0_intc.py` (new, `--selftest`), `tools/ze0_serial.py refs`,
  `tools/sh4dis.py`, `tools/sh4xref.py`, `tools/qemu-ze0/run.sh`.
- **Claims:** C-1310, C-1311, C-1312, C-1313
- **Supersedes:** none
- **Superseded by:** none

## Question

Can a `ze0` INTC model built from what `nk.exe` writes to `0xff802000…`
and `0xff804000…` deliver a TMU0 interrupt to the CPU, and does the
firmware's own ISR acknowledge it?

## Hypothesis

`nk.exe` programs an SH-4A-style two-block controller: an INTC block and an
INT2 block with a mask-set/mask-clear pair at `+0x40`/`+0x44` (the TODO
history's reading). TMU0 at `0xffd80000` uses the SH7750 register layout of
QEMU's `sh_timer`. **Falsifier:** if, with the model, the real kernel never
takes INTEVT `0x400`, or takes it but its ISR never runs or the line never
drops (interrupt storm), the source map or the priority mapping is wrong.


### Controls

- **Positive (synthetic):** shim with unmask + ack must take INTEVT `0x400`
  repeatedly at the TMU0 rate (TCOR0 `0x100000`, Pφ/4, 60 MHz →
  ≈14.3/s).
- **Negative 1:** `--no-unmask` must take none.
- **Negative 2:** `--no-ack` must stop after the line is never dropped.
- **Negative 3 (priority falsifier):** the first build mapped TMU0 to
  INT2PRI0 bits 28:24 (`0x08` → level 4, SH7785 layout); kept as
  `qemu-system-sh4.b1-shift24` and run with the same 60 s command.
- **Regression:** the declared-length boot keeps C-4311's observables.

### Scope

`nk.exe` EU2011 only, 1 executable section (313 344 B). Modelled sources:
TMU ch0–2 only. The 48 ISR-table INTEVTs other than `0x400`/`0x440` have no
source wired (masking works, nothing asserts). One 60 s run per binary.

### Falsifier

Stated in Hypothesis: no `0x400`, no ISR, or a storm.

## Observations

### Static

BSPIntrInit (`fn 0x8803dc70`, string `+BSPIntrInit` at `0x88005fe8`):

```text
0xff802044 INTMSK0  = 0xff000000      0xff802048 INTMSK1 = 0xff000000
0xff804040 INT2MSKR = 0xffffffff      (mask every INT2 source)
0xff802000 ICR0     = 0x00800000      0xff80201c ICR1    = 0x80000000
0xff802010 INTPRI   = 0xd0000000
0xff804000.. INT2PRI0..7 = 08020202 02020012 0000101c 00000800 16161600 141c1c00 1c1c1c1c 00141600
0xff804020 = 6, 0xff804024 = 0
loop over 0x88005bc8: {INTEVT, ISR, IntrPrio byte, SYSINTR}, 47 entries + terminator,
  HookInterrupt (0x88010504) -> InterruptTable 0x89e42040[(INTEVT-0x200)>>5]
  IntrPrio      -> 0x89e4280c[(INTEVT-0x200)>>5]
0xff802064 INTMSKCLR0 = 0x80000000
```

`ze0_serial.py refs` on `0xff804000+0x100`: 98 loads; registers `+0x00`
(4), `+0x04` (2), `+0x3c` (4), `+0x40` (42), `+0x44` (41), `+0x50`,
`+0x58`, `+0x80`, `+0x84`, `+0x88` (1 each), across the ISRs
`0x8803e594`…`0x8803fea0` and the BSPIntr\* functions. The hook
`fn 0x8803d168` has one call site, `0x88023036` in `fn 0x88023010`.

Timer hook `fn 0x8803d168`:

```text
jsr 0x8803d060                      (TMU setup)
INT2PRI0 (0xff804000) = 0x08020202
IntrPrio[16] = 1 ; InterruptTable[16] = 0x8803cb34      INTEVT 0x400
IntrPrio[18] = 1 ; InterruptTable[18] = 0x8803d260      INTEVT 0x440
INT2MSKCR (0xff804044) = 2                               unmask INT2 bit 1
IntrPrio[21] = 1 ; InterruptTable[21] = 0x88042f90      INTEVT 0x4a0
INT2PRI1 (0xff804004) = 0x02020012 ; INT2MSKCR = 4      unmask INT2 bit 2
```

TMU0 programming (unimp log of a 25 s full-extent run on the A6 binary,
PCs from `cpu_io_recompile`): `0x8803c9d0..0x8803ca1e` writes TSTR=0,
TCR0=`0x0021`, TCOR0=TCNT0=`0x7ffff5a8`, TSTR=1, TCR1 (`+0x1c`)=`0x0004`,
TCOR1/TCNT1=`0xffffffff`. The TMU base comes from a pointer
(`[0x89e6cacc]`, 22 loads in 9 functions), so nk holds only `0xffd80008`/
`0xffd8000c` as literals.

Interrupt entry `0x8800f210`: reads INTEVT `@(40,r7)` (r7 = `0xff000000`),
`r1 = InterruptTable[INTEVT>>5]`, `r3 = IntrPrio[(INTEVT>>5)-16]`, then
`0x8800f26e..0x8800f276`: `r2 = 0x40008000 | r3<<4; ldc r2,sr` (BL=0,
IMASK = IntrPrio) and `jsr @r1` at `0x8800f278`.

TMU0 ISR `fn 0x8803cb34`: reads TCR0 through `[0x89e6cacc]` and stores it
back with bit 8 (UNF) cleared (`0x8803cbac..0x8803cbb2`).

### Synthetic controls (`-M ze0`, 5 s each)

```text
irq         serial=70 x '4'  int log 0x400: 70
irq-noack   serial=1  x '4'  int log 0x400: 2
irq-nomask  serial=0         int log 0x400: 0
```

70 in 5 s ≈ 14/s, the programmed TMU0 rate. Without the ack the TMU line
never falls, so `sh_timer` raises no new edge: the CPU re-enters once
after `rte` and the guest then sees no further tick (2 entries, 1 char).

### Real kernel, 60 s

```text

  0x040 tlb_miss 26, 0x060 dtlb_miss_write 1, 0x180 illegal_instruction 3

  exception 0x400 [interrupt]  1
```

25 s traced run (level 1): `exception 0x400` 1; translated blocks cover

## Interpretation

- **FACT (C-1310):** the EU2011 OAL programs a two-block controller —
  INTC at `0xff802000` (ICR0, INTPRI, ICR1, INTMSK0/1, INTMSKCLR0) and INT2 at
  `0xff804000` (INT2PRI0..7, INT2MSKR `+0x40` = write-1-masks, INT2MSKCR
  `+0x44` = write-1-unmasks) — and dispatches through a 47-entry
  `{INTEVT, ISR, IntrPrio, SYSINTR}` table at `0x88005bc8` plus the timer
  hook, which places the TMU0 ISR `fn 0x8803cb34` at INTEVT `0x400` and
  unmasks INT2 bit 1.
- **FACT (C-1311):** with `ze0-0003` the real kernel takes INTEVT `0x400`
  from the TMU0 model, runs `fn 0x8803cb34`, and that ISR clears TCR0.UNF
  (TCR0 reads `0x0021` afterwards, no re-entry): delivered and
  acknowledged. The synthetic shim shows the same path at the timer rate
  (70/5 s) with both negative controls failing as predicted.
- **OBSERVED → derived (C-1312):** the source's level must equal the
  kernel's `IntrPrio` (1 for `0x400`), because the entry stub lowers IMASK
  to that value before `jsr`; INT2PRI0 bits 20:16 (`0x02` → 1) satisfy it,
  bits 28:24 (`0x08` → 4) give a 7.5 M-entry storm at `0x8800f278`. The
  field assignment for TMU1/TMU2 (12:8, 4:0) is the same inference,
  HYPOTHESIS until another source is exercised.
- **OBSERVED (C-1313):** TMU0 fired once in 60 s because the OAL reloads
  TCOR0 = `0x7ffff5a8` (≈ 572 s at the assumed 3.75 MHz count): the
  tick is not periodic on TMU0 — the kernel reprograms TCNT0 per
  reschedule. The peripheral clock (60 MHz here) is a HYPOTHESIS; M8.B2
  owns it and `CurMSec` (`0x89e41888`, read by `fn 0x8803cdd8` together with
  TCNT0/TCR0.UNF).
- **UNKNOWN:** the INTC block's run-time role (only BSPIntrInit writes it),
  and the INT2 status words `+0x50`/`+0x58` read by the `0x480`/`0x580` ISRs
  (plain read-back here).

## Conclusion

M8.B1's done-when is met on the real image: a TMU0 interrupt is delivered
(INTEVT `0x400`) to the firmware's ISR and acknowledged by it, with a
positive synthetic control, two negative ones, and a priority falsifier
that the first build actually hit. The kernel still parks at the same
place after 60 s (`pc` samples `0x88022170`); it does not get further
because of the model, which is M8.B2/B5 territory. New claims
C-1310–C-1313; `ze0-0003` also changes `hw/intc/sh_intc.c` so a level-
tracking source is compared with SR.IMASK (r2d's sources keep the old
rule).
