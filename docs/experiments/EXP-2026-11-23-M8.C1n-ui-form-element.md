## Question

On `-M ze0` with every control registered, why does the screen stay in
`INI_STARTUP`, which ScreenStateCC table entry governs the exit, and which
event/raiser drives it? (M8.C1l O6/O7 left this open.)

## Hypothesis

Hypothesis H1 from M8.C1l: the skin's start action (`SK_OTH_STARTUP`) reaches
ScreenStateCC, but the first-screen targets (InfoBar 46, UnitMainte 40,
EvNotice 41) have no windows, so the exit event is never raised. Falsifier
from the task: those three CCs create windows and the state still does not
change.

## Method

1. **Sample and hash.** `sha256sum archive/head256.img` printed the hash above.
   The 256-MiB head contains build A (`0x200200`) and B (`0x3e00200`).
2. **Commands** (run from the repo root; `S=~/projekty/leafre-work/scratch/m8.c1n`):

   ```bash
   sha256sum archive/head256.img
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img modules | grep -i screenstate
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img sections ScreenStateCC.dll
   python3 tools/nk_decomp.py section --image-start 0x200200 --module ScreenStateCC.dll --index 1 -o "$S/sscc_sec1.bin" archive/head256.img
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img extract ScreenStateCC.dll -o "$S/sscc_extract"
   # state-name table: sec1 + 0x3b8, 1-based index = state id; event-name table: sec1 + 0x970
   # state-class table scan: 16-byte records [u32 id, u32 ptrA, 0xffffffff, u32 ptrB] in code section
   python3 tools/ze0_ipl.py patch archive/head256.img --prefer-app auiapp.exe,auirtdll.dll --copy-dlls unitflash -o "$S/ipl_k.txt"
   python3 tools/ze0_aui.py archive/head256.img --no-aui-timeout --skip-module-wait audio.exe --object-store -o "$S/ipl_aui.txt"
   cat "$S/ipl_k.txt" "$S/ipl_aui.txt" > "$S/ipl_final.txt"
   python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$S/factory.qcow2"
   bash tools/qemu-ze0/run.sh --qemu "$HOME/.cache/qemu-ze0/build/qemu-system-sh4" --machine ze0 \
     --image archive/head256.img --sd "$S/factory.qcow2" --ipl-patch "$S/ipl_final.txt" \
     --verinf QSD-302-100 --mapdb 16-16 --dbgmsg 0x880404f4 \
     --icount shift=0,sleep=off --gdb=1240 --timeout 150 --workdir "$S/run_j16"
   grep -n -E "State\[|Handled at|Rejected \(Undefined\)|NOTIFY_TRANSITION" "$S/run_j16/serial.log"
   ```

   The table scans and the event-id name lookups were ad-hoc `python3 -c`
   scripts over the decompressed bytes (no committed tool); their raw outputs
   are quoted in Observations. A gdb probe (`tools/ze0_gdb.py` RSP client,
   breakpoint at `0x02b463ac` in a ScreenStateCC logger candidate) was also
   attempted in a second run (`$S/run_probe`); it recorded 0 hits in 110 s, so
   that address is **not** the generic `Handled at State` log path (that format
   string resolves to `0x03805de6` in `auirtdll.dll`, not to ScreenStateCC).
3. **Controls.** *Positive*: the J16 run reaches all the state-machine events
   C1l O6 saw (`SK_OTH_STARTUP`, `SS_FIRST_COMPLETESHOWSCREEN`, 11 distinct
   events `Handled at State[INI_STARTUP]`) — the emulator and patch chain work.
   *Negative*: C1l's J10 baseline (no `--object-store`) stops registration after
   ~52 DLLs and never runs ScreenStateCC's state machine (C-8323/C-8324), so a
   run that never reaches the state machine is the control that must fail;
   additionally, `grep -c 'State\[INI_STARTUP\]'` on a run without AuiApp would
   be 0. *Falsifier*: the three CCs create windows 40/41/46 and the state still
   does not leave `INI_STARTUP` — **not tested** (windows were not created).
4. **Scope.** One boot of EU2011 build A+B with the factory card under QEMU
   11.1.3, 150 s wall clock; static read of the uncompressed code section
   (2,067,456 B) and decompressed data sec1 (143,668 B) of ScreenStateCC.dll
   (4 sections, 1 compressed data sec1 + 1 compressed sec2 decoded). Excluded:
   the skin script grammar (undecoded, C1i O3), the `auirtdll` generic logger
   body (format strings in a compressed section, not resolved), micom/CAN peer
   frames (M8.H43–H45), and any L5 run.
5. **Falsifier before result.** A screenshot showing any AUI form element, or a

## Observations

**O1 — J16 reproduction (run `$S/run_j16`, `serial.log` 1,492 lines).**
`grep -n -E "State\[|Handled at|Rejected \(Undefined\)|NOTIFY_TRANSITION"`
printed 11 distinct events at `State[INI_STARTUP]` and no other state:
`NAVIGENERAL_CC_CAS_NAVIREG_CARSTOP`,
`SS_BACKWARDTOAV_BY_DEREGULATEOPERATION` (Rejected (Undefined)),
`NAVIGENERAL_CC_CAS_AVREG_CARSTART`, `SK_OTH_STARTUP`,
`ANTITHEFT_CC_FNR_SEQ_INVALID`, `ANTITHEFT_CC_FNR_SECURE_INVALID`,
`AV_SETTING_CC_CAS_MONITOR_OFF`, `SYSTEM_CC_ITR_DISCONNECT_SD2` (Rejected),
`NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END`, `SS_FIRST_COMPLETESHOWSCREEN`,
`NAVIMAP_CC_FNR_OWNMAPDRAW_END` (Rejected). `grep -o 'State\[[A-Z0-9_]*\]'
| sort | uniq -c` printed `11 State[INI_STARTUP]` — the state never changes.
This reproduces C1l O6 exactly.

**O2 — `SS_FIRST_COMPLETESHOWSCREEN` handler (log lines 1401–1417).**
On `SS_FIRST_COMPLETESHOWSCREEN` the state machine logs
`SetVariableValue [VAR_FIRST_COMPLETESHOWSCREEN_EXECUTED] = "true"` and then
`ExecuteFunction ctrl[44|46|40|41|1] function[NOTIFY_TRANSITION_FIRST_SCREEN]
param[0]`. For ctrl 44/46/40/41 the serial prints
`The CC Window is not exist. [id = …, handle = 0]` and
`SendNotifyMessage API failed [window=…][msg=6531][w=1007][l=0]`; only ctrl 1
(NaviEvCC) logs `rcv[NOTIFY_TRANSITION_FIRST_SCREEN]`. On
`NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END` it sets
`VAR_FIRSTMAP_DRAW_END = "true"`. Neither variable set changes the state.

**O3 — state/event name tables in decompressed sec1 (`sscc_sec1.bin`).**
`INI_STARTUP` string at code VA `0x2addb68`; its `u32` pointer occurs at sec1
offsets `0x710, 0x7bb8, 0xe7e0, 0x153c0, 0x1bfa0`. The alphabetically sorted
1-based index gives the state id: sec1+`0x3b8` index 214 → `INI_STARTUP` (id
215), index 608 → `SRT_COLD_ANTI_THEFT` (609), index 610 →
`SRT_COLD_I_AGREE` (611). These match the IDs quoted in
`docs/research/leafsdtools-companion-patches.md` (“INI_STARTUP (215)”,
“SRT_COLD_I_AGREE (611)”). The event-name table is sec1+`0x970` (1-based):
`NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END` 1593, `SK_OTH_STARTUP` 3215,
`SS_FIRST_COMPLETESHOWSCREEN` 4155, `SYSTEM_CC_ITR_DISCONNECT_SD2` 4758.
Section sizes: name-table run at `0x3b8` = 1,389 entries, at `0x970` =
5,514 entries (three and five copies respectively in sec1).

**O4 — state-class table (16-byte records in the code section).**
A scan for `[u32 id, u32 ptrA, 0xffffffff, u32 ptrB]` found a run starting at
VA `0x2b2c01c`: `id 1 → ptrA 0x2c634e6, ptrB 0x2c634f6`, …,
`id 215 (INI_STARTUP) → VA 0x2b2cd7c, ptrA 0x2c6696e, ptrB 0x2c6697e`,
then `ptrB` becomes `0xffffffff` at id 361 (`VA 0x2b2d69c`). `nk_decomp.py
pdata` says both pointers are INSIDE the function starting at `0x02c63464` (length `0x5704`). The
handler stub at `0x2c6696e` was disassembled: `jsr @r1; nop; mov r0,r3; …`,
with event compares at `0x2c6699c` (id 3752), `0x2c669d4` (2095),
`0x2c66a0e` (2737), `0x2c66a4c` (2744), `0x2c66aa8` (2736), `0x2c66ae0`
(3802), `0x2c66b18` (2741), `0x2c66b50` (3800) — none of these is one of the
11 events seen at `INI_STARTUP` in O1, so this table is **not** confirmed to
be the main state machine's per-state event table.

**O5 — a handler that does match the run.** `u16 1593` (OWNFIRSTMAPDRAW_END)
occurs in a literal pool at `0x2c1a7ba`, inside the function starting at `0x02c1a5b4`
(`nk_decomp.py pdata`: prologue 8 B, length `0x244`). The handler compares ids
2275, 2491, 2573 and 1593; on 1593 it calls `0x02c98e08` with
`r5 = 0x024c, r6 = 1`, matching the O2 log `VAR_FIRSTMAP_DRAW_END = "true"`.
`0x2c1a5b4` is slot 21 of vtable `0x2b18908` (found via a single code
reference at `0x2b1895c`), i.e. a state class's event-listener slot — but that
vtable handles only four of the eleven events, so its owning state is not
established.

**O6 — skin sequence.** `eu2011.skn` contains UTF-16 `STARTUP` at `0x1aa610`,
`SRT_COLD_ANTI_THEFT` at `0x1aa604/0x1768d4/0x1805d0` and `SK_OTH_STARTUP` at
`0x1aa920`; the byte context at `0x1aa604` reads `…STARTUP\0 …SRT_COLD_ANTI_THEFT\0`,
which is the cold-start screen sequence (next screen after `STARTUP`). The
script grammar that drives the transition is not decoded (C1i O3).

**O7 — no screenshot branch.** C1l O7 established that the composed screen in
J16 is the London map (plane 2 colour-key + Navi own-car mark, plane 1 off
screen at y=480); this run reached the identical state (`11 State[INI_STARTUP]`,
same event set), so branch 1 (AUI form element in a screenshot) is refuted
without a new PNG. No AUI form is drawn.

## Interpretation

- **FACT:** The J16 configuration reproduces C1l's baseline: the state machine
  runs, `SK_OTH_STARTUP` and `SS_FIRST_COMPLETESHOWSCREEN` fire, and the state
  stays `INI_STARTUP` (O1, O2).
- **FACT:** `INI_STARTUP` is state 215 in ScreenStateCC's 1,389-entry name
  table (O3), and its name-table pointer and a 16-byte state-class record were
  located (O3, O4).
- **OBSERVED:** `SS_FIRST_COMPLETESHOWSCREEN` broadcasts
  `NOTIFY_TRANSITION_FIRST_SCREEN` to five windows; four fail because no window
  exists (O2). This is consistent with, but does not prove, H1.
- **HYPOTHESIS:** The exit event is raised only after windows 40/41/46 respond
  to `NOTIFY_TRANSITION_FIRST_SCREEN` (or by a vehicle signal over micom/CAN),
  so it is absent on the emulator; the skin sequence then advances
  `INI_STARTUP → SRT_COLD_ANTI_THEFT` (O6).
- **UNKNOWN:** The exact event ID and raiser of the `INI_STARTUP` exit, and the
  canonical per-state transition table row, are **not established** by O1–O7.
  The 360-entry table (O4) and the vtable-21 handler (O5) each explain only
  part of the event set; neither was tied to state 215 by a checked command.
  The generic `Handled at State` logger lives in `auirtdll.dll`, whose format
  strings are in a compressed section that was not decoded here.

## Conclusion

Branch 1 of the Done-when is refuted (no AUI form; state remains
`INI_STARTUP`). Branch 2 is **not** met: I located the state name tables, the
`INI_STARTUP` id (215) and candidate state-class/table records, but I could not
name the event that leaves `INI_STARTUP` together with its ScreenStateCC table
entry and the code that raises it, with a runnable command behind each number.
Per rule 16 the task is `blocked`, not `done`. No `docs/format/` file changes;
claim rows C-8340–C-8349 record the established facts (C-8340–C-8344) and the
open question (C-8345–C-8349). Follow-up: port M8.C1p's consent-state method to
map the cold-start transition table for `INI_STARTUP`, or, if the raiser is a
micom/CAN vehicle signal, supply the frame via M8.H43–M8.H45.
