# EXP-2026-11-19-M3.27-tile-reader-args: the three M3.5 tile-reader entries, statically

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** `archive/head256.img` (IMG256, EU 2011 build A, `Navi.exe`), SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Tools:** `python3 3.15.0` / zlib 1.3.1.zlib-ng; repo tools `tools/nk_decomp.py`, `tools/pdata.py`, `tools/sh4xref.py`, `tools/callgraph.py`, `tools/sh4dis.py`, `tools/fn_audit.py`, `tools/cerom.py`
- **Claims:** C-4580–C-4589
- **Supersedes:** none (corrects the third M3.5 VA, C-864, in passing)
- **Superseded by:** none

## Question

For each of the three M3.5 reader VAs (`0x0041f26c`, `0x004259bc`, `0x0042757a`),
what is the real `.pdata` entry, which registers r4..r7 carry an argument and
what does each carry, what does the function return, and is the third VA a
thunk or a mis-addressed entry of one of the others?

## Hypothesis

`none / exploratory` for the register meanings. One structural expectation is
testable: M1.26 and the M3.27 precheck note say the third M3.5 VA may sit
inside a function, i.e. `0x0042757a` is not an entry.

**Falsifier (written before the run):** a register is named from one caller
while another caller of the same entry loads a different base into it, and the
table does not record both readings; **or** an entry takes the tile buffer in
r4..r7 directly from the caller (then the `(tile, dst)` prototype M9.13 plans
would be right after all). Secondary falsifier: `.pdata` says `START` for
`0x0042757a`.

## Method

1. **Sample and hash.** As above; build A only (`--image-start 0x200200`),
   `Navi.exe` only. No US/EU2014/EU2016 build is touched.

2. **Commands.** Runnable as written, from the repository root:

   ```bash
   # every VA below goes through pdata first (START/INSIDE/GAP)
   for va in 0x0041f26c 0x004259bc 0x0042757a 0x00427578 0x0042c4b0; do
     python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe $va
   done
   # the single static call site of each entry (literal-pool xref)
   for va in 0x0041f26c 0x004259bc 0x00427578; do
     python3 tools/sh4xref.py archive/head256.img Navi.exe --to $va
   done
   # who calls the callers, and what each entry calls back
   python3 tools/callgraph.py build archive/head256.img --module Navi.exe -o ~/projekty/leafre-work/scratch/m3.27/g.json
   for va in 0x0041f26c 0x004259bc 0x00427578; do
     python3 tools/callgraph.py callers ~/projekty/leafre-work/scratch/m3.27/g.json $va
   done
   for va in 0x0041f26c 0x004259bc 0x00427578 0x0041e5e4 0x0041e64c 0x0041e6d0; do
     python3 tools/callgraph.py callees ~/projekty/leafre-work/scratch/m3.27/g.json $va
   done
   # the call sites and the prologues (LE decoding is pinned inside the tool)
   python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x00421690 --count 12
   python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x00426500 --count 8
   python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x00427d34 --count 16
   python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x0041f26c --count 184
   python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x004259bc --count 126
   python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x00427578 --count 380
   # EDGES: callgraph drops `bsr` targets past the last function record as leaf
   # targets; sh4xref --calls decodes them.  This is the list that shows the
   # literal-pool call to 0x0041f26c that callgraph's callees omits:
   python3 tools/sh4xref.py archive/head256.img Navi.exe --calls 0x0041e5e4
   python3 tools/sh4xref.py archive/head256.img Navi.exe --calls 0x0041e64c
   python3 tools/sh4xref.py archive/head256.img Navi.exe --calls 0x0041e6d0
   # what the `bsr` immediates actually decode to (same text section, LE)
   python3 - <<'PY'
   import sys, struct
   sys.path.insert(0, 'tools')
   import cerom
   data = open('archive/head256.img', 'rb').read()
   rom = cerom.CERom(data, 0x200200)
   text = next(s for s in rom.o32(rom.module('Navi.exe')) if s['flags'] & 0x20000000)
   off = rom.va2file(text['dataptr']); code = data[off:off + text['psize']]; base = text['realaddr']
   def sx(v, b): return v - (1 << b) if v & (1 << (b - 1)) else v
   for s, n in ((0x0041e5e4, 0x68), (0x0041e64c, 0x84), (0x0041e6d0, 0xd8)):
       end, pc = s + n, s
       while pc + 1 < end:
           i = struct.unpack_from('<H', code, pc - base)[0]
           if i >> 12 == 0xB:
               print(hex(s), 'bsr.jsr-slot', hex(pc), '->', hex((pc + 4 + sx(i & 0xFFF, 12) * 2) & 0xFFFFFFFF))
           pc += 2
   PY
   ```

   The `bsr` block prints `-> 0x0041f242`, `-> 0x0041f2f8`, `-> 0x0041f640`, …,
   i.e. **literal-pool words**, not call targets: `0x0041e644` holds
   `0x0032ef78` and `0x0041e648` holds `0x0017b658`, so `bsr 0x0041f242` is the
   tool reading the pool. `0x0032ef78` is an import thunk (`mov.l @(0x0032ef80),r0;
   mov.l @r0,r0; jmp @r0`, slot `0x0055d004` = `COREDLL!NKDbgPrintfW`), and the
   caller then `jsr`-s it. These are **not** reads of `0x0041f26c`.

3. **Controls.** *Positive:* `sh4xref.py --to 0x00425f40` must find the
   `MAP_DATA READ` consumer of M3.6 (C-870), and it prints two pools
   (`0x00426d6c` → load `0x00426d4a`, `0x0042786c` → load `0x0042781e` in
   `0x00427578`), so the xref method does find a real reader. The same run
   for each of the three entries prints exactly one pool. *Negative:* the
   exact M3.5 string `--to 0x0042757a` prints `no literal pool holds
   0x0042757a in executable sections`, so it is not a call target and the
   "third reader entry" spelling is a 2-byte offset, not a function.
   *Negative (register):* `mov #11,r7` at `0x0041f320` inside `0x0041f26c`,
   `extu.w r0,r6` at `0x00425a40` inside `0x004259bc`, `mov r14,r7` at
   `0x004275fe` and `mov.l @r10,r5` at `0x0042762e` inside `0x00427578` are
   register **writes before any read**: a register written before its first
   read cannot be an input argument.

4. **Scope.** Build A (`EU2011`) `Navi.exe` `.text` only, the three M3.5
   entries and the call-graph nodes on their static caller chains
   (`0x0041f26c` ← `0x00421548` ← `0x004216dc` ← `0x0032efa8`;
   `0x004259bc` ← `0x0042613c` ← `0x00427144` ← `0x00427a34`;
   `0x00427578` ← `0x00427c4c` ← `0x00427cd4` ← `0x00428200`/`0x00428290`).
   Excluded: US/EU2014/EU2016 builds, anything reached through `jsr @Rn`
   without a same-function literal load (indirect call tables), and the
   meaning of the imports the entries call. `0x0042c4b0` — the VA the task block
   prints in its Precheck as an example — is `INSIDE` `0x0042c39c` and has no
   literal-pool xref; it is not a reader entry and is not part of this scope.

5. **Falsifier.** As in Hypothesis. Note that the "caller loads a different
   base" half is only checkable for entries with more than one static caller;
   for all three final entries (`0x0041f26c`, `0x004259bc`, `0x00427578`) there
   is exactly one, so the falsifier collapses to the tile-buffer half and to
   the earlier `0x0041e5e4`/`0x0041e64c`/`0x0041e6d0` reading, which is
   recorded below rather than dropped.

## Interpretation

- **FACT:** `0x0041f26c` and `0x004259bc` are `.pdata` `START`s of `0x170` and
  `0xfc` bytes; `0x0042757a` is `INSIDE` `0x00427578`, i.e. the M3.5 third VA
  is two bytes into a `0x2f8`-byte function and is **not** an entry (C-864 is
  corrected in passing).
- **FACT:** each of the three real entries has exactly **one** static literal-
  pool call site, and no pool in the executable sections holds `0x0042757a`.
- **FACT:** `0x0041f26c`, `0x004259bc`, `0x00427578` are three separate bodies
  (different lengths, each ends in its own `rts`), not thunks of one function.
- **OBSERVED:** the argument registers, from the single call site each (table in
  `docs/format/map-tiles.md`): VA1 `r4` record pointer, `r5` 4-entry `u32`
  array, `r6` flag/mode of unknown meaning, `r7` not an argument; VA2 `r4` mesh
  id (20-byte-table index), `r5` record/output pointer, `r6` not an argument,
  `r7` control flag; VA3 `r4` 20-byte record pointer, `r5`/`r6`/`r7` not
  arguments.
- **OBSERVED:** none of the three sets a return value: no `r0` write on any
  exit path; `r2` is spilled but the sole callers do not read it.
- **HYPOTHESIS:** `r4` of VA1 and VA3 and `r5` of VA2 are pointers into the
  already-loaded cell table, not into the tile file: the callers build a
  20-byte descriptor on the stack and the entries index BSS tables
  (`0x00e99698`, `0x00e8f5dc`) with the mesh id. Consistent with H101's
  memory-mapped tile, but the mapping call itself is not on these paths.
- **UNKNOWN:** what VA1's `r6` and VA2's `r7` mean; what `OSMDLL!#55` does;
  whether any indirect caller (none static) passes other bases.
- **CORRECTION of the earlier H101-style caller list:** `0x0041e5e4`,
  `0x0041e64c`, `0x0041e6d0` are **not** callers of `0x0041f26c`; they are a
  sibling map-maker family (`0x0041e7a8` dispatches on a subtype). The
  `callgraph.py callees` row that lists `0x0041f26c` for them is the tool's
  in-function `bsr`-immediate heuristic mis-reading a literal-pool word, the
  same class as `0x0040f0` in the M3.26 record; `sh4xref` and the `bsr` decode
  agree with each other and against `callgraph`.

## Conclusion

`docs/format/map-tiles.md` now carries the entry table (VA, build, `pdata`
length, r4..r7 with the evidence for each, return register, sole call site) and
the caller chain. The M3.5 claim C-864 is corrected in passing: the third
reader is `0x00427578`, not `0x0042757a`. For M3.25/M9.13 the practical result
is negative: **no M3.5 entry accepts the tile bytes**; the nearest runnable
consumer is `0x00425f40` (`MAP_DATA READ`, M3.6), reached from `0x00427578` with
a 20-byte record, so an L3 target built as `(tile_ptr, dst_ptr)` on any of the
three entries would test a prototype the code does not have. The remaining
unknowns (VA1 `r6`, VA2 `r7`, `OSMDLL!#55`) do not block that conclusion, and
the register that could not be resolved is recorded with both of its readings
rather than picked.

## Follow-ups

- **M3.25/M9.13:** the prototype question is settled to "record pointer, not
  tile pointer"; the runnable target should be `0x00425f40` fed from
  `0x00427578`, or the mapping call that fills `0x00e99698`/`0x00e8f5dc`.
- **Tool defect (callgraph in-function `bsr` immediates):** `callgraph.py`
  reports literal-pool words as `bsr` targets inside `0x0041e5e4`/`0x0041e64c`/
  `0x0041e6d0` (and made them look like callers of `0x0041f26c` via the
  leaf-owner fold). It cost this task one wrong first reading; a `--selftest`
  case with a `jsr @r3` whose `r3` was never loaded would pin it. Not fixed
  here (no tool changes in this task's scope).
