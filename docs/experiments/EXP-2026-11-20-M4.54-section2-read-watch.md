## Question

For one real factory level-1 section-2 block, which tile bytes does the router's consumer `0x00422eac` read (the four watched words `k+15`, `k+7`, `k+6 = d`, `k+d`), what does `k` index, and does a section-1 block read at the same `k` fail the `0x0900` gate?

## Hypothesis

M4.40 (C-5648) showed the consumer copies the reply into a slot buffer and then reads four `u16` words off `k`, which comes from a `0x00424464(19, …)` table. If the buffer really holds a part-a section-2 record, the gate word `k+15` should be a class word (top nibble bits `0x0900`) of a link entry, `k` should be a part-a node header, and `d` should index a second entry — so `k+d` reads a field in the same record. The section-1 block, read at the same `k`, must not satisfy `& 0x0f00 == 0x0900`.

**Falsifier (stated before the result):** with a real factory section-2 block in the buffer, `0x00422eac` never clears the `0x0900` test, or one of the four watched reads lands outside the copied block, or the run's `k` cannot be tied to any part-a structure.

3. **Controls.**

### Declared stubs and models (not parsing)

The tool models the task's memory manager calls, it does not run them. Every hook is logged by name and its call count is reported:

| VA / slot | Real role | Model |
| --- | --- | --- |
| `0x003edf5c` | data-access size query | returns the block length; the store copies exactly that many bytes (logged) |
| `0x003d13e8` | `memcpy` thunk | copies `r6` bytes `r5`→`r4` (logged, 3508 / 328 B) |
| `0x003ed9ac` | task lock | returns 0 (counted; 1 call) |
| `OSM_Sleep` `*0x0055d8b4` | import slot | points at a two-instruction `rts; nop` stub in a host page |
| `0x00424464` | source of `k` (**table UNKNOWN**, M4.40) | writes a declared `u16` table at a host VA (`t[0]=0x100`, `t[1]=0x1000`, `t[3]=k`) and `DIVID` into the caller frame; one run per declared `k` |
| `0x00ec3954` / `0x00e99698` / `0x00e92958` | BSS boot globals | placed by the tool (slot table, group state, the 8-entry "requested" copy that `0x004268c0` fills) |

`k` is therefore a **declared input** to this run: the tool tries the block's own passing `k` first and reports it; it does not derive `k` from `0x00424464`.

## Interpretation

- **FACT:** the reply/store path is a pass-through: `0x004268c0` copies exactly the block's plain length (3508 B / 328 B for section 2, 2424 B even for a section-1 block) from the reply pointer into the slot buffer and sets the state to 2; it does not inspect the bytes (C-5710).
- **FACT:** with a real section-2 block in the buffer, `0x00422eac` clears its gate and reads exactly four >=2-byte words — `k+15`, `k+7`, `k+6` and `k+d` — all inside the copied bytes; the section-1 block and a declared `k=0` stop at `k+15` (C-5711, C-5712).
- **FACT:** for the driven block `k=221` is part-a **node 7's header word 0** (`x = 0x4fd`, count = 3); `k+15` = node 7 entry 1 `cls` (`0x919`), `k+7` = entry 0 `cls` (`0x717`), `k+6` = `d` = entry 0 `id` (`8`), `k+d` = entry 0 `a` (`0x3b`); the result `7` is `(a & 0xf8) >> 3` (C-5713).
- **FACT:** on the second tile (`B30R058R` `0x5759f4`, `k=78`) `k` is **node 1 entry 0's `a` word** (`0x806c`), not a node header; `d = w[k+6] = 2` and `k+d` lands on entry 0 `extra` (`0x2101`). So the driven block's "`k` = node header" is a sample, not a rule for every `k` the real table may return (C-5714).
- **OBSERVED (census):** over single-`k` records whose `k` sits at a node header, `d` always equals that node's entry 0 `id` (`4513/4513` on `B48R058R`, `58/58` on `B30R058R`); but `k+d` lands on entry 0 `a` in only 92/4513, so on the corpus `k+d` is a field of the record, not necessarily `a` (C-5715).
- **OBSERVED (census):** a passing `k` exists on 24,483/65,274 (`B48R058R`) and 425/1,603 (`B30R058R`) level-1 section-2 records, and on 0/303 of `B28R070R`; `k` most often sits at a node header when there is exactly one candidate, but candidate-`k` positions overall are split between node headers, entry bases and other words (C-5716).
- **HYPOTHESIS:** `k` is a record-relative index into a node's entry block (the real `0x00424464` table, unknown); the consumer computes a node's `a` field and the `(a & 0xf8) >> 3` result is a link/road class, matching `clarion_rd`'s "travel time / length" wording only weakly. Untested.
- **UNKNOWN:** how the real `0x00424464(19, …)` table chooses `k` for a given query; whether the section-2 block is the whole reply or a sub-block; section 2 above level 1; US2011.

## Conclusion

M4.54's done-when is met: for one factory section-2 block (`B48R058R` `0xb91d078`), the run lists the tile offset and value of each word `0x00422eac` reads and names what `k` indexes (part-a node header word 0, node 7, x `0x4fd`), with a section-1 control at the same `k` rejected by the `0x0900` gate, a second tile passing and `B28R070R` as the no-`k` negative. The words are ordinary part-a fields: `k+15` and `k+7` are entry class words, `k+6` is an entry `id`, `k+d` is a field of the node (entry 0 `a` on the driven block, not on the corpus). New claims C-5710–C-5719; `docs/format/map-tiles.md` gains the word→field table and the section-1 control. `k`'s real source (`0x00424464`) and the reply's block granularity stay open, and M4.40 returns to `open` with `0x00422eac` and `B48R058R` `0xb91d078` as its start.
