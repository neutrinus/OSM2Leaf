## Question

Can the M1.2b runner be built now — LZNT1 as a real decoder, plain LZ77 and
LZ77+Huffman as honest skeletons, and a `probe` command that tries every method
at every offset and reports which attempt produces exactly the expected
`o32_vsize` — with a positive control per decoder, when the only real section
bytes in this checkout are the 30-byte prefix that EXP-2026-11-05-49 printed?

## Hypothesis

Exploratory for the image. The tool half is testable without vendor data only if
every decoder (or refusal) has its own positive control:

- **LZNT1** ([MS-XCA] 2.5) is decoded for real, and the positive control is the
  spec's own 59-byte example (chunk header `0xB038`, 142-byte output,
  "F# F# G A A …" plus NUL), not only encoder/decoder self-symmetry. A reference
  encoder covers literals, matches, chunk boundaries, the stored-chunk fallback
  and the `0x0FFF` terminator.
- **LZSS** and **LZX stored blocks** keep the EXP-52 controls (encoder symmetry,
  hand-built streams).
- **XPRESS plain LZ77** and **LZ77+Huffman** stay skeletons: each parses what
  structure exists (a 32-bit flag DWORD; a 256-byte/512-symbol code-length
  table), then raises `UNSUPPORTED(xpress-…)` with the reason. They must never
  return guessed bytes and must never show up as a `probe` match.
- **`probe`** must find a hidden LZSS stream behind a 22-byte prefix (the M1.2a
  header hypothesis), report exactly one match, and use exit 0 (a match), 1 (no
  match) and 2 (usage/IO error).

### What the 391 self-test checks now cover (new half)

- **LZNT1 spec vector**: the [MS-XCA] 2.5 59-byte example decodes to the 142-byte
  string plus NUL, with one compressed chunk and a 57-byte payload;
- **LZNT1 symmetry** over the twelve LZSS corpora (empty, 1/7/8/9 literals, a
  100-byte run, period-3 repeats, an 18-byte alphabet, 4096 B, 4097 B, LCG 5000
  and 50000), comparing bytes, chunk counts, compressed/stored split and, for
  fully compressed corpora, literal/match/max-length/max-displacement counters
  with the reference encoder; plus a max-length-18 assertion and a stored-chunk
  fallback on incompressible input;
- **chunk boundaries**: 4096 + 4096 + 4 bytes encode as three chunks with those
  exact per-chunk output sizes, and a chunk whose first token is a back-reference
  is rejected even though the previous chunk produced data (chunks are
  independent);
- **the `0x0FFF` terminator**: a hand-built chunk that produces 2049 bytes and
  then carries the displacement field `0xFFF` (word `0xFFF0`) stops there,
  records one end marker, does not treat it as a 4096-byte look-back, and the
  following stored chunk still decodes; the *bare* word `0x0FFF` at the 12 + 4
  split is asserted to be a distance-256/length-18 match, not a marker; the same
  word at 4 displacement bits is a length past the 4096-byte chunk and raises;
- **LZNT1 negatives**: wrong signature, truncated header, payload past the end,
  zero signature mid-stream, displacement before the chunk start, oversized
  match, `expected_size` mismatch, empty input, the `ntfs-lznt1` alias, and the
  documented "zero header ends the data" rule with its trailing bytes reported
  as zero padding vs. non-zero junk;
- **XPRESS skeletons**: `xpress-huffman` parses the 512-symbol table and refuses
  with `UNSUPPORTED(xpress-huffman: … Kraft 32768/32768 …)`, rejects a short
  table and an over-subscribed one; `xpress-lz77` parses the first flag DWORD,
  reports it, and refuses; both refuse instead of returning bytes for empty,
  one-byte and 300-byte inputs;
- **probe**: the hidden 22-byte-prefix fixture yields exactly one match

## Interpretation

- **FACT:** `tools/cecompress.py` now implements LZNT1 as written in [MS-XCA]
  2.5: 4 KiB chunks, a 16-bit little-endian header with the 12-bit payload size
  minus one (`payload = field + 1`, header excluded), signature `0b011` in bits
  14…12 and a compressed flag in bit 15; a stored chunk carries its payload
  verbatim; a compressed chunk is flag bytes with 0 = literal and 1 = a 16-bit
  match word whose **high** bits hold `displacement - 1` and whose low bits hold
  `length - 3`, with the split moving as `max(4, bits(u - 1))` from 4 + 12 to
  12 + 4.
- **FACT:** the split rule is taken from the spec's own pseudo-code
  (`for (iterator = block_offset - 1; iterator >= 0x10; iterator >>= 1)
  { shift--; mask >>= 1; }`, quoted by libfwnt's format notes), not from a fit,
  and the spec's worked example decodes byte-exactly with it. That example is the
  first positive control in this module that is not self-symmetry: 59 stored
  bytes → the published 142-byte string, SHA-256
  `5f298e39…` on both sides of the check.
- **FACT:** both XPRESS variants are skeletons. `xpress-lz77` (plain LZ77,
  headerless: a 32-bit flag DWORD then 16-bit match words) parses only that first
  DWORD and raises; `xpress-huffman` parses the 256-byte, 512-symbol 4-bit
  code-length table, checks the Kraft sum against 2^15 and raises. Both always
  raise `UnsupportedFormat`, so no guessed bytes can leave the module; a
  `--method xpress-*` decompress exits 1 with the reason.
- **FACT:** `probe` is the M1.2b runner: every method × every offset (default
  0…32), one record per attempt with a status drawn from
  `match/wrong-size/no-size/unsupported/error/empty-input/out-of-range`, the
  decoder's own message preserved, matches carrying SHA-256, first bytes and
  plausibility counters, and exit 0/1/2. It writes nothing and does not "pick" a
  winner beyond the exact length match.
- **OBSERVED:** on the synthetic 22-byte-prefix fixture exactly one of 165
  attempts matches (`lzss` @22, 1200 B, SHA-256 `4a005a3…`), the other 164 are
  reported with their reasons; on the real 30-byte section-1 prefix all 165
  attempts fail and the tool exits 1.
- **OBSERVED:** the LZNT1 decoder in this module accepts lengths above 18 when
  the split gives a wider length field — the spec's own example contains a
  27-byte match at `u = 9` (4 displacement + 12 length bits). The encoder caps
  matches at 18, which is the 12 + 4 maximum, so the cap belongs to the encoder
  and not to the format.
- **HYPOTHESIS:** M1.2a's "22-byte header, then a payload" shape remains the best
  guess for the real sections (M1.2a is in progress in `tools/cerom.py`); this
  EXP neither confirms nor refutes it, and `probe` is the tool that will test it
  once the stored bytes exist.
- **UNKNOWN:** which codec, if any, the ZE0 image uses for its 245
  `IMAGE_SCN_COMPRESSED` sections. Nothing here decoded a real payload: the only
  real bytes in the repository are the 30-byte prefix of section 1, which is too
  short to hold any stream. `detect` also does not rank LZNT1 or the XPRESS
  skeletons, so a real match has to be read from `probe` (or `--method`), not
  from `detect --size`.
- **UNKNOWN:** whether any producer emits the `0x0FFF` end marker, and whether
  the marker is the whole word or the 12-bit displacement field. This module
  accepts the field form (word `0xFFFn` at the 12 + 4 split), documents the bare
  word as a normal match, and records `end_markers` so a real stream would show
  which reading was needed.
