## Question

What is the line order, separator and six-line mapping of `HDD_INFO.TXT` to the
`r8` output struct of `Navi.exe` `fn 0x004e7b8c` (`HDD_INFO_read`)?

## Hypothesis

The function reads 6 lines in order with `fgetws` and copies each whole stripped
line with `wcsncpy` into inline `wchar_t[]` fields at `r8+{0x00,0x18,0x30,0x4a,
0x62,0x7a}` with maxima `{12,12,13,12,12,13}` (C-721–C-728). There is no
key:value split; the CRLF boundary is the separator.

## Method

Static disassembly of `fn 0x004e7b8c` (build A, `--image-start 0x200200`) via
`sh4xref.py --calls 0x004e7b8c` and the M2.1 trace (C-721–C-728): `fgetws`
loop, `wcschr` CR/LF strip, `wcsncpy` copy. Factory file read (read-only, not
committed) confirms 6 ASCII CRLF lines fitting the maxima. `tools/hddinfo.py`
extended with `FieldDef`/`HDD_INFO_FIELDS`/`HDD_INFO_FIELD_BY_NAME|OFFSET` and
`field_layout` in JSON output; self-test updated (43 checks).

## Result

Verified: 6-line CRLF text layout, line→field→type→struct-offset mapping
(C-740–C-749). `tools/hddinfo.py --selftest` passes (43 checks);
`tools/selftest.py` green. No numeric model-M0 validation is claimed (C-747).
