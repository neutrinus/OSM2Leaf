## Question

Can one command boot the ZE0 CE images under QEMU — stock `-M none` today,
`-M ze0` once M8.A1 builds it — leave the EXP-37-style access log in a work
directory, and print the CE thread list with the current PC resolved to a
module and section, using only the pieces that already exist
(`ce_qemu_probe.summarize_log`, `cerom.py memmap`, the QEMU `-d`/`-D`/gdbstub
options)?

## Hypothesis

The pieces exist and the work is glue plus one addressing detail: QEMU reports
the PC in whatever SH-4 segment is executing (P1 `0x8xxxxxxx`, P2
`0xAxxxxxxx`, or a low P0 stub), while `cerom.py memmap` lists P1 VAs, so a
naive VA comparison would miss P2/uncached PCs and the `0x5b90`-style
kernel-page call of EXP-37. Wrapping `summarize_log()` instead of writing a new
parser should reproduce EXP-37's access list byte-for-byte in wording.

## Method

```bash
# 1. Shell/Python hygiene (POSIX sh, no bashisms).
bash -n  tools/qemu-ze0/run.sh
dash -n  tools/qemu-ze0/run.sh
checkbashisms tools/qemu-ze0/run.sh
python3 -m py_compile tools/qemu-ze0/gdb-ze0.py

# 2. What the wrapper would run on this machine (writes nothing).
./tools/qemu-ze0/run.sh --dry-run --gdb --timeout 5
./tools/qemu-ze0/run.sh --dry-run --image /tmp/opencode/m8a7/fake.img \
  --workdir /tmp/opencode/m8a7/w50 --qemu /tmp/opencode/m8a7/ze0-qemu --gdb=1235

# 3. End to end without QEMU: a stand-in qemu-system-sh4 that only answers
#    `-M help`, writes one -d log and exits (never committed).
./tools/qemu-ze0/run.sh --image /tmp/opencode/m8a7/fake.img \
  --workdir /tmp/opencode/m8a7/final-run --qemu /tmp/opencode/m8a7/fake-qemu \
  --memmap /tmp/opencode/m8a7/mm-synth.json --gdb --timeout 5

# 4. Timeout path: a stand-in that execs `sleep 30` (one process, like QEMU).
./tools/qemu-ze0/run.sh --qemu /tmp/opencode/m8a7/slow-qemu \
  --workdir /tmp/opencode/m8a7/final-timeout --timeout 2 --no-memmap

# 5. Missing-QEMU path.
./tools/qemu-ze0/run.sh --image /tmp/opencode/m8a7/fake.img; echo $?   # 3

# 6. PC -> module/section on a real `cerom.py memmap` document.
python3 tools/cerom.py --image-start 0x200 \
  /tmp/opencode/m9.2/synthetic-rom.img memmap \
  --out /tmp/opencode/m8a7/mm-synth.json
python3 tools/qemu-ze0/gdb-ze0.py --memmap /tmp/opencode/m8a7/mm-synth.json \
  --pc 0x8ce01010 --pc 0x0ce02080 --pc 0xcce02080 --pc 0x8d001004 --pc 0xffe46000 --pc 0x00005b90

# 7. The gdb branch without gdb: import the script with a fake `gdb` module.
python3 /tmp/opencode/m8a7/fake_gdb_test.py

# 8. The script's own selftest and the repository runner.
python3 tools/qemu-ze0/gdb-ze0.py --selftest
python3 tools/selftest.py
```

## Interpretation

- **FACT:** `run.sh` produces the whole EXP-37 boot command from one
  invocation: machine selection (`-M ze0` when `qemu-system-sh4 -M help`
  lists it, else `-M none -cpu sh7785 -m 512M`), `-d unimp,guest_errors,int
  -D WORK/qemu.log`, optional `-gdb tcp:127.0.0.1:PORT`, `--timeout`, and a
  work directory holding `qemu.log`, `registers.txt` (when the HMP socket is
  reachable), `memmap.json`, `kernel.bin` and `app.bin`.
- **FACT:** `--dry-run` prints `mkdir`, the `tail | head` cuts, the `cerom.py
  memmap` call (or `cp` for `--memmap`) and the final QEMU argv, and writes
  nothing; verified by the absence of every named work directory afterwards.
- **FACT:** the log filter is literally `ce_qemu_probe.summarize_log()`, so
  the access list, the exception list and the wording are the probe's. On the
  same synthetic log the wrapper and the probe report the same two accesses and
  the same `0x180 illegal_instruction pc=0x00005b90`.
- **OBSERVED:** the PC→module step needs the alias rule. `cerom.py memmap`
  lists P1 VAs, while a PC can arrive in P2 (`0x0ce02080` resolved to
  `NK.EXE/sec1` only through `0x8ce02080`), in P3 (`0xcce02080` →
  `0x8ce02080`) or in P4 (`0xffe46000`, correctly reported as register space).
  `0x00005b90`, EXP-37's kernel-page stub VA, is deliberately *not* attributed
  to any module.
- **OBSERVED:** the gdbstub mode needs the memmap path handed over; run.sh
  prints a ready command with `set $ze0_memmap="…"`, and the script also
  accepts `$ZE0_MEMMAP` or `./memmap.json`.
- **OBSERVED:** `tools/cerom.py` must be called as
  `cerom.py --image-start N IMG memmap …`; with `--image-start` after the
  positional image argparse assigns the image path to the subcommand and fails.
  run.sh uses the working order.
- **OBSERVED:** `-M help` is executed once per `auto` run. Latency is QEMU's,
  not the wrapper's; the `--machine none|ze0` options skip the probe.
- **HYPOTHESIS:** with a real `qemu-system-sh4`, `registers.txt` will give the
  final PC the way EXP-37's probe did (it reads `info registers` over the same
  HMP socket) and the summary will print a `final pc:` line; this sandbox has
  no QEMU, so that line is untested here.
- **UNKNOWN:** whether the real SD image's 0x200-byte segment header really
  stores `physlast − physfirst` in its first u32. The wrapper relies on the
  same contract as `ce_qemu_probe.py` and
  `docs/research/full-system-emulation.md` §1, and it fails loudly when the
  stronger check (ECEC at offset+0x40) or the length plausibility check
  disagrees. No vendor image was available to confirm the length field.
- **UNKNOWN:** whether QEMU 8.2 + the M8.A1/M8.A3 `ze0` machine accepts
  `-device loader` and `-S` unchanged. Today both machine types get the loader
  devices; after M8.A3 the machine should own the copy (`-kernel`) and the
  wrapper should drop them for `-M ze0`.
