## Question

With the EU card prepared for the US unit and the unit's own kernel and
flash, does the navigation draw its map, and does it take a GPS position in
Wrocław (the M1.50 question: the US card keeps the car in Kentucky)?

## Hypothesis

The launcher passes the card (M8.C1m/C1r). On the EU map the Wrocław fix
lies on a tile, so the map-matching gate of M8.H78 passes and the car
follows the fix. Falsifier: the car stays at the backup position, or the
map does not draw.

## Interpretation

- **The EU map takes a Wrocław position on the unit's software.** With the
  map under the fix, the M8.H78 gate passes and the car moves to Wrocław
  (O3). This confirms M1.50 H2c: in the car, Kentucky holds because the US
  card has no map at Wrocław.
- **The unit's saved navigation data (VSram) stops the EU card from drawing
  the map** in the emulator (O2, 2 of 2). The trigger is in the first half of
  VSram but is **not** the car-position backup itself (A1 loads it and
  works); it lies in data that A1 removes and A2 keeps — most likely the
  first copy of the 3-block area at `0x400000–0x42FFFF` or the block at
  `0x430000` (HYPOTHESIS; which object it is was not isolated). Likely
  candidates are records that hold US-map references (stored route,
  destinations/history, map-specific caches) — HYPOTHESIS.
- **Risk for the car:** the same VSram is in the unit, so the patched EU
  card may crash `Navi.exe` there too (a navigation restart or a reset
  loop). The emulator differences (no VCAN/audio micom, power-off patched
  out) make this a HYPOTHESIS for the car, but the A/B/N controls tie the
  crash to the flash data, not to the emulator.

## Conclusion

The EU map takes a Wrocław position on the unit's software once VSram area 0 is
back to defaults: the car follows the fix and draws the map (O3, O8). With the
unit's present VSram the patched EU card crashes Navi.exe or stops before the
first map draw (O2, O4, O7); the trigger is one object of area 0 spanning payload
`0xaec0-0xba6b`, which is not isolated. The risk for the car is a HYPOTHESIS:
the emulator has no VCAN/audio micom and the power-off path is patched out.
M1.57's Done-when is met (the map takes the position under the named condition);
which object to reset remains open.

## Update 2026-11-23 (afternoon): which part of area 0

Marek: the navigation on the US card was never used, and he cleared all
navigation and personal data (service menu) when he bought the car. So the
trigger is state the navigation writes on its own, not user items.

**Layout.** The `VSram` stores are the four `SMST` areas of
`tools/unitflash_anon.py` (`AREAS`): area 0 = `0x30000` bytes at
`0x400000` with its second copy at `0x430000`; area 1 at
`0x460000`/`0x470000`; area 2 at `0x480000`/`0x490000`; area 3 at
`0x4A0000`/`0x4D0000`. A1 broke both copies of area 0; A2 broke the tail of
copy 2 plus area 1. So the crash trigger is in **area 0** (objects 03 05 0A
0C 10 19, EXP M6.24).

**Method.** Variants of Marek's dump where payload ranges of area 0 (both
copies) are replaced by the committed anonymous `sram-anon.bin`, or single
bytes are flipped, with the area sum recomputed so the area still loads.
Each object carries its own check word (e.g. at payload `+0xffc`, `+0xba68`),
so a partial splice makes that object fail its own check and load defaults
(one `OBJ_BackUp_Load Error`). Same run recipe as above, three guests in
parallel.

| run | area-0 payload taken from anon / flipped | `Exception 0e0` |
| --- | --- | --- |
| S1 | anon `0x0000–0xe000` | no |
| S2 | anon `0xe000–end` | **yes** |
| T1 | anon `0x0000–0x6000` | **yes** |
| T2 | anon `0x6000–0xe000` | no |
| U1 / U2 | anon `0x6000–end` / `0xa000–end` | no |
| U3 | anon `0xc000–end` | **yes** |
| V1 / V2 / V3 | anon `0xc2d0–0xc5e0` / `0xc000–0xe000` / `0xc800–0xe000` | **yes** |
| W1 | anon `0xa000–0xc000` (whole object, loads) | no |
| W2 | anon `0xaec0–0xaf08` only (object fails its check) | no |
| W3 | anon `0xb700–0xbc00` only (object fails its check) | no |
| Y1–Y3 | byte flip at `0xaee0` (+ one more flip elsewhere) | no |

**O6 — the crash object.** The exception needs Marek's copy of one object
of area 0 that spans at least payload `0xaec0–0xba6b` (its check word at
`0xba68`). Making only that object invalid (W2, W3, Y1–Y3) removes the
crash. Its differing fields include `+0xaef0..+0xaf00` (`59895908 15000000
3b000000` vs default `aa869908 00000080 00000080`) and text fields of
spaces at `+0xb75b..` (default zeros). What the object is: UNKNOWN.

**O7 — no first map draw without the crash.** In every no-crash variant
(S1, T2, U1, U2, W1–W3, X1–X3, Y1–Y3) Navi reaches the `SRT_COLD_I_AGREE`
screen state but `NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END` never comes (watched
up to 20 min; screen plane black; a tap and the moving-GPS recipe on Y1 did
not change it). A1 and N, where all of area 0 is invalid, draw the map. The
TMC handler logs `<BkupDataGet> CarPosCountry=255` with Marek's area 0 and

`0x25900` did not invalidate any further object.
