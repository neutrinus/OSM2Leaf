## Question

Which fields of the `RDSTM001` road records (graph tuples, speed, one-way,
restrictions) does the router read in build A, and at which VAs?

## Hypothesis

`RDSTM001` carries the routing graph, so the router must expose per-link speed,
direction and turn restrictions. (This was the working assumption behind
C-108 and the open question OQ-14.)

## Observations

### 1. Name sites (build A, all modules)

| String | VA | Where | Code refs |
| --- | --- | --- | --- |
| `RDSTM001` (8-char volume id) | `0x00179398` | volume-name table `0x00179338` (`ZCODE0`, `LCTBL0`, `INTER0`, `FRWAY0`, `ADDRE0`, `POINT0`, `RDSTM001`) | `0x003fc016` (fn `0x003fbed8`), `0x00412610` (fn `0x004125a8`) |
| `LCTBL001.DAT` (file) | `0x0017a1f8` | long-name string table | `0x0041260e` (fn `0x004125a8`) |
| `RDSTM001.DAT` (file) | `0x00179f7c` | long-name string table | **none** — pool at `0x00179d20` holds it, no load in any executable section |
| `REFER001` (volume id) | `0x00178c68` | string table | `0x00412634` (fn `0x004125a8`) |
| `INDEX003.DAT` (file) | `0x0017a118` | long-name table | `0x00412632` (fn `0x004125a8`) |

No other module in build A contains `RDSTM`/`LCTBL` map-data identifiers:
`ScreenStateCC.dll`, `EvNoticeCC.dll` and `InfoBarCC.dll` only carry the UI
token `RDSTMC_DETOUR_INFO` (`0x02ad772d`, `0x024b772d`, `0x0243772d`).

### 2. Volume selection (`0x004125a8`)

`0x004125a8(descriptor, out)` copies `u16[descriptor+8]` (data type),
`u16[descriptor+10]` (kind) and `u32[descriptor+28]` into `out+104/108/124`, then:

```
0x004125fa  mov.w  [0x00412698]=0x14e4 ; type compare
0x0041260e  mov.l  0x0017a1f8  -> r5   ; "LCTBL001.DAT"  (file inside the volume)
0x00412610  mov.l  0x00179398  -> r4   ; "RDSTM001"      (volume / directory id)
0x00412612  jsr    0x0040b358          ; volume+name lookup in the mounted volume table
0x0041261e  mov.l  r0,@(120,r8)        ; -> volume handle / entry index
```

This matches the on-card layout: `RDSTM001/` holds `RDSTM001.DAT` and
`LCTBL001.DAT`, so the selector resolves the *directory* `RDSTM001` and the
name table `LCTBL001.DAT` in one step.

The same function maps type code `0x14e8` to `REFER001` + `INDEX003.DAT`
(`0x00412632`/`0x00412634`) and, for the "no secondary name file" branch,
`INDEX001` + `INDEX006.DAT` (`0x00412620`/`0x00412626`, string table
`0x0017a098`). `0x0040b358(name, table)` is the 28-byte-entry volume-table
lookup: it validates the name, walks the table (count at `+24`, list at `+32`,
28-byte entries) and returns the entry index.

### 3. The record is a TMC location record, not a graph edge

The SDL road path builds a 48-byte request (`0x003bcb20`-`0x003bcb64`) with:

```
0x003bcb48  mov.w  [0x003bcb90]=0x14e4 -> request+24    ; same data type as the pair above
0x003bcb4c..0x003bcb5e  country, location-database no, location code -> request+32/36/40
0x003bcb60  jsr 0x003c0e68 ; 0x003bcb66 jsr 0x003bc960 (record -> struct)
```

The response is attached by `sdl_TMC_SetRecordAddr` (`0x003bc960` region,
trace tag `0x00045268`), and `0x003bc960` **decodes the raw record into a
496-byte struct at `0x006f3918`**:

| decoded offset | raw field index | extractor VA | getter (name string at) |
| --- | --- | --- | --- |
| `+0x04` u16 | 0 | `0x003f66b8` | `SDL_TMC_GetLocationCode` `0x003bbfe0` |
| `+0x06` u16 | 5 | `0x003f6734` | `SDL_TMC_GetAreaLocationCode` `0x003bc5e0` |
| `+0x08` u16 | 6 | `0x003f6780` | `SDL_TMC_GetLinerLocationCode` `0x003bc628` |
| `+0x0a` u16 | 7 | `0x003f67cc` | `SDL_TMC_GetFrontLocationCode` `0x003bc670` |
| `+0x0c` u16 | 8 | `0x003f6818` | `SDL_TMC_GetRearLocationCode` `0x003bc6b8` |
| `+0x0e` u16 | 9 | `0x003f6864` | `SDL_TMC_GetUrbanAttribute` `0x003bc700` |
| `+0x10` u16 | 11 | `0x003f68bc` | `SDL_TMC_GetInterLocationCode` `0x003bc8b8` |
| `+0x12` count, block `+0x1c` | str | `0x003bc028` | `sdl_TMC_GetRoadNumberStr` `0x003bc100` |
| `+0x14` count, block `+0x40` | str | `0x003bc194` | `sdl_TMC_GetRoadNameStr` `0x003bc26c` |
| `+0x16` count, block `+0xc4` | str | `0x003bc300` | `sdl_TMC_GetPrimaryLocationStr` `0x003bc3d8` |
| `+0x18` count, block `+0x148` | str | `0x003bc470` | `sdl_TMC_GetSecondaryLocationStr` `0x003bc548` |
| `+0x1a` count, block `+0x1cc` | str | `0x003bc748` | `SDL_TMC_GetExitJunctionNumberStr` `0x003bc820` |

`sdl_TMC_InitDataRecode` (`0x003bbf6c`) zeroes `124*4 = 496` bytes and sets
`+0x04..+0x10` to `0xffff`, so the struct is exactly `0x1f0` bytes.

Field resolution is generic, not a fixed offset: `0x003f61bc(record, ?, index)`
returns a pointer to the field, `0x003f5d98`/`0x003f56bc` walk a per-record
field directory (byte/bit lengths at `record + *(u16[record+2])*2`) and
`0x003f51e0` returns the schema/record-kind descriptor. That is why the raw
record is not a fixed-stride table (C-106).

The dump routine `0x003a0034` prints the same twelve fields in the same order
(format strings `0x0003cbb0` "hdlm recorde info", `0x0003cb90`
"LocationCode(%d)", `0x0003cb68`, `0x0003cb44`, `0x0003cb18`, `0x0003caec`,
`0x0003cac8`, `0x0003caa4`, `0x0003ca80`, `0x0003ca5c`, `0x0003ca3c`,
`0x0003ca0c`, `0x0003c9e8`).

### 4. Router side

- The route planner's own link identity is mesh-based:
  `link[mesh(0x%x),no(%d),rdtype(%d)]` (`0x00011eb2`),
  `pass(%d),mode(%d),info(%x),randl(%x)` (`0x00011eda`),
  `link[mesh(0x%x),no(%d,%d,%d),lktype(%d),rdtype(%d)]` (`0x00011f0e`),
  `dir(%d),speed(%d))` (`0x00011f46`), next to `Route Planning Function`
  (`0x000115c0`) and the `RGD(TurnList)` dump (`0x00020f30`).
- The `0x14e4` type code appears in three *code* sites only: the volume/schema
  descriptor lookup `0x003fa382` (calls `0x003f7384(type, out)`), the SDL
  request builder `0x003bcb48`, and the name-pair selector `0x004125a8`
  (`0x0041260e`). Every other swept `0x14e4` byte is data or a literal pool —
  `0x0009abe4` sits inside a `0x75f11be7` table, `0x003fa5a8` inside the pool
  `0x003fa562`-`0x003fa5bf`.
- No `RDSTM`/`LCTBL` name and no record getter is referenced from the graph
  code bands (`RGD` handlers `0x004ed410`/`0x004eeeb8`/`0x004f0b24`/
  `0x004f0d8c`/`0x004f21f8`, `SVR_Rgd*` `0x0037aed4`/`0x0037b02c`).

## Interpretation

- **FACT:** build A resolves the `RDSTM001` volume together with its
  `LCTBL001.DAT` name table under data type `0x14e4`, kind 1 (`0x004125a8`,
  lookup `0x0040b358`).
- **FACT:** `RDSTM001.DAT` as a literal string has no code reference; the volume
  is reached through the 8-char volume id table at `0x00179338` and the file
  name is built from the id (`0x003fbed8`).
- **FACT:** the firmware's road record has exactly twelve fields, matching the
  twelve `LCTBL` catalog columns in order: location code, road number, road
  name, primary name, secondary name, area code, liner code, front code, rear
  code, urban attribute, exit/junction number, inter-section code. The seven
  numeric fields are read at raw field indexes 0, 5, 6, 7, 8, 9, 11; the five
  string fields have dedicated extractors.
- **OBSERVED:** the record is looked up by `(country, location-database no,
  location code)` — a TMC location-table key, not a node/link pair.
- **OBSERVED:** the record layout is variable: a per-record field directory
  (lengths + offsets) is walked by `0x003f5d98`/`0x003f56bc`, so no constant
  stride exists.
- **UNKNOWN / negative:** no speed, one-way, turn-restriction, toll or ferry
  accessor exists in the complete road-record surface (one decoder, twelve
  getters, `InitDataRecode`, `SetRecordAddr`). The `RDSTM001` record set cannot
  give the router a cost, a direction or a restriction.
- **UNKNOWN:** how the router obtains `dir`/`speed` (the `0x00011f46` format
  takes them from a runtime link struct that was not traced to a file), and
  whether `INTER001`/`FRWAY001` supply restrictions. That is the M4.2/M4.3
  input, not an `RDSTM` one.
- **HYPOTHESIS:** `RDSTM001` is the road/name/TMC attribute database used by
  search and guidance text; the routing graph is mesh-based and built from
  `MAPAL001` tiles, which is why every factory attempt to find speed/one-way in
  `RDSTM` failed (C-108, M4.2 negative).

## Conclusion

`rdstm.md` now carries a firmware-side field list with VAs (volume pairing,
record schema, decoded struct, getters) and separates the two consumers:
search/TMC text (RDSTM) versus mesh-keyed routing (`MAPAL`). The "record fields
the router uses" part of the task resolves to: none directly — the router
consumes mesh/link identifiers, and `RDSTM001` carries the twelve TMC location
attributes. M4.1/M4.3 now have the field set and order to encode; M4.2
(speed/one-way) must not look in `RDSTM001`.
