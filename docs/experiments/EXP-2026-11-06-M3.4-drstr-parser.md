## Question

Does build A's firmware contain literal references to `DRSTR001.DAT`, `CMP.LST` or
`MAPAL001` once addresses are derived through `tools/cerom.py` (the old
"zero literal references" negative, C-331, was produced under the wrong address
model), and, if so, what parser/validation checks can be recovered?

## Hypothesis

The old negative (C-331) is an address-model artefact; the CE ROM TOC should put
the map/media-manager code at its real VA, so filename literals (if any) and
their `mov.l` loads become visible.

## Method

```bash
IMG=/home/marek/projekty/leafre-work/leaf2011.img
# 1. ASCII/UTF-16 search in the four modules' uncompressed sections.
python3 /tmp/opencode/search_strings.py   # (cerom-based; see Observations)

# 2. Raw-image scan for the DRSTR literal (first 256 MiB).
python3 - <<'PY'

while True:
    j=data.find(b'DRSTR',i)

# 3. Xrefs for each literal VA.

# 4. Positive control.
python3 tools/sh4xref.py "$IMG" Navi.exe --image-start 0x200200 --to 0x004e7d28
```

## Observations

Raw results (counts, VAs, functions):

- `DRSTR001.DAT` (ASCII) occurs in `Navi.exe` only, at VA `0x0017ab24`.
  `sh4xref --to 0x0017ab24`: literal pool `0x00419870` holds it; loaded at
  `0x00419732` (r5) in function `0x00419684`; that function is called from
  `0x00419d24`.
- `\CMP.LST` (ASCII, with leading backslash) occurs in `Navi.exe` only, at VA
  `0x0017b25c`.
  `sh4xref --to 0x0017b25c`: literal pool `0x0041bbb0` holds it; loaded at
  `0x0041bad0` (r5) in function `0x0041ba90`; that function is called from
  `0x00419ca0`.
- `MAPAL001` occurs in `Navi.exe` at VA `0x00179f98`, but only inside a
  static filename table (pools `0x00179cf8`/`0x00179d04`/`0x00179d10`); no
  `mov.l` load in any executable section (`sh4xref` reports no load lines).
  `LEV3456R.DAT` at `0x00179fa4` *does* have a code xref (`0x0040a022` in
  fn `0x0040a014`).
- `RDSTM001` (`0x00179398`) has code xrefs in fns `0x003fbed8` and
  `0x004125a8`; `REFER001.DAT` etc. appear in the same static filename table.
- Raw-image scan of the first 256 MiB found exactly three `DRSTR` occurrences:
  the build-A copy at file `0x00df8d24` (VA `0x0017ab24`), its duplicate at
  `0x02bf8d24`, and one unrelated FAT/data hit at `0x064e5a60`.
- Positive control: `sh4xref --to 0x004e7d28` reproduces the EXP-50 call site
  `0x004e7bec` in function `0x004e7b8c`, so the method would report a load if
  one existed.
- No `DRSTR001.DAT`/`CMP.LST`/`MAPAL001` literal exists in `NaviMapCC.dll`,
  `OBJDLL.dll` or `STDDLL.dll` (uncompressed sections).

## Interpretation

- **FACT:** Under the real VA model, `DRSTR001.DAT` and `\CMP.LST` *do* have
  code references in `Navi.exe` (functions `0x00419684` and `0x0041ba90`),
  so C-331's "zero literal references" is wrong for those two names.
- **FACT:** `MAPAL001` is not loaded by code directly; it survives only as a
  static filename-table entry (table at `0x00179cf8`…`0x00179d18`).
- **OBSERVED:** The two referencing functions are media/CD-ROM-manager
  routines called from `0x00419d24`/`0x00419ca0`; they are the only build-A
  code paths that name these files.
- **UNKNOWN:** No count/order/sentinel check on the DRSTR layout (40 nodes,
  324 entries, leading `u32 = 0x0000002f`) was identified in these functions;
  whether firmware validates them is unproven. The functions were not fully
  decoded (SH-4, no objdump available); only their call graph and literal loads
  are recorded.

## Conclusion

`docs/format/drstr.md` gains a "Firmware references (build A)" section with the
VAs above. `docs/research/claims.md` gains C-850–C-859; C-331 is retracted in
part. The DRSTR parser itself and its validation checks remain unidentified;
the offline file-side invariants (counts, ordering, sentinels, leading u32)
stand as the data contract (C-030–C-039) and are not yet tied to firmware code.
