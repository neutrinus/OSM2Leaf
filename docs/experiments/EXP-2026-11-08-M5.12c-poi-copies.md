## Question

Which copies of the POI names the user saw on screen (`RAB ORCHARD`,
`WENDY'S`, `MCDONALD'S`, `GODFATHER'S`, `BLIMPIE`, `HARDEE'S`) exist on the US
card, and can every POI record be renamed to a same-length test name?

## Hypothesis

A same-length POI rename, applied to every record whose name is followed by
`@`, leaves all other bytes unchanged and passes `cardcheck`. **Falsifier:** a
byte change outside an edited name, a `cardcheck` FAIL, or an edited name that
is not found at its offset after rebuild.

## Method

1. **Sample and hash.** As in Sample; `sha256sum` matches.
2. **Decode.** `tools/cmpind.py extract` on all 58 pairs into
   `leafre-work/m5.12c/decoded/` (58/58, 0 failures).
3. **Search.** `tools/poi_copies.py TREE --text NAME [--text …] --inner`
   searches the three encodings in every file and in every complete zlib
   stream inside it. Hits are `(file, inner offset, encoding)`.
   - `points/` (symlinks to the `POINT*.DAT`): five base names plus
     `RAB ORCHARD` in one pass.
   - Uncompressed files of the tree (`root-factory`, 132 non-`.cmp` files):
     exact `HANA HEALTH CENTER` search with `--inner`. **Not completed** when
     this record was written (the job was still running); no result is
     claimed here.
4. **Targets.** A hit counts only when the byte after the name is `@` (name of
   a POI, not part of an address). Built into `targets.json` (136 occurrences,
   32 inner pages, 13 `.DAT` names).
5. **Rebuild.** `tools/mutate_refer_poi.py CMP IND OUTDIR --batch plan.json`
   for each POINT pair: same-length replacement, byte check at each offset,
   refit into the original slot (see Observations), one encode per pair.
6. **Card.** `imgpatch.py --allow-resize` for each rebuilt `.cmp` and `.ind`
   into a copy of the factory image; `cardcheck.py --image`.
7. **Controls.** Positive: the S1 no-op patch is byte-identical to the factory
   image (EXP-2026-11-08-M5.13b). Negative: the `@`-rule refuses a name not
   followed by `@` (selftest case); a wrong offset and a wrong length are
   refused (selftest).

## Observations

- **Search, decoded tree, names with `(MT VERNON`.** 0 hits. The city in the
  screen list is added by the display; the stored name has no city.
- **Search, POINT pages, five base names + RAB ORCHARD.** The first pass
  missed nearly every POI because the names live inside the inner zlib
  streams. With `--inner`, `RAB ORCHARD` appears in `POINT003–008` (75 hits)
  and in `ADDRE003–008` (street names, not edited).
- **Exact `HANA HEALTH CENTER`** (M5.12 test name) in the decoded `.cmp`
  payloads: 1 hit, `POINT010` inner `0x840ba0`, the record that the M5.12
  rename already changed. Uncompressed files: not completed (see Method 3).
- **Targets (name followed by `@`).** `MCDONALD'S` 85, `HARDEE'S` 42,
  `WENDY'S` 1, `CRAB ORCHARD@` 8 (edited as `RAB ORCHARD`). `GODFATHER'S`
  and `BLIMPIE` have no `@` record and are not edited. Records of these
  names not followed by `@` are not edited either.
- **Same-length names.** `RAB ORCHARD`→`OSM2 RAB 01`, `MCDONALD'S`→`OSM2
  MCD01`, `HARDEE'S`→`OSM2 H01`, `WENDY'S`→`OSM2W01`.
- **Page framing.** The POI pages are not all the `ff ff` record chain of
  `POINT010` (`parse_page` fails on `POINT001–009`). The batch therefore relies
  on the same-length rule: the edit changes no offset, and `edit_inner`
  checks that only the edited bytes differ.
- **Encoder.** No stock zlib level or memLevel reproduces the factory inner
  streams of `POINT001–009`, so the edited streams are not byte-identical to
  the factory even when the name is unchanged. Edited streams are refit into
  the original slot with the smallest encoder that fits. Pages are not
  aligned: a stream can abut the next page, so padding is used only when the
  bytes after it are zero.
- **Unfit pages (skipped, names left unchanged).** `POINT006` page
  `0x12d94cc0` (4 edits, `POINT006` total 44 → 40 applied); `POINT008` pages
  `0x152e4a08` (1 edit) and `0x16c25820` (1 edit). The smallest zlib output
  is 33549 B for a 33299 B slot and 58692 B for a 58616 B slot.
- **Amendment (S4).** Shorter names do not fit: a shorter name shifts every
  byte after it, and the page tables are not known to this tool. A same-length
  name padded with spaces (`OSM2` + spaces) does compress better. With the
  encoder search widened to levels 1–9 × memLevel 8/9, the `0x16c25820`
  `RAB ORCHARD` page now fits and is edited as `OSM2` + spaces. The
  `0x152e4a08` `HARDEE'S` page does not fit with any filler (best 58688 B
  against a 58616 B slot). `us_S4.img` (SHA-256 `1d4eeefd…25b1c4`) has 131
  of 136 edits; 5 remain (4× `RAB ORCHARD` on `POINT006` `0x12d94cc0`, 1×
  `HARDEE'S` on `POINT008` `0x152e4a08`). `cardcheck --image us_S4.img`
  RESULT PASS. Verified on the image: 131 applied, 0 wrong, 5 skipped still
  old.
- **Build (S3, first pass).** Nine pairs rebuilt, 130 of 136 edits applied. `cardcheck --image
  us_S3.img --hash`: RESULT PASS; `cmp` 58 pairs OK; label `QSD-301-103`;
  `[version] image_copy=identical`.
- **Verification on the built image.** The nine POINT pairs extracted from
  `us_S3.img` are byte-identical to the built pairs. Decoding each applied
  page: 130 of 130 edits found at their offsets with `@` after the new name;
  0 wrong; the 6 skipped edits still carry the old name.

## Interpretation

The batch rename works on the real card for 130 of the 136 POI records found
by the search, and the card passes the structural checks. Six POI records
keep their old names because their pages cannot be recompressed into the
original slot with stock zlib. This is an encoder limit, not a format result.
The search is complete only for the names searched, in the POINT pages and the
inflated streams inside them. A name written in an encoding other than Latin-1
was searched (UTF-16LE/BE) and not found.

Not verified here: how the screen shows the edited records (no car test,
per the user's instruction). The new names are chosen to be unmistakable on
screen.
