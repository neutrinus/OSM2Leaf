## Question

Can a host program speak the receiver protocol documented by M8.H27 on the
`sci7` chardev, encode a fixed position, replay a three-point GPX/NMEA track,
and expose a control socket for the scenario runner (M8.H7), with a selftest
that would catch a wrong checksum?

## Hypothesis

The M8.H27 grammar is sufficient to build a peer: frame length comes from
`navdrv.dll`'s TX selector table, the checksum is `(sum of payload) & 0x7f`,
and the terminator's high nibble is `0xf0`. **Falsifier:** the selftest passes
with a wrong checksum routine (no negative control). **Stop:** one session.

## Method

1. Read `docs/firmware/navdrv.md` and EXP-2026-11-22-M8.H27: the two captured
   frames are 6 bytes for start `0xb0`, and `A0 00` is the position command
   family used by TestMode's `GpsDataSetLatLon` (C-8244).
2. Extract the length table from the pinned firmware head (offsets only, no
   vendor bytes committed) and compare it with the driver's dispatch:
   ```bash
   python3 -c "d=open('archive/head256.img','rb').read(); \
     f=0x4260200+(0x39e1808-0x39e1000); print(d[f:f+34].hex(' '))"
   python3 tools/sh4dis.py archive/head256.img navdrv.dll --image-start 0x3e00200 \
     --va 0x39e4302 --count 14
   ```
   Result (selector table): `00 18 04 18 …`; dispatch `14, 10, 8, 6, 44, 4, 0`
   indexed by `selector // 4`; `0xb0 → 6`, `0xa0 → 14`.
3. Implement `tools/ze0_peers/gps.py`: generic `encode_frame(start, command,
   data)`, `verify_frame`, fixed-position `A0 00` encoder (lat/lon as four
   7-bit bytes each, 1/1000 arc-minute units, two's complement for S/W),
   GPX/NMEA parsers, interpolation, `--fix/--speed/--heading/--time/--no-fix`,
   `--socket/--listen`, `--control`, `replay`, and `--selftest`.
4. Controls:
   ```bash
   python3 tools/ze0_peers/gps.py --selftest
   python3 tools/selftest.py --only ze0_peers.gps
   # live socket smoke test (host-only, no QEMU), scratch under the home tree
   W=~/projekty/leafre-work/scratch/m8.h30
   python3 -c "import socket; s=socket.socket(socket.AF_UNIX); s.bind('$W/gps.sock'); \
     s.listen(1); c,_=s.accept(); print(c.recv(4096).hex()); c.close(); s.close()" &
   python3 tools/ze0_peers/gps.py --socket "$W/gps.sock" --fix 52.23,21.01 \
     --duration 1 --rate 1
   ```
5. Corpus counted: 1 peer tool; 2 captured frames; 1 selector table (34 B);
   4 fixed coordinates + 50 seeded random fixes; 1 three-point GPX track
   (5 interpolated samples) and 1 NMEA sentence. SKIP is never a PASS.

## Observations

**O1 — example frames reproduce byte for byte.** `encode_frame(0xb0, 0x20,
[0x02, 0x00])` → `b0 20 02 00 22 f0`; `0x23` → `b0 23 02 00 25 f0`, exactly
the M8.H1 O7 frames. `frame_length(0xb0) = 6`, `frame_length(0xa0) = 14`.

**O2 — checksum has negative controls.** `verify_frame` accepts the example,
rejects `b0 20 02 00 23 f0` (wrong sum) and `b0 20 02 00 22 0f` (wrong
terminator). `encode_frame` refuses an 8-bit payload byte and an illegal
start byte (`0xa1`). The falsifier does not fire.

**O3 — position frames round-trip.** 52.23/21.01, −33.8688/151.2093,
37.4058806/−84.4876444, 0/0 and 50 seeded random fixes encode and decode
within 3×10⁻⁵ degrees (the 1/1000-arc-minute resolution). Wrocław's
`--fix 52.23,21.01` produced one live byte stream
`a000013f2268004c7838000046f0` on the local AF_UNIX socket.

**O4 — three-point GPX replay interpolates.** The fixture
`(52.00,21.00) → (52.10,21.20) → (52.20,21.40)` at 2 Hz yields 5 samples
(first, two intermediate on each leg, last); all five frames are valid and
distinct, and the middle sample lies between its neighbours. One `$GPRMC`
sentence parses to (52.35, 21.0167).

**O5 — control and state.** `gps LAT LON`, `no-fix`, `on`, `speed`, `heading`
and `status` are handled on the control socket; `--no-fix` emits no frames.
`--time`, `--speed` and `--heading` produce A0 01 / B0 20 / B0 23 frames with
**HYPOTHESIS** command semantics — `navdrv.dll` does not decode those fields,
so they must not be used as evidence of firmware behaviour.

**O6 — runner integration.** `tools/selftest.py` now discovers
`tools/ze0_peers/*.py` as `tool:ze0_peers.gps`; that suite passes 1/0/0.

## Interpretation

- **FACT (C-7270, C-7271, C-7272):** the peer encodes the documented framing
  and reproduces both captured frames (O1, O2); its length table is the
  driver's own (Method step 2).
- **FACT (C-7273, C-7274):** fixed-position encoding round-trips and a
  three-point track interpolates (O3, O4).
- **FACT (C-7275, C-7276):** control socket, `--no-fix` and host socket I/O
  work offline (O3, O5); no QEMU is needed for this task's Done when.
- **HYPOTHESIS (C-7277):** speed/heading/time command semantics; no firmware
  decoder was found in M8.H27.
- **OBSERVED (C-7278):** the receiver's own fix frames remain unknown, so this
  peer seeds positions with the TestMode command family rather than pretending
  to be a live satellite receiver. M8.H29/M8.H31 must close that gap.
- **FACT (C-7279):** selftest is registered in `tools/selftest.py` (O6).

## Conclusion

M8.H30 is done: `tools/ze0_peers/gps.py --selftest` passes, the M8.H27 example
frame is byte-identical, and a three-point GPX track yields five interpolated,
valid frames. The peer can be attached to `--serial-peer sci7=unix:PATH` from
M8.H1; the remaining uncertainty is the receiver's real fix-frame layout, not
the connector or the encoder.
