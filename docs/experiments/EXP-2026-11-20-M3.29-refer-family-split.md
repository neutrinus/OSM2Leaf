## Question

With the card mounted through the firmware's own data-access task, which
functions read each REFER family's record bytes at run time, and how much of
M3.23's static top-ten ranking does that split confirm per family?

## Hypothesis

None / exploratory (the dynamic counterpart of M3.23). The static graph gives
one shared `REFER` candidate list for `ADDRE`, `INTER`, `FRWAY`, `ZCODE` and
`COORD` because they go through one opener whose family is ctx +124 at run time
(C-3546, C-4666). A run per family with M9.38's read watch should turn that
shared list into per-family readers.

**Falsifier:**
- (a) The read watch attributes a load to a PC other than the instruction that
  executed it, or a watch changes `r0` (not inert).
- (b) A function the run credits is a caller-struct touch, not a file read
  (it loads from a buffer that is all zeroes as well).
- (c) The task reports a read of a family file that the card log does not show.

## Method

1. **Sample and hash.** As above; `sha256sum archive/head256.img` and the card
   image reproduce the two digests.

2. **Commands.**

   ```bash
   python3 tools/m3_29_family_readers.py --selftest
   python3 tools/callgraph.py build archive/head256.img -o g.json
   # per-family recall and the run's family reads; writes the rows as JSON
   python3 tools/m3_29_family_readers.py run archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --json run.json
   # the shared opener per family (does a family read start?)
   python3 tools/m3_29_family_readers.py openers archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   # M3.23's ICODE ranking for the recall denominator and the missed readers
   python3 tools/callgraph.py rank g.json --depth 6 --top 200 --family ICODE=0x003f2cc0
   ```

   The tool mounts the card with `datask_l3.py`'s `DataTask` (the data-access
   task plus the map-file task in one PySh4 machine), runs the boot to
   `both tasks idle`, and for every read completion shows the guest loads of the
   returned buffer attributed to their executing function (M9.38's watch). It
   reads the boot's own read tags (`0x0d00`, `0x0d02`, `0x0d10`, `0x0d11`) and
   maps each family to the files it asked for.

3. **Controls.**
   - *Positive:* `POINT001.DAT` and `ICODE001.DAT`/`ICADM001.DAT` are read by
     the boot; their loaders must appear (they do, below). The tool's `run`
     exits non-zero when no confirmed reader is found.
   - *Negative:* the watch is M9.38's, which runs every case twice (watch off),
     so a credited PC is the one that executed the load; the `run` JSON records
     the end state and any undelivered message so a family with no read is
     visible, not dropped.
   - *Openers:* `0x003fee70` is run five times with ctx +124 = 1/2/3/4/11 and
     must name `POINT001`/`ADDRE001`/`FRWAY001`/`INTER001`/`ZCODE001`.

4. **Scope.** EU2011 `Navi.exe` only, `POINT`/`ICODE`/`ICADM` reads the boot
   issues at map-ready (the state-2 data-access task). `ADDRE`, `FRWAY`,
   `INTER`, `ZCODE` and `COORD` are not read on a boot: the task stops at
   `both tasks idle` with a `0x1507` message queued (C-3259's message wait), so
   no reader for them is measured here. US2011 and the map DLLs are not covered.

5. **Falsifier.** As stated under Hypothesis.

## Observations

**Selftest.** `selftest: PASS` (5 checks: reader de-duplication, non-REFER
exclusion, the five family names, the five-plus-`COORD` reported set, and the
ten/ten/seven/five M3.23 list sizes).

**Graph.** `callgraph.py build archive/head256.img` prints `functions 8937
(leaf targets 1341), direct edges 21344, import edges 7757, unresolved indirect
calls 204` — the M3.23 corpus (C-3540), so the denominator is the same graph.

**Families read on a boot.** `run` ends `both tasks idle` with one undelivered
`send` (hex `0x1507`). Files the boot reads under `REFER001`: `POINT001.DAT`,
`ICODE001.DAT`, `ICADM001.DAT`. It reads **no** `ADDRE`, `FRWAY`, `INTER`,
`ZCODE` or `COORD` file:

```
family POINT  read files: ['REFER001/POINT001.DAT']
family ADDRE  read files: NONE
family FRWAY  read files: NONE
family INTER  read files: NONE
family ZCODE  read files: NONE
family COORD  read files: NONE
end: both tasks idle; message wait: ['0x1507']
```

**Readers per read tag** (the function starts the watch credits):

```
tag 0x0d00 REFER001/ICODE001.DAT        readers ['0x3eff20', '0x3f17a4', '0x3f255c']
tag 0x0d02 REFER001/ICODE001.DAT        readers ['0x3f0400', '0x3f2bc4', '0x40a8d0']
tag 0x0d10 REFER001/ICODE001.DAT        readers ['0x3f07f8', '0x3f1bb0']
tag 0x0d11 REFER001/ICODE001.DAT        readers ['0x3f0c7c']
```

`0x003f17a4` and `0x003f255c` are `ICADM` tag-`0x0d00` readers in the full row
(`ICADM001.DAT` `0x4c00` + `0x200`); `0x003f2bc4` reads the `0x0d02` header of
both `ICODE` and `ICADM`. `0x0040a8d0` is the shared REFER header reader the
`datask_l3.py` leaf list already names.

**Confirmed readers** (9), across `POINT`/`ICODE`/`ICADM`:

`0x003eff20`, `0x003f0400`, `0x003f07f8`, `0x003f0c7c`, `0x003f17a4`,
`0x003f1bb0`, `0x003f255c`, `0x003f2bc4`, `0x0040a8d0`.

**M3.23 recall per family** (confirmed readers inside the top-ten list / all
confirmed readers):

```
recall ICODE  3/9  (['0x3eff20', '0x3f07f8', '0x3f0c7c'])
recall POINT  0/9  ([])
recall REFER  0/9  ([])

```

The `ICODE` hits are three of M3.23's QC ten; `0x003eff20` is the 16th
candidate of the `ICODE` subtree (`rank --depth 6`), so it is *outside* the
top ten and the recall is `2/9` for the top-ten list. The 7 confirmed readers
M3.23's `ICODE`/`POINT`/`REFER` top tens do **not** contain are `0x003f0400`,
`0x003f17a4`, `0x003f1bb0`, `0x003f255c`, `0x003f2bc4`, `0x0040a8d0`,
`0x003eff20`.

**Graph note (corrects M3.23).** Re-running the QC query verbatim
(`rank g.json --depth 6 --top 10 --family REFER=… --family POINT=0x003ffe80
--family LCTBL=0x004125a8 --family ICODE=0x003f2cc0`) on the same `g.json`
puts `0x00409cc8` (shared, `share=0` by the tool's counter) at rank 2 of the
`ICODE` list, so `0x003f0e94`, `0x003f06a8` and `0x003eff20` fall to ranks
9–11: on the tree as committed `0x003eff20` is the **11th**, not the 8th,
candidate. The unusable candidates (`0x00409cc8`, `0x0040b358`, `0x003f6c88`,
`0x003f6e90`, `0x00409ba0`, `0x003f6f00`) are the resolver/read-request
helpers, not record readers, so they are not counted against recall: the
readers inside the ten are `0x003f0c7c` and `0x003f07f8` (`2/9`), and
`0x003eff20` is the third at 11. Recall is therefore `2/9` under either
reading; M3.23's prose that placed `0x003eff20` in the top ten is off by its
own re-run (a doc correction, not a new fact).

**Openers** (`0x003fee70`, one per family, on the card):

```
POINT  family  1 -> REFER001/POINT001.DAT          read_requests=0 r0=0x1
ADDRE  family  2 -> REFER001/ADDRE001.DAT          read_requests=0 r0=0x1
FRWAY  family  3 -> REFER001/FRWAY001.DAT          read_requests=0 r0=0x1
INTER  family  4 -> REFER001/INTER001.DAT          read_requests=0 r0=0x1
ZCODE  family 11 -> REFER001/ZCODE001.DAT          read_requests=0 r0=0x1
```

Every family resolves its file (`FRWAY001` is named, not found), the opener
returns 1, and **no** family opener queues a read request. This is the run-time
half of C-3546: the family is separable in the name it builds, but the opener
does not read the file — the read needs the state-2 task to reach it, and on a
boot that task issues no `ADDRE`/`INTER`/`FRWAY`/`ZCODE` request. `COORD001`
has no ctx +124 value and no opener (C-4666/C-4677), so it has no row here; its
absence is recorded in the `run` output above.

## Interpretation

- **FACT:** The boot's data-access task reads `POINT001.DAT`, `ICODE001.DAT` and
  `ICADM001.DAT` and stops at `both tasks idle` with message `0x1507`
  undelivered. It reads **no** `ADDRE`, `FRWAY`, `INTER`, `ZCODE` or `COORD`
  file. (Falsifier (c) did not fire: the family list is derived from the rows,
  not assumed.)
- **FACT:** Nine function starts load the returned REFER bytes; the read tag
  separates them into header (`0x0d02`: `0x003f0400`, `0x003f2bc4`,
  `0x0040a8d0`), page (`0x0d00`: `0x003eff20`, `0x003f17a4`, `0x003f255c`) and
  search-page (`0x0d10`/`0x0d11`: `0x003f07f8`, `0x003f1bb0`, `0x003f0c7c`)
  readers.
- **FACT:** M3.23's top-ten recall is `2/9` for the whole confirmed set
  (`0x003f07f8`, `0x003f0c7c`); `0x003eff20` is the 11th `ICODE` candidate
  (it was the 8th on M3.23's tree; the re-run above moved it out), and the
  other six are outside every top ten. The two `ICODE` rows C-4694 confirmed
  (`0x003f07f8`, `0x003f0c7c`) are in the top ten; the `ICADM`/header/page
  readers are not.
- **OBSERVED:** The family opener `0x003fee70` builds the right name for all
  five families but queues no read; the shared list C-3546 is not split into
  per-family *readers* by a run, because no family other than `POINT`/`LCTBL`
  reads its file on a boot.
- **HYPOTHESIS:** `ADDRE`/`INTER`/`FRWAY`/`ZCODE` are read only after the
  `0x1507` message the boot leaves queued is delivered (a route/POI request),
  which is outside this task's boot path.
- **UNKNOWN:** the per-family reader lists for `ADDRE`, `FRWAY`, `INTER`,
  `ZCODE` and `COORD`; what the `0x1507` sender is and what request delivers it.

## Conclusion

The task's Stop rule is reached: no family other than `POINT`/`LCTBL` reads its
file on the boot run, so `ADDRE`, `FRWAY`, `INTER`, `ZCODE` and `COORD` get a
recorded reason (`both tasks idle`, message `0x1507` undelivered) instead of a
reader list. The run does split the REFER list it *can* reach: nine readers of
`POINT`/`ICODE`/`ICADM` bytes, grouped by read tag, with M3.23's recall `2/9`
(whole set) and the seven missed readers named (`0x003eff20` is the 11th
`ICODE` candidate on the committed tree). `docs/format/firmware.md` and
`docs/research/reader-coverage.md` record the split; the per-family readers for
the four unread families stay open under M3.14/M3.16 and need the `0x1507`
request path (M9.52 → M9.53).
