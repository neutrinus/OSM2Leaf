# EXP-2026-11-06-M3.13: ADDRE (address) reader in build-A Navi.exe

- **Status:** done (negative / blocked: record parser not found in decodable code)
- **Date:** 2026-11-06
- **Sample:** `IMG256` = first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img`

- **Claims:** C-2180–C-2189
- **Supersedes:** none
- **Superseded by:** none

## Question

Which function in `Navi.exe` walks/reads a decoded `ADDRE0xx` record stream
(tags `c0`/`c8`/`c1`, `2*L` framing, name section `TT LL 00 ff`, point tokens
`TT 40 XX YY`, house-number range tokens, trailer/TOC as per refer.md C-970–C-979
/ M4.9), and can each grammar field be mapped to the instruction that consumes
it? Is ADDRE resolved through the same `REFER001` family mechanism as POINT?

## Hypothesis

Exploratory. ADDRE is a `REFER001` family file (refer.md), so it may resolve
through the same descriptor `0x14e8` → `REFER001`+`INDEX003.DAT` / volume-id
path as POINT (M3.11, C-880/C-881). The record parser that consumes the
M4.9 grammar is expected to read the tag byte (`0xc0|0xc8`), length `L` at `+1`,
advance by `2*L`, and parse the name marker / point / range tokens in
decompressed `ADDRE0xx` data.

## Interpretation

- **FACT (access path):** ADDRE is resolved through the same `REFER001` family
  mechanism as POINT: descriptor type `0x14e8` maps to `REFER001`+`INDEX003.DAT`
  (`0x004125a8`, C-880); the volume-id table `0x00179338` contains `ADDRE0`
  (`0x0017935c`, C-881) selected by the name builder `0x003fbed8` and resolved
  via volume lookup `0x0040b358` (`0x003fc084`); `fn 0x0040114e` additionally
  resolves `ADDRE0` via `0x0040b358` at `0x0040123c`. `ADDRE001.DAT` has no
  executable-section literal ref. This confirms the shared REFER001/INDEX003
  resolution path.
- **FACT (negative, scoped):** No function in any **uncompressed** build-A o32
  section implements the ADDRE record walk per C-970–C-979: 0 `c0`/`c8` tag
  pairs, 0 `and #0xf7`+`c0` mask walkers, 0 in-module `@(1)+cmp #0x40` point
  markers, 0 Navi.exe `@(1)+shll` `2*L` stride walkers; the 5 stride / 1
  marker hits (Speech*/IOLIB) lack tag/loop/record structure (rejected).
  Corpus = 282 sections / 23.6 MB, positive control = anchor xrefs resolve.
- **OBSERVED:** Navi.exe sec1 (16 MB virtual, compressed) and sec2 are not
  searchable; the ADDRE record/page parser may reside there, reached via the
  `0x14e8`/REFER001 read path once `ADDRE0xx` data is decompressed.
- **UNKNOWN:** VAs/arguments/output of the ADDRE record parser; which code
  consumes the directory/cell/trailer structures (C-970–C-972, C-977) vs the
  record grammar (C-973–C-976).

## Conclusion

M3.13 is **blocked with evidence** (class same as M3.11/POINT): (1) ADDRE is
confirmed to use the same `REFER001` family mechanism (`0x14e8` → `REFER001`+
`INDEX003.DAT`, id table `0x00179338`/`ADDRE0`, `0x003fbed8`/`0x0040b358`/
`0x004125a8`, `fn 0x0040114e`); (2) no ADDRE record/page parser consuming the
M4.9 grammar is found in any uncompressed build-A section (282 searched), so no
reader VA can be named and no C-970–C-979 field can be mapped to a consuming
instruction; (3) Navi.exe compressed sec1 (`0xff16ae` virtual) is the exact
blocker. `docs/format/refer.md` and `docs/format/firmware.md` record the access
path and the blocked mapping.
