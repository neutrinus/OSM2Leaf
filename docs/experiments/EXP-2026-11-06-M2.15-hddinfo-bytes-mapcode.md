## Observations

### 1. Router evaluates both checks (B `fn 0x03bd2ecc`, `0x03bd2ecc–0x03bd2efa`)

If entry `r4 == 0`: calls `fn 0x03bd2ad8` (pool `0x03bd2efc`→`0x03bd2ad8`, `jsr @r3` at `0x03bd2ed4/8`); if `r0 == 0` (`tst r0,r0; bf 0x03bd2ee4` not taken) dispatches `r4=0x50` via `fn 0x03bcafb8` (`0x03bd2ede/0/2`), **then continues** to call `fn 0x03bd2ce4` (`0x03bd2ee4/8`); on its failure dispatches `r4=0x51` (`0x03bd2eee/0/2`). So the router dispatches per failure and does not skip check 2 when check 1 fails (C-2080). C mirrors via pools `0x03bb2c54`→`0x03bb2858`, `0x03bb2c64`→`0x03bb2a64`.

### 2. HDD_INFO parse state machine / global `0x01f74b30` (B `fn 0x03bd2ad8` / `fn 0x03bd2ce4`)

Both functions load global pointer `0x01f74b30` into `r9` (pool `0x03bd2cb8` at `0x03bd2b70` in check 1; `0x03bd2ea8` at `0x03bd2da8` in check 2) and test `*r9` (`mov.b @r9,r3; tst r3,r3`). If nonzero they take the cached path (skip file read) and consume data from the global buffer at `0x01f74b30`. If zero they open `\SystemSD\VER_INFO\HDD_INFO.TXT` (`pool 0x03bd2cc0`→`0x03bc92f0`, `GENERIC_READ 0x80000000`), read 0x60 bytes into `r12=r15+0x44` (`mov #0x60,r6; jsr read fn 0x03bd3ad4` at `0x03bd2bb4/6/8`), parse, and close.

Parse loop (check 1 `0x03bd2bc0–0x03bd2c04`; check 2 same structure `0x03bd2e00+`): scans buffer bytes; on `\n` (10) / `\r` (13) sets `r10=1`; on a non-terminator when `r10==1` advances `r4 += 16` (next slot), resets `r2=0, r10=0`; if `r2 < 15` stores the char at `r9[r4+r2]` (global base `0x01f74b30`, displacement addressing). Thus lines are stored in **16-byte slots**: slot 0 = line 1 at global offset 0, slot 1 = line 2 at offset 16, slot 2 = line 3 at offset 32, etc., up to 15 chars per slot. Unwritten slot bytes keep their prior/cached value (C-2082). The `*r9!=0` branch and equal-path landing noted as open in M2.5/C-769 do not affect the mismatch decisions (fully observed); M2.15 establishes the slot layout and the cached/parse sharing.

### 3. Check 1 — `DIFFERENT MAP CODE` (0x50), B `fn 0x03bd2ad8` / C `fn 0x03bb2858`

**Unit side (NAND/system/kernel target-info):** `KernelIoControl(IOCTL 0x0101302C)` (pool `0x03bd2cac=0x0101302c`, thunk `0x03bca3e8`, `jsr @r3` at `0x03bd2b2c`; C pool `0x03bb2a2c/0x03baa0c0`). Copies **11 bytes** from `*(output_ptr @ r15+0x24) + 0x60` (+96) into `r11=r15+0x34` (`0x03bd2b36–0x03bd2b56`: 5 iterations × 2 bytes + 1 = 11; C `0x03bb28bc add #96,r3`).

**Card side (HDD_INFO):** after parse/cached, copies **11 bytes** from global slot 0 (`@r9+`, `r9=0x01f74b30`, offset 0 = line 1) into `r13=r15+0x24` (`0x03bd2c06–0x03bd2c1e`, 5×2+1). This is the first 11 bytes of the stripped line 1 content = HDD_INFO **line 1 `base_code` (M2.3 C-740), file offset `0x00`, length 11** (e.g. `QSD-302-100`).

**Compare:** byte-for-byte 11 bytes `r11[i]` vs `r13[i]`, `i=0..10` (`0x03bd2c1e–0x03bd2c3e`, bound `add #11,r3`). On mismatch formats/logs `VerInf:%s / HddInf:%s\r\n` (`pool 0x03bc9330`, `sprintf 0x03bcb7b4`, log `0x03bca3a0`) and returns `r0=0` → router dispatches `0x50` `DIFFERENT MAP CODE`. On equality returns the success path (`mov #1,r2` at `0x03bd2c92`, equal-path branch) → router proceeds to check 2 (C-2081, confirms/extends C-763–C-766).

### 4. Check 2 — `MAP DATA BASE UNMATCH` (0x51), B `fn 0x03bd2ce4` / C `fn 0x03bb2a64`

**Unit side:** `KernelIoControl(0x0101302C)` called to fill the target-info buffer. Reads 16-bit big-endian from output `+114` (`add #114,r2` at `0x03bd2d38`, `(b0<<8)|b1` stored as word at `r15+0x24` = max) and from output `+112` (`add #112,r2` at `0x03bd2d8a`, stored at `r15+0x20` = min; C `0x03bb2b0a`).

**Card side (HDD_INFO):** reads 3 bytes from global parse buffer at offsets **37, 38, 39** = slot 2 (line 3) + positions **5, 6, 7** (0-based within stripped line): `mov #37/38/39,r0; mov.b @(r0,r9),r4; jsr @0x03bd2a40` at `0x03bd2e3a–0x03bd2e54` (C `0x03bb2bba`). Each char is converted by `fn 0x03bd2a40` (B; C pool `0x03bb2c40`), which builds a 22-entry table `0-9a-fA-F` (indices 0–21) and returns the nibble value 0–15 (0–9 direct; a-f/A-F → 10–15; not-found → 0). Combined as `MapDBVer = ((d5*16)+d6)*16+d7` (`0x03bd2e56–0x03bd2e68`: two `shll2;shll2` stages with `or`).

**HDD_INFO mapping:** line **3 `build`** (M2.3 C-740, slot 2). Factory EU 2011 line 3 `02-110100-00` (file offset 26, 12 chars + CRLF): positions 5,6,7 = `'0','1','0'` (file offsets 31,32,33) → `0x010` = 16.

**Range check:** `r6 = MapDBVer`, `r5 = r15+0x20` (target `+112`, min), `r7 = r15+0x24` (target `+114`, max). Unsigned: if `r6 < r5` fail; if `r6 > r7` fail; else pass (`0x03bd2e6c–0x03bd2e7a`). On failure logs `MapDBVer : %d <= [%d] <= %d\r\n` (format `0x03bc9360`, `jsr @0x03bca3a0` at `0x03bd2e7c–0x03bd2e82`; args value,min,max) and returns `r0=0` → `MAP DATA BASE UNMATCH`. On pass returns 1 (C-2083, C-2084).

## Interpretation

- **FACT (both checks fully specified):** the card-side HDD_INFO bytes and the comparison/range logic for `DIFFERENT MAP CODE` and `MAP DATA BASE UNMATCH` are determined (C-2080–C-2084). The unit-side values are kernel target-info `0x0101302C` +96/+112/+114 (NAND/system), not the `0x06000000` copy and not an HDD_INFO text record in NAND (consistent with C-766).
- **OBSERVED/OPEN:** the exact numeric unit target-info values (+96/+112/+114) per market/unit are not known statically (C-2087), so check 2 cannot be given a definitive pass/fail for arbitrary MapDBVer values without those bounds (or L3). The 89-variant check-2 outcomes remain bounds-gated.
