# EXP-2026-11-22-M2.26: Navi.exe does not compute the SD PIN; no serial→PIN formula in the application

- **Status:** done (static; US card head). The Confirmation-code routine (a
  separate map-activation value) is not located here — follow-up.
- **Date:** 2026-11-22
- **Sample:** `US256` (first 256 MiB of `LEAF_2011-2012_US.img`,
  `tools/fetch_image.py --image US256`, SHA-256 pinned in that tool), image A
  (`--image-start 0x200200`), module `Navi.exe` (5 858 816 B; `.text` rva
  `0x1000` is `UNCOMPRESSED`, sec1/sec2 decoded with `cerom.py decompress`).
  Owner unit identity fields read from the Version / Unit-ID screens (photos,
  2026-11-22) are used only as offline test inputs; **no identifier value is
  recorded in this repo** (per AGENTS.md "Data, license, safety"). The fields
  used are the ones the menus label: model/Unit code, serial, Confirmation
  code, Product ID, Part Number, Unit ID, TCU ID, SIM ID and VIN.

- **Claims:** C-8330–C-8334
- **Supersedes:** none
- **Superseded by:** none

## Question

The owner asked whether the SD PIN could be worked out from a field a user can
read on the unit's menus (as a map-update reseller would need). Two
sub-questions: (1) does any menu number equal the PIN or map to it by a simple
formula; (2) does the navigation application (`Navi.exe`) contain a routine
that derives the PIN (or the Confirmation code) from the serial or model?

## Method

```bash
python3 tools/fetch_image.py --image US256 -o archive/us256.img
python3 tools/cerom.py --image-start 0x200200 archive/us256.img modules      # Navi.exe = mod 103
python3 tools/cerom.py --image-start 0x200200 archive/us256.img imports Navi.exe
python3 tools/cerom.py --image-start 0x200200 archive/us256.img decompress --modules Navi.exe --out <dir>
# offline (values never written to the repo): test each menu number against
#   the 4 PIN bytes under substring / difference / XOR / CRC-16 (8 variants) /
#   MD5 / SHA-1 / SHA-256, ASCII and UTF-16LE, first 4 bytes either endianness
# offline: brute the 16-bit Confirmation code from model+serial under the same set
```

## Observations

- **Menu numbers vs the PIN.** The PIN's 4 unit bytes are the value at PROD
  `+0x60` / `+0x100` (M2.25; not recorded). None of the menu fields equals it:
  serial (PROD `+0x50`), Unit ID (`+0x140`), Unit code (`+0x40`), Part Number
  (`+0xB0`), Product ID (`+0x20`), and TCU ID / SIM ID / VIN (the last three
  are not in the unit flash at all — M2.25 — they come from the TCU). Testing
  each field against the 4 PIN bytes under substring, difference, XOR, CRC-16
  (xmodem, ccitt, arc, modbus, x25, kermit, …), MD5, SHA-1 and SHA-256 (ASCII
  and UTF-16LE, either endianness): **no match**. This rules out the simple
  formulas, not every possible one.
- **`Navi.exe` imports.** 834 import slots; **none** names a lock, security,
  SDHC, CMD42, password or unlock function (the only "lock" hits are
  `STD_TimeClock_*`). The navigation application does not call the SD-lock path
  at all; the CMD42 password lives entirely in the boot loader / `SDHC.dll` /
  kernel-IOCTL layer (M2.13b, M2.25).
- **`Navi.exe` strings.** The readable `.text` strings matching `Serial`,
  `PIN`, `Operation`, `%04X`, `Confirm…` are unrelated debug text (serial-port
  check, traffic `nvc_trf_confirm_urgent_info`, UI layout). The
  Version-Information screen labels (`Unit code`, `Confirmation code`,
  `Navigation Version`) are **not** in `Navi.exe`, nor in the image A/B/C heads
  of US256: they live in a localisation/resource file on the card's FAT, so the
  Confirmation-code routine is not in this module's text.
- **Confirmation code.** It is a 16-bit value, not stored in PROD, so the unit
  computes it (the Nissan/Clarion map-update "confirmation → operation code"
  activation DRM). A blind brute from model+serial under the CRC/hash set above
  did not reproduce it; the real routine is in another module/resource
  (follow-up).

## Interpretation

- **VERIFIED (C-8330):** no number shown on the unit's menus equals the 4 PIN
  bytes, and none maps to them under the tested simple transforms.
- **VERIFIED (C-8331):** `Navi.exe` has no SD-lock / CMD42 / password import or
  code; the application never computes or sends the PIN. The PIN path is boot
  loader + `SDHC.dll` + kernel IOCTL `0x01013008`, fed from PROD (M2.13b,
  M2.25).
- **OBSERVED (C-8332):** the Confirmation code is a separate 16-bit
  map-activation value computed by the unit, not derivable to the 32-bit PIN
  and not taking the PIN as input; its routine is outside `Navi.exe`.
- **Interpretation of the reseller flow (C-8333):** a map-update card does not
  need the buyer's PIN. The unit locks the card itself from its own PROD PIN
  (M2.13b boot-time UNLOCK/LOCK; M2.13 the unit's SD LOCK menu), so a card can
  be shipped unlocked and the unit applies its own lock. What a buyer sends a
  reseller is the **Confirmation code** (map activation), which is unrelated to
  the CMD42 lock and does not expose the PIN.
- **HYPOTHESIS (C-8334):** no per-unit serial→PIN formula exists in the
  firmware examined (boot loader M2.25, `Navi.exe` M2.26); the 4 PIN bytes are
  a stored factory value (M2.25 C-8304). Only pairs of (serial, PIN) from other
  units, or the factory's PROD-writing tool, could prove or break this.

## Positive / negative controls

- Positive: `cerom.py` finds `Navi.exe`, `XGLDLL.dll`, `OSMDLL.dll` in image A
  of US256 exactly where M1.10 found them in the EU head; the decompressor
  reports `2 OK` for `Navi.exe`'s two compressed sections.
- Negative: the PIN-byte search over 12 MiB of unit dumps (M2.25) and the menu
  numbers here both come back empty, so the match at PROD `+0x60` / `+0x100` is
  the only one.

## Conclusion

Nothing in the navigation application derives the SD PIN, and no field a user
can read off the menus yields it. The reseller never needed the PIN: the unit
locks its own card. The only user-sent value in that flow is the Confirmation
code, a separate activation mechanism. No PIN, serial, VIN or vendor bytes are
committed.
