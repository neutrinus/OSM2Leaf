## Question

Is the `POINT0nn` page record walker really outside the readable code, and if
not, which function is it and does it walk a real US page the way
`refer.md` says?

## Hypothesis

The first pass assumed the walker tests `cmp/eq #0x60|#0x68` and reads `len2`
with `mov.b @(1,Rm)`. If the firmware instead reads the two bytes as **one
big-endian u16** (`tag<<8 | len2`), no `#0x60` immediate exists; the tag is
the top 6 bits (`0x60>>2 = 0x18`, `0x68>>2 = 0x1a`) and the length is
`w & 0x3ff` words. Search for the mask constants `0x03ff` / `0xfc00` instead.

**Falsifier:** (a) a compressed Navi.exe section carries `CNT_CODE` or
`MEM_EXECUTE` (then the walker could be there); (b) the candidate run on the
real page returns offsets different from `parse_page`; (c) the same run on the
**unswapped** page returns the same offsets (then the test cannot tell
anything).

## Observations

### 1. No compressed section is code

`point_walk_l3.py sections`:

```
Navi.exe realaddr=00011000 vsize=0054bd16 flags=68000020 plain CODE
Navi.exe realaddr=0055d000 vsize=00ff16ae flags=c8002040 COMPRESSED DATA
Navi.exe realaddr=0154f000 vsize=0000ed60 flags=48002040 COMPRESSED DATA
compressed=False code=False sections= 133 vsize=    745704
compressed=False code=True  sections= 149 vsize=  22767466
compressed=True  code=False sections= 245 vsize=  30212810
compressed executable sections: 0
```

sec1 is RW initialised data (`0x40|0x40000000|0x80000000`), 17,788 B of
payload for 16.7 MB of vsize — a `.data`+`.bss` image, mostly zeros. The IAT
(`0x55d000…`) and the globals used below (`0x00d5e4e4`, `0x00d53500`) live in
it. This is C-530 again; the first pass and the sixth/seventh PM passes
treated "75 % of Navi.exe is compressed" as "75 % of the code".

### 2. Constant scan

`consts`: 35 `mov.w/mov.l` loads of `0x03ff`, 13 of `0xfc00` in sec0. Both
cluster in `0x3f39d6–0x3f8d54` (the `HDLMAP_*` layer: string
`HDLMAP_Cws_RepSbTypeCd` at `0x17902c` is used by `0x3f8a5c`).

### 3. `fn 0x003f5194` — record n of a page

```
3f5194 mov r4,r2 ; mov.l #0xfc00,r7 ; r6=0 ; r3=0
3f519c loop: mov.w @r2,r1 ; extu.w r1,r4
3f51a2   and r7 ; cmp/eq r7  -> len = 0x4e8 (escape) | else len = w & 0x3ff
3f51b4   tst len -> return r6 (0)
3f51b8   cmp/eq r5,r3 -> return r2 (record n)
3f51be   r2 += 2*len ; r3++ ; cmp/hs #20000 -> stop
```

Arguments `r4 = page`, `r5 = n`; returns a pointer to record *n* or 0. It
calls nothing. Callers: only the dispatcher `fn 0x003f5cdc` (two loads), which
picks `0x3f5b88` / `0x3f5194` / `0x3f39c0` by comparing `r4` against buffer
slots of the table at `0x00d53500` (`+12,+20,+28,+36,+44,+80,+96,+112,+128,
+136,+144`).

`fn 0x003f39c0(p, n)` is the same walk as "skip n records", guarded by
`p == *0x00d5e4e4` (current page base) and `n < *0x00d5e4d0` (record count);
it uses `bf/s`. `fn 0x003f3314(&count, &base)` returns those two globals.
`fn 0x003f8a0c(rec)` = `(*(u16*)rec & 0xfc00) == 0xfc00`;
`fn 0x003f5c40` returns `rec+4` for a non-escape record (type 1 → caller
`0x3cc93c` maps it to 3); `fn 0x003f5c90` copies the last 8 bytes of a record
(`rec + 2*((w & 0x3ff) - 4)`).

### 5. The SDL (search) POI path — name accessor candidates

Debug string `" pPoiStr     : %s"` (`0x3ceac`) and its siblings
(`nPoiLen`, `nRecFlag`, `stdCharset`, `stdMesh`, `nRelateID`, `sCategory`,
`nMarkCode`, `sAreaCls`, `"===== DATA RECODE [%4d/%4d] printf ====="`) are
all loaded by **`fn 0x003a03b4`**, a debug dump of one POI record:

1. `0x3f3314(&total, &page)` (count + page base, the globals above);
2. `0x3cd8cc(page, n-1, &rec)` → `0x3cc93c` (classifies the record through
   `0x3f5c40`/`0x3f6220`);
3. **`0x3cd910` = `sdl_poi_get_data_recorde(db, rec, out)`** (its own name
   string `0x48b38`). For record class 3 it sets `out+4 = 0x40010`
   (`stdCharset`), `out+8 = 0x3ccd48(db,rec)` (`nRecFlag`), then
   **`out+12 (u16 nPoiLen) = 0x3d1150(db, rec', out+16 = pPoiStr)`**, and
   `0x3d071c(db, rec', out+28)` (`stdMesh`).
4. **`fn 0x003d1150(ctx, rec, char **out)`**: if `rec[14] != 0` →
   `*out = rec + 21`, return `rec[14]` (length); else → `fn 0x003d09a0`, which
   takes the length at `rec[19]`, text at `rec + 191`, and returns the part
   after the first separator byte read from `*0x005628e8` (`'@'` expected).
   `fn 0x003d1188` copies that name into a caller buffer (≤ 256 B, via
   `0x3d13c4` memset and `0x3d146c` copy).

`rec` here is `rec+4` of a walker record (C-2543). The offsets 14/21 do not
match POINT record 0 (`+0x5e`), so either this is a different record family
(search records) or the record is first unpacked — **open (M3.11c)**.

### 6. Where the page becomes native u16

No `mov.w @Rm(+),Rx ; swap.b ; mov.w …,@Rn` loop exists in sec0 (scan of all
4,884 `swap.b` sites with a load within 4 and a store within 5 halfwords and
a backward branch: 0 hits). The walker's `mov.w @r2` only works on a
swapped page (section 4 negative control). Either the swap is written another
way (byte loads + `shll8` + `or`, 32-bit `swap.b/swap.w/swap.b`), or it sits
in the chunk/zlib wrapper (`0x41c7e8`, `0x542148`), or the record reaches the
walker through a copy. **Open (M3.11b).**

### 7. The L3 interpreter is big-endian

`tools/l3_harness/engine.py` `PySh4._load/_store/_fetch` use
`int.from_bytes(..., "big")`; its synthetic snippet is big-endian. Navi.exe is
little-endian: run unmodified, the first instruction of `0x3f5194` decodes as
`0x4362` and raises `IllegalInstruction`. `PySh4` also refuses `bt/s`/`bf/s`,
used by `0x3f39c0` and `0x3cd910`. `point_walk_l3.py` subclasses it with
little-endian accessors; `0x3f5194` needs neither delay-slot branch.

## Interpretation

- **FACT:** build A has no compressed executable section; the "walker is in
  compressed sec1" blocker (C-2126) is refuted (C-2128/C-2129).
- **FACT:** `fn 0x003f5194(page, n)` is a page record walker whose framing is
  exactly `refer.md`'s `tag,len2` read as one big-endian u16 (6-bit type,
  10-bit word length, `0xfc00` escape = `0x4e8` words, `len 0` = end), and it
  returns the same 1000 record offsets as `parse_page` on the real US page.
- **FACT:** the first pass could not find it because it searched for
  `#0x60`/`#0x68` immediates and `@(1,Rm)` byte reads; the firmware uses
  neither.
- **INFERENCE:** a tag's two low bits are length bits 8–9 (`0x61` = 256+
  words). No current tool writes such records; a writer must keep
  `len <= 0x3ff` words and never emit `0xfc..` tags.
- **OBSERVED:** the SDL POI accessor chain (`0x3a03b4` → `0x3cd910` →
  `0x3d1150`) names the record fields the UI reads and gives a name pointer +
  length; it is not yet tied to the POINT record bytes.
- **UNKNOWN:** where the page is swapped to native u16; which function maps a
  POINT record to the name (M9.10's expected output).

## Conclusion

The record-walk half of M3.11 is done: `fn 0x003f5194` (args page, n →
pointer to record n), dispatcher `0x003f5cdc`, skip variant `0x003f39c0`, page
globals `0x00d5e4e4`/`0x00d5e4d0`, and an L3 run on the real US page that
matches `parse_page`. The name-copy half is narrowed to the SDL chain and
split out as M3.11c; the byte-order question as M3.11b. M1.2f is **not** a
dependency of any of them.
