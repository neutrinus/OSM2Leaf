## Question

Does booting image C (`kernel-off=0x5200200`) on `-M ze0` reach `TestMode.exe`
and its service screens, and what boot log stage is actually reached; if not,
which gate selects test mode, and which peer task in M8.H27…H62 owns each static
test item's driver/port?

## Hypothesis

Image C (88 modules, includes `TestMode.exe` #82 and `AppTimerDll.dll` #87)
will launch a test-mode process that build B lacks, giving the models a
vendor-diagnostics bench. **Falsifier (task line 5002):** C boots exactly like
B with no extra process — then test mode is entered another way and the EXP
says which.

The `ipl-C-mode7.txt` experiment appended one poke to force `CApi_GetBootMode`
(VA `0x03be3b60`, file `0x0552ed60`, phys `0x0832eb60`) to return 7 (boot mode
7 → mask `0x40`, the TestMode launch gate). Two attempts (one with a wrong
`mov #7,r2` encoding giving `Boot System Mode = 10`, one corrected
`mov #7,r0` = `0xE007`) both logged `Boot System Mode = 10`, no `TestMode.exe`
and no `Clarion Testmode`; the gate is not selectable with this `ipl-patch`
mechanism, so it is recorded as a negative control, not a pass.

### 3. Controls

- **Positive:** `cerom.py romhdr` at `0x5200200` prints C's distinct ROMHDR
  (88 modules, `physfirst 0x88000000`, `physlast 0x886683d8`); `cerom.py modules`
  lists `TestMode.exe` and `AppTimerDll.dll` only in C. The C boot reaches
  `Rom chain found` ×1, `XIP found` ×2, `Process Create!!!` ×40 and
  `Store Mgr Ready! [DSK1:]` ×1, so the boot and app-launch paths work.
- **Negative:** the card's `Boot System Mode` is `0` (log line
  `AppLch:: Boot System Mode = 0`); the AppLaunch table shows TestMode's
  `mode_mask = 0x40`, which mode 0 does not select. Forcing mode 7 via the IPL
  patch still logged `Boot System Mode = 10` with 0 TestMode/Clarion lines.
- **Control for "C is different from B":** C's `CAN.dll` (image C module 47,
  vbase `0x03b10000`) is in the crash return address; image A has no such
  module. This is a C-only process path, not identical-to-B behaviour.
- **Wrong-kernel control (from the tool's own selftest, not a third QEMU
  session):** `kernel_select.py --selftest` and the A/B/C ROMHDR census show
  the load only works with an `ECEC` segment; the precheck addresses come from
  `cerom.py`, not a guessed offset.

### 4. Scope

Two Analysis: 1 boot of image C at 90 s (`run-C`), 1 forced-mode boot attempt
(`run-C-mode7`, 90 s) plus 2 failed/retry attempts; 1 static module census
(image C, 88 modules); the 111-record AppLaunch table of C and 112-record table
of B; one uncompressed `TestMode.exe` section (`0x00011000`,
`0x4ca00` stored bytes) for the test-item strings. Excluded: the two compressed
`TestMode.exe` sections (`0x5f000`/`0x6b000`, `.data`/resources per C-2128),
L5 hardware, and any claim that a test-mode screen was displayed. No vendor
bytes were committed.

### 5. Falsifier

If C launched `TestMode.exe` with no extra gate, the hypothesis holds. If C
boots like B with no extra process, the falsifier fires and the EXP must name
the actual entry mechanism. Also refuting: any `Clarion Testmode`/`TestMode`
log line without mode 0x40, or a `TestMode.exe` process in the B kernel with
mode 0.

## Interpretation

- **FACT:** C is a distinct kernel that boots on `-M ze0` with the existing
  IPL-patch toolchain: `Rom chain found`, `XIP found` ×2, 40 process launches,
  `Store Mgr Ready! [DSK1:]`. Its own `CAN.dll` and `AppTimerDll.dll` run
  (O2, O3, O5).
- **FACT:** `TestMode.exe` is **not** a C-only launch entry: it is record #106
  in C's 111-record AppLaunch table and #107 in B's 112-record table, with
  identical `mode_mask 0x40`, id 0xc0, prio 200 and waits (O7). Booting C
  alone cannot enter test mode. The task's falsifier fired, and the mechanism
  is named: the launcher's boot-mode/mask gate (`CApi_GetBootMode` → mask
  `0x40` for mode 7; mode 9 = Service Tool Mode), matching EXP-M2.10's
  conclusion that entry is boot-mode-flag gated.
- **OBSERVED:** the C boot stops at a `device.exe` access violation with
  `RA=03b26e54(can.dll+0x16e54)` after repeated audio-micon timeouts
  (O5, O6). No `TestMode`/`Clarion Testmode` line and no test-mode process
  appears in any of the runs, including two attempts to force the mode (O8).
  The test-mode screens are therefore not reached at L4 in this session.
- **OBSERVED:** the static test-item table (O11) maps each `TestMode.exe`
  diagnostic to a driver/port printed by `ce_drivers.py` and to a peer task
  ID copied from `TODO.md`; two items (1seg/12seg TV) have no peer task and
  are marked "no dedicated peer" rather than invented.
- **UNKNOWN:** which physical trigger (service-tool boot flag vs key combo)
  sets mode 7/9 on a real unit — no key-combination string was found in
  `TestMode.exe` (EXP-M2.10). Whether the forced-mode patch failed because the
  mode is latched in the kernel OAL before `commondll.dll` is called.
- **Rule 13:** this is an L4 (full-system emulator) observation; no L5 claim.

## Conclusion

Image C boots on `-M ze0` with the existing `ze0_ipl.py` patch and reaches
process launch, but it does **not** launch `TestMode.exe`: the service screens
are selected by the AppLaunch `mode_mask 0x40` boot-mode gate, present
identically in kernels B and C, not by the C kernel image. The task's falsifier
fired and the entry mechanism is named (boot-mode flag → mask `0x40`/mode 7 or
`0xffff`/mode 9 "Service Tool Mode"). The C boot then faults in `device.exe`
with `RA` in C's `CAN.dll` after audio-micon timeouts, so no test-mode screen
is reached at L4. The static test-item → driver/port → peer-task table is
complete. No tool change. Marked `done` with the falsifier explicitly recorded
and the blocker named for the follow-up task that would let the boot continue.
