## Question

Which code fills the BSS table `0x00d53500` (EU2011) / `0x00c81100` (US2011), what is
its layout (slot size, slot count), where does each written slot come from, and does
running the real writer reproduce one entry that the POINT dispatcher then uses on a
factory page?

## Hypothesis

From the 2026-11-10 pass: the table is written by populate writers that copy page
pointers out of context objects, and the POINT dispatcher `fn 0x003f5cdc` (EU2011)
picks the walker when its page argument equals slot `+0x1c` (M9.38). So `fn 0x003faf04`
(EU2011), whose store `0x003fb034 mov.l r2,@(28,r9)` writes `+0x1c`, should, when
executed, write the page buffer pointer there, and the dispatcher should then reach
the walker on that buffer without any hand write.

**Falsifier:** the executed writer leaves `+0x1c` zero, writes something other than
the page object's buffer, or the dispatcher on the writer-filled table does not reach
the walker's page read / returns a different record offset than the walker alone.

1. **Sample and hash.** As above. The `.cmp`/`.ind` pairs are decoded with the same
   code path as M9.38 (`read_watch_l3.decoded_page`, then `swap16` to native u16).
2. **Commands.**

   ```bash
   S=/home/user/scratch/m3.22
   mkdir -p $S/eu $S/us
   (cd $S/eu && 7z x -y /home/user/OSM2Leaf/archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img 'REFER001/POINT010.DAT.*')
   (cd $S/us && 7z x -y /home/user/OSM2Leaf/archive/sd-images/LEAF_2011-2012_US.img 'REFER001/POINT010.DAT.*')
   python3 tools/d53500_writer.py --selftest
   python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe 0x003faf04 0x003ff6a0 0x003f5cdc 0x0040e858 0x0040e9dc 0x00412c60 0x0040e510 0x003f600c
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x00d53500
   python3 tools/sh4xref.py archive/us256.img Navi.exe --image-start 0x200200 --to 0x00c81100
   python3 tools/d53500_writer.py cases archive/head256.img --build eu2011
   python3 tools/d53500_writer.py cases archive/us256.img --build us2011
   python3 tools/d53500_writer.py writer archive/head256.img --cmp $S/eu/REFER001/POINT010.DAT.cmp --ind $S/eu/REFER001/POINT010.DAT.ind --build eu2011
   python3 tools/d53500_writer.py writer archive/us256.img --cmp $S/us/REFER001/POINT010.DAT.cmp --ind $S/us/REFER001/POINT010.DAT.ind --build us2011
   python3 tools/d53500_writer.py slots archive/head256.img --build eu2011
   python3 tools/d53500_writer.py slots archive/us256.img --build us2011
   python3 tools/read_watch_l3.py above archive/head256.img --cmp $S/eu/REFER001/POINT010.DAT.cmp --ind $S/eu/REFER001/POINT010.DAT.ind --build eu2011 --n 1
   ```

   `writer`: maps `Navi.exe` sec0 from the image and **every compressed section
   zero-filled** (BSS = zero at load; nothing invented), runs the type leaf
   (`0x0040e858` EU2011 / `0x004368b0` US2011) on a context of message type `0x14ef`
   to learn which global it names, then seeds only three declared inputs: that
   global's `+0 = OBJ`, `+16 = 1`, and `OBJ+20 = PAGE` (the decoded factory page).
   It calls the writer with `r5 = ctx` (type at `ctx+104`), `r7 = 32-byte message
   buffer`, watches every guest store into `table..table+0x100`, then — in the same
   engine, with the table exactly as the writer left it — calls the dispatcher on
   `(PAGE, n=1)` with a read watch on the page. `slots`: for each of the
   `sh4xref` load sites, a register tracker follows both branch arms in the
   containing pdata function (or `.pdata` gap), with delay slots and `jsr` killing
   r0–r7, and records every access through `table+k`.
3. **Controls.**
   - *Positive:* the walker alone on the same page (`writer` prints `walker alone`) and
     M9.38's hand-seeded `above` run must give the same `r0` as the writer-filled run.
   - *Negative:* the same writer run with message type `0x14f0` (its other branch, own
     global seeded the same way) must leave `+0x1c` zero, and the dispatcher must not
     reach the walker's page read. Selftest negatives: a host (set-up) write is never
     reported as a slot write; a tracker run whose table literal does not match finds
     only the seeded load's access; a wrong jump-table pool is a loud mismatch.
4. **Scope.** `Navi.exe` EU2011 (33 load sites, 17 functions/gaps) and US2011
   (29 load sites, 16 functions/gaps) of the table base literal; one populate writer
   executed per build (`0x14ef` path); one factory page per build (`POINT010`).
   Excluded: executing the other populate writers (`fn 0x003fc9c8`, `0x003fcbf0`,
   `0x003fd390`, `0x003fe774`, `0x00412c60` EU2011) and the clear routines (they need
   message contexts and imports, e.g. `0x003ec9fc` calls `GetTickCount`); writes
   whose base passes through memory or a pointer argument (the static tracker does
   not see them — the `+0x20` store below is one, found only by the run).
5. **Falsifier.** As stated under Hypothesis, checked by the seven `check` lines.

### Writer code (EU2011, `sh4dis`), the `0x14ef` path

- `r11 = 0x0040e858(ctx)`: a leaf (pdata GAP) that maps `@(ctx+104)` to a BSS global:
  `0x14ef → 0x014a98e0`, `0x14f0 → 0x0154ade0`, `0x14e4 → 0x014ac8e0`/`0x014a9220`,
  `0x14d0..0x14d1 → 0x014ac240`, else `0x014ac8e0`/`0x014ac1e0` by `@(ctx+124)`.
- `@(r11+16) == 0` or `r6 == -1` → message code 4, slots not touched (early exit).
- `0x0040e9dc(ctx, hdr, @(ctx+0xb0), table+0x20)` — `hdr` is the result of
  `0x0040ee4c(@(rec+8), 0)`, a lookup in a 100 × 80-byte BSS table at `0x0140e240`;
  `0x0040e9dc` writes `*out = 0`, then one of `hdr+{0,28,36,40,44,60,64,72,76}` chosen
  by the selector and `@(ctx+124)`.
- `0x003fb034: table[+0x1c] = *( *(0x014a98e0) + 20 )`.
- `0x14f0` path: `0x0040e9dc(…, sp+16)`, then `table[+0x3c] = p + 2*u16[p + 2*u16[p+2]]`
  for `p = *(sp+16)`, and `table[+0x38] = *(*(0x0154ade0) + 20)`.
- `fn 0x003fa574` (EU2011) clears the 72-byte global `0x014a98e0` (`memset` wrapper
  `0x003d13c4`, `r6 = 72`). Callers of the type leaf (EU2011 callgraph): `0x003faf04`,
  `0x003fc890`, `0x003fcbf0`, `0x003fd390`, `0x003fe774`, `0x003fef58`, `0x003ffeb4`,
  `0x00416d40`.

### Dispatcher slot roles (EU2011 `fn 0x003f5cdc`, `sh4dis`)

`r4 = page`, `r5 = n`. `page == [+0x0c]`, `[+0x14]` or `[+0x24]` with `n == 0` → returns
the page itself. `[+0x2c]` or `[+0x70]` → `0x003f5b88`. `[+0x1c]`, `[+0x60]`, `[+0x80]`,
`[+0x50]`, `[+0x88]`, `[+0x90]` → walker `0x003f5194`. Anything else → skip-n
`0x003f39c0`.

## Interpretation

- **FACT:** executed in PySh4 on both builds, the populate writer `fn 0x003faf04`
  (EU2011) / `0x00423ba8` (US2011) on message type `0x14ef` writes slot `+0x1c`
  at `0x003fb034` (EU2011) / `0x00423cd8` (US2011) with the value of
  `*(*(G)+20)`, where `G` is the BSS global its type leaf returns
  (`0x014a98e0` EU2011, `0x01319780` US2011). It also writes `+0x20` (through the
  pointer argument of `0x0040e9dc` EU2011 / `0x004369fc` US2011).
- **FACT:** with no hand write, the real dispatcher on the writer-filled table reaches
  the walker's 2-byte page read (`0x003f519c` EU2011, `0x0041db4c` US2011) and returns
  record 1 of the factory `POINT010` page at `+0x4e` (EU2011) / `+0x80` (US2011) —
  equal to the walker alone and to M9.38's hand-seeded run. One table entry is
  reproduced from a factory file through the firmware's own writer.
- **FACT (negative control):** type `0x14f0` takes the other branch and leaves `+0x1c`
  zero; the dispatcher then never reads the page through the walker.
- **OBSERVED:** the "table" is not an array of records: it is one structure of 4-byte
  slots, 46 words (`0xb8` B) in EU2011 and 44 words (`0xb0` B) in US2011; 44 / 42
  offsets are touched statically. Each slot holds a **page-buffer pointer** (or a
  pointer into one) for one family/context, written by the case of message switch
  `fn 0x003ff6a0` (EU2011) / `0x0042780c` (US2011) that matches the task-message
  type `0x14cc..0x14f0`; readers find a page's family by comparing a pointer with the
  slots (`fn 0x003f5cdc`, `fn 0x003f51e0`).
- **HYPOTHESIS:** `G+0` is the "current page object" of the POINT family and `G+20`
  its decoded-and-swapped page buffer, so whatever writes `G+0` is the page loader that
  M3.11b looks for (the swap is not on the `.cmp` path, M9.38).
- **UNKNOWN:** who stores `G+0` / `G+16` (next hop: the callers of the type leaf listed
  above); the data sources of the slots written by the writers that were not executed
  (`+0x04`, `+0x0c..+0x18`, `+0x2c`, `+0x7c`, `+0x80`, `+0x9c`, `+0xb0`, `+0xb4`) beyond
  the 2026-11-10 back-trace (context fields `@(20/24,rX)`, call results, handle words).
  Nothing in the table comes from a file header byte-for-byte: the writers store
  pointers, so there is no "schema" in the table for M4.16b to read.

## Conclusion

M3.22 is done: the writers are named (populate: `fn 0x003faf04`, `0x003fc9c8`,
`0x003fcbf0`, `0x003fd390`, `0x003fe774`, `0x00412c60` EU2011; clear: `0x0040dfa8`,
`0x00415fe8`, `0x0040e510` EU2011), with the message types that select them; the
layout is one structure of 4-byte pointer slots (46 EU2011 / 44 US2011); the source of
the POINT slot `+0x1c` is the page object named by `0x0040e858` (`0x014a98e0` EU2011),
field `+20`, proven by an L3 run that feeds the factory `POINT010` page through the real
writer, dispatcher and walker on both builds. `docs/format/firmware.md` gets the slot
map; claims C-5120–C-5127. For M3.11c the page context is: a page pointer `P` reaches
the POINT reader iff `P` sits in one of the walker slots (`+0x1c`, `+0x50`, `+0x60`,
`+0x80`, `+0x88`, `+0x90`); writing `G+0`/`G+20` and running the writer is enough —
no compressed `.data` is needed.
