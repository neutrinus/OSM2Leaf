# EXP-2026-11-22-M8.H31 — A synthetic GPS frame does not move the car position on `-M ze0` (negative)

- **Status:** blocked (negative result with controls; task Stop reached)
- **Date:** 2026-11-22
- **Task:** TODO **M8.H31**
- **Sample:** firmware/card image `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`,
  SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`;
  EU 2011 head inside it (ROM B `0x3e00200`); QEMU 11.1.3 with the 23-patch
  series including `ze0-h01-serial-chardevs.patch`.
- **Tools:** `tools/qemu-ze0/run.sh --card`, `tools/ze0_peers/gps.py`,

- **Claims:** C-7280–C-7289
- **Supersedes:** —
- **Superseded by:** —

## Question

If a host peer sends a GPS frame on `sci7` to the real firmware on `-M ze0`,
does the navigation accept it: does the live position word change, does the
card tile for the new position get read, and does a second screenshot differ
from the first?

## Hypothesis

The M8.H1 chardev plus the M8.H30 peer and the M8.H27 frame grammar are
enough: a fixed position sent on `sci7` reaches `OBJ_CarPos` and moves the map.
**Falsifier:** the position follows a frame with a wrong checksum, or no
change is observed although the peer demonstrably sent frames. **Stop:** if
the firmware ignores fixes without dead-reckoning inputs, record the filter
condition (VA) and hand over to M8.H32.

## Method

1. Prechecks: M8.H1 sci7 loopback (EXP-2026-11-22-M8.H1 O5/O6),
   `python3 tools/ze0_peers/gps.py --selftest` (EXP-2026-11-22-M8.H30), and
   the M8.H29 word/encoding (EXP-2026-11-22-M8.H29-fix-to-map). All passed.
2. One boot with the card-derived recipe and a peer on `sci7`:
   ```bash
   W=~/projekty/leafre-work/scratch/m8.h31/run4
   Q=/home/marek/.cache/qemu-ze0/build/qemu-system-sh4
   bash tools/qemu-ze0/run.sh --card \
     archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --qemu "$Q" --machine ze0 --icount shift=0,sleep=off --timeout 900 \
     --workdir "$W" --serial-peer "sci7=unix:$W/sci7.sock,server=on,wait=off"
   python3 tools/ze0_peers/gps.py --socket "$W/sci7.sock" \
     --control "$W/ctrl.sock" --fix 51.5074,-0.1278 --rate 1 --duration 880
   ```
3. After the map screen was up (384 000 non-black pixels), take a
   screenshot, dump the 128 MiB extension RAM (the user VA `0x00d940e4` is
   not readable through HMP `x` or the gdbstub `m` packet when the CPU is in
   kernel context — both answer `Cannot access memory` / `E14`), change the
   fix on the peer's control socket, wait and repeat:
   ```bash
   python3 tools/ze0_screenshot.py screen --monitor "$W/hmp.sock" -o "$W/shot_a.png"
   python3 tools/ze0_serial.py hmp "$W/hmp.sock" \
     "pmemsave 268435456 134217728 \"$W/ram_ext_a.bin\"" --timeout 300
   python3 -c "import socket; s=socket.socket(socket.AF_UNIX); \
     s.connect('$W/ctrl.sock'); s.sendall(b'gps 52.3676 4.9041'); s.close()"
   # later: shot_b.png, ram_ext_b.bin; control 'speed 30', 'heading 90',
   # 'on' and a third dump ram_ext_c.bin
   ```
4. Compare the two screenshots byte for byte and every aligned u32 of the
   three RAM dumps at physical `0x10000000…0x18000000`.
5. Corpus counted: one boot, one peer connection, three fixes (London
   51.5074/−0.1278, Amsterdam 52.3676/4.9041, with speed 30 and heading 90
   added for the third dump), two screenshots, three 128 MiB RAM dumps.

## Observations

**O1 — the peer and the screen were alive.** The map screen had 384 000
non-black pixels in both screenshots; `gps.py --selftest` and the M8.H1
loopback passed before the run. The peer's control socket accepted the
`gps LAT LON`, `speed`, `heading` and `on` commands (no error; the tool does
not echo replies back to the control client, which is why the client saw an
empty reply).

**O2 — no position word changed.** `ram_ext_a.bin`, `ram_ext_b.bin` and
`ram_ext_c.bin` are byte-identical: **0 differing aligned u32 words** across
128 MiB each. The default start word `0xa6a0cde3` (lat 51.5, lon −0.273) occurs
at 34 physical addresses in extension RAM, e.g. `0x17b7e000`, `0x17eec638`,
`0x17eed93c`; none of them moved to the words computed for the new fixes
(`0xa6a1cdf6` for London, `0xa747d07a` for Amsterdam).

**O3 — the screenshots are byte-identical.** Both PNGs have SHA-256
`66387215765503099ebda4d261532ae634e80d48c61a956bacd1b6704e681520`; no map
pan, no tile change, no visible position marker change.

**O4 — live-VA readback is not possible with the current monitor setup.**
HMP `x /1wx 0x00d940e4` answers `Cannot access memory`, gdbstub RSP `m`
answers `E14`, and HMP `xp` at that numeric address is a physical read of an
unmapped page. The word exists in extension RAM (O2), so the missing piece is
the user→physical translation for the current process, not the word itself.
`tools/ze0_position.py` was extended with `--gdb PORT` for virtual reads;
it cannot overcome the firmware's MMU context from the monitor.

**O5 — positive control.** In the same QEMU build the M8.H1 experiment saw
`sci7` guest TX and RX (C-6988, C-6984/C-6985), and the H30 selftest
reproduced the captured frames byte for byte (C-7271). So the failure is not
"the socket carried no bytes".

## Interpretation

- **FACT (C-7280):** with this boot recipe the map screen is up and stable
  (O1, O3).
- **FACT (C-7281):** a synthetically encoded `A0 00` position command does
  not change the position word in guest RAM (O2). The task's hypothesis is
  refuted; the falsifier "position follows a bad frame" does not fire because
  nothing follows any frame.
- **FACT (C-7282):** two screenshots taken before/after the fix are
  byte-identical (O3); the intended screenshot comparison pipeline works,
  but there is no movement to observe yet.
- **OBSERVED (C-7283):** the receiver's own fix-frame layout is still unknown
  (C-7267/C-7277). `A0 00` is the TestMode *host→receiver* seeding command,
  not a frame the receiver emits; M8.H29's decoder `0x003752e8` expects
  another layout (two u16s at record offsets +28/+34).
- **OBSERVED (C-7284):** no dead-reckoning inputs were supplied (wheel pulses,
  gyro, reverse = M8.H32); the task's Stop condition may also apply, but no
  firmware filter VA was observed, so it is not claimed.
- **FACT (C-7285):** HMP/gdbstub cannot read the user VA from the monitor
  context; RAM dump + physical scan is the working observation method
  (O2, O4). `ze0_position.py read --file IMAGE --offset` handles that form.
- **HYPOTHESIS (C-7286):** the firmware needs a genuine receiver fix frame
  and/or agreeing dead-reckoning samples before `OBJ_CarPos` is updated.
- **OBSERVED (C-7287):** the default position word is `0xa6a0cde3` = (51.5,
  −0.273) in extension RAM; this is consistent with the London start
  position, so the baseline is sane.
- **FACT (C-7288):** controls and the peer emitted frames (O1); M8.H1/H30
  are the positive control for the transport (O5).
- **OBSERVED (C-7289):** the Stop condition is reached with a negative
  result; the work is handed to a new task for the receiver fix frame and
  to M8.H32.

## Conclusion

M8.H31 is **blocked**, not done: the end-to-end chain works as far as the
`sci7` chardev and the frame encoder, but the firmware does not accept the
synthetic `A0 00` command as a fix, so the position word, the tile reads and
the screenshots do not change. The negative has positive controls (M8.H1
loopback and H30 selftest). Before repeating, the receiver's real fix-frame
layout must be derived (new task M8.H73), and dead-reckoning inputs (M8.H32)
may also be required.
