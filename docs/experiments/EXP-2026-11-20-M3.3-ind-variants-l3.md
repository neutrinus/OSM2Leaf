## Question

For each of the 8 `ind_mutate.py` variants of `ADDRE001.DAT.ind`, does the
firmware's `.ind` reader accept the file (and return the right bytes), and
does that match `cmpind.py`?

## Hypothesis

From M3.2/M3.2b (C-5102, C-5104, C-5330–C-5332) and the writer contract
(`cmp_reader_contract.py`, R1–R4 enforced, D1 "not tested by the firmware"):
`size_20000`, `size_8000` rejected at the `chunk_size` compare before any
`.cmp` read; `off0_1`, `off_last_m1`, `off_last_p1`, `off_last_0` rejected by
inflate (the reader seeks exactly by the index); `count_p1`, `count_m1` are not
checked by the code (D1), so their outcome is decided by what the reader asks
for — unknown before the run.

**Falsifier:** any of the six predicted rejections returning the file, or a
rejection happening at a different point than predicted (e.g. a size variant
rejected only after `.cmp` bytes were read); for the count variants nothing is
predicted, they are measured.

## Method

2. **Commands** (repo root; scratch outside the repo).

```bash

for v in size_20000 size_8000 count_p1 count_m1 off_last_m1 off_last_p1 off0_1 off_last_0; do

    --ind $S/mut/$v.ind --offset 0x10010 --length 0x100 --json > /home/user/scratch/m3.3/r2_$v.json; echo "$v rc=$?"

python3 tools/l3_harness/runner.py run cmp_ind_reader --image $IMG --cmp $S/card/REFER001/ADDRE001.DAT.cmp \
```

   The firmware verdict comes from the whole EU2011 layer (mount, `CMP.LST`
   match, open, read through the firmware's own `.ind` parser `0x0041c8c4`/
   `0x0041c5f0` and inflate), as specified in EXP-2026-11-20-M3.2. `ACCEPT` =

3. **Controls.** *Positive:* the factory `.ind` in the same batch must be

   self-test plants the agreement cases (`WRONG` vs `REJECT` disagree).
4. **Scope.** 1 pair (ADDRE001, 2 chunks), 8 variants + 1 control, whole-file
   reads, EU2011 only. Not covered: other pairs (POINT010-sized files with
   multi-batch reads), partial reads of a variant through the layer, US2011
   (the layer's VAs are not mapped for that build), the request producer
   above `0x0041855c`.
5. **Falsifier.** As under Hypothesis.

## Interpretation

- **FACT (C-5340):** firmware vs `cmpind.py` on the 8 variants: 6 agree
  (`size_20000`, `size_8000`, `off_last_m1`, `off_last_p1`, `off0_1`,
  `off_last_0` — both reject), 2 disagree (`count_p1`, `count_m1` —
  `cmpind.py` rejects, the firmware delivers). The six predicted rejections
  hold; the size variants stop at `fn 0x0041c8c4` +0x66 before any `.cmp` access,
  the four offset variants after the `.cmp` batch read, inside inflate.
- **FACT (C-5341):** `count_p1` is accepted byte-identical: the reader asks
  for chunks from the request's position and length (logical size 79,360 →
  chunks 0–1), so the extra entry is never visited, and chunk 1 is no longer
  "last", so its extent is taken as 0x10000 with only the requested 13,824 B
  copied out of the scratch buffer. The chunk count is not checked against the
  logical size.
- **FACT (C-5342):** `count_m1` is a **silent corruption**: with `count == 1`
  the single entry spans the whole `.cmp` (word 1 − offset 0) with extent =
  logical size; inflate stops at the end of the first stream (65,536 B) without
  error, and the read still returns 79,360. Bytes from 65,536 on are not the
  file. The firmware does not compare the inflated length with the entry's
  extent.
- **OBSERVED (C-5343):** `cmpind.py` is stricter than the firmware on exactly
  the D1 rule (count ↔ logical size); on R1–R4 and offset exactness the two
  agree. For a writer, `cmpind.py`/`cmp_reader_contract.py` acceptance is
  therefore sufficient but not necessary.
- **OBSERVED (C-5344):** the registered fragment target cannot judge `.ind`
  variants: it builds the chunk table itself (bypassing `0x0041c8c4`/
  `0x0041c5f0`), so a variant either breaks the harness (`BLOCKED`) or is
  decided by its Python reference (`MISMATCH`); its whole-file run exceeds the
  2M-instruction default. File-level verdicts need the layer run.
- **UNKNOWN:** whether the unit's caller (`0x0041855c` and up) notices a short
  inflate some other way (it receives r0 = requested length); the US2011
  build.

## Conclusion

M3.3's Done-when is met: accept/reject per variant is recorded from the
firmware's own `.ind` reader in PySh4 and compared with `cmpind.py` (6 agree,
2 disagree, both disagreements in the direction "firmware more lenient").
Writer consequence (added to `docs/format/cmp-ind.md`): the count must still
equal `ceil(logical/0x10000)` — a too-small count is read without error and
returns wrong bytes, so D1 is a writer obligation the firmware will not catch.
`reader-coverage.md` row 6 records the variant run. Open: US2011, multi-batch
files, the caller above `0x0041855c`.
