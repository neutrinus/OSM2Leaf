# EXP-2026-11-08-M3.11c: POINT record name accessor

- **Status:** done (static analysis + partial PySh4; full end-to-end PySh4
  blocked on HDLMAP page context in compressed `.data`, see Conclusion)
- **Date:** 2026-11-08
- **Sample:** `LEAF_2011-2012_US.img` (archive, read-only) for
  `REFER001/POINT010.DAT.cmp/.ind` (page `0x840ba0`, 42848 B compressed →
  130178 B, 1000 records; record 0 = `60 40 8f 9c …`, display name

## Question

Which function turns a raw `POINT` record (US `POINT010` page `0x840ba0`,
record 0, header `60 40 8f 9c …`) into the name string the UI shows, and what
are its VA, arguments and output?

## Hypothesis

The SDL debug-dump chain (M3.11 hint: `sdl_poi_get_data_recorde`
`0x003cd910` → name accessor `0x003d1150`) reads the display name from the raw
`POINT` record. **Falsifier:** `0x003d1150`'s `rec[14]`/`rec+21` offsets, or
any function in that chain, yield `HANA HEALTH CENTER…` for raw record 0.

## Observations

- **Precheck:** `sh4xref --to 0x3ceac` → pool `0x003a06fc` holds `0x0003ceac`,
  load `0x003a04b0` (r4) in `fn 0x003a03b4` (PASS).
- **`sdl_poi_get_data_recorde` `fn 0x003cd910`** `(r4=db, r5=ref, r6=out)`:
  `0x003cc93c` → status 3 (normal/0x003f5c40 path) sets decoded rec to
  `body = ref+4` (`0x003f5c40` returns 1, stores `rec+4`) and extracts name via
  `0x003d1150(db, body, out+16)` storing length at `out+12` (`0x3cd9ba–0x3cd9d2`).
  Status 1 path (`0x003cdc0c`): `0x003f5e78(db,rec)` → name length
  (`extu.w*2` → `out+12`, `0x3cdc1a`), `0x003f632c(db,rec)` → name pointer →
  `out+16` (`0x3cdc30`).
- **SDL name accessor `fn 0x003d1150`** `(r4, r5=rec, r6=&ptr) → r0=length`:
  `len = extu.b(rec[14])`; if `len==0` calls `fn 0x003d09a0` (delimiter split
  on byte at `*0x005628e8`, SDL layout `rec[19]`/base `rec+191`) and returns
  its result; else `*ptr = rec+21`, returns `len`. `fn 0x003d1188` wraps it
  (copies name via COREDLL, caps 255). **PySh4:** raw rec0 → r0=0; raw body
  (rec+4) → r0=0 (native & swapped).
- **HDLMAP name accessors (normal records):** `fn 0x003f632c(r4=db,r5=rec) → ptr`,
  `fn 0x003f5e78(r4=db,r5=rec) → len`. Both call `fn 0x003f8a0c(rec)` (escape
  classifier). For a normal 0x60xx record `0x003f8a0c` returns **-1** (not
  escape: header `& 0xfc00 != 0xfc00` → `movt`/sub yields -1; **PySh4 rec0: -1,
  native+swapped**), so they take the field-dispatch path: `0x003f632c` calls
  `fn 0x003f61bc(r4, rec, r6=5)` (field index 5); `0x003f5e78` calls
  `fn 0x003f5d98(r4, rec, r6=5)`. For an escape record (`0x003f8a0c` returns 0)
  they use fixed shortcuts `fn 0x003f8a80(rec)=rec+25` /
  `fn 0x003f8a90(rec)` (length computed from `rec[18]`). **PySh4 rec0:**
  `0x003f8a80`→`REC+25`, `0x003f8a90`→`2` (native)/`1` (swapped).
- **Field-dispatch chain (field 5 = facility/name):** `fn 0x003f61bc(r4,rec,r6)`
  → `0x003f51e0(r4)` context, `0x003f56bc(r4,rec,field)` locate,
  `0x003f57a8(r4)`, `0x003f5e10(loc,ctx,field)` extract pointer.
  `fn 0x003f5d98` locates via `0x003f56bc` and extracts a length byte from the
  field word (even/odd field index). `0x003f51e0` resolves `r4` against the
  HDLMAP handle table at `0x00d53500` (checks offsets `+12/+20/+28/…`) and
  performs an indirect call via `*0x0055d8f0` (`.data`) — **both in compressed
  `.data`/globals; PySh4 of `0x003f632c/0x003f5e78` on rec0 faults
  `UnmappedAccess 0x0055d8f0` with null context** (expected, context absent).
- **Raw record 0 name location (structural, 1000 recs of page `0x840ba0`):**
  `ff ff` marker pairs at `[0x5c,0x7e]`; display name = bytes between
  penultimate and trailing `ff ff` = rec `+0x5e`…`+0x7e` → `HANA HEALTH
  CENTER4590@HANA HWY\0`. Marker-count census: 999 records have exactly 2
  markers (name between them), 1 record (236) has 5 markers (body `ff ff`
  bytes present).

## Interpretation

- **FACT:** `0x003f632c`/`0x003f5e78` (Navi.exe text, head256 `92aa525d…`) are
  the HDLMAP-level POI name pointer/length accessors `(r4=db,r5=rec)`; for
  normal (non-escape, 0x60xx) records they dispatch to field index 5 via
  `0x003f61bc`/`0x003f5d98`. `sdl_poi_get_data_recorde` `0x003cd910` uses them
  on its status-1 path (`0x3cdc1a/0x3cdc30`). VAs/args verified by disassembly
  and xref.
- **FACT (refutation):** `fn 0x003d1150` (SDL, `rec[14]`/`rec+21`, fallback
  `0x003d09a0` on `*0x005628e8`) does **not** extract the raw POINT display name
  from record 0 (PySh4 raw/body/native/swapped → length 0 / no `HANA…`); it
  operates on SDL-decoded record layout. C-2545's offset mismatch is confirmed
  at the accessor level.
- **FACT:** `0x003f8a0c` classifies `0x6040` as not-escape (returns -1), so
  0x6040 records take the field-dispatch (not `rec+25`) name path.
- **OBSERVED:** The raw display name is the `ff ff`-delimited suffix
  (penultimate→trailing marker) at rec+`0x5e` for record 0; 999/1000 records on
  page `0x840ba0` share the 2-marker form.
- **HYPOTHESIS:** `0x003f61bc`/`0x003f56bc` field 5 resolves to the
  `ff ff`-delimited name region for 0x60xx POINT records (consistent with
  bit-offset "facility name 111"/variable text semantics in `refer.md` and the
  status-1 name extraction in `0x003cd910`), but the precise field→offset
  mapping requires the HDLMAP page field-descriptor table (runtime context).
- **UNKNOWN:** The exact byte/bit offset `0x003f56bc` computes for field 5 on
  page `0x840ba0` records (needs resolved page context from `0x00d53500` /
  `.data`), and whether status 3 (body path) ever carries the display name for
  0x60xx via a different decoded layout.

## Conclusion

The display-name accessor for a raw `POINT` record in `Navi.exe` is the
HDLMAP field-index-5 pair **`fn 0x003f632c(r4=db,r5=rec)→name ptr`** and
**`fn 0x003f5e78(r4=db,r5=rec)→name len`** (status-1 path of
`sdl_poi_get_data_recorde` `0x003cd910` at `0x3cdc30`/`0x3cdc1a`), dispatched
for normal 0x60xx records (`0x003f8a0c`→-1) through `fn 0x003f61bc`/`fn
0x003f5d98` (field 5) → `0x003f51e0`/`0x003f56bc`/`0x003f5e10`. The SDL
accessor `fn 0x003d1150(rec[14]/rec+21, fallback 0x003d09a0/*0x5628e8)` is
refuted for raw POINT display names (offset mismatch confirmed, PySh4 length 0).
**Open / Done-when gap:** a full end-to-end PySh4 run returning
`HANA HEALTH CENTER` for record 0 (and `OSM2LEAF TEST POI1` on the M5.12
renamed page) requires the HDLMAP page context (`0x00d53500` table +
`*0x0055d8f0` indirect) resident in compressed `.data` (sec1, C-2128) —
infeasible without M1.2f/M8.E1; simple sub-accessors were PySh4-verified.
`firmware.md`/`claims.md` record the VAs/args/chain; the L3 name confirmation
is deferred to M9.10 once context is available (M3.11b byte-order noted).
