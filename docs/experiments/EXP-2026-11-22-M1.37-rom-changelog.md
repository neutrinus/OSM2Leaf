- **Status:** done
- **Date:** 2026-11-22
- **Sample:** four 256 MiB firmware heads (vendor data, not committed), read from
  `archive/`. SHA-256, printed by `sha256sum archive/head256.img archive/eu2014-256.img
  archive/eu2016-256.img archive/us256.img`:
  - EU2011 head `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`

  - EU2014 head `30da3dce5c63dc5813f9c8092a1bbb4de493846371254f6cad4809d2bd219b58`
  - EU2016 head `208b4fdbe5b4cf7be5ffe14f82fc0444c98d295801331a0b4ca0f0a428eb135f`
- **Tools:** `python3 3.15.0` (standard library only — no `capstone`, no

## Question

For the seven modules the project cares about (`Navi.exe`, `Audio.exe`,
`BT_MGR.dll`, `BT_ENG.dll`, `BT_FW.dll`, `Speech.exe`, `DriveComputerCC.dll`),
what exactly changed between EU2011→EU2014 and EU2014→EU2016 — functions added,
removed or changed, new strings, new exports and COM methods — and does the
newer Bluetooth/navigation build contain anything we would want?

## Hypothesis

M1.36b showed *which* modules differ after reloc masking but not *what* changed.
A function-level diff built from each build's own `.pdata` plus `fn_match`'s
reloc-masked fingerprint should separate a real feature step (EU2011→EU2014)
from a small fix release (EU2014→EU2016), and should report the newer Bluetooth
modules as function-identical if M1.36b's equal-after-mask rows are meaningful.

**Falsifier:** if the tool reported 0 shared functions for a module whose code
`rom_atlas` says is equal after masking, if the EU2011 vs US2011 build-B control
reported any added/removed function (C-6281 would be contradicted), or if a
module with measured match rate < 50 % were hand-diffed instead of reported
`rewritten`. Any of these refutes the method or its conclusion.

## Method

1. **Sample and hash.** The four heads above; `sha256sum` output is quoted in
   Sample. The tool reads `READ_LIMIT = 128 << 20` bytes, which holds ROM
   segments A/B/C on all four cards (M1.36b established this on the same heads).

2. **Commands.** Runnable from the repository root with the four heads in
   `archive/` (placed by `python3 tools/fetch_image.py`):

   ```bash
   python3 tools/rom_changelog.py --selftest
   python3 tools/rom_changelog.py control --left EU2011=archive/head256.img \
       --right US2011=archive/us256.img --build B --modules BT_FW.dll nk.exe coredll.dll
   python3 tools/rom_atlas.py equal --head EU2011=archive/head256.img \
       --head US2011=archive/us256.img --negative-bcs
   python3 tools/rom_changelog.py table --left EU2011=archive/head256.img \
       --right EU2014=archive/eu2014-256.img --detail
   python3 tools/rom_changelog.py table --left EU2014=archive/eu2014-256.img \
       --right EU2016=archive/eu2016-256.img --detail
   sha256sum archive/head256.img archive/eu2014-256.img archive/eu2016-256.img archive/us256.img
   ```

   `table --json OUT` additionally writes the full row data; the generated
   per-module tables are checked in at `docs/research/rom-changelog.md`.

3. **Controls.**
   - *Positive, synthetic:* `rom_changelog.py --selftest` — 11 checks on
     `digest_sets`, `STRING_RE`, `message_like`, match-rate arithmetic and the
     `REWRITE_THRESHOLD == 0.50` Stop rule; prints `11 checks, 0 failures`.
     A duplicated-body module counts as one digest set, so code-identical
     modules do not read "changed".
   - *Positive, real:* `BT_FW.dll` build B (same size in all four cards) yields
     129 shared functions and 0 added/removed on the control; the two table
     commands report 139 functions in each build for it.
   - *Negative, real:* `python3 tools/rom_atlas.py equal --head
     EU2011=archive/head256.img --head US2011=archive/us256.img --negative-bcs`
     prints `control ROM B: 91/91 equal (as expected)`, `control ROM C: 88/88
     equal (as expected)` and exits 0 — this is the C-6281 byte-identity
     control. The independent `rom_changelog.py control --build B` then prints
     `BT_FW.dll shared=129 +0 -0 OK`, `nk.exe shared=1142 +0 -0 OK`,
     `coredll.dll shared=1709 +0 -0 OK`, `control PASS`. If masking or digest
     comparison were broken and read everything equal, or the pair really
     differed, these controls would fail.

4. **Scope.** Static diff only. Functions = `.pdata` records inside each
   module's code (compressed `.pdata` decoded with **that build's own** `nk.exe`
   `DECOMP_SECT`, located by matching the EU2011 reference function's
   reloc-masked digest — never a fitted address); function identity =
   `fn_match` digest **sets**; strings = printable ASCII runs >= 8 bytes of
   **plain** sections (the corpus excludes compressed sections, counted in the
   `csec` column); exports = `cerom` export table; COM = plain `.rgs` co-class.
   The seven named modules on 2 image pairs = 14 module rows. Excluded:
   compressed sections' full bodies, leaf code/literal pools outside `.pdata`
   records (counted only as `gap` halfwords), and any behaviour claim — no L3
   run or hardware.

5. **Falsifier.** Stated in Hypothesis. The control and the selftest both ran
   and passed; no module with match < 50 % was hand-diffed (`Audio.exe` at
   46.9 % in EU2011→EU2014 is reported `rewritten` with no named functions).

## Interpretation

- **FACT (C-6300):** `tools/rom_changelog.py` is a committed, reproducible
  tool; `--selftest` prints `11 checks, 0 failures` and the two `table`
  commands regenerate the checked-in per-module tables byte-for-byte.
- **FACT (C-6301):** build-B control — `rom_changelog.py control … --build B`
  prints 129/1142/1709 shared functions with `+0 -0` for `BT_FW.dll`, `nk.exe`,
  `coredll.dll` and `control PASS`; the C-6281 command
  `rom_atlas.py equal … --negative-bcs` prints B 91/91 and C 88/88 and exits 0.
- **FACT (C-6302):** the compressed-`.pdata` decoder comes from each build's own
  kernel: `DECOMP_SECT` EU2011/US2011 `0x88037464`, EU2014/EU2016 `0x88037994`,
  found by reloc-masked digest match of the EU2011 reference function, not by a
  fitted address.
- **FACT (C-6303):** EU2011→EU2014 changes all seven modules; six keep
  60.4–100 % of their function digests, `Audio.exe` alone is `rewritten` at
  46.9 % (Stop rule applied: no function names listed for it).
- **FACT (C-6304):** `Navi.exe` EU2011→EU2014 adds 1392 / removes 1278
  functions (81.2 % match) with new mesh-ID, route-guide and OBJ-event strings.
- **FACT (C-6305):** the 2011→2014 Bluetooth step is real in `BT_MGR.dll`
  (90.7 %, OPP/PBAP messages) and `BT_ENG.dll` (67.8 %, trace family replaced),
  while `BT_FW.dll` is 100 % function-identical (129 shared, 92 gap halfwords).
- **FACT (C-6306):** `Speech.exe` EU2011→EU2014 is 60.4 % (+2139/−1964) with new
  `PHONEME`/`TEXT` logs; `DriveComputerCC.dll` is 89.1 % (+28/−26).
- **FACT (C-6307):** EU2014→EU2016 is a small fix release: `Navi.exe` 99.1 %
  (+67/−66, build date string change), `Audio.exe` 94.6 % (+76/−75),
  `DriveComputerCC.dll` 92.0 % (+21/−14, window-handle rework).
- **FACT (C-6308):** `BT_MGR.dll`, `BT_ENG.dll`, `BT_FW.dll` and `Speech.exe` are
  100 % recorded-function-identical on EU2014→EU2016 (1306/1470/129/5406 shared,
  0 added/removed, only 10–133 gap halfwords): **the newer Bluetooth, speech
  and firmware builds add nothing recorded that we would want.**
- **FACT (C-6309):** no module gains or loses an export or a COM co-class in
  either pair (all 14 rows `+exp/-exp/+COM/-COM = 0`); the tables carry no
  vendor bytes.
- **OBSERVED:** `raw exec section = no` on every row; `gap` halfwords range
  10–1,552,259 and include relocated literal-pool words, so they are a lower
  bound of what the function diff did not look at, not a semantic count.
- **UNKNOWN:** whether the changed functions are reachable/used the same way in
  the newer builds (needs L3); what the compressed-section bodies contain;
  whether the `Audio.exe` rewrite is a better speech-guide path or a recompile.

## Conclusion

`tools/rom_changelog.py` turns M1.36b's module-level "different" verdicts into a
reproducible per-function/string/export changelog. On this corpus EU2011→EU2014
is a real feature step in every module (with `Audio.exe` rewritten at 46.9 %),
while EU2014→EU2016 is a small fix release in which the four Bluetooth/speech/
firmware modules are function-identical — so the newer Bluetooth stack has
nothing recorded worth taking. The C-6281 control holds (build B 0 changes).
Results are static counts and strings only; no behaviour is claimed without an
L3 run. The generated per-module tables are in `docs/research/rom-changelog.md`.
