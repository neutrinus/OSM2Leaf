# EXP-2026-11-22-M9.65: `vcard_l3.py` binds `STDDLL.dll` exports as native sub-calls

- **Status:** done (the binding works and the consumer passes its thunk; the
  unit-0 dereference it was expected to make is not in this function)
- **Date:** 2026-11-22
- **Sample:** EU 2011 firmware head `archive/head256.img`, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  EU 2011 card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`,
  SHA-256 `105e2032e480e8ba…76307`
- **Tools:** `python3` 3.15; `tools/vcard_l3.py`, `tools/poi_position_l3.py`,
  `tools/datask_req_l3.py`, `tools/cerom.py`, `tools/sh4fpu.py`
- **Claims:** C-6740–C-6749
- **Supersedes:** none
- **Superseded by:** none

## Question

Can `vcard_l3.py` run the real `STDDLL.dll` export behind a `Navi.exe` import
thunk (M9.65: the `STD_MeshPnt_*` mesh exports) as a native sub-call in the
same engine, so a consumer that calls one no longer stops with `Blocked:
missing import model`?

## Hypothesis

The `Navi.exe` thunk the RPF consumer calls (`0x003d1640`) tail-jumps through
IAT cell `0x0055da88`, which `cerom.py imports Navi.exe` resolves to
`STDDLL!STD_MeshPnt_isValid` (C-6022). Loading `STDDLL.dll`'s uncompressed
executable section into `vcard_l3`'s engine and pointing that IAT cell at the
export's real VA should let the consumer's `jsr` run the factory code and
return to the caller through the thunk's own `rts`. The consumer's first
unit-0 read should then follow.

- **Falsifier:** after binding, the consumer still faults before its first
  unit-0 read, or the bound `STD_MeshPnt_isValid` returns a different verdict
  than `poi_position_l3.py` on the same records.

## Method

1. **Sample and hash.** EU 2011 build A `Navi.exe` (`92aa525d…007f9`) and the
   factory EU card (`105e2032…76307`), both in `archive/`.
2. **Commands.** From the repo root:
   ```
   python3 -c "import sys;sys.path.insert(0,'tools');import vcard_l3 as V;print(len(V.MODELS),[k for k in V.MODELS if 'Mesh' in k])"
   python3 docs/experiments/m4.55-repro.py
   python3 docs/experiments/m9.65-stddll-parity.py archive/head256.img --dir ~/projekty/leafre-work/m5.14-poi/factory/REFER001 --file POINT010 --count 3
   python3 tools/poi_position_l3.py run archive/head256.img --dir ~/projekty/leafre-work/m5.14-poi/factory/REFER001 --file POINT010 --count 3
   python3 tools/vcard_l3.py --selftest
   python3 - <<'PY'
   import sys; sys.path.insert(0, "tools"); sys.path.insert(0, "tools/l3_harness")
   import vcard_l3 as V
   IMG = "archive/head256.img"; CARD = "archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img"
   EX = ("STD_MeshPnt_isValid", "STD_MeshPnt_chgLv", "STD_MeshID_judgeLevel",
         "STD_MeshPnt_initPrm", "STD_MeshPnt_chgMapPnt", "STD_MeshID_getAny")
   m = V.Machine(open(IMG, "rb").read(), V.make_card(None, CARD, {}), imports_text="",
                 native=("STDDLL.dll", EX))
   print("engine:", type(m.eng).__name__)
   for r in m.eng._regions:
       print("  %-30s %#010x..%#010x %s" % (r.name, r.va, r.va + r.size, r.rwx))
   print("native:", {k: "%#x" % v for k, v in m.native.items()})
   PY
   ```
3. **Controls.**
   - *Positive (the binding runs the factory export):* `m9.65-stddll-parity.py`
     takes the mesh point that `poi_position_l3.py` returns for 3 `POINT010`
     records (its verdict is the reference) and feeds it to
     `STD_MeshPnt_isValid` **inside** a `vcard_l3.Machine` whose `STDDLL` the
     native binding loaded. Agreement means two independent loads of the same
     factory module give the same verdict on identical input; no verdict is
     recomputed.
   - *Negative (wrong build / no binding):* without `native=`, the same consumer
     stops at `0x003367c2` with `Blocked: missing import model:
     STDDLL!STD_MeshPnt_isValid` and 0 unit-0 reads (EXP-2026-11-21-M4.55).
4. **Scope.** EU 2011 build A only. `STDDLL.dll`'s **one** uncompressed
   executable section (`rva 0x1000`, `vsize 0x19ce8`, `realaddr 0x03461000`,
   flags `0x68000020`); its four compressed sections are not mapped. The six
   named exports (the five the task lists plus `STD_MeshID_getAny`, the next
   one the consumer calls); the `STDDLL` import block of `Navi.exe` binds only
   those by name. `Navi.exe` sections, heap, stack and trampolines are reused
   unchanged; the map is checked for overlap before a range is added.
5. **Falsifier.** Stated above; the run's stop on `0x003367c2` when unbound and
   a clean return when bound is the observation that decides it.

## Interpretation

- **FACT:** `STDDLL.dll`'s uncompressed executable section (`realaddr
  `0x03461000`, `0x19ce8` bytes) maps at `0x03461000..0x0347b000` without
  overlapping any `Navi.exe` section, the heap, the stack or the trampolines;
  the six named exports resolve to the VAs above from `cerom.py exports`.
  `STD_MeshID_getAny` (`0x003d164c`) was added when the consumer called it
  after the first five were bound; it is the same `STDDLL` mesh family the
  task names.
- **FACT:** The IAT slot for each name comes from `cerom.py imports Navi.exe`
  (`STD_MeshPnt_isValid` → `0x0055da88`), not from a literal in the EXP prose.
- **FACT:** With the binding, `m4.55-repro.py` no longer faults at `0x003367c2`:
  the consumer returns `r0 0x0` after calling the real `STD_MeshPnt_isValid`
  twice (two valid mesh points). Without it, the same call faults with
  `Blocked: missing import model` (the negative control).
- **FACT:** `STD_MeshPnt_isValid` bound in `vcard_l3` gives the same verdict as
  `poi_position_l3.py` on the 3 sampled `POINT010` records (3/3).
- **OBSERVED — the plan was wrong on one point:** `0x003367a0` does **not**
  dereference the reply's unit-0 pointer itself. Its `jsr @r13` calls go to
  `0x0033629c(mode, mp, out)` (`initPrm` + `chgLv` + `isValid`), not to the
  reply list; it dispatches on `mov #76,r0; mov.l @(r0,r15),r2` (the caller's
  out-pointer) compared with `#1/#2/#3`, and it copies the reply entry into the
  buffer at `0x0061a020` (`0x00336dc0` writes the 32-byte entry there). So unit
  0 is **not read** in this function even when every mesh export is bound;
  `unit0 reads: 0` is correct for `0x003367a0`, not evidence of a remaining
  fault. The consumer that walks unit 0 is the next RPF stage, downstream of
  this one.
- **UNKNOWN:** which caller of `0x003367a0`/`0x00336dc0` reads the unit-0
  pointer it leaves at `0x0061a020`. That is M4.55's remaining work (the walk
  is not in the function this task was built to unblock), not an M9.65 defect.

## Conclusion

M9.65 is done: `vcard_l3.py` binds `STDDLL.dll`'s real exports as native
sub-calls (`Machine(..., native=("STDDLL.dll", …))`, `native_slots`), the
`Navi.exe` thunk `0x003d1640` now runs the factory `STD_MeshPnt_isValid`
(the repro no longer faults; `isValid` is 3/3 against `poi_position_l3.py`),
and the binding is covered by a vendor-free `--selftest`. The
`0x003367a0` consumer is **not** the unit-0 walker: it dispatches on its mode
argument and copies the reply entry into `0x0061a020`; M4.55's unit-0 read
therefore needs the downstream RPF stage, which this task did not have to
block. M4.55 returns to `open` (rule 15) with this record as its precheck.

## Corrections after navigator review

- The task text and the claim C-6024 expected `0x003367a0` itself to reach its
  first unit-0 read once the thunk was bound. Disassembly (`sh4dis.py`) shows
  it takes `(mode, mp, out)`, not the reply list, and never dereferences unit 0;
  the repro passes it a reply list and two valid mesh points for the `isValid`
  calls, which is what the binding had to make run. This is recorded as an
  OBSERVED fact above; the unit-0 walk belongs to the next RPF stage and is
  M4.55's remaining work.
