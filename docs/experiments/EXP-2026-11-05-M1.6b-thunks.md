## Question

M1.6b: can `cerom.py thunks [MODULE|--all]` turn every EXP-50 import stub
(`mov.l @(disp,PC),Rn; mov.l @Rn,R0; jmp @R0; nop`) and its direct
`mov.l @(disp,PC),Rn; jmp @Rn` variant into `stub_va, slot_va, module,
export, ordinal, section, confidence`, resolving the slot through the OFT and
the export tables, and report the uncovered stubs with a reason?

## Hypothesis

EXP-50 showed one stub (`0x003d1bb0`) whose literal is the IAT slot
`0x0055d390`, named `OBJDLL.dll!MAL_DataVol_getOffset` by the
OriginalFirstThunk. The same construction should hold for every stub: scan the
uncompressed code sections, read the stub's literal (the slot VA), find the
slot in the importing module's OFT, then take the name — and the ordinal —
from the exporting module's export table. Slots that are not import entries,
literals outside the image, or slots claimed by two different import entries
must come out as unresolved with a reason, never as a guessed name.

Definition used by the tool:

- **Stub**: `mov.l @(disp,PC),Rn` (`0xDnnn`) followed by
  `mov.l @Rn,R0` (`0x6n02`) + `jmp @R0` (`0x402B`) + `nop` (`0x0009`)
  (`4-insn`, the EXP-50 pattern), or `jmp @Rn` (`0x4n2B`) with a delay-slot
  `nop` (`3-insn`) or without one (`2-insn`). Only uncompressed sections with
  `CNT_CODE`/`MEM_EXECUTE` are scanned.
- **Stub VA** = section `realaddr` + offset; **slot VA** = the literal value
  the stub loads (`((stub_va + 4) & ~3) + disp*4`, read from the image). The
  literal is never dereferenced, so a compressed `.data` slot is fine.
- **Resolution**: slot → the importing module's OFT entry (`imports`) → the
  exporting DLL's export table (`exports`) for name and ordinal. A stub is
  `resolved` only when the slot is inside the image and exactly one import
  entry names it.
- **Reasons** for an unresolved stub: `slot outside image`, `no export match`
  (no OFT entry names the slot, or an ordinal import whose exporter is absent),
  `ambiguous duplicate (…)` (two different import entries claim the slot).
- **Confidence**: `high` = 4-insn pattern and the export table confirmed the
  name/ordinal; `medium` = 4-insn without that confirmation, or 3-insn with it;
  `low` = 2-insn, or unresolved.
- **Coverage** is printed as `resolved/total` plus a percentage, twice: **stub
  coverage** (named stubs / detected stubs) and **slot coverage** (import slots
  with at least one stub / all import slots — the 846-slot measure).
  `--min-coverage N` exits 1 when either is below `N`.

JSON record (stable key order): `stub_va, slot_va, module, export, ordinal,
section, confidence, status, reason, pattern, owner, segment` — `module` /
`export` / `ordinal` name the **exporter**, `owner` is the module the stub
lives in, `pattern` is `4-insn` / `3-insn` / `2-insn`.

## Interpretation

- **FACT:** the tool implements the M1.6b contract. On the synthetic ROM it
  finds exactly the three planted stubs, computes their VAs from `realaddr` +
  offset (`0x8cae5e00`, `0x8cae5e20`, `0x8cae5e40`), reads the slot VAs from
  the literals (`0x8cae6f00`, `0x8cae6f04`, `0x7fff0000`), names two of them
  through `imports` + `exports` (`OBJDLL.DLL!MAL_DataVol_getOffset` #5,
  `…!MAL_DataVol_getSize` #6) and reports the third as `slot outside image`
  instead of inventing a name.
- **OBSERVED:** both import routes resolve: a named OFT entry gains its ordinal
  from the export table, and an ordinal-only entry gains its name from it.
  Coverage arithmetic is `2/3 = 66.7 %` (stubs) and `2/2 = 100.0 %` (slots);
  `--min-coverage` is a strict `>=` on both, and the exit codes are 0 / 1 / 2
  as specified.
- **OBSERVED:** the tool prints nothing and exits 2 when a selected module has
  no stub, so an empty scan is a failure, not a silent pass.
- **UNKNOWN (image-run):** whether the real `Navi.exe` reaches the 95 % /
  846-slot threshold. This task could not read the image, so the number is not
  measured here and no percentage is claimed.
- **HYPOTHESIS:** the COREDLL imports will mostly resolve by name from the OFT
  even though `COREDLL.dll` is a separate module, so stub coverage should be
  high while slot coverage is the metric that can fail. That is untested.
