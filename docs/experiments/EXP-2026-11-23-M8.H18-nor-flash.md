## Question

Why does the `VSram` driver get `IOCTL_FMD_READ` errors on `-M ze0,flash=`?
What model of the flash removes them? What does the locator do once its
backup loads?

## Observations

O1 (driver). `flash.dll` exports `FMD_Init`, `FMD_IOControl`
(`0x03d6a2a0`), `FMD_Read`/`FMD_Write` and the rest. Its `.text` names six
chips (`SST_SST38VF6401-90`, `SST_SST39VF3201`, `SPANSION_S29JL032H`,
`SPANSION_S29AL032D`, `MXIC_MX29LV320DB`, `ST_M29W320EB`). The chip table at
`0x03d625b0` has 0x4c-byte rows with the device codes 0x536b, 0x235b,
0x227e, 0x22f9, 0x22a8 and 0x2257, which give the indexes 0–5. The command
table at `0x03d62aa0` holds the autoselect entry (0x5555/0xaa, 0x2aaa/0x55,
0x5555/0x90) and the exit (… 0xf0). `CCmdSeqCtl::GetDeviceCode`
(`0x03d6ade8`) reads the halfword at word 1.

O2 (why it failed). In S11 (ROM at phys 0) every `FMD_IOControl` call
returned 0. Those were codes 0x80112000 (read), 0x80112010 and 0x8011200c,
22 calls during boot. The call goes to `0x03d6a600`, which first asks the
chip object (`0x0003ac00`) through vtable slot 94, `0x03d6b900`: index < 6.
The index read 6, so the chip was "unknown". A ROM ignores the autoselect
writes and returns array data, so no device code matches.

O3 (model). `ze0-h18-nor-flash.patch` makes an 8 MiB `flash=` a QEMU
`pflash_cfi02` at phys 0:

- x16 bus;
- 8 × 8 KiB boot blocks, then 127 × 64 KiB (the map in
  `docs/hardware/unit-flash.md`);
- id 0x00bf/0x536b, SST38VF6401, the only 8 MiB chip in the table;
- unlock addresses 0x555/0x2aa. The 0x5555/0x2aaa writes match after the
  model's 11-bit mask.

The file is opened through a block backend. Without `flash-rw=on`, writes
go to a temporary overlay (`BDRV_O_SNAPSHOT`), so the dump never changes.
Other sizes keep the M8.C1m read-only ROM.

O4 (boot, S12). The serial log has no `IOCTL_FMD_READ`/`IOCTL_FMD_ERASE`
errors, no `OBJ_BackUp_Load Error` and no `UnLoad BackUpInfo
@OBJ_Carpos_initialize`. S10 had 8 FMD errors, 3 `OBJ_BackUp_Load` errors
and the `Carpos` error. FlashManager logs `FLM_Init -` with no error.

O5 (car position, S12). After unlock the map shows rural roads (Simpson Rd,
Tar Kiln Rd, Bishop…, Albright) instead of LAX. `OBJ_CarPos_write` (called at
`0x00497e5c`) carries the position word `0x9c03a3c0`, which is lat code
0x9c03 and lon code 0xa3c0. That decodes to (37.35, −84.55), in Kentucky.
This is where Marek's car shows itself (memory of PR #531/#539). The current
road link `*0x00dbdc30` is `0x00dc9980` (it was 0 in S10).

With a GPS fix at Wrocław (51.11, 17.03), stat 0x30: the mesh conversion
`0x00452f54` returns −1, the history entry is empty, the flags word is 0x2c,
and the car stays in Kentucky. This is the car's behaviour, reproduced.

O6 (Chicago, S12). With a fix at Chicago (41.8781, −87.6298):

- `0x0049e08c` computes the distance value 0x2710 (> 13) and the flags word
  reads 0x17c. So the bit that `0x0049e08c` sets is **0x100, not 0x200**
  (`mov #64; shll2` at `0x0049e1b0`). This corrects M8.H78 O2/C-8642.
- Bit 0x200 is set only by `0x0049e244`, when bits 0x01–0x80 and 0x100 are
  all set. Here 0x01, 0x02 and 0x80 are missing.
- Bit 0x80 needs the locator input halfword +22 ≥ 100 (`0x0049eeea`). In S12
  it reads 0. GPS speed 50 km/h does not change it. With speed 50 the word
  fell to 0x3c, so bit 0x40 is lost as well.
- So the car does not jump to Chicago. The +22 field is the vehicle's own
  speed or distance input (dead reckoning, M8.H32). Not tested.

O7 (writes). S13 (a copy of the dump, `flash-rw=on`, 400 s): the file is
byte-identical to the original. S14 (150 s, trace): 16 unlock sequences,
the autoselect enter and exit for the ID reads, and no program, sector
erase or chip erase. The guest writes the backup only on events this boot
does not produce. Ignition-off is likely, but not checked.

## Result

`FMD1:` needs a real AMD-style NOR chip with a device code from
`flash.dll`'s table. With the emulated SST38VF6401, the `VSram` and
FlashManager reads succeed, `OBJ_BackUp_Load` works, and the locator starts
from the unit's saved state: Kentucky, on a road link. A fix in Poland is
rejected exactly as in the car. A fix in the US is held back by the
"relocate to GPS" condition, which needs the vehicle's own speed input
(bit 0x80) and a steady GPS history (bits 0x01, 0x02).

Done-when: "FlashManager init returns success" is met (O4). "A guest write
is in the file after exit, and a second boot reads it back" is not shown,
because the guest made no write (O7). The falsifier ("boots identically
with and without the flash device") does not fire: O4/O5 differ from S10.
