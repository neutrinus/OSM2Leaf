## Question

Does the `LOC_map` shape walk `fn 0x0041f3dc` read the served record's shape
buffer by a rule a host model can reproduce from the buffer alone — the ordered
list of loaded offsets and the four result-table entries — and what leaves a
generated shape uncounted?

## Hypothesis

The M9.66 read tables (C-6774, C-6775) are a complete spec: 12 rows at byte
`4 + 4i`; a shape header of four words; first point at
`B + 0xe + 2·(w3 & 3) + 2·(w0 >> 13)`; each further point
`4 + 2·[x bits 0x1800 not both set] + 2·[y bit 0x2000] + 2·[y bit 0x1000] +
2·[y bit 0x0800]` bytes on; one reference word per plain point. **Falsifier:**
the model matches F but cannot match G or other records without a per-record
exception.

## Interpretation

- **FACT:** the shape/point **read order** is a pure function of the shape
  buffer: the 12 row counts, the (start, count) pairs, the shape headers, and
  the (x, y) point sequence match the firmware's non-reference read list on F
  (2849/2849), G (44/44) and the two other meshes (421/421, 693/693). Rules:
  row counts at byte `4 + 4i` with abort `>= 0x7d0`; a row's shapes from byte
  `4·start`; header four words; first point at
  `B + 0xe + 2·(w3 & 3) + 2·(w0 >> 13)`; next point
  `4 + 2·[x bits 0x1800 not both set] + 2·[y bit 0x2000] + 2·[y bit 0x1000] +
  2·[y bit 0x0800]`; next shape at `B + 2·(w0 & 0x1fff)`.
- **FACT:** the reference **word** of a plain point at byte `P` is at
  `P + 4 + 2·((y >> 13) & 1)` (`415/415` on F, `37/37`, `55/55`). The earlier
  reading that the block "targets a different point than its own word names"
  was a **block/point mispairing** in the first draft; it is retracted. The
  word `w != 0xffff` names the point at byte `2·w` (x) and `2·(w + 1)` (y),
  and the firmware reads that `y` only when the slot's `x & 0x1800 != 0`
  (`0x004201c8`): F `350/350`, M `34/34`, `49/49`; `0xffff` reads no target.
- **FACT:** the **count** is not a buffer-only function. Each reference slot
  looks its point up in a cell→node table `*0x00ec3600` (base `0x0ea1a00`)
  with index `q = (y>>9 & ~1) + (x>>10)` (`0x004200f6`–`0x0042010c`); a node
  `-1` skips, else `+1` lands in that cell's result-table row
  (`0x0042020a`–`0x00420238`). The table is filled outside `fn 0x0041f3dc`.
  In a plain G run every node is `0` and nothing counts; a one-pair patch of
  G's first point to `x=y=0x40` (`q=0`) makes the table hold a node and turns
  row 1's count to 2. This names the zero-count cause: **where the points
  fall in the cell table, not the reference words.**
- **RETRACTED (draft only):** "the block reads a point at a different offset
  than its own reference word names, through a point-node index whose slot the
  coordinates do not give." The offsets are `P + 4 + 2·((y>>13)&1)` and
  `2·(w + 1)`; the index `q` is a plain cell formula; the node table it
  indexes is the open input, not a hidden target rule.
- **UNKNOWN:** the rule that fills `*0x00ec3600` (a tile/record-derived node
  table) so the four counts can be predicted; the pipelined interleave order
  (the model matches the *read set and per-read rules*, not the interleaved
  sequence or its SHA-1); the divided branch `fn 0x004205b8`; 20 more records;
  the US2011 twins.

## Conclusion

The shape/point **read order** and the reference-**word**/**target** rules of
`fn 0x0041f3dc` are closed as a host model that matches the firmware's reads
on F, G and two other meshes (no per-record exception). The **count** stage
that turns points into the four result-table entries is **not** closed: it
indexes a cell→node table `*0x00ec3600` (filled outside the walk) and a `-1`
node skips. G counts nothing because its points land in cells whose nodes are
`0`; a low-cell patch (`x=y=0x40`) gives a non-zero count (row 1 = 2). The
Done-when (full-trace SHA-1 on F, G and 20 more records) is **not** met, so
this task is **blocked**, not done. `docs/format/map-tiles.md` now states the
shape layout and the two verified reference rules; the count rule is marked
open.
