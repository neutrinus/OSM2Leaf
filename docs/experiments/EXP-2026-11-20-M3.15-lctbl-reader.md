## Question

Which firmware functions walk an `LCTBL001.DAT` name record and decode its
name strings, and which text encoding does the decode assume? M4.16b decoded
the record directory from the card bytes; M9.38 found `0x0040de98` reads the
page buffer (C-3607); M3.23 ranked the reachable functions (C-3544). This run
names the record-walk and string-decode VAs and states the encoding the code
assumes, with a VAs-per-field table (the `Done when` of M3.15).

## Hypothesis

The C-884 field directory (`0x003f61bc` + `0x003f56bc`/`0x003f57a8`/
`0x003f5d98`/`0x003f5e10`, M4.16b) is the record walk; the twelve
`LCTBL001` catalog fields are read through it by one extractor per field; a
name field is a 16-bit-word string converted to bytes by a per-character loop
that takes the high byte first (big-endian card halfword → native little-endian
`u16`), and that byte is the name character under CP_ACP. If so, the
extractors and the convert loop are the VAs `rdstm.md` must list, and the
assumed encoding is a single code page, not two-byte text.

**Falsifier:** no extractor reads a name field through `0x003f61bc`, or the
convert loop is not on the field path, or the code assumes UTF-16 / a byte
order other than high-byte-first, or a cited VA is not `CODE sec0`.

## Observations

**`va_class.py` (`Navi.exe`, `--resolve-with 0x3e00200`).** All twenty cited
VAs print `CODE sec0`; the three sections print:
`sec0 start=0x00011000 vsize=0x54bd16 init=0x54bd16 exec plain`,
`sec1 start=0x0055d000 vsize=0xff16ae init=0x1801a COMPRESSED`,
`sec2 start=0x0154f000 vsize=0xed60 init=0xed60 COMPRESSED`.

**The record walk (C-884 directory).** `pdata.py fn`:
`0x003f61bc START length 0x64`, `0x003f56bc START length 0xec`,
`0x003f57a8 START length 0x34`, `0x003f5d98 START length 0x78`,
`0x003f5e10 START length 0x66`, `0x003f51e0 START length 0xe0`.
`sh4xref --calls 0x003f61bc` is the accessor body:
`0x003f61da jsr 0x003f56bc` (data start), `0x003f61ea jsr 0x003f57a8`
(field count), `0x003f61f0 jsr 0x003f5e10` (field offset). `sh4xref --to
0x003f61bc` lists 26 caller sites; the twelve extractors below are 26 of
them and the two string readers are two more.

**The extractor set (`sh4xref --calls 0x003bc960` + `--calls 0x003bc028`).**
`0x003bc960` (TMC record decoder, C-882) fills the 496-byte struct at
`0x006f3918` by calling, in field order:

| Field (catalog column) | Struct offset | Extractor VA | Accessor index |
| --- | --- | --- | --- |
| 0 type (location type) | `+0x04` | `0x003f66b8` | 0 |
| 2 road name | `+0x12`/`+0x40` | `0x003bc194` (via `0x003f60ec`) | 1 |
| 1 road number | `+0x14`/`+0x1c` | `0x003bc028` (via `0x003f60e0`) | 2 |
| 3 primary location | `+0x16`/`+0xc4` | `0x003bc300` (via `0x003f60f8`) | 3 |
| 4 secondary location | `+0x18`/`+0x148` | `0x003bc470` (via `0x003f6104`) | 4 |
| 5 area | `+0x06` | `0x003f6734` | 5 |
| 6 linear | `+0x08` | `0x003f6780` | 6 |
| 7 negative | `+0x0a` | `0x003f67cc` | 7 |
| 8 positive | `+0x0c` | `0x003f6818` | 8 |
| 9 urban | `+0x0e` | `0x003f6864` | 9 |
| 10 exit/junction | `+0x1a`/`+0x1cc` | `0x003bc748` (via `0x003f6110`) | 10 |
| 11 inter-section | `+0x10` | `0x003f68bc` (via `0x003f68b0`) | 11 |

The index column is read from the `mov #N,r6` + `jmp 0x003f61bc` thunks
(`0x003f60e0` → index 1, `0x003f60ec` → 2, `0x003f60f8` → 3, `0x003f6104` →
4, `0x003f6110` → 10, `0x003f68b0` → 11, `0x003f66b8` → 0). Each string
extractor clears a fixed-capacity `STD_StringImp` (`memset` thunk
`0x003d13c4`), calls `sh4xref --to`-resolved `0x003f60xx` then
`0x003f61bc(h, rec, index)`, asks `0x003f5d98(h, rec, index)` for the length
in words, calls the convert loop `0x003ca858`, then `STD_StringImp_initPrm`
`0x003d13e8` and the setter `0x003ca60c`. Capacity is clamped to 31 chars
(`0x003bc090` road number, `0x003bc1fc` road name) or 127 chars
(`0x003bc368`, `0x003bc4d8`) or 31 (`0x003bc7b0`, exit number).

**The string decode (convert loop).** `0x003ca858(r4 = buffer, r5 = byte
length, r6 = mode)`; `r6 == 1` takes the 16-bit-word branch (`0x003ca8a6`):
it counts `(len + len/2) / 2` iterations (`0x003ca8a6`–`0x003ca8ae`) and for
each `u16` at `@r2` writes `(w << 8) | (w >> 8)` (`0x003ca8bc`–`0x003ca8c2`),
`r2 += 2` (`0x003ca8c6`). The `r6 == 2` branch (`0x003ca8cc`) does the same
4-byte-at-a-time for the 4-byte-aligned mode. So the loop assumes a string of
big-endian 16-bit words and produces a native little-endian `u16` array; each
native halfword holds one character in its low byte, the pad `0x00` in its
high byte. `sh4xref --calls 0x003bc028` shows `0x003bc0ac` → `0x003ca858`
with `r6 = 1`; all four string extractors use the same call.

**Observed name bytes (`lctbl_records.py` on the real card).** Record 0 of
stream 2 (offset `0x0000`, `size 36`, `lengths [0, 0, 5, 0]`) carries
`42 65 72 61 6e 6f 76 fd 63 68` = `Beranových` in CP1252 (the `ý` is
`0xfd`), exactly the byte string the swap loop turns into one character per
native halfword.

**The page reader is not the record walk.** `sh4xref --calls 0x0040de98`
(JMP-list) shows no call to `0x003f61bc` or `0x003bc960`; `0x0040de98` only
copies `mov.l @(8,r4)/@(4,r4)` and `mov.w @(2,r4)` into a 20-byte slot of the
32×20 table at `0x00d53640` (`0x0040deb4`–`0x0040def2`). It is the per-volume
page-cache registration (M9.38's read), not the record walk. The record walk
is reached from the TMC callers `0x003bcac0`/`0x003bcbc4`/`0x003bcc7c`
(`sh4xref --to 0x003bc960`) and reads the record through `0x003bc960`, which
itself only calls `0x003bc028`-family extractors.

**Dynamic control.** `read_watch_l3.py probe` on `0x003f61bc` reports
`UnmappedAccess: no mapped region covers 0x00000000..0x00000002` — the
handle-block lookup `0x003f51e0` reads a zeroed pointer in this harness, so
the accessor cannot be called without a bound `0x00d53500` block (M9.24).
`0x003bc028`/`0x003bc194` return `0x0` with `guest-reads=0` (the struct
pointer is null, so the extractor returns early). These are the same
`BLOCKED` shapes M9.38 recorded, not a refutation of the static walk.

**M3.23 list reproduced.** `callgraph.py build` + `rank --depth 4 --family
LCTBL=0x004125a8 --family ICODE=0x003f2cc0 --family REFER=0x003fbed8` prints
`LCTBL roots=0x004125a8 subtree(depth 4)=10 unresolved=0` and the same five
candidates as C-3544 (`0x0040dd40`, `0x0040de98`, `0x004125a8`, `0x00409cc8`,
`0x0040b358`). The record walk `0x003bc960` is not in that subtree — it is
reached from the TMC message handlers (`0x003bcac0`), which is why the M3.23
reachability did not surface it.

## Interpretation

- **FACT (static):** The `LCTBL001` record walk is the C-884 field directory
  (`0x003f61bc` = `0x003f56bc` data start + `0x003f57a8` field count +
  `0x003f5e10` offset; length `0x003f5d98`), the same rule M4.16b fitted to
  247,089/247,089 records. The twelve fields are read by twelve extractor
  VAs, indexed 0–11 through the thunks above; the string fields are four of
  them (`0x003bc028` field 1, `0x003bc194` field 2, `0x003bc300` field 3,
  `0x003bc470` field 4) plus `0x003bc748` (field 10).
- **FACT (static + executed):** The string decoder is `0x003ca858` with
  `mode = 1`: a 16-bit-word buffer is read big-endian and stored little-endian
  (high byte first), one character per native `u16`. The executed control on
  a 10-byte name returns the swapped bytes, and the card record 0 carries the
  CP1252 `Beranových` bytes that the loop consumes.
- **OBSERVED:** The encoding the code assumes is **single-byte CP_ACP**
  (C-1799's system ANSI code page): the convert loop ends with one byte per
  character in the low half of each `u16`, not a UTF-16 pair. It does not
  detect a two-byte encoding and does not consult a multibyte table; the
  only conversion on the path is the 16-bit byte swap.
- **OBSERVED (negative):** `0x0040de98` is the volume page-cache registration
  (32 slots of 20 bytes at `0x00d53640`), not the record walk; the record
  walk is reached from the TMC handlers, not from `0x004125a8`'s subtree.
  The M3.23 reachability therefore cannot find it from the `LCTBL` literal.
- **UNKNOWN:** the runtime handle/field-count block (`u16 hdr[26] = 12`) is
  not built by the L3 harness, so the accessor is still a static finding (the
  M4.16b directory rule is verified on bytes, not executed end to end).

## Conclusion

M3.15 `Done when` is met: `docs/format/rdstm.md` now names the record walk
(`0x003f61bc` + `0x003f56bc`/`0x003f57a8`/`0x003f5d98`/`0x003f5e10`), the
twelve field extractors (table above), and the string decode
(`0x003ca858`, `mode = 1`, 16-bit high-byte-first swap) with the encoding
assumption (single-byte CP_ACP). The VAs-per-field table is the `Done when`
evidence; every VA is `CODE sec0` and none is `INIT`. Status `done`;
C-2205 (walk + extractors) is rewritten in place from "not identified";
C-2208 gains the `0x0040de98` page-cache negative and C-2209 becomes the
dynamic control (its "unmet" reading is superseded by C-2205). C-2200–C-2204
and C-2206–C-2207 stand unchanged. `reader-coverage.md` row 22 and
`rdstm.md` §`LCTBL001` get the VAs.
