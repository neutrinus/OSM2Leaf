## Question

M8.C1k found that ScreenState cannot reach CC window 16. M8.C1j found that
no form follows `frm_PRCOM_StartUp`. Which CC owns window 16, why is it
missing, and what does the start screen wait for?

## Hypothesis

The skin never calls SystemCC's `AUIInitializeComplete`, so the next form
never starts. Falsifier: `AUIInitializeComplete` runs and still no form
follows.

## Method

1. **Static.**
   - SystemCC's `ISystemCtl` vtable at `0x02a71590` was read from the type
     library's method order. Slot 28 is `AUIInitializeComplete`, fn
     `0x02a8094c`.
   - Window ids were found as follows. ScreenStateCC's `SetWindowHandle`
     (fn `0x02b46058`, `(mgr, id, hwnd)`, ids up to 46) starts with a
     16-byte prologue. That prologue was searched for in the text of every
     module of image A, with compressed sections decoded by `nk_decomp`.
     The `mov #id,r5` next to each literal-pool caller gives the id.
   - Kernel B's memory setup: the `Configuring: … Filesystem pages = %d`
     print in nk.exe (fn around `0x880248d4`), the TOC reader fn
     `0x88024550` (`[pTOC+56]` = ulFSRamPercent), and the OEM hook pointer
     at `0x89e69f4c`.
   - `boot.hv` was decoded with `cerom.py files --decompress`.
2. **Patches.** These are emulator-only, delivered as `ipl-patch` lines.
   - `--register-first ScreenStateCC.dll` moves that DLL to the front of
     the DllRegisterServer list.
   - `--object-store`: see O4.
   - A trial `FreeLibrary` after each DllRegisterServer was tried in J12
     and dropped.
3. **Runs.** All runs use the M8.C1j configuration with `-gdb tcp::1240 -S`.

   | run | change | breakpoints |
   | --- | --- | --- |
   | J7 | gdb jump from GetCurrentSourceID to `AUIInitializeComplete` | SystemCC |
   | J10 | none (baseline) | ScreenStateCC DllRegisterServer / DllGetClassObject |
   | J11 | `--register-first ScreenStateCC.dll` | same, `SetWindowHandle(16)` site `0x02b43ea2`, `0x02a8094c` |
   | J12 | FreeLibrary after each registration | return from DllRegisterServer |
   | J13 | ulFSRamPercent `0x20202028` only | same |
   | J14 | J13 + OEMCalcFSPages → TOC (5 404 pages) | same |
   | J15 | ulFSRamPercent `0x00808028` + hook (592 pages), FreeLibrary | same |
   | J16 | `--object-store` (= J15 without FreeLibrary) | `0x00011466`, `0x02b43ea2`, `0x02a8094c` |

## Observations

**O1 — `AUIInitializeComplete` (J7).** When it is forced through gdb,
SystemCC logs `SystemCC : AUI Initialize Complete!!!` and sends message
`0x197d` (6525) to CC window 16. The send fails, because window 16 does not
exist. In J10, J11 and J16 the skin never calls fn `0x02a8094c`.

**O2 — Window 16 is ScreenStateCC.** ScreenStateCC registers id 16 (caller
site `0x02b43ea2`). Its CLSID `{756C7016-890D-4669-91CF-BD1BC834CB0C}` is an
unnamed control in `Substance.skn` (type-6 record, index `0x150`). In J10
its DllRegisterServer returns `0x80020009`, so auirtdll's create path never
calls its DllGetClassObject. With `--register-first` (J11):

- DllRegisterServer returns 0;
- DllGetClassObject is called (31.3 s client time);
- `SetWindowHandle(16)` runs (32.0 s);
- the ScreenState state machine logs from state `INI_STARTUP`.

**O3 — The registration loop stops after about 52 DLLs.** In J10 to J13
the return values of DllRegisterServer follow one pattern, whichever DLLs
come first:

- 52 × `0`;
- 2 × `0x8002801c` (`TYPE_E_REGISTRYACCESS`);
- 18 × `0x80020009`.

(The breakpoint VA is in slot 0, so the 72 hits include some from other
processes.) FreeLibrary after each call does not change the pattern (J12).
It also makes AuiApp fault later in `naviccipcmsg.dll+0x1ffe` (TEA `0x10`),
so it was dropped.

**O4 — The cause is the object store.**

- `boot.hv` sets the registry type under `ObjectStore` and
  `SYSTEMHIVE = Documents and Settings\system.hv`. The hive lives in the
  RAM object store.
- The serial log prints `Filesystem pages = 80` (320 KiB).
- ulFSRamPercent is `0x00000028`, which gives the same 80 pages
  (512 × 40 / 256). Patching it alone (J13) still prints 80.
- The OEM hook at `0x89e69f4c` points to fn `0x88048b48`, which is
  `rts; mov #80,r0`: a fixed 80 pages, whatever the TOC says.

`--object-store` makes two changes:

- the hook's delay slot becomes `mov r5,r0`, so the hook returns the
  kernel's own result;
- ulFSRamPercent becomes `0x00808028`.

The log then prints `Filesystem pages = 592` (J15, J16), and every
DllRegisterServer returns 0. 5 404 pages (`0x20202028`, J14) leave too
little program memory: Speech.exe faults and the boot stops before AuiApp.

**O6 — ScreenState stays in `INI_STARTUP` (J11, J16).**

- Handled events: `NAVIGENERAL_CC_CAS_NAVIREG_CARSTOP`,
  `NAVIGENERAL_CC_CAS_AVREG_CARSTART`, `SYSTEM_CC_ITR_DISCONNECT_SD2`,
  `NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END`, `SS_FIRST_COMPLETESHOWSCREEN`,
  `SYSTEM_CC_ITR_CHANGE_AUDIO_SRC_ST_OFF` and `NOTICE_AUDIO_SOURCE`.
- J16 only: `SK_OTH_STARTUP` (a ScreenAction from the skin), followed by the
  antitheft checks `ANTITHEFT_CC_FNR_SEQ_INVALID` and
  `ANTITHEFT_CC_FNR_SECURE_INVALID`, and `AV_SETTING_CC_CAS_MONITOR_OFF`.
- `SS_FIRST_COMPLETESHOWSCREEN` sends `NOTIFY_TRANSITION_FIRST_SCREEN` to
  ctrl 44, 46, 40, 41 and 1. Only NaviEvCC (1) receives it. Windows 44
  (Etcs), 46 (InfoBar), 40 (UnitMainte) and 41 (EvNotice) do not exist,
  even in J16 where all of them register. EtcsCC's CLSID is in neither
  EU skin (`--skins` drops it), so 44 is expected to be missing on an EU
  unit.
- Some events are `Rejected (Undefined)` in this state, for example
  `NAVIMAP_CC_FNR_OWNMAPDRAW_END`.

## Interpretation

- C-8320/C-8321: on `-M ze0` the RAM registry is too small for image A's
  controls. On the unit the hive is the same size, so the controls are
  probably registered once and kept: the unit stays powered in the car, or
  the hive is saved. That part is a hypothesis. `--object-store` is an
  emulator-only stand-in.
- With every control registered, the skin reaches its start action
  (`SK_OTH_STARTUP`), but the screen state does not leave `INI_STARTUP`.
  Four of the five targets of `NOTIFY_TRANSITION_FIRST_SCREEN` have no
  window, and three of them (InfoBar, UnitMainte, EvNotice) are in the EU
  skin. Their controls are the most likely members of the 29 failed
  initialisations. Why they fail, and which event leaves `INI_STARTUP`, is
  M8.C1n.
- The falsifier of the M8.C1l hypothesis is not tested cleanly. In J7,
  `AUIInitializeComplete` ran only by a gdb jump, and its message went to a
  window that did not exist then.

## Conclusion

`ze0_aui.py --object-store` makes every control DLL register on `-M ze0`
by lifting kernel B's fixed 80-page object store. With it, ScreenStateCC
(window 16) runs and the skin raises `SK_OTH_STARTUP`. The UI layer still
draws no form. The state machine stays in `INI_STARTUP`, and the CCs of
windows 40, 41 and 46 do not create their windows.
