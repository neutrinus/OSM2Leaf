## Question

Where is the table from which `AppLaunch.dll` (build B) starts `\windows\Navi.exe`,
what is its record layout, which function walks it, and which SD/map-version
checks run before `Navi.exe` is allowed to run?

## Hypothesis

M1.21 found the UTF-16 path `\windows\Navi.exe` at `0x03bc0f54` (EU2011) with
no literal-pool reference, so the table holds **inline** strings in
fixed-size records and the code reaches it through one base pointer plus a
stride. The HDD_INFO checks (`fn 0x03bd2ad8`, `fn 0x03bd2ce4`) are on the path
that decides whether `Navi.exe` runs.

Falsifier: (a) no literal in the executable section points to a record start
or to a base from which `0x03bc0f54` is reached by a constant stride; or (b)
the structural parse breaks (non-printable names, types outside the dispatch
range, a record past the count still looking valid); or (c) no data flow from
the HDD_INFO checks to the `Navi.exe` thread.

## Interpretation

- **FACT (C-3528):** the launch table is base `0x03bb2330`, 112 records of
  `0x310` B (EU2011 = US2011; build C `0x03b92318`, 111), found only through the
  base getter `0x03bccb88`; the `Navi.exe` record that an EU unit starts is
  record 81 at `0x03bc1b40` (type 4, mode mask 1, area mask `0x00020000`,
  path at `+0x54` = `0x03bc1b94`, waits on ids 80/20/3/4/40/94/82, own id
  `0xa2`, priorities 217/220, no argument). The walker is `fn 0x03bcc5b0`,
  its filter `fn 0x03bcc564`, the per-record thread proc `fn 0x03bcc078`.
- **FACT (C-3529):** `Navi.exe` is created, immediately suspended, and resumed
  only when (i) its waits returned (each at most 30 s), among them id 82, which
  `MountStorage` signals after the HDD_INFO router has run on partition 0, and
  (ii) the error flag `0x01f733f0` is not 1. The flag is set by the first error
  screen of `fn 0x03bcafb8`. So the order before `Navi.exe` runs is: SD host
  open/IOCTL (`NO SD CARD` 0x80) → `DSK1:` mount, partitions (`SD INIT NG`
  0x82) → check 1 map code (`DIFFERENT MAP CODE` 0x50) → check 2 MapDBVer
  (`MAP DATA BASE UNMATCH` 0x51) → SET_ID 82 → `ResumeThread`.
- **FACT (C-5350):** the area masks are USA `0x00040000`, Euro `0x00020000`
  (not the reverse), and the filter tests boot mode against `+4` and area
  against `+0xc` (not the reverse). The table itself corroborates it: the US-only
  tuners `XMRadio`/`Rbds` carry `0x00040000`, the EU `Rds`/`Tmc` carry
  `0x00020000`.
- **FACT (C-5351, static):** the first shown error does not return to its
  caller (draw, wait for ACC off, loop forever) unless the screen object cannot
  be created. On that path a check-1 failure stops the mount thread inside the
  dispatcher, so check 2 and SET_ID 82 are not reached; `Navi.exe` times out on
  id 82 after 30 s, sees the flag and stays suspended. A second error from
  another thread hits the `EndlessLoop` branch.
- **HYPOTHESIS:** the `ProtoLevel` exception (target byte `0x1x`/`0x2x`) is a
  prototype/development-unit bypass; on such units a wrong map code or MapDBVer
  does not block `Navi.exe`. Production values of `KernelIoControl(0x01013200)`
  are not in the image.
- **UNKNOWN:** who signals wait id 94 (no record carries it; probably another
  process through `ACM9:`); the exact `SDC1:` IOCTL semantics of
  `0x80032000/4` (CMD42 unlock is the obvious candidate, not shown); the
  meaning of `+0x308`.

## Conclusion

The `Navi.exe` launch is fully table-driven and the map gate is an ordering
gate, not a check inside the record: an EU unit starts record 81
(`0x03bc1b40`), creates `\windows\Navi.exe` suspended, and resumes it only if
no AppLaunch error screen has been raised by the time the SD mount thread
signals id 82 (or its 30 s wait expires). The two HDD_INFO comparisons that
decide that for a generated card are the M2.15/M9.6 checks 1 and 2 on
partition 0 of `DSK1:`; a generated card therefore must pass check 1 (line 1
bytes 0–10 = unit `+0x60`) and check 2 (line 3 positions 5–7 within unit
`+112..+114`), in that order, and nothing in the launch record itself reads
`VER_INFO`. `docs/research/rom-registry.md` gains the table and the gate order;
claims C-3528, C-3529, C-5350, C-5351. Corrections in place (rule 17): the
area-mask tables in `docs/research/us-eu-region.md` and `docs/format/firmware.md`
swapped USA/Euro, and claim C-784 swapped the `+4`/`+12` masks and called the
`NxJpNavi.exe` mask unknown; both now point to C-5350.

**For M2.4 (HDD_INFO variant predictions):** `docs/format/validation.md` says
the router "does not skip check 2 when check 1 fails". That holds for the router
code, but on a production unit the dispatcher does not return from the first
shown error (C-5351), so a variant failing check 1 shows `DIFFERENT MAP CODE`
only; a check-2 verdict is only observable for variants that pass check 1. The
