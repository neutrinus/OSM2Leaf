# EXP-2026-11-21-M4.55: the RPF section-2 consumer stops at an unmodelled STDDLL import

- **Status:** failed (negative — the consumer was reached but cannot run)
- **Date:** 2026-11-21
- **Sample:** EU 2011 firmware head `archive/head256.img`, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  EU 2011 card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`,
  SHA-256 `105e2032e480e8ba…76307`
- **Tools:** `python3` 3.15 / zlib 1.3.2; `tools/datask_req_l3.py`,
  `tools/vcard_l3.py`, `tools/poi_position_l3.py`, `tools/sh4dis.py`
- **Claims:** C-6020–C-6029
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the RPF route path finder's `0x14b6` reply handler be driven under the L3
harness on a factory level-1 record, so that every unit-0/unit-2 word it reads
can be logged with its reading VA (M4.55's Done-when)?

## Hypothesis

M4.40 named the RPF consumer (`0x003367a0`, called by `RPF_PreMap_start`
`0x00336bf0`) and showed the data-access task replies to a kind-8 request with
pointers to units 0 and 2 (C-5922, C-5923). **Hypothesis:** driving `0x003367a0`
with the real reply list runs to completion and its read-watch reveals the
unit-0 field table.

- **Falsifier:** the consumer stops at an address it does not model (an import
  or a global), or reads no word through the unit pointer `+20`/`+24`, or the
  run reads bytes outside the record's units. Any of these refutes "the handler
  is reachable in the harness as it stands".

## Method

1. **Sample and hash.** EU 2011 build A `Navi.exe` in `head256.img`
   (`92aa525d…007f9`) and the factory EU card (`105e2032…76307`), position
   `51.70,17.45` resolving cell `B48R058R`.
2. **Commands.** From the repo root (`archive/` holding the two files):
   ```
   python3 tools/datask_req_l3.py request archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --position 51.70,17.45 0xa68cd68c:0:8
   python3 repro.py            # the script printed in full below
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 \
     --va 0x003367bc --count 3
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 \
     --va 0x003d1640 --count 3
   ```
   `repro.py` (committed alongside this record):
   ```
   import struct, sys
   sys.path.insert(0, "tools"); sys.path.insert(0, "tools/l3_harness")
   import datask_req_l3 as R, vcard_l3 as V
   IMG = "archive/head256.img"
   CARD = "archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img"
   G = 0x0061A824; RPF_INIT = 0x003360BC; RPF_CONSUMER = 0x003367A0
   c = R.Client(IMG, V.make_card(None, CARD, {}), (51.70, 17.45))
   m = c.m; eng = m.eng
   res = c.request(0xA68CD68C, 0, 8, dump=64)
   e = [x for rp in res["replies"] if "entries" in rp for x in rp["entries"] if x["status"] == 1][0]
   print("reply: kind=%#x mesh=%#x ptrs=%s unit0=%#x" % (e["kind"], e["mesh"], [hex(p) for p in e["ptrs"]], e["ptrs"][0]))
   m.call(RPF_INIT, [], max_insns=2_000_000)
   LIST = m.malloc(0x2004); lb = bytearray(0x2004)
   struct.pack_into("<H", lb, 0, 1); struct.pack_into("<H", lb, 4, 1)
   struct.pack_into("<I", lb, 8, e["kind"]); struct.pack_into("<I", lb, 12, e["word8"] & 0xFFFFFFFF)
   struct.pack_into("<H", lb, 14, e["divid"]); struct.pack_into("<I", lb, 16, e["mesh"])
   for i, p in enumerate(e["ptrs"]): struct.pack_into("<I", lb, 20 + 4 * i, p)
   m.put(LIST, bytes(lb))
   SEQ = 0x00A680D680
   m.put(G + 4, struct.pack("<I", e["mesh"]))
   m.put(G + 20, struct.pack("<I", SEQ)); m.put(G + 24, struct.pack("<I", SEQ + 1)); m.put(G + 28, struct.pack("<I", SEQ + 2))
   MSG = m.malloc(0x40); mb = bytearray(0x40)
   struct.pack_into("<HH", mb, 8, 0x14B6, 5); struct.pack_into("<I", mb, 12, 1)
   struct.pack_into("<I", mb, 20, LIST); struct.pack_into("<I", mb, 28, SEQ)
   m.put(MSG, bytes(mb))
   start = m.malloc(0x20); tmp1 = m.malloc(0x20); tmp2 = m.malloc(0x20)
   g8, g12, g16 = m.u32(G + 8), m.u32(G + 12), m.u32(G + 16)
   for v, nm in ((g8, "g8"), (g12, "g12"), (g16, "g16")): eng.watch(v, v + 0x804, "rw", nm)
   eng.arm_watch()
   try:
       r0 = m.call(RPF_CONSUMER, [start, tmp1, tmp2, g8], stack_args=[g12, g16], max_insns=40_000_000)
       print("consumer returned r0 %#x" % r0)
   except Exception as ex:
       print("consumer fault: %s: %s" % (type(ex).__name__, str(ex)[:220]))
   u0 = [h for h in eng.watch_hits() if h.name == "unit0"]
   print("unit0 reads: %d" % len(u0))
   ```
3. **Controls.**
   - *Positive (the import is real and callable):* `poi_position_l3.py run`
     calls the **same** STDDLL module's `STD_MeshPnt_isValid` and
     `STD_MeshPnt_chgMapPnt` on 3 real `POINT010` records — 3/3 match
     `point_census.fine_position` within 1 unit, controls 0/3. So the function
     the consumer wants exists and runs; the harness simply has no model for the
     `Navi.exe` import thunk.
   - *Negative (the request itself):* a kind that the data-access task has no
     data for returns status ≠ 1, so `e` is empty and the script stops before
     the consumer — the kind-8 reply is the only one that reaches unit 0.
4. **Scope.** One factory level-1 record (cell `B48R058R`), EU 2011 build A,
   the single consumer `0x003367a0` reached from `RPF_PreMap_start`. US 2011
   and level-2 parcels excluded (no such run attempted).
5. **Falsifier.** Stated above; the run's stop at `0x003367c2` on
   `STDDLL!STD_MeshPnt_isValid` is the observation that refutes the hypothesis.

The read-watch over unit 0 (`0x302abbf2`, the reply's first pointer) records
**0 reads**: execution faults at `0x003367c2` before the first `ld` through it.
The consumer's own prologue does not touch the unit; the first unit access is
inside the branch guarded by `cmp/eq #1,r0` on the `STD_MeshPnt_isValid`
return, which never runs.

## Interpretation

- **FACT:** The RPF consumer `0x003367a0` is called with the kind-8 reply list
  and faults at `0x003367c2`, `jsr @r3` with `r3 = [0x0033682c] = 0x003d1640`.
  The thunk `0x003d1640` tail-jumps through the IAT cell `0x0055da88`; the
  import is `STDDLL!STD_MeshPnt_isValid`.
- **FACT:** `vcard_l3.py` registers 81 import models and none of them is a
  `STDDLL` mesh-point export; `MODELS` has no `Mesh*` key.
- **FACT:** The same STDDLL function runs correctly in `poi_position_l3.py`
  (3/3 records, both controls 0/3), so the missing piece is the harness's
  cross-module binding, not the firmware or the reply.
- **OBSERVED:** No unit-0 read precedes the fault; the read order (M4.55's
  deliverable) cannot be observed until the thunk is bound.
- **HYPOTHESIS:** Binding `STDDLL` exports as callable sub-calls (run the real
  `STDDLL.dll` function, not a host stub) lets `0x003367a0` proceed; the
  alternative (a host stub that returns 1) would fake the verdict and is not a
  result.
- **UNKNOWN:** Whether, once bound, the consumer's unit-0 read order stays
  within the record's units (the falsifier of the positive claim).

## Conclusion

M4.55's Stop condition is met: the RPF reply handler cannot be reached "without
a model of more than two RPF globals" — here, without a binding for the
`STDDLL` mesh-point imports that the handler calls before its first unit access.
The call chain (`RPF_PreMap_start 0x00336bf0` → consumer `0x003367a0` →
thunk `0x003d1640` → IAT `0x0055da88` → `STDDLL!STD_MeshPnt_isValid`) and the
reply (`kind 8`, unit-0 pointer `0x302abbf2`) are recorded. The unit-0 field
table is **not** produced, so M4.40 is not unblocked and
`docs/format/map-tiles.md` is unchanged. The unblock is a narrow harness task:
teach `vcard_l3.py` to run `STDDLL.dll` exports for the `Navi.exe` import
thunks (M9.65), then re-run `repro.py` and record the read order.
