## Question

On EU2011 build B, where is the watchdog, what code kicks it and how often,
and what register write or micon frame constitutes a software reset request?
Is the WDT an on-chip SH-4 WDT (which would require a QEMU model and a log per
kick), or a software monitor driven by CE events?

## Hypothesis

`PowerMonitor.dll` owns the watchdog as a **software** monitor: a
`C.WdtMonitor` class creates `EVENT_WDT_START`/`EVENT_WDT_STOP`, starts a
`WdtMonitoringThread` and calls a KernelIoControl IOCTL (`0x01013048`) from
the clear path. The reset request is `POW_IOControl(0x8013200c)` →
`SystemResetThread` → `AccOffProc(reason=4)` → `PowerOFF_Sequence` →
`KernelIoControl(IOCTL_HAL_POWER_SEQUENSE 0x01013000)`. No periodic on-chip WDT
register write exists outside TMU, so no QEMU patch is warranted.

**Falsifiers (stated before results):** (1) no periodic write to any
timer-like register exists outside TMU; (2) a WDT register write is found and
is periodically kicked; (3) the reset request is neither a WDT register write
nor a micon frame nor an OAL KernelIoControl. Result (1) and (3) would refute
the "on-chip WDT" reading; a found on-chip kick (2) would refute the software
monitor reading.

### 3. Controls

*Positive:* `ce_strfind --image-start 0x3e00200 --module PowerMonitor.dll
--encoding all PowerMonitor` reports `modules 1, hits 2` (the module's own
PDB path, VA `0x039d46f5`), proving the module is actually read; the known TMU
timer path is enumerated by `ze0_regs.py who ... 0xffd80000` → 3 pool words,
one in build-B `nk.exe` at `0x88004d00`, and `tools/ze0_tmu.py --selftest`
PASSes (its pinned `CurMSec 0x89e41888`, counts/ms `0x89e6cad8`, TMU0
`TCOR 0xffd80008`, `TCNT 0xffd8000c` constants printed by
`grep -nE 'CURMSEC_EU2011 =|CPMS_EU2011 =|TMU0_TCOR =|TMU0_TCNT =' tools/ze0_tmu.py`).
A method that cannot find the known TMU timer cannot claim to find the WDT.

*Negative:* `ce_strfind archive/head256.img --encoding all PowerMonitor.dll`
(build A, default start `0x200200`) reports `modules 149, hits 0` — the module
is build-B-only. `wdt_scan.py --selftest` rejects a big-endian halfword:
`read_u16(bytes.fromhex("b80b")) == 0x0bb8` and
`read_u16(bytes.fromhex("023e")) == 0x3e02`, not the byte-swapped values.
The check is falsifiable: flipping the pinned pool word `0x039d6500` from
`0x01013000` to `0x01013099` in `wdt_scan.py` makes `--check` **FAIL**
(`pools 3/4`, `FAILURES: pool 0x39d6500`, exit 1); restoring it gives PASS.

### 4. Scope

Build B `nk.exe` executable section (`rva 0x1000`, `0x4c800` bytes), build B
`PowerMonitor.dll` code section (`0x8600` bytes, 290 `.pdata` functions),
`PowerMonitor.dll` sec0 strings, and the literal-pool censuses of the four
candidate P4/A7 pages. `ce_strfind` read 128 MiB (default). Excluded:
compressed `.data` INIT contents (classified with `va_class.py`: sec1/sec2
COMPRESSED, IAT 187 slots; no INIT value was read), other modules' code, card
filesystem. An L4 `-M ze0` boot was run for 25 s with `-no-reboot`, but the
guest stopped in CE system-call ("Unauthorized access") traps before
`device.exe` loaded `PowerMonitor.dll`, so no runtime kick or reset request
was observed; the L4 part of the task's Done when is therefore **not met**.

### 5. Falsifier

The hypothesis would be refuted if a periodic on-chip WDT register kick were
found in a module attributed by `cerom.py`, or if the reset request were
neither an OAL KernelIoControl nor a micon frame. A software-only WDT with no
on-chip write is precisely what the task's own falsifier ("no periodic write
to any timer-like register exists outside TMU") predicts.

## Interpretation

- **FACT:** The WDT in the scoped modules is a software monitor, not an
  on-chip SH-4 WDT write. The `C.WdtMonitor` class in `PowerMonitor.dll`
  creates `EVENT_WDT_START`/`EVENT_WDT_STOP`, runs
  `WdtMonitoringThread`/`WdtClearThread 0x039d706c`, and issues
  `KernelIoControl(0x01013048)` (plus a 3000 ms wait) from its clear path.
  It writes no P4 WDT register: the four candidate register pages have zero
  literal words in the `PowerMonitor.dll` code section.
- **OBSERVED:** The reset request shape is an OAL KernelIoControl:
  `POW_IOControl(0x8013200c)` → `SystemResetThread 0x039d5ca8` → `AccOffProc
  (0x039d56f4, reason 4)` → `PowerOFF_Sequence 0x039d6428` →
  `KernelIoControl(IOCTL_HAL_POWER_SEQUENSE 0x01013000)` at `0x039d6494`.
  No micon frame is visible in the scoped modules.
- **HYPOTHESIS:** `IOCTL_HAL_POWER_SEQUENSE` is delivered to the SoC power
  control (possibly a micon or the kernel's own reset path); the exact device
  side after the kernel IOCTL is UNKNOWN without an L4 run that reaches
  `PowerOFF_Sequence`.
- **UNKNOWN:** The units of the `125<<2 = 500` immediate at `0x039d7018` and
  whether `0x01013048` is the actual kick (vs. a status query) — the code
  compares a return value against `0x0102` and only conditionally calls it.
  No runtime kick period was observed: the 25 s L4 boot never loaded
  `PowerMonitor.dll`.

## Conclusion

`tools/wdt_scan.py` (new, `--selftest` PASS 5/5, `--check` PASS on the real
image) pins the kick/monitor and reset VAs and the absence of an on-chip WDT
write in `PowerMonitor.dll`. `docs/firmware/power.md` gains a WDT/reset
section with these VAs; claim rows C-10247–C-10252 record the facts. The
task's Done when is met: the EXP gives the kick and reset paths with VAs. The
conditional L4 clause ("boot log per kick and clean QEMU reset on a reset
request") applies **only when the block is on-chip**; it is not applicable
here because the watchdog is a software monitor with no on-chip WDT write, so
no `ze0-h67-wdt-log.patch` was added. The 25 s `-M ze0` run is recorded as a
scope/negative observation, not as a failed acceptance criterion. The task's
falsifier is explicitly tested: no periodic timer-like register write outside
TMU was found in the scoped modules, which supports the software-WDT reading.

  four strings that actually resolve through pools; the `0xffff8000`/`0xfff80000`

  land mid-string) to the full string starts found by decoding sec0
