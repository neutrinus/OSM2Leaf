## Question

With the C1e EU2011 boot recipe, where do the wall-clock seconds go from
kernel start to the launcher waits, and which QEMU configuration is fastest?

## Hypothesis

Three runnable configurations exist and differ in host time to the same boot
marker: **A** default TCG (no `-icount`, `-d` log to a file), **B** identical
plus `-icount shift=0,sleep=off`, **B2** B's exact QEMU argv with the
`-d … -D …` pair removed. A fourth candidate, `-accel tcg,thread=…`, does
**not** exist on this binary: `qemu-system-sh4 -accel help` prints only
`tcg` (O2). **Falsifier (TODO:5130):** if host time is dominated by one phase
that no option changes, the cut is a model, not an option; the EXP must name
it. Secondary falsifier: a mutated TSV must change the table; if it does not,
the table is not evidence.

## Method

### 1. Sample and hash

`sha256sum` on the head, the full card and QEMU; `stat -c` and `sha256sum`
again at the start of each timed run into `WORK/qemu.stat`; `ze0_card.py
describe` on the full card prints `build EU2011`, `verinf QSD-302-100`,
`mapdb 16-16` (O1). Host load context: `uptime` (O2).

### 2. Commands

Run from the worktree root. `$S` is the scratch directory; each timed boot
used a fresh qcow2 overlay. The complete sampler is
`$S/bootsample4.sh` (a scratch helper; its exact body is quoted below so the
run is reproducible without scratch). It starts QEMU, waits for the HMP
socket, then every 5 s appends `t_host bytes cur_raw` to `WORK/tsv`:
`t_host` from `date +%s.%N`, `bytes` from `wc -c < WORK/run.out`, `cur_raw`
from `python3 tools/ze0_serial.py hmp WORK/hmp.sock 'xp/4xb 0x09e41888'`
filtered to the line beginning `09e41888:`.

```bash
S=/home/marek/projekty/leafre-work/scratch/m8.h25
Q=/home/marek/.cache/qemu-ze0/build/qemu-system-sh4
CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
sha256sum archive/head256.img "$CARD" "$Q"
stat -c '%s %y' "$Q"; python3 tools/ze0_card.py describe "$CARD" --no-hash
bash tools/qemu-ze0/run.sh --card "$CARD" --machine ze0 --qemu "$Q" \
  --timeout 0 --workdir "$S/dryfull" --dry-run

# two timed configurations (240 s each, external timeout; --timeout 0 in run.sh)
"$S/bootsample4.sh" A "$S/fullA" 240
"$S/bootsample4.sh" B "$S/fullB" 240
# the cut control (90 s): B's exact argv minus "-d … -D …"
"$S/bootsample4.sh" NOLOG "$S/fullNO" 90

# phase tables (one command per configuration)
python3 tools/ze0_bootbudget.py table "$S/fullA/tsv" "$S/fullA/run.out"
python3 tools/ze0_bootbudget.py table "$S/fullB/tsv" "$S/fullB/run.out"
python3 tools/ze0_bootbudget.py table "$S/fullNO/tsv" "$S/fullNO/run.out"

# tool checks and the negative mutation (copy only; originals untouched)
python3 tools/ze0_bootbudget.py --selftest
python3 tools/selftest.py --only ze0_bootbudget
python3 - "$S/fullB/tsv" "$S/fullB/tsv.mut" <<'PY'
import sys
src, dst = sys.argv[1:]
rows = [l.rstrip("\n") for l in open(src)]
for i, l in enumerate(rows):
    p = l.split()
    if p and p[0].startswith("1795535734"):
        p[2] = "09e41888: 0xff 0xff 0x00 0x00"
        rows[i] = " ".join(p)
open(dst, "w").write("\n".join(rows) + "\n")
PY
python3 tools/ze0_bootbudget.py table "$S/fullB/tsv.mut" "$S/fullB/run.out" \
  | grep wait_timeout
grep -an -m1 'Display: HWR\|Store Mgr Ready\|ACM::WaitModule Timeout' \
  "$S/fullA/run.out" "$S/fullB/run.out" "$S/fullNO/run.out"
uptime
```

`bootsample4.sh`, verbatim (the `NOLOG` branch is the `--dry-run` QEMU argv
with the `-d unimp,guest_errors,int,invalid_mem -D WORK/qemu.log` pair
removed; `--log /dev/null` only **redirects** `-d`, it does not turn it off):

```bash
#!/usr/bin/env bash
set -u
CFG="$1"; W="$2"; DUR="$3"
ROOT=/home/marek/projekty/OSM2Leaf.task-m8.h25-boot-budget
Q=/home/marek/.cache/qemu-ze0/build/qemu-system-sh4
CARD="$ROOT/archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img"
mkdir -p "$W"
stat -c 'qemu_size=%s qemu_mtime=%y' "$Q" > "$W/qemu.stat"
sha256sum "$Q" >> "$W/qemu.stat"
IC=; [ "$CFG" = B ] && IC='--icount shift=0,sleep=off'
if [ "$CFG" = NOLOG ]; then
  python3 "$ROOT/tools/ze0_ipl.py" patch "$CARD" -o "$W/ipl.txt" >"$W/prep.out" 2>&1
  python3 "$ROOT/tools/qemu-ze0/mkoverlay.py" "$CARD" "$W/card.qcow2" >>"$W/prep.out" 2>&1
  timeout "$DUR" "$Q" -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch="$W/ipl.txt" \
    -kernel "$CARD" -nographic -monitor "unix:$W/hmp.sock,server,nowait" $IC \
    -drive "if=sd,index=0,file=$W/card.qcow2" > "$W/run.out" 2>&1 &
else
  timeout "$DUR" bash "$ROOT/tools/qemu-ze0/run.sh" \
    --card "$CARD" --machine ze0 --qemu "$Q" --timeout 0 --workdir "$W" \
    --log /dev/null --no-summary $IC > "$W/run.out" 2>&1 &
fi
RP=$!
for i in $(seq 1 600); do [ -S "$W/hmp.sock" ] && break; sleep 0.1; done
printf 't_host bytes cur_raw\n' > "$W/tsv"
printf '%s socket\n' "$(date +%s.%N)" >> "$W/tsv"
while kill -0 "$RP" 2>/dev/null; do
  t=$(date +%s.%N)
  n=$(wc -c < "$W/run.out" | tr -d ' \t\n')
  c=$(python3 "$ROOT/tools/ze0_serial.py" hmp "$W/hmp.sock" 'xp/4xb 0x09e41888' 2>/dev/null | grep '^09e41888:' | head -1)
  printf '%s %s %s\n' "$t" "$n" "$c" >> "$W/tsv"
  sleep 5
done
date +%s.%N >> "$W/tsv"
wait "$RP" 2>/dev/null
printf 'rc=%s\n' "$?"
```

### 3. Controls

- **Positive:** `ze0_bootbudget.py --selftest` prints `selftest: PASS (0
  failure(s))`; `selftest.py --only ze0_bootbudget` prints `passed=1
  failed=0 skipped=0 total=1`; all three boots print the kernel banner,
  `Display: HWR`, `ActivateSDCardDriver … Start`/`End(OK!!!!)` and `Store Mgr
  Ready`; `fullB` additionally prints 17 `ACM::WaitModule Timeout` lines
  (O4). The LE decode is checked against M8.H56 O5's `71 90 01 00` =
  102 513 ms (O5).
- **Negative / mutation:** overwriting one `cur_raw` word in a **copy**
  `fullB/tsv.mut` changes the `wait_timeout` row from `24789` to `59758`
  guest ms while its host time stays `27.27 s` (O6). A boot without the
  marker strings would print `MISSING` rows, which is not a phase table.
- **Confound control:** all three `qemu.stat` files print the same SHA
  `916676eb…0b3f1d` and size `56 178 200` (O1), so the host-time comparison
  is a property of the options, not of a mid-batch QEMU rebuild.

### 4. Scope

Three boots of one EU 2011 card (A 240 s, B 240 s, NOLOG 90 s wall clock;
all ended by an external `timeout`, `run.sh --timeout 0`), ~5 s TSV sampling
(`wc -l` on the three TSVs printed 49 / 20 / 21 rows in A / B / NOLOG,
including the header and bookkeeping rows), one
full 8 GiB qcow2 overlay per boot, eight stable marker strings, and one
mutated TSV copy. Excluded: other card years, `-accel tcg,thread=…` (the
binary prints only `tcg`), L5 (no hardware), and the README's "typical times"
(which are from 2026-11-22, `docs/emulator/README.md:187–197`, not new
measurements).

### 5. Falsifier

Identical host times to `Store Mgr Ready` across configurations, a phase
dominated by a cost no option changes, a mutated table that still reproduces,
or QEMU hashes that differ between runs would all refute the comparison.

## Observations

**O1 — samples, derived inputs and binary identity.** `sha256sum` printed
`92aa525d…007f9` (head), `105e2032…76307` (card), `916676eb…0b3f1d` (QEMU).
`ze0_card.py describe` printed `build EU2011`, `map code QSD-302-100`,
`mapdb 16-16`, `verinf QSD-302-100`, `FAT offset 0x6400400`.
`run.sh --dry-run` printed the QEMU argv with
`-icount shift=0,sleep=off` for B and without it for A; the `NOLOG` argv is
that line with the `-d … -D …` pair removed. Each `qemu.stat` printed
`qemu_size=56178200` and the same SHA-256 (A, B and NOLOG).

**O2 — available accelerators and host load.** `qemu-system-sh4 -accel
help` printed `Accelerators supported in QEMU binary:` and `tcg` only.
`uptime` at 17:08 printed `load average: 23,01, 23,59, 21,23`.

**O3 — tool checks.** `ze0_bootbudget.py --selftest` printed 8 `ok` lines and
`selftest: PASS (0 failure(s))`, including `ok LE decode: got 102513 want
102513` and `ok markers in log order: got [19, 44] want [19, 44]`.
`selftest.py --only ze0_bootbudget` printed `tool:ze0_bootbudget PASS 0.08s`
and `passed=1 failed=0 skipped=0 total=1 time=0.08s / selftest: OK`.

**O4 — phase tables.** Printed by `ze0_bootbudget.py table TSV RUN_OUT`
(host seconds from the first TSV row; guest ms = CurMSec LE bytes at that
byte offset; deltas in parentheses are between consecutive present markers

`guest_ms` is a host-load-dependent wall sample, not a guest-time budget.

**O5 — CurMSec byte order and rate.** The first B TSV row printed
`09e41888: 0xec 0x00 0x00 0x00`; `int.from_bytes(b'\xec\0\0\0','little')`
= 236 ms. The control `71 90 01 00` = 102 513 ms is checked in the tool's
selftest (O3). In A the CurMSec column plateaus at `0xf4 0x23 0x00 0x00`
= 9 204 ms from ~16 s onward while host time keeps advancing — consistent
with M8.B2 C-1323 (the kernel halts and CurMSec only jumps once per 818 s),
not with a guest clock that tracks the whole run.

**O6 — negative mutation.** The copy `fullB/tsv.mut` changed one sampled
word to `09e41888: 0xff 0xff 0x00 0x00` (65 535 ms) at host second
`1795535734.073325535`. The original table printed
`wait_timeout 27.27 24789 35937 (+16.85 s host, +24560 ms guest)`; the
mutated table printed `wait_timeout 27.27 59758 35937 (+16.85 s host,
+59530 ms guest)`. The host column is unchanged; the guest column moves by
34 969 ms, so the table is sensitive to the sampled bytes.

**O7 — recommended default evidence.** With the same binary hash (O1),
`Store Mgr Ready` came at 10.43 s in B (`-icount` + `-d` on file) and at
7.62 s in NOLOG (`-icount`, `-d` pair absent): 2.81 s earlier. A (no
`-icount`, `-d` on file) reached it at 8.64 s but never printed a
`WaitModule Timeout` in 240 s, so A and B are not a like-for-like speed
comparison of guest progress; the clean single-variable cut is B→NOLOG.

## Interpretation

- **FACT (C-7220):** the phase table of O4 for A and B, both from
  `ze0_bootbudget.py table` commands in §2 and from the same QEMU SHA
  (O1). The three cheapest cuts in descending order of observed effect:
  1. **drop the `-d` pair** — 10.43 s → 7.62 s to `Store Mgr Ready` with
     identical `-icount` and binary (O7). A future `run.sh` option should
     make this a first-class switch; today `--log /dev/null` only redirects
     the log and does not remove `-d`.
  2. **shorten or stub `ACM::WaitModule`** — B spent `+16.85 s` of host
     time between `Store Mgr Ready` and the first timeout line (O4); in A
     no timeout line appears in 240 s. This is a guest-side wait, not a QEMU
     option, so it is a model change, not a CLI default.
  3. **do not enable `-icount` for wall-clock speed** — under it CurMSec at
     a wall sample is host-load-dependent (M8.H56 C-7536; O4/O5 show 228 ms
     at 10.43 s in B versus 7 274 ms at 8.64 s in A). Keep `-icount` only
     when repeatability matters (C-1323).
- **FACT (C-7221):** `-accel tcg,thread=…` is unavailable on this binary
  (O2), so the task's thread-mode option is untestable, not untried.
- **OBSERVED (C-7222):** CurMSec plateaus after the kernel halts (O5), so a
  "guest s" column from CurMSec is meaningful only for the early boot
  phases; it is not a whole-run guest-time budget.
- **OBSERVED (C-7223):** the negative mutation changes the table (O6), and
  the tool's selftest passes (O3): the table is reproducible and sensitive.
- **HYPOTHESIS (C-7224):** the 2.81 s B→NOLOG difference comes from writing
  the multi-hundred-MB `-d unimp,guest_errors,int,invalid_mem` log; one run
  per config cannot separate that from host-noise, so the recommendation
  is a default, not a speed guarantee.
- **UNKNOWN (C-7225):** neither configuration reached `Finish Launch
  Threads!` inside its window, so host time from the launcher waits to the
  idle UI is not measured here (M8.H13/M8.H24 remain the sources for that).

## Conclusion

`tools/ze0_bootbudget.py` joins a sampled `(host t, bytes, CurMSec)` TSV with
stable marker strings in `run.out`, giving phase → guest s → host s tables
for two configurations from printing commands (O4). With the same binary,
dropping the `-d` pair cut 2.81 s off the time to `Store Mgr Ready`; the
largest remaining host cost is the launcher's `ACM::WaitModule` wait
(`+16.85 s`, B), which no QEMU option changes. `run.sh --help` now recommends
keeping `-icount` for repeatable traces and redirecting `-d` output with
`--log /dev/null` on long runs, and states that `-icount` guest time at a
wall sample is host-load-dependent and that `-d` itself still costs time.
The falsifier did not fire: the three cuts are distinguishable and one of
them is a CLI default. What remains open is the idle-UI phase and a
second-run variance estimate for the 2.81 s figure.
