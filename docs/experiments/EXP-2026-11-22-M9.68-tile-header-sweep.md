## Question

Which fields of a factory tile's `0x1000`-byte header does the map client
actually parse during a mount? We know a generated tile reads the same as
factory and a fresh-container tile fails (M9.13); we do not know the
acceptance envelope field by field.

## Hypothesis

A one-field byte flip in the common-header constants, the level/box descriptor
tables or the section list at `0x800` produces one of three verdicts against
the factory-mounted `B48R058R.DAT`: **read-same** (every tile read and every
parser byte range identical to the baseline), **read-different** (the mount
still parses the tile but the read/parser set changes), or **rejected** (the
tile is left after its header or the run is blocked), with a named rejecting
`fn`. The kind byte of a level-table entry and the section list's entry count
are among the fields the client checks; the identity strings and the box
table are not read by this mount.

**Falsifier:** no mutation is ever rejected. Then the path under test does not
parse the header and the sweep needs the next stage; the EXP records that
honestly. A second falsifier: the positive control below is classified
`read-same` (the verdict logic has no teeth).

## Plan (written before code)

**Approach.** One tile, one byte flip per field, one PySh4 mount per flip.
Baseline = unmodified factory mount. Each mutation is applied through
`vcard_l3.make_card(..., {"flip": ["MAPAL001/B48R058R.DAT@<off>:<xor>"]})`,
i.e. the existing same-size overlay path M9.13 used; no file on the card is
written. A run captures (a) every read row with its handler and per-function
byte ranges and (b) the header-check events via the same hooks as
`tools/tile_drop_l3.py`. The verdict compares the target tile's reads and
parser ranges with the baseline; rejection is detected from the header check
returning `-1` (the `+0x16e` branch), from the box finder returning `-1`, or
from a blocked/engine-stopped run. The rejecting `fn` is the header check
`0x0040acb8` for the drop path, the leaf/parser that issued a changed or
failed read for a read-different path, or the engine's stop site for a block.

**Signature/format source (exact, no guessing).**

## Method

1. **Positive control (known-good rejection).** Replace the whole third
   section-list entry at `0x80c` (`02 25 19 03 00 04` on this tile) by the
   terminator `ff ff ff ff`; M3.33 showed a tile with only two entries is left
   after its header (`tools/tile_drop_l3.py`,
   EXP-2026-11-20-M3.33-b60-header-drop). This one field mutation **must** be
   classified `rejected` by `0x0040acb8`. If it is not, the sweep has no teeth
   and the run is invalid. A separate field flips the terminator at `0x812`
   the other way (`ff`→`00`, a fourth entry) to test whether parts beyond the
   box mask are checked.
2. **Negative control (must not reject).** A flip of an identity byte that the
   mount never reads (`HITACHI` at `0x41`) and a flip of a box-table coordinate
   (box table is not loaded by the header entry, map-tiles.md line 898) must
   be classified `read-same`. A synthetic row in `--selftest` also feeds a
   deliberately wrong verdict to the classifier and requires it to fail.
3. **Falsifier.** If no mutation is rejected, state it and record the table
   anyway; do not promote `read-different` to `rejected`.
4. **Expected result.** Identity/box fields `read-same`; level-entry kind
   bytes and section-list entries change the read set or drop the tile;
   `DATA VERSION` digits are loaded by `0x0040a8d0` but do not change the
   mount's reads (`read-same` with a changed parser byte, reported as such).
5. **Controls on numbers.** Every count, offset and verdict printed in
   Observations comes from the `sweep` command output quoted there; none is
   typed by hand. The number of mutations is printed by the tool.

## Interpretation

1. The map client checks exactly two structures during this mount: the
   **level table at `0x1ac`** (table ids, entry counts, and the kind byte of a
   level whose count is non-zero) and the **section list at `0x800`**. 18 of 52
   fields changed the read set; the other 34 (33 `read-same` + 1 rejected)
   split as below.
2. `rejected` occurred once, on the positive control: removing section-list
   entry 2 makes `0x0040acb8` return -1 at its `+0x16e` branch (part 2
   missing), box status 3, and the mount continues in box 0. The falsifier
   ("no mutation is ever rejected") did not fire.
3. The three kind bytes `0x1c5`/`0x1d7`/`0x1dd` (section 1 L1 `0x92`,
   section 2 L1 `0x90`, section 4 L1 `0x93`) change the directory read length
   through the M3.31 leaf `0x0040901c(kind, 1)`; the observed readers that
   changed are `0x00414dbc`, `0x00414644` and `0x00414dbc`. The kind bytes of
   levels whose count is 0 (`0x1b1`, `0x1cb`) are read but not acted on, which
   agrees with M3.31's rule that only a non-zero-count header entry replaces
   the card-wide merged table.
4. Every sector/offset/length field of all three section-list entries is
   acted on: sector/offset changes make the firmware read a different table
   (9→7 or 9→8 tile reads), length changes alter the table read and the
   directory positions that table names. A fourth entry (`0x812`) is ignored:
   the box mask is 7, i.e. parts 0..2 only.
5. The identity strings, version, date digits, the `0x184`/`0x5d0` bounds, the
   `0x5cc`/`0x5d4` constants and all nine box-table fields are not acted on
   (`read-same`). This does **not** mean those bytes are never loaded: M3.25
   showed `0x0040a8d0` loads the date digits at `0xfa`–`0x10f`, and a flipped
   digit keeps the same reader and byte range. `read-same` in this tool means
   "the mount's read requests and per-function byte ranges are identical to
   factory", not "the byte value is never read". The box table's non-use
   agrees with `docs/format/map-tiles.md` line 898.
6. Discrepancy to scrutinise: flipping `level.n_tables` at `0x1ac` (or `0x1ad`)
   is `read-same` on `B48R058R.DAT`, while `docs/format/map-tiles.md` line 922
   reports a 402-byte walk after changing `0x1ac` on `B28R070R.DAT`. Both
   direct probes printed the factory `0x0040aa50` ranges. Either the walk is
   bounded elsewhere on this tile or the earlier note used a different byte;
   this sweep does not confirm the "no bound" claim for this tile.
7. Scope: one tile, one position, EU2011 build A, L3 only. `rejected` here is
   "the tile was left after its header or the run blocked"; it is not an L4/L5
   acceptance result. Rule 13: no reader VA is newly claimed as confirmed
   beyond the M3.25 entries already cited in `docs/format/map-tiles.md`.
