## Question

With M9.53 able to make a map request read one record block, do the EU2011
firmware's coarse-level (`LEV3456R.DAT`) record view and tile section-4 name
list agree with `lev3456.py` / `section4.py` — on a factory file and on a file
we generated — and do the existing L3 target verdicts still hold?

## Hypothesis

The mount directory checks of the 2026-11-20 EXP extend to the record level:
a `--request` for a coarse parcel makes the data-access task read and inflate
a `LEV3456R.DAT` record, and `--kind 0x40` makes it read the tile's section-4
record; in both cases the inflated window, parcel code and name list equal
the Python model's decode of the same bytes.  Firmware-side corruption or a
wrong request changes the verdict.

**Falsifier (set before the runs):** (i) no mesh id makes the DA task read
`MAPAL001/LEV3456R.DAT` (command (d) names a `BxxRyyR` tile or returns no
read); (ii) the firmware's inflated words differ from the model's decode with
all controls passing; (iii) a firmware-side flip still prints MATCH; (iv) the
selector `0x004157dc` is presented as validated (C-2442 only says it was not
read); (v) any gate count in (g) changes.  A Python-only comparison with no
`tag 0x0900` firmware read is not a result.

## Interpretation

- **FACT (C-2447):** with a coarse parcel code the EU2011 data-access task
  reads, inflates and serves a record of `MAPAL001/LEV3456R.DAT` (109,960 B
  inflated at `0x86900`/`0xee00`), and the inflated window, parcel code and
  unit-table words equal `lev3456.decode_record`'s decode.  The mesh id is
  derived from the firmware's own decoders/box table (`0xd624a0` is a runtime
  BSS table with 46 boxes, box 45 = LEV3456R, level bits `0x3c`) — never a
  guessed literal and never `fn 0xd624a0`.
- **FACT (C-2448):** `--kind 0x40` reads the tile's section-4 record (640 B
  inflated at `0x113ca500`/`0x200`) and the firmware's name-list window equals
  `section4.parse_record`'s 5 names, parcel code, type and country.
- **FACT (C-2449):** on a `lev3456gen.py` coarse file and a `tilewriter.py
  --factory` tile the firmware reads our served records and both models
  decode them identically; firmware-side flips change the reply to sub 9 and
  the verdict to MISMATCH, and a wrong request changes the parcel code.  The
  `0x004157dc` selector is a pdata START but C-2442 says it was not read, so
  it is **not** claimed as a validated section-4 selector.
- **Scope:** EU2011 build A, one card, one coarse record and one section-4
  record per case; not a statement about the unit, and no section-4 writer
  is claimed.  The two `targets.json` entries were upgraded in place; no
  target was added or renamed and `tools/l3check.py` was not edited.

## Conclusion

The hypothesis holds at record level and no falsifier fired: factory and
generated coarse/section-4 records MATCH the Python models over the
firmware-observed windows, and both firmware-side negatives are detected.
The two blocked L3 target entries now name runnable commands and verdicts;
rows 18–20 of `reader-coverage.md` carry the record-level verdicts in their
L3-result cells (F4 cells and legend left to M8.H64).  M9.18's Done when is
met.

   (`datask_l3.py --flip/--replace`), so the reply changes to sub 9; the
   `record_l3.py --selftest` synthetic MATCH/MISMATCH is labelled tool plumbing.
4. All numbers are quoted from the commands above; the mesh id `(w0<<16)|w1`
   and its `0xA40F`/`0xD405` provenance are stated.
5. Kept the two target names and `entry.kind: blocked`, 13 targets total;
   `l3check.py --selftest` stays 34 checks / 1 skipped and
   `--build-corpus` 13 targets.  `l3check.py` was not edited.
6. Rows 18–20 L3-result cells only; F4 cells and legend belong to M8.H64.
7. Stop sharpened: no mesh id reading LEV3456R, no firmware-side flip changing
