## Question

Can every SCIF of `-M ze0` be a host socket, so that the firmware's own
serial driver sends its frames to a Python peer and receives the peer's reply
through the path it already uses (the HPB-DMAC channels armed from a SCIF
`FRDR`), while a boot without `--serial-peer` stays unchanged?

## Hypothesis

`sh_serial` already implements a SCIF FIFO and a chardev backend; attaching a
chardev gives TX for free. The missing half is the receive channel: a host
byte in the FIFO must be moved into the plane the driver armed and complete
its DMAC channel. **Falsifier:** bytes written to the socket never reach the
driver's RAM buffer although the receive interrupt is delivered, or the host
never sees the frame the guest transmits, or a boot without peers differs
from the baseline.

## Method

1. Static: `python3 tools/ze0_sdhost.py inttable archive/head256.img` (47 OAL
   interrupt rows) plus EXP-2026-11-22-M8.C2a O1/O2 give the DMA setup:
   channel 10 RAM → SCIF1 `FTDR 0xffe4100c`, channels 1/3/7 from SCIF `FRDR`
   `0xffe4n014` into two 0x80-byte planes (`0xa999a800/880`,
   `0xa999c800/880`, `0xa999e800/880`), DCR `0x00052000`, and the ISR rows
   `{ch1 0xb80/0x8803e654, ch3 0xbc0/0x8803e6cc,
   ch7 0xc40/0x8803e7bc, ch10 0xca0/0x8803e8a8}`.
2. Patch: `ze0-h01` adds machine properties `sci0`…`sci8` (chardev ids),
   attaches them to the `sh_serial` devices, and makes an armed `FRDR` channel
   drain the FIFO into the guest planes (two planes, then DMAC completion and
   interrupt). No chardev keeps the old stub. `run.sh --serial-peer sciN=SPEC`
   creates the QEMU chardev and the machine property.
3. Positive controls (patch and tool):
   ```bash
   bash tools/qemu-ze0/build.sh --check-version 11.1.3
   bash tools/qemu-ze0/build.sh --force --jobs 8
   python3 tools/ze0_serial.py --selftest
   ```
4. Run P (peers, 200 s) and run B (baseline, no peers, 180 s), same head,
   card, ipl-patch and `-icount shift=0,sleep=off`; fresh qcow2 overlay each:
   ```bash
   W=~/projekty/leafre-work/scratch/m8.h1/runP
   python3 tools/qemu-ze0/mkoverlay.py \
     archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$W/card.qcow2"
   bash tools/qemu-ze0/run.sh --qemu /home/marek/.cache/qemu-ze0/build/qemu-system-sh4 \
     --image archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
     --ipl-patch ~/projekty/leafre-work/scratch/m8.h24/run/ipl.txt \
     --sd "$W/card.qcow2" --icount shift=0,sleep=off --timeout 200 --workdir "$W" \
     --serial-peer sci1=unix:$W/sci1.sock,server=on,wait=off \
     --serial-peer sci7=unix:$W/sci7.sock,server=on,wait=off
   python3 tools/ze0_serial.py peer "$W/sci1.sock" --count 8 --timeout 75 \
     --expect-hex 1002020800100319
   python3 tools/ze0_serial.py peer "$W/sci1.sock" --send-hex 1006020800100319 --nowait
   python3 tools/ze0_serial.py peer "$W/sci7.sock" --send-hex a55a0102030405060708 --nowait
   python3 tools/ze0_serial.py hmp "$W/hmp.sock" 'xp/16xb 0xa999a800'
   python3 tools/ze0_serial.py hmp "$W/hmp.sock" 'xp/16xb 0xa999e800'
   # run B: the same command without the two --serial-peer lines
   ```
5. Run G (`sci7` transmit to a file backend, 140 s), so no client has to be
   connected when the firmware writes the line:
   ```bash
   G=~/projekty/leafre-work/scratch/m8.h1/runG
   mkdir -p "$G"
   python3 tools/qemu-ze0/mkoverlay.py \
     archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$G/card.qcow2"
   bash tools/qemu-ze0/run.sh --qemu /home/marek/.cache/qemu-ze0/build/qemu-system-sh4 \
     --image archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
     --ipl-patch ~/projekty/leafre-work/scratch/m8.h24/run/ipl.txt \
     --sd "$G/card.qcow2" --icount shift=0,sleep=off --timeout 140 --workdir "$G" \
     --serial-peer sci7=file:$G/sci7.tx.bin
   xxd "$G/sci7.tx.bin"
   ```
6. Run H (guest-side breakpoint, 130 s): the same QEMU argv as run P, but
   started by `ze0_dbgmsg.py`, with `--count 0x8803e7bc` (ch7 DMA ISR) and
   `--count 0x8803e654` (ch1 DMA ISR); after the driver armed channel 7,
   send two 128-byte planes (`0x41…0xc0`) on `sci7` and read back the channel
   registers and the breakpoint counts.
7. Counted corpus: 20 QEMU patches at run time (21 after rebase); 2 hosts (sci1, sci7); 1 boot per run
   (P, B, G, H) plus three intermediate boots; one 8-byte guest frame and two
   0x80-byte injected planes. SKIP is never a PASS.

## Observations

**O1 — patch applies and builds.** `--check-version 11.1.3`: 20 applied at
run time, 21 applied / 0 failed after rebasing onto `origin/main`. `--force --jobs 8`: `qemu-system-sh4` linked and `-M help` lists
`ze0`. `qemu-system-sh4 -M ze0,sci9=nope` answers `Property
'ze0-machine.sci9' not found`; `-M ze0,sci1=nope` answers `ze0: sci1: no
chardev with id 'nope'` — the property is real and validated.

**O2 — the chardev is on the guest device.** HMP `info qtree` on run H:
`dev: sh-serial, id "ze0-scif7" … chardev = "ze0sci7"` (and the same for
`ze0-scif1`). Without `--serial-peer` no `chardev` line appears.

**O3 — sci1 TX reaches the host (positive control).** The peer tool attached
to `sci1.sock` received `10 02 02 08 00 10 03 19` — exactly the audio-network
frame of EXP-2026-11-22-M8.C2a O6. A persistent `ncat -U` listener logged
96 bytes (12 frames) over 170 s in an intermediate run.

**O4 — sci1 RX reaches the guest driver's buffer.** After writing
`10 06 02 08 00 10 03 19` to `sci1.sock`, HMP `xp/16xb 0xa999a800` printed
those eight bytes; the rest of the 0x80-byte plane was zero. The bytes are in
channel 1's RAM plane, not in a host-side log.

**O5 — sci7 RX reaches the guest driver's buffer.** After writing
`a5 5a 01 02 03 04 05 06 07 08` to `sci7.sock`, HMP `xp/16xb 0xa999e800`
printed those ten bytes at channel 7's plane 0. The same injection made
nothing change in a boot where SCI7 had not enabled its receiver yet
(SCR bit 4 = 0), which is the expected firmware-side condition, not a
chardev failure.

**O6 — the receive DMA completes and the guest ISR runs.** In run H, after
two 128-byte writes on `sci7`, channel 7's registers changed from
`DSAR 0xffe47014, DDAR 0xa999e800, DTCR 0x80, DPTR 0x0700, DSTSR 1` to
`DDAR 0xa999e900, DTCR 0, DPTR 2, DSTSR 0` with `DINTMR0 = 0x001806af`
(bit 7 enabled). `ze0_dbgmsg.py` counted **1** hit of the ch7 ISR at `0x8803e7bc`
(OAL interrupt-table entry, EXP-2026-11-22-M8.C2a O2) and 0 of the ch1 ISR
(nothing was injected on sci1 in that
run). With only one 128-byte plane written (runs 4/5) the channel switched
planes (`DDAR 0xa999e800 → 0xa999e880`, `DTCR` reloaded) and the ISR count
stayed 0 — the driver is notified after both planes, as the DCR suggests.

**O7 — sci7 guest TX reaches the host.** Run G's `sci7.tx.bin` holds 18 bytes:
`b0 20 02 00 22 f0 b0 23 02 00 25 f0 b0 23 02 00 25 f0`. The first frame is
byte `0xb0`, a command/length byte `0x20` and DLE-like `02 00 22 f0`; the
guest writes these to SCIF7 `FTDR` without any host prompt. A socket listener
connected from boot start saw 0 bytes in one intermediate run, so the frames
are stage-dependent; the file backend is the reliable observation. The TX
direction on `sci7` is the same `sh_serial` chardev path as the O3 frame on
`sci1`.

**O8 — baseline unchanged.** Run B (no peers) and run P+injections both
produced 1 583 lines of `serial.log`, the same last three lines
(`OEMIoControl:IOCTL_HAL_POWER_SEQUENSE.` after the flash error), and the
same counts of `failed wait response` (116) and `Force PowerOff` (1).
`diff` shows only differing heap pointers in `Spcom` lines, as it does
between two unpatched boots.

**O9 — tools.** `tools/ze0_serial.py --selftest` PASS (frame round-trip over
`socketpair`, partial-tail reassembly, oversize refusal, truncated peer,
short-read loop); `tools/selftest.py --only ze0_serial` PASS 1/0/0;
`bash tools/qemu-ze0/build.sh --selftest` PASS 78/0 (after the patch).

## Interpretation

- **FACT (C-6980, C-6986):** nine named machine properties and the
  `--serial-peer` launcher; the property is validated at machine init (O1, O2).
- **FACT (C-6981):** without a peer the serial log and boot stage are the
  baseline (O8); the falsifier "baseline changes" does not fire.
- **FACT (C-6982, C-6983, C-6984):** host ↔ guest bytes on both sci1 and
  sci7 reach the guest driver's DMA buffers; sci1 guest TX reaches the host
  (O3–O5). The opposite-direction falsifier does not fire.
- **FACT (C-6985):** the driver's receive path runs: both planes complete and
  its ch7 ISR is taken once (O6). The "interrupt without data" falsifier
  does not fire.
- **FACT (C-6988):** sci7 guest TX reaches a host chardev (O7); with the RX
  injection of O5/O6 this closes the same loop-back on `sci7` as on `sci1`.
  Decoding those frames is M8.H27.
- **FACT (C-6987):** the framing/peer tool has a passing selftest (O9).

## Conclusion

M8.H1 is implemented: every SCIF is a named host chardev with TX and RX, the
firmware's own `serial_scif.dll` receive path is driven by host bytes (both
planes, then its ISR), and a boot without peers is unchanged. Both directions
are measured on `sci1` and on `sci7`; the GPS frames of O7 are now available
to a protocol peer (M8.H27/H30).
