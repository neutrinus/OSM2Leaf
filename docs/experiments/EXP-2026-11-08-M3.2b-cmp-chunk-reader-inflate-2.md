# EXP-2026-11-08-M3.2b: `.cmp` chunk reader via `inflate` (pass 2, re-open)

- **Status:** blocked (Done when not met; chunk_offset[] consumer not named)

- **Tools:** `python 3.14.3`, `capstone 5.0.7` (present; scans are halfword arithmetic per `sh4scan.py`), repo tools `tools/cerom.py`, `tools/sh4xref.py`, `tools/sh4scan.py`, `tools/sh4dis.py`, `tools/chunk_decoder_l3.py` (little-endian SH-4, pinned)

## Question

Can the caller that loops over `.ind` `chunk_offset[]` and feeds the chunk
engine `fn 0x0041c7e8` be named by a static, signature-derived search of
readable (uncompressed) sections, now that C-2128/C-2129 refute the "caller is
in compressed executable sec1" premise?

## Hypothesis

Re-open hypothesis (ninth pass): "no *static* caller of `fn 0x41c7e8`" is the
shape of an **indirect call through a pointer in `.data`** (or a caller in a
module the search never named), not a compressed-code miss. A search with
`tools/sh4scan.py` (constant/mask signatures, builds A/B/C) plus an L3 probe
(hook `0x41c7e8`, record caller PC) should find it. The chunk engine is already
usable (M9.11, C-2154).

**Falsifier:** a literal pool, `bsr`/direct branch, or stored 32-bit value
`0x0041c7e8` in any **readable** section that yields the caller; or a
decompressed `Navi.exe` sec1 that contains the function-pointer slot and a
sec0 code path that loads it and does `jsr @Rn`; or an L3 run of the firmware's
`.cmp` open path that breaks on `0x41c7e8` and reports a caller PC outside the
harness. Conversely, "zlib sits in a compressed section" (positive control) would
satisfy the Done-when escape — it is **false** here (C-2060, confirmed).

   # uncompressed section of build A (527 sections, all modules).
   python3 - <<'PY'
   import struct, cerom, sh4scan
   data = open('archive/head256.img','rb').read(256<<20)
   r = cerom.CERom(data, 0x200200)
   for val in (0x0041c7e8, 0x00542148):
       t = struct.pack('<I', val); hits=[]
       for s in sh4scan.load_sections(r,data):
           if s.compressed: continue
           i=0
           while True:
               j=s.blob.find(t,i)
               if j<0: break
               hits.append((s.module,s.index,s.va+j)); i=j+1
       print(hex(val), len(hits), hits)
   PY

       r=cerom.CERom(data,start); secs=sh4scan.load_sections(r,data)
       has_navi=any('navi' in (m['name'] or '').lower() for m in r.modules())
       hits=sum(1 for s in secs if not s.compressed and t in s.blob)

## Interpretation

- **FACT (confirmed, build A):** no literal pool, no 32-bit stored value, and no
  xref resolves `0x0041c7e8` in any of the 282 uncompressed sections of all 149
  build-A modules (527 sections searched; the only `0x542148` values are the two
  Navi.exe sec0 pools already in C-2063). The same 0x41c7e8 value is absent from
  uncompressed sections of builds B/C (91/88 modules; neither has `Navi.exe`).
- **FACT:** `Navi.exe` sec1 (`0xc8002040`) and sec2 (`0x48002040`) are
  compressed `.data`, not executable sections (C-2128). `cerom.py decompress`
  cannot decode them (`UNSUPPORTED`, LZX/LZSS). Therefore a function-pointer slot
  for `0x41c7e8` stored in sec1 is **not statically readable** with the tools
  available now; the "no executable section compressed" premise (C-2128) removes
  the *code* blocker but does not make *compressed `.data`* readable.
- **FACT (controls):** zlib lives in uncompressed sec0 of 6 build-A modules
  (C-2060/C-2534) — the Done-when escape ("zlib in a compressed section") is
  false. The chunk engine runs under PySh4 (M9.11, `chunk_decoder_l3.py
  --selftest` OK) but a direct-call run does not reveal the firmware caller.
- **OBSERVED:** `.cmp`/`.ind` string xrefs in readable code reach file
  resolvers (`fn 0x417fe0`, `fn 0x418748`/C-831), not a chunk-offset consumer;
  the derived builder/header signatures did not identify the consumer in
  uncompressed map modules.
- **HYPOTHESIS (carried, refined):** `fn 0x41c7e8` is reached by an **indirect
  call through a pointer stored in compressed `Navi.exe` sec1 (`.data`)**, or
  via a dispatch path whose readable caller cannot be tied to 0x41c7e8 without
  decoding sec1. Decoding sec1 (M1.2f/M8.E1 runtime path, or a working CE
  section codec) would make the pointer slot searchable; an L3 run that executes
  the firmware's `.cmp` open path (file-stub/import binding, M9.24/M1.2f
  context) and breaks on `0x41c7e8` would yield the caller PC without decoding
  sec1. Neither was achieved here.
- **UNKNOWN:** the module/VA of the `.ind` `chunk_offset[]` consumer and table
  builder; the answers to M3.2 (chunk_size buffer-vs-`0x10000` compare,
  seek-vs-`78 9c` scan) at the `.ind`-parser layer. M3.2 remains blocked.

## Conclusion

The re-open removed the wrong premise (caller in compressed *code*) but the
static caller of `fn 0x41c7e8` is still not nameable from readable bytes: there
is **no** reference to `0x0041c7e8` in any uncompressed section of build A
(282 sections, 149 modules, exhaustive) or B/C, while the only likely storage
for an indirect function pointer — `Navi.exe` sec1 — is compressed `.data` that
`cerom.py decompress` cannot decode. The inflate/engine VAs and M3.2's
engine-layer answers remain as C-2061–C-2063; zlib is not in a compressed
section (escape false). **Done when not met** → status `blocked`. M3.2's two
questions stay open (M3.2 blocked). Unblock by decoding `Navi.exe` sec1 and
resolving the indirect slot to a sec0 `jsr @Rn` caller, or by an L3 firmware
`.cmp`-open run that records the `0x41c7e8` caller PC (needs file-stub/import
binding).

## Claims (M3.2b block, C-2060–C-2069)

- **C-2064 (scope strengthened, OBSERVED):** No literal-pool, direct, or 32-bit
  stored reference to `0x0041c7e8` exists in any uncompressed o32 section of
  build A (527 sections total, 282 uncompressed, 23,559,542 B psize, all 149
  modules; 0x542148 appears only at the two Navi.exe sec0 pools `0x41c8bc`,
  `0x542144`). Absent from uncompressed sections of builds B/C (91/88 modules;
  no `Navi.exe`). The `.ind` `chunk_offset[]` consumer is not locatable in
  readable sections; an indirect pointer in compressed `Navi.exe` sec1
  (`.data`, `cerom decompress` UNSUPPORTED) cannot be read statically.
- **C-2066 (refined, HYPOTHESIS):** The `.ind`/`.cmp` file-layer reader that
  consumes `chunk_count`/`chunk_size`/`chunk_offset[]` and feeds `0x41c7e8`
  likely reaches it via an indirect call through a pointer stored in compressed
  `Navi.exe` sec1 (`.data`), or an equivalent dispatch path; M3.2a/b remain
  open until sec1 is decoded (M1.2f/M8.E1/CE codec) or the caller PC is captured
  by an L3 firmware `.cmp`-open run (M9.24/file stubs).
- **C-2067 (VERIFIED, negative control):** `python3 tools/cerom.py
  --image-start 0x200200 $IMG decompress --modules Navi.exe` classifies
  `Navi.exe` sec1/sec2 as `UNSUPPORTED` (`cannot pick a method`; LZX
  `invalid block type 0`, LZSS back-reference before output start). The
  compressed `.data` holding a potential indirect-call target is not decodable
  by the available Python section codec.
- **C-2068 (VERIFIED, method control):** `sh4xref --to 0x542148` (Navi.exe,
  build A) resolves pool `0x41c8bc` → load `0x41c85c` in `fn 0x41c7dc`
  (`jsr 0x41c864`) and pool `0x542144`, confirming the pool-xref/exhaustive
  32-bit search finds real references in uncompressed code; the `0x41c7e8`
  negatives are therefore method-credible.
- **C-2069 (OBSERVED):** Derived signatures for the `.ind` consumer — a
  20-byte-entry builder (`add #20` with stores to `@(4/8/12/16,*4)`, same base)
  and an `.ind` header read of `@(0/4/8/12,*4)` from the same base — did not

  reach resolvers `fn 0x417fe0`/`fn 0x418748` (C-831), not the chunk-offset
  consumer.
