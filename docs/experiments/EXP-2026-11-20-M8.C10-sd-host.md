## Question

What does `SDHC.dll` need from the SD host for the launcher's `SD Check` to
pass (M8.B5: `AppLch > SD Check Error` after 3 retries, C-1353), and does
the card driver's init then return without hanging the boot?

## Hypothesis

`SDC1:`'s slot-state query (`0x80032004`, C-5353) reports state 2 because
the host's card-detect reads "no card" from an unmodelled register. A
host model that reports a card, plus QEMU's `sd-card` behind it, lets
`ActivateSDCardDriver` run.

**Falsifiers (before the runs):** card detection comes from a GPIO or
micon path the SD host cannot present; or, with the model, the launcher
still logs `SD Check Error`; or the boot hangs after the activation (no
`End(` line from `ActivateSDCardDriver`).

## Observations

### Without a model (M8.B5 binary + dbgmsg)

`h1.log`: the read `fn 0x039b963c` returns 0 (success) for both ports and
the value read back at `0x039b764c` is `r3 = 0x00000002` both times (2 = no

catch-all logs one read of `0xffe4c01c` and `0xffe4d01c` (`ze0-p4 …

### OAL interrupt table (`ze0_sdhost.py inttable`)

0x88005c58  INTEVT 0xb00  ISR 0x8803fd40  prio  9  SYSINTR 0x20

US256: the same row at the same VA. `h4.log`: `InterruptInitialize`

log around the SD init: `INT2MSKCR = 0x20080000` twice.

### The boot-stopping spin

First model run (no SCIF stubs): 12 HMP samples over 96 s all give
`pc=0x0398e8a2 sr=0x40008001` (kernel mode); `0x0398e8a2` is in
`serial_scif.dll` sec0, a `mov.w @r1,r1 / and #0x40 / tst / bt` loop on
SCFSR of channel 1 (`0x1fe41010`, logged as `Invalid read … rejected`
665 907 times in the first 50 MB of the M8.B5 baseline log). After the
SCIF stubs, a 60 s run still showed 78 M rejected reads of `0x1fe46010`
(channel 6, the debug SCIF's area-7 alias); with the alias (`c10d`) a
240 s run has no rejected access in `0x1fe40000..0x1fe4ffff`.

## Interpretation

- **FACT (C-1460):** EU2011 `SDHC.dll` detects a card from bit 5 (`0x20`)
  of the 16-bit register at `+0x1c` of the SD host (`fn 0x039bcedc`; 1 =
  present, else 2), not from GPIO; the host is an SDHI/TMIO-style block
  (16-bit registers, no shift) at `0xffe4c000` (port 0) and `0xffe4d000`
  (port 1). Negative 1 (model, no card → `SD Check Error`) and the positive
  run (card → no error) confirm the bit.
- **FACT (C-1461):** the SD host interrupts are INTEVT `0xae0`/`0xb00`, OAL
  ISRs `fn 0x8803fcdc`/`fn 0x8803fd40` (IntrPrio 9), SYSINTR `0x1f`/`0x20`
  (OAL table row `0x88005c48`, EU2011 and US2011), gated by INT2 bit 29
  (status `0xff80403c` bit 29; unmask `0x20080000`). The INT2PRI field for
  bit 29 is an assumption (INT2PRI7 bits 20:16); command completion is
  polled, so no run here depends on it.
- **FACT (C-1462):** with `ze0-0008` (`-M ze0` + a qcow2 view of the EU
  card on port 0) the launcher's SD check passes, `ActivateSDCardDriver`
  runs, and QEMU's `sd-card` answers the driver's identification sequence
  (`CMD0 CMD8 ACMD41×2 CMD2 CMD3 CMD13 CMD9 CMD10 CMD7 CMD13 ACMD6 CMD16
  ACMD42`, no command without response). The first data command
  (`ACMD13`, 64 B) asks for DMA (`CC_EXT_MODE = 2`, HPB DMAC channel at
  `0x1fc08200`); with no DMAC model it times out (`EventID = 2`, 4000 ms)
  twice, and the card driver's init returns `End(NG)` (state 8). The boot
  continues to process creation and the first display surface: the M8.C
  done-when for row C10 ("init returns without hanging boot") is met.
  F3 (the FAT partition mounted) is **not** reached: the next blocker is
  the HPB DMAC, row **M8.C1**.
- **FACT (C-1463):** `serial_scif.dll fn 0x0398e888` busy-waits in kernel
  mode on SCFSR.TEND of SCIF channels through their area-7 aliases
  (`0x1fe41010`, `0x1fe46010`); with those reads at 0 the spin starves
  device.exe as soon as the SD path runs (negative 3: the boot stops at
  line 274). `ze0-0008` maps `sh_serial` on channels 0–5 and 7 and the
  area-7 aliases of all eight (row M8.C2 owns the real model).
- **OBSERVED (C-1464):** the CID/CSD the driver reads are QEMU's synthetic
  values, not the real card's; CMD42 (unlock) is never reached because the
  data path fails first. Both matter for row M8.C11 and for the lock
  (C-1954) once the DMAC works.
- **UNKNOWN:** whether `EventID = 2` is signalled from the SDHI interrupt
  (ACCEND) or from the DMA-LIB completion; the HPB DMAC model (M8.C1)
  decides it.

## Conclusion

Row C10 is done at the M8.C level: an SD host model plus QEMU's SD card make
the EU2011 launcher's SD check pass and the card driver's init return, and
the boot goes on past the point where M8.B5 stopped. The FAT mount (F3)
needs the HPB DMAC that `SDHC.dll` uses for every data transfer (row
M8.C1, next). New claims C-1460–C-1464; patch `ze0-0008`; `run.sh --sd`;
tool `ze0_sdhost.py`.
