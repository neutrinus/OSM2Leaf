# EXP-2026-11-19-M3.25: The tile reader's entry — the data-access task run next to the map-file task

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** firmware: `archive/head256.img` (first 256 MiB of the EU card
  image) SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card: `LEAF_2011-2012_QSD-309-101_navi158_eu.img` SHA-256
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Tools:** `python3 3.13.18`; repo tools `tools/datask_l3.py` (new),
  `tools/vcard_l3.py`, `tools/pdata.py`, `tools/sh4dis.py`, `tools/sh4xref.py`,
  `tools/callgraph.py`
- **Claims:** C-4680–C-4699
- **Supersedes:** none (it answers the question EXP-2026-11-19-M3.27 left open)
- **Superseded by:** none (naming corrected by C-3250, EXP-2026-11-20-M9.13: "level directory" below is the per-section table of `clarion_tile.py`, "data block" is a directory (slot table), and the list at header `0x800` is that model's section list; the default-position hypothesis is settled by C-3251)

## Question

Which firmware function is handed the bytes of a `MAPAL001` tile, with which
arguments, and what does it return? M3.27 showed that the three "reader" VAs
of M3.5 take records and mesh ids, not tile bytes. M3.28 showed that every
file is read through one request path. So the question became: who receives
the *answer* to a tile read request?

## Hypothesis

The tile reader is not a function called with `(tile, dst)`. It is a message
handler: the client asks the map-file task for a byte range and is called
back with a completion message that carries the buffer. If the client task
is run next to the map-file task of M9.44 and each `OSM_TaskSend` is carried
to the task it names, the client will ask for tile bytes by itself and the
functions that load from the returned buffer are the tile readers.

**Falsifier:** the handler that the firmware calls for a completed tile read
does not load any byte of the returned buffer; or a changed tile byte does
not change what the firmware asks for or loads next.

## Inputs

- `Navi.exe` EU2011 build A from `archive/head256.img` (image start
  `0x200200`).
- The EU 2011 card image, served by `tools/vcard_l3.py` (M9.44).
- No other state: no saved settings, no car position.

## Method

1. Found the task. `callgraph.py callers` from the read wrapper
   `0x003f7384` upward ends in `0x003ebfb4`, which has no static caller: it
   calls `0x003f6908()` and `0x003eba78()` (initialisation), then loops on
   `OSM_TaskReceive` and passes each message to `0x003ebee8`.
2. Read the dispatcher `0x003ebee8` (`sh4dis`): it walks a table of
   `{u16 message id, u16 defer flag, u32 handler}` at data VA `0x177fd0`
   (43 rows) and compares the id with the `u16` at message `+8`. Two handlers
   use a second table keyed by the `u16` at `+10`.
3. Read the handler of message `0x04a0` (the map-file layer's read
   completion, C-4636), `0x003f72e4`: it walks a table of
   `{u16 tag class, u16 0, u32 handler}` at data VA `0x178d60` and calls the
   first row whose class equals the request tag in bits 8..14.
4. Ran it (`tools/datask_l3.py mount`). One PySh4 machine holds both tasks.
   The tool boots the card as M9.44 does, calls the two initialisation
   functions, writes two task ids into the globals the code reads them from,
   then delivers message `0x07d0` sub `100` to the dispatcher. From there it
   only carries messages: a send to the map-file task runs that task's event
   function; a send to the data-access task is passed to the dispatcher.
5. Models added for the calls the task makes (all in `datask_l3.py`):
   semaphores (no contention with one runner), `OSM_MemSize`/`OSM_MemGet`
   (one 4 MiB area from the tool's heap), `OSM_SramGet`/`OSM_SramCheck` (an
   empty block reported as not valid), `OBJ_DiscInfo_readDiscVol` (returns
   the volume header the map-file layer published with
   `OBJ_DriveInfo_writeDataVol`), and eight `OBJ_CarPos_*`/`OBJ_Event_*`/
   `OBJ_RoutePntTbl_*` calls that return 0 and write nothing.
6. For every completion the tool arms a read watch on the returned buffer,
   delivers the message, and groups the loads by the function that made them
   (`pdata` start; two leaf functions are named by their entry).
7. Controls: the same run with one byte of `MAPAL001/B28R070R.DAT` changed
   (`--flip`), once at `0x803` (XOR `0x01`) and once at `0x1ac` (XOR `0xff`).

**Not delivered:** one send of message `0x1507` sub 1 to task id 0 (the
global that holds the receiver's id was never set: its owner task is not
part of this run) and one `ErrorLogMsg(2, 10, 0, 11)` during the `REFER001`

and stays 2; the run ends because no message is left.

**Arguments at entry** (hooked in a scratch run, same inputs):

- `0x0040b8b4(r4 = message)`, `0x0040c308(r4 = message)`,
  `0x0041597c(r4 = message)`. Message: `+8 u16 = 0x04a0`, `+10 u16` tag,
  `+12 u32` status, `+16 u32` buffer, `+20 u32` length. `0x003f72e4` does not
  use `r0` after the call.
- inside the header handler: `0x003f6c3c(message, out)`, `0x0040a8d0(buffer)`,
  `0x0040acb8(kind, volume header, buffer, file record)`,
  `0x0040aea4(buffer, file index, 6, file record)` which calls
  `0x0040aa50(buffer, file index, level)` once per level.
- inside the directory handler: `0x0040be84(message, control block, table)`.
- inside the block handler: `0x004156a4(0, message, control block, slot)`,
  `0x004144a8(buffer, flags *, out *)`, then `0x004157dc` picks the body
  decoder and calls it as `(buffer, destination)`.

**The block header check** (`sh4dis --va 0x004144a8`): the `u16` at buffer
`+2` is compared with 64 and the `u16` at `+4` with 80 (`cmp/hs`); a larger
value sets bit 0 resp. bit 1 of the result instead of being stored. The
`u16` at `+10` is merged into the caller's flag word.

**Body decoders** named in `0x004157dc`'s literal pool: `0x0041509c`,
`0x00415330`, `0x00414ae0`, `0x00414dbc`, `0x0041478c`, `0x00414930`,
`0x00414500`, `0x00414644`. Four of them ran here.

**Where the directories are.** The three tile headers hold, at `0x800`, a
list of 6-byte entries ending in `ff ff ff ff`. Read as
`{u24 sector, u8 offset, u16 length}` (big-endian in the file) with
`position = sector * 0x800 + offset * 0x100` and `bytes = length * 0x100`,
the entries give exactly the directory reads the firmware made:

## Interpretation

- **FACT:** tile bytes reach the firmware as read completions. The entry is a
  handler called with one argument, the completion message; which handler
  depends on bits 8..14 of the request tag (table at data VA `0x178d60`).
- **FACT:** for `MAPAL001` files the handlers are `0x0040b8b4` (first
  `0x1000` bytes), `0x0040c308` (level directory) and `0x0041597c` (data
  block). They ran on `LEV3456R.DAT`, `B48R068R.DAT` and `B28R070R.DAT` and
  loaded bytes of each buffer.
- **FACT:** the handlers return nothing the caller reads. Their result is
  state in the file's record and the next read request.
- **FACT:** the header handler does not bound the level-table walk by the
  header size: a wrong first byte made it load up to `0x805`.
- **FACT:** the block header reader rejects a first count above 64 and a
  second count above 80.
- **OBSERVED:** the list at header `0x800` is the directory pointer list; the
  encoding fits three files and one changed byte. Not checked: more than
  three entries, and what follows the terminator.
- **OBSERVED:** the buffers are in the swapped form the map-file layer
  produces (C-4641), so a `u16` the firmware loads at buffer offset N is the
  file's big-endian `u16` at N.
- **HYPOTHESIS:** `B48R068R.DAT` is read because the car position was never
  written (all zero) and that cell holds the default position; `B28R070R.DAT`
  is read because it is file id 1 of the directory.
- **UNKNOWN:** the fields inside the level directory and inside each block
  body (only byte runs are recorded); the role of each of the eight body
  decoders; what message `0x1507` asks and who answers it; whether the mount
  reaches state 3 on the unit before or after the first data block.
- **Not a claim about the unit:** the object store, the saved settings and
  the other tasks are models or absent. The reads and the parsers are the
  firmware's own code on the card's own bytes.

## Conclusion

The hypothesis holds and the falsifier did not fire: the handlers load the
returned bytes, and changing one byte of the tile changes the next request
(`0x803`) or the loads (`0x1ac`). `M9.13` gets a documented entry: the
completion handlers, their one argument, and a tool that produces the calls
with real state (`datask_l3.py mount`). A bare `(tile, dst)` prototype does
not exist in this code path.

## Reproduction

```
python3 tools/datask_l3.py --selftest
python3 tools/datask_l3.py tables archive/head256.img
python3 tools/datask_l3.py mount archive/head256.img --card-image <EU card image> --json out.json
python3 tools/datask_l3.py mount archive/head256.img --card-image <EU card image> --file B28R070R --flip MAPAL001/B28R070R.DAT@0x803:0x01
python3 tools/datask_l3.py mount archive/head256.img --card-image <EU card image> --file B28R070R --flip MAPAL001/B28R070R.DAT@0x1ac:0xff
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f72e4 --count 70
python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x004144a8 --count 40
```

## Follow-ups

- **M9.13:** register the run as the tile target: same card with one tile
  replaced by a tile from `tilewriter.py`; compare the rows of that tile
  (positions asked, handlers, bytes loaded) with the factory run, and treat
  a `REJECT`-like difference (a directory read outside the file, block
  header bits set) as the verdict.
- **M4.40 / block grammar:** `--bytes --json` gives, per block, every byte
  the decoder loaded. The first byte it does not load bounds the record.
- **A data block of `B28R070R.DAT`:** needs a map request. Message `0x14b5`
  (handler `0x004066ac` → `0x0040638c` → `0x0040d4a0`) is the candidate; its
  body is not decoded.
- **Message `0x1507`:** find the task that owns the id global and what it
  answers; the mount may wait for it.
- **US build:** all VAs are EU2011 (H51 rule); the tables move.
