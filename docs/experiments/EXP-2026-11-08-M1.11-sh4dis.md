# EXP-2026-11-08-M1.11: `tools/sh4dis.py`, SH-4 decoder with the little-endian convention pinned

- **Status:** done
- **Date:** 2026-11-08
- **Sample:** `IMG256` = first 256 MiB of the EU 2011 card
  (`LEAF_2011-2012_QSD-309-101_navi158_eu.img`), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (checked with `sha256sum`). Modules: `nk.exe` in image B (`--image-start 0x3e00200`,
  sec0 `0x88001000`), `Navi.exe` in image A (`--image-start 0x200200`, text `0x00011000`).
  Path used on the reference machine: `/home/marek/projekty/OSM2Leaf/archive/head256.img`
  (git-ignored, not copied into the worktree).
- **Tools:** `python3` 3.15.0 (`/usr/bin/python3`); repo tools `tools/sh4dis.py`
  (new), `tools/sh4xref.py` (rerouted through `sh4dis`), `tools/cerom.py` (section and
  module table). No external disassembler: `objdump -i` has no SH target and
  `python3 -c "import capstone"` raises `ModuleNotFoundError` on this machine.
- **Claims:** C-2480 – C-2489
- **Supersedes:** none. Corrects one sentence of EXP-2026-11-06-M8.E1b (see Interpretation).
- **Superseded by:** none

## Question

Does one repo tool decode the SH-4 subset the reader work needs from little-endian
halfwords, reproduce the pinned `nk.exe` prologue at `0x880385e4` and flag test at
`0x88038666` on the real image, and give `sh4xref.py` the same output without any
external disassembler?

## Hypothesis

H1: the subset decodes correctly from LE halfwords, and the BE reading does not
(M8.E1 failure mode). H2: `sh4xref.py` output on the four M1.8 pinned call sites is
unchanged after it is routed through `sh4dis.py`.

**Falsifiers.** H1 is refuted if any pinned prologue, flag-test or pool mnemonic
differs from the EXP-2026-11-06-M8.E1b bytes, or if the BE reading of the same bytes
also matches the prologue. H2 is refuted if any of the four `sh4xref` outputs differs
by one byte from the output recorded before the change, or if `sh4xref` fails with
`PATH` set to a directory that has no binaries.

**Iteration on the way to these numbers (kept because it changes the invariant).**
The first sweep, with the literal test against the full file bytes of each section
(`psize`), reported 3 `mov.l` literals outside the section in each module. Their
addresses were `0x8804d79e`, `0x8804d7a0`, `0x8804d7e2` in `nk.exe` and `0x0055cd46`,

holds a form-1 comphdr at `0x8804d770`, M8.E1b). The sweep was then changed to decode
only up to `vsize`.

bound is the section's loaded extent from the o32 table, not a list of excluded

## Interpretation

- **FACT (VERIFIED, real bytes):** `nk.exe` at `0x880385e4` is the 8-halfword prologue
  in the table above when the bytes are read little-endian (C-2480). The flag test at
  `0x88038666` is the six-halfword sequence, and its `bf` targets `0x8803867a`
  (C-2481). The four pool slots hold the DECOMP_ALLOC, DECOMP_WRAP, DECOMP_SECT and
  DECOMP_BLK addresses (C-2482).
- **FACT (VERIFIED, control):** the BE reading of the same bytes gives `mov #47,r6`
  and fails the pinned check (C-2483). The LE convention is therefore a checked
  property, not an assumption that happens to hold.
- **FACT (VERIFIED, counts):** the `mov.l` PC-relative literals in the loaded code of
  `nk.exe` (9,666) and `Navi.exe` (142,344) all lie inside the section's file bytes and
  are 4-aligned (C-2484, C-2485).
- **OBSERVED:** when the decoder walks past `vsize`, 3 `mov.l` literals per module lie
  outside every uncompressed section (`nk.exe` `0x8804d79e`, `0x8804d7a0`, `0x8804d7e2`;
  `Navi.exe` `0x55cd46`, `0x55cd8c`, `0x55cdc2`), past the `vsize` end of the code.
- **HYPOTHESIS (not established):** those 3 loads per module decode file tail or embedded
  data rather than code (for `nk.exe` the tail holds the form-1 comphdr at `0x8804d770`,
  M8.E1b). This is an interpretation of the observed addresses. It is not verified
  against the bytes, and the sweep does not count those loads.
- **FACT (VERIFIED, parity):** `sh4xref.py` output on the four M1.8 pinned sites is
  byte-identical before and after routing its decoding through `sh4dis.py`, and it
  needs no `objdump` (C-2486).
- **FACT (VERIFIED, history):** `tools/sh4xref.py` has never invoked `objdump`
  (`git log -S objdump -- tools/sh4xref.py` is empty). The M1.11 task block said it
  shells out to `sh4-linux-gnu-objdump`; that is wrong, and the "objdump absent" case
  was already satisfied (C-2487).
- **CORRECTION (prose only, no claim changed):** EXP-2026-11-06-M8.E1b describes the
  prologue as saving "r8-r13, pr". The bytes `e6 2f 86 2f 96 2f a6 2f b6 2f c6 2f d6 2f
  22 4f` save **r14** first (`mov.l r14,@-r15` = `0x2fe6`), then r8 through r13, then PR.
  The E1b VA and prototype conclusions are unaffected.
- **UNKNOWN (C-2488):** the decoder has no independent oracle on this machine
  (no SH target in `objdump -i`, no `capstone`). Its correctness beyond the pinned
  bytes and the per-family encodings in the self-test is not established.
- **UNKNOWN (C-2489):** `mov.w @(disp,PC)` has no pinned real-image value. Its
  1,698 loads (nk) and 77,653 loads (Navi) are counted and target-checked only.
- **OBSERVED:** about 16 % (`nk.exe`) and 24 % (`Navi.exe`) of halfwords in the loaded
  code decode as `.word`. These are literal pools, data and the FPU/system opcodes the
  subset omits. The share is coverage, not a correctness rate, and it is not used as
  evidence for any claim.
- **FACT (scope of the M1.11 task block):** the block asked for `mov.b/mov.w/mov.l`,
  `add/sub/cmp/eq/tst`, `bf/bt`, `jsr/bsr/jmp/rts/nop`, `shl`, `and/or`. All are
  decoded; the prologue and flag test also needed `sts.l pr,@-r15`, `lds.l @r15+,pr`,
  `mov #imm`, `mov.l @(d,Rm)`, `shll8`, which are decoded too.

## Conclusion

`tools/sh4dis.py` decodes the subset from little-endian halfwords, pins that
convention in one function (`read_u16`, used by `Mem` in both tools), reproduces the
`nk.exe` prologue, flag test and four pool values on the real image, and fails loudly
on the BE reading. `tools/sh4xref.py` now decodes through it and gives identical output
on the four M1.8 pinned call sites with no `objdump` on `PATH`. Ledger rows C-2480 to
C-2487 are VERIFIED; C-2488 and C-2489 are UNKNOWN and are open. `docs/format/` is not
changed by this task.
