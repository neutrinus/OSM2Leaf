## Question

Can the ROMHDR → section → bytes step that at least four `*_l3.py` tools each
carry be moved into one helper without changing any tool's output on the
factory image, and with the H51 "a compressed section is decoded by the
kernel's own routine, never skipped" rule made atomic?

## Hypothesis

The four copies (`point_walk_l3.module_sections`, `mapcode_l3.module_layout`,
`chunk_decoder_l3.image_init_sections` and the section loop in
`poi_position_l3`) call the same `cerom.CERom` → `o32` → `va2file` sequence;
moving them onto one helper that returns both a rich (decoded) and a legacy
(cheap) view leaves the bytes the tools consume identical. **Falsifier:** a
tool output on `head256.img` that changes after the move (then that call site
keeps its shim, per the task Stop), or a fifth `_l3.py` that reaches
`cerom` directly and would have been wrong under the new helper (then the API
is too narrow).

## Method

1. **Sample and hash.** `archive/head256.img`, SHA-256 `92aa525d…a007f9` for
   the first 256 MiB (per EXP-2026-11-06-M2.15); factory pairs and
   `HDD_INFO.TXT` as above, read-only outside the repo.
2. **Commands.** Every before/after capture used the same argv, with
   `OSM2LEAF_DECOMP_CACHE` pointed at a fresh empty directory per capture
   (`…/scratch/m1.47/cache-before`, `…/cache-after`), so the decode cache
   cannot hide a difference:

   ```bash
   B=~/projekty/leafre-work/scratch/m1.47/after
   export OSM2LEAF_DECOMP_CACHE=$B/../cache-after
   IMG=archive/head256.img
   F=/home/marek/projekty/leafre-work/m5.13/factory/REFER001
   H=/home/marek/projekty/leafre-work/m5.4/card-factory/VER_INFO/HDD_INFO.TXT
   python3 tools/point_walk_l3.py sections "$IMG" > "$B/pw-sections.txt" 2>&1
   python3 tools/point_walk_l3.py walk "$IMG" --cmp "$F/POINT010.DAT.cmp" \
       --ind "$F/POINT010.DAT.ind" --page 0x840ba0 --page-len 42848 > "$B/pw-walk.txt" 2>&1
   python3 tools/mapcode_l3.py run "$IMG" --card "$H" --unit-from "$H" \
       --json > "$B/mapcode.txt" 2>&1
   python3 tools/chunk_decoder_l3.py run "$IMG" --cmp "$F/POINT010.DAT.cmp" \
       --ind "$F/POINT010.DAT.ind" --sec1 image > "$B/cd-image.txt" 2>&1
   python3 tools/chunk_decoder_l3.py run "$IMG" --cmp "$F/POINT010.DAT.cmp" \
       --ind "$F/POINT010.DAT.ind" --sec1 zero-mask > "$B/cd-zero.txt" 2>&1
   python3 tools/poi_position_l3.py run "$IMG" --dir "$F" --file POINT010 \
       --count 200 --json "$B/poi.json" > "$B/poi.txt" 2>&1
   for f in pw-sections.txt pw-walk.txt mapcode.txt cd-image.txt cd-zero.txt \
            poi.txt poi.json; do
       cmp -s "$B/../before/$f" "$B/$f" && echo "$f IDENTICAL" || echo "$f DIFF"
   done
   # after: all seven IDENTICAL
   python3 tools/l3check.py --build-corpus    # before (detached base) and after
   python3 tools/selftest.py                  # 183 passed, 0 failed
   ```

   The before capture ran on the claim commit `e1fbd2f2` in a detached worktree
   at `…/scratch/m1.47/base`; the after capture ran on the work commit
   `4504bcd1`.
3. **Controls.** Positive: the four tools pass on the factory image
   (`pw walk` prints `result: PASS`, `cd-image`/`cd-zero` print `verdict:
   PASS`, `poi` prints `RESULT: ACCEPT`, `mapcode` `"r0": 1, "verdict":
   "ACCEPT"`). Negative: `ce_module --selftest` fakes the decoder to raise
   `DecompError` and asserts the helper **raises** instead of returning
   `None`; a second negative asserts a compressed section outside
   `EAGER_STARTS` is `(None, None)` (lazy) and never silently decoded.
4. **Scope.** The four named call sites only. Out of scope, named so a later
   pass does not re-open it: `vcard_l3.py:324` (a loader total),
   `va_class.py:48` (a classifier), and `ce_strfind.py:66`, which has a
   same-named but different function (`module_sections(rom, module, data,
   include_compressed)` over `cecompress` statuses `RAW`/`DECODED`/
   `UNSUPPORTED`, not the ROMHDR path). Eager decode is scoped to image starts
   `0x200200`/`0x3e00200`; build B of the EU2014/2016 cards fails in
   `nk_decomp` (C-6509) and is never eagerly decoded.
5. **Falsifier.** Any `cmp` DIFF above, or an in-scope `_l3.py` that still
   reads section bytes through `cerom` directly and needed a shape the helper
   cannot give.

## Interpretation

- **FACT:** moving the four call sites onto `ce_module` leaves every tool's
  output on the factory image byte-identical (seven files `cmp`-identical,
  fresh decode cache each capture).
- **FACT:** the helper decodes a compressed section through
  `nk_decomp.section_bytes` and reports `init_len` separately from `vsize`, so
  a VA in BSS is visibly BSS, not code.
- **OBSERVED:** eager decoding Navi.exe's two compressed sections (16.7 MB
  window) costs ~2.86 s cold and ~0.016 s warm; the four call sites that need
  these bytes already paid it (`chunk_decoder --sec1 image`).
- **FACT:** one in-scope `_l3.py` remains a section-byte walker:
  `point_tree_l3.py:161` decodes every STDDLL section itself
  (`nk_decomp.decompress`, `IMAGE_SCN_COMPRESSED` at `:163`). This is the
  task's own falsifier ("a fifth `_l3.py` ... would have been wrong under the
  new helper"). It is **not** moved in this pass because the four-site
  byte-identity capture does not include `point_tree_l3 run`; moving it without
  that capture would be an unmeasured change. A follow-up captures its output
  first, then moves it.
- **HYPOTHESIS:** the other remaining `cerom.CERom(` sites in `*_l3.py` /
  `l3_harness` are import/thunk resolvers or loader totals, not section-byte
  walks — a later audit should confirm rather than fork.
- **UNKNOWN:** none new; EU2014/2016 build B stays out of the eager path by
  construction (C-6509), untested here.

## Conclusion

`tools/ce_module.py` is the one owner of the CE ROMHDR → section → bytes
step, with `module_sections` (rich, eager decode scoped to `0x200200`/
`0x3e00200`, never a silent `None`), `legacy_sections`/`legacy_module` (the
cheap 3-tuple view `point_walk_l3` and `mapcode_l3` used), `text_section` and
`find_section`. The four named call sites delegate to it; their output on
`head256.img` is unchanged, `l3check` is unchanged, and `selftest.py` is
green (183/0). No claims.md row beyond C-6630–C-6639 changed.
