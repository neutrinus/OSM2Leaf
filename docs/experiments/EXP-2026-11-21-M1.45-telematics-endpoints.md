## Question

For the Carwings/telematics stack of build A (`Telema.exe`, `ComMid.exe`,
`Telema*CC`, `Cws_Apl`, `Prb_Apl`, `DCM_API`), what is the transport, what
server endpoints and APNs are in the binary, and for which request types is
there a builder function whose payload fields are readable from strings — in
EU2011 and US2011?

## Hypothesis

`Telema.exe` is a Carwings client that does not own the modem: it drives an
HTTP/XML application over a connection set up elsewhere (RAS/PPP, Bluetooth
DUN or the DCM/TCU), with a fixed endpoint table and a small set of DLJ
session-request builders, one per request type. The two builds share the
approach and differ in `sec0` size and some string offsets; the request
builders exist in both.

Falsifier: (a) `Telema.exe` itself imports `DCM_API!Dial`/`HangUp` or opens a
COM device, which would put the dial in the same module; (b) an endpoint string
has no code xref (a dead literal, not a table); (c) the "builder" function for
a request type does not load that request's string (i.e. it is only a logger
that shares the string).

## Method

1. **Sample and hash.** The two 256 MiB firmware heads above; no other bytes.
   Module/section addresses for `Telema.exe` come from the CE ROM TOC in the
   image, read by `tools/cerom.py` (never a fitted delta).
2. **Commands.** Run from the repository root; both images are expected at the
   named paths (fetch with `tools/fetch_image.py` if absent — the images are
   not committed).

   ```bash
   # module presence and sizes (EU; the US run is the same with us256.img)
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img modules \
     | grep -iE 'telema|commid|cws|prb|dcm'

   # which module really dials the TCU
   for m in $(python3 tools/cerom.py --image-start 0x200200 archive/head256.img modules | awk '{print $2}'); do
     python3 tools/cerom.py --image-start 0x200200 archive/head256.img imports "$m" 2>/dev/null \
       | grep -iE 'DCM_API!(Dial|HangUp)' && echo "  <- $m"
   done

   # endpoint / APN strings, with VA, in each build
   for img in head256 us256; do
     python3 tools/ce_strfind.py --image-start 0x200200 archive/$img.img \
       service.caravelmap.jp cwsxanavi.myhome.cx biz.nissan-gev.com qa.nissan-gev.com \
       www.ev-itvc.jp dev.nissan-gev.com drive1-dev.saas.secureonline.jp \
       /xanavi/cws.exe /xanavi/EV_cws.exe Trial.globalm2m.net atxg.rogersm2m.apn \
       bwv8g.dcm.ne.jp attz.atxg.com bc572.dcm.ne.jp mopera.ne.jp \
       ISPDA@CINGULARGPRS.COM internet.connexion application/x-carwings-nz \
       --module Telema.exe --encoding ascii | grep -E 'needles|va=0x'
   done

   # builder VA for a DLJ request string (EU and US)
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x0002564c  # Req CreateSession
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x00025490  # Req SendData
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x000253ec  # Req SetAPN
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x00025084  # Req CloseSession
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x000232c8  # Req GetOperatorInfo
   python3 tools/sh4xref.py archive/us256.img   Telema.exe --image-start 0x200200 --to 0x00025c74  # US CreateSession
   python3 tools/sh4xref.py archive/us256.img   Telema.exe --image-start 0x200200 --to 0x00025ab8  # US SendData
   python3 tools/sh4xref.py archive/us256.img   Telema.exe --image-start 0x200200 --to 0x00025a14  # US SetAPN
   python3 tools/sh4xref.py archive/us256.img   Telema.exe --image-start 0x200200 --to 0x000256f4  # US CloseSession
   python3 tools/sh4xref.py archive/us256.img   Telema.exe --image-start 0x200200 --to 0x00023980  # US GetOperatorInfo

   # endpoint-table builder and XML envelope builder
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x00025318  # /xanavi/cws.exe  -> fn
   python3 tools/sh4xref.py archive/us256.img   Telema.exe --image-start 0x200200 --to 0x00025940  # US /xanavi/cws.exe -> fn
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x000234a8  # XML prolog      -> fn
   python3 tools/sh4dis.py archive/head256.img Telema.exe --image-start 0x200200 --va 0x000a738c --count 110
   python3 tools/sh4xref.py archive/head256.img Telema.exe --image-start 0x200200 --to 0x00023630  # cws_rcv.xml -> fn 0x000a7b10
   ```

3. **Controls.**
   - *Positive:* `DCM_API!Dial`/`HangUp` must be imported by exactly one
     module — the search above prints `PhoneBTA.exe` and nothing else; and a
     known-present string (`/xanavi/cws.exe`) must resolve to a builder
     (`fn 0x000b0d58` EU, `fn 0x000b1e68` US). Both succeed.
   - *Negative:* `0x00025c88` (a `Req CreateSession` substring that is **not**
     a literal-pool target) must print `no literal pool holds …` — it does,
     which is why the VA must be the string *start* (`0x00025c74`), not any
     offset into it. A logger-only function would load a *different* string
     than the one its request names; each builder below loads its own start VA.
4. **Scope.** Both `Telema.exe` instances in `sec0` only (the sole uncompressed
   executable section; `sec1`/`sec2` are compressed `.data`, out of scope).
   Endpoint/APN strings: 18 needles per build (19 and 18 hits in EU and US).
   Builder VAs: 5 DLJ request types per build + the endpoint-table builder +
   the XML envelope builders. Not covered: the binary struct layout handed to `DCC`/`DCM`, the
   per-data-class wire format, `ComMid.exe` routing.
5. **Falsifier.** As stated in Hypothesis: the dial living in `Telema.exe`
   (refuted — it is `PhoneBTA.exe`), a dead endpoint literal (refuted for the
   `/xanavi/…` paths — they xref to a builder), or a builder that does not load
   its own request string (refuted in the Observations).

## Interpretation

- **FACT:** the dial is not in `Telema.exe`; `PhoneBTA.exe` is the only build-A
  module importing `DCM_API!Dial`/`HangUp`. `Telema.exe` imports the socket API
  and the DCM status/ID API, and carries the RAS/PPP/AT/DUN state strings.
- **FACT:** the endpoint table (hosts, `/xanavi/…` paths, MIME,
  `service.caravelmap.jp` dispatcher, APN list) is present in both builds; the
  EU build adds a `qa.nissan-gev.com` base-URL alternate (19 vs 18 hits on the
  same 18 needles).
- **FACT:** five DLJ request types have a distinct request-emit function in both
  builds that loads its own request's trace/format string (which names the
  payload fields) and operates on a `80<<2 = 320`-byte session record; the
  fields readable from strings are session id / client port / data length /
  status words / operator id. The binary struct layout those fields occupy is
  not decoded (HYPOTHESIS below).
- **OBSERVED:** the application layer is XML (`cws_snd.xml`/`cws_rcv.xml`,
  prolog + named body; the request body is `cws_snd.xml`, the received body
  `cws_rcv.xml`, built by separate functions); the 25 `cws*` data-class names (charging points,
  traffic, route, DJ, phone info, …) are the request/receive topics.
- **HYPOTHESIS:** the binary struct order handed to `DCC`/`DCM` and the
  per-data-class wire format; only names were read, not a decoded record.
- **UNKNOWN:** `ComMid.exe` message routing.

## Conclusion

`docs/firmware/telematics.md` now lists the transport split (dial in
`PhoneBTA.exe`, HTTP/XML and bearer selection in `Telema.exe`), the endpoint
and APN table with per-build VAs, and the request builders for five types in
EU2011 and US2011, satisfying the task's "≥ 3 request types with builder VA and
string-readable payload fields". Claims C-6470–C-6479 record each part, and
C-6730–C-6731 record the two review corrections below. Still open: binary
struct layouts, per-class wire format, `ComMid.exe` routing.
