- **Date:** 2026-11-21
- **Sample:** firmware `archive/head256.img` (IMG256, EU2011 build A) SHA-256

## Question

M9.58 left the served road record copied into the client task's buffers and
handed to `LOC_map` with a `0x0fa0` sub `0x019a` message, with no code seen
to read the copy. Which function walks the shape words of that copy, how many
bytes does it load on the factory record F and on our generated record G, and
does one changed word of our record change the walk?

## Hypothesis

The walk is behind the `LOC_map` receiver `fn 0x00421548`, in one of the two
functions it calls with the message (`fn 0x0041f3dc`, `fn 0x004205b8`). M9.58
saw it return early because the group table was filled by hand and the task
id `*0x011fff74` was unset. With the groups filled by the firmware's own
position handler the receiver reaches the walk, and the walk reads the shape
buffer (`record + 0x2c`).

**Falsifier (set before the runs):** with the group and slot tables written
only by firmware code, `fn 0x00421548` still returns with 0 guest loads from
the shape buffer and the tail buffer. Then the walk needs another task's
state and the task records where it stops.

2. **Commands.**


   The tool runs firmware code only: the mount (`datask_l3.py`), the pool
   allocator `fn 0x00470914`, the client init `fn 0x00427a34`, the client
   dispatcher `fn 0x00427144` (position message, request tick, each reply),
   the data-access task (the request the client itself sent) and the
   `LOC_map` receiver `fn 0x00421548`. Declared models: message delivery

   `0x011fff74`), the position message and the tick, and `--patch` (one
   record word changed in guest memory between the inflate and the copy).
   Read watches cover the whole shape pool block and tail pool block.
3. **Controls.** Positive: the factory record F through the same chain.
   Negative: a changed word the walk does not load (`59`) must leave the
   trace SAME though the copy differs; a changed word outside the copied
   region (`4`) must leave copy and trace SAME. Positive for the reference
   word: `58` changed on G and on F must change the trace.
4. **Scope.** EU2011 build A, one mesh (`0xa6c1d6b2`), one position (x = y =
   1024, the quadrant that needs no neighbour mesh), record kind 4 only, the
   undivided-record branch of the receiver (group flag 0 -> `fn 0x0041f3dc`).
   Not run: the divided-record branch (`fn 0x004205b8`), other positions
   (`fn 0x00423538` then calls `STDDLL!STD_MeshID_getAny`, not mapped in
   this machine), `LOC_db`, `RAW_rec`, the kind-`0x40` reply's consumer.
5. **Falsifier.** As above: 0 guest loads from both buffers.

## Interpretation

- **FACT:** the requests come from firmware code. The position message
  (`0x0fa0`, sub 118/119/`0xcb`/`0xcd`, `+12` mesh, `+16` x, `+20` y, both at
  most `0x7ff`; `0x004271a4`–`0x004271e0`) reaches `fn 0x00428290`, which
  builds the wanted list with `fn 0x00427dc8` (four entries: mesh and a
  quadrant word `0x0101`/`0x0000`/`0x0001`/`0x0100`) and stores it in the
  groups through `fn 0x00427cd4` -> `fn 0x00427578`. The tick (`0x07d0` sub
  `0x7530`, `+28` = `0x03f1`; `0x004272e0`–`0x004272f6`) runs
  `fn 0x00426d3c`, which calls the requester `fn 0x00425f40` once
  (`*0x009e3e28` is its done flag): message `0x14b5` sub 2, kind 4, with the
  client's own id `*0x011fff5c` at `+12` and a list of the four (mesh, DIVID)
  pairs, sent to the data-access task; `fn 0x004266ec` sends the kind-`0x40`
  list.
- **FACT:** the data-access task answers the four entries with one record
  (DIVID `0x0303`, the undivided record): the handler `fn 0x0042613c` then
  clears the group's divided flag (`0x0042627a`), all four slots end in
  state 2 with the same shape buffer, and the client posts the `0x0fa0` sub
  `0x019a` message to `*0x011fff74` (two senders build it: M9.58's
  `0x004259bc` and `0x004277ee` in `fn 0x00427578`; two messages were sent).
- **FACT:** `fn 0x00421548` takes the message's group index, and for a group
  with divided flag 0 calls `fn 0x0041f04c` per slot (it claims one of the
  four 48-byte result entries of `*0x00e8f5dc`) and then `fn 0x0041f3dc`
  (0x11dc bytes), which loads the shape buffer. So `fn 0x0041f3dc` is the
  walk of a served record's shape words, with `fn 0x00422384` reading the
  row counts first. The falsifier did not fire: 5,363 loads (6,868 distinct
  bytes) on F and 49 loads (70 distinct bytes) on G.
- **FACT:** what the walk loads, from the instructions and the offsets: 12
  rows of (start, count) at buffer bytes `2 + 4 i`; a row's first shape at
  byte `4 * start`; shape word 0 (low 13 bits: length in words, the next
  shape; top 3 bits: extra header words), word 1 (low 12 bits: point count),
  word 2 (top nibble `0xa`/`0xb` sets a flag that takes the branch at
  `0x0041f63a` past the per-point block),
  word 3 (low 2 bits: more header words); the first point at word
  `7 + (w3 & 3) + (w0 >> 13)`; a point is an (x, y) word pair with 11-bit
  coordinates and flag bits, followed by one word for each of: x bits
  `0x1800` not both set, y bit `0x2000`, y bit `0x1000`, y bit `0x0800`
  (`0x0041f572`–`0x0041f5a8`).
- **FACT:** the walk follows one reference per point: for a point at word
  index `p` whose coordinates are neither 0 nor `0x7ff`, the word at
  `2 (p + ((y >> 13) & 1)) + 4` is the word index of another point
  (`0xffff` = none), and the walk loads that point's y, its own reference
  word and compares it with `p` (`0x00420174`–`0x004201f8`). On F the first
  such word is `0x0179` (inside the record). On G it is `0x0100`, 330 bytes
  past the end of the 184 B record and past the 512 B copy window, so the
  firmware loads stale pool bytes there (`0x202`, `0x204`).
- **FACT:** the word M9.58 called the link id (record word 59) is not loaded
  by the walk: changing it changes the copy and nothing else. The word the
  walk does load (record word 58 on G and on F) changes the trace on both
  records. A word outside the copied region changes nothing.
- **OBSERVED:** the result table has non-zero per-quadrant counts for F and
  only zeros for G, with the reference word patched or not. Which rule of
  the walk leaves our two shapes uncounted was not isolated.
- **OBSERVED:** the tail buffer (`record + 4*w17`, M9.58's second copy) is
  not loaded by `fn 0x00421548` or anything it calls in this run.
- **UNKNOWN:** the divided-record branch `fn 0x004205b8`; the consumer of
  the result table and of the `0x1774`-byte blocks at `*0x00e8f5c4`
  (`fn 0x0041f26c` runs last and sends nothing in this run); `LOC_db` and
  `RAW_rec`; the US2011 twins of every VA here.

## Conclusion

The shape walk of a served road record is `fn 0x0041f3dc` in the `LOC_map`
task (EU2011 build A), reached through `fn 0x00421548` when the client's
group table is filled by the firmware's own position handler. It loads
10,726 B (6,868 distinct) of the factory record and 98 B (70 distinct) of
our generated record. Our record is walked, but its first point's reference
word (`0x0100`) points outside the record, and none of its shapes is counted
in the result table. One changed reference word gives DIFFERENT on both
records; M9.58's word 59 is not read by this walk. Display code was not
needed.
