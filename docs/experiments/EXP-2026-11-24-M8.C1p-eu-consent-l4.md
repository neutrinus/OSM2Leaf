## Question

Why did the consent screen still show on Marek's car with the EU card, and
does a corrected card patch leave `SRT_COLD_I_AGREE` with no tap on the
unit's own kernel and flash?

## Hypothesis

The earlier EU patch never reached the consent handler. Falsifier: the
corrected patched EU card on NK1 + the owner's flash stays in
`SRT_COLD_I_AGREE`, or the unpatched control leaves it too.

## Method

### 1. Sample and hash

Hashes as in Sample (`sha256sum`). `ze0_consent.py find` on the original
and on the map-coded card; `verify` on every patched card.

### 2. Commands


## Observations

**O1 — first bug: build detection.** `card_mapcode.py --from-nk1` writes the
unit's build name `X210NBNI.147` into both NKOK headers of the EU card.
`ze0_consent.py` chose the build by that name, so it treated the map-coded
EU card as the US build and rewrote two EU literals `0x089e→0x0889` (file
`0x1405912`, `0x143f2c0` and the NB01 copies) that are not the consent
handler. `verify` printed PASS on that card. A card prepared in the
documented order (map code first, then consent) got this wrong patch.
Booted (run `pat`): `SRT_COLD_I_AGREE` 8, `VAR_I_AGREE_STATUS` 0, so the
screen stays.

**O2 — second bug: EU event ids.** With the build found correctly, the
patch `0x08a6→0x0891` (C-10110/C-10111) also left the consent screen in
place: control and patched card both log `Event[SK_OTH_SCREEN_UNLOCK]
Handled at State[SRT_COLD_I_AGREE]`, `UpdateScreenLock Lock[0]`, and no
`VAR_I_AGREE_STATUS` (runs `pat2`–`pat4`, all `VAR_I_AGREE_STATUS` 0). The
patched function `0x02bd66fc` was never entered (gdb on `pat4`, 0 hits).

**O3 — the real EU handler (gdb + sh4dis).** The handler called for state id
`0x263` (thunk at `0x02c21b04`: `mov.w #0x263,r0; rts`) is `0x02c21b0c`. gdb
caught it with `r5 = 0x088f` right after the consent screen was shown. Its
first comparison is `mov.w @(0x02c21b5a,pc),r3` = `0x08a4`; `cmp/eq r3,r5`.
`0x08a4` occurs as a compared literal exactly twice in the module
(`0x02c21b18` and `0x02c22114`, the sibling state `0x264`), the same shape as
the two US sites. So on EU `SK_SCT_AGREE_CLICK` = `0x08a4` and
`SK_OTH_SCREEN_UNLOCK` = `0x088f` (event index + 1), not `+3` as derived
earlier. Literal file offsets: `0x1436d5a`, `0x143748c` (NB00),
`0x3236d5a`, `0x323748c` (NB01).

**O4 — L4 result (corrected patch, 0 taps).**

| card | `SRT_COLD_I_AGREE` | `SK_SCT_AGREE_CLICK` | `VAR_I_AGREE_STATUS` | `ForwardState [MAP_MAPOPERATION_NORMAL_MAP]` |
| --- | --- | --- | --- | --- |
| control (map code only) | 8 | 0 | 0 | 0 |
| patched (`0x08a4→0x088f`) | 9 | 0 | 1 | 1 |

The map plane shows London (Soho, Piccadilly Circus). DU plane 1 still
holds the consent text in its upper half; the US run of M8.C1n after a real
OK tap shows the same stale half, so plane 1 is not the oracle here.

**O5 — tool controls.** `--selftest` PASS. `verify` on a card with the O1
wrong patch: FAIL with "WRONG earlier patch at 0x1405912,0x143f2c0".
`patch` on it repairs both literals and patches the right sites; the
result is byte-identical to a fresh patch of the control (`cmp` over the
first 56 MiB: 0 differences). US dry run unchanged (`0x1479a9a`,
`0x147a1b4`).

**O6 — audio, EU vs US image A.** ROM B and C are identical (M1.54). In
image A, 147 of 148 common modules differ in code. The wave drivers
(`waveapi`, `audevman`, `wavessi1/2`) have the same section sizes and differ
in 110–400 bytes of `.text` (relocation-sized differences; `audevman` more).
`Audio.exe` differs in substance: EU 228 864 B with the RDS tuner
application (`RDS APPL … IOCTL_RDS_*`, `_rds_shared_mem`, AF/TA/PTY/REG),
US 241 152 B with RBDS (`IOCTL_RBDS_GET_PS_NAME`) and Sirius XM
(`CXmMsg`, `IOCTL_XMR_GET_TEXT`, channel/category scan). Only on EU:
`RDSCC.dll`; only on US: `RBDS_CC.dll`, `XMCC.dll`, `XMStatusCC.dll`.
US `Audio.exe` signals ACM id 105, EU does not (`acm_id_scan`); no launch
record of NK1 waits for 105. NK1's launch table (the unit's, area USA)
starts the tuner drivers `TNR3:` XMRadio and `TNR4:` Rbds (area
`0x00040000`) and not `TNR2:` Rds / `TMC1:` (area `0x00020000`). In the
emulator Audio.exe never reaches its tuner code (no audio micom, 14
`WaitModule Timeout`), so none of this is visible at L4.

## Interpretation

- **FACT:** the consent screen on the car was expected: neither the
  Companion patch (does not fit ZE0, C-8359) nor our first tool version
  (O1, O2) changed the EU consent handler.
- **FACT (L4):** the corrected patch makes the EU card leave
  `SRT_COLD_I_AGREE` with zero `SK_SCT_AGREE_CLICK`, on the unit's own NK1
  and flash with area 0 erased, and the control does not (O4). M8.C1p's
  Done-when is met.
- **HYPOTHESIS (L5):** in the car the automatic `SK_OTH_SCREEN_UNLOCK`
  arrives after the consent screen is shown, as in the emulator. If it came
  earlier, the screen would simply wait for OK as before (the tap path is
  unchanged).
- **HYPOTHESIS (audio lag):** the EU `Audio.exe` drives an RDS tuner
  (`TNR2:`) that the US unit does not start, and does not drive the US
  RBDS/XM drivers the unit does start; its RDS requests fail. Whether that
  causes the lag Marek heard is not shown. Other candidates: audio settings
  of area 0 back to defaults; EU-vs-US audio microcontroller protocol (US
  part `70F3356`, EU `70F3357`, external). An easy car check: does the lag
  also happen with the radio off / BT only, and does the FM band step in
  50 kHz (EU) or 200 kHz (US)?

## Conclusion

`ze0_consent.py` (on top of H143's part-number detection) now uses the EU ids
`0x08a4→0x088f`, checks the exact known literal offsets in `verify` and
repairs both earlier wrong EU patches in `patch`. The EU consent screen is
skipped with no tap at L4. Car test is next.
