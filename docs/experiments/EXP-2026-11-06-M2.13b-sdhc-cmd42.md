# EXP-2026-11-06-M2.13b: SDHC.dll CMD42 flags and the boot-time password source

- **Status:** done (static, two images); bench confirmation is M6.9/M6.5
- **Date:** 2026-11-06
- **Sample:** `IMG256` (first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img`),
  SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Claims:** C-1950–C-1957
- **Supersedes:** C-1884 (in part: "code section compressed")
- **Superseded by:** none

## Question

Which CMD42 flag byte does the unit's SD driver send for each lock/unlock
IOCTL, what password length and buffer does it use, and where does the
password the unit unlocks with at boot come from?

## Hypothesis

`SDHC.dll` builds a textbook CMD42 data block `[flags, PWD_LEN, password]`
from a 16-byte unit value (C-1940, C-1945). Its code was believed to be
compressed (C-1884), which would have blocked a static answer.

## Method

```bash
I=head256.img
python3 tools/cerom.py --image-start 0x3e00200 $I sections SDHC.dll
python3 tools/cerom.py --image-start 0x5200200 $I sections SDHC.dll

# Disassemble image B .text (scratch file, never committed)
python3 -c "f=open('$I','rb'); f.seek(0x04270200); open('text.bin','wb').write(f.read(0xe11d))"
sh4-linux-gnu-objdump -D -b binary -m sh4 -EL --adjust-vma=0x039b1000 text.bin > text.dis

# Anchors and callers
python3 tools/sh4xref.py --image-start 0x3e00200 $I SDHC.dll --to 0x039b2498   # byFlag/byPasswordLen log
python3 tools/sh4xref.py --image-start 0x3e00200 $I SDHC.dll --to 0x039b7df4   # who refers to Lock_Unlock_Card
python3 tools/sh4xref.py --image-start 0x3e00200 $I SDHC.dll --calls 0x039b6ac4
python3 tools/sh4xref.py --image-start 0x3e00200 $I nk.exe  --to 0x01013008
```

Then, by reading `text.dis`: the IOCTL compare chain that loads
`0x80032014`…`0x80032024`; the three vtables (runs of ≥ 100 code pointers
into `.text`); the `mov #imm,r6` in each wrapper; the low-level routines; the
`nk.exe` IOCTL table entry and its handler (disassembled the same way from
`nk.exe` sec 0).

## Observations

### Sections

- B and C: `SDHC.dll` sec 0 (rva `0x1000`, psize `0xe200` ≥ vsize `0xe11d`)
  has flags `0x60000020`: code, **not** `COMPRESSED`. Only sec 1
  (`0xc0002040`) and sec 2 (`0x40002040`), the data sections, carry the
  `0x2000` compressed flag.

### IOCTL dispatch → CMD42 flag

- Image B dispatch (`0x039b5a9c`…): `cmp/eq` against pool constants
  `0x80032014` (`0x039b5b9c`), `…18`, `…1c`, `…20` (`0x039b5ba8`), `…24`, each
  selecting a vtable slot `mov #107`…`#111`, then `shll2` and `jsr` through
  `@(r0,r3)` with `r0 = *this` (pool loads at `0x039b5a9c`, `0x039b5aae`).
- Three vtables in `.text`: `0x039b1290` (111 entries), `0x039b1c30` (113),
  `0x039b2198` (111). In `0x039b1c30`, slots 106–111 are six sibling
  functions `0x84` bytes apart (`0x039b6560`…`0x039b67c0`). Slots 107–111
  each check `pBufIn = @(8,r5)` and `nInBufSize = @(12,r5)` for non-zero, then
  call vtable slot 108 of the object pointed to by `this+0x8c` (slot number
  read from `this+0x90`) with
  `r6 = #imm`, `r7 = (u8)nInBufSize` and `pBufIn` on the stack; on result 1
  they call slot 98 of the same object.

| IOCTL | slot | `r6` immediate | CMD42 meaning |
| --- | --- | --- | --- |
| `0x80032014` | 107 | `0x01` | SET_PWD |
| `0x80032018` | 108 | `0x04` | LOCK |
| `0x8003201C` | 109 | `0x00` | UNLOCK |
| `0x80032020` | 110 | `0x02` | CLR_PWD |
| `0x80032024` | 111 | `0x08` | forced ERASE |

- Image C gives the same five immediates in the same slots (wrappers
  `0x039865b0`…`0x039867c0`, IOCTL pool `0x03985b9c`…).
- Vtable `0x039b2198` slot 108 = `0x039b7df4` (the literal pool at `0x039b2348`
  has no `mov.l` load, i.e. it is a table entry). `0x039b7df4` is
  `CSDHCMain::SDHC_Lock_Unlock_Card`: it loads the `byFlag[%02X]
  byPasswordLen[%d]` format (`0x039b2498`) and the `Err = [%d]` format
  (`0x039b2408`) (C-792). Arguments: `r5` slot (u16, must be < 2), `r6` flag
  (u8), `r7` length (u8), password pointer as the fifth argument. It calls
  `0x039baa0c(slot, flag, len, pwd)` and returns 1 on success.

### CMD42 construction (`0x039baa0c` → `0x039bc050`)

- Flag accepted only if it is `8, 4, 2, 1, 0` or `5` (else error).
- Length: `cmp/hs` against 16 (error if longer).
- Checks a CSD-derived field `& 0x80` (command class 7) before sending.
- Block length set (`0x039bbda8`) to `len + 2`, or to 1 when the flag is 8;
  the previous value is saved and restored afterwards.
- `0x039bc050` writes command byte `0x6a` (`0x40 | 42`) with argument 0, and
  the data block `byte0 = flag & 0x0F`, `byte1 = len`, then `len` password
  bytes copied from the caller's buffer.
- A state byte at `this+27` is set to 1 after flags with bit 0 or bit 2 and
  cleared after flag 2 or 8.

### Boot-time unlock (`CSDHCMain` slot 109, `0x039b6ac4`)

- Called from `CDSKMain::Init` (`0x039b53c8`; the `SDHC_SecurityUnLock() Err =
  ERROR_ACCESS_DENIED` log at `0x039b1df8` follows a failed call).
- Zeroes a 16-byte stack buffer, then calls import slot `0x01f38050`
  (thunk `0x039be868`, name not resolved: imports are pre-bound) with
  `r4 = 0x01013008`, `r5 = buffer`, `r6 = 16`, `r7 = 0`.
- Then calls slot 108 (`SDHC_Lock_Unlock_Card`) with `r7 = 16` and the
  buffer: in one branch first with flag `0x04`, then with flag `0x00`. A
  branch on the slot number (`== 1`) and on two state bytes of its third
  argument skips the calls; their meaning is not established.

### Kernel source of the 16 bytes (`nk.exe`, image B)

- `0x01013008` = `CTL_CODE(FILE_DEVICE_HAL 0x101, function 0xC02, 0, 0)`.
- At `0x88009220` it is the code field of a 12-byte table record
  `{0x01013008, 1, 0x8804a568}`; neighbouring records have the same shape
  (codes `0x0101302c`, `0x01013034`, `0x01013038`…), the layout of a CE OAL
  IOCTL table.
  Image C holds the same code at `0x88009208`; `NaviSetCC.dll` (image A)
  also contains it.
- Handler `0x8804a568`: requires `inbuf != NULL` and `insize >= 16`, then
  calls `0x8804870c(inbuf, 16)`, which is
  a tail jump to `0x88040540` with `r4 = inbuf`, `r5 = 0x89e439b8 + (64 << 2)`
  and `r6 = 16`, i.e. a 16-byte copy from `0x89e439b8 + 0x100` (reading
  `0x88040540` as `memcpy` is from the register use, not from a name).

## Interpretation

- **VERIFIED (C-1950):** `SDHC.dll`'s code is uncompressed in B and C; the
  static path does not wait on M1.2. C-1884 is retracted on that point.
- **VERIFIED (C-1951):** IOCTL → flag map as in the table, identical in B
  and C.
- **VERIFIED (C-1952):** the wrappers pass the caller's buffer and
  `(u8)nInBufSize` unchanged; LeafSDTools passes 16 bytes (C-1945), so the
  card password is those 16 bytes.
- **VERIFIED (C-1953):** the driver builds the spec CMD42 frame; it accepts
  SET_PWD+LOCK (`5`) but no IOCTL uses it.
- **OBSERVED (C-1954):** at boot the driver takes 16 bytes from kernel IOCTL
  `0x01013008` and sends UNLOCK (`0x00`, len 16) with them, in one branch
  after a LOCK (`0x04`).
- **OBSERVED / HYPOTHESIS (C-1955):** the kernel handler copies 16 bytes from
  RAM `0x89e439b8 + 0x100`. That this RAM is the PROD block's shadow is a
  hypothesis: it fits LeafSDTools reading NAND block 5 + `0x100` (C-1945).
- **HYPOTHESIS (C-1956):** the 4 unit bytes are stored per unit (PROD
  `+0x100`), not derived at runtime from a serial or model code on this
  path. A card given the same 16 bytes with SET_PWD (LeafSDTools "SD LOCK")
  or SET_PWD+LOCK (the Pico `setlock`) is in the same state after power-up,
  so an independently locked card is feasible. Bench test: M6.9 / M6.5.
- **VERIFIED (C-1957):** LeafSDTools' "SD LOCK" (`0x80032014`) is SET_PWD
  only (the card locks at the next power-up); its "SD UNLOCK"
  (`0x80032020`) is CLR_PWD (the password is removed for good). The driver
  also exposes forced ERASE (`0x80032024`).
- **UNKNOWN:** the import behind slot `0x01f38050` (`KernelIoControl` is the
  natural candidate, M1.9); the meaning of the slot/state-byte branches.

## Positive controls

- The method finds known anchors: `0x039b7df4` is reached as vtable slot 108
  and is the function that loads the M2.8 `byFlag`/`byPasswordLen` string
  (C-792); B and C give the same five flags in the same slots.
- The five flags are exactly the five CMD42 values of the SD spec, one per
  IOCTL, in a monotonic IOCTL order: a wrong slot base would not produce
  that.

## Conclusion

Claims C-1950–C-1957 added; C-1884 marked as retracted on the compression
point; C-1948 (flags UNKNOWN) is resolved by C-1951. No password bytes are
committed: only offsets, VAs, IOCTL codes and flag values. No new tool:
the method uses `cerom.py`, `sh4xref.py` and binutils `objdump`.
