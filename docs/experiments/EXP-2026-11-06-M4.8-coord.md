## Question

Can the documented ZE0 coordinate formula be turned into one tested tool that
converts WGS84 lat/lon to and from the `BxxRyyR` cell, the global packed
`u16` pair and the tile-local `0..2047` coordinates, while keeping the two
longitude origins (52742 and 52736) separate? Which origin belongs to which
record family, what are the level/zoom semantics, and which parts can be
verified without the image?

## Hypothesis

The verified formulas are sufficient: `x = 32768 + lat*192`,
`y = origin + lon*128`; a cell is 8 x 8 grid units and exactly 1024 packed
units per axis. The only coherent 11-bit local mapping is
`local = 2 * (packed - tile_origin)`, giving 0..2047 strictly inside a cell
and 2048 on the far edge. `COORD001`/`POINT`/`ADDRE` use origin 52742;
`MAPAL001` stream keys use 52736. The 6-unit difference must never be mixed,
but it does not affect the cell or local coordinates.

## Method

1. Implement the two packed formulas plus the tile box from
   `tools/mesh_grid.py`'s verified rule, with the inverse used by
   `tools/imf_check.py` (B/R multiples of 8, half-open cell edges).
2. Implement tile-local coordinates from the cell's south-west packed corner:
   `local = scale * (packed - corner)`, `scale` 2 by default (0..2047) and
   1 as the documented alternative (0..1023).
3. Make the longitude origin an explicit `--origin` switch
   (`52742`/`coord` default, `52736`/`tile`), and print it in every result.
4. Expose `cell`, `xy`, `latlon`, `bbox`, `levels`, `--json` and
   `--selftest`; local inversion requires `--cell`.
5. Verify with synthetic round-trips and the fixtures already in the repo;
   do **not** claim a real-POI check without the image.

Commands:

```bash
python3 -m py_compile tools/coord.py
python3 tools/coord.py --selftest
python3 tools/coord.py cell 51.1 17.03
python3 tools/coord.py xy 43.7447916667 7.4296875 --cell B40R060R
python3 tools/coord.py xy 43.7447916667 7.4296875 --origin tile
```

## Interpretation

- **FACT:** the implemented formulas reproduce every documented cell box,
  `mesh_grid.py` over all 63 lattice cells, the `B28R070R` `0x2ac` sample and
  the five `imf_check.py` fixtures.
- **FACT:** integer packed `(x,y)` pairs and integer local pairs round-trip
  exactly at both origins; lat/lon → grid → lat/lon is within half a packed
  unit (1/384 deg lat, 1/256 deg lon, about 290 m each), and half that in
  local units at scale 2.
- **FACT:** `COORD001` region boxes, `POINT` ids and `ADDRE` ids use origin
  **52742** (default `--origin coord`); `MAPAL001` zlib stream keys use
  **52736** (`--origin tile`). The 6-unit difference is exactly
  `6/128 = 0.046875` deg of longitude and is unexplained (C-053).
- **FACT:** the local 0..2047 bound is reproduced as 2048 units per cell axis;
  2048 is the far edge and belongs to the next cell. `--local-scale 1` offers
  the packed-relative alternative (0..1023).
- **HYPOTHESIS:** the local scale factor is 2. It is the only simple mapping
  that explains why the firmware bound is 2047 rather than 1023, but no
  byte-level sample pins it yet. The 11-bit `ZCODE` leaf sub-positions
  (C-113) are consistent with a 2048-per-axis sub-grid, not proof of this
  particular factor.
- **HYPOTHESIS:** level 6 is the finest storage level. The six-level table is
  a runtime structure (`VTb … |L1..L6|`, C-865/C-866); levels 3–5 are coarse
  overviews in `LEV3456R.DAT` whose cell subdivision is UNKNOWN. No verified
  zoom-number ↔ level mapping exists, so the tool does not invent one.
- **UNKNOWN:** why the two origins differ by 6 units; the level 3–5 cell
  sizes; the relationship between the local 2048 grid and `ZCODE`
  `sub_x/sub_y`.
- **NOT CLAIMED:** that known POIs land within a few metres. That needs the
  image and is listed as the remaining step. A 4-byte `POINT` id alone has a
  packed resolution of about 600 m, so the real check must state whether it
  compares packed ids (quantisation-limited) or finer sub-position fields.

## Remaining step: the 10-POI real check

The task's "≥ 10 known POIs within a few metres" cannot be claimed from the
documented fixtures alone and was **not** attempted. It needs:

1. the EU 2011 image (SHA-256 above) or an extracted `root/` with
   `REFER001/POINT*.DAT.cmp` and `REFER001/COORD001.DAT.cmp`;
2. a POINT record decoder (the old `poipoint.py` is not in `tools/`; use
   `l2check.py` as the regression gate until it is added);
3. ten POIs identifiable in OSM, with their decoded A/B ids and cells;
4. an explicit tolerance statement: a 4-byte `POINT` id quantises to about
   600 m, so "within a few metres" is only meaningful if a finer field is
   found in the record or if the comparison is against that quantisation.

Until then, `tools/coord.py` is verified only against synthetic values and the
repo's published fixtures.
