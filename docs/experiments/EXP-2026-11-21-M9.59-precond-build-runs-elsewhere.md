# EXP-2026-11-21-M9.59: `l3_precond` classes a target against its own build, and knows targets that run outside `runner.py`

- **Status:** done
- **Date:** 2026-11-21
- **Sample:** `archive/head256.img` (EU2011 256 MiB head, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`) and
  `archive/us256.img` (US2011 256 MiB head, SHA-256
  `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`).
- **Tools:** `python3 3.15.0 / zlib 1.3.1.zlib-ng`; repo tools
  `tools/l3_precond.py` (edited), `tools/fetch_image.py` (read: the
  `PART_PINS` head owner), `tools/selftest.py`, `tools/gate.py`.
- **Claims:** C-6060–C-6069
- **Supersedes:** none
- **Superseded by:** none

## Question

Does `tools/l3_precond.py` name the true precondition class of a target whose VAs
belong to a build other than the head it was handed, and does it say what is true
about a `blocked` target whose `reason` names a real tool that runs it?

## Hypothesis

`l3_precond` should never class a build's VAs against another build's head, and a
`blocked` target that a real `tools/*_l3.py` runner executes is `RUNS-ELSEWHERE`,
not `BLOCKED` ("no entry"). Expected: (1) a `us2011` target handed the EU head is
refused or given its own US head, and its helper VAs class `CODE sec0`, not EU
`INIT`; (2) `tile_reader`/`mmain_reader` and the other `datask_l3.py` targets
report `RUNS-ELSEWHERE` with the tool name, while a target whose reason names no
existing tool stays `BLOCKED`.

**Falsifier:** a `us2011` target still prints a `sec1 … INIT` class from the EU
head, or a `blocked` target naming a real runner still prints `BLOCKED` with no
`runs_via`. Also falsified by a `blocked` target naming a *missing* tool printing
`RUNS-ELSEWHERE` (the negative must fail closed).

## Method

1. **Sample and hash.** The two 256 MiB firmware heads above; the SHA-256 of each
   is printed by `sha256sum`. The builds' pins are the same bytes from
   `tools/fetch_image.py` (one owner, no hand-typed hash in the tool).
2. **Commands.** Runnable as written, from the repo root:

   ```bash
   python3 tools/l3_precond.py --selftest
   python3 tools/l3_precond.py --target cmp_ind_reader_us2011 --image archive/head256.img
   python3 tools/l3_precond.py --target cmp_ind_reader_us2011 --image archive/head256.img --no-default-head
   python3 tools/l3_precond.py --target cmp_ind_reader_us2011 --image-us archive/us256.img
   python3 tools/l3_precond.py --target cmp_ind_reader --image archive/us256.img --no-default-head
   python3 tools/l3_precond.py --all-targets --image archive/head256.img --image-us archive/us256.img
   python3 tools/l3_precond.py --all-targets --image archive/head256.img --image-us archive/us256.img --json
   python3 tools/selftest.py --only l3_precond
   python3 tools/gate.py
   ```

3. **Controls.**
   - *Positive (gap 1):* the same `cmp_ind_reader_us2011`, given its own US head
     (`--image-us archive/us256.img`), classes helper VAs `0x00565d94`/`0x00565da4`
     as `CODE sec0` — the known-correct class (M9.33/C-3402).
   - *Positive (gap 2):* `tile_reader` (names `tools/datask_l3.py`) and
     `mmain_reader` (names `tools/mmain_l3.py`) get `RUNS-ELSEWHERE` with the
     specific tool.
   - *Negative (gap 1):* `--no-default-head` removes the on-disk fallback, so an EU
     target handed the US head is `mismatch` → `UNKNOWN`, never a guessed class.
   - *Negative (gap 2):* a synthetic `blocked` target naming
     `tools/no_such_runner_l3.py` (absent) stays `BLOCKED` with `runs_via=None`;
     covered by `--selftest`.
4. **Scope.** `l3_precond.py` only, no `targets.json` change. Both builds' 256 MiB
   heads (all three CE ROM segments are in the first 256 MiB). Not covered: ad-hoc
   `--va` (still build-A assumes `--image-start 0x200200`), and `l3check.py`
   corpus rows (they already pick the build's head through `BUILD_IMAGES`).
5. **Falsifier.** Stated in the Hypothesis; a `us2011` target printing an EU `INIT`
   class, or a runner-naming `blocked` target printing `BLOCKED`, refutes it.

## Interpretation

- **FACT:** A `us2011` target handed the EU head no longer classes its VAs against
  it. With the on-disk US head present it substitutes that head and reports
  `source: archive/us256.img` plus a reason naming the substitution; with
  `--no-default-head` it refuses (`mismatch` → `UNKNOWN`). The US helper VAs
  `0x00565d94`/`0x00565da4` now class `CODE sec0`, matching the M9.33 positive
  control (C-3402) instead of the EU `INIT`.
- **FACT:** The build's head SHA-256 comes from `tools/fetch_image.PART_PINS`
  (`build_head_sha("us2011") == PART_PINS[("US","256M")][1]`), one owner, not a
  hand-typed constant in `l3_precond.py`.
- **FACT:** Four `blocked` targets whose `reason` names an existing runner are
  `RUNS-ELSEWHERE` with that tool (`tile_reader`, `lev3456_reader`,
  `tile_section4_reader` → `tools/datask_l3.py`; `mmain_reader` →
  `tools/mmain_l3.py`). `hddinfo_compare` (runtime COM) and `mapcode_comparator`
  (retired BT_MGR code) name no existing runner and stay `BLOCKED`.
- **FACT:** The negative holds: a `blocked` reason naming an absent tool stays
  `BLOCKED` with `runs_via=None` (`--selftest`).
- **OBSERVED:** The report gained `build`, `image_pin` (`build`, `expected_sha256`,
  `actual_sha256`, `status`, `source`, `detail`) and `runs_via` in text and JSON;
  the old fields (`verdict`, `reasons`, `va_classifications`, …) are unchanged.
- **UNKNOWN:** Whether any external consumer keyed on exactly three verdict
  strings — none imports `l3_precond` (grep found no `import l3_precond`); the
  tool's own CLI is the only reader, so the Stop-condition fallback (keep `BLOCKED`
  + a `runs_via` field) was not needed.

## Conclusion

`tools/l3_precond.py` now classes a target only against a head whose SHA-256
equals that target's build pin (`tools/fetch_image.PART_PINS`), refusing (or, when
its own per-build head is on disk, substituting) a wrong-build head and naming the
fact; and it returns `RUNS-ELSEWHERE` with `runs_via` for a `blocked` target whose
reason names an existing `tools/*.py` runner, keeping `BLOCKED` when the named tool
is absent. The two M9.33 gaps (C-3401/C-3402) are closed on the real EU and US
heads; `targets.json` is unchanged. `docs/research/claims.md` gains C-6060–C-6069.
