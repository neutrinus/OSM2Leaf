## Question

With an EU 2011 card in a US 2011 unit, which `SPEECH/<ll>` folder does the firmware open, where does `<ll>` come from, what does the setup screen offer, and what happens when the folder is missing?

## Hypothesis

- **H1.** `<ll>` is the two-letter name produced by `Speech.exe` from the **unit's** `OBJ_Setting_readExpLanguage` value (the "exp language" setting), through the two `braf` switches located by M4.38 (C-3761). A US-English setting → `US`, Canadian French → `CF`. It is **not** read from a card file (`MMAIN001` `0x18c` list) and not from the area byte. Falsifier: a traced read of a card file or the area value that sets the `SPEECH/<ll>` name.
- **H2** (the task's falsifier). If the language list came from the card, an EU card would offer only European languages and nothing would be missing. Falsifier: the language name/dir table is in firmware (both 2011 builds), and the unit still asks for `US`/`CF` — dirs the EU card lacks.
- **H3.** When the folder is missing the GID/TTS/VR open fails and the debug strings `GuideData is not load` / `Guide data read Interrupt` are the error path; the exact audible result (silence vs fallback) is a runtime property that static analysis may not settle — marked `UNKNOWN` if so.

## Interpretation

- **FACT (C-8460, C-8461):** `<ll>` comes from the unit's `OBJ_Setting_readExpLanguage` value, converted by two `braf` switches in `Speech.exe` (EU2011 fn `0x000a6dfc` / `0x000a62f0`, `braf 0x000a6e36` / `0x000a6386`; US2011 `braf 0x000a7776` / `0x000a6cc6`). `Navi.exe`'s `sdl_com_hdl_get_lang` (EU `0x003c0228`, US `0x003ef04c`) calls the same import. Verified by `sh4xref --calls` and `lang_code_table.py firmware` in both builds. No card file or area byte enters this path — H1 holds, H2's "list from card" is refuted: the 10 dir names are in the firmware.
- **FACT (C-8462):** the full path `\SystemSD\SPEECH\%@\GID\S%@00000.GID` is a UTF-16 literal at `Speech.exe` VA `0x0001d0e0` in both builds. The path-building function (EU `0x0007237c`, US `0x00072ca8`) stores it into the request at `+112` and calls the `exp→speech_v` helper, storing the result at `+104`. The loader fn (EU `0x00098b0c`, US `0x0009944c`) does the file open; this answers the "locate the code that builds the path" scope item with a function name and VA.
- **FACT (C-8463):** the value 3004 (American English) maps to dir `US`, 3005 (Canadian French) to `CF` in **both** 2011 builds; the 10-name table at `VA 0x00032354` reads `CF US JP SP PT DU IT GE FR BE`. A US unit set to US English therefore asks for `SPEECH/US`; Canadian French asks for `SPEECH/CF`.
- **FACT (C-8464):** the EU 2011 card has only `BE DU FR GE IT PT SP`; `US` and `CF` are absent (tool `card`). Therefore, with a US-English or Canadian-French setting, the folder the firmware requests is not on the EU card. **Copying `SPEECH/US` (and/or `SPEECH/CF`) onto the EU card is needed for voice guidance unless the user selects one of the seven European languages the card carries.** Switching to a European language is the card-free alternative.
- **FACT (C-8466):** the setup/language list lives in firmware, not on the card. The EU2011 `Speech.exe` table names all 10 dirs including `US`/`CF`; Navi.exe's debug/help text only distinguishes `AE`, `CF` and `Other language` modes. There is no area check in the cited path, so a US unit running the EU card's applications would offer the EU build's languages — including US English and Canadian French — rather than a card-restricted European-only list. The precise user-facing setup-screen rows are `OBSERVED` from strings only; a full UI enumeration needs an L4 run (out of scope here).
- **OBSERVED (C-8465):** the GID-open failure branch in the path/loader functions emits `[F-IFC-GID] Guide Data Set Error` / `Get Error` and `GuideData is not load` / `Guide data read Interrupt`. This is the debug-side error path when the requested folder is missing.
- **UNKNOWN (C-8467):** whether the audible result of a missing folder is silence, a fallback to another language, or an error tone. Static analysis shows the failed open takes the debug-error branch, but the audio-output decision is made at runtime; no L3/L4/hardware run was done. Marked UNKNOWN, not silently upgraded to a claim.
- **OBSERVED (C-8468):** no runtime acceptance — rule 13 unchanged. The finding is a static code/data fact about which folder is requested, not an L4/L5 confirmation.

## Conclusion

Done-when is met: the EXP names the Speech.exe functions (`0x000a6dfc` / `0x000a62f0` EU2011, `0x00072ca8` loader path US2011), the path literal (`0x0001d0e0`) and the language-code source (`OBJDLL!OBJ_Setting_readExpLanguage` → two `braf` switches, anchored by `lang_code_table.py firmware` in both builds), and answers the practical question: a US unit set to US English asks for `SPEECH/US`, which the EU card does not have, so copying `SPEECH/US` onto the EU card (or selecting a European language) is needed for voice guidance. The list comes from firmware, not the card, so the task's falsifier does not hold. Changes: this EXP, a research page, claim rows C-8460–C-8469, and the own TODO line. Still open: runtime fallback behaviour (C-8467) and a full L4 setup-screen enumeration. No new tool was needed; no vendor bytes committed.
