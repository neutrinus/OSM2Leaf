## Observations

### Card layout (from the ledger, EU 2011, 8,057,257,984 B)

| Card offset | Size | Content | Kind | Source |
| --- | --- | --- | --- | --- |
| `0x0` | 512 B | DOS MBR, one FAT32 partition entry; `CLARION ID` record at `0x200` | metadata | `sd-card-layout.md`, C-003 |
| `0x00200000` | 24.4 MB (+copy at `0x02000000`) | CE ROM **A**: 149 modules, `Navi.exe` and the app DLLs (VA `0x8cae1000`) | **code** | C-060, C-160, EXP-36 |
| `0x03e00000` | 7.2 MB (+copy at `0x04800000`) | CE ROM **B**: `nk.exe`, `coredll.dll`, drivers, updaters (`PRGUpdate.exe`, `MapUpdate.exe`) | **code** (kernel) | EXP-36, C-707 |
| `0x05200000` | 6.7 MB | CE ROM **C**: kernel + `TestMode.exe` | **code** (kernel, test mode) | EXP-36, C-708 |
| `0x06400400` (LBA 204802) | 7.55 GB | FAT32 `QSD-309-101` (`\SystemSD`): `MAPAL001`, `REFER001/002`, `RDSTM001`, `MMAIN001.DAT`, `DRSTR001.DAT`, `CMP.LST`, `SPEECH`, `TMC`, `VER_INFO`, `BICON001`, `OPNG` | **map data** | `sd-card-layout.md` |
| `0x1C8400400` | ~27 MB used of 402 MB tail | TFAT16 volume (`DONT_DEL*`), rest `0xff` | system data (skin/overlay, HYPOTHESIS) | C-069, C-124, C-166 |

No bootloader is on the card (C-535): the on-board IPL loads a kernel image to
phys `0x08000000` and A to `0x0cae1000`.

### LeafSDTools (QY7XXX = our SH-4 unit)

1. **Update-mode programs run from the card.** The SH-4 card image is built by
   replacing `PRGUpdate.exe` inside the two CE ROM banks at card offsets
   `0x03E00000` and `0x04800000` (bank size `0xA00000`) and recomputing the
   SUM4 word sum (same algorithm as C-160). Those are exactly the build **B**
   offsets of our image. The README procedure: start *Software Update* from the
   service menu, the unit reboots, swap the card, cycle ignition — the unit then
   runs B (with the tool in place of `PRGUpdate.exe`) from the swapped card.
2. **The unit's own flash is small.** `FMD1:` read with IOCTL `0x80112000`;
   on QY7XXX blocks `0..0x86`, blocks 0–7 are 8 KiB, the rest 64 KiB:
   8×8 KiB + 127×64 KiB = **8,192 KiB = 8 MiB**. That matches the 64 Mbit NOR
   named by the external lead C-2004 (SST 38VF6401). Block `n ≥ 8` starts at
   `(n−7)×0x10000`.
3. **"SRAM" dump = flash blocks, not RAM.** "DUMP TO SD" writes
   `\SystemSD\sram_<prodId>_<serial>.bin` = `FMD1:` blocks `0x47..0x56`
   (16 × 64 KiB = **1 MiB**, flash `0x400000–0x4FFFFF`), then
   `\SystemSD\vflash_<prodId>_<serial>.bin` = blocks `0x57..0x84`
   (46 × 64 KiB = **2.875 MiB**, `0x500000–0x7DFFFF`). The menu calls this
   "User Data" (README: "Read&Write SRAM and VFlash (User Data)"). `\SystemSD`
   here is the card in the map slot, i.e. the LeafSDTools card, not the map card.
4. README: on QY7XXX "Head Unit won't boot back if SD is unlocked" — the stock
   card must be locked before leaving update mode.

## Interpretation

- **VERIFIED (C-5190):** the card is not data-only. ~38 MB of the first 100 MB
  are three complete Windows CE ROM images (apps A, kernels B/C); the maps are
  in the FAT32 partition after them.
- **VERIFIED, third-party source (C-5191):** in update mode the unit executes
  CE ROM B from the card (LeafSDTools works only because of that).
- **HYPOTHESIS, strong (C-5192):** in normal mode the unit also runs A (Navi.exe)
  and a kernel from the card. Size argument: A is 24.4 MB, B 7.2 MB, the whole
  unit flash is 8 MiB, of which ≥ 3.9 MiB are user data (SRAM/VFlash) and
  64 KiB the PROD/boot blocks. Neither A nor B fits; at most a ~3.9 MiB region
  (blocks `0x08..0x46`) is left for the IPL and anything else. Supporting:
  C-080 (US unit drew EU streets from an EU card), H51 (US and EU cards carry
  different `Navi.exe` builds), README point 4. This contradicts the
  `us-eu-region.md` row "card build not executed; NB04 in NAND", which came
  from an external lead and is still HYPOTHESIS.
- **OBSERVED (C-5193):** the LeafSDTools "SRAM" file is a 1 MiB flash region of
  user data (and VFlash 2.875 MiB). It is not a RAM snapshot and contains no
  OS or map code. What it holds byte by byte (settings, history, address book,
  the VSRAM complete flag C-778?) is UNKNOWN.
- **Consequence (C-5194):** "a card with maps" really means "a card with the
  OS + maps". Our generated card keeps the first 100 MB byte-identical to the
  factory card (what M5.13 `imgpatch` does), so we never write our own code.
- The dump is useful as a **backup** before card tests: C-1128 says unit-side
  state has no backup. A full `Read NAND` (8 MiB) settles C-5192 directly.

## Conclusion

The map card = MBR + three CE ROMs (OS and apps) + FAT32 maps + a TFAT16
volume. Code runs from the card in update mode (verified) and almost certainly
in normal mode too (size argument; to be confirmed by M6.17 on a flash dump).
The "SRAM" dump is user data from the unit's flash, worth taking as a backup.
