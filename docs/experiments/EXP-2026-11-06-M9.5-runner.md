# EXP-2026-11-06-M9.5: Runner `run FUNC` end to end on a synthetic target

- **Status:** done (tool); one synthetic target runs end to end. Ghidra and QEMU
  are absent here and reported as SKIP, never as a pass. No firmware reader is
  located, so every real-reader target reports BLOCKED.
- **Date:** 2026-11-06
- **Sample:** no vendor data, no firmware image, no Ghidra, no QEMU. Inputs are
  the synthetic corpus built by `tools/l3_harness/corpus.py`; the one file used
  for the end-to-end run is `cmp/factory/ADDRE001.DAT.cmp`, size 1169,
  SHA-256 `aabee610a7db6649a618234e5bc8c6f4565bf33c876a4912900453868426f76b`.
  Tool files: `runner.py` SHA-256
  `38ba315cbe5dd2ccabc49cf30a81748f4ae152cbee47fbab00c9246b4f59bbc4`,
  `targets.json` SHA-256
  `63003ae1471098149e3a43f7cc45b937fc84259d9ca3adaef133ff93cc2e2a6a`.
- **Claims:** C-1670 (text below; register in `docs/research/claims.md`)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can `runner.py run FUNC --input FILE [--engine pysh4|ghidra|qemu] --json`
execute **one named target** end to end — load the input through the virtual
file system, install the stub dispatcher with `on_exec`, run on an engine and
print `accepted`, the return value, the stub call log, the instruction/step
count and the back end — while an unlocated reader reports `BLOCKED` and an
absent back end reports `SKIP` (exit `3`) instead of a pass?

## Hypothesis

Yes, with three separate pieces already on `main`: the engine contract (M9.4,
C-1660–C-1669), the stub dispatcher with its virtual FS (M9.3, C-1650–C-1659)
and the corpus (M9.7, C-1690–C-1699). The missing part is only the wiring: a
target table, a small SH-4 program that really calls `sprintf`,
`CreateFileW` and `ReadFile`, guest memory that the stubs and the engine share,
and a verdict comparison that fails loudly. The honest claim stays narrow: a
synthetic PASS proves the pipeline, not that the firmware reader accepts a
card.

| Code / stack / data / heap | `0x8c100000` / `0x8c1ff000..0x8c200000` / `0x8c200000` / `0x8c202000` |
| Stub thunks | `0x8c100200` sprintf(path), `0x8c100210` CreateFileW, `0x8c100220` ReadFile, `0x8c100230` CloseHandle, `0x8c100240` sprintf(log) |
| Arguments | `r4` pathbuf, `r5` logbuf, `r6` readbuf, `r12` ANSI path, `r13` UTF-16LE path, `gbr` data base, `r15` stack top |
| Return sentinel | `RETURN_VA = 0x8c0fff00` (`pr`, as in M9.4) |
| Corpus | `python3 tools/l3_harness/corpus.py build /tmp/opencode/l3-corpus` -> 108 entries |
| Vendor data / Ghidra / QEMU | none / not installed / not installed |

The probe is **not** a firmware reader. It is the smallest program that
exercises the whole path:

```text
sts.l pr,@-r15 ; add #-32,r15            save pr and a 32-byte frame
sprintf(pathbuf, "%s", ansi_path)        -> dispatcher coredll!sprintf
CreateFileW(wide_path, 0x80000000, 0, 0,
            OPEN_EXISTING, 0, 0)         -> dispatcher coredll!CreateFileW
ReadFile(handle, readbuf, 1, &count, 0)  -> dispatcher coredll!ReadFile
CloseHandle(handle)                      -> dispatcher coredll!CloseHandle
sprintf(logbuf, "%s|%d", pathbuf,
        verdict)                         -> dispatcher coredll!#719
r0 = 1 iff count == 1 and readbuf[0] == 0x78, else 0
```

`0x78` is the zlib CMF byte every `.cmp` stream starts with; the probe's gate
is a real property of the container, not a constant the runner compares
against. The three stack arguments of `CreateFileW` are at `0(r15)`, `4(r15)`,
`8(r15)`; `ReadFile`'s fifth argument sits at `0(r15)`; `&count` is `r15+12`,
i.e. guest `0x8c1fffe8` (`COUNT_VA`).

Guest memory is shared, not copied: `runner._EngineMemory` subclasses
`dispatch.FlatMemory` and forwards `read`/`write` to the engine, so the bytes
`sprintf` writes are the bytes `CreateFileW` sees and the bytes read back after
the call. Each `on_exec` hook has a declared arity, resolves its target through
`StubDispatcher.resolve` (name or ordinal) and returns `StubReturn(r0)`.

`targets.json` has one runnable entry and five **blocked** entries:

| Target | Reader | Entry | Expectation |
| --- | --- | --- | --- |
| `probe-zlib-cmf` | synthetic | program `probe_zlib_cmf_v1` at `0x8c100000` | ACCEPT on the factory `.cmp` |
| `hddinfo_compare` | `hdd_info` | blocked: runtime COM object, no VA (C-521) | ACCEPT |
| `cmp_ind_reader` | `cmp_ind` | blocked: no entry point (M3) | ACCEPT |
| `tile_reader` | `tile` | blocked: no entry point (M3) | ACCEPT |
| `drstr_parser` | `drstr` | blocked: no entry point (M3) | ACCEPT |
| `mapcode_comparator` | `hdd_info` | blocked: retired `BT_MGR.dll` chain (C-520, C-528) | REJECT |

Validation refuses a target whose `corpus.case` disagrees with its
`expect.verdict`, an unknown stub name, a `planned` stub, an unknown ordinal, a
program that does not declare the stub ids it needs, and a corpus path that
escapes the root.

## Interpretation

- **FACT:** `runner.py run probe-zlib-cmf --corpus <built corpus> --json`
  executes the probe on `PySh4`, returns `r0 = 1`, reports the resolved stub
  calls (`sprintf` twice, `CreateFileW`, `ReadFile`, `CloseHandle`), 68
  instruction/stub steps, and `status = PASS` with `accepted = true`; exit 0.
- **FACT:** the same command with `--engine ghidra` or `--engine qemu` is
  `SKIP` with `MISSING_GHIDRA`/`MISSING_QEMU`, exit 3, `accepted = null`; the
  self-test marks the back end as skipped, never passed.
- **FACT:** an unlocated reader (`hddinfo_compare`, `cmp_ind_reader`,
  `tile_reader`, `drstr_parser`, `mapcode_comparator`) and an unknown target
  name both report `BLOCKED`, exit 4, `accepted = null`.
- **FACT:** a non-zlib input against the ACCEPT-expecting probe is
  `MISMATCH`, exit 5; an unmodelled export stops with `missing stub:
  OpenEventW`; a `.ind`-declared corpus file whose SHA-256 changed is
  `INVALID`, exit 1.
- **FACT:** two runs on the same input produce the identical payload.
- **OBSERVED:** the corpus manifest verdict for the same file is `ACCEPT`
  (`cmp_ind`), so the probe agrees with the Python reader on the positive
  control. The probe is not that reader and `l3_claim` stays `false`.
- **HYPOTHESIS:** the same wiring will run a real reader unchanged once M2/M3
  supply an entry VA; the only target-side change should be an
  `entry.kind = "module"` block plus its argument setup.
- **UNKNOWN:** whether Ghidra's synthetic-program path and QEMU's gdbstub
  path execute this probe identically; that is exactly what the SKIP defers.

## Conclusion

The L3 runner now has a working target mode: `targets.json` + a shared-memory
dispatcher bridge + a hand-assembled SH-4 probe that really calls the stubbed
WinCE file API. The result is a PASS on a synthetic corpus file, BLOCKED for
every unlocated reader, SKIP for the two absent back ends, and MISMATCH/INVALID
where the expectation or input is wrong. No firmware reader verdict is claimed
and `docs/format/`, `docs/research/claims.md` and the TODO board were not
changed by this EXP.

Claim text (C-1670):

> `tools/l3_harness/runner.py run FUNC --input FILE [--engine
> pysh4|ghidra|qemu] --json` runs one named target end to end on the synthetic
> corpus: it loads the input into the dispatcher's virtual FS, installs
> `module!export`/ordinal stubs as `on_exec` hooks over memory shared with the
> engine, executes `probe_zlib_cmf_v1` on `PySh4` and reports `accepted`,
> `r0`, the resolved stub call log, instruction/stub steps and the back end.
> The probe calls `sprintf` (by name and by ordinal 719), `CreateFileW` (3
> stack args), `ReadFile` (1 stack arg) and `CloseHandle`, returns ACCEPT iff
> the served first byte is the zlib CMF `0x78`, and the same run is reported
> as MISMATCH (exit 5) when the target's expectation differs. Every reader
> without a located entry point is `BLOCKED` (exit 4), an absent Ghidra/QEMU
> is `SKIP` (exit 3, `accepted = null`), and this is a pipeline result, not a
> firmware reader verdict (`l3_claim = false`).
