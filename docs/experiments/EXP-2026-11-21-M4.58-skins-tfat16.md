## Question

Where does the ZE0 unit keep skin data, what decides which skin is drawn, and
what is the `.skn` container layout (every byte range known or unknown)?

## Hypothesis

The task block expected three places: ROM A `ReleaseMain.skn` (8,224 B, the only
`FILESentry`), a TFAT16 volume at `0x1C8400400` whose contents were never
listed, and PNGs in ROM A/`OPNG/`. Expectation: `.skn` is a small
index/manifest, the TFAT16 volume holds the big pixel pool, and a skin id
selects between named variants.

**Falsifier:** if the TFAT16 volume holds no skin files, there is no skin
selection to describe (block Stop condition); if `.skn` assets do not frame as
`[u32 len][bytes]` with decodable payloads, the "pixel pool lives in the `.skn`"
model is wrong; if the per-card part number/trailer does not vary with the card,
the "selection by variant" model is wrong.

## Method

1. **Sample and hash.** The four full images and their heads, SHA-256 above;
   the extracted `substance.skn`/`ReleaseMain.skn`/`UpdateNK.skn` hashes are the
   bytes the tools read. Extraction is by cluster chain (TFAT) or
   `FILESentry` (`cerom.py extract-file`), never by a guessed offset.
2. **Commands.** Runnable as written, in one block:

   ```bash
   # TFAT16 volume listing on every card (count, placeholders, real bytes)
   for img in archive/sd-images/*.img; do
     python3 tools/skn_info.py tfat "$img"
   done

   # extract the one .skn from the TFAT volume (EU2011 shown) and parse it
   python3 - <<'PY'
   import sys, hashlib
   sys.path.insert(0, "tools")
   import skn_info
   fat = skn_info.Fat16("archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img", 0x1c8400400)
   e = [x for x in skn_info.tfat_walk(fat) if x["path"].lower().endswith("substance.skn")][0]
   data = fat.read(e["clus"])[: e["size"]]
   fat.close()
   print(len(data), hashlib.sha256(data).hexdigest())
   open("eu2011.skn", "wb").write(data)
   PY
   python3 tools/skn_info.py skn eu2011.skn

   # the three ROM skins (build A ReleaseMain, build B UpdateNK)
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img extract-file ReleaseMain.skn -o rm
   python3 tools/nk_decomp.py files --image-start 0x3e00200 --name UpdateNK.skn archive/head256.img

   # reader strings and exports (commondll is build B, not build A)
   python3 tools/ce_strfind.py --image-start 0x3e00200 --encoding utf-16le \
     --control HDD_INFO.TXT archive/head256.img 'ReleaseMain.skn' 'SkinChange\001\Substance.skn'
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img exports commondll.dll
   python3 tools/ce_strfind.py --image-start 0x200200 --encoding utf-16le \
     archive/head256.img 'Only SKN file format is supported in this version.'
   python3 tools/ce_strfind.py --image-start 0x200200 --encoding ascii \
     archive/head256.img 'PNG file corrupted by ASCII conversion' 'MULTISKINLib'
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img imports multiskin.dll
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img imports auirtdll.dll
   ```

3. **Controls.** *Positive:* the TFAT walk lists the `.skn` on all four cards
   (a file the walker must find); `ce_strfind --control HDD_INFO.TXT` returns 4
   hits in build B, so the string search works; all 3,004 (EU2011) section-3
   PNGs end in `IEND\xaeB`\x82`; the 109 zlib assets decompress. *Negative:*
   (a) `ce_strfind --image-start 0x200200` for `SkinChange` returns 0 hits while
   the same needle returns 11 in build B — the build-B-only `commondll` is not
   silently matched across builds; (`/windows/ReleaseMain.skn` is the reverse
   case: 1 hit in build B, and it is a build-A file, so the build-B copy of the
   literal is the reader's, not the file's); (b) corrupting the first PNG's magic byte
   lowers `png` 3004→3003, corrupting one `IEND` lowers `png_complete`
   3004→3003 while `png` stays 3004 (the completeness check is not a constant);
   (c) `skn_parse` on a 2-byte buffer returns no crash and no summary; (d) in the
   self-test, an odd-offset copy of the section-3 tag inside the asset area must
   not be taken as a section marker (aligned-tag search, 22 self-tests).
4. **Scope.** Offline, EU2011 first then US2011/EU2014/EU2016. Four full images
   (all 7.4–8.1 GB), four heads (256 MiB). Read: the one TFAT16 volume per card
   (3,070 entries), five `.skn` files fully (four `substance`, one
   `ReleaseMain`), build B `UpdateNK.skn` by decompressing its `FILESentry` (the
   EU2014/EU2016 decompressor run FAILs in `nk_decomp`, EU2011/US2011 OK).
   Excluded: no card was built, nothing ran on a unit (no L3/L4/L5).
5. **Falsifier.** As in Hypothesis, stated before the observations below.

## Interpretation

- **FACT:** the TFAT16 tail volume holds exactly one real payload, the
  `substance.skn` of skin slot `001`; `002`–`004` directories are absent on all
  four cards (C-6500, C-6501).
- **FACT:** `.skn` is a little-endian AUITK container with 4-aligned
  `0x0402000N` section tags; section 3 frames decodable assets as
  `[u32 len][bytes]`; the header carries a declared object count that the flat
  record walk reaches minus 56 for the player skins (C-6504, C-6508).
- **FACT:** `commondll.dll` (build B) holds the slot path literals and the
  three `CApi_*SkinID` exports; `multiskin.dll` is only the COM loader;
  `auirtdll.dll` is the AUITK/libpng runtime (C-6502, C-6503, C-6505, C-6506,
  C-6507).
- **OBSERVED:** the 56 objects that the flat walk does not see have payloads
  that do not parse as nested record chains — they are embedded objects counted
  without a header (hypothesis). The section-2 `u16` table's meaning and the
  header `0x0c` word are open.
- **HYPOTHESIS:** the built-in ROM PNGs (1,234 signatures in ROM A) are what
  the object image ids point to; the correlation is shown, the id→file mapping
  is not decoded.
- **UNKNOWN:** runtime acceptance of a rebuilt `.skn` (L3/L4); whether a
  trailer part number must match the card.

## Conclusion

`docs/format/skins.md` now lists the TFAT16 volume (3,070 entries, 3,066
`DONT_DEL` placeholders, 4 real, one 8.7/7.2/13.0/13.0 MB `.skn`), gives a
`.skn` field table with every byte range marked known/OBSERVED/unknown, and
answers the block's question: a skin is selected by skin id 1..4
(path `\SystemSD2\SkinChange\001..004\Substance.skn`, via
`CApi_GetSkinID`/`CApi_SetSkinID`/`CApi_IsAvailableSpecifiedSkin`) plus the ROM
startup layout `\windows\ReleaseMain.skn`, and its images come from section 3
of the selected `.skn` (PNGs + a shared zlib blob set) and from ROM A's built-in
PNGs (decoded by `auirtdll`'s bundled libpng). Claim rows C-6500–C-6509 back
each sentence; nothing was run on a unit.
