## Question

Does `tools/l3_harness/runner.py run` return a firmware verdict from
`AppLaunch.dll` `fn 0x03bd2ad8` (EU2011 build B, M2.5/M2.15) for the factory
`HDD_INFO.TXT` (expected accept) and for one edited line-1 variant (expected
reject)?

## Hypothesis

`fn 0x03bd2ad8` returns `1` when the 11-byte unit record (`KernelIoControl
(0x0101302C)` output `+0x60`) equals `HDD_INFO.TXT` line-1 bytes 0..10, and
`0` otherwise (M2.15, read statically). Run in PySh4 with only its imports
stubbed, it should return `1` on the factory file and `0` on a line-1 edit.

**Falsifier:** the factory file returns `0`, or the line-1 edit returns `1`,
or a line-2 edit returns `0` (the function would then read more than line 1),
or the run stops on an unmapped access or an unmodelled call (BLOCKED, with a
PC). Any of these and M9.6 stays `blocked`.

## Method

### 1. Sample and hash

`sha256sum archive/head256.img` → `92aa525d…a007f9`. The factory file is
extracted from the card's FAT (step 2) and hashed by the extractor.

How the run works (`tools/mapcode_l3.py run_compare`): `AppLaunch.dll` sec0
is mapped from the image at its `realaddr`; the two compressed sections
(sec1 `0x01f73000`, sec2 `0x03bd8000`) are mapped as zeros and every access
is logged. The eight import thunks the function calls are replaced by host
stubs. They are not hard-coded: `resolve_thunks` scans sec0 for the 4-insn
thunk shape (`d001 6002 402b 0009`), maps each literal slot (sec1 `realaddr`
based) to the rva-based import slot, and names it by ordinal from
`cerom.imports` and build B's `coredll.dll` export table. The run is BLOCKED
if any of the 8 is missing. Derived table (it matches `cerom.py thunks` +
`imports` + `exports coredll.dll`):

| thunk (B) | IAT slot | COREDLL | stub |
| --- | --- | --- | --- |
| `0x03bca3e8` | `0x01f73024` | #557 `KernelIoControl` | writes `*out = &record`, record `+0x60` = declared unit code; returns 1 |
| `0x03bca40c` | `0x01f73030` | #630 `SetKMode` | returns 0 |
| `0x03bca9b4` | `0x01f73048` | #168 `CreateFileW` | returns a handle only for `\SystemSD\VER_INFO\HDD_INFO.TXT` when a file is served, else `-1` |
| `0x03bd3ad4` | `0x01f7311c` | #170 `ReadFile` | copies from the served file; an unknown handle stops the run (BLOCKED) |
| `0x03bca9a8` | `0x01f73044` | #553 `CloseHandle` | returns 1 |
| `0x03bca99c` | `0x01f73040` | #1047 `memset` | fills |
| `0x03bcb7b4` | `0x01f73058` | #56 `wsprintfW` | `%c` only; any other format stops the run |
| `0x03bca3a0` | `0x01f7300c` | #545 `NKDbgPrintfW` | `%s` only, text logged |

### 3. Controls

- **Positive:** the factory file with the factory unit code must return
  ACCEPT. A line-2 edit (`line2_digits_4_002`, line 2 `QSD-309-101` →
  `QSD-002-101`) must also return ACCEPT: M2.15 says only line 1 bytes 0..10
  are compared.
- **Negative:** line-1 edits (`line1_digits_4_002`, and `line1_lastchar`,
  which changes byte 10, the last compared byte) must return REJECT; the
  factory file against a different unit code (`QSD-302-101`) must return
  REJECT; no served file (`CreateFileW` fails) must return REJECT.
- **Harness can fail:** the factory run with `--expect REJECT` must be
  `MISMATCH`, exit 5. Runner self-tests: missing inputs are `INVALID`; a
  non-zero declared parse cache is `BLOCKED` (only the first-call zero is
  modelled).

### 4. Scope

One function (`fn 0x03bd2ad8`, `0x20c` bytes) in one module of one build
(EU2011 build B). Six runs on the real image: 4 card files (factory, 2 line-1
edits, 1 line-2 edit) + 1 unit-code mismatch + 1 no-file. Not covered: the
router `fn 0x03bd2ecc`, the MapDBVer range check `fn 0x03bd2ce4` (`0x51`,
needs the unknown unit bounds `+112/+114`), the cached path (`*0x01f74b30 !=
0`, second call), build C (`0x03bb2858`), the US card, and the other 85
variants (that is M2.4).

### 5. Falsifier

Stated above, before the results: factory REJECT, line-1 edit ACCEPT, line-2
edit REJECT, or BLOCKED.

## Interpretation

- **FACT (C-5140, C-5141):** under the declared unit record, the firmware's own
  `fn 0x03bd2ad8` (EU2011 build B) returns ACCEPT (`r0=1`) for the factory
  `HDD_INFO.TXT` and REJECT (`r0=0`) for a line-1 edit. This is the M9.6
  done-when: a firmware verdict from `runner.py run`, with the stub log
  above.
- **FACT (C-5142):** the run confirms the static M2.15 reading: only line-1
  bytes 0..10 decide the result. A line-2 edit passes, an edit of byte 10
  fails, and the unit side is the IOCTL `+0x60` record (changing only that
  record flips the verdict).
- **OBSERVED (C-5143):** when the file is missing and the cache is empty, the
  function compares against zeros and returns 0. A card without
  `HDD_INFO.TXT` would therefore get `DIFFERENT MAP CODE` on this path, not a
  separate error.
- **HYPOTHESIS (stated in every result):** a real EU 2011 unit returns
  `QSD-302-100` at `+0x60` for this card. It is not measured. For a real unit
  the verdict is only as good as that assumption. The rule (equality of 11
  bytes) does not depend on it.
- **UNKNOWN:** the MapDBVer range check (`0x51`) and its unit bounds; the
  cached second-call path; build C.

## Conclusion

M9.6's done-when passes: `runner.py run applaunch_mapcode_compare` returns
the firmware verdict ACCEPT for the factory file and REJECT for
`line1_digits_4_002`, with the stub log recorded. The target is registered
in `targets.json` as `firmware_call` / `mapcode_compare_v1`, with the parse
cache declared as a BSS zero. The retired `mapcode_comparator` (BT_MGR)
and the stale `hddinfo_compare` entries stay `blocked` and are unchanged.
This unblocks M2.4, which can now run all 89 variants through the target.
Row 23 of `reader-coverage.md` now names the running target.
