## Question

What is in the part of a decoded POINT `.DAT` that r2 left undecoded (the
index pages, the `w0=2` pages and the 72 % that is not a zlib page), and does
any of it carry a POI position that the name pages do not?

## Hypothesis

The file is addressed from its 0x800 directory (M4.47), so every region
should be reachable from a descriptor record and have a grammar. If one of
those structures is a spatial index, its leaves say what the format treats
as the position of a POI.

**Falsifier:** a non-fill byte that no walked structure owns; a walk that
does not tile its region; a spatial leaf that does not equal fields of the
name record it points to; a position formula that is not closer to the
reference coordinates than the 1-unit reading, or that is as good with the
two fine fields exchanged.

## Method

1. **Sample and hash.** As above.
2. **Commands.**

   ```sh
   EU=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   US=archive/sd-images/LEAF_2011-2012_US.img
   W=/tmp/pt; mkdir -p $W
   python3 tools/point_census.py --selftest
   python3 tools/point_census.py extract --card-image $EU $W/eu
   python3 tools/point_census.py extract --card-image $US $W/us
   cat $W/eu/* | sha256sum
   cat $W/us/* | sha256sum
   python3 tools/point_census.py census $W/eu --json $W/census_eu.json
   python3 tools/point_census.py census $W/us --json $W/census_us.json
   python3 tools/point_census.py joins $W/eu
   python3 tools/point_census.py joins $W/us
   python3 tools/point_census.py refs --us $W/us --eu $W/eu --refs docs/experiments/EXP-2026-11-08-M4.8b-poi-refs.tsv
   ```

   `census` starts at the directory, reads the descriptor records and walks
   each structure they name: 12-byte trie entries from the root (a child must
   lie inside the trie, the nodes must tile it, a leaf offset must fall on a
   record of the index chain, a node's last entry must point back at its
   parent), the index chain (`4e20 0000`, length table, zlib streams that
   inflate to the length the descriptor gives), 16-byte spatial entries from
   the root (keys with the low 7 / 4 / 0 bits clear at levels 0 / 1 / 2, only
   zeros between nodes), the phone B-tree (0x1000-byte nodes, BCD keys,
   unused nodes blank), and the three page chains through the M4.47 locator.
   Bytes that no structure claimed are counted as fill when they are `00` or
   `ff` and as unaccounted otherwise. `joins` compares, for every spatial
   leaf, the cell key above it and its fine word with bytes 2–9 of the name
   record whose ordinal the leaf carries; for every 12-word index record of
   the cell-`0x824` chain, its key words with the bytes of the name record
   whose ordinal it carries; for every phone key, its digits with the ASCII
   number in the `INFORMATION` record of its POI. `refs` computes the
   distance from each reference coordinate to the fine position, to the
   1-unit reading and to the fine position with the two fields exchanged.
3. **Controls.** *Positive*: the synthetic file of `--selftest` (every class,
   all joins hold). *Negative (must fail)*: in the selftest, 8 stray bytes,
   a trie leaf off the record grid, a spatial child outside its tree, one
   changed fine bit in a leaf, a non-BCD phone key, a wrong chain magic. On
   the cards: each join repeated with the ordinal moved by 7,919 (must drop
   to noise); the reference check with the 1-unit reading and with the fine
   fields exchanged.
4. **Scope.** All 44 POINT files of both cards, 3,545,547,776 decoded bytes:
   5,829 name tries with 84,067,271 entries, 8,285 index-chain streams,
   2,735 spatial trees with 10,718,316 leaves, 11 phone B-trees with
   7,050,902 keys, 132 page chains. 16 reference POIs. Not covered: the
   meaning of the bit fields after byte 10 of a name record, the second id
   copy (bytes 12–15), the flag bits above the fine fields in a leaf,
   `REFER002`, and the firmware code that reads these structures (no reader
   is located here; M3.34).
5. **Falsifier.** As in Hypothesis.

## Interpretation

**What the "undecoded 72 %" is.** Nothing in a POINT file is a free-form
bit-packed page. The file is a small database, and the regions r2 could not
name are its indexes:

- *name tries* for spelling search: one over the whole file, one per
  category, one per sub-category, one for area names. Entry = next
  character, child node or index offset, result count.
- *index chains*, one per trie: sorted fixed records (the r2 "index pages",
  `w0 = 1` on the US card and `w0 = shard − 1` on the EU card, where `w0` is
  the area code of the key). A record is the key of a name record plus its
  ordinal; the key words occur verbatim in that name record. It adds no
  information and holds no position.
- *spatial trees*, one per category: the r2/M4.37 "raw 16-byte records".
- the *phone B-tree* (US card only), keyed by the BCD phone number.
- the *400 chain* (r2 "phone pages") = the `INFORMATION` table of the
  in-file dictionary, one record per name record tagged `0x60`; the *2000
  chain* (r2 `w0=2`/keyword pages) = the `ADM` table of area names.

**Where the position is.** The spatial tree answers the question M4.8d and
M4.37 left open. Its three upper levels are keyed by the name record's
copy-A id at 128-, 16- and 1-nibble resolution, and its leaves carry, for
the POI they point to, exactly the two 11-bit words that follow copy A in
the name record. A spatial index stores what it sorts by: those two words
are the next finer level of the position. They were measured before
(C-2930) and rejected as a position (C-2931) because they were tested as an
offset inside a 1-unit copy-A cell; copy A is not a 1-unit value. Its low
nibble is `11xx` in all 21,906,906 words of both cards, so a word has 12 bits
of 16-unit cell, two marker bits and a 2-bit sub-cell index of 4 units; the
11-bit field divides that 4-unit sub-cell into 2,048 steps:

```
u(v, fine) = (v & ~15) + 4 * (v & 3) + fine / 512        // packed units
lat = (u(A.x, rec[8..9])          - 32768) / 192
lon = (u(A.y, rec[6..7] & 0x7ff)  - 52736) / 128
```

That reading is closer to the reference for 16 of 16 POIs, with a median of
115 m against 3,558 m, and eight within 100 m (three within 15 m). The
longitude origin is the tile origin 52736. The "+2.8 km latitude bias" of
M4.8b (C-1903) and the origin 52742 (C-1902) were both the marker bits read
as position: a nibble of 12–15 units where the true offset is 0–16.

This is `OBSERVED` structure plus an external reference fit, not a firmware
reading: the code that turns (copy A, fine) into map coordinates has not
been located, and the marker bits and the leaf flag bits are not explained.

## Conclusion

The done-when of M4.27 is met in its second form with a stronger control
than asked: no structure outside the name pages carries a position of its
own (the spatial trees repeat the name record's, the index chains and the
`INFORMATION`/`ADM` tables have none), shown by walking every byte of all
44 files and by joins without one exception (10,718,316 spatial leaves,
28,295,255 index records, 7,018,762 phone keys). The wider result is that the
name record already holds the position to about 1 m, which re-opens M4.8b
and M4.28 and changes what a POI writer must produce: copy A with the
`11xx` nibble, the two fine words, and a spatial-tree leaf that repeats
them.
