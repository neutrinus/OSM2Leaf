# EXP-2026-11-24-M3.16-opener-follow: Following the INTER/FRWAY openers in L3

- **Status:** done (negative; done-when not met)
- **Date:** 2026-11-24
- **Sample:** `archive/head256.img` (build-A EU 2011 firmware head) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  factory `REFER001/INTER001.DAT` decoded from `INTER001.DAT.cmp`/`.ind`
- **Tools:** `python3 3.11 / zlib 1.3.1` (stdlib only, no recompression); repo
  tools `tools/name_loaders.py`, `tools/vcard_l3.py`, `tools/va_class.py`,
  `tools/nk_decomp.py`, `tools/sh4dis.py`, `tools/inter_table.py`,
  `tools/cmpind.py`, `tools/inter_l3_probe.py` (new, with `--selftest`)
- **Claims:** C-10280–C-10283 (new); C-2210, C-2215–C-2219 (context)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can following the real INTER/FRWAY openers (`0x003fbed8` and its one-call-away
read issuers `0x003fc0ec` / `0x003fc518`, C-4666) in an L3 run locate a
firmware function that consumes the 12-byte big-endian record table at
`0x1108`/`0x1110`, and thus finish M3.16's Done when (reader VAs + consumed
fields in `docs/format/refer.md`)?

## Hypothesis

Following the opener's two real read issuers in a live virtual-card run, rather
than scanning for byte signatures derived from `refer.md`, will reach the
content reader. **Falsifier:** a read-watch of those issuers on the factory
INTER001 page touches only the context header (`+0x68`/`+0x7c`) and never
`0x1108`/`0x1110`, while the LCTBL positive-control reader does read its page.

## Method

1. **Sample and hash.** `sha256sum archive/head256.img` gives the value above.
   The INTER001 page is decoded from the factory `.cmp`/`.ind` with
   `cmpind.py extract`; `inter_table.py check` confirms the big-endian layout.
2. **Commands.** Run from the repo root:
   ```bash

   R=/home/marek/projekty/leafre-work/m5.29-factory-root/REFER001
   python3 tools/cmpind.py extract "$R/INTER001.DAT.cmp" --ind "$R/INTER001.DAT.ind" -o ~/projekty/leafre-work/scratch/m3.16-r3/INTER001.DAT
   python3 tools/inter_table.py check ~/projekty/leafre-work/scratch/m3.16-r3/INTER001.DAT
   python3 tools/name_loaders.py openers archive/head256.img --graph /home/marek/projekty/leafre-work/scratch/m3.29/g.json
   python3 tools/va_class.py archive/head256.img --module Navi.exe --resolve-with 0x3e00200 0x003fbed8 0x003fc0ec 0x003fc518
   python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe 0x003fbed8 0x003fc0ec 0x003fc518
   python3 tools/inter_l3_probe.py --selftest
   python3 tools/inter_l3_probe.py openers archive/head256.img --graph /home/marek/projekty/leafre-work/scratch/m3.29/g.json --card-root /home/marek/projekty/leafre-work/m5.29-factory-root
   python3 tools/inter_l3_probe.py watch archive/head256.img --card-root /home/marek/projekty/leafre-work/m5.29-factory-root --buf ~/projekty/leafre-work/scratch/m3.16-r3/INTER001.DAT
   python3 -c "from pathlib import Path; b=bytearray(Path.home().joinpath('projekty/leafre-work/scratch/m3.16-r3/INTER001.DAT').read_bytes()); b[0x1116]^=0xFF; Path.home().joinpath('projekty/leafre-work/scratch/m3.16-r3/INTER001-mut.DAT').write_bytes(b)"
   python3 tools/inter_l3_probe.py watch archive/head256.img --card-root /home/marek/projekty/leafre-work/m5.29-factory-root --buf ~/projekty/leafre-work/scratch/m3.16-r3/INTER001-mut.DAT
   python3 tools/inter_l3_probe.py scan archive/head256.img
   ```
   The two derived scan families (no `refer.md` byte grammar): **f5** = both
   L3-observed context reads in one function (`add #124,Rn; mov.l @Rn` at
   pcs `0x003fc142`/`0x003fc65c` and `add #104,Rk; mov.l @Rk` at
   `0x003fc146`/`0x003fc65e`); **f6** = the two family-word comparisons
   (`cmp/eq #4` INTER / `cmp/eq #3` FRWAY) with a `+0x68` ctx read, from the
   `0x003fc518` dispatch at pcs `0x003fc542`/`0x003fc568`/`0x003fc534`.
3. **Controls.** *Positive (reader method):* the LCTBL reader `0x0040de98`
   run by `inter_l3_probe.py watch` on the factory INTER001 page makes 6 guest
   reads (`+0x8`, `+0x4`, `+0x2` twice); it shows the watch sees a known reader.
   *Positive (layout):* `inter_table.py check INTER001.DAT` = OK.
   *Positive (access path):* `vcard_l3.py trace 0x003fee70` with ctx+124=4
   resolves `REFER001/INTER001.DAT` (C-4666), and with =3 resolves
   `REFER001/FRWAY001.DAT`; `name_loaders.py openers` puts `INTER0`/`FRWAY0`
   in the `0x003fbed8` family table. *Negative (signature):*
   `inter_l3_probe.py --selftest` flips the synthetic context-read and dispatch
   instructions and the families miss them.
4. **Scope.** Build-A `Navi.exe` sec0 only (5,553,664 B, all executable,
   uncompressed). FRWAY001 is absent on the EU card, so the FRWAY trace names
   but cannot read content. The watch seeds a synthetic context (`+0x68` name
   id, `+0x7c` family), not the live task context; the two derived signature
   families are the only scans, and no `refer.md`-grammar byte signature was
   tried (H51).
5. **Falsifier.** A follower read-watch showing any guest read landing at
   `0x1108`/`0x1110` or in the 12-byte record run would refute the negative;
   with the LCTBL control passing, no such hit is a real negative.

## Interpretation

- **FACT:** `0x003fbed8` is the shared REFER name-builder; its family table at
  `0x001792c4` contains `FRWAY0`/`INTER0`, and its one-call-away read issuers
  are exactly `0x003fc0ec` and `0x003fc518` (C-10280). All cited VAs are
  CODE/sec0 per `va_class.py`; no `INIT` address is named.
- **FACT:** An L3 read-watch of those two followers on the factory INTER001
  page sees only context-header reads at `+0x68`/`+0x7c`, never the record
  table at `0x1108`/`0x1110`. The LCTBL reader control reads 6 guest words, so
  the watch does see a real reader; the negative is a result (C-10281).
- **OBSERVED:** The two derived signature families return 3 and 0 candidates.
  Two f5 hits are inside the opener itself; the third (`0x003fec82`, fn
  `0x003fec60`) really is a u16-key walker (`mov.w @r8`, `0xffff` compare,
  `mov.w @(6,r8)`) but is reached from REFER message handlers, not from the
  INTER/FRWAY opener, and M3.23's L3 watch of those candidates found only
  context reads (C-2218). It is not a confirmed INTER/FRWAY consumer (C-10283).
- **HYPOTHESIS:** A bare call to the follower functions cannot assemble the
  descriptor/name-string arguments built by the live task context, so a real
  record read needs the full opener/message chain (C-10282). Not proven.
- **UNKNOWN:** which firmware instructions consume `key`/`length`/`offset`/
  `b8`/`flag`, blob 0 6-byte elements, and FRWAY blob 1/2 records (C-2219).
  M3.16 Done when is not met.

## Conclusion

`docs/format/refer.md` §INTER/§FRWAY gains a short note recording that the
opener followers `0x003fc0ec`/`0x003fc518` were followed in L3 and read only
the context header, and that the two derived signature families found no
confirmed record consumer. No reader VA or consumed field was established, so
M3.16 stays `blocked` with Unblock **M3.43** (L4 QEMU zoom-out) and the negative
EXP stands (C-2213/C-2219/C-10281–C-10283).
