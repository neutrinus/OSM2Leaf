# EXP-2026-11-06-M3.9-name-collation: name comparison, sort order and name buffer limits

- **Status:** done
- **Date:** 2026-11-06
- **Sample:** `IMG256` = first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img`
  (build A), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  `LCTBL001.DAT` from the same card, SHA-256
  `8cab17754114b5f7ca47d4f46d55c95c6acf841629e1fcc42e6da45063353e9d`
- **Claims:** C-1790–C-1799
- **Supersedes:** in part C-1010 (`EXP-2026-11-05-M4.13-strings`, charset and
  collation parts)
- **Superseded by:** none

## Question

Which function does the firmware use to compare names for search, in what
order does it sort them, and what fixed length do name fields have
(M3.9; `EXP-2026-11-05-M4.13` left both UNKNOWN)?

## Hypothesis

Exploratory. From `EXP-2026-11-06-H5` the navi modules import very few C
runtime string functions, so the working expectation was that no locale API
(`CompareString`/`LCMapString`) is used in the name path and that a custom
table, if any, would show up as data referenced from a sort loop.

### 2. Name compare chain (build A VAs)

| Item | VA / slot |
| --- | --- |
| `OBJDLL.dll!OBJ_PntName_compare` (export rva `0x1c540`) | `0x0349c540` |
| `STDDLL.dll!STD_StringImp_compare` (rva `0x6ae0`) | `0x03466ae0` |
| import slot for it in OBJDLL | `0x034d70fc`, IAT runtime `0x01e330fc` |
| call sites inside `OBJ_PntName_compare` | `0x0349c588`, `0x0349c5b8`, `0x0349c5e4`, `0x0349c610` |
| `OBJDLL.dll!OBJ_PntName_initPrm` | `0x0349c4d4` |
| `OBJDLL.dll!OBJ_PntName_copy` | `0x0349c654` |
| field selectors (`r6`) | `1`, `2`, `4`, `8` |

`OBJ_PntName_compare(a, b, fields, out)` validates both pointers and `fields`
(`1|2|4|8`), then for each selected field calls
`STD_StringImp_compare(a_hdr, a_data, b_hdr, b_data, out)` where the four
field pairs are at `+0/+8`, `+0x108/+0x110`, `+0x210/+0x218`, `+0x418/+0x420`.
The compare result word is compared with `0x03f1` (1009) at `0x0349c642`;
the function returns `0x03e8` (1000) when all requested fields compare equal
(`0x0349c626`) and `0x03f2` (1010) on the first mismatch (`0x0349c63c`).

`STD_StringImp_compare` itself returns library status codes taken from its
literal pool: `0x03f1` (1009) at `0x03466c66`, `0x03f2` (1010) at
`0x03466c68`, `0x03ef` (1007) at `0x03466c6a`; it walks the two strings as
32-bit characters (function pointers `0x0346a8ec`/`0x0346a94c` returned by
`0x0346acb0`/`0x0346acbc`) and skips `0x0a` characters
(`0x0346617c`, mask `0x80000000`).

The same imported compare is called directly from `Navi.exe`
(import slot `0x0055db30`): load sites `0x0039909e`, `0x003991f2`,
`0x003e1e00`, `0x003e1e68`, `0x004c216c`, `0x004c2192`, `0x004c21a6`,
`0x004c21bc`, `0x004e4eb8`, `0x004e4ee2`, `0x004e4ef4`, `0x004e4f10`
(functions `0x00398fdc`, `0x0039912c`, `0x003e1b74`, `0x004c2084`,
`0x004e4d24`). `NaviSearchCC.dll` does not import any name compare: its only
comparisons are `strcmp`/`strncmp`/`memcmp`, used on short prefixes
(e.g. `strncmp(..., 1)` at `0x02f00c9c` and `0x02f00cb4` in fn `0x02f00bf8`).

### 3. Sort comparator and its table

| Item | VA |
| --- | --- |
| `OBJDLL.dll!OBJ_Sort_cmpStr` (export rva `0x1d3b4`) | `0x0349d3b4` |
| `OBJDLL.dll!OBJ_Sort_getPriority` (rva `0x1d368`) | `0x0349d368` |
| `OBJDLL.dll!OBJ_Sort_getNameLine` (rva `0x1d320`) | `0x0349d320` |
| weight table, low range `0x20`–`0x9f` | `0x03485400` (`u16[0x20..0x9f]`, index `c-0x20`) |
| weight table, high range `0xc0`–`0xff` | `0x03485500` (`u16[0xc0..0xff]`, index `c-0xc0`) |
| letter-class table, ASCII `A`–`z` (58 B) | `0x03485300` |
| letter-class table, `0xc0`–`0xff` (64 B) | `0x03485340` |
| comparator used by the sort at `0x034a8888` (fn `0x034a87e4`) | `OBJ_Sort_cmpStr` |
| result codes written by `OBJ_Sort_cmpStr` | `0x03f1` =, `0x03f5` <, `0x03f6` > (`0xfc0a` = negative) at `0x0349d4bc`…`0x0349d4c2` |

`OBJ_Sort_cmpStr` builds one `u16` key per input byte through
`OBJ_Sort_getPriority` (literal `0x349d4c4` → `0x0349d368`), compares the key
sequences, then breaks ties by length. Bytes with key `0x00fe` consume the
next byte (two-byte character lead in the Japanese builds).

Weight values read from the table:

| Byte | Key | Byte | Key |
| --- | ---: | --- | ---: |
| space `0x20` | `0x0000` | `A`/`a` | `0x0047` |
| `Z`/`z` | `0x0060` | `0` | `0x0064` |
| `9` | `0x006d` | `!` | `0x007e` |
| `@` | `0x0093` | `À` (`0xc0`) | `0x0047` |
| `Ç` (`0xc7`) | `0x0049` | `É` (`0xc9`) | `0x004b` |
| `Ñ` (`0xd1`) | `0x0054` | `Ò`–`Ø` | `0x0055` |
| `Ù`–`Ü` | `0x005b` | `Ý`/`ÿ` | `0x005f` |
| `ß` (`0xdf`) | `0x0048` | `é` (`0xe9`) | `0x004b` |
| `ü` (`0xfc`) | `0x005b` | | |

`OBJ_Sort_getNameLine` maps a byte to a class `0..25` (`A`..`Z`, case- and
accent-folded; `0x1a` for non-letters), using the 58-byte table at
`0x03485300` for `0x41`–`0x7a` and the 64-byte table at `0x03485340` for
`0xc0`–`0xff`.

The sort at `0x034a87e4` fills a 200-slot `u16` index table
(`OBJ_RegPntSortTbl_initPrm` `0x034a87c0` writes `0xffff` into 200 slots,
`0x034a87d2`; stride of one record is `0x134` bytes, `0x034a885c`) by
insertion with `OBJ_Sort_cmpStr`.

### 6. Fixed name-buffer lengths

String object (`STD_StringImp_initPrm` `0x03465760`):

```
+0  u16  line count    (zeroed at 0x03465772)
+2  u16  length in chars (read by STD_StringImp_getLength 0x03465798)
+4  u16  max length     (set from exts.w r6 at 0x03465778, read by
                         STD_StringImp_getMaxLength 0x03465780)
+8  u32  chars[max]     (STD_StringImp_input 0x03465888 advances 4 B/char)
```

`STD_StringImp_input` stops at the `max` field (`0x034658b2`, `0x03465920`)
and writes the length to `+2` (`0x0346594e`); over-long input is truncated,
not rejected.

`OBJDLL!OBJ_RoadName_initPrm` `0x0349fb60`:

| --- | --- | ---: | --- |
| formal name | `+0` / `+8` | 32 chars (`r6=32` at `0x0349fb76`) | `0x0349fb74` |
| common name | `+0x88` / `+0x90` | 128 chars (`r6=0x80` at `0x0349fb88`) | `0x0349fb8c` |

`OBJ_RoadName_getFormalName` `0x0349fb9c` returns `+0`;
`OBJ_RoadName_getCommonName` `0x0349fbdc` returns `+0x88`.

### 7. The on-card name table is not sorted

Applying the firmware weight table to adjacent name pairs inside the LCTBL
streams (step 6):

```
513 streams    477,173 pairs    240,619 ascending (50.4 %)    1 stream sorted
```

The one "sorted" stream (3 entries, `0x3e9f00`: `Brussel/Bruxelles`,
`Vlaanderen`, `Wallonie`) is a coincidence of three items.

## Interpretation

- **FACT:** the name path never uses the Win32 locale collation API. Across
  all 149 build-A modules no navi module imports `CompareStringW`,
  `LCMapStringW`, `_wcsicmp`, `lstrcmpW`, `lstrcmpiW`, `FoldStringW`,
  `CharUpperW` or `CharLowerW`; the only navi-side `wcscmp` is in `OSMDLL.dll`
  (task library). Positive control: the same enumeration resolves 29
  `wcscmp` and 3 `CompareStringW` imports in other modules and reproduces the
  `EXP-H5` COREDLL names.
- **FACT:** name equality in the object database is
  `OBJDLL!OBJ_PntName_compare` (`0x0349c540`) calling
  `STDDLL!STD_StringImp_compare` (`0x03466ae0`) on the four name fields at
  `+8`/`+0x110`/`+0x218`/`+0x420`; the mask selects fields, and the result is
  `1000` (all equal) / `1010` (first mismatch). `Navi.exe` calls the same
  library compare directly from the 12 load sites listed in Observations 2.
- **FACT:** name ordering is `OBJDLL!OBJ_Sort_cmpStr` (`0x0349d3b4`), a
  **custom table collation**, not byte order and not locale: one `u16` weight
  per byte from `0x03485400` (`0x20`–`0x9f`) and `0x03485500` (`0xc0`–`0xff`),
  case-insensitive and accent-folding (letters `0x47`–`0x60`, digits
  `0x64`–`0x6d`, symbols `0x7e`+, `ß`→`0x48`); ties broken by length.
- **FACT:** the only binary search over a name table
  (`OBJDLL` fn `0x034bdc10`, call `0x034bdd1c`) uses
  `STD_StringImp_comparePriority` (`0x03467d84`), so that table must be stored
  in the priority order; the map name streams are not stored in that order
  (50.4 % ascending, 1/513 streams sorted), so the card writer must not sort
  them.
- **FACT:** the firmware converts single-byte map text with
  `MultiByteToWideChar(CodePage = 0, …)` (CP_ACP) at `0x02ed41fc`/
  `0x02ed4222`; STDDLL classifies ISO-8859-1/5/6/9 but has no ISO-8859-2
  support.
- **FACT:** name fields are fixed-capacity `u16` max-length string objects:
  road formal 32 chars, road common 128, place country/state 64, county/city
  128; input is truncated at the cap, never rejected.
- **FACT:** the shipped text is ASCII + Latin-1/CP1252 letters, and letters
  outside Latin-1 are transliterated by dropping the diacritic (`Č`→`C`,
  `ř`→`r`, `ł`→`l`, `ą`→`a`): `Cesk` 214 vs `Česk` 0, `stredn` 13 vs `středn`
  0, `Zizkov` 66 vs `Žižkov` 0, while `München` keeps `ü` 234 times. Polish
  admin names in `ICADM021` are ASCII (`KEPNO`, `SLOWINO`, `DABROWA`).
- **HYPOTHESIS:** the `STD_StringImp_comparePriority` bias is the
  `0x80000000` flag of the first non-newline character (`0x0346617c`,
  `0x03466c74`), so the priority order is still the code-point order of the
  string objects, not a second table.
- **UNKNOWN:** which of the four `OBJ_PntName` fields receives a POI/street
  name (the labels are the place hierarchy), so the cap for the POI name
  string itself is not yet tied to a field.
- **UNKNOWN:** the mapping of the weight table for `0xA0`–`0xBF` (NBSP and
  symbols); it does not affect letters.

M4.13 `ISO-8859-2` rule: single-byte CP1252/Latin-1 text with non-Latin-1
letters transliterated by dropping the diacritic, no enforced sort order in
the on-card name streams, and the firmware's own case/accent-folding weight
table as the only collation. `docs/format/refer.md` points to that section for
`ADDRE`/`POINT` names. C-1010 is retracted in part (charset and collation);
C-1790–C-1799 record the new evidence.
