## Question

Can the CE 5.0 SH-4 user-slot VAs held in `PROCESS.lpszProcName` (M8.H68 C-8134)
be translated to guest physical memory from the guest's own kernel tables, so
that `tools/ze0_ps.py --monitor SOCK --no-modules --threads` prints `nk.exe`,
`filesys.exe`, `device.exe` and `Navi.exe` with thread counts read from the
kernel structures, with no name taken from the DBGMSG/serial log?

## Hypothesis

CE 5.0 on SH-4 keeps a section/page-table array in the kernel data page and
maps each 32 MB user slot through a hardware two-level PTE walk. The physical
address of a name pointer is a pure function of guest memory (no fitted delta,
no log), so it can be reproduced offline. **Falsifier:** the computed physical
address does not hold the UTF-16 name independently seen in H68's RAM scan
(`filesys.exe` at P1 `0x8c2daec4`), the four printed names disagree with the
same run's DBGMSG lines, or a name disappears when the serial log is blanked.

import re, socket, time
S='/home/marek/projekty/leafre-work/scratch/m8.h68a/live/hmp.sock'
def hmp(cmd):
    m=socket.socket(socket.AF_UNIX); m.connect(S); m.settimeout(2)
    try: m.recv(65536)
    except socket.timeout: pass
    m.sendall(cmd.encode()+b'\n')
    buf=b''; deadline=time.time()+6
    while time.time()<deadline:
        try: c=m.recv(65536)
        except socket.timeout: break
        if not c: break
        buf+=c
        if buf.rstrip().endswith(b'(qemu)'): break

def xp(addr, words):
    return [int(x,16) for x in re.findall(r'0x([0-9a-f]{8})', hmp('xp /%dwx 0x%x'%(words,addr)))]
print('TTB reg:', [hex(x) for x in xp(0xff000000, 8)])

for va in (0x0405fec4,0x0602fec0,0x080bfec4,0x0a03fecc,0x0d56fec8,0x1003fec0):

### 3. Controls

*Positive:* on the live guest, HMP `xp /8wx 0x0c2daec4` prints
`0x00690066 0x0065006c 0x00790073 0x002e0073` — `file`/`s`/`.s` of
`filesys.exe` — the same bytes the new walk resolves for VA `0x0405fec4`.
The `--selftest` synthetic image (30 checks) has a TTB, an L1/L2 chain and a
PTE that map U0 `0x0405fec4` to phys `0x0a05aec4`, where `filesys.exe` is
stored; all four original process-name checks still pass.

*Negative:* (a) zero the synthetic PTE → the name read raises `OSError` and is
recorded, not silently unchanged; (b) on the live guest, replace the
`filesys.exe` name pointer with an unmapped VA → that process drops from the
list with an explicit error while the other six remain; (c) the original
selftest negatives (empty process array, dangling name pointer, circular
thread list) still fail as designed.

### 4. Scope

One idle EU2011 kernel-B guest; six populated process-array slots (7 processes
named, 141 threads) and its six user-slot name VAs. The translation is derived
from the SH-4 section array (`aInfo[7]`/`aSections`, 64 pointers) and the
hardware page-table layout; no firmware module VA is attributed here. Not
covered: US2011/NK1/2014/2016 builds, the live PC inside `Thread.ctx`, a guest
context switch, or a name source other than the pointer at `PROCESS+0x20`.

### 5. Falsifier

The computed physical address must land on the UTF-16 name seen in H68's
independent full-RAM scan, the four names must agree with the same run's DBGMSG
lines, and none may disappear when the debug log is blanked. A name from a
hardcoded slot→name map, a RAM scan hit list or the serial log would refute the
claim. If the layout were not derivable in this session, the honest result is
`blocked` with the exact failing VA reads, not a relaxed Done when.

## Interpretation

- **FACT:** on the EU2011 kernel-B guest the SH-4 TTB register equals
  `aInfo[KINX_SECTIONS=7]` = KData `+0x31c` = `0x89e418a0`, the inline
  `aSections` array at KData `+0xa0`; every name VA translates through the
  two-level SH-4 table with a 12-byte page-group header and 4 KB pages
  (O3–O5). All reads are LE u32 (`struct.unpack("<I")` / `hmp_xp`).
- **FACT:** `tools/ze0_ps.py --monitor SOCK --no-modules --threads` now prints
  all seven processes with thread counts, including the four required, with
  zero `READ ERROR` lines (O6); names are read at the physical address of the
  pointer at `PROCESS+0x20`, not from a log (O8).
- **OBSERVED:** the guest had seven named processes and 141 threads at the
  sampled idle state; slot→process inference from H68 C-8136 is now confirmed
  by the translated name bytes for slots 1–5 and 7.
- **HYPOTHESIS:** the same section-array/PTE layout holds on other CE 5.0 SH-4
  builds, because it is the architectural SH-4 two-level table; out of scope
  here (one build, one guest).
- **UNKNOWN:** whether the live PC in `Thread.ctx` can be resolved without a
  guest context switch; unchanged from H68.

## Conclusion

`tools/ze0_ps.py` gains a `UserVaMemory` translator that walks the guest's own
SH-4 section/PTE tables, derived from the public KDataStruct field order and
validated against the `filesys.exe` anchor — no fitted delta, no hardcoded
name map, no log source. The M8.H68a Done when is met: the pinned reproduction
prints `nk.exe`, `filesys.exe`, `device.exe` and `Navi.exe` with thread counts
from the kernel tables and zero read errors, while `--selftest` passes 30/30
(checks 25→30 after five new checks). M8.H68 is re-opened by this PR (rule 15)
with its negative Result retained as history. No format doc changes; rule 13
levels are unchanged (tooling). External sources: flycast `wince.h`
(`wince_resolve_address`, commit `449d2569`) and QEMU 11.1.3
`target/sh4/helper.c` are cited in `docs/research/sources.md` — QEMU documents
the **hardware UTLB**, not CE's software tables, and neither was copied as
authority; the layout was validated against live guest bytes.
