## Question

Does the firmware's `POINT010` record walker read the record **contents** we
write, or only the record framing, i.e. would a reader that ignored the record
bytes still pass the existing L3 corpus?

## Hypothesis

`fn nth` returns the *start offset* of record `n` by summing each record's
`2*len2` size; a length change therefore moves every record **after** the
edited one and nothing else. **Falsifier:** the mutant and the factory page
return the same offsets for the sampled record after the edit (the reader
ignored the record bytes), or the record count changes (the page is corrupt).

## Method

1. **Sample and hash.** The two 256 MiB heads above; the EU factory pair from
   `leafre-work/m5.29-factory-root/REFER001/`, the US factory pair from
   `leafre-work/m5.12-us/root-factory/REFER001/` (both outside the repo).
2. **The edit.** Record 500 is a name record: US
   `HAWAII ST GOVT FREQNTLY CLLD NMBRS` (34 B) becomes
   `HAWAII ST GOVT FREQNTLY CLLD NMBRSXXXX` (+4 B) — the insertion lands
   **before** the trailing house number, so the new record reads
   `…NMBRSXXXX1700@LANAKILA AVE`; EU `DROMAHAIR GARDA STATION` (23 B) becomes
   `DROMAHAIR GARDA STATIONABCD` (+4 B), `…STATIONABCD@R288`. Each old string
   occurs exactly once in its page (`old_text_count=1`). The new size is even
   (US 152 → 156, `len2` 76 → 78; EU 90 → 94, `len2` 45 → 47), so the framing
   byte still stores `size/2`. **Only a length-changing edit moves an offset**;
   a coordinate or icon edit would not, which is why the mutation is a
   `--resize`-style name edit.
3. **Chunk-preserving rebuild.** `cmpind_codec.repack_changed_chunks` reuses
   every unchanged 64 KiB outer stream verbatim and recompresses only the one
   chunk holding `page + record_offset`; the `.ind` offsets are rebuilt. The
   changed chunk's stream is *newly compressed* with this host's zlib (zlib-ng
   here), so it is not claimed to be factory-identical; the other streams are
   byte-verbatim copies.
4. **The four runs.** Two code builds (`--build eu2011`/`us2011`) × two pages
   (US `0x840ba0`, EU `0x6e06d0`) × factory then mutant. The witness is the
   **first sampled record after the edit** (`n=501`, then 998/999): an
   in-place resize cannot move record 500's own start, so `n=500` is the
   explicit unchanged control.
5. **Falsifier** (stated before the result): mutant and factory offsets equal
   at `n=501`/998/999, or the record count differs from 1,000.

## Interpretation

- **FACT:** the firmware walker returns offsets that follow the mutated
  record's new length: the first sampled record after record 500 moves by the
  exact name delta (+4) on both builds and on both pages, while records before
  it and record 500 itself do not move.
- **FACT:** a same-length content edit (`NMBRS1700` → `NMBRZ1700`) leaves every
  sampled offset identical to the factory page on both builds, so the +4 in the
  length-changing mutant is caused by the record length, not by the changed
  bytes alone.
- **FACT:** the record count stays 1,000 on every mutant page (`parse_page`
  equals the firmware count), and `n=1000` still returns `None` (one past the
  end), so the page is a valid chain, not a corrupt page that happens to
  parse.
- **FACT:** only one outer 64 KiB stream changes (US chunk 132, EU chunk 110);
  the other 148 / 150 streams are byte-verbatim copies, and the following
  `.ind` offset shifts by the compressed-size delta (−174 US, −334 EU).
- **OBSERVED:** the changed inner stream had to be re-deflated at level 9 /
  memLevel 9 because the factory parameters do not fit this host's zlib; the
  mutant chunk is therefore not factory-identical, and no byte-identity is
  claimed for it.
- **IMPLICATION:** a reader that ignored the record bytes could not produce
  these offsets, so the POINT record walker does read the record framing we
  write. This is the record-mutated control M9.10 lacked; M9.41 can cite it as
  the negative-control page for the US walker target.
- **LIMITATION:** the observable is the *walk* over the record chain, not the
  decoded name/coordinate fields; the name text itself is read by a later
  accessor (M3.11c), not by this walker.

## Conclusion

One `POINT010` record per page was rewritten with a length change and rebuilt
chunk-preservingly; in all four code-build × page combinations the firmware
walker moved every later sampled record by the exact delta (+4), kept the
count at 1,000 and still returned `None` past the end. The falsifier (mutant
and factory offsets identical after the edit) did not fire. The corpus now
contains a page whose *records* differ, not merely a different factory card.

## Corrections after navigator review (same task, same branch)

Two numbers from the driver's first draft were replaced before the runs:

1. The draft put `0xfe4e` in the `n=500` column; `0xfe4e` is `n=501`. Factory
   `n=500` is `0xfdb6` (US) / `0xbe28` (EU), quoted from the run above.
2. The draft witness "the mutated record's own offset differs" is
   unsatisfiable for an in-place resize; the witness is the first sampled
   record **after** the edit (`n=501`, +4), with `n=500` as the unchanged
   control, and the falsifier is mutant-vs-factory equality, not `PASS`.

The driver's first scratch build also re-encoded the whole blob (all 149
streams changed); the rebuild above uses `repack_changed_chunks` and changes
one stream. The `-7006` chunk-133 `.ind` shift reported from that scratch build
was an artifact of the whole-blob re-encode; the real shifts on this path are
−174 (US) and −334 (EU), measured above.
