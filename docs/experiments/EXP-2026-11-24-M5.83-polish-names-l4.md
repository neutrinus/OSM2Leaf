## Question

For one synthetic OSM name carrying all eight diacritic Polish letters plus
the CP1252-storable `ó`, do the bytes written to the card equal
`imf_check.fold_cp1252` (C-1799), and what does the real `Navi.exe` draw for
those bytes at L4 (M8.H71 London parcel), compared with M4.87's glyph table?

## Hypothesis

The section-4 name writer stores exactly the fold's CP1252 bytes and L2
decodes them back unchanged. On-screen, the drawn characters are the folded
ASCII bases plus `ó` — the fold strips diacritics *before* the font, so the
eight stripped letters never reach the font. `ó` (kept as `0xf3`) is the sole
font-evidence row. **Falsifier:** stored bytes differ from `fold_cp1252`, a
folded glyph that M4.87 lists is missing on screen with no note, the control
name does not render byte-identically, or the crop comparison is blind to a
planted substitution.

### 3. Controls

- **Positive digital (L2):** stored bytes `5a 41 43 45 4c 4e d3 53 5a 5a`
  equal `fold_cp1252` output (O2) — the `ó` byte `0xf3` is present.
- **Negative digital (L2):** flipping byte 6 from `0xf3` to `0x6f` makes the
  byte-comparison fail in exactly 1 position (O7) — a test that can fail.
- **Positive scope (font table):** `fdl_font.py --selftest` passes and
  `ó` U+00F3 has glyphs `0x0a01 0x6601 0xda01`, `present YES` (O3).
- **Control name:** `fold_cp1252('Zizkov') = 'Zizkov'`, bytes
  `5a 69 7a 6b 6f 76` (O2) — unchanged by the fold.
- **Negative crop (MANDATORY):** with the same `diff` command, an identical
  crop prints `changed_pixels=0`, and a crop with a planted wrong-letter pixel

a finding for a new task, not a fix here.

## Interpretation

- **FACT:** the L2 half passes. One synthetic OSM Polish name reaches the
  card as exactly `ZACELNÓSZZ` = `5a 41 43 45 4c 4e d3 53 5a 5a`, equal to
  `fold_cp1252` and decoded back unchanged by the viewer. The `ó` byte `0xf3`
  is preserved; the eight diacritics are dropped by the data-layer fold before
  the font.
- **FACT:** the negative controls (wrong byte at L2, planted wrong pixel in
  the crop) both detect a substitution — the comparisons can fail.
- **FACT:** the L4 boot draws a full map frame (384000 non-black pixels), but
  our synthetic label is off-screen because the writer substituted a factory
  slot in Brittany. Per the task's Stop rule, the L2 table and the screenshot
  crop SHA-256 are recorded here; bringing the label into view is M8.H33/M8.H72.
- **Finding (new task):** the street/road-name writer path in `fa_encode`
  uses UTF-8, so a diacritic Polish name written there would store UTF-8
  multi-byte sequences, not the CP1252 fold — unlike the section-4 path. This
  must be reconciled before claiming "our generated street names store the
  fold" (rule 13; not an L4 acceptance of generated names).

## Conclusion

The compile + L2 half of M5.83 is complete and evidenced: stored bytes equal
`fold_cp1252` for all nine letters, the font table is quoted per letter, and
both negative controls have teeth. The L4 half is **not** complete: the
synthetic label is stored in an off-screen factory slot, so the L4 screenshot
cannot show it without a position control that this task does not add. Status
`blocked` per TODO rule 7, with the L2 table and screenshot SHA-256 as the
recorded partial result.
