## Question

Does the EU2011 firmware's section-4 reader return the 37 OSM place names our
M5.65 generator wrote into `B48R050R.DAT` section 4 — through the L3 run, not a
Python-only decode — so that rule 13 can be closed for our generated names?

## Hypothesis

The kind-`0x40` data request makes the firmware read and inflate our generated
section-4 record, and the stored-copy consumer `0x00422eac` (EU2011) walks the
record's name list, so a firmware run returns the 37 names equal to
`section4.py parse` of those bytes; a one-word mutation of a name changes the
firmware-returned list.  **Falsifier (set before the runs):** `0x00422eac`
returns only a single `u16` selector (not a name list), or no consumer of the
reply's name text can be driven from the reply with a stated signature — in
which case the literal Done-when is unreachable and the task is `blocked`, not
`done` from a Python-side decode.

### 5. Falsifier

The falsifier **fired**: `0x00422eac` writes a single `u16` to `*out` at
`0x00423070` (`mov.w r3,@r12`) and returns a flag in `r0` — it extracts one
signpost selector, it does not enumerate a 37-name list.  `k` comes from the
renderer table via `0x00424464(19,…)` → getter `0x0041e2bc`, which is still
unresolved; a gate pass does not tie the buffer to a name list.  The literal
Done-when "37 names returned by the firmware" and "one-word mutation changes
the firmware-returned name list" are therefore unreachable through this
consumer.  The task is `blocked` with **Unblock: M4.56** (the task exposing the
`k` source and the full name-list consumer of the kind-`0x40` reply).

## Interpretation

- **FACT:** the EU2011 firmware's data-access task reads and inflates our
  generated section-4 record (Path A: `B48R050R.DAT pos 0x413d300`, 616 B),
  the reply is sub 5+sub 3, a firmware-side byte flip changes the served
  record (616 → 768 B) and the verdict MISMATCH, and the factory control is
  unchanged.  The Python-side decode of those firmware-fetched bytes contains
  all 37 written OSM names (37/37).  This is a **supporting control** only: it
  shows the firmware served our bytes, not that a firmware consumer read the
  name list.
- **FACT:** `0x00422eac` (pdata START, CODE sec0, EU2011) ends with a single
  `mov.w r3,@r12` to `*out`; it extracts one `(buf[k+d] & 0xf8) >> 3` selector,
  not a name list.  No full name-list consumer of the kind-`0x40` reply was
  located or driven.
- **OBSERVED:** the reader can be driven with a declared `k` (`k=162` PASS,
  `k=0` GATE-REJECT), but `k`'s source `0x00424464(19,…)` → `0x0041e2bc` is not
   derived from LE disassembly to the renderer table; a gate pass occurs at
  0.28 % of section-4 words and does not identify the section (C-5924).
- **HYPOTHESIS:** a later RGD stage uses the selector returned by `0x00422eac`
  to pick one guidance item from the record; the routine that walks all name
  entries has not been located.
- **UNKNOWN:** the full name-list consumer of the `0x14b6` kind-64 reply and the
  source of `k` in the renderer table (`0x00424464`/`0x0041e2bc`, table
  `*0x00e8f604` etc.).  US2011 build was not needed (task allows it only as a
  cheap control if the VA exists).

## Conclusion

Rule 13 is **not** closed for our generated section-4 names.  The literal
Done-when is unreachable with the located consumer: `0x00422eac` returns one
`u16` selector, so neither "37 names returned by the firmware" nor "one-word
mutation changes the firmware-returned name list" can be observed through it.
Recording this as `blocked` with the positive controls above (firmware served
our bytes, flip changed them, factory control unchanged, Path B driven with a
declared `k`) rather than silently dropping the mutation control or inferring
acceptance from the Python parse.  The block is named **Unblock: M4.56** — the
task that exposes the `k` source and the full name-list consumer of the
kind-`0x40` reply.  `reader-coverage.md` row 19's L3-result cell records a
REJECT verdict pointing here; no F4 cell, legend or other row was touched.
