## Question

Where does the firmware decide the unit's market/region, and can a card carrying
European map data make a US unit read/use that data (or become a European
unit)?

## Hypothesis

External research says the market is a byte in the NAND PROD block (`0xA022`,
`0x10` JP, `0x20` US, `0x30` EU, `0x40` RU, `0x50` CN) and that `AppLaunch.dll`
compares it against `0x10`. The alternative to test is that the card itself
supplies a region that overrides the unit.

## Observations

### 1. `CApi_GetModelArea` is a runtime dispatch, not a compiled-in table

`commondll.dll` exports it as ordinal 39:

| Build | Export VA | Relatives |
| --- | --- | --- |
| B | `0x03c0398c` | `CApi_GetModelBaseType` `0x03c03a04`, `CApi_GetModelCode` `0x03c039c4` |
| C | `0x03be3994` | `0x03be3a0c`, `0x03be39cc` |

The stub reads a global object pointer (`0x01f7a168` in B; the C build uses
`0x01f76168`), returns `-1` when it is NULL, and otherwise tail-calls a binder
at `0x03c04674` (B) / `0x03be467c` (C). The object is built in `commondll`'s
init `0x03c070d8` (B) / its C counterpart. `CApi_GetModelArea` is bound to the
object's target-ID source; there is **no** `CApi_SetModelArea` export (the full
export list is 1–102, reads only).

For build B the chain is:

```
model-info +40  binder  ->  model-info +20  target-ID object
                            vtable 0x03c032dc
                            slot 2 = 0x03c0c908  returns byte[+5]
```

Build C is the same layout with vtable `0x03be32e4` and slot 2
`0x03beca64`.

### 2. The area is byte 1 of a 4-byte unit "Target ID"

`commondll` reads the target ID lazily, once, in B `0x03c0c830` / C
`0x03bec98c`:

- call target is `KernelIoControl` (coredll export ordinal 557, verified in
  `coredll.dll`'s export table);
- IOCTL code `0x01013208`, input buffer = one `u32` containing `1`, input size
  4, output buffer = object `+4`, output size 4;
- result `0` is failure; object byte `+4` must be non-zero and not `0xFF`
  (otherwise the record is rejected and the getter returns `-1`);
- on success it logs UTF-16 `Target ID Code >> %02X%02X%02X%02X`
  (B `0x03c03328`, C `0x03be3330`) with bytes `+4…+7` and sets a cached
  "valid" flag.

The getter for the model area returns the **second output byte** (`+5`).
The same object also feeds `CApi_GetModelBaseType`/`CApi_GetModelCode`
(different helpers, `0x03c05b44` / `0x03c05f54` in B), which compare the
4-byte value against constants such as `0x010100212`, `0x010200212`,
`0x010300212`.

### 3. `AppLaunch.dll` maps the area to a market and a launch mask

The area switch is B `0x03bcba58` / C `0x03bab580`. It zeroes a name buffer,
calls `CApi_GetModelArea` through the import slot (B `0x03bd6314`, C
`0x03bb6320`) and compares the return value:

| Area | Name string (B / C) | Name | Mask |
| --- | --- | --- | --- |
| `0x10` | `0x03bb1c20` / `0x03b91c00` | `Japan` | `0x00010000` |
| `0x20` | `0x03bb1c40` / `0x03b91c20` | `USA` | `0x00020000` |
| `0x30` | `0x03bb1c48` / `0x03b91c28` | `Euro` | `0x00040000` |
| `0x40` | `0x03bb1c54` / `0x03b91c34` | `Russia` | `0x00080000` |
| `0x50` | `0x03bb1c64` / `0x03b91c44` | `China` | `0x00100000` |
| other | `0x03bb1c2c` / `0x03b91c0c` | `WorldWide` | `-1` |

It logs `Launcher [Area:%02X >> %s]` (B `0x03bb1be4` / C `0x03b91bc4`).
For an unknown area it logs `Launcher: Get Area info from Env Variable.`
(B `0x03bb1c70` / C `0x03b91c50`) and calls
`KernelIoControl(0x0101304C, 0, 4, &out, 4, …)`; the returned value is used as
the mask directly. This is still a unit/kernel source.

The mask is consumed by the launcher table walker B `0x03bcc5b0` (C
`0x03bac324`) and its filter B `0x03bcc564`: an entry is started only when
`entry[+4] & area_mask` is non-zero (and `entry[+12] & boot_mask`, plus two
further predicates). The area therefore selects **which processes/drivers are
launched**. The entry table itself is in the module's compressed `.data`; the
per-entry masks were not decoded.

Process names in the launcher's UTF-16 name block include four `Navi.exe`
entries and one `NxJpNavi.exe` (B `0x03bc1224`/`0x03bc1264`), i.e. a
Japan-specific navi executable. Which mask the `NxJpNavi.exe` entry carries is
in the compressed table and remains **UNKNOWN**.

The boot-time `NK Region Error` / `NK Version Error` strings in the same module
belong to a different function (B `0x03bd1dd0`), which loops over the two NK
image slots and validates their checksums via `IOCTL` `0x01013020`; it does not
read the model area. Do not confuse the two "region" uses.

### 4. The map/navigation modules do not consume the area

Build A import scan (`CApi_GetModelArea` present/absent in each module's import
table):

| Consume it | Do not consume it |
| --- | --- |
| `Audio.exe`, `CameraCC.dll`, `AvCCWrapper.dll`, `DiagnosisCC.dll`, `Consult.exe`, `SystemEXE.exe`, `SystemCC.dll`, `AuiMonitoringCC.dll`, `TelemaAppWrapper.dll`, `UsbAudioCC.dll`, `BOLERODLL.dll`, `Usb.exe`, `unimodem.dll` | `Navi.exe`, `NaviMapCC.dll`, `NaviMapScrollCC.dll`, `NaviSearchCC.dll`, `NaviRouteCC.dll`, `NaviGuideCC.dll`, `NaviSetCC.dll`, `NaviDrawCC.dll`, `NaviStateCC.dll`, `OBJDLL.dll`, `STDDLL.dll` |

Positive control: `OBJDLL.dll` (a map/object reader) does import
`commondll.dll` (`CApi_GetLangInfo`, `CApi_SetLangInfo`), so the scan sees
`commondll` imports in a map module; it simply finds no area import there.
`SystemCC.dll` also contains the literal
`SystemCC : GetModelArea : Stub_CApi_GetModelArea Error(%d)`, confirming the
same pattern on a consumer.

### 5. The card is checked against unit-side records, not against the area

`AppLaunch.dll` opens `\SystemSD\VER_INFO\HDD_INFO.TXT`
(B `0x03bc92f0` / C `0x03ba8fc8`) and uses two functions:

| Build | Function | What it does |
| --- | --- | --- |
| B `0x03bd2ad8`, C `0x03bb2858` | unit/card version compare | reads the unit target-info record via `KernelIoControl(0x0101302C)`, copies 11 bytes from unit record `+96` and 11 bytes of the card's first `HDD_INFO` line, byte-compares them and logs `VerInf:%s / HddInf:%s` (B `0x03bc9330`) |
| B `0x03bd2ce4`, C `0x03bb2a64` | map-DB range check | reads unit map-DB minimum/maximum from target info `+112`/`+114` (big-endian `u16`), derives the card's value from the parsed `HDD_INFO` records and logs `MapDBVer : %d <= [%d] <= %d` (B `0x03bc9360`); out of range falls through to the error dispatcher |

Both use the same kernel IOCTL path (AppLaunch import slot for coredll #557);
neither calls `CApi_GetModelArea` and neither accepts a region or area from the
card. The unit-side bytes come from the kernel target-info record, not from
the card's `0x06000000` copy. Whether other modules also consume the
`0x06000000` copy is outside this experiment.

### 6. The navigation executable is a market-compiled build

Build A's `Navi.exe` contains the UTF-16 banner
`## COMPILE OPTION ## EUROPE FOR NISSAN ##` (VA `0x00011c30`, referenced from
`0x00330130`) plus debug strings `Show Eur Usa RouteInfo` /
`Disp EUR/USA RouteInfo`. This is a build-time market choice, not a runtime
switch. The card does not replace the running `Navi.exe` by being mounted: the
firmware area is an update payload and `MapUpdate.exe` is the installer (M2.6).
External research says the NAND copy is `NB04` while the card carries `NB00`;
with no US image we cannot compare the two builds.

## Interpretation

- **FACT (static, B and C):** the market/region value used by the launcher is
  the second byte of a 4-byte unit Target ID read by
  `KernelIoControl(0x01013208)`. It is exposed as `CApi_GetModelArea`
  (`commondll.dll`) and consumed by `AppLaunch.dll`'s area switch and launch
  table. The values are `0x10` Japan, `0x20` USA, `0x30` Euro, `0x40` Russia,
  `0x50` China; anything else is `WorldWide`.
- **FACT (static):** no card file, path or value is read by that chain, and
  there is no setter for the model area. A card cannot change the unit's
  market/area.
- **FACT (static):** the navigation/map modules do not import the area API. The
  area gates process launch, UI/language/audio resources and system settings —
  not the map reader.
- **FACT (static):** the card's `HDD_INFO.TXT` is compared with a unit-side
  target-info record and a unit-side map-DB range, both read through the same
  kernel IOCTL family. The card side is read-only input; the unit side cannot
  be supplied by the card.
- **OBSERVED:** the EU `Navi.exe` is compiled `EUROPE FOR NISSAN`; the launcher
  name block contains a JP-specific `NxJpNavi.exe` name (mask not decoded).
- **HYPOTHESIS:** a US unit with an EU map card will pass the SD-lock gate only
  if the card is locked with the US unit's password (the lock is unit-side,
  M2.8) and will then fail the launcher's version/map-DB checks unless the
  card's `HDD_INFO` record and map-DB value match the US unit's target-info
  values. If they match, the US unit's map engine should read the EU files
  (same packaging); the UI/area remains US and the EU card's firmware is not
  executed.
- **UNKNOWN:** the exact `HDD_INFO` line/field mapping, the `0x06000000` copy's
  role elsewhere, the per-entry launch masks (compressed `.data`), the US
  card's packaging, and the real unit's behaviour (no hardware, no US image).

## Conclusion

`docs/research/us-eu-region.md` now records the firmware chain: unit Target ID
→ `CApi_GetModelArea` → `AppLaunch` area/launch mask. The old "compares against
`0x10`" sentence is corrected: `0x10` is only the Japan branch. The card can
supply map data but cannot set the market; the remaining card-side gates are
the unit-vs-card `HDD_INFO`/map-DB checks.

`docs/format/firmware.md` gains a "Model area and Target ID" section;
`docs/format/validation.md` notes that the launcher's Sys side is the kernel
target-info record. Claims C-780–C-789 added.
