## Question

M8.C1h stubbed `HCXLog.dll` and `HCXMemory.dll`, and M8.C1i copied
`AppTimerDll.dll` from card image C. Does the unit's own flash hold these
modules? If it does, do the real modules change what AuiApp does on `-M ze0`?

## Hypothesis

The unit NAND holds the CE image that image A was built against ("NK1"),
with the three modules. The real modules load in place of the stand-ins.
Falsifier: with the real modules, controls fail that loaded with the stubs.

## Method

1. `nk1_extract.py NAND --list` lists every CE image (`ECEC` at +0x40) on a
   64 KiB boundary of the dump. The image with the most modules is cut out
   (`physlast - physfirst` bytes).
2. The cut image is searched for the PROD record's serial bytes, the 4-byte
   unit key, the 16-byte card-lock password and its ASCII tail, the serial
   as ASCII and UTF-16, and 17-character VIN-shaped strings.
3. `ze0_stubdll.copy_module` takes sections of any page count. Compressed
   sections are decoded by image B's kernel routine in PySh4
   (`nk_decomp.decompress` with image B's `nk.exe` regions) and stored
   uncompressed. The RW section keeps its decoded content; only the
   import address table is reset to the lookup table.
4. Run K1:

   ```
   ze0_ipl.py patch archive/head256.img --prefer-app auiapp.exe,auirtdll.dll \
       --copy-dlls unitflash -o ipl_k.txt
   ```

   This is followed by the `ze0_aui.py --no-aui-timeout` lines and the M8.C1i
   command line. The baseline is M8.C1i run H10 (`--stub-dlls hcx
   --copy-dlls apptimer`). K1 ran until `AppLch >> Finish Launch Threads!`
   (8 476 serial lines). After that came one screenshot.

## Observations

**O1 — NAND layout.**

| offset | VA | bytes | modules | files |
| --- | --- | --- | --- | --- |
| 0x0000000 | `0xa0000000` | 16 560 | 1 | 0 |
| 0x0010000 | `0x8b000000` | 29 152 | 1 | 0 |
| 0x0020000 | `0x8b010000` | 46 580 | 1 | 0 |
| 0x0030000 | `0x8b020000` | 63 520 | 1 | 0 |
| 0x0040000 | `0x88000000` | 2 939 624 | 51 | 10 |
| 0x03a0000 | `0x803a0000` | 21 184 | 1 | 0 |

NK1 (0x40000) holds `nk.exe`, `coredll.dll`, `filesys.exe`, `device.exe`
and the drivers (`anwdrv`, `CAN`, `gdisubdrv`, `SDHC`, `flash`, `VSram`,
`serial_scif`, …). It also holds `HCXLog.dll` (vbase `0x03c30000`),
`HCXMemory.dll` (`0x03c20000`), `AppTimerDll.dll` (`0x03c10000`),
`Antitheft.exe`, `Camera.exe`, `Failsafe.exe` and `DrawOi.exe`. Its files
are `boot.hv`, `default.hv` and `user.hv` (timestamps 2011),
`initobj.dat`, `initdb.ini`, `wince.nls`, `celog.dll`, a font and
`OIDEFALT.img`. `Cws_Apl.dll` is not in NK1.

None of the strings from Method step 2 occurs in NK1. The only VIN-shaped
hits are fill patterns such as `ZZZZ…` and `UUUU…`.

**O2 — Placement.** NK1's module windows overlap modules of image B, for
example `0x03c20000`–`0x03c52000`, so the three modules are moved:

| module | code | RW | words moved | notes |
| --- | --- | --- | --- | --- |
| HCXLog | `0x036d1000` | `0x01f4f000` | 66 | |
| HCXMemory | `0x036e1000` (3 pages) | `0x01f51000` | 382 | RW and RO data stored decompressed |
| AppTimerDll | `0x03751000` | `0x01f53000` | 86 | |

The kernel routine decodes HCXMemory's two compressed sections. `cerom.py
decompress` cannot pick a codec for them (lzx/lzss do not parse).

**O3 — The real modules run (K1).** No `DoImport Failed!` names any of
the three modules. HCXMemory logs 10
`MemoryManager::CreateSharedBuffer : BufferName[…] : BufferSize(N)` lines,
for example `tagDRVCOM_SHARED_DATA` (72 bytes),
`SharedMemory::_BTWRAPPER_SHAREDMEMORY` (2 160 bytes) and
`CCWindowHandleData`. The stubs logged nothing. The failures are the same
as in H10:

| | H10 (stubs + image C copy) | K1 (NK1 modules) |
| --- | --- | --- |
| `DoImport Failed!` | 16 (15 × `Cws_Apl.dll`, 1 × `BOLERODLL.dll` for Usb.exe) | 16, same |
| `Failed initialize control` | 6 | 6 |
| `Wait Modules ID=[6]` (Audio.exe) | 1 | 1 |
| `CreateSharedBuffer` | 0 | 10 |

**O4 — ScreenState reads a real handle table.** In K1 only:

- `ScreenStateWindowHandleManager::GetWindowHandle> The CC Window is not
  exist. [id = 16, handle = 0]` (5 times, once for id 8);
- `ScreenStateWinMsg::SendSyncMessage> SendNotifyMessage API failed
  [window=16][msg=6525]` (5 times).

With the stubs, HCXMemory ordinals 9–19 return `this` and these lines are
absent.

**O5 — Screen.** At `Finish Launch Threads` the screenshot shows the
London map alone, as in H10. No AUI element is drawn.

## Interpretation

- The unit NAND carries NK1, the kernel image that image A pairs with. Of
  image A's unit-flash imports, only `Cws_Apl.dll` is missing. It may be
  linked from a later firmware or from the telematics option.
- The stubs were good enough for the controls: the real modules fail the
  same 6 controls. The paint gate named in M8.C1i (SystemCC's activation
  of the `OFF` source, which waits for ACM module 6) is unchanged.
- O4 is new. The CC window with id 16 never registers its handle. Message
  `0x197d` is close to the range SystemCC maps to `NotifySysEvent`
  (`0x1983`, `0x1a44`–`0x1a58`). This is a lead for M8.C1j, not a finding
  about the gate.

## Conclusion

`firmware/unit-flash/nk1-QY7200ND.bin` is now in the repository, by the
owner's decision. `ze0_ipl.py patch --copy-dlls unitflash` runs image A
with the real `HCXLog.dll`, `HCXMemory.dll` and `AppTimerDll.dll`, so
`--stub-dlls hcx` and `--copy-dlls apptimer` are no longer needed. The UI
layer still does not paint. M8.C1j stays the next step.
