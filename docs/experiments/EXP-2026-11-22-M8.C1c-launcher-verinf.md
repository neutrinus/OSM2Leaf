## Question

With the card mounted under `-M ze0` (F3, C-6875) the EU 2011 launcher logs
`VerInf: / HddInf:QSD-302-100` with an empty `VerInf`, then
`AppLch >> Error Proc<00000050>!!` and starts `FailSafe.exe` (C-6877). Where
does `VerInf` come from, and what must the emulator provide so that the
applications start?

## Hypothesis

`VerInf` is the 11-byte record at `+0x60` of the buffer that
`KernelIoControl(0x0101302C)` returns (C-763). **Falsifier (from the task):**
the launcher reaches `Error Proc<00000050>` on a path that reads neither
`VerInf` nor `HddInf`.

## Inputs

- `AppLaunch.dll` B: map-code check `fn 0x03bd2ad8`, map-DB check
  `fn 0x03bd2ce4`, router `fn 0x03bd2ecc` (EXP-2026-11-06-M2.15).
- `nk.exe` B `.text` (uncompressed, file `0x03e01200`, VA `0x88001000`).

## Method

1. **The kernel side, static.** Search `nk.exe` `.text` for the IOCTL code
   `0x0101302C`; it occurs once, in a table of 12-byte rows
   `{code, flag, handler}` (`0x880091d8`…, 32 rows `0x01013000`–`0x0101308c`
   plus `0x010132xx`). Disassemble the handler and its helper with
   `sh4dis.py --image-start 0x3e00200 … nk.exe`; follow the globals with
   `sh4xref.py --to`.
2. **The launcher side, static.** Read the argument set-up before the
   `KernelIoControl` call in `fn 0x03bd2ad8`.
3. **The bytes.** Read `+0x60..+0x7f` of the five ROM image headers on the
   card (`0x200200`, `0x2000200`, `0x3e00200`, `0x4800200`, `0x5200200`).
4. **Runtime.** Boot `-M ze0` with the EU card (run V, defaults of
   EXP-2026-11-21-M8.C1b) and, after `Store Mgr Ready!`, dump with HMP `xp`:
   the selector `0x89e43c8c`, the region table `0x89e61a28`, the chain head
   `0x89e6a0a0`, `*0x880030a0` and phys `0x08000050..0x0800006f`.
5. **Model.** Add machine options `verinf=` and `mapdb=` (patch `ze0-0010`)
   that write the 32 bytes `+0x60..+0x7f` of the kernel image before it is
   registered as a ROM blob. Boot three times with
   `run.sh`-equivalent options (`-icount shift=0,sleep=off`, 330 s host time):
   W `verinf=QSD-302-100,mapdb=16-16`; controls X `verinf=QSD-302-101`
   (wrong code) and Y `mapdb=0-15` (window excludes the card's 16).
   Count markers with `ze0_sdhost.py serial`.

```bash
python3 tools/sh4dis.py --image-start 0x3e00200 --va 0x8804a5dc --count 24 archive/head256.img nk.exe
python3 tools/sh4dis.py --image-start 0x3e00200 --va 0x88049e28 --count 48 archive/head256.img nk.exe
python3 tools/sh4dis.py --image-start 0x3e00200 --va 0x03bd2ad8 --count 50 archive/head256.img AppLaunch.dll
python3 tools/sh4xref.py --image-start 0x3e00200 --to 0x89e61a28 archive/head256.img nk.exe
bash tools/qemu-ze0/run.sh --image archive/head256.img --sd CARD.qcow2 --icount shift=0,sleep=off \
     --verinf QSD-302-100 --mapdb 16-16 --timeout 330
python3 tools/ze0_sdhost.py serial WORK/serial.log
```

## Observations

**O1 — the IOCTL (static).** Row `0x88009208` = `{0x0101302C, 1,
fn 0x8804a5dc}`. The handler reads the input word (`r4 = *inbuf`) and, if the
output is at least 8 bytes, calls `fn 0x88049e28(index, out)`. That function
rejects `index > 32`, then calls `fn 0x88048ac0`, which returns 1 when
`*0x89e43c8c & 15 == 0`:

- result 0 (one XIP region): `out[0] = *(*0x880030a0 + 8)`,
  `out[1] = *(… + 12) - *(… + 8)`;
- result 1 (several regions): the same two words from the ROMHDR at
  `*(0x89e61a28 + 8*index + 4)`.

`*0x880030a0` holds `0x884e22f0`, image B's ROMHDR (`physfirst 0x88000000`,
`physlast 0x886e18a4`, EXP-2026-11-08-M8.B4). The table `0x89e61a28` is the
XIP chain: `fn 0x88049d64` copies the chain head `0x89e6a0a0` (written by the
kernel start `fn 0x88024444` as `{0, pTOC}`) into entry 0 and links entry 1;
`fn 0x88049dc4(2)` sets entry 1's ROMHDR from the image whose base is in
`0x89e43c94` when its `+0x40` is `ECEC`. In both paths index 0 is image B. So
the IOCTL returns `{physfirst, length}` of an XIP region; it is not a
"target-info" record.

**O2 — the launcher asks for index 0.** `fn 0x03bd2ad8` zeroes the input
word at `r15+28` (`mov #0,r12` … `mov.l r12,@(28,r15)`), passes in/out sizes
4 and 8, and copies 11 bytes from `*(r15+36) + 0x60` (`physfirst + 0x60`).
`fn 0x03bd2ce4` reads `+112`/`+114` of the same buffer (C-2083). The other
three callers of the IOCTL in `AppLaunch.dll` (`fn 0x03bd2870`,
`fn 0x03bd298c`, `fn 0x03bd39d0`) read `+32` (the image label) and loop over
the regions counted by IOCTL `0x01013034`; none writes the buffer.

**O3 — the card has zeros there.** All five ROM headers on the EU card have
32 zero bytes at `+0x60`; image B's header reads `UP10XXXX.500` at `+0x20`,
`ECEC` + pTOC at `+0x40`, `470-2759-01` at `+0x50` (C image: `PM10XXNI.021`,
`470-3142-00`). No other occurrence of `QSD-302-100` exists in the head image
except the `0x06000000` copy of `HDD_INFO.TXT` (offset 0, not `+0x60` of a
region).

**O4 — runtime (run V).** At F3: `*0x89e43c8c = 0x000000ff` (so the
one-region path), the table `0x89e61a28` is all zero, the chain head
`0x89e6a0a0 = {0, 0x884e22f0}`, `*0x880030a0 = 0x884e22f0`, phys
`0x08000050` = `470-2759-01`, phys `0x08000060..0x0800006f` = zero. The serial
log shows `VerInf: / HddInf:QSD-302-100`, `Error Proc<00000050>`,
`FailSafe.exe` (as C-6877).

**O5 — the model.** `ze0-0010` adds `verinf=STR` (≤ 15 characters at
`+0x60`) and `mapdb=LO-HI` (big-endian `u16` at `+0x70`/`+0x72`); with both
empty the image is unchanged. `run.sh` passes them as `--verinf`/`--mapdb`.
`build.sh --check-version 11.1.3`: 14 applied, 0 failed; `--selftest`
78 passed.

**O6 — what follows in run W.** No `Error Proc`, no FailSafe. The launch
thread loads its drivers (`PPP`/`AFD` LastError 126; `WaveSSI2`, `TAPI`,
`COM8`, `BTA2`–`BTA9` ActivateDevice LastError 2), the applications log
their own errors: the audio-network protocol `CInaiProtocol` retries
`WriteFile` (`Write size disagreement. (6:0)`, `failed wait response`) in a
loop that fills most of the 3 MB log, `BeepDrv : Can't open 'CEN1:'`,
`VIN: VIN_Init ERROR(0xAEEA10)`, `ACM::WaitModule Timeout ID[46]` (7×) and
`ID[48]` (2×). Whether `Navi.exe`'s own code runs is not established by this
log.

## Interpretation

- **FACT (C-6880):** IOCTL `0x0101302C` returns the start and length of XIP
  region `index` (O1).
- **FACT (C-6881):** the launcher's `VerInf` is image B's header `+0x60`
  (11 characters) and the map-DB window is `+0x70`/`+0x72` of the same header
  — RAM at phys `0x08000060`, not a NAND record (O1, O2, O4, O5).
- **OBSERVED (C-6882):** these 32 bytes are zero on the card and in the
  emulated boot; on a unit they must be non-zero for any factory card to pass,
  so they are written after the image is loaded and before the launcher runs,
  by code that is not on the card. **HYPOTHESIS:** the IPL in the unit's
  flash, the same code that loads image B (C-535/C-706). The `XXXX` in the
  label at `+0x20` may be filled the same way (C-6885).
- **FACT (C-6883, C-6884):** with the record supplied the launcher passes
  both checks and the boot continues; each control fails the check it
  targets with the expected log line.
- **Falsifier not met:** run V, X and Y reach `Error Proc` only through the
  logged `VerInf`/`MapDBVer` comparisons.

For the project this moves the unit side of `DIFFERENT MAP CODE` /
`MAP DATA BASE UNMATCH` from "a NAND record" to "what the IPL writes into
image B's header at boot". A card cannot change it (the IPL writes after it
loads the image), but an emulator or a test card's model can set it, and a
unit's values can be read from RAM at `0x88000060` with any memory dump.
For the EU 2011 card the values that pass are map code `QSD-302-100` and a
window containing 16; the real EU unit's window is still unknown (C-2087).

## Conclusion

`VerInf` comes from ROM image B's own header in RAM (`+0x60`, map code;
`+0x70`/`+0x72`, map-DB window), returned by the kernel's XIP-region IOCTL
`0x0101302C` for index 0. The card leaves it zero; a unit fills it before
the launcher runs. `-M ze0,verinf=QSD-302-100,mapdb=16-16` (`ze0-0010`)
supplies it: the launcher passes both checks and `FailSafe.exe` is no longer
started. The next failures are in the applications' I/O; the first and
loudest is the audio-network serial write (`CInaiProtocol`, `WriteFile`
6:0), which is row C2 (serial DMA).
