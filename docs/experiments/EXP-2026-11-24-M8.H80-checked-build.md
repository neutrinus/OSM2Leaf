## Question

Can a shipped checked/debug build of the ZE0 map modules be obtained that
carries a valid `DBGPARAM` zone record (module name + 16 zone names + mask VA),
so that a mask-set boot adds vendor `DEBUGMSG` lines over the 142-line baseline?

## Hypothesis

A checked build of `Navi.exe`/`NaviMapCC.dll`/`SDHC.dll` would have `DEBUGMSG`
zones compiled in, producing `DBGPARAM` records that `ce_dbgzones.py` can find
and a mask boot can enable. **Falsifier (stated before result):** no such build
is obtainable and every real image in hand scans to `dbgparam_candidates 0`
with 0 skipped sections — then there is no record and no mask to set. The
task's own falsifier ("a checked build with no `DBGPARAM` and no new boot
lines") is covered by the same negative.

| Image signature | `45434543` (ECEC) at file `0x200240` in each image (image-start `0x200200`) |

## Method

1. **Sample and hash.** `sha256sum` + `wc -c` on all four images (values above);
   ECEC signature checked at file `0x200240` to confirm the `0x200200`
   image-start is valid for each.
2. **Commands.** All run from the worktree root. `$S` is scratch
   (`$HOME/projekty/leafre-work/scratch/m8.h80`), deleted after this EXP.
   Scan with a decoded directory from `cerom.py decompress` so compressed
   `.data` sections are included rather than silently skipped:
   ```bash
   for f in archive/head256.img archive/us256.img archive/eu2014-256.img archive/eu2016-256.img; do
     echo "$f $(sha256sum "$f" | cut -d' ' -f1) $(wc -c < "$f")"; done
   python3 tools/ce_dbgzones.py --selftest
   S=$HOME/projekty/leafre-work/scratch/m8.h80; mkdir -p "$S"
   # EU2011, three builds:
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img decompress --out "$S/dec-head256"
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img decompress --out "$S/dec-head-0x3e00200"
   python3 tools/cerom.py --image-start 0x5200200 archive/head256.img decompress --out "$S/dec-head-0x5200200"
   python3 tools/ce_dbgzones.py archive/head256.img --image-start 0x200200 --decoded-dir "$S/dec-head256"
   python3 tools/ce_dbgzones.py archive/head256.img --image-start 0x3e00200 --decoded-dir "$S/dec-head-0x3e00200"
   python3 tools/ce_dbgzones.py archive/head256.img --image-start 0x5200200 --decoded-dir "$S/dec-head-0x5200200"
   # US2011 build A:
   python3 tools/cerom.py --image-start 0x200200 archive/us256.img decompress --out "$S/dec-us256"
   python3 tools/ce_dbgzones.py archive/us256.img --image-start 0x200200 --decoded-dir "$S/dec-us256"
   # EU2014 / EU2016 build A (decompressor limited, see Scope):
   python3 tools/cerom.py --image-start 0x200200 archive/eu2014-256.img decompress --out "$S/dec-eu2014-256"
   python3 tools/cerom.py --image-start 0x200200 archive/eu2016-256.img decompress --out "$S/dec-eu2016-256"
   python3 tools/ce_dbgzones.py archive/eu2014-256.img --image-start 0x200200 --decoded-dir "$S/dec-eu2014-256"
   python3 tools/ce_dbgzones.py archive/eu2016-256.img --image-start 0x200200 --decoded-dir "$S/dec-eu2016-256"
   ```
   Source search for a shipped checked build (local and web):
   ```bash
   grep -ni 'checked\|debug\|SDK\|service manual' docs/research/sources.md
   find /home/marek/projekty -type f \( -iname '*checked*' -o -iname '*dbg*.dll' \
        -o -iname '*navimapcc*' -o -iname '*.pdb' -o -iname '*sdk*' \) 2>/dev/null
   ```
   plus HTTP fetches of `https://files.viaaq.eu/` and
   `https://files.viaaq.eu/sd-images/` (map-data and full-card images only),
   the CE debug-zone blog, and web searches for a ZE0 checked/debug build.
3. **Controls.** **Positive:** `ce_dbgzones.py --selftest` prints
   `selftest: 9/9 checks passed`, including the synthetic 32-WCHAR `DBGPARAM`
   (name + 16 zones + `0x0000ffff` mask) found and decoded. **Negative
   mutation (mandatory):** a scratch copy with `_field_end()` changed to
   `return None` (field-end always rejected) fails the synthetic checks —
   `FAIL synthetic 32W DBGPARAM found`, `FAIL synthetic name decoded`,
   `selftest: 5/9 checks passed` — while the committed tool still prints
   `selftest: 9/9 checks passed`. This proves the 0-candidate result is the
   strict scanner rejecting absent records, not a scanner that always returns 0.
   The mutation stayed in scratch; the repo tool is unchanged.
4. **Scope.** Fully scanned with 0 skipped sections: EU2011 builds A (149
   modules / 527 sections), B (91 / 307), C (88 / 277), US2011 build A (151 /
   535). EU2014 and EU2016 build A: only 14 of 239 compressed sections decoded
   (`cerom.py decompress` fails with `UnmappedAccess: no mapped region covers
   0x00000000..0x00000002` for the X212 kernel); 239 of 542 sections skipped,
   so those two images are **partial** and never counted as "all sections".
   Excluded: BSS/zero-fill and IAT slots (no initialized `DBGPARAM`, C-3440),
   runtime `system.hv`, the fan-made language-conversion images mentioned on
   the forum (not fetched — a modified retail image, not a checked build).
5. **Falsifier.** One valid `DBGPARAM` record in any scanned section, or a
   source of a checked build with records, would have refuted the negative.
   Neither was observed. An EU2014/EU2016 compressed section containing a
   record could not be ruled out, so no claim is made about those skipped
   sections.

## Interpretation

- **FACT:** No valid `DBGPARAM` record exists in the fully scanned sections of
  EU2011 A/B/C and US2011 A (1,646 sections, 0 skipped), nor in the 28
  decoded sections of EU2014/EU2016 A; every census prints
  `dbgparam_candidates 0`.
- **FACT:** The scanner is not vacuous: it finds a synthetic record, and a
  mutation that breaks field-end parsing makes it fail the synthetic checks.
- **FACT:** No shipped checked/debug build of the map modules was found in the
  vendor mirror, local media or web sources searched; no symbols to build one
  from are available. The CE toolchain would compile `dpCurSettings` out of
  these retail modules, which matches the 0-candidate census.
- **HYPOTHESIS (untested):** a checked build exists inside Nissan's dealer-only
  service channel (firmware updates are distributed only there) but is not
  publicly obtainable. This task cannot obtain it without that channel.
- **UNKNOWN:** whether the 239 skipped compressed sections per X212 image hide
  a `DBGPARAM` — the decompressor fails on those kernels; and whether injecting
  a synthetic `DBGPARAM` and calling `RegisterDbgZones` in the guest would
  unlock lines (out of scope, no vendor record to base it on).

## Conclusion

The task's Stop path is taken. Every real image on this host scans to
`dbgparam_candidates 0`; the four fully scanned builds (EU2011 A/B/C, US2011
A, 1,646 sections, 0 skipped) and the partial X212 scans give no valid
`DBGPARAM`, and no checked/debug build or symbols were found in the vendor
mirror, local media or web sources searched. Therefore no module name, 16-zone
table or mask VA can be reported, `run.sh --debug-zones FILE` is not added
(nothing to set), and no mask-set boot gain can be measured. M8.H80 records a
**named blocker**: a checked/debug build of `Navi.exe`/`NaviMapCC.dll` (or
their `DBGPARAM` records/symbols) is not publicly obtainable; the named
unblocking path is a task that obtains such a build from Nissan's dealer service
channel and re-runs `ce_dbgzones.py` on it (rule 15 re-opens M8.H80 when that
task merges). M8.H15 stays blocked with `Unblock: M8.H80`.
No vendor bytes were committed; only this EXP, claim rows and the task status
change.
