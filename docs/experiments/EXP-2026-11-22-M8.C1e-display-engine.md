## Question

After M8.C1d the applications run, but the screen memory (phys
`0x0e700000`) stays zero, and `gdisubdrv.dll` drives two register blocks
that `-M ze0` did not model (C-6916). What does the display driver wait
for, and what is the smallest model that lets drawing reach the VRAM?

## Hypothesis

A register file plus the two interrupts (vblank, 2D command end) would
be enough for the UI to draw. Falsifier from the task: with both blocks
answering, the VRAM stays zero for the whole run.

## Method

Every run boots the EU 2011 card with
`-M ze0,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch=FILE`
and `-icount shift=0,sleep=off`. Every run used a fresh qcow2 overlay.

1. **Trace (run G1, 400 s).** New device `ze0-gfx`, read-back registers
   at phys `0xfff80000` (DU) and `0xffe80000` (2DG) and at their area-7
   aliases. `gfx-trace=on` logs each access with the guest PC.
2. **Interrupts.** We read the OAL interrupt table at `0x88005c48`
   (16-byte rows `{INTEVT, ISR, IntrPrio, SYSINTR}`) with `xp` and
   disassembled the two ISRs from guest memory. We also disassembled
   gdisubdrv's `InterruptInitialize` calls and `IntrThread_DU`.
3. **Vblank model (runs G2, 900 s, and G3, 2400 s).** A 60 Hz timer sets
   DSSR bit 11, and DSRCR clears it. The line is `DSSR & DIER` on INT2
   bit 0. The 2DG line is `SR & IER` on INT2 bit 12.
4. **Who runs.** We sampled the guest PC 25–30 times through
   `info registers` while the VRAM stayed zero. We mapped the PC to a
   module with `cerom.py modules` and disassembled it.
5. **SCIF 8/9 stubs (run G4).** These extend the M8.C10 SCIF stubs from
   channels 0–7 to 0–9.
6. **2DG handshake (run G6).** `SCLR = 1` after DLSAR sets SR.TRA. The
   list is not executed.
7. **FLDI fix (run G7, 2400 s).** On this board `FLDI0`/`FLDI1` load the
   single register whatever `FPSCR.PR` is.
8. **Software renderer (run G5).** The registry has
   `System\Automotive\Graphic\Engine = 1`. We forced the value read by
   gdisubdrv to 0 with one IPL-patch line: `0x083a458e 00e2`, which
   changes `mov.l @(28,r15),r2` at `0x03af558e` to `mov #0,r2`.
9. **Lists and VRAM.** We dumped the display lists with `xp` at each
   DLSAR value, and grabbed the VRAM with `ze0_screenshot.py grab`.

## Observations

**O1 — DU/2DG trace without a model (G1).** We saw 84 accesses, all of
them writes from gdisubdrv `Initialize`:

- DU block at `0x03af360a–0x03af3882`:
  - DSYSR `+0x00` = `0x200`, then `0x100`.
  - `+0x04` = `0x0700c000`, `+0x0c` = `0xcb3f`, `+0x18` = `0x76000000`.
  - Timing registers `+0x40–0x5c`: `0xb0, 0x3e0, 0x1f, 0x201, 0x41f,
    0x4e, 0x20c, 0x209`.
  - Four plane blocks at `+0x100/0x200/0x300/0x400` are cleared.
  - DIER `+0x10` = `0x800`.
- 2DG block:
  - SCLR `+0x00` = 0, SRCR `+0x08` = 7, IER `+0x0c` = 0 then 1.
  - `+0x48/0x4c/0x50` = 0.
  - `+0x54` = `0x0ff60000`, which is the VRAM end (`0x0e700000 + 0x1860000`).
  - `+0x58`/`+0x5c` = `0x280`, `+0x60` = 1, `+0x88` = `0xff`,
    `+0xc0` = `0x40000`.
- Then plane 3 (`+0x300–0x334`) is set up as 800 × 480 at
  `+0x320` = `0x0e700000`.

Nothing follows in 400 s. The serial log has `DDDDIFULL : VRAM size =
00000000`, and the GWES display driver's layer is hidden in the registry
(`DDDDIFull\IsShow = 0`, `LayerNo = 1`).

**O2 — Interrupts.** Two rows of the OAL table:

- `{0x3e0, fn 0x8803fc64, 4, 0x21}`. The ISR masks INT2 bit 0 (writes 1
  to `0xff804040`), tests DSSR (`0xfff80008`) bit 11, writes `0x800` to
  DSRCR (`+0x0c`) and returns SYSINTR 33.
- `{0x780, fn 0x8803fbcc, 4, 0x22}`. The ISR masks INT2 bit 12
  (`0x1000`), tests SR (`0xffe80004`) bit 0, writes 1 to SRCR
  (`+0x08`) and returns SYSINTR 34.

gdisubdrv calls `InterruptInitialize(33, …)` and `(34, …)`.
`IntrThread_DU` (fn `0x03af2dd0`) loops `WaitForSingleObject` → fn
`0x03af467c` → `InterruptDone(33)`.

**O3 — The vblank alone draws nothing (G2, G3).** Run G2 (900 s) had
427 DU vblank interrupts handled (DSRCR writes from `0x8803fc88`), 0 new
2DG writes, and VRAM all zero. `DrawOi.exe` and `SystemExe.exe` started
only near the end of the run (serial lines 758 and 790 of 880).

**O4 — A spinning serial driver starves the UI (G3).** 30 of 30 PC
samples were `0x0398e8a2`. That address is inside `serial_scif.dll`
(image B, vbase `0x03980000`), fn `0x0398e888`. The function loops on
`mov.w @r1,r1; tst #0x40` (SCFSR.TEND), and `r1` is SCIF channel 8's
SCFSR at `0x1fe48010`, which is unmodelled and reads 0. This is the same
loop the M8.C10 stubs fixed for channels 0–7, and it is the source of
the "30M polls a minute" noise in M8.C1d. The thread outranks the UI
threads and never blocks.

**O5 — With SCIF 8/9 stubbed, the UI submits a display list (G4).**
`SystemExe.exe` now starts within the first minutes, and the guest goes
idle (PC `0x880480bc`, 12 of 12 samples). Plane 2 is set up at
`0x0e932800` (stride `0x320`), and plane 4 at `0x0e9f2000`
(`+0x404` = `0x940`). The driver then:

1. writes DLSAR `+0x48` = `0x0e8d4c70` (pc `0x03af3e14`);
2. writes SRCR `+0x08` = 1 (pc `0x03af3e1a`);
3. writes SCLR `+0x00` = 1 (pc `0x03af3e1e`);
4. waits.

No SR.TRA comes, so nothing else is drawn.

**O6 — The software renderer path does not draw (G5).** Run G5 used the
patch line `0x083a458e 00e2`. A read-back confirmed `e200` at the patch
address. The banner is still `Display: HWR built on Jun 21 2010`, and
no 2DG list was started. The VRAM held the same 107/108/107-byte
fragments as G4 after 30 minutes. In this build `Engine = 0` does not
turn on a CPU renderer that we could see.

**O7 — With the handshake, Navi.exe dies on FLDI1 (G6).** Five lists ran
(SR.TRA set, the ISR acknowledged each one from `0x8803fbf6`). Then:

```
Exception 180 Thread=97f1c9b0 Proc=2c1d757e 'Navi.exe'
AKY=00000021 PC=0310b7c2(xgldll.dll+0x0001b7c2) RA=0310b78e(xgldll.dll+0x0001b78e)
Exception 'STATUS_ILLEGAL_INSTRUCTION' in Process 'Navi.exe' !!
```

The faulting instruction is `0xfb9d`, `fldi1 fr11`. It is preceded by
`sts fpscr,r3; or r8,r3; lds r3,fpscr` and followed by `fcnvsd`, which
needs PR = 1. QEMU's SH-4 translator raises an illegal instruction for
FLDI0/FLDI1 when PR = 1, but the firmware runs this code on the real
SH-4A.

**O8 — With FLDI fixed, the VRAM fills (G7).** There were 0 exceptions,
and 8 display lists were started and acknowledged. The first
`ze0_screenshot.py grab` after AuiApp started found three
frame-sized blocks with data:

| VRAM offset | non-zero bytes |
| --- | --- |
| `+0x0177000` | 14 296 |
| `+0x0697800` | 80 014 |
| `+0x0753000` | 54 702 |

The blocks are bitmaps and glyph strips written by the CPU. They are not
800 × 480 frames: the rows repeat with a narrower stride. The guest then
goes idle (PC `0x880480bc`, 12 of 12 samples).

**O9 — Display-list format (G4–G7, from memory at the DLSAR values).**
The words are little-endian u32. Lists end with `0x12000195 0x00000000`.
Seen so far:

| word 0 | operands | reading (hypothesis) |
| --- | --- | --- |
| `0x30000081` | `0xffffffc0` | first word of every list |
| `0x18000000` | `REG, VALUE` | write 2DG register (e.g. `0x88` = `0xff`, `0x4c` = source address `0xaeed4320`, `0x58` = source stride `0x10`) |
| `0x18000000` | `0x000100dc, V0, V1` | write 2 registers from `0xdc` (clip min / max; e.g. `0x00000000`, `0x031f01df` = 799/479 as `x | y<<16`… order unconfirmed) |
| `0x1800000b` / `0x1800000c` | `REG, VALUE` | register write with flags (`0xc0` = `0x00340004` / `0x00350000`) |
| `0x18000600` | `A, B` | three times at list start (`0x000e0100, 0x38`; `0x88, 0x64`; `0xc0, 0x58`) |
| `0x28000080` | `LEN` + data | block write from register `0x80`; `LEN` = `0x58` covers a 3 × 4 float matrix (`1.0` on the diagonal) and 8 more words; `0x208` in another list |
| `0x08000000` | — | sync / separator after each register group |
| `0xa0003000` | `0xcc, COLOR, P0, P1, P2` | filled quad, RGB565 colour (`0x0000`, `0x0c63`), three corner words `y<<16 | x` |
| `0xa8003100` | `COLOR, 0, SIZE, SIZE2, DST` | glyph / bitmap blit from the source set in `0x4c`/`0x58` (colour `0x0001` / `0x739c`, size `0x00070008`, destination `0x05090006`) |
| `0x12000091` | — | after each glyph blit |
| `0x12000011` | — | mid-list |
| `0xe0003020`, `0xd0007038`, `0x80003220` | 4–6 words | not decoded |

The fill commands draw into off-screen surfaces (clip `0x093f0360`,
`0x047f0280`, `0x021101df`). The text list (DLSAR `0x0edda2f0`) blits
glyphs from VRAM `0x0eed4320+` with stride 16.

## Interpretation

- The display path is: AUI runtime (`auirtdll.dll`, host `auiapp.exe`)
  builds 2DG display lists → gdisubdrv starts each one with
  DLSAR + SCLR → the 2DG renders into surfaces in VRAM → the DU scans
  out planes 2/3/4 from VRAM. The CPU writes only source bitmaps and
  glyphs into VRAM. Without a list interpreter, no screen pixel exists.
  This is the task's Stop case: a command-list engine, not a register
  model.
- Three blockers sat between the applications and the 2D engine:
  1. the DU vblank (needed by `IntrThread_DU`);
  2. a high-priority SCIF poll on channel 8 that starved everything
     below it;
  3. an FLDI quirk that killed Navi.exe.
  All three are fixed in `ze0-0013`.
- The software-renderer switch is not a shortcut in this build (O6).

## Conclusion

`ze0-0013` gives the DU a vblank and the 2DG its start/end handshake.
It also removes the channel-8 SCIF starvation and the FLDI trap. With
these changes the UI runs to idle, submits 2DG display lists, and
fills VRAM with source bitmaps. The screen itself stays empty until the
display lists are executed. The list format seen so far is in O9. The
falsifier is not met: the VRAM is no longer zero (O8).

## Next steps

- **M8.C1f:** a 2DG display-list interpreter in `ze0-gfx`. Start with
  register writes, sync, end, and filled quads (`0xa0003000`). Then add
  glyph/bitmap blits (`0xa8003100`) and the matrix-driven commands. Then
  compose DU planes 2/3/4 in `ze0_screenshot.py`. Check each step
  against the dumped lists (O9) and the glyph strips in VRAM (O8).
- The list builder is in the AUI renderer, not in gdisubdrv. No
  aligned literal of `0xa0003000`, `0x12000195`, `0x30000081`,
  `0x28000080` or `0x18000600` occurs in the uncompressed sections of
  images A/B/C (`cerom.py extract`; compressed `.data` not searched), so
  the words are probably assembled at run time. Its code is the specification
  source for the undecoded opcodes.
