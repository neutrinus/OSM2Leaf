# EXP-2026-11-22-M8.H19: Where `Navi.exe` keeps the last vehicle position

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** firmware heads `archive/head256.img` (EU2011 A) and
  `archive/us256.img` (US2011 A); cards
  `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` and
  `archive/sd-images/LEAF_2011-2012_US.img`
- **Tools:** `python3 3.15.0` (stdlib only); repo tools `tools/coord.py`,
  `tools/datask_l3.py`, `tools/position_store_l3.py`, `tools/sh4dis.py`,
  `tools/sh4xref.py`, `tools/cerom.py`, `tools/nk_decomp.py`,

## Question

Which persistent record supplies the start position to `Navi.exe` at boot in
the EU2011 and US2011 builds, how is it encoded and validated, and does
changing the stored word change the first map request?

## Hypothesis

Expected: a small record in the `VSram` backup area holds a packed position
word with a validity marker/checksum; the init code loads it and falls back to
a per-area default table. Falsifier (from the task): changing the stored word
in L3 does **not** change the first map request. A second falsifier added by
this experiment: a position word planted in the VSram block at any offset does
not change the RAM word after init — then the block is not the position store.

4. **Scope.** `Navi.exe` build A, EU2011 and US2011: 8 functions that load the

- `sh4xref --to`: EU `0x00d940e4` is loaded in functions
  `0x003eba78`, `0x003f6b1c`, `0x00403564`, `0x00407160`, `0x0040acb8`,
  `0x0040b5ac`, `0x0040b6b0`, `0x00415a3c`; US `0x00cc1ce4` in

  `0x004336ac`, `0x004337b0`, `0x0043d80c`. All are pdata STARTs.
- `fn_match`: 11 pairs `UNIQUE`, `0x003eba78 → 0x00414598` `DIFFERENT`

  to `0x00d940e4` on return 0, else `0xa6a1cde3`. US `0x004146ec`:
  `call 0x0042b604(buf[32])`; `0x004146fa` writes `buf[0]` to `0x00cc1ce4`
  on return 0, else `0x98d09737`.
- `sh4xref --calls 0x00403504`: `OBJDLL!OBJ_CarPos_initPrm` at `0x003d188c`,

  names the same two thunks in Vehicle.exe/Telema.exe; `OBJ_CarPos_write` is

  `REJECT return=0x9 marker=0x5`; `controls: PASS (5 cases)`.

- `position_store_l3.py pattern`: EU `position word 0x00d94280 at 0x00d940e4;

## Interpretation

- **FACT:** the RAM word and the default table VAs, the eight writer/reader VAs
  per build, the init call chain, the VSram id/size/acceptance rule and the
  four L3 tile outcomes are reproduced by the commands above.
- **FACT:** the VSram block `0x8e` is the *settings* container; a pattern
  planted anywhere in it does not become the start-position word. The
  hypothesis "the position word is stored directly in that block" is refuted.
- **OBSERVED:** the start value arrives from `OBJDLL!OBJ_CarPos_read` in the
  caller's own process. The L3 harness models this call as a stub that returns
  0 without filling its 32-byte output, so the resulting word is stale stack
  (`0x00d94280` / `0x00cc1e80`); the harness cannot yet exercise the real
  object-store value.
- **HYPOTHESIS:** the OEM restores the object-store value from the VSram
  mirror before `Navi.exe` starts; the block's `+0x330`/`+0` markers would
  then gate that restore. Not tested (needs M8.H18 flash or a QEMU boot).
- **UNKNOWN:** the driver-side checksum polynomial/bounds inside
  `commondll!CApi_GetSramVirtualAddressi` / `VSram.dll` (build B), and the
  process that repopulates the object store after a cold boot. The task's Stop
  clause ("message from another process") does not apply to the observed init
  path; the only other `OBJ_CarPos_write` importer is `NaviSetCC.dll`.

## Conclusion

`docs/firmware/position-store.md` now records the per-build VAs, word
encoding, VSram block `0x8e` layout/acceptance rule, default tables, the
negative VSram result and the L3 falsifier outcome. `tools/coord.py` gained
`position_word`/`decode_position_word`, a `position` subcommand and two
selftests (24/24). `tools/position_store_l3.py` reproduces the VSram
acceptance matrix and the pattern-fill negative control on both builds. The
task falsifier was **not** triggered: changing the word changes the first tile
on both builds. Still open: the flash-side checksum and the object-store
restore (M8.H18/M8.H20). Claims C-7160–C-7169 record the verified facts and
the two explicit unknowns.
