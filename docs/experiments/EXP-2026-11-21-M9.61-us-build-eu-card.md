## Question

The only hardware is a US unit running the US2011 `Navi.exe` (H51), while every
map-client result (mount, directory reads, record read) is EU2011. Region is a
property of the unit, not of the card (M2.7). Does the US2011 data-access task,
given the EU2011 card at a Poland position, read the card like the EU2011 build
does — or does it name the first check or table that refuses a tile outside
North America?

## Hypothesis

The US map client is the same code: its completion handlers, table keys and
read order equal the EU2011 task's, so on the EU card it asks for the same
files, positions and lengths. Region is not consulted in the tile path.

**Falsifier (set before the runs):** the US build mounts the US card but, on the
EU card, stops before the first tile read with no error-log call — then the
position/mesh table, not the file layer, is market-bound. A second falsifier:
on the US card the US build differs from the EU build (it then reads region
from the card, not from the unit).

## Method

1. **Sample and hash.** The two firmware heads and the two cards above; the
   M5.11 tile built from `tools/fixtures/m5.37-splice.osm` (EXP-2026-11-19-M5.11)
   and copied out of that card-ladder tree.
2. **Per-build VA table.** `tools/datask_l3.py` gains `DA_US2011` next to
   `DA_EU2011` (and `SDL_US2011` next to `SDL_EU2011`). Every US function is the
   `fn_match` pair of the EU function (`fn_match.py match`, content hash, no
   fitted delta) and is a `.pdata` START in the US image; the five `leaves` are
   `.pdata` GAP functions. Table VAs were read from the US image and hold the
   same keys in the same order (handlers differ). Data cells are the pool value
   at the same load index of the paired `init` function. The EU→US shift is
   per-handler (`+0x28100` for most, also `+0x28960`, `+0x27dd0`, `+0x28b20`,
   `+0x28ca4`, `+0x289a0`), so one delta fails.
3. **Stop gate.** `datask_l3.py port` runs the EU mount + the request, hooks
   every EU `.pdata` START to record entry, and asks `fn_match` for the US pair
   of each entered EU function (content hash, then the ANCHOR pass); it prints
   the verdict census and exits 1 below 90 %.
4. **Runs** (each: a full `datask_l3.py mount`, then optionally one request;
   the card is read in place, the generated tile by `--replace` overlay):
   - 1: US build, US card, 37.77,−122.42 (positive control, factory pair);
   - 1c: EU build, US card, 37.77,−122.42 (EU control of run 1);
   - 2: US build, EU card, 51.70,17.45;
   - 2c: EU build, EU card, 51.70,17.45 (EU control of run 2);
   - 3: US build, EU card + M5.11 tile, 51.70,17.45;
   - 3c: EU build, same card and tile (EU control of run 3);
   - 3b: US build, same card and tile, 51.10,16.93 (the position the M5.11
     tile's roads were spliced into, dir (76,940)); 3bc: EU build, same;
   - 4: US build, EU card, 51.70,17.45, `--request 0xa6cdd6be`;
   - P: US build, US card, 51.70,17.45 (position control: same card, EU position);
   - N1: US build, EU card, wrong record code `--request 0x26c18ab2`;
   - N4: run 3 with `--request 0xa6cdd6be --flip
     MAPAL001/B48R058R.DAT@0xa1b6000:0xff` (a byte inside our compressed
     record block);
   - N2/N3: wrong image for `--build`, wrong `--build` for the image.
5. **Compare.** `datask_l3.py diff` compares read for read (file, position,
   length, status, who parsed the buffer). The handler VAs and reader VAs differ
   by build, so a raw `diff` of a US run against an EU run is expected to end
   `DIFFERENT` on every parsed read; the build-independent keys are compared
   separately (the table below).

## Interpretation

- **FACT:** The US2011 data-access task runs on the EU2011 card at a Poland
  position, mounts it (state 2, progress 1, 46 tile files, map version `0x802`)
  and issues 28 reads in exactly the file/tag/position/length order the EU2011
  build does.
- **FACT:** The same holds on the US card (32 reads, 113 tile files, both
  builds identical read for read), on the EU card with the M5.11 generated
  tile (29 reads, the request reads our record at `0xa1b5f00`, inflates it, and
  answers `sub 3`), and at the tile's own position 51.10,16.93 (28 reads, the
  US build walks the directories the splice changed, identically to the EU
  build).
- **FACT:** Damaging the compressed record to `sub 9` on the US build (N4)
  shows the US request path inflates and validates the record, not just reads
  it.
- **OBSERVED:** `datask_l3.py diff` of a US run against its EU control prints
  `DIFFERENT`, but only because handler and reader VAs differ by build; the
  build-independent read keys are 100 % equal.
- **OBSERVED:** 236 of 236 entered EU functions have a UNIQUE or ANCHOR US pair
  (Stop gate 100 %, above the 90 % gate).
- **HYPOTHESIS:** Region is read by the launcher's map-code check (M2.5/M2.15),
  not by the tile/map client; this run cannot see the launcher.
- **UNKNOWN:** whether the US build's downstream consumers (renderer, router,
  `REFER` name index) also accept the EU card's data; this run covers the
  data-access task and the read-completion handlers only.

The falsifier did not fire: the US build does not stop before the first tile
read on the EU card, and on the US card the two builds read identically — so
the map client is not market-bound.

## Conclusion

`tools/datask_l3.py` now takes `--build us2011` from a per-build VA table next
to `build_targets.py`, derived by `fn_match` and confirmed by `.pdata`, plus a
`port` subcommand that *is* the Stop gate (run the EU mount, pair every entered
EU function, exit 1 below 90 %); the `--selftest` covers the build switch (both
builds' dicts share keys, no US VA equals the EU one, US done table 20 classes
with the US role handlers, a live US run on the EU card: same 28 reads, state 2,
version `0x802`, request `0xa6cdd6be` → tag `0x0900`/handler `0x0042cfe4`/sub 5
then 3, `0x26c18ab2` → sub 9) and the census. In L3 the US build reads the EU
2011 card's Poland position exactly as the EU build does, mounts it, and serves
a record request from the M5.11 generated tile; the read path is not
market-bound. `reader-coverage.md` rows 17, 18, 19, 20 and 10 gain the sentence
that their L3 verdict now holds on US2011. Still open: the launcher's map-code
check (M2.5/M2.15), routing, and the renderer (M9.58).
