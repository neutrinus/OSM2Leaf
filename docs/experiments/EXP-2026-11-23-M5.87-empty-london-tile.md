# EXP-2026-11-23-M5.87 — Z2: an empty London tile — what disappears from the screen

- **Status:** done
- **Date:** 2026-11-23
- **Sample:** EU 2011 card `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`; factory tile `B48R068R.DAT`
  `76aa5246…d3e60e`; `archive/head256.img` `92aa525d…a007f9`.
- **Tools:** Python 3.13, `tools/tile_relayout.py empty` (new sub-command),
  `tools/s1_wide_dir.py`, `tools/section4_wide.py`, `tools/dir_read_len.py`,
  `tools/rebuild_manifests.py`, `tools/imgpatch.py`, `tools/cardcheck.py`,
  `tools/datask_l3.py`, QEMU 11.1.3 `-M ze0`, `tools/ze0_screenshot.py`.
- **Claims:** C-8670–C-8674 (C-8675–C-8679 reserved)
- **Supersedes:** none
- **Superseded by:** none

## Question

Rung Z2: does the firmware accept a London tile whose container (section
tables, all 191 directories) is written by our tool and which holds **no
record at all**, and which items of the London start screen come from this
tile?

## Hypothesis

The mount reads the same directories and finds every slot empty; the screen
loses what this tile carries. Falsifier for "accepted": a boot that stops, a
new error line, or a mount read past the end. M8.H71 left place labels
(SOHO, PICCADILLY CIRCUS) unchanged after rewriting road records, which
suggested they come from another file; if they stay on the empty-tile screen,
they do.

## Inputs

As in M5.85; London start position 51.5098 N, 0.1342 W.

## Method

1. **Sample and hash.** See the Sample bullet above.
2. **Commands.**

   ```bash
   python3 tools/tile_relayout.py empty $FAC/MAPAL001/B48R068R.DAT -o $W/z2/B48R068R.DAT --pad
   python3 tools/s1_wide_dir.py census $W/z2/B48R068R.DAT
   python3 tools/section4_wide.py census $W/z2/B48R068R.DAT
   python3 tools/dir_read_len.py predict $W/z2/B48R068R.DAT
   cp -al $FAC $W/z2/tree   # then replace MAPAL001/B48R068R.DAT, DRSTR001.DAT, MMAIN001.DAT with real copies, new tile in
   python3 tools/rebuild_manifests.py --root $W/z2/tree --fast
   python3 tools/imgpatch.py --image $W/img/eu2011.img --file MAPAL001/B48R068R.DAT --from $W/z2/B48R068R.DAT --allow-resize -o $W/z2/z2.img
   python3 tools/imgpatch.py --image $W/z2/z2.img --file DRSTR001.DAT --from $W/z2/tree/DRSTR001.DAT
   python3 tools/cardcheck.py --image $W/z2/z2.img
   python3 tools/datask_l3.py mount archive/head256.img --card-image $W/z2/z2.img --position 51.5098,-0.1342 --json $W/z2/l3.json
   python3 tools/datask_l3.py diff $W/z1/l3-fac.json $W/z2/l3.json
   # L4 as in EXP-2026-11-23-M5.85 (run.sh, screenshot after `Pow Off 1st Detect`)
   ```

3. **Controls.**
   records is pixel-identical to the factory (C-8762), so the container
   writer itself is not what changes the screen. Negative: the first
   empty-tile attempt wrote `0xffffffff` empty pairs in level-1 rows; the
   census then read 64 of 68 directories as wide (`kind_rule_ok=4`, FAIL) —
   bit 31 marks a wide row (M5.53). The factory's empty level-1 pair is
   `0x7fffffff` (20,168 columns), level 2 `0xffffffff` (882), section 2 an
   all-`0xff` body (70 slots); the tool now writes those. A first
   `cardcheck` also failed (`//MAPAL001: DRSTR size 3521119232 != actual
   3258829568`) until DRSTR001 was rebuilt from the tree, so the L1 gate is
   live.
4. **Scope.**
5. **Falsifier.**

## Observations

**O1 — the tile.** `empty: tables=3 dirs=191 records=0 size=2226688 B`,
SHA-256 `2394350fad54e4c3c713bc221f642c8446cb5e7417de726873adac8512e3835d`
(padded so every directory read is backed: `directories read past the end of
the file: 0`). `s1-wide census: dirs=68 … records=0 … OK`, `s4-wide census:
dirs=55 … records=0 … OK`.

**O2 — L1.** `rebuild_manifests`: DRSTR001 changed, MMAIN001 unchanged (`count_fields_changed:
0`). Card SHA-256
`f832787c4d27d257149bbceef52fdd2128ba49ae6b93d9ffb400b2de3b0aa29f`.
`cardcheck --image`: `RESULT: PASS`.

DRSTR001 SHA-256: `f779afc8a984171d59280f4a11314eff8192c0c50738e4d8f252a1a9c4e6abc8`.

**O3 — L3.** `reads 28`, `tile reads parsed by the firmware: 18` (as
factory). `diff` vs factory: 7 reads of `B48R068R` at other positions with the
same tags and lengths (5 directories and the section-2/section-4 tables,
which moved in the 2.2 MB file); no read fails.

**O4 — L4.** Boot reaches `Pow Off 1st Detect` at 15 s. The serial log has
the same 1,043 error/fail lines as the factory run (no new line, none
missing). Both screenshots (5 s apart) SHA-256
`8ef5ee6280cf09e16a777efc610e0362f270e14266f0fe03c470e6eb70e29be2`:
**126 non-black pixels** — a black screen with a thin outline near the
centre (the vehicle-position mark). Against the factory screen (384,000
non-black): gone are the land fill, the park and river fills, every road,
every street label (`AIR STREET`, `KING STREET`, `RICHMOND MEWS`), every
shield (`A4`, `A400`, `A401`, `A3201`) and every place label (`SOHO`,
`PICCADILLY CIRCUS`, `LEICESTER SQUARE`, `TROCADERO CENTRE`).

## Interpretation

- **FACT:** an all-empty London tile written by our container code is
  accepted: L1 passes, L3 mounts it with the same 28 reads, L4 boots to the
  map screen with no new error. The falsifier did not fire.
- **FACT:** at the level-1 start screen **everything visible except the
  position mark comes from `B48R068R`**: background (land, water, parks),
  roads, street labels, shields and place labels. No other card file draws
  anything there. So the place labels that survived M8.H71 came from the
  tile's records that M8.H71 did not rewrite (odd background records /
  section 4), not from another file — Z4/Z5/Z6 must write them.
- **HYPOTHESIS:** the place labels are the background records' point-label
  anchors (`0x..0c`) with their names, not section 4 (section 4 is not read
  by the located MAP_DATA path, C-875). Test: Z4 with point labels written,
  section 4 left empty.
- **UNKNOWN:** whether the router or search notices the empty tile (no route
  was asked).

## Conclusion

Z2 passed: the from-zero container (tables + 191 empty directories, 2.2 MB)
is a valid tile for the real `Navi.exe`, and the empty screen sets the
baseline for Z3–Z6: every pixel they add is ours. Screenshot given to Marek
(vendor-free: nothing of the factory map is visible).
