## Question

What is a section-1 **level-2** directory's parcel grid — the same 32 × 32 parcels over a
4 × 4-mesh `4° × 8/3°` box that `clarion_bg.parcel_geo(2, …)` walks, or the 8 × 8 over a
1 × 1-mesh box that `parcel_census.directory_bbox(2, …)` and `tilewriter.parcel_of(…, 2)`
produced — and does a factory-backed splice of real OSM geometry into one level-2
directory complete and pass the gates while changing only that directory?

## Hypothesis

Only `clarion_bg.parcel_geo` is right: the level-2 directory is 4 × 4 meshes and is
filled by the full 32 × 32 parcel set (`clarion_bg.LEVELS[2]` has `rows = cols = 32`), so
`directory_bbox` and `parcel_of` are wrong at level 2. `parcel_census --selftest` only
asserts the level-1 span, so the 4× disagreement was never caught. **Falsifier:** the
factory tile's level-2 directory declares (in its level-table box) or fills (by its
parcel codes) a 1 × 1-mesh, 8 × 8-parcel grid, i.e. the old 1° × 2/3° box is correct and
`parcel_geo` is the wrong one. For the run: a section other than 1 changes, a second
directory changes, or a level-2 record does not decode back at the grid the census
prints.

### 6. A dense level-2 parcel overflows the record (found, out of scope to fix)

With **all** roads of a level-2 parcel written (no class filter), a single dense parcel
exceeds the road record's 16-bit word count. `--osm-bbox 16.90,51.05,17.15,51.20`
(309,302 in-directory nodes) makes `mesh_split` succeed and `tilewriter` fail while
packing the record (the pipeline's stored stderr is truncated to 400 B in `dense.json`;
the untruncated traceback is `dense-tilewriter.stderr` beside it):

```text
File ".../tools/ze0-viewer/tools_ze0/fa_encode.py", line 186, in build_record
    plain = struct.pack('>22H', *w) + struct.pack('>%dH' % len(unit), *unit)
struct.error: 'H' format requires 0 <= number <= 65535
```

The two offending parcels measured by `build_road_record` are `(76,940,5,8)` and
`(76,940,5,7)`; in the same window `(76,940,4,8)` is 130,600 plain words and
`(76,940,4,7)` 68,258, so the overflow starts when one parcel holds roughly 65,000
record words of shape geometry. Level-1 parcels are 4 × 4 times smaller in area, which is
why M5.34 did not hit it. The pipeline copied the factory root before `tilewriter` ran, so
`dense-out` is a partial tree — a `tilewriter` failure leaves one, unlike the guard
refusal in §5.

## Interpretation

- **FACT:** the level-2 directory is a **4 × 4-mesh** box filled by a **32 × 32** parcel
  grid of `1/8° × (2/3)/8°` parcels. The factory tile states the box (level-table entry,
  4 meshes) and fills the grid (every **filled** pair slot carries `parcel_code(2, 76*8+row,
  940*8+col)`). `clarion_bg.parcel_geo` is correct; `directory_bbox` and `parcel_of` were
  wrong at level 2 (1/4-size box, and an 8-column clamp).
- **FACT:** routing a real OSM window into one level-2 directory of `B48R058R` completes
  under stock zlib 1.3.2: `tilewriter`, `rebuild_manifests`, `cardcheck` and the targeted
  `l2check` (`tiles=1`, `tile_checked=True`) all exit 0; `changed_sections=[1]`, exactly
  one level-2 directory `(76,940)` changed, and the tile grows 138,994 B.
- **FACT:** every written level-2 record decodes at the census grid (the
  `fa_encode.parse_record` scan: 1,022 filled records, 0 code mismatches, 0 vertices
  outside a parcel bbox; the out tile has 205,496 vertices vs the factory's 204,941), so
  the splice is not merely self-consistent — an independent scan places each record's
  parcel code and geometry where `parcel_geo` says.
- **FACT:** a node that leaves the chosen level-2 directory is refused with the sibling
  directory's kind named, before any tree copy or tile write (exit 2, no `--out`).
- **FACT:** `prove_tile_change` compares every section-1 directory at every level and
  attributes a level-1 change during a level-2 splice, so `only_parcel_directory_changed`
  is False and the gate FAILs (the round-1 level filter made that falsifier unfalsifiable;
  fixed in round 2 with a selftest that changes both levels).
- **OBSERVED:** `one_tile_pipeline.py` gained `--level` (passed to `tilewriter`, the
  directory box, `guard_parcel` and `prove_tile_change`), not a second pipeline.
- **OBSERVED:** writing *all* roads of a dense level-2 parcel overflows `fa_encode`'s
  record word limit; the sparse window above is a real but small corner of the directory.
- **UNKNOWN:** whether the unit reads a level-2 splice (rule 13); the road-class filter
  that keeps a level-2 record under the word limit (M5.3/M4.2); whether the level-2
  directory should carry only major roads (it does in factory data, but the class
  mapping is provisional).

## Conclusion

The 4× grid disagreement is resolved in favour of `clarion_bg.parcel_geo`: a level-2
directory spans 4 × 4 meshes and holds a full 32 × 32 parcel grid, proven from the
factory tile's own level-table box and parcel codes. `parcel_census.directory_bbox` and
`tilewriter.parcel_of` are fixed and their selftests now assert the level-2 span
(`parcel_census`) and the full 32 × 32 grid (`tilewriter`), both red on the old values.
One level-2 directory of `B48R058R` then takes a real OSM window through the whole
pipeline: all gates PASS, only section 1 and only directory `(76,940)` change, and every
written record decodes at the census grid. `docs/format/map-tiles.md` records the
level-2 grid. Open: the dense-parcel word overflow and the class filter that would bound
it, and rule-13 firmware acceptance.

## Corrections after navigator review

- **R1 (blocking): the cross-level falsifier was unfalsifiable.** `prove_tile_change`
  filtered the byte-slice set to the target `level`, so a level-1 directory change during

## Follow-ups

- **Dense-parcel word overflow.** A level-2 parcel written with all roads can exceed
  `fa_encode`'s 65,535-word record limit (`struct.error` at `fa_encode.py:186`). The
  fix belongs with the road-class filter (M5.3/M4.2): a level-2 directory should carry
  only the classes factory level-2 records carry, which also bounds the record size.
  Until then a level-2 run needs a sparse `--osm-bbox` (as here). Candidate new task.
- **`tilewriter` failure leaves a partial `--out`.** The pipeline copies the factory root
  before `tilewriter` runs; a `tilewriter` crash (as above) leaves a partial tree at
  `--out` (the guard refusal does not). A `tilewriter` failure should remove or not
  create the tree, or the copy should follow a successful build. Candidate new task.
- **Rule 13 unchanged.** `mapping=provisional-v0`; no L3/L4/L5 run has read this tile.
