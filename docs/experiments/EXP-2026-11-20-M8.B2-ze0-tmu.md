## Question

At what rate must the `ze0` TMU count so that the kernel's `CurMSec`
advances in step with time, and does it advance at all?

## Done-when (made concrete before the runs, commit `b0f6260`)

The TODO line "Done when `CurMSec` advances" was vague, so the block
now says: on `-M ze0 -kernel archive/head256.img`, EU2011 `CurMSec`
(`0x89e41888`), sampled over HMP, makes a jump of at least 1000 ms, and
`ze0_tmu.py rate` puts (CurMSec delta / 1000) per host second within
[0.98, 1.02]. Negative controls: with `-M ze0,tmu=off` `CurMSec` makes no
such jump, and the old 60 MHz clock gives a ratio outside the band. Also,
two `-icount` boots give the same exception sequence, interrupts included.
(The history's "and `OEMIdle` wakes" is not testable yet: the kernel
reaches its `Halting system` loop before it goes idle; see below.)

## Hypothesis

The OAL's timer descriptor names the TMU count rate. With TCR0 = `0x0021`
(TPSC = 1, Pφ/16) the model needs Pφ = 16 × that rate. **Falsifier:**
with that clock, the ratio falls outside [0.98, 1.02], or `CurMSec` does
not jump.

## Observations

### Static

- Timer descriptor at `0x88004cf8`: `0x00280de8` (2 625 000) and, at
  `0x88004d00`, `0xffd80000`. The TMU base reaches the code only through
  this descriptor (`[0x89e6cacc]` = base + 8).
- `fn 0x8803d060`: counts/ms = descriptor / 1000 (`dmulu` by `0x10624dd3`,
  `shad -6`) → `0x89e6cad8`; max period = `0x7fffffff / counts/ms − 1`
  (`0x88042594`) → `0x89e6cac4`; target = `CurMSec` + max period →
  `0x89e6cae4`; TCOR/TCNT = max period × counts/ms → `0x8803c9d0`.
- TMU0 ISR `fn 0x8803cb34`: bumps a 64-bit tick count, clears TCR0.UNF,
  stores the target `[0x89e6cae4]` into `CurMSec` (`0x8803cbf0`), adds the
  next period (≤ max period) to the target and reloads TCNT through
  `0x8803c948`.
- `CurMSec` is loaded in 23 functions (`sh4xref --to 0x89e41888`); the ISR is
  the only store seen in this run.
- `0xffd81000` (TMU ch3–5) has no literal pool in executable sections; its
  one occurrence (`0x88453ea4`) is data. No run touched it.
- HMP at run time: counts/ms `0x00000a41` (2625), max period `0x000c7ba8`
  (818 088 ms), TCOR0 `0x7ffff5a8` = 818 088 × 2625.
- The kernel ends its boot in `0x88022164`: `jsr 0x8802aa78` with
  `"Halting system\r\n"` (`0x88002bd4`), then `bra 0x88022170` to itself. It is
  entered once, with PR `0x88011ce2` (`jsr @[0x89e42b14]` in the
  exception path). So the kernel is halted, not idle, and only the
  max-period TMU0 interrupt moves `CurMSec` after that.

### Sampled runs (`ze0_tmu.py rate`)

```text
on42.csv   (42 MHz, 900 s)
  TMU0 TCNT0 rate: 2624999 counts per host second (OAL assumes 2625000)
  CurMSec 0x0 (from 0.5 s) -> 0x105 at 2.0 s: +261 ms   (small, ignored; boot-time interrupts)
  CurMSec 0x105 (from 2.0 s) -> 0xc7cad at 820.0 s: +818088 ms in 818.0 s, ratio 1.0001 [0.9976..1.0026]
old60.csv  (60 MHz, 660 s)
  TMU0 TCNT0 rate: 3750002 counts per host second
  CurMSec 0x1e4 (from 2.0 s) -> 0xc7d8c at 574.1 s: +818088 ms in 572.0 s, ratio 1.4301 [1.4249..1.4353]
off.csv    (tmu=off, 60 s): CurMSec first 0x0 last 0x0 — no jump (rc 3)
on42-60.csv (42 MHz, 60 s): CurMSec 0x0 -> 0x70, then flat; no jump >= 1000 ms within 60 s (rc 3)
```

Each jump is exactly the max period (818 088 ms = `0xc7ba8`). `-d int`:
3 × `0x400` in `on42`, 4 in `old60`. With `tmu=off` the TMU accesses go to the
P4 catch-all (`ze0-p4` offsets `0x580004`–`0x58001c`: 213 reads, 8
writes), the boot has no `0x400`, and the other exceptions are unchanged
(`0x040` ×26, `0x060` ×1, `0x180` ×3).

## Interpretation

- **FACT (C-1320):** the EU2011 OAL assumes a TMU0 count rate of 2 625 000 Hz
  (descriptor `0x88004cf8`), so counts/ms is 2625 and the max period
  818 088 ms (TCOR0 `0x7ffff5a8`). With TCR0 TPSC = 1 (Pφ/16) the TMU input
  clock is Pφ = 42 MHz; `ze0-0005` sets it (was 60 MHz).
- **FACT (C-1321):** with `ze0-0005` `CurMSec` advances: it jumps by the
  max period after 818.0 host seconds, a ratio of 1.0001
  ([0.9976, 1.0026] from the 2 s sampling), and TCNT0 falls at
  2 624 999 /s. With the old 60 MHz clock the same jump comes at 572 s
  (ratio 1.43): `CurMSec` ran 43 % fast. Done-when met, and the falsifier
  was able to fire.
- **OBSERVED (C-1322):** with `-M ze0,tmu=off` `CurMSec` stays 0, so the TMU
  is the only thing that advances it. TMU ch3–5 at `0xffd81000` are not
  used by `nk.exe` and stay unmodelled.
- **OBSERVED (C-1323):** after boot the kernel sits in its `Halting system`
  loop (`0x88022170`, entered from `0x88011ce2` in the exception path). So
  `CurMSec` moves only once per 818 s, and `OEMIdle` is never reached.
  Under `-icount shift=0,sleep=off` two boots give the same exception
  sequence, including the timer interrupt (count 1, pc `0x88022170`),
  which the real-time runs did not (1–4).
- **UNKNOWN:** the real Pφ of the board (42 MHz is what the OAL implies,
  not a measurement); why the kernel halts (an M8.B5 / exception-path
  question).

## Conclusion

M8.B2 is done: the TMU model now counts at the rate the OAL assumes, and
`CurMSec` advances at 1.000 × real time (positive), not at all without the
TMU (negative 1), and 1.43× with the old clock (negative 2). `-icount
shift=0,sleep=off` makes whole boots repeatable, timer interrupt included.
