## Question

Does the current `-M ze0` model give the guest a second SD slot on port 1 when
a card is supplied, so the firmware mounts a second volume (`DSK8:`,
`\UserSD`) without touching the map card, and is the boot unchanged when no
second card is given?

## Hypothesis

The SD host model already has port 1 at `0xffe4d000` and the HPB-DMAC already
wires channel 9 to it (row C10 / M8.C1b). Adding only a `-drive if=sd,index=1`
ought to make the guest assert card-detect, enumerate the card and mount
`DSK8:`. The falsifier from the task: the guest never issues a command on port
1 even with card-detect asserted (then the gap is in the driver or the model,
not in run.sh).

## Method

### 1. Sample and hash

The two real samples and their SHA-256 are in the header; `user16.img` is a
generated 16 MiB FAT16 volume (`mkfs.vfat -F 16 -n USERSD`). The port-0 card
is read only through an 8 GiB qcow2 overlay, so the factory image is never
written. The firmware head supplies CE image B (kernel) at file `0x3e00200` and
image A (applications) at `0x200200`.

### 2. Commands

Run from the worktree root with `$W` the scratch directory and `$QEMU` the
patched QEMU:

```bash
W=$HOME/projekty/leafre-work/scratch/m8.h17
QEMU=$HOME/.cache/qemu-ze0/build/qemu-system-sh4

# prepare the generated, vendor-free artifacts
python3 tools/ze0_ipl.py patch archive/head256.img -o "$W/ipl.txt"
python3 tools/qemu-ze0/mkoverlay.py \
  archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$W/eu2011.qcow2"
truncate -s 16777216 "$W/user16.img"
mkfs.vfat -F 16 -n USERSD "$W/user16.img"
sha256sum "$W/user16.img"

# run.sh --sd2 builds the port-1 drive; baseline omits it (both boots 120 s)
bash tools/qemu-ze0/run.sh --qemu "$QEMU" --machine ze0 \
  --image archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
  --ipl-patch "$W/ipl.txt" --sd "$W/eu2011.qcow2" \
  --sd2 "$W/user16.img" --icount shift=0,sleep=off --timeout 120 \
  --workdir "$W/run-sd2"

# the trace boots: direct QEMU argv (same as run.sh, plus trace options and
# -d unimp only so the log stays small); baseline omits the second -drive
$QEMU -M "ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch=$W/ipl.txt,sdhi-trace=on,hpbdmac-trace=on" \
  -kernel archive/head256.img -nographic \
  -monitor "unix:$W/card/hmp.sock,server,nowait" \
  -serial "file:$W/card/serial.log" -icount shift=0,sleep=off \
  -drive "if=sd,index=0,file=$W/eu2011.qcow2" \
  -drive "if=sd,index=1,file=$W/user16.img" \
  -d unimp -D "$W/card/qemu.log"              # 120 s, then TERM
# logs: "$W/base/qemu.log"/serial.log (no --sd2) and "$W/card/qemu.log"/serial.log
python3 tools/ze0_sdhost.py ports "$W/base/qemu.log"
python3 tools/ze0_sdhost.py ports "$W/card/qemu.log"
python3 tools/ze0_sdhost.py sdtrace "$W/card/qemu.log"
python3 tools/ze0_sdhost.py serial "$W/base/serial.log"
python3 tools/ze0_sdhost.py serial "$W/card/serial.log"
python3 tools/ze0_sdhost.py dmatrace "$W/card/qemu.log"
python3 tools/ze0_sdhost.py dmatrace "$W/card/qemu.log" --card "$W/user16.img"
python3 tools/ze0_sdhost.py --selftest
```

`run.sh --dry-run` shows the exact QEMU argv; with no `--sd2` it is byte-for-byte
the baseline command, with `--sd2` it adds one
`-drive if=sd,index=1,file=…`.

### 3. Controls

- **Positive:** the existing port 0 (`--sd`) always enumerates its card: 877
  `SD_CMD` writes, card-detect reads of `SD_INFO1 = 0x00a1` (bit 5 set),
  422 HPB-DMAC channel-8 transfers, and `Store Mgr Ready! [DSK1:]` in the
  serial log (both boots). This proves the trace and card-detect decoding work.
- **Negative:** the baseline boot without `--sd2` has 0 port-1 `SD_CMD`
  writes and its single port-1 `SD_INFO1` read returns `0x0000` (bit 5 clear,
  no card). The serial log has 0 `EVT_SD_MOUNT`, 0 `DSK8:`-attached, 0
  `SdMountPartition()` and 0 `SYS_NOTIFY_USER_SD_CARD_MOUNT` lines. A selftest
  case asserts these second-slot markers are absent from a system-SD-only
  line, and a `ports` selftest case asserts `cd_seen == False` for
  `SD_INFO1 = 0x0000`.
- **Negative (tool):** `run.sh --sd2 MISSING` fails with
  `no such --sd2 image: …` and exit 1 (observed). A second selftest case
  mutates the port-1 `SD_INFO1` line from `0x0000` to `0x00a0` and expects
  `cd_seen == True`, so the card-present verdict can fail.

### 4. Scope

Two boots of the EU 2011 card on the patched QEMU, 90 s (baseline) and 120 s
(with `--sd2`), both with `sdhi-trace=on,hpbdmac-trace=on -d unimp`. Logs:
baseline `qemu.log` 1,237,257 B / `serial.log` 120,912 B; card `qemu.log`
1,286,754 B / `serial.log` 122,585 B. No US/2014/2016 card, no L5/unit, no
write-back test to the port-1 card (the card is read-only in this run), and no
change to the QEMU patch series — the device model already existed. Only
`tools/qemu-ze0/run.sh` (a new option) and `tools/ze0_sdhost.py` (new reporting)
changed. The firmware's `\UserSD` file-layer reader is not exercised beyond
the mount (no user file seeded for Navi.exe to open).

### 5. Falsifier

Per the task: if the guest issued no command on port 1 even with card-detect
asserted, the hypothesis is false. Also refuting: no `DSK8:` mount line in the
serial log with `--sd2`, or any port-1 activity / `DSK8:` line in the baseline
without it, or a `run.sh --sd2` command line that does not add an SD drive on
port 1.

## Observations

**O1 — Baseline (no `--sd2`).** `python3 tools/ze0_sdhost.py ports base.log`:

```
port 0: 877 commands, card-detect reads 2605, last SD_INFO1 0x00a1, card present
port 1: 0 commands, card-detect reads 1, last SD_INFO1 0x0000, card absent
```

The single port-1 `SD_INFO1` read returns `0x0000` (bit 5 clear). The serial log
has `sys_mount_event 1` and `user_mount_event 0`, `dsk8_attached 0`,
`user_part_mount 0`, `user_sd_notify 0`.

**O2 — With `--sd2 user16.img`.** `ports card.log`:

```
port 0: 877 commands, card-detect reads 2605, last SD_INFO1 0x00a1, card present
port 1: 49 commands, card-detect reads 125, last SD_INFO1 0x00a1, card present
```

Port-1 `SD_INFO1` reads now return `0x00a0`/`0x00a1` (bit 5 set).

**O3 — Port-1 command sequence.** `sdtrace card.log` for port 1:

```
CMD0 CMD8 CMD55 ACMD41 CMD55 ACMD41 CMD2 CMD3 CMD13 CMD9 CMD10 CMD7 CMD13
CMD55 ACMD6 CMD16 CMD55 ACMD42 CMD55 ACMD13+data CMD13 CMD55 ACMD51+data
CMD13 CMD6+data CMD13 CMD6+data CMD13 CMD6+data CMD13 CMD7 CMD13 CMD9 CMD7
CMD13 CMD17+data CMD13 CMD17+data ... (49 commands total)
```

This is a full SD-card enumeration, capacity/CSD/CID read, bus-width and
block-length setup, three CMD6 switch sequences and seven single-block CMD17
data reads. No `no-response` and no `DMA-mode requested` lines on port 1.

**O4 — `\UserSD` mount.** `serial card.log` second-slot markers:

```
user_mount_event 1     # ###SDHC(Port=1)-->Stub_SetEvent[EVT_SD_MOUNT]
dsk8_attached    1     # Detect DSK8: is Attached.
user_part_mount  1     # CMemoryCardStatus::SdMountPartition() Start/End
user_sd_notify   9     # SYS_NOTIFY_USER_SD_CARD_MOUNT to 9 processes
```

The serial lines are 494 (`EVT_SD_MOUNT`), 877 (`Detect DSK8: is Attached.`),
878 (`Mount Execute.`), 879–880 (`SdMountPartition() Start`/`End`) and
881–889 (`SYS_NOTIFY_USER_SD_CARD_MOUNT` to RADIO, NAVI_IOMCD, NAVI,
NAVI_LOC, NAVI_USERDATA_CC, SPEECH, SDMNG, TLM and SYSTEM). The baseline has
none of these lines; its only mount thread lines are for `DSK1:`.

**O5 — DMA channel.** `dmatrace card.log` reports 434 transfers / 5,391,888 B:
port 0 uses channel 8 (422 lines), port 1 uses channel 9 (12 lines: 1×ACMD13
64 B, 1×ACMD51 8 B, 7×CMD17 3584 B, 3×CMD6 192 B). The Stop condition
("port 1 uses a DMA channel the model lacks") does not fire: channel 9 is
wired in ze0-0009.

**O6 — Card bytes.** `dmatrace card.log --card user16.img` compares 424 block
reads against one image (420 mismatch, expected: it also compares port 0's
map-card reads). A port-1-only check shows the first four reads — boot sector
at block 0 (crc32 `0x883ce2c2`) and FSInfo at block 1 (`0xb2aa7578`), each
read twice — match the file byte-for-byte; the later reads at blocks
`0x800`, `0x4800`, `0x8800` are FSInfo/backup copies for which QEMU's sd-card
returns its own layout, not the raw file bytes. The driver's first reads do
carry the generated FAT image.

**O7 — Tool checks.** `python3 tools/ze0_sdhost.py --selftest` passes with
`selftest: PASS (0 failure(s))`, including the new `ports` cases and the
second-slot serial-marker positive/negative cases. `run.sh --dry-run` with
`--sd2` adds `-drive if=sd,index=1,file=…`; without it the command equals the
baseline; a missing `--sd2` file fails with exit 1.

**O8 — End-to-end through `run.sh --sd2`.** A 90 s boot via the committed
`run.sh --sd2 user16.img` (not the probe script) produced a serial log with
the same second-slot mount markers; `ze0_sdhost.py serial run-sd2/serial.log`
counted `dsk8_attached 1`, `user_sd_notify 9`. (The run's `-d` log was removed
after counting; it was 590 MB and scratch disk is limited.)

## Interpretation

- **FACT:** the model already had both SD ports and both SD DMAC channels
  (rows C10 / M8.C1b); no QEMU patch change was needed. The missing piece was
  only the run.sh plumbing to attach a second `sd-card` to port 1 (C-7140,
  C-7141).
- **FACT:** with `--sd2` the guest asserts card-detect on port 1, enumerates
  the card, reads its boot sector/FSInfo and mounts it as `DSK8:` / `\UserSD`,
  broadcasting the mount to nine processes (C-7142–C-7145).
- **OBSERVED:** port 1 uses HPB-DMAC channel 9, already in the model; no new
  DMA channel is needed (C-7146).
- **OBSERVED:** the baseline without `--sd2` is unchanged, including 0 port-1
  commands and 0 second-slot mount lines, so today's behaviour is preserved
  (C-7147).
- **HYPOTHESIS:** a user file placed on a generated FAT image at port 1 can be
  made visible to Navi.exe through `\UserSD` (e.g. a `VER_INFO/HDD_INFO.TXT`
  to drive M2.1's UserSD branch). Not demonstrated here: no file was seeded
  and no file read by the firmware was traced.
- **UNKNOWN:** whether the guest ever writes to the port-1 card, and which
  `\UserSD` paths Navi.exe actually opens at boot. The card was read-only in
  these runs.
- **Rule 13:** this is an L4 (full-system emulator) observation of the guest's
  own mount behaviour, not an L5 car/bench acceptance.

## Conclusion

`run.sh --sd2 FILE` attaches the file to SD host port 1. With a 16 MiB FAT16
card there, the EU 2011 guest enumerates it (49 commands), asserts card-detect
(`SD_INFO1 = 0x00a1`), moves data over HPB-DMAC channel 9 and mounts `DSK8:` as
`\UserSD`, broadcasting `SYS_NOTIFY_USER_SD_CARD_MOUNT` to 9 processes. Without
`--sd2` the boot log equals the baseline (0 port-1 commands, 0 second-slot
mount lines). The falsifier did not fire. The Done-when is met. The remaining
step is to seed a real user file and trace a firmware read of it (follow-up).
