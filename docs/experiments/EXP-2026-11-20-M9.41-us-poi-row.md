## Question

Can the already-running `point_walk_l3 walk --build us2011` run be registered as an
S1/S2 evidence row so that `python3 tools/l3check.py --build-corpus` lists it as
**runnable with its verdict**, using only the files M9.41's Scope names
(`targets.json` + `l3check.py` `TARGET_EVIDENCE` + the POI row of
`reader-coverage.md`)?

## Hypothesis

No. The Done-when requires the row to be *runnable* under `--build-corpus`, but
(a) `l3check` corpus mode constructs the runner namespace with only
`engine/input/corpus/max_insns/dry_run` and never passes `--image/--cmp/--ind`
(so every `firmware_call` target there is BLOCKED by design), and (b) `runner.py`
dispatches only the `cmp_ind_chunk_v1` and `mapcode_compare_v1` `firmware_call`
programs, so a POINT-walker entry would be `unknown firmware_call program`. Making
it runnable needs new `runner.py` dispatch + `l3check` CLI plumbing, which the
Scope forbids.

**Falsifier** (stated before the result, C-4227): a POINT target added to
`targets.json` exactly within the Scope is *not* BLOCKED under `--build-corpus`;
i.e. `l3check.py --build-corpus` lists it as runnable and prints a verdict without
any change to `runner.py`/`l3check.py` argument plumbing. (The falsifier only
concerns registration *runnability*; it is not the M9.41 Falsifier line, which is a
wrong-build check, C-4226.)

## Method

1. **Sample and hash.** As above (`sha256sum archive/us256.img archive/head256.img`).
2. **Commands** (from the worktree root; `S` = the US factory pair dir, `O` = a
   scratch dir outside the repo):

   ```bash
   S=/home/marek/projekty/leafre-work/m5.12-us/root-factory/REFER001
   O=/home/marek/projekty/leafre-work/scratch/m9.41

     --cmp "$S/POINT010.DAT.cmp" --ind "$S/POINT010.DAT.ind" \
     --page 0x840ba0 --page-len 42848 --build us2011 --n 499,500,501,998,999,1000
   ```

## Interpretation

- **FACT:** The US POI walk runs and passes on the US build, and the M9.39 mutant
  is a positive witness that moves `n=501/998/999` by +4 (record count unchanged).
- **FACT:** A wrong-build pairing is a clean `result: FAIL (unmapped …)`, exit 1,
  one `result:` line, no traceback (this is the M9.41 Falsifier's shape, C-4226).
- **FACT:** `l3check --build-corpus` has 8 targets and no POINT row; a POINT
  `firmware_call` target added exactly within the Scope is BLOCKED because
  `runner.py` has no `point_walk_v1` dispatch, and `--build-corpus` never supplies
  `--image/--cmp/--ind` (C-4223–C-4225).
- **OBSERVED:** The registration the Done-when demands ("lists the new US target as
  runnable with its verdict") requires `runner.py` (a new program kind that runs
  `point_walk_l3.walk`), `l3check.py` (corpus-mode `--image/--cmp/--ind` plumbing)
  and `l3_harness/corpus.py` (a POINT page entry) — three files the Scope forbids.
  The second Done-when element ("M9.10's Status cites the new row as its S1
  evidence") is chained to the first, so it cannot be met alone either.
- **HYPOTHESIS:** The honest cheap end-state — a POINT row visible to `l3check`
  as BLOCKED-with-reason — is worth registering, but it must not be described as
  "runnable with its verdict". It is M9.55's job, together with the `runner.py`
  runner that makes it actually run.
- **UNKNOWN:** Whether the name half can be ticked from the walker row: it cannot
  — the accessor is separate (C-4178), so M9.10's name half still needs M3.11c.

## Conclusion

M9.41 is **blocked, not done**: the Done-when asks for a `--build-corpus` row that
is runnable with its verdict, and that needs `runner.py` dispatch plus `l3check`
argument plumbing outside the task's Scope. The walker evidence itself is
unimpaired (factory + M9.39 mutant PASS, wrong-build FAIL), so nothing in
`docs/format/` or the claim ledger is retracted. The unblocking task is **M9.55**
(run the US POI walk from `runner.py` and register the target so it reports a
verdict), which re-opens M9.41; M9.10 keeps its walk half as runnable evidence
(C-4222) and its name half open on M3.11c. No new VA was retyped (the walker VAs
are read through `build_targets.py`, the single owner).
