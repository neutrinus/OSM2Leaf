## Question

Can `tools/l3_harness/runner.py` run the M3.10 `DRSTR001.DAT` reader
(`sub_00419350` in `Navi.exe`, called from `0x00419684`) on the factory
`DRSTR001.DAT` (EU and US) and reject a corrupted tree?

## Hypothesis

Falsifier-first. The runner can run the reader if `targets.json` can name it
by module VA and the runner accepts that entry kind. Refuted if the
`drstr_parser` target runs and returns ACCEPT on factory input and REJECT on
the corrupted case.

Prediction before the run: the runner cannot, because `targets.json` supports
only `entry.kind` `synthetic` and `blocked`, and the module-entry kind is the
M9.20 follow-up (`entry.kind = "module"`), still open on `origin/main`.

## Method

1. **Sample and hash.** None for the blocked run. Controls use two synthetic
   files written to the scratch directory: a zlib stream
   (`probe_ok.cmp`, `zlib.compress(b'DRSTR probe payload')`) and a non-zlib
   file (`probe_bad.cmp`, bytes `00 11` + `not-zlib`).
2. **Commands** (run from the repo root):

```bash
python3 tools/l3_harness/runner.py targets
python3 tools/l3_harness/runner.py run drstr_parser --json
python3 tools/l3_harness/runner.py run probe-zlib-cmf --input /tmp/claude-1000/scratch_m914/probe_ok.cmp --json
python3 tools/l3_harness/runner.py run probe-zlib-cmf --input /tmp/claude-1000/scratch_m914/probe_bad.cmp --json
python3 tools/l3_harness/selftest.py
python3 -c "import json; d=json.load(open('tools/l3_harness/targets.json')); print([(t['name'], t['entry']['kind']) for t in d['targets']])"
```

3. **Controls.** *Positive*: `probe-zlib-cmf` on the zlib stream must PASS
   with `accepted: true`, exit 0. *Negative*: the same probe on the non-zlib
   file must not PASS (MISMATCH, exit 5). The `drstr_parser` run is the
   target under test, not a control.
4. **Scope.** The entire L3 target list (6 targets, 1 synthetic, 4 blocked
   readers, 1 blocked `mapcode_comparator`). The DRSTR reader itself was not
   executed. The firmware VA was taken from the M3.10 EXP and was not checked
   with `tools/cerom.py`: the full EU image is not under `archive/` on this
   machine (`archive/` holds only `.gitkeep`), and the
   `leafre-work/leaf2011.img` path given in AGENTS.md does not exist here.
5. **Falsifier.** A `drstr_parser` run that returns `accepted` true for the
   factory tree and false for the corrupted tree, with `status` not `BLOCKED`,
   would refute the block. The probe controls must hold for the negative to
   count: if the probe fails its positive control, the runner result is
   INVALID, not evidence.

## Interpretation

- **FACT:** `drstr_parser` in `targets.json` is `blocked` with reason "no
  parser entry point recovered (M3)". The reason is stale: M3.10 (done)
  recovered `sub_00419350` / call site `0x00419684`. The runner cannot take a
  module VA as an entry at all, so updating the reason alone is not enough.
- **FACT:** The module-entry kind and `engine_hook` belong to M9.20 (open,
  `Depends: —`, not on `origin/main`). M9.5's Follow-ups list the same
  `entry.kind = "module"` item. Rule from the task: a missing module-entry kind
  is a blocker, so M9.14 cannot honestly reach its Done-when check on
  `origin/main`.
- **FACT:** The runner pipeline itself works: the synthetic probe PASSes on
  the zlib control and exits 5 on the negative. The block is in the target
  kind, not in the dispatcher or the engine.
- **OBSERVED:** No ACCEPT/REJECT verdict for factory or corrupted DRSTR input
  was produced. Done-when is not met.
- **HYPOTHESIS:** Once M9.20 lands, a `module` entry carrying the M3.10 VA and
  stack-argument setup for `sub_00419350` will let M9.14 run. This is a
  prediction, not tested here.
- **UNKNOWN:** Whether `sub_00419350` runs on PySh4 to the factory ACCEPT
  without further stubs (the M3.10 notes list `_modlu` and `>=200` caveats);
  whether the EU factory tree is byte-identical to the US one.

## Conclusion

Status is `blocked`, not `done`. Blocker: the runner has no module-entry
target kind (`entry.kind = "module"`, `engine_hook`), which is M9.20, still
open on `origin/main`. Unblock: M9.20. Done-when (EU and US factory accept,
M5.6 rebuild accept, one corrupted reject) is not met and no DRSTR verdict is
claimed. `docs/format/` and `docs/research/claims.md` are unchanged. The
M3.10 `Navi.exe` VA was not re-attributed with `cerom.py`; that is still to
be done when the image is present, before the module entry is written.
