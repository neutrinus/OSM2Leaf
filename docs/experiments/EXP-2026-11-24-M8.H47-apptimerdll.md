## Question

Who provides `AppTimerDll` for `Speech.exe` on the real unit, and can the voice
process be made to run on `-M ze0`?

## Hypothesis

H1: the unit's own flash kernel NK1 (from the M6.18/M6.19 dump) provides
`AppTimerDll.dll` (module 48) and card image A imports its four exports; a
provisioned L4 boot (NK1 as kernel) therefore executes `Speech.exe`.
Falsifiers, stated before the result:
- f1 — `Speech.exe` imports nothing from `AppTimerDll` (the failure has another
  cause, the task's own Falsifier);
- f2 — NK1 lacks the module, or A/B carry it (the flash hypothesis is wrong);
- f3 — a "running" claim backed only by launcher `Process Create!!!` /
  `Not Create!!!` lines with no execution hit from Speech.exe's own code;
- f4 — the unprovisioned negative control still runs Speech.exe at idle.

## Method

### 2. Commands

From the task worktree, with `I=archive/head256.img`,
`NK=firmware/unit-flash/nk1-QY7200ND.bin`, `US=archive/sd-images/LEAF_2011-2012_US.img`,


### 3. Controls

- *Positive (static):* the same `cerom.py modules | grep -i apptimer` command
  finds image C's module 87 and NK1's module 48, and `imports Speech.exe |
  grep -i apptimer` prints four slots (O3–O6). The `strings` of Speech.exe's
  own sec0 contain the DBGMSG format strings (O7), so a hit is attributable.
- *Positive (L4, branch a):* the same serial log also shows already-running
  processes (`Navi.exe` initialisation, `NaviEvCC :InitSpeech` = 1), proving the
  debug sink is live; the execution lines from Speech.exe's code (48 `Spcom
  -->`, 18 `speechguideaccess.cpp`, 1 `speechg2paccess.cpp`, 1 `[RGD-SPEECH]`)
  are the positive execution signal.
- *Negative (historical, provision absent):* with kernel B only (no NK1, no
  AppTimerDll joined), EXP-2026-11-22-M8.C1i O7 and C-6917/C-8214 record
  `DoImport Failed! Unable to import Library 'AppTimerDll.dll' for
  '\windows\Speech.exe'`; the older EU baseline log (C1p
  `live-eu-correct/serial.log`) has `grep -c 'Spcom -->'` = 0 and one
  `Launch Process Not Create!!! -> \windows\Speech.exe`. f4 is therefore not
  met: without provision the process does not reach its own code.
- *Mutation (assertion can fail):* on a copy of the captured log,
  `printf ' Spcom --> ...\n'` raises `grep -c 'Spcom -->'` from 48 to 49 and
  a `[RGD-SPEECH] MUTATED` line raises that count from 1 to 2 (O11). The
  numbers are counted, not `grep -q`, so a lost/hidden duplicate is visible.

`python3 --version` = 3.15.0; QEMU = 11.1.3; HEAD = `ca66e13a…6560`.

**O2 — precheck, where the module lives.** `cerom.py --image-start 0x5200200
archive/head256.img modules | grep -i apptimer` prints one line:
` 87 AppTimerDll.dll              attr=1007 size=    5120 load=888bb000 vbase=01e40000 objs=3`.

apptimer` prints one line:

byte-identical to image C's four export RVAs.

**O4 — card/unit pairing (no card patch needed).** `card_mapcode.py show

**O5 — L4 execution (branch a).** In `$S/run-us/serial.log` (1,200 lines)

`speechguideaccess.cpp` traces. The `Spcom`/`SpeechGuide`/`SpeechG2P` format
strings exist in `Speech.exe.00011000.bin` (O7), so these lines come from
Speech.exe's code, not from the launcher or another module.

**O6 — attribution of execution strings.** `cerom.py ... extract Speech.exe

## Interpretation

- **FACT (C-7440, C-7441):** the unit's own flash kernel NK1 (module 48,
  `vbase=0x03c10000`, exports the four `APPTIMERDLL!*` names) supplies
  `AppTimerDll.dll`; card image A imports exactly those four names; images A
  and B carry no such module. The falsifier f1/f2 do not fire.
- **FACT (C-7442):** this is the real-unit dependency, not an emulator
  artefact: M6.19 C-5212 (VERIFIED) shows NK1 and card A are one linked
  system (RAM end = A's start, DLL windows abut, build labels pair), and
  C-8291 names `AppTimerDll` among NK1's modules; the unit-flash README
  states the same. This satisfies Done-when branch (b).
- **FACT (C-7443, branch a):** on one L4 boot with NK1 as kernel and the US
  card, `Speech.exe` executes its own code — 48 `Spcom -->` lines, 18
  `speechguideaccess.cpp`, 1 `speechg2paccess.cpp`, 1 `[RGD-SPEECH]` — with
  zero `DoImport Failed` and zero `Not Create`. The launcher's `Process
  Create!!!` lines alone would not have been accepted (f3); the DBGMSG
  attribution to Speech.exe's sec0 is what makes this branch valid.
- **OBSERVED (C-7444):** the negative baseline without provision has zero
  `Spcom -->` lines and one `Launch Process Not Create!!!` for Speech.exe;
  historically (C1i O7) the cause without provision is the AppTimerDll import
  failure. f4 does not fire.
- **OBSERVED (C-7445):** the log-key mutation raises the counted greps by 1,
  so the execution assertion can fail loudly.
- **HYPOTHESIS (C-7446):** on the EU card the earlier C1p run reached the
  ACM/region gate (M8.C1p, C-8436) instead; whether the same NK1 provision
  makes Speech.exe emit its own DBGMSG on the EU card would need a small
  patched-card boot (blocked on disk space in this session — no 8 GB copy
  could be written). The US-card result already meets the task's Done when.
- **UNKNOWN:** whether `Speech.exe` runs with no micon/audio peer present for
  an indefinite idle; the run lasted 160 s and the log ends with Speech
  activity, but no longer soak was done.

## Conclusion

The unit flash supplies `AppTimerDll.dll` (NK1 module 48); card A's
`Speech.exe` imports its four exports, and no card image carries the module.
With NK1 as the kernel on `-M ze0` and the unmodified US card (whose map code
matches NK1), Speech.exe reaches its own code and emits 48 `Spcom -->` and
one `[RGD-SPEECH]` DBGMSG line, with zero import failures and zero failed
launches. Both Done-when branches are met: branch (a) by the execution hit and
branch (b) by the M6.18/M6.19 dump evidence (C-5212/C-8291). Claims
C-7440–C-7449 added via `board.py add-claims`; no `docs/format/` change is
needed (this is a firmware/provisioning finding). What stays open: the EU-card
variant of the same boot (disk-limited here) and the downstream voice-prompt
capture (M8.H48, depends on H46/H47).
