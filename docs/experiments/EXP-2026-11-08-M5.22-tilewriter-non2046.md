## Question

For the section-1 level-1 directory kinds other than `0x2046` found in EU 2011 tiles, is the directory slot table (header, slot tags, pair/body tables, declared-size tail) modelled well enough for `tilewriter.py` to *safely preserve* those directories during a factory splice, and if not safe to mutate, is that refusal justified by a concrete invariant?

## Hypothesis

`clarion_tile.read_dir`/`write_tile` already preserves the container structure byte-identically (round-trip), but `tilewriter`'s mutation path is unsafe for non-`0x2046` kinds because parsed record boundaries can be wrong (so shared-block detection and any splice would be unreliable). **Falsifier:** a non-`0x2046` section-1 directory whose slot table is not preserved by a `0x2046` splice (directory bytes differ), or a case where `clarion_tile` does not round-trip the tile, or evidence that record boundaries are reliably parseable so mutation would be safe.

## Observations

"Unclean" by the M5.4 metric (`block_off>=0x1000 and recs and all zlib`) for B48R058R sec1 lv1 totals 420 clean / 575 unclean / 28 empty over the 1,023 non-0x2046 slots (1,024 including? 32 dirs × 32 minus 0x2046: 34 dirs×32=1088? — counted 34 non-0x2046 dirs: 13+6+6+3+2+1+2+1=34, 1088 slots minus 65 empty/clean accounting gives the per-dir totals above summing to 420/575/28 = 1023 slots). Reasons: predominantly `non_zlib` (parsed recs present, not zlib magic) and typically 1 `no_recs` per dir.

Diagnostic (B48R058R, 0x2146 dir y=72 x=938): slot 14 tag `0x000007b0` → block 0xe800, pair table includes `(a=0xb2c, b=0xffffffff)` and other `0xffffffff` fields; `clarion_tile.read_dir` skips `ln==0xffffffff` but breaks on `X==0xffffffff (> 0x10000)`, yielding `recs=0, block_end=block_off`. Raw block bytes at 0xe800 are non-zlib. Four slot entries across four directories alias block_off 0xe800 (0x2146 (72,938) slot14, 0x2746 (72,941) slot26, 0x2346 (73,941) slot27, 0x2246 (73,943) slot5); many parsed non-0x2046 spans cover 0xe800 with large (often over-broad) ranges due to the same boundary misparse. `clarion_tile` still round-trips byte-identically because `_try_preserve_random` starts from `src` and overwrites only modelled components (tables/dirs/parsed slot blocks), leaving unmodelled regions as source bytes.

Tilewriter after M5.22: same M5.4 splice command produces identical output `sha256 a1292979f2c30ef1b69469360793e33327b3dc349d9c1da37e161933ffb8c10a` (289,637,538 B), `result PASS`. `l2check --root .../m5.4/card-gen --tiles B48R058R.DAT --semantic-tiles B48R058R.DAT --no-golden --skip-mutation` → `RESULT: PASS` (census 480, drstr ok, cmp 20/20, tile_roundtrip OK, tile_semantic B48R058R=2331449). `python3.13 tools/tilewriter.py --selftest` → 59/59 OK. `python3 tools/selftest.py` → 62 passed, 0 failed, 18 skipped. `python3 tools/claims_check.py` → OK.

## Interpretation

- **FACT:** All tested EU 2011 tiles (5 pinned + B48R058R) round-trip byte-identically through `clarion_tile`. Section-1 level-1 non-0x2046 kinds 0x2146/2246/2346/2446/2546/2646/2746/2946 share a modelled container: 12-byte header, 32 slots × (4-byte tag + 512-byte pair/body table), optional declared-size tail (`n*512` bytes for 0x2n46, n=1–7 observed); `dir_bytes`/`read_dir` preserve this structure.
- **FACT:** Many non-0x2046 slot blocks contain non-zlib records and/or pair-table `X=0xffffffff` entries that make `clarion_tile.read_dir` break early, so parsed `recs`/`block_end` can under-represent the real block and the same block offset can appear aliased across dirs. Record-boundary inference is therefore unsafe for mutation.
- **FACT:** `tilewriter` now treats 0x2046 as spliceable and the observed 0x2x46 family as structure-modelled/preserve-only (mutation refused with a clear reason), detects same-offset block aliasing in `shared_slot_blocks`, and `verify_factory` checks preserve-only directory bytes are unchanged when not written. The M5.4 0x2046 splice remains byte-identical and L2-passing on B48R058R.
- **HYPOTHESIS:** 0x2946's zero tail in B48R058R (n=9, not 4608) is a kind-specific variant; only one instance observed.
- **UNKNOWN:** Semantic meaning of 0x2x46 kinds and their non-zlib record format; safe mutation would require a record-boundary/parser model for 0xffffffff-pair cases. Unit acceptance (rule 13).

## Conclusion

M5.22's done-when is met in the *preserve-only* branch: the slot-table container for the failing kinds is modelled/preserved (`clarion_tile` round-trip, `verify_factory` dir-bytes check), `tilewriter.py` safely preserves non-spliceable 0x2x46 dirs and refuses mutation with a justified invariant, `--selftest` covers aliasing/same-offset sharing + 0x2146 preserve/refusal (59/59), and L2 passes on real B48R058R (contains 0x2146/2246/2346/2446/2546/2646/2746/2946) with the M5.4 0x2046 splice reproduced byte-identically (`a1292979…`). Mutation inside non-0x2046 kinds remains refused (opaque content / unsafe boundaries). No format doc change beyond the EXP/claims; `map-tiles.md` already notes 0x2146 tails/B30R048 and container structure.
