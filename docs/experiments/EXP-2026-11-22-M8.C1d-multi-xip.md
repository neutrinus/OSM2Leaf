## Question

Marek asked whether the missing audio unit (M8.C2a) is what stops the
applications, and whether the emulator can be booted and a screenshot
taken. What does a long boot reach, and what blocks the screen?

## Hypothesis

The applications wait on the audio unit. **Falsifier:** an application
start fails for a reason unrelated to the audio protocol.

## Method

1. Run L: 1000 s boot, `-M ze0,verinf=QSD-302-100,mapdb=16-16`
   (`ze0-0011`), serial log and HMP monitor; VRAM (`gdisubdrv` logs `VRAM
   Base >> AE700000`, size `0x01860000`) saved twice with `pmemsave`.
2. With `-gdb … -S`: breakpoint after the launcher's `CreateProcessW`
   (AppLaunch.dll `0x3bcbfdc`, the call through the IAT thunk
   `0x3bcb7a8` → coredll #493), then call coredll `GetLastError`
   (`0x03fac6f0`, export #516) by setting PC/PR and restore the registers.
3. Read nk.exe B (OEMInit, the HAL IOCTL table at `0x88009200`, the
   loader) for what decides whether a second ROM image is used.
4. Poke candidate values into RAM through the gdb stub before the CPU
   starts (runs M, XA, XB, XC, XD), then make the working set a patch file
   (`tools/ze0_ipl.py`) and a machine option (`ze0-0012`, run P).
5. Run Q: as P with `-d unimp,invalid_mem,guest_errors` for 60 s, to see
   where the display driver's register accesses go.

```bash
python3 tools/ze0_ipl.py plan archive/head256.img
python3 tools/ze0_ipl.py patch archive/head256.img -o ipl.txt
qemu-system-sh4 -M ze0,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch=ipl.txt \
  -kernel archive/head256.img -drive if=sd,index=0,file=CARD.qcow2,format=qcow2 \
  -icount shift=0,sleep=off -nographic -serial file:serP.log \
  -monitor unix:mon.sock,server,nowait -d unimp -D qP.log
python3 tools/ze0_screenshot.py grab --monitor mon.sock -o shot
grep -a -c 'Launch Process Not Create' serP.log
```

## Observations

**O1 — run L (no patch).** The launcher waits 27 times
`ACM::WaitModule Timeout ID[n] WaitTime[30000]` (IDs 18, 41, 46 ×7,
48 ×2, 60–68, 76–78, 81, 94, 96, 161), then logs
`AppLch >> Finish Launch Threads!`: nothing blocks for good. Before that,
19 `Launch Process Not Create!!!` lines cover every application
(DrawOi, Camera, AntiTheft, SystemExe, Speech, Audio, Usb, CPF, ComMid,
PhoneBTA, Telema, Vehicle, Consult, Navi). The kernel log has
`Looking for rom chain` / `Rom chain NOT found`; the launcher logs
`AppLch >> Single NK Image`. Both VRAM dumps (early and at about 8 min)
are all zero.

**O2 — why the starts fail (gdb).** At AppLaunch `0x3bcbfdc` the
`CreateProcessW` result is 0 for every application, and `GetLastError`
returns **2** (file not found) every time (23 calls in the first 20 s).
`Navi.exe`, `DrawOi.exe`, `SystemEXE.exe`, `Speech.exe` … exist only in
image A (file `0x200200`, 149 modules, no `nk.exe`, `physfirst
0x8cae1000`); image B (the running kernel, file `0x3e00200`) has 91
modules and none of them.

**O3 — what joins a second image (nk.exe B).**

| Item | Where | Card value | Use |
| --- | --- | --- | --- |
| XIP chain pointer | `.data` var `0x89e43c90` (template `0x88599c90`) | `0xffffffff` | fn `0x88048c08` (`Looking for rom chain`): count, then 0x290-byte `XIPCHAIN_ENTRY`s; an entry with flag bit 0 whose `pvAddr + 0x40` is `ECEC` adds `pvAddr + 0x44` (pTOC) to the ROM list |
| boot type | var `0x89e43c8c` | `0xff` | low nibble 0 → fn `0x88049d64` instead (entry 1 = a ROMHDR copy in `.data` at `0x89e47468`); HAL IOCTL `0x01013034` (handler `0x8804a5ac`) returns that test to the launcher |
| NK2 base | var `0x89e43c94` | `0xffffffff` | HAL IOCTL `0x01013020`/`0x0101301c`: the launcher's multi path (AppLaunch fn `0x03bd1f10`) reads it and asks the kernel to add its pTOC |
| opening-image buffer | vars `0x89e43c98`/`0x89e43c9c` | `0x8c6e0000` / `0x00401000` | ends exactly at image A's `physfirst` |
| RAM | ROMHDR B `ulRAMEnd` | `0x8e600000` | covers image A (`0x8cae1000`–`0x8e233c88`) |

The `.data` vars are initialised from ROMHDR copy entry 0 (`0x88598000` →
`0x89e42000`), so a value must be placed in the template, not in
`0x89e4…`, before the kernel starts.

**O4 — the multi path (boot type 0) fails.** Run M (`+0x8c = 0xf0`,
`+0x94 = 0x8cae1000`): `s_pNextRom[1].pTOC = 0x89E47468`, then
`loader.c line 3484: Failed to reserve Memory (05cc0000, 01cc0000,
01f80000)`. The `.data` ROMHDR at `0x89e47468` is not image A's (127
modules, `physfirst 0x84281000`); its DLL window `0x01cc0000–0x01f80000`
overlaps B's (`0x01bf0000–0x02000000`). The reservation loop
(fn `0x88027278`) reserves every listed image's DLL data window in each
new process slot and stops on the first overlap.

**O5 — the XIP chain path, step by step.** Chain = {B, A}, gdb pokes:

| Run | Extra pokes | Result |
| --- | --- | --- |
| XB | B `ulRAMEnd = 0x8c6e0000` | `Rom chain found`, `XIP found: NK`, `XIP found: NK2`; RAM section 0 now `0x89e74000 + 0x2869000`; `Failed to reserve Memory (05a80000, 01a80000, 01f90000)` (A vs B) |
| XB | + A `dllfirst` low half = `dlllast` | boots; every application `Process Create!!!`, none `Not Create`; `Load Opening Image Data to 0x8c6e0000 (Size=4198400 Bytes)`; 25 × `Paging in from uncompressed R/O page from XIP module -- should've never happened` and exceptions in `serial_uat.dll` (device.exe) |
| XD | + both TOCs compacted (rule below) | no exception; `OSM_MSGDLL : DLL_PROCESS_ATTACH`, `OSMDLL : DLL_PROCESS_ATTACH`, `+++ERROR UnLoad BackUpInfo @OBJ_Carpos_initialize` (Navi.exe's OBJDLL running) |
| XC | kernel C (`kernel-off=0x5200200`, `dbgmsg=0x880404b4`) instead of B | chain found, processes created, `DoImport Failed! … 'OBJDLL.dll' for '\windows\Speech.exe'`; A's DLL data window overlaps C's (`0x01e4…`), so Navi.exe's DLLs collide too |

**O6 — overlap between the images.** Section windows in the shared DLL
space: A code `0x03001000–0x03c037c0`, data `0x0154f000–0x01f8f1fc`;
B code `0x03531000–0x03ffbf50`, data `0x01bfb000–0x01fffea4`. 21 module
names are in both. Of A's other modules, the application DLLs
(`Navi*CC.dll`, `OBJDLL`, `OSMDLL`, `SYS`, `STDDLL`, `XGLDLL`, …) overlap
only B's `BT_FW.dll` and the `*UpdateCC.dll` updater screens; A's
networking stack (`afd`, `ndis`, `tcpstk`, `ws2`, `usbd`, …) and
`SpeechCC.dll` overlap B's drivers (`gdisubdrv`, `CAN`, `serial_uat`,
`AppLaunch`, …).

**O7 — the patch (`tools/ze0_ipl.py`, `ze0-0012`).** `plan` on the EU
image: chain var `0x89e43c90`, template `0x88599c90`, XIPCHAIN at phys
`0x0e6f0000`, RAM end `0x8c6e0000`; kernel keeps 81/91 modules (drops
`BT_FW.dll`, `MonitoringCC.dll`, `UpdateMngCC.dll` and seven
`*UpdateCC.dll`), image A keeps 111/149 (drops 22 duplicates and 16 that
overlap a kernel module). `patch` writes 8 lines. `build.sh
--check-version 11.1.3`: 16 applied, 0 failed. Run P (machine option
`ipl-patch=`, no gdb): `Rom chain found` 1, `XIP found` 2,
`Launch Process Not Create` 0 (run L: 19), `AppLch >> Process Create` 13,
`OSMDLL : DLL_PROCESS_ATTACH` 1, `OBJ_Carpos_initialize` 1,
`Exception` 0, `DoImport Failed` 1 (`AppTimerDll.dll` for
`Speech.exe`: the DLL is only in image C).

**O8 — the screen.** `tools/ze0_screenshot.py grab` in run P (three
times, up to the end of the run): `no non-zero pixel in 25559040 bytes
of VRAM`. `gdisubdrv.dll` maps its registers with `VirtualCopy`
(IAT thunk `0x3b18d58`, coredll #560) from `PAGE_PHYSICAL` sources
`0x00fff800` and `0x00ffe800` (phys `0xfff80000` and `0xffe80000`,
flags `0x604`). In run Q the guest's accesses arrive at the 29-bit
physical aliases and hit no device: `Invalid read/write at addr
0x1FF80…` (66) and `0x1FE80…` (17) in 60 s. The `ze0-stubs` block at
P4 `0xfff80000` is never reached through that mapping.

## Interpretation

- **FACT (C-6910):** in run L every application start fails with
  LastError 2 because the applications are in image A and the kernel
  never adds it (O1, O2). The falsifier of the audio hypothesis fires: the
  audio unit costs 30 s timeouts but blocks nothing (O1).
- **FACT (C-6911, C-6912):** the second image is joined either through the
  XIP chain pointer or through the boot-type path; both are `.data`
  fixups that the card leaves at "absent" (O3). The boot-type path fails
  on the card's own placeholder ROMHDR (O4).
- **FACT (C-6913):** images A and B (and A and C) overlap in the DLL
  space, so they were not built as one multi-region set (O5, O6).
  **HYPOTHESIS:** A's partner on a unit is a kernel outside the card
  (the `NK1` flash slot of C-707); B is the updater kernel (it carries
  `PRGUpdate` and the `*UpdateCC.dll` screens).
- **FACT (C-6914, C-6915):** with the XIP chain, RAM below A and both TOCs
  compacted, the applications start and Navi.exe's own DLLs run (O7). The
  opening-image buffer just below A fixes where RAM must end (O5).
- **FACT (C-6916):** the VRAM stays empty; the display driver's register
  blocks (phys `0x1ff80000`, `0x1fe80000`) are not modelled (O8).
- **OBSERVED (C-6917):** `Speech.exe` needs `AppTimerDll.dll`, which only
  image C has (O7).

## Conclusion

The measurement Marek asked for answers the audio question: the audio
unit is not the blocker, it only adds about 13 minutes of timeouts. The
applications did not run because image A was never joined; the IPL patch
fixes that without changing the card, and Navi.exe now starts and reaches
its own initialisation. The screenshot path works but there is nothing on
the screen yet: the display engine (registers at phys `0x1ff80000` and
`0x1fe80000`) has no model, so nothing reaches the VRAM.
