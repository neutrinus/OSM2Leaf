## Question

Can `UAT3:`/`UAT4:` be modelled so that a host socket's bytes reach the
guest driver's read path and the driver's own writes appear on that socket,
with an unchanged boot when no peer is attached?

## Hypothesis

The 16550-like register file of M8.H2 can be implemented as an MMIO device at
`0x19b00000`/`0x19e00000` with a 16-bit stride and a chardev, and an INTC
line can deliver RX interrupts. **Falsifier (task):** `CAN.dll` opens `UAT3:
` successfully before the patch (then the chip was not needed). **Second
falsifier:** the guest driver never reads a byte injected on the socket even
though the interrupt is delivered.

## Observations

- O1 — Build: `build.sh` applies 20 patches to QEMU 11.1.3; `-M help` lists
  `ze0`. `tools/ze0_peers/uart.py --selftest`: 5/5; `tools/ze0_uart_probe.py
  --selftest`: 5/5; `tools/selftest.py` discovers both.
- O2 — Kernel-only boot with `uat3=ze0uat3`: `qemu.log` has **196**
  `ze0-uart` access lines, including `write idx=3 val=0x83` (LCR|DLAB),
  `write idx=0 val=0x9d`, `write idx=1 val=0x00` (divisor 157), then
  `write idx=3 val=0x03` — the DLAB sequence of `0x039a4b84` in C-6995.
- O3 — Hook at `0x039a4cd8`: `r4=0x0000001b` at 1.3-4.3 s, i.e.
  `InterruptInitialize(SYSINTR=0x1b, event)`. A second hook at
  `0x039a3eca` (the IST setup path) produced no hit in the same boot.
- O4 — Full boot with the card: `CCanDriverIF::Init CALL bAccStatus[0]
  bIgnStatus[0]` and `CCanDriverIF::CanDriverWaitThread+++` appear in
  `serial.log`, `ze0_sdhost.py serial` reports `store_ready 1`,
  `part_mounted 2`, `event2_timeout 0`; the UAT3 chardev file is **0 bytes**
  and `qemu.log` has exactly one `write idx=0`, a divisor write with DLAB=1.
  CAN.dll therefore emits **no** THR bytes in the first 150 s.
- O5 — With a delayed host byte (`0x5a`) and `uat3-intevt=0x8c0`,
  `qemu.log` has one `ze0-uart chr read 1 bytes, fifo=1` line, and the ISR
  entry hook at `0x8800f210` reports `r6=0x8c0` from 19.095 s until the end
  of the run. There is **no** `ze0-uart read idx=0` line and no hit at
  `0x039a3e14`: the byte sits in the FIFO and the driver never reads it.
- O6 — The runtime InterruptTable dump (`--dump 0x89e42000:1024:file`,
  VBR+0x600 reads INTEVT and indexes `[INTEVT >> 5]`) has 51 non-default ISRs;
  a scan of all 51 functions with `sh4dis.py` finds **no** `mov #27,` return,
  so no ISR in EU2011 nk.exe returns SYSINTR `0x1b`. Patching r4 to `0x12`
  at `0x039a4cd8` and delivering INTEVT `0x8c0` (whose ISR does return
  `0x12`) still produced no RBR read — the event was not signalled.
- O7 — Negative control: injecting bytes at 0.2 s into INTEVT `0x8c0` hangs
  the boot before the hook; all 20 INTEVT candidates in the first sweep
  reported `IST_hits=0` because of that storm, not because of an
  inconclusive sweep. The delayed-byte variant above is the valid test.
- O8 — Baseline control: a 150 s factory-card boot **without**
  `--serial-peer` gives a 1583-line `serial.log` whose only difference from
  the UAT3-chardev boot is one SDL trace counter (`30797` vs `30796` on
  line 1022); all `ze0_sdhost.py serial` milestones are equal
  (`activate_ok 1`, `event2_timeout 0`, `store_ready 1`, `part_mounted 2`,
  `launch_not_create 16`). Attaching the chardev does not change the boot.

## Interpretation

- **FACT:** the QEMU device is correct at the register level: the real
  `serial_uat.dll` maps it, performs the 16-bit DLAB divisor sequence and the
  FCR/LCR accesses of C-6993–C-6997 (O2).
- **FACT:** `CAN.dll` publishes `CAN1:` and initializes `CCanDriverIF`, but
  it writes no UAT3 payload during a 150 s factory boot (O4), so the task's
  "bytes CAN.dll writes at start" clause has no sample to observe.
- **FACT:** host bytes do reach the model's RX FIFO and the IRQ is delivered
  to the guest CPU as INTEVT `0x8c0`, but the driver's IST never reads RBR
  (O5, O6).
- **FACT:** no OAL ISR returns SYSINTR `0x1b` (O6), so `InterruptInitialize`
  registered the UAT3 event on an unroutable SYSINTR. The mapping is the
  blocker; it is not a wrong register model.
- **UNKNOWN:** the real SYSINTR→INTEVT/chained-ISR path for UAT3, and whether
  the sub-CPU uses a GPIO/chained interrupt instead.

## Conclusion

The patch, `run.sh` support and two selftested tools are committed, and the
register model is verified against the firmware's own accesses. **M8.H3 is
blocked**: the RX loopback and the "CAN.dll startup bytes on the socket"
clause of Done when could not be demonstrated. Blocker: UAT3's measured
SYSINTR `0x1b` has no OAL ISR in EU2011, so the guest driver's receive path
never runs. Unblock task: M8.H3b (pin the UAT3 interrupt routing). Ten claim
rows C-7000–C-7009 were added, including the negative result. M8.H51 stays
open and cannot be claimed while its dependency is blocked.
