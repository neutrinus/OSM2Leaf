## Question

Can `tools/cerom.py` walk every `o32_rom` section carrying
`IMAGE_SCN_COMPRESSED` (0x2000), hand exactly `psize` stored bytes to
`tools/cecompress.py` with `expected_size = vsize`, and report per section
whether the decode is `OK`, `UNSUPPORTED` (codec/block type) or `FAIL` — with a
machine-readable record and an exit code an agent can gate on (TODO M1.3)?

## Hypothesis

None / exploratory for the format. The tool half is testable without vendor
data: a synthetic ROM can carry a real LZSS stream produced by
`cecompress.encode_lzss` (must decode to `vsize`, bytes and SHA-256 pinned) and
an LZX **verbatim** block header (must be refused, never written). The
"245 sections" half of M1.3 cannot run here: no vendor image is in this
checkout (`archive/` is empty, the working set lives on another machine) and
hardware access is unavailable. EXP-2026-11-05-49 already showed that the
`NaviMapCC.dll` `.data` section (`psize 0x2c6`, `vsize 0x5b8`) does not decode
with zlib raw/zlib/gzip, LZMA or bz2 from the stream start — a negative without
a positive control, so it rules out those stdlib formats only in that form, not
every header-skipping variant and not the CE codecs.

CLI shape implemented (TODO M1.3):

```
cerom.py IMG decompress [--modules M1,M2] [--section NAME]
                        [--method auto|lzss|lzx] [--out DIR]
                        [--check] [--json]
```

`--section` accepts `sec<N>`, `MODULE/sec<N>` or a hex RVA (`0x2000`);
`--modules` is case-insensitive and exits 2 for a name the ROM does not
contain.  `--check` writes nothing even when `--out` is given; without `--out`
the command is check-only.  Multiple CE segments in one file (build A/B are each
stored twice) are all walked: a byte-identical copy is listed under
`duplicate_segments` and not walked, and distinct segments write to
`DIR/seg<N>/` so equal `<module>.<rva>.bin` names cannot collide.  An
unreadable image is reported as `error: …` with exit 2 (previously a traceback
and exit 1).

## Interpretation

- **FACT:** `tools/cerom.py decompress` implements the M1.3 interface: it walks
  every compressed `o32_rom` record of every discovered segment, passes exactly
  `psize` bytes to `cecompress.decompress_info(..., expected_size=vsize)`, and
  classifies the result `OK` (length == `vsize`), `UNSUPPORTED`
  (`UnsupportedFormat`: unknown codec, weak-only `auto` candidate, LZX
  verbatim/aligned block, E8 stream) or `FAIL` (`DecodeError`/any other
  exception, plus an empty or out-of-image stored range). Each record keeps
  module, section, rva, vsize, psize, flags, file offset, the method that was
  tried and used, a SHA-256 whose `sha256_scope` says whether it is the
  `decoded` output or the `stored` input, and the first error.
- **FACT:** output is written only for `OK` decoding, as
  `<module>.<rva>.bin` (`seg<N>/` when several distinct segments are walked);
  `--check` writes nothing. A non-OK section leaves no file, so compressed bytes
  cannot be mistaken for section data.
- **FACT:** exit codes are 0 only when every requested section is `OK`
  (or no error at all was recorded), 1 when some are `UNSUPPORTED`/`FAIL`, 2 on
  a usage/IO error (unknown module, bad `--section`/`--method`, no matching
  section, unreadable image, segment discovery failure).
- **FACT:** the 167 synthetic checks include a genuine LZSS round-trip through
  the new command (2048 B from 283 stored bytes, output and SHA-256 pinned) and
  a real refusal of an LZX verbatim block (4 stored bytes, `UNSUPPORTED`), so
  the classification logic itself is exercised, not just the parser.
- **OBSERVED:** `auto` selects LZX for the 4-byte verbatim header and then
  refuses it; that ordering is what makes the "unsupported block type" case
  reachable rather than being misread as LZSS, whose decoder happily returns 3
  bytes for the same input.
- **UNKNOWN:** whether any real `IMAGE_SCN_COMPRESSED` section decodes to
  `vsize` with either codec. The real 245-section run is impossible here: no
  vendor image exists in this checkout and hardware access is unavailable, and
  EXP-2026-11-05-49 already showed that the `NaviMapCC.dll` `.data` section does
  not decode from the stream start with zlib raw/zlib/gzip, LZMA or bz2. That
  EXP is a negative without a positive control, so it does not rule out
  header-skipping prefixes or the CE-specific families implemented in
  `cecompress.py`; nothing in the repo has decoded a real section.
