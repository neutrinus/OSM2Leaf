## Question

Which firmware code reads the entries of the POINT spatial tree (directory
cell `0x85a`: 16-byte entries `0008, u32 ptr, u16 size_w, u16 kx, u16 ky,
u32 fine`, node end `0005 …`), and which fields of an entry and of a leaf
does it use? M5.63 needs this to know what the unit reads when a POI is
moved or added.

## Hypothesis

The tree is read by a search that descends by key and takes the leaf's fine
words as a position: a function loads entry words 4/5 (`kx`, `ky`) as a mesh
key, loads the child node by `ptr`/`size_w`, and for a leaf masks the fine
words with `0x7ff`. Run on a factory tree, it returns for a cell exactly the
name-record ordinals `point_census.py` reads below that cell.

**Falsifier (set before the runs):** no function that loads the header cells
`0x85a`–`0x85e` leads to code that reads entry words 4–7; or the located
code, run on a factory tree, returns ordinals that differ from the host
reading on a cell.

## Method

1. **Sample and hash.** EU2011 build A; the five pairs are read from the
   card image above. Trees per file: 53, 30, 58, 63, 33.
2. **Static.** `sh4xref.py --to` on the header-cell offsets and the slot
   table found the loader of cells `0x85a`/`0x85c`/`0x85e`
   (`fn 0x0040f338`), then its users; `sh4dis.py` listings of
   `fn 0x0040f944`, `fn 0x004110dc`, `fn 0x004114dc`, `fn 0x00408ea4`.
3. **Commands.**

```bash
python3 tools/point_census.py extract --card-image CARD /tmp/pt_eu     # never commit
for f in POINT010 POINT001 POINT025 POINT033 POINT017; do
  python3 tools/point_tree_l3.py run archive/head256.img --dir /tmp/pt_eu \
      --file $f --tree all --cells 60 --json run_$f.json
done
python3 tools/point_tree_l3.py --selftest
```

   The tool maps `Navi.exe` and all `STDDLL.dll` sections from the image,
   binds the `STDDLL` exports, and runs the firmware's child loader, step
   function, node walker and distance function on a decoded tree. Modelled
   by hand: the block cache (served from the decoded file), `memset`/
   `memmove`/`_modlu`, `STDDLL`'s own `COREDLL` math imports, the error
   logger, and the search state the set-up code would have written (tree
   base block, origin, distance window, result buffers, no category filter,
   `*0x0056389c = 0x2000`, `*0x00d5d7e4 = 1`). The origin is the first kept
   leaf's own name record. Per tree up to 60 cells are sampled evenly.
4. **Controls.** Positive: the origin leaf must come back at distance 0.
   Negative, on the first kept leaf of every tree: (a) fine y changed by
   1024 steps must move it by half a mesh of latitude (about 1,158 m);
   (b) a `0005` terminator written over the leaf must remove it and what
   follows; (c) the leaf flag `0x0800` cleared must drop a leaf that sits in
   the cell's node; (d) where the sample has a leaf with a code other than 0
   or 63, it must be absent with `*0x005638ec = 0` and present with that
   code.
5. **Scope.** EU2011 build A; 5 of 33 files, all 237 trees of them, 8,475
   sampled cells with 16,616 leaves. Levels `0x1001`–`0x1005`. Not run: the
   upper-level drivers `fn 0x00411fd4`/`fn 0x0041235c` (the tool calls the
   step function per entry), the root loader `fn 0x0040f674` and the
   set-up `fn 0x0040f338`/`fn 0x0040f2fc` (static only), the category
   filter, US2011.
6. **Falsifier.** As above.

## Interpretation

- **FACT:** the spatial tree is read by the nearest-POI search of EU2011
  `Navi.exe`. `fn 0x0040f338` loads the header cells `0x85a`/`0x85c`/`0x85e`
  (and `0x82a`/`0x82c`/`0x82e`) into the 40-byte slot table `0x00563918`;
  `fn 0x0040f2fc(slot)` copies a slot into the search state at `0x00d94100`.
  Cell `0x85a` points at a descriptor with one reference per category, not
  at a tree.
- **FACT:** `fn 0x0040f944(entry, slot, ctx, level, request)` is the child
  loader. It loads entry `+2`/`+4` as the `u32` pointer (`0x0040f968`,
  `0x0040f96c`), `+6` as `size_w` (`0x0040f972`) and `+8`/`+10` as the key
  `kx`, `ky` (`0x0040f9b4`, `0x0040f9ba`). The child's first block is
  `(ptr >> 7) + *0x00d5b858`, its length
  `((ptr & 0x7f) + size_w + 127) >> 7` blocks of 128 words (256 bytes);
  `ptr = 0xffffffff` or `size_w = 0` means no child.
- **FACT:** `fn 0x004110dc(level, n, index, ctx, -, request)` steps to entry
  `index` of a node by `2 * word 0` bytes per entry and calls the loader at
  `level + 1`. Levels: root node `0x1001`, level-1 node `0x1002`, cell
  entry `0x1003`, cell node `0x1004`, category node `0x1005`.
- **FACT:** `fn 0x004114dc(level, request)` walks a node at levels `0x1004`
  and `0x1005`. It ends at the first entry whose word 0 is below 8 (the
  `0005` terminator). At `0x1004` an entry without `word 6 & 0x0800` is an
  inner entry and is descended; the flag is tested at that level only (in
  the 3 trees per file whose leaves sit one level lower, clearing the flag
  changes nothing). For a leaf it loads words 6 and 7 (`0x00411680`,
  `0x00411688`): `x = word 6 & 0x7ff`, `y = word 7 & 0x7ff`, and a 6-bit
  code `((word 6 & 0x8000) | (word 7 >> 1)) >> 10`.
- **FACT:** a leaf is kept only when its code is 0, 63 or equal to
  `*0x005638ec`. The usual leaf (`0x8800 | fine_lon`, `0xf800 | fine_lat`)
  has code 63. Leaves with codes 2–10 exist in the factory trees and are
  skipped while `*0x005638ec = 0` (control 33/33).
- **FACT:** the leaf's position is the parent key with the level mask plus
  the two 11-bit fine values; the distance to the search origin
  (`*0x00d5d7e8`, x/y at `0x00d5b864`) is computed by `fn 0x00408ea4` with
  `STDDLL!STD_MeshLine_initPrm`, `STD_MeshPnt_chgLv`,
  `STD_MeshLine_calcLength` (unit 0.1 m), and the leaf is stored when
  `*0x00d5b848 < distance <= *0x00d5b840`. The result table `0x00d5d800`
  holds up to 128 records of 24 bytes (`+4` distance in metres, `+16` the
  entry's `ptr` = name-record ordinal), counted in `*0x00d5b85c`.
- **FACT:** on 8,475 cells of 237 factory trees the firmware code returns
  the ordinals `point_census.py` reads and distances that agree with the
  host position formula of M4.27/M3.34. So a leaf needs: the `0x0800` flag
  in word 6, code 63 (or 0), `ptr` = ordinal, the two 11-bit fine values,
  and a `0005` terminator after the last entry of its node. With no
  category filter set the walk does not load a leaf's `size_w`, `kx` or
  `ky`; with a filter (`0x00d5d7dc`, not run) it compares entry word 5.
- **HYPOTHESIS:** the 6-bit code selects a variant of the same POI
  (several leaves with different codes follow each other); `*0x005638ec`
  would then be a setting such as the language. Not tested.
- **UNKNOWN:** the writers of `*0x005638ec`, `*0x0056389c` (`0x2000` here),
  `*0x00d5d7e4`; the upper-level drivers and the category filter
  (`0x00d5d7dc`); one error-log call from `0x004192ea` (a file-state check)
  that the run passes; US2011 twins.

## Conclusion

The reader of the POINT spatial tree is the nearest-POI search: child loader
`fn 0x0040f944`, step `fn 0x004110dc`, node walker `fn 0x004114dc`, distance
`fn 0x00408ea4` (EU2011 build A). Run in L3 on 237 factory trees it agrees
with the host reading on all 8,475 sampled cells. The fields the unit reads
are named: `ptr`, `size_w`, `kx`, `ky` of inner entries; of a leaf the
`0x0800` flag, the 6-bit code, the two 11-bit fine values and `ptr`. New
for the writer: a leaf's code must be 63 (or 0), otherwise the search skips
it unless a global holds that code.
