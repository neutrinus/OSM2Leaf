## Question

Can HMP PC sampling, mapped to module/function, show where guest CPU time goes
during an EU2011 launcher wait and at idle, or are both phases one uniform loop
where the method fails?

## Hypothesis

Two phase histograms differ: the launcher wait spreads over kernel scheduler,
driver and UI functions; idle concentrates in the OAL idle loop (EXP-C1e O5/O8:
PC `0x880480bc`, 12/12 samples). Falsifier (TODO:5010): both histograms uniform
over one idle loop → PC sampling alone useless, EXP says what else is needed.

## Method

### 1. Sample and hash

Printing commands and their verbatim output are in Observations O1/O2:

### 2. Commands

Runnable from the repo root, no ellipsis:

```bash
python3 tools/ze0_pcsample.py --selftest
python3 tools/selftest.py --only ze0_pcsample
python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img scratch/card.qcow2
bash tools/qemu-ze0/run.sh --qemu ~/.cache/qemu-ze0/build/qemu-system-sh4 \
  --image archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
  --ipl-patch scratch/ipl.txt --sd scratch/card.qcow2 \
  --icount shift=0,sleep=off --timeout 1200 --workdir scratch/live \
  --log /dev/null --serial file:scratch/live/serial.log
python3 tools/ze0_pcsample.py --monitor scratch/live/hmp.sock \
  --modules-from-ps --image archive/head256.img --cache scratch/pdata-cache \
  --n 300 --interval 0.05 --top 15 --label 'phase A' --save scratch/wait-capture.txt
python3 tools/ze0_pcsample.py --monitor scratch/live/hmp.sock \
  --modules-from-ps --image archive/head256.img --cache scratch/pdata-cache \
  --n 500 --interval 0.05 --top 15 --label 'phase B' --save scratch/idle-capture.txt
python3 tools/ze0_pcsample.py --file scratch/wait-capture.txt \
  --image archive/head256.img --cache scratch/pdata-cache --json
```

PC parse is anchored `^pc=0x([0-9a-fA-F]{8})` after ANSI/echo strip; the
printing command `grep -c 'pc=0x'` vs `grep -cE '^pc=0x'` on
`scratch/m8.h13/factory/registers.txt` gives 3 vs 1 (`spc=`/`delayed_pc=`
also contain the substring). The selftest includes the negative case.

### 3. Controls

- **Positive (tool):** the two known PCs from EXP-C1e replay to the exact
  functions printed by pdata (O3): `0x8803d266 -> nk.exe fn 0x8803d264`
  (1 218 pdata records), `0x0398e8a2 -> serial_scif.dll fn 0x398e888`
  (219 records, image B); both are enforced by `--selftest`.
- **Positive (live):** an EU2011 boot reaches `Store Mgr Ready!` and creates
  36 processes, including `Navi.exe` and `AuiApp.exe` (O5).
- **Negative (mandatory):** a corrupt `pc=0xZZZZZZZZ` line yields no sample
  and dropping one valid PC lowers the parsed count exactly by one
  (`--selftest`, O1); `spc=`/`delayed_pc=` are not counted.

### 4. Scope

Samples: 300 (phase A) + 500 (phase B) HMP `info registers` replies from one
EU2011 boot each, parsed/attribute rate 300/300 and 500/500. Functions from
build-B pdata (nk.exe 1 218, serial_scif.dll 219, gdisubdrv.dll 558 records,
O3); module ranges from the live CE module table (59 modules in the probed
`ze0_ps.py --json` snapshot) plus the build-B `nk.exe` vbase/vsize range
`0x88000000..0x88880000`, which the live table omits. Excluded: current
process name (HMP `info cpus` prints only thread id/model, O7). Ambiguous
static matches (15 samples phase A, 16 phase B) and unresolved PCs (23 each)
are reported, never guessed.

### 5. Falsifier

If both histograms are uniform over one idle loop, the EXP must say PC
sampling alone is useless and name what else is needed. The idle phase is
indeed concentrated (`0x8803d264` at 35.20 %), so this is recorded honestly in
Interpretation/Follow-ups; the launcher-wait phase is genuinely spread over
many functions, so the method is not useless overall. `blocked` would have
been acceptable if the live run could not be completed; it was completed.

## Interpretation

- **FACT:** the tool produces reproducible module/function histograms from a
  live HMP socket and replays saved captures; its selftest covers anchored PC
  parsing, live/static/ambiguous attribution, known pdata anchors and the
  negative mutation (O1–O4).
- **OBSERVED:** the launcher-wait phase spreads over at least 15 functions in
  nk.exe, gdisubdrv.dll, coredll.dll, auirtdll.dll and navdrv.dll (O5); the
  later phase concentrates 35.20 % in one `nk.exe` loop (O6, O8).
- **OBSERVED:** the falsifier is partially met for the idle phase alone: PC
  sampling by itself cannot tell which thread waits for which device; the
  module histogram does still identify the subsystems that are active during
  the launcher wait.
- **HYPOTHESIS:** the `0x8803d264` loop is the kernel's idle/scheduler return
  path (O8); naming the blocked thread needs per-thread wait state
  (`ze0_ps.py --threads`) and device traces (`ze0_sdhost.py`, `gfx-trace=on`).
- **UNKNOWN:** the current process per sample; a gdbstub-based reader of the
  `Thread` context PC could add it (follow-up).

## Conclusion

`tools/ze0_pcsample.py` turns the manual HMP PC sampling of EXP-C1e into a
tool: 300- and 500-sample EU2011 histograms with live module and pdata
function attribution, top-3 functions named for each phase, all
auto-discovered `--selftest` checks passing. The two phase distributions
differ (launcher spread vs idle concentration), so the method is useful for
the wait phase; the idle phase confirms the task's falsifier caveat and is
reported honestly. No format doc changed. Claims C-7200–C-7207.
