# EXP-2026-11-21-M4.35: the LCTBL `class_code` is the TMC location type on the US card too; reference columns and road-number syntax confirm it

- **Status:** done (the done-when is met in both forms: second-country control with a negative control, and the firmware reader path named)
- **Date:** 2026-11-21
- **Sample:** `RDSTM001/LCTBL001.DAT` of the EU 2011 card (`archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`, SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`): 7,489,024 B, SHA-256 `8cab17754114b5f7ca47d4f46d55c95c6acf841629e1fcc42e6da45063353e9d`; and of the US 2011 card (`archive/sd-images/LEAF_2011-2012_US.img`, SHA-256 `53342430a1bb58d3ed6eb68c5563f079c710a400134d522e6192489b324c5383`): 9,041,408 B, SHA-256 `87f11053c9d081187249376325e0d547ace887ebe509cfd6aa0d05eda08c9db1`. Firmware: EU 2011 `archive/head256.img` (IMG256, SHA-256 prefix `92aa525d`), module `Navi.exe`. No vendor bytes committed.
- **Tools:** Python 3.13.18 (stdlib); `tools/lctbl_kind.py` (new, `--selftest`), `tools/lctbl_build.py` (`parse`, `decode_record`), `tools/lctbl_lookup_l3.py extract`, `tools/sh4dis.py`, `tools/sh4xref.py`
- **Claims:** C-3200, C-3201, C-3202, C-3203, C-3204
- **Supersedes:** none (closes the open question of EXP-2026-11-08-M4.17-road-class and EXP-2026-11-08-M4.29-classcode-control-r2; extends C-5961 of EXP-2026-11-20-M4.31-tmc-road-type-link-class)
- **Superseded by:** none

## Question

M4.17 found `class_code` values that were pure for one road class in one
Polish sample and could not tell "road class code" from "numbering, page or
region code"; M4.29 could not test a second country for lack of OSM data.
M4.31 has since read the field as the TMC location type on the EU card
(C-5961). Does that reading hold on a second country without OSM, with a
control that would fail for a numbering or region code, and which firmware
code reads the field?

## Hypothesis

`class_code` is field 0 of the record (the in-file dictionary calls it
`kind code`) and equals `10000·class + 100·type + subtype` of the TMC
location type, class 0 = area, 1 = linear, 2 = point. If so (a) the
reference columns obey the class on every record of every country: `liner
ref` names a linear, `area ref` an area, the offsets a record of the same
class; (b) for roads `L1.x`, the subtype agrees with the road class that
the *syntax of the road number* gives in countries where the number shows
the class, on both cards.

**Falsifier:** a kind code outside class 0–2; a reference to a record of the
wrong class; agreement of subtype and road-number class below 95 % in a
country, or no drop when the kind codes are permuted inside each table.

## Method

1. **Sample and hash.** As above.
2. **Commands.**

   ```sh
   EU=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   US=archive/sd-images/LEAF_2011-2012_US.img
   IMG=archive/head256.img
   W=/tmp/lct; mkdir -p $W
   python3 tools/lctbl_kind.py --selftest
   python3 tools/lctbl_lookup_l3.py extract --card-image $EU -o $W/eu.DAT
   python3 tools/lctbl_lookup_l3.py extract --card-image $US -o $W/us.DAT
   python3 tools/lctbl_kind.py census $W/eu.DAT
   python3 tools/lctbl_kind.py census $W/us.DAT
   python3 tools/lctbl_kind.py roadclass $W/eu.DAT --market eu
   python3 tools/lctbl_kind.py roadclass $W/us.DAT --market us
   python3 tools/lctbl_kind.py kinds $W/us.DAT
   # firmware side
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x003bbfe0 --count 28
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --resolve-with 0x3e00200 --to 0x003bbfe0
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x003a0034 --count 150
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x004d197c --count 50
   ```

   `census` splits every field 0 and follows the reference columns inside
   their table (a reference is a location code, the key of the table's
   B-tree). `roadclass` takes the `L1.x` records with a road number and
   labels them by number syntax only: Czechia `D` / `I/` / `II/` / `III/`,
   Germany `A` / `B` / `L` or `S` / `K`, United Kingdom `M` / `A`, USA `I-` /
   `US-` / `CR-` → `L1.1` / `L1.2` / `L1.3` / `L1.4`. The table's country is
   the high byte of the table code (an ASCII hex digit, M5.60).
3. **Controls.** *Positive*: the synthetic table of `--selftest`. *Negative
   (must fail)*: both tests repeated with the kind codes permuted among the
   records of each table (seed 20261120); in the selftest also class 3 and
   type 0 codes. A numbering, page or region code would pass neither the
   reference test (references cross road numbers and regions) nor keep its
   agreement across four countries with different numbering.
4. **Scope.** EU 2011: 30 tables, 247,089 records, 668,574 resolvable
   references, 4,494 labelled `L1.x` records in three countries. US 2011: 34
   tables, 303,023 records, 999,057 references, 3,358 labelled records.
   Firmware: one build (EU2011), static reading of four functions; the code
   that consumes the copied value was not followed.
5. **Falsifier.** As in Hypothesis.

## Interpretation

- The M4.17 question is settled against "numbering, page or region code".
  All 1,667,631 resolvable references of both cards obey the class that the
  kind code gives their target, and none does not; with permuted codes 36 %
  do. A code tied to numbering or region could not make `liner ref` always
  land on class 1 and the offsets always on the record's own class.
- It is a road class only where the standard makes it one: for linear
  records `L1.1`–`L1.4` (motorway, first, second, third class road). There
  the subtype agrees with the class shown by the road number in 7,831 of
  7,852 records of four countries, two cards. M4.17's "motorway-pure" code
  `0x2775` is `L1.1`; its "secondary-dominated" `0x2777` is `L1.3`; its
  "mixed default" `0x283c` is `L3.0`, a road segment of any class; the
  point codes it saw (`0x4e8e`, `0x4e91`) are junction types. So the LORO
  failure of M4.17/M4.29 was the test, not the field: most joined rows were
  segments and points, whose type says nothing about the road's class.
- The US card is the second country M4.29 lacked. It uses fewer types (31
  against 120) and no exit numbers, but the same code system.
- The firmware reads the field (extractor, decoder slot `+4`, getter) and
  its programmers call it `LocationCode`, where the file's own dictionary
  says `kind code` and the values are location types (3,136 EU records
  share the value 100, so it is not a location's code). The location code
  proper is the key of the lookup (M5.60), not a record field. What the
  consumer after fn `0x004d197c` does with the value is not known.
- The type names used in this record (`L1.1` motorway and so on) are the EN
  ISO 14819-3 location types as remembered, not checked against the
  standard's text; the class/type/subtype split and the tests above do not
  depend on the names.

## Conclusion

`class_code` is the TMC location type of the record (class, type, subtype),
on both cards. For `L1.x` records its subtype is the road class; for other
records it is the kind of area, segment or point. C-1825 is resolved in
that form and M4.35 is closed; a generator must write a valid type for
every record and can take the road class of an `L1.x` record from OSM
`highway`.
