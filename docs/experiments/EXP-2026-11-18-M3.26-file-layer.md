## Question

What does each of the 117 functions in `Navi.exe` `0x00417d00…0x0041cab0`
(EU2011 build A) do, which handler does each dispatcher message reach, and what
do the two M3.2 questions — where the `chunk_size` divisor comes from, and
whether the chunk reader seeks by `.ind` offset or scans for `78 9c` — read off
`0x0041c990`?

## Hypothesis

`none / exploratory`: the block is the map-file layer, the stdio wrappers are
its only filesystem door, and `0x0041c990` is the chunk driver. Falsifier
stated before the run: **a map file read that does not pass through the block**,
i.e. a function that imports `ReadFile`/`MapViewOfFile`/`CreateFileMapping*` and
is reachable from a map path such as `0x0040b358` (the `ADDRE` resolve).

## Method

1. **Sample and hash.** The first 256 MiB of the EU 2011 image, SHA-256 above;
   `Navi.exe` is module build A (`vbase 0x00010000`; section 2 `.pdata` at
   `0x32ed9c…0x558300`, 7,596 records); `Navi.exe` sec0 is uncompressed
   (`rva 0x1000`, file `0x00c8f200`), so both the code and the `0x0017xxxx`
   constants are mapped directly.
2. **Commands.** Runnable as written from the repo root; the graph is rebuilt,
   not reused.

```bash
python3 tools/callgraph.py build archive/head256.img -o g.json
# functions 9000 (leaf targets 1404), direct edges 22867, import edges 7721,
# unresolved indirect calls 589, functions with no static caller 956

python3 tools/callgraph.py path g.json 0x40b358 0x4192c0      # positive control 1
python3 tools/callgraph.py path g.json 0x417924 0x41b4f8      # positive control 2
python3 tools/callgraph.py path g.json 0x40b358 0x3d2218      # negative control
python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe --index 2 0x00417d48
python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe --index 2 0x0041a600
# whole 117-VA sweep, one image parse: build the list from the table itself
awk '/^### The 117 functions/{f=1;next}/^### Block boundaries/{f=0} \
     f&&/^\| `0x/{gsub(/[|`]/," ");print $1}' docs/format/firmware.md > /tmp/opencode/vas.txt
xargs -n 117 python3 tools/nk_decomp.py pdata archive/head256.img \
      --module Navi.exe --index 2 < /tmp/opencode/vas.txt
# expected: 109 lines START, 8 lines GAP, 0 INSIDE
# adjacency of the table: branch table bytes, then the 20-word state table
python3 -c "d=open('archive/head256.img','rb').read(); print(d[0xdf8a88:0xdf8aa4].hex(' '))"
python3 -c "d=open('archive/head256.img','rb').read(); print(d[0xdf8d38:0xdf8d88].hex(' '))"
# byte-level constants in the block (file range of 0x417d00..0x41cab0):
python3 -c "d=open('archive/head256.img','rb').read(); b=d[0x1095f00:0x109acb0]; print(len(b), b.count(b'\x78\x9c'), b.count(b'\x00\x00\x01\x00'))"
# disassembly: the block is 0x4db0 B = 9944 halfwords, one command
python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x417d00 --count 9944 > block.dis
grep -c 'shll16' block.dis      # 12
grep -c 'mov #78,' block.dis    # 2
grep -c ']=0x00010000' block.dis  # 0
python3 tools/sh4xref.py archive/head256.img Navi.exe --to 0x004192c0
```

`/tmp/opencode/vas.txt` is the 117-line list taken from the table's first
column (the graph nodes in `[0x417d00, 0x41cab0)`); `xargs` runs the sweep in
one process. The role map itself is a reading of that one `block.dis`; it uses
no other input.

3. **Controls.**
   - *Positive 1 (read path exists):* `path g.json 0x40b358 0x4192c0` prints
     `0x0040b358 -> 0x004192c0` — the `ADDRE` resolve does call the block.
   - *Positive 2 (chunk path exists):* `path g.json 0x417924 0x41b4f8` prints
     `0x00417924 -> 0x0041b058 -> 0x0041b240 -> 0x0041b3bc -> 0x0041ac28 ->
     0x0041a438 -> 0x00419350 -> 0x0041b4f8`.
   - *Positive 3 (the table read is a table):* the dispatcher's byte table at
     file `0xdf8a88` is `00 06 0c 12 18 1e 24 30 36 3c 46 4c` followed by
     `IOM_CD DEBUG!!!`; `0x417d70` is `braf r0` with delay slot `0x417d72`, so
     the twelve `0x417d74 + offset` targets land on the twelve `mov.l`/`bra`

   - *Negative (the falsifier):* `users` on the Win32 file API returns 13
     functions; `path g.json 0x40b358 <each>` prints `no static path` for all
     13 (e.g. `0x3d2218`, the `MapViewOfFile` wrapper).
4. **Scope.** EU2011 build A `Navi.exe` only; the 117 graph nodes in
   `0x00417d00…0x0041cab0` (109 `.pdata` `START` + 8 `GAP`), the dispatcher

`0x41c8c4` (read from the disassembly): `head` is the 16-byte `.ind` header
buffer `0x41c8da`'s call to `0x41c404` fills. `0x41c8e6 add #8` builds A from
`head+0x8..+0xb` as `b[+0xb]<<24 | b[+0xa]<<16 | b[+0x9]<<8 | b[+0x8]` (the
`0x41c8fc mov.b @r2` byte is read with the original `r2`), and `0x41c8fe
add #4` moves `r2` to `head+12` to build B from `head+0xc..+0xf` the same way.
Both are **little-endian**.
`0x41c924 mov #78` / `shll2` loads `ctx+0x138` and `cmp/eq` it with **B**
(`cmp/eq r3,r8`, `r8` = B), so the compared word is `head+12`; A is compared
only with the quotient (`0x41c962 cmp/gt r2,r9`). The divides are
`0x41c932 _divlu(*r5, B)`, `0x41c93c _divlu(*r5 + r12, B)` and
`0x41c946 _modlu(*r5 + r12, B)` — `r5` is the caller's second argument
(`0x41c8de mov.l @r5,r10`) and `r12` its third; A is **not** a `_divlu`
operand. `0x41c958` decrements the quotient when the remainder is 0 and the
quotient is non-zero. The file itself carries the `0x10000` **as a value**:
in 2,875 of 2,875 factory `.ind` pairs the four LE u32 are
`(logical, compressed, ceil(logical/chunk), chunk)` and `chunk` is `0x10000`
in every one — a value, never a compare against a `0x10000` literal. On the
measured POINT010 `.ind` header these two loads give A = 149 (u32 #2, the
chunk count) and B = 65536 (u32 #3, the chunk size), which is the same
little-endian `(logical, compressed, count, chunk)` layout. `0x41c5f0` opens the `.ind`
through its own `0x41c404` call and reads the header itself (`r9` = LE u32 at
`head+0`, `r10` = LE u32 at `head+4`), then fills 20-byte entries with `+4` =
an offset difference, `+8` = source tag, `+12` = end tag, and `0x41c990`
writes each entry's `+0x10` from a running sum. `0x41c7dc` adds `entry+0x10` to the base in `r13+0x13c`, and calls
`0x00542148` with `r7 = entry+4`, `r6 = entry+16`, `r5 = entry+12`,
`r4 = out`.

## Interpretation

- **FACT:** the 117 addresses are the graph nodes in the range, 109 `.pdata`
  `START` and 8 `GAP`; every `GAP` ends at the next `fn` start and contains an
  `rts`.
- **FACT:** the two dispatch tables are readable constants: 12 message offsets
  at `0x0017a888` followed by the string, and a 20-word table at `0x0017ab38`
  indexed `(state*5 + kind)*4` with `kind < 5` and `0x42af34` (`rts`+`nop`) as
  the empty handler.
- **OBSERVED:** the block is self-contained for file I/O (stdio only through
  the wrappers, `FindFirstFileW`/`FindNextFileW` in `0x418748`), and no
  `ReadFile`/`MapViewOfFile` user has a static path from a map entry — the
  block is the whole map-file layer (C-4440, the negative control).
- **OBSERVED (M3.2a):** the `_divlu` divisor is the `.ind` header word at
  `+8`; nothing in the block loads or compares `0x10000` (0 literal hits, 0
  byte hits), so it is a chunk-count divisor, not a buffer size (C-4446).
- **OBSERVED (M3.2b):** chunks are located through the `.ind` (table built by
  `0x41c5f0`, offsets carried in the 20-byte entries and the descriptor
  callbacks at `0x41ca28`/`0x41ca38`); there is no `78 9c` scan (0 hits in the
  block) (C-4447). This closes the consumer question C-832/C-833 left UNKNOWN.
- **REFUTED:** the earlier M3.2b HYPOTHESIS (C-2063) that the 20-byte entry is
  `+4` offset / `+8` uncompressed / `+12` compressed — `0x41c7dc` adds
  `+0x10` to a base and never reads `+4` as an absolute offset (C-4448).
- **HYPOTHESIS (unchanged):** the entry `+4`/`+8`/`+12`/`+0x10` words are
  consumed by the reader as above; no run exercises them yet (M9.11/M9.44).
- **UNKNOWN:** which of the two header words `0x41c8c4` divides (A by B) is
  the logical size and which is the chunk size — both are `.ind` u32s whose
  order the reader does not consume as four u32s; `0x41c124`'s ops struct in
  `r7` is a per-call vtable, not a global table.

## Conclusion

`docs/format/firmware.md` now carries the 117-row role table with the build
named, the message → handler map, the `(state*5 + kind)` table, and the two M3.2
answers with VAs (C-4440–C-4449). The block is the whole map-file layer under
the stated falsifier (no Win32-file-API bypass with a static path from a map
entry); `tools/l3_harness/targets.json` was not touched (that is M9.44). Still
open: the `.ind` u32 order and the `0x41c124` ops vtable, recorded as

dispatcher's two outside handlers (`0x4178e4` task-info dump, `0x417ab4`

## Corrections after navigator review

Round 0 (driver, before handoff) corrected this record and `firmware.md` after
re-reading the disassembly; each fix is recorded here so the navigator sees
what moved and why:

1. **The second-level table was transposed in the first draft** (`5 x 4` with
   keys listed as "kind 0..3"). The code is `(state*5 + kind)` with
   `state = *0x009cfce0` and `kind = r4 < 5` (`0x00419c42`, `0x00419c60`), i.e.
   a 4-row (state) x 5-column (kind) table; the fifth column was missing. Both
   the table and the `0x419c38` row now carry the fifth column.
2. **The earlier M3.2b entry layout is refuted, not repeated.** The first draft
   said `0x41c7dc` "consumes the compressed pointer+length directly" and kept
   the `+4` offset / `+8` uncompressed / `+12` compressed reading. The code
   adds `entry+0x10` to a base (`0x41c87a`, `0x41c886`) and passes
   `+4`/`+16`/`+12`; C-4448 records the refutation.
3. **The `.ind` header order** in the first draft (`+0/+4/+8/+12` compared
   against `ctx+0x4e*4`) did not match the disassembly: A is built from
   `head+0x8..+0xb` and B from `head+0xc..+0xf`, little-endian
   (`b[+3]<<24|b[+2]<<16|b[+1]<<8|b[0]`), and `ctx+0x138` is compared with B.
   The text and C-4445 now say what the loads do.
4. **Roles that the strings contradicted were rewritten**: `0x419ca0` is a
   mount-state `DIR` dump (not unmount), `0x41a52c` is a disc-volume dump (not
   "MMAIN slots"), `0x419964` prints `STATUS INFOMATION`, `0x41b6e8`'s 12
   `shll16` are size fields, and the default handler `0x417ca0` sits outside
   the block.
5. **"No `0x10000`" is now a counted fact**, not a prose claim: 0/392 pool
   values, 0 byte hits for LE `u32 0x00010000` and 0 for `78 9c` in
   `0x1095f00…0x109acb0`, 12 `shll16`, 2 `mov #78`.
6. **The snapshot moved**: the new EXP adds L3 citations, so
   `docs/research/fn-audit-l3-corpus-2026-11-16.json` was refreshed with
   `--write-snapshot` (906 -> 909 rows for this EXP's citations, then 910
   after round 1 added a `0x0032efa8` citation; `0060a008…` -> `b3ce422a…` ->
   `a591571e…`, and a second write reproduces `a591571e…`) in the same
   commit; the docs base stayed byte-identical (328 rows, same summary).
   Claim numbering moved to C-4440–C-4449 because C-4420–C-4429 are held by
   the open M5.43/M5.44 branches.
7. **Navigator round 1 (CHANGES, 2026-11-18)** found three factual defects, all
   reproduced here before editing: (a) **`0x4180f0` is a graph false edge** —
   `sh4xref --to 0x00417924` prints only `fn 0x0032efa8`, the full
   disassembly of `0x4180f0..0x418146` loads only `0x418d50`/`0x41bbec`, and
   the `0x00417924` literal occurs at exactly one pool in the 256 MiB head
   (`0x32f45c`); C-4440 and `firmware.md` now say one static caller and call
   the second an unestablished graph edge. (b) **the dispatcher branch was
   wrong twice** — `0x417d70` is `braf r0` (`0023`) with delay slot
   `0x417d72`, and `r0 = table[msg-1]`, so `target = 0x417d74 + offset`, not
   `0x417d72 + offset*2`; C-4441, `firmware.md` and Positive 3 carry the
   `braf` reading and the twelve targets. (c) **the `.ind`-header sentence
   contradicted C-4445** — the head is what `0x41c404` returns (not
   `0x41c474` directly), and the compare is against the second loaded word.
   The review's suggested sentence said `_divlu(head+8, head+4)` with B at
   `head+4`; the bytes refute that label — `0x41c8e6 add #8` builds A at
   `head+8`, then `0x41c8fe add #4` moves to `head+12` to build B
   (`head+0xf…+0xc`), so B is `head+12` and the compare word is `head+12`.
   The byte order is little-endian (`b[+3]<<24|b[+2]<<16|b[+1]<<8|b[0]`), and
   the real POINT010 `.ind` gives A = 149 (u32 #2, the count) and B = 65536
   (u32 #3, the chunk), so A/B are the header's `count`/`chunk` words. The
   divides take the caller's word, not A: `_divlu(*r5, B)` /
   `_divlu(*r5+r12, B)` / `_modlu(*r5+r12, B)`. The measured file answer is in
   the Observations (2,875/2,875 `.ind` pairs: `(logical, compressed,
   ceil(logical/chunk), chunk)`, `chunk == 0x10000` always); the text keeps
   "a `0x10000` value in the file, no `0x10000` compare in the layer" apart
   instead of implying the layer never meets the number.
