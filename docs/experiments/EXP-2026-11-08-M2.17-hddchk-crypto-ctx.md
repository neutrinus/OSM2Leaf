## Question

What is the source/population path of `SilentAuthenticate` `ctx+120` (the
20-hex-char / 10-byte decoded attestation field), what inputs feed the
`sub_0001e3f4` range `0x1e582–0x1e5e8` (XOR/seed/compare path), and can an
`HDD_CHK.ATT` generator be produced without a factory sample or without device
state?

## Hypothesis

None / exploratory (follow-up to M2.16). **Falsifier (ctx+120):** a static
store chain that populates the 20-hex `ctx+120` field from a card file, a
constant, or a derivable value with no device dependency. **Falsifier
(0x582–0x5e8 inputs):** the operands do not depend on the `*0x21100` id-5/id-6
dispatch or can be computed from card-only data. **Falsifier (feasibility):**
all inputs (ids 5/6, ctx+120 value, sub_1e330 binding) are statically
derivable.

## Observations

### 1. `ctx+120` in `SilentAuthenticate` (VA `0x1c210`, sec1 file `0x434f410`)

- Entry: `r8=ctx`, `r11=flag` (0x1c226/228). Flag selects HDD_CHK path:
  `flag!=0` → `\SystemSD\HDD_CHK.ATT` (pool `0x1c3f4`=`0x13cc4`, ctx code 108)
  via `CreateFileW` (pool `0x1c3f8`→IAT, `jsr 0x1c26a`); `flag==0` →
  `\UserSD\HDD_CHK.ATT` (pool `0x1c3fc`=`0x13c9c`, 107) (`jsr 0x1c27c`).
  Positive control string/API path: `GENERIC_READ/OPEN_EXISTING/ReadFile 0x80`.
- File read into `ctx+0x11a` (0x1c2a6–2ce, `r10=r8+0x11a` via word `0x011a` at
  `0x1c3ec`); requires `bytesRead==0x80` (0x1c2d8–2de).
- **`ctx+120` source read:** `0x1c2e0: e408 mov #8,r4`; `0x1c2e2: 6983 mov r8,r9`;
  `0x1c2f0: 7978 add #120,r9` => `r9 = ctx+120`. The 20-hex-char field is read
  from `ctx+120` and decoded (10 iterations, pairwise `sub_19eb4` hi/lo nibbles,
  C-1872) into 10 bytes at `r14+8` (0x1c31a–344). CRC16 of those 10 bytes must
  be 0 (C-1873, `CApi_MakeCRC16` IAT `0x21104`); on CRC==0 calls
  `sub_1e3f4(file_buf=ctx+0x11a, decoded=r14+8, bytesRead=0x80)` (0x1c35a–362).
- **Callers (`sh4xref --to 0x1c210`):** `fn 0x1ccfc` loads pool `0x1cf1c`=`0x1c210`
  and calls `jsr @r3` at `0x1cdd4` (r5=1, SystemSD) and `0x1ce46` (r5=0, UserSD);
  before each it sets `r4 = @(8,r8)` (`0x1cdd0`/context at `0x1cd16` loads from
  caller ctx+8). `fn 0x1cee8` calls at `0x1d002` (r5=0, pool `0x1d058`). Thus
  `SilentAuthenticate`'s `ctx` is `caller_ctx->+8` (a subobject); `ctx+120` is
  `subobj+120` of that caller subobject.
- **Population of `ctx+120`:** not closed statically in this pass. No direct
  `@(120,…)` byte-displacement store was found by a text scan of disassembly
  (120 is not encodable as a single SH-4 `mov.b/w/l @(disp,Rn)` immediate
  displacement for byte/word; stores may use computed base+120). HDD_INFO.TXT
  UTF-16LE path strings (corrected module VAs, see §4) are referenced by
  `fn 0x1b0fa` (pools `0x1b2bc`→`0x12c80` load `0x1b19a`, `0x1b2b4`→`0x12cc0`
  load `0x1b17c`), `fn 0x1bad0` (`0x1bd48`→`0x12c80` load `0x1bc8c`),
  `fn 0x1c3ec` (`0x1c5a8`→`0x12c80` loads `0x1c488`,`0x1c55a`), `fn 0x1d268`
  (`0x1d394`→`0x12cc0` load `0x1d330`). A dataflow from these HDD_INFO readers to
  `subobj+120` of the `SilentAuthenticate` callers was **not** established here.

### 2. `sub_0001e3f4` range `0x1e582–0x1e5e8` (VA `0x1e3f4`, file `0x43515f4`)

(`0x1e41c–44c`); id-6 4B→8 hex nibbles to `* *0x212c8+8` (`0x1e44e–4c2`);

### 3. Device/provider inputs: id-5 and id-6 (`*0x21100`)

- `sub_199b8` (`0x199b8`, pool `0x199fc`→`0x21100`): sets `len=8`@`r15+16`,
  zeroes `0x80` bytes at `0x21140` (`memset` pool `0x199f8`), calls
  `(* *0x21100)(r4=5, r5=0x21140, r6=&len)`; on `r0!=0` returns `r9=0x21140`.
  Output: 8 bytes (`*0x21140` copied to `* *0x212c8[0..7]` at `0x1e426–44c`).
- `sub_19978` (`0x19978`, pool `0x199b0`→`0x21100`): calls
  `(* *0x21100)(r4=6, r5=r15+16, r6=r15+20)` with 4-byte out; on success returns
  `sub_1d948(out)`. The 4-byte value is rendered to 8 hex-ASCII nibbles
  (`&0xf + '0'`, no A–F branch in `0x1e454–4c4`) stored at `* *0x212c8+8`.
- `*0x21100` is a global dispatch pointer at VA `0x21100` (sec2, realaddr
  `0x21000`, vsize `0x771`, psize `0x106`, flags `0xc0300040`, **compressed**).
  Literal refs in sec1 at pools `0x199b0`,`0x199fc`. `*0x21300`/`*0x21760`
  (used by `sub_1e760`/`1e7c8` path via `0x1e9c0`/`0x1eaa0`/`0x1ed9c`, pools
  `0x1e7b8/7c0/828/82c`) are in the same compressed sec2. **The runtime pointer
  values and provider identity are not readable statically.** `MapUpdate.exe`
  imports only `COREDLL.dll` and `CEDDK.dll` (no crypto DLL import), so the
  provider is obtained/initialized at runtime (init path not in uncompressed
  sec1 pools resolved here).

## Interpretation

- **FACT (0x1e582–0x1e5e8):** the range XORs `decoded[0..7]` (ctx+120-derived,
  C-1872) with id-5 material `*0x212c8[0..7]` in place at `*0x212cc`, seeds
  `*0x212d0=[xored,~xored]`, copies the 0x80B file buffer, builds a type-2/0x80
  stack ctx, optionally runs `sub_1e760/1e7c8`, and calls `sub_1e330(file_copy,
  xored@*0x212cc, bytesRead, *0x212d0)`. VAs/inputs tabled above.
- **FACT (ids):** id-5 returns 8B, id-6 returns 4B→8 hex nibbles, both via
  `(* *0x21100)(id,...)` (sub_199b8/19978). `*0x21100/*0x21300/*0x21760` are in
  **compressed sec2** and their runtime values/provider are unreadable statically.
- **OBSERVED (ctx+120):** `ctx+120` is the 20-hex CRC16==0 attestation field
  read by `SilentAuthenticate` (C-1872/C-1873) from the caller-supplied subobj
  (`caller->+8`); HDD_INFO path readers exist in other MapUpdate functions, but
  the dataflow/population of `ctx+120` was not closed statically.
- **UNKNOWN / BLOCKER:** (1) provider identity and semantics of `*0x21100` ids
  5/6 (device-bound? derivable?) — compressed-data pointer + runtime init;
  (2) origin/generation rule of the ctx+120 20-hex value; (3) full
  sub_1e2d4/1e330 binding and on-disk `HDD_CHK.ATT` record layout; (4) no
  genuine `HDD_CHK.ATT` sample on factory EU/US (C-2090/C-2091). A generator is
  **not feasible** from static evidence alone: at minimum the id-5/id-6 provider
  outputs and the ctx+120 source rule are missing, and ids 5/6 are delivered via
  a runtime dispatch through compressed data (device/provider state cannot be
  assumed derivable).
- **HYPOTHESIS:** id-5/id-6 are device/security identifiers supplied by a
  runtime provider object referenced from sec2; falsified only by resolving
  `*0x21100` init to a pure function of card/verifiable data.

## Conclusion

M2.17 traces the `sub_0001e3f4` `0x1e582–0x1e5e8` path to concrete inputs:
`decoded` (ctx+120, 10B) is XORed with **id-5** (8B, `*0x21100` id=5) at
`0x1e582–590`, seeded/inverted into `*0x212d0`, and verified via `sub_1e330`
together with the 0x80B file buffer and optional `*0x21300/*0x21760` transforms.
`ctx+120` is read by `SilentAuthenticate` (`r8+120`, C-1872) from the caller
subobject (`fn 0x1ccfc/0x1cee8` pass `caller->+8`), but its population/source
(20-hex CRC16==0 value) is not statically closed. **Ids 5 and 6 are obtained via
`(* *0x21100)` whose pointer lives in compressed sec2 — runtime provider,
unreadable statically — so both are treated as unavailable without
hardware/runtime resolution.** Therefore an `HDD_CHK.ATT` generator is **blocked**
(missing id-5/id-6 provider outputs, missing ctx+120 generation rule, no
factory sample, crypto dispatch unresolved). `docs/format/validation.md` updated;
claims C-2610–C-2616 added.

**M5.11 impact:** `HDD_CHK.ATT` is read only by `MapUpdate.exe` (B), not by
`Navi.exe` at boot/map load (C-1870/M2.12). It does **not** gate the
L1/L2/map-data acceptance path that M5.11 targets. M5.11 is unaffected unless a
deliverable includes running the updater path (out of scope for a generated map
card).
