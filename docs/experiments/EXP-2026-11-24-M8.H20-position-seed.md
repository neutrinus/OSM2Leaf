## Question

Can a host-written flash file make `Navi.exe` boot with a chosen start position, so two L4 boots of the EU card request two different, coordinate-matching map tiles — and can the exact flash record offset and checksum be derived from the firmware structure rather than guessed?

## Hypothesis

The start position reaches `Navi.exe` through the object store (`OBJ_CarPos_read` at init, EU fn START `0x003eba78` → `0x00403504`, import slot `0x0055d280`), whose value is restored from the flash backup after reboot. If that restore record's offset and checksum were known, `ze0_seed.py` could write the packed word (`coord.py position`) and two seeded boots would read `B48R058R.DAT` vs `B48R060R.DAT`. Falsifier: both boots read the same tile, or the firmware rejects the record (Stop condition).

- O2 (ROM structure, printed): `romhdr` → `nummods=0x95` (149), `physfirst=0x8cae1000`, `physlast=0x8e233c88`, ROMHDR file `0x01951b78`; `cerom.py modules` → `OBJDLL.dll vbase=03480000`, 4 objects. `sh4xref --to 0x00d940e4` finds 8 literal-pool loads, each in a `.pdata` START (`0x003eba78`, `0x003f6b1c`, `0x00403564`, `0x00407160`, `0x0040acb8`, `0x0040b5ac`, `0x0040b6b0`, `0x00415a3c`). `sh4xref --calls 0x00403504` shows the two `jsr @r3` imports `OBJDLL!OBJ_CarPos_initPrm` (`0x003d188c`) and `OBJDLL!OBJ_CarPos_read` (`0x003d1880`) — an indirect call through the IAT, exactly the pattern the repo warns about.
- O3 (backup backend, printed): `ce_strfind --encoding all OBJ_BackUp` → 19 hits in `OBJDLL.dll` at `rva=0x1eb4/0x1ecc` (ASCII `OBJ_BackUp_Load Error`, `OBJ_BackUp_Save Error`) and UTF-16LE strings at `rva=0x26e6…0x298c` (`OBJ_BackUpInfo.*`). `sh4xref --to 0x03481eb4` finds literal pools at `0x03495cdc`, `0x03495d80`, `0x03495ebc` loaded in functions `0x03495c4c`, `0x03495ce8`, `0x03495e28` (all `[pdata]`). Disassembly of `0x03495c4c`/`0x03495ce8` shows each function calls `0x03495bb8` (bounds check against a table pointer at `0x01e54ee4`), then `0x0349874c` which computes `r4*36` (56-byte stride) plus a base at `0x03482c68`, then `0x03495a5c` (a 64-byte scratch / `0x1f40`-size operation) and `0x03497b64`-family calls. The imports of `OBJDLL.dll` are `commondll!CApi_CommitSram/GetSramVirtualAddress{,i}` and OSMDLL slots only; no FMD/flash IOCTL is imported by OBJDLL. The backup manager name `OBJ_BackUpMgr` appears only as a task-name string in `Navi.exe` (`rva=0x11ec`).
- O4 (no record in the committed image, printed): rebuilding the anonymous flash in memory gives 8,388,608 bytes; all four `SMST` stores validate. Searching it for the five known position words (`0xa6a1cde3`, `0x98d09737`, `0x9c03a3c0`, `0xa6c6d6c0`, `0xa747d079`) gives **0 hits each**. So the anonymous flash carries no position word to select or patch, and the record format is not visible in the committed data.
- O5 (L3 positive control, printed): `datask_l3.py mount` with `--position 51.70,17.45` prints `MAPAL001/B48R058R.DAT` as the second read; with `--position 52.37,4.90` prints `MAPAL001/B48R060R.DAT`. Both end `state 2 … tile files 46 … reads 2`, `tile reads parsed by the firmware: 2`. The harness documents that it writes the RAM word directly and stubs `OBJ_CarPos_initPrm`/`OBJ_CarPos_read` — it does not feed a flash record through the object store.
- O6 (negative mutation, printed): byte-swapping `0xa6c6d6c0` → `0xd6c0a6c6` decodes to (115.666667, −78.5); `swapped != original: True`. A big-endian or otherwise wrong-order seed is rejected by the encoder's own round-trip, so the mutation gate holds at the encoding level.
- O7 (Precheck, printed): `bash run.sh --help | grep -ci 'flash\|start-position'` → `0`; `test -e tools/ze0_seed.py` → `ABSENT`. These were to be produced by this task; no L4 seed run was possible without a derived format.
- O8 (decision gate): the flash→object-store restoration path is the OBJDLL backup manager, whose record frame and checksum are **not derived** by the commands above: the 56-byte stride table at `0x01e54ee4`, its 36-byte records at the `0x03482c68` base, and the `0x1f40`-size scratch are observed structure, but none of them was shown to hold a CarPos word or to accept a checksum we can compute. M8.H19 (C-7167) already records the restorer as UNKNOWN and refuted the only candidate store (VSram block `0x8e`). With no real dump on this machine (the M6.18 backup exists only outside the repo), there is no second witness to pin the format. Inventing one would violate "derive the signature; do not guess it from the doc".

## Interpretation

- **FACT:** the encoder, the two EU tile names, the 149-module ROM structure, the eight literal-pool loads of the RAM word, the OBJDLL backup-manager functions, and the L3 position→tile change (C-7169) are all reproduced by the commands above.
- **OBSERVED:** the anonymous 8 MiB flash contains none of the five known position words; the backup backend uses a 56-byte-stride table and a 36-byte-per-record base, but no record is tied to a CarPos word.
- **UNKNOWN:** the exact on-flash offset, record layout and checksum of the persisted last position, and which code restores it into the object store. This is the same UNKNOWN M8.H19 left open (C-7167), not a new guess.
- **Result:** the task's prerequisite fails before the falsifier can be exercised. No `ze0_seed.py` format was invented; no `run.sh --start-position` was added with a fake format; no L4 boot was run; no native-persistence or rule-13 L4 acceptance claim is made. Per the PLAN REV 2 decision gate agreed with the navigator, the honest status is `blocked` with an unblocking task for the record-location research.
