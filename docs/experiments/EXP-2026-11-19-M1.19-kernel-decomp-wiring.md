## Question

Once the kernel's own routine (`DECOMP_SECT 0x88037464`, H51) is called from
`cerom.py`, the L3 memory map and the `cmp_ind` targets, does every
compressed section of build A decode to exactly its `comphdr`
`uncompressed_len`, and do the registered readers run on the image's own
`INIT` bytes instead of a declared table?

## Hypothesis

H51 decoded 245/245 build-A sections with `nk_decomp check` but compared
only the return value. Expected: `r0 == uncompressed_len` for all 245 EU2011
(and the 249 US2011) sections; `cmp_ind_reader` passes with sec1 mapped from
the image and the same instruction count as with the declared table (M9.40
already read the 17 mask words); the M9.35 probes reach the same next stop,
because nothing before it reads `INIT`.
**Falsifier:** any section with `r0 = -1` or `r0 != uncompressed_len`; a
`cmp_ind` run that changes verdict or `insns` once the image bytes replace the
declared table; a run with sec1 zero-filled (no mask) that still passes (the
bytes would then not be load-bearing); a probe whose next stop is an `INIT`
read under the guard.

## Method

1. **Sample and hash.** As above; the cache key is SHA-256 over (stored
   bytes, `vsize`), so the EU and US images share identical sections.
2. **Commands.**
   ```bash
   export OSM2LEAF_DECOMP_CACHE=/home/user/scratch/m1.19/decomp
   S=/home/user/scratch/m1.19; EU=archive/head256.img; US=archive/us256.img
   F=/home/user/scratch/factory-eu/REFER001
   # selftests (synthetic)
   python3 tools/nk_decomp.py --selftest
   python3 tools/cerom.py --selftest
   python3 tools/l3_harness/runner.py --selftest
   python3 tools/va_class.py --selftest
   python3 tools/l3_precond.py --selftest
   python3 tools/reader_precheck.py --selftest
   # precheck + the full decode (fills the cache; ~25 min on the shared 4-CPU host)
   python3 tools/nk_decomp.py section $EU --module NaviMapCC.dll --index 1
   python3 tools/nk_decomp.py check $EU --cache --json $S/check_eu_A.json
   # done-when 1: r0 == comphdr uncompressed_len for every section
   python3 tools/cerom.py --image-start 0x200200 $EU decompress --check
   python3 tools/cerom.py --image-start 0x200200 $EU decompress --check --json > $S/cerom_eu_A.json
   python3 tools/cerom.py --image-start 0x200200 $US decompress --check --json > $S/cerom_us_A.json
   python3 tools/cerom.py --image-start 0x200200 $EU decompress --check --method lzss   # codec path unchanged
   # done-when 2: cmp_ind readers with the image's sec1 bytes
   python3 tools/l3_harness/runner.py run cmp_ind_reader --image $EU --cmp $F/POINT010.DAT.cmp --ind $F/POINT010.DAT.ind --init-from-image --json
   python3 tools/l3_harness/runner.py run cmp_ind_reader --image $EU --cmp $F/POINT010.DAT.cmp --ind $F/POINT010.DAT.ind --init-from-image --mutate corrupt-ind --json
   python3 tools/l3_harness/runner.py run cmp_ind_reader_us2011 --image $US --cmp $S/us/POINT010.DAT.cmp --ind $S/us/POINT010.DAT.ind --init-from-image --json
   python3 tools/chunk_decoder_l3.py run $EU --cmp $F/POINT010.DAT.cmp --ind $F/POINT010.DAT.ind --sec1 image
   python3 tools/chunk_decoder_l3.py run $EU --cmp $F/POINT010.DAT.cmp --ind $F/POINT010.DAT.ind --sec1 zero
   # done-when 3: M9.35 probes with real INIT bytes, and the guarded control
   python3 tools/cerom.py --image-start 0x200200 $EU memmap --modules Navi.exe --out $S/memmap_navi_eu.json
   python3 tools/l3_harness/rommap.py convert --report $S/memmap_navi_eu.json --out $S/rommap_init_eu.json --init-from-image --image $EU --image-start 0x200200 --resolve-with 0x3e00200
   python3 tools/l3_harness/rommap.py convert --report $S/memmap_navi_eu.json --out $S/rommap_guard_eu.json --bss-zero --init-guard --image $EU --image-start 0x200200 --resolve-with 0x3e00200
   P=tools/l3_harness/probes/m1.19-init-probes.json
   python3 tools/l3_harness/runner.py run mmain_reader_probe --targets $P --rommap $S/rommap_init_eu.json --image $EU --engine pysh4 --json
   python3 tools/l3_harness/runner.py run drstr_sub_00419350_probe --targets $P --rommap $S/rommap_init_eu.json --image $EU --engine pysh4 --json
   python3 tools/l3_harness/runner.py run mmain_reader_probe --targets $P --rommap $S/rommap_guard_eu.json --image $EU --engine pysh4 --json
   python3 tools/l3_harness/runner.py run drstr_sub_00419350_probe --targets $P --rommap $S/rommap_guard_eu.json --image $EU --engine pysh4 --json
   python3 tools/va_class.py $EU --module Navi.exe --resolve-with 0x3e00200 0x00574de0
   ```
3. **Controls.** *Positive:* NaviMapCC.dll sec1 (H51's `r0=0x484`); the
   declared-table `cmp_ind` run (M9.32) as the reference counters.
   *Negative:* `--method lzss` on the same 245 sections (the pure-Python
   codec must still fail); sec1 mapped as zeros (`--sec1 zero`) must not
   pass; `--mutate corrupt-ind` must be rejected; synthetic: `r0 = -1` is
   never cached (nk_decomp selftest), `r0 != uncompressed_len` is refused
   (cerom selftest), a tampered cache file is `BLOCKED` (runner selftest),
   `--init-from-image` with `--init-guard` is refused.
4. **Scope.** Build A only (EU2011 245, US2011 249 compressed sections);
   builds B/C (133 + 113 sections each) are not run here. `cmp_ind`: one
   factory pair per build (M9.32 already covered S1/S2 with the declared
   table). Probes: two scratch module probes, context-less, no verdict.
5. **Falsifier.** As in the Hypothesis, stated before the results.

## Interpretation

- **FACT:** the kernel routine decodes every build-A compressed section of
  EU2011 to exactly its `comphdr` `uncompressed_len` (245/245, 1,674,478 B):
  H51's count is now a length check, and `cerom.py decompress --check` says so
  (C-3500). The same holds for US2011 (249/249, 1,684,059 B; C-3501).
- **FACT:** `cmp_ind_reader` (EU2011) and `cmp_ind_reader_us2011` pass on the
  image's own sec1 bytes with the declared-table counters unchanged; the
  inflate_mask words at `0x00574de0` / `0x005987b0` equal `2^n - 1`, so the
  HYPOTHESIS note in `targets.json` is replaced by a read (C-3502–C-3504).
  The zero-sec1 run fails, so the image bytes are load-bearing.
- **OBSERVED:** both M9.35 probes stop at a bound-but-unmodelled import
  (`wcstombs`, `OSM_Malloc`) before any `INIT` read; the guarded control
  shows the same stop, so real `INIT` bytes neither help nor hurt them yet
  (C-3505). Their next blocker is stubs/context (M9.24), not data.
- **OBSERVED:** `drstr`'s stop moved since M9.35 (`UNMAPPED 0xfffffec6` then,
  `OSM_Malloc` now) under both models; the change predates this task.
- **UNKNOWN:** builds B/C on either image (246 sections each, not run).
- **OBSERVED:** 55 of the 249 US2011 build-A sections are byte-identical (stored bytes and `vsize`) to an EU2011 section.

## Conclusion

`nk_decomp` now has a cached library interface (`section_init`,
`section_bytes`, `load_image`, `DecompError`) that `cerom.py decompress`,
`rommap.py --init-from-image`, `runner.py` and `chunk_decoder_l3.py` call;
`INIT` is printed `INIT (readable: nk_decomp)` and `l3_precond`/`reader_precheck`
no longer call it an M1.2f blocker. Both `cmp_ind` targets read their table
from the image (no declared values). Claims C-3500–C-3506 registered;
`reader-coverage.md` row 6 updated. Per rule 15, M1.2f and M8.E1 close as
superseded (M1.2e, M1.2g, M8.E1c, M9.29, M9.30 were already closed by H81).
M1.4 stays blocked: its Unblock is M1.21 (`FILESentry` payloads, which are not
`o32` sections and are not decoded here).
