# EXP-2026-11-06-M2.11: trigger and retry logic of the `HDD_INFO.TXT` reader (`fn 0x004dd028`)

- **Status:** done
- **Date:** 2026-11-06
- **Sample:** `archive/images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`
  (8,057,257,984 bytes, SHA-256
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`);
  the tools read the first 128 MiB, whose SHA-256 is
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (same `IMG256` pin as C-856).
- **Module:** build A, `Navi.exe` module #101, `.text` realaddr
  `0x00011000`, psize `0x0054be00`; producer module `NaviSetCC.dll`
  module #96, `.text` realaddr `0x02e31000`, psize `0x0002a400`.
- **Claims:** C-1770–C-1779
- **Supersedes:** none (corrects the prose of EXP-2026-11-05-M2.1, not a claim)
- **Superseded by:** none

## Question

M2.11 done-when: name the "table" at `0x004dd2e4`, the caller of that entry,
why `fn 0x004dd028` reads `HDD_INFO.TXT` twice, what the `Sleep` loop waits
for, and what the `wcsncmp` compares against. In other words: is the read
triggered at boot, on SD insert, or from a menu, and what is the retry logic?

## Hypothesis

`none / exploratory`. The only prior facts were: `fn 0x004dd028` calls the
parser `fn 0x004e7b8c` twice and `Sleep`/`wcsncmp` once, and its only literal
reference is the pool word `0x004dd2e4` (EXP-2026-11-05-M2.1, C-1710/C-1711,
C-720).

## Observations

### 1. `0x004dd2e4` is a literal-pool word, not a table

`--to 0x004dd2e4` gives exactly one reading:

```
pool 0x004dd2e4 holds 0x004dd028
  load 0x004dd2b4 (r3)  fn 0x004dd270  jsr 0x004dd2b6
```

The 7-word block `0x004dd2d0`–`0x004dd2eb` sits immediately after the `rts`
of the previous function (`0x004dd2ca`, delay slot `0x004dd2cc`) and its
words are exactly the constants of `fn 0x004dd270`:

| Slot | Value | Load | Role in `fn 0x004dd270` |
| --- | --- | --- | --- |
| `0x004dd2d0` | `0x00b00224` | `0x004dd278` | `g_init` pointer/flag |
| `0x004dd2d4` | `0x00b0022c` | `0x004dd28a` | `CRITICAL_SECTION` |
| `0x004dd2d8` | `0x0053a2ac` | `0x004dd28c` | `COREDLL!EnterCriticalSection` thunk (#4) |
| `0x004dd2dc` | `0x00b00220` | `0x004dd292` | `g_ready` flag |
| `0x004dd2e0` | `0x0053a5e8` | `0x004dd2a4` | `Errlogdll!ErrorLogMsg` thunk |
| `0x004dd2e4` | `0x004dd028` | `0x004dd2b4` | the worker function |
| `0x004dd2e8` | `0x0053a2a0` | `0x004dd2bc` | `COREDLL!LeaveCriticalSection` thunk (#5) |

There is no array base, no RTTI and no self-pointer: it is the compiler's
literal pool for one function. The M2.1 wording "dispatch/vtable entry" is
prose, not a claim; this record replaces it.

### 2. Caller `fn 0x004dd270` (lock + policy switch)

Key words: `0x004dd278 d215`, `0x004dd280 2228` (`tst r2,r2`),
`0x004dd282 8f02` (`bf/s`), `0x004dd292 d212`, `0x004dd298 8b0c` (`bf`),
`0x004dd2a2 e485` (`mov #-123,r4` -> `extu.b` = `0x85`),
`0x004dd2ac 430b`, `0x004dd2b4 d30b`, `0x004dd2b6 430b`.

Decoded flow:

```
if (*(u32*)0x00b00224 == 0) return 0xff;
EnterCriticalSection(&0x00b0022c);
if (*(u32*)0x00b00220 == 0)
    ErrorLogMsg(0x85, 0, 0, 11, 1, 0);   /* r4=0x85,r5=0,r6=0,r7=11, stack 1,0 */
else
    rc = fn_004dd028();
LeaveCriticalSection(&0x00b0022c);
return rc;
```

`--to 0x004dd270` finds one reference:

```
pool 0x004beb4c holds 0x004dd270
  load 0x004beaf8 (r3)  fn 0x004beae0  jsr 0x004beafa
```

### 3. Handler `fn 0x004beae0` and the message that reaches it

`fn 0x004beae0` calls, in order, `0x004dd61c` (init), `0x004dd270`
(read/compare, result in `r8`), `0x004dd700` (validate, only if `r8 == 0`)
and `0x004dd214` (teardown), logging each result through `0x004be4ec`.
`--to 0x004beae0` gives:

```
pool 0x004bdeb8 holds 0x004beae0
  load 0x004bde00 (r3)  fn 0x004bda20  jsr 0x004bde02
```

The enclosing dispatcher starts at `0x004bda44` (`0x004bda44 4f22`,
`0x004bda46 7ff0`, `0x004bda48 5241` = `mov.l @(4,r4),r2`; the
`function_start` heuristic reports `0x004bda20`, which is the **literal pool**
of the previous function — `0x004bda20` holds `0x00387f74`, not code). The
dispatcher compares `[r4+4]` against a binary-search set of `0x8410xxxx`
ids. The case for `0x841000f7` is:

```
0x004bddea d330      mov.l @0x004bdeac,r3 =0x841000f7
0x004bddec 3230      cmp/eq r3,r2
0x004bddee 8907      bt 0x004bde00
0x004bde00 d32d      mov.l @0x004bdeb8,r3 =0x004beae0
0x004bde02 430b      jsr @r3
```

Neighbour handlers: `0x841000f6` -> `0x004be540`, `0x841000f8` ->
`0x004c64e4`; `0x841000f5`/`f9`/`fa` go through the table at
`0x0018a0e8`+ (`0x841000f5` -> `0x004c8240`). `0x841000f6`/`f7`/`f8` are
hard-coded switch cases, not table entries.

### 4. The only producer of `0x841000f7`: `NaviSetCC.dll`

A 4-byte scan over all uncompressed sections finds the literal `0x841000f7`
only in:

| Module | Address | Context |
| --- | --- | --- |
| `NaviSetCC.dll` | `0x02e3ef14` | literal pool of routine `0x02e3eef8` |
| `Navi.exe` | `0x004bdeac` | the dispatcher case above |

The adjacent table entry `0x02e3ef18` does **not** hold the id as a literal;
it builds a message descriptor from its `r5` argument (the caller supplies the
id), so it is not counted as a second producer here.

`0x02e3eef8` (words `6042 e700 9307 d504 033e 430b e600`) decodes as:

```
r0 = *(u32*)r4;                 /* object/interface pointer */
r5 = 0x841000f7;
r3 = 0x278;                     /* method offset */
r3 = *(u32*)(r0 + r3);
jsr @r3;                        /* r6 = 0, r7 = 0 */
```

so it sends request id `0x841000f7` with `wParam = 0`, `lParam = 0`. The
method pointer is stored twice, at `0x02e335b4` and `0x02e34494` (offset
`+0x74` in both), in two identical C++ function-pointer table copies at
`0x02e33540` and `0x02e34420` (`NaviSetCC.dll`; `DllGetClassObject` at RVA
`0x185cc` shows it is an in-proc COM server).

The adjacent table entry `0x02e3ef18` (offset `+0xa8` in the same two
tables) builds a global message descriptor at
`0x01d154b8`/`0x01d15498` and jumps through the thunk at `0x02e58cf4`
(`jmp @` through the global at `0x01d14214`). It receives the message id in
`r5`; the literal `0x841000f7` is not stored in it, so the producer claim
rests on `0x02e3eef8`.

### 5. Why `fn 0x004dd028` reads the file twice

`fn 0x004e7b8c`'s arguments are `r5` = source selector and `r6` = output
struct; `r4` (the device object) is **saved nowhere and never read** before
it is overwritten at `0x004e7bcc`. The selector is tested at
`0x004e7bde`/`0x004e7be6`:

| `r5` | Path literal | Literal VA |
| --- | --- | --- |
| 0 | `\SystemSD\VER_INFO\HDD_INFO.TXT` | `0x001d5168` (pool `0x004e7d2c`) |
| 1 | `\UserSD\VER_INFO\HDD_INFO.TXT` | `0x001d51a8` (pool `0x004e7d28`) |
| other | log error 21, return 0 | — |

Each call does its own `_wfopen` (`COREDLL` #1145) + `fgetws` (#1143) +
`fclose` (#1118); there is no cached handle, so "twice" means **two files**,
not a retry. `fn 0x004dd028` calls it at `0x004dd15e` with `r5=0` into the
stack struct at `r15+32` and at `0x004dd16c` with `r5=1` into the struct at
`r15+0xb8` (`r10 = r15 + extu.b(-72)`). The first argument passed by the caller
(`*0x00b00244`) is dead.

The parser fills six inline wchar fields per struct:

| Field | Offset | Buffer wchar | Max line |
| --- | --- | --- | --- |
| 0 | `+0x00` | 12 | 11 |
| 1 | `+0x18` | 12 | 11 |
| 2 | `+0x30` | 13 | 12 |
| 3 | `+0x4a` | 12 | 11 |
| 4 | `+0x62` | 12 | 11 |
| 5 | `+0x7a` | 13 | 12 |

The factory sample `VER_INFO/HDD_INFO.TXT` (2011, 2014 and 2016) has six
CRLF lines: `QSD-302-100`, `QSD-309-101`, `02-110100-00`, `SDC08-EVEUR`,
`11-05`, `470323501005` — all within the field limits (line 1 is 11 wchar).

### 6. What the `Sleep` loop waits for

After creating the objects (`0x004dd2ec` -> the 0x5a0 model,
`0x004dd388` -> the 28-byte object and `SDC1:`; `0x004e7940` opens `DSK8:`),
the worker does:

```
g_flag = 0;                                  /* 0x00b00228 */
do {
    if (!fn_004e787c(*g_dev, &status)) return 0xff;   /* 0x004dd104 */
    if (status == 4) break;                            /* 0x004dd110 */
    if (count == 5) {                                  /* 0x004dd116 */
        if (status == 1) return 1;                     /* 0x004dd148 */
        return 0xff;
    }
    Sleep(100);                                        /* 0x004dd11c, r4=100 */
    count++;
} while (count <= 5);                                  /* 0x004dd124/126 */
```

`fn 0x004e787c` is the status query. It takes the handle at `*(u32*)0x00b00244`
and issues `DeviceIoControl` (`COREDLL` #179) on `SDC1:` with IOCTL
`0x80032004`, input a 2-byte value 1, output a 4-byte status; it retries up to
4 times with `Sleep(50)`. It decodes the masked status (`& 0x7fffffff`) as:

| raw | out | meaning |
| --- | --- | --- |
| 1 | 1 | — |
| 2 | 2 | — |
| 4 | 4 | the value the worker waits for |
| 8 | 8 | — |
| other | 0xff | — |

So the loop polls the `SDC1:` device state every 100 ms, six times (five
`Sleep(100)` calls), and proceeds only on state 4. State 1 on the last poll is
treated as "no card / not applicable" and returns success **without reading
the files**. Any other timeout gives `0xff`.

### 7. What `wcsncmp` compares

The direct call is `0x004dd17c` (`d31c` = wcsncmp thunk `0x0053a4bc`,
`COREDLL` #65) with:

```
r4 = struct A (r15+32)      /* SystemSD copy, field 0 */
r5 = struct B (r15+184)     /* UserSD copy, field 0 */
r6 = 11                     /* 0x004dd178 e60b */
```

So it compares the first 11 wchar of the **first line** of the two copies
(`QSD-302-100` on the factory cards). There is **no literal string** in this
call; the decimal task note "(string at its literal)" does not apply to
`0x004dd028` itself. The only literal in the chain is inside the numeric
helper `fn 0x004e7d4c`, which calls wcsncmp with `L"000"` at `0x001d51e4`
(pool `0x004e7dcc`) and length 3 at `0x004e7da2`, after copying `s+10` with
`wcsncpy` (#66, `n=3`: the last two wchar plus the terminator of a 12-wchar
field-0 string).

`fn 0x004e7d4c` is called twice (`0x004dd188` with A, `0x004dd196` with B).
It returns `-1` unless the field is exactly 12 wchar; it copies
`wcsncpy(buf, s+10, 3)` (the last two wchar plus the terminator for a
12-wchar string), returns `0` if that tail equals `"000"`, and otherwise
returns `_wtol(tail)` when positive, else `-1`. On success the worker returns
`0` and sets `*(u32*)0x00b00228 = 1` only when
`value(SystemSD) > value(UserSD)`; otherwise it returns `3`.

### 8. Return codes and the rest of the policy

| Return | Condition |
| --- | --- |
| `0` | both copies opened/parsed, `wcsncmp` equal, `value(SystemSD) > value(UserSD)`; `g_flag 0x00b00228 = 1` |
| `1` | sixth poll saw state 1 (no card path), files not read |
| `2` | `fn 0x004e7940` (`DSK8:` query) failed, `[r15+24] == 0`, or `fn 0x004e7dd8` == 0 |
| `3` | `wcsncmp` != 0, or `value(SystemSD) <= value(UserSD)` |
| `0xff` | no device object, status query failed, timeout with state != 1, parser failure, or `fn 0x004e7d4c` == -1 |

The DSK8/HDD stage is `fn 0x004e7940` (IOCTL `0x80032010`, 0x50-byte output)
and `fn 0x004e7dd8` (constructor/open of the second object plus the same
DSK8 query, retried 4x50 ms). The guarded validate entry `fn 0x004dd700` calls
`fn 0x004dd68c`, which first reads `g_flag 0x00b00228` and then re-queries
`0x004e7ec8`, `0x004dd458`, `0x004e75d8`, `0x004e768c` and `0x004e7714`.

## Interpretation

- The reader is driven by a **NaviSetCC COM request**; no boot-time or SD-insertion path to it was found:
  `NaviSetCC.dll` method `0x02e3eef8` sends `0x841000f7`; Navi.exe's
  dispatcher `0x004bda44` routes it to `0x004beae0`, which runs a complete
  init -> read/compare -> validate -> teardown cycle. The service is torn down
  after every message (`0x004dd214` destroys the 0x5a0 model and the 28-byte
  device object), so every request re-opens `SDC1:`/`DSK8:` and re-reads the
  file. `NaviSetCC` is the settings component; whether it sends the message
  during its own start-up and which screen item calls `0x02e3eef8` are not
  determined by static data (UNKNOWN).
- The two reads are the **SystemSD (built-in) copy and the UserSD (card)
  copy**. The parser is a one-file, six-line parser and is called once per
  copy; this is not a retry and not a duplicate read of the same file.
- The retry policy is layered: `fn 0x004e787c` tries the SDC1 IOCTL four
  times 50 ms apart; the worker then polls the decoded state six times
  100 ms apart and only proceeds on state 4. State 1 is the "no card" bypass
  that returns success without reading. Each `fn 0x004e7940`/`0x004e7dd8`
  DSK8 query has the same 4x50 ms retry.
- The **file read itself is not retried**: `fn 0x004e7b8c` returns `0` on any
  `_wfopen`/`fgetws`/length failure and `fn 0x004dd028` immediately returns
  `0xff`. A new request message starts the whole cycle again.
- `wcsncmp` compares the **first line of both copies**, 11 wchar; the later
  numeric comparison uses the same field and the `"000"` literal in the
  helper.

## Correction to M2.1

EXP-2026-11-05-M2.1 described `fn 0x004dd028` as reachable through a
"dispatch/vtable entry" at `0x004dd2e4`. It is a **literal-pool slot** of the
wrapper `fn 0x004dd270`; there is no function-pointer table. The M2.1
observations (addresses, names, parser calls) stand.

The address-attribution tool has one trap here: `--to 0x004dd388` reports
"slot 0x004dd388 is read by load 0x004dd2e4". That is a false positive — the
pool word `0x004dd028` at `0x004dd2e4`, read as an instruction, is
`0xd028` (`mov.l @(0xa0,pc),r0`, target `0x004dd388`). The real reference is
`pool 0x004dd450 holds 0x004dd388` in `fn 0x004dd420`. Pool words must be
attributed by their loaders, not by decoding the pool as code.

## Open questions / caveats

- The numeric helper `fn 0x004e7d4c` requires **exactly 12 wchar** in field 0
  (and parses `s+10`, 3 wchar), while the parser's field-0 buffer admits at
  most 11 wchar and every factory `HDD_INFO.TXT` sample has an 11-wchar line 1.
  On such a file the helper returns `-1`, i.e. `0xff`. Whether the runtime
  SystemSD copy uses a different line-1 format, or the 12-wchar check is a
  legacy guard, is **UNKNOWN** (C-1779). This does not affect the trigger or
  the retry logic.
- The exact menu item/screen that invokes `NaviSetCC.dll` routine `0x02e3eef8`
  and whether `NaviSetCC` sends the message during its own start-up are not
  named by any static string in the module; the trigger is established at the
  message level (UNKNOWN at the UI-label/emission-time level, C-1775).
- Builds B/C were not re-checked; the addresses are build A. The coredll
  ordinal names come from image B (C-1710 method).
- The semantics of IOCTL `0x80032004` states 1/2/4/8 and of IOCTL
  `0x80032010` are not documented in any module; "state 4 = card ready" is an
  inference from use, not a verified label.
