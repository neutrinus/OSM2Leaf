## Question

Can a 2014/2016 X212 kernel ROM (builds B/C) be used on Marek's 2011 X210
`QY7200ND`, judged statically from ROMHDR RAM windows, BSP/platform strings,
driver set and launcher unit checks — and can the `fmmdrv_05`/`_07` selection
rule be read from the stored bytes?

## Hypothesis

The two generations are not drop-in compatible: the RAM window moves and the
flash driver set splits into two model-specific variants, while the BSP PDB
path and launcher check strings stay the same. **Falsifier:** any quoted ROMHDR
field is the same in 2011 and 2014 but recorded as different; the CETUS
positive control fails; the 2011-vs-US2011 control shows a generation-like
difference; or a claimed selection VA has no printed `sh4xref`/`pdata` evidence.

### 3. Controls

- **Positive:** `ce_strfind --control CETUS` reports 69/73/74 hits (build B,
  EU2011/EU2014/EU2016); `--control fmmdrv` finds the named variants (2 hits
  2011, 3 in 2014, 4 in 2016); `--control 'MAP DATA BASE UNMATCH'` finds 1 hit in
  every head. A tool that cannot find known-present data is not evidence of absence.
- **Negative:** exact `X210`/`X212` = 0 hits in build B of every head, while CETUS
  is present — the platform tokens are ROM-A header bytes, not kernel strings.
- **Region control:** `head256` vs `us256` build B has the same ROMHDR windows and
  module census (C-6281 and §Observations), so the 2011→2014 diff is generational.
- **Tool-failure control:** stock `ce_drivers.py` fails on EU2014/EU2016 with
  `UnmappedAccess … 0x00000000..0x00000002` (hard-coded decompressor entry);
  decoding with each build's discovered `DECOMP_SECT` succeeds with 0 dangling
  links. The failure is a tool limitation, not absent registry data.
- **Xref negative:** `sh4xref --to 0x039a58ec` in `devmgr.dll` has no literal pool
  hit; the PDB name is a self-identifier, not a load-name literal.

### 4. Scope

Builds B/C of EU2011, EU2014, EU2016 plus US2011 B as region control. Methods:
`cerom` TOC/ROMHDR/modules (no fitted deltas), `ce_strfind` on uncompressed sec0
with compressed sections listed as `UNSUPPORTED`, `cehive`/`ce_drivers` registry
rows decoded with each build's own `DECOMP_SECT`, and `sh4dis`/`sh4xref` literal
xref (SH-4 little-endian). Excluded: compressed `.data` outside the hive decode
(not needed for the string/module checks; the `UNSUPPORTED` list is the counted
limit — no "searched all bytes" claim), all of build A except the header
build-name bytes, and L3/L4 execution. No card built, no hardware.

### 5. Falsifier

The verdict "X212 is not a static drop-in" and the selection-rule result would be
refuted if: a quoted ROMHDR field is equal in 2011/2014 but recorded as different;
the CETUS or MAP DATA BASE UNMATCH control fails; the 2011-vs-US2011 control shows
a driver/RAM-window difference; an FMM_Init function reads a model/hardware ID
and branches to select its variant; or a claimed selection VA lacks a printed
`sh4xref`/`pdata` citation. Every check above can print a contradicting number.

## Interpretation

- **FACT (C-6310):** X210→X212 moves `ulRAMStart` by `+0x800000`, keeps `ulRAMEnd`,
  and changes `nummods` and `physlast`; both build B and build C. US2011 B
  matches EU2011 B (region control), so this is a generation change.
- **FACT (C-6311):** the BSP PDB path is `CETUS` in all heads; `X210`/`X212` are
  ROM-A header build-name bytes, not kernel strings (0 hits in B).
- **FACT (C-6312):** the flash-driver set changes from one `fmmdrv.dll` (2011) to
  `FlashManager2` + `fmmdrv_05`/`_07` (2014/2016); LCD and SDHC keep their names.
- **FACT (C-6313/C-6314):** the newer hives decode with the build's own
  `DECOMP_SECT` (`0x88037994`). The two FMM variants are registered with identical
  Prefix, Index, Order and ServisID — there is no static discriminator value.
- **OBSERVED / UNKNOWN (C-6315, Done-when):** neither `FMM_Init` reads a
  model/hardware ID; both are the same 3-import + helper shape. The choice between
  `fmmdrv_05` and `fmmdrv_07` therefore cannot be attributed to a stored select
  value or to either `FMM_Init` (VAs `0x039a15a4` / `0x0399159c` are where the
  choice is *not* made). It is made at device registration by hardware probing or
  a loader path not present in these stored bytes; the exact runtime
  discriminating VA is **unknown**. Per Stop, this is recorded as unknown, not
  as a decoded rule.
- **FACT (C-6316):** the launcher's `DIFFERENT MAP CODE` / `MapDBVer` strings and
  their positive control persist into X212. Per C-2081–C-2084 the runtime checks
  compare unit target-info from `KernelIoControl(0x0101302C)` with the card's
  `HDD_INFO.TXT`; their code identity in the newer builds is not proven here.
- **OBSERVED (C-6317):** verdict — **not a static drop-in**. Check table:
  RAM window → different; module count → different; BSP PDB path → same;
  platform build name → different; flash driver set → different; LCD/SDHC module
  names → same; launcher unit-check strings → same.
- **OBSERVED (C-6318/C-6319):** all negative controls passed; scope is one static
  pass with no card, no L3/L4 run and no hardware (rule 13). Regret: the FMM
  runtime selector remains open; a follow-up with the unit's flash/NAND target
  info (M6.19) or a QEMU run could close it.

## Conclusion

A 2014/2016 X212 kernel ROM is not a static drop-in on the 2011 X210
`QY7200ND` (C-6317): build B/C `ulRAMStart` moves from `0x89e40000` to
`0x8a640000` (`+0x800000`) while `ulRAMEnd` stays `0x8e600000`, `nummods`
grows `0x5b`→`0x5f`/`0x60`, and the flash-driver set changes from one
`fmmdrv.dll` to `FlashManager2` + `fmmdrv_05`/`_07` (C-6310/C-6312/C-6314).
The BSP PDB path stays `CETUS` and the launcher's `DIFFERENT MAP CODE`/
`MapDBVer` strings persist, but those alone do not make the newer ROM bootable
on the old board. The flash-driver selection rule is readable as a registry
registration table but the runtime choice between `_05` and `_07` is unknown
(C-6315): both keys have identical Prefix/Index/Order/ServisID and neither
`FMM_Init` reads a hardware ID, so no static selector value exists; the exact
runtime-discriminating VA is not in the stored bytes examined. No card was
built and no L3/L4 run was performed (rule 13).

**Blocker (task Stop rule):** the Done-when requires the selection rule OR
`unknown` with the VA where the choice is made. The VA is not recoverable from
the stored bytes examined: both FMM keys carry identical registration values and
neither `FMM_Init` reads a hardware ID, so the choice is made by the generic
device loader / hardware probe at registration. Unblock with an L4 boot of the
X212 kernel on `-M aze0` (M8.G4), where the chosen driver is observable.
