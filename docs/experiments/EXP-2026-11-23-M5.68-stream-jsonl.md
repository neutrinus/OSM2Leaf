## Question

Does `tilewriter` stream a cell split one record at a time, so that the
`B48R050R` read that the old whole-file reader killed at ~5.2 GB (C-6255)
completes inside a 7,735 MB host — and does the full `m5_61_build_tile.py`
build then reach `verify_factory`?

## Hypothesis

`read_jsonl` as a generator over the open text handle removes the three big
terms of C-6255 — the whole 1.8 GB string, the 14.4 M-entry `splitlines()`
list, and the 14.4 M parsed-record list — leaving `load_imf`'s `nodes` dict and
kept-`ways` list, i.e. **O(nodes + ways), not O(1)**. If the reader is the only
5.2 GB term, `tilewriter` finishes. The end-to-end driver separately re-parses
the split with `json.loads` into its own `nodes`/`ways`/`parcel_ways`/`runs`
dicts and then spawns `tilewriter` as a child; that second copy is the task's
`Stop:` case.

**Falsifier:** a "streaming" reader that still returns a list of all records, or
a build whose peak is unchanged on the same split. **Negative control:** the
`origin/main` reader on the *same* split must OOM.

## Method

1. **Sample and hash.** The kept split above; its SHA-256 is captured before
   and after every run (`sha256sum -c` prints `DOBRZE`/`OK`), so both arms and
   the driver run are measured on the same bytes.
2. **Commands.** Two arms, same split, same driver-equivalent `tilewriter`
   command, only the reader differs. `before-main/` is `git archive origin/main
   tools` (tilewriter hash verified `4743e568…`); the driver is byte-identical
   to `origin/main`. Then one end-to-end `m5_61_build_tile.py` run with a 2 s
   RSS sampler that attributes peak RSS to the driver and to the `tilewriter`
   child by cmdline.
3. **Controls.**
   - *Positive:* the after arm's reader round-trips the split — it yields the
     same records (its own selftest equality case) and reaches the writer's
     record build (it gets as far as `verify_factory`, failing only on the
     M5.69 splice).
   - *Negative:* the `origin/main` reader on the same split is killed by
     `signal 9`.
4. **Scope.** `B48R050R` level 1, one cell. Two arms use the split as the
   driver leaves it (`kept`); the end-to-end arm uses the driver from the cut
   PBF with the split already materialised (so `osm_ingest` is skipped). The
   driver's own data structures are the `Stop:` copy, measured separately.
5. **Falsifier.** As in Hypothesis.

```bash
S=/home/marek/projekty/leafre-work/scratch/m5.68
FAC=/home/marek/projekty/leafre-work/m5.4/card-factory
REPO=/home/marek/projekty/OSM2Leaf.task-m5.68-stream-jsonl
cd "$S"
sha256sum B48R050R-L1.kept.split.jsonl   # f3cf5b32…7b70

# BEFORE: origin/main's reader (git archive origin/main tools -> before-main/)
sha256sum before-main/tools/tilewriter.py  # 4743e568…434f
/usr/bin/time -v python3.13 before-main/tools/tilewriter.py \
  B48R050R-L1.kept.split.jsonl --cell B48R050R \
  --factory "$FAC/MAPAL001/B48R050R.DAT" --class-table ctab.json \
  --no-names --level 1 --out TW-before.tile.DAT --json 2> TW-before.time

# AFTER: this branch's reader
/usr/bin/time -v python3.13 "$REPO/tools/tilewriter.py" \
  B48R050R-L1.kept.split.jsonl --cell B48R050R \
  --factory "$FAC/MAPAL001/B48R050R.DAT" --class-table ctab.json \
  --no-names --level 1 --out TW-after.tile.DAT --json 2> TW-after.time

# END-TO-END driver, same split already present (ingest skipped), 2 s sampler
python3.13 "$REPO/tools/m5_61_build_tile.py" --osm "$S/cut-B48R050R.osm.pbf" \
  --cell B48R050R --level 1 --factory-root "$FAC" \
  --out "$S/B48R050R-L1.tile.DAT" --scratch "$S" --report "$S/driver2.json" \
  2> driver2.stderr        # sampled by measure_driver2.sh -> rss-driver2.log
```

## Observations

**1. AFTER — patched reader, `tilewriter` alone.** Reads the whole 1.8 GB split
and reaches the writer's record build; **no `signal 9`**:

```
$ grep -E 'check failed|Maximum resident|Elapsed|signal' TW-after.time
tilewriter: check failed: section-1 record at (75, 945, 11, 53) changed but was not regenerated
Command exited with non-zero status 1
	Elapsed (wall clock) time (h:mm:ss or m:ss): 5:10.45
	Maximum resident set size (kbytes): 4657860
```

**2. BEFORE — `origin/main` reader, same split, same command.** Killed while
reading:

```
$ grep -E 'Maximum resident|Elapsed|signal' TW-before.time
Command terminated by signal 9
	Elapsed (wall clock) time (h:mm:ss or m:ss): 0:36.61
	Maximum resident set size (kbytes): 5454440
```

No `TW-before.tile.DAT` is produced (killed before the build).

**3. Same input both arms.** `sha256sum -c kept-after.sha256` prints
`B48R050R-L1.kept.split.jsonl: DOBRZE` after both runs; the file mtime
(`07:25:01`) precedes both runs.

**4. END-TO-END driver — the `Stop:` copy.** The 2 s sampler attributes the
peak to the driver process itself; the `tilewriter` child is never spawned
(`writer_child=0` throughout), so the driver OOMs building its *own*
`json.loads` dicts:

```
$ grep '^PEAK\|driver_rc' rss-driver2.log
driver_rc=137
PEAK driver_own=5512296kB writer_child=0kB system_used=7902088kB
```

`driver2.json` is absent (killed before it was written); `driver2.stderr` is
empty; `B48R050R-L1.tile.DAT` is not produced. `sha256sum -c
split-driver2.sha256` prints `DOBRZE`.

**5. After reader is a generator, not a list.** `tilewriter --selftest`:
`read_jsonl is a generator`, `read_jsonl yields the first record before a later
bad line`, `negative control: a list reader fails the laziness check`,
`streamed records equal per-line json.loads` (50,000 lines), `.gz streams to
the same records`, `empty input still raises the no-records error` — all pass.

## Interpretation

- **FACT:** On the same pinned split, `origin/main`'s `tilewriter` reader is
  killed by `signal 9` at 5,454,440 kB Max RSS; this branch's reader completes
  the read and the record build at 4,657,860 kB with no signal (Obs. 1 vs 2).
  The falsifier "a streaming reader that still returns a list, or a build whose
  peak is unchanged" does not hold: the peak drops ~0.8 GB and the OOM is gone.
- **FACT:** The end-to-end `m5_61_build_tile.py` run OOMs at 5,512,296 kB in the
  **driver's own** parse, before the `tilewriter` child starts (Obs. 4). This
  is the task's named `Stop:` copy, not the reader.
- **OBSERVED:** With the reader fixed, `tilewriter` still exits 1 on
  `section-1 record at (75, 945, 11, 53) changed but was not regenerated` — the
  same even/odd-pair splice defect the M5.61 record logged as M5.69
  (`(81, 941, 22, 59)`), reached here at a different key because this tile's
  parcel set differs.
- **HYPOTHESIS:** The driver's peak is its `nodes` dict (12.7 M entries) plus
  `ways` + `parcel_ways` + `runs`; streaming it (or feeding `tilewriter`
  without a second parse) is the remaining 5.5 GB. Not proven — the driver was
  not changed (out of this task's `Scope`).
- **UNKNOWN:** whether the driver can be made to fit and pass `verify_factory`
  before M5.69 lands; the M5.69 fix is a hard prerequisite either way (Obs. 1).

## Conclusion

The `read_jsonl` streaming change is correct and does what M5.68 asked at the
reader: the `origin/main` whole-file read that died at 5.45 GB now completes at
4.66 GB on the identical split, with a real generator, `.gz` streaming, a
deferred empty-file error and a negative-control selftest. `load_imf` keeps
`nodes` + kept-`ways` — **O(nodes + ways), not O(1)**. The task's end-to-end
`Done when` (a `B48R050R` level-1 tile through `m5_61_build_tile.py` that passes
`verify_factory`) is **not** met: the driver itself OOMs at 5.51 GB in its own
`nodes`/`ways` parse (the `Stop:` copy), and once that is passed, `tilewriter`
stops on the M5.69 even/odd splice. The task is set `blocked` with `Unblock:
M5.99` (stream the driver's own data structure, opened here) and `M5.69` (the
splice). C-6255's "tilewriter RAM, signal 9" is now split: the *reader* no
longer OOMs on `B48R050R`, the *driver's parse* does.
