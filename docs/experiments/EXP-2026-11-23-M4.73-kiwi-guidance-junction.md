## Question

For one EU2011 motorway junction with a signpost (`0=POZNAN:KALISZ:(36):RAWICZ` in `B48R058R` section 4, M4.40/C-5925), which map file holds the signpost text, how is it tied to the link, and which KIWI V1.22 route-guidance record does it resemble?

## Hypothesis

KIWI §8.4's Guidance Data Frame lists separate Intersection Name / Road Name / Toward Name / Direction Indicator records; if ZE0 follows the same decomposition, the destination string should be stored as a name record next to an intersection/node reference in `INTER0nn`/`FRWAY0nn`, with a lane/direction field in the same family.

**Falsifier (task):** the signpost text is found in **no** map file — then it is composed from road names at run time. A secondary falsifier for the lane part: no lane field appears in the two Poland shards examined (a scope-limited negative, reported with a positive control).

## Method

1. **Sample and hash.** `sha256sum` on IMG256, the tile and the two `.cmp` shards; `cmpind.py extract` writes the decoded shards into scratch; the section-4 payload is inflated from the tile at a fixed offset with the script in part 2 and its SHA-256 recorded above.
2. **Commands.** All paths absolute; `S` is scratch, `R` the decoded EU REFER001 tree, `T` the factory tile directory.

```bash

R=/home/marek/projekty/leafre-work/m4.8b-eu/REFER001
T=/home/marek/projekty/leafre-work/m5.4/card-factory/MAPAL001

sha256sum archive/head256.img "$T/B48R058R.DAT" \
  "$R/INTER021.DAT.cmp" "$R/FRWAY021.DAT.cmp"

python3 - "$T/B48R058R.DAT" "$S/sec4_payload.bin" <<'PY'

  --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
  --position 51.70,17.45 0xa6bed6ee:0:0x40
```

## Interpretation

- **FACT:** the signpost string is stored **verbatim** in one map file — tile `B48R058R` section 4, record at `0x113ca000`, name at payload word offset `0x35` = 53, length 18 words, country 616 — with a second name `2=11:25` at `+0x86`. The task's falsifier ("found in no map file") does **not** fire. (C-7720)
- **FACT:** the record is tied to the link by its **parcel/mesh code** `a6bed6ee` (record words 0–1). The firmware's kind-`0x40` reply points at word 0 (`+16`), the name at word 53 (`+24`) and word 9 (`+28`), the first guidance item after the 9-word header; the same mesh in `INTER`/`FRWAY` is represented by the 12-byte table (`key/id/length/index`) and INTER's 187 `4000 0000 XXXX` node refs. No single record in these files carries both the destination text and a link id. (C-7721, C-7722)
- **OBSERVED (KIWI resemblance):** the section-4 destination list `POZNAN:KALISZ:(36):RAWICZ` matches the field *kind* of KIWI V1.22 §8.4.1.4 **Toward Name** (destinations) with §8.4.1.3 **Road Name** / the `Route number flag` for `(36)`; FRWAY021's `FREEWAY-NAME` + `ENTRANCE/EXIT` + `Entrance/Exit name` schema and its Wrocław street names match §8.4.1.2 **Intersection Name** and the §10.13 `Road Reference Table`; INTER021's node refs match §10.6/§10.7 Node/Link frames. The `2=11:25` name is not assigned to a KIWI record (could be exit/junction number — UNKNOWN). (C-7723)
- **OBSERVED (negative, scoped):** no **lane / Direction Indicator** field was found in the two Poland shards: `LANE` is 0 in both schemas, and every `LANE` substring in INTER021's 230 inner streams sits inside a Polish street name. This is a negative result for these two files only; it does not rule out lane data in tile sections 1/2/4 or in another shard. (C-7724)
- **HYPOTHESIS:** the ZE0 decomposition differs from KIWI's: the router fetches a parcel-scoped guidance blob (tile section 4), while intersection identity and route numbers live in a separate `REFER001` family. The `0=`/`2=` name prefixes and word 9's item list are candidate section-4 record kinds, but `0x00422eac` was not run on this reply (M4.56 is still open), so no reading VA is claimed.
- **UNKNOWN:** the meaning of `key`, `length` and `b8` in the 12-byte INTER/FRWAY records (M3.16, C-2217–C-2219); how the section-4 word-9 item list selects a link; whether a firmware guidance reader consumes these names at all (rule 13 unchanged).

## Conclusion

The signpost is not composed from INTER/FRWAY road names at run time: it is a verbatim section-4 tile record keyed by the parcel mesh code, with the component words present in INTER021/FRWAY021 only as unrelated street names. KIWI's §8.4 record list predicts the field *kinds* (Toward Name, Intersection/Road Name, Node/Link refs) but not their ZE0 container — consistent with M4.63/M4.65 ("common concepts, different container"). Lane data has no counterpart in the two shards examined. `docs/format/refer.md` gains a short INTER/FRWAY guidance-field note; `docs/research/kiwi-sources.md` gains the chapter-8 pointer; M4.56's `Input` records the junction and its link tie. No firmware reader VA, writer change or generated card is claimed. C-7720–C-7724.
