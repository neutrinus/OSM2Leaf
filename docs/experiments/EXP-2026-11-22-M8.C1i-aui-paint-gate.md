## Question

After M8.C1h every non-telematics control loads, but AuiApp only clears its
surface. Which call or event makes AuiApp paint its first form, and what
stops it on the emulator?

## Hypothesis

AuiApp paints once the system side finishes its start sequence. That
sequence waits for the audio microcontroller, which no peer answers
(EXP-2026-11-22-M8.C1h-hcx-stubs, C-8216). Falsifier from the task: forcing
the suspected gate open still leaves the AUI surface cleared only.

## Observations

**O1 — AuiMonitoringCC signals INIT_END from its own init.**
`AuiMonitoringCC.dll` `fn 0x02a381e4` creates three event handles through
`vtbl+12`: `AUIMONI_EVT_FOR_SYS_INIT_END` (stored at `this+16`),
`AUIMONI_EVT_FOR_SYS_UNLOAD_END` (`this+20`), and a thread
(`vtbl+432`, thread routine `0x02a381d8`, at `this+24`). It then calls the
import thunk `0x02a38d84` with `(this+16, 3)`. The thunk's slot
`0x02a3c108` is `COREDLL!EventModify` (`cerom imports`), and 3 is
`EVENT_SET`. The control's type library has `init`, `OnLoad` and
`OnUnLoad` and an event `NotifyAUIMonitoringEvent`;
`Substance.skn` names `Notify_AuiMonitoring_FormOnLoad_Event` at file
offset `0x138c68`.

**O2 — SystemEXE's 45 s timeout is a watchdog on that event.**
`SystemEXE.exe` `fn 0x0001fad0` (`CAuiMonitorCmn::ThreadProc`) loops while
`this+20` is set. It waits through `vtbl+8` on 3 handles at `this+4` with
a 45 000 ms timeout (literal `0x0000afc8`). On `0x102` (WAIT_TIMEOUT) it
prints `CAuiMonitorCmn::ThreadProc::TIMEOUT!!!!!`, writes error log
`(23, 10, 57)` and calls `vtbl+412`. In H4 the next lines are
`Pow Off 1st Detect` and `Force PowerOff`. So the 45 s shutdown of
M8.C1g means that no `AUIMonitoringCC.AUIMonictl` control was initialised:
the form that holds it never loaded.

**O3 — The start form.** The record walk of `ReleaseMain.skn` (65
records) shows `frm_PRCOM_StartUp` with two controls:

- `ctl_PRCOM_System`, CLSID `{6697E855-84AE-4A4B-A5D3-2D38DA30C7EB}`
  (`SystemCC.SystemCtl`);
- CLSID `{5099533B-7DBA-48D4-89B2-48C25CA9674E}` (`multiskin.dll`), whose
  record holds `\SystemSD2\SkinChange\001\Substance.skn`.

The file also defines `var_PRCOM_SystemInitFlg`, `act_PRCOM_SystemInit`,
the layer table `tbl_PRCOM_Layer` and two script records naming `Show` and
`Start`. `Substance.skn` has `frm_PRCOM_StartUp` too (`0x1aabe4`), next to
the sequence names `STARTUP`, `SRT_COLD_ANTI_THEFT`,
`SRT_COLD_I_AGREE`, `SRT_COLD_OPENING_ANIMATION`, `SRT_COLD_SECURE` and
`ActiveForm`. The script grammar is not decoded, so which event moves the
sequence on is not read from the skin.

**O4 — After the skins load, AuiApp runs its draw loop with nothing to
draw (H10).** Breakpoints for 210 s after
`AUI SKN: … Skins = 36905`:

| VA | what | hits |
| --- | --- | --- |
| `0x037c5446` | `auirtdll` draw routine `fn 0x037c5440` (`AUI Draw Time`), `this = 0x7db10` | 335 in 150 s, then 136 in 60 s |
| `0x037c547a` | its early return when `[this+0x113c] == 0` (no pending invalidation) | the same 335 and 136 |
| `0x037def4a` | invalidate method `fn 0x037def48` | 1 (at 128 s, same `this`) |
| `0x037dffe8` | control instantiation (`CoGetClassObject`, `fn 0x037dffdc`) | 0 |
| `0x037bef06` | `Screen` `IDispatch::Invoke`, `fn 0x037beeec` | 0 |
| `0x02a381f0` | AuiMonitoringCC init (O1) | 0 |

So AuiApp is alive and polls about twice a second, but no form is loaded
or shown after the skins, and the single invalidation does not lead to a
draw. `Screen`'s Invoke handles DISPID 4 `EnableUpdate` (put: counter = 0
or 1), 5 `StartUpdate` (counter − 1 if > 0) and 6 `StopUpdate` (counter + 1)
on the global `0x01f2b348`. The draw routine checks the same global right
after the pending word. The names come from `fn 0x037bed80`
(`GetIDsOfNames`).

**O5 — SystemCC's events to the skin come from window messages.**
`SystemCC.dll` `fn 0x02a7ece8` fires `_ISystemCtlEvents::NotifySysEvent`
(`IDispatch::Invoke`, DISPID 1) with a name. `fn 0x02a7f3d0` maps window
messages `0x1983` and `0x1a44`–`0x1a58` to names such as
`NotifySourceChange`, `NotifyDiscEject`, `NotifyUSBConnectStatusChange`
and `NotifySystemShutdown`. None of these names appears as a literal
string in either skin.

**O6 — SystemCC's resource request goes to Audio.exe, which did not run.**
SystemCC logs `Send Resource Actevate Message` and
`IPC Send::[MSG_PROCESS_SYSTEM] -> [MSG_PROCESS_OFF] MsgId[SYS_REQ_ACTIVATE]`
(H1, H4, H10). SystemEXE's name tables give `MSG_PROCESS_OFF =
0x8200000C`, `SYS_REQ_ACTIVATE = 0x81120011` and
`SYS_NOTIFY_ACTIVATE_COMPLETE = 0x81120012`. Among image A's modules only
`Audio.exe` (3, 5 and 6 literal words), `SystemCC.dll` and
`SystemEXE.exe` hold all three; `Usb.exe` and `PhoneBTA.exe` hold the two
message IDs only. Up to M8.C1h the serial log has
`DoImport Failed! Unable to import Library 'AppTimerDll.dll' for
'\windows\Audio.exe'` and `Launch Process Not Create!!! ->
\windows\Audio.exe`, and no `ACTIVATE_COMPLETE` ever follows.

**O7 — Copying `AppTimerDll.dll` from ROM image C.** The module (4
exports, 14 `COREDLL` imports) has code at `0x01e41000`, an RW section
(import table plus one global) at `0x01e42000` and `.pdata` at
`0x01e43000`. These addresses lie inside the data of image A's
`OBJDLL.dll` (`0x01e33000`–`0x01e54efc`), so `--copy-dlls apptimer`
moves it. Code and `.pdata` go to `0x03751000`/`0x03753000`, and 86
aligned words that point into the old sections are rewritten (67 in the
code: literal pools and a pointer table; 19 in `.pdata`). The first
placement put the RW page at `0x01a7c000`, a free page in image A's own
DLL data window. Every importer still failed (H9). A breakpoint trace of
the kernel loader for `AppTimerDll.dll` shows:

- `fn 0x88029670` (LoadOneLibrary) calls `fn 0x88029018`, which returns
  `0xe`;
- inside it, LoadO32 `fn 0x88026df4` maps the code section at
  `0x03751000`, then its per-section routine `fn 0x88026ba0` returns
  `ERROR_OUTOFMEMORY` (14) for the RW section at `0x01a7c000`.

With the RW page at `0x01f4f000`, inside the kernel image's DLL data window
(its `dllfirst` high word `0x01bf`), every importer loads. Audio.exe,
Speech.exe, Vehicle.exe, PhoneBTA.exe and CameraCC no longer report
`AppTimerDll.dll`. Usb.exe now stops at `BOLERODLL.dll` (not investigated).

**O8 — Audio.exe then waits for the microcontroller (H9, H10).** Audio.exe
starts (`[Audio::] Create Thread[0] …`). Thread 1 waits 60 s for module
ID 6:

```
ACM::WaitModule Timeout ID[45] WaitTime[60000]
[Audio::] Create Thread[1] Wait Modules Error LaunchId=[45] Wait Modules ID=[6]
[Audio::] FuncThreadLaunch Error[0] ThreadId[1]
[Audio::]AvLaunchMain::ModuleLauncher() Error
```

The audio network driver keeps logging `ANWDRV >> Audio connect NG retry`
and `CInaiProtocol … WriteData() FAILED` (820 lines in H9).
`SYS_NOTIFY_ACTIVATE_COMPLETE` never appears, and O4's counts were taken
in this state. `tools/acm_id_scan.py --id 6` finds no static setter for
ID 6; two functions load it dynamically.

## Interpretation

- The 45 s power-off and the empty AUI surface have one cause. AuiApp
  loads both skins and runs `frm_PRCOM_StartUp`, but no further form
  loads. So `AuiMonitoringCC` (O1) is never created, and SystemEXE's
  watchdog (O2) fires. With the watchdog disabled, the draw loop
  (O4) runs on an empty invalidation list.
- The code that refuses to draw is `auirtdll` `fn 0x037c5440`, with its
  pending word `this+0x113c` and the stop-update counter `0x01f2b348`.
  That check is not the gate, because nothing is queued for drawing.
- The likeliest gate is the audio-source activation chain: SystemCC
  sends `SYS_REQ_ACTIVATE` to the OFF source in Audio.exe (O6). Audio.exe
  could not start before this task. It now starts, but its launcher stops
  on ACM module 6 while the audio microcontroller link is silent (O8).
  This is a hypothesis: no run has shown that the skin waits for
  `ACTIVATE_COMPLETE` or for `NotifySourceChange`, and the skin script
  grammar is not decoded (O3, O5).
- Per the task's stop rule, the chain ends at the microcontroller
  handshake: M8.H43 (frame protocol, which `WaitModule` reply counts as
  present) and M8.H44 (the peer).

## Conclusion

AuiApp paints no form because no form after `frm_PRCOM_StartUp` loads.
The draw loop runs about twice a second and finds no pending invalidation
(`auirtdll` `fn 0x037c5440`, `this+0x113c`). The control that would signal
SystemEXE's 45 s watchdog sits on a later form. `--copy-dlls apptimer`
copies `AppTimerDll.dll` from image C into image A's TOC. With it,
Audio.exe (the `MSG_PROCESS_OFF` source that SystemCC asks to activate)
starts for the first time on the emulator, then waits for ACM module 6
behind the silent audio microcontroller link. A form screenshot needs
that link answered (M8.H43–M8.H45) or the activation answered some other
way (M8.C1j).
