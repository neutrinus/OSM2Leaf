# EXP-2026-11-20-M3.16: `INTER` / `FRWAY` record layout corrected; content reader still not found

- **Status:** done (negative / blocked: record layout corrected, content reader VAs not found)
- **Date:** 2026-11-20
- **Sample:** `IMG256` = first 256 MiB head of build-A EU 2011 SD image (build A),
  SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (file `archive/head256.img` on this machine). Factory shards extracted from
  `REFER001/*.cmp`+`.ind` (EU 2011 root); no vendor bytes committed.
- **Tools:** `python3 3.13` / `zlib 1.3.1` (decode only, no recompression);
  `tools/cmpind.py` (extract), `tools/inter_table.py` (new, `--selftest`),
  `tools/inter_reader_scan.py` (new, `--selftest`), `tools/sh4dis.py`,
  `tools/read_watch_l3.py` (L3 harness), `tools/cerom.py`.
- **Claims:** C-2215–C-2219 (supersedes C-2211/C-2213's reading of the record
  form; C-2210 still holds)
- **Supersedes:** none (C-2211/C-2213 stay; C-2215 corrects the layout they
  cited)
- **Superseded by:** a follow-up that finds the content reader VA, or proves it
  is reached only through an indirect path with a bound positive control (M3.29
  / M9.38)

## Question

Is the `INTER0nn` / `FRWAY0nn` 12-byte record table at `0x1108` the little-endian
form `refer.md` documented, and which build-A firmware function reads its fields
(M3.16 done-when: reader VAs and consumed fields in `refer.md`)?

## Hypothesis

The `refer.md` record form (`u8 id, u16 n, u16 0, u16 offset, u16 length 6*k,
u16 0`, `0xffff` length terminator) is a writer's-inverse description of the
factory bytes, so its field offsets and the `0xffff` position should be
satisfied by the records in a real shard.

**Falsifier:** if the documented field offsets (little-endian) are violated by
every factory record while a different, self-consistent layout holds in all of
them, the documented form is refuted. For the reader question, the falsifier is
a decodable function that consumes the real table (`0xffff` key at +0, +6/+10
fields) — found here or by L3 watch of the M3.23 candidates; if none is found
after the four families, the reader is not located and done-when is not met.

## Method

1. **Sample and hash.** `archive/head256.img` SHA-256 above; factory shards from
   the EU 2011 `REFER001` `.cmp`/`.ind` pair. No vendor bytes committed.
2. **Commands** (run from repo root; runnable as written):

   Decode the factory shards (authoritative stream decode, not the stale
   `decoded/` tree):
   ```bash
   mkdir -p ~/projekty/leafre-work/scratch/m3.16
   R=~/projekty/leafre-work/m5.29-factory-root/REFER001
   for n in INTER001 INTER002 INTER003 INTER004 INTER005 \
            FRWAY002 FRWAY003 FRWAY004 FRWAY005 FRWAY007; do
     python3 tools/cmpind.py extract "$R/$n.DAT.cmp" --ind "$R/$n.DAT.ind" \
       -o ~/projekty/leafre-work/scratch/m3.16/$n.DAT
   done
   ```

   Layout check (new BE record form; exit 0 = every shard conforms):
   ```bash
   python3 tools/inter_table.py check ~/projekty/leafre-work/scratch/m3.16/*.DAT   # exit 0
   ```

   Endianness refutation (old LE 11-byte form vs the real one):
   ```bash
   python3 tools/inter_table.py refute ~/projekty/leafre-work/scratch/m3.16/*.DAT
   ```

   Four reader signature families over `Navi.exe` sec0:
   ```bash
   python3 tools/inter_reader_scan.py scan archive/head256.img
   ```

   Disassemble the single f3 candidate:
   ```bash
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 \
     --va 0x00392100 --count 60
   ```

   L3 read-watch of the M3.23 candidate readers on the factory `INTER001` page:
   ```bash
   python3 tools/read_watch_l3.py probe archive/head256.img \
     --buf ~/projekty/leafre-work/scratch/m3.16/INTER001.DAT --len 39936 \
     --entry 0x003fdd18,0x0040eed8,0x00407724,0x003f0aec,0x003fd690,0x003fbbac,0x0040dfa8,0x0040d704,0x0040da3c,0x003fc0ec,0x003fc518
   ```

3. **Controls.**
   *Positive (layout):* `inter_table.py check` decodes all 10 factory shards to
   `OK`, and the synthetic shard in `--selftest` round-trips its own three
   records (`key` 0x24/0x30/0x18, `length` +6, `index` +10); the negative
   vectors (a `0xffff` key ends the run, nonzero `u16@+2` stops it) FAIL as
   required. The `check`/`refute` decoder is thus sensible on both a clean and a
   broken shard.
   *Positive (reader method):* `read_watch_l3.py probe` on the LCTBL reader
   `0x0040de98` with the factory `LCTBL001` page reads 6 guest words (`+0x8`,
   `+0x4`, `+0x2` twice) and reports `result: PASS` — the L3 watch does see a
   known reader touch its page.
   *Negative (layout):* `inter_table.py refute` scores the old LE form 0/177 on
   `u16@+3==0`, `u16@+7==0xffff` and `u16@+8==0xffff`, while the real BE
   `u16@+2==0` holds 177/177. A correct layout must not be 0/177.
   *Negative (reader):* the same `read_watch_l3.py probe` run on the 11 M3.23
   candidates reads only generic context bytes (`0x00407724`: `+0x0..+0x1c`;
   `0x003f0aec`: `+0x0` u16) or faults on a null pointer (`0x003fdd18`,
   `0x0040eed8`, `0x003fd690`, `0x003fbbac`, `0x0040dfa8`, `0x0040d704`,
   `0x003fc0ec`, `0x003fc518`), none reading the `0x1108`/`0x1110` table.

4. **Scope.** Build-A `Navi.exe` sec0 only: `5553664` B stored / `5553430` B
   vsize of uncompressed executable halfwords (C-2128: 0 compressed executable
   sections, so "not found" is a signature failure, not hidden bytes). Shards:
   10 EU 2011 `INTER`/`FRWAY` files (177 table records total). FRWAY blob 1/2
   (route refs, mesh id, serial+text) are not walked — only the shared 12-byte
   table. The M3.23 candidate list is the call-graph reachability set from the
   REFER family access roots (7 readers + 2 read issuers + 2 more), fixed before
   the L3 run (C-3545/C-3546).

5. **Falsifier.** For the layout: a factory record set where the documented LE
   offsets hold and the BE offsets do not. For the reader: a decodable function
   (or a passed L3 watch) that loads the `0xffff` key / +6 / +10 fields from the
   table. Neither occurred.

## Interpretation

- **FACT:** The 12-byte record is big-endian: `u16 key` (+0, `0xffff` =
  terminator), `u16 0` (+2), `u8 id` (+4), `u8 flag` (+5), `u16 length` (+6),
  `u16 b8` (+8), `u16 offset` (+10). All 10 factory shards (177 records) conform
  (`inter_table.py check`, exit 0). `u16@+2 == 0` in 177/177.
- **FACT:** The pre-M3.16 doc form (LE, 11 bytes, `u16 0` at +3, `0xffff` at
  +8) holds in 0/177 records on every tested assertion (`inter_table.py
  refute`). It is refuted, not merely unverified.
- **OBSERVED:** `u16@+8` (b8) and `u8@+5` (flag) are variant fields: b8 is
  nonzero in 25/35 INTER002, 8/29 INTER003, 23/31 INTER004, 25/36 INTER005; flag
  in 4 INTER005 records. `u16@+6` (length) and `u16@+10` (offset) are populated
  in all records; their meaning (`length` vs `6*k`, offset into which blob) is
  not separately proven here.
- **OBSERVED:** Over 5,553,664 B of decodable `Navi.exe` sec0, four halfword
  families yield only one candidate (`0x00392122`), which is a byte-string
  `0xff` walker (f3 hit), not the u16-key table. Families f1 (the r2 +8 form,
  now known wrong), f2 (`0x1108` construction) and f4 (+10/+6 read) find 0.
- **OBSERVED:** L3 watch of the 11 M3.23 candidates on the factory `INTER001`
  page: none reads the `0x1108`/`0x1110` table; `0x00407724` reads only the
  context header `+0x0..+0x1c`, `0x003f0aec` a `u16` at `+0x0`, the rest fault
  on an unmapped null target. The LCTBL positive control passes, so a reader
  *can* be watched.
- **HYPOTHESIS:** The content reader is reached through an indirect dispatch
  (`.data` pointer / callee-carried cursor) or consumes a decompressed page
  through a wrapper, not a direct 12-byte loop the signature families can see;
  M3.29 (per-family runtime split) is the next probe.
- **UNKNOWN:** which instructions consume `key`, `length`, `offset`, `b8`,
  `flag`, the blob-0 6-byte elements, and FRWAY blob 1/2 records. Done-when not
  met.

## Conclusion

`refer.md`'s INTER/FRWAY 12-byte record form was wrong in endianness and field
offset; the factory bytes are big-endian with `0xffff` at +0 and `length`/`offset`
at +6/+10 (C-2215, C-2216). That correction is now a committed checker and a
refutation command, and the sections in `docs/format/refer.md` are rewritten to
match. The content-reader question is still open: four signature families and an
L3 watch of the M3.23 candidates find no function that consumes the real table,
so consumed fields are UNKNOWN (C-2217–C-2219); M3.16 stays `blocked` on
M3.29/M9.38.
