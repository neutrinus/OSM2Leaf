### 3. Controls

- *Positive (method not blind):* `datask_l3.py mount --file REFER001` must still
  attribute ICODE001 reads to `fn 0x003f07f8`, `fn 0x003f0c7c`, `fn 0x003f0400`,
  `fn 0x003f2bc4`, GAP leaf `0x0040a8d0` (C-5762/C-5763); if it does not, the
  read-watch method is broken and the whole negative is void.
- *Negative (probe artifact):* a hit that also occurs on the 4,608 B zero buffer
  is a struct touch, not a file read (per-hit comparison, F1).
- *Negative mutation (the `+0x18` gate):* zeroing only bytes `0x18..0x1b` of real
  COORD001 must drop `fn 0x004078e4` from 1,025 reads to 1; writing `0xff` at
  `0x14..0x1b` of the zero buffer must restore 1 → 1,025. If the verdict does not
  change under either mutation, the claimed gate is wrong.
- *Negative (id literal):* the COORD001 id `0x00060022` must be found if F2 is a
  real signature; `sh4xref.py --to` returning "no literal pool holds" is the
  family's own test.
- *Positive (mapping, not signature):* `name_loaders.py openers` must still name the
  ZCODE/ICODE opener (`fn 0x003f2cc0`, table `0x001792c4` ZCODE0) — used only to
  re-confirm the known name path, **not** as a COORD001 search (C-4677).

## Interpretation

- **FACT:** F1's five "readers" are not content-bound. Four (`0x003f0aec`,
  `0x003fdd18`, `0x0040d704`, `0x00407724`) have identical offsets and counts on
  real COORD001, the zero buffer and ZCODE018 — struct/process-state touches at
  `BUF_VA` (C-5760). The fifth, `fn 0x004078e4`, is gated solely by the word at
  `+0x18`: zeroing it drops 1,025 → 1 reads; writing `ff` at `+0x14..0x1b` on an
  otherwise zero buffer restores 1 → 1,025. It walks the global 76-byte-node
  list `0x00d77d20`, not file records.
- **FACT:** F2 fails — no executable literal pool holds the COORD001 file id
  `0x00060022` (C-5761). The task's `Stop:` (two families) is reached.
- **FACT:** the read-watch method is not blind: the same card run attributes
  ICODE001 reads to real functions (C-5762/C-5763) but shows no ZCODE/COORD row.
- **FACT:** `COORD001` has no `Navi.exe` name reference (C-4677/C-5765) — this is
  an existing negative, not a newly searched third family.
- **HYPOTHESIS (unchanged):** the ZCODE trie walk and any COORD001 lookup are on a
  route/search path the mount-state machine never exercises; only a search-path
  read-watch (M3.43's purpose) can attribute them.
- **UNKNOWN:** whether the tool set has any command that seeds a real ZCODE page
  through the search path with a read-watch. Verified this cycle that
  `read_watch_l3.py` `probe` calls entries directly (`eng.call(entry,[BUF_VA])`,
  line 228), `walk`/`above` are POINT-only, `chain` is the `.cmp` caller only, and
  `datask_l3.py` has `{tables,mount,port,diff}` — no search-path page watcher.
- **UNKNOWN:** the ZCODE record-walker VA; any COORD001 reader; whether `Navi.exe`
  reads COORD001 at all.

## Conclusion
