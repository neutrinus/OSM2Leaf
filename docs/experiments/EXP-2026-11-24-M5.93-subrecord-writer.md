## Question

Can our writer emit a dense level-1 parcel as a parent plus four 2×2
sub-records in a factory `0x2n46` wide row, and does the firmware reader read
all four sub-records?

## Hypothesis

A factory wide row already has a sub-record slot structure; replacing its four
sub-records with regenerated ones (parent + 4 subs, M5.53 codes, flag on the
even `ln`) keeps the directory size, kind and census valid, and each sub-code
is read by the firmware's map-request/slot-parser path. Falsifier: the written
tile fails `s1_wide_dir census`, a sub-code is wrong, an L3 map request for a
sub-code produces no tile read, or a negative control passes when it must fail.

## Method

### 2. Commands

`W=/home/marek/projekty/leafre-work/scratch/M5.93`,
`FAC=/home/marek/projekty/leafre-work/m5.4/card-factory`:

```bash

  python3 tools/tilewriter.py --selftest       # 148/148
python3 tools/s1_wide_dir.py --selftest         # 24/24
```

`$W/split.imf.jsonl` is generated by `tools/tilewriter.py --selftest`'s
`_m593_split` helper: four 2-node residential ways, one per quadrant of dir
77,923 row 8 col 27. No script is elided.

### 3. Controls

Positive: factory census exits 0 (`sub_code_ok=912`); the 4-way forced split
produces a parent + four full `0x00fa` records with codes
`a6a0cde3/a6a0cde7/a6a4cde3/a6a4cde7 = sub_code(parent a6accdef, k)`;
`m593_l3.py` prints a tile read with reply sub 3 for all four sub-codes;
`locmap_l3.py run --mesh 0xa6a0cde3` walks shapes (`RESULT: walk ran`).
Negative: (a) zeroing the four sub size words changes the row body from
`0009 0032 0009 0032 0009 0014 0009 0014` to `ffff…`; (b) flipping one byte
of a sub code fails census; (c) forcing the split into a directory that does
not cover the parcel is refused; (d) **sparse splits** (1/2/3 quadrants) keep
size words index-aligned with the subN record keys (the navigator-review bug;
selftest 148/148); (e) the 512-byte directory read misplaces wide rows
(`rows_512_reader_wrong_tag=628`).

### 4. Scope

Section 1 level 1 of one tile (`B48R068R`), one directory (77,923), one row
(8), one column (27), four sub-records; the parent keeps the whole parcel's
runs. The writer only splits into an *already-wide* row: widening a narrow row
grows the directory by 512 B and needs relocation, which is refused. Street
names are not carried into split subs (`name_off=0xffff`) because a union names
section needs a per-sub offset remap, out of scope. L4 drawing was attempted
but the 600-s QEMU run never reached `Pow Off 1st Detect`; no screenshot was
produced. Excluded: US2011, section 2/4 rewriting, OSM-derived geometry.

### 5. Falsifier

Any written sub-code not equal to `sub_code(parent,k)`; `census` reporting
`records_bad>0` or `block_overlaps>0`; an L3 map request for a sub-code with no
tile read; or a negative control passing when it must fail. A bare L4 SKIP is
never a pass.

## Observations

**O1 — writer selftest and census.** `tilewriter --selftest` (TMPDIR set because
`/tmp` is a 3.8 GiB tmpfs and earlier runs hit `ENOSPC`) prints
`tilewriter selftest: OK (148/148 checks)`, including 17 M5.93 checks:
a real 4-way split, the M5.53 codes, the even flag, re-read, `verify_factory`,
**1/2/3-quadrant sparse splits**, and four negatives (dropped sub sizes, wrong
sub-code, wrong directory, narrow refusal). `s1_wide_dir --selftest`: `OK
(24/24 checks)`; `m593_l3 --selftest`: `OK (3/3 checks)`. The forced build
reports `splits 1 split_parts 5 reason forced split`. Factory census and
written-tile census both print `dirs=68 kind_rule_ok=68 size_ok=68
roundtrip_ok=68 records=117305 records_bad=0 block_overlaps=0 OK`,
`cols_with_subs=228 sub_records=912 sub_code_ok=912`. `wc -c` prints
`266087634` bytes for the tile.

**O2 — the four sub-records.** Decoding dir 77,923 row 8 column 27 of the
written tile: `parent a6ac,cdef, 8 points, x/y 307..1741`;
`sub0 a6a0cde3 x 307..717 y 307..717`;
`sub1 a6a0cde7 x 1331..1741 y 307..717`;
`sub2 a6a4cde3 x 307..717 y 1331..1741`;
`sub3 a6a4cde7 x 1331..1741 y 1331..1741`. All four codes equal
`sub_code(parent,k)`. This reproduces the factory measurement on dir 72,920
row 27 col 5 (subs 4,952/5,956/11,856/12,280 B, codes a463cc11/a463cc15/
a467cc11/a467cc15, point counts 520/520/966/953 in four quadrant boxes).

**O3 — L1/card.** `rebuild_manifests --root $W/tree --fast` printed
`drstr: changed True`, `refer_ind: rebuilt 194 errors 0`. After imgpatch,
`cardcheck --image $W/split.img` printed `RESULT: PASS` (`[drstr] OK [mmain]
OK [cmp] OK [version] OK`). Before the DRSTR rebuild the same check failed
with a DRSTR size mismatch.

**O4 — L3 read proof (all four quarters read).** `tools/m593_l3.py` on the
patched card printed, for the four sub-codes:

```
0xa6a0cde3: reply_subs=[5, 3] tile_reads=[('0xfd6c500', 256)]
0xa6a0cde7: reply_subs=[5, 3] tile_reads=[('0xfd6c500', 256)]
0xa6a4cde3: reply_subs=[5, 3] tile_reads=[('0xfd6c500', 512)]
0xa6a4cde7: reply_subs=[5, 3] tile_reads=[('0xfd6c600', 256)]
m593_l3: tile_reads=4 meshes=4
```

Every sub-code produced reply sub 3 and one tile read of the row's record
block. The reader VAs printed in `--json` are `0x00404ee4` (record-block
handler, 90 B), `0x003f6968` (byte-swap/inflate, 256/512 B) and
`0x0054233c`/`0x0054331c`/`0x00545978` (inflate/table readers). This is the
firmware slot-parser path (C-5546: `0x00414dbc`) reading the wide row; all
four quarters are READ at L3.

**O5 — L3 walk and the harness limit.** `locmap_l3.py run --mesh 0xa6a0cde3`
(SW quarter) prints `replies sub [5]`, `window 256 B`, `rows with shapes: row 5
start 0xd count 1`, `RESULT: walk ran`, trace sha1
`c24467a4ff3712c0959d6667c3bbcef84cf67f83`. The same command for sub1/sub2/
sub3 (`0xa6a0cde7/0xa6a4cde3/0xa6a4cde7`) produces **no LOC_map message** —
and so does the *unmodified factory card* for those meshes. The cause is the
harness's position message (`x=y=1024`): the firmware's location handler fills
the four groups with divids `0x1,0x0,0x100,0x101` and posts the LOC_map walk
only for the group whose divid encodes the SW quarter (`0x1`); it cannot inject
a position inside another quarter without the `STD_MeshID_getAny` import model
(a stub returning `arg(0)` was tried and still leaves `loc=0`). Thus the
unwalked quarters are **sub1 (SE), sub2 (NW), sub3 (NE) at the LOC_map-walk
consumer**; they are not unread — O4 proves all four are read by the map-request
layer. No quarter is silently claimed drawn.

**O6 — L4.** QEMU boot ran 600 s and stopped; the log has 34 boot/error-family
lines and **zero** `Pow Off 1st Detect` markers. `ze0_screenshot.py screen` got
`ConnectionRefusedError`, so **no screenshot exists**. L4 drawing of the four
quarters is NOT VERIFIED; this is not folded into a pass.

## Interpretation

- **FACT:** the writer emits a parent plus four full `0x00fa` sub-records in an
  already-wide `0x2n46` row; the directory size, kind and census checks stay
  valid (`records_bad=0`, `block_overlaps=0`, `sub_code_ok=912`). Sparse splits
  keep the size words aligned (148/148 selftest).
- **FACT:** the four sub-codes follow the M5.53 `sub_code` rule and their points
  occupy the four quadrants of the parent 0..2047 lattice (O2).
- **FACT:** the firmware's map-request path READS all four sub-records (reply
  sub 3, real tile reads at VAs 0x404ee4/0x3f6968, O4). This is the part the
  writer changed; it is L3-verified.
- **OBSERVED:** the `LOC_map` walk consumer, driven by the harness's fixed
  x=y=1024 position, walks only the SW group. The three other quarters are
  *not proven unwalked by the firmware in general* — the same failure occurs
  on the factory card — they are simply not exercised by this harness (O5).
- **UNKNOWN:** L4 drawing of the four quarters. No screenshot and no quarter
  proven unread at L4 (O6). Rule 13: L3-verified writer, not L4-accepted.
- **HYPOTHESIS:** splitting a genuinely over-budget (>68,000 B) OSM parcel
  keeps all four quarters walkable; the test used the force hook below budget
  (M5.92 probed the size separately, C-8724).

## Conclusion

`tools/tilewriter.py` writes 2×2 sub-records into an already-wide `0x2n46` row
when a level-1 parcel exceeds the 68,000-B inflated budget, or when
`--force-subrecord` names a parcel; narrow directories refuse the split.
`tools/m593_l3.py` proves the firmware reads all four sub-codes at L3. The
written tile passes `s1_wide_dir census`, `verify_factory` and `cardcheck`.
L4 never reached the map screen, so the "all four quarters drawn" clause is
unverified; the task is blocked on the L4 boot recipe (M8.C1p), not failed.
Claims C-8730–C-8739 record the writer, sub-code rule, sparse-split fix,
census and the L3/L4 status. Next: an L4 boot that reaches the screen with the
split parcel on it, and widening a narrow directory for real over-budget OSM
parcels.
