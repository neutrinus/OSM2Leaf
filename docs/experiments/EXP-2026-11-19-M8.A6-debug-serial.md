# EXP-2026-11-19-M8.A6 — Debug serial on `-M ze0`: wired, but the retail boot banner never reaches it

- **Status:** done
- **Date:** 2026-11-19
- **Task:** TODO **M8.A6** (debug serial)
- **Sample:** EU 2011 image head `archive/head256.img`, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
  (image B at `0x3e00200`, `physfirst 0x88000000`, `physlast 0x886e18a4`;
  image A at `0x200200`, `physfirst 0x8cae1000`, `physlast 0x8e233c88`,
  `cerom.py romhdr`). Every VA below is **EU2011** `nk.exe`.
- **Tools:** QEMU **8.2.10** built from the `v8.2.10` git tag
  (`build.sh --from-git`; download.qemu.org is blocked in this sandbox) with
  the six `tools/qemu-ze0/patches/*.patch`; gcc 13.3.0, ninja 1.11.1,
  meson 1.3.2, Python 3.13.18. Repo tools: `tools/ze0_serial.py` (new,
  `--selftest`), `tools/sh4dis.py`, `tools/sh4xref.py`, `tools/cerom.py`,
  `tools/qemu-ze0/run.sh` (new `--serial`).
- **Claims:** C-1280, C-1281, C-1282, C-1283
- **Supersedes:** none
- **Superseded by:** none

## Question

With QEMU's `sh_serial` (SCIF mode) mapped at the kernel debug port
`0xffe46000` and connected to `-serial`, does the EU2011 kernel print its
boot banner (`Windows CE Kernel for Hitachi SH …`, `Booting Windows CE
version …`), and if not, why not?

## Hypothesis

The board guessed that the writer at `0x8804cfa4` (pointer loaded at
`0x8804ce78`, C-534) is the kernel's debug-output routine, so a model at
`0xffe46000` should show the banner unless a retail flag disables it.

**Falsifier (stated before the runs):** if any boot run's serial log
contains a banner line, the "not routed to the SCIF" reading is wrong. If
the positive-control shim (the firmware's own writer called with the
banner string) prints nothing, the model or its wiring is wrong and an empty
boot log means nothing.

### 1. Static: who touches the debug SCIF, who calls the writer

```bash

python3 tools/ze0_serial.py refs archive/head256.img          # window 0xffe46000+0x1000, writer 0x8804cfa4
python3 tools/sh4dis.py archive/head256.img nk.exe --image-start 0x3e00200 --va 0x8804cfa4 --count 26
```

`refs` scans every 4-aligned word of the executable sections of `nk.exe`
for values in the window, lists each `mov.l @(disp,PC)` that loads it, and
finds the writer's callers by literal pool **and** by `bsr`, then walks the
caller chain three levels.

## Interpretation

- **FACT (C-1280):** `-M ze0` with `ze0-0002` carries the debug SCIF at
  `0xffe46000` to serial port 0; the firmware's own writer prints through it
  (positive control), and the baseline machine without the model does not
  (negative control).
- **FACT (C-1281):** in EU2011 `nk.exe` the SCIF at `0xffe46000` is touched
  by exactly one routine, the leaf writer `0x8804cfa4`, whose only static
  caller is the AER exception reporter `fn 0x8804cdf8` (itself reached only
  indirectly, from `ErrorHandling` `fn 0x8804c018`). It is an exception
  dump channel, not the boot console.
- **OBSERVED (C-1282):** the boot banner is passed (`0xa801041c`) to
  `fn 0x880404f4`, which always writes it into an AstLog log
  (`0x88044478`, `L"DefultDebugMessage"`) and forwards it to a second
  `DebugLog` path only when the words at `0x89e613b0` and `0x89e613b4` are
  both 1; in both boots that gated block was never reached, and neither path
  references the SCIF. So the banner **cannot** appear on `0xffe46000`
  in this retail build, with or without the flags.
- **HYPOTHESIS:** setting both flags in emulation would route the banner to
  the `DebugLog` consumer (`0x88044fe8`), not to the serial port; a serial
  banner would need an emulator-side hook on `0x880404f4` (HLE), not a flag.
- **UNKNOWN:** what sets `0x89e613b0` in a normal boot (`0x88049f58`
  copies a caller-supplied word; its callers are indirect).

## Conclusion

M8.A6's done-when is met by its second branch: the serial model is wired and
proven by a positive and a negative control, and the EXP shows why the
banner does not appear — the retail kernel routes `OEMWriteDebugString`-style
output to AstLog, and the only SCIF writer is the AER exception dump. The
SCIF stays useful as an **exception oracle**: when a later stage triggers the
AER path, its report lands on `-serial`. New claims C-1280–C-1283; the
`run.sh --serial` option is the user-visible change. The full-extent boot's
3 `illegal_instruction` exceptions did not reach the AER reporter in 60 s.

C-1283 records a tooling defect found on the way: `run.sh` sizes each
image from the `u32` **at the image start** (`0x3e00200`), which is code
(589 833 B), not the CE length; the length word sits 0x200 earlier
(`0x3e00000`: `0x006e18a4` = `physlast − physfirst`, EXP-2026-11-05-37).
This is M8.A3's input (the built-in loader copies `physfirst..physlast`).
