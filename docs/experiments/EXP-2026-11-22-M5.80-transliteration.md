# EXP-2026-11-22-M5.80-transliteration: glyph-table-driven name fallback

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** EU2011 font table from `EXP-2026-11-22-M4.87-polish-glyphs` (C-7880–C-7889); synthetic town `tools/osm_synth.py --seed 1 --tile B48R058R` (deterministic); factory tile `B48R058R.DAT` `e9c9cb22…3ff52`
- **Tools:** Python 3.15.0; `tools/transliterate.py` (new, `--selftest`), `tools/tilewriter.py --transliterate` (new flag), `tools/mesh_split.py`, `tools/roadclass_v0.py`, `profiles/pl-glyphs.json`
- **Claims:** C-7990–C-7994
- **Supersedes:** none
- **Superseded by:** none

## Question

Can names the EU2011 map font cannot draw be transliterated in one compiler place, driven by M4.87's glyph table, while names whose glyph exists stay unchanged — and does a generated tile carry the expected strings?

## Hypothesis

A profile with `present` (8 letters) and `transliterate` (10 letters) is enough: map each missing character once, keep everything else, including ASCII and `1=` name prefixes. **Falsifier:** a present letter changes, an ASCII name changes, or a generated tile contains the original undrawable spelling.

## Inputs

| Item | Value |
| --- | --- |
| Glyph source | M4.87: drawable `Ą ą Ć ć Ę ę Ó ó`; undrawable `Ł ł Ń ń Ś ś Ź ź Ż ż` |
| Profile | `profiles/pl-glyphs.json` (`source` field cites the EXP) |
| Generated tile | scratch `tile2.DAT`, built from the seed-1 synthetic town with `--transliterate` |
| Tool / version | `python3 tools/transliterate.py --selftest`, Python 3.15.0 |

## Method

1. **Sample and hash.** No vendor data is committed; the factory tile stays in the extracted tree and the synthetic town comes from a committed generator.
2. **Commands.**

   ```bash
   S=/home/marek/projekty/leafre-work/scratch/m5.80
   python3 tools/transliterate.py --selftest
   python3 tools/selftest.py --only transliterate
   python3 tools/transliterate.py name 'Łódź Święta Ą ć'
   python3 tools/osm_synth.py --seed 1 --tile B48R058R -o $S/town.jsonl
   python3 tools/mesh_split.py $S/town.jsonl -o $S/split
   python3 tools/roadclass_v0.py --class-table-out $S/ctab.json
   python3 tools/tilewriter.py $S/split --out $S/tile2.DAT --cell B48R058R \
     --factory /home/marek/projekty/leafre-work/m5.29-factory-root/MAPAL001/B48R058R.DAT \
     --class-table $S/ctab.json --country 616 --level 1 --transliterate
   python3 tools/transliterate.py tile $S/tile2.DAT --text '1=Wroclawska'
   python3 tools/transliterate.py tile $S/tile2.DAT --text '1=Wrocławska'
   ```
3. **Controls.** *Positive:* the 8 present letters and an ASCII name are unchanged; the 10 missing letters map exactly as the profile says. *Negative:* the generated tile must have 0 hits for the original spelling of a changed name. *Tool control:* `tilewriter --selftest` stays 89/89 with the new flag added.
4. **Scope.** Polish letters only, one level-1 tile, road/place names in the IMF name path plus a standalone JSONL command for POI/address name fields. Excluded: the unlocated byte→Unicode conversion (M4.87 UNKNOWN), L3/L4 rendering, and search-collision resolution.
5. **Falsifier.** Any present letter changes, or the tile still carries `1=Wrocławska`, would invalidate the implementation.

## Observations

```text
transliterate selftest: 8 kept, 10 mapped, ASCII/prefix unchanged
tool:transliterate PASS; tilewriter --selftest: OK (89/89 checks)
$ python3 tools/transliterate.py name 'Łódź Święta Ą ć'
Lódz Swięta Ą ć
tile 1=Wroclawska  -> hits=4
tile 1=Wrocławska  -> hits=0
```

## Interpretation

- **FACT:** the profile drives the mapping: 10 missing letters are replaced, the 8 drawable ones and all other characters (including `1=` prefixes) pass through. The task's illustrative `Łódź → Lodz` is deliberately **not** reproduced because M4.87 says `ó` is drawable; table-driven output is `Lódz`.
- **FACT:** a generated tile carries 4 streams with the transliterated name and none with the original spelling, so the compiler name path applies the fallback before encoding.
- **UNKNOWN:** the byte→Unicode conversion in the firmware was not located by M4.87; transliteration guarantees the code points are in the font's cmap, not that the unit displays the intended glyphs. Any collision in the name index is recorded but not solved (task's falsifier).
- **OBSERVED:** POI/address names can be pre-processed with `transliterate jsonl`; they are not written by `tilewriter` itself.

## Conclusion

M5.80's Done-when is met: the selftest covers all 18 Polish letters plus ASCII and a drawable letter, and a generated tile decodes to the expected names. The fallback lives in one function, `tools/transliterate.py:apply`, driven by `profiles/pl-glyphs.json`.
