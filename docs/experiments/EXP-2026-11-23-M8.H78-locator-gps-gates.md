## Question

`OBJ_GpsInfo` gets the injected fix (C-8576), but `OBJ_CarPos` stays put
(C-8577). Which condition in the locator keeps the GPS position out? Can a
peer meet it?

## Hypothesis

The locator cycle `0x0049fa44` writes the positioning state `0x00dbce00` from
the GPS only when a flag is set. The flag needs something the peers do not
send yet, for example wheel pulses (M8.H32).

## Observations

O1 (gate 1, flag). `0x0049fa44` calls `0x0049eeb4`, then tests
`(*0x00dbd8ac & 0x200) == 0x200` at `0x0049fa58`. Only then does it read the
newest GPS history entry (`0x0049d9ec`) and write mesh, x×1e6 and y×1e6 to
`0x00dbce00`. After that it calls the direction init `0x004aa070`, whose error
text is `--- Dir init err(PRB,GPS) ---`. In S10, every hit had `r2 = 0x7c`,
so the bit was clear.

O2 (who sets the flag). *Corrected by EXP-2026-11-23-M8.H18-nor-flash O6.*
Bit 0x200 is set only in `0x0049e244`, and only when bits 0x01, 0x02, 0x04,
0x08, 0x10, 0x20, 0x40, 0x80 and 0x100 of `*0x00dbd8ac` are all set. The
first version of this EXP said `0x0049e08c` sets 0x200. It actually sets
0x100 (`0x0049e1ae`–`0x0049e1b8`, `mov #64` then `shll2`), when a value
computed with the FPU from the distance between the car's mesh and the GPS
mesh is above 13 (`0x0049e1a4`, `cmp/ge r3,r2` with r2 = 13). That value is
computed only when both hold:

- the newest GPS history entry is not empty (`@(40,r15) != 0` after
  `0x0049d9ec`);
- the car's mesh `*0x00dbce00` is in the loaded mesh table at `0x00dd48e8`
  (lookup `0x00452f1c`, entries of 32 bytes, count at +4).

Otherwise bit 0x100 is cleared (`0x0049e1c2`–`0x0049e1d0`). If the car's mesh
is missing from the table, the other branch (`0x0049e164`) resets
`0x00dbce00` from `0x00def7c0`/`0x00dc0408`/`0x00dbd104`. Its error text is
`--- Dir init err(PRB,POS) ---`. Bit 0x80 is set in `0x0049eeb4` when the
locator input's halfword +22 is at least 100. Bits 0x01–0x40 come from
`0x0049da38`, `0x0049dba0`, `0x0049dc04`, `0x0049dd30`, `0x0049de60`,
`0x0049df90` and `0x0049e00c`, which check the last 15 or 4 GPS history
entries.

O3 (gate 2, stat byte). The GPS history ring is at `0x00dbee60`: 15
entries, the index at +0x3c0, 48-byte records, and mesh triples at +0x30c.
Its writer `0x0046fa60` converts the report to a mesh, using `0x00452f54`
on x and y, only when the first halfword of the report record is 0x00,
0x10, 0x20 or 0x30. Any other value stores a zero triple. The halfword is
the A0 report's stat byte. With stat 0x2f, the value that M8.H73 used and
every variant tried there had low bits set, the record read
`2f00 0100 2e57 2600 c4c5 afff …` and the entry was empty. With stat 0x30,
the entry for Chicago is the triple `0x9f62a223, 0x06c56ca6, 0x00db0130`.
This is the M8.H73 falsifier for the stat values: none of `2f/3f/1f/5f/
6f/7f/0f` could ever pass.

O4 (gate 3, empty mesh table). With stat 0x30, the GPS entry is valid, but
`0x00452f1c` returns −1 for the car's mesh `0x997192c3`. The table at
`0x00dd48e8` holds pointer `0x00dbede0` and count 0. The table is filled
only by `0x00451f8c` (through `0x0056d09c`, r7 = the table). In S10 that
function did not run in 12 s. Its only caller on the 0x66 path is
`0x00479d44`, and only after `0x00456cc8` returns no error. That call
returns `0xffff` (`@(36,r15)` at `0x00479dea`).

O5 (gate 4, no current road link). `0x00456cc8`, the map-matching cycle,
whose pool holds the debug texts `pos_jg condition`,
`LOC_LMgps_posUse_infTbl_cnt` and `HDOP = … long_axis`, exits at
`0x00456eb0` (`braf` to the epilogue at `0x00458d54`) when the current
road link `*0x00dbdc30` is 0. It is 0 in S10. The link is set only by
`0x0045ece4` and cleared by `0x00478e18`. None of the 6 functions that call
`0x0045ece4` (`0x004652a4`, `0x0046f600`, `0x00477e98`, `0x00479644`,
`0x00489a74`, `0x0049106c`) ran in 15 s. `0x00477e98` (subcode 110) builds
the candidate links from the saved locator data at `*0x00dbdcb0`
(count at +0x470).

O6 (why the locator has no state on ze0). The serial log shows the
`VSram` flash driver failing at start: `IOCTL_FMD_READ Error` (6 times),
`IOCTL_FMD_ERASE Error`, then `OBJ_BackUp_Load Error` and `+++ERROR UnLoad
BackUpInfo @OBJ_Carpos_initialize`. `Navi.exe` has the texts `OBJ_CarPos read
error set DefaultPos`, `===   LOC SRAM OK (Ver. %d <--> %d)   ===`,
`Locator SRAM clear` and `*** GPS Pos use BACKUP DATA NO DATA ***`. So
the car position (33.92, −118.52, C-8577) is the default, and the saved
road link and mesh table of the real unit never load.

O7 (Poland). With stat 0x30 and the fix at Wrocław (51.11, 17.03),
`0x00452f54` returns −1 (r0 = 0xffffffff at `0x0046faea`), and the history
entry stays empty. Chicago in the same run returns 0 and a mesh. The US map
build has no mesh for a point in Poland, so the GPS fix there can never
pass gate 2. That holds whatever the link, flag or sensor state.

O8 (screenshot). After unlock the screen shows the LAX map (Airport Blvd,
W Century Blvd) with no car mark. It is the same before and after the
stat change.

Not tested: the date shifted by −1024 weeks (no date compare was met on
the paths above), and moving wheel pulses (M8.H32).

## Result

The GPS position reaches the car position only through the locator's
map-matching. It needs four things, in this order:

1. a report stat byte of 0x00, 0x10, 0x20 or 0x30;
2. a GPS point that the map build turns into a mesh;
3. a current road link `*0x00dbdc30`;
4. the car mesh in the loaded mesh table, and every bit 0x01–0x100 of
   `*0x00dbd8ac` set (one of them needs the vehicle's own speed input),
   before bit 0x200 can move the car to the GPS.

On `-M ze0`, gate 1 is now met by the peer (default stat 0x30). Gates 3 and
4 fail because the locator backup in `VSram` does not load. That is
emulator work (M8.H18). For the US unit in Poland, gate 2 alone already
rejects every fix, so the car stays on its last matched road. The trailer
case is the same. A map that covers Poland fixes this, not a GPS patch
(C-8647, hypothesis until a car or emulator run shows it).

Hypothesis outcome: partly refuted. The flag is the gate (O1), but what
blocks it here is the missing locator backup and the stat byte, not wheel
pulses.
