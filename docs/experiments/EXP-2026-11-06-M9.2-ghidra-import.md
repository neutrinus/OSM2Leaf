## Question

Can `tools/cerom.py memmap` output be turned, without Ghidra and without
vendor data, into an exact, checkable plan for a headless Ghidra program —
one memory block per `o32_rom` section at its VA with rwx, zero-filled BSS,
compressed sections skipped or flagged, export and thunk labels, and the SH-4
calling convention — and does the tool refuse to claim any import result when
`analyzeHeadless` is absent?

## Hypothesis

`rommap.py` already owns the section rules (overlap, size, range,
`IMAGE_SCN_COMPRESSED`). A second layer only has to (1) rewrite `size` from
`o32_psize` to `o32_vsize` so a Ghidra block covers the runtime extent and a
BSS section is not "zero-sized", (2) keep the stored extent for the bytes read,
(3) add `MODULE::name` labels from `cerom.py exports` and `cerom.py thunks`,
and (4) emit the exact two `analyzeHeadless` invocations. If Ghidra is absent,
`--plan` must still print the plan and the real run must exit `3` with
`MISSING_GHIDRA`, never `0`.

    # 2. drop the raw image block(s); only the CE sections stay.
    for block in list(memory.getBlocks()):

    # 3. create one block per section at its VA.
    for entry, payload in zip(doc["blocks"], payloads):
        address = toAddr(int(entry["address"]))
        name = entry["ghidra_name"]
        size = int(entry["size"])
        if payload is not None:
            block = memory.createMemoryBlock(name, address, size, False)
        else:
            block = memory.createUninitializedBlock(name, address, size, False)
        block.setRead(bool(entry["read"]))
        block.setWrite(bool(entry["write"]))
        block.setExecute(bool(entry["execute"]))
        if payload is not None:
            memory.setBytes(address, payload)

## Interpretation

- **FACT:** `ghidra_import.py` converts the real `cerom.py memmap` document of
  the synthetic ROM into a plan: 2 section blocks at `o32_realaddr`
  (`0x8ce01000` rw-, `0x8d001000` r-x), 2 compressed sections skipped, one
  zero-filled 16 MiB `RAM` block, and the exact two `analyzeHeadless`
  command lines; exit `0`.
- **FACT:** the block extent is the runtime extent (`o32_vsize`) and the stored
  prefix (`o32_psize`) is what is read from the image; a BSS section
  (`psize` 0, `vsize` > 0, `0x80`) becomes a zero-filled block instead of
  being rejected as zero-sized. `rommap.py` is unchanged and still owns
  overlap, range and compressed-section rejection.
- **FACT:** export labels are placed at `e32_vbase + export rva`; the real
  `cerom.py exports NK.EXE` output (`rva=00001100`, no `0x` prefix) is parsed
  as hex, and both prefixed and bare RVAs are covered by the self-test.
- **FACT:** `--plan` writes nothing (no project directory, no artifacts) and
  exits `0` without Ghidra; `--selftest` needs neither Ghidra nor vendor data.
- **FACT:** with no `analyzeHeadless`, a run exits `3` with `MISSING_GHIDRA`,
  lists every searched location plus the `pyghidra` verdict, writes a report
  with `"result": "MISSING_GHIDRA", "pass_claimed": false`, and creates no
  project; an `analyzeHeadless` that exits non-zero is `BLOCKED` `4`, never
  `PASS`.
- **OBSERVED:** `cerom.py thunks --all --json` on this synthetic ROM exits `2`
  with `error: no import stub matched` — the sample has no import table, so
  the thunk path is proven only against a hand-written thunks JSON in the
  self-test, not against tool output.
- **OBSERVED:** the two Jython scripts are generated and statically checked
  (`createMemoryBlock`, `createUninitializedBlock`, `removeMemoryBlock`,
  `setExecute`, `getOrCreateNameSpace`, `createLabel`, `setCallingConvention`,
  `getDefaultCallingConvention`, `getReferencesTo`, `setName`,
  `@runtime Jython`) but **have never been executed**: there is no Ghidra in
  this environment.
- **HYPOTHESIS:** `SuperH:BE:32:SH-4` (the `rommap.py` language id) is the
  right Ghidra language for this code; `processor.verified` therefore stays
  `false` until a real run reads the program's language back and it matches.
- **UNKNOWN (needs a real run):** whether Ghidra 12.2 still ships a Jython
  script provider (otherwise the scripts need the PyGhidra runtime); whether
  `BinaryLoader` imports the image at base `0x0` as one removable block;
  whether `createMemoryBlock` + `setBytes` for a ~25 MiB section is acceptable;
  whether the SH-4 compiler spec has a non-null default calling convention;
  whether an hour of analysis is enough for 149 modules.
- **NOT CLAIMED:** that Ghidra shows `OBJDLL::MAL_DataVol_getOffset` at
  `0x003778b2`/`0x00377b46` or the `HDD_INFO` xref at `0x004e7d28`. The tool
  reports both (export reference counts, and `--xref 0x004e7d28`), but no
  Ghidra run has produced those numbers. L3 is still not claimed.
