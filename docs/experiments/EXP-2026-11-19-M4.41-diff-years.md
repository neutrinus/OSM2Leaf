## Question

For every `MAPAL001/BxxRyyR.DAT` tile common to two editions, which section
changes, by how many records, and which tiles change the least — as a **census**
of what changes *together with* what, with no field-level interpretation.

## Hypothesis

`none / exploratory`. The falsifier: a tile reported "changed" whose section-1,
section-2 and section-4 record multisets, sizes and hashes are all identical
between the two editions, or an added section-1 record that is not a plain
insertion (i.e. the identity match mis-counts an edit as add+remove).

## Inputs

| Item | Value |
| --- | --- |
| Images | the three EU `.img` above (SHA-256 in the header) |
| Tiles | the 45 `BxxRyyR.DAT` names (the `LEV3456R.DAT` coarse-level file is excluded; M4.41 `Scope`) |
| Section framing | `clarion_tile.read_tile` section table: a section spans its `taddr` to the next section's `taddr` (last to EOF) |
| Records | zlib streams the container reaches (`tile_diff.structural_index`); plain SHA-256 |
| Repo tool | `tools/diff_years_tiles.py` (the one that produced the numbers) |

## Method

1. **Sample and hash.** Open each image with `cardcheck.Fat32Image` and read
   `MAPAL001/<tile>` only for the 45 `BxxRyyR.DAT` names common to both inputs;
   no file is extracted to disk.

2. **Commands.** Runnable as written from the repo root:

   ```bash
   python3 tools/diff_years_tiles.py \
     archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     archive/sd-images/LEAF_2014_EU_QSD-357-101.img --top 20 --pairs --json
   python3 tools/diff_years_tiles.py \
     archive/sd-images/LEAF_2014_EU_QSD-357-101.img \
     archive/sd-images/ENV200_2016_EU_QSD-390-100.img --top 20 --pairs --json
   ```

   Record classification (per section): **kept** = plain-SHA multiset
   intersection; **changed** = content-leftovers with the same logical key
   `(level, dir_y, dir_x, slot, first-4 plain bytes)`; **added / removed** = the
   rest, counted by key. Section sizes and SHA-256 are over the section span.

3. **Controls.** *Positive:* `--selftest` builds a synthetic pair where one
   vertex moves in place (must be `changed=1, added=0, removed=0`) and a pair
   with one extra directory record (must be `added=1, removed=0, kept=2`); both
   pass. *Negative:* the same lexicographic stream diff for a moved block is
   reported as moved, not changed, in `tile_diff`'s own self-test; and the
   `B28R070R` 2014→2016 tile whose three section spans are byte-identical is
   reported with `added=0 removed=0 changed=0` (see Observations).

4. **Scope.** 45 tiles × 2 pairs = 90 tile-pair comparisons, three sections
   each; `LEV3456R.DAT` excluded. Every record is inflated, never written, so
   no vendor byte is committed — only counts, sizes and hashes.

5. **Falsifier.** As in Hypothesis: a "changed" tile with no differing section
   span or record, or a section-1 "added" count that an identity match turns
   into an edit.

**Section-2 note.** The "sec2 bytes differing" column counts differing file
bytes inside the declared section span. It is `0` even when section 2's record
multiset changes, because the container re-packs (moves) section-2 blocks
between editions: section 2's *span* then starts at a different offset and the
per-offset byte diff is dominated by that relocation, not by content. The
authoritative section-2 signal is the `kept/changed/added/removed` triple, not
the byte count; the byte count is kept only as the raw file-level measurement.

**One byte-identical tile (2014→2016 `B28R070R`).** All three section spans are
byte-identical (`sec1`, `sec2`, `sec4` SHA-256 equal; the `1,083,392 → 1,092,608`
in its 2011→2014 row is the *file* size and a different pair). Its 2014→2016
counts are `added=0 removed=0 changed=0` in every section — the negative control
that a real change would move, and it does not.

Honest limitation, stated because the done-when asks for three clean pairs:
**the byte-identical edition pair does not produce clean single-variable pairs.**
Every non-trivial tile changes section 1, section 2 and section 4 *together*
(the same street edit moves a background shape, its section-2 graph record and
its section-4 name). A section-4-only rename exists (below) but the other
near-identical tiles also carry section-1/2 edits, so no tile is a one-variable
sample for "one added road" or "one routing-only change". The census is the
result; the clean pairs are the `Stop:` case, published as such.

## Interpretation

- **FACT:** the section framing (section span = `taddr` … next `taddr`) gives a
  stable per-section size and SHA-256 for 45 tiles × 2 pairs; the census counts
  are reproducible from the two commands above.
- **OBSERVED:** every near-identical tile changes sections 1, 2 and 4 together;
  there is no tile with only a section-2 or only a section-4 edit in the 20-tile
  tails. The cleanest samples are section-4 renames (header identical, names
  differ) in 2011→2014 and 2014→2016.
- **OBSERVED:** section-2 byte-diff within the declared span is `0` when the
  container re-packs the section (the span relocates); the record
  kept/changed/added/removed triple is the usable section-2 signal.
- **HYPOTHESIS:** none offered. M4.41 is a census; assigning a field meaning to
  an added section-1/2/4 record is M4.40 (section 2), M4.36 (section-4 index)
  and M4.23/M4.24.
- **UNKNOWN:** which section-2 field corresponds to a section-1 road; the
  section-4 record's pre-names binary fields (M4.21 documents them only partly).

## Conclusion

The census is published: 45 tiles per pair, per-section `kept/changed/added/
removed`, the 20 smallest section-1 changes each, and the section-4 rename pairs
and section-1 add samples named by tile and offset. Per the `Stop:` rule, fewer
than three *clean one-variable* tile pairs exist — the editions move all three
sections together — so the census is the result and the pair search stops. The
section-4 rename pairs and the `B60R060R` added-road tile are the handoff to
M4.36 (name index), M4.40 (section 2) and the section-4 reader; the "constant
section-2 bytes per added road" hint is refuted on two tiles.
