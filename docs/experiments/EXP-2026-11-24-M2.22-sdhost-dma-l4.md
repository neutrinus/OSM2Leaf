## Question

Does a genuinely rebuilt `mkcard` card boot at L4 the same way as the factory
card and as a byte-identical in-place patch, and which of the differences the
fourth PM review attributed to rebuilding (lost volume label, new FAT layout)
actually changes the firmware's verdict on this boot path?

## Hypothesis

The rebuilt card passes L4 with the same stage, launcher and map-file verdict
as the factory card: this boot path checks card *content* (`HDD_INFO`, MMAIN,
map files) but not the root attr-`0x08` label entry or the cluster layout,
consistent with C-794/C-795/C-798. **Falsifier (task):** the rebuilt card is
rejected at a stage the same-session factory card passes — name the log line.
**Second falsifier:** the rebuilt card behaves the same while the in-place rule
says it fails on the unit → the emulator lacks the check, and the EXP must name
the unmodelled check (label read vs cluster/FAT layout). A negative control
that does *not* fail at F4 invalidates the run.

### 3. Controls

- **Positive:** factory (a) must exit 0 with F0–F4 PASS, `launcher ACCEPT`,
  `map_files OPENED`, 0 `ERR_PRC_NAVI [0x28]` lines. F5 PASS or NOT RUN.
- **Negative (mandatory):** the truncated-MMAIN card (e) must exit 1, fail F4,
  and show ≥1 `[ERR_PRC_NAVI],[0x28]` line. If it passed, the gate would be
  silently passing the rebuild too and the run would be void.
- **Neutral:** (d) in-place no-op must be byte-identical to (a) — both SHA-256
  `105e2032…76307` — and its `--verify` must print `matches: true, ok: true`.
- **Structural negative:** `cardcheck.py --selftest` PASS; (e) L1 FAILs with
  `MMAIN001.DAT` 47 B vs DRSTR 4096 B, while (a)–(d) L1 PASS.
- **Discriminator:** the 8 `Launch Process Not Create!!!` lines are identical
  on all four good cards and are not a verdict.

### 4. Scope / corpus

One build (EU 2011), one factory card, five card states, one `--timeout 900`
boot window each, same IPL patch recipe. Corpus: **5 L1 checks, 5 L4 boots,
1 negative control**, four good cards + one bad. Excluded: US/2014/2016,
L5 hardware, `-d unimp` logs (multi-GB `tlb_miss`), CMD42/lock work (M2.23),
display rendering and position-seeded runs. The one-byte TTS change is a
second variable in the rebuilt cards; its role is to trigger the fresh-FAT
path, not to test speech data.

### 5. Falsifier

Same verdict for (b) and (a) while the in-place rule says (b) fails on the
unit → emulator lacks the check; name it. All four good cards identical with
no differing log line → report that none of the rebuilt-card differences is
checked on this boot path. (b) differing from (a) → name the first differing
log line and keep the rule. A first-session early QEMU exit is re-run, never
silently counted as a pass.

## Interpretation

- **FACT:** a genuine `mkcard` rebuild (fresh FAT, `tree_diffs=1`,
  `diff_ranges=200`) exits L4 0 with F0–F5 PASS, `ACCEPT`/`OPENED`, 0 map-file
  errors — indistinguishable from the factory card at this gate. The task's
  second falsifier is met: on this boot path the firmware does not check the
  rebuilt cluster layout or the root attr-`0x08` label entry.
- **FACT:** explicit `--label QSD-309-101` produces a **byte-identical** card
  (same SHA-256 `d785e8ca…531908`) because `mkcard.py:638-647` preserves the
  factory label by default; the 'lost volume label' of EXP-2026-11-06-H10 is a
  historical property of an older builder and is not reproducible with the
  current tool. There is no flag to omit the label (`make_label_entry('')`
  raises `ValueError`), so the label-loss case cannot be built at L4 without a
  tool change (out of scope).
- **FACT:** in-place patching is a strict no-op when the bytes are unchanged —
  (d) is byte-identical to the factory (same SHA) and `--verify` reports a
  match; the rule's "patch in place" cost is unchanged at L4 because both
  routes pass.
- **OBSERVED:** marker-selected serial lines are identical across all four
  good cards; the raw logs differ only in volatile addresses and
  thread-interleaving/one non-fatal `0x15` error, which the gate does not treat
  as a card rejection.
- **UNKNOWN / not modelled:** whether the unit (L5) checks the FAT layout,
  the volume label or an SD lock state that the emulator's `-M ze0` model
  omits; this record licenses no L5 claim. If a future L5 run rejects a rebuilt
  card that passed here, the missing check to model is the label read
  (`attr 0x08` root slot 0 vs BPB `NO NAME`) or the cluster chain layout in
  `SDHC.dll`, neither of which produced a differing verdict line above.

## Conclusion

`docs/research/card-test-plan.md` gains one L4-scoped sentence: the in-place
rule is **kept as a unit-side precaution but not supported by any L4
difference** — all of (a)–(d) pass F0–F5 with identical launcher/map verdicts,
a rebuilt card is byte-different yet L4-equivalent, and the emulator models no
check that distinguishes label or FAT layout, so L4 cannot license lifting the
rule for the unit. Claims C-8040–C-8049 record the card hashes, the rebuild
trigger, the verdict table and the negative control. No format doc changed.
