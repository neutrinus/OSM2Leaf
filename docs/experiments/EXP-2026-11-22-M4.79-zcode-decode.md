## Question

What does `REFER001/ZCODE0nn` contain, field by field, and what fraction of each shard's bytes does a reproducible decode explain — on both on-disk forms and both cards?

## Hypothesis

M4.12 (EXP-2026-11-06-M4.12) verified Form A (ZCODE018/033) addressing and left Form B's offset base unresolved. Expectation: a second header block and a uniform halfword base exist for Form B, so every shard decodes and the byte census explains well over half of each file.

**Falsifier:** if the decode explains under half of a shard's bytes, the layout is wrong or partial. Then say which byte range is unexplained, with its histogram — do not guess.

3. **Controls.**
   - *Positive:* the synthetic `--selftest` builds a Form-A and a Form-B file whose structures are known by construction and checks the decode against them; on real data, ZCODE018 record 0 at `unaddr(0xbaf00)=0x5d7800` is the M4.12-verified `(42830,53372,1712,467,42830,53372,2012,280)`, and ZCODE002's `rec_size/8` = 2808 equals the ladder count the M4.12 EXP reported.
   - *Negative:* `--mutate 0x1012:0xff` on real ZCODE018 moves the record base and must break a check; the selftest also mutates a nodew, a `rec_size` and a Form-B tag.

4. **Scope.** All 33 EU shards (56,487,168 B decompressed). US factory has 0 ZCODE files, so nothing to census there. Firmware reader VAs are unchanged (C-5764/C-5620/C-5623) — this is an offline byte-accounting result, not an L3 run.

5. **Falsifier.** Stated in the Hypothesis; checked per shard (fraction < 0.5 would be reported, not hidden).

## Interpretation

- **FACT:** Form B's real header is mirrored at `0x1100`; `record_base = unaddr(rec_addr_enc@0x1112)` and `records = rec_size@0x1116 / 8` fit all 31 Form-B shards (C-7800, C-7801).
- **FACT:** Form-B child target is `0x1204 + offset*2`, resolved as a nested table or a `count`-long area-ladder block; the walk reaches every Form-B tree with no invalid target (C-7802). This closes the Form-B base C-1005 marked UNRESOLVED.
- **FACT:** the census explains 96.45 % of the 33 EU shards in aggregate, ≥ 67.7 % per shard, so the falsifier does not fire (C-7805).
- **OBSERVED:** Form-B `size` (multiple of 6, 12–66) and the second entry halfword are not pinned; record payloads are per-file (ZCODE002 area ladders, ZCODE018 coord-like pair) (C-7803, C-7809).
- **UNKNOWN:** the firmware record walker is still not located; the field-decode has no VA confirmation (C-7808, unchanged from C-5764).

## Conclusion

`tools/zcode_decode.py` reproduces the `ZCODE0nn` decode and counts explained bytes for every shard. `docs/format/coord-zcode-icode.md` §Form B gains the `0x1100` header mirror and the two verified bases; the matrix row 8 Offline cell changes from `claim` to `tool` with this command cited. The remaining unexplained bytes (0–32 % per shard) are mid-tree alignment gaps and inter-table padding, listed per shard as a 4 KiB-block histogram; no field is guessed. Firmware-side confirmation (a reader VA / L3 run) stays open in C-5764.
