## Question

Do factory EU and US SD card images carry `HDD_CHK.ATT` as a file, and what are
the statically observable verification semantics of
`MapUpdate.exe!sub_0001e3f4` (the final `SilentAuthenticate` check)?

## Hypothesis

None / exploratory refinement of M2.12. M2.12 found `HDD_CHK.ATT` referenced only
by `MapUpdate.exe` (not `Navi.exe`) and left `sub_0001e3f4` and on-card presence
open. **Falsifier (presence):** any `HDD_CHK.ATT` directory entry / file content
found in the EU or US factory card data area (not in CE firmware module strings)
with a recoverable path/size/SHA-256. **Falsifier (1e3f4):** `sub_0001e3f4` is a
plain byte memcmp of `(file_buf, decoded, bytesRead)` or ignores `file_buf`.

### 2. `sub_0001e3f4` disassembly (IMG256 B, `--image-start 0x3e00200`)

Module VA `0x0001e3f4`, file `0x43515f4`. Callee-saved r8–r13,pr; 32B frame.
Entry args preserved: `r12=file_buf(r4)`, `r8=decoded(r5)`, `r13=bytesRead(r6)`
(M2.12 caller: `file_buf=ctx+0x11a`, `decoded=r14+8` (10B from ctx+120 hex),
`bytesRead=0x80`).

- **`0x1e40a–414`:** `bytesRead > 0xC0` (unsigned, `cmp/hs r13,r3` with `r3=0xC0`)
  => set `r8=1`, branch to epilogue => **return 1**.
- **Setup:** `jsr 0x1e270` (`*0x1e610`) zeros/inits a workspace and sets globals
  `*0x212c8/0xd0/0xcc/0xd4/0xd8` to offsets within `*0x21220`. `jsr 0x199b8`
  (`*0x1e614`) calls `(* *0x21300)(id=5, buf, &len=8)` (memset via COREDLL
  `#1044` inferred by `(dest,fill?,n)`/memcpy usage at 0x4c6/5b6; returns buf or
  0); its 8B output is copied to `* *0x212c8` (0x426–44c). `jsr 0x19978`
  (`*0x1e61c`) calls `(* *0x21300)(id=6, ...)` → 4B transformed to 8 hex ASCII
  nibbles (`+'0'`, no A–F alpha fixup) stored at `(*0x212c8)+8` (0x454–4c2).
- **Template transform:** `memcpy(*0x212d0, 0x157ec, 16)` where 0x157ec =
  `b"VerUp Secret KEY\0\0\0\0"` (16B) (0x4c6–4cc). `sub_1e2d4(*0x212d0,0x157ec,16)`
  builds a stack ctx (type bytes `2,2` at +24,+25; `0x80` at +28), calls
  `0x1e6f8(ctx)` then `0x1e834(ctx,dest,src,len,...)` (pools 0x1e328/32c →
  0x1e6f8/0x1e834); requires result `==16` (0x4ce–4da). `sub_1e2d4(*0x212c8,
  *0x212d0,16)` similarly (0x4dc–4e8). Either `!=16` => **return 2** (0x4ea).
- **Buffer assembly:** copies `file_buf[0..7]` → `*0x212d0[0..7]` (0x52e–552);
  copies `decoded[0..7]` → `*0x212cc[0..7]` (0x556–580); performs an 8-iteration
  XOR/transform over `*0x212cc` (0x582–590, operands per disasm/register state;
  r4 set from `*0x212cc` at 0x54e => self-relative index 0 observed) then builds
  `*0x212d0[0..7]=*0x212cc[0..7], *0x212d0[8..15]=~*0x212cc[0..7]` (0x592–5aa).
  `memcpy(*0x212d8, file_buf, bytesRead)` (0x5ac–5b8, COREDLL `#1044`).
- **Final check / return:** sets up a small stack ctx (0x5ba–5ca), optionally
  calls `sub_1e760`/`sub_1e7c8` on it (0x5ce–5e8, type-2 ctxs via
  `*0x21300/*0x21760` function pointers 0x1e9c0/1eaa0/1ed9c), calls
  `sub_1e330(r4=*0x212d8=file_buf copy, r5=*0x212cc, r6=bytesRead, r7=*0x212d0)`
  (0x5ea–5f4), **saves `sub_1e330`'s r0 into r8 in the `jsr 0x1e270` delay slot**
  (0x5f8/5fa), runs `sub_1e270` cleanup, returns **r8 = `sub_1e330` result**.

`sub_0001e330` (VA 0x1e330): scans `r4[0..r6)` for `\r\n` (0x0d,0x0a); not found
or `r6<=0` => **return 3**. Found: `p+=2`; builds 16B at `r7` as
`[p[0..7], ~p[0..7]]` (0x372–3b2); calls `sub_1e2d4(r7, 0x157ec, 16)` (0x3b4–3bc;
pool 0x1e3ec/3f0 → 0x157ec/0x1e2d4); compares `r7[0..7]` vs `r5[0..7]` (0x3d4–3e6)
=> **return 0 on match, 3 on mismatch**.

`sub_0001e2d4` (0x1e2d4): builds a type-2 stack ctx, calls `0x1e6f8` (init) then
`0x1e834` (transform) via pools 0x1e328/32c; returns transform byte count/result
(or 0 on init failure). `sub_0001e760`/`1e7c8` gate on ctx byte `+4 == 2` and call
function pointers at `*0x21300`/`*0x21760` (0x1e9c0/1eaa0/0x1ed9c).

## Interpretation

- **FACT (presence):** Neither the EU nor US factory card images carry a
  `HDD_CHK.ATT` data file. Extracted roots contain `VER_INFO/HDD_INFO.TXT` but no
  `HDD_CHK.ATT` (positive control). Raw-image hits are exactly the 4 UTF-16LE
  path strings inside `MapUpdate.exe` (CE B + B copy) in both images — firmware
  strings, not card files. C-2090, C-2091.
- **FACT (1e3f4):** `sub_0001e3f4` is not a plain memcmp. It rejects
  `bytesRead>0xC0` (ret 1), derives device material via `*0x21300` ids 5/6,
  transforms the `"VerUp Secret KEY"` template and buffers via the `sub_1e2d4`
  crypto-context path, incorporates `file_buf[0..7]`/`decoded[0..7]` and the
  full `file_buf` copy, and returns `sub_1e330`'s result (0/3). C-2092–C-2094.
- **FACT (1e330/layout implication):** `sub_1e330` requires `\r\n` within the
  0x80-byte read and consumes 8 bytes immediately after it, verifying them
  (through `sub_1e2d4` against 0x157ec) against the derived check value. This
  constrains `HDD_CHK.ATT` to a record containing a CRLF followed by ≥8 bytes of
  payload within the first 0x80 bytes — but the full field layout and the
  authoritative generator/byte-range binding remain **UNKNOWN**. C-2095.
- **OBSERVED:** the crypto/transform primitives (`sub_1e2d4` → `0x1e6f8/1e834`,
  `1e760/1e7c8` → `*0x21300/*0x21760` → `0x1e9c0/1eaa0/1ed9c`, type-2 contexts)
  resemble a CE crypto/provider dispatch but their exact algorithm and keying are
  not identified from this static pass; the 0x582–590 XOR operand provenance has
  a disassembly-ambiguous index (self-relative observed) that needs a value-trace
  to state as a firm data-flow fact.
- **UNKNOWN / DEFERRED:** exact `HDD_CHK.ATT` on-disk layout and byte-range
  attested; exact binding of `ctx+120`/`decoded` to file content; identification
  of the crypto API/algorithm and the `*0x21300`/`*0x21760` objects. **Blocks:**
  resolve CE function-pointer tables / ordinals for the crypto dispatch
  (or a dynamic trace with a real `HDD_CHK.ATT`), and recover a genuine
  `HDD_CHK.ATT` sample (none on factory EU/US). No vendor bytes to commit.

## Conclusion

Factory EU and US cards do **not** carry `HDD_CHK.ATT` as a file (roots clean;
raw-image `HDD_CHK.ATT` strings occur only as `MapUpdate.exe` path data in CE B
and its copy, same offsets on both images). `sub_0001e3f4` (MapUpdate.exe B
`0x0001e3f4`) is a multi-step verifier, not memcmp: it enforces `bytesRead≤0xC0`,
derives device/transform material (`*0x21300` ids 5/6, `"VerUp Secret KEY"`
template via `sub_1e2d4` crypto context), and returns the result of `sub_1e330`,
which scans the 0x80-byte file buffer for CRLF, takes the 8 bytes after it, and
verifies them (via `sub_1e2d4`/template 0x157ec) against the derived value
(return 0 accept / 3 reject). Exact crypto primitives and the full `HDD_CHK.ATT`
record layout remain deferred (no factory sample, crypto dispatch unresolved).
