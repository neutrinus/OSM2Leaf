## Plan (written before coding)

- **Approach.** (1) Extract both factory `LCTBL001.DAT` files and list every catalog code, decoded to `(CC, LTN)`, with per-country counts; read whether a code with high byte ASCII `'3'` (Poland) is present instead of assuming it. (2) Write a two-table synthetic Polish spec whose two tables hold the *same* location code with distinguishable records; build it with the new table-code flag and run the firmware lookup (`0x14e4` sub 1, country 3) once for the catalog present code and once for an absent code; compare the `0x14fb` answer records. (3) Express the result as a one-line generator rule, add it as a `lctbl_build.py synth` flag with a synthetic negative-control selftest, and put the rule in `docs/format/rdstm.md` §LCTBL.
- **Signature / format source.** The catalog code is read by the **writer's inverse** (`tools/lctbl_build.py walk`: `u16` at `+28` of each 46-byte group-1 descriptor, written by `build()` as `TABLE_CONST + p16(code)`); `(CC, LTN)` is decoded by `tools/tmc_reception.py code_cc_ltn`. The request and answer words come from an **L3 run** of `tools/lctbl_lookup_l3.py` (firmware code in PySh4), not from a format doc. The `table_code(cc, db) = ord(hex digit of cc) << 8 | db` rule was established in EXP-2026-11-20-M4.16d / M5.60; this record tests which code a generator must write, not the rule itself.
- **Files.** `tools/lctbl_build.py` (flag + catalog listing + selftest only), `docs/format/rdstm.md` (§LCTBL rule only), this EXP, claim rows and the M5.64 task block through `tools/board.py`. Read-only: `tools/lctbl_lookup_l3.py`, `tools/lctbl_records.py`, `tools/tmc_reception.py`.
- **Intended Done when.** The EXP states EU/US catalog codes counted per country, the Poland code a unit would request, the hit vs absent-table-fallback `0x14fb` answer words, and a one-line `generator table code = …` rule; `lctbl_build.py` takes the rule as a flag with a `--selftest` negative control; `rdstm.md` §LCTBL carries the rule and cites this run.

## Question

Which table codes do the EU2011 and US2011 `LCTBL001.DAT` catalogs actually carry (counted per country), does either contain a Poland table, and which table's record does the firmware's `0x14fb` answer reflect for a Poland (country 3) request — the code in the catalog or the first-table fallback observed in M5.60?

## Hypothesis

Neither 2011 catalog has a Poland (CC `'3'`) table; the firmware still accepts a generated table with a code of the form `ord('%X' % CC) << 8 | LTN`, and for CC 3 that means `0x33nn`. A request naming a code present in the catalog returns that table's record; a request naming a code absent from the catalog is served from the file's **first** table (M5.60's "observed" line), so the same location code returns a *different* record.

**Falsifier (fixed before the run):** a generated file holding the predicted Poland code whose record is not returned for a matching request; or an absent-code request that returns a record from a table other than the first one (then M5.60's fallback line is retracted); or a Poland table found in the catalog with a high byte other than ASCII `'3'`.

   `synth --table-code CC,DB` assigns `ord('%X' % CC) << 8 | (DB + table index)` to the spec's tables; `catalog` prints each code with its decoded `(CC, LTN)` and a per-country tally. The L3 tool mounts the EU card, replaces `RDSTM001/LCTBL001.DAT` with `POL.DAT`, sends one `0x14e4`/sub-1 request per lookup and carries every message until the `0x14fb` answer.
3. **Controls.** *Positive (catalog hit):* `3,0x11,1234` names table `0x3311`, which the generated catalog holds; its answer record must equal table 1's record (kind code `20111`, "ulica catalog-table"). *Negative (absent table):* `3,0x12,1234` names `0x3312`, which the catalog does **not** hold; per M5.60 the answer must come from the **first** table (`0x3310`, kind code `100`, "ulica first-table"). *Negative (selftest):* a wrong country code must make `lctbl_lookup_l3`'s model helper miss the record. The factory catalogs are the control that the catalog listing is read from the files, not invented.
4. **Scope.** Two factory catalogs (EU2011 30 tables, US2011 34 tables as printed by `check -v`), one generated two-table file, three L3 lookups in EU2011 build A only; no US L3 run (no US firmware build in `head256.img`), no car/bench run (L5 unavailable). Excluded: record contents of the 64 factory tables (only codes/counts are read), 2014/2016 cards (different unit generation).
5. **Falsifier.** As stated under Hypothesis; additionally the selftest must fail if the wrong code is accepted.

## Interpretation

- **VERIFIED (C-6610, C-6611):** neither factory catalog has a Poland table. EU2011: 30 tables / 247,089 records in 11 CC groups, `Poland CC 3: 0 tables, 0 records`; US2011: 34 tables / 303,023 records in 2 CC groups, `Poland CC 3: 0 tables, 0 records`. The Stop rule does not fire because the request country *is* readable from the runs (O5–O7 print country 3 → table `0x33nn`).
- **VERIFIED (C-6612, C-6613):** `code 0x3319 -> (3, 25)` and `CC3 -> ISO [616]`; the catalog code is `ord(hex digit of CC) << 8 | LTN`. A unit in Poland requests country 3 → `0x33nn`; `nn` (LTN) cannot be read from either 2011 catalog and remains UNKNOWN.
- **VERIFIED (C-6614):** the `0x14e4` sub-1 request with the catalog code returns `0x14fb` status 1 and the catalog table's record; the firmware keys LCTBL by the table code the writer writes.
- **VERIFIED (C-6615, C-6616):** an absent code also returns status 1, but the `0x14fb` answer reflects the **first** table's index/directory/page and record — on the generated file and on the untouched factory card. M5.60's "observed" fallback is confirmed, not retracted.
- **VERIFIED (C-6617, C-6618):** the one-line rule is `generator table code = (ord("%X" % (CC & 0xF)) << 8) | (LTN & 0xFF)` (`0x33nn` for Poland); `synth --table-code 3,0x10` writes `0x3310, 0x3311`, and a wrong CC 4 misses the record.
- **OBSERVED (C-6619):** the task's third precheck command (`tmc_reception.py table --help`) is stale on this revision; the capability is `join --help` / `code_cc_ltn()`.
- **HYPOTHESIS:** an actual Polish TMC receiver sends CC 3 with an LTN that is not on these 2011 cards; the generator must pick that LTN and write the matching `0x33nn` table or the unit will be served the first table's names.
- **UNKNOWN:** Poland's LTN (no 2011 catalog row, no `reception.dat` Polish row in M4.16d), and the US firmware build's lookup path.

## Conclusion

The EU2011 and US2011 catalogs contain no Poland (CC 3) table (0/30 and 0/34). The firmware's `0x14e4` sub-1 request for country 3 reaches a generated table only if the generator writes a code of the form `0x33nn`: the catalog-hit lookup (`0x3311`) returned that table's record, while an absent code (`0x3312`, and `0x3301` on the factory card) was answered from the **first** table. The rule `generator table code = (ord("%X" % (CC & 0xF)) << 8) | (LTN & 0xFF)` is now a `lctbl_build.py synth --table-code` flag with a negative-control selftest and is recorded in `docs/format/rdstm.md` §LCTBL. Open: Poland's LTN, a unit (L5) check of the fallback, and the US build.
