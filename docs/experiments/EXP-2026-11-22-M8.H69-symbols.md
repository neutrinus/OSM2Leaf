# EXP-2026-11-22-M8.H69: Symbol file for the ZE0 guest from `.pdata` and exports

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** `archive/head256.img` (EU 2011 firmware head, 268,435,456 B), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  negative control `archive/us256.img`, SHA-256
  `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`
- **Tools:** python3 3.15.0 (stdlib only), gdb 18.1 (Python-enabled); repo tools
  `tools/ze0_syms.py`, `tools/qemu-ze0/gdb-ze0.py`, `tools/cerom.py`,
  `tools/pdata.py`, `tools/nk_decomp.py`, `tools/build_targets.py`,
  `tools/selftest.py`. No recompression; `tools/zlibinfo.py` not applicable.
- **Claims:** C-8140–C-8149
- **Supersedes:** none
- **Superseded by:** none

## Question

Can one JSON symbol table name the functions of all three CE ROM segments of a
ZE0 card image, so that a PC — in particular the `MMAIN001.DAT` reader at
`0x0041a438` — resolves by name in both directions, including inside gdb,
without a function start being silently attributed to the wrong build where A
and B/C overlap (C-6913)?

## Hypothesis

Yes. Every `.pdata` START becomes `fn_0x<VA>` unless a module export lands on
the same VA or a known role VA from `tools/build_targets.py` /
`tools/fixtures/fn_match_eu_us_2011.json` names it; keeping one table per build
and printing the build with every hit prevents cross-build mis-attribution.
**Falsifier:** the MMAIN reader VA fails either lookup direction; a build-shared
start loses one of its real `build!module` owners; a US-only role VA is attached
to the EU image; or a start resolves only into a module of the wrong build.

## Method

1. **Sample and hash.** `sha256sum archive/head256.img archive/us256.img`
   yields the two hashes in the header. Both are the 256 MiB firmware heads;
   the full 8 GiB cards are not used. No bytes are written to the image.
2. **Commands.** All run from the task worktree; the scratch paths are
   disposable and are recreated by the commands themselves.

   ```bash
   cd /home/marek/projekty/OSM2Leaf.task-m8.h69-symbols
   python3 tools/ze0_syms.py --selftest
   python3 tools/selftest.py --only ze0_syms
   python3 tools/qemu-ze0/gdb-ze0.py --selftest
   python3 tools/nk_decomp.py pdata archive/head256.img 0x0041a438 --module Navi.exe
   python3 -c "import sys; sys.path.insert(0,'tools'); import build_targets; print('ROLES rows', len(build_targets.ROLES))"
   python3 -c "import json; d=json.load(open('tools/fixtures/fn_match_eu_us_2011.json')); print('fixture rows', len(d['rows']))"
   python3 tools/ze0_syms.py archive/head256.img
   python3 tools/ze0_syms.py archive/head256.img lookup 'Navi.exe!mmain_reader' 0x0041a438
   python3 tools/ze0_syms.py archive/head256.img verify
   python3 tools/ze0_syms.py archive/head256.img lookup 0x00012b58
   python3 tools/ze0_syms.py archive/us256.img lookup 'Navi.exe!mmain_reader'
   python3 tools/ze0_syms.py archive/us256.img --builds A lookup 0x0041a438
   python3 tools/cerom.py archive/head256.img memmap --modules Navi.exe \
       --out /home/marek/projekty/leafre-work/scratch/m8.h69/memmap_navi_real.json
   python3 tools/ze0_syms.py archive/head256.img \
       -o /home/marek/projekty/leafre-work/scratch/m8.h69/syms_real.json
   python3 tools/qemu-ze0/gdb-ze0.py \
       --memmap /home/marek/projekty/leafre-work/scratch/m8.h69/memmap_navi_real.json \
       --syms   /home/marek/projekty/leafre-work/scratch/m8.h69/syms_real.json \
       --pc 0x41a438
   gdb -q -batch \
       -ex 'set $ze0_memmap = "/home/marek/projekty/leafre-work/scratch/m8.h69/memmap_navi_real.json"' \
       -ex 'set $ze0_syms = "/home/marek/projekty/leafre-work/scratch/m8.h69/syms_real.json"' \
       -ex 'source tools/qemu-ze0/gdb-ze0.py' -ex 'ze0-threads'
   python3 tools/ze0_syms.py archive/head256.img \
       -o /home/marek/projekty/leafre-work/scratch/m8.h69/syms_a.json
   python3 tools/ze0_syms.py archive/head256.img \
       -o /home/marek/projekty/leafre-work/scratch/m8.h69/syms_b.json
   sha256sum /home/marek/projekty/leafre-work/scratch/m8.h69/syms_a.json \
             /home/marek/projekty/leafre-work/scratch/m8.h69/syms_b.json
   ```
3. **Controls.** *Positive:* `tools/nk_decomp.py pdata` independently confirms
   `0x0041a438` is a real pdata `START` in `Navi.exe`;
   the synthetic ROM selftest names an export start and a role start; the US
   image must resolve `Navi.exe!mmain_reader` to its own VA `0x0044219c`.
   *Negative:* the EU VA `0x0041a438` queried on the US image must **not** get
   the `mmain_reader` name; an overlapping start must be reported `ambiguous`
   rather than silently assigned to one module; `verify_attribution` with a
   zero-length function span must report one missing owner (selftest).
4. **Scope.** Three CE segments of each of two 256 MiB heads: build A at
   `0x200200`, B at `0x3e00200`, C at `0x5200200` — EU A 149 modules /
   87,530 functions, B 91 / 21,930, C 88 / 25,243; US A 135,659 functions in
   total across the three builds. Role names come from 45 `build_targets.ROLES`
   rows and 13 rows of `fn_match_eu_us_2011.json`; only the image SHA-256
   selects the EU or US column. Module `.pdata` exception directories are read
   through `tools/pdata.py` (decompressing a stored table where needed);
   compressed `.data` otherwise stays unread. The gdb check sources the script
   against a stopped target with 0 CE threads, so it exercises file loading and
   PC decoration, not a live breakpoint hit.
5. **Falsifier.** A start owned by two builds resolving to only one of them;
   an EU-only name appearing on the US image; the MMAIN reader failing either
   direction; or a `.pdata` START being attributed to the wrong module.

## Interpretation

- **FACT:** `0x0041a438` is a `Navi.exe` pdata START (length `0xf4`)
  in the EU 2011 head; `tools/build_targets.py` names it
  `mmain_reader` and both lookup directions print that name (C-8141).
- **FACT:** All 328 modules across A/B/C of the EU image decode their pdata
  table with 0 errors; 134,703 function starts are indexed, 1,367 of them
  numerically shared between builds. Each shared start still resolves to all
  of its owners, and within-build multi-owner starts are marked `ambiguous`
  (C-8143, C-8144).
- **FACT:** A role name is selected by image SHA-256: the US image resolves
  `mmain_reader` to `0x0044219c`, while `0x0041a438` there is unnamed
  (C-8145).
- **OBSERVED:** 87,530 EU build-A starts yield only 3,534 named functions;
  exports supply 4,606 names overall but `Navi.exe` exports none, so reader
  functions depend on the 45-row role table (13 fixture rows add slugs such as
  `mmain`) (C-8142).
- **OBSERVED:** The symbol JSON is byte-identical across two runs on the same
  image (C-8148), and gdb prints the name when `$ze0_syms` points at it (C-8146).
- **HYPOTHESIS:** The same table will decorate live L4 breakpoints once a debug
  session is attached; only the loader path is verified here (C-8149).
- **UNKNOWN:** The 19 unplaced EU role VAs and the 51 per kernel build are
  mostly data helpers/leaf functions without pdata records; this tool does not
  invent names for them.

## Conclusion

`tools/ze0_syms.py` turns the CE ROM TOC, `.pdata` and export tables into one
deterministic `syms.json`, with `lookup` in both directions and a `verify`
command for the cross-build falsifier. `tools/qemu-ze0/gdb-ze0.py` consumes that
file from `$ze0_syms`, `$ZE0_SYMS` or `./syms.json`, and prints
`<module!name>` on each PC; its output is unchanged without the file. The
selftests are registered (`tool:ze0_syms PASS`), the MMAIN reader resolves both
ways, and no start is silently mis-attributed across builds A/B/C. No
`docs/format/` page changed — this is a debugging tool, not a format claim.
Eight claims C-8140–C-8147 are verified, C-8148 is observed and C-8149 is a
hypothesis.
