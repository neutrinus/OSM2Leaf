## Question

Can the M9.39 mutant `POINT010` pair (`ea2d0e0f…` US, `e75c298f…` EU, one
differing outer stream) be regenerated by a committed command, instead of the
`python3.13 - <<'PY'` heredoc its EXP shipped?

## Hypothesis

The heredoc is `read_ind` → `decode` → `resize_name` → `slot_budget.
fit_page_inplace` → `cmpind_codec.repack_changed_chunks` → `build_ind`, i.e.
exactly the CLI's own steps with a different final container build. Wiring the
last step to `repack_changed_chunks` should reproduce both EXP SHAs byte for
byte on the runtime M9.39 used. **Falsifier:** the chunk-preserving CLI still
emits a `.cmp` whose streams differ from more than one, or its SHAs do not
equal the EXP's pins on the EXP's runtime.

## Method

1. **Sample and hash.** Both 256 MiB heads above; both factory pairs hashed
   above; `read_ind` prints the stream counts and `0x10000` chunk size.
2. **The edit.** The same two `--resize` name edits M9.39 used, with the same
   text, pages and +4 B delta (`mutate_refer_poi.resize_name`).
3. **The rebuild.** The CLI now defaults to a chunk-preserving outer rebuild:
   `cmpind_codec.repack_changed_chunks` copies every unchanged 64 KiB stream
   verbatim and re-deflates only the chunk the inner page lives in; `.ind` is
   rebuilt with `cmpind_codec.build_ind`. `--whole-blob` restores the old
   all-streams path. The inner page still goes through
   `slot_budget.fit_page_inplace` (factory encoder first, then the smallest of
   levels 1–9 × memLevel 8/9 — the documented level-9 fallback of C-4175).
4. **Controls.** *Positive*: the factory page on both builds prints the
   factory offsets. *Negative*: (a) a name absent from the page is refused
   (exit 1) and writes nothing; (b) a same-length content edit leaves every
   walked offset at the factory value; (c) `--whole-blob` on the same edit is
   the old path and must keep working (M5.12c).
5. **Falsifier** (stated before the result): the CLI changes more than one
   outer stream, or its US/EU `.cmp`/`.ind` SHAs differ from `ea2d0e0f…` /
   `5d576d62…` / `e75c298f…` / `077937ea…` on this runtime.

## Interpretation

- **FACT:** the committed chunk-preserving command reproduces all four M9.39
  SHAs byte for byte on stock zlib 1.3.2 (the runtime M9.39 names — M9.39
  wrote `python3 3.13.17 / zlib 1.3.2`), and changes exactly one outer stream
  per pair (132/149 US, 110/151 EU).
- **FACT:** the four firmware walks on the committed-command mutant pages give
  the same offsets as M9.39 (`n=501`/998/999 +4; `n=500` fixed; 1,000
  records; `n=1000` `None`), so the L3 corpus M9.41 cites is now rebuildable
  from the repo.
- **FACT:** the same-length control leaves every offset at the factory value,
  so the +4 the walker follows is the record length, not the byte change.
- **OBSERVED:** a different zlib runtime (zlib-ng) moves only the re-deflated
  chunk and therefore the `.cmp`/`.ind` SHAs; the untouched streams stay
  verbatim. The pins are valid on stock zlib 1.3.2 and are recorded with
  `tools/zlibinfo.py`.
- **IMPLICATION:** the M9.39 `Method` heredocs can be replaced by one committed
  command per pair; the mutating code no longer lives only in a session.

## Conclusion

`tools/mutate_refer_poi.py` now rebuilds the outer container
chunk-preservingly by default (`cmpind_codec.repack_changed_chunks`), with
`--whole-blob` as the explicit old path. The committed command reproduces the
M9.39 mutant pairs (`ea2d0e0f…`/`5d576d62…` US, `e75c298f…`/`077937ea…` EU)
on stock zlib 1.3.2, one differing stream per pair, and the four L3 walks are
unchanged. No format claim changes; C-4173/C-4174 keep their pins.

## Corrections after navigator review (same task, same branch)

1. **Claim IDs renumbered** from C-4460–C-4469 to **C-4480–C-4489**: another
   open branch (M5.46) takes C-4470–C-4479, and the old numbers collided with
   nothing only because that branch had not merged yet. Check with
   `grep -n 'C-44[5-9][0-9]' docs/research/claims.md` — the M9.43 header is
   `(C-4480–C-4489)` and its rows run C-4480…C-4489; no `C-446x` row remains
   in `claims.md` (this Corrections section is the only place the old block is
   named, by design).
2. **The same-length `.cmp` pin was the zlib-ng value** (`7249d8f4…`/
   `1e711d17…`) under a `python3.13`-only Tools header. The committed command
   under `python3.13` gives `d81a912b…`/`914418c5…` (C-4484 and the M9.39
   same-length block), which is what the EXP now quotes; the zlib-ng pair is
   named as such in the same bullet. Shown by re-running the command in the
   Reproduction block.
3. **The whole-blob message text was the `--batch` form.** The single-file
   path prints `outer rebuild: whole-blob (1/149 stream(s) differ)`; `(149
   stream(s))` is only what `--batch` prints. Shown by
   `python3.13 tools/mutate_refer_poi.py … --page 0x840ba0 --old 'NMBRS1700'
   --new 'NMBRZ1700' --whole-blob`. The old rationale ("same bytes because
   this host reproduces the changed chunk") was wrong: the coincidence is
   that stock zlib 1.3.2 re-encodes the untouched factory chunks to the same
   bytes, while under zlib-ng whole-blob gives `5950a042…` against
   chunk-preserving `7249d8f4…`.
4. **The first follow-up bullet was false**: it said EXP-M9.39's Method still
   showed the two heredocs, but `grep -c "python3.13 - <<'PY'"
   docs/experiments/EXP-2026-11-17-M9.39-point010-mutant.md` is `0` and its
   `Follow-up M9.43` section records the replacement (C-4487). The bullet now
   says the heredoc half is closed.
5. **The pre-change defect row (C-4480) is a zlib-ng readout** and now says
   so; the stock-1.3.2 behaviour of the old code is stated next to it.
