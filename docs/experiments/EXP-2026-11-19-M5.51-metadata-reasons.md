# EXP-2026-11-19-M5.51-metadata-reasons: per-range reasons for the metadata a card diff admits

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** EU 2011 image `LEAF_2011-2012_QSD-309-101_navi158_eu.img`, SHA-256 `105e2032…76307`; the M5.30 result card `b0faf119ee2ccfb3ce757bafa49ba7bdac6730d32c8ac97a2337fb18e3c33237`
- **Tools:** `python3 3.13.17 / zlib 1.3.2` (stock, for the splice); `python3 3.15.0 / 1.3.1.zlib-ng` (read-only checks); repo tools `tools/imgpatch.py`, `tools/mkcard.py`, `tools/fit_census.py`
- **Claims:** C-4610–C-4619
- **Supersedes:** none (extends C-3063, which stated the whole-sector class)
- **Superseded by:** none

## Question

When `imgpatch --check-diff --allow-metadata` accepts a card whose only diffs
outside the replaced files are FAT/FSInfo sectors, can each accepted range be
**named** — which FAT entry/copy and which link of the move, or which FSInfo
word — so that a planted byte in FAT slack is refused rather than admitted as
"metadata"?

## Hypothesis

Yes. A relocation rewrites exactly the FAT entries on the replaced files' old
and new chains (`FAT[old_cluster]` freed, `FAT[last_new]` terminated, the
neighbours linked) in each FAT copy, plus the FSInfo free-count and next-free
words. Every other byte in the FAT/FSInfo sectors is slack. If each metadata
range is attributed to a specific entry index and compared against the old/new
chains of the replaced files, then the 9 real ranges of the M5.30 card each get
a `fat{0,1}_link` / `fsinfo_{free,nxt}` reason, and a byte planted anywhere
else is named `fat*_slack` / `fsinfo_unknown` and refused by a strict mode.

**Falsifier:** a metadata range whose bytes are not one of the move's own
`FAT[old]`/`FAT[new]`/neighbour links or FSInfo free/next words is labelled
`fat*_link`/`fsinfo_*` and passes strict mode — i.e. a planted slack byte is
admitted as expected.

## Method

1. **Sample and hash** as above; the card is rebuilt from M5.30's Reproduction
   (copy the image, patch the M5.44 tile with `--allow-resize`, patch
   `DRSTR001.DAT`), which reproduces `b0faf119…33237`.
2. **Commands** — one block, run as written (see §Reproduction). `--check-diff
   --strict-metadata` implies `--allow-metadata`.
3. **Controls before the result:**
   - positive A: the real card, strict mode — 9 metadata ranges, 0 unexpected;
   - positive B: the same card without `--strict-metadata` — the M5.30 wide
     behaviour, `outside 0`, 9 metadata (must be unchanged);
   - negative A: flip FAT0 entry 50,000 (not on the move's chain) to
     `0x0FFFFFFF` — strict must name it `fat0_slack` and fail;
   - negative B: flip a byte at FSInfo sector 1 offset `0x100` (not the
     free/next words at `0x1e8`/`0x1ec`) — strict must name it
     `fsinfo_unknown` and fail;
   - unit: `--selftest` on a synthetic resize plants a free FAT entry off the
     chain and asserts it is named `fat0_slack` and fails strict, while the
     wide mode still admits it.
4. **Counted corpus:** the real card's 586 diff ranges / 152,815 B, of which
   9 metadata ranges; the mutants add 1 range each.
5. **Falsifier** from the Hypothesis, run as negative A/B.

## Interpretation

The 9 real ranges are exactly the move: `FAT[94806]` was the tile's last old
cluster (`268435455` = EOF) and now points at `29687`; `29687 → 29688`;
`29688` is the new EOF (`268435448` = `0x0FFFFFF8`, the on-disk EOF marker);
the free count and next-free move in both FSInfo copies. No FAT entry is
touched outside `{94806, 29687, 29688}`, and no FSInfo byte outside the two
words. That is a stronger statement than "the metadata sector changed": it can
be checked entry by entry, and a planted byte in the same sector is caught.

The `fat*_slack` class is what the M5.30 navigator's planted FAT0-entry mutant
belongs to; before this task it was admitted as metadata (whole-sector). It is
now named and refused under strict mode, which is the falsifier being
*prevented*, not merely observed.

## Conclusion

- `--check-diff --strict-metadata` names every admitted metadata range and
  fails any range that is not one of the move's own FAT links or FSInfo words.
- The M5.30 card passes it (exit 0, 9 named ranges, 0 unexpected) and the two
  planted-byte mutants fail it (exit 1, 1 unexpected each).
- Wide `--allow-metadata` is unchanged, so M5.30's recorded numbers still hold.

## Follow-ups

- The wide `--allow-metadata` remains the M5.30 default for the recorded card;
  making `--strict-metadata` the default on a produced card is a policy call
  for M5.30's consumer (M5.41's expected-change-set), not this task.
- A future FSInfo field (if the writer ever touches boot-signature words) would
  need its own reason; strict mode refuses it until then, by design.
