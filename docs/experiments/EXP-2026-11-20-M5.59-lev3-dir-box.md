## Question

After the change, does `lev3456gen.py` write the level-3 roads of an extract
into the directory whose box holds them, with points that decode back onto
the roads, and does the firmware read that directory at the extract's
position? Are levels 4 and 5 placed by the same geometry?

## Hypothesis

The directory head gives the box: `y = 1.5 · lat`, stored `x = lon − 100`,
and a level-3 directory is 16 × 16 parcels of 0.5 units. Choosing the
directory by that box puts the Krotoszyn fixture (51.70 N 17.45 E) in
directory 24 and a London fixture in directory 22. Levels 4 and 5 have one
directory over the whole database, so the old proportional rule already
equals the box rule there.

**Falsifier:** a changed level-3 directory whose box does not hold the
extract; a stored point that does not decode onto a road; a record header
that differs from the template's parcel code for the slot; the firmware
reading another level-3 directory at the position.

   `placement` does not use the generator's split. It lists the records of
   the generated file that differ from the template, decodes their road
   shapes, turns every stored 11-bit point back into lat/lon from the
   directory head (`point_in_dir`) and measures its distance to the nearest
   road segment of the extract in coordinate steps (limit 2). It also compares
   the record header with the header of the template record in the same slot.
   `codes` counts, over all section-1 records of levels 3/4/5 of the template,
   the headers that equal `parcel_code` (the C-2805 rule in half units).
3. **Controls.** *Positive*: `codes` on the factory file (the geometry must
   explain every factory header); the London fixture must land in directory
   22. *Negative (must fail)*: the generator before this change (commit
   `8e0f913`) on the Krotoszyn fixture; the London file checked against the
   Krotoszyn roads; `codes` with the column index shifted by one. An empty
   extract must give back the template byte for byte.
4. **Scope.** Section 1, levels 3, 4, 5 of one file (EU 2011: 45 + 1 + 1
   directories; 12,059 + 1,021 + 62 records for the header census). Two
   positions. The firmware run covers the mount (directory read and slot-table
   parse); no coarse record is read at mount (M9.53), so the firmware has not
   drawn these roads. Not changed: the container writer, the segment split
   (bisection into two-point shapes), rows the template does not have.
5. **Falsifier.** As in Hypothesis.

## Interpretation

- **Verified:** the generator now selects the level-3 directory by its box
  and quantises against the 30′ × 20′ parcel inside it; the fixture's roads
  are in directory 24, the points decode back to within 1.1 coordinate steps
  of the roads, and the firmware reads that directory at Krotoszyn. The
  London control lands in directory 22.
- **Verified:** levels 4 and 5 were already placed correctly (one directory
  whose box is the database bounds, so the proportional rule equals the box
  rule); no change was needed there. The check that says so reads the
  geometry from the file.
- **Verified:** the record header code of levels 3, 4 and 5 is a function of
  the directory head and the slot (1,083 + 12,059 factory records, 0 with the
  column shifted). The stop condition (header code against box geometry) does
  not apply: they agree. The generator now computes the code and refuses a
  template record that disagrees, instead of copying the template's header
  or writing `(0, 0)` into an empty slot.
- **Not verified:** that the unit draws these roads at level 3 (no record is
  read at mount, M9.53/M9.58).
- **Unknown:** what to do with roads in a row the template has no block for
  (counted as `l3_shapes_skipped_no_row`, 0 in both fixtures) and outside
  every directory (`l3_segments_outside_every_directory`).

## Conclusion

C-2445 is closed: generated level-3 roads are in the right place on the
coarse map. `placement` is the check to run on every generated
`LEV3456R.DAT`.
