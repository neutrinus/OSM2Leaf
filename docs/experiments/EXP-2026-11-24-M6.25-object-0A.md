## Question

What is object `0x0A` of the `OBJDLL.dll` object store, which `VSram` data id and store does it use, and can an anonymous/fresh unit ever have it saved?

## Hypothesis

The `[0x0A]` argument in `OBJ_BackUp_Load Error` is the object's registration index into a 56-byte descriptor table; index `0x0A` is the odometer semantic object, whose data lives under a VSram area id in the main `SMST` store. A fresh `-M ze0` boot has no odometer record because no distance was ever driven (no accepted vehicle-speed frames), so the load fails until a save path runs. Falsifier: after running the object's own save path the error still logs `[0x0A]`, or a mutation of the object's own record leaves the log unchanged.

### 3. Controls

- **Positive:** the committed anon image reproduces exactly one `OBJ_BackUp_Load Error` with `ErrorLogMsg() Called. [ERR_PRC_OBJ],[0x64],[0x0A]...` (precheck_f2); `unitflash_anon.py check` prints `ok: PROD sum, NK1 sum, SMST stores`; `unitflash_anon.py --selftest` prints `selftest: PASS` (12 checks). The name string `OBJ_SEM_ODOMETER` is present at the printed name-table index, and entry `0x1e` is `SID_PLUGINPNT`, a positive control that the lookup is by registration index, not by `+0xc`.
- **Negative (mandatory mutation, run):** flipping one byte at `AREA 0 +0x1234` in both copies and recomputing the store sums gives `sram-neg` SHA-256 `d87946b4b9a23a3f05ccc7f488e34ea48fa259211f5580f2b246b49e52f45ff1`, built image SHA-256 `3937fd6654cc662b30b3d61087e2465cfbd4241df110062806cfab9e80980078`; its boot logs **two** `OBJ_BackUp_Load Error` lines, `[ERR_PRC_OBJ],[0x64],[0x0A]` and `[ERR_PRC_OBJ],[0x64],[0x17]`, vs one line in the unmutated boot. The error set is not invariant under mutation of the object's store, so the test can fail. (EXP M6.24 O6 observed the related effect with a *broken* sum: objects `03 05 0A 0C 10 19`.)
- **Negative (fresh unit):** no vehicle-speed frames are accepted in `-M ze0` (M8.H49: UAT3 wire framing unknown, C-7469), so the odometer accumulator is never fed; the fresh boot logs the load error.
- **Tool control:** `unitflash_anon.py --selftest` PASS; `cerom.py` `cerom`/`sh4xref` VAs checked against `nk_decomp.py pdata` START labels.

### 5. Falsifier

Stated before the result: (1) if running the odometer's own save path left `[0x0A]` in the log, the hypothesis is refuted; (2) if mutating the object's store left the error set unchanged, the attribution is refuted; (3) if the descriptor index argument were not the same index used by the name-table lookup, the naming is refuted. Result: (1) the save path is not reachable on a fresh `-M ze0` (no accepted speed/ignition input), so the load error persists — this is the "why a fresh unit cannot have it" branch of Done-when; (2) the mandatory mutation moved the error set from one to two objects; (3) `extu.b r8,r6` in the log caller and the name-table `mul #36,r4` both use the registration index, so the naming holds.

O3 (descriptor semantics, all SH-4 LE, every VA from `cerom.py`/`nk_decomp.py`):

## Interpretation

- **FACT:** Object `0x0A` is `OBJ_SEM_ODOMETER` (name-table index `0x0A`, `id=10`); the `[0x0A]` log argument is the same registration index used to index the name and descriptor tables (O1, O2).
- **FACT:** its descriptor has `+0=1` → SRAM/VSram medium, `+0xc=0x1e` (30) → VSram data id, `+0x10=8` → size/count argument to the VSram record comparator `0x034735f4` (O3). STORE: `SMST` AREA 0 of `SRAM`, which `tools/unitflash_anon.py` `AREAS[0]` places at mirror `0x00000` size `0x30000`, flash copy1 `0x400000`, copy2 `0x430000`. No finer within-store byte offset is claimed: the descriptor carries no store pointer.
- **FACT:** the name-table `id` field at index `0x0A` is `10`, and entry `0x1e` is `SID_PLUGINPNT`; therefore descriptor `+0xc=0x1e` is a VSram data id, NOT the semantic class id. (Correction of an earlier driver misreading, per navigator round 1.)
- **OBSERVED:** an anonymous boot has exactly one load error, object `0x0A` (O4). Flipping one byte in AREA 0 makes two objects fail (`0x0A`, `0x17`), so the error set is mutable (O5).
- **HYPOTHESIS:** a real unit gets the odometer record when the odometer accumulator is fed by accepted vehicle-speed/ignition inputs and the VSram store is committed; a fresh `-M ze0` unit never receives such input, so it cannot have the object.
- **UNKNOWN:** the within-store byte offset of the odometer record and the exact ignition-off commit event that persists it; both need an accepted UAT3/VCAN trace (M8.H49/H51). The record is therefore not regenerated here; Done-when is met by the "why a fresh unit cannot have it" branch.

## Conclusion

Object `0x0A` is `OBJ_SEM_ODOMETER`, stored in VSram under data id `0x1e` (30) in `SMST` AREA 0 (`SRAM` copy1 `0x400000` / copy2 `0x430000`); its descriptor's `+0=1` selects the SRAM medium and `+0x10=8` is a size/count argument. A fresh anonymous unit cannot have it: `-M ze0` supplies no accepted vehicle-speed or ignition input, so the odometer accumulator never runs and no record is committed; the boot therefore logs one `OBJ_BackUp_Load Error` for `0x0A`. The mandatory mutation moved the error set to two objects, so the attribution can fail. Changes: claim rows C-8870–C-8879 and TODO M6.25 `Result` only; no format or tool code changes.

## Corrections after navigator review

Round 1 (CHANGES): the driver first read descriptor `+0xc` as the semantic
class id. Navigator corrected this with a command-quoted ruling: `+0` is the
storage-medium selector (fn `0x0347753c`: 0/1/2 → INVALID/SRAM/FLASH),
`+0xc=0x1e` is the VSram data id (name-table `0x1e` = `SID_PLUGINPNT`, not
`OBJ_SEM_ODOMETER`), and `+0x10=8` is a size/count argument to comparator
`fn 0x034735f4`. All three corrections are applied above in Inputs, O3 and
Interpretation. Round 2: final APPROVE; navigator re-ran both mandatory
checks (negative mutation 1→2 errors; numbers quoted; exp_check /
claims_check / todo_check OK). Non-blocking advisory: the `80 hits / 2 with
id 0x1e` breakpoint stdout of `cap_sram.py` was printed in the session but
not saved to a file, so that count is not retained as an artifact; the
`+0xc=0x1e` value itself is independently verified statically via
`sh4dis --va 0x034776a4` (O3) and does not depend on the count.
