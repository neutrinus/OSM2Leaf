## Question

Can the `ze0` machine skeleton (`hw/sh4/ze0.c`) be added on top of the merged
M8.A1/M8.A4/M8.A5 work so that `bash tools/qemu-ze0/build.sh --force` applies
every `tools/qemu-ze0/patches/*.patch`, builds `qemu-system-sh4`, and
`-M ze0` both lists the machine and reproduces the `ce_qemu_probe.py` access
list?

## Hypothesis

The machine can be implemented as a small SH-4A board that reuses `sh4-ccn`
(M8.A4) and `ze0-stubs` (M8.A5), and the five-patch series applies cleanly in
`build.sh`'s `LC_ALL=C sort` order. The build/runtime parts of the done-when
depend on a host that can configure QEMU 8.2.7 `sh4-softmmu` (glib-2.0 dev,
pixman, meson/ninja toolchain) or on a prebuilt LE `qemu-system-sh4`.

## Interpretation

- **VERIFIED (patch apply):** The M8.A2 machine skeleton patch integrates
  cleanly with M8.A4/M8.A5 in build.sh sort order on pristine QEMU 8.2.7
  (tarball SHA-256 pinned). The full five-patch series applies without
  rejects.
- **OBSERVED:** The host cannot configure/build QEMU 8.2.7 `sh4-softmmu`
  (missing glib-2.0 dev/pkg-config) and has no prebuilt `qemu-system-sh4`.
  This is an environment blocker, not a code rejection.
- **HYPOTHESIS (runtime, unverified):** On a host that builds the patched
  tree, `qemu-system-sh4 -M help` will list `ze0` and `-M ze0` with
  `ce_qemu_probe.py`-style `-device loader` setup will reproduce the probe's
  unmodelled-access progression as far as CCN/ze0-stubs cover (CCN accesses
  become modelled; ze0-stubbed windows no longer appear as invalid). The exact
  access list will differ from the stock `-M none` probe because the machine
  models CCN and boot-stub windows by design.
- **UNKNOWN:** Whether the P1/P2 alias regions cause any conflict with SH-4
  softmmu translation in this QEMU version; whether the catch-all priority
  interactions are sufficient for all boot-path accesses; and the final PC /
  first-failing access when run against a real kernel image with the built
  binary.
