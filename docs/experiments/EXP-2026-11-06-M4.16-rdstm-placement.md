## Question

Is there a join key that places `RDSTM001` rows on the map (row → tile/mesh →
coordinate), matching rows to tile road segments with coordinates, as required
by M4.2, M4.3 and M5.3?

## Method

Tested candidate join keys from M4.1's 16-byte row layout
(`id,pad2,ref:u32,src:u16,dst:u16,code:u16,tail:u16` — field meanings
HYPOTHESIS, C-106/C-555) against tile identifiers:

1. **M4.1 fields vs tile road identifiers** (section 1 road-shape link ids
   `lid`, section 2 graph link/entry ids `id & 0x1fff`, section 2 parcel codes,
   section 1/2 parcel u32 codes, stream `(A,B,tag)` keys) over 8 `MAPAL001`
   tiles, for the 34 rows in `0x1000..0x1220` (the region before M4.15's
   drift/padding, C-1801).
2. **Value-space / random-key controls:** for each u16 key, compared hits to
   (a) the expected rate `|row_values| * |target| / space` and (b) a random
   control (uniform sample of `|target|` ids from the same value space, seed 1).
   For `ref` (u32) vs `INTER*` byte patterns, compared real refs to 500
   random `u32` values (seed 42) across the same 5 decompressed `INTER` files.
3. **Distribution check:** section 1 `lid` values are heavily skewed (all
   0–255 present; ids restart per class/chain), so bare membership is not a
   row→segment join.

Tool: `tools/rdstm_place.py` (`probe`, `--selftest`, synthetic no vendor data).

most common `(0,32357),(1023,15754),(5120,10781),(8222,10203),…`; **all values
0–255 present** (`256/256`). A bare u16 membership hit is therefore not a match
to a specific road segment (ids are non-unique across class/parcel/tile).

### 2. `ref` (u32) vs stream keys / parcel codes

- stream `(A<<16|B)` keys (6 tiles): `ref∩AB = 0`, `src/dst/code∩A,B ≈ 0`

- `ref` (both byte orders) vs section 1/2 parcel u32 codes (8 tiles):
  `ref∩sec2_parcels = 0`, `ref∩sec1_parcels = 0`, random fake-u32 control 0.

Real > random suggests `ref` values share structure/value range with `INTER`
contents, but this is **not** an aligned-record match and provides no

### 4. 0x1a700 tuple arrays

`rdstm.md`/C-106 note `0x1a700` holds `u16` tuple arrays (ids + two references,
`0x0000` separators); `rdstm_schema.py scan --start 0x1a700` prefers 2-byte
records (score 0.342). A coarse intersection of 0x1a700 u16 values with
section-2 ids across 10 tiles (2540 vs random 1174) is explained by coverage
(`62671 * 2652 / 65535 ≈ 2536`), i.e. no enrichment — no join established.

## Interpretation

- **FACT (negative):** none of the M4.1 16-byte row fields (`id,pad2,ref,src,
  dst,code,tail`), tested as `src/dst/code` vs section 1/2 link ids, `ref` vs
  parcel/stream keys, and `ref` byte patterns vs tile/INTER, yields a
  reproducible row→tile road segment join with a random-key control showing
  ~0 *segment-specific* matches. Apparent u16 id hits track the dense lid value
  space (sec1 lids cover ~38% of u16 and every 0–255 value), not row identity.
- **FACT (context):** M4.15 disproved the 16-byte `src/dst` graph framing
  (0/10 reciprocity, drift at `0x10a0`, C-1800–C-1802) and M3.7 identifies
  `RDSTM001` as a TMC location record table decoded via a per-record field
  directory (C-882–C-887), not a mesh-keyed routing graph. A valid row→segment
  placement therefore likely requires the per-record directory / TMC→location
  mapping, not the M4.1 byte offsets.
- **HYPOTHESIS (lead):** the `INTER*` `ref` byte-pattern enrichment (real >>
  random u32) may indicate a shared index space; an aligned-record comparison
  and an `INTER`→tile/mesh coordinate hop are needed to confirm.
- **Join key:** **not identified** from M4.1 fields. Done-when (≥20 rows
  matched to tile road segments with coordinates, join key named, ~0 random-key
  control) is **not met**.
