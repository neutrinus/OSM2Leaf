## Question

Where does `Navi.exe` (EU2011) take the length of a tile directory read
from, so that a writer can compute it for any tile?

## Hypothesis

The length is not the directory's size (C-3257). It comes from a constant
table indexed by a per-(section, level) value of the header.

**Falsifier:** a fourth tile (not `B48R058R`, `B48R068R`, `B28R070R`) shows a
directory read length that the rule did not predict; or a header change of
the kind byte does not change the read length as the table says.

## Predictions (written and committed before the runs that test them)

Rule: `length = 0x100 * T[kind].n`, `T` = the 16 rows printed by
`python3 tools/dir_read_len.py table archive/head256.img`; `kind` = byte 1 of
the level-table entry `(level, kind, u16 count)` at header `0x1ac`; a kind
with no row gives no read. `--flip P@OFF:X` XORs the byte with `X`
(`vcard_l3.py`).

- **P1, fourth tile `B60R048R.DAT`** (two sections, no section 4), position
  65.0 N 30.0 E: every directory read of section 1 level 2 and section 2
  level 2 is `0x14100`, section 1 level 1 `0x8100`, section 2 level 1
  `0x2100`; no section-4 directory read (`dir_read_len.py predict` on the
  tile).
- **P2, B48R068R with two kind bytes changed** (default position):
  `@0x1c5:0x13` makes the section-1 level-1 kind `0x92 ^ 0x13 = 0x81` →
  `0xa100` (a length no run has shown); `@0x1dd:0x93` makes the section-4
  level-1 kind `0x93 ^ 0x93 = 0x00` → `0x1100`. Section 2 unchanged
  (`0x14100`, `0x2100`).
- **P1b (added after P1 read only the `B60R048R` header, see Observations;
  committed before its run), `B40R060R.DAT`** (359,412,736 B, SHA-256
  `b5d8a9a37e6c257af7c4dedc52ea04d0e3d7fb094350f8c8d034081903fa2bc9`, three
  sections), position 45.46 N 9.19 E: section 1 and 2 level 2 `0x14100`,
  section 1 level 1 `0x8100`, section 2 level 1 `0x2100`, section 4 level 1
  `0x6100`. A second position in `B60R048R` (64.5 N 29.0 E) is run with the
  P1 prediction.
