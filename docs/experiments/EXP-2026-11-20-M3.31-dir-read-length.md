## Question

Where does `Navi.exe` (EU2011) take the length of a tile directory read
from, so that a writer can compute it for any tile?

## Hypothesis

The length is not the directory's size (C-3257). It comes from a constant
table indexed by a per-(section, level) value of the header.

**Falsifier:** a fourth tile (not `B48R058R`, `B48R068R`, `B28R070R`) shows a
directory read length that the rule did not predict; or a header change of
the kind byte does not change the read length as the table says.

## Predictions (written and committed before the runs that test them)

Rule: `length = 0x100 * T[kind].n`, `T` = the 16 rows printed by
`python3 tools/dir_read_len.py table archive/head256.img`; `kind` = byte 1 of
the level-table entry `(level, kind, u16 count)` at header `0x1ac`; a kind
with no row gives no read. `--flip P@OFF:X` XORs the byte with `X`
(`vcard_l3.py`).

- **P1, fourth tile `B60R048R.DAT`** (two sections, no section 4), position
  65.0 N 30.0 E: every directory read of section 1 level 2 and section 2
  level 2 is `0x14100`, section 1 level 1 `0x8100`, section 2 level 1
  `0x2100`; no section-4 directory read (`dir_read_len.py predict` on the
  tile).
- **P2, B48R068R with two kind bytes changed** (default position):
  `@0x1c5:0x13` makes the section-1 level-1 kind `0x92 ^ 0x13 = 0x81` →
  `0xa100` (a length no run has shown); `@0x1dd:0x93` makes the section-4
  level-1 kind `0x93 ^ 0x93 = 0x00` → `0x1100`. Section 2 unchanged
  (`0x14100`, `0x2100`).
- **P1b (added after P1 read only the `B60R048R` header, see Observations;
  committed before its run), `B40R060R.DAT`** (359,412,736 B, SHA-256
  `b5d8a9a37e6c257af7c4dedc52ea04d0e3d7fb094350f8c8d034081903fa2bc9`, three
  sections), position 45.46 N 9.19 E: section 1 and 2 level 2 `0x14100`,
  section 1 level 1 `0x8100`, section 2 level 1 `0x2100`, section 4 level 1
  `0x6100`. A second position in `B60R048R` (64.5 N 29.0 E) is run with the
  P1 prediction.

## Observations

**Static.** One literal pool holds `0x00179c08` (`0x00409048`, loaded at
`0x0040901c`). The leaf at `0x0040901c` walks 16 rows of 12 bytes for
`row[0] == r4`, returns `row[r5]` (`mul.l`, `shll2`, `mov.l @(r0,r6)`), or 0
when no row matches. Two callers load it: `fn 0x0040ba48` (call at
`0x0040bb96`, column 2, adds the value to a running pointer) and
`fn 0x00414338` (call at `0x004143e2`, column 1). In `0x00414338` the kind
is `u16 @(0xd982a0 + 12 * (6 * r9 + r10))` (`r9`, `r10` = arguments 3, 4)
and the result is shifted left by 7 (`n << 7` = length / 2, i.e. the
length in `u16` units) and stored at request `+24` (stack `+40`), then
`0x004086b4(request)` is called. The request the map-file layer receives
(`0x0041841c`) carries the length / 4 at `+12`; the conversion between the
two is not read here, so the byte rule `0x100 * n` is the length measured at
L3 (every run below).

**Call chain (static, EU2011).** The section-table handler `fn 0x0040c308`
calls `fn 0x00415a3c`, which calls `fn 0x004158b4`, which calls the request
builder `fn 0x00414338`, which calls the leaf `0x0040901c`: the builder is
in the `0x0040c308` subtree that the task's Scope names. `table` prints the 16 rows
(kinds `0x00`–`0x03`, `0x80`–`0x83`, `0x10`–`0x13`, `0x90`–`0x93`) and
"matches the copy".

**Kind writer (probe, not committed: a write watch on `0xd982a0`).** Every
entry is written by `fn 0x00409834`, first at `0x0040987a` (from the
constant rows at `0x00564218`), then at `0x00409960` (`extu.b` of the
merged level-table word). Values in the default run: index 0 (section 1)
levels 1..6 `0x92 0x91 0x91 0x91 0x90 0x80`; index 1 `0x90 0x91 – 0x91
0x91`; index 2 `0x93`. Hooking `0x0040aa50` in C1 shows the B48R068R
header entry as loaded is `(1, 0x03, 0x40)`: `--flip` XORs (`0x92 ^ 0x91`).

## Interpretation

- **FACT:** the directory read length is `0x100 * T[kind].n`, with `T` the
  16-row table at `0x179c08` and `kind` the runtime kind of the (section,
  level) pair, computed in `fn 0x00414338` by the leaf `0x0040901c`
  (EU2011). It explains C-3257: the four constants are the rows of the four
  kinds every EU2011 tile carries.
- **FACT:** the kind is the header's level-table kind byte (byte 1 of the
  entry at `0x1ac`), merged across mounted headers by `0x0040aa50`; a
  count-0 entry does not take part (C5). A kind with no row loses the
  directory read (C3).
- **FACT:** the rule predicted all five directory reads of a fourth tile
  (`B40R060R`) and the two never-seen lengths of P2 (`0xa100`, `0x1100`)
  before the runs.
- **OBSERVED:** at two positions inside `B60R048R` (its 0x2ac boxes cover
  64.0–69.33 N, 28.0–36.0 E) the mount reads only that tile's header and
  then reads `B28R070R`'s directories; the rule is not tested on
  `B60R048R`, and why the mount leaves it is not read here (new **M3.33**).
- **OBSERVED:** three of the six files checked have section-4 directories whose
  firmware read runs past the end of the file; whether the firmware fails
  on them (as on the 22 KiB fresh tile, C-3256) is not run here (M5.56).
- **UNKNOWN:** what bits of the kind mean (bit 7 does not change the
  length); the use of column 2 by `fn 0x0040ba48`.

## Conclusion

`docs/format/map-tiles.md` gains "Where the directory read length comes
from" with the rule, the table and the VAs; the M9.13 section's
"OBSERVED" note points to it. Claims C-5820–C-5826. A writer computes the
length from the kind byte it writes (`tools/dir_read_len.py predict`), which
is what M5.56 needs. Open: B60R048R not mounted at its own positions
(M3.33), the factory short section-4 reads (M5.56).

## Corrections after navigator review

1. **Count.** The headline "105/105 directory reads" was a sum error: the run
   table holds 8 runs with 11 directory reads and 3 with 10, so **118/118**.
   Corrected in this EXP (Scope, Observations), `map-tiles.md`, C-5824 and the
   TODO Result line.
2. **Short-read scope.** The list of directories read past the end of the
   file covered only the six files checked, not the card. Over all 46 EU2011
   `MAPAL001` files (`for f in FROOT/MAPAL001/*.DAT; do python3
   tools/dir_read_len.py predict $f; done`), **35 files** have such reads,
   **53 directories**, all section 4 level 1. `map-tiles.md`, C-5826 and the
   TODO line now say so. M5.56 shows the firmware cuts these reads at the
   DRSTR001 size.
3. **Unit of `n << 7`.** C-5820 and Observations said the builder stores
   `n << 7` without naming the unit, which looked inconsistent with
   `0x100 * n`. `n << 7` is the length in `u16` units (length / 2); the
   conversion to the `length / 4` word the map-file layer receives is not
   read, and the byte rule is stated as measured at L3.
4. **Call chain** `0x0040c308 → 0x00415a3c → 0x004158b4 → 0x00414338 →
   0x0040901c` added to Observations (navigator, static).
5. **US256 offset.** The full table's file offset in US256 (`0xdff7e0`) is
   given next to the rows at `0xdff870`.
