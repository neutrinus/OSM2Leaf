# EXP-2026-11-06-M1.2b: XPRESS plain LZ77 implemented and probed on the real sections

- **Status:** done (tool + probe; negative result on the real payloads)
- **Date:** 2026-11-06
- **Sample:** `IMG256` `/tmp/opencode/head256.img`, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Claims:** C-650–C-659
- **Supersedes:** EXP-2026-11-05-M1.2b-decoder-probe (tool half only)
- **Superseded by:** none

## Question

Is the real CE ROM compressed payload (M1.2a form 1, `NaviMapCC.dll` sections
1 and 2) an XPRESS plain LZ77 stream, now that the decoder is implemented
instead of a skeleton?

## Hypothesis

The 22-byte M1.2a header hides a plain LZ77 stream starting at offset 22.
If so, `decompress_xpress_lz77` (ported from the klauspost/compress reference)
must produce exactly `0x484` (section 1) / `0xcc0` (section 2) bytes with
plausible content (pointers into `0x8c…`, strings).

## Inputs

| Item | Value |
| --- | --- |
| Section 1 stored bytes | file offset `0x01580ce0`, length `0x2c6` (SHA-256 of stored block recorded by `cerom.py`) |
| Section 1 header | `84 04 00 c6 02 00 10 00 00 00 84 04 00 00 b0 02 00 00 84 04 00 00` (22 B) |
| Section 1 payload | 688 B (`0x2b0`), expected uncompressed `0x484` = 1156 |
| Section 2 stored bytes | file offset `0x015aca7c`, length `0x68c` |
| Section 2 payload | 1654 B, expected uncompressed `0xcc0` = 3264 |
| Tools | `tools/cecompress.py` (`decompress_xpress_lz77`, `probe`), `tools/xpress.py` |

## Method

1. Implemented XPRESS plain LZ77 in `tools/cecompress.py` (`_xpress_lz77_decode`,
   `decompress_xpress_lz77`) and a standalone `tools/xpress.py`, ported from the
   klauspost/compress Go reference (32-bit flag groups, MSB-first within the
   group; clear bit = literal; set bit = match with the shared-nibble / raw
   length tiers). Positive control: `cecompress.py --selftest` (390 checks) and
   `xpress.py selftest` (8 checks), including a 32-literal + end-marker round
   trip.
2. Ran `probe` on both payloads with `--methods all --offsets 0-40` and with
   the exact expected size (`0x484` / `0xcc0`).
3. Ran `probe` with `--methods xpress-lz77 --offsets 0-40`.

## Observations

- Positive control passes: the implemented decoder round-trips its own streams
  (32 literals + end marker, matches, shared-nibble and raw-length tiers).
- On section 1 (expected 1156): 0 matches in 115 attempts (23 offsets × 5
  methods); xpress-lz77 raises `corrupt offset` at every offset 0..40; lzss,
  lzx, lznt1 and xpress-huffman also fail (reserved-bit / chunk-length /
  over-subscribed-table errors).
- On section 2 (expected 3264): same outcome, 0 matches in 115 attempts.
- At offset 22 (the M1.2a payload start) the xpress-lz77 first match word
  decodes an offset larger than the output so far (e.g. section 1 `moff 6878 >
  0`), so the stream is not plain LZ77 from that point.

## Interpretation

- The real payload is **not** an XPRESS plain LZ77 stream, nor LZSS/LZX/LZNT1/
  xpress-huffman, at any offset 0..40 or at the documented payload start.
- M1.2a's 22-byte header and per-block records are still valid (187/245 hold),
  but the codec behind them is not among the public MS-XCA variants tried.
- The per-block framing hypothesis (M1.2a form 2 multi-block) and the CE ROM's
  own decompressor (M1.2c, `nk.exe`) remain the next leads.

## Claims

- C-650: XPRESS plain LZ77 implemented and self-tested (positive control:
  32-literal + end marker, matches, shared-nibble and raw-length tiers) in
  `tools/cecompress.py` / `tools/xpress.py`.
- C-651: XPRESS plain LZ77 does not decode either real section at any offset
  0..40 (corrupt offset at the payload start).
- C-652: none of lzss, lzx, lznt1, xpress-lz77, xpress-huffman produces the
  expected length for either real section at offsets 0..40.
- C-653: the M1.2a 22-byte header and per-block record layout are unchanged;
  only the codec behind them is still unknown.
- C-654–C-659: reserved.
