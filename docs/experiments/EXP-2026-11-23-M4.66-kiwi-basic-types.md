## Question

Do the three basic KIWI data types — `SWS` size word, `D` offset word and the 1.2.7 four-byte sector address `ssssssss ssssssss ssssssss DLnnnnnn` — describe the offset/size words already documented for our tile directory, tile `.ind` table, `MMAIN001` level totals and `DRSTR001` tables on EU2011 and US2011?

## Hypothesis

The ZE0 container is not KIWI (M4.63), but its authors reused the word-count idiom: expect `SWS` to fit the two-byte-word size fields inside tiles and the other two types to misfit the u32 byte offsets/sizes. **Falsifier:** a table fits on one card and fails on the other; or a claimed fit consists only of zero/sentinel values; or an informative u32 offset/size decodes correctly as a KIWI type.

## Method

1. **Sample and hash.** Two extracted factory card trees, named above; the four `MMAIN001.DAT`/`DRSTR001.DAT` and six sampled tile SHA-256 values are printed by the census command and listed in the preamble. No file is written into the repository.
2. **Commands.**

   ```bash
   python3 tools/kiwi_types.py --selftest
   python3 tools/kiwi_types.py census /home/marek/projekty/leafre-work/m5.29-factory-root --json - > ~/projekty/leafre-work/scratch/M4.66/eu.json
   python3 tools/kiwi_types.py census /home/marek/projekty/leafre-work/m5.29-factory-root
   python3 tools/kiwi_types.py census /home/marek/projekty/leafre-work/m5.12-us/root-factory --json - > ~/projekty/leafre-work/scratch/M4.66/us.json
   python3 tools/kiwi_types.py census /home/marek/projekty/leafre-work/m5.12-us/root-factory
   ```

3. **Controls.** `kiwi_types.py --selftest` ends `kiwi_types selftest: OK (0 failure(s))`: its positive control decodes three synthetic `SWS` words to 3/3 fits, its negative control shifts one byte and scores 2/3, and its `SA` control on plain byte offsets scores 1/3 with the single fit flagged degenerate. The synthetic checks must pass while the real u32 offset tables fail. The `MMAIN001` oracle is a positive control for the census itself: the 11 stored totals match the summed per-file `0x1ac` counts on both cards (0/11 degenerate after the fix that includes `LEV3456R.DAT`).
4. **Scope.** Three KIWI types only. Every `0x1ac` row of both `MMAIN001` files (11 each); the `0x1ac` tables and all directory heads of the three smallest `B*.DAT` tiles per card (EU 24 dirs / 4,854 zlib streams; US 16 dirs / 4,292 streams); all `.ind` chunk offsets (EU 36,581 across 194 files; US 57,152 across 58 files) and all `.ind` size words; all DRSTR node listings (40 EU, 20 US) and 324/208 directory entries. Excluded: the wide-row sub-record size words, `LEV3456R.DAT` record internals, compressed firmware `.data`, and any firmware VA (rule 13).
5. **Falsifier.** Report `informative` fits (excluding stored 0, `0xffff`, `0xffffffff`, a zero oracle and an SA word index of 0) separately from raw fits; a type is accepted only when the informative fits are all rows on **both** cards. A table that fits one card only is listed, not explained.

## Interpretation

- **FACT:** three tile tables fit `SWS` on both cards with zero degenerate rows: directory header word 0 (24/24 EU, 16/16 US), slot `ln` (4,854/4,854 EU, 4,292/4,292 US) and slot `X` (same counts). The slot fits include section 1 (4,704/4,704 EU, 4,237/4,237 US), section 2 (150/150, 47/47) and US section 4 (8/8). The oracle is a zlib stream's own end, rounded up to the documented 4-byte padding for `ln` and the uncompressed output length for `X`, not the stored word itself.
- **FACT:** all offset/address tables misfit on both cards. The 1.2.7 `SA` decode reproduces 0/300 informative slot tags (EU) and 0/269 (US) — the 41/35 raw fits are all tags with a zero word index. It reproduces 0/35,812 informative `.ind` offsets (EU) and 0/56,196 (US); the 194/58 raw fits are exactly the zero first offset of each file. ZE0's own address formula is `(tag>>8)*2048 + (tag&0xff)*256`: a 16-bit sector and an 8-bit page, not KIWI's 24-bit sector and 6-bit word.
- **FACT:** the remaining size/count tables misfit `SWS`/`D`: `MMAIN001` level totals 0/11 on both cards, tile level counts 0/9 informative EU and 0/8 US (the 17/15 raw fits are zero counts), `.ind` compressed sizes 0/194 and 0/58, DRSTR listing offsets 0/40 and 0/20, DRSTR entry values 0/210 and 0/60.
- **OBSERVED:** the MMAIN oracle itself is self-consistent: all 11 stored totals equal the summed per-file `0x1ac` counts on both cards, so the 0/11 result is a real unit mismatch, not a broken oracle. The `D` sentinel `0xffff` is not present in the DRSTR u32 listing words; the tool reads their low half and notes that in the table.
- **HYPOTHESIS:** the shared word-count idiom is a naming convenience, not evidence of a KIWI container — the u32 offsets, level totals and medium addresses are ZE0-native. This agrees with M4.63/M4.67/M4.68/M4.69/M4.70/M4.72.
- **UNKNOWN:** the 4-byte padding of a compressed slot stream (2 KIWI words) is ZE0-specific; the two DL flag bits of KIWI 1.2.7 have no ZE0 counterpart. No firmware VA is attributed by this record (rule 13).

## Conclusion

M4.66's Done-when is met: `tools/kiwi_types.py` decodes the three types, its `--selftest` passes 10/10, and `census ROOT` prints fits/total for ten documented tables on both cards. The only tables renamed with a KIWI term are the three SWS size words in `docs/format/map-tiles.md` (directory header word 0, slot `ln`/`X`, including the section-4 pair); `docs/format/cmp-ind.md` and `docs/format/drstr.md` are unchanged because none of their tables fits. The falsifier did not fire: every SWS fit is on both cards with non-degenerate values, and every u32 offset/address table fails on both.
