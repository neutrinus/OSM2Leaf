## Question

Run through `runner.py` on the US build, does the firmware's own POINT name
accessor return `HANA HEALTH CENTER` for record 0 of the factory `POINT010`
page `0x840ba0` and `OSM2LEAF TEST POI1` for the page `mutate_refer_poi.py`
wrote, and what does the firmware do with a corrupted record length byte
(`len2`) that the Python parser refuses?

## Hypothesis

Yes for both names: M3.11c ran the accessor pair (`0x0041ec8c` name,
`0x0041e7d8` length, US2011) from its own tool on a page renamed in memory;
the runner port feeds the same context and a pair written to disk decodes to
the same page. For `len2`: the accessor places the name through the record
header word `u16[rec+10]`, so it should still return the name; the walker
steps by `len2` and should land 4 bytes late.

**Falsifier:** a name other than the expected one, a record whose name +
address differ from its display text, a negative control that returns a
pointer, or a PASS with the EU image.

## Method

1. **Sample and hash.** As above.
2. **Commands.**

   ```sh
   IMG=archive/us256.img
   CARD=archive/sd-images/LEAF_2011-2012_US.img
   mkdir -p /tmp/us
   python3 - "$CARD" /tmp/us <<'PY'
   import hashlib, sys
   sys.path.insert(0, "tools")
   import vcard_l3 as V
   card = V.make_card(None, sys.argv[1], {})
   for name in ("POINT010.DAT.cmp", "POINT010.DAT.ind"):
       data = V.Expected(card).read("REFER001/" + name, 0, 1 << 31)
       open(sys.argv[2] + "/" + name, "wb").write(data)
       print(name, len(data), hashlib.sha256(data).hexdigest())
   PY
   RUN="python3 tools/l3_harness/runner.py run poi_record_decode --image $IMG"
   # factory page
   $RUN --cmp /tmp/us/POINT010.DAT.cmp --ind /tmp/us/POINT010.DAT.ind --expect-name "HANA HEALTH CENTER"
   # renamed pair, as it would be on the card
   python3 tools/mutate_refer_poi.py /tmp/us/POINT010.DAT.cmp /tmp/us/POINT010.DAT.ind /tmp/us_mut \
     --page 0x840ba0 --old "HANA HEALTH CENTER" --new "OSM2LEAF TEST POI1"
   $RUN --cmp /tmp/us_mut/POINT010.DAT.cmp --ind /tmp/us_mut/POINT010.DAT.ind --expect-name "OSM2LEAF TEST POI1"
   # negative controls: the other name on each pair; the EU image
   $RUN --cmp /tmp/us/POINT010.DAT.cmp --ind /tmp/us/POINT010.DAT.ind --expect-name "OSM2LEAF TEST POI1"
   $RUN --cmp /tmp/us_mut/POINT010.DAT.cmp --ind /tmp/us_mut/POINT010.DAT.ind --expect-name "HANA HEALTH CENTER"
   python3 tools/l3_harness/runner.py run poi_record_decode --image archive/head256.img \
     --cmp /tmp/us/POINT010.DAT.cmp --ind /tmp/us/POINT010.DAT.ind
   # the len2 control
   $RUN --cmp /tmp/us/POINT010.DAT.cmp --ind /tmp/us/POINT010.DAT.ind --mutate corrupt-len2
   # the corpus row and the selftests
   python3 tools/l3check.py --build-corpus
   python3 tools/l3_harness/runner.py --selftest
   python3 tools/l3check.py --selftest
   python3 tools/point_name_accessor.py --selftest
   ```

   `point_name_v1` decodes the pair, inflates the page, finds the file's
   field dictionary block (`point_name_accessor.find_dictionary`, must be
   unique), swaps page and dictionary to native `u16` (M3.11b: the firmware's
   own swap is `swap16`), lets the firmware's populate writer fill the slot
   table (M3.22), binds the one import the resolver calls
   (`OSMDLL!taskIdSelf` → 1) and calls the name, length and field-6 accessors
   on every record. ACCEPT needs: both slots filled, every record's name +
   address equal to the record's display text, both built-in negative
   controls (no dictionary; a `db` that is not in the slot table) returning
   -1, and record 0's name equal to `--expect-name`.
3. **Controls.** *Positive*: the factory page (1,000 records, every one
   checked against its display text). *Negative (must fail)*: the wrong
   expected name on each pair; the EU image under the US target; on the
   synthetic page a 7-field dictionary in place of the 9-field one (runner
   selftest); the two built-in controls of every run.
4. **Scope.** One build (US2011), one page of one file (`POINT010.DAT`
   `0x840ba0`, 1,000 records) in its factory and renamed form, plus the
   3-record synthetic corpus page. The page is fed decoded: the `.cmp` layer
   is M9.11 and the page loader M4.52. Not covered: the EU build through the
   runner (the accessor tool runs it, M3.11c), pages other than `0x840ba0`,
   the `--card` gate (M9.12), the display path above the accessor.
5. **Falsifier.** As in Hypothesis.

## Interpretation

- **Verified:** through `runner.py`, the US firmware's accessor returns
  `HANA HEALTH CENTER` on the factory page and `OSM2LEAF TEST POI1` on the
  pair `mutate_refer_poi.py` wrote; all 1,000 records of both pages split
  into name and address exactly as their display text. The check can fail
  (wrong name, wrong image, wrong dictionary).
- **Verified:** the stub log is one import, `OSMDLL!taskIdSelf`.
- **Verified (control):** the firmware handles a corrupted `len2`
  differently from the Python parser. `parse_page` refuses the page (no
  `ff ff` at the claimed record end). The name accessor does not use `len2`
  and returns the name; the walker follows `len2` and puts record 1 4 bytes
  late, with no check. A wrong `len2` is therefore not rejected by the unit:
  it shows record 0 correctly and mis-frames what follows. Writer rule: keep
  `parse_page` as the gate for `len2`, the firmware will not catch it.
- **Hypothesis:** the same holds on the unit; the page loader and display
  code above the accessor are not in this run.
- **Unknown:** how the `--card` gate should find the changed page of a POINT
  pair (M9.12).

## Conclusion

The name half of the US POI check is a registered, runnable L3 target. With
`point_walk_us2011` (M9.55) the S2 rename is now checked in software on the
US build for both framing and name, before any card goes to the car.
