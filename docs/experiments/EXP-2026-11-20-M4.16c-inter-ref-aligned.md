## Question

Does the C-1811 lead hold when it is tested properly? C-1811 found that 500 RDSTM `ref` values (the M4.1 16-byte-row `u32` at +4, `0x1000..0x1a700`) occur in `INTER001`–`INTER005` far more often than 500 uniform random `u32`. The proper test asks whether they occur as **aligned fields** of the `INTER` records and **more often than controls with the same byte make-up**.

## Hypothesis

If `INTER` stores RDSTM references, the real values hit (a) aligned 4-byte words, (b) the `u32` at +2 of the blob-0 6-byte elements (`4000 0000 XXXX` node refs, `refer.md`) or (c) the 12-byte table fields more often than controls with the same byte composition. **Falsifier (stated before the run):** the real values fail to beat the byte-profile control (each byte drawn from the pooled byte histogram of the real values) in the byte scan and in every aligned test. If that happens, the C-1811 enrichment comes from the byte composition of the values (many `00` and small bytes), not from shared identities. The decoded M4.16e link refs (`(group << 16) | entry`, the firmware-meaningful form of an RDSTM reference) are tested the same way.

## Method

1. **Sample and hash** as above (`sha256sum`).
2. **Commands** (repo root; `E=/home/user/scratch/factory-eu`; the scan takes about 19 minutes because `INTER005` is large):

   ```bash
   E=/home/user/scratch/factory-eu
   sha256sum $E/RDSTM001/RDSTM001.DAT $E/REFER001/INTER00[1-5].DAT.cmp
   python3 tools/inter_ref_probe.py --selftest
   python3 tools/inter_ref_probe.py scan $E/RDSTM001/RDSTM001.DAT $E/REFER001 --decoded
   ```

3. **Controls**, each with 500 values: *uniform* (the C-1811 control); *zero*
   (each real value keeps its zero bytes in place, and the other bytes are random
   non-zero); *bytes* (every byte drawn from the pooled byte histogram of the
   real values). *Positive (tool):* the selftest builds a blob of small
   big-endian pairs, where small real values hit 100 %, uniform values miss
   and zero-matched values hit like the real ones; so the tool can tell a
   composition effect from an identity.
4. **Scope.** EU 2011, `INTER001`–`INTER005` (the five C-1811 files);
   `FRWAY` and `INTER006`–`033` are not scanned. Tests: any LE/BE byte
   occurrence; aligned `u32` (both byte orders, every 4-byte offset); blob-0
   element `u32` at +2; table `(key, 0)`, `(length, b8)`, `key`, `length`.
5. **Falsifier** as stated under Hypothesis.

## Interpretation

- **VERIFIED (C-2310):** the C-1811 effect reproduces against uniform
  random values (257 vs 10 over five files), but the byte-profile control hits
  more often than the real values in every file and in every test (byte 477
  vs 257, aligned 135 vs 55, elem+2 30 vs 7, table 15 vs 3). The enrichment
  comes from the byte composition of the M4.1 "ref" values (zero-rich, small
  bytes), not from shared identities: C-1811 is refuted as a join lead.
- **VERIFIED (C-2311):** the decoded M4.16e link refs, the real form of an
  RDSTM reference, also stay below their byte-profile control (byte 35 vs
  149, aligned 10 vs 30, elem+2 4 vs 9, table 0 vs 0), so `INTER001`–`005` do
  not carry RDSTM link references in any tested field.
- **OBSERVED (C-2312):** the zero-matched control explains only part of the
  real byte-scan count (54 of 257); the rest follows the byte histogram (the
  `bytes` control). Uniform random `u32` is therefore not a valid control for
  byte-pattern searches in these files.
- **OBSERVED (C-2313):** no `INTER` → tile/mesh → coordinate hop was tested,
  because no RDSTM key reaches `INTER` and M4.16 placement no longer needs
  one (C-5950).
- **UNKNOWN (C-2314):** what the blob-0 node refs and the FRWAY 4-byte "mesh
  ids" encode. The two FRWAY values `refer.md` quotes (`9fbeda1e`,
  `a06fdbcf`) end in nibbles `e`/`f`, not the level-2/level-4 parcel-key
  nibbles `2`/`4` that `rdstm_links.parcel_origin` accepts, so they are not
  section-2 parcel keys in that form (2 values, not a census).

## Conclusion

M4.16c closes negative: the `INTER`/`FRWAY` `ref` lead (C-1811) is a
byte-composition artifact, tested as aligned fields with byte-matched
controls. Neither the M4.1 values nor the decoded M4.16e link refs reach
`INTER` above those controls. RDSTM placement goes through
the M4.16b/M4.16e link groups (C-5950); the `INTER`/`FRWAY` content remains
an M3.16 reader question.
