## Question

Can one synthetic POI with a name and a lat/lon be *added* (not moved) to a
copy of the EU 2011 `POINT010` pair, so that the firmware's own record walker
and nearest-POI reader accept it while the census still reaches every byte?

## Hypothesis

Yes: the name chain can be relocated through its verified locator (M4.47), a
leaf fits in the zero gap after a cell node's terminator, and one 24-byte index
key fits in the 76 B slack of the last index stream. Falsifier: any of those
three allocations needs a file-size/layout change the readers reject, or a
firmware walk returns the neighbouring record instead of the new one.

## Method

1. **Sample and hash.** The two files and the firmware head above; all counts
   below come from the commands in (2) run on those exact bytes.

2. **Commands.** Runnable from the repo root with `S` a scratch directory and
   `Z` the stock zlib library (both defined in the reproduction block).
   ```bash
   mkdir -p "$S/factory" "$S/out" "$S/noop" "$S/neg-leaf" "$S/neg-index"
   cp /home/marek/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.cmp "$S/factory/"
   cp /home/marek/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.ind "$S/factory/"
   sha256sum "$S/factory/POINT010.DAT.cmp" "$S/factory/POINT010.DAT.ind"

   python3 tools/point_add_poi.py --selftest
   python3 tools/point_census.py census "$S/factory" --files POINT010
   python3 tools/point_census.py joins  "$S/factory" --files POINT010
   python3 tools/cmpind.py verify "$S/factory"

   python3 tools/point_add_poi.py "$S/factory/POINT010.DAT.cmp" "$S/noop" \
       --noop --ind "$S/factory/POINT010.DAT.ind" --libz "$Z" --json "$S/noop.json"
   sha256sum "$S/factory/POINT010.DAT.cmp" "$S/noop/POINT010.DAT.cmp" \
             "$S/factory/POINT010.DAT.ind" "$S/noop/POINT010.DAT.ind"

   python3 tools/point_add_poi.py "$S/factory/POINT010.DAT.cmp" "$S/out" \
       --name "OSM2LEAF NEW POI" --libz "$Z" --json "$S/add.json"
   python3 tools/point_census.py census "$S/out" --files POINT010
   python3 tools/point_census.py joins  "$S/out" --files POINT010
   python3 tools/cmpind.py verify "$S/out"
   python3 tools/point_walk_l3.py walk archive/head256.img \
       --cmp "$S/out/POINT010.DAT.cmp" --ind "$S/out/POINT010.DAT.ind" \
       --page 10476456 --n 0,468,469 --build eu2011
   python3 tools/point_tree_l3.py run archive/head256.img \
       --dir "$S/out" --file POINT010 --tree 0 --cells 300

   python3 tools/point_add_poi.py "$S/factory/POINT010.DAT.cmp" "$S/neg-leaf" \
       --name "OSM2LEAF NEW POI" --libz "$Z" --control break-leaf
   python3 tools/point_census.py joins "$S/neg-leaf" --files POINT010
   python3 tools/point_add_poi.py "$S/factory/POINT010.DAT.cmp" "$S/neg-index" \
       --name "OSM2LEAF NEW POI" --libz "$Z" --control break-index
   python3 tools/point_census.py joins "$S/neg-index" --files POINT010
   python3 tools/point_add_poi.py "$S/factory/POINT010.DAT.cmp" "$S/neg-zlib" --name X
   python3 tools/point_add_poi.py "$S/factory/POINT010.DAT.cmp" "$S/neg-zlib2" \
       --name X --allow-nonreference
   python3 tools/point_walk_l3.py walk archive/head256.img \
       --cmp "$S/out/POINT010.DAT.cmp" --ind "$S/out/POINT010.DAT.ind" \
       --page 0x73d4a8 --n 469 --build eu2011
   ```

3. **Controls.** *Positive:* the unchanged factory pair passes both censuses
   and `cmpind verify`; the no-op rewrite is byte-identical; the new record is
   read back through `mutate_refer_poi.name_field` before the pair is written;
   `point_walk_l3` returns the same offset as `parse_page` for records 0, 468
   and the new 469; `point_tree_l3` ACCEPT on the tree containing the new leaf.
   *Negative:* flipping one bit of the new leaf's fine word drops
   `leaf_match` to 15,378/15,379 and `VERDICT: FAIL`; corrupting key word 0 of
   the appended index entry drops `index_match` to 35,526/35,527 and FAIL;
   omitting `--libz` exits 3 before reading the pair; `--allow-nonreference`
   is refused because zlib-ng reproduces only 15,984 of 16 factory pages;
   walking the old, zeroed page offset raises `unknown compression method`.

4. **Scope.** EU 2011 `POINT010` only: 9,864,704 B decoded factory blob, 16
   name pages / 15,469 records, 53 spatial trees / 19,499 nodes / 15,378 leaves,
   107 tries / 35,526 index records, one new record. Excluded: the other 43
   POINT shards, US 2011, the 400/2000 chains (unchanged), the spelling-search
   trie (no new trie leaf), the phone B-tree, `REFER002`, and any L4/L5 result.
   Rule 13: the record walker and the nearest-POI tree reader are firmware code
   run in L3; the unit display is not tested.

5. **Falsifier.** `census` reporting `unaccounted > 0`, `joins` FAIL, a
   firmware walk at the new page returning a different offset, `point_tree_l3`
   REJECT, a non-byte-identical no-op, or a changed byte outside the named
   structures would each refute the claim. The tool stops before writing on
   all of those.

## Interpretation

- **FACT:** one name record, one spatial leaf and one index key can be added
  to the EU 2011 POINT010 pair with `unaccounted=0`, `joins hold`, `cmpind
  verify` PASS, 0 changed bytes outside the named structures, and a no-op that
  is byte-identical. The firmware record walker returns the new record
  (`n=469`, L3 PASS) and the nearest-POI reader accepts the tree (L3 ACCEPT).
- **OBSERVED:** the three allocations used 16 B of a 230 B inter-node gap,
  8 B of 76 B index-chain slack, and a chain relocation from `0x6a7f00` to
  `0x968600`. The new position is 15,470th record in the same copy-A cell as
  its host, ~36 m from it. A `0x68` template is required: a `0x60` record
  needs a 400-chain INFORMATION record, which is not written.
- **HYPOTHESIS:** the appended index key makes the new name findable by the
  spelling search, because `joins` proves its key bytes occur in the new
  record and the key is in the trie's index chain; no trie leaf was added and
  no L3 spelling-search run was performed.
- **UNKNOWN:** whether the unit displays the new POI in a routable context
  (L4/L5); how the per-node trailing 4 terminator bytes (`1a 80`) are derived;
  whether the 6,399 name records without leaves can be used as free slots.

## Corrections after navigator review

1. The first plan put the new entry in the cell node. `walk_spatial` marks a
   leaf above `CELL_DEPTH` as `shallow_leaf`, so the entry goes in the host's
   depth-3/4 *leaf* node and the parent's `csize` (entry `+6`, not `+4`) grows.
2. `chain_words` is at `0x1016` (ref `0x1002` + 20), not `0x1012`; the index
   chain has 76 B of slack, not room for arbitrary growth. The tool stops if
   the grown stream exceeds it.
3. `apply_names` cannot append a record, so the last page is built explicitly
   and passed through `pack_chain` + `write_pair_grown`.
4. `point_walk_l3 --n` is page-local; the verification uses `--n 469` at the
   relocated page, not global 15,469 at the old base.
5. The changed-byte envelope was extended to cover the spatial node, the index
   chain and the relocated chain + padding, with `outside=0` required.
6. A `0x60` template broke `records_400 == tag60`; the host selector now
   requires a `0x68` template.
7. "M4.47 verified reader-side" was narrowed to codec/locator verification;
   this record supplies the first L3 name-walk on a relocated pair.
