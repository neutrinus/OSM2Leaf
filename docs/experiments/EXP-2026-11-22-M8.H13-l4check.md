## Question

Can a boot of the EU 2011 card under `-M ze0` be reduced to one command whose
exit code and JSON name the reached stage, the launcher verdict, the map-file
outcome and the time to idle — and does that command separate a factory card
from a card with a broken map file?

## Hypothesis

Yes: the kernel debug (DBGMSG) serial log contains ordered milestones that
separate the stages, and the broken map file adds a `Navi.exe` error-log line
that the factory card never prints. **Falsifier (from the task):** the broken
card and the factory card give the same verdict. A second falsifier: no log
line separates "card accepted" from "card rejected" — then report the two logs
side by side and stop.

## Plan (written before `tools/l4check.py`)

**Approach.** A new stdlib-only `tools/l4check.py`:

1. resolve card, head and QEMU binary; absence of any of the three is
   `NOT RUNNABLE`, exit **3**, never a pass;
2. read `VER_INFO/HDD_INFO.TXT` out of the card's FAT partition with
   `tools/mkcard.py` (`open_map_partition`/`img_read`) and derive the two unit
   values from it: `verinf` = stripped line 1 (11 bytes), `mapdb` =
   `extract_mapdbver` of line 3 positions 5/6/7, passed as `LO-LO`;
3. build the IPL patch with `tools/ze0_ipl.py patch --prefer-app
   auiapp.exe,auirtdll.dll --copy-dlls unitflash` plus `tools/ze0_aui.py
   --no-aui-timeout` (the C1k/C1i recipe), and a qcow2 overlay with
   `tools/qemu-ze0/mkoverlay.py` (the SD model needs a power-of-two size);
4. launch QEMU directly with the `run.sh` machine options
   (`kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=…,mapdb=…,
   ipl-patch=…`, `-icount shift=0,sleep=off`, `-serial file:…`, `-monitor
   unix:…`) but **without** `-d`: a 300 s run with `-d unimp,guest_errors,int`
   wrote a 7.0 GB `qemu.log`, while the DBGMSG serial log was 489 KB, and every
   exception in that log is a routine `tlb_miss`; the serial log is the signal;
5. poll `serial.log` while QEMU runs: record the wall-clock second in which
   `AppLch >> Finish Launch Threads!` first appears (time to idle), stop early
   on idle or on any decisive reject line, otherwise at `--timeout` (default
   900 s — this host runs ~15 agents and a 300 s window was too short), then
   parse the whole log into stage rows;
6. print one line per stage, the launcher verdict, the map-file verdict, the
   derived values, the time to idle and the log path; `--json` writes the same
   document; exit 0 when the card-verdict stages F0..F4 pass, 1 when a stage
   fails (the failed stage and its log line are named), 3 not runnable.
   F5 (idle) is **informational**: a loaded host may not reach it inside the
   window (status `NOT RUN`), which does not reject the card.
   `--selftest` parses canned logs (positive, negative, reject, no-idle and
   empty cases) and needs no card, head or QEMU.

## Method

1. **Sample and hash.** The two SHA-256 values in the header, printed by
   `sha256sum archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   archive/head256.img`. No vendor bytes enter the repo.
2. **Commands.** Positive control (factory card), run by hand before code:

   ```bash
   cd /home/marek/projekty/OSM2Leaf.task-m8.h13-l4check
   S=~/projekty/leafre-work/scratch/m8.h13
   python3 tools/ze0_ipl.py patch archive/head256.img --prefer-app auiapp.exe,auirtdll.dll \
       --copy-dlls unitflash -o "$S/ipl_k.txt"
   python3 tools/ze0_aui.py archive/head256.img --no-aui-timeout -o "$S/ipl_aui.txt"
   cat "$S/ipl_k.txt" "$S/ipl_aui.txt" > "$S/ipl_final.txt"
   python3 tools/qemu-ze0/mkoverlay.py archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img "$S/factory.qcow2"
   bash tools/qemu-ze0/run.sh --qemu ~/.cache/qemu-ze0/build/qemu-system-sh4 --machine ze0 \
       --image archive/head256.img --sd "$S/factory.qcow2" --ipl-patch "$S/ipl_final.txt" \
       --verinf QSD-302-100 --mapdb 16-16 --dbgmsg 0x880404f4 \
       --icount shift=0,sleep=off --timeout 300 --workdir "$S/factory"
   python3 tools/ze0_sdhost.py serial "$S/factory/serial.log"
   ```

   Negative control (same card, one variable):

   ```bash
   printf 'MMAIN001.DAT truncated for L4 negative control\n' > "$S/mmain-short.bin"
   python3 tools/imgpatch.py --image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
       --file MMAIN001.DAT --from "$S/mmain-short.bin" --allow-resize -o "$S/bad-mmain.img"
   python3 tools/qemu-ze0/mkoverlay.py "$S/bad-mmain.img" "$S/bad.qcow2"
   timeout 300 ~/.cache/qemu-ze0/build/qemu-system-sh4 \
       -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,verinf=QSD-302-100,mapdb=16-16,ipl-patch="$S/ipl_final.txt" \
       -kernel archive/head256.img -nographic -serial file:"$S/bad/serial.log" \
       -monitor unix:"$S/bad/hmp.sock",server,nowait -icount shift=0,sleep=off \
       -drive if=sd,index=0,file="$S/bad.qcow2",format=qcow2
   python3 tools/ze0_sdhost.py serial "$S/bad/serial.log"
   grep -a 'ErrorLogMsg() Called. \[ERR_PRC_NAVI\],\[0x28\]' "$S/bad/serial.log" | sort | uniq -c
   ```

   Card-side derivation (inspects the same fields the tool will read):

   ```bash
   python3 -c 'import sys; sys.path.insert(0,"tools"); import mkcard,hddinfo; CARD="archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img"; fh=open(CARD,"rb"); p,g,f=mkcard.open_map_partition(fh); h=mkcard.img_read(fh,g,f,"VER_INFO/HDD_INFO.TXT"); print(repr(h)); r=hddinfo.parse(h); print(hddinfo.extract_mapdbver(r)["value"])'
   ```
3. **Controls.** *Positive:* the factory card must reach `Finish Launch
   Threads!` with 0 `0x28` Navi error-log lines. *Negative:* truncating one map
   file must add `0x28` lines and remove the idle marker. Both were run above.
   The 8 `Launch Process Not Create!!!` lines on **both** cards are a control
   that this string is *not* the discriminator.
4. **Scope.** One build (EU2011), one card family, two card states (factory,
   truncated `MMAIN001.DAT`), two 300 s boots, one IPL patch (C1k+C1i recipe).
   Excluded: US/2014/2016 builds, L5 hardware, `-d unimp` traces (7.0 GB per
   run, all exceptions `tlb_miss`), the wrong-volume-label card (C-798 says
   the firmware does not check the label; the truncated map file is the
   measured negative control), and full display-list rendering (M8.C1f).
5. **Falsifier.** Identical verdicts for the factory and broken card, or no
   log line separating them. Both are tested by the two commands above.

## Observations

Raw results only; each number is quoted from the command that printed it.

**O1 — factory boot.** `python3 tools/ze0_sdhost.py serial
"$S/factory/serial.log"` printed `lines 9733`, `activate_ok 1`,
`security_unlocked 2`, `store_ready 1`, `part_mounted 2`, `applch_error 0`,
`failsafe_start 0`, `launch_not_create 8`, `verinf_mismatch 0`,
`mapdb_out_of_range 0`. `grep -a -n "Finish Launch Threads"
"$S/factory/serial.log"` printed `8392:AppLch >> Finish Launch Threads!`.
`grep -a 'ErrorLogMsg() Called. \[ERR_PRC_NAVI\],\[0x28\]' … | sort | uniq -c`
printed nothing (0 lines). `ls -lh "$S/factory/qemu.log"` printed `7,0G`;
`ce_qemu_probe.summarize_log` of a 1 s control boot printed
`exceptions: 39782` at `pc=0xfffffcad…`, i.e. the `-d int` count is dominated
by routine TLB misses.

**O2 — broken-card boot.** `python3 tools/ze0_sdhost.py serial
"$S/bad/serial.log"` printed `lines 7287`, with the same `activate_ok 1`,
`store_ready 1`, `part_mounted 2`, `applch_error 0`, `launch_not_create 8`,
`failsafe_start 0`, `verinf_mismatch 0`, `mapdb_out_of_range 0` as O1, **no**
`Finish Launch Threads!`, and the same 8 `Launch Process Not Create!!!`.
The `0x28` class count printed by `grep … | sort | uniq -c` was
`35 …[0x00000105]` + `33 …[0x00000101]` = **68**; the same command on the
factory log printed 0. First occurrence: `grep -a -n "\[0x28\]"
"$S/bad/serial.log"` → `1210:ErrorLogMsg() Called. [ERR_PRC_NAVI],[0x28],
[0x0B],[ERR_LVL_B],[0x00000105]`.
`python3 tools/imgpatch.py …` printed `4096 -> 47 B, clusters 1 -> 1` and
`verify: cardcheck.Fat32Image 47 B sha256 3e50bf869f5218ce… OK`.

**O3 — derived unit values.** The card-derivation command printed
`b'QSD-302-100\r\nQSD-309-101\r\n02-110100-00\r\n…'` and `16` (line 3 positions
5/6/7 = `0`,`1`,`0` → `((0*16)+1)*16+0`). These equal the `verinf=QSD-302-100,
mapdb=16-16` of EXP-2026-11-22-M8.C1c O5 that made the launcher pass.
`python3 tools/l4check.py` on the same card printed
`verinf=QSD-302-100 mapdb=16-16 (MapDBVer line 3 positions ['0', '1', '0']),
MMAIN001.DAT 4096 B` and `sha256 105e2032…76307`.

**O4 — host load and the idle milestone.** An early gate run with a 300 s
window reached F0..F4 (`Process Create!!! -> \windows\Navi.exe` at serial line
454) but not `Finish Launch Threads!`; its last audio retry was `count
up![100]` where the hand run of O1 was at `count up![199]` when idle appeared.
`uptime` during the gate run printed `load average: 14,66, 13,88, 9,82` from
parallel agents. This is a host-speed effect, not a card verdict, so F5 idle
was made informational and the window 900 s with early stop on decisive lines.

## Interpretation

- **OBSERVED:** the two cards reach the same SD/launcher milestones (O1, O2)
  and differ in exactly two measured ways: the broken card emits 68 Navi
  `ERR_PRC_NAVI [0x28]` lines and never reaches `Finish Launch Threads!`.
- **FACT:** a one-command gate can separate them on the serial log alone; the
  `0x28` line is a loud, countable, stage-naming discriminator. Its trigger in
  this experiment is the `MMAIN001.DAT` truncation; its precise firmware
  semantics (which field of the map file it reports) is not established here.
- **HYPOTHESIS:** `0x105`/`0x101` are the Navi map-data error codes; confirming
  the enum is a follow-up, not a precondition for the gate.
- **UNKNOWN:** whether a wrong volume label alone changes the verdict — not
  measured; C-798 suggests it does not.
