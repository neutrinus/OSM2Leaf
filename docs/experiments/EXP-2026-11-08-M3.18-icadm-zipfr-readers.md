## Question

Which function(s) in `Navi.exe` (build A) read `ICADM0nn` and `ZIPFR001` record
fields, and which fields does each consume (ICADM: 462-byte blocks, 7×64-byte
slots, `u16` tag `0x00e7`, big-endian ISO-3166 numeric, `char[60]` terms, C-136;
ZIPFR: 14-byte records `char key[10] + u32 LE mask`, C-137)? If field-level
reading cannot be shown, can the firmware be shown to copy the block without
parsing fields (positive control required)?

## Hypothesis

Exploratory (re-run r2). Falsifier for "reader found": a reproducible function
VA in decodable build-A executable code whose disassembly loads/compares the
format's defining field constants (ICADM stride/tag/slot; ZIPFR 14-byte stride +
mask/key access) against a buffer obtained via the REFER001/ICADM/ZIPFR access
path. Falsifier for "not found in tested scope": neither of two structural
signature families (derived from the writer's inverse / format structure, not
the byte grammar text) produces a plausible ICADM/ZIPFR field-consuming site in
the 22,806,528 B of build-A uncompressed executable sections.

         if (hw&0xF000)==0x9000:

             hits.append((mod['name'],hex(tva+o),hex(ea),'l',hex(struct.unpack_from('<I',blob,eo)[0])))
   print('scanned',total,'hits',len(hits)); [print(h) for h in hits]

## Observations

### 1. Precheck (Navi.exe, IMG256 `92aa525d…`, build A `0x200200`)

`reader_precheck.py`: executable decodable **5,553,430 B** (sec0 only);
executable compressed **0 B**; data compressed **16,778,254 B** (sec1+sec2, 75.1%
of vsize). Compressed sections are data (`0xc8002040`, `0x48002040`), consistent
with C-2128 (0 compressed executable sections in build A). Indirect calls through
a slot in compressed sec1: 3560 (lower bound) — a reader reached only via a
pointer stored in sec1 is out of static decodable scope.

### 2. ICADM/ZIPFR strings and access-path anchors (Navi.exe sec0, correct mapping)

| VA | Content (sec0, correct `va2file(dataptr)` mapping) | xref / role |
| --- | --- | --- |
| `0x00178c60` | `ICADM0\0\0REFER001...` | pool `0x003f16f4` → load `0x003f16b6` (r5) in `fn 0x003f1640`; pool `0x00178c10` holds it (data) |
| `0x00178c68` | `REFER001` | pool `0x003f1704` → load `0x003f16d8` (r4) in `fn 0x003f1640`; matches C-2122/C-880 `0x14e8`→`REFER001` |
| `0x00178e08` | `ZIPFR001.DAT\0...` | **no literal-pool xref in executable sections** (`sh4xref --to 0x00178e08`) |
| `0x00178c88` | `ICODE001.DAT\0...` | context: near ICADM/REFER001 strings; ICODE001 opener is `fn 0x003f2cc0` (C-2194) |

`fn 0x003f1640` (disassembled): takes `r4` (zero-extended, +1), formats a 2-digit
decimal index (divide-by-10 via `0x66666667` magic, `dmuls.l`/shifts) into a
stack buffer, then calls string routines (`0x003d1514`, `0x003d13b8` ×2) to build
`ICADM0`+digits (+ suffix via `0x00178c58`) and resolves the name in `REFER001`
(`r4=0x00178c68`, `r5=built name`) via volume lookup `jsr 0x0040b358` at
`0x003f16dc` (returns to `0x003f16e6`). `sh4xref --to 0x003f1640` shows pool
`0x003f2df0` holds `0x003f1640` with load `0x003f2d9e` (r3) in `fn 0x003f2cc0`
(`jsr 0x003f2da0` context). **This is an ICADM name-builder/opener (resolver path),
not a record-field reader.**

Task anchors present in decodable code per prior claims: `0x003fbed8` (C-2120),
`0x0040b358` (C-2121), `0x004125a8` (C-2122/C-880, `0x14e8`→`REFER001`+`INDEX003`).

### 3. Family 1 — ICADM stride/tag constants (0x01CE/0x00E7), build-A uncompressed exec

Correct-mapping scan (`va2file(dataptr)`): **22,806,528 B scanned, 24 hits** of
`mov.w @(disp,pc)`/`mov.l` loading `0x01CE`/`0x00E7`; **0 hits in `Navi.exe`**.
Hits by module: `mspart.dll` (3, load `0x01CE`), `auirtdll.dll` (1), `IconDrawCC.dll`
(1), `ScreenStateCC.dll` (16, mixed `0x01CE`/tag-like loads — UI module, not
REFER001 map data), `TelemaFvtRegCC.dll` (1), `TelemaImageDrawCC.dll` (1),
`PhoneBTA.exe` (1 in an earlier count position) — none attributable to ICADM/REFER001
record parsing in the navigation/map path. No `0x00E7` slot-tag comparison chain
identified as ICADM. **Result: negative for tested signature in decodable exec.**

Positive control: the scan finds `0x01CE` pool loads (mechanism works) and Navi.exe
is known to use `mov.w` pool constants for record masks (C-2540 `0x03FF`/`0xFC00`).

### 4. Family 2 — ZIPFR 14-byte stride, Navi.exe sec0

`add #14,rn` (`7n0E`) sites in Navi.exe sec0 (correct mapping): **79**. The raw
stride count is present (positive control for stride-form existence) but a 14-byte
advance alone is not specific to ZIPFR (`char[10]+u32 mask`); no site was
confirmed to pair the +14 cursor with a 10-byte key compare and a `u32` mask read
at record offset +10 against a buffer sourced from `ZIPFR001`/REFER001. ZIPFR001.DAT
has **no executable-section literal-pool xref** (obs. 2), and Navi.exe sec1 (where
a filename table/pointer could live) is compressed data — so a decodable static
anchor into a ZIPFR-specific read loop was not established. **Result: no confirmed
ZIPFR field-consuming reader in tested decodable scope (negative / inconclusive
for specificity).**

### 5. Mapping pitfall (recorded)

An initial ad-hoc scan used `va2file(sec['realaddr'])` / wrong offset arithmetic
and produced false `0x01CE` hits (e.g. VA `0x11ca6c` read as `0x9355` loading
`0x01CE`, while correct `va2file(dataptr)` mapping shows `0xc137` `.word` at
`0x11ca6c`, matching `sh4dis`). All scan results above use the correct
`va2file(dataptr)` / `va-realaddr` mapping (same as `sh4dis.load_segments`).

## Interpretation

- **FACT:** Navi.exe sec0 (uncompressed exec, build A IMG256 `92aa525d…`) contains
  `ICADM0` at `0x00178c60`, `REFER001` at `0x00178c68`, and `ZIPFR001.DAT` at
  `0x00178e08` (correct section mapping). `fn 0x003f1640` loads `0x178c60`, builds
  an `ICADM0`+2-digit name, resolves it in `REFER001` (`0x178c68`) via
  `jsr 0x0040b358` (`0x003f16dc`), and is referenced from `fn 0x003f2cc0` (ICODE
  opener context, C-2194) — **ICADM opener/name-builder path located**.
  `ZIPFR001.DAT` (`0x178e08`) has no literal-pool xref in executable sections.
- **OBSERVED:** Family 1 (0x01CE/0x00E7 pool-constant stride/tag) over 22.8 MB of
  build-A uncompressed exec finds 0 Navi.exe hits and no ICADM-attributable hit.
  Family 2 finds 79 `add #14` in Navi.exe sec0 but no confirmed ZIPFR key/mask
  record-consumer tied to `ZIPFR001`. Navi.exe has 0 compressed executable
  sections but 16.8 MB compressed `.data` (sec1) with 3560 indirect slot calls —
  a field reader reached only via a sec1-resident pointer/table remains out of
  static decodable scope.
- **HYPOTHESIS:** ICADM/ZIPFR data may be consumed by code reached indirectly
  through compressed sec1 pointers, or accessed via a generic buffer/read path
  that does not expose the defining field constants as tested (e.g. byte-wise
  copy, table-driven offsets in `.data`, or different arithmetic than 462/14
  immediates). "Firmware copies block, reads no field" is **not established**
  (no positive control demonstrating a copy-only path for these files).
- **UNKNOWN:** Field-consuming reader VAs and the specific ICADM/ZIPFR fields
  consumed by firmware; ZIPFR open/resolve path (no exec xref to `0x178e08`).

## Conclusion

M3.18 (r2) **partially** satisfies its goal: it names decodable access-path/
opener evidence (ICADM string `0x178c60`, REFER001 `0x178c68`, ZIPFR001.DAT
`0x178e08`; `fn 0x003f1640` ICADM name-builder+`0x0040b358` resolver) and records
two structural signature families tested with negative/inconclusive results in
build-A uncompressed executable scope. It **does not** meet the full done-when
("names the reader VAs and the fields each consumes, or shows copy-without-field
with a positive control") because no field-consuming reader VA is located and no
copy-only positive control is demonstrated. Per M3.18 Stop/rule 14: **blocked**
after two signature families; unblock requires a method that can (a) resolve
sec1 indirect targets/pointer tables (follow-on to sec1 decompression/data
recovery context, noting C-2128: exec is readable but sec1 is compressed
*data*) or (b) an L3/runtime trace of ICADM/ZIPFR access from the opener path.
