# EXP-2026-11-22-M9.69: One trace record for L3 reader calls (`mmain_l3`, `drstr_l3`)

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** firmware head `archive/head256.img`, SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; EU card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` (SHA-256 prefix `105e2032e480e8ba`, as in C-5970); `DRSTR001.DAT` `2b7f2fb8901bf18a2ad48334154a6d604c23a775083cb84754626d64417b25f6` (11,968 B, `m422/eu2011`)
- **Tools:** `python3` 3.15.0 (standard library only); repo tools `tools/reader_trace.py` (new), `tools/mmain_l3.py`, `tools/drstr_l3.py`, `tools/l3check.py`, `tools/selftest.py`, `tools/claims_check.py`, `tools/todo_check.py`
- **Claims:** C-8010–C-8013
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the two existing L3 reader tools (`mmain_l3`, `drstr_l3`) write one shared
JSON record (build, function, arguments, reads, result) that a validator
accepts, without changing any verdict they already print or `l3check`'s
verdicts?

## Hypothesis

A schema with the five named fields plus an optional derived-check object can
express both tools' outcomes: `mmain_l3` reads one `MMAIN001.DAT` per case and
then compares a firmware buffer, while `drstr_l3` returns one parser verdict
with `r0`/`stage`/log codes. Both can be adapted by a small `--trace-out PATH`
written after the tool already printed and computed its exit code, so the
verdict logic is untouched.

**Falsifier:** a field needed to compare two runs of the same reader is missing
from the schema for one of the two tools. Concretely: two accepted
`MMAIN001.DAT` files of equal size (factory vs edited) read the same bytes and
hold the same verdict, yet leave different firmware buffers — if the record
cannot tell those runs apart, the schema is insufficient.

## Method

1. **Sample and hash.** `archive/head256.img` (EU2011 build A), the EU 2011
   card, and the EU factory `DRSTR001.DAT` above. No vendor byte is written to
   the repo; traces hold file names, offsets, hashes and verdicts only.

2. **Commands.** Runnable as written from the repo root (`S` is a scratch dir):

   ```bash
   S=/home/marek/projekty/leafre-work/scratch/m9.69
   mkdir -p "$S"

   # Precheck: the L3 ladder and the producer count
   python3 tools/l3check.py --help >/dev/null && echo "l3help OK"
   ls tools/*_l3.py | wc -l

   # BEFORE
   python3 tools/mmain_l3.py --selftest
   python3 tools/drstr_l3.py --selftest
   python3 tools/l3check.py --build-corpus > "$S/l3-before.txt" 2>&1; echo "l3rc=$?"
   python3 tools/mmain_l3.py run archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --json "$S/mmain-before.json" > "$S/mmain-before.txt" 2>&1; echo "mmain rc=$?"
   python3 tools/drstr_l3.py controls archive/head256.img \
     --file m422/eu2011/DRSTR001.DAT --json "$S/drstr-controls-before.json" \
     > "$S/drstr-controls-before.txt" 2>&1; echo "controls rc=$?"

   # Schema and its selftest
   python3 tools/reader_trace.py --selftest

   # AFTER: the same runs with --trace-out
   python3 tools/mmain_l3.py run archive/head256.img \
     --card-image archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img \
     --json "$S/mmain-after.json" --trace-out "$S/mmain.trace.json" \
     > "$S/mmain-after.txt" 2>&1; echo "mmain rc=$?"
   python3 tools/drstr_l3.py run archive/head256.img \
     --file m422/eu2011/DRSTR001.DAT --json "$S/drstr-run-after.json" \
     --trace-out "$S/drstr-run.trace.json" > "$S/drstr-run-after.txt" 2>&1; echo "drstr run rc=$?"
   python3 tools/drstr_l3.py controls archive/head256.img \
     --file m422/eu2011/DRSTR001.DAT --json "$S/drstr-controls-after.json" \
     --trace-out "$S/drstr-controls.trace.json" > "$S/drstr-controls-after.txt" 2>&1; echo "controls rc=$?"
   python3 tools/l3check.py --build-corpus > "$S/l3-after.txt" 2>&1; echo "l3rc=$?"

   # Done-when: the validator accepts every trace
   python3 tools/reader_trace.py validate \
     "$S/mmain.trace.json" "$S/drstr-run.trace.json" "$S/drstr-controls.trace.json"

   # Unchanged output: same stdout and same --json document (sorted keys)
   diff "$S/mmain-before.txt" "$S/mmain-after.txt"
   diff <(python3 -c "import json;print(json.dumps(json.load(open('$S/drstr-controls-before.json')),sort_keys=True))") \
        <(python3 -c "import json;print(json.dumps(json.load(open('$S/drstr-controls-after.json')),sort_keys=True))")
   diff <(grep -v "corpus   /tmp" "$S/l3-before.txt") <(grep -v "corpus   /tmp" "$S/l3-after.txt")

   # Falsifier: two accepted cases that read the same bytes differ in the record
   python3 -c "
   import json, sys; sys.path.insert(0, 'tools'); import reader_trace as R
   by = {r['arguments']['case']: r for r in json.load(open('$S/mmain.trace.json'))}
   print('factory/edited differ:', R.compare_records(by['factory'], by['edited']))
   print('factory/factory differ:', R.compare_records(by['factory'], by['factory']))
   print('buffer hash equal:', by['factory']['result']['checks']['buffer_sha256']
         == by['edited']['result']['checks']['buffer_sha256'])
   "
   ```

3. **Controls.**
   - *Positive*: both producers' own `--selftest` pass before and after
     (`mmain_l3` 11 checks, `drstr_l3` 14 checks), and `reader_trace --selftest`
     passes 54 checks over the schema, both adapters and `compare`.
   - *Negative*: `validate` exits 1 on a record with a bad `function`, an empty
     array, and invalid JSON (selftest cases); `compare` reports `DIFFERENT` on
     a changed read, verdict, or argument, and on a record-count mismatch.
   - *Falsifier control*: `factory` vs `factory` compares SAME; `factory` vs
     `edited` are both ACCEPT and read the same bytes, yet `compare_records`
     names `arguments` and `result` and their `buffer_sha256` differ.

4. **Scope.** Two producers only (`mmain_l3`, `drstr_l3`); the other 19
   `tools/*_l3.py` are not adapted here (the task names two). EU2011 build A
   only. The record does not run firmware and claims no new verdict; `l3check`
   and both tools' `--json`/stdout are byte-compared before vs after.

5. **Falsifier.** If two runs that a reader must be able to distinguish (same
   verdict, same reads, different content) compare SAME, the schema is missing
   a field. That is exactly the `factory`/`edited` case below.

## Interpretation

- **FACT:** Both adapted tools write records that `python3
  tools/reader_trace.py validate` accepts (6 + 1 + 9 records), and their
  stdout/`--json` and `l3check --build-corpus` output are unchanged before vs
  after (the diffs above are empty; `l3check` stays `pass=3 fail=0 … runnable=3/13`).
- **FACT:** The schema needed `result.checks` beyond the five named fields:
  `factory` and `edited` `MMAIN001.DAT` are both ACCEPT and read the same
  4,096 bytes, but the firmware buffer hash differs; without `checks` the
  falsifier would fire. The failing selftest case ("falsifier: two ACCEPT cases
  with the same read differ") is the guard against removing it.
- **OBSERVED:** The record is additive: `--trace-out` is written after the tool
  printed and computed its exit code, so any adapter bug is caught by
  `write_trace`'s own validation rather than by a changed verdict.
- **UNKNOWN:** Whether an L4 producer (M8.H11) needs a call-graph or
  fault-PC field the record does not have yet; top-level unknown keys are
  tolerated so a later producer can add them without a schema break.

## Conclusion

`tools/reader_trace.py` defines `osm2leaf.reader_trace/v1` with the required
`build`, `function`, `arguments`, `reads`, `result` fields and an optional
`result.checks` object of the producer's derived assertions; `validate`
accepts every record both adapted tools write, `compare` distinguishes runs a
reader must distinguish, and neither the producers' verdicts nor `l3check`'s
verdicts changed. `docs/research/feedback-loop.md` gains a "One trace record
for L3 and L4 reader calls" section. No claim in `docs/format/` changes; the
claims below are tool facts (C-8010–C-8013).
