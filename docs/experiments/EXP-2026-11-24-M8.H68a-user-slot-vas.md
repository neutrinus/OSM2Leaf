## Question

Can the `lpszProcName` user-slot VAs of the CE 5.0 SH-4 process table be
translated to guest physical memory so `tools/ze0_ps.py --monitor SOCK` prints
`nk.exe`, `filesys.exe`, `device.exe` and `Navi.exe` with thread counts, with
every name decoded from guest bytes and none from the DBGMSG log?

## Hypothesis

The user VAs are mapped by the CPU page tables rooted at KData `aInfo[7]`; an
SH-4 two-level walk (section → 1 KiB/4 KiB page) reaches the physical page that
holds the UTF-16 name. Falsifier: a name cannot be decoded from the physical
bytes reached by the walk, or a name survives when its page-table entry or
name bytes are corrupted, or a name agrees with DBGMSG only because it was
copied from the log.

## Method

1. **Sample and hash.** `sha256sum archive/head256.img
   archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` printed the two
   hashes in the header. No vendor bytes enter the repo; the qcow2 overlay,
   IPL patch and logs stay in the scratch directory.
2. **Commands.** Reproducible from the repo plus the two named images:

   ```bash
   W=/home/marek/projekty/OSM2Leaf.task-m8.h68a-user-slot-vas
   S=/home/marek/projekty/leafre-work/scratch/M8.H68a
   python3 $W/tools/ze0_ps.py --selftest
   python3 $W/tools/ze0_ipl.py patch $W/archive/head256.img -o $S/ipl.txt
   python3 $W/tools/qemu-ze0/mkoverlay.py \
     $W/archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img $S/card.qcow2
   TMPDIR=$S bash $W/tools/qemu-ze0/run.sh \
     --qemu /home/marek/projekty/leafre-work/qemu-ze0-m8h6/qemu-system-sh4 \
     --image $W/archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
     --ipl-patch $S/ipl.txt --sd $S/card.qcow2 \
     --icount shift=0,sleep=off --timeout 0 --gdb=1241 --workdir $S/live
   python3 $W/tools/ze0_gdb.py xp --monitor $S/live/hmp.sock 0x09e41b1c 4
   python3 $W/tools/ze0_gdb.py xp --monitor $S/live/hmp.sock 0x0c2daec4 6
   python3 $W/tools/ze0_ps.py --monitor $S/live/hmp.sock --no-modules --threads
   python3 $W/tools/ze0_ps.py --monitor $S/live/hmp.sock --no-ptb --no-modules
   python3 $S/negctrl_live.py
   python3 $W/tools/selftest.py --only ze0_ps
   ```

   The walk is derived from structure: `aInfo[7]` gives the section-array
   base, L1 is indexed by `va[31:25]`, L2 by `va[24:16]`, PTE by `va[15:10]`
   at L2+12, `reg=PTE-1`, `sz=(reg>>8)&3`, mask
   `[0x3ff,0xfff,0xffff,0x3fffff]`, and
   `phys=(reg & 0x1fffffff & ~MASK[sz]) | (va & MASK[sz])`. No fitted delta.
3. **Controls.** *Positive:* the physical bytes at `0x0c2daec4` spell
   `filesys.exe` (xp words `00690066 0065006c 00790073 002e0073 00780065
   00000065`), independently found in M8.H68's RAM scan; the synthetic
   selftest maps a U0 VA to a known physical page and decodes its name.
   *Negative:* `--no-ptb` must reproduce M8.H68's 1-process/6-error baseline;
   in `negctrl_live.py`, zeroing the slot-6 L1 word at `0x09e418b8` in a
   wrapping reader copy must make `Navi.exe` disappear with an explicit
   `invalid level-1 entry` error; the synthetic selftest zeroes L1, L2, PTE
   and the section base and requires a loud failure each time.
4. **Scope.** One idle EU2011 kernel-B guest; 7 populated process-array slots,
   145–141 live threads (count varies with boot), 59 modules in the circular
   module list; 6 user-slot name VAs translated. `--selftest` covers 4 synthetic
   processes / 10 threads / 4 modules plus one synthetic page-table walk.
   Not covered: US2011/NK1 builds, the live PC inside `Thread.ctx`, a guest
   deliberately parked in another ASID, and hardware (L5).
5. **Falsifier.** Names disagreeing with DBGMSG, a name surviving the
   corruption of its page-table entry or name bytes, or a name sourced from
   the log rather than guest memory would refute the claim.

## Observations

- `ze0_ps.py --selftest`: `checks: 32, failures: 0` / `ze0_ps selftest: OK`;
  `selftest.py --only ze0_ps`: `tool:ze0_ps PASS`.
- `ze0_gdb.py xp ... 0x09e41b1c 4`: `09e41b1c 89e418a0`,
  `09e41b20 89e69f30`, `09e41b24 8adb3024`, `09e41b28 01a70000`.
- `ze0_gdb.py xp ... 0x0c2daec4 6`: words `00690066 0065006c 00790073
  002e0073 00780065 00000065` = `filesys.exe`.
- Page-table anchor (scratch `probe_chain.py`, idle guest):
  `VA=0405fec4 -> PA=0c2daec4 'filesys.exe'`,
  `0602fec0 -> 0c28bec0 'device.exe'`,
  `080bfec4 -> 0c082ec4 'gwes.exe'`,
  `0a03fecc -> 0bf36ecc 'CPF.exe'`,
  `0d56fec8 -> 0b272ec8 'Navi.exe'`,
  `1003fec0 -> 0adb0ec0 'SystemExe.exe'`; all `sz=1` (4 KiB pages).
- Live reproduction (`--no-modules --threads`, my guest): `KData phys
  0x09e41800 ... ptb_walks=384`, `== CE processes (7) ==` with rows
  `NK.EXE 0 ... 2`, `filesys.exe 1 ... 3`, `device.exe 2 ... 79`,
  `gwes.exe 3 ... 4`, `CPF.exe 4 ... 6`, `Navi.exe 5 ... 43`,
  `SystemExe.exe 7 ... 8`; `== CE threads (145) ==`; zero READ ERROR lines.
  The four names required by M8.H68 are all present. (On the earlier shared
  guest, `device.exe` had 75 threads and 141 threads total.)
- `--no-ptb` control: `== CE processes (1) ==`, only `NK.EXE ... 2`, and six
  `READ ERROR: process slot N ... no virtual mapping` lines for the six U0
  VAs — identical to M8.H68's negative result.
- `negctrl_live.py`: `L1 slot word phys=0x09e418b8 value=8b2a5000`;
  `BEFORE: [..., 'Navi.exe', ...]`; `AFTER: [...]` without `Navi.exe`;
  `ERRORS: ['process slot 5 at 0x89e6b2b0: U0 VA 0x0d56fec8: invalid
  level-1 entry 0x00000000']`; `NEGATIVE CONTROL: PASS`.
- Provenance: `grep -aoE '(NK.EXE|filesys.exe|device.exe|gwes.exe|Navi.exe|...)'
  boot.out` finds only `CPF.exe`, `Navi.exe`, `SystemExe.exe` in the DBGMSG
  log; the tool contains no log-reading code and the names above are decoded
  from guest physical bytes through the page-table walk.

## Interpretation

- **FACT:** CE 5.0 SH-4 `aInfo[7]` is the base of the inline 64-entry section
  array; the *first word* at that address is slot 0's L1 pointer, not the TTB
  itself. A U0 VA is translated by L1 (`va[31:25]`) → L2 (`va[24:16]`) →
  PTE (L2+12+`va[15:10]`) → physical page.
- **FACT:** the physical address computed for `0x0405fec4` contains the UTF-16
  bytes of `filesys.exe`, matching M8.H68's independent RAM scan; five more
  name VAs resolve to printable names, so the layout is validated on six
  independent addresses, not fitted to one.
- **FACT:** with the walk enabled the tool prints all seven processes and
  145 threads from the kernel tables with no read errors; with it disabled
  the M8.H68 baseline returns. Thus the name source is guest memory, not the
  DBGMSG log, and the falsifier is discharged.
- **HYPOTHESIS:** process-array index `i` corresponds to CE slot `i+1` and
  Navi.exe is slot 5; its name was read directly here, so this is now a fact
  for this build.
- **UNKNOWN:** the translation assumes the guest's current section array is
  the one that maps all process slots; a guest deliberately switched to a
  different ASID was not tested, and US2011/NK1 builds were not covered.

## Conclusion

`tools/ze0_ps.py` now walks the CE 5.0 SH-4 page tables from `KData aInfo[7]`
and decodes every `lpszProcName` from guest physical bytes; the pinned M8.H68
reproduction prints all four required names with thread counts and no read
errors, and the 32-check selftest passes. Rule 15 re-opens M8.H68 in this PR.
Claim block C-10230–C-10236 is used because the TODO-assigned C-9940–C-9949
is occupied by M4.8b/M3.14. No format doc changes; the page-table VAs and
fields are recorded in the claims, not vendor bytes.
