# EXP-2026-11-05-M2.9: Error-screen catalogue from firmware strings

- **Status:** done
- **Date:** 2026-11-05
- **Sample:** `archive/images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` (SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`)
- **Claims:** C-800–C-809
- **Supersedes:** none
- **Superseded by:** none

## Question

Which firmware module holds the unit's error screens, at what VAs are those strings,
and which function shows them?

## Hypothesis

The error screens are UTF-16LE strings somewhere in the CE ROM modules; the
already-known `DIFFERENT MAP CODE` / `MAP DATA BASE UNMATCH` / `NAVI VERSION NG`
triplet suggests a single shared block. Build A was already reported to lack
`DIFFERENT MAP CODE` (C-205).

## Inputs

| Item | Value |
| --- | --- |
| Image | `archive/images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` |
| SHA-256 | `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307` |
| Builds | A (`0x200200`), B (`0x3e00200`/`0x4800200`), C (`0x5200200`) |
| Tool | `tools/cerom.py` |

## Method

```bash
# 1. Locate the UTF-16LE block in each build's modules.
python3 - <<'PY'
import sys; sys.path.insert(0,'tools')
from cerom import CERom
IMG='archive/images/LEAF_2011-2012_QSD-309-101_navi158_eu.img'
data=open(IMG,'rb').read()
for start in [0x200200,0x3e00200,0x5200200]:
    cr=CERom(data,image_start=start)
    for m in cr.modules():
        for s in cr.o32(m):
            if not s['psize'] or (s['flags']&0x2000): continue
            ss=cr.va2file(s['dataptr']); se=ss+s['psize']
            if data.find('DIFFERENT MAP CODE'.encode('utf-16-le'),ss,se)>=0:
                print(start, m['name'], hex(ss))
PY

# 2. Extract every null-terminated UTF-16LE string from that section and filter
#    the error-screen block; record string VAs with cerom file2va.

# 3. For each string, search the same section for its module VA (little-endian)
#    to find the literal-pool references; recover the showing function by the
#    nearest sts.l pr (@-r15) prologue (0x4f22) before that pool, including the
#    leading mov.l @-r15 pushes (0x2f?6).
```

## Observations

- `DIFFERENT MAP CODE` (UTF-16LE) occurs at file offsets `0x4136abc`,
  `0x4b36abc` (build B and its copy) and `0x5540a9c` (build C). All three map
  to `AppLaunch.dll`, section rva `0x1000` (uncompressed). Build A has no
  occurrence (C-205).
- The surrounding block in build B (`0x41369cc`–`0x4136af8`) contains 25
  null-terminated UTF-16LE strings: `UNKNOWN ERROR`, `SD ACCESS NG`,
  `SD INIT NG`, `SD UNLOCK NG`, `NO SD CARD`, `NAVI STARTUP NG`,
  `NO SERVICE TOOL`, `MAP DATA BASE UNMATCH`, `DIFFERENT MAP CODE`,
  `NAVI VERSION NG`, `NAVI-2 FILE READ NG`, `NO NAVI-2 FILE`,
  `MAIN TEST FILE READ NG`, `MAIN TEST FILE SIZE NG`, `NO MAIN TEST FILE`,
  `TEST FILE READ NG`, `TEST FILE SIZE NG`, `NO TEST FILE`,
  `UPDATE FILE READ NG`, `UPDATE FILE SIZE NG`, `NO UPDATE FILE`, `NAVI-1 NG`,
  `NO NAVI-1 FILE`, `TARGET INFO NG`, `E-BOOT NG`.
- Build C's block (`0x55409cc`–`0x5540ad8`) contains the same list minus
  `NO SERVICE TOOL` (24 entries).
- Every string has exactly one literal-pool reference in its module, all in one
  shared pool; the pool is preceded by one `sts.l pr,@-r15` prologue, giving one
  showing function per build: `0x8834ffb8` (B) and `0x88359c90` (C).
- No other module in any build contains this string set.

## Interpretation

- **FACT:** The error screens live in `AppLaunch.dll`, not `Navi.exe`.
- **FACT:** Build A has none of these strings.
- **FACT:** One dispatcher function per build selects the screen from an error
  code; `UNKNOWN ERROR` is the fallback.
- **HYPOTHESIS:** The function-entry VAs are correct up to the prologue heuristic
  (C-807); exact boundaries need symbol/RE confirmation.
- **UNKNOWN:** The error-code-to-index mapping and the inputs that trigger each
  screen (hardware required).

## Conclusion

Added an error-screen catalogue table to `docs/format/validation.md` and claims
C-800–C-809. Refined C-165 to point at `AppLaunch.dll`.
