## Question

With the M4.38 code table on `main`, do the M4.22 identity fields (`0x180`
words, `0x18c` code list, `BICON001` stamp) hold on all four real cards read
directly from the card FAT, and does the code→`SPEECH/` join hold on EU 2016
too, so the task's done-when is met?

## Hypothesis

The 2026-11-08 values (read from 7-Zip extractions on another machine) are
reproduced byte for byte by a FAT read of each card; `header_block.py check`
passes all eight MMAIN001/BICON001 headers and fails on `DRSTR001.DAT`; the
M4.38 join passes on EU 2016 as well.

**Falsifier:** any parsed field differing from the 2026-11-08 table; any of
the eight headers failing `check`; a `DRSTR001.DAT` passing `check`; the EU
2016 join leaving a `SPEECH/` dir uncovered or naming an absent one; a
negative join control passing.

## Method

### 1. Sample and hash

As above. The sparse EU 2014/2016 card files are built by the loop in step 2:
`identity_fields.py card` names the cluster it cannot read (`NEED … offset O
length 65536`), the range is fetched and written at `O`, and the call is
repeated until it exits 0. A probe path (`SPEECH/PROBE.DAT`) makes it name
the `SPEECH` directory cluster.

### 2. Commands

```bash
S=/home/user/scratch/m4.22
A=/home/user/OSM2Leaf/archive/sd-images
mkdir -p $S
python3 tools/fetch_image.py --image EU2014 --part 256M -o $S/eu2014_head256.img
python3 tools/fetch_image.py --image EU2016 --part 256M -o $S/eu2016_head256.img

done
python3 tools/header_block.py check $S/us2011/DRSTR001.DAT      # negative: exit 1
python3 tools/header_block.py check $S/eu2016/DRSTR001.DAT      # negative: exit 1

python3 tools/lang_code_table.py join archive/head256.img $A/LEAF_2011-2012_QSD-309-101_navi158_eu.img
python3 tools/lang_code_table.py join archive/us256.img $A/LEAF_2011-2012_US.img
python3 tools/lang_code_table.py join $S/eu2014_head256.img $S/eu2014_sparse.img
python3 tools/lang_code_table.py join $S/eu2016_head256.img $S/eu2016_sparse.img

# who consumes the MMAIN001 header copy (EU2011 build A)
python3 tools/cerom.py --image-start 0x200200 archive/head256.img exports OBJDLL.dll
python3 tools/cerom.py archive/head256.img thunks Navi.exe
python3 tools/sh4xref.py archive/head256.img Navi.exe --to 0x003d1c64
python3 tools/sh4xref.py archive/head256.img Navi.exe --to 0x01205040
python3 tools/nk_decomp.py pdata archive/head256.img --module Navi.exe 0x00377ae0
python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x00377ae0 --count 200
python3 tools/sh4dis.py archive/head256.img OBJDLL.dll --va 0x03498d28 --count 120
python3 tools/sh4xref.py archive/head256.img Navi.exe --to 0x003c0228
python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x003c0f5c --count 150
python3 tools/sh4dis.py archive/head256.img Navi.exe --va 0x003f0054 --count 60
```

The import census (which of the build-A modules import
`OBJ_DriveInfo_readDataVol`) ran `python3 tools/cerom.py archive/head256.img
imports MODULE` for each of the 149 `.exe`/`.dll` names that `cerom.py
archive/head256.img modules` lists, and kept the modules whose import list
contains `readDataVol`.

### 3. Controls

- *Positive, extractor:* `identity_fields.py --selftest` builds a synthetic MBR
  + FAT32 image and reads a root file and a subdirectory file; it must report
  `NEED` (with the right offset) for a directory cluster past EOF and for an
  all-zero file cluster (a sparse hole), never return zeros as data.
- *Positive, independent hash:* the EU 2014 `MMAIN001.DAT` read here has the
  SHA-256 M4.38 recorded (`d430813a…22e0c`), and the EU 2014 `SPEECH`
  cluster matches M4.38's (`dc4dd14b…fabd064`).
- *Negative, structure:* `header_block.py check` on `DRSTR001.DAT` (no common
  header) must exit 1.
- *Negative, join:* `lang_code_table.py join` shifts the card codes by ±1 and
  reads them without the Navi table; each must fail on every card.

### 4. Scope

Four cards, 12 header files (MMAIN001, BICON001, DRSTR001 × 4; first 4,096 B),
four `SPEECH/` listings; firmware: four build-A heads for the join, and the
EU2011 build-A import tables of 149 modules for the `readDataVol` census.
Not covered: tracing the `Navi.exe` code that reads `0x18c` (M4.42 is added
for it), the meaning of `0x180`–`0x183`, and any L3/L4 mutation run.

### 5. Falsifier

Firmware (EU2011 build A):

- `OBJ_DriveInfo_readDataVol` is OBJDLL export #240 (rva `0x39904`). Of the
  149 modules, only `Navi.exe` imports it (thunk `0x003d1c64`, slot
  `0x0055d3cc`), and the thunk is loaded once, in fn `0x00377ae0`
  (`nk_decomp pdata`: `START`, length `0x3b4`). That function clears
  `0x1000` bytes at `0x01205040`, calls `readDataVol(…, 0x01205040)`, then
  `MAL_DataVol_getOffset(7, …)`/`getSize(7, …)`, copies the range they name
  (from `0x01205040`) to the stack and swaps the two bytes of each u16 there. `0x01205040` is loaded by 4 functions (`0x00377ae0`,
  `0x003796bc`, `0x003798bc`, `0x0037a2c0`); no literal pool holds
  `0x01205040 + 0x18c` (`0x012051cc`) or neighbouring field addresses.
- `MAL_DataVol_getSize`/`getOffset` (`0x03498d28`/`0x03498d48`) index a 21-entry
  4-byte table at `0x01e33290`, and `getAreaRect` (`0x03498d68`) reads entries
  there; none of them reads a fixed header offset such as `0x184` or `0x18c`.
- The two callers of `sdl_com_hdl_get_lang` (`0x003c0f5c`, `0x003c14a0`) pass
  the code to fn `0x003f19c8` → `0x003f0054`, which stores it in a slot table
  (`0x005638ec`/`0x005638f4`) and posts message `0x14d7`. They do not compare
  the code with the `0x18c` list.

## Interpretation

- **FACT (C-5280):** a direct FAT read of all four cards reproduces every
  2026-11-08 identity value (words, bounds, code lists, fills, stamps, DRSTR
  node values), and `header_block.py check` passes all eight headers.
- **FACT (C-5281):** `identity_fields.py card` extracts card files from a full
  image, a 256 MiB head, or a sparse head plus fetched clusters, and names the
  missing cluster instead of returning zeros.
- **FACT (C-5282):** the M4.38 code→`SPEECH/` join passes on EU 2016's own card
  (16/16, negative controls fail), so it now holds on all four cards.
- **OBSERVED (C-5283):** only `Navi.exe` fn `0x00377ae0` (EU2011) reads the
  `MMAIN001` header copy through `OBJ_DriveInfo_readDataVol`, into
  `0x01205040`. The get_lang path stores the code and posts a message; it does
  not read the list. The reader of `0x18c` is still not found (M4.42).
- **UNKNOWN:** `0x180`–`0x183` meaning; codes `14 17 18 19 1a`; whether any
  reader consumes the `BICON001` stamp.

## Conclusion

M4.22's done-when is met: `file-header.md` gives each field a meaning or
`UNKNOWN` with the mutation that would settle it; the language codes are
matched to the `SPEECH/` sets (M4.38's table, re-checked here on four cards,
EU 2016 included); `header_block.py check` runs on the four real samples
(eight headers PASS, DRSTR negative fails); `drstr.md` and `assets.md` are
updated in the same commit. New task M4.42 traces the `0x18c` reader.
