# EXP-2026-11-08-M3.11b: Where the POINT page becomes native u16

- **Status:** negative (Done when not met; task set `blocked`)
- **Date:** 2026-11-08
- **Sample:** `archive/head256.img` (first 256 MiB of the EU 2011 card), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; US pair
  `REFER001/POINT010.DAT.cmp` SHA-256 `48812f8cc4…` (first 16 hex digits
  `48812f8c44bcc641`), `POINT010.DAT.ind` SHA-256 `7ac54e3b5af6dae6…`, both
  from `leafre-work/m5.13/factory/`. Page `0x840ba0`, 130,178 B, 1,000 records.
- **Tools:** `tools/point_walk_l3.py` (this branch), `tools/point_swap_scan.py`
  (new, this branch), `tools/sh4scan.py` (M3.19, loader reused),
  `tools/sh4xref.py`, `tools/sh4dis.py`, `tools/cerom.py`, all little-endian
  SH-4; Python 3.13 standard library only.
- **Claims:** C-2547, C-2548, C-2549 (M3.11 second-pass block; C-2545 unchanged)
- **Supersedes:** none
- **Superseded by:** none

## Question

Which firmware code converts the factory POINT page from big-endian file order
to native u16 before `fn 0x003f5194` (the walker) reads it, and is that code a
loop of the swap (or a copy the walker receives)?

## Hypothesis

Three places, in the order the task gives them. (1) The writers of the page
pointer `*0x00d5e4e4` and of the table `0x00d53500` hand the walker a buffer
that some earlier code has already swapped. (2) A 16-bit swap loop exists in
Navi.exe sec0 (`mov.w` load, `swap.b`, `mov.w` store, back-branch), or a byte
pair assembly `mov.b` + `shll8` + `or`. (3) The tails of `0x41c7e8` and
`0x542148` (M3.2b) contain the byte-pair assembly.

**Falsifier:** a function in the POINT page path that loads a u16 from the
inflated buffer, swaps its bytes and stores it back, followed by a back-branch
(or a copy of the page made by such code). A scan that finds no such shape in
any code section that the page path reaches refutes "the swap is a loop in
Navi.exe sec0". A walker that is fed from a function whose page is not swapped
refutes "the walker's input is already native".

## Method

1. **Sample and hash.** `archive/head256.img` and the US pair as in the header.
   Hashes printed by `sha256sum` before the run (C-2556 lists the same values).
2. **Commands.** Run from the repository root. `IMG=archive/head256.img`,
   `US=/home/marek/projekty/leafre-work/m5.13/factory/REFER001`. `archive/` is
   git-ignored: in this checkout `IMG` is the main checkout's copy,
   `/home/marek/projekty/OSM2Leaf/archive/head256.img`.

   ```bash
   python3 tools/point_walk_l3.py --selftest
   python3 tools/point_walk_l3.py sections $IMG
   python3 tools/point_walk_l3.py walk $IMG --cmp $US/POINT010.DAT.cmp --ind $US/POINT010.DAT.ind --page 0x840ba0 --page-len 42848
   python3 tools/cerom.py --image-start 0x200200 $IMG imports Navi.exe
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --to 0x00d5e4e4
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --to 0x00d53500
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --to 0x0055d8ec
   python3 tools/sh4xref.py $IMG Navi.exe --image-start 0x200200 --calls 0x003f40ec
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x003f40ec --count 60
   python3 tools/sh4dis.py $IMG Navi.exe --image-start 0x200200 --va 0x00546c84 --count 66
   python3 tools/point_swap_scan.py --selftest
   python3 tools/point_swap_scan.py scan $IMG --image-start 0x200200 --list
   python3 tools/point_swap_scan.py scan $IMG --image-start 0x200200 --module OSMDLL.dll --list
   python3 tools/point_swap_scan.py scan $IMG --image-start 0x200200 --range 0x41c7e8:0x41c8b6
   python3 tools/point_swap_scan.py scan $IMG --image-start 0x200200 --range 0x542148:0x5421b0
   python3 tools/point_swap_scan.py control $IMG --image-start 0x200200
   ```

   `tools/point_swap_scan.py` classes (halfword patterns, even VAs, LE):
   `loop` = backward branch within 24 halfwords of its target whose body holds
   a swap op, a load and a store; `loop16_exact` = the body holds a `mov.w`
   load into Rd, a `swap.b Rm,Rn` with Rm = Rd, and a `mov.w` store (data flow
   checked, so `swap.b` of an unrelated register is rejected); `pair_strict` =
   `shll8 Rd` with a `mov.b` load into Rd in the three halfwords before and an
   `or` reading or writing Rd in the three after; `swap32` = `swap.b` and
   `swap.w` within three halfwords; `loopb` = byte-pair loop.
3. **Controls.**
   *Positive, walker:* `walk` runs `fn 0x003f5194` on the swapped factory page
   and must equal `parse_page` for n = 0, 1, 2, 3, 10, 500, 998, 999, and
   return 0 at n = 1000 (C-2541).
   *Negative, walker:* the unswapped page must give the wrong offsets (expected
   `0x80`/`0xf8`, got `0xc0`/`0x4c0`).
   *Positive, scan:* `control` copies the real Navi.exe sec0 bytes, plants one
   swap loop (`mov.w @r5+,r0; swap.b r0,r0; mov.w r0,@-r6; dt r7; bf -12 B`)
   at halfword 64 of the copy, and must find +1 `loop` and +1 `loop16_exact`
   site. *Synthetic:* `--selftest` pins each class on a planted pattern and on
   negatives (plain copy loop, forward branch, loop longer than the span,
   a `swap.b` of an unloaded register, a `shll8` of an unloaded register).
   *Negative, scan:* the copy loop and the forward branch in the selftest.
4. **Scope.** Counted corpus:
   - Navi.exe: 1 uncompressed executable section (sec0, `0x11000`, vsize
     5,553,430 B); 0 compressed executable sections (`point_walk_l3.py sections`:
     149 plain code sections across all modules, 0 compressed executable). Navi.exe
     sec1 (`0x55d000`, vsize 16.7 MB) and sec2 (`0x154f000`) are compressed data
     (`0xc8002040`, `0x48002040`): they hold the import address table (see
     Observations, C-2548). Not decoded.
   - OSMDLL.dll: 1 uncompressed executable section (sec0, vsize 24,178 B); sec1
     and sec2 compressed, data flags only.
   - Other modules (COREDLL, OBJDLL, STDDLL, ...) were **not** scanned. The
     callee of the page loader is an OSMDLL import (see Observations), so the
     page producer may be in a module not yet counted.
   - M3.2b tails: `0x41c7e8..0x41c8b6` and `0x542148..0x5421b0` (from the entry
     to the first `rts`); `--range` filters the reported sites only, the loop
     search runs over the whole section.
   - The `pair` class (`shll8` followed by an `or` within 6 halfwords) gave
     403 sites; without data flow it is mostly ALU code, so only `pair_strict`
     is counted as a byte-pair candidate.
   - `tools/reader_precheck.py` (M1.12, rule 14) is **not on main**; its
     "executable vs data" counts were taken from `point_walk_l3.py sections`
     and `sh4scan.py`, and the rule 14 precheck of the TODO line is the walker
     run above.
5. **Falsifier.** Stated above. A `loop16_exact` hit in any section the page
   path reaches would support the hypothesis; the planted control shows the
   scan would have reported one.

**The page loader `fn 0x003f40ec`** (entry from the pool at `0x3f424c`):

```
0x3f4140 mov.l @(0x3f41a8,pc),r2  ; 0x011fff50 (handle cell)
0x3f4144 mov.l @(0x3f41ac,pc),r3  ; 0x0055d8ec (import cell)
0x3f4148 mov.l @r2,r4             ; handle
0x3f414a mov.l @r3,r3             ; pointer read from the IAT cell
0x3f414c jsr @r3                  ; call through the cell
0x3f4150 mov.l @r9,r4             ; *0x00d5e428 (out-parameter)
0x3f4156 jsr @r3 (0x3f3cf0)      ; sets a flag at +12 (not a swap)
0x3f4158 mov.l r4,@r2             ; *0x00d5e4e4 = page pointer
```

`0x0055d8ec` is **not** code in compressed sec1. `cerom.py imports Navi.exe`
lists it as an import slot: `OSMDLL.dll slot=0055d8ec #12`. The export table of
OSMDLL.dll numbers `OSM_TaskSend` as 12 (`cerom.py exports OSMDLL.dll`), so the
page request is an `OSM_TaskSend` message (ordinal mapping: OBSERVED from the
two listings, not from the import directory's name table). The answer comes back
in `*0x00d5e428`, which five other functions also read (`0x3f33e0`, `0x3f425c`,
`0x3f8b54`, `0x410208`, `0x410334`). So the page is produced by another task.

**The same IAT pattern in M3.15.** `0x0055d924` and `0x0055d954`, the two
"compressed sec1 helpers" of M3.15's blocker, are also import slots
(`OSMDLL.dll slot=0055d924 #71`, `slot=0055d954 #69`). `sh4xref` reports
indirect calls through IAT cells as `sub_<cell>` and does not follow the cell.

## Interpretation

- **FACT (observed):** the page walker `0x3f5194` is fed by a page whose
  pointer is written at `0x3f4158` in `fn 0x3f40ec`, after an `OSM_TaskSend`
  call (import ordinal 12 of OSMDLL.dll) that returns the page through
  `*0x00d5e428`. The conversion is therefore not in the walker's own call path
  inside Navi.exe sec0 as a loop.
- **FACT (observed, counted):** Navi.exe sec0 has no 16-bit swap loop of the
  `mov.w`/`swap.b`/`mov.w`/back-branch shape (0 `loop16_exact`), with the
  planted control found. OSMDLL.dll sec0 has none either. The M3.2b tails have
  none.
- **OBSERVED:** the one byte-pair loop (`0x546d20`) reads big-endian lengths in
  file order, which is consistent with a file-order reader and not with a page
  swap.
- **OBSERVED (later main, `EXP-2026-11-08-M9.11-chunk-decoder`):** the firmware
  chunk loop `fn 0x41c7e8` run under PySh4 returns page `0x840ba0`
  byte-identical to `cmpind.decode`, which is file order (big-endian headers).
  So the decoder does not swap; a byte-order change, if any, is downstream of
  `0x41c7e8`, in the consumer. M9.11 itself stays blocked on M9.11b, so the
  unblock named for this task is not yet met.
- **HYPOTHESIS:** the swap happens in the task that answers the `OSM_TaskSend`
  message, that is in another module or thread, or it happens inside the
  chunk decoder on the path that feeds it (M9.11's dynamic run). The sec0 scan
  cannot reach either.
- **UNKNOWN:** which task owns the message queue `*0x011fff50`; what the
  other 14 table loaders store; whether any module besides Navi.exe and OSMDLL
  sec0 holds the swap (COREDLL, OBJDLL, STDDLL, XGLDLL were not scanned).
- **Scope correction (for the board):** "Navi.exe sec0 only" in the M3.11b
  Scope line is too narrow: the page crosses into OSMDLL.dll through an
  import. The same import-slot misreading (`0x0055d8ec`, `0x0055d924`,
  `0x0055d954` are IAT cells, not sec1 code) is a candidate cause of the
  C-2206 "compressed sec1 call edges" and of M3.15's blocker. That claim is not
  retracted here; it needs its own EXP (new task, rule 9).

## Conclusion

Done when is **not met**. The loop of the swap (or a proof that the walker gets
a copy made by a swap loop in Navi.exe sec0) was not found: 0 exact swap loops
in Navi.exe sec0 and OSMDLL.dll sec0, 0 in the M3.2b tails, against a planted
control that is found. The page arrives from another task through an
`OSM_TaskSend` reply. Task set to `blocked`, unblock by M9.11 (dynamic run of
the chunk decoder, watching the buffer the walker receives). C-2547 records the
loader and its import; C-2548 records the counts and the control; C-2549
records the big-endian length reader that was checked and rejected.
