## Question

Executed, not read: does the firmware's `.ind` reader (a) compare
`chunk_size` with `0x10000` or size a buffer from it, and (b) locate a chunk
by seeking to `chunk_offset[i]` or by scanning the `.cmp` for `78 9c`?

## Hypothesis

M3.2b's static reading (C-5102, C-5104): `chunk_size` is compared for equality
with the mount configuration word ctx `+0x138` (= `0x10000`) at `0x0041c92a`
and `0x0041c696`, then used only as divisor/multiplier; the reader seeks the
`.cmp` to `chunk_offset[first]` and reads the batch in one call.

**Falsifiers (stated before the runs):** (a1) a `.ind` with `chunk_size`
`0x8000` or `0x20000` is read (any return other than -1), or is rejected only
after `.cmp` bytes were read (then the value would be checked by inflate, not
compared); (a2) with the harness changing *only* the mount word to `0x20000`,
the factory `.ind` is still accepted (then the compare is against a literal,
not the configuration); (b1) the `.cmp` seek offsets differ from
`chunk_offset[i]`; (b2) with a valid `78 9c` decoy stream prepended to the
`.cmp` and the index shifted by the same amount, the reader returns the decoy
or fails (a scan from 0 would find the decoy first); (b3) an index whose last
offset is 1 byte early is still read correctly (a scanner would resync).

## Interpretation

- **FACT (C-5330), M3.2(a):** `chunk_size` is compared with the mount's
  configuration word, not used to size anything: a 0x8000 or 0x20000 field is
  rejected at `0x0041c92a` before any `.cmp` byte is read (c3, c4, 8,255
  instructions, read returns -1, error log `(4,11,4,10)`); with only the mount
  word changed, the *factory* file is rejected the same way (c5) — the right
  side of the compare is the configuration (ctx `+0x138`), not a literal.
- **FACT (C-5331):** once the compare passes, the field is the chunk geometry:
  with both at 0x20000 (c6) the reader treats ADDRE001 as one chunk, reads
  only `chunk_offset[0]..chunk_offset[1]` (0x8a17 B), and returns 79,360 bytes
  that differ from the file — no further check catches it. The firmware's only
  `chunk_size` defence is the equality compare.
- **FACT (C-5332), M3.2(b):** the reader seeks by the index. Every `.cmp`
  access is one `ops.seek(chunk_offset[first], SEEK_SET)` followed by one
  `ops.read` of the batch's summed length (c0, c1, c7); with a valid `78 9c`
  decoy at offset 0 and the index shifted by 0x1000 it seeks to 0x1000 and
  returns the right bytes (c2); with the last offset one byte early it reads
  the same bytes but inflate fails and the read returns -1 (c8) — no resync.
- **OBSERVED (C-5333):** the `.IND` is read twice per open+read: the 16-byte
  header at open (`0x0041c474`) and the whole file through the cache
  (`0x0041d084`), which seeks to 0 and asks for 0x800 B; the `.cmp` is opened
  at open time and kept.
- **OBSERVED (C-5334):** the factory pairs pass through the full EU2011 layer
  (mount, `CMP.LST` match, open, seek, read, inflate) byte-identical to
  `cmpind_codec.decode` for ADDRE001 (whole file) and POINT010 (page
  `0x840ba0`, 42,848 B), extending M9.11's fragment run of `0x0041c7dc` to the
  parser and the opener.
- **UNKNOWN:** the request producer above `0x0041855c` (M3.28/M9.44) and the
  meaning of the error-log codes `(4,11,4,10)`.

## Conclusion

M3.2's Done-when (both answers in `cmp-ind.md` with VAs) was met statically by
M3.2b; this run confirms both answers by execution and adds what a writer
needs: `chunk_size` must equal 0x10000 exactly (any other value is rejected
before the `.cmp` is touched; a matching wrong configuration would silently
mis-decode), and chunk offsets must be exact (no `78 9c` resync).
`docs/format/cmp-ind.md` gets an "L3 run" paragraph; claims C-5330–C-5334;
`reader-coverage.md` row 6 records the layer run. Still open: the 5 other
`ind_mutate` variants (M3.3, same tool, `batch`), the US2011 build, and the
request producer.
