## Question

The "SD PIN" screen with `Using PIN … / Unlocking. OK` (EXP-2026-11-06-M2.13)
comes from LeafSDTools. Where does that tool get the 16-byte PIN, in what order
does it print it, and how does it lock/unlock the card?

## Method

```bash
git clone --depth 1 https://github.com/developerfromjokela/leafsdtools src
grep -n "ReadFullSDPin\|ChangeSDLock\|DeviceIoControl" src/LeafSDTools/*.cpp
# read LeafSDTools/SDPinControl.cpp (menu, display) and Flash.cpp (PIN read, IOCTL)
```

## Observations

- `SDPinControl.cpp` `RunSDPinControl()`: the "S D   P I N / Lock & unlock SD
  card protection" screen is LeafSDTools' own menu (buttons `SD UNLOCK`,
  `SD LOCK`, `EXIT`). It refuses to run on `NEW_NAV` units.
- PIN buffer: `BYTE pinCode[0x10]`, filled by `ReadFullSDPin()`.
- `Flash.cpp` `ReadFullSDPin()`: reads `0x2D1` bytes of NAND block **5**
  (old nav; block 2 on `NEW_NAV`) through `FMD1:` IOCTL `0x80112000`, then
  copies **16 bytes from offset `0x100`**. With 8192-byte blocks 0–7
  (comment in `Flash.cpp`), block 5 starts at `0xA000`, so the PIN is at
  flash `0xA100`.
- Display loop: for bytes 0–15, a byte is printed as text if it is printable
  **and its index is > 3**, otherwise as `%02X`. Bytes 0–3 are therefore
  always printed as two hex digits each, **in buffer order**.
- `ChangeSDLock()`: opens `DSK8:` and calls `DeviceIoControl` with the same
  16-byte buffer, length `0x10`; IOCTL `0x80032014` for lock, `0x80032020` for
  unlock. Up to 5 attempts, success when the call returns 1. The CMD42 frame
  is built by the unit's SD driver behind that IOCTL, not by LeafSDTools.

## Interpretation

- **VERIFIED (source, C-1945):** the CMD42 password LeafSDTools uses is the
  16 bytes at flash `0xA100` (PROD block 5 + `0x100`), passed unchanged
  to the unit's SD driver. This confirms C-075 ("stored near `0xA100`") and
  the 16-byte length of C-1940/C-1883.
- **VERIFIED (source, C-1946):** the 8 hex digits on the screen are bytes
  0–3 in buffer order. Typing them as `hex:<8 digits>` in the Pico tool gives
  the same bytes, so the byte-order UNKNOWN of C-1940 is resolved; the
  reversed-order fallback of the hardware doc §7.4 is only a last resort.
- **OBSERVED (C-1947):** the "SD PIN" lock/unlock menu is LeafSDTools, a
  third-party program run on the unit, not a factory menu. "The unit has its
  own SD LOCK/UNLOCK menu" (EXP-2026-11-06-M2.13, M6.9 note) holds only for a
  unit that runs LeafSDTools.
- **UNKNOWN (C-1948):** which CMD42 flags the driver sends for IOCTL
  `0x80032014` (only `LOCK`, or `SET_PWD`+`LOCK` on a card without a
  password). LeafSDTools does not show it; that is `SDHC.dll` (C-792, M1.2
  compression).

## Conclusion

Nothing in LeafSDTools changes the Pico tool: it sends the same 16 bytes
over a different host. `docs/hardware/sd-blocker-pico.md` §3 now says where
the PIN comes from and that the displayed order is the byte order. No PIN
value committed.
