## Question

Why does the kernel end in its `Halting system` loop (`0x88022170`), and
what does `-M ze0` need for `filesys.exe` and `device.exe` to start and the
kernel to run 60 s without a fault?

## Done-when (made concrete before the controlled runs, commit `e272540`)

The TODO line is "`filesys.exe` and `device.exe` start, 60 s without a
fault" (history: "start (log or gdb) and the kernel survives 60 s"). The
block now says: one `-M ze0 -kernel archive/head256.img -icount
shift=0,sleep=off` boot under `ze0_dbgmsg.py run` ends with (1)
`ze0_dbgmsg.py modules` on a RAM dump of `0x89e40000`+256 KiB listing
`filesys.exe` and `device.exe`; (2) 0 hits at `0x88011cb8` (prints
"Unhandled exception") and `0x88022164` ("Halting system"), and no
`Exception` line in the kernel's debug output; (3) `CurMSec`
(`0x89e41888`) ≥ 60 000 at the end. Negative controls: `ext-ram=off` and the
M8.B2 binary must fail (1) or (2). The exploratory runs that found the two
causes came first; the runs in §4 were made after the block was committed.

## Hypotheses

1. The halt is the kernel's reaction to an exception QEMU raises
   wrongly. **Falsifier:** the kernel's own report names a fault that
   QEMU models correctly.
2. Once that is fixed, the next blocker is missing hardware or memory.
   **Falsifier:** both processes start with no model change.

## Observations

### Cause 1: the API trap raised the wrong exception

The kernel's own report on the M8.B2 binary (`f-b2.log`, also `old.log`):

```text
Load Lib Error (aerhd.dll)
Exception 180 Thread=8a6c8024 Proc=0a6c8002 'NK.EXE'
AKY=ffffffff PC=fffffd51(???+0xfffffd51) RA=8804c128(NK.EXE+0x0004c128) TEA=03fa1f10
 | Unhandled exception c000001d:
Terminating thread 8a6c8024, PSR = 40008000
Exception 180 ... PC=fffffd4d(???+0xfffffd4d) RA=03fafe9c(coredll.dll+0x0000fe9c)
...
Can't terminate thread 8a6c8024, sleeping forever
```

`0x8804c124` is `jsr @r3` with `r3 = 0xfffffd51` (sign-extended `mov.w
0xfd51`), an API call. The general exception handler `0x8800ed10` reads
EXPEVT (`@(36,r7)`), compares it with `0x0e0`, then requires SPC to be odd
and ≥ `0xffff7e03`, and dispatches `(SPC − 0xfffffe01) >> 1` as the call.
QEMU raised 0x180 (illegal instruction) instead of the SH-4 instruction
address error for an odd fetch address. With `ze0-0006` the same three
traps are taken as `0x0e0 [addr_error]`. In the positive run there are
2 318 of them (API calls) and no "Exception" line.

### Cause 2: the second DRAM bank

After the trap fix the kernel prints:

```text
Memory Sections:
[0] : start: 89e74000, extension: 00005000, length: 04787000
[1] : start: 90000000, extension: 00008000, length: 07ff8000
ERROR: d:\wince500\private\winceos\coreos\nk\kernel\physmem.c line 254:
GrabFirstPhysPage : invalid address 0x00000000 (PFN 0x00000000)      (x20 in f-noext)
```

The OAL memory table in `nk.exe` .data (ROM `0x88599c98`, copied to
`0x89e43c98`): `{0x8c6e0000, 0x00401000}`, `{0x90000000, 0x08000000}`,
`{0x89e40000, 0x047c0000}`, `{0x8e600000, 0x00100000}`,
`{0x8e700000, 0x01900000}`. So `0x88000000..0x90000000` and
`0x90000000..0x98000000` are both DRAM: 256 MiB, the second half at phys
`0x10000000`, where `ze0` had an area-4 catch-all. With that RAM
(`ze0-0006`) the errors are gone (0 in `f-pos`). With `ext-ram=off` the
system has no process except `nk.exe`, and the timer ticks at idle
(`CurMSec` `0xc37d98da`).

## Interpretation

- **FACT (C-1350):** the `Halting system` loop of earlier runs is the
  kernel's response to `Exception 180 … PC=fffffd51`: QEMU raised an
  illegal instruction for the CE API trap (a `jsr` to an odd address in
  `0xffff7e03..0xfffffe01`). The EU2011 handler at `0x8800ed10` expects
  EXPEVT `0x0e0`. `ze0-0006` makes an odd-PC fetch raise the SH-4 instruction
  address error (SPC = TEA = PC), and the traps dispatch. Hypothesis 1
  confirmed: QEMU modelled the fault wrongly.
- **FACT (C-1351):** the EU2011 OAL declares 256 MiB of DRAM, the second
  128 MiB at VA `0x90000000` (phys `0x10000000`). Without RAM there the
  kernel logs `GrabFirstPhysPage : invalid address 0` and starts no
  process. `ze0-0006` maps it, and `ext-ram=off` keeps the old map as a
  negative control.
- **FACT (C-1352):** with both, `filesys.exe` and `device.exe` start
  (loader records at `0x89e6afc0` and `0x89e6b090` reference their TOC
  entries; their code prints from slots 2 and 3). The kernel runs
  839 s of guest time with no unhandled exception and no halt. Done-when
  met, and both negative controls fail as required.
- **OBSERVED (C-1353):** what runs first in device.exe is the Clarion stack
  (ACM, POW, LOG, FlashDriver, Launcher, GDISUB display 800×480 with VRAM at
  `0xae700000`, CAN driver interface, SDHC driver, DMA-LIB). The launcher
  stops at `SD Check Error` (3 retries) and `Error Proc<00000080>`, and
  issues 132 failing `KernelIoControl` calls. `gwes.exe` is not started in
  the run.
- **OBSERVED (C-1354):** `tools/ze0_dbgmsg.py` reads the kernel's debug
  output without a UART or an SH-capable gdb. It sets a breakpoint on the
  EU2011 debug sink `0x880404f4` and reads the UTF-16 string at `r4` over
  the gdbstub. This replaces the M8.A6 follow-up "HLE hook on `0x880404f4`".
- **Next blockers:** the SD host (TODO **M8.C10**, the launcher's `SD
  Check`), the OEM `KernelIoControl` codes the launcher and filesys ask
  for (`OEMIoControl: Unsupported Code 0x101008c …`), and `gwes.exe`. No
  new task: M8.C10 and the M8.C rows already own them.

## Conclusion

F1 is reached. On `-M ze0` with `ze0-0006`, the EU2011 kernel starts
`filesys.exe` and `device.exe` and runs 14 guest minutes without an
unhandled exception. It took two fixes: SH-4 address-error semantics for
odd-PC fetches (the CE API trap) and the second 128 MiB DRAM bank. Both
were found from the kernel's own debug text, which `ze0_dbgmsg.py` now
reads.
