## Question

Can a tool turn a prepared card tree into an SD image the unit could read,
reproducing the factory layout (MBR, FAT32 partition 0 at LBA 204802 /
0x6400400, 64 KiB clusters, 128 sectors/cluster, 2 FATs, 900 FAT sectors,
reserved 32, root cluster 2, label `QSD-309-101`, OEM `MSDOS5.0`, root entry
order with `MMAIN001.DAT` present in the root directory cluster, and the
`VER_INFO/HDD_INFO.TXT` copy at `0x06000000` that `cardcheck.py --image`
checks), with firmware/pre-partition regions copied verbatim from the source
image?

## Hypothesis

For an unchanged tree, copying the source image and reconciling an identical
map partition yields a byte-identical image. For a changed tree, rebuilding the
map partition produces a structurally valid FAT32 image whose differences from
the source are explainable (timestamps, allocation/free-cluster order, and the
changed file content/clusters).

## Interpretation

- **FACT:** `mkcard.py --from-image IMG --tree ROOT -o out.img` rebuilt the map partition from an unchanged tree and produced an output byte-identical to IMG (SHA-256 match). Firmware/pre-partition bytes and the `0x06000000` copy were preserved by copying the source image; the map FAT32 partition content matched the tree with zero differences.
- **FACT:** `cardcheck.py --image` passed on the rebuilt image with the same structural counts as the reference EU 2011 card.
- **FACT:** The tool reports differing byte ranges with explanations (FAT copies, reserved/BPB/FSInfo/backup, data-area cluster, pre-partition/firmware, `0x06000000`) and states what it cannot reproduce (SD lock state, CID).
- **OBSERVED:** For changed trees, `mkcard.py` rebuilds the map partition (fresh FAT32 population derived from source geometry) into the copied image; this preserves pre-partition/`0x06000000` and yields a readable filesystem, but timestamps/LFN encoding quirks, free-cluster order and directory allocation differ from factory layout and are reported as explained diff ranges rather than claimed byte-identical.
- **OBSERVED:** ROOT and IMG content were identical on this machine; the unchanged-tree identity path is the verified primary case. The fresh-build path is exercised synthetically.
- **HYPOTHESIS:** A fresh-built (non-identical) image passes structural validators but unit acceptance of non-factory allocation/timestamps/LFN details remains unproven until the bench test (M6.5/S0/S1). Lock state/CID remain external prerequisites.
