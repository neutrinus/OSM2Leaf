## Question

Can one standard-library tool turn an extracted card tree into an SD image that
keeps the factory container exactly — MBR, pre-partition firmware area, FAT32
geometry and label, post-partition tail, and the `0x06000000` `HDD_INFO` copy —
while changing only what the tree changes, so that (a) an unchanged tree
rebuilds byte-identically, (b) a changed file produces a small, enumerable set
of differing ranges, and (c) the result passes the L1 card checks?

## Hypothesis

A **layout-preserving rebuild** is both simpler and safer than formatting from
scratch: copy the source image, then patch only FAT/directory/file bytes that
the tree forces. The factory allocation then survives by construction, so an
unchanged tree must produce zero patches, a same-size byte edit must produce
exactly one byte, and the new `HDD_INFO` (if edited) must also land at
`0x06000000` because `cardcheck.check_version` compares the image copy against
the visible file. Expected failure modes: directory/LFN bookkeeping mistakes
and FAT allocation slips — both caught by reading the result back with
`cardcheck.Fat32Image`.

Each check has a different job:

| --- | --- |
| `fixture reads back` | the fixture is a real FAT32 image, read by `cardcheck.Fat32Image` (positive control for the source) |

## Interpretation

- **FACT (C-1910):** a stdlib tool rebuilds a Leaf ZE0 card image from a tree
  while keeping the factory container: MBR, pre-partition area and tail are
  copied verbatim, the FAT32 geometry, label, volume id, FAT count and cluster
  size are taken from the source and never rewritten, and only tree-driven
  bytes are patched. On the synthetic factory-shaped image (512 B sectors,
  65,536 B clusters, two FATs, label `QSD-309-101`, `0x06000000` copy) an
  unchanged tree yields a byte-identical image (0 changed ranges, equal
  SHA-256); one flipped byte at file offset `0x100` yields exactly one 1-byte
  range; a 100-byte append yields exactly the size-field byte and the appended
  bytes; create, delete and grow all round-trip through
  `cardcheck.Fat32Image`; rebuilding from the rebuilt image is a no-op; and
  the result passes the complete `cardcheck` L1 set
  (mbr/fat/tree/headers/cmp/drstr/mmain/version).
- **FACT:** the `0x06000000` copy is written from the tree's
  `VER_INFO/HDD_INFO.TXT` on every build (10 bytes changed at `0x06000000` and
  10 in the file for the same edit), so `cardcheck.check_version` compares two
  copies that `mkcard` kept consistent; the tool refuses (exit 1, no image) if
  `HDD_INFO` line 2 would no longer match the FAT label, unless
  `--allow-label-mismatch` is given.
- **FACT:** allocation is first-fit ascending from cluster 2, so new files and
  grown files can land in a different free-cluster order than a factory writer
  would choose; kept files never move. Freeing a shrunk file zeroes the FAT
  chain tail; freed cluster *contents* are left as they were.
- **OBSERVED:** directory entries for kept files (short name, LFN, case,
  timestamps, attributes) are preserved byte-for-byte; only the 4-byte size
  field (and cluster fields, if a chain moved) changes when a file changes.
  New entries get `--timestamp` (default `2011-08-23 21:20:54`, the factory FAT
  modification time from `sd-card-layout.md`) and a standard LFN checksum, not
  the card's non-standard WinCE checksum; `cardcheck` accepts both, and no
  new LFN checksum is written for files the tree did not add.
- **OBSERVED (limits, by design):** a case-only rename is reported and the
  image name is kept; `.cmp`/`.ind`/`DRSTR001.DAT`/`MMAIN001.DAT` are copied,
  never regenerated (that is M5.6/M5.9's job — the fixture regenerates DRSTR by
  hand to keep the test card consistent); the volume label and volume id are
  never changed (C-794/C-795 found nothing that checks them).
- **HYPOTHESIS:** the same build on the factory image is byte-identical for an
  unchanged tree, because the tool only writes what differs from the source and
  the source's own directory/FAT bytes are what it preserves. Not proven here:
  the image is unavailable (see below).
- **UNKNOWN / cannot be reproduced by an image builder:** the SD card's
  **lock state (CMD42)** and its **CID/CSD registers** are hardware state, not
  image bytes; the burst/transfer behaviour of a card is likewise outside the
  image. The tool reproduces only what is in the image (including the FAT
  volume label/serial, which the factory image itself carries).
- **UNKNOWN / real-image risks:** whether the factory FSInfo free count equals
  the FAT's own count (the tool adjusts it by a delta, so a wrong factory value
  stays wrong by the same constant); whether every factory LFN sequence is
  contiguous (a non-contiguous one would be read as a short name and the plan
  would show a create/delete instead of a keep); and whether any directory
  cluster holds stale non-zero bytes past its last entry (appends would then
  land at the cluster end, still valid but not factory-shaped).
- **Cost on the real card:** the build writes a full 7.5 GB image (the disk
  space check refuses if the target is short) and the "keep" decision reads the
  whole 5.17 GB tree against the partition; a dry run pays the same read cost.

## Conclusion

`tools/mkcard.py` closes the missing link between the writers and a bench test:
a tree goes in, a full card image comes out, with the factory MBR, firmware
area, FAT geometry, label and tail untouched, and only tree-driven bytes
changed. The synthetic evidence is complete for the tool's own logic (identity,
minimal diffs, create/delete/grow, LFN, HDD copy, idempotence, full L1) but the
**real-image round-trip is not done**: the vendor image is not on this machine,
so `docs/format/sd-card-layout.md` is unchanged and no claim about the factory
image is made here. `docs/research/claims.md` is untouched (the C-1910 row is
stated in this record only).

**What the real-IMG round-trip still needs**

1. The EU 2011 image (`105e2032…76307`) or the US image, plus `7z x` to
   `root/` (39 dirs, 480 files, 5,173,965,667 bytes for the EU set).
2. `mkcard.py --from-image IMG --tree root -o out.img`, then
   `sha256sum IMG out.img`: expect equality for the unchanged tree, or a
   shortest-possible list of differing ranges with a reason per range.
3. `cardcheck.py --image out.img` must PASS (194/194 `REFER001` pairs, DRSTR,
   MMAIN, `HDD_INFO` copy), and `l2check.py --root root` should be unchanged.
4. Check the three real-image risks above on the first run (FSInfo count,
   LFN sequences, directory slack) and record the observed values.
5. Only then can a writer's output (M5.4/M5.6/M5.11) be put on a card image
   for S0/S1/S3 of `card-test-plan.md`; the SD lock and CID/CSD gates stay with
   the bench (M6.5), not with this tool.
