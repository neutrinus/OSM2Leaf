## Question

What does `navdrv.dll` send to and receive from the GPS receiver on `SCI7:`,
and is the format documented in a public spec (NMEA or a chip vendor) that a
host peer can implement?

## Hypothesis

No `$GP`/GGA/RMC string and the earlier TestMode `A0 … F0` frame (C-8244)
suggest a vendor binary format. It should be possible to derive the frame
grammar and checksum from the driver alone. **Falsifier:** the driver reads
no serial data (position arrives pre-computed). **Stop:** if the sync bytes
match a named public protocol, cite the spec instead of deriving every field.

## Observations

**O1 — placement and identity.** `navdrv.dll` is module 58 of build B,
virtual base `0x039e0000`, sec0 `0x039e1000` for `0x6b02` bytes. `pdata`
has 110 records; all ten labelled functions below are STARTs. Its sec0
SHA-256 `e920886f…6b806` is identical in EU and US heads; sec2 also matches,
so no `fn_match` was needed (C-7252).

**O2 — the driver really reads serial data.** Imports resolve to
`CreateFileW("SCI7:")` in `function 0x39e3ec0`, `ReadFile` in `function 0x39e4a54`,
`WriteFile` in `function 0x39e44e8`, `WaitCommEvent`/`ClearCommError` in
`function 0x39e4c50`. The falsifier does not fire.

**O3 — line settings.** `CommInit` `function 0x39e3ec0` writes `BaudRate =
0x12c0` = 4800 from the halfword at `0x39e4040` (`mov.w @(…),r3` at
`0x039e3f94`, `mov.l r3,@(8,r14)` at `0x039e3f98`), 8N1-style DCB bytes,
read timeout 200 ms and write timeout 1000 ms. The value `0x4b00` (19200)
has zero occurrences in this module. This conflicts with C-6425's
`SCI7: 19200` row, recorded from a different table.

**O4 — frame grammar.** Start byte has bit 7 set; the scanner at
`leaf 0x39e41ec` compares against `0xa0`, `0xa2`, `0xa5`, `0xaf`, `0xb4`,
`0xbf`, `0xc1` (`0x039e41fe…0x039e4230`) and accepts `0xa0`, `0xa5…ae`,
`0xb4…be`, `0xc1…ff`. Length comes from two 34-byte tables right after the
`SCI7:` string (`0x39e17e4` RX, `0x39e1808` TX) through a `braf` dispatch
(`leaf 0x39e42a4`/`0x39e42e8`); `0xb0` maps to 6 bytes. `function 0x39e44e8`
requires `frame[len-1] & 0xf0 == 0xf0`.

**O5 — checksum.** `leaf 0x39e4248`: after a length check it reads bytes
1…len-3, rejects any with bit 7 set (`and r8,r1` at `0x039e4272`), sums them
into a byte, and compares `(sum & 0x7f)` with `frame[len-2]` at
`0x039e429a`. Checksum byte index is `len-2`, not `len-1`.

**O6 — the captured frames decode.**
```
b0 20 02 00 22 f0    Σ(20 02 00)=0x22, 0x22 & 0x7f = frame[4], frame[5]=f0
b0 23 02 00 25 f0    Σ(23 02 00)=0x25, 0x25 & 0x7f = frame[4], frame[5]=f0
```
Both are 6 bytes, as the TX table says for `0xb0`. `0xb0` is not in the RX
scanner's accepted ranges, so these are commands **to** the receiver, not
fixes **from** it. Command semantics (`0x20`, `0x23`) are HYPOTHESIS.

**O7 — receive path and ring.** `function 0x39e4c50` waits on `EV_RXCHAR|EV_ERR`;
`function 0x39e4a54` reads four bytes at a time into two 100-byte buffers, calls
the scanner, the length leaf, the `0xf0` search in `function 0x39e4630`, the
checksum leaf, then `function 0x39e4324` (24-slot × 100-byte ring at object
`+0x980`) and `function 0x39e4700`. `function 0x39e4f60` copies 36-byte records out;
`DeviceIoControl(0x800f2000, …)` and event index 1 notify the consumer.

**O8 — date frames and MMIO.** `function 0x39e4988` reads frame bytes
`+16…+21` into a `SYSTEMTIME`-shaped structure and calls `SetSystemTime` at
`0x039e4a14`, adjusting a two-digit year by 1900 (`0x076c`) or 2000
(`0x07d0`). `0xffc5a000`/`0xffc5b000` are gyro/speed-pulse ADC mappings in
`function 0x39e6f74` (C-7250/C-7251). `0x19800000` is reached as P2 alias
`0xb9800000` at `0x039e6bec` in `function 0x39e6b70` via `MmMapIoSpace`; its role
is UNKNOWN (C-1302).

**O9 — no public name.** No `$GP`, `GGA`, `RMC`, `SiRF` or `UBX` string in
ROM B; start bytes `0xa0`/`0xb0`/`0xb3`/`0xb4` do not match UBX `b5 62` or
SiRF `a0 a2` (the latter has `0xa0` but a different second byte and length).
The format matches the `A0/B0/B3/B4` + 7-bit-sum + `F0` family of C-8244,
but the chip/vendor remains UNKNOWN; the task's Stop clause therefore does
not apply.

## Interpretation

- **FACT (C-7240, C-7241, C-7242):** module/VAs, Win32 COM interface and EU/US
  identity (O1, O2); line settings including the 4800/19200 conflict (O3).
- **FACT (C-7243, C-7244, C-7245):** start-byte/length grammar, 7-bit sum and
  `F0` terminator (O4, O5); the two live frames decode exactly (O6).
- **FACT (C-7246, C-7247):** receive thread, assembler, ring and IOCTL path
  (O7); date frame → `SetSystemTime` (O8 first half).
- **OBSERVED / HYPOTHESIS (C-7248):** command IDs, date-field order and the
  role of the P2-mapped area-6 device are not resolved here (O6, O8).
- **FACT (C-7249):** lat/lon/speed/heading/satellites are **not** decoded by
  `navdrv.dll`; they must be found on the `Navi.exe` side (M8.H29).
- The falsifier "driver reads no serial data" is refuted by O2 and by the
  M8.H1 RX/ISR measurements (C-6984/C-6985).

## Conclusion

The GPS link is a vendor binary protocol, not NMEA: `[start with bit7]
[payload] [sum(payload) & 0x7f] [0xf0]`, with start-byte-specific lengths from
two tables. A host peer can already encode the two observed commands; a
synthetic *fix* still needs the receiver's fix-frame layout and the consumer
decode in `Navi.exe` (M8.H29).
