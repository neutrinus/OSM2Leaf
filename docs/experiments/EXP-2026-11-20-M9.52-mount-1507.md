## Question

Every `datask_l3.py mount` run (M9.13, M3.25) ends with the data-access
task's state word (data VA `0xd62490`) at 2 and one undelivered send,
message `0x1507` sub 1 to task id 0 (C-4697). Which task receives it, what
does it answer, and is that answer what keeps the mount from reaching
state 3?

## Hypothesis

Exploratory, with one expectation from the task: the receiver answers
`0x1507` with a message that the data-access task's dispatcher maps to the
function that writes 3 into the state word.

**Falsifier (stated before the runs):** the state word reaches 3 without any
reply to `0x1507` (then the wait is on something else), or the receiver
answers and the state word stays 2.

## Observations

**The sender.** `0x00401e94(msg)` stores `taskIdSelf()` at `msg+0` and calls
`OSM_TaskSend(*0x011fff50, msg, -1)` (`0x00401eaa`–`0x00401eba`). On a send
failure it arms a timer (`0x0040346c`) and retries up to 250 times; on
success it returns 0 and waits for nothing. `0x00402690(0, 0)` builds the
message on its stack: `+8 u16 0x1507`, `+10 u16 1`, `+12`…`+28` = 0. Its
three static callers are `0x003f0394`, `0x00402fe0` (row `0x14cb`) and
`0x004030f0` (completion class `0x0a`). `0x003f0394` sends it when
`*0x005638e8 == 2` and the `REFER001` search block at `0xd5e580` has its
words `+36` (not 0/-1), `+0xc8` (1) and `+0x5c` (1) set, then calls
`0x0040b114`; in the run the send follows the `ICODE001`/`ICADM001`
reads.

**The receiver.** `0x0032efa8` (called from `0x0032ed9c`, next to the module entry
`0x0032edd0`; it calls `OSM_StartUp`, `OSM_memLibInit`) creates the tasks one by one with
`OSM_TaskCreate(name, priority, 0, stack, entry, …)` and stores each result
in a global. At `0x0032f38c`–`0x0032f39c`: name VA `0x11154` = `SDL_task`,
entry `0x0039d854`, result to `0x011fff50`. At `0x0032f0de`–`0x0032f0e6`:
name VA `0x1120c` = `HDL_MapMainTask`, entry `0x003ebfb4` (the data-access
task, C-4681), result to `0x011fff58`; the next call is `0x003eba4c`.

`SDL_task` (`0x0039d854`) calls `0x003c001c` once, then loops on
`OSM_TaskReceive` and hands each message to `0x0039d6f0`. That dispatcher
handles `0x07d0` itself (`0x003c1b14`: subs 100, 101, 102) and otherwise
routes by the sender at `+0`: `*0x011fff8c` → `0x0039cdcc`,
`*0x011fff58` → `0x0039d18c`, `*0x011fffa8` → `0x0039d2b8`,
`*0x011fff4c` → `0x0039d3e4`, `*0x011fff50` → `0x0039c978`.

`0x0039d18c` first calls `0x003c009c(msg)`: it returns -1 unless
`msg+12 == *0x006f4650` **and** `*0x006f4654 == 1`; on -1 the handler logs
the string at `0x3a3a8` (`[SDL]… SDL receive msg from hdl. ReqId Error`)
and returns. Otherwise `0x0039ca00(state, 0x39e30, msg, &out)` looks the
`s16` state at `0x9379b8` up in a 20-row `{u32 state, u32 handler}` table at
data VA `0x39e30` (states 2, 0x17, 0x13, 3, 0x18, 0x11, 0x12, 0x14, 0x15,
0x24, 0x21, 8, 0x20, 0x10, 0x23, 0x22, 0xb, 0x27, 0x28, 5).

A full-module literal search finds `0x1507` loaded in two places only:
`0x0040269c` (the builder) and `0x0050d560` (a literal-pool word, not code).
No `{u16 0x1507, u16 0|1, u32 handler}` row exists in `Navi.exe` data.

**The run with SDL_task** (`--sdl`; the tool writes id 3 into `0x11fff50`,

Selftest controls (`datask_l3.py --selftest`, 46 checks, 0 failed):

**The state word.** Of the nine functions that load `0xd62490`
(`sh4xref --to`), four store it: `0x003f6908` (0, init), `0x003f75e4` (2),
`0x003f6bb0` (1), `0x003f6b1c` (3). `0x003f6b1c(msg)` reads the car position
(`0x00403504` → `0xd940e4`), then, if `msg+28 == 16`, calls
`OSM_SramClear(0x8e)` and writes `0xff` to the `u16` at `*0xd8b080` when the
word at `0xd8b084` is set, and stores 3 when the state is not 0
(`0x003f6b38`–`0x003f6b62`). `0x003f6bb0` stores 1 when
`msg+28 == 0x3f7` after `0x0053a918` (`OBJ_DiscInfo_answerJudge`). All
three are rows of the `0x07d0` sub-table (`datask_l3.py tables`): sub 11 →
`0x003f6b1c`, sub 13 → `0x003f6bb0`, sub 100 → `0x003f75e4` (also 6 →
`0x00403564`, 12 → `0x0042af34`, 199 → `0x003f6b84`).

The dispatcher `0x003ebee8` runs a row with the defer flag (only `0x14b5`)
at once only when the progress word `0xd98fcc` is 1 **and** the state word
is 3 (`0x003ebf14`–`0x003ebf22`); otherwise it calls `0x003ebd44`. The run
ends with progress 1 (`0x003f7624` takes the short path because the `u16` at

**Where 0x07d0 comes from.** `OBJ_Event_setPrm` (`OBJDLL.dll` rva

**Change control.** The tool now writes the two task ids before the two
initialisation calls (`0x0032efa8` stores them right after `OSM_TaskCreate`,
before the task runs). `diff pre.json sdl.json`:
`verdict: SAME (0 difference(s))` over 31 reads. With the old order the init
subscribed task 0 (`OBJ_Event_setPrm(prm, 0x0, 0x6, 0x2)` from `0x004034c0`).

**New model:** `tickGet` (a counter), first called by SDL_task's state step
(`0x003a268c`).

## Interpretation

- **FACT:** message `0x1507` sub 1 goes to `SDL_task`, the task whose id
  `0x0032efa8` stores in `0x011fff50`; it is a notice the data-access task
  sends after the `REFER001` search data is in (`0x003f0394`), fire and
  forget (C-5900, C-5901).
- **OBSERVED:** `SDL_task` takes a message from the data-access task only
  as the answer to a request of its own (gate `0x003c009c`); with nothing
  pending it drops `0x1507` and answers nothing. The gate is the only
  dropping point: with a request pending the same message reaches the state
  machine (C-5902, C-5903).
- **FACT:** no data-access code waits for an answer to `0x1507`; the only
  writer of state 3 is `0x003f6b1c`, the handler of object-store event
  `0x07d0` sub 11, and it writes 3 only when the event's `+28` is 16
  (C-5904, C-5905). So the mount does not wait on `0x1507`: it waits on that
  event. The falsifier's first half (state 3 without a reply to `0x1507`)
  holds, and it names what the wait is on.
- **OBSERVED:** delivered as a stand-in, that event moves the run to state 3
  with progress 1, the condition under which the dispatcher runs map
  requests (`0x14b5`) at once; the two negative events do not (C-5906).
- **UNKNOWN:** who subscribes the data-access task to event sub 11, and
  which object and condition make the event carry 16. It is an
  object-store event (OBJDLL notifier, message `0x07d0`), but none of the
  92 subscriptions in `Navi.exe` names sub 11 for this task (C-5907).
  New task M9.57.

## Conclusion

The task's Done when is met by its second branch and, with a labelled
stand-in, by its first: the next message the mount waits for is named
(object-store event `0x07d0` sub 11 with `+28 = 16`; sender: OBJDLL's
notifier `0x034942d8` for a subscription not yet located; receiver: the
data-access task; answering function `0x003f6b1c`), and a `mount --sdl
--event 11:16` run ends with state 3. `0x1507` itself has no answer in this
build state: its receiver drops it, and the reply model in `datask_l3.py`
says so. `docs/format/firmware.md` ("What the run needs that the unit
provides") is updated; M9.53 can run its map request on top of
`--event 11:16`. Open: the sub-11 subscriber (M9.57).
