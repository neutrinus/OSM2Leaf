# EXP-2026-11-06-M1.2c: ROM decompressor in nk.exe (image B)

- **Status:** done (VAs/prototypes recorded, handed to M8.E1; pure-Python block
  decode of EXP-49 sections not achieved)
- **Date:** 2026-11-06
- **Sample:** `IMG256` (first 256 MiB of the EU 2011 image), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Claims:** C-660–C-669
- **Supersedes:** none
- **Superseded by:** none

## Question

Where in `nk.exe` (image B, `--image-start 0x3e00200`) is the CE
`IMAGE_SCN_COMPRESSED` (o32_flags `0x2000`) section loader/decompressor, and
what is its prototype/call target?

## Hypothesis

The kernel loader walks o32 records, tests `o32_flags & 0x2000`, and for
compressed sections calls a decompressor that understands the M1.2a/M1.2d
section framing (form 1: 22-byte header + `0x8d80805b`-marked payload; form 2:
`[u24×n][0x10,0x1000,X,0x1000]` + marker blocks) and decompresses LZXD-like
blocks to `vsize`/`ulen`.

## Method

1. `cerom.py --image-start 0x3e00200 IMG256 romhdr|modules|sections nk.exe` to
   map nk.exe; read ROMHDR copy entries (2 entries, copy+zero-fill, not
   decompression).
2. Searched nk.exe sec0 for `IMAGE_SCN_COMPRESSED` checks: literal `0x2000`
   (none in pools), `mov #0x20,r2; shll8 r2` (25 sites, 6 produce 0x2000),
   `mov.l @(5,Rm),Rn` (o32 flags at offset 0x14) near 0x2000 tests, and
   o32-walk patterns (stride 0x18, rva compare).
3. Traced `fn 0x880385e4` which loads/walks o32 records (r8, stride 24,
   compares `@(4,r8)` to section id, checks `@(20,r8)` flags). Identified the
   `flags & 0x2000` branch at `0x88038666..0x88038670` and followed the
   compressed path: calls `0x88037590(dataptr, psize, ..., vsize)`.
4. Traced the call chain: `0x88037590` (wrapper) → `0x88037464` (section
   framing, loops calling block decompressor) → `0x8803a384` (per-block LZXD-
   like). Confirmed call sites by literal-pool xref.
5. Positive controls: (a) `cerom.py comphdr NaviMapCC.dll` confirms EXP-49
   sections are form 1, ulen 0x484/0xcc0; (b) `tools/cecompress.py` LZX on the
   form-1 payload (stripped of 22-byte header) with `e8_translation=True`
   reports `UNSUPPORTED(lzx block type unknown(4))` / E8 framing detected —
   confirming the payload is LZXD-like but not the CAB-LZX variant cecompress
   implements (consistent with M1.2b); (c) `sh4xref.py`-style literal/call
   tracing reproduces the wrapper→sect caller sites.
6. Attempted `cecompress` decode of EXP-49 form-1 payloads (all methods,
   offsets 0-4, wb 15-21, e8 on/off): **0 matches** to `0x484`/`0xcc0`.

## Observations

### nk.exe (image B, 0x3e00200)
- `nummods 0x5b`, `ulCopyEntries 2` at `0x88553ac4` (file `0x4353cc4`):
  `(0x88598000→0x89e42000, 0x6790, 0x2f1e0)`, `(0x882ffb88→0x89e72000, 0x442, 0x4e4)`
  — copy+zero-fill, no decompression. nk.exe sec2 matches copy entry 0
  (psize 0x6790 < vsize 0x2f1e0, flags `0xc0000040`, no `0x2000`).
- No nk.exe section has `IMAGE_SCN_COMPRESSED`. nk.exe contains the loader that
  handles compressed sections of *other* modules.
- Marker bytes `5b 80 80 8d` (`0x8d80805b`) appear once in nk.exe sec0 at
  `0x8804d786` (align %4==2, near section end `0x8804d800`), not in any
  literal pool and with no PC-relative load — not a code-referenced constant.

### Loader path: o32_flags & 0x2000
**`fn 0x880385e4`** (sec0, `0x880385e4..~0x8803883e`, ~0x25a bytes), section
loader. Walks o32 records (`r8`, stride `add #24,r8` / 0x7818 at `0x88038660`,
loaded via `@(24,r1),r8`), compares `@(4,r8)` (o32 rva/id) to `r4`.
At the matched record:

```
0x88038666: e220        mov #32,r2        ; 0x20
0x88038668: 5385        mov.l @(20,r8),r3 ; o32_flags (offset 0x14)
0x8803866a: 4218        shll8 r2          ; r2 = 0x2000 = IMAGE_SCN_COMPRESSED
0x8803866c: 2329        and r2,r3
0x8803866e: 2338        tst r3,r3
0x88038670: 8b03        bf 0x8803867a     ; compressed -> 0x8803867a
; not compressed: return rva=@(4,r8), dataptr=@(12,r8)
0x8803867a: (compressed path) r5=@r8(vsize), call 0x88034d94 -> r9
           r7=@r8(vsize), r6=r9, r5=@(8,r8)(psize), r4=@(12,r8)(dataptr)
           call 0x88037590(r4=dataptr,r5=psize,r6,r7=vsize) at 0x88038698
```

Caller (literal-pool): load/call from `0x880388fc` (fn `0x88038870`).

### Decompressor chain

| VA | Name/role | Size~ | Prototype (OBSERVED, SH-4 r4-r7/r0) | Callers |
| --- | --- | ---: | --- | --- |
| `0x88037590` | wrapper | 0x82 | `r0 fn(r4=src, r5=psize, r6=dest, r7=vsize)` — lock/context, calls `0x88037464`, returns handle | `0x880260d2, 0x88026cdc, 0x88038694, 0x880390d2, 0x88039112` (5) |
| `0x88037464` | section framing | 0x11e | `r0 fn(r4=src, r5=psize, r6=dest_ctx, r7=vsize)` — reads src header bytes, sets up stack state (r14 frame), loops calling `0x8803a384` per block, returns decompressed size/status | `0x880375de, 0x88037bec` (2) |
| `0x8803a384` | block decompressor | 0x9c (first rts) | `r0 fn(state from 0x88037464: r4/r5/r6/r7 incl. frame ptr r14)` — per-block LZXD-like decode of `0x8d80805b` blocks | called from `0x88037464` loop (jsr @r3=`0x8803a384` at `0x88037542`) |
| `0x88034d94` | alloc/setup | 0x46 | called with vsize before wrap | from loader |

`0x88037590` passes args through: saves r4-r7 to r10,r9,r8,r11 and calls
`0x88037464(r4=src, r5=psize, r6=dest, r7=vsize)` at `0x880375de`.
`0x88037464` saves `r10=src,r11=vsize,r12=dest,r5=psize context`, parses the
stream from `r10` (reads bytes/fields, e.g. `mov.b @r10,r0` at `0x880374bc`),
builds a per-iteration state on `r14`, and calls `0x8803a384` (`mov.l @(pc),r3
[0x8803758c]=0x8803a384; jsr @r3` at `0x88037534/42`) in a `bf/s` loop back to
`0x8803751e`, returning `@(4,r14)` as the decompressed result.

`cecompress.decompress_lzx(payload, 0x484, e8_translation=True)` →

block decoder.

## Interpretation

- **FACT:** `nk.exe` sec0 (build B) tests `o32_flags & 0x2000` at `0x88038666`
  in `fn 0x880385e4` while walking o32 records (stride 24). The compressed
  branch loads `dataptr/psize/vsize` from the o32 record and calls
  `0x88037590(dataptr, psize, dest, vsize)` at `0x88038698`.
- **FACT:** the decompressor chain is `0x88037590` → `0x88037464` → `0x8803a384`
  (all nk.exe .text VAs, image B `0x3e00200`). `0x88037464` is the section-level
  framing handler that iterates blocks and calls `0x8803a384` per block
  (`0x88037542`); this matches the M1.2a/M1.2d form 1/2 framing + `0x8d80805b`
  block structure.
- **FACT (negative, with control):** cecompress LZX recognizes E8/block framing
  on the EXP-49 form-1 payloads but reports block type 4 (unsupported) and
  decodes 0/2 sections to `0x484`/`0xcc0` across all tried methods/params —
  confirming the codec is a CE LZXD variant, not the implemented CAB-LZX/LZSS/
  LZNT1/XPRESS (control: the same probe framework matched synthetic streams in
  M1.2b/M1.2d self-tests).
- **OBSERVED:** parameter roles (src/psize/dest/vsize) are derived from
  call-site register flow in `0x880385e4` and `0x88037590`; argument `r6`'s
  exact role (destination buffer pointer vs context handle set up by
  `0x88034d94`) needs confirmation under M8.E1.
- **UNKNOWN:** the exact CE LZXD bitstream/block-type-4 encoding; a
  byte-faithful pure-Python port was not completed.

## Conclusion

M1.2c done-when is met via the **VA handoff path**: decompressor VAs and
prototypes are recorded (`0x88037590` wrapper, `0x88037464` section framing,
`0x8803a384` block decompressor; loader flag check `0x88038666` in
`0x880385e4`), and the call target is handed to **M8.E1** (emulate/call
`0x88037590` or `0x88037464` in nk.exe, segment B, with
`(r4=src/psize-bytes, r5=psize, r6=dest, r7=vsize)`) to decode the two EXP-49
sections to `0x484`/`0xcc0`. `tools/cedecomp.py` records these targets and has
a synthetic self-test; it raises `UnsupportedDecompression` (naming M8.E1) for
actual decode until the block codec is ported.
