## Question

Does one KIWI string rule (name-record string length form and code set) describe
our `LCTBL001` name slots, `POINT` names and tile section-4 names, and does a
single decoder cover all three?

## Hypothesis

The KIWI 7.4 name-record rule is *length in 16-bit words × 2 bytes, payload =
raw single bytes, no code-set tag*. All three ZE0 families use the same word
count × 2 form and the same single-byte CP_ACP/CP1252 family (byte-pair byte
order on the card only changes which byte is first in a word, not the code set).
If so, one common decoder (word count × 2 → bytes → CP1252) covers all three,
and the "Polish letters" question is a code-page question, not a per-family
question. **Falsifier:** the same byte decodes to different letters in two
families, or one family uses another length form (byte count, NUL terminator,
UTF-16) or a two-byte code set. A second falsifier is a mutated mandatory check
that still passes.

### 3. Controls

- *Positive, firmware convert loop:* `lctbl_string_decode.py … --expect swap`

- *Positive, accessor:* `point_name_accessor.py run … --expect 'NATIONAL
  TRANSPORT MUSEUM'` must print `records: ok=1000 of 1000`, both internal
  negatives `0xffffffff`, and `result: PASS`.
- *Positive, byte order:* `point_byteorder_l3.py run …` must print `RESULT: PASS
  (9/9)` with the file-order leaf and the walker agreement lines.
- *Negative, intentionally wrong expectation:* `--expect none` on the same
  swapped name must print `ok: false` and exit 1; the wrong entry `0x003CA85C`
  must leave the bytes unchanged, `swap_signature: false` and exit 1; the wrong
  POI expectation must print `result: FAIL` and exit 1. These are the two
  mandatory solo-task checks: a gate that could not fail would not be a result.
- *Negative, code page:* M3.9's printed counts (`München` 234× with `0xfc`,
  `Cesk` 214 vs `Česk` 0) are the existing positive/negative control for
  transliteration; this run reprints the byte-value table only.

## Interpretation

- **FACT:** KIWI 7.4 and all three ZE0 families use a word count × 2 byte
  length for name strings; the ZE0 LCTBL slot length is a `u8` word count, the
  POINT and section-4 lengths are `u16` word counts, and KIWI's is a `u16`
  word count — same unit, different container field width.
- **FACT:** The convert loop `fn 0x003ca858` swaps each 16-bit pair of the
  LCTBL name in place; POINT names have the same byte-pair swap on the card
  (M9.26 `point_byteorder_l3.py`, 9/9). This is byte order, not a code set.
- **FACT:** At L3 the accessor returns the stored single bytes unchanged
  (1,000/1,000 records; 1000 `ok`), including non-ASCII names proved by M9.70
  (`Łódź Żabieniec.` → `a3f364bc20af616269656e6965632e`).
- **OBSERVED:** The common byte range `0xc0..0xfe` decodes identically in
  CP1252 and Latin-2 for the letters actually present in these samples
  (`ü 0xfc`, `ý 0xfd`, `ó 0xf3`, `Ö 0xd6`, `Ä 0xc4`, `Á 0xc1`, `É 0xc9`,
  `Ú 0xda`); the ambiguity is the low range `0xa1..0xbf`, where CP1252 has
  symbols and Latin-2 has Polish letters.
- **HYPOTHESIS (not confirmed):** one decoder `u16/u8 word count × 2 → raw
  bytes → CP_ACP/CP1252` covers all three families; the write rule stays
  "transliterate outside Latin-1" (M3.9). A Polish name written with Latin-2
  bytes `ą/ł/ę/ż` would be seen as `±/³/ê/¿` by a CP1252 reader, so the four
  families do *not* disagree on bytes — they disagree only if one assumes the
  wrong code page for those bytes.
- **UNKNOWN:** the display/font path above the accessor, whether section 4 is
  ever read as text by the firmware, and any real KIWI volume (M4.77).
  The 4-tile census cannot decide a code page from bytes shared by both pages.

## Conclusion

The task `Done when` is met: the family → length form → code set → sample →
same-decoder table is in this EXP, and a common decoder is proposed. The
falsifier did not fire: no letter has different bytes across families; the
only family-specific step is the card byte-pair swap (POINT) and the field
width holding the word count (u8 for LCTBL, u16 for POINT/section 4/KIWI).
The single decoder is `word_count × 2 → raw single bytes → CP_ACP/CP1252`,
with the firmware's convert loop swapping pairs first where the card layer
requires it. `docs/format/refer.md` already states the CP1252 write rule and
`docs/research/claims.md` C-1799/C-8025 already cover the byte-level
evidence; no format doc change is demanded by this task. C-7740–C-7747 record
the table, the negative mutations and the scope.
