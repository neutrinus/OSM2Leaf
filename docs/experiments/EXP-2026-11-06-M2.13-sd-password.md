# EXP-2026-11-06-M2.13: the SD unlock PIN tail is a firmware literal

- **Status:** done (static half verified); the runtime prefix and the CMD42
  byte form are a follow-up (M2.13b)
- **Date:** 2026-11-06
- **Sample:** `IMG256` (first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img`),
  SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Claims:** C-1880–C-1889
- **Supersedes:** none
- **Superseded by:** none

## Question

A unit service screen ("SD PIN", Lock & unlock SD card protection) photographed
by the owner shows `Using PIN <prefix><tail> / Unlocking. OK`, where the tail is
a 12-character alphanumeric string. Is that PIN present in the firmware, which
module holds it, and is it the CMD42 SD-lock password M2.8/M2.13 is after?

## Provenance of the plaintext (not committed)

The PIN was read off the unit's own `SD PIN` service screen (owner photo,
2026-11-06), not recovered by us. Per `AGENTS.md` "Data, license, safety", the
plaintext is treated as manufacturer data and is **not** committed: this record
keeps only offsets, VAs, a hash and the surrounding non-secret strings. The
plaintext stays with the owner / in the session that received the photo.

## Method

```bash
I=head256.img   # IMG256, verified SHA-256 above; never committed
# 1. search the displayed PIN and its two halves, ASCII and UTF-16LE
python3 - "$I"   # substring scan for the tail, the 8-digit prefix, and "Clarion"
# 2. locate the module that owns each hit
python3 tools/cerom.py --image-start 0x3e00200 $I sections PRGUpdate.exe
python3 tools/cerom.py --image-start 0x5200200 $I sections TestMode.exe
# 3. hash the 12-byte literal (identity without committing it)
```

## Observations

- The **12-byte tail** of the displayed PIN occurs as a NUL-terminated ASCII
  literal three times in `IMG256`:
  - image B, abs `0x042e5698` → **`PRGUpdate.exe` VA `0x00012498`**
    (.text `rva 0x1000`, realaddr `0x00011000`);
  - image B copy, abs `0x04ce5698` (same module in the `0xA00000` B-copy);
  - image C, abs `0x057729f8` → **`TestMode.exe` VA `0x000157f8`**.
  - SHA-256 of the 12 bytes: `249e0da5d349ebe359d7465bbbae29658482138d6b4bd0bd146475d3824f939f`
    (length 12, no trailing NUL in the hash).
- Surrounding strings (UTF-16LE) at the `PRGUpdate.exe` site:
  `… SecuritySet failed) · # NG! SecurityCheck (Flash access failed) ·`
  **[literal]** `· # SecurityCheck ProductTestData OK · PROD ·
  # NG! SecurityCheck(IOCTL_DISK_GET_INFORMATION) · CreateUpdateList! …`.
  So the literal is the value compared in a **SecurityCheck / ProductTestData**
  routine of the updater.
- The **8-digit prefix** of the displayed PIN is **not** a literal anywhere in
  `IMG256`: no ASCII or UTF-16LE match, and no `5147xxxx` ASCII run exists. The
  displayed PIN is therefore assembled at runtime from a runtime prefix plus
  the firmware tail.
- The displayed PIN is 20 characters. The SD lock password (CMD42) is at most
  16 bytes, so the 20-character string cannot be a raw CMD42 password as shown.
- **Reconciliation with C-075 (prior forum research).** C-075 (and
  `us-eu-region.md`) already stated, as HEARSAY, that the CMD42 password is
  "4 unit-specific bytes + ASCII `Clarion95321`". The displayed prefix is 8
  characters and all hex digits, i.e. **4 bytes shown as 8 hex digits**; with
  the 12-byte ASCII tail that is **4 + 12 = 16 bytes**, exactly the CMD42
  maximum. So the 20-character display is a 16-byte password: 4 unit bytes
  (hex) followed by the firmware literal. This experiment turns the
  `Clarion95321` half of C-075 from HEARSAY into a firmware-VERIFIED fact and
  confirms the overall structure.

## Interpretation

- **VERIFIED:** the 12-byte PIN tail is a hardcoded `ProductTestData` /
  `SecurityCheck` value in `PRGUpdate.exe` (VA `0x12498`) and `TestMode.exe`
  (VA `0x157f8`). It is the firmware half of the SD unlock PIN the unit
  displayed.
- **OBSERVED (behavioural):** the unit itself unlocked the card with this PIN
  (`Unlocking. OK` on the service screen), so the value is confirmed to work on
  real hardware — stronger than a static xref, which is why a code trace was
  not required to confirm the value.
- **OBSERVED:** the 8-digit prefix is runtime-generated (candidate sources: a
  unit serial, model code, or `CApi_GetModelCode`, which the updater imports —
  C-526/M2.6), not a stored constant.
- **HYPOTHESIS (strong, M2.13b):** the CMD42 password is 16 bytes = the 4
  unit-specific bytes (the 8 hex digits of the displayed prefix) + the 12-byte
  ASCII literal. This matches C-075 and the 16-byte CMD42 limit. To confirm:
  read the 4 bytes as the hex of the prefix and find how they are derived per
  unit (serial/model).
- **UNKNOWN (M2.13b):** the derivation of the 4 unit-specific bytes, and the
  exact `SDHC.dll` `SDHC_SecurityUnLock` call that assembles and consumes the
  16-byte buffer. `SDHC.dll`'s code section is `IMAGE_SCN_COMPRESSED` (M1.2),
  so a static xref waits on decompression (M1.2b/c) or L3.

## Conclusion

The SD unlock PIN the owner photographed is real and half of it is a firmware
constant in the updater and test-mode modules; the unit's own menu unlocks with
it. A cloned card's lock state can thus be set **using the unit's built-in SD
LOCK/UNLOCK menu**, without a separate CMD42 station, as long as the same card
is used in the same unit. Producing an independently locked card still needs
the runtime-prefix derivation and the CMD42 byte form (M2.13b). No plaintext,
no vendor bytes committed. Claims C-1880–C-1889 added.
