## Question

Where does the `TT LL 00 ff` name section of a 2011 ADDRE `c0` record start, what is `TT` on each
of the 33 EU2011 shards, and does `addre.parse_record` name every `c0` record once it places the
section by position instead of by `TT`?

## Hypothesis

The section starts at `4 + 2*rec[2] + 2*rec[3]` (the word counts that `route_link_join.street_name`
uses). With that rule `parse_record` names every `c0` record of every shard and no `c8` record,
whatever `TT` is; the old rule (`TT` in `0x03`/`0x04`) names exactly the records whose `TT` is
`0x03` or `0x04`.

**Falsifier** (before the results): any `c0` record without `TT LL 00 ff` at that position (the
task's `Stop`: record the shard and its first 16 bytes), any `c0` record the new parser leaves
unnamed, any `c8` record it names, or a legacy-rule count that differs from the `TT 0x03 + 0x04`
count of its shard (then the old miss was not `TT`).

## Method

1. **Sample and hash.** `cd $F/REFER001 && sha256sum ADDRE0*.DAT.cmp` (table above).
2. **Commands** (worktree root):

   ```bash
   F=/home/user/scratch/factory-eu
   python3 tools/addre.py --selftest
   python3 tools/route_link_join.py --selftest

   python3 tools/addre.py names $F/REFER001/ADDRE0*.DAT.cmp --parse

   python3 tools/addre.py names $F/REFER001/ADDRE0*.DAT.cmp --parse --legacy

   python3 tools/addre.py verify $F/REFER001/ADDRE003.DAT.cmp
   ```

   `--legacy` runs `parse_record(rec, structural=False)`, which is the pre-M4.46 function body
   (the token scan with `rec[i] in (0x03, 0x04)`). It stands in for the task's precheck on the
   pre-fix tool: the pre-fix `sections()` re-copied the rest of the file once per zlib stream and
   did not finish ADDRE001–005 within ~15 min on this shared host; the new `_zlib_at` feeds 64 KiB
   pieces and returns the same stream and end offset (`layout` output byte-identical to the pre-fix
   tool on ADDRE001/017; `verify` PASS on 001/003/017).
3. **Controls.** *Positive:* the shards C-974 already verified (001/017 `TT 0x03`, 003 `TT 0x04`)
   must keep 692/249/56,988 names under both rules. *Negative:* (a) the legacy rule on `TT 0x05`
   records must name none; (b) no `c8` record may be named; (c) self-test: a synthetic `TT 0x05`
   record whose reference block holds a `05 40 00 ff` point token (same shape as the section) is
   named at the word-count position, the point stays a point, the legacy rule misses it, its `c8`
   twin stays unnamed, and a record whose item count is off by one word places no section.
4. **Scope.** 33 EU2011 ADDRE shards, 4,610,363 `c0` + 7,424,226 `c8` records (every record
   before the first `c1`). Not covered: records after the first `c1` in the 10 shards that have
   one, US2011 shards, the 4–8-byte header between marker and name, the ADDRE writer, firmware.
5. **Falsifier.** Stated under Hypothesis.

## Interpretation

- **FACT:** in all 4,610,363 `c0` records of the 33 EU2011 shards (before the first `c1`), the
  name section `TT LL 00 ff` sits at `4 + 2*rec[2] + 2*rec[3]`; no `c8` record has one there. The
  `Stop` did not fire.
- **FACT:** `TT` takes three values, `0x03`/`0x04`/`0x05`, and is a per-record byte: 7 shards mix
  two values (e.g. ADDRE005: 456 × `0x04` in 1,421,386).
- **FACT:** the pre-M4.46 rule names exactly the `TT 0x03`/`0x04` records; it missed 3,275,685
  names (71.0 % of `c0`) across 14 shards, 9 of them entirely. Every ADDRE name census built on it
  undercounts those shards (C-5156's 18 of the first 81,313 is a prefix of ADDRE005's 456).
- **FACT:** with the positional rule `parse_record` names every `c0` record of all 33 shards and no
  `c8` record. Done-when needs ≥ 3 shards with different `TT` (e.g. 001 `0x03`, 003 `0x04`, 002
  `0x05`): met on 33.
- **HYPOTHESIS:** `TT` is the area-level count that `addre_io.name_record`
  (`tools/ze0-viewer/tools_ze0/`) writes before the level halfwords (`LL 00` being the first
  halfword, the name length in words); the mixed shards would then be records with one level
  fewer. Not tested here.

## Conclusion

`tools/addre.py` places the `c0` name section by the record's word counts (`name_section_pos`),
so the street name is read on every shard whatever `TT` is; the old token-scan rule stays
available as `parse_record(…, structural=False)` / `names --legacy`. A new `names` subcommand gives
the per-shard census, now tabulated in `docs/format/refer.md` §Address records. `_zlib_at` no
longer re-copies the file tail per stream, which makes the large shards readable in minutes.
C-5157–C-5159.
