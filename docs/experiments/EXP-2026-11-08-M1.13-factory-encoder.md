# EXP-2026-11-08-M1.13: Which deflate encoder reproduces the factory REFER001 POI pages

- **Status:** done
- **Date:** 2026-11-08
- **Sample:** US 2011 card `REFER001/POINT001.DAT` … `POINT009.DAT`, `.cmp` and `.ind` (18 files, SHA-256 in Inputs); the files were extracted from `archive/sd-images/LEAF_2011-2012_US.img` (SHA-256 `53342430a1bb58d3ed6eb68c5563f079c710a400134d522e6192489b324c5383`, as recorded in `docs/research/image-versions.md`; not recomputed here)
- **Tools:** `tools/factory_zlib.py` (this commit, `--selftest` 25 checks); `tools/mutate_refer_poi.py` (`read_ind`, `decode`, `PAGE_ALIGN`); Python 3.15.0 (`zlib` runtime `1.3.1.zlib-ng`); Python 3.13.17 (`zlib` runtime `1.3.2`, stock); gcc 16.2.1 (Red Hat 16.2.1-3); zlib releases built from the zlib.net tarballs listed in Inputs
- **Claims:** C-2570, C-2571, C-2572, C-2573, C-2574, C-2575, C-2576, C-2577, C-2578, C-2579
- **Supersedes:** none
- **Superseded by:** none

## Question

Which deflate encoder reproduces the factory inner zlib page streams of `REFER001/POINT001–009` byte for byte, so that M5.12c can test slot-fit edits against the real encoder?

## Hypothesis

The factory pages are stock zlib output at level 6, memLevel 8, default strategy (the zlib defaults), possibly from zlib 1.1.3 (the release that Navi.exe links, C-2061). The M1.13 block also records a claim that stock zlib 1.3.x at levels 1–9 is 0.8 % larger than the factory encoder; this run tests that claim too.

**Falsifier:** a page of POINT001–009 whose factory bytes are not reproduced by any release at level 6 / memLevel 8 (the hypothesis fails), or a page that reproduces only at a non-default cell while L6/m8 fails (the default-encoder hypothesis fails). A stock release at level 6 that is more than 0.8 % from the factory total on these pages falsifies the premise.

## Method

1. **Sample and hash.** The 18 files of the Inputs table, `sha256sum` of each (`cd` to the REFER001 directory, then run the hash command in Commands). Decoded through `.ind` (`read_ind`, `decode` from `tools/mutate_refer_poi.py`); a page is a zlib stream at a 0x100-aligned offset of the decoded blob (`PAGE_ALIGN`), found by its header and an end-of-stream decompress.
2. **Commands.** Runnable as written from the repo root. `$S` is an empty scratch directory.

3. **Controls.**
   - *Positive:* the ten stock releases and zlib 1.3.2 (python3.13) reproduce the factory bytes on every page (C-2570, C-2571). The tool's `--selftest` builds a synthetic `.cmp`/`.ind` pair and checks that the page is found, reproduced, and that the negative control differs (25 checks).
   - *Negative, strong:* zlib-ng (`1.3.1.zlib-ng`, the default `libz` of Python 3.15) reproduces 0 of 471 pages (C-2572); a 90-cell level × memLevel grid on page 0 leaves only L6/m8 (C-2573). These are the controls that can fail: any other cell or any other release could have matched.
   - *Negative, weak:* flipping one plain byte of page 0 in each file gives a different stream (C-2574). This is a weak control on its own, because the adler32 trailer changes with any byte; it only confirms the comparison is not vacuous.
4. **Scope.** Covered: the nine `.cmp` files of POINT001–009, 471 zlib pages found by the aligned header scan over the decoded blobs (counts per file in Observations). Every stream that decompresses to end-of-stream inside a 1 MiB window is counted; no page with a valid header was dropped. Not covered: the outer 64 KiB `.cmp` chunk streams (C-2578); POINT010 and other REFER001 shards; the EU card; the M5.12c edited pages (not in this corpus; C-2579). The `page_encoder` named in the M1.13 input does not exist (C-2576). An earlier exploratory matcher (not committed, superseded by `tools/factory_zlib.py`) gave the same result on POINT001–006 (327 of 327 pages at L6/m8 across the same releases); it is not counted separately.
5. **Falsifier.** As in Hypothesis: a page not reproduced by L6/m8 on any release, or a non-default cell that reproduces where L6/m8 does not, or a stock L6 total off the factory total by more than 0.8 %.

## Interpretation

- **Identified:** the factory inner pages are stock zlib deflate at level 6, memLevel 8, default strategy (C-2570). Ten releases (1.1.3 to 1.3.1) and zlib 1.3.2 give identical bytes on all 471 pages (C-2571), so the corpus does not name a version. zlib 1.1.3 is the release that Navi.exe links (C-2061), which is consistent with that release but is not evidence for it, since 1.2.x and 1.3.x match too.
- **Excluded:** zlib-ng (C-2572). Any POI tool run under the default Python 3.15 `libz` produces non-factory streams, so a byte-identical claim from such a run is invalid until the library is stock.
- **Premise not reproduced:** the M1.13 block says stock zlib 1.3.x at levels 1–9 is 0.8 % larger than the factory encoder on the same bytes. On these pages stock zlib 1.3.2 at L6 is exactly the factory size, L1–L5 are 2.5 % to 15.4 % larger, and L7–L9 are 0.9 % to 2.5 % smaller (C-2575). No level is uniformly 0.8 % larger, so the premise is not reproduced on this corpus. Its source is not identified; the M5.12c run that produced it is not in the repo.
- **Done when:** met. 471 pages reproduced exactly (≥ 20 required), with the negative controls above, and the candidate is named: stock zlib deflate, level 6, memLevel 8, default strategy, release-indistinguishable across 1.1.3 to 1.3.2.
- **What this does not settle:** why the five M5.12c records overflow their slot. If the factory bytes are L6/m8, a larger edited stream means the edited content grew, not that the factory encoder is smaller (C-2579, HYPOTHESIS, untested). The outer `.cmp` chunk streams are not covered (C-2578, UNKNOWN). A follow-up task should rerun the five records under stock zlib L6/m8, with the slot check, before any edit is written.
