## Question

Which concrete byte blocks make `tools/map_signals.py` report `B48R058R` as only
76 % explained, and which existing or new format task owns each of the largest
five?

## Hypothesis

The unexplained bytes are a few large zlib-stream blocks belonging to wide
directory rows (section 1, level 1, kinds `0x2146`–`0x2946`) that the simpler
`clarion_tile` reader does not step over, not a uniform scatter of padding.
**Falsifier:** the unexplained bytes are spread roughly evenly over many small
padding gaps (no gap is more than a few times the median), in which case the
ranking has no actionable top block and this is reported honestly.

## Method

A **spec**, not a narrative.

1. **Sample and hash.** The single file above, full length; hash quoted from
   `sha256sum /home/marek/projekty/leafre-work/m5.4/card-factory/MAPAL001/B48R058R.DAT`.
   The 76.29 % is the lowest of the three tiles on the same command line.
2. **Commands.** Runnable as written:

   ```bash
   python3 tools/map_signals.py --factory-root /home/marek/projekty/leafre-work/m5.4/card-factory tile_bytes
   python3 tools/tile_unknown.py /home/marek/projekty/leafre-work/m5.4/card-factory/MAPAL001/B48R058R.DAT --top 12
   python3 tools/tile_unknown.py --factory-root /home/marek/projekty/leafre-work/m5.4/card-factory --top 12
   python3 tools/tile_unknown.py --selftest
   ```

   `tile_unknown.py --factory-root` selects the lowest-percentage tile using
   `map_signals.TILE_NAMES` and `map_signals.tile_explained_percent`, so the
   target is selected by a stable rule, not typed by hand.
3. **Controls.** *Positive*: a known-explained range (a directory span read from
   the same tile model) must be covered by an explained interval and appear in
   no gap; the synthetic tile from `tilewriter.make_factory` must have no gap
   above a few dozen bytes. *Negative*: a synthetic tile with one injected
   run of 4,096 nonzero bytes (`0xa5`) in the trailing free region must rank
   that run first, ahead of the two small pre-existing synthetic gaps. Both
   controls live in `tools/tile_unknown.py --selftest` and pass (10 checks,
   0 failures).
4. **Scope.** One tile (`B48R058R`, 289,319,168 B, 286,441,973 nonzero bytes
   past `0x1000`); baseline explained spans are the union of directory
   ``(off, end)`` and slot ``(block_off, block_end)`` intervals from
   `clarion_tile.read_tile`. A second pass adds 2,176 `s1_wide_dir` row-block
   spans to measure how much of the "unexplained" total is already modelled.
   Nothing is inferred about other tiles or other card years.
5. **Falsifier.** A gap-size distribution with no dominant block (max gap ≲ 3×
   the median nonzero gap) would refute the "one large block" hypothesis.

## Plan

Written before the tool was coded:

1. Reuse the exact union-of-spans arithmetic of `map_signals.tile_explained_percent`
   so the headline percentage is not redefined (directory `(off,end)` + slot
   `(block_off,block_end)`, nonzero bytes only, tail past `0x1000`).
2. Enumerate maximal nonzero runs in the complement of those spans; attribute
   each run to a directory (section, level, kind) and to an even/odd record
   using the wide-row record parts where available, else the slot parity.
3. Add a second pass with `s1_wide_dir` row blocks to separate "already modelled
   wide-row sub-records" from "genuinely unexplained"; report both totals.
4. Describe each top block's first bytes by shape (zlib signature, inflated
   length, first big-endian `u16` words) without dumping vendor bytes.
5. Group by `(section, level, directory kind, even/odd)`, sort by nonzero byte
   count, print the ranked table; add `--selftest` with the two controls above
   and register the claim rows.

## Interpretation

- **FACT:** the baseline 76.286 % is the same arithmetic as `map_signals`; the
  unexplained 67,928,024 B is in 71 nonzero ranges, not in padding dust.
- **FACT:** adding the 2,176 `s1_wide_dir` row blocks moves the figure to
  99.872 %; the top eight groups are already-modelled section-1 wide rows
  (inflated records start with a parcel code and `0x00fa`).
- **OBSERVED:** the residual 366,814 B / 36 ranges is all section 4 level 1,
  kinds `0x1146`–`0x1946`, record kind `0x0009`, with the same zlib+parcel-code
  shape — the `0x1046`-based wide-row family the M5.53/M5.54 model does not cover.
- **HYPOTHESIS:** section 4 uses the row grammar of `s1_wide_dir` with a
  different narrow base (`0x1046`); extending the model would explain the
  residual, but this has not been tested here.
- **UNKNOWN:** whether the section-4 rows carry sub-records as section 1 does;
  no firmware reader VA is claimed here (rule 13).

The falsifier is not triggered: the largest group (15,290,889 B) is > 13× the
largest residual gap (48,647 B), so there is an actionable top block. The
hypothesis is partially confirmed and corrected: the top blocks are modelled,
and the genuinely unexplained block is a *different* (section-4) wide-row
family.

## Conclusion

`tools/tile_unknown.py` (new, `--selftest`-covered) ranks the unexplained byte
ranges of the lowest-scoring sample tile by `(section, level, kind, even/odd)`
and describes their first bytes without dumping them. The 76.29 % headline is a
reader-model artifact: with `s1_wide_dir` row blocks the same tile is 99.872 %
explained. Ten claim rows C-7870–C-7879 record the numbers. A new task M4.93
owns the remaining 366,814 B of section-4 wide rows. Nothing in `docs/format/`
changed here: these are known-format records, not a new format claim.

## Corrections after navigator review (self-review, solo mode)

1. The first exploratory grouping used the 0-based index into
   `tile["sections"]` and printed the residual as "sec2"; the committed tool
   uses `section["id"]`, so the residual is correctly section **4** everywhere
   in this record and in the claim rows.
2. The first parity attribution used only the record at each gap's start,
   which labelled every multi-megabyte block `even` by accident. The tool now
   votes parity by the bytes of every wide-row record overlapped by the gap;
   ranks 9 and 12 became `even` and rank 11 `odd` after the fix.
3. The shape routine first described the leading zero pad of a gap
   (the negative control showed `w=[0x0000,…]`); it now skips to the first
   nonzero byte, so the injected `0xa5` block is named `0xa5a5` and the real
   zlib streams are recognised.
4. An unused `wide_ranges` set was removed from `analyze()`.
