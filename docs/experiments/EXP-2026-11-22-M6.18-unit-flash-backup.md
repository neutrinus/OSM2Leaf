# EXP-2026-11-22-M6.18: LeafSDTools backup of Marek's unit (flash, SRAM, VFlash, PROD)

- **Status:** done
- **Date:** 2026-11-22 (files written by the unit; its clock stamps them
  2009-07-10, so the day of the dump is not in the files)
- **Sample:** four dump files and one log written by LeafSDTools on Marek's US
  LEAF 2011–2012 head unit (`QY7200ND`, Product ID `10 20 02 12`); SHA-256 in
  Observations. The files are **not in the repository** and never will be:
  they hold the SD PIN, the unit serial, a phone book and stored destinations.
- **Tools:** LeafSDTools on the unit (version not printed in the log;
  `111-beta` on the 2026-11-05 photo); `sha256sum` (coreutils), `python3`
  3.14.10 on the host
- **Claims:** C-5203–C-5206
- **Supersedes:** none (completes EXP-2026-11-20-M6.18-prod-screen, which had
  the photo only)
- **Superseded by:** none

## Question

Do the backup files of M6.18 exist with the expected sizes, and are they one
consistent copy of the flash?

## Hypothesis

`nand_*.bin` is the whole 8 MiB of `FMD1:`; `sram_*.bin` and `vflash_*.bin`
are blocks `0x47..0x56` and `0x57..0x84` of the same flash (C-5193);
`prod_*.bin` is the first `0x2D2` bytes of block 5.

Falsifier: a size other than 8,388,608 / 1,048,576 / 3,014,656 B, or a
partial file that differs from the same range of the full dump.

| Item | Value |
| --- | --- |
| Files | `nand_10200212_<serial>.bin`, `sram_…`, `vflash_…`, `prod_…`, `leafsdtools.log` (the name carries Product ID and the 8-digit serial; the serial is not recorded here) |
| Where | outside Git (`.gitignore`: `/MarekDumpSD/`, `nand_*.bin`, `sram_*.bin`, `vflash_*.bin`, `prod_*.bin`) |
| Block map | C-5193: blocks 0–7 of 8 KiB, then 64 KiB; block `n ≥ 8` at `(n−7)×0x10000` |

## Method

1. **Sample and hash.** The five files as copied from the card; hashes below.
2. **Commands.** `D` is the directory with the files.

   ```bash
   cd "$D" && ls -l && sha256sum nand_*.bin sram_*.bin vflash_*.bin prod_*.bin leafsdtools.log
   python3 -I - "$D" <<'PY'
   import glob, sys
   d = sys.argv[1]
   one = lambda p: open(glob.glob(d + "/" + p)[0], "rb").read()
   n, s, v, p = one("nand_*.bin"), one("sram_*.bin"), one("vflash_*.bin"), one("prod_*.bin")
   print("sram   == nand[0x400000:0x500000]", s == n[0x400000:0x500000])
   print("vflash == nand[0x500000:0x7e0000]", v == n[0x500000:0x7e0000])
   print("prod   == nand[0x00a000:0x00a2d2]", p == n[0xa000:0xa2d2])
   print("prod sum", hex(sum(p[:0x2d0]) & 0xffff), "stored", hex(p[0x2d0] | p[0x2d1] << 8))
   print("shifted control", s == n[0x400001:0x500001])
   PY
   ```
3. **Controls.** Positive: `PROD` is at `0xA000` of the full dump and the
   Product ID at `+0x20` equals the photo of EXP-2026-11-20-M6.18-prod-screen.
   Negative: the same comparison shifted by one byte must be `False`.
4. **Scope.** 5 files, 12,454,426 B. The content is mapped in M6.19, not here.
5. **Falsifier.** As in Hypothesis.

## Interpretation

- **OBSERVED (C-5203):** the backup exists: full flash 8,388,608 B, SRAM
  1,048,576 B, VFlash 3,014,656 B, PROD 722 B, with the hashes above. The
  tool skipped nothing: the full dump is exactly 8 MiB.
- **VERIFIED (C-5204):** the three partial files are byte-identical to
  `0x400000–0x4FFFFF`, `0x500000–0x7DFFFF` and `0xA000–0xA2D1` of the full
  dump, so the block map of C-5193 holds on a real unit and one file
  (`nand`) is enough for analysis.
- **VERIFIED (C-5205):** the PROD checksum is the 16-bit sum of bytes
  `+0x000..+0x2CF`, stored little-endian at `+0x2D0` (`0x9CBE` here).
- **OBSERVED (C-5206):** the photo values of C-5200/C-5202 are in the dump
  at the stated offsets (Product ID, model, IMMO code, IMMO flag).
