## Question

Why do people get Android Auto on AZE0 Nissan Leaf head units and not on ZE0
units: which capability does the ZE0 lack, and is the AZE0 solution native
firmware or an external box?

## Hypothesis

Marek's: the phone stream is H.264 and needs a hardware video decoder; AZE0
has one and ZE0 does not. Alternatives to test: USB host/AOA support, CPU
headroom for 800x480 software decode, Wi-Fi, CE version/codec libraries, and
the projection-like modules on X212 (`UsbConMngCC.dll`, `Celavi*`, `Telema*`,
DirectDraw). Falsifier from the task: an H.264 decoder module or VPU driver in
the ZE0 2011 ROMs too (then the decoder is not the reason). For the public
source part, the Stop clause: if the AZE0 solution is an external box (video
on a separate input), record that and stop the codec search.

## Method

1. **Sample and hash.** The four image heads above; hashes printed by
   `sha256sum archive/*.img` and by `aa_probe.py --json` (`sha256` field). The
   public URLs were opened 2026-11-24 and recorded in
   `docs/research/sources.md`.
2. **Commands.** Runnable from the repository root:
   ```bash
   python3 tools/aa_probe.py --selftest
   python3 tools/aa_probe.py --out ~/projekty/leafre-work/scratch/m8.g3-android-auto/aa_probe.json \
       archive/head256.img archive/us256.img archive/eu2014-256.img archive/eu2016-256.img
   python3 tools/aa_probe.py --image archive/eu2014-256.img --build A --json
   python3 tools/aa_probe.py --image archive/head256.img --build A --json
   # attribution of a single needle (no hit in any image):
   python3 tools/ce_strfind.py archive/eu2014-256.img --image-start 0x200200 \
       --encoding all --json 'Android Auto' 'CarPlay' 'AOAP' 'DirectShow' \
       'OpenMAX' 'IH264D' 'VideoDecoder' 'UsbConMngCC' 'USB Disk' 'EHCI' 'h264'
   # module census and exports:
   python3 tools/cerom.py --image-start 0x200200 archive/eu2014-256.img modules
   python3 tools/cerom.py --image-start 0x200200 archive/eu2014-256.img exports Celavidll.dll
   python3 tools/cerom.py --image-start 0x200200 archive/eu2014-256.img exports AvCCWrapper.dll
   sha256sum archive/head256.img archive/us256.img archive/eu2014-256.img archive/eu2016-256.img
   strings -a -t x archive/eu2014-256.img | grep -iE 'ECNI|NBNI|JANI'
   ```
   The search uses `ce_strfind.scan_image()`: it walks the CE ROM TOC and
   decompresses compressed sections before searching, so a name stored in
   compressed data is still found. A section the codec cannot handle is
   reported as `UNSUPPORTED`, never silently skipped. `aa_probe.py` records
   per-needle hit counts, hit modules, a module-name census and a summary
   matrix for all 12 (image, build) segments.
3. **Controls.** Positive: `gwes.exe` must be found in every real segment
   (`ctrl +2..+8` on all 12); the synthetic ROM in `--selftest` uses the export
   name `MAL_DataVol_getOffset`, also found. Negative: a 49-byte string that
   cannot exist in a Leaf ROM (`THIS_STRING_CANNOT_EXIST_IN_A_LEAF_ROM_7f3a9b21`)
   returns 0 hits in all 12 segments and in the synthetic ROM. The
   `--selftest` prints 4/4 OK. An earlier, broader needle set (`VPU`, `AVC`,
   `projection`, `celt_decoder`) produced false positives from random bytes
   (`RGVPUJ`, `NAVConv`) and speech-library text; it was replaced with the
   definitive markers above and that rejection is recorded here so the counts
   are not mistaken for the first scan's.
4. **Scope.** 4 images x 3 CE segments = 12 segments. Module census: build A
   149/151/153/153 modules, B 91/91/95/96, C 88/88/92/92 (printed by
   `cerom.py … modules | wc -l`). Needles searched in all sections of all
   modules, including decoded compressed sections; the sections reported
   `UNSUPPORTED` (e.g. `AVSettingCC.dll sec1/sec2`, `AppLaunch.dll sec1/sec2`)
   are LZX verbatim blocks the pure-Python decoder refuses, so a marker stored
   only there would be missed. No L4/L5 run, no unit, no new card, no vendor
   bytes committed. The public sources are secondary (HYPOTHESIS), not proof
   of firmware facts.
5. **Falsifier.** An H.264 decoder module / VPU driver in the ZE0 2011 ROMs as
   well would refute the "decoder is what ZE0 lacks" hypothesis. For the
   public-source branch, any credible report that the AZE0 solution is a
   video-over-separate-input box would remove the need for a codec search.

## Interpretation

- **FACT:** no H.264/AVC/VPU/DirectShow/Android Auto/CarPlay/AOA marker was
  found in any of the 12 scanned segments, ZE0 **or** AZE0. The task's
  falsifier is **met**: the decoder is not something AZE0 has and ZE0 lacks.
  Marek's hardware-decoder hypothesis is **refuted as stated**.
- **FACT:** the AZE0 images add USB mass-storage support (`UsbConMngCC.dll`,
  `usbdisk6.dll`/`usbmsc.dll`, `USB Disk`) and DirectDraw; ZE0 has only OHCI
  with HID/mass-storage clients listed in `head-unit.md`. USB host *mode*
  exists in both; Android Open Accessory protocol support appears in neither.
- **OBSERVED:** AZE0 adds `Celavi*`, enlarged `Audio.exe` and three `Telema*`
  modules, and drops `Bolero`. These are media/telematics libraries; their
  exported names show no video decode path. `AvCCWrapper.dll` is identical in
  both generations and is an IPC wrapper, not a codec.
- **HYPOTHESIS (community, not reproduced by us):** the AA capability lives in
  a later hardware generation (QY8xxx / NissanConnect), whose firmware can be
  modified to enable AA/CarPlay; ZE0/QY7xxx units get only SD-card
  translation/radio modifications. This is consistent with 0 AA strings in
  all four CE image sets we hold and with the absence of an OEM-screen video
  input solution in the public sources.
- **UNKNOWN:** CPU clock and therefore software-decode headroom is not
  printed by any command used here (only a 42 MHz TMU Pphi is documented in
  `docs/format/firmware.md`); no AOA stack exists in any image; Wi-Fi is
  absent from all four images (C-6947). Whether a QY8xxx firmware could be
  ported to X212 CE hardware is a public-source claim, not an L3/L4 result.
- **Answer to "what does the ZE0 lack":** based on evidence we can reproduce,
  the ZE0 lacks the *software stack* for phone projection (AA/AOA/DirectShow
  UI and mass-storage/USB-connection manager) and the later QY8xxx hardware
  generation that community sources associate with AA/CarPlay. It does not
  lack a hardware H.264 decoder that AZE0 has — neither generation has one in
  firmware. Stop clause: the AZE0 solution is **firmware/SD-card software**,
  not an external box; the codec search was completed anyway and was negative.

## Conclusion

`tools/aa_probe.py` is added with a synthetic-ROM selftest; the 12-segment
needle census and public URLs are recorded. Claims C-6960–C-6969 capture the
verdicts. No H.264 decoder/VPU or AA/AOA/DirectShow stack exists in any held
image, and the only AA-capable hardware named by public sources is the later
QY8xxx generation (not the QY7xxx/ZE0 or the X212/AZE0 images we hold).
Open: a QY8xxx card image (or an AA-enabled modified X212 firmware) would be
needed to see what the AA software actually adds; no such image is held, so
the "QY8xxx hardware" part remains a community hypothesis.
