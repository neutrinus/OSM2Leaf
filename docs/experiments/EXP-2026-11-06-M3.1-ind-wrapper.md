## Question

## Interpretation

- **OBSERVED (C-820):** Navi.exe `fn 0x00377870` (VA `0x00377870`, uncompressed `.text`, ~0xf6 bytes to delay slot) encloses MAL call sites `0x003778b2` (`MAL_DataVol_getOffset`) and `0x003778bc` (`MAL_DataVol_getSize`). It iterates data-volume ids `{3,4,7,8}` (stack table at `r15+0x1c`), calling `getOffset/getSize(id, &u16_out)` to `r15+0x14/0x16`, zero-extends and `*2`-scales the 16-bit offset/size, and `memcmp`s `arg1_base + off*2` vs `arg2_base + off*2` for `size*2` bytes; returns status `0x03f1` (no match) / `0x03f7` (match) in `r0` and stores it in `arg0(r4)+0x8/+0xc`. Signature observed: `(r4=ctx, r5=baseA, r6=baseB) -> r0 status`.
- **OBSERVED (C-821):** Navi.exe `fn 0x00377ae0` (VA `0x00377ae0`, frame ~0x1c8) encloses MAL call sites `0x00377b46`/`0x00377b52`. It calls `OBJ_DriveInfo_readDataVol` into mapped buffer `r11=[0x00377dbc]=0x01205040` (0x1000 bytes zeroed), then `getOffset/getSize(r4=7, &u16)` for **volume 7**, and `memcpy(r15+0x30, 0x01205040 + offset*2, size*2)`. It proceeds through version/disc checks (`SYS_CdVerCmp`, `OBJ_DiscInfo_*`, new-disc init) and conditionally calls `sub_00377870`. Signature observed: `(r4=ctx/status@r8) -> r0=*r8`.
- **OBSERVED (C-822):** `MAL_DataVol_getOffset/getSize` are invoked as `fn(vol_id_or_type, u16 *out)` (SH-4: `r4`=id, `r5`=pointer; delay-slot sets `r4`). Volume 7 is queried explicitly in `0x00377ae0`; volumes 3,4,7,8 are probed in `0x00377870`. The returned 16-bit values are consumed as offset/size with `*2` word scaling relative to base `0x01205040` (memcpy src `base + off*2`, len `size*2`) and as scaled compare windows in `memcmp`.
- **OBSERVED (C-823):** Callers of `fn 0x00377870`: exactly `fn 0x00377ae0` at `0x00377ce4` (literal pool `0x00377e54`, `sh4xref --to` + `--calls` agree). Callers of `fn 0x00377ae0`: **none found** in uncompressed executable sections (no `bsr`/`bra`, no literal-pool 4-byte ref, no LE `0x00377ae0` in full IMG256); `.rdata`/`.data` are compressed, so a caller via compressed data tables remains possible but unverified.
- **OBSERVED (C-824):** `OBJDLL.dll` (image A, module 59, `vbase 0x03480000`) exports 6 `MAL_*` symbols: `MAL_DataVolType_show(#1,0x18e7c)`, `MAL_DataVol_getAreaRect(#2,0x18d68)`, `MAL_DataVol_getOffset(#3,0x18d48)`, `MAL_DataVol_getSize(#4,0x18d28)`, `MAL_DataVol_show(#5,0x19110)`, `MAL_FileType_show(#6,0x18fd8)`. Navi.exe imports only `getOffset`/`getSize` among `MAL_*` (slots `0x55d390`/`0x55d38c`). Thunks `0x003d1bb0`/`0x003d1ba4` confirmed.
- **OBSERVED (C-825):** `fn 0x00377ae0` loads data volume content via `OBJ_DriveInfo_readDataVol` into `0x01205040` (fixed/constant base from literal `0x01205040` at pool `0x00377dbc`) before using `MAL_DataVol` offset/size to `memcpy` a subrange — tying `MAL_DataVol_getOffset/getSize` to that mapped data-volume buffer (volume 7).
- **OBSERVED (C-826):** `fn 0x00377870` is a content-fingerprint matcher over volume ids `{3,4,7,8}` (not a single-volume accessor): it selects/matches by comparing buffer windows at `MAL_DataVol`-reported (offset,size) against two supplied bases, yielding status `0x03f1`/`0x03f7`.
- **HYPOTHESIS (C-827):** The `*2` scaling of the 16-bit offset/size suggests word-element units or a 2-byte stride in the mapped volume/index; confirming the unit requires resolving `MAL_DataVol_*` in `OBJDLL.dll` or the buffer element type (deferred, M3.2/OBJDLL read).
- **HYPOTHESIS (C-828):** `fn 0x00377ae0` is a disc/data-volume validation & installation/update routine (DiscInfo read/write/refuse/judge, `SYS_CdVerCmp`, `initNewDisc*`, `SYS_Timer_setMsg`), with volume-7 index data copied as an input; its caller is likely reached through a compressed dispatch/vtable (unresolved here).
- **UNKNOWN (C-829):** Exact byte layout of the `u16` written by `getOffset`/`getSize` beyond "16-bit word read via `mov.w @(disp,r15),r0`" (endianness/semantics in OBJDLL), the full higher-level meaning of base `0x01205040` and volume-id set `{3,4,7,8}`, and `fn 0x00377ae0`'s caller.
