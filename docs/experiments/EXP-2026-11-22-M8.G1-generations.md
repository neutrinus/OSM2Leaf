## Question

How do the head units of the three Leaf generations differ in hardware, using
only static evidence from the card images we hold, and which differences matter
for emulation?

## Hypothesis and falsifier

Expected: ZE0 (`X210`, EU/US 2011) and AZE0 (`X212`, EU 2014/2016) are distinct
board generations — the M1.36 census already shows different kernel builds,
`FlashManager2` and `fmmdrv_05`/`_07` on X212 — while no ZE1 (Leaf 2, 2018+)
image is held, so that column is `unknown` except where the 2019 QY8x e-NV200
image could be inspected as a non-Leaf, post-2016 data point.

**Falsifier:** if the EU 2014 kernel ROM names the **same BSP string and RAM
window** as EU 2011 (and the module/flash differences are only added drivers),
then AZE0 is a board revision of the same platform, not a new platform; the
table and interpretation must say so. The second falsifier is architectural:
if the 2019 image is not Windows CE on SH-4, its column stops at the recorded
architecture and no CE/SH-4 facts are asserted for it.

## Plan

Approach: one column per generation, with the QY8x 2019 image inspected only to
decide its architecture and to say why it is not a Leaf 2. No card is opened or
changed; only read-only ranged reads of vendor images. Facts come from commands
that print them, as follows.

| Table row | Command that produces the evidence | Where the number/string appears |
| --- | --- | --- |
| OS / ROMHDR / RAM windows | `python3 tools/cerom.py --image-start 0x3e00200 IMG romhdr` (and `0x200200` for A) | ROMHDR `nummods`, `cpu`, `physfirst`/`physlast`, RAM window, kernel build string |
| Module inventory (flash driver, USB, BT, audio, camera, telematics, display, CAN) | `python3 tools/cerom.py IMG modules`, confirmed with `tools/rom_atlas.py atlas` | module names per build A/B/C, e.g. `fmmdrv.dll` vs `fmmdrv_05.dll`, `FlashManager2.dll`, `UsbConMngCC.dll` |
| Platform / BSP / header strings | `strings -a -el IMG \| grep -iE 'R0P7772\|X210\|X212\|SH7772\|CETUS\|Windows CE'`, plus `strings -a -t x IMG \| grep ECNI` | UTF-16LE BSP/platform strings, header string at file `0x200015`/`0x200014` |
| Register / driver evidence (OHCI, SCI, SSI, I2C) | `python3 tools/sh4xref.py IMG MODULE --image-start 0x3e00200 --to VA` and `docs/hardware/head-unit.md` (read-only) | literal-pool loads, device bases |
| 2019 architecture | `curl -r 0-268435455` head + `python3 tools/cerom.py --image-start 0x3e00200 HEAD romhdr`; `strings -a HEAD \| grep -iE 'Linux\|Android\|ECEC\|Windows CE\|SH-4'` | ROMHDR present or absent, kernel magic strings |
| Wi-Fi | `strings -a -el IMG \| grep -iE 'wifi\|wlan\|802\.11\|wpa_supplicant'` and a full module-name scan | module/string or absence → `unknown` |

Intended Done when: `docs/hardware/generations.md` has one column per generation
(ZE0 / AZE0 / ZE1-or-QY8x), every cell carries evidence (string, module, VA) or
`unknown`, and this EXP lists the three emulation-relevant differences. The

### 3. Controls

- **Positive control:** `python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img romhdr`
  printed `usCPUType 0x000001a6`, `physfirst 0x88000000`, `physlast 0x886e18a4`
  — the SH-4 CE kernel ROMHDR pinned in AGENTS.md.
- **Negative control:** `python3 tools/cerom.py --image-start 0x12345000 archive/head256.img romhdr`
  produced `struct.error: unpack_from requires a buffer of at least 305418316 bytes
  for unpacking 12 bytes at offset 305418304` and **no ROMHDR**. The reader is a
  real test of the image start.
- **Falsifier control:** EU 2014 build-B `R0P7772A00020S` / `CETUS_SH4` versus
  EU 2011, and `ulRAMStart 0x8a640000` versus `0x89e40000`.

### 4. Scope

Static only. Four CE firmware heads (first 256 MiB of EU2011, US2011, EU2014,
EU2016 cards) plus one failed ranged GET of the 2019 QY8x head. Builds A
(`0x200200`), B (`0x3e00200`) and C (`0x5200200`) are covered for module names;
ROMHDR/RAM windows come from A and B. The EU2011 `default.hv` registry decoded
(126,976 B, 516 keys, 1,149 values); the 2014/2016 hives did not decode
(`nk_decomp.py files`: `FAIL … UnmappedAccess: no mapped region covers
0x00000000..0x00000002`), so X212 registry-only facts are `unknown`. Modulo that
limit, uncompressed sections of the heads were scanned; compressed `.data` was
not decoded. Excluded: card modification, FAT/map data beyond the firmware
head, hardware probing, and any asserted ZE1 fact.

### 5. Falsifier

Stated above: (a) EU2014 same BSP string and RAM window as EU2011 ⇒ AZE0 is a
board revision; (b) 2019 image not CE/SH-4 ⇒ record its architecture and stop
that column. A negative control that wrongly succeeds also voids the study.

## Interpretation

- **FACT (C-6940):** all four images are Windows CE 5.0 / SH-4 CE ROMs with the
  same CPU type `0x01a6`, the same BSP string `R0P7772A00020S` and platform name
  `CETUS_SH4`, and the same CE segment layout A/B/C.
- **FACT (C-6941):** the header string marks the generation: `FX210…`/`X210…`
  for ZE0 versus `X212…` for AZE0.
- **FACT (C-6942):** AZE0's ROMHDR RAM window starts 8 MiB higher
  (`0x89e40000` → `0x8a640000`) while the 102 MiB DRAM ceiling stays at
  `0x8e600000`; the CE window shrinks from 71.75 to 63.75 MiB. **The task's
  falsifier is not met as a whole**: the BSP string is identical but the RAM
  window is not, so AZE0 is a revision inside the CETUS BSP family with a
  shifted memory map, not the same board plus only added drivers.
- **FACT (C-6943):** the flash driver set changes in X212: `FlashManager2.dll`
  appears in build B and `fmmdrv_05.dll`/`fmmdrv_07.dll` replace `fmmdrv.dll`
  from 2014 C / 2016 B onward. The exact NOR/NAND geometry of X212 is
  **UNKNOWN** because its registry hive could not be decoded here.
- **FACT (C-6944):** the graphics path changes: kernel B of X212 adds
  `ddraw.dll`/`ddcore.dll`/`ddhel.dll` and drops `Bolero.dll`; `ddddifull.dll`
  stays. Resolution of X212 is **UNKNOWN** from the heads.
- **OBSERVED (C-6945):** USB and telematics gain modules on X212
  (`UsbConMngCC.dll`, `usbdisk6.dll`/`usbmsc.dll`, three new `Telema*`, `USB
  Disk` string), but the host controller is still OHCI — no EHCI module.
- **OBSERVED (C-6946):** `CAN.dll` and `VIN.dll` exist in both generations;
  ZE0's `CAN.dll` opens `UAT3:`, while no CAN port string survives in the
  uncompressed X212 sections, so the AZE0 CAN link is **UNKNOWN**, not proven
  unchanged.
- **OBSERVED (C-6947):** no Wi-Fi driver or Wi-Fi string was found in any of
  the four images; absence of evidence is not proof of absent hardware, so the
  cell is `unknown`.
- **UNKNOWN (C-6948):** all ZE1 facts. The only post-2016 image named in the
  task is a QY8x e-NV200 (C-123/C-1028, a different engine family) and is no
  longer hosted; no ZE1 card image is held. What is needed: the first ~256 MiB
  of a 2018+ Leaf 2 / ZE1 navigation SD card.
- **FACT (C-6949):** the negative control failed as required, so the ROMHDR-
  derived numbers are a property of the image start, not of the tool alone.

## Three differences that matter most for emulation

1. **RAM map shift (C-6942).** AZE0 moves `ulRAMStart` up by exactly 8 MiB
   (`0x89e40000` → `0x8a640000`), leaving 63.75 MiB of CE RAM instead of
   71.75 MiB under the same 102 MiB ceiling. A `-M aze0` machine must place the
   CE RAM/object store and the fixed driver-buffer region 8 MiB higher; today's
   `-M ze0` memory map cannot be reused unchanged.
2. **Flash subsystem (C-6943).** `FlashManager2.dll` and the `fmmdrv_05`/`_07`
   variants replace the single `fmmdrv.dll`; the firmware expects different
   flash hardware or geometry. Boot/storage emulation needs a different FMD
   binding and a flash model for X212, and the exact device is still unknown
   because the X212 registry will not decode with the current tools.
3. **Graphics/media path (C-6944).** X212 kernel B adds DirectDraw
   (`ddraw.dll`/`ddcore.dll`/`ddhel.dll`) and drops the ZE0 `Bolero.dll`, while
   A adds `Celavi*` — the display and media-decoder devices a full-system
   emulator must provide differ, even though `ddddifull.dll` remains.

Runner-up (not top three): the X212 USB mass-storage and telematics additions
(C-6945).

## Conclusion

`docs/hardware/generations.md` now carries the per-generation table: 12 rows
(`awk '/^\| \*\*/{n++} END{print n}' docs/hardware/generations.md` → 12), three
columns, every cell with a quoted string, module, VA or `unknown`. The
three emulation-relevant differences are the 8 MiB RAM-window shift, the new
flash-driver set, and the DirectDraw/Bolero→Celavi graphics change. The
falsifier was evaluated and **not met as a whole** (same BSP name, different
RAM window and header string), so AZE0 is a BSP-family revision with a shifted
memory map. No ZE1 architecture is asserted: no ZE1 image is held and the
named 2019 QY8x image is a different engine family and no longer downloadable.
