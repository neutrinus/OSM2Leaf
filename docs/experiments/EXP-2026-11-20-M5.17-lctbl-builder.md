## Question

Can every byte of `LCTBL001.DAT` outside the record payload be derived from
the records themselves, so that a builder writes a complete file for a new
(Polish) name set, and does the firmware's record walk read that file?

## Hypothesis

The file is a paged database whose catalog, index and page tables are
functions of the record set (table code, location code per record, record
bytes). Falsifier, stated before the run: a builder that regenerates every
non-record byte from that model does **not** rebuild the EU and US files
byte for byte (any differing byte refutes the model); or the firmware field
walk `fn 0x003f61bc` (EU2011 build A `Navi.exe`), fed the catalog descriptor
and the records of a generated file, returns a field offset or length that
differs from the model.

## Method

1. **Sample and hash** — above.
2. **Commands** (`S` is a scratch directory outside the repo, `R` the EU tree):

```bash

L=$R/RDSTM001/LCTBL001.DAT
python3 tools/lctbl_build.py --selftest
python3 tools/lctbl_build.py extract archive/sd-images/LEAF_2011-2012_US.img -o $S/US_LCTBL001.DAT

python3 tools/lctbl_build.py rebuild $S/US_LCTBL001.DAT

python3 tools/lctbl_build.py check $S/US_LCTBL001.DAT
python3 tools/lctbl_build.py example-spec -o $S/pl-spec.json
python3 tools/lctbl_build.py synth $S/pl-spec.json -o $S/LCTBL001-synth.DAT
python3 tools/lctbl_build.py synth $S/pl-spec.json -o $S/LCTBL001-synth2.DAT --header-from $L
cmp $S/LCTBL001-synth.DAT $S/LCTBL001-synth2.DAT
python3 tools/lctbl_build.py rebuild $S/LCTBL001-synth.DAT
python3 tools/lctbl_build.py check -v $S/LCTBL001-synth.DAT
# L1 / L2 on a card tree carrying the file (symlinks to the EU tree, DRSTR rebuilt)
python3 tools/lctbl_build.py tree $R $S/LCTBL001-synth.DAT -o $S/tree-synth
python3 tools/lctbl_build.py tree $R $S/LCTBL001-rebuilt.DAT -o $S/tree-rebuilt
python3 tools/cardcheck.py --root $S/tree-synth --fast
python3 tools/cardcheck.py --root $S/tree-rebuilt --fast
cp -as $S/tree-synth $S/tree-neg && rm $S/tree-neg/DRSTR001.DAT && ln -s $R/DRSTR001.DAT $S/tree-neg/DRSTR001.DAT
python3 tools/cardcheck.py --root $S/tree-neg --fast
python3 tools/l2check.py --root $S/tree-rebuilt --cmp-limit 20 --no-tiles
python3 tools/l2check.py --root $S/tree-synth --cmp-limit 20 --no-tiles
# L3: firmware field walk and name decode on the generated file
python3 tools/lctbl_build.py l3 archive/head256.img $L --per-table 20
python3 tools/lctbl_build.py l3 archive/head256.img $S/LCTBL001-synth.DAT --per-table 3000
python3 tools/lctbl_string_decode.py archive/head256.img --hex "75 6c 69 63 61 20 5a f3 6c 74 61 20 36 00"
python3 tools/lctbl_string_decode.py archive/head256.img --hex "75 6c 69 63 61 20 5a f3 6c 74 61 20 36 00" --mode 0 --expect none
```

3. **Controls.** *Positive:* `rebuild` on the EU file (the model must
   reproduce all 7,489,024 bytes) and `l3` on the factory file (the
   firmware walk must agree with the model on factory records).
   *Negative:* the `l3` command patches the catalog descriptor to 11 fields
   and sets record type 7 (both must change/reject the walk); `cardcheck` on
   `tree-neg` (new file, stale DRSTR) must FAIL; `lctbl_string_decode
   --mode 0` must leave the bytes unchanged; the selftest corrupts a stream
   byte and a catalog byte (walk must raise) and feeds unsorted codes (build
   must refuse). The US file is an independent control of the layout rules
   (34 tables, none of which was used to derive the rules).
4. **Scope.** Two files, 64 location tables, 550,112 records, 1,138 record
   pages. Of the 64 indexes, 49 have two levels (16 EU, 33 US). L3 covers the
   record walk (`0x003f61bc`/`0x003f5d98`) and the name decode
   (`0x003ca858`); the index lookup and page loader were **not** executed

5. **Falsifier** — stated under Hypothesis.

## Interpretation

- **FACT (C-2410):** every pointer in the file is a sector address
  `((s // 8) << 8) | (s % 8)` of the 0x100-byte sector `s`; sizes are in
  16-bit words. Rebuilding both files byte-identically proves the encoding
  on every pointer they hold.
- **FACT (C-2411):** the catalog at `0x1000` is three lists with one entry
  per table — table descriptors (46 B: next, schema pointer, index address
  and words, page geometry constants, table code, name), column schemas
  (376 B: data address and words, max record words, first-column word 0x16,
  12 columns each `next, 0, max length words, type 0x8000 number / 0x6000
  string, index, name`) and page-directory descriptors (34 B: directory
  address and words, 500 records per page). Slot 7 of the 300-entry slot
  table at `0x800` points at the catalog and holds its sector count.
- **FACT (C-2412):** each table's index is a B-tree of 0x1000-byte pages
  keyed by `u32 ordinal + 4-byte BCD location code`; the split rule above
  reproduces 49/49 two-level indexes. Record order is location-code order.
- **FACT (C-2413):** record pages are zlib level 6 streams of ≤500 records,
  4-byte aligned inside a table, each table sector aligned; the page
  directories (`u16 500, u16 0`, then `offset, compressed, plain` words per
  page) sit after the last stream, not in an `0xff` pad.
- **FACT (C-2414):** the range block at `0x5cc` (16 B prefix + 12 B per table) carries, per table,
  the BCD first and last location code; its prefix repeats the header's
  south/west bounds and a flag word that differs EU/US (meaning UNKNOWN).
- **OBSERVED (C-2415):** the firmware field walk `0x003f61bc` reads its
  field count and column chain from a block laid out exactly like the
  catalog column descriptor (`+24` first column word, `+26` field count,
  column `+0` next, `+12` index); fed our generated descriptor and records
  it returns the model's 12 offsets and lengths for 3,668/3,668 records.
  ASSUMPTION: the RAM copy is the card descriptor 16-bit-swapped (the
  loader that builds it is not located).
- **HYPOTHESIS:** a single-leaf index holds at most 339 keys; the largest
  factory single-leaf table has 110 keys and the smallest two-level one 391,
  so the limit between them is inferred from the 339-key full leaves.
- **UNKNOWN:** the index lookup and the page loader were not executed;
  `0x0b0b`/`0x0f0f` flag meaning; why slot 7.

The task's sort-order clause: the file is ordered by location code (the
B-tree key, C-2412); the names are not collated (rdstm.md "Writer rules for
names" rule 4, M3.9: 50.4 % of adjacent pairs ascend under the firmware
key). The selftest checks the order that the file depends on (codes
ascending, unsorted input refused); no name collation is applied, because
nothing in the file uses it.

## Conclusion

`tools/lctbl_build.py` writes a complete `LCTBL001.DAT` from a table/record
model. The model reproduces the EU (247,089 records) and US (303,023 records)
files byte for byte, a synthetic Polish name set builds into a file that
passes the structural walk, L1 `cardcheck` and the L2 checks that do not
compare against the factory golden, and the firmware field walk reads it at
L3. `rdstm.md` §LCTBL now carries the full layout; reader-coverage row 22
moves to "L3 partial (record walk)". Open: the index/page-loader run on a
generated file (M5.60).
