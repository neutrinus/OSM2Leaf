## Question

Rung Z3: can we fill the from-zero container of M5.87 with level-1 road
records built from OSM for the whole London bbox, with no factory record in
the tile, so that the real `Navi.exe` draws them on the start screen?

## Hypothesis

`tilewriter.build_road_record` records placed by our own layout code into the
empty directories mount and draw like the spliced ones of M8.H71. Falsifier:
a new error line, a failing L3 record read, or a black start screen.

## Inputs

London bbox `-0.51,51.28,0.33,51.70`; start position 51.5098 N, 0.1342 W;
class table `provisional-v0`; names off (Z5).

## Method

1. Sample and hash: above.
2. Commands (`W` scratch, `FAC` factory tree, `L4` as in M5.85):

   ```bash
   python3 tools/osm_ingest.py $W/osm/London.osm.pbf --bbox=-0.51,51.28,0.33,51.70 -o $W/london/london.imf.jsonl --json
   python3 tools/mesh_split.py $W/london/london.imf.jsonl -o $W/z3/split.jsonl --json
   python3 tools/roadclass_v0.py --class-table-out $W/z3/class.json
   python3 tools/tile_from_zero.py --selftest
   python3 tools/tile_from_zero.py $W/z3/split.jsonl --template $FAC/MAPAL001/B48R068R.DAT --cell B48R068R \
       --class-table $W/z3/class.json --country 826 -o $W/z3/B48R068R.DAT
   python3 tools/tile_provenance.py $FAC/MAPAL001/B48R068R.DAT $W/z3/B48R068R.DAT --require-zero
   python3 tools/s1_wide_dir.py census $W/z3/B48R068R.DAT
   python3 tools/dir_read_len.py predict $W/z3/B48R068R.DAT
   (cd tools/ze0-viewer && python3 harness.py verify $W/z3/B48R068R.DAT)
   # card: hardlinked factory tree + new tile, rebuild_manifests, imgpatch tile + DRSTR001 (as M5.87), then
   python3 tools/cardcheck.py --image $W/z3/card.img
   python3 tools/datask_l3.py mount archive/head256.img --card-image $W/z3/card.img --position 51.5098,-0.1342 \
       --request 0xa6accdef --bytes --json $W/z3/req.json
   # L4: run.sh + ze0_screenshot.py screen after `Pow Off 1st Detect`; serial-log error lines vs the factory run
   ```

   The street names `build_road_record` returns for the odd partner are
   discarded (Z3 writes no odd record; names are Z5).

3. Controls. Positive: the factory card at L3 with `--request 0xa6accdef`
   inflates the 23,204-byte start-parcel record and replies `sub 3` (data).
   Negative: the first from-zero tile (below, O2) replied `sub 9` and logged
   `<MeshDtChk>READ DATA NG!`, so both the L3 request and the L4 log catch a
   bad record. The M5.87 empty tile is the black baseline (126 pixels).
4. Scope: one tile, section 1 level 1 even records only; odd (background)
   records, level 2, sections 2 and 4 empty.
5. Falsifier: as in Hypothesis.

## Observations

**O1 — the IMF.** 1,946,278 nodes, 376,492 ways (185,148 named), all in cell
`B48R068R`. `tile_from_zero`: 602 parcels, one road record each, in 46 rows;
record plain size min 148, median 25,016, p99 101,128, max 156,356 B;
tile 11,513,856 B, SHA-256
`0fe1b1274b26ebbed1c3bc9d469fcecebc73f12074d5d0d27ba10e403d9b6bba`.
`tile_provenance --require-zero`: `section 1 level 1: factory_records=0/602`,
`container_constant_bytes=4089/4096`, exit 0. `s1-wide census: dirs=68 …
records=602 records_bad=0 block_overlaps=0 OK`; directories read past the
end: 0; `harness.py verify`: `byte-identical rebuild OK`, `records ok 601 bad
0`, `roundtrip OK`.

**O2 — two defects found on the way.**

- *Shape length.* `fa_encode` stores a shape's point count in one byte; a
  302-point OSM way failed the readback. `tilewriter.build_road_record` now
  splits a run longer than 255 points into pieces that share their end
  points (selftest: a 300-point run → 2 readable shapes; tilewriter 89/89).
- *Empty odd pair.* The first card passed L1 and L3 (no request) but L4
  logged `<MeshDtChk>READ DATA NG! mid=a6accdef typ=6 did=4cc5a6f4`
  (`ERR_PRC_NAVI 0x0A`, `LVL_A`/`LVL_B`) and stayed black. A smaller variant
  without service/track/footway roads (max 86,488 B) and one capped at
  78,832 B failed the same way, with a different `did` each time. At L3,
  `--request 0xa6accdef` read the record at file position `0x10048ca00` —
  4 GiB past its real offset `0x48ca00` — inflate stopped on the first byte,
  `0x004048cc` loaded the raw buffer, reply `sub 9`. Cause: our empty odd
  pairs were `0x7fffffff`. The factory's level-1 columns are only (record,
  record) 45,184, (empty `0x7fffffff`, record) 18,803 and (empty
  `0x7fffffff`, empty `0xffffffff`) 1,549: an empty **odd** pair is always
  `0xffffffff`, never `0x7fffffff`, and no factory column has a record with
  an empty odd partner. The firmware adds `2 × 0x7fffffff` to the record
  offset. `tile_relayout.empty_model` and `tile_from_zero` now write
  `0xffffffff` odd pairs (selftest check added). `did` in the log is the
  word the firmware found where it expected the parcel code, i.e. garbage
  from the wrong read, not a size check.

**O3 — L1/L3.** Card SHA-256
`43dd4ceb251ab9f851b6d229df84bfb6eaaf4f2b450f41a11a1e337c52da9635`:
`cardcheck --image` `RESULT: PASS`. `--request 0xa6accdef`: one read of
`B48R068R` (`0x9a00` B block), inflate window `0x18c00`, `0x003f6968` loads
101,128 B of the inflated record, `0x004048cc` the code, `0x00405078` the
unit table, reply `sub 3`. `--request 0xa68ccdff` (the largest record,
156,356 B): window `0x26300`, reply `sub 3`. The window is the record size
rounded up to 256; no ceiling was reached.

**O4 — L4.** Boot to `Pow Off 1st Detect`; the serial log has the same
1,043 error/fail lines as the factory run (no `MeshDtChk` line). Both
screenshots SHA-256
`806d6ce865647e55894dffe592757bd78b1deda1063f8c013fbc17688d113aa3`,
68,906 non-black pixels (empty tile: 126; factory: 384,000, 348,191 pixels
differ from it). By eye: the Soho / Mayfair street grid with Regent Street's
curve, Piccadilly, Shaftesbury Avenue and Charing Cross Road as wide brown
roads and the side streets and service roads as thin grey lines, on black
(no background yet), no labels. A variant capped at 78,832 B per record
(21 parcels lost 12,595 low-rank runs) draws 63,671 pixels and differs from
the uncapped one in 5,328 pixels (the dropped service roads). The screenshot
holds only OSM data and is given to Marek in the project thread.

## Interpretation

- **FACT:** a London tile whose every record is generated from OSM and placed
  by our own layout code (0/602 factory records; only the 4 KiB header
  constants come from the template) is accepted by the real `Navi.exe` and
  its roads are drawn. Z3 passed.
- **FACT:** in a level-1 column the empty odd pair is `0xffffffff`; with
  `0x7fffffff` the firmware reads the even record 4 GiB away. A record with
  no odd partner is accepted when the odd pair is `0xffffffff`, although the
  factory never writes one.
- **FACT:** a 101,128-byte level-1 record draws at L4 and a 156,356-byte one
  reads at L3; the factory's largest even record in this tile is about
  59 KB. Record size is not the limit at this scale (input for M5.92).
- **UNKNOWN:** whether the router and the search tolerate the empty
  sections 2 and 4 (no route was asked); what limits the size at L4 beyond
  101 KB.

## Conclusion

`tools/tile_from_zero.py` builds the first from-zero tile: OSM roads for the
whole London bbox in the Z2 container, accepted at L1/L3/L4. Next: Z4
(M5.89) background fills, so the screen is no longer black.
