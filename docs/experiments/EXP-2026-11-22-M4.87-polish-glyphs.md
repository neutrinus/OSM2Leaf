## Question

Which code points can the map text renderer (`xglXtpDrawXanaviCharacter`) actually draw on EU2011, and specifically are the 18 Polish letters (ą ć ę ł ń ó ś ź ż and their uppercase forms) present in the font it uses, with what fallback for a missing glyph — so the compiler can decide keep vs transliterate?

## Hypothesis

`xglXtpDrawXanaviCharacter` is an export of `XGLDLL.dll` (precheck: `ce_strfind` prints that module) and reaches a Xanavi font table (glyphs indexed by a code-point → glyph map) built into ROM A or in a skin/font resource. A Latin letter such as `A` will resolve to a glyph (positive control); a code point outside the font's map will resolve to a fallback/blank (negative control). **Falsifier (from the task):** the glyph table lists a Polish letter as present but Polish town names on the factory card are stored without diacritics — then data, not font, is the limit and that must be recorded. A second falsifier: no code-point table can be located from structure (only from a guessed literal), which would make any per-letter verdict unsupported.

## Plan (written before firmware search)

1. **Identify the renderer from structure, not a guessed literal.** `tools/ce_strfind.py archive/head256.img --image-start 0x200200 xglXtpDrawXanaviCharacter` already printed `XGLDLL.dll` at VA `0x03123b16` (this is the export-name string in the export-name table). Get the *function* entry from `tools/cerom.py IMG exports XGLDLL.dll` (the export address is in the module's e32/OFT, derived from the ROM headers), then confirm the entry is a real function with `tools/nk_decomp.py pdata IMG --module XGLDLL.dll <VA>` → expect `START` (or `INSIDE` → use the true start). Every VA quoted below is obtained this way; no address comes from a fitted delta or a code-literal guess.
2. **Find the font resource.** Enumerate `XGLDLL.dll` strings and imports (`tools/cerom.py ... imports`, `tools/ce_strfind.py` with font-related needles: `Font`, `font`, `.ttf`, `Xanavi`, `glyph`, `Glyph`, `DCW_`, `rasterizer`). Follow the module's imports/exports with `tools/sh4xref.py --calls FUNC_VA` to see the call chain from the renderer to the raster/font engine (`rasterizer_dll.dll` `DCW_Create`/`DCW_Raster`/`DCWx_initFontCache` per `docs/format/skins.md`). Decide from the call chain and VAs whether the font is a ROM A file, a `.skn` asset, or a dedicated font file on the card.
3. **Locate the code-point table from data/structure.** Use `tools/sh4xref.py --to VA` on any pointer used by the renderer, and inspect the section at that VA with `tools/sh4dis.py dump`. Derive the table shape (entry size, key encoding — e.g. UTF-16 code unit vs Shift-JIS/CP1252 byte) from the data itself and from the writer's inverse (how `M4.13`/`tools/name_strings.py` encodes Polish letters), not from the format doc alone.
4. **Check the 18 Polish letters one by one.** For each of `Ą ą Ć ć Ę ę Ł ł Ń ń Ó ó Ś ś Ź ź Ż ż`, quote the character (code point, and the encoded byte pair the firmware uses) and search the derived table; record present yes/no with the command that printed the evidence. Positive control: `A`/`a` must be present. Negative control: a code point known absent (e.g. a CJK or Cyrillic code point) must be absent and route to fallback.
5. **Fallback + recommendation.** From the renderer's disassembly (`tools/sh4xref.py --calls`, `tools/sh4dis.py dump`) name the VA that handles a missing glyph (blank box / substitution / skip). Write the per-letter table, the fallback behaviour with its VA, and a keep/transliterate recommendation into `docs/research/osm-pipeline.md`.
6. **Card cross-check (falsifier).** Sample Polish place names on the factory EU2011 card map files (via `tools/cmpind.py extract` into a home-tree scratch dir) and count how many are stored with diacritics vs transliterated. Record the result.
