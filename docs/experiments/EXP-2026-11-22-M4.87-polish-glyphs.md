## Question

Which code points can the map text renderer actually draw on EU2011, and specifically are the 18 Polish letters (ą ć ę ł ń ó ś ź ż and their uppercase forms) present in the font it uses, with what fallback — so the compiler can decide keep vs transliterate?

## Hypothesis

`xglXtpDrawXanaviCharacter` is an export of `XGLDLL.dll` (precheck prints that module) and reaches a Xanavi font table. A Latin letter such as `A` will resolve to a glyph (positive control); a code point known absent will resolve to the fallback (negative control). **Falsifier:** the glyph table lists a Polish letter as present but Polish town names on the factory card are stored without diacritics — then data, not font, is the limit. A second falsifier: no code-point table derivable from structure (only from a guessed literal), making a per-letter verdict unsupported.

## Plan (written before firmware search, commit b695db7f)

1. **Identify the renderer from structure, not a guessed literal.** `tools/ce_strfind.py archive/head256.img --image-start 0x200200 xglXtpDrawXanaviCharacter` prints `XGLDLL.dll` at VA `0x03123b16` (export-name string). Get the *function* entry from `tools/cerom.py IMG exports XGLDLL.dll` (RVA from the module e32/OFT), then confirm with `tools/nk_decomp.py pdata`. Every VA below is obtained this way; no address comes from a fitted delta or a code-literal guess.
2. **Find the font resource.** Enumerate `XGLDLL.dll` strings and imports (`tools/cerom.py ... imports`, `tools/ce_strfind.py` needles `Font`, `Xanavi`, `Character`, `glyph`, `DCW_`, `rasterizer`). Follow the import chain to the raster/font engine (`rasterizer_dll.dll`) and decide from VAs whether the font is a ROM A file, a `.skn` asset, or a font file on the card.
3. **Locate the code-point table from data/structure.** Use `tools/sh4xref.py --to`/`--calls` on the renderer, then inspect the data itself. Derive the table shape (entry size, key encoding) from the sorted data and the writer's inverse (how `M4.13`/`tools/name_strings.py` encodes Polish letters), not from the format doc alone.
4. **Check the 18 Polish letters one by one.** For each letter quote its Unicode code point and search the derived table; positive control `A`, negative control a code point known absent.
5. **Fallback + recommendation.** Name the miss/fallback behaviour with its VA; write the per-letter table and a keep/transliterate recommendation into `docs/research/osm-pipeline.md`.
6. **Card cross-check (falsifier).** Count Polish letters in the factory `LCTBL001.DAT` name database with `tools/name_strings.py`.

## Interpretation

- **FACT:** The named `xglXtpDrawXanaviCharacter` is a no-op returning 0 (`0x030fd118`, `rts; mov #0,r0`); it draws nothing on EU2011.
- **FACT:** Map names are drawn through `XGLDLL.dll` imports of `RASTERIZER_DLL.dll`; `DCW_Font_getNamFontAddr` (`0x0344fb08`) returns the FDL font `dig_pfont_ucs_iso88591_hei_wx` at VA `0x03431020` (magic `FDL Font`), which is in ROM A, not a card file.
- **FACT:** That font's cmap (`0x034310f4`..`0x0343d06c`) covers U+0001..U+011F only. 8 of the 18 Polish letters have code points inside that range; 10 have no entry at all.
- **FACT:** A cmap miss returns 0 from `DCWx_findFontData` at `0x03451ede`; the cmap tail is filled with a repeated notdef glyph (`0x8500` at the very end, per-cp fills such as `0x1f00`/`0xc100`/`0xe500` earlier). No L3/L4 run was performed, so the pixels drawn on a miss are not directly observed.
- **OBSERVED:** The font is named `iso88591` yet its cmap includes U+0104–U+0119 (Latin Extended-A); the name is not a reliable repertoire statement.
- **HYPOTHESIS:** The repeated per-cp glyph ids encode one entry per font size/style, with the repeated id being notdef for variants that lack the glyph.
- **UNKNOWN:** The byte→Unicode conversion between the single-byte ISO-8859-2 card strings (M4.13) and this Unicode cmap was not located. If the firmware passes the raw Latin-2 byte as the code point, `ą` (byte `0xB1`) would index U+00B1 `±`, which *is* in the cmap — so cmap presence alone does not prove correct rendering. An L3/L4 run is needed to settle this.
- **UNKNOWN:** Whether the later (2014/2016) cards use a different font with fuller Polish coverage (M4.89 is the natural follow-up).

## Conclusion

The map text font on EU2011 can draw **8 of 18** Polish letters: `Ą ą Ć ć Ę ę Ó ó`. It cannot draw `Ł ł Ń ń Ś ś Ź ź Ż ż` — those code points are beyond U+011F and have no cmap entry. The named `xglXtpDrawXanaviCharacter` call is itself a no-op. The compiler recommendation (in `docs/research/osm-pipeline.md`) is to transliterate the 10 missing letters, keep the 8 present ones, and flag the unlocated byte→Unicode conversion as the open risk. `docs/research/osm-pipeline.md` open question 1 is updated accordingly; claims C-7880–C-7889 carry the evidence.
