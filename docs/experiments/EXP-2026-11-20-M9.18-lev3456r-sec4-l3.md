## Question

Does the EU2011 firmware read `LEV3456R.DAT` and a tile's section 4 the way
`lev3456.py` and `clarion_tile.py` (the readers `lev3456gen.py`,
`tilewriter.py` and `section4.py` build on) say the files are laid out, for a
factory file and for a file `lev3456gen.py` generated (M5.16)?

## Hypothesis

M3.25 and M9.13 showed that the mount reads `LEV3456R.DAT` and, of the tile
under the start position, every section table and one directory per level.
If the Python readers are right, every one of those reads asks for a table
or directory the Python model lists, and each slot-table parser loads exactly
the directory the model describes (from `+0xa` to the end its header word 0
declares). A generated `LEV3456R` whose records moved is then read the same
way relative to its own model.

**Falsifier:** a factory read that asks for an offset the model does not
list, or a parser that loads a different range than the model's directory
size; or a damaged directory header that still checks as MATCH (the check
would have no teeth).

## Method

1. **Sample and hash.** The files above; `FACT` is the EU 2011 card's tree
   (any FAT32 extraction; check the two SHA-256 values above).
2. **Commands** (each mount takes 12–15 s on this host):

   ```bash
   IMG=archive/head256.img
   CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   FACT=/home/user/scratch/factory-eu          # EU 2011 card tree, read-only
   W=/home/user/scratch/m9.18
   python3 tools/lev3456gen.py generate --template $FACT/MAPAL001/LEV3456R.DAT --extract tools/fixtures/m9.18-krotoszyn-lev3456.json -o $W/G-LEV3456R.DAT
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 51.70,17.45 --bytes --json $W/F.json
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 51.70,17.45 --replace MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT --bytes --json $W/G.json
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 51.70,17.45 --replace MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT --flip MAPAL001/LEV3456R.DAT@0x279ca03:0x60 --bytes --json $W/C1.json
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 51.70,17.45 --flip MAPAL001/B48R058R.DAT@0x113c7f03:0x60 --bytes --json $W/C4.json
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 51.505,-0.273 --json $W/P-LON.json
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 40.42,-3.70 --json $W/P-MAD.json
   python3 tools/datask_l3.py mount $IMG --card-image $CARD --position 41.90,12.50 --json $W/P-ROM.json
   python3 tools/mount_dirs_l3.py check $W/F.json --file MAPAL001/LEV3456R.DAT=$FACT/MAPAL001/LEV3456R.DAT --file MAPAL001/B48R058R.DAT=$FACT/MAPAL001/B48R058R.DAT
   python3 tools/mount_dirs_l3.py check $W/G.json --file MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT
   python3 tools/datask_l3.py diff $W/F.json $W/G.json
   python3 tools/mount_dirs_l3.py compare $W/F.json $W/G.json --file-a MAPAL001/LEV3456R.DAT=$FACT/MAPAL001/LEV3456R.DAT --file-b MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT
   python3 tools/mount_dirs_l3.py check $W/C1.json --file MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT
   python3 tools/mount_dirs_l3.py compare $W/G.json $W/C1.json --file-a MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT --file-b MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT
   python3 tools/mount_dirs_l3.py check $W/C4.json --file MAPAL001/B48R058R.DAT=$FACT/MAPAL001/B48R058R.DAT
   python3 tools/mount_dirs_l3.py compare $W/F.json $W/C4.json --file-a MAPAL001/B48R058R.DAT=$FACT/MAPAL001/B48R058R.DAT --file-b MAPAL001/B48R058R.DAT=$FACT/MAPAL001/B48R058R.DAT
   python3 tools/mount_dirs_l3.py check $W/F.json --file MAPAL001/LEV3456R.DAT=$W/G-LEV3456R.DAT
   python3 tools/mount_dirs_l3.py changed $FACT/MAPAL001/LEV3456R.DAT $W/G-LEV3456R.DAT
   for p in LON MAD ROM; do python3 tools/mount_dirs_l3.py check $W/P-$p.json --file MAPAL001/LEV3456R.DAT=$FACT/MAPAL001/LEV3456R.DAT; done
   ```

   `mount_dirs_l3.py check` takes each read of the named file from the
   mount JSON and looks it up in the Python model: a section-table read must
   be at a table address from the `0x800` section list and the table walker
   `0x0040be84` must load only inside its `2 × words`; a directory read must
   be at a directory address from a group table (section, level, index), and
   the one slot-table parser that ran must load exactly `0xa … 2·size − 1`
   (header word 0). `compare` does the same for two runs and compares the
   model coordinates (section, level, directory index, parser, loaded range)
   instead of file offsets, and every read of other files byte-for-byte as
   `datask_l3.py diff` does (`SAME-RELOCATED` = same walk, other offsets).
   `changed` lists the `LEV3456R` directories whose inflated records differ.
3. **Controls.**
   - Positive: F against the factory files (must MATCH);
     `mount_dirs_l3.py --selftest` (11 checks on a synthetic container both
     `lev3456.py` and `clarion_tile.py` read).
   - Negative C1: G with the level-3 directory's row count (header word 1)
     16 → 112 (`@0x279ca03:0x60`).
   - Negative C4: factory tile with the section-4 level-1 directory's header
     word 1 changed (`@0x113c7f03:0x60`).
   - Negative C0: the factory run F checked against G's model (wrong file):
     must not MATCH.
4. **Scope.** EU2011 build A, EU 2011 card, PySh4 with the `datask_l3.py`
   models. Covered: what the mount reads of `LEV3456R.DAT` (header, 2
   section tables, 7 directories: L6, L5, L4, one of 45 L3 in section 1; L5,
   L4 in section 2) and of `B48R058R.DAT` (header, 3 section tables, 6
   directories, of which 1 in section 4). Not covered: any record block
   (coarse road/background/name records, section-4 name records): the mount
   stops at state 2 before a map request (M9.52/M9.53). Section 4 of a
   *generated* tile is not tested: no writer changes it (`section4.py build`
   exits 3, `tilewriter.py` copies it verbatim, so M9.13's generated tile has
   the factory section 4 byte for byte).
5. **Falsifier** as stated under Hypothesis.

## Interpretation

- **FACT (C-2440):** at mount the EU2011 firmware reads from `LEV3456R.DAT`
  the header, both section tables, the L6, L5 and L4 directories of section
  1, the L5 and L4 directories of section 2, and exactly one of the 45
  level-3 directories: the one whose box holds the start position, with the
  box coordinates of `map-tiles.md` (`y = 1.5·lat`, `x0 − 1024 = lon + 924 −
  1024`): four positions, four different directories, each the cell of the
  `BxxRyyR` tile read at the same time.
- **FACT (C-2441):** on the factory files every one of these reads (9 of
  `LEV3456R`, 9 of `B48R058R`) is at an offset the Python reader lists, and
  each slot-table parser loads exactly the directory the reader decodes,
  `+0xa` to `2·size − 1`. The firmware takes the directory length from header
  word 0, the same field `lev3456.read_dir`/`clarion_tile.read_dir` use.
- **OBSERVED (C-2442):** the slot-table parser follows the directory `typ`
  word on these 13 directories: `0x80`/`0x90` → `0x00414644`, `0x91` →
  `0x00414930`, `0x92` → `0x00414dbc`, `0x93` → `0x00415330`. `0x93` occurs
  here only in section 4, so `0x00415330` is the section-4 directory consumer
  of the mount. The selection code in `0x004157dc` was not read.
- **FACT (C-2443):** the `lev3456gen.py` file is walked like the factory file
  relative to its own model (SAME-RELOCATED): the firmware follows the moved
  directory and table pointers, and every directory it reads has the size
  and slot table the Python reader decodes.
- **FACT (C-2444):** the check has teeth: a level-3 directory with a wrong
  row count is dropped by the firmware (no parser), and a changed section-4
  directory header makes `0x00415330` parse the whole read buffer.
- **FACT (C-2445), defect:** `lev3456gen.py` put the Krotoszyn level-3 roads
  into directory 22, the cell the firmware reads for London; at Krotoszyn the
  firmware reads directory 24, which the generator did not change.
  `l3_cell_for_point` maps a point with a proportional 9 × 5 grid over the
  database bounds ("structurally valid regardless of exact geographic
  placement", its own docstring) instead of the directory boxes. Level 4/5
  parcel placement is not tested here (single directories; the mount does
  not pick a parcel). New task **M5.59**.
- **UNKNOWN (C-2446):** whether the firmware accepts the generated coarse
  *records* or decodes the section-4 *name list* as `lev3456.py` /
  `section4.py` do: no record block is read during the mount. That is the
  Done-when of M9.18, so the task is **blocked on M9.53** (a map request).
- **Scope:** EU2011 build A, EU card, PySh4 with `datask_l3.py`'s models. Not
  a statement about the unit.

## Conclusion

The hypothesis holds at directory level and no falsifier fired: the mount's
view of `LEV3456R.DAT` and of tile section 4 equals the Python readers' view
on the factory files (18/18 reads), a generated `LEV3456R` is walked the same
way after relocation, and both negative controls are detected. Two L3 targets
are registered as `blocked` entries that name the tools
(`lev3456_reader`, `tile_section4_reader` in `targets.json`); rows 18–20 of
`reader-coverage.md` carry the directory-level verdicts. The task's
Done-when (records and name list equal to the Python tools) is not met:
M9.18 is `blocked`, `Unblock: M9.53`. One generator defect was found
(level-3 placement, C-2445) and filed as M5.59. `docs/format/map-tiles.md`
gets the level-3 selection and the parser-by-`typ` table.
