## Question

Can `runner.py` run the M3.10 DRSTR reader `sub_00419350` (the parser called
from `0x00419684`, M3.10) on the factory `DRSTR001.DAT`, EU and US, and accept
the factory tree and reject a corrupted one?

## Hypothesis

Falsifier-first. Refuted if a module-entry run of `0x00419350` or `0x00419684`
returns `ACCEPT` on factory input and `REJECT` on a corrupted tree, with
`status` not `BLOCKED`, and the memory the reader touches is mapped.

Prediction before the run: the reader cannot run. Its file input and its
globals sit in `Navi.exe` `sec1`, which is compressed and therefore not
mapped (the memory map skips it, M1.2f). Its CRT calls (coredll `fopen`,
`fread`, ...) are not in the stub table and have no bound import slots.

## Method

1. **Sample and hash.** IMG256 head, SHA-256 `92aa525d…` (verified by
   `fetch_image.py`); the memory map carries `image_sha256` for the first
   128 MiB, and the runner refuses the run (`INVALID`) on a mismatch, so a
   `BLOCKED` result means the hash matched. No DRSTR file was run (see Scope).
2. **Commands.** Runnable as written, one block, from the repo root:

```bash
python3 tools/fetch_image.py --image IMG256 -o archive/IMG256-head.img
python3 tools/cerom.py --image-start 0x200200 archive/IMG256-head.img romhdr
python3 tools/cerom.py --image-start 0x200200 archive/IMG256-head.img memmap --modules Navi.exe --out MEMMAP.json
python3 tools/l3_harness/rommap.py convert --report MEMMAP.json --segment 0 --skip-compressed --out ROMMAP.json
python3 tools/cerom.py --image-start 0x200200 archive/IMG256-head.img va2file 0x00419350
python3 tools/cerom.py --image-start 0x200200 archive/IMG256-head.img imports Navi.exe   # slots 0x0055d000+
```

   Probe runs: a scratch targets file `PROBE.json` (module entries in the
   M9.20 format, written by a throwaway script in the session scratchpad, not
   committed). Each entry uses `"endian": "little"` and `"stubs": []` (a module
   function may call no declared stub); `args` `["0x0"]` for `sub_00419350`
   (fd = 0, a probe value, not a file) and `[]` for `sub_00419684`; a
   placeholder `verdict_map` `{"0x0": "REJECT", "0x1": "ACCEPT"}`, which is
   never a reader verdict. Then:

```bash
python3 tools/l3_harness/runner.py run ctl-point-walker-0x3f5194 --targets PROBE.json --rommap ROMMAP.json --image archive/IMG256-head.img --engine pysh4 --json
python3 tools/l3_harness/runner.py run ctl-compressed-0x0055d100 --targets PROBE.json --rommap ROMMAP.json --image archive/IMG256-head.img --engine pysh4 --json
python3 tools/l3_harness/runner.py run ctl-outside-0x8cae1000 --targets PROBE.json --rommap ROMMAP.json --image archive/IMG256-head.img --engine pysh4 --json
python3 tools/l3_harness/runner.py run drstr-sub_00419350 --targets PROBE.json --rommap ROMMAP.json --image archive/IMG256-head.img --engine pysh4 --json
python3 tools/l3_harness/runner.py run drstr-sub_00419684 --targets PROBE.json --rommap ROMMAP.json --image archive/IMG256-head.img --engine pysh4 --json
```

   The reader VA is taken from M3.10 and checked with `cerom.py va2file`
   above; no delta is fitted. The `drstr_parser` target in `targets.json`
   stays `blocked`: a module entry needs a `verdict_map`, and the reader's
   return convention is not decoded (M3.10 gives only error codes 26, 23, 20
   and 10). Its `reason` and `notes` are rewritten; the stub list is kept with
   a note that it is not the reader's call list.
3. **Controls.** *Positive (pipeline, real image):* `ctl-point-walker-0x3f5194`,
   the M9.20 point-walker entry (C-2540), must reproduce the M9.20 real-run
   result (`UNMAPPED` at `0x0`). *Negative (compressed VA):*
   `ctl-compressed-0x0055d100` must be `BLOCKED` with the "compressed section"
   reason. *Negative (outside VA):* `ctl-outside-0x8cae1000` must be `BLOCKED`
   "outside every loadable block". The positive control is the M9.20 result,
   reproduced here, not a new one.
4. **Scope.** Covered: one image head (IMG256, first 256 MiB), one module
   (`Navi.exe`), five module-entry runs (1 positive control, 2 negative
   controls, 2 DRSTR probes), 0 DRSTR inputs, 0 verdicts. Mapped: 1 of 3
   blocks (`sec0`); skipped: 2 (`sec1`, `sec2`). Not covered: the EU card
   (not on this machine, and the head holds no DRSTR file), the US factory
   file (`leafre-work/m5.12-us/root-factory/DRSTR001.DAT`, sha `41c87b3d…`,
   checked but not run, because the reader faults before it reads a file),
   and any corrupted or M5.6-rebuilt tree (M5.6 is open, so none exists).
   Excluded by design: the other modules, the full image, Ghidra and QEMU.
5. **Falsifier.** A DRSTR probe that reaches a `return` with `ACCEPT` on
   factory input and `REJECT` on a corrupted tree, with the memory it reads

  `va2file 0x00419350` returns file offset `0x01097550`, inside `sec0`.
- `sec1` is at VA `0x0055d000`, flags `0xc8002040` (COMPRESSED), and the
  import slots `COREDLL #1113` (fopen, slot `0x0055d1e0`), `#1118` (fclose,
  `0x0055d1e8`), `#1120` (fread, `0x0055d1a0`), `#1126`/`#1127`
  (ferror/clearerr), `#1130`/`#1131` (fseek/ftell) all lie in `sec1`.
  `sec2` at `0x0154f000` is also compressed.
- The coredll ordinal names (`#1113` fopen, `#1118` fclose, `#1120` fread,
  `#1126` ferror, `#1127` clearerr, `#1130` fseek, `#1131` ftell) are taken
  from M3.10, not re-derived: `cerom.py exports coredll` raises `KeyError:

- The DRSTR fault `0x0055d8fc` is a data access inside `sec1`. The runner
  does not report the PC, so the instruction is not identified.
- `sub_00419684` reads `0x8c20fec0`, above the stack top the runner sets

  caller frame is absent. Not explained further.
- No `ACCEPT`/`REJECT` verdict was produced by any DRSTR run.

## Interpretation

- **FACT:** The module path works on the real image (controls reproduce; the
  two negatives stop where they should).
- **FACT:** `sub_00419350` lies in mapped, executable `sec0`; its reads of
  the import slots and its buffer global lie in compressed `sec1`. The first
  reader access the runner can reach is unmapped, so the reader cannot run
  until `sec1` is decompressed (M1.2f, the port of `DECOMP_BLK`; M1.3's
  "0 OK / 245 UNSUPPORTED" stands).
- **FACT:** Even with memory, the runner has no import binding for module
  entries (`IAT` slots are not written with stub VAs), and no stub models
  coredll `fopen`/`fread`/`fseek`/`ftell`/`ferror`/`clearerr`/`fclose`
  (`tools/l3_harness/stubs.py` has none of them, checked with `stubs.py list`).
  The stale `drstr_parser` stub list (`CreateFileW`, `ReadFile`, ...) does not
  match the decoded calls.
- **FACT:** The Done-when cannot be met on `main` for a second reason: the
  rebuilt-by-M5.6 DRSTR does not exist (M5.6 is open).
- **FACT:** M9.22 (the `B30R048R` assertion) does not add an input region. Its
  block is about a tile round-trip. The M9.14 block's input-region clause
  therefore has no task that provides it: a new task is filed (M9.24) for the
  binding and the stubs.
- **OBSERVED but unexplained:** the `0x8c20fec0` read.
- **HYPOTHESIS (untested):** after `sec1` is decompressed and the import
  slots are bound, `sub_00419350` on a factory file returns a verdict. The
  reader's return convention is not decoded, so no `verdict_map` is written.

## Conclusion

Status: `blocked`. Done-when is not met; no DRSTR verdict is claimed, and the
probe results are pipeline observations with `l3_claim: false`.

Blocker (one line): `sub_00419350` reads its imports and buffer global from
compressed `Navi.exe` `sec1` (UNMAPPED `0x0055d8fc`), and the Done-when needs
an M5.6 rebuild, which is open.

Unblock: **M1.2f** (decompress `sec1`), then **M9.24** (import binding and
coredll file stubs); the Done-when also waits on **M5.6**.
