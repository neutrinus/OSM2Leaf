## Question

The re-opened M4.40 starts from M4.54: the router consumer `0x00422eac` (EU2011) reads four words of the
`0x14b6` kind-64 reply, and M4.54 mapped them to section-2 part-a fields after storing a section-2
block in the reply buffer itself. Which tile section does the data-access task actually put into that
reply, and which code asks for section 2?

## Hypothesis

M4.40 and M4.54 assumed that the request kind `0x40` of `RGD_DATA READ` `0x004266ec` means "section 2"
(an OBSERVED pairing: the renderer sends kind 4 and reads section 1). If that holds, the data-access
task, asked with kind `0x40` for a parcel, reads that parcel's section-2 record.

**Falsifier (stated before the runs):** with the firmware's data-access task serving the request on the
real card, a kind-`0x40` request makes the map-file task read a record that is **not** a section-2
record of the tile, or a section-2 record is read only for other kinds.

## Interpretation

- **FACT:** the data-access task maps a request kind to a tile-section index through the table at
  `0x179b20` (EU2011): kinds 1/2/4 → index 0, 8/`0x10`/`0x20` → index 1, `0x40` → index 2 (group 1).
  In the L3 runs index 0 read a section-1 `0x00fa` record, index 1 a section-2 record and index 2 a
  `0x0009` record of the tile's third section — tile section **4** (`B48R058R`'s sections are 1, 2, 4).
  (C-5920, C-5921, C-5922)
- **FACT:** the router's `RGD_DATA READ` request (kind `0x40`, `0x004266ec`) therefore fetches the
  parcel's **section-4** record, and the `0x14b6` kind-64 reply that `0x004268c0` stores and
  `0x00422eac` reads is a section-4 record (pointer `+16` = record word 0, the source the store copies).
  The section-2 reading of that buffer (M4.40 C-5646–C-5648 wording, M4.54 C-5713–C-5715) was a
  premise, not a finding: M4.54 placed a section-2 block in the buffer by hand and chose `k` as the
  first word index that clears the gate; such a `k` exists in 24,483 of 65,274 section-2 records of
  `B48R058R` (0.27 % of words), at the same rate as in section-4 records (0.28 %), so passing the gate
  says nothing about which section is in the buffer. (C-5921, C-5924)
- **FACT:** section 4 is not an "administrative/place-name index" only: the two records the router got
  hold signpost texts (`POZNAN:KALISZ:(36):RAWICZ`, `(SP44):POZZALLO NORD … SIRACUSA`: destinations and
  road numbers). `RGD` reads as route guidance. The firmware's reply pointer `+24` is the name text and
  equals header word 6 (53, 107); word 7 is its length in words (18, 21); pointer `+28` is word 9, the
  first word after the nine-word header. (C-5925)
- **FACT:** the section-2 requester is the route path finder: `0x00336bf0` (`RPF_PreMap_start`,
  EU2011) sends `0x14b5` kinds 8 and `0x10`. A kind-8 reply points `+16` at **unit 0** (word 27, the
  node/entry list `clarion_rd` parses) and `+24` at **unit 2** (word 6113, 10 words, on `a6bed6ee`);
  absent units stay `0xffffffff`. So the reply's pointer slots follow the record's unit table, which the
  data-access task reads before the router path finder gets the data. (C-5922, C-5923)
- **OBSERVED:** kind `0x10` for `a68cd68c` returns status 4 without a read and kind `0x20` is refused
  (status 9 / entry 3); both are section index 1 in the table, so they differ in something the lookup
  checks after the section (level or parcel form); not resolved here.
- **OBSERVED:** at data-access state 3 (after `0x07d0` sub `0x0b`) `0x00405970` refuses every request;
  the runs stay at state 2. `datask_l3.py` names state 3 "ready"; that name may be wrong.
- **HYPOTHESIS:** `0x00422eac`'s gate (`w[k+15] & 0x0f00 == 0x0900`) selects one kind of guidance item
  in a section-4 record; neither of the two records has one. The `k` source `0x00424464` reads the
  renderer's section-1 buffer (`*0xe8f604` slot table, a renderer-side table: `0x00425f40` and
  `0x0042613c` load it), so a section-1 point may carry the section-4 word offset. Untested (M4.56).
- **UNKNOWN:** the route path finder's reply handler and the code that walks units 0 and 2 (that is
  where the section-2 grammar is read); US2011.

## Conclusion

The falsifier fired. With the firmware's own data-access task serving requests on the EU 2011 card,
the router's kind `0x40` reads tile section 4 (signpost / guidance records), not section 2, on two
tiles; section 2 is read for kind 8, which the route path finder `RPF_PreMap_start` `0x00336bf0`
(EU2011) sends, and its reply points at units 0 and 2 of the record. M4.40's premise ("the router's
reader `0x004266ec` → `0x00422eac` is the section-2 reader") is wrong, so the section-2 field table
cannot be read from it, and M4.54's mapping of the four consumer words onto section-2 part-a fields is
retracted (C-5713–C-5715 → C-5924). M4.40 is `blocked` on M4.55 (drive the route path finder's reply
of kinds 8/`0x10` and read-watch the code that walks unit 0); M4.56 takes section 4 with
`0x00422eac`. `docs/format/map-tiles.md` gains "Which section each request kind fetches" and a
correction note on the M4.54 table; `reader-coverage.md` rows 18 and 19 name the requesters.
C-5920–C-5927.
