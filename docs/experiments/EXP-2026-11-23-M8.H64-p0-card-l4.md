## Question

Does the P0 ladder card (one tile's section-1 roads from OSM, plus the grown
`DRSTR001.DAT`) boot through `tools/l4check.py` to the same stage, launcher
verdict, map-file verdict and set of files read as the EU 2011 factory card in
the same session, and what does that witness prove about rule 13?

## Hypothesis

Yes: the P0 change is confined to a tile the firmware does not open without a
position seed, so the launcher and map-file layers see an accepted card.
**Falsifier (task):** P0 rejected at a stage the same-session factory card
passes (record the log line) → `Status: blocked` + negative EXP. **Falsifier
(files-read claim):** any difference in `coverage[].path` between the two
traced boots before a position change.

## Method

1. **Sample and hash.** Scratch `S=/home/marek/projekty/leafre-work/scratch/M8.H64`,
   `TMPDIR=$S/t` (49 chars, never `/tmp`), `IMG=archive/sd-images/…eu.img`,
   `W=$HOME/projekty/leafre-work/m5.44/out`. `sha256sum` printed the four
   source hashes in O1. Prechecks: `card_ladder steps --check`,
   `l4check --selftest`, `ze0_sdtrace --selftest`, `l3check --selftest`.
2. **Commands.** Copy the factory card to `$S/p0.img`, then M5.30's exact
   patch commands including `--hash`:

   ```bash
   cp "$IMG" "$S/p0.img"
   python3 tools/imgpatch.py --image "$S/p0.img" --file MAPAL001/B48R058R.DAT \
     --from "$W/MAPAL001/B48R058R.DAT" --allow-resize --hash --json > "$S/patch-tile.json"
   python3 tools/imgpatch.py --image "$S/p0.img" --file DRSTR001.DAT \
     --from "$W/DRSTR001.DAT" --hash --json > "$S/patch-drstr.json"
   python3 tools/imgpatch.py --check-diff --image "$S/p0.img" --reference "$IMG" \
     --file MAPAL001/B48R058R.DAT --file DRSTR001.DAT --allow-metadata --json > "$S/checkdiff.json"
   python3 tools/imgpatch.py --check-diff --image "$S/p0.img" --reference "$IMG" \
     --file MAPAL001/B48R058R.DAT --file DRSTR001.DAT --json > "$S/checkdiff-strict.json"
   python3 tools/cardcheck.py --image "$S/p0.img"
   sha256sum "$S/p0.img"
   python3 tools/l4check.py --card "$IMG"     --qemu "$QEMU" --timeout 900 --json > "$S/factory.json"
   python3 tools/l4check.py --card "$S/p0.img" --qemu "$QEMU" --timeout 900 --json > "$S/p0-l4.json"
   ```

   For the card-side negative, `python3 tools/l4check.py --card
   ~/projekty/leafre-work/scratch/m8.h13/bad-mmain.img --qemu "$QEMU" --timeout
   900 --json > "$S/bad-l4.json"`. Each trace boot copied that JSON's
   `boot.command` (a list), replaced its `-serial file:…`, `-monitor unix:…`
   and `-drive …file:…` with fresh paths in a fresh log dir and a fresh
   `mkoverlay.py` qcow2, and appended exactly
   `-trace enable=sdcard_read_block,file=$S/<card>-trace/sd-trace.log`; the
   scratch driver `trace_boot.py` (not committed) stops on l4check's own
   idle/fatal markers. It never uses `-d` (a 7.0 GB `qemu.log` already sits in
   `scratch/m8.h13/`). Then:

   ```bash
   python3 tools/ze0_sdtrace.py "$S/factory-trace" --card "$IMG"     --json > "$S/factory-trace.json"
   python3 tools/ze0_sdtrace.py "$S/p0-trace"      --card "$S/p0.img" --json > "$S/p0-trace.json"
   python3 tools/ze0_sdtrace.py "$S/bad-trace"     --card "$BAD"      --json > "$S/bad-trace.json"
   python3 tools/l3check.py --card-gate --card "$S/p0.img" --factory "$IMG" --json > "$S/p0-cg.json"
   ```

3. **Controls.** *Positive:* the factory card must boot to `result PASS`,
   `stage_reached F5` in the same session (M8.H13 measured **214.62 s and
   363.07 s on two real boots** — neither number is used as a control here);
   the P0 card must reproduce the pinned SHA and the `check-diff` class

   selftest process's exit). *Negative, card level:* the truncated-MMAIN card
   exits 1 with `failed_stage F4` and changes the traced file list — so a

4. **Scope.** One EU2011 factory image and one P0 image (two changed files:
   `MAPAL001/B48R058R.DAT`, `DRSTR001.DAT`), two `l4check` boots plus one
   re-run after an early host-side QEMU exit, two `--card-gate` runs, three

## Interpretation

- **FACT:** The P0 generated card reaches the same L4 verdict as the
  same-session factory card (F5, `PASS`, `ACCEPT`, `OPENED`, all stages PASS)
  and its 17-file SD read list and per-file ranges are identical.
- **FACT:** The card-side negative shows the comparison can detect a real
  change: a bad-MMAIN card reads 7 instead of 17 files (10 different paths,
  one range change) and fails at F4. The P0 null result is therefore an
  observed equality, not an untested one.
- **OBSERVED:** One factory boot exited early (`qemu-exit`, 55.54 s) amid
  audio-network retries; the re-run reached idle. F5 is informational by
  l4check's own definition, so this does not alter the F0–F4 verdict, but it
  is why the baseline was re-run rather than cited from M8.H13.
- **OBSERVED:** FAT extents rise 79294 → 79296 (the tile's relocated cluster
  chain) while traced read ranges stay identical.
- **HYPOTHESIS:** The changed `DRSTR001.DAT` bytes are read at boot (the file
  is in the 17-path list) without opening any new file; the changed tile bytes
  are not reached because no position was seeded. The first L4 witness is a
  first-boot accept, not a display or route result.
- **UNKNOWN:** What the renderer draws from the new roads, route/search
  consistency for the spliced tile, and any car/bench (L5) behaviour.

**Rule-13 limit (verbatim from the navigator spec, numbers filled from O5):**
> No position was seeded in either boot. M8.H8's factory read list contains
> `MAPAL001/B48R068R.DAT`, **not** the P0 card's changed `B48R058R.DAT`; with no
> position, neither boot reads our changed tile. Therefore equal file lists /
> the listed differences show only that the P0 card reaches the same launcher
> and map-file verdict with no new file-open error. They are **not** rule-13
> acceptance of the generated tile's bytes: `M8.E4` (full `Navi.exe` on a
> generated card, with a position) remains the acceptance oracle.

## Conclusion

The P0 card built in place from the M5.44 tile and manifest reproduces the
pinned card SHA, passes L1/card-gate and boots under `-M ze0` to the same
same-session L4 verdict as the factory card, with an identical 17-file SD read
list. This is recorded in the F4 column as the first `L4 generated (M8.H64)`
witness and in claim rows C-7610–C-7619. It is explicitly **not** M8.E4
acceptance of the generated tile: no position was seeded, and neither boot
read `B48R058R.DAT`. The task's Done-when passed, so `TODO.md` is set to
`done`, not `blocked`.
