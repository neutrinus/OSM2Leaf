# EXP-2026-11-06-M4.10: POI category/brand codes to `BICON001` icons

- **Status:** done
- **Date:** 2026-11-06
- **Sample:** EU 2011 image
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Claims:** C-980…C-989
- **Supersedes:** C-214 (icon mapping UNKNOWN)
- **Superseded by:** none

## Question

Which numeric code in a `POINT0nn` record selects a `BICON001` icon, and
which icon belongs to which POI category or chain brand?

## Hypothesis

`POINT` records carry a 16-bit category/brand code next to the facility name;
`BICON001` contains one logo per branded category plus a few generic glyphs,
so the code can be joined to an icon through the brand name.

## Inputs

| Item | Value |
| --- | --- |
| Image | `leaf2011.img` |
| SHA-256 | `105e2032…76307` |
| Icon container | `BICON001/BICON001.DAT`, 114,598 bytes |
| POINT shards | 002, 004, 005, 008, 011, 018, 020, 021, 022, 025, 026, 029, 030, 033 |
| Tool | `tools/poi_icons.py` |

Vendor files stay outside the repo; nothing extracted here is committed.

## Method

1. Extract every icon with `tools/poi_icons.py bicon`, then render a numbered
   contact sheet and read the logo text/pictogram by eye.
2. Decompress each `POINT0nn.DAT.cmp` once with `tools/cmpind.py extract`.
3. Walk the inner zlib record streams of each extracted file. Record framing
   is `u8 tag ∈ {0x60,0x68}`, `u8 length/2`, then `length` bytes.
4. In a `0x60` record, locate the facility-name text. The name block is
   bracketed by two 16-bit codes:
   `<tag> <category:u16> NAME \0 [house@street] <brand:u16>`.
   The **last two bytes of the record are the brand code**; the two bytes
   immediately before the name are the category code.
5. Count `(brand code, name)` pairs over all shards. A brand code is accepted
   when hundreds of records of the same chain share it across countries.
6. Join brand code to icon by the visible logo. Confirm with the independent
   block of UK chain codes (`0x0e24`…`0x0e39`), whose icons are readable.

Commands:

```bash
python3 tools/poi_icons.py bicon archive/root/BICON001/BICON001.DAT
# 103 PNGs: 98 x 32x32, 5 x 30x30, first at 0x1408

for s in 002 004 005 008 011 018 020 021 022 025 026 029 030 033; do
  python3 tools/cmpind.py extract \
    archive/root/REFER001/POINT$s.DAT.cmp -o /tmp/poi/POINT$s.DAT
done

python3 tools/poi_icons.py codes /tmp/poi
python3 tools/poi_icons.py verify /tmp/poi \
  --bicon archive/root/BICON001/BICON001.DAT
```

`verify` ends with `RESULT: PASS` for all 34 rows.

## Observations

### `BICON001` table (C-980)

```
0x100a  u16 103                  icon count
0x100e  103 * (u32 start, u32 size), big-endian, in 2-byte units
0x1408  first PNG; offset = 0x1408 + 2*start
```

Parsed sizes: 98 icons are 32×32 and 5 are 30×30. The five 30×30 entries are
exactly the generic glyphs 0 (fuel pump), 18 (restaurant), 19 (pharmacy
cross), 20 (parking) and 21 (hotel bed); every chain logo is 32×32. Four
slots hold byte-identical copies of the Holiday Inn logo (25/60/75/76) and
two hold Crowne Plaza (23/59); duplicate table slots are not distinct brands
(C-986).

### Record codes (C-981, C-987)

| Record | category | brand | interpretation |
| --- | --- | --- | --- |
| `ARAL 15@BÜRENER STRASSE` | `0x01bc` | `0x01bc` | brand-coded fuel station |
| `CORA 31@RUE MERCURE` | `0x0190` | `0x01e2` | fuel category + Cora brand |
| `BEST WESTERN …` | `0x0dac` | `0x0dad` | hotel category + chain brand |
| `CLARION …` | `0x0dac` | `0x0e24` | hotel category + chain brand |
| `HOLIDAY INN …` | `0x0dac` | `0x0db8` | hotel category + chain brand |

The brand code is not a checksum or a string id: 1,055 Best Western records
in 14 shards share `0x0dad`, 435 Mercure records share `0x0df2`, and 82
Radisson records share `0x0e2e`.

Top-level code ranges observed:

```
0x01xx  fuel station / shop          (0x0190 generic, 0x0191 Agip, 0x0193 BP, …)
0x03xx  restaurant / cafe            (0x0391 generic, 0x0385…0x039c cuisines)
0x0dxx  hotel (early block)          (0x0dac generic, 0x0dad Best Western, …)
0x0exx  hotel (later/UK block)       (0x0e24 Clarion, 0x0e29 Park Inn, …)
```

### Icon order (C-985, C-986)

Icon order is **not** category-code order. Counterexample: Comfort (`0x0dd1`
= 3537) is icon 34 while Campanile (`0x0dc3` = 3523) is icon 35. The UK block
`0x0e24`→47, `0x0e29`→51, `0x0e2a`→53, `0x0e2e`→57, `0x0e32`→61, `0x0e39`→65
is ascending, so order is a build artefact, not a lookup rule. The mapping
must be applied from the table, not computed as `rank(code)`.

## Interpretation

- **FACT:** `BICON001` has 103 PNG entries; 98 are 32×32 and 5 are 30×30.
- **FACT:** `POINT` name blocks carry a 16-bit category code and a 16-bit
  brand code; the brand code is stable per chain across countries.
- **FACT:** 34 codes map to an icon whose logo text matches the chain name.
- **OBSERVED:** the container mixes generic glyphs (fuel, restaurant, bed)
  with chain logos (fuel, supermarket, hotel).
- **HYPOTHESIS:** the runtime looks up the brand code in a static table that
  is equivalent to the table above. The exact lookup table is not stored in
  the map data, so the join is by logo identity.
- **UNKNOWN:** the schema field at bit 219 (`icon code`) is not byte-aligned
  in these records; whether it is the same brand code (C-215) is unresolved.

## Conclusion

`docs/format/assets.md` now carries a 34-row category/brand code → icon
table, and `tools/poi_icons.py` reproduces the scan and the check. The old
statement that the icon mapping is unknown (C-214) is retracted.
