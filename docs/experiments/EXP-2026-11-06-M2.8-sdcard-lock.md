## Question

Does the firmware check CID/CSD, an SD lock password or the FAT
serial/label before using the card, i.e. what raises `SD UNLOCK NG`?
Which card properties must a cloned card reproduce?

## Observations

### 1. `SD UNLOCK NG` screen

`SD UNLOCK NG` is an entry in the `AppLaunch.dll` UTF-16LE error-screen block
(build B at physical VA `0x8833681c`, build C at `0x8834081c`), shown by the
single dispatcher at `0x8834ffb8` (B) / `0x88359c90` (C) (C-790). It is the
screen reached when the SD security-unlock step fails.

### 2. AppLaunch.dll security-lock check

`AppLaunch.dll` checks the SD card security state before launching and logs:

| String (UTF-16LE) | Build B VA | Build C VA | Referencing function |
| --- | --- | --- | --- |
| `AppLch >> Error!!! SD Card is [Security lock state] or [no Security]....` | `0x88336278` | `0x88340278` | B `0x8834f5f4`, C `0x883592cc` |
| `AppLch >> SD Card Security Unlocked!` | `0x88336310` | `0x88340310` | B `0x8834f5f4`, C `0x883592cc` |
| `AppLch > SD Check Error` | `0x88337828` | `0x88341828` | (no literal-pool hit) |
| `AppLch > SD Check Retry %d` | `0x883378b4` | `0x883418b4` | (no literal-pool hit) |

The function at `0x8834f5f4` (B) / `0x883592cc` (C) is the one that decides
whether the card is in an acceptable security state; both the "security lock
state" (locked with a non-matching password) and "no security" (no password set
at all) cases are treated as errors (C-791, C-797).

### 3. SDHC.dll lock/unlock implementation

`SDHC.dll` implements the SD physical lock (CMD42) through two internal
methods:

| Method (string anchor) | Build B VA | Build C VA | Notes |
| --- | --- | --- | --- |
| `CDSKMain::Init()->SDHC_SecurityUnLock() Err = ERROR_ACCESS_DENIED` | `0x88470df8` | `0x8847bdf8` | referencing function B `0x884743c8`, C `0x8847f3c8` |
| `CSDHCMain::SDHC_Lock_Unlock_Card() Err = [%d]` | `0x88471408` | `0x8847c408` | referencing function B `0x88476df4`, C `0x88481df4` |
| `CSDHCMain::SDHC_Lock_Unlock_Card() byFlag[%02X] byPasswordLen[%d]` | `0x88471498` | `0x8847c498` | same function |
| `dPassword[%02X]` | `0x88471476` | `0x8847c476` | password bytes logged |
| `SecurityUnLock` (ASCII method name) | `0x88470e84` | `0x8847be84` | same function group |
| `GetCardInformation` (ASCII) | `0x88470e94` | `0x8847be94` | card info read |
| `SDHC_CardCheck` (ASCII) | `0x88470ea8` | `0x8847bea8` | card check |

`SDHC_Lock_Unlock_Card` logs `byFlag`, `byPasswordLen` and every password byte
(`dPassword`), i.e. the lock command carries an explicit password buffer
(C-792, C-793). The password is a firmware-side value; nothing in the strings
or in the examined code paths derives it from CID, CSD, FAT serial number or
volume label.

### 4. Negative results: no CID / CSD / FAT serial / label check

- **CID / CSD.** A whole-image UTF-16 search for `CID` (97 hits) and `CSD`
  (14 hits) finds only identifiers such as `CSDCMain`, `CSDHCMain`,
  `CSDDirectAccess`, screen-state identifiers (`CIDE_MAP_*`) and unrelated
  telecom/SQL modules. None of `SDHC.dll`, `AppLaunch.dll` or
  `SdCardLch.exe` references a CID or CSD register, and no comparison of a
  card's CID/CSD against a stored value exists in those modules (C-794).
- **FAT serial / label.** No string in `SDHC.dll`, `AppLaunch.dll` or
  `SdCardLch.exe` mentions a volume serial number or label comparison.
  `SdCardLch.exe` reads `partInfo.szVolumeName` and `partInfo.szFileSys`
  but only logs them (see below) (C-795).

### 5. `SdCardLch.exe` (image C)

`SdCardLch.exe` (module #79) is an SD-card launcher/mounter only. It mounts
`DSK1:`/`DSK8:`, logs partition/volume/filesystem names (`partInfo.szVolumeName`,
`partInfo.szFileSys`, `partInfo.szPartitionName`), the filesystem `RELIANCE`,
and mount status. It performs no identity comparison and contains no
CID/CSD/serial/label check (C-796).

## Conclusion

The only identity check on the SD card before use is the **SD physical security
lock** (CMD42): the firmware attempts to unlock the card with a hardcoded
password inside `SDHC.dll`; success logs `SD Card Security Unlocked!`, failure
returns `ERROR_ACCESS_DENIED` from `SDHC_SecurityUnLock` and AppLaunch shows
`SD UNLOCK NG`. A card that is locked with a different password, or that has no
password set at all ("no security"), is rejected.

Based on the firmware strings and code paths examined, the firmware does **not**
check CID, CSD, FAT serial number or volume label. Therefore a cloned card must
reproduce the **SD lock state / unlock password** (it must be locked with the
firmware's known password, or otherwise be acceptable to the unlock routine),
but need not reproduce CID, CSD, FAT serial number or volume label (C-798).
