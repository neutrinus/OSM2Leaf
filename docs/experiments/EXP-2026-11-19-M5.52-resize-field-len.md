## Question

After `mutate_refer_poi.py --resize` renames a POI to a different length, does the
firmware's own name accessor return the whole new name and the unchanged address?

## Hypothesis

The accessor places field 5 from the per-record field-length bytes (C-5115), not from
the `ff ff` framing. If `--resize` also writes the field-5 length byte
(`old + delta/2` words), then for a shorter, equal and longer name the accessor returns
the new name, field 6 (address) is unchanged, and every other record still splits
correctly (`ok=1000 of 1000`).

**Falsifier:** after the fix, any run below prints `mismatch`, `fault` or `not-text`
for any record, returns a record-0 name other than the expected one, or the address
of the renamed record changes; or the pre-fix tool also passes the +2 rename (then
the length byte was not the defect).

## Observations

### Firmware layout (EU2011)

`nk_decomp pdata`: `fn 0x003f56bc` START (len `0xec`), `fn 0x003f5e10` START (len
`0x66`), `fn 0x003f632c` START, `fn 0x003f5e78` START; `0x003f8a0c` GAP (a leaf after
`fn 0x003f8950`).

- `fn 0x003f56bc`: `w = u16[rec]`; refuses `(w & 0xe000) > 0xc000` and
  `(w & 0x1800) >> 11` ∉ {0,1}; class `w >> 13` 3 or 2 → `r8 = (u16[rec+10] >> 8) +
  (u16[rec+10] & 0xff) + 8`, result `rec + 2*r8` (`0x003f5750..0x003f5786`).
- `fn 0x003f5e10(loc, n, f)`: skip `(n+1)/2` words, then for `i < f` read
  `u16[loc + 2*(i>>1)]` and take the high byte when `i` is even, the low byte when odd
  (`0x003f5e2e..0x003f5e62`). In the file-order (big-endian) page the length of field
  `f` is therefore byte `loc + f`.
- `0x003f8a0c(rec)`: returns 0 (escape) iff `u16[rec] & 0xfc00 == 0xfc00`; both page
  tags `0x60`/`0x68` take the field path.

## Interpretation

- **FACT:** the firmware's name accessor (US2011 `0x0041ec8c`/`0x0041e7d8`, EU2011
  `fn 0x003f632c`/`fn 0x003f5e78`) returns the whole new name and the unchanged address
  after a `--resize` rename of −2, 0, +2 and +10 bytes on US2011 and −2/+2 bytes on
  EU2011 (two records), with all 1000 records of each page still splitting correctly.
  The pre-fix tool fails the same +2 rename. The field-5 length byte was the defect.
- **FACT:** on 2000/2000 records of the two pages the header class is 3 and the nine
  field lengths end exactly at the record end, so `--resize` can place every record it
  will meet on these pages; the refusal path for other classes is exercised only
  synthetically (no real record of another class was found).
- **OBSERVED:** the M9.39 US mutant pair (`ea2d0e0f…`), used as a control by
  M9.39/M9.41/M9.42/M9.43, was built with the defect: the firmware reads record 500's
  name 2 words short. Its outer-container and walker results are unaffected (they do
  not read field lengths), but the pair is not a well-formed rename. The fixed CLI now
  produces `34fb3aab…` for the same command, so C-4482 ("the committed command
  reproduces `ea2d0e0f…`") no longer holds at `main` after this merge. Re-pinning is
  M9.52 (new).
- **UNKNOWN:** whether other per-record bytes depend on the name length in pages or
  readers not exercised here (other `POINT0nn` pages, the search index, the UI copy
  path, M3.11b). The accessor reads only the length bytes and field data.

## Conclusion

`tools/mutate_refer_poi.py --resize` now places field 5 the way `fn 0x003f56bc` /
`fn 0x003f5e10` do (EU2011), requires the old text to be inside field 5, patches both
`len2` and the field-5 length byte, refuses a delta that is not a whole number of
words and any record whose field area it cannot place, and verifies that every other
field of the record is byte-identical. `--census` counts header classes and placeable
records of a page. Done-when met: the precheck command exits 0 with `ok=1000 of 1000`
and the expected name on +2 and −2 renames (both builds). `docs/format/refer.md` and
the `reader-coverage.md` POINT row now say different-length renames are read by the
firmware accessor. Claims C-5260–C-5265; C-5117 is closed by C-5261.
