# EXP-2026-11-24-M1.60: why the radio screen is dead after the audio transplant, and a card-side fix to try

- **Status:** done (static + emulator boot); car test open
- **Date:** 2026-11-24
- **Sample:** `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (whole image SHA-256
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`);
  first 100 MiB of `LEAF_2011-2012_US.img` (range SHA-256
  `3e6dca604729b985af8282a891afd88f5908275be1a50029c1fff81147790f88`);
  NK1 `firmware/unit-flash/nk1-QY7200ND.bin` (committed); Marek's 8 MiB
  flash dump of 2026-11-24 with `0x400000–0x45FFFF` set to `0xFF` (not
  committed), emulator run only.
- **Tools:** python3 3.13.18; Ghidra 11.4.2 headless (JDK 21), language
  `SuperH4:LE:32:default`, functions from `.pdata`; `tools/cerom.py`,
  `tools/sh4dis.py`; new `tools/audio_rds_launch.py` (`--selftest`);
  `tools/ze0_launch.py`, QEMU 11.1.3 + ze0 series.
- **Claims:** C-10310–C-10317
- **Supersedes:** none
- **Superseded by:** none

## Question

Marek's car test of the M1.59 transplant (US `Audio.exe` in the EU card's
image A, USA unit): equalizer and beeps work, FM "does not fully work", and
"the UI does not seem to talk to what the hardware does; icons are not tied
to stations". How do the radio screen, `Audio.exe` and the tuner driver
talk to each other in the EU and the US build, where is the chain broken,
and what can a card-side patch do? Does XM need to be switched off?

## Hypothesis

The EU radio screen control (`RDSCC.dll`) and the US `Audio.exe` use
different message ids, so the screen is not connected.
**Falsifier:** `RDSCC.dll` and `RBDS_CC.dll` send the same IPC ids and read
the same shared block, or the US `Audio.exe` also serves the RDS ids.

## Method

1. **Sample and hash.** As above.
2. **Commands.**

   ```bash
   EU=LEAF_2011-2012_QSD-309-101_navi158_eu.sys   # first 100 MiB
   US=LEAF_2011-2012_US.sys
   NK=firmware/unit-flash/nk1-QY7200ND.bin
   for m in Audio.exe RDSCC.dll; do python3 tools/cerom.py --image-start 0x200200 $EU extract $m -o eu; done
   python3 tools/cerom.py --image-start 0x200200 $EU decompress --modules Audio.exe,RDSCC.dll --out eu/dec
   for m in Audio.exe RBDS_CC.dll; do python3 tools/cerom.py --image-start 0x200200 $US extract $m -o us; done
   python3 tools/cerom.py --image-start 0x200200 $US decompress --modules Audio.exe,RBDS_CC.dll --out us/dec
   # NK1 sections are compressed with the kernel routine, which cerom takes
   # from build B of the same file: append NK1 to a card file and address it
   cat $EU $NK > combo.img
   python3 tools/cerom.py --image-start 0x6400000 combo.img extract anwdrv.dll -o nk
   python3 tools/cerom.py --image-start 0x6400000 combo.img decompress --modules anwdrv.dll,AppLaunch.dll --out nk/dec
   python3 tools/cerom.py --image-start 0x6400000 combo.img files --extract nkf --decompress   # default.hv
   # Ghidra: code section imported raw at its VA, data sections added at
   # their realaddr, one function per .pdata entry, import stubs named from
   # `cerom.py imports --resolve-with`; all functions decompiled to a file
   # outside the repository
   python3 tools/audio_rds_launch.py --selftest
   python3 tools/audio_rds_launch.py show $EU
   cp eu.img eu_rds.img && python3 tools/audio_rds_launch.py patch eu_rds.img --in-place
   python3 tools/sh4dis.py --image-start 0x200200 eu_rds.img Audio.exe --va 0x45150 --count 40
   python3 tools/ze0_launch.py --qemu $QEMU --card eu_rds.img --flash nand_a0erased.bin \
     --workdir run/rds --peer panel --peer gps --gdb 1260 --ui-start --ipl-extra extra.txt --timeout 900
   ```

   IOCTL sets: the IOCTL dispatcher of each tuner class is a `switch`; the
   case values were read from its jump tables and compare constants
   (`FUN` at vtable `+0x300`). The IOCTLs an `Audio.exe` sends are the
   words `0x800c2000`–`0x800c23ff` in its code section.
3. **Controls.** *Positive:* the US pair agrees with itself (`RBDS_CC.dll`
   ids = the ids the US `Audio.exe` holds; every tuner IOCTL of the US
   `Audio.exe` outside the XM range is a `CRbds` case), and the EU pair
   likewise with `CRds`. *Negative:* `audio_rds_launch.py show` refuses the
   US card and the transplanted EU card ("OpenDriver bytes differ"); the
   selftest's out-of-reach branch raises.
4. **Scope.** Static reading of the six modules; emulator boot of the
   patched card to the first map draw. The emulator has no audio
   microcontroller (M8.H45): `anwdrv` never connects, so no tuner class is
   exercised and the new routine does not run there.
5. **Falsifier.** Stated under Hypothesis.

## Observations

**O1 — three layers, each region-specific.**

```
radio screen (skin form)        EU: RDSCC.dll  (RDSCC.RDSCtrl)      US: RBDS_CC.dll (RBDS_CC.RBDSCtl)
   | AvCCWrapper SendDataIpc    ids 0x83000001 / 0x82000001         ids 0x83000002 / 0x82000002
   | window id (SetWindowHandle) 10                                  20
   | shared block (HCXMemory)   rds_shared_mem                      rbds_shared_mem
Audio.exe                       queue AVOSM_QUEUE_RDS               queue AVOSM_QUEUE_RBDS (+ AVOSM_QUEUE_XM)
   | CreateFile + DeviceIoControl  TNR2:                            TNR4: (+ TNR3: for XM)
   | named events               RDS_STATE_CHANGE, RCV_RDS_*,        RBDS_STATE_CHANGE, RCV_RBDS_TEXT,
   |                            RCV_RADIO_TEXT, RCV_PS_TITLE ...    RCV_XMR_* ...
anwdrv.dll class (unit NK1)     CRds, mode id 3                     CRbds, mode id 0xd (CXmRadio 6)
   | serial frames
audio microcontroller           (not readable from here)
```

- `RDSCC.dll` builds its IPC header in fn `0x035ab2f0` (words
  `0x83000001`, `0x82000001`); `RBDS_CC.dll` in fn `0x035a9000`
  (`0x83000002`, `0x82000002`). The word `0x83000001` occurs once in the EU
  `Audio.exe` and not in the US one; `0x83000002` once in the US one and
  not in the EU one. XM uses `0x83000003` (`XMCC.dll`, US `Audio.exe`).
- The US `Audio.exe` creates `AVOSM_QUEUE_RBDS` (fn `0x362b4`) and
  `AVOSM_QUEUE_XM`; it never creates `AVOSM_QUEUE_RDS`. The EU one creates
  `AVOSM_QUEUE_RDS` only.
- `RDSCC.dll` sends commands by number through one method (vtable `+0x1f8`):
  e.g. 1 `MSG_RDS_CHANGE_TUNE_MODE`, 2 `MSG_RDS_CHANGE_BAND_TUNE`, 3 and 5
  `MSG_RDS_SEEK_UPDOWN`.

**O2 — `anwdrv.dll` holds all four tuner classes; the index picks one.**
`TNR_Init` (fn `0x03e0cbfc`) creates by device index: 1 `CRadio` (mode id
7), 2 `CRds` (3), 3 `CXmRadio` (6), 4 `CRbds` (0xd). Each registers itself
with the mode manager under its mode id.

**O3 — IOCTL sets (`0x800c2000 + n`).**

| Set | Count | Codes `n` |
| --- | --- | --- |
| `CRds` cases | 42 | `000–008`, `020–058`, `0f0–14c` |
| `CRbds` cases | 26 | `000–04c`, `058`, `1e0–1f0` |
| `CRadio` cases | 25 | `000–058`, `078`, `07c` |
| sent by EU `Audio.exe` | 29 | `000 004 020 024 02c 040 048 04c 058` + 20 in `0f0–14c` |
| sent by US `Audio.exe` | 22 | `000 00c 01c 020 024 02c 040 048 058`, `1e8 1ec 1f0`, 10 in `168–190` (XM) |

All 29 EU codes are `CRds` cases; only 9 of them are `CRbds` cases. The
20 RDS codes (`0f0–14c`: station list, PTY, TA, AF, REG, RDS text, PS
name) exist in `CRds` only.

**O4 — events.** Every radio event name the EU `Audio.exe` holds
(`RDS_STATE_CHANGE`, `RCV_RDS_CURRENT_BAND`, `RCV_RDS_STATION_LIST`,
`UPDATE_RDS_STAION_LIST`, `RCV_RADIO_TEXT`, `RCV_PS_TITLE`) is a string of
`anwdrv.dll` next to `CRds`; `CRbds` uses `RBDS_STATE_CHANGE`,
`RCV_RBDS_TEXT`, `RCV_RBDS_PS_NAME`.

**O5 — the key for `TNR2:` exists on the USA unit; only the launcher
skips it.** NK1's `default.hv` has `Drivers\Launch\Rds` (`Prefix TNR`, `Dll
anwdrv.dll`) beside `Radio`, `XMRadio`, `Rbds`. `AppLaunch.dll` activates a
table entry with `ActivateDevice(entry+0x54, 0x32)` (fn `0x03e4bb28`); the
string at `+0x54` is `\Drivers\Launch\Rds`, and the entry carries the area
mask `0x00020000` (Euro, M1.58). The EU `Audio.exe` already imports
`COREDLL!ActivateDevice` (IAT `0x46104`, stub `0x3d11c`).

**O6 — `audio_rds_launch.py`.** EU `Audio.exe` `OpenDriver` (fn `0x35a98`)
calls `CreateFile(L"TNR2:", 0xc0000000, 0, 0, 3, 0x80, 0)` through vtable
`+0x13c`; on `-1` it only logs through pool word `0x35af4`. The code
section has `0xb2` zero bytes after its end inside `psize`. The tool writes
a `0x98`-byte routine at `0x45150` and points the pool word at it: activate
`\Drivers\Launch\Rds`, open `TNR2:` once more, continue on the function's
own success (`0x35ada`) or failure (`0x35ad6`) path. On the EU card: 2 ×
(0x98 + 4 + 4) bytes change, SUM4 `0xcdf87db0` -> `0xa8ddfd9d`; `show`
after `patch` reports `patched` and SUM4 ok for both copies; `unpatch`
restores the bytes.

**O7 — emulator.** NK1 + the patched card + the flash with area 0 erased
(run `rds`, same setup as M1.59's control): `Sum Check NK2` passes,
`AppLch >> Process Create!!! -> \\windows\\Audio.exe`, and
`NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END` is handled, as in the control run. No
`Exception`, `Error Proc` or FailSafe line. `anwdrv` reports no audio
connection there, so `OpenDriver` and the routine did not run.

**O8 — XM.** The XM parts are the `XMCC.dll`/`XMStatusCC.dll` controls
(not on the EU card, also not after the transplant) and one thread of the
US `Audio.exe` (`TNR3:`, queue `AVOSM_QUEUE_XM`, ids `0x8x000003`). With no
XM control on the card nothing sends to that queue.

## Interpretation

- **FACT:** after the M1.59 transplant the EU radio screen sends to ids
  nobody serves and reads a shared block nobody fills; the US `Audio.exe`
  answers to window 20 and block `rbds_shared_mem`, which have no user on
  the EU card (O1). This is the "UI not connected" Marek saw. The audio
  path itself (volume, equalizer, sources) is the common part and works.
- **FACT:** `audio_tnr_patch.py` (`TNR2:` -> `TNR4:`) cannot give a working
  EU radio: 20 of 29 IOCTLs fail in `CRbds` and the EU `Audio.exe` waits
  on events `CRbds` never sets (O3, O4). The tool stays as a diagnostic.
- **FACT:** XM does not need to be removed for this: with the original EU
  `Audio.exe` there is no XM code at all; with the transplant the XM
  thread has no sender (O8).
- **HYPOTHESIS (H1):** with `\Drivers\Launch\Rds` activated from the card
  (O6), `TNR2:` opens on the USA unit and the whole EU chain
  (`RDSCC` ↔ EU `Audio.exe` ↔ `CRds`) is complete.
- **UNKNOWN:** whether the USA unit's audio microcontroller serves mode id
  3 (RDS) frames, and which FM/AM raster it tunes. If it answers only the
  RBDS mode (0xd), H1 gives an opened driver and a silent tuner; then the
  remaining way is the US chain complete (US `Audio.exe` + `RBDS_CC.dll` +
  the US radio screens), task M1.61.
- **UNKNOWN:** whether activating `TNR2:` while `TNR3:`/`TNR4:` are active
  disturbs `anwdrv` (three classes registered under three mode ids).

## Conclusion

Claims C-10310–C-10317 added. The transplant fixed the common audio path
and cut the radio screen off (different IPC ids, queue and shared block).
Next car test: the **original** EU card (consent and map-code patches as
before, no transplant, no TNR patch) plus `audio_rds_launch.py patch`.
Check, in this order: equalizer still works (it did not with the plain EU
card: no tuner, M1.58); FM screen shows a frequency and reacts to seek and
presets; sound; station names.
