## Question

At L4 (full-system emulation), can a stock-QEMU TCG plugin record executed
basic blocks of an EU2011 boot and let the host name which `Navi.exe` functions
ran — specifically the located mount readers — without patching QEMU or
setting breakpoints, and is the POINT walker absent before any POI search?

## Hypothesis

One boot that reaches mount executes the three located reader functions
(`MMAIN001` reader `0x0041a438`, `DRSTR` open `0x00419684`, parser
`0x00419350`) and no block in the POINT walker body
`[0x003f5194, 0x003f51d4)`. Falsifier (TODO): any located reader absent from
the executed set at mount, or the walker present before a search → L3/L4
disagree on the mount path (a finding for M9), task is blocked/failed, not
`done`.

SO=tools/qemu-ze0/plugins/libze0_cov.so

  -M ze0,kernel-off=0x3e00200,app-off=0x200200,dbgmsg=0x880404f4,\
verinf=QSD-302-100,mapdb=16-16,ipl-patch="$W/ipl.txt" \
  -kernel archive/head256.img -drive if=sd,index=0,file="$W/eu2011.qcow2" \
  -nographic -serial file:"$W/run-a/serial.log" \
  -monitor unix:"$W/run-a/hmp.sock,server,nowait" \
  -icount shift=0,sleep=off -d plugin -D "$W/run-a/plugin.log" \
  2>"$W/run-a/qemu.stderr.log"

### 3. Controls

- **Positive:** the executed set from run A contains all three reader VAs
  (O7 from a printing command, O10 shows them `executed: true`). Count 3/3.
- **Negative:** zero raw executed blocks in `[0x003f5194, 0x003f51d4)` — the
  POINT walker is a `.pdata` GAP (O7), so the check uses raw TB VAs, not
  function starts. O10 prints `"absent": true, "hits": []`.
- **Mandatory negative mutations (O12):**
  (a) in-place `sed` of `--enable-plugins` → `--disable-plugins` in build.sh
  makes its selftest fail `dry-run --plugins plan: output lacks
  '--enable-plugins'` (restored afterwards);
  (b) dropping all blocks in the MMAIN reader body makes its hit `false` and
  the reader count drop from 3 to 2;
  (c) injecting one block at `0x003f51b0` makes `point_walker.absent` false.
- **Baseline:** the same boot command without the plugin prints
  `AppLch >> Store Mgr Ready! [DSK1:]` and `Launcher End !` in `serial.log`,
  so the scenario reaches mount before any reader check.

### 4. Scope

One EU2011 firmware head and one EU2011 card, two boots (run A/B, 300 s each),
one synthetic selftest trace, two mutations of the saved log and one mutation
of build.sh. All 149 modules of image A are loaded in the guest, but this
report maps only the module named `Navi.exe` (`.pdata` 7,596 records, O8);
executed blocks in other modules are counted but not attributed here. No
2014/2016 or US card, no L5, no POI search scenario (the walker negative is
therefore a pre-search absence, not a run-B appearance). Build A has zero
compressed executable sections (C-2128), so an absent reader would not be
hidden bytes.

### 5. Falsifier

Any of the three reader VAs absent from the executed set while the serial log
shows mount reached; or any raw block in the walker body before a search; or
the tool reporting the same reader count after its supporting block was
deleted (H69). All would make the task blocked/failed.

## Interpretation

- **FACT:** the stock QEMU 11.1.3 build has plugin support; an out-of-tree C
  plugin records executed TB VAs and counts, and the host maps them to 1,341
  `Navi.exe` function starts from `.pdata` without any QEMU source patch.
- **FACT:** in a boot that reaches mount, all three located mount readers
  ran, and no raw block fell in the POINT walker body. L4 agrees with L3 on
  the mount path; the task falsifier is not met.
- **OBSERVED:** the function set is identical across two boots; raw blocks
  differ slightly (42 more unique blocks in run B) because an idle boot's
  timer/IRQ paths vary with host scheduling.
- **UNKNOWN:** whether a POI search would bring the walker into the executed
  set — that needs a search-driving scenario (follow-up), so the negative
  control here is pre-search absence only.
- **OBSERVED (scope):** `build.sh --selftest` has two pre-existing lint
  failures on `origin/main` (the `ze0-m223-...` patch name); this task's new
  assertions pass. No gate snapshot or fn_audit JSON was added or changed.
- **OBSERVED (scope):** after rebasing on `origin/main` (`2e240312`),
  `claims_check --strict --count-check` reports `DUP C-10270`–`C-10273` and
  several pre-existing `NOEXP` names; the same four DUP rows are present in
  `git show origin/main:docs/research/claims.md`, and `board.py resolve`
  correctly kept both sides. None of the ten new C-7060–C-7069 rows duplicate
  an ID or add a missing EXP reference (the EXP file is committed alongside).
- **OBSERVED (scope):** `tools/gate.py`'s `fn_audit` gate reports FAIL with
  `CORPUS STALE: 3 new / 0 gone / 0 moved` for both base and overlay; the new
  citations are `TODO.md:0x003fec60`, `docs/format/refer.md:0x003fbed8`/
