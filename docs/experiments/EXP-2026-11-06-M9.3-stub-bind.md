- **Status:** done (tool); ordinals beyond `sprintf` stay unbound (no image here)
- **Date:** 2026-11-06
- **Sample:** no vendor data and no firmware image used. The export-names
  fixture is a four-entry synthetic JSON file; the files, registry, heap and

- **Claims:** C-1650 (text below; register in `docs/research/claims.md`)

- **Superseded by:** none

## Question

Can the declarative stub table stop being a list of C names and become a
**bound dispatcher**: every entry keyed by `module!export` (plus an ordinal
where one is verified), a call target `(module, name|ordinal)` resolved to the
entry and then to a deterministic host implementation, while an export the
table does not model stops the run with exactly `missing stub: NAME`?

The task also asks for executable models of `sprintf` (ordinal 719), file I/O
over a virtual FS, `LocalAlloc`, critical sections and a registry loaded from
JSON. The old table had 14 modeled + 3 planned entries; seven new exports are
required for the last two models, and `sprintf` moves from `planned` to
`modeled`, so the expected end state is 22 modeled + 2 planned.

## Hypothesis

Yes, provided the binding is **data**, not a Python name convention: a
`module`/`export`/`ordinal` triple per entry makes the key explicit and lets
`cerom.py` export names fill ordinals without touching the implementations.
The only real ordinal available in this checkout is C-527's `sprintf` = 719;
every other ordinal must stay `null` rather than be guessed. A dispatcher
built from `binding_index()`/`ordinal_index()` can then answer all three
target forms, and a table entry without an implementation is a loud
`MISSING_STUB`, never a zero return.

## Method

### Binding

Each entry gained three fields:

| Field | Meaning |
| --- | --- |
| `module` | exporter (`coredll.dll`) or `internal`; normalised to `coredll`/`internal` |
| `export` | symbol inside that module; binding key `module!export` |
| `ordinal` | verified export ordinal, else `null` — never inferred |

`stubs.py` now exposes `normalize_module`, `stub_key`, `ordinal_key`,
`binding_index`, `ordinal_index`, `load_export_names` and `bind_exports`.
`load_export_names` accepts the same three shapes as `cerom.py`'s names DB
(`{"modules": {...}}`, a flat module map, or a list of records), and
`bind_exports` fills a `null` ordinal from it. A table ordinal that disagrees
with the names DB is a problem, not an overwrite.

### Dispatch

`dispatch.py` implements the call surface:

```python
dispatcher.resolve(("coredll.dll", "CreateFileW"))   # table entry by name
dispatcher.resolve(("coredll", 719))                 # table entry by ordinal
dispatcher.call(("coredll", "ReadFile"), [h, buf, n, count, 0])
```

Resolution order is ordinal index → names-DB name → name index. Unknown targets
raise `MissingStub`, whose message is exactly `missing stub: NAME`
(ordinal-only targets use `module!#ordinal`). An entry with `status=planned`
or no implementation raises the same error; there is no fallback return value.

### Deterministic models

| Model | Rule |
| --- | --- |
| Virtual FS | in-memory, case-insensitive, seeded from a dict or a corpus directory; `\Storage Card\` stripped; `..` and drive letters rejected; host FS never consulted |
| `CreateFileW`/`A` | read access + `OPEN_EXISTING` only; missing file returns `INVALID_HANDLE_VALUE` + `ERROR_FILE_NOT_FOUND`; synthetic handles from `0x10` |
| `ReadFile` | copies `min(requested, remaining)`, zero-fills the tail, writes the count, advances the cursor; EOF returns 0 + `ERROR_HANDLE_EOF` (38); `lpOverlapped` is a fault |
| `SetFilePointer`/`GetFileSize`/`CloseHandle` | begin/current/end, signed 32-bit distance (plus high dword when passed), negative seek → `0xffffffff` + 131; size high dword; close logs the unread byte count |
| Heap | one guest region, 8-byte alignment, zero on `LMEM_ZEROINIT`/`HEAP_ZERO_MEMORY`, `0xcd` poison otherwise **and on free**; double free is a fault, unknown pointer follows the documented return rule; leaks are listed |
| Critical sections | init/enter/leave/delete with a recursion depth per pointer; entering an uninitialised section, leaving without entering, deleting while held are faults (nothing is serialised: one thread) |
| Registry | JSON fixture only; `RegOpenKeyExW`/`RegQueryValueExW`/`RegCloseKey`; `REG_SZ` UTF-16LE+NUL, `REG_DWORD` 4 bytes, `REG_BINARY` verbatim; short buffer → `ERROR_MORE_DATA` (234) with the required size |
| `sprintf`/`OSM_Printf` | `%s %d %u %x %%` only, optional `-`/`0` flags and decimal width; any other conversion / too few arguments is a fault; no clock, no terminal |
| `memset`/`memcpy`/`strlen` | mapped-range checked; overlapping `memcpy` is a fault; `strlen` refuses a missing NUL |

Guest DWORD byte order follows the engine/`rommap.py` declaration
(`SuperH:BE:32`, `engine.py`), with `StubContext(endian="little")` available
for a target whose structs are little-endian. WCHAR and registry strings are
UTF-16LE by definition. Heap allocation is a bump allocator (freed blocks are
not reused), so two runs give identical addresses and logs.

## Interpretation

- **VERIFIED (synthetic):** every one of the 24 entries has a unique
  `module!export` key; only `coredll!#719` (`sprintf`) has an ordinal, matching
  C-527. `binding_index()` has 24 entries and `ordinal_index()` has exactly
  one. No ordinal was invented for the other 23.
- **VERIFIED (synthetic):** `load_export_names` reads the three `cerom.py`
  names-DB shapes and `bind_exports` fills a `null` ordinal; a disagreeing
  ordinal is reported. This is the binding path that will consume
  `cerom.py exports coredll.dll` on the real image.
- **VERIFIED (synthetic):** the dispatcher resolves name, ordinal and
  `module!export` targets, and stops with exactly `missing stub: NAME`
  (`missing stub: OpenEventW`), `missing stub: coredll!#4242` for an unknown
  ordinal, and `missing stub: OSM_LogMsg`/`StatusData` for planned entries.
- **VERIFIED (synthetic):** the virtual-FS round-trip returns the file bytes
  across `CreateFileW` → `GetFileSize` → `ReadFile` → `SetFilePointer` →
  `ReadFile` → `CloseHandle`; EOF is `0` + error 38; a missing file is
  `INVALID_HANDLE_VALUE` + error 2; two runs produce identical call logs.
- **OBSERVED:** `sprintf` formats `%s %d %u %x %%` (with `-`/`0`/width) and
  rejects `%q`; the heap zero/poison contract, double-free detection,
  critical-section order checks, and the registry `REG_SZ`/`REG_DWORD`/
  `ERROR_MORE_DATA` paths all behave as modelled.
- **UNKNOWN:** the real ordinals of the other 23 exports. `archive/images/` is
  empty in this checkout, so `cerom.py exports coredll.dll` could not be run
  and no ordinal beyond C-527 is claimed. Feeding a names DB is the intended
  next step, not a code change.
- **HYPOTHESIS:** the guest DWORD byte order is big-endian because
  `engine.py`/`rommap.py` declare `SuperH:BE:32:SH-4`. That is inherited, not
  independently re-derived here; `StubContext(endian="little")` exists for a
  target that proves otherwise.
- **NOT DONE:** wiring `dispatch` into `engine.on_exec` (argument fetch from
  `r4`–`r7`/stack and `r0` return) belongs to M9.5. This task delivers the
  resolution and the host behaviour, which is what the runner will call.
