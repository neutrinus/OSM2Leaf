## Question

`fn 0x0041f3dc` reads a point's reference word at shape-buffer byte
`2 (p + ((y >> 13) & 1)) + 4` (C-6775). Our generated record G0 carries
`0x0100` there, 330 bytes past its 184 B record, and the walk loads stale pool
bytes at `0x202`/`0x204` (C-6776). What does the factory put in that word on
the records of one tile, and what must `fa_encode` write so a generated record
is walked inside its own bytes?

## Hypothesis

The word is an in-record index of another point (a "none" `0xffff` when the
point is isolated), and the writer's `0x0100` is the link header's middle
("value") word, which happens to sit exactly in that slot. Writing `0xffff`
there (a start point has no earlier point to point at) should keep the walk
inside the `512 B` copy window.

**Falsifier (set before the runs):** factory records carry reference words
that leave the record; then the word is not a plain in-record index and the
census must print those counter-examples.

A factory shape with links makes the word an in-record point; an isolated
start uses `0xffff`. Example (record `(72,938,…)`, shape 1): start at word 72
reads slot 53 = `0x00b0` → record word 132 = the point at word 132, whose own
reference at slot 60 is `0xffdc` → record word 110 = back to the start (mutual
back-reference).

**The writer's word.** `fa_encode.shape_words` writes each level-1 link
header as `[style, 0x0100, lid]` (fresh style) or `[0x0100, lid]`. For the
first start point at record word `p`, the walk reads `p + ((y >> 13) & 1) + 2`,
which lands on that header's middle word (the `0x0100` in the bare form; the
`style` word does **not** move the slot, verified on F: shape 0 start at word
55 with `y = 0x2961` (bit 1) reads slot 36 = record word 58 = `0xffff`, and
shape 1 start at word 72 with `y = 0x2f0e` (bit 1) reads slot 53 = `0x00b0`).
So the writer's `0x0100` is exactly the reference word; `0x0100` = buffer word
256 = record word 278, past a 184 B / 92-word record, hence the `0x202`/`0x204`
loads (C-6776).

## Interpretation

- **FACT:** the word the walk reads as a point reference is, on the factory
  records of `B48R058R`, an in-record point index on 83.27 % of points that
  carry a dedicated word, `0xffff` on 16.54 %, and a link-header `val` word on
  0.22 %; no factory word points past the record (0 / 5,898,373). So the word
  is an in-record index with `0xffff` = none (C-6850, C-6851).
- **FACT:** the writer's `0x0100` is the link header's middle word, which is
  exactly the reference slot of the start point; on F that slot is `0xffff` or
  a real point index and never `0x0100` (C-6852).
- **FACT:** emitting `0xffff` keeps the walk inside the copy window (G1: 0
  out-of-window loads; the old 0x202/0x204 gone), and re-patching word 58 to
  `0x0100` brings them back (C-6853).
- **OBSERVED:** the result table is still all zeros for G1 (the same as G0):
  the reference word is no longer out of the record, but the shapes are still
  not counted. Which rule leaves them uncounted is M9.67; it does not depend on
  this word being wrong (C-6855).
- **OBSERVED:** 0.22 % of factory references are link-header `val` words
  (`0x0021`…), so a small share of factory references are not point indices;
  they are still in-record and do not leave it. The counters of C-6851 are the
  measurement; the 95 % bar (99.776 %) does not depend on classifying them.
- **HYPOTHESIS (not fixed here):** the whole-shape byte that sits at a
  generated shape's final-point slot is `0x0000` (the factory `0021/0026/0028`
  `val` word is another value), and the shape's own end reference is `0x0000`
  rather than a back-reference; that layout is left to M9.67, since it needs
  the counted-shape rule to be testable (C-6854, C-6856).
