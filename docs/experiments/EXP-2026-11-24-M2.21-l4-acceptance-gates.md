## Question

Do the card-acceptance gates read statically at L3 and catalogued in M2.9 /
M2.4 / M2.19 (wrong `HDD_INFO.TXT` map code, wrong MapDBVer, wrong unit map
code, raw-copy-only edit) stop the EU 2011 launcher at the predicted place when
the full-system emulator (`-M ze0`) boots a mutated card, and does every
predicted verdict agree with the L4 verdict?

## Hypothesis

The launcher's check 1 (`0x50`) compares the card's `HDD_INFO.TXT` line 1 with
the unit record `+0x60` (M2.4 C-5290, M8.C1c C-6881); check 2 (`0x51`) compares
MapDBVer from line 3 positions 5/6/7 with the unit window `+0x70`/`+0x72`
(M2.19 C-5296). Under explicit, declared unit values `QSD-302-100` / `16-16`
(M8.C1c C-6883/C-6884), the offline `hddinfo.py predict` verdict should equal
the L4 launcher verdict for every mutation: ACCEPT → PASS/F5, DIFFERENT MAP
CODE → FAIL/F4 with `VerInf:`/`0x50`, MAP DATA BASE UNMATCH → FAIL/F4 with
`MapDBVer:`/`0x51`. A line-2 edit should not move the verdict (C-5292); a raw
`0x06000000` copy edit should not move L4 but must fail L1 (C-8356).
**Falsifier:** all mutated cards pass like the factory card, or any case
disagrees with its prediction (a disagreement is then a claim correction; a
wholesale pass means finding the missing emulator precondition and a `blocked`
result). A second falsifier: the pinning overrides do not reach QEMU, so the
card-derived values self-cancel the mutation (navigator round 1).

### 3. Controls

- **Positive:** factory card (A) must PASS/F5/ACCEPT/OPENED with 0 `verinf`,
  `mapdb`, `error_proc`, `failsafe` and `navi_map_error` marker lines; line-2
  edit (B) must also PASS.
- **Negative:** C with pinned unit `QSD-302-100` must FAIL F4 with `0x50`;
  E with wrong unit must FAIL F4 with `0x50`; F with card MapDBVer 5 vs unit
  16-16 must FAIL F4 with `0x51`. The F4 reject path is scored only from the
  reject markers: removing them (plus a Navi-create line) flips
  `make_verdict` from `FAIL 1 F4` to `PASS 0 None` — this is the navigator's
  mandatory negative mutation, re-run after the tool change (O7).
- **Self-cancel control (C-ctrl):** C without override must PASS with
  effective = card-derived = `QSD-301-100` in JSON, proving the override is
  load-bearing. A sabotage of `apply_unit_overrides` that ignores
  `unit_verinf` makes the effective value fall back to `QSD-301-100` (O7).
- **L1 scope control (D):** L1 FAILs because the raw copy differs; L4 PASSes.
  Both are recorded; neither is treated as a disagreement with a claim.
- **A first run with auto-detected QEMU** (`/usr/bin/qemu-system-sh4`, no
  `-M ze0`) timed out at 900.92 s with F5 NOT RUN but still PASS/F4/ACCEPT/
  OPENED. It was re-run with the explicit binary (O1/A row); the first run is
  scope evidence, not a pass for the precheck.

### 4. Scope

EU2011 only: one card family, one firmware head, 7 L4 boots plus one D-pin

check; offline predictions for 7 case files. Predictions use declared unit

bytes are committed; scratch is deleted after this EXP is written.

Stated in Hypothesis before the results: wholesale pass of all mutants, any
prediction/L4 disagreement, or overrides that fail to reach QEMU. All three
