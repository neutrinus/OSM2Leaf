## Question

Now that a TMC location record reaches a routing link (M4.16b/M4.16e:
location code → RDSTM link record → ref → level-2 section-2 `(parcel, node,
link)`), do the `LCTBL001` class codes that M4.17 found motorway-pure, and
the TMC record attributes around them, co-vary with a link attribute of
the section-2 graph better than a shuffled label?

## Hypothesis

`class_code` (header `u16` at +14, M4.17) is the TMC location type
(rdstm.md, field 0), so `0x2775` = 10101 = `L1.1` motorway is
motorway-pure by definition. If the section-2 entry class word (`cls &
0xf`, part of the link key C-5150) carries a road class, the road type of a
record (`L1.1` motorway, `L1.2` first class, `L1.3` second class, `L1.4`
third class) predicts the class nibble of the links its refs name, above a
within-table shuffled-label null.

**Falsifier (stated before the 14-table run, after a one-table probe of
table 0):** (a) `class_code` differs from field 0 in any record; (b) the
road-type modal accuracy is within 0.05 of its shuffled null maximum; (c)
the positive control (road identity) fails to beat its null, or the
negative control (`code & 1`) beats its null, which would make the score
meaningless; (d) `L1.1` maps to different modal classes in most tables.

## Method

1. **Sample and hash** as above (`sha256sum`).
2. **Commands** (repo root):

   ```bash
   E=/home/user/scratch/factory-eu
   sha256sum $E/RDSTM001/RDSTM001.DAT $E/RDSTM001/LCTBL001.DAT
   python3 tools/rdstm_class_hint.py --selftest
   python3 tools/rdstm_class_hint.py run $E/RDSTM001/LCTBL001.DAT $E/RDSTM001/RDSTM001.DAT $E/MAPAL001 --top 16
   python3 tools/rdstm_class_hint.py run $E/RDSTM001/LCTBL001.DAT $E/RDSTM001/RDSTM001.DAT $E/MAPAL001 --tables 0 --shuffles 5
   ```

   Per record: join by location code alone (C-5402) to the set-1 link
   record, resolve every ref to its level-2 section-2 entry, take the
   majority `cls & 0xf` of those entries (`--pick majority`, default). The
   record's road = field 6 followed up to 4 hops to a linear of type
   `L1.x`/`L2.x`; its road type is that record's field 0. Score = modal
   accuracy (share of records whose class equals the modal class of their
   group; groups < 20 records pooled), null = the same score with the label
   shuffled within each table, 20 shuffles, seed 1.
3. **Controls.** *Positive:* road identity (the road's location code): a
   road is mostly one class, so it must beat its null. *Negative:* `code &
   1`: carries no class, so it must equal its null. *Independent
   cross-check:* the OSM→level-2 class table of the pinned writer
   (`fa_encode.CLASSES`, second element: motorway 1, trunk 3, primary 4,
   secondary 5, tertiary and below 7; provisional per C-2662) is compared
   with the TMC result; it was not used to choose the score.
4. **Scope.** EU 2011, all 14 set-1 RDSTM tables (14 countries), 247,089
   LCTBL records, 158,445 with at least one resolved link, 1,871,333 of
   1,872,163 refs resolved, 32,240 level-2 parcels in 31 tiles. Level 4 (set
   0), US 2011 and EU 2014 are not run. No firmware reader (M4.49).
5. **Falsifier:** as stated under Hypothesis.

## Interpretation

- **FACT:** `class_code` (M4.17) is the TMC location type, field 0, in
  247,089/247,089 records. `0x2775` = 10101 = `L1.1` (motorway road),
  `0x283c` = 10300 = `L3.0` (order-1 segment, which M4.17 saw as "mixed"),
  `0x4e8e` = 20110 and `0x4e91` = 20113 are point types `P1.10`/`P1.13`.
  The "motorway-pure" codes are pure because the TMC type says so.
- **OBSERVED:** with the location-code join (M4.16b/M4.16e) a record's road
  type predicts the class nibble of its section-2 links: modal accuracy
  0.608 against a null maximum of 0.382 over 158,445 records, with the
  positive control above its null (0.539 vs 0.400) and the negative
  control at its null (0.350 vs 0.350).
- **OBSERVED:** `L1.1` motorway → class 1 in 9 of the 10 tables with
  ≥ 20 motorway records (BE → 4, DK → 2); `L1.4` → 7 in 5 of 6. `L1.2` and
  `L1.3` map per country (CZ, CH, IT, NL, GB, DE, ES, FR: `L1.2` → 4; FI, DK,
  SE: `L1.2` → 3): TMC road classes are national, so their mapping is not
  one table.
- **HYPOTHESIS (generator hint, falsifiable):** the level-2 section-2 class
  nibble is a road class with 1 = motorway, 3 = trunk-like, 4 = primary
  (first class), 5 = secondary, 7 = tertiary and below; this is the order
  the pinned writer already uses for level 2 (`fa_encode.CLASSES`, C-2662
  "provisional"), so the factory data now back its level-2 column for
  motorway, primary, secondary and tertiary. It is falsified if a
  firmware reader (M4.49, M4.40) treats the nibble as something other than a
  class, or if OSM-tagged roads (M4.2) fail to show the same order.
- **UNKNOWN:** classes 2 and 6 (seen for DK motorways, NO first-class roads),
  10–12 (ferries at levels 3–5, C-2662 analogue), and why 34,069 records
  carry no road-level linear.

## Conclusion

M4.31's done-when is met: the pure `class_code` groups are TMC location
types, and the road type co-varies with the section-2 link class far above
a within-table shuffled null, with the join key (TMC location code) and
the corpus (158,445 records, 14 tables) stated; the result is a named
hypothesis for the generator (level-2 class: motorway 1, primary 4,
secondary 5, tertiary 7, matching `fa_encode.CLASSES`). `rdstm.md` gains a
"Road class from TMC road type" note. C-2971/C-2975 (no join) are
superseded by C-5960.
