# EXP-2026-11-19-M9.38: Who reads the decoded page — a read/write watch on the L3 engine

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** `head256.img` (EU 2011 firmware head) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  `us256.img` (US 2011 head) SHA-256
  `70d945d823f93f04cae4e6c7113a723cae3a992ab7a6f9b24e94ce2e006a04da`;
  EU factory `POINT010.DAT.cmp` `d02a8d87…ec3`, US factory `POINT010.DAT.cmp`
  `48812f8c…657`, EU `ADDRE001.DAT.cmp` `bbeb60f2…025`, EU
  `RDSTM001/LCTBL001.DAT` `8cab1775…e9d`.
- **Tools:** `python3 3.15.0`, `zlib 1.3.1.zlib-ng` (decompression only, so the

- **Superseded by:** none

## Question

Which firmware functions read (and write) a decoded map page, attributed per
instruction, with the call chain running for real — and does the chunk engine's
caller reach the POINT walker at all?

## Hypothesis

None / exploratory (the dynamic counterpart of M3.23). **Falsifier:** a watch
that changes a run's `r0`, OUT SHA-256, `sec_reads` or instruction count (the
watch would not be inert), or a walker attributed to a function other than the
one that executed the load.

## Method

1. **Sample and hash.** The four files above; the page bytes are the decoded
   `.cmp` slice (`mutate_refer_poi.decode` then zlib decompress), not a guess.

2. **Commands** (each prints the numbers quoted below):

   ```bash
   # attribution labels (GAP vs START)
   python3 tools/l3_harness/watch.py label archive/head256.img --entry 0x003f5194 0x003f5194
   python3 tools/pdata.py fn archive/head256.img --module Navi.exe 0x003f5194 0x003f5cdc 0x003fbed8 0x003f9254 0x004125a8

   # POINT: the real dispatcher routes the page to the walker
   python3 tools/read_watch_l3.py above archive/head256.img \
     --cmp ~/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.cmp \
     --ind ~/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.ind \
     --build eu2011 --n 1
   python3 tools/read_watch_l3.py above archive/us256.img \
     --cmp ~/projekty/leafre-work/m5.12-us/root-factory/REFER001/POINT010.DAT.cmp \
     --ind ~/projekty/leafre-work/m5.12-us/root-factory/REFER001/POINT010.DAT.ind \
     --build us2011 --n 1

   # POINT: the walker alone, on the swapped page (positive control)
   python3 tools/read_watch_l3.py walk archive/us256.img \
     --cmp ~/projekty/leafre-work/m5.12-us/root-factory/REFER001/POINT010.DAT.cmp \
     --ind ~/projekty/leafre-work/m5.12-us/root-factory/REFER001/POINT010.DAT.ind \
     --page 0x840ba0 --page-len 42848 --build us2011 --n 0,1,2

   # the static walker control still passes (C-2541)
   python3 tools/point_walk_l3.py walk archive/us256.img \
     --cmp ~/projekty/leafre-work/m5.12-us/root-factory/REFER001/POINT010.DAT.cmp \
     --ind ~/projekty/leafre-work/m5.12-us/root-factory/REFER001/POINT010.DAT.ind \
     --page 0x840ba0 --page-len 42848 --build us2011

   # the chunk-engine caller's destination (chain)
   python3 tools/read_watch_l3.py chain archive/head256.img \
     --cmp ~/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.cmp \
     --ind ~/projekty/leafre-work/m5.29-factory-root/REFER001/POINT010.DAT.ind \
     --build eu2011

   # LCTBL candidates (M3.15 list) on the plain LCTBL file
   python3 tools/read_watch_l3.py probe archive/head256.img \
     --buf ~/projekty/leafre-work/m422/eu2011/RDSTM001/LCTBL001.DAT \
     --entry 0x003f020c,0x0040dd40,0x0040de98,0x0040b358,0x004125a8

   # ADDRE candidates (M3.13 chain) on the decoded ADDRE001 blob
   python3 tools/read_watch_l3.py probe archive/head256.img \
     --buf ~/projekty/leafre-work/m5.29-factory-root/REFER001/ADDRE001.DAT.cmp \
     --entry 0x003f56bc,0x003fbed8,0x0040b358,0x004125a8,0x0040114e
   ```

3. **Controls.**
   - *Positive*: `above` on both builds credits the walker through the real
     dispatcher; `walk` alone credits it on the swapped page; `point_walk_l3`
     still returns `result: PASS`.
   - *Negative*: the unwatched half of every buffer records 0 hits; the same
     run with the watch **off** records 0 hits and the same `r0`; a watch range
     outside a mapped region is a `UsageError` at arm time (engine selftest).
   - *Inertness*: `chain` compares watch-on vs watch-off on `r0`, OUT SHA-256,
     `sec_reads` and instruction count — all four must match.

4. **Scope.** EU2011 `Navi.exe` (0x003f5194 walker leaf, 0x003f5cdc dispatcher,
   0x003fbed8 / 0x003f9254 / 0x004125a8 ADDRE path, 0x0040de98 LCTBL path) and
   US2011 `Navi.exe` (0x0041db44 walker, 0x0041e63c dispatcher, 0x00443da8
   chunk caller) on the four files above. The `.cmp` chunk engine itself is
   M9.11/M9.11b; this EXP watches only where the decoded bytes land and who
   reads them.

5. **Falsifier.** A watch that changes any of the four inertness fields, or a
   walker credited to a PC other than the one that executed `mov.w @page`.

## Interpretation

- **FACT:** All watches are inert: every chain run reports
  `control (watch on vs off): IDENTICAL` on `r0`, OUT SHA-256, `sec_reads` and
  instruction count; every watch-off control reports `hits=0`.
- **FACT:** The POINT page is read by one 2-byte `mov.w @page` instruction in
  the walker (`0x003f519c` EU2011, `0x0041db4c` US2011), through the real
  dispatcher (`0x003f5cdc` EU, `0x0041e63c` US) that selects the walker from
  its own literal pool (slot `+0xa8`, same byte in both builds), not by a direct call.
- **FACT:** The chunk-engine caller `0x0041c044` writes/returns the page
  (OUT SHA-256 `283f079d…498b`, `r0=0x17b86`) but the destination is **never
  read** by a guest instruction in that run; the only writes to it are the
  stubbed `memcpy` (`api-w=2`). The `.cmp` chain is decode-only.
- **OBSERVED:** ADDRE readers are `0x003fbed8` (+0x68, and its callee
  `0x003f9254` at +0x7c) and the shared header read `0x004125a8` (+0x8);
  LCTBL's reader is `0x0040de98` (GAP, 8/4/2-byte fields at +0x8/+0x4/+0x2).
- **HYPOTHESIS:** the 2-byte `mov.w` read on the swapped page confirms that
  M3.11b needs a writer of a *swapped copy*, and it is not on the `.cmp`
  decode path.
- **UNKNOWN:** which function performs the byte swap before the walker (the
  chain run does not contain it); the ADDRE/LCTBL entries faulted on `0x0` /
  `0x68` after reading, so more of their consumed fields remain (M3.13/M3.15).

## Conclusion

M9.38 delivers the tracer: `engine.PySh4` records guest loads/stores in-body
(never via monkeypatch), tags `api`/`x` separately, and arms only after setup,
so a watch cannot change a verdict. `watch.py` attributes a hit to the executing
instruction and labels a `.pdata` GAP as its container plus the entry, never the
preceding record's `fn`. On the three corpora the POINT page's reader is the
walker itself (through the real dispatcher on both builds); ADDRE's readers are
`0x003fbed8`/`0x003f9254`/`0x004125a8`; LCTBL's reader is `0x0040de98`. The
`.cmp` chain is decode-only, so M3.11b's swap is not there — M3.11b, M3.13 and
M3.15 get the lists in their blocks.
