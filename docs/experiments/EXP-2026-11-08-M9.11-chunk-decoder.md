- **Superseded by:** none

## Question

Does the firmware's own chunked `.cmp` reader, `fn 0x0041c7e8` in `Navi.exe`
(sec0), run under PySh4 on the three POINT010 pairs and return page `0x840ba0`
byte-identical to `cmpind.decode`, reject a corrupt `.ind`, and fail on a wrong
table field (M9.11 done-when)?

## Hypothesis

The chunk loop and the zlib code it calls run to completion on real bytes with
only host stubs for the allocator and coredll imports, and the page comes out
byte-identical. **Falsifier:** (a) a completed run whose output differs from
`cmpind.decode(...)[0x840ba0:0x840ba0+42848]` on any pair refutes the decoder
path; (b) a corrupt `.ind` the firmware accepts refutes the rejection path; (c)
a swapped `+4`/`+8` table field that still returns the page means the layout is
not what the loop reads. A run that stops on an unmapped access is recorded as
blocked, not as a refutation.

## Observations

### 1. Engine fixes (found by traces of the stops)

```
engine.IllegalInstruction: system opcode 0x0000469d at 0x005422c6 is not modelled
```
`0x469d` = `shld r9,r6` (inflate's bit shift). Fixed: `shad`/`shld`
(`0x469c`/`0x469d`) in `_exec_system`.

```
trace: 0x54238c braf r0 (0x0023), r0=0x94 -> next PC 0x542397, not 0x542424
```
`braf`/`bsrf` read the m field; SH-4 encodes the register in n (`0000 nnnn
0010 0011`). inflate's jump table branched to `pc+4+Rm`. Fixed: `braf`/`bsrf`
use `rn`.

```
trace: 0x5452b2 mov.w @(disp,PC),r1 -> r1 = 0x0000f914 (expected 0xfffff914)
engine.UnmappedAccess: no mapped region covers 0x300106b4..0x300106b8
```
Byte and word loads into registers zero-extended; SH-4 `mov.b`/`mov.w`
sign-extend. Fixed: every register-destination byte/word load goes through
`_load_signed`.

`engine.py --selftest` = `OK (19 checks, 2 skipped)` (new checks: `shad/shld
...`, `braf/bsrf take the target from the n field`, `mov.b/mov.w loads into a
register sign-extend`). Regression: `point_walk_l3.py walk` = `result: PASS`
(n = 0, 1, 2, 3, 10, 500, 998, 999, 1000 match `parse_page`); `skip` = `result:
PASS`.

- A zero-length `memcpy` raised a usage error in the stub. Now a no-op.

## Interpretation

- **FACT:** `fn 0x41c7e8` takes `(ctx, &offset, length, count)`, walks `count`
  entries from `*(ctx+28)`, reads the destination from `S+40`, and returns the
  bytes copied or `-1` (C-2151).
- **FACT:** with the 17-entry `inflate_mask` table available, the firmware chunk
  loop and zlib 1.1.3 inflate produce page `0x840ba0` byte-identical to
  `cmpind.decode` on the factory, S1 and S2 pairs (C-2154). Without the table the
  run fails (`-1`).
- **FACT:** the table is read at `0x54369e` as `hold & inflate_mask[n]`, and the
  12 + 8 reads are all inside its 17 entries. No other sec1 object is read on
  these paths.
- **OBSERVED:** a corrupt `.ind` is rejected (`-1`), and a swapped field fails
  cleanly (C-2156).
- **HYPOTHESIS:** the 17 values equal `Navi.exe` sec1 bytes. They come from
  public zlib source (`2^n - 1`); the sec1 bytes are not decoded (M1.2f open),
  so this is not checked against the firmware. A wrong value at an index read
  would change the bit extraction, which the byte-identical output argues
  against, but this is a consistency argument, not a byte comparison.
- **HYPOTHESIS:** coredll `#1044` is memcpy, and the zcalloc and zcfree
  trampolines are calloc and free (the call shape fits; the copies are checked
  by the output compare).
- **UNKNOWN:** the caller of `fn 0x41c7e8` (C-2064); the other 148 chunks; any
  other card.

## Conclusion

The M9.11 firmware path passes: on the three pairs the firmware's chunk loop and
zlib 1.1.3 return page `0x840ba0` byte-identical to `cmpind.decode`, the corrupt
`.ind` is rejected, and the swapped `+4`/`+8` field fails cleanly. The earlier
"blocked on sec1" verdict (Observation 3) was true for the raw section and wrong
about the cause: the path reads one 68-byte constant table, which the harness
supplies from public zlib source. The provenance is disclosed everywhere; closing
it needs M1.2f.

What is still missing from the done-when: `targets.json` `cmp_ind_reader` is not
filled. `runner.py` has no entry kind that calls a firmware function with memory
setup (the `module` kind passes register arguments only). So the status is
`blocked`, with the follow-up M9.11b (runner firmware-call kind), not `done`.

Claims: C-2150 to C-2156 in `docs/research/claims.md` (M9.11 block).
