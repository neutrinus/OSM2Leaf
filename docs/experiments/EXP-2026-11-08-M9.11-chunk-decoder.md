## Question

Does the firmware's own chunked `.cmp` reader, `fn 0x0041c7e8` in `Navi.exe`
(sec0, plain), run under PySh4 on the three POINT010 pairs, return page
`0x840ba0` byte-identical to `cmpind.decode`, reject a corrupt `.ind`, and fail
on a deliberately wrong table field (M9.11 done-when)?

## Hypothesis

The chunk loop is self-contained in sec0: it reads the table entries, calls the
one-shot zlib wrapper `0x542148` (zlib 1.1.3, plain sec0) and `memcpy`, and the
zlib code needs only host stubs for the allocator and the coredll imports.
Then PySh4 completes the call with `r0` = bytes copied (42,848) and the output
equal to the reference slice.

**Falsifier:** (a) a completed run whose output differs from
`cmpind.decode(...)[0x840ba0:0x840ba0+42848]` on any pair refutes the decoder
path; (b) a corrupt `.ind` that the firmware accepts refutes the rejection
path; (c) the swapped `+4`/`+8` table field must not return the page; if it
does, the table layout is not what the loop reads. A `BLOCKED` stop is recorded
as blocked, not as a refutation of the chunk loop.

   The tool builds the 149-row table from `.ind` (`+4` = next offset minus this
   offset, last = `csize`; `+8` = `i*65536`; `+12` = `min(65536, usize-off)`;

   that holds the offset (`*(ctx+28)` = entry 132) with `count` = chunks spanned
   (1 for this page), writes the offset cell, `*(ctx+308)` (scratch buffer) and
   `S+40` (destination). It maps the sec0 text at its module realaddr and stubs
   the four entry points listed under Inputs; any access the engine cannot map
   stops the run with `BLOCKED` and the section of the VA.

3. **Controls.** *Positive:* `point_walk_l3.py walk` and `skip` (M9.21 PASS, run

4. **Scope.** One function, one page (`0x840ba0`, chunk 132 only), three pairs,
   one chunk walk per run (count 1). Not covered: the other 148 chunks, the POI
   reader, any card other than the three pairs. Modules: `Navi.exe` sec0 only;

   runs.
5. **Falsifier.** Stated under Hypothesis.

## Observations

### 1. Engine fixes found by this run

Each was found by a trace of the instruction, PC and registers at the stop.

```
engine.IllegalInstruction: system opcode 0x0000469d at 0x005422c6 is not modelled
```
`0x469d` = `shld r9,r6` (inflate's bit shift). Fixed: `shad`/`shld` (`0x469c`,
`0x469d`) in `_exec_system`.

```
trace: 0x54238c braf r0 (0x0023), r0=0x94 -> next PC 0x542397, not 0x542424
```
`braf`/`bsrf` read the m field; SH-4 encodes the register in n (`0000 nnnn
0010 0011`). inflate's state-machine jump table branched to `pc+4+Rm`. Fixed:
`braf`/`bsrf` use `rn`.

```
trace: 0x5452b2 mov.w @(disp,PC),r1 -> r1 = 0x0000f914 (expected 0xfffff914)
engine.UnmappedAccess: no mapped region covers 0x300106b4..0x300106b8
```
Byte and word loads into registers zero-extended; SH-4 `mov.b`/`mov.w` sign-
extend. The stack pointer moved up by `0xf914`. Fixed: every register-
destination byte/word load goes through `_load_signed`.

Engine self-test after the fixes: `engine.py --selftest` = `OK (19 checks, 2
skipped)`, with three new checks (`shad/shld ...`, `braf/bsrf take the target
from the n field`, `mov.b/mov.w loads into a register sign-extend`). Regression:
`point_walk_l3.py walk` = `result: PASS` (n = 0, 1, 2, 3, 10, 500, 998, 999,
1000 match `parse_page`), `skip` = `result: PASS`.

### 2. Harness fixes (not firmware)

- The walk first started at entry 0 (`*(ctx+28)` = table base). The firmware
  walks from the entry `*(ctx+28)` points to, so the first run inflated chunk 0
  for a request in chunk 132. Fixed: the tool starts at the entry that holds the
  offset. The same sec1 stop follows (Observation 3).
- A zero-length `memcpy` raised a usage error in the stub. Fixed: a zero-length
  copy is a no-op.

### 3. Factory pair (`run`, exit 4)

```
BLOCKED: no mapped region covers 0x00574df8..0x00574dfc (text, cmp, stack, ctx, tab, out, cache, heap)
  firmware access lies in sec@0055d000 COMPRESSED of Navi.exe
  before the stop: insns=4694 mod-calls=1 memcpy=1 calloc=6 free=1 last_pc=0x0054369e
```

`memcpy=1` is zlib's own stored-block copy inside `inflate_blocks` (COREDLL
`#1044` at `0x54350c`), not the chunk loop's copy.

### 4. S1 pair (`s1-recomp`, exit 4)

Same output as the factory pair (the `.cmp` is byte-identical, so the run is the
same): `insns=4694 mod-calls=1`, stop at `0x00574df8`.

### 5. S2 pair (exit 4)

```
BLOCKED: no mapped region covers 0x00574dfc..0x00574e00 (text, cmp, stack, ctx, tab, out, cache, heap)
  firmware access lies in sec@0055d000 COMPRESSED of Navi.exe
  before the stop: insns=143454 mod-calls=13 memcpy=5 calloc=6 free=1 last_pc=0x0054369e
```

The S2 walk makes 13 `#2006` calls before the stop. Its dividends are
`0x789c` (the header) then `0xb407f`, `0x79038c90`, `0xb62e1`, `0x7f065a53`, …,
which are not header values, so `#2006` is used for other divisions too. The
divisors were not recorded; those results are not verified (see Interpretation).
The factory run stops after one call, so its blocker does not depend on them.

### 6. The stop

The access is `mov.l @(r0,r3),r2` at `0x54369e` (`0x023e`) with `r0 = 0x18`
and `r3 = 0x574de0`, inside inflate's state machine after the header check. The
same instruction stops S2 with `r0 = 0x1c`. `0x574df8` lies in `Navi.exe` sec1
(`realaddr 0x55d000`, vsize `0xff16ae`, `psize 0x457c`, `COMPRESSED`; C-2126,
C-2128). The sec0 mapping ends at `0x55cd16`. `cecompress.py detect` on the
17,788 sec1 bytes reports `method none` (`lzx: invalid block type 0`, `lzss:
match at output 1 refers 258 bytes back`); `cedecomp.py` raises
`UnsupportedDecompression` (M1.2f open).

### 7. Negative controls

- **corrupt `.ind` (factory, `--mutate corrupt-ind`), exit 0, PASS:**
  ```
  firmware: r0=-1 copied=42848 insns=638 memcpy=0 calloc=4 free=4 mod-calls=0
  verdict: PASS (firmware rejects the corrupt .ind)
  ```
  The moved chunk starts with `0x47`. Its low nibble is 7, not zlib's
  compression method 8, so inflate rejects it before the `%31` call (`mod-calls=0`).
  The reference `cmpind.decode` also rejects the corrupt pair (selftest).
- **swapped `+4`/`+8` (factory, `--mutate swap-4-8`), exit 4, BLOCKED:**
  `insns=4676 mod-calls=1`, stop at `0x00574df8` (the same table read). The
  swapped `+4` is read as `avail_in`, so the firmware is not rejected before the
  sec1 read: **this control is undecided**. The table layout is not yet shown
  to be what the loop reads.

## Interpretation

- **FACT:** `fn 0x41c7e8` takes `(ctx, &offset, length, count)`, walks `count`
  entries from `*(ctx+28)`, and writes the destination from the caller slot
  `S+40`; it returns the bytes copied or `-1` (C-2151). The 20-byte row layout
  is read from the code; `+16` is confirmed as the stream pointer by the header
  bytes (`0x789c` on the real chunk, `0x47` on the moved one).
- **FACT:** The four harness and engine faults (shift opcodes, `braf`/`bsrf`
  register field, unsigned byte/word register loads, zero-length `memcpy`) were
  real. The engine ones change the path of real zlib code; each is fixed with a
  self-test, and `point_walk_l3` still passes.
- **OBSERVED:** On the factory and S1 pairs the firmware passes the zlib header
  check and then stops at a table read in compressed sec1, before any chunk is
  inflated to its end. On S2 it runs much further and stops at the same
  instruction (`0x54369e`) on a different table entry. So the chunk decoder is
  **not** self-contained in sec0.
- **OBSERVED:** `--mutate corrupt-ind` is rejected by the firmware with `r0=-1`.
  This is one negative with a control (the reference rejects too); it is not the
  full rejection test, since the run never reaches the inflate tables.
- **HYPOTHESIS:** the table at `0x574de0` is zlib's constant data (inflate's
  length/distance tables), placed in sec1. Not checked against bytes, since sec1
  is compressed.
- **HYPOTHESIS:** coredll `#1044` is memcpy and `#2006` is `%`-like, with the
  zlib allocator trampolines calling `calloc`/`free`. Only the header-check use
  of `#2006` is supported by the call shape; the others are unverified.
- **UNKNOWN:** the caller of `fn 0x41c7e8` (C-2064, still not located); the
  table layout on a path that runs to the end (the swapped-field control did not
  decide it).

## Conclusion

M9.11's done-when is **not met**: no pair returns page `0x840ba0` byte-identical,
and the swapped-field control is undecided. The status is `blocked`, with
`Unblock: M1.2f` (decode Navi.exe sec1, the `DECOMP_BLK` codec). The TODO's
re-scope note ("the chunk loop is runnable now") is too optimistic: the loop is
runnable, but the inflate code it calls reads its constant tables from sec1.
The engine and harness fixes stay in this PR: each is a correctness fix on real
firmware bytes, covered by a self-test, and needed to reach this result.

Claims: C-2150 to C-2156 in `docs/research/claims.md` (M9.11 block).
