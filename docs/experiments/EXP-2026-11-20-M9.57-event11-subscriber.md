# EXP-2026-11-20-M9.57: nobody subscribes the data-access task to object-store event 11

- **Status:** done (counted negative with positive controls)
- **Date:** 2026-11-20
- **Sample:** `archive/head256.img` (IMG256, SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`), EU2011
  build A: all 149 modules of the segment at image start `0x200200`
- **Tools:** Python 3.13.18; `tools/event_subs.py` (this task),
  `tools/sh4dis.py`, `tools/sh4xref.py`, `tools/cerom.py`
- **Claims:** C-6000–C-6006
- **Supersedes:** none (answers the UNKNOWN of C-5907)
- **Superseded by:** none

## Question

M9.52 found that the data-access task (`HDL_MapMainTask`, id global
`0x011fff58`, EU2011) writes 3 into its state word only in `0x003f6b1c`, the
handler of object-store event `0x07d0` sub 11 with `+28 = 16` (C-5904), and
did not find the subscription among `Navi.exe`'s literal call sites (C-5907).
Which call, in which module, subscribes the task to event 11?

## Hypothesis

One of three places holds the subscription: a `Navi.exe` site whose event id
is not a literal, an `OBJ_Event_setPrmForMP` site, or another module.

**Falsifier of the negative:** one row of the census, in any module, whose
sub is 11 and whose task is `*0x011fff58`, an argument, or unresolved; or a
census that does not contain the task's known subscriptions (subs 100, 199,
13, 6: the positive controls).

## Method

1. **Sample and hash.** The first 128 MiB of `archive/head256.img` (hash
   above); every module of the CE segment at `0x200200`.
2. **Commands.**

   ```bash
   python3 tools/event_subs.py --selftest
   # the whole census, with the known sub-100 site as positive control
   python3 tools/event_subs.py archive/head256.img --expect-site 0x003eb99c
   # the task's own subscriptions against its event table
   python3 tools/event_subs.py archive/head256.img --task 0x011fff58 \
       --handler-table Navi.exe:0x001796f4:6 --expect-site 0x003eb99c
   # every subscription with sub 11, any task
   python3 tools/event_subs.py archive/head256.img --sub 11
   # the question itself (exit status 1 = no row)
   python3 tools/event_subs.py archive/head256.img --task 0x011fff58 --sub 11
   # the two rows the walk does not resolve, read by hand
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x0037a75c --count 4
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x0037a838 --count 6
   # the handlers of the two rows without a subscription
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x0042af34 --count 2
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x003f6b1c --count 36
   # hand-built 0x07d0 messages: functions that address the task
   python3 tools/sh4xref.py archive/head256.img Navi.exe --image-start 0x200200 --to 0x011fff58
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x005262e4 --count 20
   python3 tools/sh4dis.py archive/head256.img Navi.exe --image-start 0x200200 --va 0x0039d712 --count 8
   ```

   `event_subs.py` takes each module's own import table (the slot address is
   relocated to the section's real address, which `cerom.py thunks` does not
   do for DLLs), finds the import stubs of `OBJ_Event_setPrm` and
   `OBJ_Event_setPrmForMP`, lists every `jsr`/`bsr` to them (one load of the
   stub address into a callee-saved register counts once per `jsr` through
   it), and walks back from each call to the source of the task and sub
   arguments. A site whose task or sub is the function's own argument is a
   helper: it is listed once per caller with the value read at that call.
3. **Controls.** *Positive:* the four subscriptions of the task that M9.52
   read by hand (C-5905) must appear with the right sub: `0x003eb99c` (100),
   `0x003eb9d4` (199), `0x003eba06` (13) and the helper `0x004034c0` called at
   `0x003ebbec` (6); `--expect-site` makes a census without the first one
   exit 2. *Negative:* `--task 0x011fff58 --sub 11` must print no row and
   exit 1; the selftest's synthetic module has a sub-11 filter that must find
   nothing and a sub-100 filter that must find one site.
4. **Scope.** 149 modules read, 149 executable sections, 0 compressed. 10
   modules import one of the two functions; 131 call sites (98
   `OBJ_Event_setPrm`, 33 `OBJ_Event_setPrmForMP`); 143 rows after helpers
   are expanded through 30 caller sites. Not covered: a subscription block
   filled without either function (not seen: the only reference to the
   `OBJ_Event_setPrm` import slot `0x0055d290` in `Navi.exe` is its stub);
   a stub address that reaches a `jsr` through memory; code that sends
   `0x07d0` by hand from a task id it did not load from `0x011fff58`; the
   second and third ROM segments (kernels, no `Navi.exe` task runs there);
   US2011.
5. **Falsifier.** As in the Hypothesis: any sub-11 row for the task, or a
   missing positive control.

## Interpretation

- **FACT:** in EU2011 build A no call of `OBJ_Event_setPrm` or
  `OBJ_Event_setPrmForMP`, in any of the 149 modules, subscribes any task to
  sub 11 except the two sites above, whose tasks are `*0x011fff8c` and
  `*0x011fffa8`. The data-access task subscribes subs 1, 6, 13, 100 and 199.
- **FACT:** the task's event table has six rows; four have a subscription
  the census finds, two (11 and 12) have none, and the handler of 12 is
  empty.
- **OBSERVED:** no function that addresses the task builds a `0x07d0`
  message by hand.
- **HYPOTHESIS:** rows 11 and 12 are left over from a build with more
  position events. The sub-11 handler has the shape of a car-position event
  handler; `OBJ_CarPos_setEventFactor` takes a factor mask (both sites in
  `Navi.exe`, `0x0033741e` and `0x0051c7a0`, pass 4), so `+28 = 16` would be
  one factor bit. Not tested.
- **UNKNOWN:** whether any run-time path of this build puts the task in
  state 3. No static path does.

## Conclusion

The search the task asked for is negative and counted, with the task's four
known subscriptions found by the same method. State 3 has no sender in this
firmware, so the `--event 11:16` stand-in of `datask_l3.py` models nothing a
card can cause and stays a test switch only. This agrees with M9.53's run
result that the map is served in state 2, where the mount already ends: the
mount model needs no event 11. `docs/format/firmware.md` now says so in the
event table; claims C-6000–C-6006; C-5907 points here. The tool
`tools/event_subs.py` is general: it lists who listens to which object-store
event (131 sites), which names the receiver of any `0x07d0` message in later
work.
