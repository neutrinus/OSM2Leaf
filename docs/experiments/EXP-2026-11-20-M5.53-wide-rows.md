## Question

Can `tilewriter` write OSM roads into a section-1 level-1 `0x2146` directory of a real EU2011 tile, and what is the record grammar of the `0x2146`–`0x2946` "kinds" that M5.22 found unsafe to mutate?

## Hypothesis

Header word 0 of a section-1 directory is its size in `u16` words (`0x2046` = 12 + 32 × 516 bytes). A `0x2n46` directory is then not a `0x2046` directory plus an `n*512`-byte tail, but one whose **n rows carry a 1,024-byte body**; reading every row as 512 bytes (`clarion_tile.read_dir`) shifts every later tag and pair, which would produce exactly M5.22's `0xffffffff` pair fields, non-zlib "records" and aliased block offsets. If so, every record of every directory decodes once rows have the right width, and a written parcel can be spliced like a `0x2046` one.

**Falsifier (stated before the result):** any directory where the number of wide rows found by the row model differs from `n = (kind − 0x2046) >> 8`, or the rows do not end at `off + 2*kind`, or any record at its model position is not a whole zlib stream inflating to its declared `X` words, or two row blocks overlap; for the splice: `verify_factory`/`cardcheck`/`l2check` failing, or any byte outside directory `(76,941)` changing in the factory part of the tile.

## Interpretation

- **FACT (C-5270):** Section-1 level-1 header word 0 is the directory size in `u16` words, and `0x2n46` = a `0x2046` directory with exactly n 1,024-byte rows, no tail (1,855/1,855 directories on 45 EU2011 tiles, n up to 22). M5.22's tail model happened to round-trip because `clarion_tile` preserves unmodelled bytes; its 0x2946 "0-byte tail" was its 4,096-byte tail limit.
- **FACT (C-5271):** Wide-row layout and block order as in `docs/format/map-tiles.md`; the width is decided by bit 31 of the row's first body word. All 2,443,997 records of the corpus are whole zlib streams at the model's positions; no block overlaps.
- **FACT (C-5273):** M5.22's "non-zlib blocks", `0xffffffff` pair fields and aliased block offsets (C-2811, C-2812) are the 512-byte misreading, not a property of the data. The `shared_slot_blocks` heuristic in `tilewriter` was built on that misreading; it is left in place (it only makes the `0x2046` path append instead of rewriting in place) so the M5.4/M5.44 outputs do not change.
- **OBSERVED (C-5272):** the four sub-records are a 2 × 2 split of the parcel (8,611/8,611 codes follow the rule). In the one case dumped, the flagged parent record has no layer-0 table entry and no names-section words (`w[17..18] = 0`) while its four sub-records carry layer 0 and names. **HYPOTHESIS:** a dense parcel stores part of its content (layer 0 + names) per quarter; the firmware's use is UNKNOWN.
- **FACT (C-5274), L2 only:** `tilewriter` splices OSM ways into `0x2146` `(76,941)`; the written parcel's sub-records are dropped with its old even record, the row narrows, the directory becomes `0x2046`, and every other record keeps its bytes (`verify_factory` model-level compare + the byte diff confined to the directory). `cardcheck` PASS, `l2check --semantic-tiles` PASS, readback 16/16 within 1 m. Whether the unit draws a parcel whose dense quarters were replaced by one record is not known (rule 13; the record size limits are the same as on the `0x2046` path).
- **Deviation from the Done-when token (C-5275).** The block asks the precheck to print `spliceable=10 preserve-only=10` on the generated tile. That token assumed `0x2146` stays classified preserve-only while the spliced directory turns into `0x2046`. Because `parcel_census` classifies by kind and `0x2146` is now spliceable, the factory tile itself now prints `spliceable=14 preserve-only=6`, and so does the generated tile. The measurement the token stood for — one directory more is written and now plain `0x2046` — is printed by the new by-kind line: `narrow(0x2046)=10 wide(0x2n46)=10` (factory: `9` / `11`). Printing the old token would have meant mislabelling four writable directories.
