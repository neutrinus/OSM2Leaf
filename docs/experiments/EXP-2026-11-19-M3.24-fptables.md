# EXP-2026-11-19-M3.24: Function-pointer tables in `Navi.exe` sec0 rodata and sec1 `INIT`

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** `archive/head256.img` (EU 2011 IMG256), SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`; US2011
  `archive/us256.img` (SHA-256 prefix `70d945d823f93f04`) for one count only
- **Tools:** Python 3.13.18; `tools/fptables.py` (new, `--selftest`),
  `tools/nk_decomp.py` (sec1 and pdata), `tools/callgraph.py` (read-only, graph
  build), `tools/sh4dis.py` (listings)
- **Claims:** C-3550–C-3559
- **Supersedes:** none
- **Superseded by:** none

## Question

Which tables of code pointers exist in the readable data of `Navi.exe` (EU2011)
— sec0 rodata and the stored bytes of sec1 `INIT` — which function indexes
each, and does any of them hold the `POINT`/`ADDRE`/`LCTBL` readers?

## Hypothesis

H112: the indirect calls of the 1,167 functions with no static caller go
through runs of code pointers in sec0 rodata and sec1, and tying each run to
its loader explains most of the 395 unresolved `jsr @Rn`. The `Lv*` strings in
sec1 sit next to a pointer table used by a tile/level reader.

**Falsifier:** (a) the scan does not find M3.26's hand-found table `0x0017ab38`
with its user `0x00419c38` (the scan is wrong); (b) shifting every word by a
few bytes finds about as many tables as the real scan (the matches are chance);
(c) a reader VA occurs as an aligned word in a table — then it *is* called
indirectly and "called directly" is wrong.

   Definitions (in the tool): a table is ≥ 3 code pointers (`START` or `GAP`)
   at one stride, 4…64 B; stride 4 allows NULL slots (≤ 16 in a row); `INSIDE`
   ends a run; each word joins one table (smallest stride wins). A user is the
   function owning a `mov.l @(disp,PC)` whose literal is the base or an entry
   address (*exact*), or lies in the first row before the pointer column
   (*prefix*; a prefix value whose word reads as text is dropped). Pool words
   are skipped while scanning code (H112 rule).
3. **Controls.** *Positive:* M3.26's table `0x0017ab38` (20 words, state x
   kind) with user `0x00419c38` must be found. *Negative:* `--shift ±2` and
   `--shift 0x10` add a constant to every word before classifying, which
   destroys real pointers but keeps the byte statistics; `0x005628e8` and the
   `Lv*` block must hold no code pointer if they are data. Selftest: 12 cases
   (strided rows, sparse matrix, hole limit, shift, IAT skip, pool skip, prefix
   string filter, data refs, reverse reach).
4. **Scope.** EU2011 `Navi.exe` only: sec0 rodata `0x31dd9c` B (816,999 aligned
   words) and sec1 stored bytes after the IAT `0x172e4` B (23,737 words).
   Excluded: BSS (written at run time; `0x00d53500` is there), `braf` jump
   tables inside code, vtables written by constructors into BSS objects, other
   modules. US2011: one total, not curated.
5. **Falsifier.** As stated under Hypothesis, (a)–(c).

## Interpretation

- **FACT (C-3550):** EU2011 `Navi.exe` has 69 code-pointer tables in its
  readable data (62 sec0, 7 sec1); 481 of the 1,167 functions with no static
  caller are entries. The real scan finds 7–17× more tables than the shifted
  controls, which is the noise floor of the `GAP` class.
- **FACT (C-3551):** the tables explain few of the unresolved calls: 21 of 395
  `jsr @Rn` sites are in table users. 620 of the uncalled functions are code
  literals (callbacks passed as arguments). The rest of the indirect calls are
  object/argument calls, which a data scan cannot resolve.
- **FACT (C-3552):** sec1 `INIT` holds a shell command table (`0x0055ddfc`) and
  three sparse state x event matrices; `0x0055e348` is a 5 x 15 matrix
  dispatched by `0x003335c0` with the state at `*0x00618650`.
- **FACT (C-3553):** `0x0017a0a4` is a message dispatcher (`fn 0x004124dc`,
  message id `u16 @(8,msg)`) whose entries are one or two calls above the
  LCTBL/INDEX load `0x004125a8`, the `0x00d53500` writer `0x00412ac0`, the
  POINT access path `0x003fbed8` and `0x003fcbf0`/`0x003fd390`.
- **FACT (C-3554):** no table holds a POINT/ADDRE/LCTBL reader VA; they are
  direct callees under table entries. The POINT walk `0x003f5194` and the
  chunk engine `0x0041c7dc` are reached from no table entry within 4 calls.
- **OBSERVED (C-3555):** the `Lv*` names are in a data block with no code
  pointer and no direct reference; it is not a function-pointer table.
- **HYPOTHESIS (C-3555):** `Lv*` and the `RT0…RT5`/`GS`/`WK` tag groups are a
  debug/log category set reached by base + index from `fn 0x00340f18`, not map
  levels; the lead for M3.5/M3.6 is weak.
- **FACT (C-3556):** `0x005628e8` is a data record (pointers into sec0 data),
  not a dispatch table.
- **OBSERVED (C-3557):** the three `0x00d53500` functions load no table; the
  per-family reader vtable the board expected is not a static table — it is
  the `0x0017a0a4` message map one or two calls above them.
- **UNKNOWN (C-3558, C-3559):** the roles of 59 of the 69 tables; whether the
  20 unreferenced tables are reached by base + offset of a larger struct.

## Conclusion

`docs/format/firmware.md` now lists the 69 tables (VA, stride, slots, users,
role where read). Answer to the task: **no** table contains the `POINT`,
`ADDRE` or `LCTBL` readers; the table that sits above the REFER/LCTBL access
path is `0x0017a0a4`, indexed by message id in `fn 0x004124dc`; the `ADDRE`
path and the POINT name lead are reached from the `{id, fn}` tables at
`0x00039d5c…0x00039fec`. The `Lv*` block is data, unreferenced directly (tie
to `fn 0x00340f18` is a hypothesis). The table edges (`--edges`, 1,113) are
ready for M3.23's reachability; `callgraph.py` itself was not changed.
