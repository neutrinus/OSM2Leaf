## Question

Where does a GPS frame received by `navdrv.dll` end up as the position the
navigation map uses, and what exact guest VA can M8.H31 read to see the
vehicle move? Does the task's falsifier fire — is that word only written at
startup?

## Hypothesis

The receiver frames reach `Navi.exe` through the `NAV1:` stream driver, are
decoded by an SNSWrapper task, published on an OSM message and an object-store
event, and end in the same packed COORD001 word that M8.H19 found at
`0x00d940e4`. **Falsifier:** that word is never written after start (then it
is a request parameter, not the car position). **Stop:** if more than one
process is involved, document the first two hops and the final variable.

## Observations

**O1 — the build-A consumer is `Navi.exe`, not a DLL.** There is no
`NAVDRV.dll` import and no `0x800f2000` literal in build A; `navdrv.dll`
registers `NAV1:` (UTF-16 at `0x039e13ec`) while `Navi.exe` opens
`L"NAV1:"` in function `0x00374d14` at `0x00374d14+…` via import slot
`0x0055d064`, and opens `EVENT_NAV_CYCLE_DATA` via slot `0x0055d0xx`. The
handles live at `0x01205020` / `0x01205024`. `Vehicle.exe` imports
`DeviceIoControl` for telematics only.

**O2 — the fix decoder.** Function `0x003752e8` copies the 36-byte driver
record to a local buffer, reads two u16s at `+28` and `+34`, performs a
floating divide (`_divls` thunk `0x003d13f4`) and calls functions
`0x00374e0c` (ring write + `OSM_MsgSend`, OSMDLL import slot `0x0055d8d4`,
target task handle `*0x011fff78`) and `0x00374edc` (status message). The
16-byte records go into a 256 × 16-byte ring at `0x006239b0`, indexed by
`u16 *0x006255e0 & 0xff`. `function 0x00375040` builds host→driver frames with
`DeviceIoControl(0x80102010)`; `function 0x00375158` reads status via `0x80102008`.

**O3 — the object-store hop.** Function `0x00473388` reads the SNSW record,
`0x0046f540` builds a 44-byte `OBJ_GpsInfo` block (mode flags `+0`, values
`+4/+8/+12/+14/+16/+42`, an explicit ×10 at `0x0046f676`) and calls
`OBJ_GpsInfo_write` through import slot `0x0055d840`. The deg/min/sec×100
family matches C-8249; individual field names remain HYPOTHESIS.

**O4 — the final word.** The literal `0x00d940e4` is referenced 8 times in
`Navi.exe`, all in pdata STARTs. Writers: init `0x003eba78` (`0x003ebbda`),
event sub 11 handler `0x003f6b1c` (`mov.l r2,@r3` at `0x003f6b36`, with the
`0xa6a1cde3` fallback) and event sub 6 handler `0x00403564` (`0x004035a0`,
mask compare `0xffff7700`); five other functions only read it. The event
table at `0x001796f4` maps `{0x00403564, sub 6}` and `{0x003f6b1c, sub 11}`.
The **falsifier does not fire**: the word is written after start.

**O5 — encoding and reader.** The word is
`(32768 + 192*lat)<<16 | (52742 + 128*lon)`, i.e. 1/192° latitude and 1/128°
longitude (≈600 m; `tools/coord.py`). US uses `0x00cc1ce4`, same encoding.
`tools/ze0_position.py read --monitor SOCK` sends HMP `x /1wx 0x00d940e4`,
parses the `ADDR: 0xWORD` reply and prints/decodes the position; it also
accepts `--file IMAGE --offset` for a synthetic memory image. Its selftest
passes 13 checks: exact grid point `0xa640d686` → (51, 17), byte swap changes
the position, short reads and empty HMP replies are refused, and arbitrary
points are within half a grid cell.

## Interpretation

- **FACT (C-7260, C-7261, C-7262):** build-A consumer `NAV1:`/`EVENT_NAV_CYCLE_DATA`
  in `Navi.exe` (O1); SNSW ring and OSM message hop (O2); host→driver frame
  write path (O2).
- **FACT (C-7263, C-7264):** `OBJ_GpsInfo` block and its ×10 scaling (O3);
  the final position word and its post-start writers, which refute the
  falsifier (O4).
- **FACT (C-7265):** the packed COORD001 encoding and resolution from
  `tools/coord.py` (O5).
- **FACT (C-7266):** `tools/ze0_position.py` exists, reads HMP or a synthetic
  image, and its selftest is registered in `tools/selftest.py` (O5).
- **HYPOTHESIS (C-7267):** exact receiver-frame→degree constants in
  `function 0x003752e8` (FPU code) and the names of the `OBJ_GpsInfo` fields.
- **OBSERVED (C-7268):** the kernel-side object bridging navdrv's
  `0x800f2000` to `EVENT_NAV_CYCLE_DATA` is not pinned by a build-A literal;
  the consumer side is measured from the event name and the SNSW ring.
- **FACT (C-7269):** `LOC_map` consumes a 32-byte mesh/x/y message
  (`0x0fa0` sub 119, M9.66); the driver→word path above is the upstream half.

## Conclusion

M8.H29 is done: the chain is
`SCI7 → navdrv ring → 0x800f2000 → NAV1:/EVENT_NAV_CYCLE_DATA → Navi.exe
SNSW ring (0x006239b0) → OBJ_GpsInfo → OBJ_CarPos event 6/11 → 0x00d940e4`,
and `tools/ze0_position.py` can read that word from a live QEMU monitor
socket. The same word is the map centre's upstream source via the existing
`LOC_map` consumer. The remaining unknowns are semantic field names and the
exact FPU constants, not the observable word.
