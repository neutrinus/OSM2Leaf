## Question

Can `runner.py run` call a function at a module VA of a memory map without a
hand-written loader list, can the stub dispatcher hand a target handler the
argument registers, and does the Ghidra back end have one documented entry
script that the runner and the docs agree on? Does the real-image path (CE
ROM TOC, memory map, image bytes) reach the engine?

## Hypothesis

The three pieces can be built in pure Python on `PySh4`, with no Ghidra. The
real-image path maps `Navi.exe` sec0 and stops at the engine's byte-order limit,
because PySh4 is big-endian and the firmware is little-endian (C-2546). The
falsifiers, stated before the run:

- **F1.** If `engine_hook` reads the arguments in the wrong order, or the
  stack words in the wrong byte order, the `read_args` checks fail.
- **F2.** If the mapped function did not execute, `r0` would not be `arg + 1`
  (0x42). The positive control asserts `returned == 0x42`, so a PASS cannot
  come from the expectation alone.
- **F3.** If a VA outside every block, in a non-executable block, or in a
  compressed section runs anyway, the BLOCKED checks fail.
- **F4.** If `r0` absent from `verdict_map` yields a verdict, the
  "no verdict is guessed" check fails.
- **F5.** If a `BLOCKED` result from the entry script is reported as a
  mismatch or a pass, the legacy-run check fails.
- **F6.** If the shipped probe changes its payload between `origin/main` and
  this tree, the payload diff is non-empty.
- **F7 (real image).** If the walker VA `0x3f5194` returned a verdict, the
  endianness limit would be wrong. A `BLOCKED` at the first instruction is the
  predicted outcome.

## Method

   hash is checked by `sha256sum` (Method 2). The memory map carries the
   window hash above; the runner hashes the same window and refuses any other
   scope.
2. **Commands.** Runnable as written from the repository root. `$W` is a
   scratch directory, not the repository.

3. **Controls.**
   - *Positive (synthetic):* a module entry whose function returns `arg + 1`
     with `verdict_map {"0x42": "ACCEPT"}` and `args ["0x41"]` is `PASS`,
     `returned 0x42`, `blocks_mapped` = both module blocks, and
     `image_sha256_checked` = true with `image_sha256_bytes` 4096.
   - *Positive (real):* none possible. No reader in this build has a PySh4
     path (C-2546); a `PASS` on real firmware is not claimed.
   - *Negative (synthetic):* a wrong expectation is `MISMATCH` (exit 5); an
     `r0` absent from `verdict_map` is `BLOCKED` ("no verdict is guessed"); a
     VA outside every block, in the `rw-` block, or in a compressed section
     (`.zdata`) is `BLOCKED` with the section named; a wrong hash, an
     unrecognised hash scope, and a scope covering another image size are
     `INVALID` (exit 1) and run nothing; no `--rommap` is `BLOCKED`;
     `--engine ghidra` is `SKIP` (exit 3), never `PASS`.
   - *Negative (real, bytes of the head):* VA `0x0055d100` (sec1) and
     `0x8cae1000` (outside) are `BLOCKED` (exit 4).
   - *Entry script:* invalid input exits 1 and writes no result; a wrong
     argument count exits 2; a valid run writes `BLOCKED` with no cases; through
     the legacy runner that is exit 4; an empty `ghidra/` directory on
     `sys.path` is not the Ghidra API.
   - *Validation negatives:* `endian: little`, five arguments, missing
     `verdict_map`, a verdict other than ACCEPT/REJECT, a repeated key, an
     unknown entry key, a missing `va`, an empty `module`.
4. **Scope.** Synthetic: one module, two mapped blocks, `PySh4` only.
   Real: one head (256 MiB of 7.4 GB), the `Navi.exe` module of the EU 2011
   build, one mapped block (sec0, 5,553,664 bytes), two compressed sections
   skipped (sec1, sec2), three runs (one entry, two controls). Excluded: the
   other 147 modules, the full image, the US and 2014/2016 images, the
   Ghidra and QEMU back ends (not installed: SKIP), stack arguments for module
   entries (rejected at validation), and the in-Ghidra execution of
   `ghidra/l3_run.py` (no Ghidra here).
   **Real Ghidra run: out of scope for this task.** No Ghidra or Java is
   installed, and this task may not install software (no sudo). The Ghidra path
   is unexecuted; C-2508 stays `UNKNOWN`.
5. **Falsifier.** F1–F7 above. A failure of any of them refutes the claim it
   guards.

## Interpretation

- **FACT:** `runner.py run NAME --rommap MAP --image FW` calls a module VA
  through `Backend.call` after mapping the module's loadable blocks from the
  image bytes; no loader list is written by hand (synthetic PASS control; real
  head: sec0 mapped and the first instruction executed).
- **FACT:** on the real head, the map's hash window is checked and accepted
  after the fix. Before it, the runner refused a correct image: a bug the
  synthetic checks did not catch, found by the real run (rule 11).
- **FACT:** `StubDispatcher.engine_hook` reads `r4`–`r7` and the stack words in
  the context's byte order and raises `Blocked` with `missing stub: NAME`
  (dispatch selftest). The shipped probe payload is byte-identical to
  `origin/main` (C-2501).
- **FACT:** the real Navi.exe walker stops at its first instruction under
  big-endian decode (`0x4362` at `0x3f5194`), the same limit C-2546 records. So
  the first real module run yields no verdict and this is correct; PASS would
  have been a refutation of C-2546 and it did not happen.
- **FACT:** compressed sections are named as such, not reported as a wrong VA.
- **OBSERVED:** `ghidra/l3_run.py` is the single documented Ghidra entry
  script. It writes `BLOCKED` results with no cases; the runner reads that as
  exit 4. An empty `ghidra/` directory on `sys.path` is not the Ghidra API, so
  the probe imports a real submodule.
- **UNKNOWN:** whether `ghidra/l3_run.py` and `engine.GhidraBackend` behave under
  a real Ghidra 12.2+ with PyGhidra. Not run here.
- **HYPOTHESIS:** a located reader (M9.6, M9.11, M9.13, M9.14) becomes a module
  target by filling `module`, `va` and its corpus row, without further runner
  changes, once M9.21 provides a little-endian engine. Not tested.

## Conclusion

The three M9.20 deliverables are in place and pass their offline checks: module
entries (`entry.kind = "module"`), the `engine_hook` argument path, and one
documented Ghidra entry script. The real EU 2011 head runs the module path up
to the engine's byte-order limit, and found one runner bug (the hash window),
now fixed. `tools/README.md` and `tools/l3_harness/README.md` describe the
code; `docs/research/l3-ghidra.md` no longer calls the entry script missing.

Ten claims in C-2500 to C-2509: nine `VERIFIED` (eight on synthetic inputs, a
real-image head, or an absence; C-2509 on scope: no firmware verdict is made)
and one `UNKNOWN` (C-2508, the Ghidra run).

Open: a real Ghidra run of `ghidra/l3_run.py` (needs Ghidra 12.2+, Java and
pyghidra, which this environment does not have); a little-endian engine for the
firmware (M9.21, which the real walker run now needs); stack arguments for
module entries; the located readers as module targets (M9.6, M9.13, M9.14).
