- **Date:** 2026-11-08
- **Sample:** EU 2011 image, first 256 MiB (`fetch_image.py --image IMG256`),
  file SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`

  `tools/l3_harness/selftest.py` use a synthetic 8 KiB image built in a

- **Tools:** `python3 3.15.0` (CPython, stdlib only); repo tools

## Question

Can `runner.py run` call a function at a module VA of a memory map without a
hand-written loader list, can the stub dispatcher hand a target handler the
argument registers, and does the Ghidra back end have one documented entry
script that the runner and the docs agree on? Does the real-image path (CE
ROM TOC, memory map, image bytes) reach the engine?

## Hypothesis

The three pieces can be built in pure Python on `PySh4`, with no Ghidra. The
falsifiers, stated before the run:

- **F1.** If `engine_hook` reads the arguments in the wrong order, or the stack
  words in the wrong byte order, the `read_args` checks fail.
- **F2.** If the mapped function did not execute, `r0` would not be `arg + 1`
  (0x42). The positive control asserts `returned == 0x42`.
- **F3.** If a VA outside every block, in a non-executable block, or in a
  compressed section runs anyway, the BLOCKED checks fail.
- **F4.** If `r0` absent from `verdict_map` yields a verdict, the "no verdict
  is guessed" check fails.
- **F5.** If a `BLOCKED` result from the entry script is reported as a mismatch
  or a pass, the legacy-run check fails.
- **F6.** If the shipped probe payload differs from `origin/main`, the diff is
  non-empty.
- **F7 (endianness).** The same little-endian entry must pass over
  little-endian bytes and must not pass over big-endian bytes of the same
  function. On the real walker, big-endian decode of the firmware's
  little-endian code stops at its first instruction (C-2546's prediction).
  Little-endian decode must run further.

3. **Controls.**
   - *Positive (synthetic, endianness):* a little-endian entry over
     little-endian code is `PASS`, `returned 0x42`, engine `interpreter`. A
     big-endian image under the same entry is not `PASS`.
   - *Positive (synthetic):* a big-endian entry over big-endian code is
     `PASS`, `returned 0x42`, `blocks_mapped` = both module blocks, and
     `image_sha256_checked` = true with `image_sha256_bytes` 4096.
   - *Positive (real):* none. No reader has a verdict on real bytes in this
     task; a `PASS` on firmware is not claimed.
   - *Negative (synthetic):* a wrong expectation is `MISMATCH` (exit 5); an
     `r0` absent from `verdict_map` is `BLOCKED` ("no verdict is guessed"); a
     VA outside every block, in the `rw-` block, or in a compressed section
     (`.zdata`) is `BLOCKED` with the section named; a wrong hash, an
     unrecognised hash scope, or a scope covering another image size is
     `INVALID` (exit 1) and runs nothing; no `--rommap` is `BLOCKED`;
     `--engine ghidra` is `SKIP` (exit 3) for big-endian, and `BLOCKED` for
     `little` ("needs the pysh4 engine"), never `PASS`.
   - *Negative (real):* VA `0x0055d100` (sec1) and `0x8cae1000` (outside) are
     `BLOCKED` (exit 4) with their reasons.
   - *Entry script:* invalid input exits 1 and writes no result; a wrong
     argument count exits 2; a valid run writes `BLOCKED` with no cases; through
     the legacy runner that is exit 4; an empty `ghidra/` directory on
     `sys.path` is not the Ghidra API.
   - *Validation negatives:* an endian other than big/little, five arguments,
     missing `verdict_map`, a verdict other than ACCEPT/REJECT, a repeated key,
     an unknown entry key, a missing `va`, an empty `module`.
4. **Scope.** Synthetic: one module, two blocks, `PySh4` in both byte orders.
   Real: one head (256 MiB of 7.4 GB), one module of the EU 2011 build,
   one mapped block (`Navi.exe` sec0, 5,553,664 bytes), two compressed sections
   skipped, four runs (walker in both byte orders, two controls). Excluded: the
   other modules, the full image, the US and 2014/2016 images, the Ghidra and
   QEMU back ends (not installed), stack arguments for module entries, the
   page input that the walker needs (no input region is mapped by this
   harness), and the in-Ghidra execution of `ghidra/l3_run.py`.
   **Real Ghidra run: out of scope for this task.** No Ghidra or Java is
   installed, and this task may not install software (no sudo). C-2508 stays
   `UNKNOWN`.
5. **Falsifier.** F1–F7 above. A failure of any of them refutes the claim it
   guards.

## Interpretation

- **FACT:** `runner.py run NAME --rommap MAP --image FW` calls a module VA
  through `Backend.call` after mapping the module's loadable blocks from the
  image bytes; no loader list is written by hand (synthetic PASS; real head:
  sec0 mapped, and the function executed under little-endian decode).
- **FACT:** the byte order is now a checked property. The same little-endian
  function passes over little-endian bytes and not over big-endian bytes
  (F7, synthetic). On the real walker, big-endian decode stops at
  `0x00004362` (C-2546), and little-endian decode runs further.
- **FACT:** on the real head the map's hash window is checked and accepted
  after the fix. Before it, the runner refused a correct image: a bug the
  synthetic checks did not catch, found by the real run (rule 11).
- **FACT:** `StubDispatcher.engine_hook` reads `r4`–`r7` and the stack words in
  the context's byte order and raises `Blocked` with `missing stub: NAME`
  (dispatch selftest). The shipped probe payload is byte-identical to
  `origin/main` (C-2501).
- **FACT:** compressed sections are named as such, not reported as a wrong VA.
- **OBSERVED:** `ghidra/l3_run.py` is the single documented Ghidra entry
  script. It writes `BLOCKED` results with no cases, which the runner reads as
  exit 4. An empty `ghidra/` directory on `sys.path` is not the Ghidra API, so
  the probe imports a real submodule.
- **UNKNOWN:** whether `ghidra/l3_run.py` and `engine.GhidraBackend` behave under
  a real Ghidra 12.2+ with PyGhidra. Not run here.
- **HYPOTHESIS:** a located reader (M9.6, M9.11, M9.13, M9.14) becomes a module
  target by filling `module`, `va`, `endian` and an input region for its
  arguments, with no further runner change. The input region is the open
  question; it is not tested.

## Conclusion

The three M9.20 deliverables are in place and pass their offline checks:
module entries (`entry.kind = "module"`, both byte orders on PySh4), the
`engine_hook` argument path, and one documented Ghidra entry script. On the EU
2011 head the module path maps `Navi.exe` sec0, and the firmware's walker runs
under the firmware's byte order until it reads its page argument, which no
input maps. The real run found one runner bug (the hash window), now fixed.

Ten claims in C-2500 to C-2509: nine `VERIFIED` (on synthetic inputs, a
real-image head, or an absence; C-2509 on scope: no firmware verdict is made)
and one `UNKNOWN` (C-2508, the Ghidra run).

Open, in order: an input region for module entries, so the walker can read a
page (a new task; the page source is in the image and not yet located for this
entry); a real Ghidra run of `ghidra/l3_run.py` (needs Ghidra 12.2+, Java and
pyghidra); stack arguments for module entries; the located readers as module
targets (M9.6, M9.13, M9.14).
