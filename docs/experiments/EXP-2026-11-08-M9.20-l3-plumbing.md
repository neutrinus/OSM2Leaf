## Question

Can `runner.py run` call a function at a module VA of a memory map without a
hand-written loader list, can the stub dispatcher hand a target handler the
argument registers, and does the Ghidra back end have one documented entry
script that the runner and the docs agree on?

## Hypothesis

The three pieces can be built in pure Python on `PySh4`, with no Ghidra. The
falsifiers, stated before the run:

- **F1.** If `engine_hook` reads the arguments in the wrong order, or the
  stack words in the wrong byte order, the `read_args` argument check fails.
- **F2.** If the mapped function did not execute, `r0` would not be `arg + 1`
  (0x42). The positive control asserts `returned == 0x42`, so a PASS cannot
  come from the expectation alone.
- **F3.** If a VA outside every block or in a non-executable block runs
  anyway, the BLOCKED checks fail.
- **F4.** If `r0` absent from `verdict_map` yields a verdict, the
  "no verdict is guessed" check fails.
- **F5.** If a `BLOCKED` result from the entry script is reported as a
  mismatch or a pass, the legacy-run check fails (exit code and status).
- **F6.** If the shipped probe changes its PASS, its stub call log, or its
  payload between runs, the probe checks fail.

## Method

1. **Sample and hash.** No vendor data. The synthetic image and its memory map
   are created inside `tools/l3_harness/selftest.py` (`module_fixture`) for
   each check, in a temporary directory, and the map carries the image hash.
2. **Commands.** Runnable as written from the repository root:

```bash
python3 tools/selftest.py
python3 tools/claims_check.py
python3 tools/l3_harness/selftest.py
python3 tools/l3_harness/dispatch.py --selftest
python3 tools/l3_harness/engine.py --selftest
python3 tools/l3_harness/runner.py selftest
python3 tools/l3_harness/ghidra/l3_run.py --selftest
python3 tools/l3check.py --selftest
python3 tools/l3_harness/runner.py targets
```

   The shipped probe (`probe-zlib-cmf`) is checked by the runner's own
   selftest cases `test_run_accept`, `test_run_reject` and
   `test_run_determinism`, which run inside `tools/l3_harness/selftest.py`.
3. **Controls.**
   - *Positive:* a module entry whose function returns `arg + 1` with
     `verdict_map {"0x42": "ACCEPT"}` and `args ["0x41"]` must be `PASS`,
     `returned 0x42`, `blocks_mapped` = both module blocks, and
     `image_sha256_checked` = true. The shipped probe must keep its
     `ACCEPT`/PASS and its `test_run_determinism` equality.
   - *Negative:* the same target with a wrong expectation is `MISMATCH` (exit
     5); with `r0` absent from `verdict_map` it is `BLOCKED` (exit 4, "no
     verdict is guessed"); a VA outside every block and a VA in the `rw-` block
     are `BLOCKED`; an edited map hash is `INVALID` (exit 1); no `--rommap` is
     `BLOCKED`; `--engine ghidra` is `SKIP` (exit 3), never `PASS`.
   - *Negative for the entry script:* invalid input exits 1 and writes no
     result; a wrong argument count exits 2; a valid run writes `BLOCKED`
     with no cases; through the legacy runner that is exit 4.
   - *Validation negatives:* `endian: little`, five arguments, a missing
     `verdict_map`, a verdict other than ACCEPT/REJECT, a repeated `verdict_map`
     key, an unknown entry key, a missing `va`, an empty `module`.
4. **Scope.** Covered: the synthetic module and its two blocks (2 of 2 blocks
   of the one synthetic module); `PySh4` only; the 24-stub table (22 modeled,
   2 planned) through the new `engine_hook`; the shipped `targets.json` (6
   targets: 1 synthetic, 5 blocked), **unchanged**. Excluded: Ghidra and QEMU
   back ends (not installed, so SKIP); Navi.exe and any firmware VA (`PySh4` is
   big-endian and the firmware is little-endian, M9.21); stack arguments for
   module entries (not modelled, rejected at validation); the in-Ghidra
   execution of `ghidra/l3_run.py` (no Ghidra here).
   **Real Ghidra run: out of scope for this task.** No Ghidra or Java is
   installed and this task may not install software (no sudo). The Ghidra
   path is therefore unexecuted and claim C-2508 stays `UNKNOWN`.
5. **Falsifier.** F1–F6 above, stated before the run. Any of them failing
   refutes the corresponding claim.

## Interpretation

- **FACT:** `runner.py run NAME --rommap MAP --image FW` calls a module VA
  through `Backend.call` after mapping the module's loadable blocks from the
  image bytes; no loader list is written by hand (observed: the
  `blocks_mapped` list and the PASS control). Synthetic data only.
- **FACT:** `StubDispatcher.engine_hook` reads `r4`–`r7` and the stack words
  in the context's byte order, resolves the stub when called and raises
  `Blocked` with `missing stub: NAME` (`dispatch selftest`, 17 checks, 3 of
  them `engine_hook`). The `StubBridge` probe run is unchanged (observed).
- **FACT:** module runs are `BLOCKED`, not guessed, in every negative case
  listed in Method 3; `l3_claim` is `false` on every module payload.
- **FACT:** `ghidra/l3_run.py` is the one documented entry script. It writes
  `BLOCKED` results with no cases, and the runner reads that as exit 4.
- **OBSERVED:** the shipped `targets.json` is unchanged, so no firmware reader
  is an L3 target. Module entries still run on `PySh4` only (big-endian).
- **UNKNOWN:** whether `ghidra/l3_run.py` and `engine.GhidraBackend` behave
  under a real Ghidra 12.2+ with PyGhidra. Not run here (no Ghidra, no Java).
- **HYPOTHESIS:** a located firmware reader (M9.6, M9.11, M9.13, M9.14) can
  become a module target by filling its `module` and `va` and its corpus row,
  without further runner changes. Not tested on firmware.

## Conclusion

The three M9.20 deliverables are in place and pass their offline checks:
module entries (`entry.kind = "module"`), the `engine_hook` argument path, and
one documented Ghidra entry script. `tools/README.md` and
`tools/l3_harness/README.md` now describe the code; `docs/research/l3-ghidra.md`
no longer calls the entry script missing. Ten claims are registered in C-2500
to C-2509: nine `VERIFIED` (eight on synthetic inputs or an absence, C-2509
on scope: no firmware reader verdict is made) and one `UNKNOWN` (C-2508, the
Ghidra run). Nothing here is a reader verdict and nothing
was tested in a car.

pyghidra, which this environment does not have); a little-endian engine for
