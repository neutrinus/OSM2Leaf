## Question

What DMAC hardware does `SDHC.dll` program for SD data transfers, which
registers/channel does it use, and how does it detect completion? (C10:
the first data command ACMD13 sets `CC_EXT_MODE = 2`, programs HPB DMAC
channel registers at `0x1fc08200`–`0x1fc08234` and `0x1fc08814`, then
times out with `EventID = 2`, 2×4000 ms — C-1462.)

## Hypothesis

`SDHC.dll` uses an HPB-DMAC channel in the `0xffc08000` block (mapped to a
P2/uncached virtual address) for SD host data transfers, and waits for a
DMA completion event with a 4000 ms timeout; a model that performs the
transfer and signals completion (TE/event/interrupt path) should unblock
the wait. `0xff801000` is the general DMAC base used for other channels.

**Falsifiers:** the SD path uses a different DMA engine than the one
`fn 0x039be010` maps; completion is not expressible from channel/common
register state alone (needs undocumented sideband); or the observed
`0x1fc08200` accesses do not correspond to the `0xffc08000`-based map.

## Observations

### O1. SDHC selects HPB-DMAC vs general DMAC by channel index (`fn 0x039be010`)

`fn 0x039bcf20` (host init, programs SDHI regs +0x20/+0x22/+0x38/+0xd8 per
C10) calls `fn 0x039be010` at `0x039bcf76` with `r4 = 8` when port 0
(`mov.w @r4,r3` zero → `mov #8,r4`) else `r4 = 9` (from `0x01f38214` path)
— consistent with port 0/1 setup.

`fn 0x039be010` (`r9=r4`): for valid `r9 <= 22`,
- `r9 < 21` (0–20): loads `r11 = 0xffc08000` (`[0x039be32c]`), sets type=1,
  `r10=9` (→ `r5 = r10<<8 = 0x0900` mapping extent), channel index `r9` kept.
- `r9 >= 21` (21–22): loads `r11 = 0xff801000` (`[0x039be330]`), sets type=2,
  `r10=5` (→ `0x0500`), `r9 -= 21`.

It allocates/maps the register window via `VirtualAlloc`/`VirtualCopy`
(thunks `0x039be934`/`0x039be940`) using `r11` (physical base, passed as
`r5 = r11>>8` in the `VirtualCopy`/mapping call sequence at
`0x039be12c`–`0x039be13a` with `r6=r10`, `r7=0x0604`) and stores the
returned mapped base (`r2`, from ctx+8) as the base for computed register
pointers.

### O2. Per-channel register pointer layout (from `fn 0x039be010`)

For both types the channel block base is `mapped_base + (channel_index << 6)`
(`r3 = r2 + shad(r9,6)`, 0x40-byte stride). The context stores pointers
(offsets from ctx in `r8`): +12/+16/+20/+24/+28/+32/+36/+40/+44 and
+52/+56/+60/+64 point to channel block offsets
`+0x00,+0x04,+0x08,+0x0C,+0x10,+0x14,+0x18,+0x1C,+0x20,+0x28,+0x2C,+0x30,+0x34`
respectively.

**Type 1 (HPB-DMAC, base 0xffc08000, ch 0–20):** common/register pointers
include `base+0x080c` (ctx+80), `base+0x0810` (+84), `base+0x0814` (+88),
`base+0x0818` (+92); DMARS/selector-like `base + (0x0207 + ch)*4`
(= `base + 0x081c + ch*4`, ctx+96); `base+0x0890` (+104), `base+0x0894`
(+108), `base+0x0898` (+112); ctx+100 zeroed.

**Type 2 (general DMAC, base 0xff801000, ch 21–22 → index 0–1):** channel
offsets `+0x0404,+0x040c,+0x0410,+0x0414,+0x0418,+0x0420,+0x0480` stored at
ctx+68..92; DMARS-like `base + (0x0109 + ch)*4` (ctx+96); `base+0x0490`
(+104); `base+0x04c0..0x04d4` at ctx+120,124,128,132,136,140.

(Offsets are as decoded from `fn 0x039be010` at
`0x039be20c`–`0x039be42e` / `0x039be344`–`0x039be42e`; the exact register
names/semantics for this SoC variant are not asserted here beyond the
address/stride map — M8.C1 follow-up/model work must bind them to observed
read/write behavior.)

### O3. Correlation with C10's dynamic DMA observation

C10 observed HPB DMAC channel registers programmed at `0x1fc08200`–`0x1fc08234`
and `0x1fc08814` for the ACMD13 data transfer (C-1462). `0x1fc08200` =
`0x1fc08000 + 0x200` = mapped base region for channel 8 (`8 * 0x40 = 0x200`)
of the `0xffc08000` HPB-DMAC block — consistent with SDHC selecting port 0
as channel index 8 (`fn 0x039bcf20` passes `r4=8`). `0x1fc08814` aligns
with common register offset `+0x0814` in the same mapped block (O2). This
supports that `VirtualCopy` maps the `0xffc08000` physical window to a
`0x1fc0xxxx` virtual address on this firmware (virtual address is a runtime
value; the `0x1fc08200` literal does not appear in the static image).

### O4. nk.exe DMAC users (0xffc08000 common area)

`nk.exe` (build B) loads `0xffc0880c/810/814` (offsets +0x80c/+0x810/+0x814)
from pool literals in functions `0x8803e004`, `0x8803e294`, `0x8803e618`,
`0x8803e654`, `0x8803e690`, `0x8803e6cc`, `0x8803e708`, `0x8803e744`,
`0x8803e780`, `0x8803e7bc`, `0x8803e7f8`, `0x8803e850`, `0x8803e8a8`,
`0x8803e8e4`, `0x8803e98c`, `0x8803ea14`, `0x8803ea9c`, `0x8803ead0`,
`0x8803eb10`, `0x8803eb4c`, `0x8803eb88`, `0x8803ebc4`, `0x8803ec00`
(`ze0_serial.py refs`). No `0xff801000` window refs found in SDHC or nk by
the same scan; `fn 0x039be010` still carries the `0xff801000` base for
channel 21–22 selection (O1).

### O5. DMA completion wait path (SDHC)

`fn 0x039bafcc` (pdata) computes an event handle from `0x01f381c4` indexed
by `(r4*3 + r5)` and waits via `WaitForMultipleObjects` (thunk
`0x039be898` → IAT slot `0x01f38060`, import idx 24). Timeout `r6` is
clamped to a **minimum of 0x0FA0 (4000 ms)** (`cmp/hs` at `0x039bb00c`: if
`r10 < 4000` then `r10 = 4000`). On `WAIT_TIMEOUT` (`0x0102`, checked at
`0x039bb018`) it records/logs timeout and sets error `0xfb7b` (`0x039bb030`);
on signal it stores status from `0xa9980a00/0xa9980a04` indexed by port.

`fn 0x039bb0ec` / `0x039bb0a0` perform related short event waits
(`WaitForSingleObject` thunk `0x039be88c`, idx 23, timeouts 2/3 in the
observed call sites). DMA transfer routines `fn 0x039bd2b0` and
`fn 0x039bd594` call into internal DMA helpers (`sub_039be4d0`,
`sub_039be50c`, `sub_039be59c`, `sub_039be5d8`, `sub_039be614`,
`sub_039be6b8` per `sh4xref --calls 0x039bd2b0`) and wait via
`fn 0x039bb0ec` (`jsr 0x039bd388`). The exact register program/write order
inside those helpers is not yet fully decoded.


### O6. DMA channel register programming helpers (`sub_039be4d0/50c/59c/5d8`)

Each helper takes `(ctx, value, ...)` and writes through the ctx pointer table
built in `fn 0x039be010` (O2). After the standard NULL/`ctx[48/52/56/60]` guard
and error path, the stores are:

- `sub_039be4d0`: `mov.l r5,@r2` with `r2 = *(ctx+48)` → **channel +0x24**.
- `sub_039be50c`: mode 0 (`r5 == 0`) writes `r6 → *(ctx+12)` (ch+0x00, SAR-like),
  `r7 → *(ctx+16)` (ch+0x04, DAR-like), stack arg `@(32,r15) → *(ctx+20)`
  (ch+0x08, TCR-like). Mode 1 (`r5 != 0`) writes `r6 → *(ctx+24)` (ch+0x0C),
  `r7 → *(ctx+28)` (ch+0x10), stack `@(32,r15) → *(ctx+32)` (ch+0x14).
- `sub_039be59c`: `r5 → *(ctx+52)` → **channel +0x28**.
- `sub_039be5d8`: `r5 → *(ctx+56)` → **channel +0x2C**.

So the transfer setup covers SAR/DAR/TCR (+0x00/04/08) and the secondary set
(+0x0C/10/14) plus +0x24/+0x28/+0x2C, consistent with a multi-register DMA
descriptor/program sequence (exact field names/CHCR/DMARS not yet bound).

### O7. Channel enable, trigger and completion poll (`sub_039be614`, `sub_039be6b8`)

`sub_039be614` (enable/mask): waits up to 0x7530 ms via `WaitForMultipleObjects`
(thunk `0x039be898`) on the handle pair at `0x01f381f8`/`0x01f381fc` selected by
`ctx[1]` (`mov.l @(4,r4),r3; add r3,r3; mov.l @(r0,r2),r4`), then computes
`mask = 1 << ctx[0]` (`e301 mov #1,r3; 4c4d shad r4,r3`) and ORs it into
`*ctx[88]` (`r2 = *(ctx+88)` HPB common base+0x0814 = `0xffc08814` physical per
O2/O3; `or r3,r3; mov.l r3,@r2`). The common +0x0814 register is therefore
treated as a per-channel enable/mask bitfield (consistent with nk/C10 use).

`sub_039be6b8` (start/poll): writes `1` to `*ctx[60]` (ch+0x30) and busy-waits
`while ((*ctx[64]) & 1) continue` (ch+0x34 bit 0). This provides a synchronous
"transfer active" poll primitive (trigger at +0x30, status/active at +0x34 bit 0).
It is distinct from the event-based completion wait in `fn 0x039bafcc` (O5);
how +0x34 bit 0 clearing relates to the 4000 ms event/IRQ path (and to DMAC
interrupt/TE signaling) is not yet traced.


## Interpretation

- The **0xffc08000** block is the HPB-DMAC (+mux/clock/common area) used by
  SDHC for port 0/1 DMA (channels 8/9 by host-init argument), with 0x40
  channel stride and common regs at +0x80c..+0x818/+0x890+; the **0xff801000**
  block is the general DMAC path for channels 21–22 in the same dispatcher
  (not yet observed in the SD transfer trace). This matches M8.C1's stated
  scope.
- C10's `0x1fc08200` is explained as the virtual mapping of channel 8's
  register window within the 0xffc08000 physical block (not a static
  literal), consistent with `VirtualCopy`-based MMIO mapping in
  `fn 0x039be010`.
- `sub_039be50c/4d0/59c/5d8/614/6b8` decode (O6,O7): transfer setup programs
  SAR/DAR/TCR (+0x00/04/08) and +0x0C/10/14/24/28/2C; channel enable ORs
  `(1<<ctx[0])` into common +0x0814 (`*ctx[88]`); transfer start writes 1 to
  +0x30 and a synchronous primitive polls +0x34 bit 0. A minimal model must at
  least honor this program/enable/trigger sequence and present a clearing
  +0x34-bit-0 / completion indication compatible with the driver.
- SD data DMA completion is also gated on an event waited with a >=4000 ms
  timeout (`fn 0x039bafcc` / `WaitForMultipleObjects`, O5; matches C10's
  2×4000 ms). Whether satisfying +0x34 is sufficient, or whether the model must
  also raise a DMAC IRQ / nk-handled completion that signals the 0x01f381c4
  event, depends on the still-untraced DMARS request-source for SD ch 8 and the
  nk ISR/INTC linkage for 0xffc0880c/810/814.
- `nk.exe`'s references to 0xffc0880c/810/814 indicate kernel/OAL
  involvement in HPB-DMAC common/mux/interrupt status; a model likely needs
  compatible behavior there in addition to channel registers.

## Falsifiers / risks

- Channel/register field names (CHCR, DMARS request ID, TE/interrupt flags) are
  still inferred from pointer/offset arithmetic and usage, not from a datasheet
  bind or runtime trace; wrong mapping would mis-model transfer/ack behavior.
- `sub_039be6b8` proves a synchronous +0x30/+0x34-bit-0 handshake exists, but
  the 4000 ms `WaitForMultipleObjects` completion path (O5) may additionally
  require a DMAC interrupt routed through INTC/nk to signal the event at
  `0x01f381c4`.
- DMARS request-source binding for SD channel 8 and the nk ISR/handler for
  0xffc0880c/810/814 remain unresolved.
