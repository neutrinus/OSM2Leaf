# EXP-2026-11-23-M8.H32-trailer-test: wheel pulses on `-M ze0`, and a trailer move from Kentucky to Chicago

- **Status:** done, with a negative result for the trailer. The speed input
  works: the firmware's speed variable follows the pulse rate (50 km/h
  within 1 %, 0 at 0). The car does not move to the GPS position. The
  locator jumps to it once, and the next cycle puts it back on the old road.
- **Date:** 2026-11-23
- **Task:** TODO **M8.H32**. Marek: "Czyli możesz odpalić emulację, przesunąć
  lokalizacje (odpowiednik lawety), potem pokręcić kołami i gyro, dać 15
  dobrych fixów gps i zobaczymy czy się przesunie?"
- **Sample:**
  - card `LEAF_2011-2012_US.img`, same SHA-256 as EXP M8.H73;
  - NK1 `firmware/unit-flash/nk1-QY7200ND.bin`;
  - the US unit flash dump from M6.18 (never committed), passed as
    `flash=` with the M8.H18 NOR model.
- **Tools:** `tools/sh4dis.py`, `tools/sh4xref.py`, `tools/cerom.py imports`,
  QEMU 11.1.3 `ze0` with the new `ze0-h32-dr-sensors.patch`,
  `tools/ze0_launch.py --peer panel --peer gps --gdb P --ui-start`, HMP
  `qom-set`/`qom-get`, a gdb breakpoint probe (C-8579), and
  `tools/ze0_screenshot.py screen`.
- **Claims:** C-7290–C-7299
- **Supersedes:** none. It extends EXP-2026-11-23-M8.H18-nor-flash O6 (bit 0x80).
- **Superseded by:** none

## Question

M8.H18 left the car in Kentucky. A US fix was held back by bit 0x80, the
vehicle's own speed, and by bits 0x01 and 0x02. Can the emulator turn the
wheels? With wheels turning and 15+ good fixes at a far US place (the
trailer case), does the car move there?

## Method

1. Static: in `navdrv.dll` (US card ROM B, `--image-start 0x3e00200`; NK1 runs
   the same code at +0x310000), follow the speed getters to the sample thread
   and its wait. Read the NK1 OAL interrupt table from the running guest.
2. Model the two pages and the interrupt in QEMU (`hw/sh4/ze0_dr.c`). Inputs
   are QOM properties of `/machine/dr`. Boot runs S17–S20; `ZE0_DR_TRACE=1`
   logs the first register accesses.
3. Run S20: unlock (panel `tap 277 98`), then GPS fix at Chicago (41.8781,
   −87.6298) moving north at 30 km/h, re-sent every 0.2 s. Set the pulses
   with `qom-set /machine/dr pulses-milli N`. Read the flags `*0x00dbd8ac`,
   the speed `*0x00dbdc2e` (store at `0x0049ca7c`) and the car word at
   `OBJ_CarPos_write` (`0x00497e5c`, r5). Take screenshots.
4. Change one thing at a time: the pulses (0 / 3000 / 5000 / 6000 / 8333),
   the GPS speed, the fix on/off, the stat byte (0x30 → 0x00).

## Observations

O1 (the wait). The sample thread `0x039e55b0` calls `InterruptInitialize`
(coredll #627 through stub `0x039e6efc`) with SYSINTR 46. It then loops:
wait, `0x039e5194` (sample, via the builder `0x039e59e4`), `0x039e5290`
(record ring), `0x039e74bc` (writes 1 to the status-clear register),
`InterruptDone(46)`. In the guest's NK1 OAL table at `0x88005bc8`, row 20 is
{INTEVT 0x760, ISR `0x8803f004`, IntrPrio 11, SYSINTR 0x2e}. That ISR writes
0x00400000 to `INT2MSKR` (`0xff804040`), so INT2 bit 22, and returns 46. QEMU
had no source for 0x760, so the thread never woke. `gyroAdc_GetAddData` hits
seen in S15 come from another caller (`0x03cf636c` on NK1).

O2 (registers). The pointer tables give the offsets of C-7291. The trace of
S20 shows the driver's init writes: gyro +0x00 = 1, +0x08 = 0xd2, +0x0c =
0xcd14, +0x04 = 1; speed +0x04 = 0xd2, +0x1c = 0x54, +0x08 = 1, then 0. After
that, every tick reads gyro +0x30…+0x3c and +0x40, speed +0x0c, +0x10,
+0x104 and +0x110, then writes speed +0x18 = 1. All of it goes through the
area-7 aliases. A model at the P4 addresses alone saw no access (S19).

O3 (model). `ze0-h32-dr-sensors.patch` adds INT2 source `DR` (0x760, bit 22,
level 11) and the object `/machine/dr`:

- +0x0c returns a pulse counter latched each tick; the thread takes the u16
  difference (`0x039e5634`–`0x039e5650`);
- +0x10 returns the tick count;
- the line goes up every `tick-ms` (100) of virtual time once the driver has
  written the latch enable, and down on the status-clear write.

Raising it from the first tick (S18) held the CPU in the interrupt before
the driver was ready: in 7 minutes only 15 s of guest time passed. With the
model, `0x0049c7f0` (message 0x04c1 subcode 0x131, dispatched by
`0x00498fbc`) runs about once a second.

O4 (speed). `*0x00dbdc2e`, read at `0x0049ca7c`:

| pulses/s | GPS | value |
| --- | --- | --- |
| 0 | moving, 30 km/h | 0 |
| 30 | none yet, right after boot | 209 |
| 30, 50, 60 | moving, 30 km/h | 300 |
| 60 | fix, speed 0 | 360 |
| 30 | fix, speed 0 | 180 |
| 30 | no fix | 180 |
| 83.33 | no fix | 498, 504, 498 |

The unit is 0.1 km/h. Without GPS speed the value is linear in the pulse
rate, with a scale the firmware learned while the GPS was moving (209 →
180 for the same rate). 50 km/h comes out within 1 %, and no pulses give 0.
With pulses on, bit 0x80 (`+22 ≥ 100`, `0x0049eeea`) is set.

O5 (stat byte). With pulses and stat 0x30 the flags word reads 0x1fc: bits
0x01 and 0x02 are missing. `0x0049dba0` (bit 0x02) clears the bit unless the
first halfword of each of the last 4 GPS history entries is 0x00 or 0x10.
`0x0049da38` (bit 0x01) weighs the last 15 entries differently for 0x00/0x10
and 0x20/0x30. After `stat 00` the word went 0x1fc → 0x1fe → 0x1ff → 0x3ff.
The peer's default is now 0x00.

O6 (the jump and the way back). With 0x3ff, `0x0049fa44` writes the GPS
position `0x9f62a223`, which decodes to (41.84, −87.77), to `0x00dbce00` and
calls the direction init `0x004aa070`. In the next cycle `0x0049e08c` looks
the car mesh up in the table at `0x00dd48e8`, gets −1 (the table holds 1
mesh: pointer `0x00dbede0`, count 1, and the Kentucky mesh), and
`0x0049e164` writes back `0x9c03a3c0`. `OBJ_CarPos_write` alternates
between the two words (15 and 15 in 40 s). The flags word alternates
between 0x3ff and 0x0ff. After 5+ minutes of driving the screen still showed
Simpson Rd with the car mark, the same picture as before.

O7 (why it goes back). The mesh table is filled only after a successful
map-matching cycle (`0x00456cc8` → `0x00451f8c`, EXP M8.H78 O4). Here it
returns 0xffff each time (`@(36,r15)` at `0x00479dea`), and the current
road link `*0x00dbdc30` stays `0x00dc9ac0`. Its exit at `0x00458990`
follows a counter, `*0x00dbd5ac` (`0x004588f0`–`0x0045897a`). The counter goes up
when the match state `*0x00dd48d4` is 1, goes down when it is −1, and at 8
or more calls `0x00454be8(3)` and `0x00478e18(2)`. That is a partial reset
which keeps the road link (O9). In S20 the state was 0 and the counter 0 on
every hit.

O8 (the match state). `*0x00dd48d4` is written only in `0x00456098`
(`0x00456814`–`0x004568dc`, called from `0x00456cc8`). After 30 samples
(counter `*0x00dca7bc`) it compares two speed sums, `*0x00dd48e0` against
the reference in `@(32,r15)`, as a percentage. Outside 81–119 % it sets the
lost-road counter `*0x00dbd5ac` straight to 8. Inside 96–104 % it writes −1,
and otherwise +1. In S20 with 50 pulses/s and GPS 30 km/h the ratio was 100
and the state −1. With 100 pulses/s (wheels twice as fast as the GPS) the
ratio fell to 91, 90, 89, the counter reached 8, and `0x00478e18(2)` ran
(called from `0x0045897c`, and with 4 from `0x004562da`). So the counter
measures whether the wheel speed agrees with the GPS speed, not whether the
GPS position agrees with the road. A trailer move followed by normal driving
keeps the two speeds in agreement.

O9 (what a reset clears). `0x00478e18` with 2 or 4 skips the first block
(`0x00478e2c`–`0x00478e38` branch to `0x00479288`) and leaves the road link
`*0x00dbdc30` in place. In S20 it stayed `0x00dc9ac0` after the mismatch
reset. Only arguments 0, 1 and 3 clear it. Those come from the positioning
message dispatcher `0x00452738`: subcode 110 (`0x478e18(1)`, then
`0x00477e98`) and subcode 116 (`0x478e18(3)` or `(1)` by the parameter at
+12). They also come from `0x00452968` (0, 1, 2). The senders of those
subcodes were not found: the subcode is a data field, not an immediate
next to `0x0fa0`.

O10 (forcing a reset). A gdb hook at `0x00452758` rewrote one 0x66
message into subcode 116 with parameter 1. The road link became 0 and
stayed 0. In another try it was rewritten three times into 110 with
parameter 0. Either way the car word kept alternating between Chicago
(`0x9f70a223`, a little further north than in O6) and Kentucky, and the flags between
0x3ff and 0x0ff. With no road link, `0x00456cc8` exits at once (EXP M8.H78
O5), so the mesh table is never refilled. The reset branch `0x0049e164`
keeps restoring the saved position from `0x00def7c0`/`0x00dc0408`/
`0x00dbd104`.

Not tested: gyro values other than 0 (the scale and zero of
`gyroAdc_GetAddData` are unknown), reverse, a drive long enough for the
counter to move, and a matched start on a road near the new place.

## Result

The emulator now has wheels. `navdrv` gets its 100 ms interrupt, the samples
reach `Navi.exe`, and the speed variable follows the pulse rate (M8.H32
done-when: 50 km/h within 5 %, 0 at 0, C-7294).

With wheels turning and good fixes (stat 0x00), every "relocate to GPS"
condition of the locator is met, and it does write the Chicago position. But
map-matching still holds the Kentucky road. The mesh check of the next
cycle undoes the jump twice a second, and the screen never leaves Kentucky.
The only way out seen in the code is the lost-road counter (C-7296), and
nothing in this run moved it. The counter measures how wheel speed agrees with GPS speed
(O8), so a car that was moved and is then driven normally never trips it.
Even when it trips, it does not clear the road link (O9). Forcing the
positioning subcodes that do clear the link did not help either (O10): the
mesh table stays on Kentucky, and the saved position wins every cycle. So in
the emulator a trailer move inside the US is not recovered by GPS and wheel
pulses (C-7297, C-7298, C-7299). The Poland case
of C-8647 is unchanged: there the fix fails earlier, at the mesh conversion.

Falsifier ("the speed variable does not change with the pulse rate"): does
not fire (O4).
