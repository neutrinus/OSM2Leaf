## Question

M5.19 asks for one of two exits: (a) a writer whose output the firmware decoder walks with the expected values for ≥ 20 rows (L3), or (b) evidence that copying the factory rows is correct because they do not depend on the region. Which exit holds for a Poland card, and can a writer reach it offline?

## Hypothesis

Exit (b) fails: M4.16e/M4.16b showed that a link reference names a node and link of one MAPAL section-2 parcel and that every table places on its own country's nodes (C-5139, C-5370, C-5400). A copied file therefore points at the factory graph, and a card with a generated section 2 needs references re-pointed to the generated nodes.

For exit (a), the hypothesis is that the file layout is fully determined by the location records, the triples, the reference targets `(parcel, a, b)` and a parcel → group rule. A writer built on that rule should then reproduce the factory file byte for byte. The rows the firmware walks with a known VA are the twelve-field TMC location records. Their accessor is `fn 0x003f61bc` (EU2011; the US2011 candidate `0x0041eb1c` is listed DIFFERENT in `fn_match_eu_us_2011.json` and is not run here). The writer's records should walk in L3 exactly as the M4.16b rule predicts.

**Falsifier (fixed before the runs):**
1. `repack` or `regroup` output differs from the factory file in any byte.
2. After a node and link renumbering of the section-2 parcels, the re-pointed file resolves below the factory file's own fit, or the copied file still resolves at the same rate (then copying would be safe).
3. The firmware walk in PySh4 returns other offsets or lengths than the M4.16b rule for any written row.
4. A control (wrong type, wrong field count, unswapped bytes, file-order numbering) still passes.

## Method

1. **Hashes** as above (`sha256sum`).
2. **Commands** (repo root; `E=/home/user/scratch/factory-eu`, `I=archive/head256.img`):

   ```bash
   python3 tools/rdstm_write.py --selftest
   python3 tools/rdstm_write.py repack  $E/RDSTM001/RDSTM001.DAT
   python3 tools/rdstm_write.py regroup $E/RDSTM001/RDSTM001.DAT
   python3 tools/rdstm_write.py regroup $E/RDSTM001/RDSTM001.DAT --entry-order file      # control
   python3 tools/rdstm_write.py repoint $E/RDSTM001/RDSTM001.DAT $E/MAPAL001 --tiles B48R058R.DAT --seed 1
   python3 tools/rdstm_write.py l3 $I $E/RDSTM001/LCTBL001.DAT --count 24
   python3 tools/rdstm_write.py l3 $I $E/RDSTM001/LCTBL001.DAT --sample 500 --show 0
   python3 tools/rdstm_write.py l3 $I -                                                  # 24 synthetic Polish rows
   ```

3. **What each command does.**
   - `repack` reads the file into a model (preamble, header words, two sets × 14 tables of link chunks and triples, group index and data) and writes it back.
   - `regroup` goes further. It replaces every `u32` ref by its target `(parcel_key, a, b)` and drops the group index and data. It then rebuilds each table from its records and its `{code: (negative, positive)}` triples alone. Finally the writer assigns groups and entries:
     - set 1 uses aligned 4 × 4 level-2 parcel boxes in key order;
     - set 0 uses the input's parcel → group table, because 3 of the 33 level-4 groups hold parcels outside their box;
     - inside a group, parcels go in key order, and each parcel's entries in the location-code order of the records.
   - `repoint` stands in for a generated section 2. It permutes the node indices and the link ids of all 4,071 level-2 parcels of `B48R058R` (seeded shuffle; coordinates kept). It re-points the set-1 targets through the same permutation, writes the file, and resolves each file against each section 2 with the M4.16e `resolve` (node is an end of the link).
   - `l3` maps build A `Navi.exe` into PySh4: sec0 and sec2 are plain; the compressed sec1 is zero-filled. It stubs the import slot `0x0055d8f0` (OSMDLL #21 `taskIdSelf`) and enters a handle → block pair at `0x00d53500 + 12/+16` (EU2011, BSS, `fn 0x003f51e0`). The block carries the field count at `hdr + 26` (`fn 0x003f57a8`) and a descriptor chain from `hdr + 24`: each descriptor's `+0` is the next descriptor and `+12` its field index, which `fn 0x003f56bc` requires to equal the requested index. For each written row and field `i = 0..11`, it calls `fn 0x003f61bc(handle, rec, i)` (pointer) and `fn 0x003f5d98(handle, rec, i)` (length in words), and compares them with `tmc_fielddir`'s walk and with the writer's input fields.
4. **Controls.**
   - *Positive:* byte identity with the factory file; the factory file against the factory section 2; the 24 first and 500 random factory rows re-encoded by the writer (they must equal the factory record bytes).
   - *Negative:* entries numbered in file order (`--entry-order file`); the copied file against the renumbered section 2; the written file against the factory section 2; a record with type bits 7; a block declaring 13 fields; the record in card byte order without the 16-bit swap.
5. **Scope.** EU 2011 only, both sets, all 28 tables and 3,165 groups (`repack`, `regroup`). One tile (4,071 level-2 parcels, 200,987 set-1 entries) for `repoint`. For `l3`: 24 + 500 factory rows and 24 synthetic Polish rows (public place names on the A2/A4, transliterated by the M3.9 rule). Left out: the US 2011 card (other offsets, M4.16b), the link-group firmware reader (M4.49, no VA yet), and generating a Polish TMC location table (no source in the repo).

## Observations

**Layout (factory file, from the model).** All 68 table blocks and all 3,165 group-data runs follow one another without gaps, each zero-padded to whole `0x100` blocks. The order is:
- header `0x1000` (0x180 words, rows end at `0x1224`, zeros to `0x1300`);
- set 0 tables, then set 1 tables, each as link chunks then the triple block;
- set 0 index `0xcda000`, set 0 data, set 1 index `0xe78500`, set 1 data to EOF `0x1641300`.

Other fixed details:
- Group heads are padded to whole dwords (`size_dwords`): 1,686 of 3,165 heads carry 2 zero bytes.
- Every link record's size word has `w >> 11 = 0` (233,746 records), and 41 chunk ends carry `0xffff`.
- Records inside a chunk are sorted by location code. A table's records are split into 1, 2 or 4 chunks of equal count, with the remainder going to the last chunks. Four chunks are stored in the order 0, 2, 1, 3 (tables `4401` and `4620` of set 1), and the triples follow the stored chunk order.
- The chunk count is 1 up to 506,394 record bytes, 2 from 575,240 to 956,122, and 4 from 1,340,644. This fits all 28 tables with a limit of `0x80000` bytes per chunk (the threshold is a HYPOTHESIS).

The firmware reads the record and the length table with `mov.w` (little-endian) and takes field `2k` from the **high** byte of the halfword (`0x003f5dd2`–`0x003f5dec`, EU2011). The M4.16b rule therefore holds for the card bytes only after a 16-bit swap; the run swaps each halfword before the call. The loader that does this swap is not located.

## Interpretation

- **VERIFIED (exit b fails, C-2430):** copying is not region-independent. Under a renumbered section 2 the copied file resolves at the random-node rate (3.4 %, vs 5.7 % random node in C-5139), while the re-pointed file resolves exactly as the factory pair does. Together with C-5370/C-5400 (every table places in its own country), a Poland card cannot reuse the factory rows.
- **VERIFIED (writer, C-2431, C-2432):** the writer reproduces the factory `RDSTM001.DAT` byte for byte, both from the parsed model and from records + triples + targets. The positive and negative runs pin these rules:
  - set-1 grouping is aligned 4 × 4 level-2 boxes in key order;
  - entries are numbered per parcel in the location-code order of the records (file order fails);
  - tables are split into 1, 2 or 4 chunks of equal count, stored 0, 2, 1, 3.
- **VERIFIED (re-point, C-2433):** feeding the writer `(parcel, node, link)` targets in the generated numbering yields a file that resolves 200,190/200,987 against that numbering, identical to the factory pair, and keeps every ref's node coordinate.
- **VERIFIED (L3, C-2434):** the firmware field accessor and length getter walk writer-produced TMC rows with the expected offsets and lengths for 24 + 500 factory rows and 24 synthetic Polish rows, with three negative controls at 0. This meets exit (a) for the rows that have a firmware reader with a VA.
- **OBSERVED (C-2435):** the handle block that `fn 0x003f51e0` returns carries more than a field count. It holds a descriptor chain whose `+12` must equal the requested field index (`fn 0x003f56bc`), and a 13-field block shifts every offset. This refines C-5130: the block is a field schema in RAM, even though the `0x00d53500` table is only a handle cache.
- **HYPOTHESIS (C-2436):**
  - the 16-bit swap between card bytes and the walked record (a page loader not located);
  - the `0x80000`-byte chunk limit;
  - the set-0 grouping rule (a parcel → group table is an input).

## Limits

- **No firmware reader for the link groups.** The link file (`RDSTM001.DAT` header, chunks, triples, groups) has no reader VA yet (M4.49, another agent). It is checked by factory byte identity and by the M4.16e reader, not in L3. When M4.49 lands its reader VA, run it on a `regroup`/`repoint` output: one written file, ≥ 20 refs.
- **Writer inputs are not produced in the repo yet.** Polish TMC location records, their location codes and their `(parcel, node, link)` targets in a generated section 2 have no source in the repo. The writer takes them as input. The roles `k & 3` and the entry flag bits (`a`/`b` 0x4000/0x8000) are copied from input, not derived (C-5371/C-5403).
- **US 2011 is out of scope.** It uses other offsets (M4.16b); not run.

## Conclusion

Exit (b) is closed negative: the rows are region-tied, and a copied file resolves at random against a renumbered graph.

Exit (a) is met for the TMC rows. `tools/rdstm_write.py` writes records that the EU2011 firmware accessor `0x003f61bc` walks correctly for ≥ 20 rows (548 in total, including 24 Polish rows), with controls at 0. The same tool rebuilds the link file byte for byte from records, triples and reference targets, and re-points the references to a renumbered section 2 without loss.

M5.19 is **done**. The L3 of the link-group reader follows M4.49.
