# EXP-2026-11-21-M3.34: the firmware's own POI position arithmetic, run on factory records, equals the M4.27 formula

- **Status:** done for the conversion (routine named, arithmetic written out, 15,469/15,469 records of one file and 9,483 sampled records of all 33 files agree with `point_census.fine_position` within 1 unit of 1/512″); **negative for the spatial-tree reader** (not found in one session; what was ruled out is in Observations §8, follow-up M3.35)
- **Date:** 2026-11-21
- **Sample:** `archive/head256.img`, the first 268,435,456 bytes of the EU 2011 card, SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9` (build EU2011: `Navi.exe`, `STDDLL.dll`); the 33 `REFER001/POINTnnn.DAT` pairs of the same card extracted with `point_census.py extract` (not committed), e.g. `POINT010.DAT.CMP` SHA-256 `d02a8d87fa0c87b9a1c1cc84aa0a5e76bd97a7010e17656427f6ae46bfaf9ec3`, `.IND` `3eaa47bb653dce9950c2e375801f175b537915dab84ce2ca6e9a3af82381e3ec`
- **Tools:** `tools/poi_position_l3.py` (new, `--selftest`), `tools/sh4fpu.py` (new: SH-4 FPU on top of the PySh4 engine, `--selftest`), `tools/point_census.py` (changed: the latitude fine word is masked like the longitude one), `tools/sh4dis.py`, `tools/cerom.py`
- **Claims:** C-6540, C-6541, C-6542, C-6543, C-6544, C-6545, C-6546

- **Superseded by:** none

## Question

M4.27 read the fine POI position from the file and fitted the formula to 16
reference points. Which firmware code turns a name record into a map
coordinate, what arithmetic does it use, and does it give the same position
as `point_census.fine_position` on factory records? Which code reads the
spatial tree (cell `0x85a`)?

## Hypothesis

The firmware treats bytes 2–5 of a name record as a mesh id whose two
`11xx` nibbles carry two marker bits, and bytes 6–9 as two 11-bit offsets
inside that mesh; its result equals
`u = (v & ~15) + 4·(v & 3) + fine/512`, `lat = (u_x − 32768)/192`,
`lon = (u_y − 52736)/128`.

**Falsifier:** a factory name record for which the firmware's map point
differs from `fine_position` by more than one output unit (1/512″); or the
control readings (fine fields exchanged, one-unit reading) matching as well.

| Item | Value |

| Image | `archive/head256.img`, application image at `0x200200` |
| Code | `Navi.exe` text (VA `0x00011000`), `STDDLL.dll` text (VA `0x03461000`), both uncompressed |

## Method

1. **Sample.** Image and pairs above. No vendor byte is committed; the tool
   reads the code from the image at run time.
2. **Commands.**

   ```bash
   python3 tools/point_census.py extract --card-image CARD /tmp/pt_eu     # never commit
   python3 tools/poi_position_l3.py --selftest
   python3 tools/sh4fpu.py --selftest
   python3 tools/poi_position_l3.py run archive/head256.img --dir /tmp/pt_eu --file POINT010 --count 100000
   for i in $(seq -w 1 33); do
     python3 tools/poi_position_l3.py run archive/head256.img --dir /tmp/pt_eu --file POINT0$i --count 300
   done
   python3 tools/poi_position_l3.py mesh archive/head256.img 0x8b608b60 0 0
   python3 tools/poi_position_l3.py mesh archive/head256.img 0x8b608b60 100 200
   python3 tools/poi_position_l3.py mesh archive/head256.img 0x8b6c8b60 0 0
   ```

   The tool maps the two code sections and an import table in which the
   three slots used by the routine point at the `STDDLL.dll` exports the
   import table names (resolved from the modules' own import and export
   tables), then calls `fn 0x003c032c` (EU2011) and
   `STDDLL!STD_MeshPnt_chgMapPnt`. Only the error logger `0x003c5580`
   (EU2011) is replaced by a recorder.
3. **Controls.** *Negative:* the same firmware result compared with the two
   fine fields exchanged and with the pre-M4.27 one-unit reading — neither
   may match; a record whose class bits are cleared must be refused by the
   firmware; a mesh id with the marker bits left in must be refused by the
   library. *Positive:* synthetic mesh points with a position known by
   construction (`mesh`).
4. **Scope.** All 15,469 name records of `POINT010`; up to 300 evenly spaced
   records of each of the 33 files (9,483). One build (EU2011). The
   functions run in an emulator, not on the unit.
5. **Falsifier.** As above; the tool exits 1.

## Observations

1. **The routine.** `fn 0x003c032c(db, rec, out)` (EU2011, 0xcc bytes)
   builds an 8-byte mesh point `{u32 id, s16 x, s16 y}`:
   - `STD_MeshPnt_initPrm(mp)` (thunk `0x003d1634`);
   - `id = fn 0x003f52e8(db, rec) & 0xfff3fff3`, where the accessor returns
     `(u16[rec+2] << 16) | u16[rec+4]` (native words after the byte-pair
     swap) for record classes 1–3 (`class = word0 >> 13`);
   - `x = fn 0x003f5368 = u16[rec+6] & 0x7ff`, `y = fn 0x003f53e8 =
     u16[rec+8] & 0x7ff`;
   - `STD_MeshPnt_isValid(mp)` (thunk `0x003d1640`), then
     `STD_MeshPnt_chgLv(mp, 1, out)` (thunk `0x003d1658`), then
     `isValid(out)`; on a failure it logs through `0x003c5580` with source
     line 649, 668, 675 or 682 and returns −1.
   Callers: `0x003b1b44`, `0x003b42c0`, `0x003b4b58`, `0x003b5024`,
   `0x003b5808`, `0x003c0bf4`, `0x003d0110` (all EU2011). The three
   accessors are also called from `0x003a63d8`, `0x003ccd48`, `0x003cd910`.
   A second accessor triple with the same masks (`0x003f58a0`, `0x003f58e4`,
   `0x003f5928`) serves another record kind through `fn 0x003c0440`.
2. **The marker bits.** The mask `0xfff3fff3` clears bits 3:2 of each half
   of the id. `STD_MeshID_judgeLevel` (`STDDLL.dll` rva `0xc36c`) returns
   level 1 only when `(id & 0x000c000c) == 0` (levels 2–6 are the keys
   `0xf2`…`0xf6` built from the two low nibbles); with the bits left in
   (`0x8b6c8b60`) it returns `0x7fff` and `chgMapPnt` returns status 2. So
   the `11` of the `11xx` nibble is a marker of the stored form that the
   reader strips, and the remaining two bits belong to the position.
3. **The arithmetic** (`STD_MeshPnt_chgMapPnt`, rva `0x13cc8`, double
   precision floating point; measured, see `mesh`): the result is
   `{s32 a, s32 b}` in 1/512 arc second (1,843,200 per degree). The high
   half of the id and `y` give `a` (latitude), the low half and `x` give
   `b` (longitude). One level-1 mesh is 38,400 units of latitude (1/48°)
   and 57,600 of longitude (1/32°) and is divided into 2048 fine steps.
   `0x8b608b60`, (0, 0) → (27955199, −245606400) = 15.1667°, −133.25°;
   (100, 200) → +3750, +2813 (= 200·38400/2048 and 100·57600/2048, rounded).
   With `m` = the half with bits 3:2 removed (`(v & ~15) >> 2 | (v & 3)`),
   this is `4·(m + fine/2048)` units of 1/192° and 1/128°, origins 32768 and
   52736 — the M4.27 formula with the fitted origins.
4. **Factory records.** `POINT010`: 15,469/15,469 records give the mesh
   point the formula expects and a map point within 1 unit of
   `fine_position`; mesh level 1 for all. All 33 files, 300 records each:
   9,483/9,483, every run `ACCEPT`. First record of `POINT010`:
   `6027 a76f c95e 0f68 03c1` → mesh `0xa763c952`, x 1896, y 961 → (96901218,
   −17111475) = 52.572275°, −9.283569°.
5. **The exact difference.** The firmware result is an integer. On 2,210
   records of `POINT010` (every 7th): `b` is the host value rounded **up**
   (equal when the host value is whole, 254 records); `a` is the host value
   rounded **down**, except that 413 of the 573 records whose host value is
   whole give one unit less. The largest difference is 1 unit = 1/512″
   (about 6 cm).
6. **Controls.** Fine fields exchanged: 0/15,458 match (11 records have
   equal fields). One-unit reading: 0/15,469. A record with class bits
   cleared: status −1, logger line 668. `sh4fpu.py --selftest` and
   `poi_position_l3.py --selftest` pass.
7. **`point_census`.** Every one of the 2,727,806 EU name records is class 3
   and not an escape record; word 6 always has `0x0800` set above the 11
   bits (the firmware masks it away); word 8 is never above `0x7ff`.
   `fine_fields` masked only word 6; it now masks both, as the firmware
   does. No position changes.
8. **Spatial-tree reader: not found.** Checked and ruled out: the four
   functions of the record-accessor file (`0x003f5100`–`0x003f5c00`, EU2011)
   that load `0x7ff` are the two triples above, and they refuse class 0;
   the other 382 loads of the literal `0x07ff` in `Navi.exe` were not
   examined one by one (the two in `fn 0x003cd59c` clamp a text length).
   No function was found that reads the leaf layout
   `u32 ptr, u16 size, u16 kx, u16 ky, u32 fine`. One structural note: the
   tree entry starts `0008` and the node end `0005`, and the entries are 8
   and 5 words long, so they fit the generic record framing of the walker
   `fn 0x003f5194` (length in words in the low 10 bits, class 0).

## Interpretation

- **Fact (measured):** observations 1–7. The position of a POI in the
  firmware is the M4.27 formula; the origins 32768/52736 and the scales
  192/128 are the library's, not a fit.
- **Fact (code):** the reader takes the position from the **name record**
  (bytes 2–9). The seven callers of `fn 0x003c032c` were not analysed.
- **Hypothesis:** the one-unit differences of observation 5 are the
  library's `double`→`int` conversions; they depend on the FPU model of
  `sh4fpu.py` (IEEE double in Python, truncation on `ftrc`) and were not
  compared with the unit.
- **Hypothesis:** the spatial tree is walked with the generic record
  walker (observation 8); the code that does it is not identified.
- **Not measured:** US2011 (the VAs here are EU2011 only; the US build is a
  different `Navi.exe`); escape records (`word0 & 0xfc00 == 0xfc00`), which
  no EU name record uses; mesh levels 2–6; the second record kind of
  `fn 0x003c0440`.

## Conclusion

The hypothesis holds for the conversion. `fn 0x003c032c` (EU2011) with
`STDDLL!STD_MeshPnt_chgLv`/`chgMapPnt` is the firmware's POI position
code; its arithmetic is written out above and agrees with
`point_census.fine_position` on every factory record tried, within the
1-unit rounding of its integer result. The spatial-tree reader is not
named: this half of the task is a negative result and continues as M3.35.
