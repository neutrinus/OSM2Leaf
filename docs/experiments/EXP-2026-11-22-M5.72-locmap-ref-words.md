## Question

Can the road writer emit the point reference word the `LOC_map` walk reads so that no guest load leaves the 512-byte copy window, and can a factory census explain that word on ≥95 % of the points that carry it?

## Hypothesis

`0x0100` in `fa_encode.shape_words` is the constant placeholder for the reference word (C-6776); writing `0xffff` or a mutual pair of link-start word indices inside the same record should keep every load in-window. **Falsifier:** loads beyond the window persist, or the factory census shows the word is not a word index at all. The second half of the falsifier fired: the census cannot reach 95 % without the host model of M9.67.

## Interpretation

- **FACT:** replacing the constant `0x0100` with `0xffff` plus mutual link-start pairs in `fa_encode.build_record` removes every out-of-window load in the L3 run; the firmware still walks the record (46 loads, 92 B). L2 and the 89 tilewriter checks pass.
- **FACT:** all factory mutual references occur on points with bit 13 of y set (95,068/95,068), but only 66.2 % of those y13 references are mutual inside a single record. The remaining 33.8 % and the 70 % outside-record values are consistent with references into the shared ~11 KB shape buffer (several records copied together, M9.66), which this per-record census cannot resolve.
- **UNKNOWN / blocked:** the ≥95 % explanation of the carried word needs the host model of the M9.66 shape walk (M9.67) to classify which flags create a reference slot and which buffer record a value targets. Per the task's Stop rule, M5.72 is set `blocked` with `Unblock: M9.67`; the in-window writer fix and all controls remain merged.
- **OBSERVED:** the result table still has zero counts for G3, as for G in M9.66; that is M9.67's remaining goal, not M5.72's Done-when.

## Conclusion

The writer-side half of M5.72 is done and proven (no stale loads, L2 PASS), but the 95 % census condition is not, so the task is `blocked` on M9.67 rather than `done`. No car or L4 claim is made.
