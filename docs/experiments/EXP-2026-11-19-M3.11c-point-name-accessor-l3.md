## Question

Does the accessor pair `fn 0x003f632c` / `fn 0x003f5e78` (EU2011; US2011 `0x0041ec8c` /
`0x0041e7d8`) return record 0's display name on the factory `POINT010` page when it runs
with the page context the firmware builds, and does it follow the M5.12 rename?

## Hypothesis

The 2026-11-08 pass stopped at the resolver `fn 0x003f51e0` (EU2011), which needs the BSS
slot table `0x00d53500` and the import `OSMDLL!taskIdSelf`. M3.22 found that the POINT
writer fills slot `+0x1c` (page) and slot `+0x20` (from a header-table entry). Reading the
resolver: a `db` that equals slot `+0x1c` resolves to slot `+0x20`, and `fn 0x003f56bc`
reads a field dictionary there. If the writer is given a page and the file's dictionary
block, the accessor should return the name pointer of every record.

**Falsifier:** the dictionary block is not unique in the file, or the accessor returns
-1/0 or faults. The accessor could also return a range that is not the record's display
text, or that does not split it into name and address (field 6). For the M5.12 page, the
falsifier is that it does not return `OSM2LEAF TEST POI1`.

   `run` maps the module (compressed sections zero-filled), the page and the dictionary
   block (both **swapped to native u16**, as the walker needs, M9.38) and a stub for
   `taskIdSelf`. Its declared inputs are the M3.22 seeds (`G+0 = OBJ`, `G+16 = 1`,
   `OBJ+20 = page`) plus one more: header-table entry `+44 = dictionary`. That is the field
   that `0x0040e9dc` (EU2011) copies into slot `+0x20` for type `0x14ef`. The writer then
   fills both slots. The tool calls the name and length accessors (`r4 = page`,
   `r5 = record`) and the field-6 accessors (`r6 = 6`) on all 1000 records. The text is
   read at the returned offset from the file-order page.
3. **Controls.**
   - *Positive:* record 0 of the US2011 page must be `HANA HEALTH CENTER` (the M5.12
     S2 target). The M5.12 same-length rename must change it to `OSM2LEAF TEST POI1`. On
     every record, name + address (field 6) must equal the record's display text, the
     suffix after its inner `ff ff`. This text comes from `parse_page`, a framing tool that
     knows nothing about fields.
   - *Negative:* (a) the same run without the dictionary (slot `+0x20` stays 0);
     (b) `db = page+2`, a pointer that is not in the table. Both must give no pointer.
     Selftest negatives: a dictionary with a wrong field id or with only 5 fields is
     rejected, and a wrong name/address split is a `mismatch`.
4. **Scope.** One page per build (EU2011 1000 records, US2011 1000 records), field 5
   (name) and field 6 (address). Out of scope: the escape path (`0x003f8a0c` → 0,
   `rec+25`), because none of the 2000 records is an escape record (all tags `0x60`/`0x68`);
   the loader that puts the dictionary block in memory and the header entry (`+44`) — both
   are declared inputs; the byte order of the text in memory (M3.11b).
5. **Falsifier.** As in Hypothesis. The tool exits 1 if one record is not `ok`, or if
   either negative returns a pointer.

## Observations

### Accessor chain (EU2011, `sh4dis`)

- `fn 0x003f632c(r4=db, r5=rec)`: `0x003f8a0c(rec) == 0` (escape) → `0x003f8a80(rec)`;
  else `fn 0x003f61bc(db, rec, 5)`; returns -1 when that gives 0.
- `fn 0x003f61bc(db, rec, f)`: `0x003f51e0(db)` (≠ -1) → `loc = 0x003f56bc(db, rec, f)` →
  `n = 0x003f57a8(db)` → `0x003f5e10(loc, n, f)`.
- `fn 0x003f51e0(db)`: calls `*0x0055d8f0` (`taskIdSelf`), then compares `db` with slot
  pairs `(+0x0c→+0x10)`, `(+0x14→+0x18)`, `(+0x1c→+0x20)`, `(+0x24→+0x28)`,
  `(+0x2c→+0x00)`, `(+0x38→+0x3c)`, `(+0x40→+0x44)`, `(+0x60→+0xa4)`, `(+0x50→+0xa0)`,
  `(+0x70→+0xa8)`, `(+0x80→+0xac)`, `(+0x88→+0x8c)`, `(+0x90→+0x94)` and returns the
  companion slot. If none match, it calls `0x003f3a10(db)`; it returns -1 for 0.
- `fn 0x003f56bc(db, rec, f)`: `C = resolver(db)`, `D = C + 2*u16[C+2]`; it requires
  `(w & 0xe000) <= 0xc000` and `(w & 0x1800) >> 11 ∈ {0,1}` for `w = u16[rec]`, and
  `f < u16[D+26]`. It walks `e = D + 2*u16[D+24]`, then `e = D + 2*u16[e]` f times, and
  requires `u16[e+12] == f`. The data start depends on `w >> 13`: 3 or 2 →
  `rec + 2*(hi+lo+8)` of `u16[rec+10]`; 6 → `rec + 2*(hi+lo+2)` of `u16[rec+2]`;
  5 → `rec+8`; 0 → `rec+2`.
- `fn 0x003f57a8(db)` = `u16[D+26]` (the field count).
- `fn 0x003f5e10(loc, n, f)`: `loc` begins with `n` byte-sized field lengths in words
  (high byte = even field, low byte = odd field, `(n+1)/2` words). The field starts at
  `loc + 2*((n+1)/2 + Σ len[0..f-1])`.

### Dictionary block

US2011 `.DAT` (9,715,200 B): `dictionary candidates=1 C=0x749500/D=0x74952a/n=9`.
EU2011 `.DAT` (9,864,704 B): `candidates=1 C=0x6a7d00/D=0x6a7d2a/n=9`. Without the
`u16[C] == 0xffff` condition one more offset passes in each file (`0x73ed2a`,
`0x687f2a`), with the same `D`. The block holds the ASCII field names that `refer.md`
lists (`area code` … `icon code`, 9 fields; field 5 = `facility name`, field 6 =
`address`).

## Interpretation

- **FACT:** with the page context built by the firmware's own writer, the name accessor
  `fn 0x003f632c` (EU2011) / `0x0041ec8c` (US2011) is called with `r4 = page`
  (`db`, the value in slot `+0x1c`) and `r5 = record`. It returns a pointer to field 5, and
  `fn 0x003f5e78` / `0x0041e7d8` returns that field's length in 16-bit words. On US2011
  record 0 the field is at `+0x5e`, 9 words: `HANA HEALTH CENTER`, without the address
  `4590@HANA HWY`, which is field 6. After the M5.12 rename it is `OSM2LEAF TEST POI1`.
- **FACT:** on 1000/1000 records per build, the name and the field-6 address split the
  record's display text exactly. Both negatives return -1.
- **FACT:** the name is located through the file's own field dictionary (9 fields, one
  block per file at `.DAT` `0x749500` US2011 / `0x6a7d00` EU2011) and through per-record
  field-length bytes. It is not located by an `ff ff` delimiter: the earlier
  "`ff ff`-delimited suffix" reading (C-2925) is the whole display text, name + address.
- **OBSERVED:** the dictionary pointer reaches slot `+0x20` through header-table entry
  `+44` (`0x0140e240` EU2011 / `0x0127ea40` US2011, an entry of the 100 × 80-byte table
  that `0x0040ee4c` searches). Who loads the block and fills that entry was not run (it
  is a declared input).
- **HYPOTHESIS:** the accessor reads lengths as native u16, so the page in memory is the
  swapped copy that the walker needs. In that copy the name bytes are pairwise swapped
  (`AHAN…`), so the text itself is either swapped back or drawn from another copy. That is
  M3.11b. This EXP fixes the offsets and lengths; byte order does not change them.
- **UNKNOWN:** the escape path (`rec+25`, `0x003f8a90`); there is no escape record on
  these pages.

## Conclusion

M3.11c is done. The name accessor for a `POINT` record is `fn 0x003f632c(db=page,
rec) → pointer`, with `fn 0x003f5e78(db, rec) → length in words` (EU2011; US2011
`0x0041ec8c` / `0x0041e7d8`). Both run in PySh4 on the factory page with the context the
M3.22 writer builds, and they return `HANA HEALTH CENTER` (US2011 record 0) and
`OSM2LEAF TEST POI1` after the M5.12 rename. `docs/format/firmware.md` and
`docs/format/refer.md` get the field-dictionary mechanism; C-5110–C-5117;
`reader-coverage.md` row 10 records the located name reader. Open: M3.11b (in-memory byte
order) and who loads the dictionary block.
