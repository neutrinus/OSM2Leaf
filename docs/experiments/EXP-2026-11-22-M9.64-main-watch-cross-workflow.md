## Question

Does the H117 watchdog count a green run of **one** workflow as covering a red
run of **another** workflow on `main`, so that a red `CI quality gate` run is
reported `shadowed` (and stays quiet) because a later `L1/L2 synthetic fixtures`
run was green, even though the two workflows test different things?

## Hypothesis

`classify()` in `.github/scripts/main_watch.py` kept a single `later_green`
boolean that any `success` run set, regardless of `workflowName`. The watchdog
`workflow_run` trigger lists both `CI quality gate` and `L1/L2 synthetic
fixtures`, so a run list that contains both workflows lets an L1/L2 success
mark a red gate run `shadowed`. The gate workflow is the one that runs
`selftest`/`claims_check`/`todo_check`/`fn_audit`; the L1/L2 workflow runs the
card round-trips. A green in the second says nothing about the first.

**Falsifier:** a red gate run that the new classifier still reports `shadowed`
whose only later green is a non-gate workflow — or the new classifier changing
a real verdict on today's `main` where the recorded history does not justify it.

## Interpretation

- **FACT:** the pre-change `classify()` counts the recorded gate-red/L1/L2-green
  pair as `1 shadowed` (exit path `GREEN`); the post-change one counts it as
  `1 salient` + `1 unrelated green`. The two workflows test different things
  (gate: selftest/claims_check/todo_check/fn_audit; L1/L2: card round-trips),
  so the old verdict was wrong in principle.
- **OBSERVED:** today the wrongness has not flipped a final verdict, because
  `a92f5a9b`'s own later gate green (`86669dbc`) covers it in the full window;
  the pair only shows the defect when the L1/L2 green is the *only* later
  green. The fixture isolates that case and the selftest pins it.
- **OBSERVED:** the pre-change `--replay` would have reported the same red-tip
  moments on this window; its defect is in the shadow decision, not the replay
  list. Post-change `--replay` classifies each tip against its own workflow, so
  a saved two-workflow list cannot cross-shadow, and it labels each moment.
- **HYPOTHESIS:** with the change merged, a red gate run followed only by a
  green L1/L2 run (and no green gate run) opens a `[H117] fix:` issue and fails
  the watchdog, instead of being counted `shadowed` and staying quiet.
- **UNKNOWN:** whether the two-step sweep produces any change on the next real
  red, because the current tip is green; the first real red after merge is the
  end-to-end check (Follow-up).

## Conclusion

`.github/scripts/main_watch.py` now scopes shadowing to the red run's own
`workflowName` (a green of another workflow is `unrelated-green`, never
shadowing), and `.github/workflows/main-watch.yml` runs the sweep once per
workflow with its own `--workflow`, so the gate and the L1/L2 fixtures each get
a verdict line and neither trigger is dropped. The `--selftest`/`--replay`
contract and the RED set and issue marker are unchanged. New fixture
`main_watch-crossworkflow.json` pins `gate-red then l1l2-green → 1 salient` and
the existing case pins `gate-red then gate-green → 0 salient`. Today's `main`
stays `0 salient`; `tools/gate.py` is 5 pass / 0 fail / 0 skip. Claims
C-6690–C-6699.
