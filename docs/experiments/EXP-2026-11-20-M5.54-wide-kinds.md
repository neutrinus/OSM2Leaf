## Question

Can `tilewriter` write OSM roads into the remaining six wide-row directories in the Dolnośląskie bbox (`0x2246`, `0x2346` ×2, `0x2546`, `0x2646`, `0x2946`) through the M5.53 row model? Does a directory with several wide rows narrow to `0x2046` only once none of its rows keeps a sub-record?

## Hypothesis

The M5.53 row model is kind-independent. A `0x2n46` directory differs from `0x2146` only in having more wide rows. So the same splice path works once the kinds are allowed and narrowing is decided per directory: all wide rows narrow together, or none does.

**Falsifier (stated before the result):** any of the following.
- For any of the six directories, a pipeline run that writes every sub-record parcel:
  - does not end with the directory as `0x2046`;
  - changes bytes outside that directory's `2*kind` bytes in the factory part of the tile;
  - fails `cardcheck`, `one_tile_one_directory`, the `l2check` tile checks or the `s1_wide_dir` census.
- A partial run (one wide row left) changes the kind word or fails the census.

## Interpretation

- **FACT (C-5540):** `tilewriter` splices into every kind `0x2146`–`0x2946` through the row model.
  - On real `B48R058R`, each of the six remaining bbox directories narrowed to `0x2046` once its sub-record parcels (2–22 ways) were written.
  - The factory part of the tile changed only inside that directory.
  - `cardcheck`, `one_tile_one_directory`, the `l2check` tile checks and the row-model census pass.
  - P1's bbox now has 20 of 20 section-1 directories spliceable; 6 of 20 are proven end to end here, 1 in M5.53, and 4 more `0x2146` by the M5.53 navigator.
- **FACT (C-5541):** narrowing is decided per directory.
  - A partial splice keeps every wide row wide and the kind word unchanged.
  - The written row loses only its written column's sub-records and flag; column 0 keeps the row marker.
- **FACT (C-5542):** `clarion_tile.read_dir` kept a declared remainder only up to 4,096 bytes. So a `0x2946` directory (4,608 B) ended 4,608 bytes early for its readers, including `one_tile_pipeline.prove_tile_change`. With the limit at `31*512` the real tile still rebuilds byte-identically.
- **FACT (C-5543):** the full `l2check` cannot PASS on any EU tree since M5.52.
  - The cause is `refer_rename_resize`, a REFER check unrelated to tiles; the factory-tree control fails identically.
  - This task's `l2check` evidence is therefore the tile subset (`--skip-mutation`: census, files, drstr, cmp, `tile_roundtrip`, `tile_semantic`), which passes on all seven outputs.
  - The REFER check is filed as M5.55.
- **Rule 13:** the firmware's reading of wide rows and sub-records is still UNKNOWN. M3.25 located the directory and block handlers on the card (EU2011) and eight body decoders. Which one handles a wide row is a lead for a reader task, not a claim here.
