## Question

Are the five M4.96 class-d residual ranges on `B48R058R` (1,326 B / 2 ranges)
and `B30R048R` (176 B / 3 ranges) padding or a named record block, and does the
block produce a covering span that moves the `tile_bytes` headline?

## Hypothesis

The five ranges are the **section header table** of each tile's three sections
(sec1/sec2/sec4), a count-word bounded block read by `clarion_tile.read_tile`
(`clarion_tile.py:39-41` reads `u16@taddr` as the word count). They are NOT
padding: their first words are structured offsets, and the alignment fill past
the table end carries 0 nonzero bytes. Counting these spans in the producer of
`tile_bytes` (`map_signals.tile_explained_percent`) should move the headline.
The reader is a TOOL reader, not a rule-13 firmware VA.

**Falsifier, stated before the result.** If any row's `u16@taddr` is not the
table's word count, or its nonzero bytes are not bounded by
`[taddr, taddr + 2*count)`, or `outside_nz > 0`, the "bounded named block" call
is refuted for that row. If injecting one nonzero byte past the table end does
not flip `outside_nz` and the sum, the byte test is not load-bearing. If adding
the spans leaves `tile_bytes` unchanged while the tool still reports nonzero
unexplained bytes, the falsifier "a span added covering no real bytes" is not
exercised — the move must be quoted, not assumed. Branch (b) ("every class-d
byte is padding") is refuted by structured table words and the zero-fill tail
carrying 0 bytes.

## Interpretation

- **FACT:** Every class-d row is bounded by `[taddr, taddr + 2*u16@taddr)`,
  has `inside_nz == bytes`, `outside_nz == 0`, `overlaps == 1`, and is read by
  `clarion_tile.read_tile` (O1–O3). The zero-fill tail carries 0 nonzero bytes.
- **FACT:** The five rows sum to the tool's own still-unexplained figure
  (1,326/1,326 and 176/176, `sum_ok=True`) (O1, O2, O4).
- **OBSERVED:** Adding the section-table spans to `tile_bytes` moves the
  headline for B28/B30 and leaves B48 at 76.29% at two decimals (O5).
- **HYPOTHESIS (confirmed):** The class-d residual is one named block per
  section — the section header table — not padding. The M4.96 label "section
  table span artifact (no reader VA)" is compatible: the block is real; the
  metric merely excluded it. The reader is a tool reader, not a firmware VA.
- **UNKNOWN:** nothing within this task's scope. Whether a future reader-model
  decision should also change the `tile_bytes` definition is now moot — it has
  been changed here per the M4.96 follow-up.

## Conclusion

The class-d residual of `B48R058R` (and control `B30R048R`) is the section
header table: count-word bounded (`u16@taddr = 419/417/388` and
`83/33/10`), read by `clarion_tile.read_tile`, NOT padding. Five rows sum to
the tool's own 1,326 B / 176 B with `sum_ok=True`; each row is assigned the
named `section-table-header` block, with the count-word bound and zero-fill
byte tests quoted and the count-word/past-end mutations shown to flip the
verdict. Branch (a) of Done when is taken: the covering spans were added to
`map_signals.tile_explained_percent` (the producer of `tile_bytes`) with
`--selftest` cases, and the moved percentages are quoted — B28 `99.98% →
100.00%`, B30 `95.86% → 95.88%`, B48 stays `76.29%` at two decimals.
`tile_unknown --selftest` stays green. No writer, firmware search, reader VA
or vendor bytes in the repo; vendor `tools_ze0/` untouched.
