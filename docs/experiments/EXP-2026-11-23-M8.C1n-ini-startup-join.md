# EXP-2026-11-23-M8.C1n-ini-startup-join: what leaves `INI_STARTUP`, and touch on the running UI

- **Status:** done. Done-when, second branch: the event that leaves
  `INI_STARTUP` is named, with its handler and the code that raises it.
  With an emulator-only patch the state machine also leaves the state.
  Touch then reaches the AUI: a tap on "OK" of the consent screen goes on

## Question

M8.C1l left the screen state in `INI_STARTUP` (C-8324, C-8325). Which event
leaves it, who raises it, and why does it not come on `-M ze0`? Once it
leaves, does touch reach the UI? EXP M8.H35 found touch dropped in
`kepdrv` (C-8441, C-8442).

## Hypothesis

`INI_STARTUP` waits for an input that the emulator does not provide: a
vehicle signal or a micom answer. The touch lock in `kepdrv` is lifted by
the same start-up path.

**Falsifier:** the event that leaves `INI_STARTUP` is raised inside the
UI with no outside input, or touch stays dropped after the state changes.

## Method

1. **Sample and hash.** The files in the Sample bullet above: EU 2011 build A
   `Navi.exe` in `archive/head256.img`, the US 2011 card and NK1. No byte on the
   card changes; the guest patch is applied at load.

2. **Commands.** From the repo root (`$Q` = built `qemu-system-sh4`, `$W` =
   scratch outside the repo):

   ```bash
   python3 tools/ze0_uistart.py find archive/sd-images/LEAF_2011-2012_US.img   # join sites, id 3265
   python3 tools/ze0_launch.py --card archive/sd-images/LEAF_2011-2012_US.img \
     --flash ~/projekty/leafre-work/m6.18/nand.bin --gdb 1240 --ui-start \
     --peer panel --workdir $W/s7 --timeout 1500
   printf 'tap 277 98\n' | socat - UNIX-CONNECT:$W/s7/panel.ctl
   python3 tools/ze0_screenshot.py plane --monitor $W/s7/mon.sock -n 1 -o $W/p1.png
   python3 tools/cerom.py --image-start 0x200200 archive/head256.img imports ScreenState.dll
   python3 tools/sh4dis.py archive/head256.img ScreenState.dll --image-start 0x200200 \
     --va 0x02b924f4 --count 20
   ```

   The live boot, the `ScreenStateDebug` grep, the state-object breakpoint at
   `0x0331e07a`, the static symbolic pass over `ScreenStateCC`, the guest patch
   of the join at `0x02b924fe`, the `kepdrv` breakpoints and the plane-1 dump
   are the steps 1–7 of the original Method; each printed result is quoted in
   Observations O1–O9.

3. **Controls.** Positive: S3 (gdb by hand), S7 and S8 (`--ui-start`) log
   `ForwardState [MAP_RELAY]` within 30 ms of `COMP_OK`, and a cleared guard
   reaches the posting step `0x03d27450` with the agree click. Negative: L1,
   G1, L3, S2, S4 and S6 stay in `INI_STARTUP` with no patch; before the guard
   is cleared taps hit `IsKeyControlNotify` only; a tap at panel (277, 382)
   gives no `ScreenAction` (Y flip). Both directions are in the Controls
   section below.

4. **Scope.** EU 2011 build A `Navi.exe` `ScreenState.dll` handler
   `0x02b921c0` and join `0x02b924f4`; NK1 `kepdrv` `0x03d267b4`,
   `0x03d27450` and `commondll` `0x03e898d0`/`0x03e86bf8`; US 2011 card only
   (the EU join pair is found but not run). The 29 failing controls and
   windows 8/37/40/41/44/46 are out of scope (Not done). Screens stay outside
   the repository.

5. **Falsifier.** The event that leaves `INI_STARTUP` is raised inside the UI
   with no outside input, or touch stays dropped after the state changes. The
   join needs audio micom input and the guard is cleared only through
   `CApi_AntitheftUnlock` (O4, O7), so the falsifier did not fire.

## Observations

**O1 — Event ids.** ScreenStateCC's `.data` holds alphabetical name
tables:
- states: 671 names at data `+0x3b8`;
- events and functions: 5 117 names at `+0x1968`;
- variables: 1 049 names at `+0x14990`.

Each table starts after a zero word. In S1 the event ids in `r5` match
the log order when the id is the table index **+3**:

| `r5` | Logged event |
| --- | --- |
| `0x228` | `NAVIGENERAL_CC_CAS_NAVIREG_CARSTOP` |
| `0x88b` | `SK_OTH_STARTUP` |
| `0x23a` | `NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END` |
| `0x29` | `ANTITHEFT_CC_NTF_COMP_OK` |

Variable ids are the index **+1**. The handler of `SK_OTH_STARTUP` sets
variables 10 and 11, and the log names them `VAR_ANTITHEFT_PLEASEWAIT_STATUS`
and `VAR_ANTITHEFT_SECURE_STATUS`. State ids are also the index **+1**: a
handler's `ForwardState(622)` is logged as `STS_RELAY`, and 237 as
`MAP_RELAY` (O3).

**O2 — The `INI_STARTUP` handler.** In S1 every `INI_STARTUP` event goes
through vtable slot 21 = `0x02b921c0` (state object `0x004b0030`). The
handler compares the event with a chain of `cmp/eq`:

| Event | Action |
| --- | --- |
| `SK_OTH_STARTUP` | `SetVariableValue(PLEASEWAIT, …)`, `SetVariableValue(SECURE, …)`, `ExecuteFunction(42, 1190)` (`STATUSGET_ANTITHEFT_SEQUENCE` in the log) |
| `SS_JON_TRANSITION_LAST_SCREEN` | `ExecuteFunction(19, 236)` (`GET_LAST_STATUS_SCREEN_KIND`) |
| `SYSTEM_CC_FNR_LAST_STATUS_SCREEN_{TBT,AIRCON,ELE}` | set `VAR_NEXT_STATUS_SCREEN`, then `ExecuteFunction(19, 235)` (`GET_LAST_SCREEN_KIND`) |
| `SYSTEM_CC_FNR_LAST_SCREEN_MAP` | `ForwardState(SRT_COLD_OPENING_ANIMATION_FIRST)` or `ForwardState(MAP_RELAY)`, depending on `VAR_I_AGREE_STATUS` and `VAR_FIRSTMAP_DRAW_END` |
| `SYSTEM_CC_FNR_LAST_SCREEN_AUDIO` | `ForwardState(ADO_RELAY_MOVIE / ADO_RELAY_OPERATION)` |
| `SYSTEM_CC_FNR_LAST_SCREEN_STATUS` | `ForwardState(STS_RELAY)` |
| anything else | the base-class handler `0x02b482c4` |

So the only way out of `INI_STARTUP` is `SS_JON_TRANSITION_LAST_SCREEN`.
That event leads to the two SystemCC queries, and their answers lead to
`ForwardState`.

**O3 — The join.** The function at `0x02b924f4` calls
`State::ExecuteCompositeEvent` (ScreenState export 21, thunk
`0x02c66bd0`). Its arguments are `(SS_JON_TRANSITION_LAST_SCREEN = 3265,
2, 41, 1756)`:
- 41 = `ANTITHEFT_CC_NTF_COMP_OK`;
- 1756 = `NOTICE_AUDIO_SOURCE`.

In S3 the call is hit on events of the live state (`pr = 0x0331e0c4`, in
`State::EventHandler`). The same 5-instruction site is also at
`0x02befcda`, so there are two sites with the same arguments.
`ze0_uistart.py find` lists both on the US card. On the EU card it lists
two more, with id 3279 and the same first event 41. The 2011 EU card's
own pair is the 3279 pair.

**O4 — Who sends the two events.**
- `ANTITHEFT_CC_NTF_COMP_OK` arrives at about 120 s guest time. It comes
  after `ACM::WaitModule Timeout ID[48] WaitTime[60000]` starts
  `AntiTheft.exe` (L1, S3, S7).
- `NOTICE_AUDIO_SOURCE` never arrives in any run. In ScreenStateCC it is
  raised only by about 30 small functions
  (`0x02b90240`–`0x02b9219a`). Each one sets `VAR_CURRENT_AUDIO_SOURCE`
  (variable 20) to a source name and then calls
  `StateContext::EventHandler(1756)`. These are the handlers of SystemCC's
  audio-source events.
- The audio side does not come up on the emulator. `serial.log` repeats
  `AudioNetwork … CInaiProtocol[TX]::WriteData: write failed` and
  `ComReStart … COMSTS_WAIT_RESPONCE` (2 062 lines in L1). Those come from
  the audio micom link on `SCI1:`, which M8.H45 models.

**O5 — Join patched, state leaves.** S3 used gdb by hand. It set `r6 = 1`
at the `jsr` `0x02b92502` and wrote `e601` over `e602` at `0x02b924fe`.
After `ANTITHEFT_CC_NTF_COMP_OK` the log shows, in order:
- `ExecuteFunction ctrl[19] function[GET_LAST_STATUS_SCREEN_KIND]`;
- `SYSTEM_CC_FNR_LAST_STATUS_SCREEN_AIRCON`;
- `GET_LAST_SCREEN_KIND`;
- `SYSTEM_CC_FNR_LAST_SCREEN_MAP`;
- `ForwardState [MAP_RELAY]`;
- `MAP_RELAY::CompleteShowScreen`;
- `ForwardState [SRT_COLD_I_AGREE_NAM]` (the consent screen of the US
  build);
- `SystemCC : AUI Initialize Complete!!!`.

S7 and S8 reach the same result with `ze0_launch.py --ui-start`, without
any manual step.

**O6 — Where patches must go.**
- An IPL patch line for the site is applied at load (`qemu.out`: "app
  image: 1 ipl-patch line(s) applied"), but the bytes read back as `e602`
  later (S2). NK1 loads ROM image A from the card itself.
- In S4 the tool's write to the P1 address was refused with `E14`: the
  stop is in user mode, and the stub cannot reach P1 there.
- In S6, reading the second site failed with `E14`: that page is not
  mapped in the process at that moment.
- The tool now writes through the code VA of each mapped site and skips
  sites that are not mapped. In S7 it reported:
  - `16.1 s: hit 1 at 0x02b92502: r6 := 1; e601 written at 0x02b924fe`;
  - `16.4 s: hit 2 …, patch still in place; detaching`.

**O7 — Touch is still locked after the state change.** A tap in S3 still
stops in `IsKeyControlNotify`. At the breakpoint, `obj = r4 = 0x0005ee10`,
`obj+0xc4 = 00`, `obj+0xc5 = f1`.

In `kepdrv`:
- the constructor writes `0xf1` to `+0xc5` (`0x03d25c88`–`0x03d25c90`);
- the log names this byte `m_byKeyGuardAllKey` (string `0x03d21534`);
- the only setter is `SetGuardAllKey` (`0x03d267b4`, strings `0x03d21a5c`,
  `0x03d21a8c`). `KEP_IOControl`'s dispatcher (`0x03d26d74`, codes
  `0x801f2000 + 4·i`) reaches it for IOCTL `0x801f2028`.

The NK1 module that uses this code is `commondll.dll`:
- `0x801f2028` is loaded at `0x03e8990a` in the function `0x03e898d0`;
- that function first writes guard 0, then `0xf0` for mode 4 or `0xf1`
  for mode 5;
- its only caller is `CImplSetting::AntitheftUnlock` (`0x03e86bf8`, string
  `0x03e81638`), behind the export `CApi_AntitheftUnlock`.

The importers of `CApi_AntitheftUnlock` are Audio.exe, SystemEXE.exe,
SystemCC.dll, CameraCC.dll and AvCCWrapper.dll (`cerom.py imports`). In S4
and S7, `[VCL]Antitheft UnLock!` is printed, but breakpoints on
`0x03d267b4`, `0x03e898d0` and `0x03e86bf8` are never hit.

**O8 — Touch with the guard cleared.** In S7 the guard byte was written to
0 at the `IsKeyControlNotify` stop. The same tap then reached the posting
step `0x03d27450` with `r6 = 0x190`, `r7 = 0xf0` (400, 240).

A tap at panel (277, 98) gave this log sequence:
- `ScreenAction(SK_OTH_SCREEN_LOCK)`;
- `ScreenAction(SK_SCT_AGREE_CLICK)` at `SRT_COLD_I_AGREE_NAM`;
- `ExecuteFunction ctrl[25] function[TELEMA_NOTIFY_AGREE]`;
- `VAR_I_AGREE_STATUS = "true"`;
- `ForwardState [MAP_RELAY]`;
- `ForwardState [MAP_MAPOPERATION_NORMAL_MAP]`.

On screen (277, 382) is the "OK" button. The panel y is flipped (touch.md
§4: 480 − 382 = 98). A tap at panel (277, 382) gave no event.

**O9 — The AUI layer is drawn, but `screen` does not show it.**
- After the transition the DU has planes 1 and 2 on (both mode `0x1002`,
  key `0x83ff`/`0x3ff`). Plane 1 has window y = 480. Before it, only
  plane 4 was on.
- `ze0_screenshot.py screen` still shows only the map. It reads plane 1
  from row 480, which is black, and it drops pixels without the 1555
  alpha bit; the text pixels (`0x6f7f`) have no alpha bit.
- The raw plane 1 buffer (`ze0_screenshot.py plane`, rows 0–479) shows:
  - first the US consent text, "Touch OK to accept" and "OK"/"Decline";
  - after the tap, drawn over it: "Map Menu", "ZOOM OUT", "1/16mi",
    "ZOOM IN" and the popup "XM NavTraffic is expired".

Screenshots contain vendor screens and map data, so they are kept outside
the repository.

## Result

- **The exit event is the join `SS_JON_TRANSITION_LAST_SCREEN` of
  `ANTITHEFT_CC_NTF_COMP_OK` and `NOTICE_AUDIO_SOURCE`.** The handler of
  `INI_STARTUP` (`0x02b921c0`) handles it and moves on through SystemCC's
  last-screen answers. The join is registered at `0x02b924f4`. The second
  input, `NOTICE_AUDIO_SOURCE`, needs an audio-source change. The audio
  side waits for the audio micom (M8.H45).
- The touch lock has the same cause. The key guard `0xf1` is cleared only
  through `CApi_AntitheftUnlock`, and on the emulator nobody calls it.
- The hypothesis holds: the missing input is the audio micom, not
  something inside the UI.
- `ze0_launch.py --ui-start` is the emulator-only bridge until M8.H45. It
  runs `ze0_uistart.py run --touch-unlock`, which makes the join need one
  event and clears the guard at the first touch. No byte on the card
  changes.

## Controls

- Negative, no patch: L1, G1, L3, S2 (the IPL line was overwritten), S4
  (the write was refused) and S6 (the tool stopped). In all of them the
  state stays `INI_STARTUP` after `ANTITHEFT_CC_NTF_COMP_OK`, with no
  `ForwardState` line.
- Positive: S3 (by hand), S7 and S8 (tool) each log `ForwardState
  [MAP_RELAY]` within 30 ms of `COMP_OK`.
- Touch, negative: in S3 and S7, before the guard was cleared, taps hit
  `IsKeyControlNotify` only. Positive: after the guard was cleared, the
  posting step is hit and the agree click is logged.
- Y flip: the tap at panel (277, 382) gave no `ScreenAction`. The tap at
  (277, 98) gave `SK_SCT_AGREE_CLICK`.

## Interpretation

- **FACT:** the exit event is the join `SS_JON_TRANSITION_LAST_SCREEN` of
  `ANTITHEFT_CC_NTF_COMP_OK` and `NOTICE_AUDIO_SOURCE`, handled at
  `0x02b921c0` and registered at `0x02b924f4`; the audio source never arrives
  on the emulator because the audio micom link is down (O1–O4).
- **FACT:** touch stays locked because the key guard `0xf1` is cleared only
  through `CApi_AntitheftUnlock`, whose callers do not run on the emulator;
  `--ui-start --touch-unlock` is the emulator-only bridge (O7, O8).
- **OBSERVED:** the AUI plane 1 is drawn but `screen` composes it wrong; that
  is M8.C1t (O9).
- **UNKNOWN:** which caller of `CApi_AntitheftUnlock` should run with which
  mode; the EU card was not run.

## Conclusion

The event that leaves `INI_STARTUP`, its handler and the code that raises it
are named (O2–O5), and with an emulator-only patch the state leaves: a tap on
the consent "OK" goes to the map screen and the AUI buttons are drawn into
plane 1. M8.C1n's second Done-when branch is met; plane-1 composition is
M8.C1t and the micom bridge is M8.H45.
