## Question

`docs/research/full-system-emulation.md` §4 defines stage **F0** as "kernel
debug log on stdout; if debug output is disabled in the retail build, F0 =
MMU on, no fault". Does the current `-M ze0` reach F0 on EU2011, and which
registers does the boot touch that no model covers yet?

## Hypothesis

With the `dbgmsg` hook (M8.B6) the kernel's debug strings reach serial port
0, MMUCR.AT is 1 and neither the kernel halt nor the unhandled-exception
path runs in a 150 s boot. The registers left unmodelled are the ones of
devices that later stages need (DMA, HPB DMAC, CAN/micon, LCD), reached
mostly through area-7 aliases.

**Falsifiers (before the runs):** serial port 0 stays empty with
`dbgmsg=0x880404f4`; MMUCR bit 0 (AT) reads 0 at the end; either fault
counter (`0x88022164` halt, `0x88011cb8` unhandled exception) is above 0;
the serial log contains `Exception occurred!!` or `AER Exception Report
Start`.

## Inputs

| Item | Value |
| --- | --- |
| Debug sink | `fn 0x880404f4` (r4 = UTF-16 string, C-6240) |
| Fault counters | `0x88022164` (kernel halt loop), `0x88011cb8` (unhandled-exception report) |
| MMU state | MMUCR `0xff000010` bit 0 = AT |
| Clock | CurMSec `0x89e41888` |
| Unmodelled access log | QEMU `-d unimp,guest_errors` (`ze0-p4`/`ze0-area4`/`ze0-area6` catch-alls and `Invalid read/write` for unmapped addresses) |

## Method

All runs one QEMU at a time, in `/home/user/scratch/m8.a8/` (outside the
repo). `IMG=archive/head256.img`, `CARD=…/eu-card.qcow2`,
`QEMU=qemu-system-sh4.c10d`.

### 1. Positive run (F0)

```sh
python3 tools/ze0_dbgmsg.py run --duration 150 \
  --count 0x88022164 --count 0x88011cb8 --word 0xff000010 --word 0x89e41888 \
  -o f0-dbg.log -- $QEMU -M ze0,dbgmsg=0x880404f4 -kernel $IMG \
  -drive if=sd,index=0,file=$CARD,format=qcow2 -icount shift=0,sleep=off \
  -nographic -serial file:f0-serial.log -monitor none \
  -d unimp,guest_errors -D f0-unimp.log
python3 tools/ze0_serial.py banner f0-serial.log
```

### 2. Negative control (same binary, hook off)

```sh
python3 tools/ze0_dbgmsg.py run --duration 40 \
  --count 0x880404f4 --count 0x88022164 --count 0x88011cb8 --word 0xff000010 \
  -o neg-dbg.log -- $QEMU -M ze0,dbgmsg=0 -kernel $IMG \
  -drive if=sd,index=0,file=$CARD,format=qcow2 -icount shift=0,sleep=off \
  -nographic -serial file:neg-serial.log -monitor none
```

The `--count 0x880404f4` here is also the positive control of the counter:
it must be above 0 while the fault counters stay 0.

### 3. Register census and attribution

```sh
python3 tools/ze0_regs.py census f0-unimp.log --top 200
python3 tools/ze0_regs.py who archive/head256.img 0x19400000 0x19b00000 \
  0x19e00000 0xff800250 0xff801000 0xffc08000 0xffc08810 0xffc40008 \
  0xffc5a040 0xffc5b004 0xffe41030 0xffe48020 0xffe80000 0xfff80000 0xfff90000
python3 tools/ze0_regs.py --selftest
```

`census` folds the catch-all lines to one row per register (bases
`ze0-p4` `0xff800000`, `ze0-area4` `0x10000000`, `ze0-area6` `0x18000000`;
`Invalid` addresses in `0x1fxxxxxx` are printed as their P4 form
`0xffxxxxxx`, source `a7-alias`). `who` scans the literal pools of every
module's executable sections in images B and A for the page, the area-7
page, `phys >> 8` (VirtualCopy `PAGE_PHYSICAL`) and the exact register.

### Controls

- Negative: `dbgmsg=0` on the same binary and card → 0 serial bytes while
  the sink runs (counter above 0).
- Positive (counter): `--count 0x880404f4` reads 176 in 40 s, so a count of
  0 at the fault VAs is a real 0.
- Census selftest: synthetic lines for each source (P4, area 6, area-7
  `Invalid`, unmapped, `Unauthorized access`) fold to the expected rows.
- `who` negative: area-6 pages `0x19400000`, `0x19b00000`, `0x19e00000`
  and `0xffc40000` give 0 pool words in either image.

## Interpretation

- F0 is reached in its stronger form: the kernel's debug log reaches the
  UART (through the M8.B6 hook, not through any firmware SCIF path, C-6240),
  and the weaker form holds too (MMU on, no fault counter hit, no AER
  report). The negative control shows the text comes from the hook.
- The 9 358 `Unauthorized access` lines are QEMU's `target/sh4/helper.c`
  message for a user-mode access to P1/P2/P4; it raises an address error.
  WinCE on SH-4 makes API calls by jumping to trap addresses in kernel space,
  so most of these are probably system calls, not faults (HYPOTHESIS; the
  fault counters stay 0).
- All 148 unmodelled on-chip registers are reached through the area-7
  alias (`0x1fxxxxxx`), which the P4 catch-all does not cover; only two
  (`0xffc08810`, `0xffc08814`) are also reached through P4. `0xfff80000`
  has a P4 read-back stub (`ze0-stubs`), but the drivers use its A7 alias,
  so the stub is never hit there.
- The two biggest writers are the DMA drivers (`0xff801000` DMAC and
  `0xffc08000` HPB DMAC, the M8.C1 blocker) and IOLIB.dll (`0xffe80000`,
  `0xfff80000`, `0xfff90000`). `0xffc5a040` (170 reads) belongs to
  kepdrv/navdrv; the 170 reads of unmapped `0xa000` and the `0x5554`/`0xaaaa`
  writes look like a NOR-flash CFI/ID probe (HYPOTHESIS, no reader traced).
- The area-6 devices (`0x19400000`, `0x19b00000`, `0x19e00000`) have no
  literal-pool reference, so their drivers build the address at run time or
  take it from the registry (not traced).

## Conclusion

F0 is done on EU2011 (C-1300). The register table — modelled windows with
address, size, reset value and reader, and the 177 unmodelled registers of
the F0 boot — is in `docs/format/firmware.md` § "ze0 register table"
(C-1301–C-1303). `tools/ze0_regs.py` repeats both steps from a log and an
image (C-1304).
