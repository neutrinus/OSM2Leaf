# EXP-2026-11-21-M8.A9: the `ze0` series ported to QEMU 11.1.3 builds and boots Windows CE exactly as the 8.2.10 pin does

- **Status:** done (the port builds, `-M help` lists `ze0`, and a 10 s boot gives the same observables as the 8.2.10 build of the same twelve patches; the task's literal oracle "0 exceptions, one `write 0x38`" is obsolete on both versions and is replaced by that comparison, see Observations §5)
- **Date:** 2026-11-21
- **Sample:** `archive/head256.img`, the first 268,435,456 bytes of the EU 2011 card, SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9` (build EU2011); `qemu-11.1.3.tar.xz` SHA-256 `5a8289c7940dc77d3873c81a6c29ba3afe1446fc9d36e77fa1658cdbecb84b22`, 141,819,712 bytes; `qemu-8.2.10.tar.xz` SHA-256 `37b4a643da8ed6015eef35f5d7f06e7259d9c95359965a0a98e9667c621ab2bb`, 132,685,948 bytes (both from `https://download.qemu.org`)
- **Tools:** `tools/qemu-ze0/build.sh` (changed: 11.1.3 pin, series choice, cumulative `--check-version`, `--disable-fdt`), `tools/qemu-ze0/run.sh` and `tools/ce_qemu_probe.py` (changed: `-d invalid_mem`), `tools/qemu_boot_cmp.py` (new, `--selftest`), gcc 13, x86-64 Linux host, 4 cores
- **Claims:** C-4320, C-4321, C-4322, C-4323, C-4324, C-4325, C-4326
- **Supersedes:** none (completes the plan of `docs/research/qemu-ze0-port-delta.md`; narrows C-4311 to the five-patch skeleton it measured)
- **Superseded by:** none

## Question

The `ze0` machine exists only as patches against QEMU 8.2, a line that is
end-of-life. Can the whole series be carried to current QEMU (11.1.3) so
that it builds, lists `ze0`, and boots the card's CE images with the same
guest-visible behaviour as the 8.2.10 pin?

## Hypothesis

The series uses no QEMU facility that 11.1.3 removed; every rejection and
every compile error is a rename or a signature change, so a port needs no
new device logic and the guest cannot tell the two builds apart.

**Falsifier:** a hunk with no 11.1.3 equivalent other than the known ITLB
`abort()`; a build that needs new logic in a device model; or a 10 s boot on
11.1.3 whose kernel debug text, API-trap sequence, interrupt counts or
unmodelled-access list differ from the 8.2.10 build of the same patches.

## Inputs

| Item | Value |
| --- | --- |
| Image | `archive/head256.img` (kernel image at `0x3e00200`, application image at `0x200200`) |
| Size / hash | 268,435,456 bytes, SHA-256 `92aa525d…07f9` |
| 8.2 series | `tools/qemu-ze0/patches/*.patch`, 12 files |
| 11.x series | `tools/qemu-ze0/patches/11.1/*.patch`, 12 files (this task) |
| Reference build | QEMU 8.2.10 + the 8.2 series, same host, same configure options |

## Method

1. **Sample.** The image and the two tarballs above, with their SHA-256.
   The port was made on a pristine extraction of `qemu-11.1.3.tar.xz`
   committed to a scratch git repository; no QEMU source is in this
   repository.
2. **Commands.**

   ```bash
   # port: every 8.2 patch through the rename table of patches/11.1/README.md,
   # then patch -p1, fix rejects, build, one commit per patch, git diff C^ C
   tools/qemu-ze0/build.sh --check-version 11.1.3          # 12 applied, 0 failed (exit 0)
   tools/qemu-ze0/build.sh --check-version 8.2.10          # 12 applied, 0 failed (exit 0)
   tools/qemu-ze0/build.sh --version 11.1.3 --srcdir ~/.cache/qemu-ze0-11   # build, -M help
   tools/qemu-ze0/build.sh --version 8.2.10 --srcdir ~/.cache/qemu-ze0-8    # reference
   for q in 8 11; do
     sh tools/qemu-ze0/run.sh --image archive/head256.img --machine ze0 \
        --qemu ~/.cache/qemu-ze0-$q/build/qemu-system-sh4 --timeout 10 \
        --icount shift=0,sleep=off --workdir /tmp/w$q
     python3 tools/ce_qemu_probe.py --qemu ~/.cache/qemu-ze0-$q/build/qemu-system-sh4 \
        --seconds 10 archive/head256.img
   done
   python3 tools/qemu_boot_cmp.py /tmp/w8 /tmp/w11         # verdict: SAME
   python3 tools/qemu_boot_cmp.py --selftest
   bash tools/qemu-ze0/build.sh --selftest                 # as a non-root user
   ```

3. **Controls.** *Positive:* the 8.2.10 build booted twice; the comparison
   must say `SAME` for the same binary. *Negative for the comparison:* the
   8.2.10 build with `--dbgmsg off`, which must be reported `DIFFERENT`.
   *Negative for the probe:* each series against the other version must exit
   4. *Noise floor:* the 11.1.3 build booted three times (two from a manual
   build, one from the `build.sh` build).
4. **Scope.** 12 of 12 patches, 18 files touched in the QEMU tree; one
   image, one boot length (10 s wall clock, `-icount shift=0,sleep=off`),
   one host. Compiled as a whole series only.
5. **Falsifier.** As in the hypothesis; the comparison tool exits 1 on any
   difference in the four observables.

## Observations

1. **Apply and build.** The ported series applies to pristine 11.1.3 with
   `patch -p1 -F0` (no fuzz, no offset) and with `git apply --check`, 12 of
   12. `build.sh --version 11.1.3` verifies the tarball hash, applies the
   series, configures `sh4-softmmu`, builds and prints
   `OK: ze0  Nissan Leaf ZE0 navigation unit (SH-4A, research skeleton)`;
   `--version` reports `QEMU emulator version 11.1.3`; `-M help` lists
   `none`, `r2d`, `ze0`. A compile of the series shows no warning in any
   file it adds or edits. `-M r2d` still starts and its memory tree contains
   the `sh4-ccn` region on both versions.
2. **What had to change.** Ten rename/signature rows (table in
   `tools/qemu-ze0/patches/11.1/README.md`). Four were not in the pre-port
   inventory and were found by compiling: `class_init(…, const void *)`,
   `DEFINE_PROP_END_OF_LIST()` removed with `const Property[]`,
   `sdbus_do_command()` taking the response size, and the log item below.
   No device logic was added or rewritten.
3. **The `abort()`.** 8.2 aborts after an ITLB data-array write; 11.1.3 does
   not. The port follows 11.1.3. The 8.2.10 build, which keeps the abort,
   ran both 10 s boots to the end, so the guest made no such write.
4. **Boot comparison** (`qemu_boot_cmp.py`, reference = 8.2.10 run 1):

   | Run | Debug text | Traps | Interrupts | Unmodelled accesses | TLB misses (info) | Verdict |
   | --- | --- | --- | --- | --- | --- | --- |
   | 8.2.10 run 1 | 13,949 B, SHA-256 `ae3527e18af01cd4…` | 2,920 | 7 × `0x400` | 138 | 26,333 | reference |
   | 8.2.10 run 2 | same | same sequence | same | same list | 26,333 | SAME |
   | 11.1.3 run 1 | same | same sequence | same | same list | 26,324 | SAME |
   | 11.1.3 run 2 | same | same sequence | same | same list | 26,351 | SAME |
   | 11.1.3 (`build.sh` build) | same | same sequence | same | same list | 26,341 | SAME |
   | 8.2.10, `--dbgmsg off` (negative control) | 0 B | 2,923 | 8 × `0x400` | same list | 26,374 | **DIFFERENT** |

   The debug text starts `Windows CE Kernel for Hitachi SH Built on Oct 23
   2008` and ends, in every run, at
   `KEPV:CreateAudioNetDrvObj AUD1: CreateError (INVALID_HANDLE_VALUE)`.
   The 2,920 traps are 2,910 instruction-address errors (the CE API calls)
   and 10 `0x0c0`. The TLB-miss stream is identical between the two 8.2.10
   runs, but the two 11.1.3 runs agree with each other only for the first
   800 exceptions, and 8.2.10 run 1 agrees with 11.1.3 run 1 for the first
   18,683.
5. **The old oracle.** With the current twelve patches the 8.2.10 build
   takes 29,260 exceptions in 10 s and lists 138 unmodelled accesses; "0
   exceptions, one `write 0x38`" (C-4311) was measured on the five-patch
   skeleton and holds on neither version now.
6. **The stock-machine oracle.** `ce_qemu_probe.py` (`-M none`, no `ze0`
   code involved) prints the same 22 lines on both builds: 15 unmodelled
   accesses in the same order (`write 0xff00001c` … `read 0xffe70808`),
   `exceptions: 0`, `final pc: 0x88048b6a`. So the 15-entry list reproduces
   on 11.1.3 as well as on 8.2.10 — once the log item is right:
7. **Log item.** Before the script change the 11.1.3 `-M ze0` log had 0
   `Invalid read/write` lines where the 8.2.10 log had 9,477,786; QEMU now
   logs them under `-d invalid_mem`. With `invalid_mem` added the 11.1.3
   log has 8,967,257 such lines against 9,194,710 on 8.2.10 in the same
   wall-clock time, and the access list is the same 138 entries.
8. **`--check-version`.** It tested every patch with `--dry-run` against the
   pristine tree, so on a series whose later patches edit files the earlier
   ones add it reported `5 applied, 7 failed` for 8.2.10 with its **own**
   series. Applying cumulatively gives 12/0 for 8.2.10 and for 11.1.3; the
   wrong pairings give `8 applied, 4 failed` (8.2 series on 11.1.3) and
   `10 applied, 2 failed` (11.x series on 8.2.10), exit 4. A relative
   `--patch-dir` failed every patch (`patch -d` resolves the path inside the
   tree); the path is now made absolute. Selftest: 89 passed, 0 failed.
9. **Host notes.** On 11.1.3 `configure` installs `qemu.qmp` into its venv
   and, with no system `libfdt`, tries to clone `dtc` from gitlab;
   `--disable-fdt` avoids the clone and the resulting binary boots the same
   (row 5 of the table).

## Interpretation

- **Fact (measured):** observations 1, 4, 5, 6, 7, 8.
- **Fact (measured):** the guest-visible behaviour of the first 10 s is the
  same on both builds by four independent observables, and the comparison
  detects a changed machine option.
- **Hypothesis:** the run-to-run variation of the TLB-miss stream on 11.1.3
  comes from QEMU's own soft-TLB sizing, which is driven by host time; it
  was not investigated. It is the reason TLB misses are excluded from the
  comparison, and it means an exception *count* is not a usable oracle on
  11.x.
- **Decision (to confirm by a human if anyone disagrees):** dropping the
  ITLB `abort()` on 11.x. It is unobservable here; it would matter only for
  a guest that writes the ITLB data array, which then dies on 8.2 and runs
  on 11.x.
- **Not measured:** boots longer than 10 s, an SD card attached (`--sd`),
  gdbstub use, each patch compiling on its own, QEMU 9.x/10.x, hosts other
  than x86-64 Linux.

## Conclusion

The hypothesis holds. `tools/qemu-ze0/patches/11.1/` is the twelve-patch
series for QEMU 11.1.3; it needed renames and signature changes only, builds
through `build.sh --version 11.1.3`, and boots `archive/head256.img` (build
EU2011) to the same point with the same debug text, API-trap sequence,
interrupt counts and unmodelled-access list as the 8.2.10 pin. The pin is
now a tested range (8.2.7, 8.2.10, 11.1.3) with one series per API
generation.
