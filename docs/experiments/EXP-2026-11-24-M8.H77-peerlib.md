## Question

Can the duplicated control-command loop, frame splitter and socket accept loop
of the `ze0_peers/*` tools be factored into one stdlib-only module without
changing any peer's check count, wire frame or negative control?

## Hypothesis

Yes: a `LinePeer` accept loop, a generic `dispatch` skeleton and the BT SLIP
frame helpers can be shared, while each peer keeps its own command grammar and
wire encoders (GPS 7-bit, panel ANW DLE/BCC, VCAN decoded CAN). Falsifier: a
check count or frozen vector changes, a negative control stops failing, a new
full-selftest failure appears, or a migration silently changes a wire byte.

### 3. Controls

- **Positive:** each migrated peer's `--selftest` passes with the same check
  count; the four registry suites pass; every frozen vector matches its
  pre-migration bytes; the new `peerlib --selftest` passes.
- **Negative:** a one-byte flip of the gps pinned checksum (`0x63`→`0x62`)
  makes both the byte equality and `verify_frame` fail; a wrong gps checksum
  is rejected; `c00102c0` differs from `c00103c0`; the panel bad BCC `...63`
  yields NAK `1015`; the panel out-of-range tap and the vcan out-of-range soc
  are refused; `0x280` differs from `0x281`; bt bad hex is refused.

### 4. Scope

In scope: `tools/ze0_peers/peerlib.py` (new), `bt.py`, `gps.py`, `panel.py`,
`vcan.py`, this EXP, claim rows C-8540–C-8549 and the M8.H77 TODO line (both
edited only with `tools/board.py`). Not migrated: `micon.py` and `uart.py` —
their control methods write straight to a socket and their peers are
persistent one-shot streams, so using `LinePeer` would change semantics;
they are named here as the Stop-rule exclusions. Excluded: firmware images,
card data, L3/L4 runs, and any change to `tools/selftest.py` policy or counts.

### 5. Falsifier

Refuted if a check count or frozen vector changes, a negative control stops
failing, a new full-selftest failure appears, or a migration changes a wire
byte behind a new flag.

## Interpretation

- **FACT:** the four migrated peers' selftests pass with unchanged check
  counts (gps 54, panel 45, bt 13, vcan 9) and byte-identical frozen vectors.
- **FACT:** `python3 tools/selftest.py` after migration prints 283 pass /
  0 fail / 21 skip / 304 total; the failing set from the flaky red baseline
  is empty in this run — no new failure appeared. The previous red was an
  environment (disk quota / load) artefact, not a peer defect.
- **FACT:** only three peers had a reply-string `control_commands`; vcan's
  contribution to the shared loop is the socket accept/read path, via
  `peerlib.LinePeer`, while its command grammar stays in `Peer.control`.
- **OBSERVED:** `micon.py` and `uart.py` were left unchanged (Stop rule).
- **HYPOTHESIS:** a new connector can now be a grammar plus a table of rules
  rather than a transport loop; the shared code is stdlib-only and owns no
  wire bytes.
- **UNKNOWN:** no L4 run (hardware unavailable); the effect on the guest is
  unmeasured and out of scope for this host-tool refactor.

## Conclusion

Added `tools/ze0_peers/peerlib.py` with SLIP frame/split helpers (derived from
the `BT_FW.dll` framer recorded in C-7523), a generic `dispatch` skeleton and a
`LinePeer` AF_UNIX accept loop. Migrated `bt.py`, `gps.py`, `panel.py` and
`vcan.py` without changing a verb, reply, check count or wire byte; left
`micon.py`/`uart.py` unchanged because their control methods write to a
socket and cannot use the reply loop without a semantic change. Claims
C-8540–C-8549 record the verified facts below.
