## Question

Which input decides the `DIFFERENT MAP CODE` error-screen message: HDD_INFO line 1 (`base_code`), the `0x06000000` raw image copy (checked by `cardcheck.py`), or a NAND/system record? Name the deciding input with the code path VA.

## Method

All addresses attributed through `tools/cerom.py` / `tools/sh4xref.py` on the real image (AGENTS rule 3). SH-4 listing by `rz-asm -a sh -b 32 -d` on slices extracted at module-local `realaddr` offsets from `AppLaunch.dll` section 1 (uncompressed, `rva 0x1000`, `realaddr 0x03bb1000` B / `0x03b91000` C, `psize 0x24c00`). PC-relative literal pools decoded from raw section bytes (`EA = (PC & ~3) + 4 + disp*4`, SH-4 `mov.l @(disp,PC),Rn`). Positive control: `HDD_INFO.TXT` (ASCII) present in `Navi.exe` (A) and `AppLaunch.dll` (B/C) sections; `DIFFERENT MAP CODE` (UTF-16LE) present only in `AppLaunch.dll` B/C.

## Observations

### 1. String location and dispatcher (build B, corroborated by M2.9)

`DIFFERENT MAP CODE` (UTF-16LE) is at file `0x4136abc` in `AppLaunch.dll` build B section 1 (dataptr `0x88336000`, file `0x04136200`, realaddr `0x03bb1000`), module VA `0x03bb18bc`; build C file `0x5540a9c`, module VA `0x03b9189c` (C sec1 realaddr `0x03b91000`). Positive control `HDD_INFO.TXT` found in `Navi.exe` A (`0xe5338e`), `AppLaunch.dll` B (`0x414e516`), C (`0x55581ee`). No `DIFFERENT MAP CODE` in build A (confirms C-205/C-808).

`AppLaunch.dll` dispatcher `fn 0x03bcafb8` (B, prologue `mov.l r8,@-r15`…`sts.l pr,@-r15`, frame `add 0xfe12,r15` = -494 via `mov.w @(0x1ee,pc),r1`; `mov r4,r11` takes error code) builds an (error_code, UTF-16 string pointer) lookup table on the stack and selects the screen by error code (M2.9 C-807 heuristic). It loads `DIFFERENT MAP CODE` (`0x03bb18bc`) at `0x03bcb0ca` (`mov.l @(0x310,pc),r2`, EA `0x03bcb3e0` holds `0x03bb18bc`) paired with error code `0x51` (`0x03bcb0c8 mov #0x51,r3`, stored with that string). The adjacent entry stores code `0x50` with `0x03bb1890` = `MAP DATA BASE UNMATCH` (`0x03bcb0be @(0x318,pc)` EA `0x03bcb3dc`).

Dispatcher table entries decoded (B, around `0x03bcb060`–`0x03bcb0ce` / pool `0x03bcb3d4`–`0x03bcb3e0`):

| pool EA (B) | string module VA | UTF-16LE text | error code |
| --- | --- | --- | --- |
| `0x03bcb3dc` | `0x03bb18bc` | `DIFFERENT MAP CODE` | `0x50` |
| `0x03bcb3e0` | `0x03bb1890` | `MAP DATA BASE UNMATCH` | `0x51` |
| `0x03bcb3d8` | `0x03bb18e4` | `NAVI VERSION NG` | (adjacent) |
| `0x03bcb3d4` | `0x03bb1904` | `NAVI-2 FILE READ NG` | (adjacent) |

`--to 0x03bcafb8` (B) shows the dispatcher is called (pool-held function pointer, `jsr @r3`) from `fn 0x03bca688`, `0x03bcc680`, `0x03bd1d14`, `0x03bd1dd0`, `0x03bd224c`, `0x03bd2748`, `0x03bd2ecc`.

### 2. Error-code producer / decision router: `fn 0x03bd2ecc` (B) — code path VA

`fn 0x03bd2ecc` (B, `0x03bd2ecc..~0x03bd2efa`, prologue `sts.l pr,@-r15; add 0xf0,r15`) is the decision router for the two HDD_INFO/map checks (pool refs resolved):

| site (B) | loads | value | meaning |
| --- | --- | --- | --- |
| `0x03bd2ed4` `@(0x024,pc)` | `r3` | `0x03bd2ad8` | VerInf/HddInf compare |
| `0x03bd2ede` `@(0x020,pc)` | `r3` | `0x03bcafb8` | dispatcher |
| `0x03bd2ee2` | `r4` | `0x50` | error code → `DIFFERENT MAP CODE` |
| `0x03bd2ee4` `@(0x01c,pc)` | `r3` | `0x03bd2ce4` | MapDBVer range check |
| `0x03bd2eee` `@(0x010,pc)` | `r3` | `0x03bcafb8` | dispatcher |
| `0x03bd2ef2` | `r4` | `0x51` | error code → `MAP DATA BASE UNMATCH` |

Control flow (disassembled):
- `0x03bd2ed0 tst r4,r4; 0x03bd2ed2 bf` — if entry `r4 != 0`, skip checks (branch past check/dispatch region; pool follows at `0x03bd2efc`).
- if `r4 == 0`: `jsr @0x03bd2ad8` (`0x03bd2ed4/8`); `tst r0,r0; bf 0x03bd2ef4` (`0x03bd2eda/c`, pass → skip 0x50). If `0x03bd2ad8` returns 0 (mismatch): `jsr @0x03bcafb8` with `r4=0x50` (`0x03bd2ede/0/2`) — **shows `DIFFERENT MAP CODE`**.
- `jsr @0x03bd2ce4` (`0x03bd2ee4/8`); `tst r0,r0; bf 0x03bd2f1a+?` / on fail path `jsr @0x03bcafb8` with `r4=0x51` (`0x03bd2eee/0/2`) — shows `MAP DATA BASE UNMATCH`.
- epilogue `0x03bd2ef4 add 0x10,r15; lds.l @r15+,pr; rts`.

Build C mirror (pool refs to the same check roles): pool load `0x03bb2c54` holds `0x03bb2858` (f2ad8 equivalent), `0x03bb2c64` holds `0x03bb2a64` (f2ce4 equivalent), pool entries at C VAs `0x03bb2c7c`/`0x03bb2c84`; C f2ad8-equivalent `0x03bb2858` performs `KernelIoControl(0x0101302C)` (pool `0x03bb28a4` = `0x101302c`, `0x03bb28a6` = `0x03baa0c0` thunk). C dispatcher loads `DIFFERENT MAP CODE` string module VA `0x03b9189c` at fn area around `0x03baada2` (C sec1).

**Code path VAs that decide/produce `DIFFERENT MAP CODE` (error code `0x50`):** B `fn 0x03bd2ecc` decision site `0x03bd2ed4/0x03bd2eda–0x03bd2ee2` (calls `0x03bd2ad8`, on `r0==0` dispatches `r4=0x50` via `0x03bcafb8` at `0x03bd2ede/0x03bd2ee0/0x03bd2ee2`); C mirrors `0x03bb2858` (compare) and `0x03bb2a64` (range) with the same router structure (`pool 0x03bb2c54`/`0x03bb2c64`).

### 3. The compare that produces the `DIFFERENT MAP CODE` decision: `fn 0x03bd2ad8` (B)

`fn 0x03bd2ad8` (B, `0x03bd2ad8..` epilogue at `0x03bd2c94`, frame via `add r1,r15` from `@(0x110,pc)` at `0x03bd2ae6`; prologue saves r8–r13/pr). It compares an 11-byte **unit target-info record** (NAND/system, via kernel IOCTL) against an 11-byte value parsed from the **card's** `\SystemSD\VER_INFO\HDD_INFO.TXT`.

Key operations (raw, disassembled):
- `0x03bd2af6 mov.l r12,@(0x24,r15)` clears output buf ptr slot; `r11 = r15+0x34` (`0x03bd2aee/0x03bd2af4`) is zeroed to 11 bytes (`0x03bd2b04–0x03bd2b2a`).
- **Unit/system record (NAND side, not card):** `KernelIoControl` `jsr @r3` at `0x03bd2b2c` with `r4 = 0x0101302C` (pool `0x03bd2cac`), `r3 = 0x03bca3e8` (thunk, pool `0x03bd2cb0`), `r5 = r15+0x1c`, `r6 = 4`, `r7 = r15+0x24` (ptr), `@(0x10,r15)=8`, `@(0x14,r15)=0`. It copies 11 bytes from `*(u32 @(0x24,r15)) + 0x60` (+96) into `r11` (`0x03bd2b36–0x03bd2b56`: loop `dt r1` 5 iterations copying 2 bytes + final byte = 11 bytes). Pool `0x03bd2cb8` = `0x1f74b30` (global ptr, module-external/OOB for AppLaunch sec1, observed).
- **Card HDD_INFO (from card filesystem):** selects path `r9 = 0x1f74b30`-based global in the `@r9==0` branch? `0x03bd2b78 mov.b @r9,r3; 0x03bd2b7e tst r3; bf 0x03bd2cb0-path` — if `*r9 != 0` branches (taken to `0x03bd2cb0` target = `0x03bd2b80+4+0x12e` = `0x03bd2cb2`, near pool, observed branch target); if `*r9 == 0` opens `\SystemSD\VER_INFO\HDD_INFO.TXT` (pool `0x03bd2cc0` = module VA `0x3bc92f0` = `\SystemSD\VER_INFO\HDD_INFO.TXT` ASCII/UTF-16LE text bytes observed as `\`-prefixed; `r5` from `0x03bd2b8a` = `0x80000000` GENERIC_READ, `r3` create = `0x3bca9b4` at `0x03bd2b98`). Reads 0x60 bytes (`mov #0x60,r6` at `0x03bd2bb4`) with read fn `0x03bd3ad4` (`0x03bd2bac`), closes `0x03bca9a8`.
- **Parse/extract 11 bytes from HDD_INFO:** scans the read buffer (`r12 = r15+0x44`) byte-by-byte (`0x03bd2bca–0x03bd2c02`), splitting on `0x0a`/`0x0d`; for the selected line context it copies up to 0x10 bytes per 16-byte slot into `r9` buffer (line bytes to `r9[r4+r2]` when in the first-field path, `r10` toggles line index; `0x03bd2be0 cmp/eq #1,r10; bf` controls offset `add 0x10,r4`). After parsing, `0x03bd2c06–0x03bd2c1e` copies **11 bytes** from `r9[0..10]` (5×2 + 1, `dt r2` from 5) into `r13 = r15+0x24` buffer.
- **Compare (the deciding test):** `0x03bd2c1e–0x03bd2c3e` compares 11 bytes `r11[i]` vs `r13[i]` for `i=0..10` (`add 0x0b,r3` bound at `0x03bd2c24`; `sub r1,r5; tst r5; bf 0x03bd2c32` on first mismatch; `cmp/eq r3,r2` loop). On full equality `tst r5; bt` at `0x03bd2c3c/3e` goes to the equal path (bt target `PC+4+disp` → `0x03bd2dfc` region, outside the dumped tail slice; epilogue sets return `r2` — see Returns).
- **On mismatch:** formats the two 11-byte records bytewise (loop `0x03bd2c40–0x03bd2c80`, 11 iterations `mov #0x0b,r3; cmp/hs`) with `sprintf` (`0x3bcb7b4`, pool `0x03bd2cd8`) and format `pool 0x03bd2cd4 = 0x3bb14e8` (raw bytes `b'%\x00c\x00...\x00'`, UTF-16LE fragment observed) into two 0x20-spaced output slots, then logs `VerInf:%s / HddInf:%s\r\n` (`pool 0x03bd2cdc = 0x3bc9330`, `jsr @0x03bd2ce0=0x3bca3a0` at `0x03bd2c86/8a`). Then `0x03bd2c8e bra 0x00000006` with delay slot `0x03bd2c90 mov #0,r2` reaches epilogue `0x03bd2c98` (`lds.l @r15+,pr`…`rts; mov r2,r0` at `0x03bd2ca6/8`) → **returns `r0 = 0` on mismatch**. (`0x03bd2c92 mov #1,r2` is the alternate return-value setup reached by the equal path’s branch target into the epilogue region.)
- **Returns:** mismatch → `r0 = 0` (triggers `DIFFERENT MAP CODE` in `fn 0x03bd2ecc`); equality → returns nonzero/`1` path (equal-path `bt` leaves the mismatch/log path; `mov #1,r2` at `0x03bd2c92` sets the success value used by the epilogue). The exact equal-path branch landing was not fully disassembled to a single instruction here (bt target `0x03bd2dfc` is beyond the 800-byte slice; the mismatch path and return contract are fully observed).

**Deciding inputs (as used by `fn 0x03bd2ad8`):**
1. **System/NAND side (unit):** 11-byte target-info record read by `KernelIoControl(IOCTL 0x0101302C, ...)` and taken from output buffer offset `+0x60` (+96). This is a kernel/target-info record (C-780/C-783: IOCTL `0x01013208` fills the model area object; `0x0101302C` is the related target-info IOCTL used by the two launcher checks per validation.md/C-783/M2.7 context). It is **not** read from the SD card and **not** read from the `0x06000000` image copy.
2. **Card side:** the 11-byte value parsed from the card's `\SystemSD\VER_INFO\HDD_INFO.TXT` file (opened/read from the card filesystem path `\SystemSD\VER_INFO\HDD_INFO.TXT`, pool `0x3bc92f0`). The 11 bytes come from the parsed HDD_INFO content (first field/line bytes as extracted into the compare buffer; C-740–C-743 identify line 1 as `base_code`, 11-char factory example `QSD-302-100`). It is **not** the raw `0x06000000` block.

`fn 0x03bd2ad8` does not reference `0x06000000`, does not read the card's raw pre-partition `HDD_INFO` copy, and does not compare against an HDD_INFO text record stored in NAND; it compares the kernel target-info record (`0x0101302C`, +96) to the parsed card HDD_INFO file field.

### 4. Build C corroboration

- C `AppLaunch.dll` section 1: `realaddr 0x03b91000`, `dataptr 0x884a4000`. `DIFFERENT MAP CODE` module VA `0x03b9189c` loaded at `fn` area around `0x03baada2`.
- C `0x03bb2858` (`va2file` → `0x05561a58`): same compare role, `KernelIoControl(0x0101302C)` (pool `0x03bb28a4` = `0x101302c`, thunk `0x03baa0c0` at `0x03bb28a6`).
- C pool refs: `0x03bb2c54` → `0x03bb2858` (compare), `0x03bb2c64` → `0x03bb2a64` (range check) — mirrors B's `fn 0x03bd2ecc` routing to 0x50/0x51. C range check `0x03bb2a64` matches validation.md/M2.7.

### 5. `MAP DATA BASE UNMATCH` (contrast, same decision router)

`fn 0x03bd2ecc` calls `fn 0x03bd2ce4` (B, `0x03bd2ce4`; C `0x03bb2a64`) after the VerInf compare passes; on failure it dispatches error code `0x51` → `MAP DATA BASE UNMATCH` (`0x03bb1890`). This is the MapDBVer range check (validation.md: "range-checks the card's map-DB value against unit target-info bounds `+112`/`+114` and logs `MapDBVer : %d <= [%d] <= %d`"). It is a different decision/input path from `DIFFERENT MAP CODE`.

## Interpretation

- **FACT (deciding input for `DIFFERENT MAP CODE`):** The message is selected by `AppLaunch.dll` `fn 0x03bd2ecc` (B) when `fn 0x03bd2ad8` (B; C `0x03bb2858`) returns 0. `fn 0x03bd2ad8` decides by a byte-for-byte compare of 11 bytes: (a) the **unit target-info record** obtained from `KernelIoControl(0x0101302C)` output offset `+0x60` (+96) — a **NAND/system/kernel target-info record** — versus (b) 11 bytes parsed from the **card's `\SystemSD\VER_INFO\HDD_INFO.TXT`** (card filesystem file). A mismatch logs `VerInf:%s / HddInf:%s` and produces error code `0x50` → dispatcher `fn 0x03bcafb8` shows `DIFFERENT MAP CODE`.
- **FACT (what does NOT decide it on this path):** `fn 0x03bd2ad8` does not read the `0x06000000` raw HDD_INFO copy, and it does not read an HDD_INFO text copy from NAND. The `0x06000000` copy is not an input to this comparison. (This extends C-783/validation.md "does not prove the `0x06000000` copy is unused everywhere; it only rules it out for these two launcher checks" — M2.5 now names `DIFFERENT MAP CODE`/code `0x50` as the `0x03bd2ad8` branch of that pair: decided by kernel target-info `0x0101302C`+96 vs card HDD_INFO file, **not** `0x06000000`.)
- **FACT (card-side field):** the compared card value is the parsed HDD_INFO field content (11 bytes of the first field context in `fn 0x03bd2ad8`'s parse buffer, consistent with line 1 `base_code`, C-740–C-743). The exact semantic mapping of those 11 bytes to `base_code`/market tokens is the same line-1 field family discussed in validation.md/M2.3; M2.5 proves the *source* (card HDD_INFO file vs kernel target-info record) and the code path, not a new line semantics claim beyond the 11-byte extraction observed.
- **OBSERVED (scope):** this is the `AppLaunch.dll` launch-time path that produces error code `0x50`. Other modules/paths that might show `DIFFERENT MAP CODE` were not found by string xref (the UTF-16LE string occurs only in `AppLaunch.dll` B/C in IMG256; A has none). A different runtime path producing the same text cannot be fully excluded without a whole-image call-graph beyond string refs, but no other holder was observed.

## Conclusion

`DIFFERENT MAP CODE` (AppLaunch dispatcher `fn 0x03bcafb8` B / C dispatcher area `~0x03baada2`, error code `0x50`) is decided by **`AppLaunch.dll` `fn 0x03bd2ad8` (B, C `0x03bb2858`)** via the router **`fn 0x03bd2ecc` (B, `0x03bd2ed4/0x03bd2eda–0x03bd2ee2`; C mirror via pools `0x03bb2c54`/`0x03bb2c64` to `0x03bb2858`/`0x03bb2a64`)**. The deciding comparison is: **NAND/system kernel target-info record** (`KernelIoControl(0x0101302C)` output `+0x60`/+96, 11 bytes) **vs the card's `\SystemSD\VER_INFO\HDD_INFO.TXT` parsed line-1/field value** (11 bytes). It is **not** the `0x06000000` raw copy and **not** an HDD_INFO text record stored in NAND. On mismatch it logs `VerInf:%s / HddInf:%s` and dispatches `DIFFERENT MAP CODE`; on match it proceeds to the MapDBVer range check (`fn 0x03bd2ce4` B / `0x03bb2a64` C, code `0x51` = `MAP DATA BASE UNMATCH`).
