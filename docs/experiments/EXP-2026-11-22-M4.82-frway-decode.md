## Question

Can the `FRWAY0nn` shard layout be reproduced from a committed tool that walks every shard of both 2011 cards, and which bytes remain unexplained?

## Hypothesis

The M3.16 corrected 12-byte big-endian table plus the shared `REFER001` stream/dictionary walk explains at least half of every factory shard, and in practice nearly all of it; exactly one small byte per shard is expected to remain unexplained because it sits between the table terminator and the name-initial directory.

**Falsifier:** any shard explaining under half of its bytes. The tool prints `BELOW HALF EXPLAINED (the falsifier fires)` and exits 1; the unexplained region must then be named rather than guessed. A second, stronger falsifier: a flipped marker or a mutated byte must be detected or refused (negative controls below).

## Method

1. **Sample and hash.** The two factory roots and the two decoded shards above; hashes from `sha256sum` on the decoded bytes. The census reads the `.cmp`/`.ind` pairs through `addre.load_blob`; the decoded bytes were checked byte-identical to that output for EU FRWAY002 (`7859f717…`, `equal: True`).
2. **Commands.** Runnable as written, from the repository root:

   ```bash
   python3 tools/frway_decode.py --selftest
   python3 tools/selftest.py --only frway_decode
   python3 tools/frway_decode.py census /home/marek/projekty/leafre-work/m5.29-factory-root \
       --json /home/marek/projekty/leafre-work/scratch/m4.82/eu.json
   python3 tools/frway_decode.py census /home/marek/projekty/leafre-work/m5.12-us/root-factory \
       --json /home/marek/projekty/leafre-work/scratch/m4.82/us.json
   ```

   The type-block marker validation, the unexplained-byte histogram and the negative controls are all inside the committed tool (`type_block()`, `census()['unexplained_detail']`, `selftest()`); no uncommitted heredoc produced a number quoted here.
3. **Controls.** *Positive*: a synthetic factory-shape shard (four type-block markers, two 12-byte records and a `ffff` terminator, one directory row, index/route/main zlib streams, a two-field schema dictionary) decodes with `unexplained == 0` and `fraction_explained == 1.0`; all 16 `--selftest` checks pass, and all 37 real shards pass the same four marker words and decode the same two dictionary names. *Negative*: (a) one mutated byte appended at `0x1fff` leaves exactly one unexplained byte, named with its offset, relative position and value; (b) flipping the `0x4d40` type-block marker raises `FrwayError`; (c) changing the `ffff` table key to `00ff` raises `FrwayError`.
4. **Scope.** 26 EU + 11 US = **37 shards**, 2,921,728 + 5,141,760 = **8,063,488 decoded bytes**, all from `.cmp`/`.ind` pairs. Excluded: the firmware record consumer (M3.16 negative, C-2219), the meaning of each schema field's offset in a record, and the `0x0d` byte's semantics. Zero/`ff` filler is reported as `padding` and counted explained separately from real unexplained bytes; no byte is silently assumed to be data.
5. **Falsifier.** Under half the bytes explained on any shard, or a negative control that does not fire. Both were checked before the result was read.

## Interpretation

- **FACT:** The committed `tools/frway_decode.py` walks all 37 shards and explains 99.56 % (EU) / 99.90 % (US) of the bytes; the falsifier did not fire (C-7830, C-7837, C-7838).
- **FACT:** The 0x108-byte type block has four fixed big-endian markers in every shard and is validated, not skipped (C-7831). The 0x1108 table is an 8-byte block header followed by 12-byte BE records from 0x1110 with a `ffff` terminator (C-7832), followed by a 12-byte name-initial directory at terminator+0x10 (C-7833).
- **FACT:** The zlib streams are the shared `2*(u16 & 0x3ff)` record walk; every shard has one index stream, one route stream and 1…25 main streams, all framed exactly (C-7834). The schema dictionary decodes to the same two names everywhere (C-7835).
- **FACT:** The EU factory census lists 26 shards, not the 24 stated in `docs/format/refer.md` and matrix rows 12/13; the seven missing numbers are 001, 006, 013, 014, 017, 024, 032. US has 11 (001…011) (C-7837, C-7838, C-7839).
- **OBSERVED:** Exactly one byte per shard, always at table-terminator+0x0d, is not covered; its value is a multiple of 6 in all 25 affected shards (EU 14, US 11) (C-7836).
- **HYPOTHESIS:** That byte is a count in six-byte units belonging to the directory header, but no consumer reads it, so no meaning is assigned.
- **UNKNOWN:** What each schema field offsets into a main-blob record; what the `0x0d` byte counts; which firmware function consumes FRWAY records (M3.16/C-2219 remains negative). The 24-shard figure in matrix row 12 was not edited here (another task's row) — it is a follow-up.
