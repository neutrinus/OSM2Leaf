## Question

Can the CE 5.0 kernel process, thread and module tables of a running `-M ze0`
EU2011 guest be read through QEMU's HMP monitor (with gdbstub as needed) so
that the process names and thread counts of `nk.exe`, `filesys.exe`,
`device.exe` and `Navi.exe` are printed?

## Hypothesis

The public CE 5.0 headers (`pkfuncs.h`, `kernel.h`, `nkintr.h`) give fixed
offsets from the kernel data page; `KINX_PROCARRAY` and `KINX_MODULES` are
pointers to tables that HMP `xp` can read as guest physical memory. Falsifier:
the tables do not yield the process names of the same run's DBGMSG lines, or
the structures have to be relocated by fitted deltas.

## Method

1. **Sample and hash.** `sha256sum archive/head256.img archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img`
   printed the two hashes in the header. No vendor bytes enter the repo; the
   qcow2 overlay, IPL patch and logs stay in the scratch directory.
2. **Commands.** Offline controls and the live boot:

   ```bash
   W=/home/marek/projekty/OSM2Leaf.task-m8.h68-ze0-ps
   S=/home/marek/projekty/leafre-work/scratch/M8.H68
   python3 $W/tools/ze0_ps.py --selftest
   python3 $W/tools/ze0_ipl.py patch $W/archive/head256.img -o $S/ipl.txt
   python3 $W/tools/qemu-ze0/mkoverlay.py \
     $W/archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img $S/card.qcow2
   TMPDIR=$S bash $W/tools/qemu-ze0/run.sh \
     --qemu /home/marek/projekty/leafre-work/qemu-ze0-m8h6/qemu-system-sh4 \
     --image $W/archive/head256.img --verinf QSD-302-100 --mapdb 16-16 \
     --ipl-patch $S/ipl.txt --sd $S/card.qcow2 \
     --icount shift=0,sleep=off --timeout 0 --gdb=1240 --workdir $S/live2
   python3 $W/tools/ze0_ps.py --monitor $S/live2/hmp.sock --gdb 1240 \
     --no-modules --threads
   python3 $W/tools/ze0_gdb.py xp --monitor $S/live2/hmp.sock 0x09e41b00 32
   python3 -c "import sys; sys.path.insert(0,'$W/tools'); import ze0_ps as z; \
     m=z.Memory(z.HmpMemory('$S/live2/hmp.sock')); \
     h=m.u32(z.KDATA_P1+z.AINFO+4*z.KINX_MODULES); \
     print('head=0x%08x modules=%d'%(h,len(z.walk_modules(m,h))))"
   ```

   The `run.sh` command was left running with `--timeout 0` (so the guest stays
   idle with a live HMP socket). The first attempt with
   `--serial-peer sci6=unix:…` exited immediately with
   `qemu-system-sh4: Property 'ze0-machine.sci6' not found`; that optional
   peer was dropped, and the kernel debug text then goes to `run2.out`.
3. **Controls.** *Positive:* the synthetic image in `--selftest` has four
   processes with 3/2/1/4 threads; all 25 checks pass, and on the real guest
   the module-list walk at `KINX_MODULES` returns 59 named modules with no
   read errors. NK.EXE's name string is read directly at `0x88001ea4` as
   `NK.EXE`, so the name-read path is exercised on real bytes once.
   *Negative:* the selftest zeroes the process array (0 processes), corrupts a
   name pointer (`<invalid>` path + recorded error) and closes a thread loop
   (1 thread, not unbounded). On the live guest, HMP `x /4wx` at
   `0x0405fec4`, `0x0602fec0`, `0x080bfec4`, `0x0a03fecc` answers
   `Cannot access memory` for all four, and gdbstub `m` returns `E14` for
   `0x0405fec4`, while `xp` at P1 `0x8c2daec4` reads `filesys.exe` — the
   strings exist in physical RAM but the user-slot VAs in `lpszProcName`
   cannot be translated with these channels.
4. **Scope.** One idle EU2011 kernel-B guest; 8 populated process-array slots,
   59 modules in the circular module list, 2 threads readable on NK.EXE;
   `--selftest` covers 4 synthetic processes / 10 threads / 4 modules. Not
   covered: user-slot page-table walking, a stopped CPU with a changed ASID,
   the US2011/NK1 builds, and the live PC inside `Thread.ctx` (CPU-specific;
   the tool reports `dwStartAddr` instead).
5. **Falsifier.** The names printed for the live guest do not match the
   DBGMSG lines of the same run, or an assumed offset has to be fitted to make
   a name appear.

## Interpretation

- **FACT:** on EU2011 kernel B the KData page is at `0x89e41800` and its
  `aInfo` array has the public `pkfuncs.h` indices; `aInfo[0]` is an **array of
  inline PROCESS structs** with stride `0xd0`, not an array of pointers.
- **FACT:** the CE 5.0 SH-4 MODULE list is circular via `+0x04`, name `+0x08`,
  BasePtr `+0x54`, `e32_vbase +0x78`, `e32_vsize +0x7c`; 59 modules walk
  cleanly. Thread chains (`PROCESS+0x10`, `THREAD+0x08`) and states
  (`THREAD+0x02/+0x03`) are readable from HMP physical memory.
- **FACT:** `lpszProcName` (`PROCESS+0x20`) holds user-slot VAs for every
  process except NK.EXE. HMP `x`, HMP `xp` on the apparent physical address
  and gdbstub `m` all fail on those VAs; the tool therefore prints NK.EXE with
  its 2 threads and records explicit read errors for the other slots.
- **HYPOTHESIS:** process-array index `i` corresponds to CE slot `i+1` (file
  system, device manager, GWES are the first three user processes), and slot 5
  with `e32` image size `0x0154e000` is Navi.exe; this was not verified by a
  name read and is **not** used as a name source by the tool.
- **UNKNOWN:** how to translate a CE 5.0 user-slot VA to guest physical memory
  (section/PTE walk) or switch the gdbstub CPU context so those name pointers
  become readable.

## Conclusion

`tools/ze0_ps.py` is implemented with a 25-check synthetic selftest and
correct CE 5.0 SH-4 offsets, but the `Done when` is **not met**: on the live
idle EU2011 guest it prints only NK.EXE (2 threads) and explicit read errors
for the user-slot names, not the four required process names. The task is
`blocked`; the follow-up needs a user-VA→physical translation (or a guest
context switch) before the process list can be completed. No format doc is
changed. The offsets found here are recorded in C-8130–C-8136.
