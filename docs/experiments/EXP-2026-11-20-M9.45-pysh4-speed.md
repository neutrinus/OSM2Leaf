# EXP-2026-11-20-M9.45: PySh4 runs the kernel decompressor about ten times faster

- **Status:** done
- **Date:** 2026-11-20
- **Sample:** `archive/head256.img` (EU IMG256, build EU2011) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  `archive/us256.img` (US IMG256, build US2011) SHA-256

  (only for the `d53500_writer.py` regression run)
- **Tools:** `python3 3.13.18` (stdlib only); `tools/l3_harness/engine.py`
  (changed: fast path), `tools/nk_decomp.py` (new `section --time` flag only),

- **Superseded by:** none

## Question

Can PySh4 run the EU2011 kernel decompressor (`nk.exe` `0x88037464`, H51) about
ten times faster, in pure Python, with byte-identical output and no change of
behaviour for any other user of the engine?

## Hypothesis

The baseline profile (below) shows the time going into per-instruction
overhead — `_fetch` + `_block` (a linear region search on every fetch, load
and store), `_step`, `_dispatch`, `_get_pc` — not into the instruction
semantics. Translating each straight-line run of instructions into one Python
function, once, removes that overhead.
**Falsifier:** any of the 245 compressed sections decoding to a different
`(module, section, r0, sha256)` row; any engine self-test changing outcome; the
fast path and `_step` disagreeing on any halfword or random block in the new
differential self-tests; or the single-section benchmark below 3× (the task's
Stop line).

## Method

1. **Sample and hash.** As above.
2. **Before tree.** A copy of `tools/` with only `engine.py` replaced by the
   `aa50417` version, so both columns run the same `nk_decomp.py --time`:

   ```bash
   mkdir -p /home/user/scratch/m9.45/before_tree/archive
   cp -r tools /home/user/scratch/m9.45/before_tree/
   git show aa50417:tools/l3_harness/engine.py > /home/user/scratch/m9.45/before_tree/tools/l3_harness/engine.py
   ln -s "$PWD/archive/head256.img" /home/user/scratch/m9.45/before_tree/archive/head256.img
   ```

3. **Commands** (each run in both trees; the benchmark three times,
   interleaved before/after):

   ```bash
   time python3 tools/nk_decomp.py section archive/head256.img --module Navi.exe --index 1 --time
   python3 -m cProfile -s tottime tools/nk_decomp.py section archive/head256.img --module Navi.exe --index 1
   time python3 tools/nk_decomp.py check archive/head256.img --json /home/user/scratch/m9.45/check.after.json
   python3 tools/l3_harness/engine.py --selftest
   python3 tools/l3_harness/engine.py --selftest --full
   python3 tools/d53500_writer.py cases archive/head256.img --build eu2011
   python3 tools/d53500_writer.py cases archive/us256.img --build us2011
   python3 tools/gate.py
   ```

   (`check` in the before tree writes `check.before.json`; the two files are
   compared with `cmp`.)
4. **Controls.**
   *Positive:* three new self-tests in `engine.py`: (a) every templated
   halfword run once through the fast path and once through `_step` from three
   register states (pointers into a data page, odd pointers, arithmetic seeds
   that send addresses off the map), comparing count, exception type and
   message, all registers, 4 KiB of memory, `_delay` and `_arm` (quick mode:
   n, m ∈ {0, 1, 5, 15}, every other nibble; `--full`: all 65,536);
   (b) 400 random blocks of templated instructions in a `dt`/`bf/s` loop,
   `run_until` versus the stepped `Backend.run_until`, with stop addresses
   inside blocks, budgets of 7/50/400 instructions, and on every fifth case
   code mapped `rwx` with pointers into it (self-modifying stores);
   (c) the fallbacks: a subclass overriding `_execute` still sees every
   instruction, a callable `stop` sees every PC, a hook registered by another
   hook mid-run is honoured, and `Runaway` at `max_insns` 1/5/11 has the same
   message and state as the stepped loop. On the image: a lockstep run of the
   benchmark, block by block, comparing every register with a stepped engine
   after each block (scratch script, not committed).
   *Negative:* the sign-extension bug met during the work
   (`exts.b` template without `& 0xFF`) put back in a scratch copy: tests (a)
   and (b) fail (`0x600e state 2 … regs differ in ['r0']`; random case 78).
5. **Scope.** `PySh4` only; no C extension. The fast path is used only by
   `PySh4.run_until`; `_step`/`_execute` and every `_exec_*` arm are
   unchanged.
6. **Falsifier.** As in Hypothesis, stated before the runs.

## Observations

**Design** (in `engine.py`, "PySh4 fast path (M9.45)"):

- `_tc_insn(word, pc)` returns a Python-source template for 109 forms
  (105 named arms plus the 4 `@(R0,Rn)` moves that `_exec_misc` leaves
  unnamed; 49,684 of 65,536 halfwords) (moves,
  ALU, shifts, compares, all branches, PC/GBR/indexed loads and stores), each a
  transcription of its `_exec_*` arm with the same order of register writes,
  loads and stores. Any other form (FPU, `div*`, `mac.*`, `trapa`, `rte`,
  MMU, `tas.b`, the `@(R0,GBR)` byte ops…) ends the block and runs through
  `_step`.
- `_tc_build` joins templates into a block (≤ 64 instructions, ending at a
  branch plus its delay slot, a `bt`/`bf`, or an untemplated word), keeps
  registers in locals inside the block and writes them back on every exit,
  and gives each load/store site a one-region cache cell; a miss goes through
  `_load`/`_store`, so faults raise exactly what `_step` raises. A fault
  leaves `pc` = faulting PC + 2 and `_arm` = its arm, as `_step` does.
- A stop address, an `on_exec` hook or `RETURN_VA` is never inside a block; a
  store into an executable region drops every block and ends the current one;
  `write_mem` to an executable region and `map` drop every block.
- `run_until` falls back to the stepped loop for a callable `stop`, while a
  watch is armed or a delay slot is pending, when a block would cross
  `max_insns`, and for any subclass or instance that overrides an interpreter
  method (`runner.GuardedPySh4`/`WatchedPySh4`, `div1_l3.ShimSh4`,
  `chunk_decoder_l3`'s patched `_execute`) — those engines run exactly as
  before.
- Compiled blocks are shared across engines in one process, keyed by start PC
  and instruction words (`nk_decomp check` builds one engine per section).

**Baseline profile** (`cProfile`, before, 88,740,800 calls, 69.4 s under the
profiler), top by own time: `_fetch` 8.96 s (5,754,750 calls), `run_until`
8.17 s, `_block` 8.06 s (7,739,522), `_execute` 7.95 s, `_step` 6.97 s,
`_dispatch` 4.27 s, `Region.end` 3.10 s (15,297,953).

**After profile** (3,031,319 calls, 3.96 s under the profiler): `run_until`
0.77 s, `compile` 0.40 s (518 blocks), the hottest block (`0x880408ee`,
62,157 calls) 0.33 s, image read 0.25 s, `pack_into` 0.22 s, `dict.get`
0.19 s (663,920 block look-ups, 8.7 instructions per block). The profile is
flat: the loop, the block bodies and one-off compile/IO.

**Benchmark** (`Navi.exe` sec1, machine shared, load average 9.4–10.0 during
the interleaved runs; `engine:` is `run_until` alone, `wall`/`user` the whole
command):

| Run | before `engine:` | after `engine:` | before wall / user | after wall / user |
| --- | --- | --- | --- | --- |
| 1 | 26.206 s = 219,597 insn/s | 3.263 s = 1,763,683 insn/s | 26.92 / 13.47 s | 3.97 / 1.46 s |
| 2 | 25.892 s = 222,263 insn/s | 2.538 s = 2,267,152 insn/s | 26.49 / 13.34 s | 3.03 / 1.49 s |
| 3 | 25.173 s = 228,612 insn/s | 2.293 s = 2,510,099 insn/s | 25.58 / 13.01 s | 2.92 / 1.40 s |

Medians: `run_until` 25.89 s → 2.54 s (**10.2×**), whole command wall
26.49 s → 3.03 s (8.7×), CPU (user) 13.34 s → 1.46 s (9.1×). In a quieter
moment earlier (load average 2.5): `run_until` 14.405 s (399,496 insn/s)
before, 1.346 s (4,274,911 insn/s) after (10.7×). Output line identical in
every run: `r0=0x1801a OK sha256(dest[:r0])=1c73ad74ffafe39757b4c057c22c77922cd6ae8a6052252959476257d4e39fee`
(the H51 value).

**Full check** (245 sections): before `real 9m58.3s, user 5m23.1s`; after
`real 0m58.9s, user 0m27.3s` (user 11.8×). `check.before.json` and
`check.after3.json` are byte-identical (SHA-256
`50e18a74d5ce7d5566a26f6d359e4339f0b11c4020d97887267cabfb0d65553f`); both
print `245 OK, 0 failed, 245 sections, 1674478 bytes decoded`. After merging
`main` (M1.19 rewired `nk_decomp`), the `(module, section, r0, sha256)` rows
are again equal to the before run on all 245.

**Self-tests:** `engine.py --selftest` → `OK (26 checks, 2 skipped, quick)`
(about 11 s CPU); `--selftest --full` → `OK (26 checks, 2 skipped, full)`
(all 65,536 halfwords, 6 m 49 s wall under load). The 23 checks that existed
before pass unchanged. Lockstep on the benchmark: `done 5754750`, no register
difference after any block. `d53500_writer.py cases` on EU2011 and US2011:
identical output before and after. `gate.py` (before merging `main`):
`selftest PASS, claims_check PASS, todo_check PASS, fn_audit PASS`.

## Interpretation

- **FACT:** on the decompressor benchmark the engine runs about 10× faster
  (`run_until` medians 25.89 s → 2.54 s under load; 10.7× in a quieter
  moment), with the same output SHA-256; the full 245-section `check` gives
  byte-identical results in about one tenth of the CPU time.
- **FACT:** the fast path agrees with `_step` on all 65,536 halfwords from
  three states (`--full`), on 400 random blocks including self-modifying code,
  stops and budgets, and register by register on the 5.75 M-instruction
  benchmark.
- **INFERENCE:** the remaining cost is the dispatch loop (about one third)
  and the block bodies; a further large step would need blocks that chain to
  their successors without returning to the loop, which complicates the
  stop/hook/budget rules — not attempted.
- **LIMIT:** engines that override an interpreter method (all `runner.py`
  targets through `GuardedPySh4`, `div1_l3`, `chunk_decoder_l3`) still run
  stepped, at the old speed; making `GuardedPySh4`'s INIT guard a fast-path
  hook would be the next step for L3 targets.

## Conclusion

Done-when met: the benchmark is ≥ 8× faster (`run_until` 10.2× median under
load, 9.1× CPU for the whole command) with the same output SHA-256;
`engine.py --selftest` (all 23 earlier checks unchanged, 3 new), `selftest.py`
via `gate.py`, and the 245-section `check` are unchanged. Behaviour change for
users: none intended; plain `PySh4.run_until` now executes translated blocks.
