## Question

Which card file is the launcher's opening image, what is its on-disk layout,
and is its pixel data a raw 800×480 framebuffer that can be decoded and
re-encoded byte-identically?

## Hypothesis

The `BASS` container `OPNG/MKR_OPNG/NISSAN/OIXX…` holds raw 800×480 frames,
so a pixel-format decoder gives a viewable picture and a verbatim re-encode.
**Falsifier:** under every plausible raw-pixel format the payload is
unrecognizable noise, while the container structure itself still parses and
round-trips. The pixel hypothesis is then refuted and no format is guessed.

## Method

1. **Sample and hash.** The two factory files above, in full. SHA-256 from
   `sha256sum`; the launcher identification is L4's
   `Load Opening Image Data to 0x8c6e0000 (Size=4198400 Bytes)` in
   EXP-2026-11-21-M8.C1b-hpb-dmac-model O3.
2. **Commands.** All runnable from the repo root, with the card roots named:
   ```bash
   EU=/home/marek/projekty/leafre-work/m5.4/card-factory/OPNG/MKR_OPNG/NISSAN/OIXXEVNI.001
   US=/home/marek/projekty/leafre-work/m5.12-us/root-factory/OPNG/MKR_OPNG/NISSAN/OIXXNVNI.001
   S=/home/marek/projekty/leafre-work/scratch/m4.91
   python3 tools/opng.py --selftest
   python3 tools/opng.py info "$EU" > "$S/info-eu.txt"
   python3 tools/opng.py info "$US" > "$S/info-us.txt"
   python3 tools/opng.py decode "$EU" -o "$S/eu.png"
   python3 tools/opng.py encode "$S/eu.png" -o "$S/eu-back.001"
   python3 tools/opng.py decode "$US" -o "$S/us.png"
   python3 tools/opng.py encode "$S/us.png" -o "$S/us-back.001"
   cmp "$EU" "$S/eu-back.001"; cmp "$US" "$S/us-back.001"
   sha256sum "$EU" "$S/eu-back.001" "$US" "$S/us-back.001"
   python3 tools/zlibinfo.py
   ```
   The negative pixel test rendered 22 candidate views (RGB565 LE/BE, RGBA,
   BGRA and 8-bit gray at payload offsets `0x60`, `0x650`, `0x800`, `0x1000`,
   plus tail offsets) as 800×480 PNGs with a throwaway pure-stdlib writer,
   then measured horizontal-adjacency correlation of the byte/`u16` streams.
   Those renderings are scratch, never committed.
3. **Controls.** *Positive:* `tools/opng.py --selftest` builds a synthetic
   BASS container with 3 and with 2 frames and round-trips both (10 checks,
   0 failures); `cmp`/`sha256sum` on the two factory files are the real-data
   positive controls. *Negative:* the selftest rejects bad magic, a bad
   `800×480` descriptor, an 8-byte truncation and a corrupted carrier; the
   swapped/changed-header control is EU vs US, where 4 header bytes change and
   the checksum-like bytes change with them.
4. **Scope.** Two factory files (EU2011, US2011), 1,606,224 B each; one
   firmware head searched for the name/magic strings. Excluded: EU2014/EU2016
   cards (not on the task's input list) and the TFAT16 `.skn` assets (M4.58).
   The animation payloads of all 35 frames are covered by the entropy and
   format tests; the proprietary pixel grammar is explicitly **not** decoded.
5. **Falsifier.** A coherent picture under any tested format would have
   supported the raw-frame hypothesis; none appeared, and the correlation
   metric stayed at or below −0.03 for gray8/RGB565 on frame 1. The falsifier
   fired, so the pixel claim is refuted.

## Observations

- `tools/opng.py info` on both files: `size 1606224 (0x188250)`;
  `declared_size@0x14 1606224`; `frame_count@0x40 35`; `field@0x44 2`;
  `descriptor_count 35`; `duration_sum_ms 5000`; `eof_trailer_bytes 2`;
  `payload_bytes 1605582`.
- Magic EU `42415353573743d8` (`BASSW7C\xd8`), US
  `42415353603743d2` (`BASS` + `` ` `` + `7C\xd2`). Identity EU
  `'OIXXEVNI.001470-2827-00 '`, US `'OIXXNVNI.001470-2821-00 '`.
- Frame table (EU and US identical): frame 0 at `0x050` has
  `payload_len 1504`, `duration_ms 400`; frames 1–33 have
  `duration_ms 70` and `payload_len` 22,212…37,948; frame 34 at `0x17faf6`
  has `payload_len 34632`, `duration_ms 2290`. 400 + 33×70 + 2290 = 5000.
  Every frame header has `prefix 0`, `w 800`, `h 480`.
- EU vs US differ in exactly 4 of 1,606,224 bytes: offsets `0x04`
  (`0x57`→`0x60`, +9), `0x07` (`0xd8`→`0xd2`, −6), `0x20` (`E`→`N`, +9)
  and `0x2f` (`7`→`1`, −6). All 1,605,582 payload bytes are equal.
- Payload entropy `5.2559` bit/byte overall; with the dominant `e0 ff 00 00`
  fill removed, `5.2709`. Per frame: 0 → `1.5066`, 1 → `1.9750`,
  17 → `4.8426`, 34 → `5.7526`. Top payload `u16`: `0x00a0` (82,963),
  `0x0041` (63,497), `0x0000` (60,379), `0x0001` (34,226), `0x0042`
  (31,040), `0x00e0` (28,365). No zlib `78 9c/da/01`, PNG `89 50 4e 47`,
  JPEG `ff d8 ff` or LZSS header signature anywhere in the file.
- Horizontal-adjacency correlation on frame 1: gray8 `−0.1248` (offset 0)
  and `−0.1254` (offset 4), RGB565-LE `−0.0287`, RGB565-BE `−0.2730`.
  All 22 rendered views are banded noise with no recognizable picture.
- Each frame payload ends in a `u32` that is a multiple of `0x20`
  (frame 0 `0x00005de0`, frame 1 `0x000024a0`, frame 2 `0x000093e0`,
  frame 34 `0x0000ca60`) followed by `u32 0`; no tested checksum
  (sum8, xor8, CRC-32 of payload or of payload minus that word) reproduces it.
- `tools/opng.py --selftest`: `10 ok, 0 fail`. On the real files,
  `decode`/`encode` printed `1606224 bytes, 35 frames` for both, `cmp` was
  silent for both, and `sha256sum` matched the source hashes exactly.
- Firmware head: `OIXXEVNI.001470-2827-00 ` occurs once, at file offset
  `0x5c0021c`; an exact copy of the whole EU file (1,606,224 B) starts at
  `0x5c00200`. `OIXXXXXX.FFFFFFFFFFFFFFF` template headers occur at
  `0x4415ce0`, `0x4e15ce0` and `0x58622d0`. Reader code was not located.

## Interpretation

- **FACT (C-8170):** the opening image is the single `OPNG` file on each card;
  the L4 launcher log and the firmware's own exact copy of it establish the
  identification (C-6875 stands).
- **FACT (C-8171, C-8172):** the container is `BASS` + a 0x50-byte header with
  a declared size, an identity string and a frame count of 35; each frame is a
  16-byte header (zero `u32`, 800×480 `u16`s, payload length, duration) plus
  its payload, followed by a 2-byte EOF trailer.
- **FACT (C-8173):** the 35 durations sum to exactly 5000 ms — a 5-second
  animation (400 ms first frame, 70 ms middle frames, 2290 ms last frame).
- **OBSERVED (C-8174):** EU and US payloads are byte-identical; only four
  header bytes differ, and the two checksum-like bytes move by exactly the
  same deltas as the two identity-string characters. The checksum algorithm
  is **UNKNOWN** (simple contiguous sums and CRC variants fail).
- **OBSERVED (C-8175, C-8179):** entropy and the small `u16` alphabet show a
  structured, coded payload, not encryption or a stock compressed stream;
  the per-frame trailing `u32` values are not a checksum we could identify.
- **FACT (C-8176):** the raw-800×480-frame hypothesis is refuted — no tested
  format yields a picture, and the adjacency correlation is ≈0 or negative.
  The payload is a proprietary coded/display-list grammar; **UNKNOWN**.
- **FACT (C-8177, C-8178):** `tools/opng.py` round-trips the container
  byte-identically on both cards (L2 container check). This is *not* a pixel
  decode: the PNG carries the original bytes verbatim in a `zTXt` chunk and
  draws a byte-map view. The firmware's embedded copy and BASS templates are
  recorded as the starting point for a future reader search.

## Conclusion

`docs/format/assets.md` §OPNG now records the header, 35-frame table,
durations, the four differing bytes and the negative pixel result; claims
C-8170–C-8179 carry the reproducible commands. The task's own check passes —
`tools/opng.py --selftest` is green and decode→encode is byte-identical on
both factory files — but the *picture* is not decoded: the falsifier fired,
so no pixel format is asserted. What is still open is the proprietary frame
payload grammar (and therefore how to replace the image with a self-made one)
and the checksum-like header bytes.
