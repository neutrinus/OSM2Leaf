## Interpretation

- **FACT:** the monitor entry path has **zero** static backing in this repo; the
  only source is a secondary write-up. The same is true of the pinout, levels
  and baud rate.
- **FACT:** the kernel debug SCIF (C-534) is a *different* interface from the
  reported service connector. Conflating them would produce a wrong wiring plan;
  whether they share pads is UNKNOWN.
- **FACT:** the strongest static statement about entry is a **negative**:
  no key-combination string was found and test mode is boot-flag gated
  (C-818, C-708). A key sequence is therefore the weakest candidate, not the
  default.
- **OBSERVED:** `TestMode.exe` exists only in image C of the reference image
  (C-526, C-810). A service-menu route on a retail A+B unit has no static
  support.
- **HYPOTHESIS:** `DSW=0006` is either a hardware switch/strap read by the
  IPL/monitor (M-A) or a monitor variable set with `s`/`e` (M-B). No repo text
  distinguishes them; the plan resolves it by reading, never writing.
- **HYPOTHESIS:** a positive-control read of the `nk.exe` string at VA
  `0x8800e5a8` / physical `0x0800e5a8` (C-705, C-535) will reveal whether the
  monitor reads virtual or physical addresses. A mismatch is a negative on the
  address model, not on the monitor.
- **UNKNOWN:** whether retail firmware exposes the monitor at all; pin
  assignment; 3.3 V vs other levels; baud/framing; whether entry is
  non-destructive; whether `DSW` persists; whether the monitor reaches the map
  card or only raw flash.
- **UNKNOWN (and not fixable statically):** whether the monitor lives in the
  CE image or in the on-board IPL/flash (C-535, C-706). Absence from the CE
  modules does not refute it.
