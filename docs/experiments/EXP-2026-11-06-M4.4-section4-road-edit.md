# EXP-2026-11-06-M4.4: Tile section 4 under a road edit

Task: M4.4. Done when: a one-tile road edit with verbatim section 4 passes L2
and the EXP states which section-4 fields depend on road content (or none).

## Question

Can section 4 (the per-parcel administrative/place-name index) stay byte-identical
when a road is edited, or do some of its fields have to change with the road
content?

## Hypothesis

Section 4 parcels are derived from the set of road-containing parcels (see
`tools/ze0-viewer/tools_ze0/sec4_write.py`, which builds section 4 from
section 2 level-1 road parcels). A road edit that stays inside an existing
parcel (one shifted vertex) does not change the parcel set, so the whole
section-4 payload can remain verbatim. The parcel words (0x00/0x02) depend on
road content only at parcel granularity; the country code (0x10) and the name
strings are administrative and independent of road geometry.

## Method

1. Copy the EU 2011 root to a scratchpad root; keep the original tile aside.
2. Find a section-1 background (odd-pair) record in `B30R048R.DAT` that
   `clarion_bg` rebuilds byte-exactly, with a vertex whose +40 shift stays
   inside the same parcel and whose recompressed stream fits in the original
   stream length.
3. Mutate that vertex (1903, 2031) -> (1943, 2031), rebuild the record,
   recompress with zlib level 9, and pad with NUL bytes to the original stream
   length (180 -> 178 compressed words; trailing NULs are ignored by
   `zlib.decompress`).
4. Patch only those bytes into a copy of the original file. No other byte
   (including every section-4 stream) is touched; file size stays
   1,358,592 bytes.
5. Verify the patched tile:
   - `harness.py verify PATCHED` (round-trip + record inflate + background
     rebuild).
   - `section4.py verify` on the extracted section-4 payload of both tiles
     (preserve round-trip, record/name counts, sha256).
   - `l2check.py --root PATCHED_ROOT --no-golden` (census, DRSTR, cmp
     round-trip, tile round-trip, tile semantic, tile mutation, refer
     mutation).

Commands:

```bash
python3 /tmp/opencode/patch_tile2.py
# creates /tmp/opencode/B30R048R-patched.DAT
cd tools/ze0-viewer && python3 harness.py verify /tmp/opencode/B30R048R-patched.DAT
python3 tools/section4.py verify /tmp/opencode/orig-sec4.bin
python3 tools/section4.py verify /tmp/opencode/patched-sec4.bin
python3 tools/l2check.py --root /tmp/opencode/root-m4.4-patched --no-golden --cmp-limit 5
```

## Observations

- Patched tile differs from the original in exactly **116 bytes**
  (`0x2fac5..0x2fb73`), one compressed stream; every other byte is identical.
- `harness.py verify PATCHED`:
  - byte-identical rebuild: OK (1,358,592 bytes)
  - records: 3396 ok, 0 bad
  - background rebuild: 2955 ok, 0 bad (65 opaque)
  - graph parse: 228 ok, 0 bad
  - round-trip: OK
- Section 4 payload (extracted from both tiles):
  - bytes: 3028, sha256 `4cbf35f2b3a77b0a9ed9de599099de3d8667d536434e95b5f98044361c7aad03`
  - records: 20, names: 68 (unique 54) in both
  - `section4.py verify`: preserve round-trip OK byte-identical in both
- `l2check.py --no-golden` on a root carrying the patched tile: RESULT: PASS
  (census, drstr_roundtrip, cmp_roundtrip (5/5), tile_roundtrip (5 tiles),
  tile_semantic, tile_mutation (1 removed / 1 added / 1 changed vertex),
  refer_mutation (PASS)).
- The patched tile still has 22 section-4 records at the `clarion_tile` level
  (20 of them carry place names; 2 are empty-flagged slots), identical to the
  original.

## Interpretation

- **FACT:** A one-vertex road edit that stays inside one parcel can be applied
  without changing any section-4 byte; the section-4 payload is byte-identical
  before and after (sha256 `4cbf…aad03`, 20 records / 68 names).
- **FACT:** The edited tile passes `harness.py verify` and `l2check.py
  --no-golden` (RESULT: PASS).
- **OBSERVED:** Section 4's parcel words (`0x00`/`0x02`) enumerate the
  road-containing parcels (derived from section 2 level 1 in `sec4_write.py`).
  They depend on road content only at parcel granularity: a vertex shift inside
  a parcel does not change them; adding or removing a road parcel would.
- **FACT:** The country code at `0x10` (300 = Greece) and the name strings
  (`0=RODOS`, `1=LINDOS`, …) are administrative/place-name data and are
  independent of road geometry.
- **HYPOTHESIS:** The undocumented bytes at `0x06..0x0f` and the name-list
  placement are not affected by a within-parcel road edit; they must in any
  case be preserved verbatim because their grammar is unknown
  (`section4.py encode build` refuses them, exit 3).
- **UNKNOWN:** Whether a road edit that changes the parcel set (new or removed
  road parcel) can be accompanied by an incremental section-4 update, or
  whether the whole section-4 payload must be regenerated. `sec4_write.py`
  regenerates it from the road parcels, so the safe rule is: regenerate
  section 4 whenever the road parcel set changes; carry it verbatim otherwise.

## Conclusion

Section 4 **can stay verbatim** for a road edit that does not change the set of
road-containing parcels (the common case for a vertex shift or attribute change).
Fields that depend on road content: the parcel words at `0x00`/`0x02` and the
directory slot layout, but only at parcel granularity. Fields that do not
depend on road content: the country code (`0x10`) and the name strings, plus
the opaque bytes. `tools/section4.py encode preserve` is the correct writer
path for an edited tile unless the road parcel set changes, in which case
section 4 must be regenerated (e.g. via `sec4_write.py`).
