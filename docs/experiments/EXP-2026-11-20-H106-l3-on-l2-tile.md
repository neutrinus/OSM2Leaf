## Question

Has an L3 target run on the tile our L2 pipeline writes, and does
`l3check` say which of our tiles it ran on?

## Hypothesis

Before this task: `tile_reader`'s only corpus in `targets.json` is the
factory `B28R070R.DAT`, and `l3check --build-corpus` reports it BLOCKED,
so "L3 on our data" is not visible. M9.13 (merged the same day) found the
entry and ran `datask_l3.py mount` on a generated tile G whose OSM input is
not committed, so the tile that the card ladder and `l2check` use (M5.11,
`one_tile_pipeline` from the committed fixture) still has no L3 run. The
task's Stop clause applies: because the reader now runs, a row must show the
tile the run served (named in the run's own log), not only that the tile is
listed.

Expectation: the M5.11 tile, mounted at a position inside directory
(76,940), reads the same as the factory tile (as G did for (77,941)), and the
fresh-container synthetic tile fails at its first directory read.

**Falsifier:** the mount never reads directory (76,940), or its parser
does not load the changed pair entries, so SAME would say nothing. Another
falsifier: the header-count flip control also compares SAME, so the
comparison cannot detect anything. A third: the run log does not name the
served tile.

## Interpretation

- **FACT (C-4370):** the firmware's tile mount (EU2011, PySh4, `datask_l3.py`)
  has run on the tile the L2 pipeline writes for the card ladder (M5.11,
  `1927c3a9…`). Placed at 51.10 N 16.93 E, it reads directory (76,940), and
  its slot-table parser loads both changed pair entries. All 28 reads are the
  same as the factory tile's. The header-count control is DIFFERENT, so the
  comparison can fail.
- **FACT (C-4371):** `datask_l3.py mount --json` now records the card source,
  the mods and, per overlaid file, the size and SHA-256 of the bytes served.
  A run therefore names the tile it ran on, which the Stop clause required.
- **FACT (C-4372):** `targets.json` keeps one `tile_reader` target and adds
  `generated_corpus` (4 entries). `l3check` lists those entries with a status
  that follows the SHA-256: `RAN (recorded)`, `STALE`, `NOT RUNNABLE in
  runner.py`, `NOT RUN (no tree)` or `NOT RUN (file is not the listed tile)`.
  `ran_on_our_generated_data` is true only for a recorded run of the listed
  hash. Target count and `runnable` are unchanged versus main (H107); a STALE or wrong file makes the run exit 1 (navigator correction 1).
- **OBSERVED (C-4373):** the M5.34 tile (`b746427c…`, Geofabrik input, zlib
  1.3.2) has never been mounted and cannot be rebuilt in this sandbox. Its
  row says `NOT RUN (no tree)`.
- **UNKNOWN:** whether the firmware accepts our road records: no record block
  is read before the mount stalls at state 2 (M9.52, M9.53).

## Conclusion

The Done-when's statuses changed while this task ran: M9.13 made the reader
runnable outside `runner.py`. The Stop clause therefore applied, and the rows
now carry a recorded run of the listed hash. Two of them (M5.11 and synthetic)
were run in this task, and the run log names the served SHA-256. The M5.34
row is `NOT RUN (no tree)`. Nothing claims a record-level verdict.
`reader-coverage.md` row 17 and the L3 target table point to the new rows.
C-4370–C-4373 added.
