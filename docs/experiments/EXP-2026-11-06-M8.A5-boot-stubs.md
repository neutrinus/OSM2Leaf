## Question

Can the five register windows that block the retail ZE0 kernel before its
scheduler — the unnamed `0xffe70000` block whose `+0x808` poll is the first
blocker, the CPG at `0xffc80000`, `0xfff80000`, the UBC at `0xff200000` and
the area-6 device at `0x19300000` — be modelled as read-back stubs precisely
enough that the unpatched kernel reaches the point that today requires
`ce_qemu_probe.py --patch 0x88048b70=0900`?

## Hypothesis

Yes, for the boot path observed so far. The kernel's blocker is one fixed
response (`0xffe70808` must read bits 31:30 set) plus ordinary
write/read-back of registers it configures; none of the five blocks needs a
functional model before the scheduler. `MSTPCR` needs write/read-back so a
read-modify-write of module-stop bits is stable, and `MSTPACK` must reflect
that state. A self-contained QEMU device with those semantics, mapped at
priority above any unimplemented-device catch-all, removes the `--patch`
workaround without touching the firmware.

## Method

### 1. Patch authoring

`hw/sh4/ze0_stubs.c` (312 lines) is a plain `TYPE_DEVICE`
(`TYPE_ZE0_STUBS`, `-device ze0-stubs`) with:

- five `MemoryRegion`s, each a byte-addressed register file with
  `min/max_access_size = 1/4` and little-endian ops (the CE build is SH-4
  little-endian);
- a tiny descriptor list for the only non-plain registers: a forced/RO word
  at `0xffe70808` (`0xc0000000`) and a mirror at `0xffc80044` (OR of the
  words at `0xffc80030/34/38/3c`);
- `read()` resolving each byte: descriptor word if the byte belongs to one,
  otherwise the stored byte; `write()` latching bytes except in RO/mirror
  registers;
- `realize()`: `memory_region_add_subregion_overlap(get_system_memory(),
  base, mr, 1)` — priority 1 over the machine's priority-0 catch-all;
- reset re-zeroing each block and restoring the descriptor reset values.

The `hw/sh4/meson.build` hunk appends `sh4_ss.add(files('ze0_stubs.c'))`
**after** `hw_arch += {'sh4': sh4_ss}` (last line), deliberately away from
the top-of-file block the parallel M8.A4 series edits.

Compilation against the public 8.2.7 layout was checked here only because the
pinned tarball happened to be cached on this machine. **From the repository
alone — no QEMU tree — compilation is UNVERIFIED**, and that is the state a
reader of this repo starts from.

### 2. Generation and verification commands

```bash
# staging: a minimal git repo holding the pristine 8.2.7 hw/sh4/meson.build
# and the new file; diff generated with git, then:
git apply --stat 0002-sh4-ze0-boot-stubs.patch
#   hw/sh4/meson.build |    1
#   hw/sh4/ze0_stubs.c |  312 +++++++++++++++++++++++++++++++++++++++++++
#   2 files changed, 313 insertions(+)

# pristine 8.2.7 tree
cd qemu-8.2.7
git apply --check -p1 /path/tools/qemu-ze0/patches/0002-sh4-ze0-boot-stubs.patch ; echo rc=$?
git apply         -p1 /path/tools/qemu-ze0/patches/0002-sh4-ze0-boot-stubs.patch
./configure --target-list=sh4-softmmu --disable-werror --disable-docs \
            --disable-tools --disable-guest-agent --disable-docs
ninja -C build qemu-system-sh4 -j12

# device registration and register semantics (no machine, no CPU execution)
build/qemu-system-sh4 -M none -device help | grep ze0
build/qemu-system-sh4 -M none -cpu sh7785 -m 512M -device ze0-stubs -S \
    -display none -serial none -qtest unix:/tmp/qt.sock,server,nowait
# qtest: read/write/read at the addresses in the table
```

`patch -p1 --forward --batch --dry-run -i …` (the `build.sh` invocation) was
run too, on pristine 8.2.7 and with a simulated
`sh4_ss.add(when: 'CONFIG_SH4_CCN', …)` line inserted after line 1.

### Register semantics (qtest, `-M none -cpu sh7785 -m 512M`)

qtest prints the bytes of a read in memory order, so `0xc0000000`
little-endian appears as `c0 00 00 00`.

| Operation | Result |
| --- | --- |
| `read 0xffe70808 4` at reset | `c0 00 00 00` → `0xc0000000` |
| `write 0xffe70808 4 0x00000000` then read | unchanged `c0 00 00 00` (RO) |
| `write 0xffe70858 4 0x80000000` (bytes `80 00 00 00`) | read back `80 00 00 00` |
| `write 0xffc80030 4 0x01000000` (value 1), `write 0xffc8003c 4 0x00000080` (value `0x80000000`) | both read back unchanged |
| `read 0xffc80044 4` | `01 00 00 80` → `0x80000001` = OR of the two MSTPCR values |
| clear `0xffc80030` (write 0), then `read 0xffc80044` | `00 00 00 80` → `0x00000080` |
| reset values of all other listed registers | 0 |

### Access evidence reused (EXP-2026-11-05-37, C-533)

Unpatched, first-seen order ended at `ffc8003c` R/W, `ffe70858` R/W,
`ffe70800` W, `ffe70804` W, `ffe70808` R (forever). Patched
(`0x88048b70=0900`) added `ffe70094`, `ffe7009c`, `ffe7080c`, `ffe7081c`.
The `-m 256M` run added writes at `0x19300010`–`0x19300018`. `0xfff80000`
and `0xff200000` were not touched in the 4 s window; they are stubbed from
`nk.exe` literals (C-532).

### What was not observed

No boot of `nk.exe` with the stubs; therefore no confirmation that the
kernel's poll exits at `0xffe70808` and no measurement of the resulting PC.
The vendor image is not available on this machine (the M8.A5 done-when needs
one).

## Interpretation

- **OBSERVED:** the five windows are exactly the ones the current boot probe
  reports, plus two literal-only windows; the model reproduces the required
  fixed value and write/read-back at the register level.
- **HYPOTHESIS (C-1270):** this is sufficient for the unpatched kernel to
  reach the post-wait point. The falsifier is simple: an unpatched run that
  still spins at `0x88048b70` with the device present.
- **HYPOTHESIS, not fact:** `MSTPACK` at `0xffc80044` and its OR semantic;
  `MSTPCR2` at `0xffc80038`; reset 0 for the MSTPCRs; SH7750-style UBC
  register names; every area-6 register role. The block purposes at
  `0xffe70000` and `0xfff80000` remain **UNKNOWN**. All of these are listed
  with their falsifiers in `tools/qemu-ze0/patches/README.md` §B.5.
- **Design choice:** a user-creatable device rather than code in
  `hw/sh4/ze0.c`. It needs no machine, so it is testable on `-M none` today,
  it merges independently of M8.A2/A3, and `-device ze0-stubs` makes the
  modelled hardware explicit. The machine should create it once instead of
  adding the option twice.
- **Coordination fact (not part of this task):** the existing sibling
  `m8a4-0002-…` (meson/Kconfig) and `m8a4-0003-…` (sh7750.c) hunks target
  8.2.0 and fail on the pinned 8.2.7 tree; `build.sh` stops at the first
  failed patch, so M8.A4 must rebase before a full run reaches this file.
  This patch applies directly to 8.2.7 today.

## Conclusion

Claim **C-1270** (proposed, EXP-only):

> **C-1270** — A self-contained QEMU device (`ze0-stubs`) that maps five
> read-back windows — `0xffe70000`+`0x1000` with `0xffe70808` reading the
> constant `0xc0000000` (writes ignored), CPG `0xffc80000`+`0x100` with
> `MSTPCR0..3` at `0xffc80030/34/38/3c` reading back writes and `MSTPACK`
> at `0xffc80044` returning their OR, `0xfff80000`+`0x100`, UBC
> `0xff200000`+`0x100` (no break ever raised) and area 6
> `0x19300000`+`0x100` — lets the **unpatched** ZE0 `nk.exe` pass the
> `0xffe70808` boot wait and reach the point that
> `ce_qemu_probe.py --patch 0x88048b70=0900` reaches by force (the
> `illegal_instruction` at user VA `0x5b90`, then idle at `0x8803d266`),
> so the `--patch` workaround is no longer needed. Status **HYPOTHESIS**:
> the patch applies to 8.2.7 and compiles, and the register semantics are
> unit-checked with qtest, but no kernel boot was run here (no vendor
> image); the access sequence being modelled is OBSERVED in C-533.
