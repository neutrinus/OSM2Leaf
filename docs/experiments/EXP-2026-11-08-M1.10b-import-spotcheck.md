## Question

M1.10 named 846/846 `Navi.exe` import slots by export-table lookup
(C-2470–C-2476). Can two of the newly named exporters — one `XGLDLL!` and one
`OSMDLL!` — be confirmed at a **call site** (not just by name resolution), with
an argument shape consistent with the export's role?

## Hypothesis

The resolved slot VAs for `OSMDLL!OSM_Printf` and `XGLDLL!xglDisable` are
loaded from literal pools and called indirectly (`mov.l @(pc),rN; mov.l @rN,rN;
jsr @rN`) from `Navi.exe` code, and the register setup before `jsr` is
consistent with a printf-style function (`OSM_Printf`) and a capability/disable
function (`xglDisable`).

**Falsifier:** (a) the precheck does not list either name; (b) `sh4xref.py
--to <slot>` finds no call site (no `jsr` following a load of the slot) for
the chosen name; or (c) the observed argument setup is clearly incompatible
with the export's role (e.g. a zero-arg call shape for a function whose role
requires arguments, or an obviously unrelated register pattern) — in which
case the name/call-site link would remain `OBSERVED` only, not confirmed.

## Method

1. **Sample and hash.** `IMG256` as above; SHA-256 recorded in Inputs and
   verified: `sha256sum /home/marek/projekty/OSM2Leaf/archive/head256.img`.
2. **Commands** (runnable from repo root with `IMG256` path; `cd` to worktree
   or set paths as shown):

```bash
IMG=/home/marek/projekty/OSM2Leaf/archive/head256.img
RES="--resolve-with 0x200200 --resolve-with 0x3e00200 --resolve-with 0x5200200"
# Precheck (must list both names)
python3 tools/cerom.py "$IMG" imports Navi.exe $RES | grep -E 'OSMDLL!OSM_Printf|XGLDLL!xglDisable'
# Find call sites that load each slot VA
python3 tools/sh4xref.py "$IMG" Navi.exe --image-start 0x200200 $RES --to 0x0055d954
python3 tools/sh4xref.py "$IMG" Navi.exe --image-start 0x200200 $RES --to 0x0055db94
# Confirm the slot VA appears as a jsr target in the containing function
python3 tools/sh4xref.py "$IMG" Navi.exe --image-start 0x200200 $RES --calls 0x0039c978
python3 tools/sh4xref.py "$IMG" Navi.exe --image-start 0x200200 $RES --calls 0x003da074
# Argument-shape context around each jsr
python3 tools/sh4dis.py "$IMG" Navi.exe --image-start 0x200200 --va 0x0039c990 --count 30
python3 tools/sh4dis.py "$IMG" Navi.exe --image-start 0x200200 --va 0x003da098 --count 12
```

3. **Controls.**
   - *Positive (name resolution):* precheck lists `XGLDLL!xglDisable` at
     `slot=0055db94` and `OSMDLL!OSM_Printf` at `slot=0055d954` (and many other
     `XGLDLL!`/`OSMDLL!` names), consistent with M1.10 (846/846, C-2470).
   - *Positive (xref mechanism):* `sh4xref.py --to 0x0055d954` and `--to
     0x0055db94` both return multiple `pool ... holds <slot> / load ... jsr`
     records — the method finds real call sites, not an empty result.
   - *Negative (non-slot VA):* `sh4xref.py --to 0x00000001` returns pool/load
     hits for the literal value `1` (a different, common constant) rather than
     a structured import-slot call pattern tied to `OSMDLL`/`XGLDLL`; it does
     not fabricate an `OSMDLL!`/`XGLDLL!` slot identity. The slot-to-name link
     therefore rests on `cerom imports` (export-table resolution), not on
     `--to` alone.
4. **Scope.** `Navi.exe`, build A image segment (`--image-start 0x200200`),
   two import slots (`0x0055d954`, `0x0055db94`) and one call site examined in
   detail per slot (`fn 0x0039c978` call at `0x0039c9ba` for `OSM_Printf`;
   `fn 0x003da074` call at `0x003da0aa` for `xglDisable`). `--to` reports 88
   load records across 24 pools for `OSM_Printf` and 42 load records across 21
   pools for `xglDisable` (corpus of call-site candidates in this image
   segment); only the two detailed sites above were decoded for argument shape.
   No new naming pass; no other modules.
5. **Falsifier.** As stated in Hypothesis: missing precheck name, no `jsr`
   call site found for the slot, or argument setup clearly incompatible with
   the export's role.

## Observations

### Precheck (positive control)

`cerom.py imports Navi.exe --resolve-with 0x200200 --resolve-with 0x3e00200
--resolve-with 0x5200200 | grep -E 'OSMDLL!OSM_Printf|XGLDLL!xglDisable'`:

```
XGLDLL.dll           slot=0055db94 XGLDLL!xglDisable
OSMDLL.dll           slot=0055d954 OSMDLL!OSM_Printf
```

### OSM_Printf (`OSMDLL!OSM_Printf`, slot `0x0055d954`)

`sh4xref.py --to 0x0055d954` (excerpt; 24 pools / 88 load records total):

```
pool 0x0039c9f8 holds 0x0055d954
  load 0x0039c9b4 (r3)  fn 0x0039c978  jsr 0x0039c9ba
...
pool 0x0039eeb4 holds 0x0055d954
  load 0x0039ed7c (r3)  fn 0x0039ecf4  jsr 0x0039ed82
  ...
```

`sh4xref.py --calls 0x0039c978`:

```
  0x0039c99a jsr @r3 -> 0x003a26b8  sub_003a26b8
  0x0039c9ba jsr @r3 -> 0x0055d954  sub_0055d954
  0x0039c9ca jsr @r3 -> 0x003a26b8  sub_003a26b8
  0x0039c9dc rts
```

Disassembly around `0x0039c9ba` (`sh4dis.py --va 0x0039c990 --count 30`,
key lines):

```
0x0039c9ae  d311  mov.l @(0x0039c9f4,pc),r3  ; [0x0039c9f4]=0x0055d8e4
0x0039c9b0  9616  mov.w @(0x0039c9e0,pc),r6  ; [0x0039c9e0]=0x056a
0x0039c9b2  6532  mov.l @r3,r5
0x0039c9b4  d310  mov.l @(0x0039c9f8,pc),r3  ; [0x0039c9f8]=0x0055d954
0x0039c9b6  d411  mov.l @(0x0039c9fc,pc),r4  ; [0x0039c9fc]=0x0003a060
0x0039c9b8  6332  mov.l @r3,r3
0x0039c9ba  430b  jsr @r3
0x0039c9bc  6723  mov r2,r7               (delay slot)
```

Observed register setup at `jsr 0x0039c9ba`: `r3` = dereferenced slot
`0x0055d954` (call target); `r4` = literal `0x0003a060`; `r5` = word loaded
indirectly via slot `0x0055d8e4`; `r6` = constant `0x056a` (1386); `r7` = `r2`
(delay slot). Four arguments in `r4`–`r7`.

### Negative control

`sh4xref.py --to 0x00000001` returns literal-pool hits for the value `1`
(e.g. `pool 0x000117c8 holds 0x00000001`, etc.), not an `OSMDLL!`/`XGLDLL!`
import-slot call site. This confirms `--to` reports literal loads generically;
the *named import* identity for the two chosen slots comes from `cerom.py
imports` export-table resolution (M1.10).

## Interpretation

- **VERIFIED (C-2600):** Slot `0x0055d954`, resolved as `OSMDLL!OSM_Printf` by
  `cerom.py imports --resolve-with 0x200200,0x3e00200,0x5200200` (M1.10), is
  loaded from literal pools and called indirectly at real `Navi.exe` (build A)
  call sites. `sh4xref.py --calls 0x0039c978` shows `jsr @r3 -> 0x0055d954` at
  `0x0039c9ba`; `--to 0x0055d954` finds 88 load records / 24 pools.
- **OBSERVED (C-2601):** At `fn 0x0039c978` / `0x0039c9ba`, four arguments
  (`r4`–`r7`) are set up: `r4` is a fixed PC-relative literal (`0x0003a060`),
  `r5` is an indirect data word, `r6` is the constant `0x056a`, `r7` is a
  computed value. This multi-argument shape with a fixed first literal and a
  small constant argument is consistent with a printf-style/logging role for
  `OSM_Printf`; the exact signature and the meaning of `0x0003a060` are not
  established here (bytes at the mapped file offset of `0x0003a060` were not
  confirmed as an ASCII format string in this spot check).
- **VERIFIED (C-2602):** Slot `0x0055db94`, resolved as `XGLDLL!xglDisable`, is
  loaded and called indirectly at real call sites. `sh4xref.py --calls
  0x003da074` shows `jsr @r3 -> 0x0055db94` at `0x003da0aa`; `--to 0x0055db94`
  finds 42 load records / 21 pools.
- **OBSERVED (C-2603):** At `fn 0x003da074` / `0x003da0aa`, two arguments are
  set up: `r4` passed through from the enclosing function's context (`mov
  r8,r4`) and `r5` = constant `0x00800000`; the return value in `r0` is stored.
  This shape (a context/handle-like first arg plus a fixed capability constant)
  is consistent with a disable/capability role for `xglDisable`; the exact API
  and the meaning of `0x00800000` are not established here.
- **UNKNOWN:** whether `sh4xref.py --calls` resolves slot-VA targets to import
  names in its label column (it printed `sub_0055d954`/`sub_0055db94` here);
  the name confirmation relies on `cerom imports`. Also unknown: the exact
  prototypes of `OSM_Printf` and `xglDisable`.

## Conclusion

One `OSMDLL!` and one `XGLDLL!` name from M1.10's 846/846 resolution are
confirmed at real `Navi.exe` call sites by slot-VA load + indirect `jsr`, with
argument shapes consistent with their export roles (`OSM_Printf`: 4 args,
printf-style/logging-consistent; `xglDisable`: 2 args with capability constant
`0x00800000`, disable-consistent). The slot-to-name mapping is supported by the
export-table resolution (M1.10, positive precheck) plus the call-site evidence;
exact prototypes remain unestablished. No code changes required.
