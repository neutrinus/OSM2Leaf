## Question

Which function in `Navi.exe` walks a decoded `POINT0xx` name page
(`tag,len2` records, `0x60`/`0x68`, record size `2*len2`, refer.md C-952/C-953)
and which function copies a POI name out (VAs, arguments, output), to target
the US POI rename software check (M9.10)?

## Hypothesis

Exploratory. The walker reads byte 0 (tag `0x60|0x68`) and byte 1 (`len2`),
advances by `2*len2`, and the name-copy extracts the printable Latin-1 suffix
before the `ff ff` terminator; reachable from the `POINT0` volume-id /
`0x14e8`→`REFER001`+`INDEX003.DAT` access path (C-880, C-881).

false-positive pairs at odd addresses `0x3d73d3/0x3d73e3` and `0x4ba22b/0x4ba22f`
— those halfwords are not `0x8868/0x8860`; positive control for the correction:
the aligned scan reports `0x8860`/`0x8868` counts and the false pairs do not
reappear).

The 26 `#0x60` / 23 `#0x68` aligned hits were inspected in context: they are
type/ID/flag dispatches and value checks (e.g. `0x3715cc` word masked `&0x70==0x60`,
`0x37c268` part of a `#102..#105` dispatch, `0x46f5bc` maps `#80/#96/#112` to 5/6/7,
`0x471228` range check on 104, `0x4ee5f8` in a data/bit-walk region after `rts` in
surrounding flow). **None** combines a `0x60|0x68` tag accept with a `2*len2`
(`@(1,ptr)` doubled) pointer advance in a record loop.

### 3. Candidate `fn 0x003715a0` (tag mask, rejected as walker)

Prologue `0x3715a0` (`sts.l pr,@-r15`): reads `mov.w @r4,r3; and #0x70;
cmp/eq #0x60` (accepts tags whose masked bits equal `0x60`, which includes
`0x60` and `0x68` since `0x68&0x70==0x60`) but only when two global flags
(`0x3717a8/0x3717ac`) gate entry. It then performs range/distance checks using
`@(4,r4)`/`@(8,r4)`, logs/sends messages (`jsr` via `0x3717bc`, status stores
to `0x3717c4/0x3717c8/0x3717cc`), and returns. **No loop, no read of `@(1,r4)`
as `len2`, no `2*len2` advance, no name extraction.** It validates/acts on a
single record/header — not a POINT page walker/name copier. (Positive control:
the mask mechanism is real; negative: structure does not match framing.)

### 4. POINT name-page framing (refer.md, the target pattern)

Name page: `u8 tag (0x60|0x68)|u8 len2|body|text|ff ff`, record size `2*len2`,
packed with no gaps/offset table, NUL or `ff ff` ends text (C-952/C-953). A
conforming walker must (a) test tag for `0x60|0x68`, (b) read `len2` at `+1`,
(c) advance the cursor by `2*len2`, over a decoded page buffer.

### 5. Compressed-section blocker (exact)

`Navi.exe` sec1: realaddr `0x55d000`, vsize `0xff16ae` (16,704,174 B virtual),
psize `0x457c`, **`IMAGE_SCN_COMPRESSED`**. sec2: realaddr `0x154f000`,
vsize `0xed60`, psize `0x8884`, **compressed**. M1.3: 245 compressed o32
sections, 0 OK / 245 UNSUPPORTED (CE codec unresolved; M1.2f/M8.E1 open). All
searches above cover **only uncompressed** A o32 sections (527 sections'
uncompressed bytes; sec0 of Navi.exe plus every other module's uncompressed
sections). Code inside Navi.exe sec1/sec2 is undecodable with current repo
tools, so a walker residing there cannot be located or refuted statically.

## Interpretation

- **FACT:** The `POINT0` volume-id / `0x14e8`→`REFER001`+`INDEX003.DAT` access
  path is anchored in uncompressed Navi.exe: `0x003fbed8` selects the `POINT0`
  id (pool `0x003fc0d8`→`0x001792c4`→`0x00179364`) and calls volume lookup
  `0x0040b358`; descriptor switch `0x004125a8` maps `0x14e8` to
  `REFER001`/`INDEX003.DAT` (C-880/C-881 confirmed). `POINT001.DAT` and the
  Navi.exe `POINT\0` at `0x1d12a9` have no executable-section literal refs.
- **FACT (negative, scoped):** No function in any **uncompressed** build-A o32
  section implements the POINT name-page walk as specified: 0 aligned
  `#0x60/#0x68` tag pairs; 0 `and #0xf7`+`#0x60` mask walkers; 0
  `@(1,ptr)→2*len2` stride sequences by the heuristic; the single
  `&0x70==0x60` tag candidate (`fn 0x003715a0`) lacks the loop/stride/name-copy
  structure (rejected). 49 tag-immediate sites in Navi.exe sec0 inspected in
  context, none match.
- **OBSERVED:** Navi.exe sec1 (16 MB virtual, compressed) and sec2 are not
  searchable; the page walker/name-copy may reside there. The access path
  (name build → volume lookup → `0x14e8` descriptor) is in sec0, but the page
  parser that consumes decoded `REFER001/POINT0xx` bytes was not found in
  decodable code.
- **HYPOTHESIS:** The `2*len2`/tag-`0x60|0x68` walker and the name-copy helper
  are in Navi.exe compressed sec1 (vsize `0xff16ae`), reached via dispatch from
  the `0x14e8`/POINT read path once a page is decompressed (M3.2b/M1.2f).
- **UNKNOWN:** VAs/arguments/output of the record-walk and name-copy functions.

## Conclusion

M3.11 is **blocked with evidence** (not silently done): the required
record-walk and name-copy functions (VAs, args, output tied to refer.md
framing) were **not** located in decodable (uncompressed) code. `docs/format/firmware.md`
should note the POINT access-path anchors and that the page walker is not found
in uncompressed sections (compressed-sec1 blocker). M9.10 cannot yet target a
firmware VA for the US rename check until the walker is found (decode sec1 via
M1.2f/M8.E1, or dynamic trace).
