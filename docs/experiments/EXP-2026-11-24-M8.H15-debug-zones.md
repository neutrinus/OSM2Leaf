## Question

Do the retail CE 5 modules of the ZE0 firmware carry `DBGPARAM` debug-zone
records whose masks can be set so that a `-M ze0` boot prints vendor debug
lines naming file opens, positions and errors?

## Hypothesis

Retail modules carry `dpCurSettings` (`DBGPARAM`) blocks with 16 zone names
and a `ulZoneMask`. Setting that mask adds `DBGMSG`/`DEBUGMSG` lines.
**Falsifier (stated before result):** no valid `DBGPARAM` record exists in
any module of the three builds, in which case there is no mask to set and the
task's own Stop path applies. A related falsifier from the task block:
"setting the mask adds no line for any module."

   The tool `ce_dbgzones.py` reads stored section bytes through
   `cerom.py` and decoded `.data` sections from the `--decoded-dir` written by
   `cerom.py decompress`. For each section it scans both `DBGPARAM` layouts:
   the authoritative CE 5 layout (32-WCHAR zone names, mask at `+0x440`) and a
   secondary 16-WCHAR variant (mask at `+0x240`), so a wrong stride cannot
   silently cause a false negative. A record is accepted only when the module
   name and all 16 zone names are printable UTF-16LE, NUL-terminated and
   zero-padded within their fields and a 32-bit mask follows.
3. **Controls.** **Positive:** `ce_dbgzones.py --selftest` prints
   `selftest: 9/9 checks passed` and covers a synthetic 32-WCHAR `DBGPARAM`
   (name + 16 zone names + mask found), the synthetic mask value, and the
   format-string counter on a `'%'`-bearing string. The baseline boot proves
   the debug-sink hook works (`hook hits: 142`). **Negative:** the same
   selftest shows a corrupted zone name rejected, a read at the wrong `+0x240`
   offset yielding the wrong mask, and the 16-WCHAR stride on a 32-WCHAR image
   finding nothing. `ce_strfind.py DebugZones` is a positive control for the
   registry string in `nk.exe` (2 hits in build B), showing the search method
   finds a string that is present even though it finds no `DBGPARAM`.
4. **Scope.** Corpus counted by `ce_dbgzones.py`: build A 149 modules /
   527 sections (282 stored + 245 compressed-decoded, 0 skipped),
   build B 91 / 307 (174 + 133, 0 skipped), build C 88 / 277 (164 + 113,
   0 skipped): 1,111 sections scanned, 0 `DBGPARAM` candidates. Excluded:
   BSS/zero-fill and import tables (no initialized `DBGPARAM` there, C-3440);
   runtime `system.hv` after first boot (not in the ROM). The census covers
   stored bytes and all decoded compressed sections; no section was skipped.
   All numbers come from the printing commands above.
5. **Falsifier.** A single valid `DBGPARAM` record (module name + 16 zone
   names + mask) in any scanned section, or a registry `DebugZones` value in
   the ROM hives, would have refuted the "no mask to set" conclusion. Neither
   was observed. The task's own falsifier ("setting the mask adds no line for
   any module") is moot because there is no mask record to set.

## Interpretation

- **FACT:** No `DBGPARAM`-shaped record (module name + 16 zone names + mask,
  either 32-WCHAR or 16-WCHAR stride) exists in any of the 1,111 sections of
  builds A, B and C of the EU2011 image, with every compressed section decoded
  and 0 skipped.
- **FACT:** No `DebugZones` registry value exists in the ROM's `default.hv`
  or `boot.hv`; the only `DebugZones` string is the kernel's registry-key path.
- **FACT:** Format strings are present (8,017 / 1,987 / 2,408), so the messages
  were not all stripped; but they are reached through `NKDbgPrintfW` /
  `RETAILMSG` paths without a module zone mask, as the boot log shows only
  kernel/OAL lines (the kernel's own logging does not need a module
  `DBGPARAM`).
- **HYPOTHESIS (not tested further):** module-level `DEBUGMSG` zones were
  compiled out of this retail build; the format strings that remain are
  unconditional `RETAILMSG`/`NKDbgPrintfW` calls, so there is no zone mask to
  turn on. The kernel `DebugZones` key path is the registry route a checked
  build would use, but no value is seeded in the ROM hives.
- **UNKNOWN:** whether a checked/debug build of these modules exists with
  `DBGPARAM` records (not in the shipped image); whether injecting a synthetic
  `DBGPARAM` into guest RAM and calling `RegisterDbgZones` would unlock new
  lines — out of scope of the task's "find how to enable them" step, since
  there is no record to find.

## Conclusion

The task's Stop path is taken. `tools/ce_dbgzones.py` was added (with a
9-check selftest, auto-discovered by `tools/selftest.py`) and a full census
of all three builds of `archive/head256.img` found **zero** `DBGPARAM` records
and no registry `DebugZones` override, while the debug-sink hook itself works
(142 baseline lines). There is therefore no zone mask to set for `Navi.exe`
map modules or `SDHC.dll`/`navdrv.dll`/`lcddrv.dll`, and the Done-when table
(module -> mask VA -> default -> lines gained) cannot be populated: no module
has a mask VA or default. `M8.H15` is set `blocked`, with the exact blocker
and an `Unblock` pointing at a task that would obtain a checked/debug build
of the modules (or otherwise supply a `DBGPARAM` record). No `run.sh
--debug-zones` option is added: with no mask there is nothing for it to set.
No vendor bytes were committed; the tool contains only a synthetic fixture.
