## Question

Can the AUI button labels (Map Menu / ZOOM OUT / 1-16mi / ZOOM IN) be made
opaque in the windowed L4 screenshot, and which 2DG op writes their pixels
with the alpha bit that the keyed DU plane needs?

## Hypothesis

The AUI blits its labels into keyed DU plane 1 as `0xa8xxxxxx` alpha
glyphs whose destination alpha is cleared by `ze0-0014`'s `blend()` (which
preserves `dst & 0x8000`), so C-8502's colour key drops them. Rendering the
glyph destination with bit 15 set makes them opaque under the 0x03ff key.
**Falsifier:** the labels appear only in a non-key `plane -n 1` render and
never in `screen` after the fix, or a non-2DG (CPU/gdisubdrv) path is the
real writer, in which case the task Stop rule applies.

## Method

1. **Sample and hash.** The files and SHA-256 values in the Sample bullet,
   printed by `sha256sum <path>` on this host on 2026-11-24.

2. **Commands.** `$W` is the scratch work dir outside the repo; `$Q` the
   built `qemu-system-sh4`. Positive (patched) boot, identical for the
   negative-control binary (single `| 0x8000` removed in `glyph()`):

   ```bash
   python3 tools/unitflash_anon.py build -o $W/full.bin
   python3 tools/ze0_ipl.py patch archive/sd-images/LEAF_2011-2012_US.img \
     -o $W/ipl.txt --nk firmware/unit-flash/nk1-QY7200ND.bin
   "$Q" -M ze0,dbgmsg=0x880404c4,nk=firmware/unit-flash/nk1-QY7200ND.bin,\
   ipl-patch=$W/ipl.txt,flash=$W/full.bin,sci3=csci3,gfx-trace=on \
     -kernel archive/sd-images/LEAF_2011-2012_US.img \
     -drive if=sd,index=0,id=sd0,file=archive/sd-images/LEAF_2011-2012_US.img,format=raw,snapshot=on \
     -chardev socket,id=csci3,path=$W/pos2/sci3.sock,server=on,wait=off \
     -icount shift=0,sleep=off -nographic -serial file:$W/pos2/serial.log \
     -monitor unix:$W/pos2/mon.sock,server,nowait -gdb tcp::1249 \
     -d unimp,invalid_mem -D $W/pos2/qemu.log &
   python3 tools/ze0_peers/panel.py --sci3 $W/pos2/sci3.sock \
     --control $W/pos2/panel.ctl --forever --out $W/pos2/panel.events &
   python3 tools/ze0_uistart.py run archive/sd-images/LEAF_2011-2012_US.img \
     --port 1249 --touch-unlock --nk firmware/unit-flash/nk1-QY7200ND.bin
   printf 'tap 277 98\n' | socat - UNIX-CONNECT:$W/pos2/panel.ctl   # repeat until MAP_MAPOPERATION_NORMAL_MAP
   python3 tools/ze0_screenshot.py screen --monitor $W/pos2/mon.sock -o $W/pos2/after-map.png
   printf 'pmemsave 0x0ef6c400 0x2ee000 "%s/pos2/p1-map.bin"\n' "$W" | socat - UNIX-CONNECT:$W/pos2/mon.sock
   ```

   The bit-15 pixel counts come from a stdlib Python reader of the saved
   plane bytes: for each pixel `u16` at `(y*800+x)*2`, count `px & 0x8000`
   (opaque under the key) and `px and not px & 0x8000` (text dropped by the
   key) inside bbox x 740-793, y 252-434. The same loop over all 800x480
   pixels counts visible plane pixels. A second reader decodes the PNG RGB
   to confirm the label bbox colour histogram. The glyph emitter is
   attributed by `tools/cerom.py --image-start 0x200200 archive/head256.img
   modules | grep XGLDLL` (`XGLDLL.dll` vbase `0x030f0000`, sec0 file
   `0x00a2e200`) and `tools/sh4dis.py --image-start 0x200200
   archive/head256.img XGLDLL.dll --va 0x03120840 --count 60`: the
   instruction at VA `0x031208b0` loads the literal `0xa8000000` from the
   pool at `0x031208f0` (file offset `0x00a5daf0`); the glyph emitter
   function starts at `0x031208ae`. SH-4 code is little-endian throughout.

3. **Controls.** *Positive:* a patched QEMU with the `0xa8` glyph op
   rendering its destination alpha set — the labels must become opaque and
   survive the key. *Negative (mandatory mutation):* the same binary and
   boot flow with only the `| 0x8000` in `glyph()` removed (SHA printed
   above) — the label pixels must go back to bit 15 clear and the count must
   drop. The two builds' object files were disassembled with `objdump -d`
   to show the presence (`or $0x8000,%r10w`) and absence of that instruction.
   *Falsifier control:* compare `screen` (keyed) against `plane -n 1`
   (non-key) on the same state; if labels survived only the non-key render,
   C-8502 would be the mechanism and the task would be blocked.

4. **Scope.** One card (US 2011) on NK1 + anonymous flash, one `--ui-start`
   boot to `MAP_MAPOPERATION_NORMAL_MAP`, one static map screen; the last
   full UI display list `0x0e8d4c70` targeting plane 1 at `0x0ef6c400`
   (178 trace lines, 61 drawn / 15 skipped / 479 steps) with an op census
   of 52×`0xa8`, 9×`0xa2`, 6×`0xaa`, plus 6×`0x82`, 6×`0xe0`, 6×`0xd0`.
   The whole boot logged 17,291 `ze0-2dl` lines. The 0xa8 emitter is
   attributed to image A XGLDLL.dll; C1f also names an equivalent emitter
   in image B auirtdll.dll (`0x03d07a14` family) but the VA quoted here is
   the one whose literal was printed in this run. The guest lazy-redraw
   consent page under the widgets (C-8505) is out of scope.

5. **Falsifier.** Stated in Hypothesis and Controls.

## Observations

**O1 — the op.** The last AUI display list `0x0e8d4c70` targets plane 1
(`ze0-2dg: target 0x0ef6c400`) and logs `61 drawn, 15 skipped, 479 steps`.
Its glyph commands are `0xa8003100` (52 occurrences; word 1 colours
`0x6f7b`, `0x1084`, `0x7fff` — the same values that were bit-clear text
before the fix), plus `0xaa003103` (6) and `0xa2003900` (9). The emitter
literal `0xa8000000` is at XGLDLL.dll `0x031208f0`, loaded by the
instruction at `0x031208b0` in function `0x031208ae` (cerom attribution
above). This is a 2DG op; the task Stop case (CPU blit) is not met.

**O2 — before the fix (negative baseline).** Plane 1 page `pmemsave`
(counts printed by the reader): whole page 1,502 bit-15-set pixels and
24,665 pixels neither 0 nor the key with bit 15 clear; bbox x 740-793,
y 252-434 has 491 bit-15-set pixels and 991 bit-15-clear text pixels in
30 distinct colours (top values `0x6b5a` 145, `0x6f7b` 114, `0x7fff` 113,
`0x1084` 80, `0x7bde` 77). The composed `screen` PNG SHA-256
`7ed73dc11e16f10ec2a65083107333a0c539aad0a99010bcd65cf920e7ab879b`
(383,947 non-black pixels) shows the map but none of those labels.

**O3 — patched (positive).** The same flow with `ze0-h47` produces
`ze0_screenshot.py screen`: plane 1 `0x1002` at `0x0ef6c400`, key `0x03ff`,
259,644 non-black pixels; PNG SHA-256
`cbba3f310f47a36bd9c4a5c424c310614769238f52a317c4697021ef25146509`
(kept in `$W/pos2/after-map.png`, outside the repository). The plane-1
page dump now has 49,655 visible (bit-15-set, non-key) pixels across the
page; in the label bbox it has 2,378 bit-15-set pixels and **0** bit-15-clear
text pixels. The formerly bit-clear text colours are now bit-15-set inside
the bbox: `0x6b5a` 162, `0x6f7b` 125, `0x1084` 80, `0x7bde` 75, `0x2529`
81, `0x1084` present — i.e. the same glyphs as O2, now opaque. An ASCII
rendering of the bbox pixels shows the letter shapes of the button labels.

**O4 — negative mutation.** With only the `| 0x8000` removed from
`glyph()` (binary SHA printed in Tools; object `objdump` shows only
`and $0x8000,%si` from `blend()`, no alpha-setting `or`), the same boot and
map screen gives bbox bit-15-set **441** and bit-15-clear text **1,010**.
The composed PNG SHA-256
`8d55c17565143be0e5e0ffccfc84961b46d1f2a2dd4ea88678e6dd5e88ce2022`
(261,658 non-black pixels). The opacity count drops from 2,378 to 441 and
the dropped-text count rises from 0 to 1,010, as the mutation predicts.

**O5 — key rule survives.** In O3 the composed `screen` is the keyed composer
(`mode 0x1002`, `+0x48 & 0x7fff = 0x03ff`); the label pixels have bit 15
set, so they are not equal to the key and are drawn. The `plane -n 1`
non-key view is not needed for the labels and the falsifier of C-8502 is
not met: the labels appear in the keyed `screen`.

## Interpretation

- **FACT:** the AUI label glyphs are 2DG `0xa8` blits emitted by XGLDLL.dll
  at `0x031208ae` (literal `0xa8000000` at `0x031208f0`); the task's Stop
  case (non-2DG path) does not apply.
- **FACT:** the pre-fix `blend()` kept the destination alpha clear, so the
  keyed plane dropped the text; setting bit 15 on glyph writes makes the
  same glyph colours opaque and visible in the windowed `screen`.
- **FACT:** the negative mutation removes the effect without changing the
  card, tap flow or renderer, so the alpha bit is the one variable.
- **OBSERVED:** `0xa2`/`0xaa` ops also occur in the AUI list and were not
  individually decoded; the glyph fix alone was sufficient for this screen.
- **UNKNOWN:** whether the hardware 2DG literally ORs bit 15 in its glyph
  path or achieves opacity through a separate destination-alpha register;
  the model is validated at L4 against the expected screen, not against a
  hardware trace.

## Conclusion

Patch `ze0-h47-aui-glyph-alpha.patch` makes the `0xa8` alpha-glyph blit write
an opaque destination pixel. At L4 the map screen now shows the AUI button
labels over the map in `ze0_screenshot.py screen`, their pixels carry bit 15
and survive the 0x03ff key (bbox 2,378 opaque / 0 dropped, versus 491/991
before and 441/1,010 after the negative mutation). The 2DG op is named with
its VA (`XGLDLL.dll 0x031208ae`, literal at `0x031208f0`). The screenshot is
kept outside the repository with SHA-256 recorded in O3. The leftover
consent page under the widgets is the C-8505 lazy-redraw artefact and is not
addressed here.
