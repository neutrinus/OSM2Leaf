## Question

Can the rule-17 `card_step` number be made to read a fresh, validated card
ladder report instead of the 2026-11-17 P0 pin, so a real gate run can move it,
while a missing or failed gate can never promote a number?

## Hypothesis

Yes: if `card_step_from_report` trusts only a report that has a `step` in
P0..P4, both `cardcheck_ok`/`l2check_ok` true, both gate rc values equal to 0,
a full 64-hex card SHA-256, and a step present in `card_ladder.py steps
--check`'s step grouping, then a fresh report for the P0 card prints `P0`, and
every missing/false/disagreeing mutation prints `NOT RUN` / `none`.
**Falsifier:** a report whose gate did not pass still prints a promoted step,
the printed step disagrees with the ladder groups, a missing step or false ok
is treated as P0, an rc/ok disagreement prints as a clean step, or any of the
other three rule-17 lines changes.

## Method

1. **Sample and hash.** The sample is the fresh report JSON above plus the
   named P0 card it gates. `sha256sum

2. **Commands.** Run in the worktree, in this order:

   ```bash

     --json ~/projekty/leafre-work/scratch/m9.76/cc-p0.json

     ~/projekty/leafre-work/scratch/m9.60/p0.img

     --no-golden --cmp-limit 20 --json ~/projekty/leafre-work/scratch/m9.76/l2-p0.json
   # exit 0; JSON "ok": true, "errors": []
   sha256sum ~/projekty/leafre-work/scratch/m9.60/p0.img

   python3 -c "
   ```

   - **Negative — false ok:** mutating `cardcheck_ok` to `false` in a copy of

## Interpretation

- **FACT:** the fresh report for the named P0 card records the full card
  SHA-256, both real gate exit codes (0/0), and a ladder step derived from the
  tile bytes; `--report <fresh>` prints `card_step: P0`.
- **FACT:** every negative mutation of that report prints `NOT RUN` / `none`,
  never a promoted number; the positive mutation to `P1` moves the printed
  number, so the signal is not a hidden constant.
- **FACT:** the other three rule-17 lines are byte-identical; the stale
  2026-11-17 report now reads `NOT RUN`, which is the honest state for a
  report with no `step` key.
- **OBSERVED:** `card_ladder.py steps --check` exits 1 today for unrelated
  board tags; its parsed step groups are usable and are used as the oracle.
- **UNKNOWN:** no firmware reader verdict is implied — rule 13 is unchanged
  (M9.12/M9.31 gate the card, M8 owns L4). The step printed is the card's
  ladder content step from `build.ladder_step`, not a claim of car acceptance.

## Conclusion

`tools/map_signals.py` now reads a validated `step` from a fresh out-of-repo
report instead of the 2026-11-17 P0 pin. The fresh report for the M5.30 P0 card
(`b0faf119…c33237`) records both gate rc values and prints `card_step: P0`;
the four rule-17 numbers are re-quoted in TODO Priorities with that report's
