## Question

Can the compressed `FILESentry` payloads of image B (`boot.hv`, `default.hv`, `user.hv`, `ceconfig.h`, `initobj.dat`, `UpdateNK.skn` and other `csize != rsize` entries) be extracted and decoded to their `rsize` lengths (with `ceconfig.h` readable text) using the M1.2b/c path, without a CE-LZXD block-codec port?

## Hypothesis

Exploratory. EXP-51 showed stdlib formats (zlib raw/zlib/gzip, LZMA, bz2, skip 0–16) do not decode the payloads. The M1.2b/c path (`cecompress` methods lzss/lzx/lznt1/xpress-lz77/xpress-huffman, and the nk.exe decompressor identified in M1.2c) might suffice only if a public method matches or if the payload format differs from CE `IMAGE_SCN_COMPRESSED`. **Falsifier (met for decode):** every `csize != rsize` entry is `UNSUPPORTED`/no-match under public methods and carries the CE-LZXD block marker, so `rsize`-length readable output cannot be produced without the CE-LZXD codec (M1.2f/M8.E1).

## Interpretation

- **OBSERVED:** All 8 compressed FILESentry entries in build B have extractable stored bytes and carry the CE block marker `0x8d80805b` (`5b 80 80 8d`) at a per-entry offset (25–1459). For 7/8 small/medium entries the first LE `u16` equals `rsize` (ceconfig 6611, initobj 15706, boot 32768, user 28672, initdb 7172, celog 7168) and `default.hv` gives `u16=61440` while `rsize=126976` (u16 insufficient); `UpdateNK.skn` gives `u16=0` with `rsize=1966080` — consistent with EXP-51's note that the first field is not a plain u16 size for large payloads.
- **OBSERVED (negative, with positive control):** No public `cecompress` method decodes `ceconfig.h` to 6611 bytes at any tested offset (0–80), and `cerom.py files --extract --decompress --json` classifies all 8 as `UNSUPPORTED` with 0 `OK`. Positive control: the same tools decode/classify synthetic known streams (EXP-55/C-573, `cerom --selftest`; EXP-M1.2b probe finds lzss@22).
- **HYPOTHESIS:** The FILESentry compressed payloads use the same nk.exe CE-LZXD block codec family as `IMAGE_SCN_COMPRESSED` sections (marker `0x8d80805b` present; M1.2c identified `DECOMP_WRAP/SECT/BLK`), wrapped in a FILESentry-specific header (u16/u32/fields before the marker). The exact header layout and block framing are not fully decoded.
- **FACT (blocker):** M1.2c delivered decompressor VAs; M1.2f is **blocked** (no pure-Python CE-LZXD port, no `qemu-system-sh4` oracle in session). Therefore `ceconfig.h` cannot be made readable text and `rsize`-length decoded output cannot be produced by the M1.2b/c path in this repo state.

## Conclusion

M1.4 **extraction and characterization** succeeded: stored `csize` bytes for all compressed FILESentry entries of build B are extractable (`cerom.py files --extract`) and classified (all `UNSUPPORTED` under public methods). **Decode is blocked**: every payload carries CE marker `0x8d80805b` and no public method matches, so producing `rsize` bytes and readable `ceconfig.h` requires the CE-LZXD codec (unblock M1.2f and/or M8.E1 runtime oracle, then resume M1.4 decode). M1.4 done-when ("payloads whose length is `real` and `ceconfig.h` is readable text") is **not met**; task set to `blocked` per rule 6.
