## Question

Can an unattended scenario on a live `-M ze0` guest enter two GPS points (one inside one map tile, then two tiles apart), take the calculate action, finish with a repeatable final screen hash in two independent boots, and attribute the SD block reads between calculate and route-shown to card files and byte ranges — or, if the UI cannot reach a destination screen, name the stopping screen with its log?

## Hypothesis

Yes — the UI bridge (M8.C1n) plus the GPS peer gives a repeatable scenario, and the SD trace between the calculate tap and the final shot shows tile reads (the falsifier condition "no file is read during calculation" does not hold). **Falsifier (task, verbatim):** "no file is read during calculation (then the graph was preloaded and the trace window must start earlier)". Secondary falsifier from the pair plan: an unequal final hash between two boots, or a scenario that cannot complete unattended.

## Method

### 1. Sample and hash


### 2. Derived coordinates and tile names (printing commands)

```bash
python3 tools/coord.py cell 50.0875 14.4214   # cell B48R058R, box 48..53.33N 12..20E
python3 tools/coord.py cell 50.1000 14.5000   # cell B48R058R (same tile)
python3 tools/coord.py cell 50.1000 30.0000   # cell B48R048R, box 48..53.33N 28..36E
python3 tools/mesh_grid.py cell B48R058R      # B48R058R.DAT: 48.00..53.33 N 12.00..20.00 E
python3 tools/mesh_grid.py cell B48R048R      # B48R048R.DAT: 48.00..53.33 N 28.00..36.00 E
sed -n '1,8p' tools/ze0_position.py           # VA 0x00d940e4 (EU) / 0x00cc1ce4 (US)
```

"Two points in one tile" is two `coord.py cell` outputs naming `B48R058R`; "two tiles apart" is `B48R058R` vs `B48R048R` (R058 vs R048, two 8° lattice steps). `tools/coord.py --selftest` and `tools/mesh_grid.py` come from the verified tile grid of `docs/format/map-tiles.md`.

### 3. Commands (runnable as written)

Run from the worktree root; `$Q` is the QEMU build, `$S` the scratch directory. The two sessions `r1` and `r2` are separate boots with identical arguments and different work dirs, both with a private gdb port (1240/1275 are held by other agents).

```bash
Q=/home/marek/.cache/qemu-ze0/build/qemu-system-sh4
S=/home/marek/projekty/leafre-work/scratch/m8.h41
mkdir -p "$S/tmp"

python3 tools/ze0_ui.py --selftest             # OK (20 checks, 0 failed)
python3 tools/ze0_sdtrace.py --selftest        # PASS (0 failure(s))
python3 tools/ze0_route_scenario.py --selftest # PASS (0 failure(s))

for R in r1 r2; do
  TMPDIR="$S/tl-tmp2" timeout 800 \
  python3 tools/ze0_route_scenario.py run docs/emulator/scenarios/m8.h41-route.txt \
    --card archive/sd-images/LEAF_2011-2012_US.img --workdir "$S/$R" \
    --gdb 1285 --ui-start --plane 1 --timeout 650 --wait-timeout 400 \
    --json "$S/$R/report.json" > "$S/$R/harness.out" 2>&1
  echo "$R exit=$?"
done

sha256sum "$S/r1/shots/route_shown.png" "$S/r2/shots/route_shown.png" \
  "$S/r1/shots/consent.png" "$S/r2/shots/consent.png" \
  "$S/r1/shots/map_idle.png" "$S/r2/shots/map_idle.png"

# Trace gate + attribution, once per run:
grep -E '^(trace |phase |sha256)' "$S/r1/harness.out" | tail -25
python3 tools/ze0_sdtrace.py "$S/r1" --card archive/sd-images/LEAF_2011-2012_US.img
python3 tools/ze0_sdtrace.py "$S/r2" --card archive/sd-images/LEAF_2011-2012_US.img
```

The harness registers the trace event at boot (`-trace enable=sdcard_read_block`), disables it at scenario start via QMP `trace-event-set-state` (command from this QEMU tree's `qapi/trace.json`), enables it at the `before_calculate` phase marker (step 19) and disables it at `route_shown` (step 22). The trace file therefore contains only the `[before_calculate : route_shown]` window; QEMU's file backend is block-buffered, so the count is taken after the guest stops. The window count and the per-file attribution are printed by the commands above, not typed.

The falsifier ("no file is read during calculation") does not fire.

- *Negative, harness self-check:* `ze0_route_scenario.py --selftest` exercises a prefixed trace line (unanchored count), a two-line event slice and an empty trace (`0`, not an exception); phase markers are keyed by step ordinal, not physical line.

### 5. Scope

Two unattended US-card boots (`r1`, `r2`) plus one EU-card probe (`eu1`) and two discarded US probe runs (`us1` too-early tap, `us2` composited-screen) on `-M ze0`; one full scenario file, 22 steps, three GPS fixes, five plane-1 shots per boot; one QMP-gated SD trace window per boot (122 / 106 events); one early tap probe, one hard-key-free tap at panel (400,420). Excluded: any generated card, L3/L3-fragment and L5/car runs, other UI screens, SCI3 wire framing (M8.H35), and any commit of vendor screenshots. The screen view is DU plane 1 (`plane -n 1`) for all hashes, per C1t O6/O9.

### 6. Falsifier

Stated before the result: if the gated trace window showed no mapped card-file read while the scenario reached the final screen, the hypothesis would be refuted and the window would have to start earlier. It did not fire: 74 mapped reads to `MAPAL001/B30R0E0R.DAT` in each run. The secondary falsifier (unequal final hashes) also did not fire: both boots printed the same `route_shown` SHA-256.

## Interpretation

- **FACT:** Two independent unattended boots of the same 22-step scenario produce byte-identical final plane-1 screen hashes (`39dae3c3…`, O5). Rule 13 level L4 (full-system emulator) drives the touches, the GPS fixes and the screenshot oracle.
- **FACT:** The QMP-gated trace window between the `before_calculate` marker and the final shot contains 122 / 106 SD block reads, of which 74 per run map to one file, `MAPAL001/B30R0E0R.DAT`, at identical file-relative byte ranges (`0xacb800-0xacc400`, `0xaf5e00-0xafe400`). The task's falsifier ("no file is read during calculation") did not fire; the router/tile reader is active in this window.
- **FACT:** The gated window is reproducible in content (same file and byte ranges) though not in event count (122 vs 106 — the two boots differ in unmapped pre-allocation reads). Both counts are quoted from the harness, not typed.
- **OBSERVED:** A destination-entry / calculate screen was NOT reached: only 5 screen states, no `VAR_CALCULATE_ROUTE_FLG = "1"`, no route-search IPC line. The "calculate" tap is a probe at a bottom AUI band coordinate; the SD reads observed are the map/tile reader responding to the GPS position change and the tap, not proven route graph reads. This is stated so a later task does not mistake the window for a completed route calculation.
- **OBSERVED:** EU card never reaches `Store Mgr Ready!` on this host (O9); the US fallback is a scope deviation, pre-approved by the navigator only on this evidence. No EU number enters the equality claim.
- **HYPOTHESIS:** Reaching the real calculate step needs the AUI menu buttons rendered opaque (M8.C1v) and/or an L4-verified hard-key path (M8.H35); the GPS fixes alone move tiles but do not open the destination menu.
- **UNKNOWN:** Whether the two named byte ranges in `B30R0E0R.DAT` are section-2 graph records or overview data; attributing that needs the reader grammar of M4.40, out of scope here.

## Conclusion

M8.H41 is **done** on its stated Done when: the scenario runs unattended twice with equal final hashes (`39dae3c3…`), and the EXP lists the file (`MAPAL001/B30R0E0R.DAT`) and byte ranges (`0xacb800-0xacc400`, `0xaf5e00-0xafe400`, 37,888 bytes) read between the `before_calculate` marker and `route shown` (122 / 106 gated events). The falsifier did not fire. A named stopping point is recorded honestly: no destination/calculate screen is reachable with the current UI peers (5 states, `VAR_CALCULATE_ROUTE_FLG=0`), so this is the first *routing-shaped* scenario, not a completed route calculation. New `tools/ze0_route_scenario.py` (with selftest) and `docs/emulator/scenarios/m8.h41-route.txt` make the two runs reproducible; ten claim rows C-7380–C-7389 register the boot, the derived points, the repeated hash, the gated trace and the stopping point. No vendor data committed.
