# EXP-2026-11-06-M1.7: Which kernel (B or C) boots with A

- **Status:** done (verdict: IPL-selected)
- **Date:** 2026-11-06
- **Sample:** `LEAF_2011-2012_QSD-309-101_navi158_eu.img`,
  SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
  (vendor data, not committed). Working window: first 128 MiB.
- **Claims:** C-700–C-709
- **Supersedes:** none (resolves the open part of C-529 for the boot choice;
  C-529's compression half stays open)
- **Superseded by:** none

## Question

Does the SD image decide whether kernel build B or build C runs alongside
application build A, and if so through which field? The answer feeds M8.B4
(boot arguments at phys `0x08000020`–`0x0800002b`).

## Hypothesis

`UpdateMng.exe`/`PRGUpdate.exe` presence in B and `TestMode.exe` in C
(C-526) describe *build role*, not the boot choice, and the ROMHDR fields
recorded so far (`ulRAMStart`, `pExtensions`, module set) are identical
between B and C. The on-board IPL (C-535) is therefore the only selector;
the 4-byte header difference and the boot-argument bytes are the two
candidates worth testing.

import cerom
d=open("$IMG",'rb').read()
rom=cerom.CERom(d,0x3e00200)
targets={0xa8000020+i for i in range(12)}
for m in rom.modules():
    for sec in rom.o32(m):
        if sec["flags"] & 0x2000: continue
        if not (sec["flags"] & (cerom.CNT_CODE | cerom.MEM_EXECUTE)): continue
        off=rom.va2file(sec["dataptr"]); b=d[off:off+sec["psize"]]; base=sec["realaddr"]
        for i in range(0,len(b)-1,2):
            w=int.from_bytes(b[i:i+2],'little')
            if (w & 0xF000)==0xD000:
                lit=(base+i & ~3)+4 + (w & 0xff)*4
                try: fo=rom.va2file(lit)
                except: fo=None
                if fo and fo+4<=len(d) and int.from_bytes(d[fo:fo+4],'little') in targets:
                    print(m["name"], hex(base+i))
PY

# the nk.exe function that consumes the boot args
python3 tools/sh4xref.py "$IMG" nk.exe --image-start 0x3e00200 --calls 0x8804cc42

| Field | A | B | C |
| --- | --- | --- | --- |
| `physfirst` | `0x8cae1000` | `0x88000000` | `0x88000000` |
| `physlast` | `0x8e233c88` | `0x886e18a4` | `0x886683d8` |
| `nummods` | 149 | 91 | 88 |
| `numfiles` | 1 | 11 | 10 |
| `ulRAMStart` | `0x89e40000` | `0x89e40000` | `0x89e40000` |
| `ulRAMFree` | `0x89e73000` | `0x89e73000` | `0x89e73000` |
| `ulRAMEnd` | `0x8cae1000` | `0x8e600000` | `0x8e600000` |
| `ulCopyEntries` | 0 | 2 | 2 |
| `pExtensions` | `0x880030a4` | `0x880030a4` | `0x880030a4` |
| `usCPUType` | `0x01a6` | `0x01a6` | `0x01a6` |
| `nk.exe` entry VA | n/a | `0x8800ebd0` | `0x8800ebb0` |

- `pExtensions` block (512 bytes at `0x880030a4`): byte-identical between B and C
  except one character of a build-path string — B `d:\wince500\…\loader.c`,
  C `c:\wince500\…\loader.c`. The block is the standard WinCE `nk` debug string
  pool (`SC_SetCleanRebootFlag`, `Booting kernel with clean memory
  configuration:`, …); it contains no selection flag.
- First 16 bytes of the two images:
  - B `09 00 09 00 01 d0 09 00 2b 40 09 00 d0 eb 00 88`
  - C `09 00 09 00 01 d0 09 00 2b 40 09 00 b0 eb 00 88`
  Bytes 12–15 are the `nk.exe` entry point (`0x8800ebd0` vs `0x8800ebb0`).
  This is the "4-byte header difference" (C-263).
- Boot-argument scan: across all 91/88 modules of build B, the only code that
  references any of `0xa8000020`–`0xa800002b` is `nk.exe` at
  `0x8804ccd6` … `0x8804cd2e` (12 `mov.l` loads, one per byte).
- That code is the AERTRACE dump function starting at `0x8804cc42`; its
  literals include `0x8800e5a8` = `"Navi Version : %c%c%c%c%c%c%c%c-%c%c%c"`
  and `0x8800e7a0` = `"AERTRACE: Dumping system state info."`. The 12 bytes are
  printed as an 11-character version string plus one trailing byte; no
  comparison, mask or branch on any of them was found in `nk.exe`.
- `tools/kernel_select.py` on the recorded B/C fields (EXP-54) returns
  `UNKNOWN` with a single discriminator (`updater_set`); feeding the now-recorded
  `ulRAMFree`/`ulRAMEnd` (both `0x89e73000`/`0x8e600000` for B and C) does
  not add a second structural difference, so the tool still refuses a verdict.
- `PRGUpdate.exe` strings in B: `UpdateToFlash` (`BOOTLOADER`, `NK1`, `NK2`),
  `UpdateToSysSD`, `UpdateToUnfrm`, `NK1VerChk`/`NK2VerChk`/`UnfrmVerChk`,
  `CreateUpdateList! : No Recovery / Recovery`. The unit therefore carries two
  kernel slots in flash and can update either; this is a *maintenance* path, not
  the SD boot choice.
- `TestMode.exe` (C) imports `CApi_GetBootMode`/`SetBootMode`/`GetBootModeEx`
  (C-818), so image C is the test-mode build entered through a boot-mode flag.

## Interpretation

- **FACT:** Builds B and C are byte-different kernel images with different
  `nk.exe` entry points and different module sets, but identical `ulRAMStart`,
  `ulRAMFree`, `pExtensions`, `usCPUType` and `ulCopyEntries`; `kernel_select.py`
  cannot separate them structurally (C-529, EXP-54).
- **FACT:** The only consumer of the 12 boot-argument bytes
  (`phys 0x08000020`–`0x0800002b`, accessed as P2 `0xa8000020`–`0xa800002b`)
  in the whole firmware is `nk.exe`'s AERTRACE dump, which formats them as the
  `"Navi Version"` string. No firmware branch keys on them.
- **OBSERVED:** The SD card carries no bootloader (C-535); the IPL is in
  on-board flash and copies one of the two kernel images to phys `0x08000000`.
  The SD image therefore does not, by itself, say which kernel runs; the IPL
  selects. Build C is additionally reachable as the test-mode image (C-818).
- **HYPOTHESIS:** The 12 bytes are a version string stamped by the IPL/loader,
  not a selector. For M8.B4 they should be provided as the factory
  `"Navi Version"` bytes (or left zero) and are not expected to change the
  kernel that is loaded.
- **UNKNOWN:** The actual IPL selection condition (hardware switch, flash flag,
  or `UpdateNK.skn` version) cannot be determined from the SD image; it needs
  the on-board flash or a dynamic break.

## Conclusion

Verdict for M1.7: **IPL-selected**. The SD image provides both kernels and
both are structurally bootable; the on-board IPL chooses, and no field in the
12-byte boot-argument block selects between B and C. M8.B4 should treat
`0x08000020`–`0x0800002b` as a version string, not a kernel selector.
C-529's "which kernel boots" half is resolved (IPL-selected); its compression
half remains open (M1.2/M1.3).
