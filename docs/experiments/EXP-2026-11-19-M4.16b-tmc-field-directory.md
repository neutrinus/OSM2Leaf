## Question

What does the C-884 accessor (`0x003f61bc` and helpers, EU2011) compute from a record, does that rule recover true field boundaries on the card's TMC records, and do the decoded records map to tile/mesh/coordinates with a named join key and a ~0 random-key control?

## Hypothesis

Reading the five helper functions as code (not as a schema lookup) gives a rule that needs only the record bytes and a field count. If the rule is right, it frames every record of the TMC volume exactly, and a decoded field (or a key derived from it) joins the records to `RDSTM001.DAT` and from there to tiles.

**Falsifier:** (a) the rule, applied with 12 fields, leaves any record of the stream with a length sum different from its size word, or a wrong field count (11, 13) frames the stream equally well; (b) the location code join gives as many neg/pos agreements at a shifted ordinal as at shift 0; (c) the placement probe on the decoded keys finds no key above its random control and no per-record key into a tile id.

## Observations

**Firmware (EU2011 build A).**

- `pdata`: `0x003f61bc` START len `0x64`; `0x003f51e0` START len `0xe0`; `0x003f56bc` START len `0xec`; `0x003f57a8` START len `0x34`; `0x003f5d98` START len `0x78`; `0x003f5e10` START len `0x66`; `0x003f66b8` START len `0x4c`.
- `0x003f61bc(r4, r5, r6)`: calls `0x003f51e0(r4)`, fails on `-1` or `r5 == 0`; `p = 0x003f56bc(r4, r5, r6)`; `n = 0x003f57a8(r4)`; returns `0x003f5e10(p, n, r6)`.
- `0x003f51e0(r4)`: first `jsr @[0x0055d8f0]`, which `va_class` names `IAT OSMDLL.dll!taskIdSelf` (its result is not used); then compares `r4` with the words at `+12, +20, +28, +36, +44, +56, +64, +80, +96, +112, +128, +136, +144` of `0x00d53500` and returns the word after the matching one (`+16, +24, …`); no match → `0x003f3a10(r4)`, which compares `r4` with `@0x00d5e4e4` and returns `@0x00d5e474`. Nothing else is read from `0x00d53500`.
- `0x003f56bc(h, rec, i)`: `base = 0x003f51e0(h)`; `hdr = base + 2*u16[base+2]`; `w = u16 rec[0]`; reject if `(w & 0xe000) > 0xc000` or `((w & 0x1800) >> 11) ∉ {0,1}`; require `i < u16 hdr[26]`, walk a linked list `hdr + 2*u16[...]` from `u16 hdr[24]` `i` times and require `u16 [node+12] == i`; return by `w >> 13`: 0 → `rec+2`; 5 → `rec+8`; 2 or 3 → `rec + 2*(hi+lo+8)` of `u16 rec[10]`; 6 → `rec + 2*(hi+lo+2)` of `u16 rec[2]`; else −1.
- `0x003f57a8(h)`: returns `u16 hdr[26]` (the field count).
- `0x003f5d98(h, rec, i)`: `x = u16 p[2*(i>>1)]`; returns `x >> 8` for even `i`, `x & 0xff` for odd `i` (field length in words).
- `0x003f5e10(p, n, i)`: `words = (n+1)/2 + Σ_{k<i} len[k]`; returns `p + 2*words` (`-1` if `i > n`).
- `0x003f66b8(h, rec)`: `ptr = 0x003f61bc(h, rec, 0)`, `len = 0x003f5d98(h, rec, 0)`; returns `u16 @ptr` if both non-zero, else `0xffff`.

## Interpretation

- **FACT (code):** `0x00d53500` is a handle → block cache (key/value word pairs) consulted by `0x003f51e0`; it holds no field lengths. The field directory is **in the record**: a length table of one byte per field (words), padded to whole halfwords, followed by the fields in index order. The only value the walk takes from outside the record is the field count (`u16 hdr[26]` of the handle's block, runtime state). The M4.16b blocker "schema unreadable" (C-2305, C-2309) therefore does not block the walk; M3.22 is not its unblocker.
- **VERIFIED (data):** with 12 fields and big-endian halfwords the rule frames 247,089/247,089 EU and 303,023/303,023 US `LCTBL001.DAT` records exactly; 13 fields frame none, 11 fields only the records without field 11, and the swapped pairing breaks field 0. The M4.18 "16-byte header + 4 slots + footer" layout is this directory seen from outside: the "marker 0x01" is the length of field 0, `len1..len4` are fields 1–4, the 7 "attribute" bytes are the lengths of fields 5–11 and the "footer" is fields 5–11.
- **OBSERVED:** the records the C-884 accessor reads are the `LCTBL001.DAT` page records (the volume pairs `RDSTM001` with `LCTBL001.DAT`, C-880); the code reads native `u16`, so the card's big-endian halfwords must be converted on load (not located in code; HYPOTHESIS for the mechanism).
- **OBSERVED:** raw field 0 is the TMC **location type** (120 values: 100 continent, 300 country, 20111 …), not the location code; `docs/format/rdstm.md` called it "location code" after the firmware's `LocationCode(%d)` label. The location code is not a record field: it is the BCD value of the ordinal → code index (one run per location table).
- **VERIFIED (join key):** the **TMC location code** joins the decoded records to `RDSTM001.DAT`: 167,204 of 172,752 testable records (96.8 %) have the same (negative, positive) pair as the RDSTM triple of their code; at ordinal shifts ±1 and +2 the agreement is 0 in all 28 pairs. Each code carries 1–n groups of `u32` link references.
- **OBSERVED (negative):** no decoded key, and no RDSTM reference read as `(hi16, lo16)`, `lo16 & 0x1fff` or `u32`, joins a tile id of `B48R058R` above chance; the three `CHECK` rows are small-value keys (area, intersection) against id sets that are also dense at small values — set overlap, not a per-record join. The references are `(group 0..3131, index)` pairs whose groups are sequentially numbered lists; 3,132 groups and 2,294,877 indexed entries fit the ~9.9 MB of 4-byte entries after `0xccce00`, which this EXP did not decode.
- **UNKNOWN:** the group → mesh/parcel mapping and the format of the 4-byte group entries; whether `ref` group numbers are mesh numbers; the US index/`RDSTM001.DAT` layout.

## Conclusion

The C-884 field directory is decoded from the code and verified on both 2011 builds (EU 247,089, US 303,023 records, zero mismatches; controls fail as they must). The `0x00d53500` "schema" is a handle cache and not needed. The decoded records are joined, by the TMC location code from the `LCTBL001` index, to the `RDSTM001.DAT` location → link records (167,204/172,752 neg/pos agreements, 0 at every shifted control), which is the named join key for the first leg. The second leg — `RDSTM001` link reference → MAPAL mesh/parcel/link → coordinate — is not decoded, and the re-run placement probe finds no direct tile join, so **≥20 records mapped to tile/mesh/coordinates is not met: M4.16b is `blocked`** on a new task M4.16e (decode the RDSTM001 link groups after `0xccce00`). `docs/format/rdstm.md` gets the directory rule, the index, the RDSTM block layout and the field-0 correction; `claims.md` gets C-5130–C-5136; `reader-coverage.md` rows 21–22 point to the located walk.
