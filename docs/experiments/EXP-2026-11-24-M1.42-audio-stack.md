## Question

What does the SH-4 do itself and what does it delegate to the audio
microcontroller over `SCI1:` in the `Audio.exe` / `anwdrv` / `wavessi` /
`DspDrv` / `MuteDrv` / `BeepDrv` stack, and what is the `anwdrv` iNai message
set with direction and meaning?

## Hypothesis

The SH-4 produces PCM in `wavessi1/2` (SSI1/2, DMA 12/13) and sends source,
volume, guidance and radio controls to the MCU over `anwdrv.dll`; the iNai
command byte can be derived from code (`mov #N,r6` in the `CInaiMsg` jsr delay
slot) rather than guessed from a doc. **Falsifier:** fewer than 20 messages
resolve to a handler VA; a command byte cannot be tied to a literal; the PCM
producer cannot be named from a cited VA/observation. Then the Done when
fails and the task is `blocked`.

   ```bash
   python3 tools/sh4xref.py archive/head256.img anwdrv.dll --image-start 0x3e00200 --to 0x3b833d1

   ```

   `tools/anw_msgs.py` is the committed version of the scan: it takes the
   exec section from `cerom.py`, function starts from `pdata.py`, collects
   `[Msg:p*Buf]` literals, finds each `mov.l @(disp,PC),Rn` literal load and
   the preceding `[jsr @Rn][mov #N,r6]` pair, and prints the code-derived
   command byte plus the enclosing function VA. No heredoc scan is used.
3. **Controls.** *Positive*: `exports anwdrv.dll` prints 80 rows in seven
   10-export device groups; `sh4xref --to 0x3b833d0` prints
   `pool 0x03b90cbc holds 0x03b833d0` / `fn 0x03b90bbc [pdata]`, matching

4. **Scope.** Static EU 2011: build A modules `Audio.exe`, `wavessi1/2`,

   `DspDrv`, `BeepDrv`, `MuteDrv`, `wavessi1`, `AudioUpdateCC`. Only

## Interpretation

- **FACT:** `anwdrv.dll` has 80 stream exports over 7 logical devices and 98
  distinct message literals in uncompressed code; 80 of those carry a
  code-derived command byte and a `.pdata` handler VA. The table is derived
  from the bytes, not from the format doc.
- **FACT:** the PCM producer is the SH-4 wave driver (`wavessi1/2`, SSI1/2,
  HPB-DMAC ch 12/13), and the M8.H46 model captured non-silent PCM through
  that path; the firmware's real sample rate/bit depth remain UNKNOWN.
- **OBSERVED:** `Audio.exe` issues source/volume/guidance controls through
  `commondll CApi_*` imports and the `AUD1:` device; radio goes through
  `TNR2:` in the EU build.
- **HYPOTHESIS:** where guidance is mixed over media is decided outside the
  resolved SH-4 code (in the audio MCU); no mixer VA was found, so the page
  records `unknown` rather than inventing one.
- **UNKNOWN:** the meaning of many 3–4 letter log ids (marked HYPOTHESIS in
  the page); the V850 microcontroller firmware (out of scope).

## Conclusion

`docs/firmware/audio.md` was added with the template sections of
`docs/firmware/README.md`, a PCM path diagram naming the producer and SSI
channels, and 71 `anwdrv` message rows with direction and meaning or
`unknown`; `tools/anw_msgs.py` makes the derivation reproducible. The
Done when is met (71 >= 20). Claims C-6440–C-6449 record the evidence. No
patch was built and no hardware run is claimed. Open: the physical mixing
site and the meaning of the text-only log ids.
