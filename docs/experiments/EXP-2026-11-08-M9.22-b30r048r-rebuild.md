## Question

Which background record does `B30R048R` refuse to rebuild, which invariant
fails, and does the tile still round-trip byte-identically (so the L2 pin can
be trusted)?

## Hypothesis

The H14 transcript is `AssertionError((6, 29))` from `clarion_bg.parse_record`
on an opaque background record. Falsifier: if the refused records have a
layer region that the header bounds and that holds a used layer entry, the
failure is a real layer, not a table-length artefact, and the pin must be
marked "known non-round-tripping". If any record of a control tile is refused,
the refusal is not specific to B30R048R. If the bounded reading changes the
parse of any record that parses today, the bound is wrong.

## Interpretation

- **FACT (VERIFIED):** the refused records are three level-1 background records
  in directory `0x2ad00`, slots 6, 8 and 11. Their header sets the geometry
  region to `geo_len = 26` units, all empty; the table that `parse_record` reads
  has 29 entries and the non-empty entries sit outside the region (index 28
  onward). This is the invariant `nlayers == len(table)` failing, not a layer
  reading the table.
- **FACT (VERIFIED):** B30R048R round-trips byte-identically at the tile level
  under both interpreters. The three refused records and the 62 opaque records
  are kept verbatim by the writer, so the tile-level pass does not show that
  those records rebuild from the model. The L2 tile checks pass on all five
  tiles.
- **FACT (VERIFIED):** the refusal happens only in B30R048R among the four pinned
  tiles (controls: zero refusals).
- **FACT (VERIFIED):** the bounded rule rebuilds the three refused records
  byte-identically without the fallback. For the 2,955 parsed records of
  B30R048R, the parser's table length never exceeds `geo_len`
  (`cap would bite on parsed 0`), so capping at `geo_len` cannot change their
  table. This is a necessary condition checked on the parse output, not a
  rebuild of those 2,955 records under the bound.
- **OBSERVED:** the H14 `AssertionError((6, 29))` reproduces as text, but the
  verify run does not fail. Before this task the harness printed it as
  `background record (opaque)` with no record location and no invariant.
- **HYPOTHESIS:** the three records use a layer layout the model does not
  express (a table longer than the geometry region, with used entries after
  the region). The bounded reading is consistent with that, but whether the
  entries past the region are real layers, shared data or padding is not
  established. This is not decided here.
- **UNKNOWN:** whether the 62 opaque-by-design records (level 1–2 records with
  an extra section or unusual geometry offset) rebuild from the model if their
  sections are modelled; not tested.

## Conclusion

The B30R048R pin is trustworthy at the tile level. The rebuild assertion is
explained: three records whose layer table extends past the header's geometry
region. The harness now names them (dir, slot, k, the invariant) instead of
printing a bare tuple, and `bg_refused.py` shows the bounded reading that
rebuilds them. The L2 pin for B30R048R is re-set in this EXP with the values
above (tile SHA-256 `0916101547…5eb28`, golden digest `138f904f…6363`,
semantic features 16,684): both checks pass on the real bytes. The golden file
is unchanged because its digest already matches; `--update-golden` was not run. Not changed: the vendored parser `tools_ze0/clarion_bg.py`
(no edit, so no change to `ze0-tools.patch` or `PROVENANCE.md`), the verify
exit policy (refused records stay non-fatal, as designed), and the golden file.
Open: a parser that reads the bounded table would change the model for three
records of one tile; that is a follow-up task (see TODO.md M9.23), not this one.
