# EXP-2026-11-07-M1.10: naming the last 149 `Navi.exe` import slots

- **Status:** done
- **Date:** 2026-11-07
- **Sample:** `IMG256` (first 256 MiB of `LEAF_2011-2012_QSD-309-101_navi158_eu.img`),
  SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`
- **Claims:** C-2470–C-2476
- **Supersedes:** none
- **Superseded by:** none

## Question

`cerom.py imports Navi.exe --resolve-with 0x3e00200` leaves 149 of 846 import
slots as `#NNN`. Which modules export them, and do the exporters exist in any
image?

## Hypothesis

The unresolved slots are ordinal imports from `XGLDLL.dll` and `OSMDLL.dll`,
which are modules of **image A** (`0x200200`), not of image B. The resolver
was given only B, so it could not see them.

## Inputs

| Item | Value |
| --- | --- |
| Image | `IMG256` (above) |
| Importer | `Navi.exe`, image A (`0x200200`), 846 import slots |
| Exporters | `XGLDLL.dll` (219 exports), `OSMDLL.dll` (110 exports), both image A |
| Tool | `tools/cerom.py` (`imports`, `exports`, `sections`), no changes |

## Method

```bash
I=head256.img
# baseline: resolver = image B only
python3 tools/cerom.py $I imports Navi.exe --resolve-with 0x3e00200
# resolver = A, B and C
python3 tools/cerom.py $I imports Navi.exe \
    --resolve-with 0x200200 --resolve-with 0x3e00200 --resolve-with 0x5200200
# which modules exist in each image (scratch script, not committed)
#   for s in 0x200200 0x3e00200 0x5200200: list module names with cerom.CERom
# export RVAs against the executable sections (flags & 0x20)
python3 tools/cerom.py $I sections XGLDLL.dll
python3 tools/cerom.py $I sections OSMDLL.dll
python3 tools/cerom.py $I exports XGLDLL.dll
python3 tools/cerom.py $I exports OSMDLL.dll
```

## Observations

- Baseline (B only): `697/846 resolved, 149 unresolved`. The 149 are
  `XGLDLL.dll` (108 slots) and `OSMDLL.dll` (41 slots), printed as `#NNN` with
  `no export table for OSMDLL.dll` for the latter.
- Module census: `XGLDLL.dll` and `OSMDLL.dll` are in image A only. Image B
  (91 modules) and image C (88 modules) contain neither. Both images do contain
  `commondll.dll`, `Errlogdll.dll`, `ceddk.dll` and `SYS_INF.dll`, which the
  unresolved list did not need.
- Resolver = A + B + C: `846/846 resolved, 0 unresolved`.
- Diff against the baseline, slot by slot: 0 slots changed among the 697 that
  were already named; 0 duplicate slot addresses; the 149 newly named slots are
  exactly the previously `#NNN` ones (`XGLDLL!…` 108, `OSMDLL!…` 41).
- Newly named samples: `XGLDLL!xglDisable`, `XGLDLL!xglViewport`,
  `XGLDLL!xglOrtho`, `XGLDLL!xglGetFrameSize`, `OSMDLL!OSM_Printf`,
  `OSMDLL!OSM_MemFree`, `OSMDLL!taskLibGetIDfromName`.
- `XGLDLL.dll`: 218 of 219 exports point into executable sections. The one
  that does not is `6 g_hWnd` (RVA `0xd6ef0`, data), and `Navi.exe` does not
  import it. `OSMDLL.dll`: 110 of 110 exports point into executable sections.
- Ordinal ranges: `XGLDLL` 4–224, `OSMDLL` 1–114.

## Interpretation

- **VERIFIED:** the 149 slots are ordinal imports from `XGLDLL.dll` and
  `OSMDLL.dll`; both exporters are in image A, so the earlier "no exporter in
  any image" wording in the TODO was a resolver-scope issue, not a missing
  module. (C-2471)
- **VERIFIED:** every slot in `Navi.exe` now has a name; none is "no exporter
  in any image". (C-2470)
- **VERIFIED (positive control):** the 697 slots already resolved by name are
  unchanged when image A is added to the resolver, so the new resolver scope does
  not reassign existing names. (C-2473)
- **VERIFIED:** neither B nor C contains `XGLDLL.dll` or `OSMDLL.dll`. (C-2472)
- **OBSERVED:** the `XGLDLL` names are graphics-library calls (`xgl*`), and the
  `OSMDLL` names are the OSM runtime API (`OSM_*`, `taskLib*`); the names come from
  the export directories, not from our reading of the code. (C-2474, C-2475)
- **HYPOTHESIS:** the ordinal-to-name mapping in the export directory is correct.
  It is supported by the RVA checks above (the exports land in code) but not
  yet by a call site in `XGLDLL` that matches the name. A call-site check is
  left to the L3 work (M9). (C-2476)

## Conclusion

`Navi.exe` imports: 846/846 named. Use `--resolve-with 0x200200 --resolve-with
0x3e00200 --resolve-with 0x5200200` for any future import listing; the default
B-only resolver under-reports by 149. No `tools/` change was needed.
