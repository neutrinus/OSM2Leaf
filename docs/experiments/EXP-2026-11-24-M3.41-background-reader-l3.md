## Question

Which firmware function reads the odd-partner (background, water/forest) record
of a ZE0 level-1 map tile on the L3 mount/draw path available in this repo, and
what fields does it read in order? If none does, what path was tried and what is
the next unblocking task?

## Hypothesis

The odd background record has a reader reachable from the map-file layer, just
as the even road record is walked by `fn 0x0041f3dc` in `LOC_map` (M9.66). The
read-watch on a real odd record should attribute at least one guest read to a
function that is not the road-shape walk.

**Falsifier (set before the runs):** (a) the odd record is read by the same
`fn 0x0041f3dc` as the even record with a type switch — then there is no
separate reader; or (b) no guest read of the odd record occurs on the available
L3 path — then the Stop branch fires and the task is blocked on M8.H10 (the L4
read-watch), not done.

## Interpretation

- **FACT (run):** the only function that reads the seeded odd background record
  is the row-count helper `fn 0x00422384` (one 2-byte read at `+4`), which is
  the road-shape walk's prologue. The main walk `fn 0x0041f3dc` faults on the
  odd record's header before any polygon read; `fn 0x00421548` and
  `fn 0x004205b8` only load the message pointer at `+0x14`. No background-block
  reader (no function that walks the `w9/w10` layer table / `0001 0003` groups)
  is observed on the available L3 path.
- **FACT (run):** the L3 mount/draw chain serves only the even road record to
  the shape walk — the watched buffer differs from the odd record (`cmp`
  exit 1). A direct kind-4 request for the odd parcel's pair 33 also returns
  the even record (`0x9aeadb8`, road block at `w7/w8`). So the odd/background
  record is not placed in the watched buffer and cannot be observed by this
  path. This is the navigator's "method defect" avoided: the odd record *was*
  seeded and watched; it simply is not read.
- **FACT (control):** the watch credits a read when it occurs (selftest, and
  5,363 loads on the even record) and fails closed on the even record and on
  zeros (`guest-reads=0`). The negative is a real negative, not an inert watch.
- **OBSERVED (falsifier a):** no type switch inside `fn 0x0041f3dc` was found;
  the even/odd distinction is a slot/pair table selection made before the
  record is served. The falsifier "same function with a type switch" did not
  fire; there is also no separate reader on this path.
- **UNKNOWN:** whether an L4 read-watch (M8.H10) on the full system reaches a
  background renderer that consumes the odd record; the divided branch on a
  real divided record; the fill rule of the cell→node table (M9.67, blocked);
  US2011.

## Conclusion

M3.41's Stop branch fires: on the mount/draw path available at L3, nothing
reads the odd-partner background record as a polygon source. A real odd record
was named by its slot/pair, seeded into a read-watch, and only the road walk's
row-count prologue touched it; a kind-4 request for the odd parcel returns the
even record. There is no `l3check.py` target for a background reader to add,
so the recipe above is the L3 evidence and no `done` claim is made. The task is
**blocked**, with `Unblock: M8.H10` (the L4 read-watch, the next level that can
drive a real map draw and watch the odd record). Matrix row 17 notes the
negative; a separate reader of background polygons remains UNKNOWN. Rule 13 is
not satisfied for any background writer: no L3/L4 run has been shown to read
our background file.
