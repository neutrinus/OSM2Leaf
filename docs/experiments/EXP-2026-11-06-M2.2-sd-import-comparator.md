## Question

Which fields are compared by the `SD Import: … is different` comparator, against what, and with which checks? In particular: trace each compared field to a struct offset and a source (card vs system copy), and confirm or refute `0 < userdata_type < 6` **in this module**.

## Method

Task inputs: literal/pool slots at `0x004e8584` / `0x004e995c` (both hold pointer `0x001d5438` = `"SD Import: destination_id is different Sys[0x%x] SD[0x%x]\n"`, UTF-16LE) and the `Sys[0x%x]`/`SD[0x%x]` format family. ### 2. Compared fields, checks, and sources (both comparators)

Record base = `r8` (arg `r4`), the buffer filled by `sub_004df31c` (see §3). On any mismatch the comparator stores `*r9 = 0` and prints the message (Sys arg, SD arg) then takes the fail return path; on full pass it stores `*r9 = 1` (`0x004e856a`/`0x004e9942`: `mov #1,r3; mov r10,r2; mov.l r3,@r9`) and returns `r0 = 0` (epilogue `mov r2,r0`), with fail-path return `r0 = 0xff` (`0x004e8566`/`0x004e993e`: `mov #0xff,r2`).

| SD record field (base `r8`) | check (fn 0x004e84c4 VAs / fn 0x004e989c VAs) | SD source | Sys / reference source | evidence |
| --- | --- | --- | --- | --- |
| `+0x0c` u16 (word, `extu.w`) — **destination_id** | equality: `r8+0x0c` vs caller-ref `r15_comp+0x18` (`0x004e84f6/84f8/84fa..8502`; `0x004e98ce..98da`). mismatch → `*r9=0`, printf(Sys=`r15_comp+0x18`, SD=`r8+0x0c`) | `\UserSD\userdata\<file>` read by `sub_004df31c` into `r8` (§3) | comparator stack `r15_comp+0x18` (read `mov.w @(0x18,r15),r0`, encoding 0x85fc). Populated by the caller's frame context before the call; the exact producing struct/offset upstream of `fn 0x004e90c8`/`fn 0x004ea402` is **not resolved** in this module (C-738) | `0x004e8506/850c` loads `0x001d5438` "destination_id is different" |
| `+0x0e` u16 — **manufacturer_id** | equality: `r8+0x0e` vs caller-ref `r15_comp+0x1a` (`0x004e8514..8520`; `0x004e98ec..98f8`). mismatch prints Sys=`r15_comp+0x1a`, SD=`r8+0x0e` | same SD file/buffer | comparator stack `r15_comp+0x1a` (0x85fd); caller-frame source upstream, **not resolved** here (C-738) | `0x004e8524` → `0x001d53c0` "manufacturer_id is different" |
| `+0x12` u16 — **userdata_type** | **equality to a constant** (not a caller ref, not a range): loads `r2` from `mov.w @(0x27,pc),r2` at `0x004e852c` / `0x004e9904` (EA `0x004e857e` / `0x004e9956`, decoded from raw: const = `0x1010` / `0x1011`); `cmp/eq r2, extu.w(r8+0x12)` at `0x004e8530` / `0x004e9908`. mismatch → `*r9=0`, printf(Sys=`r2`=const, SD=`r8+0x12`) at `0x004e8536/853a` / `0x004e990e/9912` | same SD file/buffer | **constant in code/data**: `0x1010` for `fn 0x004e84c4` (storedlocation), `0x1011` for `fn 0x004e989c` (homelocation) — *not* read from a dynamic Sys HDD_INFO field in this comparator | `0x004e8538` → `0x001d5348` "userdata_type is different" |
| `+0x03` u8 — **finished** flag | `extu.b(r8+0x03); tst; bf` pass if nonzero (`0x004e853e..8544` / `0x004e9916..991c`). zero → `*r9=0`, print `"SD Import : finished not found. \n"` (`0x004e8546/8560` → `0x001d5300`) | same SD file/buffer | n/a (validity flag on the SD record) | nonzero required |
| `+0x02` u8 — **application type** | accept only if `r8+0x02` is one of `{1, 0x21, 0x31}` (`cmp/eq #1,#0x21,#0x31` at `0x004e854c..855c` / `0x004e9924..9934`; any match → pass with `*r9=1`). otherwise `*r9=0`, print `"SD Import : application type not correct. \n"` (`0x004e855e/8560` → `0x001d52a8`) | same SD file/buffer | n/a (value-set check on the SD record) | exact allowed set `{0x01,0x21,0x31}` |

**`0 < userdata_type < 6` in this module:** refuted. In `fn 0x004e84c4` and `fn 0x004e989c` (the Navi.exe functions that emit the task's `SD Import: userdata_type is different Sys[0x%x] SD[0x%x]` message) `r8+0x12` is tested by `cmp/eq` against the constants `0x1010`/`0x1011` only; no range comparison (`cmp/gt`/`cmp/hi`/bounds) `0 < x < 6` on `r8+0x12` appears. The only range/value-set checks in these comparators are `r8+0x03 != 0` and `r8+0x02 ∈ {1,0x21,0x31}` (not `1..5`).

### 3. SD record reader and file sources (card/UserSD)

`sub_004df31c` (`0x004df31c`, file `0x0115d51c`; calls `memset`, `strlen`, `mbstowcs`, `CreateFileW`, `ReadFile`, `CloseHandle`, `NKDbgPrintfW`) takes `(r4, r5 = narrow path, r6 = dest buffer)`, converts the path to wide, opens it with `CreateFileW`, and `ReadFile`s **0x100 bytes** (`mov #0x40,r6; shll2 r6` → 256 at `0x004df384/8c/8e`) into `r6`/dest. It is called to fill the comparator's `r8` record:

| comparator | caller `fn` (no literal-pool holder; reached internally) | call site | `sub_004df31c` dest `r6` = comparator `r4/r8` | path built (`sprintf` format `\UserSD\%s\%s` @ `0x001cf504`, ASCII) | file read (SD/UserSD) |
| --- | --- | --- | --- | --- | --- |
| `sub_004e84c4` | `0x004e90c8` | `0x004e91dc` (df31c), `0x004e91e6` (comparator, `r4=r11`, `r5=&r15_caller+0x20` status) | `r11 = r14+8` (0x004e91c8/cc) | pool `r11`=`"userdata"` `0x19a2bc`, `r9`=`"storedlocation.slc"` `0x19a294` | `\UserSD\userdata\storedlocation.slc` |
| `sub_004e989c` | `0x004ea402` | `0x004ea4f8` (df31c), `0x004ea502` (comparator, `r4=r10`, `r5=&r15_caller+0x28` status) | `r10 = r15+0x12c` (0x004ea4e4/4e8/4ea) | pool `r10`=`"userdata"` `0x19a2bc`, `r9`=`"homelocation.hlc"` `0x19a2a8` | `\UserSD\userdata\homelocation.hlc` |

Both callers: `sub_004de624` (attribute/existence check; builds its own path and uses `GetFileAttributesW`) → build `\UserSD\%s\%s` path → `mbstowcs` → `sub_004df31c(0, path, dest)` reads the UserSD file into dest → `comparator(dest, &status)` → proceed (CreateFileW/ReadFile/...) only if status set. `sub_004de624` is called with `(0, r11, r9, &status)` and does not supply the destination_id/manufacturer_id reference words; those reach the comparator via the caller's stack frame (C-738).

## Interpretation

The Navi.exe `SD Import` validators are `sub_004e84c4` (stored location) and `sub_004e989c` (home location), invoked from `fn 0x004e90c8`/`fn 0x004ea402` during the SD/UserSD import flow. Each reads a 256-byte record from a `\UserSD\userdata\*.{slc,hlc}` file (`sub_004df31c`) and validates it by printing the exact `SD Import: <field> is different Sys[0x%x] SD[0x%x]` / flag messages (task literals `0x004e8584`/`0x004e995c` resolve here).

**Field → offset → source (done-when):**
- `destination_id` = SD record `r8+0x0c` (u16) vs **Sys ref** at comparator `r15+0x18` (caller-frame, producer upstream/unresolved here).
- `manufacturer_id` = SD record `r8+0x0e` (u16) vs **Sys ref** at comparator `r15+0x1a` (caller-frame, upstream/unresolved).
- `userdata_type` = SD record `r8+0x12` (u16) vs **constant** `0x1010` (`0x004e84c4`) / `0x1011` (`0x004e989c`) — no dynamic Sys field in this comparator.
- `finished` = `r8+0x03` (u8, must be nonzero); `application type` = `r8+0x02` (u8, must be in `{1,0x21,0x31}`) — SD-record validity checks.
- **SD source (card/UserSD):** `\UserSD\userdata\storedlocation.slc` or `\UserSD\userdata\homelocation.hlc`, 0x100 bytes read by `sub_004df31c`.

**`0 < userdata_type < 6`: refuted in this module.** The check on `userdata_type` (`r8+0x12`) is `cmp/eq` to `0x1010`/`0x1011`; there is no `0 < x < 6` range test. `r8+0x02`'s accepted set `{1,0x21,0x31}` is also not a `1..5` range. (Note: `tools/hddinfo.py` model M0 and older C-301 text describe a `userdata_type` range `0..5` for the `HDD_INFO.TXT` line-1/family field — a *different* field/source than this SD location-record word at `r8+0x12`; C-521/C-611 already separate the real Navi.exe `SD Import` messages from the retired BT_MGR comparator chain.)

## Open questions

- C-738: the exact producer (function/struct/offset) of the Sys reference words consumed at comparator `r15_comp+0x18`/`+0x1a` (destination_id/manufacturer_id) — upstream of `fn 0x004e90c8`/`0x004ea402`; not written in these functions. Resolve by tracing callers of `0x004e90c8`/`0x004ea402` and the frame slots that alias `r15_comp+0x18/1a`.
- C-739: the on-disk/binary layout of `storedlocation.slc` / `homelocation.hlc` beyond the validated offsets (`+0x02,+0x03,+0x0c,+0x0e,+0x12` within 0x100 bytes) and the meaning of constants `0x1010`/`0x1011` and application-type codes `{1,0x21,0x31}`.
- `sub_004df31c`'s third caller `fn 0x004ddee4` (pool `0x004ddfb0`) not traced here; may read a related record.
- Relationship to any range-based `userdata_type` check elsewhere in `Navi.exe`/the updater (different module/path than these two comparators) remains open; M2.2's refutation is scoped to this module.
