## Question

Which drivers does the ROM registry of build B load, with which `IoBase`/
`Irq` (or other resources), and in what order? This is the M8.E2 driver
table for `docs/format/firmware.md`.

## Hypothesis

`default.hv` holds the CE device-manager keys (`Drivers\BuiltIn`, loaded by
`BusEnum.dll` in `Order`) with the usual `IoBase`/`Irq` values, and
`boot.hv` the boot-phase drivers. Falsifier: a hive that does not parse
closed (dangling links), a driver key with no `Dll`/`Entry`, or a launch
table whose entries do not match the hive keys.

## Method

1. **Sample and hash.** As above. Nothing is written to disk except the
   tool's optional `--json` (names and numbers only) under
   `/home/user/scratch/m1.4/` (deleted after the run).
2. **Commands.**

   ```bash
   S=/home/user/scratch/m1.4
   python3 tools/ce_drivers.py --selftest
   python3 tools/ce_drivers.py archive/head256.img --image-start 0x3e00200 --json $S/m8e2-B.json
   python3 tools/ce_drivers.py archive/head256.img --image-start 0x3e00200 --markdown
   python3 tools/ce_drivers.py archive/head256.img --image-start 0x5200200 --json $S/m8e2-C.json
   python3 tools/ce_drivers.py archive/us256.img --image-start 0x3e00200 --json $S/m8e2-USB.json
   python3 tools/sh4literal.py --image-start 0x3e00200 archive/head256.img AppLaunch.dll bytes 44007200690076006500720073005c004c00610075006e0063006800
   ```

   `ce_drivers.py` decodes the two hives through `cerom.files_report`
   (kernel routine, `r0 == rsize`), parses them with `cehive.tree`, lists
   the direct subkeys of `Drivers\BuiltIn` and `Drivers\Launch` with
   `Dll`, `Prefix`+`Index`, `Order`, `Flags`, `IoBase`, `IoLen`, `MemBase`,
   `MemLen`, `Irq`, `SysIntr`, sorts each root by `Order` (stable), prints
   `init` `LaunchNN`/`DependNN` and `Drivers\Resources`, and joins each
   `Drivers\Launch` key to its `AppLaunch.dll` record through M1.34's
   `applaunch_table` (getter pair → table base and count → records; index,
   device name, own id, wait ids). As a cross-check it also finds the
   records structurally: the UTF-16 string `\Drivers\Launch\` (the hex in
   the last command) repeated at one stride; the tool exits if the two key
   lists differ.
3. **Controls.** Positive: both hives parse closed (`dangling 0`, every key
   reached), and the hive SHA-256s equal M1.21's. The stride parser
   finds 3/3 entries in a synthetic table in `--selftest`; on the real image
   the M1.34 getter parse must give the same 63 keys (the tool exits
   otherwise). Negative:
   `--selftest` breaks a hive link (must count as dangling) and gives a
   blob with no `\Drivers\Launch\` (must yield no table). Cross-check: the
   independently compiled table and the hive keys must agree (62 of 63 keys
   do).
4. **Scope.** The ROM hives `boot.hv`, `default.hv` of build B (EU2011,
   US2011) and build C (EU2011): 2 roots, 72 driver keys per build. Not
   covered: `user.hv` (HKCU, no drivers); keys deeper than one level under
   the roots (`Drivers\PCCARD\…` templates, `Drivers\USB\…` client keys);
   the runtime `system.hv` written after first boot; the code that walks the
   `AppLaunch.dll` table.
5. **Falsifier.** As stated under Hypothesis, before the result.

## Observations

Build B, EU2011 (`--image-start 0x3e00200`):

- `boot.hv` 32,768 B, SHA-256 `3636dfd3…`, keys 16, values 61, dangling 0;
  `default.hv` 126,976 B, SHA-256 `65322773…`, keys 516, values 1,149,
  dangling 0.
- `init`: `Launch20=device.exe`, `Launch30=gwes.exe`, `Depend30` = `14 00`.
- `boot.hv` `Drivers\BuiltIn` has no subkey (only the bus values `Dll
  BusEnum.dll`, `Flags 0x8`, `BusIoctl 0x2a0048`).
- `default.hv` `Drivers\BuiltIn`: 9 drivers, all `Order 0`: `notify`,
  `DResUsage`, `Battery`, `ErrHandServ`, `ACM`, `PowerMonitor`,
  `LogDriver`, `Flash`, `AppLch` (`AppLaunch.dll`, `LDR1`).
- `default.hv` `Drivers\Launch`: 63 keys; `Order` histogram `0:12, 1:11,
  2:4, 3:1, 5:3, 8:1, 9:23, 10:3, 256:1, none:4`.
- Resources on driver keys: `OHCI` `MemBase=0x099a1000 SysIntr=0x1c`
  (`Order 2`, table 32), `WaveSSI1` `SysIntr=0x24` (table 35), `WaveSSI2`
  `SysIntr=0x25` (table 36). 0 driver keys carry `IoBase` or `Irq`.
- `Drivers\Resources\IRQ`: `Minimum 0x10`, `Space 0x18`, `Ranges
  19-21,25,36-39`, `Shared 36-39`; `Drivers\Resources\ID`: `Ranges
  0-0x3FFFF` (same in `boot.hv`).
- `AppLaunch.dll` (sec0 `0x03bb1000`): `\Drivers\Launch\` occurs 63 times,
  all at stride `0x310`, and the same 63 keys are M1.34's records #7–#69 of
  the 112-record table at `0x03bb2330` (#7 `gdisubdrv.dll`/`GDISUB`, #8
  `GPI1:`/`GPIO`, #9 `SCI0:` id `0x5`, #33 `NAV1:`/`Navigation` id `0x14`
  waits 11/15, #34 `SDC1:`/`SD` id `0x2` waits 1, …, #69 `PPP`). 62 of 63
  hive keys have a record; `WAPIMAN` has two (#40, #41); `I2C_1` has none.
  `sh4literal bytes` finds 0 pool pointers, 0 `mova` and 0 data words equal
  to any of the 63 string addresses (the walker reaches records by base +
  index, M1.34).

Build C, EU2011 (`0x5200200`): `boot.hv` `109f7c7d…`, `default.hv`
106,496 B `d751e5d9…`, keys 372, dangling 0; the same 9 + 63 driver keys
with the same `Dll`/`Order`; the launch table has 62 entries (stride
`0x310`), `UART3` is missing from it, so `UART3` and `I2C_1` have no record.

Build B, US2011 (`us256.img`, `0x3e00200`): every printed row equals the
EU2011 build-B output (`diff` empty).

`--selftest`: 11 checks PASS.

## Interpretation

- **FACT:** the ROM registry names 72 driver keys per build: 9 under
  `Drivers\BuiltIn` (device manager bus) and 63 under `Drivers\Launch`.
  `Drivers\Launch` is not a CE bus; its keys are named by 63 records of
  the `AppLaunch.dll` launch table (M1.34), and `AppLaunch.dll` is itself
  the last BuiltIn driver.
- **FACT:** the registry carries almost no hardware resources: one
  `MemBase` and three `SysIntr` values, no `IoBase`/`Irq` on any loaded
  driver. Addresses and IRQs of the other drivers are compiled into the
  DLLs (or come from the IRQ resource range `19-21,25,36-39`).
- **FACT (with M1.34):** the walker `fn 0x03bcc5b0` visits records in index
  order and each record's thread waits on its wait ids, so the load order
  of `Drivers\Launch` is record index plus waits (#7 `GDISUB` first). The
  hive `Order` value is not what orders them.
- **UNKNOWN:** whether `ActivateDevice` inside the record thread reads the
  key's `Order` at all (it is a standard device-manager value).
- **UNKNOWN:** whether the runtime system hive changes any row.

## Conclusion

The driver table is in `docs/format/firmware.md` ("Registry driver table,
as loaded from the ROM hives"), generated by `tools/ce_drivers.py`
(C-1610–C-1616). The M8.E2 Done-when (driver table in `firmware.md`) holds
on the static route; the RAM-dump route (M8.B5 QEMU) is not needed for it
and would only add the runtime hive.
