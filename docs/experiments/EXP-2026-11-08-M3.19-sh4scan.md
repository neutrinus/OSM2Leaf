## Question

Do the committed scans in `tools/sh4scan.py` reproduce the counts that M3.11,
M3.13 and M3.2b published for build A, so that those negatives can be re-run
rather than trusted as prose?

## Hypothesis

All eight published counts reproduce with the pattern definitions written in
the tool's docstring. **Falsifier, fixed before the run:** any count that
differs from the list in the Scope section, under the stated definition, means
the published number (or its pattern text) is wrong. The tool is not changed to
make the count match.

## Method

1. **Sample and hash.** `archive/head256.img`, bytes `0x0`–`0x0fffffff`
   (256 MiB, whole file), SHA-256 above. The tool prints the hash of the bytes
   it read; it must print `92aa525d…`.
2. **Commands.** Run from the repository root:

```bash
IMG=/home/marek/projekty/OSM2Leaf/archive/head256.img
python3 tools/cerom.py --image-start 0x200200 $IMG romhdr
python3 tools/cerom.py --image-start 0x200200 $IMG memmap --out archive/memmap-head256.json
python3 tools/sh4scan.py --selftest
python3 tools/sh4scan.py $IMG --image-start 0x200200 corpus
python3 tools/sh4scan.py $IMG --image-start 0x200200 tags --module Navi.exe
python3 tools/sh4scan.py $IMG --image-start 0x200200 tags
python3 tools/sh4scan.py $IMG --image-start 0x200200 pattern 8868 --module Navi.exe
python3 tools/sh4scan.py $IMG --image-start 0x200200 mask-pair --and 70 --cmp 60
python3 tools/sh4scan.py $IMG --image-start 0x200200 mask-pair --and f7 --cmp 60
python3 tools/sh4scan.py $IMG --image-start 0x200200 stride
python3 tools/sh4scan.py $IMG --image-start 0x200200 anchors
python3 tools/sh4scan.py $IMG --image-start 0x200200 dump --module Navi.exe --va 0x3715c0 --count 8
python3 tools/sh4scan.py /home/marek/projekty/OSM2Leaf/archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img --image-start 0x200200 tags --module Navi.exe
```

   Pattern definitions (LE halfwords, even addresses only, in
   `tools/sh4scan.py`): `cmp/eq #ii,R0` = `0x88ii`; `and #ii,R0` = `0xC9ii`;
   `mov.b @(1,Rm),R0` = `0x84m1` (mask `0xFF0F == 0x8401`); `shll R0` = `0x4000`;
   `add R0,R0` = `0x300C`; `add R0,Rn` = `0x300C | n<<8`. Tag pair = two distinct
   tags within 24 B. Mask pair = `and #imm,R0` followed by `cmp/eq #tag,R0`
   within 14 B. Stride = `mov.b` site, then a doubling within 8 halfwords, then
   `add R0,Rm` within 8 halfwords. Zlib anchors = the three marker families of
   the M3.2b table (see Interpretation for the fourth).

3. **Controls.**
   - *Positive, pattern:* `pattern 8868 --module Navi.exe` must equal the
     published `cmp/eq #0x68` count (23); the count and the hit `0x37c268`
     (named in M3.11 §2) are both checked.
   - *Positive, anchors:* each marker family must find its published hits in
     the modules the M3.2b table names (3 + 6 + 5 = 14).
   - *Positive, funnel:* the stride scan's first stage must be non-empty
     (3,179 sites) before its last stage is read as 0.
   - *Positive, real bytes for the mask pair:* none is available for the
     committed definition; see Observations §5, where the published site is
     read with `dump`.
   - *Negative, synthetic (`--selftest`):* big-endian reading of `88 60` must
     not match `0x8860`; a tag at an odd byte must not match; a tag pair at 28 B
     must not count at a 24 B window; a mask at 16 B must not count at 14 B;
     `add R0,R5` must not satisfy the cursor advance for `R3`; a stride without
     doubling must stop at stage 1; `mov.b @(2,R3)` must not match.
   - *Second sample (control):* the same `tags` scan on the full EU card
     (`archive/sd-images/…eu.img`) must give the same counts, and its first
     256 MiB must hash to the same SHA-256.

4. **Scope.** Build A only (`--image-start 0x200200`), 149 modules, 527 o32
   sections, read from the 256 MiB head. The corpus, as printed by `corpus`:
   282 uncompressed sections (23,559,542 B psize; 23,513,170 B vsize) scanned;
   245 compressed sections (607,121 B psize; 30,212,810 B vsize) listed, not
   decoded, not scanned (M1.2f / M8.E1 open). The compressed share is 56.24 %
   of vsize (2.51 % of psize). A "0" below means zero matches in these 282
   sections, not in the image.
   Not run here: builds B and C (`0x3e00200`, `0x5200200`), and the 2014/2016
   images.

5. **Falsifier.** Stated in the Hypothesis section above: any mismatch between a
   published count and the output of the commands in §2 under the definitions
   in §2 refutes that count as published. Recorded before the run.

## Interpretation

**Reproduced (7 of the 8 counts that M3.11, M3.13 and M3.2b published as
precheck numbers):** 527 o32 sections; 282 uncompressed sections with
23,559,542 B psize; 245 compressed; 26 aligned `cmp/eq #0x60` and 23 `cmp/eq
#0x68` in Navi.exe sec0; 0 tag pairs within 24 B; 0 stride candidates at the
third stage; 14 zlib anchor hits in the M3.2b table families. The Navi.exe
compressed share (75.13 % of vsize) matches the value AGENTS.md gives.

**Not reproduced: the M3.11 mask count.** The record reports `and #0x70,r0`
followed by `cmp/eq #0x60` as 1 hit in all of build A, at `fn 0x003715a0`. The
committed definition (`and #imm,R0` = `0xC9ii`) finds 0. The one site in the
corpus that has this shape, at `0x3715c8–0x3715cc`, is `mov #0x70,R3`, then
`and R3,R0` (a register AND), then `cmp/eq #0x60,R0`. So the record's pattern
text is wrong for the site it names, and an immediate `and` cannot match it.
Counting the register form would be a new definition chosen after seeing this
result, and the stop rule for this task forbids that. The tool is unchanged.
The next step is a named variant and a corrected M3.11 claim, not a re-count
here (see M3.20).

**Zlib anchors: 14 depends on which marker set is named.** M3.2b's Inputs list
`invalid block type` as an anchor, but its table has no row for it. The table's
14 hits come from the three other families. Adding `invalid block type` gives 3
more (17 in total, in auirtdll.dll, IconDrawCC.dll and TelemaImageDrawCC.dll).
The tool reports the table families and prints the extra family on its own line.
The published "14" is reproduced only under the table's definition.

**Not checked here.** M3.13's second funnel count (`mov.b @(1,Rm),R0` plus
`shll R0`, 5 hits) is not in this task's precheck, and its window was never
stated. The tool's stride funnel gives 3,179 sites at stage 1 and 7 at stage 2
with `add R0,R0` also counted as doubling, so the 5 is not checked and is not
claimed.

**Scope of the zeros.** Every 0 here is a zero within the 282 uncompressed
sections. Navi.exe sec1 (16.7 MB vsize) is compressed and was not searched, so
these zeros say nothing about the compressed 56.24 % of build A.

## Claims (C-2530–C-2539)

Listed in `docs/research/claims.md` under "M3.19 — sh4scan".

- C-2530 — build A on IMG256: 527 o32 sections, 282 uncompressed (23,559,542 B psize), 245 compressed (30,212,810 B vsize; 56.24 %).
- C-2531 — Navi.exe sec0 aligned `cmp/eq #0x60,R0` 26, `cmp/eq #0x68,R0` 23; tag pairs within 24 B 0.

- C-2533 — stride funnel over the 282 uncompressed sections: 3,179 `mov.b @(1,Rm),R0`, 7 with doubling within 8 halfwords, 0 with a cursor advance to Rm.
- C-2534 — zlib markers of the M3.2b table families in build A: 3 + 6 + 5 = 14. `invalid block type` adds 3 more; the record's Inputs and table disagree on the marker set.
- C-2535 — the `sh4scan` self-test pins LE reading, the even-address rule, the 24 B and 14 B windows, the stride stages and the zlib families on synthetic halfwords.
- C-2536 — the first 256 MiB of the full EU card hashes to `92aa525d…`, the same as `archive/head256.img`; the `tags` counts on the full card equal those on the head.
- C-2537 — `pattern 8868 --module Navi.exe` = 23 and includes `0x37c268`, the hit M3.11 §2 names.
