# EXP-2026-11-22-M5.74-osm-background-writer: water, river and forest from OSM into one tile

- **Status:** done
- **Date:** 2026-11-22
- **Sample:** factory `MAPAL001/B48R058R.DAT` `e9c9cb2236f6b53ad4fe9687a18a351afe80a46a63c0a1f18dc46d6c8af3ff52`; built tile `5f65eaca49d6948277cdd98957bbfe4de12be52007f506be661861d5f874eacd`; OSM extract `5d72b72906cb0fda1bd13a5e5c4baed3c25a9c460d9dbefb8773d155aa848553`
- **Tools:** Python 3.15.0 (stdlib only); `tools/bg_writer.py` (new, `--selftest`); `tools/tilewriter.py --background` (new flag); `tools/ze0-viewer/harness.py`; `tools/cardcheck.py`, `tools/rebuild_manifests.py`, `tools/l2check.py`, `tools/datask_l3.py`, `tools/selftest.py`. Recompression uses stock zlib level 6 / wbits 15 through `tilewriter.compress` (no new zlib claim).
- **Claims:** C-7930–C-7937
- **Supersedes:** none (M4.70 closed the KIWI-layer alternative; this record uses its ZE0 grammar)
- **Superseded by:** none

## Question

Can OSM water, river and forest geometry be written into an odd-partner background record of a real ZE0 level-1 tile so that (a) the written geometry decodes back with the same shape counts and vertices, (b) L1/L2 structural gates pass, and (c) the firmware's data-access task mounts the changed tile exactly like the factory tile?

## Hypothesis

The ZE0 background grammar recorded by M4.70 (26 two-word layer pairs, `0001 0003` groups, `count/type/ref/x0/y0` plus `int8` deltas) is sufficient to encode clipped OSM polygons; the container can be spliced like the road writer's. **Falsifier:** the readback shape/vertex check fails, or L1/L2 fail, or the L3 mount verdict differs from the factory run (status error, missing read, `DIFFERENT`).

## Method

1. **Sample and hash.** One EU2011 factory tile, one small live OSM XML extract (URL, date and SHA-256 above; kept outside the repo), and one generated tile. All hashes printed by the commands below.
2. **Commands.** Runnable as written from the repository root (`S` is the scratch directory):

   ```bash
   S=/home/marek/projekty/leafre-work/scratch/m5.74
   curl -sS 'https://api.openstreetmap.org/api/0.6/map?bbox=16.46,50.96,16.56,51.02' -o $S/osm.xml
   sha256sum $S/osm.xml
   python3 tools/bg_writer.py --selftest
   python3 tools/tilewriter.py --selftest
   python3 tools/tilewriter.py --background $S/osm.xml \
     --factory /home/marek/projekty/leafre-work/m5.29-factory-root/MAPAL001/B48R058R.DAT \
     --cell B48R058R --out $S/B48R058R-bg.DAT
   sha256sum $S/B48R058R-bg.DAT
   cp -al /home/marek/projekty/leafre-work/m5.29-factory-root $S/root
   rm $S/root/MAPAL001/B48R058R.DAT
   cp $S/B48R058R-bg.DAT $S/root/MAPAL001/B48R058R.DAT
   python3 tools/rebuild_manifests.py --root $S/root
   python3 tools/cardcheck.py --root $S/root --fast
   python3 tools/l2check.py --root $S/root --no-golden --tiles B48R058R.DAT \
     --semantic-tiles B48R058R.DAT --cmp-limit 20
   (cd tools/ze0-viewer && python3 harness.py verify $S/B48R058R-bg.DAT)
   python3 tools/datask_l3.py mount archive/head256.img \
     --card-root /home/marek/projekty/leafre-work/m5.29-factory-root \
     --position 50.96875,16.515625 --json $S/l3-factory.json
   python3 tools/datask_l3.py mount archive/head256.img --card-root $S/root \
     --position 50.96875,16.515625 --json $S/l3-bg.json
   python3 tools/datask_l3.py diff $S/l3-factory.json $S/l3-bg.json \
     --file MAPAL001/B48R058R.DAT
   ```
3. **Controls.** *Positive:* `bg_writer --selftest` builds a ZE0 record from synthetic water geometry and parses it back (26 layers, type `0xc015`); `tilewriter --selftest` is unchanged (89/89) and the `--background` path returns `roundtrip OK` with the exact same output bytes as the direct `bg_writer` call. *Negative:* a parcel with fewer than two feature kinds is refused (`ValueError`, exit 1 through `tilewriter`); the L3 `diff` compares against a factory run at the same position, so a firmware rejection or a changed read would show as `DIFFERENT`. *ZE0-side control:* `harness.py verify` on the built tile reports the same `records ok 203147 bad 84 | background rebuild ok 48152 bad 0 | graph parse ok 73416 bad 0 | roundtrip OK` as the factory tile (both exit 1 for the same pre-existing `bad 84` road records).
4. **Scope.** One level-1 tile (`B48R058R`), one parcel, three OSM feature classes (water polygon, river line, forest polygon), one small bbox on this host. Clipping is Sutherland–Hodgman for rings and `tilewriter.parcel_runs` for lines; simplification uses `slot_budget.dp_simplify` at the M5.75 level-1 default of 3 m; coordinates are quantised to 0..2047 and `clarion_bg.build_shapes` densifies steps above 127 units. Excluded: level 2, `LEV3456R`, section 2/4, `REFER001`, routing, names, styles/colours, US cards and any car test. No vendor bytes were committed.
5. **Falsifier.** Any mismatch between expected and decoded shape counts/vertices, an L1/L2 failure, or an L3 `DIFFERENT` verdict would have invalidated the writer.

## Interpretation

- **FACT (tool):** one odd background record now carries all three OSM-derived classes. The decoder sees exactly the shapes written: 24 forest rings, 2 water rings, 1 open river line; the 509/17/47 vertices include the deterministic `int8` densification both writer and reader apply. This is the M5.74 "count and vertex check".
- **OBSERVED (container):** the new record (1,528 B inflated, 1,314 B compressed) did not fit its old slot block, so the writer appended a new block at the next 256-byte boundary and repointed slot 14; the tile grew 54,566 B and `DRSTR001.DAT` was rebuilt. All other sections stay byte-identical (`verify_factory` inside `tilewriter` and `cardcheck` agree).
- **FACT (L1/L2):** both gates pass. `tile_semantic` rises from the factory's 2,333,602 features to 2,333,623 (+21), consistent with the 27 written shapes replacing the parcel's previous background shapes (the digest counts all decoded features, not just this parcel).
- **FACT (firmware fragment):** the L3 mount at the parcel's centre has the same 28 reads, 18 parsed tile reads and the same 9 compared rows as the factory run — `SAME (0 differences)`. That is the task's "reads it like the factory tile" check; it is **not** a rendering or L4 acceptance (rule 13).
- **UNKNOWN:** no visual check was made, no real car; the `bad 84` road records in `harness verify` are a factory baseline shared by both files, not introduced here. Only one parcel of one tile is written; the rest of Poland is untouched.

## Conclusion

M5.74's Done-when is met: `python3 tools/tilewriter.py --background` writes a tile whose background record decodes to the same OSM polygons (count + vertices), L1/L2 pass, and the L3 data-access mount equals the factory run. The work is a first slice: one parcel, three classes, no styling, no routing/names. Factory bytes and OSM data stayed outside the repo; the only committed inputs are tools, this EXP and claim rows.

## Follow-ups

- M5.74 does not touch level 2, `LEV3456R`, section 4 or routing; a whole-region background writer needs a parcel loop and a slot-budget check per parcel (M5.75 defaults are imported here).
- No visual gate: M5.66 (render a generated tile to PNG) is the natural acceptance test for these polygons.
- The OSM API bbox is small and reproducible; a Poland-scale run should use the local PBF extract with a background-aware IMF schema (v1 drops `landuse`/`natural`/`waterway`, see `intermediate-format.md`).
