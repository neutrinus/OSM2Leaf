## Question

M8.C1i left a hypothesis (C-8238): the first form after `frm_PRCOM_StartUp`
waits for SystemCC's `SYS_REQ_ACTIVATE` to the `MSG_PROCESS_OFF` source
(Audio.exe), which is never answered while the audio microcontroller is
silent. If Audio.exe answers, does a form follow?

## Hypothesis

C-8238 holds: once Audio.exe answers, SystemCC raises a `NotifySysEvent`
and the skin shows the next form. Falsifier from the task: the answer is
injected and logged by SystemCC, but control creation (fn `0x037dffdc`) and
invalidation (fn `0x037def48`) stay silent.

## Method

1. **Static.**
   - `sh4xref.py --to 0x81120011/0x81120012` found the literals in
     SystemCC, Audio.exe, SystemEXE, Usb.exe and PhoneBTA.exe.
   - `sh4dis.py` read SystemCC's IPC dispatcher and Audio.exe's handler.
   - It also read the launcher that prints `Create Thread[%d] Wait Modules
     Error LaunchId=[%d] Wait Modules ID=[%d]`. The function was found
     through its format string at `0x00011c40`.
2. **Patch.** `ze0_aui.py --skip-module-wait audio.exe` finds the
   WaitModule call in the launcher by its byte pattern, so the patch does
   not depend on a hard-coded VA. It then turns the error branch at site
   `0x00026934` (`bra` to the error log) into a branch to the next loop
   step. The 30 s wait stays as it is. Only the failure no longer stops the
   thread from being created.
3. **Runs.** All runs use the M8.C1k configuration (`--copy-dlls
   unitflash`, `--no-aui-timeout`) and the M8.C1i command line, plus `-gdb
   tcp::1240 -S`. A step-over client sets breakpoints before the first
   instruction.

   | run | Audio.exe patch | breakpoints | watched |
   | --- | --- | --- | --- |
   | J1 | no | dispatcher fn `0x02a819d0` | about 7 min |
   | J2 | yes | dispatcher | 6 min, then late re-attach |
   | J3 | yes | dispatcher, `0x02a81a32` (after vtbl+0x340), `0x02a81b1e` (event post), Fire_NotifySysEvent fn `0x02a7ece8`, fn `0x02a7f3d0`, fn `0x037def48`, fn `0x037dffdc`, AuiMonitoringCC init fn `0x02a381e4` | 21 min |

## Observations

**O1 — SystemCC's dispatcher.** Fn `0x02a819d0` compares `r7` with a
list of message ids. For `0x81120012` it does the following:

1. It calls vtbl+0x340 of `[this+12]` with the sender and stops unless
   that returns 1.
2. It calls its own vtbl+0x3f0.
3. It reads the source kind (`[this+12]` vtbl+0x360) and its own state
   (vtbl+0x2c0).
4. It posts `0x1a44` or `0x1a5a` with vtbl+0x3d0. When the state is not 2,
   `[this+68]` decides, together with the sender `0x8200000a`/`0x8200000b`.

**O2 — Audio.exe.** Its handler fn `0x00026fc0` takes `0x81120011`, calls
vtbl+0x308 and sends `0x81120012` straight back through vtbl+0x310. The
launcher fn `0x000268b8` loops over 16-byte wait records per thread. For
each record it calls WaitModule (vtbl+0x1a4) with timeout `+0x7530`. If
that returns 0, the launcher logs the error and returns 0, so the thread is
never created. Usb.exe holds the same byte sequence (site `0x00023d96`
region).

**O3 — The answer arrives with the patch.**

- J1/J4 (no patch): the dispatcher sees only `0x81140055` (from
  `0x81000001`). SystemCC fires one event, `NotifySdStatusChange` (`0x1a59`).
- J2/J3 (patch): the serial log has
  `IPC Send::[MSG_PROCESS_OFF] -> [MSG_PROCESS_SYSTEM]
  MsgId[SYS_NOTIFY_ACTIVATE_COMPLETE]`.
- J3: the dispatcher receives `r7=0x81120012` from `r5=0x8200000c`, and
  vtbl+0x340 returns 1 (`0x02a81a32`). It posts `0x1a5a`. Fn `0x02a7f3d0`
  maps that to `NotifySourceChange` (`0x02a71a40`), and Fire_NotifySysEvent
  (fn `0x02a7ece8`) runs with that name.

**O4 — Nothing follows (J3).** After `NotifySourceChange` (J3 at about
29 s of client time) no breakpoint is hit for the remaining 20 minutes:

- no control creation and no invalidation;
- AuiMonitoringCC's init never runs.

The screenshot is the London map alone. The 2DG trace has the same 10
display lists as M8.C1k K1 and M8.C1i H10. The failed-control count stays
at 6.

**O5 — Controls are created early (J3 and J4).** In both runs,
`0x037dffdc` is hit 18 times and `0x037def48` 7 times in the first ~20 s
of client time. That is before any SystemCC IPC, and it happens whether or
not Audio.exe is patched. C-8233 (M8.C1i, run H10, stub DLLs) says no
control is instantiated. The two configurations differ: stubs versus the
real NK1 modules. When H10's breakpoints were set has not been re-checked,
so C-8233 is narrowed to H10 rather than retracted.

## Interpretation

- The audio-source activation is not the paint gate. Once Audio.exe answers,
  SystemCC does exactly what its code says (`NotifySourceChange` to the
  skin), and the skin does nothing visible with it. C-8238 is retracted.
- The controls of `frm_PRCOM_StartUp` exist, at least with the real NK1
  modules. What is missing is the transition to the next form. On the real
  unit the next screens are the opening and the caution screen
  (`frm_PRAGR_AgreeCaution` in `ReleaseMain.skn`). The skin's start
  sequence most likely waits for an input that SystemCC/SystemEXE get from
  the vehicle side (ACC/ignition over the micom or CAN). It could also wait
  for an action variable (`var_PRCOM_SystemInitFlg`, `act_PRCOM_SystemInit`)
  set by a control that fails. Both are hypotheses.

## Conclusion

`ze0_aui.py --skip-module-wait audio.exe` makes the Audio.exe launcher start
its threads without the audio microcontroller. The `SYS_REQ_ACTIVATE` /
`SYS_NOTIFY_ACTIVATE_COMPLETE` exchange then completes and SystemCC fires
`NotifySourceChange`, but AuiApp still paints no form. The next step is to
read what `frm_PRCOM_StartUp` waits for in the skin (M8.C1l).
