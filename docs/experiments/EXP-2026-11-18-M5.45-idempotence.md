## Question

Does `splice_factory` give the same bytes for the same input twice, and how
many bytes does a second and a third splice of the same directory add to the
tile (the M7.1 size budget inherits that number)?

## Hypothesis

The M5.34 tile is +4,671,350 B over factory and its hypothesis is "the appended
slot blocks for the parcels written". If the writer is idempotent, running the
same input over the *generated* tile adds 0 B and leaves the bytes identical;
if it is not, the second splice re-appends the grown blocks and the tile grows
again. **Falsifier:** two runs of the same input produce different tile bytes,
or the second splice grows the tile by the first splice's superseded bytes
again. For the *update* case (different input) the falsifier is unbounded
growth: a second splice over an already-spliced directory whose delta is larger
than the new blocks it writes.

3. **Controls.**
   - *Positive (determinism):* `A0` is the same input built again from the
     factory; it must equal `A1` byte for byte. It does (`sha256 b746427c…`).
   - *Positive (append branch exercised):* the first splice must report
     `appended = 32 > 0`; a "0 appended" everywhere would make the second-splice
     result vacuous. It does.
   - *Positive (unchanged branch reported):* the second splice must report
     `unchanged = 32`; before the branch the same run took the in-place path
     (`in_place = 32`) and also kept the size (section 6).
   - *Negative (append-always mutant, the red control):* a scratch copy of the
     tools with the unchanged and in-place branches disabled must grow the tile
     on the second splice and make both selftests FAIL. It does: `M1 =
     293,990,518 B → M2 = 298,662,006 B` (+4,671,488 B), `appended = 32`,
     `superseded_bytes = 4,667,408`, and `tilewriter --selftest` 69/73
     (4 FAIL) / `one_tile_pipeline --selftest` 3 failures. Restored: the real
     `A2` stays at 293,990,518 B.
   - *Negative (level-2 acceptance/refusal matrix):* the four level-2
     directories are not uniform; `(72,936)` is refused, the other three are
     accepted (section 5, C-4463).

4. **Scope.** One tile (`B48R058R`), section 1. The level-1 run writes all
    1,024 parcels of directory `(76,940)` (`changed_pairs` count 1,024,
    `parcels` 1,024); the level-2 runs write two parcels of directory
    `(76,940)` (V1/V2) or one parcel of one of the four level-2 directories
    (matrix). Excluded: the other 45 tiles, `LEV3456R.DAT`, router graph
    (M5.6), names (`--no-names`, M5.7), boundary joins (M5.5), class filtering
    (M5.3), section 2/4 content, and firmware acceptance (rule 13). The tile's
    other sections are compared, not regenerated (`splice_factory` only writes
    section 1).

5. **Falsifier.** Stated above, before the result.

### 3. Where a slot block lives relative to its directory

The census query prints:

```text
B48R058R.DAT file 289319168 dir off/end 161602560 161619084 min block_off 161619200 max block_end 163413460
A1.DAT file 293990518 dir off/end 161602560 161619084 min block_off 289319168 max block_end 293990518
```

So in the factory the 32 row blocks sit immediately after the 16,524-byte
directory container (`161,619,200`), and in `A1.DAT` the appended region starts
at the factory **file size**, `289,319,168`, extending to the tile end
`293,990,518`. A splice appends at `pad256(len(out))`. Consequence: the row's
"free room" is the appended region at the end of file, not next to the slot
table.

### 4. Level-1 full-directory superseded bytes are the old blocks

## Interpretation

- **FACT:** two builds of the same input from the factory are byte-identical
  (`b746427c…`), and the second and third splices over the output are
  byte-identical to the first, adding 0 B: `289,319,168 → 293,990,518 →
  293,990,518 → 293,990,518`. The 1/2/3-splice sizes are recorded in claim
  C-4460.
- **FACT:** the second splice reports `unchanged = 32`, `appended = 0`,
  `superseded_bytes = 0`: every written block is recognised and kept
  (C-4460).
- **FACT:** a different input over the spliced tile is bounded by its own
  blocks (C-4461): the level-2 update stays at 289,319,168 B and the repeat
  adds nothing; the full level-1 update repeats at 293,990,518 B with
  `superseded_bytes = 0`.
- **FACT:** the row block addresses lie in the appended region, past
  `directory["end"]`; in-place rewrite room for a changed row exists only
  there (C-4462).
- **OBSERVED:** the M5.34 "+4,671,350 B is the appended slot blocks" hypothesis
  is mostly right: 1,789,864 B is the superseded factory blocks that stay
  behind, 4,667,408 B is the new block content and 3,942 B is pad256 alignment
  between appended blocks. The growth is one-time; a repeat adds 0.
- **OBSERVED:** the level-2 refusal is scoped to `(72,936)` (C-4463): the other
  three level-2 directories of `B48R058R` are accepted, and the cause is
  **physical aliasing** — the container at `5120` sits inside the parsed spans
  of 9 level-1 preserve-only slots whose parse begins at a copy of a level-2
  directory header (garbage lengths) and emits parser phantoms. **Unresolved:**
  either a parser phantom block or a real level-1 write; the follow-up decides,
  and until then the bounded claim covers level-1 owned slots only.
- **HYPOTHESIS:** the shared-key case the task's Stop clause names is real in
  section 1, but it is a *level pair*, not two directories: 7,763 record keys
  exist at both level 1 and level 2 with **different** bytes (`0` identical),
  and 4,089 more in section 2; all of them are same-`(y, x)` level pairs, and
  no two distinct directories in a section share a key. So the bounded claim is
  made only for the owned level-1 slots; the shared case is recorded, not
  claimed.
- **UNKNOWN:** whether the unit reads the generated tile (rule 13); the class
  table (M5.3); the M7.1 Europe-wide budget (one tile's one-time append is
  measured here, the 45-tile sum is not).

## Conclusion

`tools/tilewriter.py:splice_factory` gained an `unchanged` branch: when the
rebuilt block equals the block already at the slot's tag, the slot body is
rewritten but the block is not. This reports a repeat identical splice as
`unchanged` instead of rewriting the same blocks in place, and it is the only
branch that leaves a shared block untouched. Output bytes do not change (A0 =
A1 = the M5.34 tile `b746427c…`). The measured 1/2/3-splice sizes for the
level-1 `(76,940)` directory of `B48R058R`, over the **whole** clipped
907,969-node / 112,965-way corpus, are 293,990,518 B each (+4,671,350 B once,
+0 B thereafter); a successive-different-input update stays at its own size
with `superseded_bytes = 0` on the repeat. `docs/format/map-tiles.md` states
the append rule and the size consequence. The level-2 refusal (C-4463) is
scoped to `(72,936)` and is **unresolved** — either a parser phantom block or a
real level-1 write; the follow-up decides, and until then the bounded claim
covers level-1 owned slots only. The level-1/level-2 duplicate keys (7,763 in
section 1, 4,089 in section 2, all different bytes) are recorded but not
claimed. Not done here: the unit's acceptance (rule 13), the M7.1 all-Europe
budget, and the 5120-aliasing follow-up.
