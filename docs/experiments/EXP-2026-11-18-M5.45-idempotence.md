## Question

Does `splice_factory` give the same bytes for the same input twice, and how
many bytes does a second and a third splice of the same directory add to the
tile (the M7.1 size budget inherits that number)?

## Hypothesis

The M5.34 tile is +4,671,350 B over factory and its hypothesis is "the appended
slot blocks for the parcels written". If the writer is idempotent, running the
same input over the *generated* tile adds 0 B and leaves the bytes identical;
if it is not, the second splice re-appends the grown blocks and the tile grows
again. **Falsifier:** two runs of the same input produce different tile bytes,
or the second splice grows the tile by the first splice's superseded bytes
again. For the *update* case (different input) the falsifier is unbounded
growth: a second splice over an already-spliced directory whose delta is larger
than the new blocks it writes.

3. **Controls.**

     result vacuous. It does.
   - *Positive (unchanged branch reported):* the second splice must report
     `unchanged = 32`; the pre-branch writer reported `in_place = 32` instead
     (section 6 below).
   - *Negative (selftest red on the old writer):* with `tools/tilewriter.py`
     stashed, `one_tile_pipeline --selftest` fails (`KeyError: 'unchanged'` in
     the M5.45 block); with the branch restored it is green.

## Observations

### 1. Level-1, same input, 1/2/3 splices

`a1.json`/`a2.json`/`a3.json` (`container`), sizes in bytes:

```text
factory 289319168
a1  {'size': 293990518, 'appended': 32, 'in_place': 0, 'unchanged': 0,  'superseded_bytes': 1789864}
a2  {'size': 293990518, 'appended': 0,  'in_place': 0, 'unchanged': 32, 'superseded_bytes': 0}
a3  {'size': 293990518, 'appended': 0,  'in_place': 0, 'unchanged': 32, 'superseded_bytes': 0}
a0  {'size': 293990518, 'appended': 32, 'in_place': 0, 'unchanged': 0,  'superseded_bytes': 1789864}
```

Sizes: splice 1 = 293,990,518 B (+4,671,350 over factory), splice 2 =
293,990,518 B (+0), splice 3 = 293,990,518 B (+0). `sha256sum`:

```text
b746427cb05612cb34202b012be7e615d5e77ba244f455d67ab52ef62534c2ef  A0.DAT
b746427cb05612cb34202b012be7e615d5e77ba244f455d67ab52ef62534c2ef  A1.DAT
b746427cb05612cb34202b012be7e615d5e77ba244f455d67ab52ef62534c2ef  A2.DAT
b746427cb05612cb34202b012be7e615d5e77ba244f455d67ab52ef62534c2ef  A3.DAT
```

`cmp` of each consecutive pair is silent (identical). A0/A1 share the SHA-256
with the M5.34 report (`b746427c…`), so the new branch changes no output byte.

A different level-2 input changed in place (the block fitted its factory slot);
the repeat of the same input touched nothing.

### 3. Where a slot block lives relative to its directory

`(76,940)` factory: `directory["off"] = 161,602,560`, `directory["end"] =
161,619,084` (`span 16,524` B); row blocks start at `161,619,200` (row 0) and
the last at `163,380,224` (row 31), all in the tile body after the container.
In `A1.DAT` the last appended block was placed at `293,904,896` and the tile
ends at `293,990,518`, so a splice appends at `pad256(len(out))`. Consequence:
the row's "free room" is the appended region at the end of file, not next to
the slot table.

### 4. Level-1 full-directory superseded bytes are the old blocks

`a1.json` `superseded_bytes = 1,789,864` = the sum of the 32 factory row-block
lengths (`clarion_tile.block_bytes` per row: min 33,236 B, max 89,248 B). After
one splice the 32 rows measure 2,726,278 B of block bytes at their block
boundaries plus 256-byte padding between blocks (4,667,408 B is the sum of the
32 block lengths read by `block_bytes`, and the rest of the +4,671,350 B is
`4,671,350 − 4,667,408 = 3,942` B of pad256). The superseded count is the
*old* blocks only; the new content is what was appended.

### 5. Negative control: level-2 splice over the factory tile is refused

`tilewriter fail.imf.jsonl … --level 2` exits 1 with:

```text
tilewriter: check failed: section-1 record at (76, 939, 31, 0) changed but was not regenerated
```

The splice writes **8 bytes** in the common prefix, offsets `5,132..5,159`:
bytes `5,132..5,135` are the 4-byte slot tag of level-2 directory `(72,936)`
row 0 (`tagpos = 5120 + 12`), and `5,154..5,159` are its repointed block header.
`records_by_position(tile, 1)` (`tilewriter.py`) keys records by
`(dir_y, dir_x, slot, pair)` with **no level component**, so the check sees the
level-2 write as a change to several level-1 records, including
`(76,939,31,0)` (level-1 kind `0x2346`, row-31 parsed range `4096..180840`).
Nine level-1 preserve-only row-31 records have parsed spans of
`~95..271 kB` that all cover offset `5,132`.

### 6. Pre-fix control

With the new `unchanged` branch removed (the file stashed), the same level-1
1/2/3 run gives `appended 32 → 0 → 0`, `in_place 0 → 2 → 2` for the small
fixture family and `in_place 32` for the full 1,024-parcel directory — the size
still does not grow, but the writer rewrites the blocks every run. With the
branch, the repeat reports `unchanged = 32` and writes no bytes. The
`one_tile_pipeline --selftest` M5.45 block is red on the stashed writer
(`KeyError: 'unchanged'`).

## Interpretation

- **FACT:** two builds of the same input from the factory are byte-identical
  (`b746427c…`), and the second and third splices over the output are
  byte-identical to the first, adding 0 B: `289,319,168 → 293,990,518 →
  293,990,518 → 293,990,518`. The 1/2/3-splice sizes are recorded in claim
  C-4460.
- **FACT:** the second splice reports `unchanged = 32`, `appended = 0`,
  `superseded_bytes = 0`: every written block is recognised and kept
  (C-4460).
- **FACT:** a different input over the spliced tile is bounded by its own
  blocks (C-4461): the level-2 update stays at 289,319,168 B and the repeat
  adds nothing; the full level-1 update repeats at 293,990,518 B with
  `superseded_bytes = 0`.
- **FACT:** the row block addresses lie in the appended region, far past
  `directory["end"]`; in-place rewrite room for a changed row exists only
  there (C-4462).
- **OBSERVED:** the M5.34 "+4,671,350 B is the appended slot blocks" hypothesis
  is mostly right: 1,789,864 B is the superseded factory blocks that stay
  behind, 4,667,408 B is the new block content and 3,942 B is pad256 alignment
  between appended blocks. The growth is one-time; a repeat adds 0.
- **OBSERVED:** the level-2 splice over the real factory tile is refused
  because `records_by_position` is level-blind and the parsed spans of
  preserve-only row-31 records reach into the header area (C-4463). This is a
  verification-tool limit, not a writer defect: the writer wrote 8 bytes and
  `verify_factory` cannot tell which level owns them.
- **HYPOTHESIS:** the shared-block case the task's Stop clause names is real
  in `B48R058R` but not on the level-1 rows M5.34 writes: 7,763 record keys
  have more than one directory owner (a level-1 and a level-2 directory share
  the same `(y, x, slot, pair)` key), while all 32 rows of the level-1
  `(76,940)` are unshared. So the bounded claim is made only for the owned
  level-1 slots; the shared case is recorded, not claimed.
- **UNKNOWN:** whether the unit reads the generated tile (rule 13); the class
  table (M5.3); the M7.1 Europe-wide budget (one tile's one-time append is
  measured here, the 45-tile sum is not).

## Conclusion

`tools/tilewriter.py:splice_factory` gained an `unchanged` branch: when the
rebuilt block equals the block already at the slot's tag, the slot body is
kept and the block is not written. This makes a repeat identical splice report
`unchanged` and write no bytes, without changing any output byte (A0 = A1 =
the M5.34 tile). The measured 1/2/3-splice sizes for the level-1 `(76,940)`
directory of `B48R058R` are 293,990,518 B each (+4,671,350 B once, +0 B
thereafter), and a successive-different-input update stays at its own size
with `superseded_bytes = 0` on the repeat. `docs/format/map-tiles.md` now
states the append rule and the size consequence. The level-2 splice failure
(C-4463) is a `verify_factory` limitation recorded as a negative; the shared
level-1/level-2 record keys are recorded but not claimed (the bounded claim
covers owned slots only). Not done here: the unit's acceptance (rule 13), the
M7.1 all-Europe budget, and a level-aware `records_by_position`.
