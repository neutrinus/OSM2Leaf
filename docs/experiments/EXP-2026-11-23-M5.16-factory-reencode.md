# EXP-2026-11-23-M5.16: byte-identical re-encoding of factory `LEV3456R.DAT`, levels 3–6

- **Status:** done
- **Date:** 2026-11-23
- **Sample:** firmware head `archive/head256.img` (EU 2011 build A) SHA-256
  `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card `archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img` SHA-256
  `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`;
  from that card `MAPAL001/LEV3456R.DAT` 76,066,304 B SHA-256
  `08a584feacf049cc39260ff29f742c3dcf1b53059cb98bd3e9798e7ab819df35`
- **Tools:** `python3.13 3.13.17`, zlib 1.3.2 (stock, *not* the pinned 1.3.1 —
  `python3.13 tools/zlibinfo.py` prints `zlib: zlib 1.3.2, runtime 1.3.2 (stock,
  not the pinned reference 1.3.1)`); `python3 3.15.0`, zlib
  `1.3.1.zlib-ng` (`python3 tools/zlibinfo.py` prints the zlib-ng warning).
  Repo tools: `tools/lev3456.py` (this task), `tools/datask_l3.py`,
  `tools/mount_dirs_l3.py`, `tools/zlibinfo.py`.
- **Claims:** C-2405–C-2409 (C-2404 becomes history: its blocker is specific to
  the earlier OSM-writer scope)
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the factory `LEV3456R.DAT` coarse levels 3–6 (both sections) be decoded and
written back by our own container code so that the file is byte-identical to the
factory file and the firmware's L3 mount reads it the same way (M5.16, re-scoped
to factory data only, no OSM writer)?

## Hypothesis

Yes. The earlier proof covered section 1 level 5 only; the container writer can
be extended to every non-empty coarse level region. The one section-1 level-6
record is raw, so its declared slot pair — not the length of `Record.plain`,
which holds the raw bytes — is the value to write back. If any level region
differs, or the firmware mount of the rebuilt file differs from the factory
mount, the hypothesis is wrong.

**Falsifier:** a non-zero `cmp` / different SHA-256 after `rebuild --all-levels`;
a `verify` verdict other than OK; a mount read that the model does not list or a
`mount_dirs_l3.py check` verdict other than MATCH; a negative control that still
passes.

### 2. Commands

```bash
W=/home/marek/projekty/leafre-work/scratch/m5.16
F=/home/marek/projekty/leafre-work/root/MAPAL001/LEV3456R.DAT
IMG=archive/head256.img
CARD=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img

python3.13 tools/zlibinfo.py
python3.13 tools/lev3456.py --selftest
sha256sum "$IMG" "$CARD" "$F"

python3.13 tools/lev3456.py verify "$F" --level 3 --level 4 --level 5 --level 6
python3.13 tools/lev3456.py rebuild "$F" --all-levels -o "$W/ALL.DAT"

python3 tools/datask_l3.py mount "$IMG" --card-image "$CARD" \
  --position 51.70,17.45 --bytes --json "$W/F-mount.json"
python3 tools/datask_l3.py mount "$IMG" --card-image "$CARD" \
  --position 51.70,17.45 --replace MAPAL001/LEV3456R.DAT="$W/ALL.DAT" \
  --bytes --json "$W/G-mount.json"
python3 tools/mount_dirs_l3.py check "$W/F-mount.json" --file "MAPAL001/LEV3456R.DAT=$F"
python3 tools/mount_dirs_l3.py check "$W/G-mount.json" --file "MAPAL001/LEV3456R.DAT=$W/ALL.DAT"
python3 tools/mount_dirs_l3.py compare "$W/F-mount.json" "$W/G-mount.json" \
  --file-a "MAPAL001/LEV3456R.DAT=$F" --file-b "MAPAL001/LEV3456R.DAT=$W/ALL.DAT"
python3 tools/datask_l3.py diff "$W/F-mount.json" "$W/G-mount.json"
```

### 3. Controls

- **Positive:** the unmodified factory file must rebuild byte-identically and
  its mount must check as MATCH 9/9 (this is the known-good case).
- **Negative 1 (compressor):** `python3 tools/lev3456.py rebuild "$F"
  --all-levels -o "$W/NG.DAT"` with zlib-ng must NOT claim byte identity — exit
  3, `UNVERIFIABLE`.
- **Negative 2 (byte identity):** copy the factory file, change one padding byte
  inside the level-6 region (`0xb910`, `0x00 → 0xaa`), rebuild that copy; the
  byte-identity check must fail (exit 1, "level differs at 0xb910").
- **Negative 3 (L3 check):** copy `ALL.DAT`, change the level-6 directory's
  size word at `0x1301` from `0x0a` to `0x0c`, then check the *factory* mount
  against it; `mount_dirs_l3.py` must report MISMATCH (exit 1).

```bash
python3 tools/lev3456.py rebuild "$F" --all-levels -o "$W/NG.DAT"
cp "$F" "$W/FLIP.DAT"
python3.13 -c "
p='$W/FLIP.DAT'
with open(p,'r+b') as f:
    f.seek(0xb910); f.write(b'\xaa')
"
python3.13 tools/lev3456.py rebuild "$W/FLIP.DAT" --all-levels -o "$W/FLIP-OUT.DAT"
cp "$W/ALL.DAT" "$W/DIRFLIP3.DAT"
python3.13 -c "
p='$W/DIRFLIP3.DAT'
with open(p,'r+b') as f:
    f.seek(0x1301); f.write(b'\x0c')
"
python3 tools/mount_dirs_l3.py check "$W/F-mount.json" --file "MAPAL001/LEV3456R.DAT=$W/DIRFLIP3.DAT"
```

### 4. Scope

The EU 2011 card's `LEV3456R.DAT`, sections 1 and 2, the six non-empty regions
of levels 3–6; 76,066,304 B, 13,970 decoded records. Excluded: the OSM writer
(`lev3456gen.py` is a separate tool and not changed here), US/2014/2016 cards,
record-level map requests (`--request MESH` fetches a tile record block, not
this file), and the car (L5). The firmware evidence is the mount at one start
position (Krotoszyn), as in M9.18.

### 5. Falsifier

Any rebuilt byte differing from the factory file; a verify verdict other than
OK; fewer than 9/9 MATCH reads; a non-SAME mount diff; or any negative control
passing.

## Interpretation

- **FACT:** with stock zlib 1.3.2, `rebuild --all-levels` reproduces all six
  non-empty level regions and the whole 76,066,304-byte file byte-identically
  (same SHA-256, silent `cmp`); `verify` reports every region identical.
- **FACT:** the firmware mount reads of the rebuilt file match the factory
  mount: 28/28 read records SAME, 9/9 directory reads MATCH against the model
  for both files.
- **FACT:** the three negative controls fail as required; the byte-identity
  check and the L3 directory check can both fail loudly.
- **OBSERVED:** the level-6 record is raw (`parts=(21122, 0)`); before the fix,
  `rebuild_level` measured `len(plain)=42244` and wrote 21,122 plain words,
  shifting the slot pair and failing at `0x1316`. 60 factory-zlib records
  (41 in s1 L4, 19 in s1 L3) plus the raw L6 record are copied verbatim;
  `verify` prints `streams 0/1` for L6 because the record has no zlib stream.
- **OBSERVED:** zlib-ng exits 3 (`UNVERIFIABLE`, not FAIL) — this is a
  compressor limitation, not a data-level refutation.
- **HYPOTHESIS:** the same container writer can splice generated level
  records, but the firmware verdict for *generated* records is a different
  question (the earlier M9.18/M9.53 one) and is not tested here.
- **UNKNOWN:** 2014/2016 cards, other start positions, record-level map
  requests for this file, and any in-car result; `mount_dirs_l3.py` does not
  compare the directory `typ` byte.

## Conclusion

`tools/lev3456.py` now rebuilds `LEV3456R.DAT` levels 3–6 of both sections in
one pass, with the raw level-6 slot pair written from its declared value. The
EU 2011 factory file is reproduced byte-for-byte and the firmware reads the
rebuilt file identically at the Krotoszyn start position. `docs/format/map-tiles.md`
records the raw-record rule and the whole-file command; `docs/research/claims.md`
gains C-2405–C-2409 and C-2404 is left as history for the earlier, wider scope.
M5.16 is re-scoped to this factory-data path; no OSM writer is claimed. The
OSM-generated level set and its firmware acceptance remain separate work.
