# EXP-2026-11-22-M2.25: the 4 unit bytes of the SD password are stored in PROD, not derived from the VIN

- **Status:** done (static, one unit; a second unit's PROD would test the factory rule)
- **Date:** 2026-11-22
- **Sample:** Marek's US head unit `QY7200ND`, LeafSDTools dumps taken by the
  owner: NAND 8 MiB (SHA-256 `dc2b30dfd2ab9e61adeb38a13bc6a167228f7954d952a08f073025b21e2cbb8b`),
  SRAM 1 MiB (`4ca46edfb0041c5eda4cd6c7f9472ae585451c011733068cad2807ca67e0db6e`),
  VFlash 2.875 MiB (`c3e37e6fdbfb465e2f63fae104e1481858519caeb1f6b9268268aa0fe67cbe1b`),
  PROD 722 B (equal to NAND `0xA000…0xA2D1`; its hash is not recorded, because
  with only 4 unknown bytes a hash would allow a brute-force of the PIN).
  None of the dumps is committed.
- **Claims:** C-8300–C-8305
- **Supersedes:** C-1955, C-1956 (hypotheses, now verified on a real dump)
- **Superseded by:** none

## Question

The owner asked: how is the SD card PIN (CMD42 password) generated, and can it
be worked out from the car's VIN alone? M2.13/M2.13b left the source of the 4
unit-specific bytes as a hypothesis ("stored per unit in PROD `+0x100`").

## Method

```bash
N=nand_<id>_<serial>.bin   # owner's dump, never committed
# 1. search all four dumps for: the 4 PIN bytes (BE, LE, ASCII, UTF-16LE),
#    the serial, the product ID, the 12-byte tail, VIN-shaped strings
#    (17 chars, WMI JN1/1N4/SJN/5N1/3N1, ASCII and UTF-16LE)
# 2. find every 32-bit constant in the flash that points into the PROD block
#    (0xA000A000..0xA000A3FF and 0x8000A000..0x8000A3FF, step 2)
# 3. disassemble the loader that owns them
dd if=$N of=ldr.bin bs=1 skip=$((0x20000)) count=$((0x20000))
sh4-linux-gnu-objdump -D -b binary -m sh4 -EL --adjust-vma=0x8b010000 ldr.bin
```

The load address (`flash 0x20000` = VA `0x8b010000`) comes from the literal
pool: pool words `0x8b021290`, `0x8b0212c4`, `0x8b0212e0` at flash `0x33408`,
`0x33428`, `0x3350c` point exactly at the strings at flash `0x31290` (tail
literal), `0x312c4` (`OK! SecuritySD`), `0x312e0` (`NG!PROD SUM=%X, GET SUM=%X`).

## Observations

### What the dumps hold

| Item | NAND | SRAM | VFlash |
| --- | --- | --- | --- |
| 4 PIN bytes (raw) | `0xA060`, `0xA100` only | none | none |
| 4 PIN bytes as ASCII / UTF-16LE hex, or byte-reversed | none | none | none |
| 12-byte tail literal | `0xA104` (PROD), `0x31290` (loader literal) | none | none |
| Serial (4 bytes) | `0xA050`, `0xA142` | none | none |
| Product ID `10 20 02 12` | `0xA020` | none | none |
| VIN-shaped string | none | none | none |

- PROD layout seen in the dump (offsets from `0xA000`): `+0x00` `PROD`,
  `+0x20` product ID (4 B), `+0x40` model `QY7200ND`, `+0x50` serial (4 B),
  **`+0x60` the 4 PIN bytes**, `+0x90` 9 flag bytes, `+0xB0` `3NA0D` (5 ASCII),
  **`+0x100` the 16-byte password = the same 4 bytes + the 12-byte tail**,
  `+0x140` `10 01` + serial, `+0x180` `02 00 01 00`, `+0x2D0` 16-bit checksum.
  Everything else is `0xFF`.
- The dump file names LeafSDTools writes are `<product ID>_<serial>`; neither
  number equals the PIN.
- All 8 nibbles of the 4 PIN bytes are decimal digits (0–9), like the serial
  (packed BCD). For random bytes that happens with probability (10/16)^8 ≈ 2 %.

### The loader routine (flash `0x332ac`, VA `0x8b0232ac`)

- Builds a 16-byte buffer at `0x8b0de9e0`: zero-filled, then the first 4 bytes
  = constant `0x99999999` (pool `0x8b023404`), then 12 bytes copied from the
  literal at `0x8b021290` (the tail).
- If the flag word at `0x8b0b004c` is 1 **and** the 12 bytes at
  `0xA000A104` (PROD `+0x104`) equal the literal byte for byte
  (loop `0x8b02330a`…`0x8b02331c`), it calls `0x8b02d714(buffer, 0xA000A100, 16)`:
  a 16-byte copy from PROD `+0x100` over the buffer.
- It then calls `0x8b02a2c4(0, flag, 16, buffer)` with flag `0` (prints
  `OK! SecuritySD`) or flag `4` (prints `OK!LOCK` / `NG!LOCK`): the CMD42
  UNLOCK and LOCK values of M2.13b, length 16.
- In the whole 8 MiB there are only two constants that point at the password
  (`0xA000A104`, `0xA000A100`, both in this routine) and two pairs that point
  at the block start and its checksum (`0xA000A000` / `0xA000A2D0` at flash
  `0x33514` and `0x8867c`). No code reads `+0x60`, the serial or the product ID
  to compute a password.

## Interpretation

- **VERIFIED (C-8300):** the 16-byte SD password is stored verbatim in the
  unit's flash at PROD `+0x100` (flash `0xA100`): 4 unit bytes + the 12-byte
  firmware tail. The same 4 bytes are repeated at PROD `+0x60`. This confirms
  C-1955/C-1956 and the LeafSDTools field of C-5200's table on real bytes.
- **VERIFIED (C-8301):** the loader does not compute the password. It copies
  the 16 bytes from PROD `+0x100`; when PROD is not valid or the tail there
  does not match, it uses the default `99 99 99 99` + tail.
- **VERIFIED (C-8302):** the unit's flash (NAND, SRAM, VFlash) holds no VIN
  string, so the unit cannot derive the password from the VIN: it does not
  know the VIN in any stored form we can see.
- **OBSERVED (C-8303):** the 4 bytes look like an 8-digit decimal number in
  packed BCD (as do the serial and the default `99999999`).
- **HYPOTHESIS (C-8304):** the value is assigned at the Clarion factory with
  the rest of the PROD record (the loader has a `PRODUCT.INF` / `PROD-DAT`
  path). Whether the factory picks it at random or computes it from the serial
  cannot be told from one unit; the firmware contains no such formula. Two or
  more (serial, PIN) pairs from other units would test it.
- **VERIFIED (C-8305):** a unit whose PROD block is blank or damaged locks
  and unlocks with `99 99 99 99` + tail.

## Positive and negative controls

- Positive: the search finds the serial and the product ID where LeafSDTools
  says they are (`+0x50`, `+0x20`), and PROD equals the NAND bytes at `0xA000`.
- Negative: the PIN bytes do not occur anywhere else in 12 MiB of dumps in four
  encodings, so the hits at `+0x60` / `+0x100` are not chance.

## Conclusion

The answer to the owner's question is no: the VIN is not an input. The
password is a per-unit value written into the head unit's flash at the
factory. To learn it one needs the unit (its service screen, or a PROD/NAND
dump read with LeafSDTools), not the car's VIN. No password bytes, no serial
and no vendor bytes are committed.
