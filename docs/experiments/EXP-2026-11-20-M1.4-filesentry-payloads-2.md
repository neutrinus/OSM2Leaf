# EXP-2026-11-20-M1.4-2: `cerom.py files --decompress` and `extract-file NAME` decode the ROM files at their real length

- **Status:** done
- **Date:** 2026-11-20
- **Sample:** `archive/head256.img` (IMG256, EU2011 firmware head, 256 MiB),
  SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  build B `--image-start 0x3e00200`, build C `--image-start 0x5200200`
- **Tools:** Python 3.13.18; `tools/cerom.py` (`files --decompress`, new
  `extract-file`), `tools/nk_decomp.py` (`decode_cached`, unchanged),
  `tools/cecompress.py` (codecs, unchanged), `file` (libmagic) for the type check
- **Claims:** C-5990–C-5994 (C-5995–C-5999 reserved)
- **Supersedes:** EXP-2026-11-08-M1.4-filesentry-payloads (its decode blocker; the extraction/characterisation stays)
- **Superseded by:** none

## Question

Does `cerom.py` itself now write the compressed `FILESentry` payloads
(`boot.hv`, `default.hv`, `user.hv`, `ceconfig.h`, `initobj.dat`,
`UpdateNK.skn`) at their `real` length, with `ceconfig.h` as readable text,
which is the M1.4 Done-when?

## Hypothesis

M1.21 decoded every compressed `FILESentry` payload with the kernel's own
routine in `nk_decomp.py files`. If `cerom.py files --decompress` hands the
payloads the stdlib/`cecompress` codecs call `UNSUPPORTED` to the same
routine (`r0 == rsize` or refuse), and `extract-file NAME` writes one entry,
the outputs equal M1.21's hashes.

Falsifier: any `UNSUPPORTED`/`FAIL` row on build B or C under `--method
auto`; a decoded SHA-256 different from M1.21's table
(EXP-2026-11-19-M1.21); an output whose length is not `real`; or
`ceconfig.h` not being text. Also: the codec-only path (`--method lzss`)
must still refuse and write nothing, else the "refuse a wrong decode" rule
(C-573) is broken.

## Method

1. **Sample and hash.** IMG256 as above; outputs go to
   `/home/user/scratch/m1.4/` (outside the repo; vendor bytes, deleted after
   the run).
2. **Commands.**

   ```bash
   S=/home/user/scratch/m1.4
   python3 tools/cerom.py --selftest
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img files --decompress --json > $S/eu-B.json
   python3 tools/cerom.py --image-start 0x5200200 archive/head256.img files --decompress --json > $S/eu-C.json
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file ceconfig.h -o $S/eu-B/ceconfig.h
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file initobj.dat -o $S/eu-B/initobj.dat
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file boot.hv -o $S/eu-B/boot.hv
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file default.hv -o $S/eu-B/default.hv
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file user.hv -o $S/eu-B/user.hv
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file UpdateNK.skn -o $S/eu-B/UpdateNK.skn
   python3 tools/cerom.py --image-start 0x3e00200 archive/head256.img extract-file ceconfig.h --method lzss -o $S/neg/ceconfig.h
   file $S/eu-B/ceconfig.h
   head -n 3 $S/eu-B/ceconfig.h
   ```

   Change in `tools/cerom.py`: `files_report` accepts `--method kernel`; under
   `auto`, a payload the codecs raise `UnsupportedFormat` for is decoded by
   `KernelDecoder.decode_file` (section frame `skip 0, step 1, block 0x1000`,
   `r4=src, r5=csize, r6=dest, r7=rsize`, M1.21) and is `OK` only when
   `r0 == rsize`. Records gain `decoded_sha256` and `kernel` (additive keys).
   `extract-file NAME -o PATH` writes one entry: a copy for `csize == rsize`,
   otherwise the `OK` decode; anything else prints `REFUSED` and writes
   nothing (exit 1).
3. **Controls.** Positive: decoded SHA-256s must equal M1.21's table (an
   independent call path, `nk_decomp.py files`); `ceconfig.h` must start
   `#ifndef`. Negative: `--method lzss` on `ceconfig.h` must be `REFUSED`,
   exit 1, no file; the synthetic `--selftest` ROM (no build B, so no
   kernel) must keep `boot.hv` `UNSUPPORTED` and `extract-file boot.hv`
   refused (exit 1, nothing written). The shifted-payload negative of the
   kernel call itself is M1.21's (`--src-skip`, `r0 = 0xffffffff`).
4. **Scope.** All `FILESentry` rows of builds B and C of the EU2011 head
   (21 rows, 15 compressed). Not covered: build A (1 row, stored), the US2011
   head (M1.21 showed byte-identical build B and the same build-C hashes),
   the copies at `0x4800200`/`0x2000200`, and the content of the files
   (vendor data; ≤ 3 lines of `ceconfig.h` quoted).
5. **Falsifier.** As stated under Hypothesis, before the result.

## Interpretation

- **FACT:** every hash above equals the M1.21 table
  (EXP-2026-11-19-M1.21-filesentry-decode) for the same build, through a
  second call path (`cerom.py` → `KernelDecoder.decode_file` →
  `nk_decomp.decode_cached` instead of `nk_decomp.py files`).
- **FACT:** the M1.4 Done-when holds: `cerom.py extract-file NAME` writes
  payloads whose length is `real`, and `ceconfig.h` is readable text.
- **OBSERVED:** the stdlib/`cecompress` codecs still decode none of these
  payloads (the `lzss` negative); the kernel routine is the only decoder,
  as in M1.21.
- **UNKNOWN:** the format of `UpdateNK.skn` (first word `01000204`, M1.21)
  is not read here.

## Conclusion

`cerom.py files --decompress` (default `auto`) now reports 8/8 build-B and
7/7 build-C compressed `FILESentry` rows `OK` via the kernel routine, and
`extract-file NAME` writes one file at its real length or refuses. This
closes the M1.4 decode blocker of EXP-2026-11-08 (C-682) with C-5990–C-5994.
