## Question

Can the nk.exe CE ROM decompressor (M1.2c) be called directly under
`qemu-system-sh4 -M none` + gdbstub with RAM-only state, like an L3 call, to
decode the two EXP-49 sections to M1.2a expected lengths, then extend to all
245 sections and FILESentry payloads?

## Hypothesis

Per M1.2c/TODO M8.E1: call `DECOMP_WRAP 0x88037590` or `DECOMP_SECT 0x88037464`
(nk.exe, image B `--image-start 0x3e00200`) with `(r4=src,r5=psize,r6=dest,r7=vsize)`
under `qemu-system-sh4eb -M none -cpu sh7785` + gdbstub, mapping nk.exe
sections via `-device loader`; read dest to obtain 0x484 / 0xcc0 bytes.

## Method

1. **Execution environment setup.** Ran `qemu-system-sh4eb -M none -cpu sh7785 -m 512M -S -gdb tcp::PORT` with `-device loader,file=…,addr=<phys>,force-raw=on` for nk.exe sec0/sec1/sec3 and scratch buffers (stack/src/dst/vectors), controlled via minimal GDB RSP client (stdlib Python). Compared with `-M r2d -cpu sh7751r`. Key finding: `-device loader` makes regions CPU-executable; gdbstub `M` writes alone do not create CPU-executable mappings on `-M none`. `-M r2d` RAM starts at 0x0c000000 so cannot map nk.exe at physical 0x08000000; `-M none` + loader can.
2. **Positive controls.** (a) Trivial SH-4 snippet `e02a 000b 0009` (`mov #42,r0; rts; nop`, BE) executed on `r2d`/sh7751r: step 1 gave r0=`0x2a`, PC returned to PR — PASS. (b) nk.exe sec0 bytes loaded by `-device loader` readable via gdbstub at physical 0x08001000 (`000000003fc91e4c…`). (c) Overwriting a word inside loader-mapped nk sec0 (e.g. 0x88037464) with the trivial snippet and executing from it yielded r0=`0x2a` in the working state (after accounting for `-M none` init/reset quirk) — confirms loader-mapped nk range is CPU-executable.
3. **M1.2c VA verification (negative).** Searched nk.exe sec0 (base 0x88001000, 313344 bytes) and whole IMG256 for M1.2c's reported flag-test pattern `e22053854218232923388b03` (`mov #32,r2; mov.l @(20,r8),r3; shll8 r2; and r2,r3; tst r3,r3; bf`): **0 hits** in sec0, **0 hits** in IMG256. Searched `eN20 4N18` (`mov #0x20,rN; shll8 rN`): **0 hits**. Literal `0x00002000`: 1 hit at 0x88042298 with no PC-relative `mov.l @(disp,PC)` reference found. `add #24,rN` (o32 stride): 5 hits (0x880128e4 r8, 0x88019b6c r1, 0x8803a748 r4, 0x8803acbe r7, 0x88047744 r12), none near o32_flags `@(20,Rm)` loads or 0x2000 tests. Read bytes at M1.2c VAs: 0x88038666 = `20e2 8553 1842` (not `e220 5385 4218`); 0x8803758c literal = `0x84a30388` (not `0x8803a384`); 0x88037542 = `0x0b43` (not jsr@r3). Capstone (SH4/SH4A BE) decodes 0x88037464 as `mov #47,r6` then fails on `862f`; SH2A mode gives nonsensical prologue (bra/bsr to far addresses).
4. **Execution attempt at M1.2c VAs.** With VBR mapped and CPU primed, calling DECOMP_SECT 0x88037464 (r4=src,r5=0x2c6,r6=dst,r7=0x5b8) caused an immediate general exception (vector 0x100) on the second instruction path / reset behavior depending on vector setup; dst remained zero. PySh4 executed `e62f` (mov #47,r6) then raised `IllegalInstruction` on `862f` at 0x88037466. **Control:** the same execution harness correctly runs a known-good snippet placed in nk sec0.
5. **Tool.** Created `tools/cedecomp_run.py` (stdlib, QEMU+gdbstub framework, nk section loading, EXP-49 vectors, `--selftest`/`info`/`probe`/`exp49`; refuses M1.2c VAs as `exp49` entry).

## Observations

- **QEMU control (OBSERVED, controls pass):** `qemu-system-sh4eb -M none -cpu sh7785 -S -gdb` with `-device loader` executes SH-4 BE code from loader-mapped nk.exe physical 0x08000000 range and returns results via gdbstub. `-M none` has init quirks (first execution from some states resets to 0xa0000000; VBR must point to a loader-mapped, CPU-fetchable region to catch exceptions). `r2d` is reliable for control snippets but cannot map 0x08000000.
- **M1.2c VAs refuted (OBSERVED, negative with controls):** none of M1.2c's reported instruction patterns exist in IMG256 (nk sec0 or whole image); bytes at M1.2c's key VAs do not match M1.2c's disassembly; literal/branch targets M1.2c cited are different values. Controls: the search found 1 `0x00002000` literal elsewhere and 5 `add #24` sites (search works); capstone/PySh4 decode real bytes consistently.
- **EXP-49 lengths (FACT, from comphdr/M1.2a):** sec1 form-1 ulen 0x484, vsize 0x5b8, psize 0x2c6; sec2 ulen 0xcc0, vsize 0xcc0, psize 0x68c. Not decoded by execution in this EXP (blocker).
- **Decode result:** **not achieved** for either EXP-49 section (no verified decompressor entry point).

## Interpretation

- **FACT (negative):** M1.2c's recorded decompressor VAs/prototype for nk.exe image B in IMG256 are not verifiable against the actual bytes and its reported instruction sequences are absent. M8.E1 cannot call "the nk.exe decompressor at the recorded VA(s)" because those VAs do not identify the decompressor in IMG256.
- **OBSERVED:** A working SH-4 execution framework (QEMU sh4eb + loader + gdbstub) is feasible and has passing controls; it is ready to call the real decompressor once the correct VA/prototype is established.
- **UNKNOWN:** The real nk.exe (image B, 0x3e00200) decompressor entry point, its prototype, and required kernel context/globals; the actual decoded bytes of the two EXP-49 sections; form-2/multi-block (245 sections) and FILESentry payload decode.

## Correction (M8.E1b, 2026-11-06)

This EXP's core negative finding (C-1600, C-1603: M1.2c VAs/pattern absent,
execution fault at 0x88037464) was caused by **BE interpretation of LE-encoded
SH-4 instructions** in nk.exe. M8.E1b (EXP-2026-11-06-M8.E1b-nk-decompressor-derive)
showed: LE halfword decode of 0x880385e4 gives a valid prologue and the flag-test
pattern exists at 0x88038666 (LE bytes `20e28553184229233823038b`, 1 hit);
M1.2c pool/literal values match under LE; 0x88037464 has a valid LE prologue
(DECOMP_SECT). **C-1600, C-1603 superseded by C-2290–C-2293, C-2296.** C-1601's
loader mechanics remain valid but nk.exe requires `qemu-system-sh4` (LE). C-1602
updated. C-1604 decode remains not executed but M8.E1 is unblocked (real VAs
verified). `tools/cedecomp.py`/`cedecomp_run.py` corrected.
