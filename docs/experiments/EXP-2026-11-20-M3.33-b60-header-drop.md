## Question

At 65.0 N 30.0 E and 64.5 N 29.0 E, both inside `B60R048R.DAT`, the mount
reads that tile's header and then the directories of `B28R070R.DAT`
(C-5825). Which branch leaves the tile, and which header field does it test?

## Hypothesis

Exploratory. Expectation from M3.31: the header handler `0x0040b8b4` tests
a field of the first `0x1000` bytes that `B60R048R` and `B48R058R` hold
differently.

**Falsifier:** the field named below is changed in `B60R048R` and the tile
is still left; or it is changed the other way in a tile that mounts
(`B48R058R`) and that tile still mounts.

Every tile box has mask (`+4`) 7 and level bits (`+6`) 3; the `LEV3456R` box
(45) has level bits `0x3c`. Box 0 is `B28R070R` (y `0x28`–`0x30`, x
`-0x70`–`-0x68`).

Code (EU2011). Header handler `0x0040b8b4`: for a file kind below 6 with a
box, `0x0040b92e` calls the check `0x0040acb8(kind, volume, buffer, box)`
and leaves at once when it returns non-zero (`0x0040b934`–`0x0040b936`).
The check loops `part` = 0…5: bit `part` of the box's `+4`, the entry
address `buffer + 2 * [0x179dd0 + 4 * part]` (parts 0, 1, 2 → `0x800`,
`0x806`, `0x80c`), a row of the table at `0x179e84` (3 bytes: part, level
bits, x) whose level bits meet the box's `+6`. At `0x0040ad36`–`0x0040ad48`
it compares the entry's first two words with `0xffff`. If both are, and
five "already loaded" words of that part are all zero (`0x0040ad4a`–
`0x0040ad78`), it goes to `0x0040ae26`: box `+16` = 3. Then, only when the
progress word is 0 and the box's `+8` is not 100 (`0x0040ae2e`–`0x0040ae40`),
it calls `0x0040a61c(position, kind)` and returns -1. `0x0040a61c` asks
`0x0040a1dc` for the box of the position; `0x0040a1dc` skips a box with
status 3 (`0x0040a25e`–`0x0040a264`) and returns -1 when none is left; the
caller maps a negative answer to index 0 (`0x0040a6d2`–`0x0040a6d8`:
`cmp/pz r2; subc r3,r3; and r2,r3`) and opens that box when its status is 6.

## Interpretation

- **FACT:** the branch is `0x0040ad36`–`0x0040ad78` → `0x0040ae26` of the
  header check `0x0040acb8`; the field is the third entry of the section
  list, header bytes `0x80c`–`0x80f` = `ff ff ff ff`. Both causal controls
  move the result with only that entry changed.
- **FACT:** a tile left this way gets box status 3; on the first mount the
  position is asked again, no box is left for it, and the mount goes on in
  box 0 of the table, on this card `B28R070R.DAT`. That tile also has two
  entries and is also given status 3, but the next stage reads its section
  tables all the same (the same -1 → 0 mapping).
- **OBSERVED:** 8 of the 45 factory tiles have fewer than three entries, so
  this is the factory behaviour for a first mount inside them, not damage.
- **OBSERVED:** with a copied third entry `B60R048R` mounts and the firmware
  reads the copied table as part 2; the run ends with progress 5, not 1 (it
  waits for part-2 directories the copy does not describe). The control
  shows the gate, not a usable tile.
- **HYPOTHESIS:** part 2 is the third section of a tile (the most detailed
  one); a two-entry tile is a tile without it. Not decoded here.
- **UNKNOWN:** what the unit shows at such a position; whether a later
  position event mounts a status-3 tile (the 64.5 N run mounted a
  neighbour, not `B60R048R`).

## Conclusion

The rule for generated tiles: **a `BxxRyyyR.DAT` tile must list three
sections at header `0x800`**, or the first mount at a position inside it
ends in the first tile of the box table. `tilewriter.py`'s fresh container
already writes three entries (checked on `one_tile_pipeline.py --synthetic`:
`0x1000`, `0x5500`, `0x5600`), and the `--factory` path keeps the factory
list, so a rebuilt two-entry factory tile inherits the factory behaviour.
`docs/format/map-tiles.md` gains the rule and the box table fields; claims
C-6080–C-6087. Follow-up **M5.61**: make `l2check` refuse a generated tile
with fewer than three section entries.
