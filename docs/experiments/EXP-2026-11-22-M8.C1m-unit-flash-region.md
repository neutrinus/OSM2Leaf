## Question

Marek's hypothesis: his unit's flash carries the region (Product ID
`10 20 02 12`, area USA), so the EU card will not start on it. With the
unit's data in the emulator instead of hand-set values, which launcher gate
does the EU card hit?

## Hypothesis

The area comes from the unit's flash. Whether the EU card is refused by the
area or by the map-code check is open. Falsifier from the task: the launcher
reads the area only from the card, and no read from the dumps changes the
outcome.

## Method

1. **Static.**
   - nk.exe (image B) `IsEvModel` is fn `0x880480c8`. It calls
     `KernelIoControl(0x01013208)`, whose handler is fn `0x88048754` (OAL
     ioctl table entry at `0x880091fc`).
   - The handler calls fn `0x88048604`. That function compares the magic
     `PROD` (`0x88008a80`) with a RAM cache (`0x89e439b8`) and with the
     flash at `0xa000a000`, then copies the block into the cache.
   - `IsEvModel` accepts Target IDs `0x10100212`, `0x10200212` and
     `0x10300212`.
2. **Model.** `ze0-0017` adds `flash=FILE`. The dump is mapped read-only at
   phys 0, and the CPU reaches it through P2 `0xa0000000`. ze0 had nothing
   there before.
3. **Runs.** Both runs use the M8.C1l configuration and `mapdb=16-16`:

   | run | `verinf=` | `flash=` | watched |
   | --- | --- | --- | --- |
   | J16 (M8.C1l) | `QSD-302-100` | none | 240 s |
   | U1 | `QSD-302-100` | unit dump | 240 s |
   | U2 | `QSD-301-100` (the unit's own, see O3) | unit dump | until FailSafe |
   | U3 | `QSD-301-100` | unit dump | card patched: both copies of the map code `QSD-302-100` → `QSD-301-100` |
   | U4 | `QSD-301-100` | unit dump | card patched: `HDD_INFO.TXT` (FAT, image offset `0x7a405400`) only |
   | U5 | `QSD-301-100` | unit dump | card patched: raw copy at image offset `0x06000000` only |

   U3–U5 write one byte (`2` → `1` at `+6`) into the qcow2 overlay through
   the HMP `qemu-io` command before the CPU starts. The card image itself is
   unchanged (Marek, 2026-11-22: "podmień w mapie europejskiej kod, odpal
   go na moich danych").

## Observations

**O1 — Without the flash (J16).** The kernel prints
`IsEvModel OALIoCtlGetProductInfo[0]`, `IsEvModel return bRet[0]`, then
`Launcher: Get Area info from Env Variable.` and
`Launcher [Area:FFFFFFFF >> Euro]`.

**O2 — With the flash (U1).**

- The kernel prints `IsEvModel OALIoCtlGetProductInfo[270533138]`
  (`0x10200212`) and `IsEvModel return bRet[1]`.
- `GetBackUpAreaInfoTbl END[2] … Size[65536]` is new.
- Then `Target ID Code >> 10200212` and `Launcher [Area:20 >> USA]`.
- The set of created processes is the same as in J16. U1 has 30
  `Process Create` lines and J16 has 40, but the difference is repeated
  creations of the same processes, not a smaller table.
- With the EU map code forced through `verinf=`, the launcher passes both
  card checks (no `Error Proc`).

**O3 — The unit's map code is in NK1's header.** The flash dump holds
`QSD-` once, at `0x40060`. That is NK1's image header `+0x60` (NK1 starts
at `0x40000`). The fields are:

| field | value |
| --- | --- |
| `+0x50` | `470-2817-33` |
| `+0x60` | `QSD-301-100` |
| `+0x70` / `+0x72` | map-DB window, big-endian u16: `0x0010` / `0x0010` |

The committed `firmware/unit-flash/nk1-QY7200ND.bin` has the same bytes.
M8.C1c showed that the launcher reads `VerInf` and the map-DB window from
the header of the running kernel image (XIP region 0) (C-6881). On the
unit, that image is NK1. The VFlash and SRAM dumps contain no `QSD-` string.

**O4 — The unit's values refuse the EU card (U2).**

```
Target ID Code >> 10200212
Launcher [Area:20 >> USA]
VerInf:QSD-301-100 / HddInf:QSD-302-100
 AppLch >> Error Proc<00000050>!!
*** FailSafe.exe Start ***
```

`Error Proc 0x50` is the map-code mismatch (M8.C1c run X, C-6877). The
map-DB window 16–16 matches the card, so the `0x51` check (`MapDBVer`) is
not reached as a failure.

**O5 — The EU card with the map code changed on the card (U3, U4, U5).**

- U3 and U4 log `Launcher [Area:20 >> USA]` and no `VerInf` line, `Error
  Proc` or FailSafe. The launcher creates `Navi.exe`, ScreenState handles
  `NAVIMAP_CC_NTF_OWNFIRSTMAPDRAW_END`, and the screenshot shows the
  London map of the EU card (as in M8.C1l).
- U5 (raw copy only) logs `VerInf:QSD-301-100 / HddInf:QSD-302-100` and
  `Error Proc<00000050>`.

The launcher's card-side map code (`HddInf`) is therefore the file
`VER_INFO/HDD_INFO.TXT` in the FAT partition, not the raw copy at
`0x06000000`. This answers the M2.5 question (C-077, C-165) for the
map-code check.

**O6 — GPS time fix from LeafSDTools Companion 1.2.1 (static, outside the
emulator).** The patch (`patch/gpstimefix_qy7`, credited to YDean, 4pda)
works on NK1 in the unit's flash (NAND `0x40000`), not on the card:

- In `navdrv.dll` it changes two instructions (`+0x24`, `+0x8e` from a
  signature). The function that sets the system time from the GPS then
  passes the raw GPS buffer instead of a `SYSTEMTIME`.
- It renames the import `COREDLL.dll` → `COREXLL.dll` and adds the file
  `COREXLL.dll`, a shim. The shim reads `YY MM DD hh mm ss` at buffer
  `+0x10..+0x15`, adds `0x1600A391000000` × 100 ns (exactly 1024 weeks),
  writes the date back into the buffer and calls `SetSystemTime`.
- It recomputes NK1's checksums (SUM2 at header `+0x30`, SUM4 at `+0x84`).

A dry run on the committed NK1 (`nk1-QY7200ND.bin`) passes:

- the original's checksums verify;
- the signature matches and the patch applies in `navdrv.dll` at VA
  `0x03cf4988`;
- the ROM size is unchanged.

Nothing was written to a unit.

## Interpretation

- Marek's hypothesis holds, but the gate is not the one he named. The area
  byte (PROD `+0x20`, USA) only changes the launcher's process table. The
  EU card is stopped by the **map code**: the unit's kernel header says
  `QSD-301-100`, and the card says `QSD-302-100`. This matches the
  on-screen `DIFFERENT MAP CODE` path, but the screen text itself was not
  observed in the emulator.
- Both values come from the unit's NAND, at two separate places: PROD at
  `0xa000` and NK1's header at `0x40060`. The card and its image B carry
  neither: image B's header has zeros at `+0x60`, which is why `verinf=` was
  needed.
- The reverse direction works without touching the unit. With
  `HDD_INFO.TXT` on the EU card changed to the unit's map code, the EU card
  passes the launcher with area USA, and Navi draws its map (U3, U4). The
  map-DB window 16–16 already matches. The emulator has no GPS peer, so
  whether Navi then accepts a Wrocław fix (M1.50/M1.51, H2c: no map under
  the position) is for the car.
- NK1 carries checksums (O6). A change of its `+0x60` would have to fix
  SUM2/SUM4, as LeafSDTools Companion does.
- Not tested: whether changing NK1's `+0x60` to `QSD-302-100` alone lets the
  EU card start with area USA. It would, if the launcher has no other
  check. It is a flash change on a real unit, so it belongs in
  [us-eu-region.md](../research/us-eu-region.md)'s spare-unit tests, not
  here.

## Conclusion

With `-M ze0,flash=` and the unit's dump, the kernel reads the PROD block
itself (`Target ID Code >> 10200212`, `Area:20 >> USA`). With the unit's
own map code (NK1 header `+0x60`, `QSD-301-100`), the EU 2011 card stops at
the launcher's map-code check (`Error Proc<00000050>`, FailSafe). Changing
the EU card's `HDD_INFO.TXT` to `QSD-301-100` lets it pass and draw its map
on the US unit's data. The
region lock on this unit is NK1's map code first. The area byte comes
second and only selects the launch table.
