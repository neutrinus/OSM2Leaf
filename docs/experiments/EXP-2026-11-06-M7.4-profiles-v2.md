## Question

Can the four shipped profiles move off the version-1 legacy adapter onto the
canonical version-2 schema without changing the resolved tile counts or the
`build.py` size estimates, and can `build.py --dry-run` show the M5 compiler
spine while still refusing to write anything?

## Hypothesis

The version-1 normalizer already produced the same document the version-2
schema describes (region + buffer in degrees, one or two tiers, whole tiles),
so a hand migration should preserve the resolved counts **1 / 1 / 4 / 56** and
the estimates **44.6 / 1.5 / 178.4 / 253.4 MB** exactly. With the files
migrated, `profile_validate.py --strict` should report zero errors and zero
warnings for all four. The only obstacle is the old `W009` warning for a
selection wider than the 45 shipped tiles; it describes the lattice, not the
profile, so it belongs in a non-fatal class.

## Method

```bash
# 1. Migrate the four profiles by hand to schema v2 (whole-tiles, degrees,
#    coverage tiers, attribution, limits, outputs); schema.json unchanged.
# 2. Add a note severity to profile_validate.py (N001 replaces W009), and pin
#    the shipped profiles as strict regressions in its --selftest.
# 3. Add the M5 stage plan to build.py --dry-run/--json and pin the shipped
#    estimates in build.py --selftest.
# 4. Verify:
python3 -m py_compile tools/profile_validate.py tools/build.py
python3 tools/profile_validate.py --strict \
  profiles/dolnoslaskie-detail.json profiles/dolnoslaskie-test.json \
  profiles/poland-full.json profiles/europe-motorways.json
python3 tools/profile_validate.py --strict profiles/*.json   # schema.json skipped
python3 tools/build.py --profile profiles/dolnoslaskie-detail.json --dry-run
python3 tools/build.py --profile profiles/dolnoslaskie-detail.json   # expect 3
python3 tools/profile_validate.py --selftest
python3 tools/build.py --selftest
python3 tools/selftest.py
```

## Interpretation

- **FACT:** all four shipped profiles are now schema version 2 and
  `--strict` returns `OK (0 error(s), 0 warning(s))` for each; the legacy
  adapter is no longer used by any shipped file.
- **FACT:** the resolved tile counts are unchanged — 1, 1, 4, 56 — with the
  same ids and the same tier split (`detail` 4 + `corridor` 52 for
  `europe-motorways`).
- **FACT:** the dry-run estimates are unchanged — 44.6 MB, 1.5 MB, 178.4 MB,
  253.4 MB — and are now regression constants in both `--selftest`s.
- **FACT:** `build.py` prints the four M5 stages plus the card-image writer,
  each containing the literal `NOT IMPLEMENTED`; `--json` carries the same
  list with `"implemented": false`. Without `--dry-run` it still exits 3.
- **OBSERVED:** `W009` was the only warning that a correct version-2 profile
  could not avoid (`europe-motorways` selects 56 lattice cells of which 45
  exist as files). It was reclassified as note `N001`: printed like a warning
  but never promoted by `--strict`. The 18-cell difference is a property of
  the lattice/sea mask, not of the profile.
- **OBSERVED:** `region.name`, tier `description` and `outputs.card_label`
  are new, non-semantic fields; the tile resolver ignores them. `outputs.verify`
  is `true` in the shipped profiles as intent, but the verify stage is part of
  the unimplemented writer.
- **OBSERVED:** the validator now recognises `profiles/schema.json` and skips
  it with a stderr line, so `profiles/*.json` (the example in its own
  docstring) exits 0 while validating only the four profiles.
- **HYPOTHESIS:** when M5.2/M5.4/M5.6 land, the stage plan can keep its shape
  and only flip `implemented`/status; wiring `osm_ingest` first should not
  change the estimate arithmetic.
- **UNKNOWN:** whether the v2 field set is final — a routing-graph block is
  deliberately absent until a graph exists, and `attribution.location:
  "manifest"` is still a placeholder, not a legal decision.
