# EXP-2026-11-19-M9.44: Virtual card — the firmware's map-file layer mounts and reads a card in PySh4

- **Status:** done
- **Date:** 2026-11-19
- **Sample:** firmware: `archive/head256.img` (first 256 MiB of the EU card
  image) SHA-256 `92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`;
  card: `LEAF_2011-2012_QSD-309-101_navi158_eu.img` (8,057,257,984 bytes)
  SHA-256 `105e2032e480e8ba162a2a9d4b6624cb1dafee380379a9908f3f101b15076307`
- **Tools:** `python3 3.13.18 / zlib 1.3` (host side; the firmware side uses the
  firmware's own zlib), repo tools `tools/vcard_l3.py` (new),
  `tools/l3_harness/engine.py` (PySh4), `tools/nk_decomp.py`, `tools/cerom.py`,
  `tools/callgraph.py` (`parse_exports`), `tools/cardcheck.py` (`Fat32Image`,
  `decode_cmp`), `tools/drstr_ze0.py`, `tools/cmpind_writer.py`, `tools/sh4dis.py`
- **Claims:** C-4630–C-4655
- **Supersedes:** none
- **Superseded by:** none

## Question

Can the map-file layer of `Navi.exe` (EU2011 build A) run on a whole card
without a unit: mount it, build its file table and return file bytes, with a
verdict that changes when the card is damaged?

## Hypothesis

Yes: the layer reaches the card only through C runtime file imports, so a model
of those imports that serves a card tree is enough, and no firmware function
needs replacing.

**Falsifier:** the factory EU card is rejected (state other than `2/2`), or a
file read through the layer differs from the card's bytes (plain files) or from
the host decode (`.cmp`/`.ind` pairs), or a damaged `DRSTR001.DAT` is accepted
with an unchanged table in every control.

## Method

1. **Sample and hash.** As above. The card image is read in place through
   `cardcheck.Fat32Image`; nothing is extracted.
2. **Commands.**

   ```bash
   IMG=archive/head256.img
   C=archive/sd-images/LEAF_2011-2012_QSD-309-101_navi158_eu.img
   W=archive/work/vc
   python3 tools/vcard_l3.py --selftest
   python3 tools/vcard_l3.py boot $IMG --card-image $C --tree
   python3 tools/vcard_l3.py sweep $IMG --card-image $C --bytes 0x4000 -v
   # controls: one changed file per run
   python3 tools/vcard_l3.py boot $IMG --card-image $C --hide DRSTR001.DAT
   python3 tools/vcard_l3.py boot $IMG --card-image $C --truncate DRSTR001.DAT@0x800
   python3 tools/vcard_l3.py boot $IMG --card-image $C --flip DRSTR001.DAT@0x2f
   python3 tools/vcard_l3.py boot $IMG --card-image $C --flip DRSTR001.DAT@0x18:0x01
   python3 tools/vcard_l3.py boot $IMG --card-image $C --flip DRSTR001.DAT@0x24:0x40
   python3 tools/vcard_l3.py boot $IMG --card-image $C --flip DRSTR001.DAT@0x28:0x01
   python3 tools/vcard_l3.py boot $IMG --card-image $C --flip DRSTR001.DAT@0x640:0x01
   python3 tools/vcard_l3.py boot $IMG --card-image $C --hide CMP.LST
   python3 tools/vcard_l3.py boot $IMG --card-image $C --hide MMAIN001.DAT
   python3 tools/vcard_l3.py boot $IMG --card-image $C --flip MMAIN001.DAT@0x0
   python3 tools/vcard_l3.py boot $IMG --card-image $C --truncate MMAIN001.DAT@0x800
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT --flip REFER001/ADDRE001.DAT.cmp@0x100
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT --flip REFER001/ADDRE001.DAT.ind@0x4
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT --flip REFER001/ADDRE001.DAT.ind@0x11
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT --hide REFER001/ADDRE001.DAT.ind
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT --hide CMP.LST
   python3 tools/vcard_l3.py read $IMG --card-image $C MAPAL001/B28R070R.DAT --length 0x10000
   python3 tools/vcard_l3.py read $IMG --card-image $C MAPAL001/B28R070R.DAT --length 0x1000 --swap
   python3 tools/vcard_l3.py read $IMG --card-image $C MAPAL001/B28R070R.DAT --offset 0x108000 --length 0x1000
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/POINT010.DAT --length 0x1000 --swap
   # rule 13: our writers' output read by the firmware
   python3 tools/cmpind_writer.py recompress ADDRE001.DAT.cmp ADDRE001.DAT.ind $W/re ADDRE001.DAT --level 9
   python3 tools/vcard_l3.py read $IMG --card-image $C REFER001/ADDRE001.DAT \
       --replace REFER001/ADDRE001.DAT.cmp=$W/re/ADDRE001.DAT.cmp \
       --replace REFER001/ADDRE001.DAT.ind=$W/re/ADDRE001.DAT.ind
   python3 tools/vcard_l3.py compare $IMG --card-image $C --other-image $C --replace DRSTR001.DAT=$W/DRSTR_grown.DAT
   python3 tools/vcard_l3.py compare $IMG --card-image $C --other-image $C --replace DRSTR001.DAT=$W/DRSTR_noref.DAT
   ```

   The two `DRSTR` inputs come from `drstr_ze0.build(root, order=…)` on a tree
   with the card's names and sizes (data files sparse, every `.ind` real):
   `DRSTR_grown.DAT` = reference order, `MAPAL001/B28R070R.DAT` grown by 6,144
   bytes (SHA-256 `ff926993…855d5e33`); `DRSTR_noref.DAT` = built with the
   reference `DRSTR001.DAT` removed, so with the writer's own order (SHA-256
   `62290dfa…2702e04d`). `drstr_ze0.build` on the unchanged tree is
   byte-identical to the card's file. `ADDRE001.DAT.cmp/.ind` for
   `recompress` are the card's files, copied out with `Fat32Image.read_range`.
3. **Controls.** *Positive*: the factory card must mount and every file must
   read back equal. *Negative*: the changed cards above; each must change the
   verdict, the firmware's error log, the read log or the volume table.
4. **Scope.** EU2011 build A code on the EU 2011 card. The layer is functions
   `0x00417924…0x0041cab0` plus the firmware zlib; 81 imports have models
   (file, string, memory, printf, heap, task and object calls). A map *client*
   (router, renderer, search) is not run: requests are made by this tool with
   the record the API expects. US2011 code is not covered (its addresses
   differ; `us256.img` is a truncated image and cannot serve as a card).
5. **Falsifier.** As stated under Hypothesis.

**A harness defect found by the sweep.** The first sweep stopped after 214
files with a null-pointer store: the heap model never reused freed blocks and
its 32 MiB ran out. `free` now returns blocks to exact-size lists, and a
request that does not complete is withdrawn with the firmware's own cancel
`0x00418428` before its buffer is released. The numbers above are from the
re-run.

**Selftest.** `python3 tools/vcard_l3.py --selftest`: 19 host-side checks on a
synthetic card (path translation, read log, overlay, expectation, printf
subset), plus 3 firmware checks when both images are present (mount, tile read,
truncated-`DRSTR` reject).

## Interpretation

- **FACT:** the layer's init, mount state machine, `DRSTR` parser, request
  queue, worker, `.cmp`/`.ind` decoder and zlib run unmodified in PySh4 and mount
  the factory EU card with no error-log call.
- **FACT:** the mount reads three files only: `CMP.LST` (19 bytes),
  `MMAIN001.DAT` (`0x1000` bytes), `DRSTR001.DAT` (whole, one read). No tile and
  no `REFER001` file is touched at mount.
- **FACT:** `MMAIN001.DAT` is checked for presence and length only; its content
  is not looked at during mount.
- **FACT:** `DRSTR001.DAT` is checked structurally (length, listing offsets);
  byte `0x2f` and directory-record names are not read; counts and listing names
  go straight into the table.
- **FACT:** without `DRSTR001.DAT` the layer builds the table from the file
  system. The table differs from the `DRSTR` one (digest), so the ids differ.
- **FACT:** file ids are positions in `DRSTR001.DAT`. A rebuilt file with
  another order mounts and yields another id assignment.
- **FACT:** the byte swap M3.11b looked for is in the completion routine
  `0x00417eac`, selected by request word +20.
- **FACT:** a `.cmp`/`.ind` pair produced by `cmpind_writer.py recompress` is
  read by the firmware's own decoder and gives the same payload: the first
  full-path rule-13 pass for row 6.
- **HYPOTHESIS:** map clients address files by fixed ids (as `0x00030001`), so a
  `DRSTR` with another order would make clients open the wrong files. Not
  tested: no client was run. Until tested, writers keep the reference order.
- **HYPOTHESIS:** `.ind` +4 is used as the end of the last chunk and is not
  compared with the `.cmp` size.
- **UNKNOWN:** what the unit does after "not mounted" (states `0/1`, `1/1`):
  the retry timer and recognition status 1 are recorded, their effect on the
  screen is not.

## Conclusion

The hypothesis holds on the EU 2011 card: all 285 files of the firmware's table read back equal to the host's view (8,874,828 bytes compared, 194 of the files through the firmware's `.cmp`/`.ind` decoder). The factory card is
accepted, 10 of 13 boot changes alter the verdict, the error log or the table,
and the 3 that do not are bytes the firmware never reads (`0x2f`, a record
name) or does not check at mount (`MMAIN` content).

Difference from the task text: the task asked for `runner.py run mmain_reader
--card-root`. The result is a separate tool, because the unit of work turned
out to be the whole layer (state machine and queue), not one function with a
stubbed wrapper; `mmain_reader` and `drstr_parser` run inside `boot` with the
arguments the firmware itself passes. The wrappers were not stubbed either: the
imports behind them are modelled, so the wrappers' own error handling runs.

## Reproduction

The commands under Method, with the two images in `archive/` (git-ignored).
`boot` 9 s, a compressed 64 KiB read about 4 s, the full sweep about 20 min.

## Follow-ups

- M3.11b: answered for the file layer (word +20); what remains is which client
  passes 0 for `POINT`.
- M3.25 / M3.28: run a client (`0x0040b850` chain) up to `OSM_TaskSend`, decode
  its request with the table in `firmware.md`, serve it with `Session.request`,
  deliver the completion; the read log is the tile reader's view of the format.
- M5.6 / M5.15: add `vcard_l3.py boot` + `sweep` as the gate for a generated
  card tree before any image is built.
- US2011: addresses through `fn_match`, then the same tests on the US card.
- M9.45: a native-speed engine would bring the sweep under a minute.
