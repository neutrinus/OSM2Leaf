## Question

Does every `IMAGE_SCN_COMPRESSED` `o32` section begin with the 22-byte header
hypothesised in TODO M1.2a, and do its length/flag invariants hold?

## Hypothesis

The two section starts recorded in EXP-2026-11-05-49 differ by exactly 22 bytes
between the declared total and the declared payload (`0x2c6 − 0x2b0` and
`0x68c − 0x676`), so the stored bytes are:

| Offset | Type | Meaning |
| --- | --- | --- |
| +0 | `u24` LE | uncompressed length |
| +3 | `u24` LE | compressed total (= `o32_psize`) |
| +6 | `u32` LE | flags, expected `0x10` |
| +10 | `u32` LE | uncompressed length |
| +14 | `u32` LE | payload length (= `psize − 22`) |
| +18 | `u32` LE | uncompressed length |
| +22 | bytes | payload |

Invariants: `compressed_total == psize`, `payload_len == psize − 22`, the three
length words agree, `flags == 0x10`, and `uncompressed_len <= vsize`.

`comphdr MODULE` selects one module (case-insensitive, every segment);
`comphdr --all` walks every compressed section. Exit code 0 when every parsed
section `HOLDS`, 1 when any is `REFUTED`/`UNPARSED`, 2 on a usage/I/O error.

## Interpretation

- **FACT:** on both recorded starts, the six little-endian fields parse to the
  values above and all five invariants hold; the payload offset is 22.
- **FACT:** the parser does not accept arbitrary streams: a one-byte change to
  the flags word refutes, and the synthetic LZSS/LZX streams do not hold.
- **OBSERVED:** the two cases exercise both length shapes found in EXP-49:
  section 1 has `uncompressed_len` (`0x484`) **below** `vsize` (`0x5b8`),
  section 2 has it **equal** to `vsize` (`0xcc0`).
- **HYPOTHESIS:** the repeated `u32` length is a per-block record field carried
  at three header positions; the parser only requires that the three agree, so
  the reading does not depend on which one the kernel uses.
- **OBSERVED:** `compressed_total` is the stored `psize`, so the 22-byte header
  is inside `psize`, not additional to it.
- **UNKNOWN:** whether all 245 compressed sections follow this layout. Only the
  two acceptance vectors are measured, both from `NaviMapCC.dll`.

## Conclusion

`tools/cerom.py` gained `comphdr MODULE|--all [--json]` with a synthetic
self-test built from the two recorded prefixes. C-640 records the layout and the
two field vectors; C-641 records the `HOLDS`/`REFUTED`/`UNPARSED` semantics and
the negative controls. No format doc changes: the layout is stated only for the
two measured sections and is not yet general.

Exceptions measured: **0 of 2** recorded vectors (both `HOLDS`).
Exceptions still needing the image: **the 245 compressed sections minus the 2
measured = 243 unmeasured**; the exception count among them is UNKNOWN. The
project-wide `--all` run must report `counts.sections == 245`,
`counts.exceptions == <number>`.
