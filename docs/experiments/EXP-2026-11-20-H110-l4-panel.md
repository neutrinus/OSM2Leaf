## Question

Can the L4 full-system emulator readiness that `prompt_qa.txt` asks the matrix
to show ("what can run, what is blocked") be a committed panel with one row per
stage (`F0`…`F4`), each naming its gate, evidence claim and blocker task, and a
`NOT RUN` status whenever no run log is supplied — instead of the four prose
lines in TODO's critical path plus the M8.A2 block?

## Hypothesis

Two facets must stay apart, and a naive panel conflates them:

1. **Status is execution.** It can come only from a run log; with no log it is
   `NOT RUN` for every stage (test-system.md §4: `NOT RUN` is never `PASS`).
2. **Blocked is readiness.** It comes from the board (which M8/M9 task must
   land), independent of any run.

If the panel scores status from a log and readiness from committed task IDs,
then "`NOT RUN` for every F-row without a log" and "`F4 BLOCKED (M8.A3, M8.A6,
M9.16)`" are both true at once. **Falsifier:** if a boot-log key could move a
stage past what the key measures (e.g. a clean `exceptions: 0` promoting F1's
"filesys/device started"), the panel would assert a pass it cannot see. A
second falsifier: if a row printed a number without naming a claim, it would
violate the "every number names its claim" rule.

## Method

### 1. Sample and hash

No vendor bytes are read by `tools/l4_status.py`; the run-summary fixture below
is synthetic. The EU2011 head is named only because a *real* `--run-log` would
be one. `sha256sum archive/head256.img` on this host still prints
`92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9`.

### 2. Commands

```bash
# the panel, no run log: every F-row status NOT RUN, F4 BLOCKED (readiness)
python3 tools/l4_status.py ; echo "exit=$?"

# a clean C-4311-style summary moves only F0 to PASS
printf 'unmodelled register accesses (first-seen order): 1\n  write 0x00000038\nexceptions: 0\nfinal pc: 0x8802ec44\n' \
  > /tmp/l4-clean.log
python3 tools/l4_status.py --run-log /tmp/l4-clean.log

# a faulting boot is an honest FAIL for F0 and F1
printf 'exceptions: 3\nfinal pc: 0x00005bd0\n' > /tmp/l4-bad.log
python3 tools/l4_status.py --run-log /tmp/l4-bad.log

# a log without the run.sh keys is NOT RUN, never inferred
printf 'workdir: /tmp/x\nlog: /tmp/x/qemu.log\n' > /tmp/l4-nokeys.log
python3 tools/l4_status.py --run-log /tmp/l4-nokeys.log

# JSON + the standing checks
python3 tools/l4_status.py --json -
python3 tools/l4_status.py --selftest
python3 tools/selftest.py --only l4_status
python3 tools/claims_check.py ; python3 tools/todo_check.py
```

### 3. Controls

- **Positive (reader contract):** `--selftest` round-trips a synthetic
  `run.sh` summary (`exceptions: 0`, one `write 0x38`, `final pc`), so the
  "log row" `PASS` is a measured property, not an assertion.
- **Negative (no key):** a log with no `exceptions:`/accesses/`final pc` lines
  leaves every F-row `NOT RUN` — a missing key is *not* the base `PASS`.
- **Negative (fault):** `exceptions: 3` gives `F0 FAIL` (and `F1 FAIL`), so the
  panel can fail, not only pass.
- **Boundary (no promotion):** a clean kernel boot log leaves F1–F4 `NOT RUN`;
  F4 is never moved by any boot log (it needs an M8.E4 `Navi.exe` run).

### 4. Scope

Covered: the six-row panel (F0–F4 + the run-summary reader row), the
`run.sh` key parser, the four reachable statuses and the readiness legend, all
synthetic. Excluded: an actual QEMU build or boot (C-4310/C-4311 own those;
this task adds no QEMU to CI and runs none), F1–F4 evidence beyond the claims
they cite, and any `Navi.exe` run (M8.E4). No new metric is defined: the panel
prints claim IDs and run-log keys, nothing recomputed.

### 5. Falsifier

A clean `exceptions: 0` log promoting F1 (or any F-row past what its key
measures), or any row printing a number without a claim, refutes the design.
Stated before the result.

## Interpretation

- **FACT:** the panel prints `F4 BLOCKED (M8.A3, M8.A6, M9.16)` with no log and
  exits 0 (C-4412); every F-row status is `NOT RUN` without a log (C-4412,
  C-4417).
- **FACT:** a clean `exceptions: 0` summary moves only F0 to `PASS`; a non-zero
  count is a `FAIL` for F0/F1 (C-4413); `final pc` is never scored (C-4411).
- **FACT:** the reader row's `PASS` rests on `--selftest`'s synthetic round-trip
  (C-4411, C-4417).
- **OBSERVED:** `C-1352` (F1 milestone) already exists on the board, yet F1
  stays `NOT RUN` without a log — the panel does not treat a done task's EXP as
  a run of its own (the honest reading).
- **HYPOTHESIS:** when M8.C lands and an SD-mounting run log exists, F3/F2 will
  still need keys `run.sh` does not print today; that extension is a future
  `run.sh` change, recorded as a follow-up, not invented here.
- **UNKNOWN:** none for the panel's own behaviour; the stage *contents* stay
  C-537's `HYPOTHESIS`.

## Conclusion

`docs/research/test-system.md` gains §L4 (`F0`–`F4` + log row, each naming a
gate, an evidence claim and a blocker task), and `tools/l4_status.py` prints
that panel from a `run.sh` summary (best-effort, `--json`, `--selftest`). The
L4 delta is now a row: a QA pass runs one command instead of re-reading EXP/TODO.
The panel asserts no stage passes; F4 is blocked by `M8.A3, M8.A6, M9.16` with
M9.16 the open link. Claims C-4410–C-4418; C-4419 reserved. Nothing in
`docs/format/` changes.
