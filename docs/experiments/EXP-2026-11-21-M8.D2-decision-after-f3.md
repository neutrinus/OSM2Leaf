## Question

Is TODO **M8.D2** ("after F3, go to F4?") due today, and if the trigger were
reached, does the record support a recommendation to enter F4 while keeping F5
out of scope?

## Hypothesis

M8.D2's own Precheck defines the trigger: `tools/l4_status.py --run-log RUN.log`
must print `F3    PASS` for a boot log of the F3 run. No such log is in the
repository, the archive or the role logs, and the only SD-host record says F3
is not reached, so the honest state is **the gate is not due**
(`Status: blocked`, the trigger task is the unblocker) and the F4/F5 text is a
recommendation, not a decision.

**Falsifier:** an `F3    PASS` line in any boot log in the repo/archive (then
the gate *is* due and this record is wrong), or a `l4_status.py` panel that
promotes F3 from a log key (then the precheck would not discriminate), or an

### 3. Controls

- **Positive — what a due gate looks like:** the panel promotes a stage from a
  log key when the key is present. A synthetic clean log
  (`exceptions: 0`, one unmodelled access, a `final pc`) moves **F0** to
  `PASS` in the same table where F3 stays `NOT RUN`
  (`python3 tools/l4_status.py --run-log "$L"` with
  `printf 'unmodelled register accesses (first-seen order): 1\n  write 0x00000038\nexceptions: 0\nfinal pc: 0x8802ec44\n' > "$L"`).
  That proves the reader can emit `PASS` and that the precheck is capable of
  firing; `tools/l4_status.py --selftest` pins the same behaviour
  (`clean log (exceptions 0): F0 PASS from run-log`).
- **Negative — today's state:** with no log every F-row is `NOT RUN`
  (`run log: none`), exactly the "trigger is not reached" case; a log without
  the summary keys is also `NOT RUN` (`log without run.sh keys parses to
  all-None`), so a non-F3 log cannot be mistaken for a pass.
- **Negative — the board's witness:** `EXP-2026-11-20-M8.C10-sd-host` states
  `F3 (the FAT partition mounted) is **not** reached`, so no F3 log can exist
  from the SD-host work that landed on 2026-11-20.

## Interpretation

- **FACT:** M8.D2's Precheck does not fire: with no F3 log every F-row is
  `NOT RUN`, and `F3    PASS` appears in no file under `docs/experiments`,
  `archive` or `dev_process` (0 hits).
- **FACT:** F3 cannot have been reached by the merged work: the SD-host EXP
  records the FAT mount as not reached and names the HPB DMAC (row M8.C1) as
  the next blocker.
- **FACT:** in this `l4_status.py` revision F1–F4 are never scored from a log
  key, so the literal `F3    PASS` of the task text is currently
  unreachable even with a real F3 boot; the task's gate would need either the
  tool's F3 evidence or a recorded FAT-mount observation.
- **OBSERVED:** the F4 inputs (M8.C4 micon/power, M8.C5 CAN, M8.C18 display)
  and the F5 input (M8.C19 graphics engine) have no per-row task on the board;
  the M8.C umbrella is open and only C10 is done.
- **HYPOTHESIS (untested):** if F3 lands, F4's scriptability hinges on a finite
  boot handshake from `PowerMonitor`/`ActivateCtlDriver` and a finite set of
  frames `CAN.dll` waits for — unknown today, so a recommendation for F4 can
  only be conditional.
- **UNKNOWN:** whether F4 is ever worth its 1–3 months while L3 already answers
  the per-function format questions it would answer in context.

## Conclusion

The gate is **not due**: the trigger (an F3 FAT mount with a boot log) is not
reached, and no log in the repo, `archive/` or `dev_process/` gives
`F3    PASS`. The task is recorded `blocked`, with the F3-producing work (the
M8.C row chain, next blocker M8.C1 HPB DMAC) as the unblocker and Marek's
answer as the alternative. The recommendation written into the block is:
enter F4 only after F3 **and** only if M8.C4/C5 collapse to a finite, scripted
handshake (and M8.C18 display init does not fail); F5 stays out of scope
because the plan of record says "Do not plan for F5" and M8.C19 (the only
possible frame-buffer path) is unstarted. `docs/research/claims.md` gains
C-1595–C-1599 (no `RESERVED` rows remain in that block); no format doc, tool
or code changes.
