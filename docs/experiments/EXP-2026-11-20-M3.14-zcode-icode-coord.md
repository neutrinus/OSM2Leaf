## Question

With M3.23's candidate-reader lists (call-graph reachability) and M9.38's
read-watch tracer, which build-A `Navi.exe` functions read the record bytes of
`ZCODE0nn`, `ICODE001` and `COORD001`, and which record fields does each one
consume (M3.14 done-when)?

## Hypothesis

A family's reader lies in the subtree of its access path and reads the decoded
file buffer in memory. Running the M3.23 candidates, and the C-4694 loaders,
under the M9.38 read watch on a buffer seeded with the real decoded file bytes
identifies the reader: a hit is content-bound (a different file changes which
fields are touched) and survives a zero-buffer control.

**Falsifier:**
- (a) A probe hit is **content-independent**: the same function, offsets and
  widths occur on a buffer of a completely different file, and on an all-zero
  buffer of the same length (a struct/context touch, not a file read).
- (b) The COORD001 file **id** literal (`0x00060022`, C-4666-era lookup) is
  loaded by no plain-code literal pool (a second signature family fails, the
  rule-14 `Stop:`).
- (c) The mount run reads no ZCODE/COORD row (they are not on the mount path).

3. **Controls.**
   - *Positive (content-bound reader):* the mount run must attribute ICODE001
     load reads to real functions, and those functions must touch different
     offsets in different ICODE001 regions (they are keyed by the file bytes).
   - *Negative (probe artifacts):* a probe hit that also occurs on a zero
     buffer of the same length is not a file read. Compared per-hit.
   - *Positive (method):* the same probe method must return a content-bound
     reader somewhere (the mount run is that reference here).
   - *Negative (id literal):* the COORD001 id `0x00060022` must be found if the
     id-literal family is a real signature; it is the family's own test.

4. **Scope.** EU2011 `Navi.exe` only (23 MB of executable bytes, 0 compressed

   dynamic reads only within the mount run and the seeded-buffer probe. US2011

5. **Falsifier.** Stated above; the three cases (a), (b), (c) fire in the

## Interpretation

- **FACT:** The M3.23 rank list is reproducible (C-3544 control) but every
  candidate the probe credits reads a **struct at the buffer address**, not the
  decoded file: the same offsets and widths occur on a zero buffer and on four
  different files (falsifier a).
- **FACT:** The file-id literal family finds no pool load for any file id,
  including the COORD001 id `0x00060022` (C-4677/C-4666) — a second signature
  family fails (falsifier b).
- **FACT:** On the card, the mount run reads `ICODE001`/`ICADM001` and credits
  real readers (`0x003f07f8`, `0x003f0c7c`, `0x003f1bb0`, `0x003f0400`,
  `0x003f2bc4`, leaf `0x0040a8d0`), and those readers touch the refer-header
  slots 4 `(512,60)` and 13 `(2308,1)`. No ZCODE or COORD row appears, even at
  a position inside ZCODE018's region (falsifier c).
- **OBSERVED (ICODE001, content-bound):** `0x003f0400` consumes the slot-4
  header `addr=512/blk=60` at `+0x818..+0x81d`; `0x0040a8d0` and `0x003f2bc4`
  consume slot 4 and slot 13 `blk` at `+0x84e..+0x853`; `0x003f07f8` walks the
  area-name records (2-byte `mov.w @r3` / `+4` / `+10` with `& 0x7fff`,
  `cmp/hi #6`, `cmp/eq #-1`) at the per-language root; `0x003f0c7c` reads the
  country chain (2-byte at `+0x90` onward); `0x003f255c` reads `+0x2/+0x4`.
- **OBSERVED (ZCODE):** the opener `0x003fbed8` resolves the file (type
  11/12); the record/trie walker is not reached by the mount run and not
  separable by the probe.
- **HYPOTHESIS:** the ZCODE trie walk and the COORD001 bbox table are read on a
  search/route path (search types 11/12 and the coordinate lookup) that the
  mount-state machine does not exercise; M3.29 (split the shared REFER list per
  family at run time) and the read issuer `0x003fc518` are the next lever.
- **UNKNOWN:** the ZCODE record walker VA; any COORD001 reader; whether
  COORD001 is read by `Navi.exe` at all (no name, no id literal, C-4677).

## Conclusion

Done-when not met. `coord-zcode-icode.md` gains an ICODE001 field-to-reader map
with VAs (`0x003f0400`, leaf `0x0040a8d0`, `0x003f2bc4`, `0x003f07f8`,
`0x003f0c7c`, `0x003f255c`, `0x003f1bb0`), and for ZCODE0nn and COORD001 only
the opener (`0x003fbed8`) and the negative (no reader located). Both rule-14
signature families failed in EU2011 `Navi.exe` (call-graph candidate probe with
a zero-buffer control; file-id literal scan), so M3.14 is `Status: blocked`.
`Unblock: M3.29` (split the shared list per family at run time) — confirmed by
a search-path run, not the mount path. Claims C-2190–C-2199 update.
