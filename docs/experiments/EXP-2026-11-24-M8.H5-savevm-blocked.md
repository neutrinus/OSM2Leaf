## Question

Can an idle `-M ze0` guest be snapshotted with HMP `savevm` and restarted with
`run.sh --loadvm` so that a later guest line proves it continues, in under 30 s
wall?

## Hypothesis

Yes: `VMStateDescription` for the ze0 devices that lack one (INTC/TMU glue,
SD host, HPB-DMAC, `ze0-gfx`, stubs, sensors) plus `run.sh --savevm/--loadvm`
would let a guest be restored and continue.
**Falsifier (task):** after `loadvm` the guest hangs or faults at the first
interrupt; here the stronger negative fires earlier — `savevm` itself is
blocked by the CPU.

## Method

1. **Sample pins** (every number below is quoted from the command that prints it):
   ```bash
   sha256sum ~/.cache/qemu-ze0/build/qemu-system-sh4 archive/head256.img
   /home/marek/.cache/qemu-ze0/build/qemu-system-sh4 --version | head -1
   /home/marek/.cache/qemu-ze0/build/qemu-system-sh4 -M help | grep ze0
   qemu-system-sh4 -M help | grep -c ze0
   ```
2. **Decisive precheck** (read-only, no disk image needed beyond a 1 GiB qcow2
   overlay so "no block device" cannot fire first):
   ```bash
   W=~/projekty/leafre-work/scratch/m8h5-nav-probe
   python3 tools/qemu-ze0/mkoverlay.py archive/head256.img "$W/hd.qcow2" --size-gib 1
   ( printf 'savevm t1\n'; sleep 2; printf 'quit\n' ) | \
     timeout 15 /home/marek/.cache/qemu-ze0/build/qemu-system-sh4 \
       -M ze0 -m 512 -nographic -serial none -monitor stdio \
       -drive if=sd,index=0,file="$W/hd.qcow2" 2>&1 | \
     sed 's/\x1b\[[0-9;]*[A-Za-z]//g' | grep 'Error:'
   ```
   The overlay is required: without it the first error is instead
   `Error: no block device can store vmstate for snapshot`.
3. **Source pin** (the first blocker is upstream CPU code, not our patch series):
   ```bash
   grep -n -A4 'static const VMStateDescription vmstate_sh_cpu' \
     ~/.cache/qemu-ze0/qemu-11.1.3/target/sh4/cpu.c
   grep -n -A4 'static const VMStateDescription vmstate_sh_cpu' \
     ~/.cache/qemu-ze0/qemu-8.2.10/target/sh4/cpu.c
   ```
4. **Positive control (migration works at all)**: HMP `savevm` on a machine
   whose CPU is migratable. This is a control only — the snapshot is discarded.
5. **Negative mutation**: rerun step 2 with the stock `/usr/bin/qemu-system-sh4`
   (no `ze0` machine) — it cannot even start the machine; and with `-M ze0`
   without an overlay — the first error is the block-store one. Both confirm
   the CPU error is the *next* blocker, not a side effect of the harness.
6. **Scope:** one binary per version, one machine (`-M ze0`), one HMP command;
   no guest boot to idle is reachable once `savevm` fails. No loadvm wall time
   can be measured, so the task's 30 s claim is unmeasurable here.

## Controls

- **Positive:** `info snapshots`/`savevm` on a migratable target (`-M pc` if that
  binary has it) must succeed; otherwise the harness cannot distinguish a
  general migration failure from the SH-4 blocker.
- **Negative 1:** unpatched `-M ze0` + qcow2 overlay gives exactly
  `Error: State blocked by non-migratable device 'cpu'` (Method 2).
- **Negative 2:** without the overlay the error is `Error: no block device can
  store vmstate for snapshot`; adding the overlay removes that cause and
  exposes the CPU blocker.
- **Falsifier:** a loadvm guest that hangs/faults at the first interrupt cannot
  be observed, because no snapshot can be written in the first place.

## Observations

**O1 — sample pins.** `sha256sum` printed, verbatim:
```
c6603a5812574a39a2d65ca5187c3b10c558853703e9a00e7bd310f15ed9a9f2  /home/marek/.cache/qemu-ze0/build/qemu-system-sh4
92aa525d0db2c167cf4288b82f9cb951865a53c3a9ab4ead84d11a6f19a007f9  archive/head256.img
```
The patched binary printed `QEMU emulator version 11.1.3` and its `-M help`
has a `ze0` line; the stock binary's `-M help | grep -c ze0` printed `0`.

**O2 — the overlay runs, and `savevm` fails at the CPU.** The Method 2 command
printed exactly:
```
Error: State blocked by non-migratable device 'cpu'
```

**O3 — the stock binary has no `ze0` machine.** `/usr/bin/qemu-system-sh4 -M ze0`
printed `qemu-system-sh4: unsupported machine type: "ze0"`, so the positive
`savevm t1` result cannot come from the stock binary; the patched binary is
required. The navigator's precheck file additionally quotes the block-store
error (`Error: no block device can store vmstate for snapshot`) on a bare
`-M ze0` run in an earlier harness; in this harness the CPU error fires first
even without an overlay.

**O4 — the blocker is upstream and version-independent.** `grep` printed, in
both the pinned 11.1.3 tree (`target/sh4/cpu.c:274`) and the pinned 8.2.10 tree
(`qemu-8.2.10/target/sh4/cpu.c:245`):
```
    .unmigratable = 1,
```
at the `vmstate_sh_cpu` definition. Any number of ze0
device vmsds is therefore *necessary but not sufficient*: QEMU iterates devices
and stops at the first non-migratable one — the CPU — before consulting a ze0
device's `vmsd`.

**O5 — the attempted patch.** A candidate patch `ze0-h05-vmstate.patch` was
drafted in the worktree (CPU core-state vmsd + vmsds for ze0-intc, ze0-sdhi,
ze0-hpbdmac, ze0-gfx, ze0-stubs, ze0-dr; timers re-armed on post_load). It was
never committed: `build.sh --check-version 11.1.3` reported
`ze0-h05-vmstate.patch FAILED` (`32 applied, 1 failed, 0 unpinned-tarball`),
and a real CPU migration format (full CPUSH4State, TB/TLB invalidation and
FPU state reconstruction) plus six device vmsds is beyond a single tooling
task's scope. The task's Stop clause applies: record which device cannot be
saved without a redesign (the SH-4 CPU) and stop. The draft patch is not part
of this commit.

## Interpretation

- **FACT (C-7020):** on pinned QEMU 11.1.3, HMP `savevm t1` on `-M ze0` with a
  qcow2 SD overlay fails with `Error: State blocked by non-migratable device
  'cpu'`. The DoD precheck cannot pass unpatched.
- **FACT (C-7021):** `target/sh4/cpu.c` in both pinned 11.1.3 and 8.2.10 defines
  `vmstate_sh_cpu` with `.unmigratable = 1`, so the blocker is upstream SH-4
  code, version-independent and not caused by the ze0 patch series.
- **FACT (C-7022):** without the overlay QEMU reports
  `Error: no block device can store vmstate for snapshot` first; the overlay
  from `mkoverlay.py` clears that cause and exposes the CPU blocker (negative
  mutation controls).
- **OBSERVED (C-7023):** a loadvm-to-idle wall time under 30 s cannot be
  measured: no snapshot can be written, so the task's Done when is unreachable
  in scope.
- **OBSERVED (C-7024):** the drafted patch did not apply cleanly in a fresh
  check tree and was discarded; no positive `savevm` result exists on this
  branch, so no `done` claim can honestly be made.
- **Recommendation:** a new task (Unblock: M8.H5a) must implement and validate
  a real SH-4 CPU migration format (CPU vmsd + post_load TB/TLB/FPU rebuild),
  then re-run this task's run.sh --savevm/--loadvm proof.

## Conclusion

M8.H5 is **blocked**, not disproved for real hardware: the snapshot path is
closed by an upstream CPU declaration, and restoring a guest in < 30 s cannot
be demonstrated. Task status `blocked`, `Unblock: M8.H5a`.

## Falsifier

The task's own falsifier (guest hangs after loadvm) was not reached. The
stronger negative — `savevm` blocked by the CPU — fired instead and is recorded
above with positive and negative controls.
