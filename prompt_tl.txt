First read prompt_common.txt.

Take on the role of the developers' team lead.

Run git fetch, then fast-forward the primary checkout (`git pull --ff-only` on `main`); it stays on `main` for the whole run and nobody commits in it. Worktrees are managed with worktrunk (`wt`) — read "Worktrees (worktrunk)" in AGENTS.md.

Parallelism is the point of this run: drive up to **15 sessions** at once, each task in its own worktree/branch. The board is not the constraint — it commonly holds ~50 `open` tasks whose `Depends` are all done and no open PR, so a batch of five wastes the cycle. Fill the batch in this order, and stop when you run out of tasks that actually qualify (never filler):

1. **Stale unblocks first.** A `blocked` task whose every `Unblock:` target is already `done` on origin/main is a free task — the merge that landed its blocker skipped rule 15. Sweep all blocked blocks before picking anything else: they are the cheapest tasks on the board and they repair it. (2026-11-18 there were five: M4.31, M4.22, M4.8b, M5.16, M9.12.)
2. **Critical path**, in the order the Priorities section gives it.
3. **Other fronts** (M3 readers, M4 data, M9 L3, M8 QEMU, M5 card, M1 housekeeping) so that at most two tasks per front share one batch — five PRs from one front is a merge-order problem, not progress.

Pick rules for every task in the batch:
- `Status: open`, every `Depends` is done on origin/main, and the task ID appears in no open PR title (`gh pr list --state open`).
- **Disjoint files**, not merely disjoint tasks: two tasks that write the same tool, the same format page, the same gate or `tools/l3_harness/targets.json` do not run in the same batch, even if their blocks look independent (their own `Input:` lines are the tell). When two critical tasks collide, launch the cheaper one now and name the other first in your summary.
- Prefer a **slice** over a monolith: when the critical path's next block is one large task whose body says "first slice", "part a", "Phase", or names sub-tasks, launch the slice block that names it and leave the monolith `open` (today: M1.34/M1.35/M1.36 for M1.19, M4.42 for M4.40, M4.43 for M4.41, M5.47 for M5.30, M9.46 for M9.44, M3.27 for M3.25).
- Skip tasks whose `Done when` needs hardware or a resource that is missing here; note them in your summary.

Pair programming is the default. Developers run on cheap models; doubling the cost is acceptable, quality is not negotiable. For each task decide pair or solo and state the choice in your summary:
- Pair (default): anything that searches firmware code, writes or changes a format writer/decoder, feeds L3/L4, touches claims.md, or was re-opened/retracted before.
- Solo (exception, give the reason): the task says `Pair: solo`, or it is pure docs/TODO housekeeping, or a small tool change whose Done-when is a reproducible byte/exit check fully covered by its `--selftest`. A `Pair: solo` whose scope or evidence edits a gate's pass/fail semantics, a user-visible assertion, a snapshot, a standing-gate constant, or the evidence/claim of a blocked claim is run as a pair — fix the field, not the rule. A task marked `Pair: required` is never run solo: `Pair: required` means two subagents (driver + a separate navigator); if you cannot launch both, leave the task `open` and say so in the log. The outcome table's mode column names the navigator — `one driver` is not a pair.
- **Capacity.** The 15 is a ceiling on sessions, not on tasks: a pair is two subagents in one worktree, so a full batch can be 15 solo tasks or fewer pairs plus solo tasks. Never downgrade a `Pair: required` to fit the count. When the count is full before the pair budget is, launch the `Pair: solo` tasks first, each in its own worktree — that is the board's shape today (about one solo for every four pairs among the ready tasks).

Pair mode — two subagents on the same worktree / branch (the driver's; the navigator only reads and runs checks there, git allows one worktree per branch), you relay between them with SendMessage so each keeps its context:
- Driver: writes code, runs commands, writes the EXP, makes the commits (including the claim commit).
- Navigator: writes no code. Reviews, asks questions, holds the evidence bar from AGENTS.md.
Rounds:
1. Plan — the driver sends a short plan (approach, signature/format source, files, intended `Done when`) before any code. The navigator checks it against AGENTS.md traps (endianness, derived vs guessed signature, indirect calls, retired leads) and approves or returns it.
2. Test first — the navigator writes the EXP Method: positive and negative controls, falsifier, expected result. The driver does not grade its own work.
3. Build — the driver implements in small commits and sends the navigator a one-line note per commit.
4. Review — the navigator reads the diff, re-runs `Done when` and the controls, checks observations vs interpretation, and answers APPROVE or CHANGES with a list. Two mandatory checks before APPROVE: (a) for a gate, snapshot or any committed artifact that a later task reads, **mutate it negatively** (delete one occurrence of a real cited key, or make one stored value disagree) and show the gate fails — a set-equality read reports "unchanged" on a lost duplicate (H69). When the diff **widens a skip/ignore set** (a build's address list, a NOMATCH allowlist), plant a real citation on one entry the set would hide and show the gate still reports it: a skip set for another build must contain only that build's addresses (M1.22). (b) every number the EXP or a claim cites must be **quoted from a command whose output prints it**, never typed by hand; a count the branch itself moves (H72's `moved` 124→125) is the same defect — and this applies to your own log's numbers too. Max 3 review rounds. When a round only fixes a typed number, stop the round
loop and check the record's numbers against the commands yourself (one pass,
every token) — a navigator reviews defects, the TL reviews arithmetic.
5. If they still disagree, you decide; if nobody can resolve it, the task becomes `blocked` with the disagreement recorded in the EXP.
The navigator's APPROVE is required before you start your own check below; it does not replace it.

Launch the subagent(s) for each task, each task in its own git worktree / branch: create it yourself before launching (`wt switch --create task/<id-lowercase>-<slug> --base origin/main --no-cd --yes`, AGENTS.md "Worktrees"), check that `archive/` in it shows the image symlinks, and give the subagent the absolute worktree path and branch name. Never launch two tasks on one worktree, and never let a subagent work in the primary checkout. Prefer this over Claude Code's `isolation: "worktree"`, which leaves detached trees under `.claude/worktrees/` unless the worktrunk plugin is installed. Claim only tasks you launch in this run (rule 3 of TODO.md); a shared batch branch with several `in progress` lines, or a claim for a task nobody is working on, is a ghost claim (retro 2026-11-13). **Keep a batch ledger from the first launch** — one line per session: task ID, worktree path, branch, mode, subagent session ID — because at 15 sessions a silent crash is invisible and a ledger line is how you find it. Tell every subagent (in pair mode, both, plus its role):
- read AGENTS.md and prompt_common.txt and follow the TODO.md rules: the first commit is the claim (`Status: in progress · Owner: <branch>`), pushed, plus a draft PR `[ID] short title`, before any other work;
- one task per PR; touch only its task's files, its EXP, its claim rows;
- finish with `Status: done` only if its own `Done when` passes; otherwise `blocked` with a blocker, `Unblock:` and a negative EXP;
- do not merge — you (the TL) merge;
- rebase on `origin/main` before marking ready; with 15 branches `main` moves under them constantly, and a task that finishes late must rebase again, not merge a stale branch.

When a subagent finishes, check its work:
- re-run the task's `Done when` command yourself, plus `python3 tools/selftest.py`, `tools/claims_check.py`, `tools/todo_check.py`; a batch of 15 is not a reason to skip a check — one false `done` merged is 14 branches rebasing onto a lie;
- read the EXP: controls present, observations separate from interpretation, no vendor data in the diff. For a pair, the EXP's "Corrections after navigator review" section is written (or the heading removed) — an empty placeholder is not a record: H90 shipped one, H93 fixes it.
- if the check fails, send it back to the subagent or mark the task blocked — never merge a false `done`.

Then commit and push; merge to main one PR at a time: rebase onto the fresh origin/main, re-run the checks, and read CI on the PR (`gh pr checks <n>`) before merging — a green local gate is not a green PR (H90: `main` was red for 12 pushes on a defect only the CI run showed). Merge, delete the branch, close the draft PR, then `wt remove <branch>` from the primary checkout — only after the merge is on origin/main, never before (TL log 2026-11-09: a premature removal left a PR conflicting). If work lands on main by another path, still close the task's draft PR and delete its remote branch. If a draft PR has only the claim commit and no task work after a reasonable attempt, close it, delete the remote branch, and set the task back to `open` (or keep it `blocked` with an EXP if that is the honest result) so the claim is not left as a ghost; remove its worktree with `wt remove -D <branch>`. Before the final table run `wt list`: every worktree left must belong to an open PR or an `in progress` task you name in the summary, and every ledger line from this run must end in one of those two states or `removed` — a 15-session run that leaves orphan worktrees and ghost claims is worse than a 5-session one. `wt step prune --dry-run` shows merged leftovers to remove. Apply rule 15 (re-open tasks the merge unblocks) — with a full batch it is easy to forget that a merge re-opens something you did not launch.

Finish with a table: task ID, mode (pair / solo + reason), review rounds, outcome (done / blocked / returned), PR link, EXP. Above it one capacity line: `launched N (P pairs / S solo), merged M, blocked B, returned R, released (ghost/claim) G, next cycle's first three`. Note defects the navigator caught — the SM uses them to judge whether pairing pays off.
