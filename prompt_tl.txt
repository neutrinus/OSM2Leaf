First read prompt_common.txt.

Take on the role of the developers' team lead.

Run git fetch, then fast-forward the primary checkout (`git pull --ff-only` on `main`); it stays on `main` for the whole run and nobody commits in it. Worktrees are managed with worktrunk (`wt`) — read "Worktrees (worktrunk)" in AGENTS.md.

First clear the queue: merge or return every open PR that is not a draft (`gh pr list --state open --draft=false`), critical-path IDs first, before you launch anything. A finished PR that waits collects one conflict per merge on `main` (retro 2026-11-20-2: six ready PRs, 21–35 merges behind).

Pick up to 30 tasks from TODO — as many as actually qualify, never filler. This is the batch size of every run; if fewer than 30 tasks qualify, launch fewer and say why in the log — never pad the batch with a task that fails a filter below:
- `Status: open`, every `Depends` is done on origin/main, and the task ID appears in no open PR title (`gh pr list --state open`).
- Prefer tasks on the critical path in the Priorities section.
- The tasks must touch disjoint files (apart from their own TODO line and their own claim block); two tasks writing the same tool or format doc do not run in the same batch.
- Skip tasks whose `Done when` needs hardware or a resource that is missing here; note them in your summary.

Pair programming is the default — quality is not negotiable, and at 30 tasks the second subagent is exactly what stops solo drift from shipping. Subagents run on cheap models; doubling the cost is acceptable. For each task decide pair or solo and state the choice in your summary:
- Pair (default, driver + a separate navigator = 2 subagents): every task except the documented solo exception below. This includes anything that searches firmware code, writes or changes a format writer/decoder, feeds L3/L4, touches claims.md, edits a standing gate's pass/fail semantics, a user-visible assertion, a snapshot or a standing-gate constant, edits the evidence/claim of a blocked claim, was re-opened/retracted before, or carries `Pair: required`. A `Pair: required` task is never solo: if you cannot launch both subagents, leave it `open` and say so in the log. Fix the field, not the rule.
- Solo (exception, give the reason): only a task marked `Pair: solo`, or pure docs/TODO housekeeping, or a small tool change whose `Done when` is a reproducible byte/exit check fully covered by `--selftest` — and only if none of the high-risk conditions above apply. A `Pair: solo` whose scope or evidence edits a gate, assertion, snapshot or a blocked claim's evidence is still run as a pair.
- Count subagents, not just tasks: a batch of T tasks with S solo exceptions launches 2T − S subagents. The outcome table's mode column names the navigator — `one driver` is not a pair. Never collapse a pair to one agent to fit a limit; leave that task `open` instead.

Pair mode — two subagents on the same worktree / branch (the driver's; the navigator only reads and runs checks there, git allows one worktree per branch), you relay between them with SendMessage so each keeps its context:
- Driver: writes code, runs commands, writes the EXP, makes the commits (including the claim commit).
- Navigator: writes no code. Reviews, asks questions, holds the evidence bar from AGENTS.md.
Rounds:
1. Plan — the driver sends a short plan (approach, signature/format source, files, intended `Done when`) before any code. The navigator checks it against AGENTS.md traps (endianness, derived vs guessed signature, indirect calls, retired leads) and approves or returns it.
2. Test first — the navigator writes the EXP Method: positive and negative controls, falsifier, expected result. The driver does not grade its own work.
3. Build — the driver implements in small commits and sends the navigator a one-line note per commit.
4. Review — the navigator reads the diff, re-runs `Done when` and the controls, checks observations vs interpretation, and answers APPROVE or CHANGES with a list. Two mandatory checks before APPROVE: (a) for a gate, snapshot or any committed artifact that a later task reads, **mutate it negatively** (delete one occurrence of a real cited key, or make one stored value disagree) and show the gate fails — a set-equality read reports "unchanged" on a lost duplicate (H69). When the diff **widens a skip/ignore set** (a build's address list, a NOMATCH allowlist), plant a real citation on one entry the set would hide and show the gate still reports it: a skip set for another build must contain only that build's addresses (M1.22). (b) every number the EXP or a claim cites must be **quoted from a command whose output prints it**, never typed by hand; a count the branch itself moves (H72's `moved` 124→125) is the same defect — and this applies to your own log's numbers too. Max 3 review rounds. When a round only fixes a typed number, stop the round
loop and check the record's numbers against the commands yourself (one pass,
every token) — a navigator reviews defects, the TL reviews arithmetic.
5. If they still disagree, you decide; if nobody can resolve it, the task becomes `blocked` with the disagreement recorded in the EXP.
The navigator's APPROVE is required before you start your own check below; it does not replace it.

Launch all subagents for all tasks **in parallel** — one wave of background/async subagent calls, not one task at a time. Create every worktree first, verify the `archive/` symlinks in each, then start all drivers (and navigators for paired tasks) before you wait for any result: a serial launch of a 30-task batch is not a 30-task batch. Keep a manifest in your TL log (task ID → worktree, branch, subagent IDs, mode) so you can route messages to the right agent as results arrive. Each task gets its own git worktree / branch: create it yourself before launching (`wt switch --create task/<id-lowercase>-<slug> --base origin/main --no-cd --yes`, AGENTS.md "Worktrees"), check that `archive/` in it shows the image symlinks, and give the subagent the absolute worktree path and branch name. Never launch two tasks on one worktree, and never let a subagent work in the primary checkout. Prefer this over Claude Code's `isolation: "worktree"`, which leaves detached trees under `.claude/worktrees/` unless the worktrunk plugin is installed. A 30-task batch in pairs is ~60 subagents; if the host cannot sustain that many worktrees/agents, launch as many tasks as it can, stagger the rest in waves and record the cap in the log — never drop a pair or a check to fit a number. Claim only tasks you launch in this run (rule 3 of TODO.md); a shared batch branch with several `in progress` lines, or a claim for a task nobody is working on, is a ghost claim (retro 2026-11-13). Tell every subagent (in pair mode, both, plus its role):
- read AGENTS.md and prompt_common.txt and follow the TODO.md rules: the first commit is the claim (`Status: in progress · Owner: <branch>`), pushed, plus a draft PR `[ID] short title`, before any other work;
- one task per PR; touch only its task's files, its EXP, its claim rows;
- edit TODO.md and claims.md only with `tools/board.py` (claim, done, block, add-claims; `resolve` on a conflict) and check `board.py lost --base origin/main` before pushing;
- finish with `Status: done` only if its own `Done when` passes; otherwise `blocked` with a blocker, `Unblock:` and a negative EXP;
- delete the task's `scratch/<task>/` before finishing (once the EXP captures its numbers) — a task is not done while its cards, trees, QEMU dirs and logs still hold disk; keep only bytes another open task or a reproducible EXP command reads;
- keep generated cards, extracted trees, QEMU work dirs and logs in `~/projekty/leafre-work/scratch/<task>/`, never in `/tmp` (a 3.8 GiB tmpfs; with ~60 agents it fills much faster) — use short TMPDIR paths for Unix-socket tools; before deleting any path there, confirm no process holds it and no `docs/`/`TODO.md` reference names it; replace factory-identical images with a verified symlink to `archive/sd-images/` rather than removing the path;
- with ~30 agents pushing claim commits at once, re-read the task line on `origin/main` and `gh pr list --state open --search "[ID]"` immediately before `board.py claim`, and run `board.py lost --base origin/main` before every push; if two PRs claim one ID, the lower PR number wins and the other agent stops;
- do not merge — you (the TL) merge.

As results arrive, merge finished PRs in a steady serial stream — do not wait until all 30 tasks are done before starting the merge queue; a ready PR that waits collects one conflict per merge on `main` (retro 2026-11-20-2). Merge one PR at a time, but begin the next as soon as the previous is on `origin/main`.

When a subagent finishes, check its work — for a solo task you are the only reviewer, so do not rubber-stamp it:
- re-run the task's `Done when` command yourself, plus `python3 tools/selftest.py`, `tools/claims_check.py`, `tools/todo_check.py`; apply the two mandatory checks of pair round 4 yourself (negative-mutate any gate/snapshot/committed artifact the task touched and show it fails; show every number in the EXP/PR is quoted from a command that prints it);
- read the EXP: controls present, observations separate from interpretation, no vendor data in the diff. For a pair, the EXP's "Corrections after navigator review" section is written (or the heading removed) — an empty placeholder is not a record: H90 shipped one, H93 fixes it.
- check `~/projekty/leafre-work/scratch/<task>/` is gone (or name in your log exactly which bytes you kept and which open task / EXP command still reads them); a finished task must not leave a multi-GB scratch tree. If it was removed, confirm `df -h /` has headroom before starting the next merge wave.
If the check fails, send it back to the subagent or mark the task blocked — never merge a false `done`.

Then commit and push; merge to main one PR at a time: rebase onto the fresh origin/main, re-run the checks, and read CI on the PR (`gh pr checks <n>`) before merging — a green local gate is not a green PR (H90: `main` was red for 12 pushes on a defect only the CI run showed). `gh pr ready <n>` **before** merging — GraphQL refuses to merge a draft (`Pull Request is still a draft`, cycle 15) even when the branch is fine. Merge, delete the branch, close the draft PR, then `wt remove <branch>` from the primary checkout — only after the merge is on origin/main, never before (TL log 2026-11-09: a premature removal left a PR conflicting). If the squash is already on main but the PR still reports a conflict or a draft (main moved after the branch was rebased), do **not** re-push: close the PR with a comment naming the squash SHA and `wt remove -D <branch>` — the content is on main and a second merge would duplicate it (cycle 15: M3.27, M5.48). If work lands on main by another path, still close the task's draft PR and delete its remote branch. If a draft PR has only the claim commit and no task work after a reasonable attempt, close it, delete the remote branch, and set the task back to `open` (or keep it `blocked` with an EXP if that is the honest result) so the claim is not left as a ghost; remove its worktree with `wt remove -D <branch>`. Before the final table run `wt list`: every worktree left must belong to an open PR or an `in progress` task you name in the summary; `wt step prune --dry-run` shows merged leftovers to remove. Also run `du -sh ~/projekty/leafre-work/scratch/*/ | sort -hr` and `df -h /`: any multi-GB scratch directory that is not an `in progress` task is unclaimed garbage — delete it only after the `lsof`/reference check in prompt_common.txt, and record the reclaimed space in the log. Apply rule 15 (re-open tasks the merge unblocks).

Finish with a table: task ID, mode (pair / solo + reason), subagent(s) launched, review rounds, outcome (done / blocked / returned), PR link, EXP. State the task count and the total subagent count (2T − S, with S = solo exceptions) next to the table. Note defects the navigator caught — the SM uses them to judge whether pairing pays off.
