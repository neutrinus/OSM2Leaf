Shared preamble for every role prompt (PO, QA, SE, SM, TL). Read this first.

Goal: OSM-derived navigation maps that a Nissan Leaf ZE0 (2011–2012) reads and
displays. Everything else serves this goal.

Before you start:
- Read AGENTS.md and the "How to take a task" rules at the top of TODO.md
  (rules 1–16, ID allocation, task fields). They override anything here.
- Run `git fetch` and work from an up-to-date `origin/main`.

Hard rules:
- All repo content (code, docs, TODO, commits, retros) is English, even if the
  conversation is Polish.
- Hardware access is currently unavailable. Do not plan L4 work as near-term;
  prepare it so it is cheap when hardware returns.
- Never commit vendor data (images, .DAT, .cmp, .ind, …) — see AGENTS.md.
- Never force-push `main`. Never edit a task another agent has
  `in progress`, except to note a dependency in your own task.
- When your task's commits are on `origin/main` (done or blocked), close its
  draft PR and delete the remote branch. Do not open a second PR for the same
  task ID; update the existing draft or coordinate through the TL.

Verification levels (details: docs/research/feedback-loop.md):
- L1 structural: `tools/cardcheck.py` — card/FAT/files/sizes/indexes consistent.
- L2 semantic/golden: `tools/l2check.py` — decode → model → compare with OSM
  or golden; round-trips byte-identical.
- L3 firmware function emulation: `tools/l3check.py` — real firmware reader
  functions run against our data (exit 3 = nothing runnable, never a pass).
- L4 bench/car: the real unit boots our card. Expensive, one variable per run.
Prefer the cheapest level that can falsify the hypothesis. SKIP is never PASS.

Editing TODO.md concurrently (~15 agents write to it):
- Keep edits small and local; do not reflow or reorder unrelated sections.
- New task IDs and claim blocks follow "ID allocation" in TODO.md.
- Every new task has: Depends, Input, Done when (a command that can fail),
  and a falsifier. A task without a runnable Done when is not ready.
- Optional `Pair:` field. Developer tasks run as a driver/navigator pair by
  default (see prompt_tl.txt); write `Pair: solo` only for low-risk work
  (docs, housekeeping, selftest-covered small tools) and `Pair: required`
  for high-risk work (firmware searches, format writers, L3/L4 inputs).
  Omitted = TL decides, default pair.
- Before pushing: `git fetch && git rebase origin/main`, resolve conflicts by
  keeping both sides' content, then run
  `python3 tools/todo_check.py` and `python3 tools/claims_check.py`.
- Commit style per AGENTS.md (`docs:`, `tools:`, `chore:` …, imperative,
  why in the body).

Role order when run as a cycle: SM → SE → PO → QA → TL. Each role reads the
latest output of the previous one (retro, new tasks, its dev_process/ log)
instead of re-deriving it.

Work log (every run of every role prompt, no exceptions — also when the run
finds nothing to do or fails):
- File: `dev_process/YYYY-MM-DD-HHMM-N-<role>.log`, UTC start time, `N` =
  1 + number of logs already in dev_process/ for that date (so names never
  collide), `<role>` = po | qa | se | sm | tl. Example:
  `dev_process/2026-11-09-1430-3-tl.log`.
- Create it when you start (header lines), append as you go, finish it
  before your last commit. Plain English text, aim for under ~80 lines:
    role, model, start/end time (UTC), origin/main SHA at start
    inputs read (retro, previous logs, PRs) — names only
    actions taken, in order, each with its reason (one line each)
    task IDs added / changed / moved / blocked / re-opened; PRs; commits
    decisions made and alternatives rejected (one line each)
    problems, dead ends, anything that cost time
    handoff: what the next role should look at first
  TL also lists each task's mode (pair/solo), subagents launched and their
  outcome. Never paste command output, diffs or vendor bytes — reference
  files, SHAs and task IDs instead.
- Commit the log in your final commit (or a `chore: <role> work log` commit)
  and push it; a run that changed nothing still commits its log.
- Read only the logs since your own previous run, never the whole folder.

Finish with a short summary for the user: what you changed, which task IDs
you added/moved/blocked, and anything that needs a human decision, plus the
path of your work log.
