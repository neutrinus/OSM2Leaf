Shared preamble for every role prompt (PO, QA, SE, SM, TL). Read this first.

Goal: OSM-derived navigation maps that a Nissan Leaf ZE0 (2011–2012) reads and
displays. Everything else serves this goal.

Before you start:
- Read AGENTS.md and the "How to take a task" rules at the top of TODO.md
  (rules 1–17, ID allocation, task fields). They override anything here.
- Run `git fetch` and work from an up-to-date `origin/main`.

Hard rules:
- All repo content (code, docs, TODO, commits, retros) is English, even if the
  conversation is Polish.
- Hardware access is currently unavailable. Do not plan L5 (car/bench) work as
  near-term; prepare it so it is cheap when hardware returns. L4 (QEMU
  full-system emulator, M8) is the software substitute where feasible.
- Never commit vendor data (images, .DAT, .cmp, .ind, …) — see AGENTS.md.
- **Keep large scratch off `/tmp`.** It is a 3.8 GiB tmpfs (RAM) here and has
  filled twice: generated card images, extracted trees, QEMU work dirs and
  probe outputs belong in `~/projekty/leafre-work/scratch/<task>/`, deleted
  when the task's EXP is written. Use `/tmp` only for small, short-lived files
  the same command removes (e.g. `tempfile.TemporaryDirectory` in a selftest).
  Never point a tool's work dir, card output or log at `/tmp` for a long run.
- **Clean up `scratch/<task>/` before you mark the task done or blocked.** A
  task is not finished while its generated cards, extracted trees, QEMU work
  dirs and logs still consume disk (2026-11-24: stale scratch held 122 GB and
  the root filesystem reached 100 % with 76 MB free). Delete the whole
  directory once the EXP records the result, so every number the EXP quotes is
  captured before the bytes go away. Keep only what another open task or a
  reproducible EXP command still reads.
- **Before deleting anything under `~/projekty/leafre-work/`**, check that no
  process has it open (`lsof +D` / `ps`) and that no `docs/` or `TODO.md`
  reference names it; an EXP command or a claim's sample path must keep
  resolving. If the file is byte-identical to a factory image in
  `archive/sd-images/`, replace it with a symlink to the original instead of
  deleting the path — verify with `sha256sum` first. Large QEMU `-d` logs are
  usually only *described* in an EXP (size quoted), not read by it: those can
  go. Never `rm` a path a live task or claim cites.
- Never force-push `main`. Never edit a task another agent has
  `in progress`, except to note a dependency in your own task.
- When your task's commits are on `origin/main` (done or blocked), close its
  draft PR and delete the remote branch. Delete the remote branch only after
  the PR is merged (or already `ready`); deleting a branch under an open draft
  auto-closes the PR as a draft — recover it from `refs/pull/<n>/head`, never
  re-push. Do not open a second PR for the same task ID; update the existing
  draft or coordinate through the TL.
- One task = one owner branch + one draft PR. Never set several tasks
  `in progress` under one shared batch branch: a claim with no PR and no work
  log is invisible and unreviewable (retro 2026-11-13).

Verification levels (details: docs/research/feedback-loop.md; mapping note there — **before 2026-11-09 L4=car/bench, L5=full-system emulator; after 2026-11-09 L4=full-system emulator, L5=car/bench**):
- L1 structural: `tools/cardcheck.py` — card/FAT/files/sizes/indexes consistent.
- L2 semantic/golden: `tools/l2check.py` — decode → model → compare with OSM
  or golden; round-trips byte-identical.
- L3 firmware fragments: `tools/l3check.py` — original firmware code fragments
  (decoder/decompressor/reader), run via Ghidra/harness on our data (exit 3 =
  nothing runnable, never a pass).
- L4 full-system emulator: original software runs in an emulator (QEMU `ze0`,
  M8). Catches integration/file-open/error-screen paths the model can see.
- L5 bench/car: the real unit boots our card (M6). Expensive, one variable per
  run. Hardware currently unavailable.
Prefer the cheapest level that can falsify the hypothesis. SKIP is never PASS.

Editing TODO.md concurrently (a normal cycle has ~15 agents, a 30-task TL batch ~60 in pairs):
- Change task blocks and claim rows only with `python3 tools/board.py`
  (claim, done, block, field, add-task, add-claims, claim-status, archive;
  AGENTS.md has the command list). Never rewrite, regenerate or paste back a
  whole TODO.md or claims.md: PR #340 lost 42 tasks and 199 claim rows that
  way. The tool refuses any write that drops an ID.
- Keep edits small and local; do not reflow or reorder unrelated sections.
- New task IDs and claim blocks follow "ID allocation" in TODO.md. Before
  allocating, check open PR titles and their claim blocks too (`gh pr list
  --state open`): `next-id`/`next-claims` only see `main`, so an ID held by an
  open PR is invisible to them. Never take a block whose owner has not merged
  or released it.
- Every new task has: Depends, Input, Done when (a command that can fail),
  and a falsifier. A task without a runnable Done when is not ready.
- Any command in a `Done when`, `Precheck` or evidence cell selects its rows by
  a stable key — a claim ID, a task ID, or a property that survives row
  insertion — never by a line number or offset (H71's `sed -n '2802,2807p'`,
  H80's Precheck). If a later edit moves what the command selects, the record
  says at which revision it was measured.
- Optional `Pair:` field. Developer tasks run as a driver/navigator pair by
  default (see prompt_tl.txt), including in a 30-task batch; the TL pairs
  everything except the documented solo exception. Write `Pair: required`
  for high-risk work (firmware searches, format writers, L3/L4/L5 inputs,
  and **any task that adds or edits a standing gate, a user-visible
  assertion, a snapshot, or the evidence/claim of a blocked claim**) — never
  solo. Write `Pair: solo` only for low-risk work (docs, housekeeping,
  selftest-covered small tools) and only if none of the high-risk conditions
  apply. Omitted = TL decides, default pair.
- Every number in a task, an EXP record or a claim row must be **quoted from a
  command whose output prints it** — never typed by hand, and never copied from
  an earlier record. If the branch itself moves the number (a `moved` count, a
  line offset, a selftest size), cite the command and the stable part
  (`0 new / 0 gone`), or say at which revision the number was measured.
- For any recompression or byte-identical claim, record the interpreter that
  produced the bytes with `python3 tools/zlibinfo.py` (or `--stamp`); a
  `--stamp` WARNING means the runtime is not stock zlib 1.3.1 and the claim is
  `UNVERIFIABLE` on that host unless rerun with stock zlib 1.3.1.
- Before pushing: `git fetch && git rebase origin/main`, resolve conflicts by
  keeping both sides' content (`python3 tools/board.py resolve TODO.md`, same
  for `docs/research/claims.md`), then run `python3 tools/board.py lost --base
  origin/main` (exit 0, or only the IDs you archived), `python3
  tools/todo_check.py` and `python3 tools/claims_check.py`.
- Commit style per AGENTS.md (`docs:`, `tools:`, `chore:` …, imperative,
  why in the body).

Role order when run as a cycle: SM → SE → PO → QA → TL. Each role reads the
latest output of the previous one (retro, new tasks, its dev_process/ log)
instead of re-deriving it.

Work log (every run of every role prompt, no exceptions — also when the run
finds nothing to do or fails):
- File: `dev_process/YYYY-MM-DD-HHMM-N-<role>.log`, UTC start time, `N` =
  1 + number of logs already in dev_process/ for that date (so names never
  collide), `<role>` = po | qa | se | sm | tl. Example:
  `dev_process/2026-11-09-1430-3-tl.log`. Check with
  `ls dev_process/YYYY-MM-DD-* | sed 's/.*-\([0-9]*\)-[a-z]*\.log/\1/' | sort -n`
  — the free `N` is `max+1`, not a count (subagent logs such as `-driver`
  already reuse small numbers; do not add to that collision).
- Create it when you start (header lines), append as you go, finish it
  before your last commit. Plain English text, aim for under ~80 lines:
    role, model, start/end time (UTC), origin/main SHA at start
    inputs read (retro, previous logs, PRs) — names only
    actions taken, in order, each with its reason (one line each)
    task IDs added / changed / moved / blocked / re-opened; PRs; commits
    decisions made and alternatives rejected (one line each)
    problems, dead ends, anything that cost time
    handoff: what the next role should look at first
  TL also lists each task's mode (pair/solo), subagents launched (≈ 2T − S for
  a T-task batch with S solo exceptions) and their outcome. Never paste command output, diffs or
  vendor bytes — reference files, SHAs and task IDs instead.
- Commit the log in your final commit (or a `chore: <role> work log` commit)
  and push it; a run that changed nothing still commits its log.
- A developer (driver or navigator) writes no log of its own: its record is
  the EXP (with "Corrections after navigator review") and the PR body. A
  batch of tasks run from a chat thread is a TL run: commit its `-tl.log`
  with the first merge and append to it, so the table exists while the batch
  runs (retro 2026-11-20-2).
- Read only the logs since your own previous run, never the whole folder.

Finish with a short summary for the user: what you changed, which task IDs
you added/moved/blocked, and anything that needs a human decision, plus the
path of your work log.
